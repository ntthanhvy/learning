Making a custom validation rule run in the browser too

Lesson 133 named its own out-of-scope next step: a custom ValidationAttribute only ever runs on the server, after a full round trip, even though the rule it encodes (classic movies need an early release year) could just as easily be checked the moment the user types. This lesson is that next step — the interface a custom attribute implements to also run client-side, and the simpler escape hatch for when the rule can't run client-side at all.

1 · The rule still only runs on the server, until it says otherwise

Lesson 133's ClassicMovieAttribute works end to end, but only on the server: submit the form, wait for the response, then see the error. Built-in attributes like [Required] and [Range] don't make the user wait — the browser flags the problem before the request is even sent. That gap exists because [Required] and [Range] do one extra thing ClassicMovieAttribute doesn't yet do: implement a second interface, IClientModelValidator, alongside ValidationAttribute itself.

2 · The one method: AddValidation

IClientModelValidator has exactly one method: public void AddValidation(ClientModelValidationContext context). It doesn't check anything — it writes data-val-* HTML attributes onto the rendered form element, which a client-side library reads later to do the actual checking in the browser.

public class ClassicMovieAttribute : ValidationAttribute, IClientModelValidator
{
    public ClassicMovieAttribute(int year) => Year = year;

    public int Year { get; }

    public void AddValidation(ClientModelValidationContext context)
    {
        MergeAttribute(context.Attributes, "data-val", "true");
        MergeAttribute(context.Attributes, "data-val-classicmovie", FormatErrorMessage(""));
        MergeAttribute(context.Attributes, "data-val-classicmovie-year",
            Year.ToString(CultureInfo.InvariantCulture));
    }

    protected override ValidationResult? IsValid(
        object? value, ValidationContext validationContext)
    {
        // unchanged from Lesson 133 -- server-side logic still lives here
    }
}

Two interfaces, two jobs, on the same class: ValidationAttribute.IsValid still does the real check on the server; IClientModelValidator.AddValidation only ever emits markup. Nothing about adding the second interface changes or replaces the first.

3 · Who actually renders those attributes, and who reads them

Razor's own Tag Helpers and HTML helpers are what call AddValidation while building a form, folding each attribute's data-val-* output straight into the rendered <input> tag:

<input type="date"
    data-val="true"
    data-val-classicmovie="Classic movies must have a release year no later than 1960."
    data-val-classicmovie-year="1960"
    data-val-required="The Release Date field is required."
    id="Movie_ReleaseDate" name="Movie.ReleaseDate" value="">

That markup alone does nothing — it's inert data until something reads it. Two separate jQuery libraries split that job: jQuery Validation is the generic engine that runs named rules against form fields, and jQuery Unobtrusive Validation is the adapter that scans a page for data-val-* attributes and feeds them to jQuery Validation as rules — in Microsoft's own words, "effectively ‘copying’ the server-side validation logic to the client." Neither library knows anything about ClassicMovieAttribute by name; they only ever see the data-val-classicmovie/data-val-classicmovie-year attribute pair AddValidation happened to emit, plus whatever client-side JavaScript rule was separately registered under the matching "classicmovie" adapter name to interpret them.

Frontend-habit trap: this looks like a Zod schema shared between a Next.js server action and a client-side form hook — one schema, both sides free, because both sides run the same JavaScript. The gap that doesn't carry over: IsValid is C#, and a browser cannot run C#. AddValidation doesn't export the C# logic to the browser — it emits a few data attributes, and a separate, hand-written JavaScript adapter (registered with jQuery Validation under a matching rule name) has to re-implement the same comparison in JavaScript for those attributes to mean anything. Nothing here shares one check across both languages the way Zod does.

4 · When re-implementing the rule in JavaScript isn't worth it: [Remote]

Writing a parallel JavaScript adapter is only worth it for logic simple enough to duplicate safely, like comparing a year to a constant. A rule that needs a database lookup — checking an email address is unique — can't be re-implemented client-side at all, short of shipping the whole user table to the browser. For that case ASP.NET Core ships a narrower, purpose-built attribute: [Remote]. Instead of emitting a comparison for a JavaScript library to run locally, the Microsoft Learn docs describe it as implementing "client-side validation that requires calling a method on the server to determine whether field input is valid" — the browser still makes an asynchronous round trip, but it fires automatically on blur, not only on submit, so the result shows up before the user moves through the rest of the form.

[Remote(action: "VerifyEmail", controller: "Users")]
public string Email { get; set; }

[Remote] and a custom IClientModelValidator implementation solve opposite shapes of the same problem: one skips writing JavaScript entirely by calling the server again; the other skips calling the server again by duplicating simple logic in JavaScript. The docs frame the choice directly: a client-side validator is worth writing when the rule "doesn't do any server-side validation and doesn't need any services from DI" — anything needing DI or a database lookup is [Remote]'s job, not a hand-written adapter's.

Scope line

This lesson covers the IClientModelValidator interface, its one method AddValidation(ClientModelValidationContext context), the data-val-* attribute contract between Razor's renderer and jQuery Unobtrusive Validation/jQuery Validation, and [Remote] as the alternative for server-dependent rules. It does not cover writing the matching JavaScript adapter itself (the $.validator.addMethod/$.validator.unobtrusive.adapters.add calls that give data-val-classicmovie an actual browser-side check), nor any non-jQuery client validation approach — both reasonable next steps, not today's.
