CSP's real job: locking down scripts, not just frames

Lesson 99 used exactly one Content-Security-Policy directive — frame-ancestors — to close the clickjacking gap, and explicitly scoped out the rest of CSP as "a deeper XSS-mitigation topic in its own right." That's today: the directive CSP was actually built for first, script-src, plus the two mechanisms that make it usable on a real site without breaking everything — nonces and violation reporting.

1 · The threat CSP's script-src actually targets

Lesson 17 covered SQL injection: untrusted input reaching a query as code instead of data. The browser has its own version of that same mistake. If a handler ever writes user-supplied text into an HTML page without escaping it — a comment, a display name, a search query echoed back — and that text contains <script>...</script>, the browser just runs it, with the full privileges of your page: it can read cookies, submit forms as the logged-in user, call your API with their session. This is XSS (cross-site scripting), and escaping output correctly is the primary defense — but escaping is a discipline every template call site has to get right, every time, forever. CSP's script-src is the backstop for when that discipline slips once: it tells the browser which sources are allowed to supply JavaScript at all, so even a successfully injected <script> tag simply never executes.

Content-Security-Policy: script-src 'self' https://cdn.example.com

This line says: only run JavaScript that comes from this page's own origin, or from cdn.example.com. An attacker's injected <script>alert(document.cookie)</script> is inline — it isn't loaded from either allowed source — so the browser refuses to execute it and logs a console error instead. The injection still happened; it just can't do anything.

2 · The problem: your own inline scripts just broke too

A bare script-src 'self' blocks every inline <script> tag and every inline onclick="..." handler — including the legitimate ones your own templates render, like a small analytics snippet or a per-page config object. Allowing all inline scripts back with 'unsafe-inline' defeats the entire point: that reopens the door to the exact injected-script case Section 1 just closed, since an attacker's inline script would be "allowed" too. The fix is letting the server mark its own inline scripts as trusted without trusting inline scripts in general. A nonce does exactly that:

Content-Security-Policy: script-src 'self' 'nonce-r4nd0mBase64'
...
<script nonce="r4nd0mBase64">
  window.APP_CONFIG = { userId: 42 };
</script>

The server generates a fresh random value on every single response, puts it in the header, and stamps the same value onto the one inline <script> tag it actually wrote. The browser executes that tag because its nonce attribute matches the header. An attacker's injected script has no way to know that value in advance — it's regenerated per response — so it still gets blocked exactly as before. The nonce must never be reused across responses; a nonce that's predictable or repeated defeats the whole mechanism, same as a session ID that never rotates.

Frontend-habit trap: a nonce looks like a client-side concern because it shows up as an HTML attribute in the rendered page. It isn't generated or chosen client-side at all — the server picks a fresh random value per request and has to inject it in exactly two places in the same response: the Content-Security-Policy header, and every inline script tag it renders. A frontend build step has no way to participate, since it doesn't run per-request.

3 · Finding out when the policy blocks something — without breaking production first

Shipping a strict script-src cold, on a real site, risks silently breaking some legitimate script you forgot about — a third-party widget, an old inline handler nobody remembers writing. CSP has a built-in way to find out before that happens: a report-only mode that logs violations without blocking anything yet.

Content-Security-Policy-Report-Only: script-src 'self'; report-to csp-endpoint
Reporting-Endpoints: csp-endpoint="https://example.com/csp-reports"

With the -Report-Only header instead of the enforcing one, nothing gets blocked — every script still runs — but the browser POSTs a CSP violation report to the named endpoint for every script that would have been blocked. The rollout path this enables: deploy report-only first, watch the reports for a few days, fix or allowlist every legitimate source the reports surface, then switch to the enforcing Content-Security-Policy header once the report volume is quiet. In enforcing mode, the same reporting mechanism keeps working — now as an early-warning signal that an actual injection attempt is being blocked in production, worth alerting on the same way Lesson 13 treats any other anomaly in logs.

4 · Setting it from Go

A nonce has to be fresh per request, which Lesson 99's static header value didn't need — the middleware now has to generate one and make it available to the template that renders the inline script:

// cspWithNonce generates a fresh per-request nonce, sets it in the CSP
// header, and stores it on the request context so the handler/template
// rendering the one trusted inline script can stamp the same value onto it.
func cspWithNonce(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        buf := make([]byte, 16)
        if _, err := rand.Read(buf); err != nil {
            http.Error(w, "internal error", http.StatusInternalServerError)
            return
        }
        nonce := base64.StdEncoding.EncodeToString(buf)

        policy := "script-src 'self' 'nonce-" + nonce + "'"
        w.Header().Set("Content-Security-Policy", policy)

        ctx := context.WithValue(r.Context(), nonceCtxKey, nonce)
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}

Using crypto/rand (not math/rand) matters here the same way it matters for Lesson 48's password hashing and Lesson 30's webhook secrets: a nonce an attacker could predict from a weak generator is no defense at all. The handler then reads nonce back off the context to stamp it onto the one inline <script> tag the template actually renders — the same value, generated once, used in exactly the two places Section 2 named.

Q: "Your team wants to tighten CSP's script-src. What's the rollout, and why not just ship it enforcing on day one?" A strong answer, out loud: "Ship it first as Content-Security-Policy-Report-Only with a reporting endpoint — nothing gets blocked yet, but the browser tells us about every script that would have been. We watch those reports for however long it takes to see the volume settle, fix or explicitly allowlist every legitimate source that shows up — third-party widgets, old inline handlers — and only then switch to the enforcing header. Shipping it enforcing cold risks silently breaking something in production the first time a real user hits the blocked code path, with no warning beforehand." The signal: treating report-only as a required rollout step, not an optional nicety — the same instinct as a canary release (Lesson 89) for a change that can break things in ways tests won't catch.

Scope line

This lesson covers script-src, nonces, and violation reporting — the three pieces needed to actually ship a script-blocking CSP safely. It doesn't cover CSP's other directives (style-src, img-src, connect-src, and a dozen more follow the same shape once script-src makes sense), hash-based allowlisting as a nonce alternative for static assets, or CSP's interaction with service workers — all extensions of today's same mental model rather than new concepts.
