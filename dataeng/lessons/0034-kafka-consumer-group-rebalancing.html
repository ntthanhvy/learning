1 · The question every one-consumer run has dodged since Day 5

Day 5 named the consumer group and said Kafka "assigns each partition to exactly one consumer within a group at a time." That sentence has never been tested, because every run since — Day 5's inspector, Day 6's warehouse loader, Day 16's retry demo, Day 18's lag demo — started exactly one consumer process per group. With one consumer, "assigns each partition to exactly one consumer" is trivially true: that one process gets all three partitions of order_events, there is nobody else to assign anything to. The interesting mechanics — what happens when a second consumer joins the same group, or the first one dies — have stayed pure vocabulary. Today runs two.

2 · What a rebalance actually is

When a new consumer joins a group (or an existing one leaves, by graceful shutdown or by timing out), Kafka's group coordinator — one broker, elected per group — triggers a rebalance: every partition the group owns gets reassigned among whichever consumers are members right now, including ones that just joined and excluding ones just judged dead. "Judged dead" is not instant — a consumer that stops sending heartbeats is only dropped after session.timeout.ms (10 seconds, confluent-kafka's default) passes with no heartbeat, which is why a kill-and-rejoin below takes a few seconds to settle rather than reassigning the instant a process dies.

Two things matter about a rebalance that the one-consumer runs so far could never show: first, exactly one consumer owns a given partition at any moment within a group — never two at once, which is exactly what makes "each partition's committed offset means one thing" still true with multiple consumers; second, a partition's committed offset is what lets the new owner pick up from where the old owner left off, the same mechanism Day 6's crash-and-restart test already proved, just now handing a partition to a different process instead of a restarted one. Nothing about ON CONFLICT (event_id) DO NOTHING changes — the idempotent write from Day 6 absorbs a redelivered message during a rebalance exactly like it absorbed one after a crash.

3 · Build: run two consumers, same group, and watch the split

Produce a fresh batch first so there is real traffic to divide, then start two instances of Day 6's unmodified consumer in the background, both reading GROUP_ID = "warehouse-loader":

uv run --with confluent-kafka python3 scripts/produce_order_events.py

uv run --with confluent-kafka --with "psycopg[binary]" python3 scripts/consume_order_events.py &
CONSUMER_A=$!
uv run --with confluent-kafka --with "psycopg[binary]" python3 scripts/consume_order_events.py &
CONSUMER_B=$!
sleep 3

With both running, describe the group. This is the moment the one-consumer runs never showed — two distinct CONSUMER-ID values, each owning a disjoint subset of the 3 partitions:

docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group warehouse-loader

Expected shape — partition ownership split across the two active members, every CONSUMER-ID distinct, and no partition appearing under two different consumers at once:

GROUP             TOPIC         PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG  CONSUMER-ID                        HOST       CLIENT-ID
warehouse-loader  order_events  0          8               8               0    rdkafka-3f1a...-1                 /172.18.0.1  rdkafka-3f1a...
warehouse-loader  order_events  1          4               4               0    rdkafka-9c2e...-1                 /172.18.0.1  rdkafka-9c2e...
warehouse-loader  order_events  2          4               4               0    rdkafka-3f1a...-1                 /172.18.0.1  rdkafka-3f1a...

Read it as: partitions 0 and 2 landed on one consumer instance, partition 1 on the other — a 2-and-1 split across 3 partitions and 2 consumers, the only split 3 partitions can make across 2 owners. Which exact partitions go to which process is not something you choose; the default RangeAssignor/cooperative-sticky assignment strategy decides it, and it can differ between runs. What must hold regardless: every partition has exactly one owner, both consumers' rows sum to all 3 partitions, and total lag across the group is 0 once both have caught up.

4 · Build: kill one, watch the rebalance happen live

Now remove a member the way Day 6 already removed one — a hard kill, no graceful shutdown — and watch the coordinator hand its partition(s) to the survivor:

kill -9 $CONSUMER_B
sleep 12   # past session.timeout.ms (10s default) so the coordinator judges it dead
uv run --with confluent-kafka python3 scripts/produce_order_events.py   # fresh traffic so the survivor has something to prove it owns every partition now
sleep 3
docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group warehouse-loader

Expected — all 3 partitions now under the single surviving CONSUMER-ID, lag back to 0 once it catches up on the fresh batch:

GROUP             TOPIC         PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG  CONSUMER-ID         HOST         CLIENT-ID
warehouse-loader  order_events  0          12              12              0    rdkafka-3f1a...-1   /172.18.0.1  rdkafka-3f1a...
warehouse-loader  order_events  1          8               8               0    rdkafka-3f1a...-1   /172.18.0.1  rdkafka-3f1a...
warehouse-loader  order_events  2          8               8               0    rdkafka-3f1a...-1   /172.18.0.1  rdkafka-3f1a...

Partition 1 — the one the killed consumer owned — now shows the surviving consumer's CONSUMER-ID, not the dead one's. That reassignment is the rebalance: nobody restarted anything, nobody re-pointed a config, Kafka's coordinator simply noticed the missed heartbeats and handed the orphaned partition to whichever member was still alive, resuming from that partition's last committed offset exactly the way Day 6's single-process restart resumed from its own.

Confirm no duplicates snuck in across the whole exercise. Two consumers briefly owning different partitions of the same group, then one dying mid-stream, is exactly the kind of multi-actor chaos an idempotent write exists for: 
docker compose exec -T postgres psql -U fdp -d fdp -c \
  "SELECT count(*) AS total, count(DISTINCT event_id) AS distinct_events FROM raw.order_events;"
Expected: total equal to distinct_events, same equality Day 6 proved after a single-process crash — this is the same guarantee, now shown holding across two cooperating processes instead of one restarted one.

Clean up the survivor so nothing keeps running after today's lesson:

kill -9 $CONSUMER_A

5 · Why this matters beyond the demo

This is the mechanism that makes a consumer group a real scaling lever, not just a label. Day 28's own glossary entry already named "partition count as a parallelism ceiling" — a topic with 3 partitions can never have more than 3 consumers in one group doing useful work at once, because a 4th consumer joining would get zero partitions assigned and sit idle. Today is the other half of that fact: scaling from one consumer to two (up to the partition count) is exactly the rebalance just watched, nothing more exotic — add a process with the same group.id, the coordinator reassigns automatically, the written code never has to ask "which partition am I on now?" because confluent-kafka's own consumer loop hands it whatever it's currently assigned. The same mechanism is also why losing a consumer is self-healing rather than an outage: a crashed instance's partitions migrate to whoever is left, bounded only by how long session.timeout.ms takes to notice.

Q: "What happens inside Kafka when you add a second consumer to an existing consumer group?" A strong answer, out loud: "The group's coordinator — one broker elected per group — detects the new member joining and triggers a rebalance: every partition the group owns gets reassigned across the consumers now in the group, with the rule that exactly one consumer owns any given partition at a time. Consumption briefly pauses for the affected partitions while this gets agreed, then each consumer resumes reading only what it was assigned, picking up from that partition's last committed offset — the same resume-from-commit mechanism a single restarted consumer uses, just handing ownership to a different process instead of the same one restarting. The ceiling is the partition count: a topic with 3 partitions can only usefully support 3 consumers in one group, a 4th would sit idle with nothing assigned. And because a redelivered message during the handoff is possible, same as any Kafka redelivery, the consumer's write still needs to be idempotent — I saw this directly: I ran two consumers against order_events, confirmed the 3 partitions split across them with kafka-consumer-groups.sh --describe, killed one, and watched the coordinator hand its partition to the survivor with zero duplicate rows in the warehouse afterward." The signal: naming the coordinator and the one-owner-per-partition rule precisely, and tying the handoff back to the same idempotent-write guarantee from Day 6 instead of treating rebalancing as an unrelated new risk.
