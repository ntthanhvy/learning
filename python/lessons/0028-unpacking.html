Unpacking: naming the pieces instead of indexing for them

Two lessons back-to-back made the same promise and neither kept it: Day 2's slicing section wrote header, *rows = [...] and called it "preview only — unpacking is Day 4," and Day 3's zip(names, ages) section said "unpacking it fully is Day 4." Day 4 arrived and taught functions, key=, and lambda instead — no unpacking anywhere in it. Today finally delivers on both promises, and closes the last unstarted item on MISSION.md's own idiom checklist ("comprehensions, unpacking, sorted(key=…), dict/set … collections … itertools") — every other item on that list already has its lesson.

Bridge from SQL: a SQL query with three selected columns is fetched into three named variables all at once — city, amount, date = cursor.fetchone() — no manual indexing into a row tuple by position needed. Unpacking is that same "several names, one assignment" move, generalized to any Python sequence.

1 · The basic move: names on the left, a sequence on the right

A tuple or list can be assigned to several names at once, matched by position, instead of pulling each element out by index one at a time:

point = (3, 4)
x, y = point                # x = 3, y = 4 — one statement, two names bound

# the equivalent written the long way, by index:
x = point[0]
y = point[1]

The number of names on the left must match the number of items on the right exactly, or Python raises ValueError rather than silently dropping or padding anything:

x, y, z = (3, 4)      # ValueError: not enough values to unpack (expected 3, got 2)
x, y = (3, 4, 5)      # ValueError: too many values to unpack (expected 2)

This already explains something seen since Day 3 without a name for it: for name, age in zip(names, ages): unpacks each (name, age) tuple zip produces into two names, once per loop iteration — the exact mechanism this section just introduced, already in daily use for three lessons. Day 3's dict comprehension ({n: a for n, a in zip(names, ages)}) unpacks the same way, inside the comprehension's own for clause. Day 4's sorted(city_counts.items(), key=lambda pair: pair[1]) reached into a (city, count) tuple with pair[1] indexing instead, because a lambda's parameter list has no for clause to unpack inside — indexing was the only option available there.

2 · for loops unpack every iteration, automatically

Section 1's zip callback generalizes: any for loop whose loop variable is written as several comma-separated names, not one, unpacks each item on every pass:

rows = [("Hanoi", 120), ("HCMC", 80), ("Danang", 200)]
for city, amount in rows:
    print(city, amount)     # unpacks each (city, amount) tuple fresh, once per iteration

# a dict's .items() gives (key, value) pairs — the single most common case
prices = {"apple": 3, "pear": 5}
for fruit, price in prices.items():
    print(fruit, price)

Nothing new is happening mechanically here versus section 1 — for city, amount in rows runs section 1's exact tuple-unpacking assignment once per row, silently, which is precisely what every for name, age in zip(...) loop since Day 3 has already been doing.

3 · Star-unpacking: *rest collects "everything else" into a list

Plain unpacking demands an exact count match. A single name prefixed with * relaxes that — it collects however many leftover items remain into a list, so the count no longer has to match exactly:

header, *rows = ["id,name", "1,An", "2,Binh", "3,Chi"]
# header = "id,name"
# rows   = ["1,An", "2,Binh", "3,Chi"]   — a list, even though only 1 item is "left over" isn't required

first, *middle, last = [10, 20, 30, 40, 50]
# first = 10, middle = [20, 30, 40], last = 50 — * can sit anywhere, not just first or last

This is Day 2's own preview example, unblocked at last: header, *rows peels the header row off a CSV-shaped list and collects every remaining line into rows, in one line, with no slicing or index arithmetic. Exactly one *name is allowed per unpacking assignment — Python has no way to know how to split leftovers between two star-names — but that one star can appear in any position, not only the last.

This is the same star seen before, in a different position. Day 4 taught def f(*args) collecting extra positional call arguments into a tuple named args — star meaning "collect the rest" in a function definition. Today's *rest in an assignment is that identical idea, one position over: star still means "collect the rest," just gathering leftover unpacking targets into a list instead of leftover call arguments into a tuple.

# Day 4's *args — collects extra call arguments, in a function definition:
def f(*args):
    return args           # f(1, 2, 3) -> (1, 2, 3), a tuple

# today's *rest — collects extra unpacking targets, in an assignment:
first, *rest = [1, 2, 3]     # rest = [2, 3], a list

4 · The swap idiom, and unpacking a function's return value

Unpacking makes swapping two names' objects a single line, with no temporary third name needed:

a, b = 1, 2
a, b = b, a          # a = 2, b = 1 — the whole right side is built as one tuple FIRST, then unpacked

# the equivalent every other mainstream language needs a temp variable for:
temp = a
a = b
b = temp

The reason this works and isn't a race between overwriting a too early: Python fully evaluates the entire right-hand side into a tuple before any assignment on the left happens — b, a is built as (2, 1) first, in full, then unpacked into a and b only after. Same rule as section 1, just with the right side written directly as a comma-separated tuple instead of a variable already holding one.

A function that returns several comma-separated values is really returning one tuple — the exact object section 1 already knows how to unpack, right at the call site, with no intermediate variable holding the whole tuple at all:

def min_max(values):
    return min(values), max(values)   # one tuple returned: (min, max)

lowest, highest = min_max([120, 80, 200, 45])
# lowest = 45, highest = 200 — unpacked directly from the call, no min_max(...)[0] indexing needed

min(values), max(values) after return is just two expressions separated by a comma — Python packs them into a tuple automatically, the same implicit tuple-building the swap idiom's right-hand side just relied on. Calling min_max(...) without unpacking gives back that one (45, 200) tuple whole; writing lowest, highest = min_max(...) unpacks it immediately, reading exactly like "this function gives me two things, name them both."

Where pandas goes from here: df.shape returns a (rows, cols) tuple that gets unpacked the exact same way — n_rows, n_cols = df.shape — once data/ introduces DataFrames. Not demonstrated here; that's data/'s job, and this is the only sentence in this lesson that names it.
