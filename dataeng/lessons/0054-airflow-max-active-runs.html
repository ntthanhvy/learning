1 · The gap: a backfill was named on Day 19, never actually bounded

Day 19 described backfill with a concrete scenario this exact pipeline could hit: raw.orders for three days gets corrupted and re-loaded, so mart_delivery_sla needs recomputing for each of those logical dates. What that lesson never asked is what happens the moment someone actually runs airflow dags backfill for a three-day range: by default, Airflow is free to start all three runs' tasks at once, because nothing in the DAG said otherwise. Three concurrent dbt_build tasks, each running dbt build against the same Postgres warehouse at the same time, is a real problem — not a hypothetical one — because fct_orders and mart_delivery_sla are tables, not append-only logs, and two overlapping dbt build runs rebuilding the same table from different source snapshots can interleave in ways that leave it correct for neither date.

The fix is not "write smarter dbt SQL." It's a DAG-level setting that was always available and never set: max_active_runs. Every DAG this course has written since Day 7 left it at its default, 16 — fine for a single daily schedule where only one run is ever pending at a time, silently dangerous the moment a backfill queues several.

2 · Confirmed live: the setting round-trips through a real parse

Built a scratch DAG shaped exactly like the real food_delivery_pipeline — load_raw, Day 51's dbt_models TaskGroup wrapping dbt_build, then check_dead_letters — with two new keyword arguments added to the DAG(...) call itself, not to any task:

with DAG(
    dag_id="food_delivery_pipeline",
    start_date=datetime(2026, 9, 21),
    schedule="@daily",
    catchup=True,
    max_active_runs=1,
    dagrun_timeout=timedelta(minutes=30),
) as dag:
    ...

Parsed it with a real DagBag against an installed apache-airflow==3.3.1 and read both settings straight back off the parsed DAG object, not assumed from the constructor signature:

import errors: {}
max_active_runs: 1
dagrun_timeout: 0:30:00
catchup: True

Zero import errors, and both values survived the parse exactly as written. catchup=True staying True alongside max_active_runs=1 matters specifically: the two settings are not in tension. catchup decides how many runs get created for missed intervals; max_active_runs decides how many of those created runs are allowed to be actively executing at once. A three-day catchup with max_active_runs=1 still creates all three runs — they just execute one after another instead of together, exactly the ordering the shared-warehouse problem in Section 1 needs.

The second setting, confirmed the same way: dagrun_timeout is a per-DAG-run deadline, separate from Day 35's per-task retries/retry_delay. If a run's tasks haven't all finished within the window (30 minutes here), Airflow marks that entire run failed and moves on — without it, a single hung dbt build inside a max_active_runs=1 DAG would block every queued date behind it indefinitely, since the next run can't start until the active one's slot frees up. The two settings solve complementary problems: max_active_runs bounds concurrency, dagrun_timeout bounds how long any one occupant of that concurrency slot is allowed to sit in it.

3 · Build: add both to the real DAG

In your food-delivery-pipeline repo, edit dags/food_delivery_pipeline.py. Today only touches the DAG(...) call's own keyword arguments — no task, no dependency edge, changes:

# new import, alongside the existing datetime import
from datetime import datetime, timedelta

# the existing `with DAG(...) as dag:` block gains two keyword arguments;
# everything else inside it (load_raw, dbt_models, check_dead_letters,
# and the dependency wiring) is untouched
with DAG(
    dag_id="food_delivery_pipeline",
    start_date=datetime(2026, 9, 21),
    schedule="@daily",
    catchup=True,
    max_active_runs=1,  # one date's dbt build at a time against the shared warehouse
    dagrun_timeout=timedelta(minutes=30),  # a hung run can't block every date behind it forever
) as dag:
    ...

max_active_runs=1 is the conservative, correct default for this specific pipeline: one Postgres warehouse, one set of dbt tables being written by every run regardless of which logical date it's processing. A pipeline whose runs wrote to date-partitioned tables instead could safely set this higher and gain real parallelism across a backfill; this one can't, because fct_orders and mart_delivery_sla have no date-scoped write target to keep two concurrent runs from touching the same rows.

Q: "You need to backfill three days of a daily DAG that writes to a shared warehouse table. What stops the three runs from corrupting each other?" A strong answer, out loud: "By default Airflow will happily run up to 16 DAG runs of the same DAG concurrently, which for most pipelines is fine but is actually dangerous here, because every run's dbt build writes to the same physical tables regardless of which logical date it's processing — two overlapping builds racing against fct_orders can leave it correct for neither date. The fix is max_active_runs on the DAG itself, set to 1: catchup still creates all three backfilled runs, but Airflow only lets one be actively executing at a time, so they queue and execute strictly in order instead of racing. I'd pair that with a dagrun_timeout too, because a max_active_runs=1 DAG has a new failure mode: one hung run now blocks every queued run behind it indefinitely, since the next one can't start until the active slot frees up — a per-run deadline makes sure a stuck build fails and releases that slot instead of wedging the whole backfill." The signal: naming that the shared-warehouse write target, not the backfill mechanism itself, is what makes concurrency unsafe here — and that capping concurrency creates its own new failure mode a timeout is needed to close.

Scope line

This lesson covers max_active_runs and dagrun_timeout as DAG-level settings, confirmed live via a DagBag parse. It does not cover max_active_tasks (the equivalent cap on concurrent tasks within one run, a different knob for a DAG with real intra-run parallelism, which this course's linear load_raw >> dbt_models >> check_dead_letters shape doesn't currently need), Airflow pools (vocabulary only here — the right tool once more than one DAG shares one constrained resource, which this single-DAG portfolio doesn't have yet), or max_consecutive_failed_dag_runs (an Airflow 3 setting that auto-pauses a DAG after N straight failed runs, worth a look once the dead-letter alerting from Days 45-47 is judged mature enough to need an upstream circuit breaker too).
