Data Pipelines · Reference

Glossary

Every jargon term used in the lessons, in one place, grouped by the lesson that introduced it. The Tiếng Việt column is dev-style: how Vietnamese data engineers actually say it, not a textbook translation.

Day 1 — The pipeline map & the repo

TermTiếng Việt (dev-style)In software
pipelinegiữ nguyên "pipeline" — chuỗi bước tự động di chuyển/biến đổi dữ liệuA scheduled, repeatable sequence of steps that moves and transforms data from a source to somewhere it can be used — the umbrella term for the whole thing this course builds.
ETLgiữ nguyên "ETL" — biến đổi TRƯỚC khi load vào đíchExtract, Transform, Load — data is transformed in a separate processing engine before it ever reaches the destination, so the destination only ever sees clean, final-shaped data.
ELTgiữ nguyên "ELT" — load THÔ trước, biến đổi SAU ngay trong warehouseExtract, Load, Transform — raw data is loaded into the destination first, untransformed, and transformation happens afterward inside that same destination using its own compute. This course's approach; dbt is the T.
raw layergiữ nguyên "raw layer" — dữ liệu thô, y nguyên lúc mới vào, chưa xử lý gìThe schema holding data exactly as it arrived from its source, before any cleaning or reshaping — the permanent, replayable starting point every transformation can be re-run from.
dbtgiữ nguyên "dbt" — công cụ biến đổi dữ liệu bằng SQL, chạy ngay trong warehouseA SQL-based transformation tool: you write SELECT statements, it compiles and runs them inside the warehouse, tracks which model depends on which via ref(), and can test the results — the T in this course's ELT.
Kafkagiữ nguyên "Kafka" — hệ thống log phân tán, nhận sự kiện liên tục theo thời gian thựcA distributed append-only log system: producers write events to topics, consumers read them in order, and it's built for continuously arriving data rather than periodic batches.
Airflowgiữ nguyên "Airflow" — công cụ lập lịch và điều phối, tự nó không xử lý dữ liệuA scheduler and orchestrator: it runs a defined sequence of tasks (a DAG) on a schedule, retries failures, and tracks whether each run succeeded — it does not transform or move data itself, it triggers the tools that do.
idempotentgiữ nguyên "idempotent" — làm 1 lần hay N lần, kết quả như nhauAn operation that produces the same end state whether performed once or many times — safe to retry blindly, which matters wherever a step might run twice. Same idea as backend/'s idempotency keys, applied to a pipeline.

Day 2 — dbt: sources, staging & ref()

TermTiếng Việt (dev-style)In software
dbt modelgiữ nguyên "dbt model" — 1 file .sql chứa 1 câu SELECT, dbt biên dịch và chạy để tạo ra 1 view/tableA single dbt model — one .sql file containing one SELECT statement, compiled and run by dbt, that produces one view or table in the warehouse.
DAGgiữ nguyên "DAG" — sơ đồ phụ thuộc dbt tự dựng từ ref()/source(), quyết định thứ tự buildThe directed acyclic graph dbt builds from every ref() and source() call in a project — which model depends on which, and therefore the only valid build order.
staginggiữ nguyên "staging" — lớp model đầu tiên trên raw, mỗi model ứng với 1 bảng nguồn, chỉ dọn nhẹ, không joinThe dbt layer immediately above raw sources — one model per source table, doing only light cleanup (renaming, casting, light derivations), never joining across sources.
sourcegiữ nguyên "source" — khai báo trỏ tới bảng raw có sẵn, model gọi qua source() thay vì viết tên schema.table cứngA dbt-declared pointer at a raw table that already exists in the warehouse (not built by dbt) — lets models reference it via source() instead of a hardcoded schema.table name, and is what freshness checks attach to.
materializationgiữ nguyên "materialization" — cách SELECT của model biến thành đối tượng trong warehouse: view, table, hay incrementaldbt's setting for how a model's SELECT becomes warehouse objects — view (query re-runs every time it's read, always fresh, no storage), table (query runs once at build time, stored, stale until next run), or incremental (Day 4).
viewgiữ nguyên "view" — dbt bọc SELECT trong CREATE VIEW, không lưu dữ liệu, luôn mới nhấtA materialization where dbt wraps the SELECT in CREATE VIEW — no data is stored, the query re-runs on every read, always reflects current raw data, cheapest to build.

Day 3 — dbt: tests catch bad data

TermTiếng Việt (dev-style)In software
data testgiữ nguyên "data test" — phép kiểm tra dbt chạy trên dữ liệu thật, query trả về hàng nào là fail hàng đóA dbt-run assertion against real warehouse data, expressed as a query — it fails if the query returns any rows, and runs alongside models via dbt build.
generic testgiữ nguyên "generic test" — test dùng lại được, khai báo trong YAML, áp cho cột nào cũng đượcA reusable, parameterized dbt test defined once (built into dbt or a package) and applied to any column via YAML — not_null, unique, relationships and accepted_values are the four that ship with dbt itself.
relationships testgiữ nguyên "relationships test" — kiểm tra khóa ngoại, giá trị cột này phải tồn tại ở cột kiaA generic dbt test asserting that every value in a column exists as a value in another model or source's column — the relational-integrity check, e.g. every stg_orders.restaurant_id must exist in stg_restaurants.restaurant_id.
not_null testgiữ nguyên "not_null test" — kiểm tra cột không có giá trị NULLA generic dbt test asserting every value in a column is non-NULL.
unique testgiữ nguyên "unique test" — kiểm tra cột không có giá trị trùngA generic dbt test asserting every value in a column is distinct — no duplicates.
singular testgiữ nguyên "singular test" — test viết riêng bằng 1 file .sql trong tests/, không dùng lại được cho cột khácA one-off dbt test written as a single .sql SELECT file in tests/ — fails if the query returns any rows, for a business rule too specific to express as a generic test.
source freshnessgiữ nguyên "source freshness" — kiểm tra dữ liệu nguồn có bị cũ/trễ không, dựa vào cột thời gianA dbt check on a source's timestamp column comparing its most recent value to now — warns or errors if the data is older than a configured threshold, catching a stalled loader before anyone notices missing rows.
loaded_at_fieldgiữ nguyên "loaded_at_field" — tên cột thời gian dùng để tính độ mới của dữ liệuThe sources.yml field naming which timestamp column freshness should read from — required for any source with a freshness block configured.

Day 4 — dbt: marts, facts, dimensions & incremental

TermTiếng Việt (dev-style)In software
martgiữ nguyên "mart" — lớp model trên cùng, join nhiều staging model lại thành bảng người dùng cuối thực sự truy vấnThe dbt layer built on top of staging, joining across staging models into the shapes a dashboard, analyst or downstream consumer actually queries — the layer this course's headline tables (fct_orders, dim_restaurants, dim_couriers, mart_delivery_sla) live in.
fact tablegiữ nguyên "fact table" — 1 dòng/sự kiện, chứa khóa ngoại tới dimension và các số liệu để tính tổng/trung bìnhA mart table holding one row per business event, at a fixed grain, with foreign keys to its dimensions and the numeric measures analysts aggregate — fct_orders is one row per order, the event this whole pipeline exists to track.
dimension tablegiữ nguyên "dimension table" — 1 dòng/thực thể, chứa các thuộc tính để filter hoặc group byA mart table holding one row per real-world entity, with the descriptive attributes people filter or group by — dim_restaurants is one row per restaurant, the entity orders reference by foreign key.
graingiữ nguyên "grain" — mức chi tiết 1 dòng đại diện, phải nói rõ ràng (ví dụ "mỗi dòng = 1 order")The level of detail one row of a table represents — stating it explicitly (e.g. "one row per order") is what lets anyone check a model is right without reading its SQL.
table (materialization)giữ nguyên "table" — dbt lưu kết quả SELECT thành bảng thật, đọc nhanh hơn view nhưng phải build lại mới cập nhậtA materialization where dbt runs the SELECT once at build time and stores the result as a real table — faster to query than a view, but stale until the next dbt run rebuilds it from scratch.
incremental modelgiữ nguyên "incremental model" — sau lần build đầu, dbt chỉ xử lý dòng mới/thay đổi, không build lại toàn bộA materialization where, after the first build, dbt only processes new or changed rows instead of rebuilding the whole table from scratch — the right default for a large, append-heavy table where reprocessing everything every run wastes time.

Day 5 — Kafka: topics, partitions, keys & offsets

TermTiếng Việt (dev-style)In software
loggiữ nguyên "log" — chuỗi record chỉ được append, có thứ tự, không sửa/xoá tại chỗThe append-only, ordered sequence of records inside one Kafka partition — records are never updated or deleted in place, only appended, and each one gets a permanent position number.
topicgiữ nguyên "topic" — luồng dữ liệu có tên trong Kafka, producer ghi vào, consumer đọc raA named, durable feed of records in Kafka that producers write to and consumers read from — the basic unit of organization, roughly Kafka's answer to a table name, except it holds an ordered log rather than queryable rows. This course's one topic is order_events.
producergiữ nguyên "producer" — bên ghi record vào topicA client that writes records to a topic.
consumergiữ nguyên "consumer" — bên đọc record từ topic, đọc theo thứ tự, tự theo dõi vị trí đã đọcA client that reads records from a topic, in order, tracking its own position.
partitiongiữ nguyên "partition" — 1 trong các log con của topic, Kafka chỉ đảm bảo thứ tự TRONG 1 partition, không đảm bảo giữa các partitionOne of the ordered, append-only logs a Kafka topic is split into — Kafka guarantees order only within a single partition, never across partitions of the same topic.
keygiữ nguyên "key" — chuỗi gắn vào message để Kafka hash ra partition; cùng key luôn vào cùng 1 partitionThe string a producer attaches to a message that Kafka hashes to pick which partition the message goes to — every message with the same key always lands on the same partition, which is what makes per-key ordering possible. This course keys every order_events message by order_id.
offsetgiữ nguyên "offset" — số thứ tự cố định của record trong 1 partition, bắt đầu từ 0A record's permanent position number within one partition, starting at 0 and increasing by 1 per record — a consumer group tracks the next offset it needs to read as its bookmark into that partition.
committed offsetgiữ nguyên "committed offset" — offset mà consumer group đã xác nhận xử lý xong, Kafka tự lưu lạiThe offset a consumer group has confirmed processing up to, for one partition — persisted by Kafka itself so a consumer that restarts resumes from here instead of from the beginning.
consumer groupgiữ nguyên "consumer group" — tập consumer cùng group.id, chia nhau đọc các partition, dùng chung offset đã commitA named set of consumers that coordinate to split a topic's partitions between them and share one committed-offset bookmark per partition — the unit Kafka scales consumption with, and the unit the kafka-consumer-groups.sh --describe CLI command inspects.

Day 6 — Kafka → warehouse: at-least-once, landed safely

TermTiếng Việt (dev-style)In software
at-least-oncegiữ nguyên "at-least-once" — consumer có thể xử lý lại 1 message (sau khi crash/restart) nhưng không bao giờ mất messageA delivery guarantee where a consumer may process the same message more than once (after a crash and restart, for example) but never loses a message outright — the default a plain manual-commit Kafka consumer gives you, and the one this course's consumer is built around.
idempotent writegiữ nguyên "idempotent write" — ghi lại nhiều lần với cùng input vẫn ra kết quả như ghi 1 lầnAn operation safe to perform more than once with the same input, because repeating it produces no different end state than performing it once — the property that makes an at-least-once delivery guarantee safe to build on.
ON CONFLICT DO NOTHINGgiữ nguyên "ON CONFLICT DO NOTHING" — nếu INSERT đụng unique constraint thì bỏ qua, không báo lỗi, không ghi đèA Postgres INSERT clause that, when the row being inserted would violate a uniqueness constraint, does nothing instead of raising an error — the standard way to make a Postgres write idempotent on a natural or surrogate key.
manual offset commitgiữ nguyên "manual offset commit" — tắt auto-commit, tự gọi commit() đúng lúc mình muốn, thường là sau khi ghi xongA Kafka consumer setting (enable.auto.commit=False) where the client library never commits an offset on its own timer — the application calls commit() explicitly, at the exact moment it chooses, which is what lets this lesson's consumer guarantee the write happens first.

Day 7 — Airflow orchestrates the batch & ship it

TermTiếng Việt (dev-style)In software
Airflow DAGgiữ nguyên "Airflow DAG" — đồ thị các task và phụ thuộc, Airflow lên lịch và chạy như 1 đơn vịA directed graph of tasks and their dependencies that Airflow schedules and runs together as one unit — the file that defines what runs, in what order, and how often. The same graph idea as dbt's DAG (Day 2), one level up: tasks depend on tasks, not models on models.
airflow standalonegiữ nguyên "airflow standalone" — lệnh chạy Airflow nhẹ nhất cho local dev, gộp webserver+scheduler+migrate vào 1 processAirflow's own lightest local-dev command: it runs the webserver, scheduler and a one-time database migration all in a single process, defaulting to SQLite metadata storage and LocalExecutor — no separate containers, queue or worker fleet, unlike the official reference docker-compose.yaml.
retriesgiữ nguyên "retries" — số lần Airflow tự chạy lại 1 task bị fail trước khi đánh dấu fail hẳnAn Airflow task setting: how many additional times a failed task is automatically re-run before the run is marked failed for good, with retry_delay controlling the pause between attempts.
catchupgiữ nguyên "catchup" — Airflow có tự chạy bù các lần lịch đã bị bỏ lỡ từ start_date tới nay hay khôngAn Airflow DAG setting controlling whether, on first deploy or after downtime, the scheduler creates one run for every missed schedule interval between start_date and now (catchup=True, the default) or only the most recent one going forward (catchup=False).
BashOperatorgiữ nguyên "BashOperator" — Airflow task chạy 1 lệnh shell trong subprocess, thành/bại theo exit codeAn Airflow operator that runs a given string as a shell command in a subprocess — the task succeeds or fails based on that subprocess's exit code, with no Airflow-specific knowledge of what the command actually does. Lives in airflow.providers.standard.operators.bash as of Airflow 3, not Airflow core.

Day 8 — dbt: the intermediate layer

TermTiếng Việt (dev-style)In software
intermediate modelgiữ nguyên "intermediate model" — lớp giữa staging và marts, gộp 1 logic join/biến đổi cụ thể để nhiều mart dùng lại, tránh lặp codeThe dbt layer between staging and marts: models prefixed int_, doing one specific piece of joining or reshaping logic that more than one downstream mart needs, so that logic exists in exactly one place — not meant to be queried directly, only by other dbt models.
ephemeralgiữ nguyên "ephemeral" — không tạo view/table riêng, dbt nhúng thẳng SELECT vào model gọi nó lúc compileA materialization that isn't a database object at all — dbt inlines the model's SELECT directly into whichever downstream model queries it, at compile time, so it costs nothing to build and never shows up as its own table or view. The house-style default for intermediate models, since nobody outside dbt queries them directly.

Day 9 — dbt snapshots: SCD Type 2 for commission_rate

TermTiếng Việt (dev-style)In software
slowly changing dimensiongiữ nguyên "slowly changing dimension" (SCD) — thuộc tính dimension thay đổi theo thời gian, ví dụ commission_rateA dimension attribute that changes over time — restaurants.commission_rate is one, since a restaurant's rate can be renegotiated — as opposed to an attribute like restaurant_id that never changes for the life of the row. Kimball's own vocabulary, predating dbt.
SCD Type 1giữ nguyên "SCD Type 1" — ghi đè giá trị cũ bằng giá trị mới, không giữ lịch sửThe simplest way to handle a slowly changing dimension: overwrite the old value with the new one, keeping no history at all — what raw.restaurants does today via a plain UPDATE, and the reason last month's commission_rate is already gone by the time you'd want to ask about it.
SCD Type 2giữ nguyên "SCD Type 2" — giữ mỗi giá trị lịch sử thành 1 dòng riêng, có khoảng thời gian hiệu lực, cho phép hỏi "giá trị tại thời điểm X là gì"The SCD approach that keeps every historical value of a changing attribute as its own row, each stamped with the time window it was actually true for — so a query can ask "what was this attribute's value at time X" instead of only "what is it now." What a dbt snapshot builds.
snapshot strategygiữ nguyên "snapshot strategy" — cách snapshot phát hiện 1 dòng đã đổi: "timestamp" so sánh 1 cột updated_at, "check" so sánh trực tiếp danh sách cộtA dbt snapshot's setting for how it decides a row changed — timestamp compares one column (usually an updated_at) and treats any change to that timestamp as a new version; check instead compares a named list of columns directly and treats any difference in those columns as a new version.
dbt_valid_from / dbt_valid_togiữ nguyên "dbt_valid_from" / "dbt_valid_to" — cột dbt tự thêm, đánh dấu khoảng thời gian 1 phiên bản dòng dữ liệu có hiệu lực; dbt_valid_to null nghĩa là phiên bản hiện tạiThe two columns dbt adds automatically to every snapshot table: dbt_valid_from is the timestamp a given version of a row started being true, dbt_valid_to is when it stopped — null for the row that is still current. Together they define the exact window each historical version was accurate for.
point-in-time joingiữ nguyên "point-in-time join" — join theo trạng thái đúng tại 1 thời điểm cụ thể trong quá khứ, không phải trạng thái hiện tạiA join condition that matches a row on the state something was in during a specific window of time, rather than the state it is in now — here, matching each order to the restaurants_snapshot row whose dbt_valid_from/dbt_valid_to window contains the order's own placed_at, instead of a plain equi-join on restaurant_id alone.

Day 10 — dbt: Jinja, macros & var()

TermTiếng Việt (dev-style)In software
Jinjagiữ nguyên "Jinja" — ngôn ngữ template dbt dùng để biên dịch .sql trước khi gửi tới Postgres, {{ }} cho biểu thức, {% %} cho if/forThe templating language dbt compiles every .sql file through before sending it to Postgres — {{ }} for expressions, {% %} for control flow like if/for, running at compile time, not query time. ref() and source() are Jinja functions dbt provides.
var()giữ nguyên "var()" — biến cấp project, khai báo default trong dbt_project.yml, đọc bằng {{ var('name') }}, ghi đè được qua --vars mà không sửa SQLA dbt project-level setting, declared with a default in dbt_project.yml and readable from any model via {{ var('name') }}, and overridable per-invocation with --vars without touching any SQL file.
macrogiữ nguyên "macro" — hàm Jinja tái sử dụng, định nghĩa 1 lần trong macros/, gọi từ model bằng {{ macro_name(args) }}, tránh lặp code SQLA reusable Jinja function defined once in macros/ with {% macro %}...{% endmacro %}, callable from any model with {{ macro_name(args) }} — dbt's answer to not copy-pasting the same SQL fragment or Jinja logic into multiple files. Only earns its place with a second real caller; one caller is pure indirection.

Day 11 — dbt packages: dbt_utils and when to write a test instead

TermTiếng Việt (dev-style)In software
dbt packagegiữ nguyên "dbt package" — gói macro/test dbt cài qua packages.yml và dbt deps, giống thư viện Python/npm nhưng cho dbtA bundle of dbt macros and generic tests, distributed as a git repo, that a project pulls in via packages.yml and dbt deps — the dbt equivalent of a Python or npm library, extending what Jinja and YAML tests a project has access to without hand-writing them. dbt_utils, maintained by dbt Labs, is the most widely installed one.
surrogate keygiữ nguyên "surrogate key" — cột khóa nhân tạo (thường hash từ cột khác) dùng làm định danh duy nhất, khác với khóa tự nhiên có sẵn trong dữ liệu nguồnA column whose value is manufactured (typically hashed) from other columns specifically to serve as a unique identifier, as opposed to a natural key that already existed in the source data — used when a model's real-world grain has no single natural column to test unique/not_null against. dbt_utils.generate_surrogate_key() builds one by coalescing, concatenating and hashing a list of columns.

Day 12 — dbt unit tests vs. data tests

TermTiếng Việt (dev-style)In software
unit test (dbt)giữ nguyên "unit test" (dbt >= 1.8) — dòng input giả cố định thay cho ref()/source() thật của model, so với dòng kết quả kỳ vọng tự viếtA dbt test (dbt-core >= 1.8) that replaces a model's real ref()/source() inputs with small, hand-written fake rows via given, runs the model's actual SQL against them, and diffs the result against hand-written expect rows — proving the transformation's logic is correct on known inputs, independent of whatever data is really in the warehouse. Complements, not replaces, a data test (Day 3).

Day 13 — dbt incremental strategies in depth

TermTiếng Việt (dev-style)In software
incremental strategygiữ nguyên "incremental strategy" — cách 1 incremental model hợp nhất dòng mới với dữ liệu đã có: append (chỉ insert), delete+insert (xoá rồi insert lại), merge (1 câu MERGE, vừa update vừa insert)A dbt incremental_strategy setting for how an incremental model reconciles new rows with what's already in the table — append does a plain insert with no unique_key; delete+insert deletes any existing row sharing a key with the new batch then inserts the whole batch (dbt-postgres's own default once unique_key is set); merge runs a single MERGE statement that updates matching keys in place and inserts new ones.
--full-refreshgiữ nguyên "--full-refresh" — cờ bảo dbt bỏ qua is_incremental(), build lại toàn bộ incremental model từ đầuA dbt run/dbt build flag that drops and rebuilds an incremental model's table entirely from its full, unfiltered select, ignoring is_incremental() for that one invocation — the blunt, correct-but-expensive fix for a late correction the incremental filter's own column never caught.
late-arriving eventgiữ nguyên "late-arriving event" — sự kiện thật đến trễ, sau khi dòng/nhóm nó thuộc về đã được xử lý xong, filter incremental chỉ nhìn về phía trước sẽ bỏ sót nóA real event a model's incremental logic needs to account for that arrives after the row or bucket it belongs to has already been processed — a filter that only looks forward from the last run will silently miss it unless it re-checks a short lookback window.

Day 14 — dbt docs, exposures & model contracts

TermTiếng Việt (dev-style)In software
model contractgiữ nguyên "model contract" — khai báo trước tên cột, kiểu dữ liệu và ràng buộc not_null/unique/primary_key của 1 model, dbt so khớp SELECT đã compile với khai báo đó trước khi cho build hoàn tất, bắt lỗi hình dạng trước khi bản build sai lọt qua thay vì test sauA dbt model config (contract: {enforced: true}) that declares a model's exact column names, data types and column-level not_null/unique/primary_key constraints up front in YAML, and has dbt compare the model's compiled SELECT against that declared shape before allowing the build to finish — catches a shape mismatch before a bad build ever lands, rather than testing the output afterward. On Postgres these constraints are real, database-enforced DDL, not just declared metadata, unlike on some other warehouses dbt supports.
exposuregiữ nguyên "exposure" — khai báo 1 bên tiêu thụ downstream không phải dbt (dashboard, notebook, pipeline khác), nêu rõ phụ thuộc vào model/source nào qua ref()/source(), trở thành 1 node thật trong DAG của dbt dù dbt không build nóA dbt YAML declaration (exposures: key) naming a non-dbt downstream consumer — a dashboard, notebook or pipeline — and the dbt models/sources it depends on via ref()/source(), added as a real node in dbt's own DAG and lineage graph even though dbt never builds it. A broken ref() inside one fails dbt parse immediately, the same as a broken ref() between two models.

Day 15 — dbt in CI: GitHub Actions, state:modified+, deferral

TermTiếng Việt (dev-style)In software
CI (continuous integration)giữ nguyên "CI" — tự động build/test mỗi thay đổi trước khi merge, chạy trên server chứ không phải máy dev, bắt lỗi trước khi lọt vào mainThe practice of automatically building and testing every proposed code change before it merges, on a server rather than a developer's own machine, so a broken change is caught before it reaches main — here, a GitHub Actions workflow running dbt build against a disposable Postgres service container on every pull request.
service containergiữ nguyên "service container" — container GitHub Actions khởi cùng job, các step trong job gọi qua localhost, chỉ tồn tại trong lúc job chạy rồi bị xoáA container GitHub Actions starts alongside a job's own runner, reachable at localhost from every step in that job, that exists only for the duration of the job and is discarded afterward — used here for a throwaway postgres:17 instance, one per CI run.

Day 16 — Delivery semantics: at-most/at-least/exactly-once, the idempotent producer

TermTiếng Việt (dev-style)In software
at-most-oncegiữ nguyên "at-most-once" — message có thể mất nhưng không bao giờ bị xử lý 2 lầnA delivery guarantee where a message might be silently dropped but is never processed more than once — the trade you get by committing an offset before the corresponding write happens. Day 6 explicitly rejected this ordering for order data.
exactly-oncegiữ nguyên "exactly-once" — không mất, không xử lý 2 lần, nhưng chỉ đúng trong phạm vi 1 chặng cụ thể mà Kafka thực sự kiểm soát, không tự động lan ra hệ thống ngoàiA delivery guarantee where a message is neither lost nor processed more than once, from the point of view of one specific hop — Kafka provides this between a producer and a topic (the idempotent producer) and internally within Kafka Streams/consume-transform-produce chains, but it does not automatically extend to an arbitrary external system a consumer writes to, such as Postgres.
idempotent producergiữ nguyên "idempotent producer" — enable.idempotence=true, broker tự gán producer ID + số thứ tự per-partition, retry gửi lại thì broker tự nhận ra và bỏ qua, không tự viết code dedupA Kafka producer config (enable.idempotence=true) under which the broker assigns the producer a hidden producer ID and tracks a per-partition sequence number for every message it sends, so a retried send that already landed is recognized and dropped by the broker itself instead of being written a second time. Deduplicates on (producer ID, sequence number), not on any application-level field like event_id.

Day 17 — Schema evolution: why JSON-without-a-schema bites

TermTiếng Việt (dev-style)In software
backward-compatible changegiữ nguyên "backward-compatible change" — đổi schema mà code đọc theo schema CŨ vẫn đọc đúng message theo schema MỚI, thường là thêm field optional có defaultA schema change where every message written under the new shape can still be correctly read by code written against the old shape — typically adding a new optional field that old readers simply ignore, or giving a field a default so its absence is never an error.
Schema Registrygiữ nguyên "Schema Registry" — server riêng lưu từng phiên bản schema của mỗi topic, nếu cấu hình rule tương thích (backward/forward/full) thì chặn luôn producer đăng ký schema mới phá rule đó, bắt lỗi lúc publish thay vì lúc consumer crashA separate server that stores every version of every topic's message schema and, when configured, rejects a producer's attempt to register a new schema version that breaks a configured compatibility rule (e.g. backward) before that version is ever published to the topic — catching the mistake at publish time instead of at every consumer's crash time. Confluent's implementation is the common one; it isn't part of Apache Kafka itself.
Avrogiữ nguyên "Avro" — format binary gọn, schema định nghĩa riêng ngoài data, message chỉ mang schema ID, check tương thích dựa vào schema định nghĩa chứ không đoán qua payload mẫuA compact binary serialization format with a schema defined separately from the data, commonly paired with a Schema Registry; messages carry a schema ID instead of repeating field names, and compatibility rules are checked against the schema definition directly rather than inferred from example payloads.
Protobufgiữ nguyên "Protobuf" — format binary của Google, schema định nghĩa trong file .proto, sinh code theo từng ngôn ngữ, cũng hay dùng với Schema Registry giống AvroGoogle's binary serialization format with schemas defined in .proto files and generated code per language — the other common Schema-Registry-backed format, chosen over Avro mainly for its generated-code ergonomics and wide use outside the Kafka ecosystem.

Day 18 — Retention vs log compaction, and consumer lag as the health metric

TermTiếng Việt (dev-style)In software
retention.msgiữ nguyên "retention.ms" — cấu hình topic (hoặc default toàn broker) quy định message được giữ bao lâu trước khi bị xoá, tính bằng milliseconds kể từ lúc append, xoá theo lịch chứ không quan tâm consumer đã đọc hay chưaA Kafka topic (or broker-wide default) config controlling how long a message is kept in the log before it's eligible for deletion, measured in milliseconds since the message was appended — enforced on a schedule independent of whether any consumer group has actually read the message.
retention.bytesgiữ nguyên "retention.bytes" — cấu hình topic (hoặc default toàn broker) giới hạn kích thước (byte) partition log được phép lớn tới đâu trước khi segment cũ bị xoá để nhường chỗ, thường để unbounded trừ khi disk là ràng buộcA Kafka topic (or broker-wide default) config capping how large a partition's log is allowed to grow, in bytes, before older segments are deleted to make room — the other retention lever, usually left unbounded unless disk space is the binding constraint.
log compactiongiữ nguyên "log compaction" (cleanup.policy=compact) — broker định kỳ viết lại log, chỉ giữ message mới nhất của mỗi key, bỏ hết message cũ hơn cùng key, biến topic thành changelog "giá trị hiện tại theo key" thay vì ghi lại mọi message từng viếtA Kafka topic cleanup policy (cleanup.policy=compact) under which the broker periodically rewrites a partition's log to keep only the most recent message for each distinct key, discarding every older message sharing that key — turns the topic into a changelog of "current value per key" rather than a record of every message ever written. Contrasts with the broker's default cleanup.policy=delete (plain time/size retention, Section 2).
consumer laggiữ nguyên "consumer lag" — với 1 partition, là khoảng cách giữa high-water-mark offset hiện tại và committed offset của 1 consumer group cụ thể trên partition đó; lag tăng nghĩa là consumer xử lý chậm hơn tốc độ producer ghi, hoặc bị stuck/crashFor one partition, the difference between its current high-water-mark offset (the offset of the next message the broker would write) and a specific consumer group's committed offset on that partition — a rising lag means the consumer group is either processing slower than the producer is writing, or stuck/crashed outright. Read directly off the LAG column in kafka-consumer-groups.sh --describe; the single most-watched Kafka health metric in production.
high-water markgiữ nguyên "high-water mark" — offset của message kế tiếp partition log sẽ nhận, hiểu là "tổng cộng đã viết bao nhiêu message," con số dùng để tính consumer lagThe offset of the next message a partition's log would receive — effectively "how many messages have been written total," the number consumer lag is measured against. Shown as LOG-END-OFFSET in kafka-consumer-groups.sh --describe output.

TermTiếng Việt (dev-style)In software
logical_dategiữ nguyên "logical_date" — timestamp Airflow gắn cho 1 lần chạy để định danh, là đầu kỳ dữ liệu run đó đại diện, KHÔNG phải giờ thực tế chạy; Airflow 2 gọi là execution_dateThe timestamp Airflow assigns to identify a specific DAG run — for a scheduled run, the start of the period that run represents, not the wall-clock time the run actually executed; for a manual or backfilled run, whatever date was requested. backfillgiữ nguyên "backfill" — chủ động tạo và chạy lại DAG cho các logical_date trong quá khứ chưa chạy, hoặc cần chạy lại; bản chủ động, theo yêu cầu của thứ catchup=True làm tự độngDeliberately creating and running DAG runs for past logical dates that never ran, or that need to be rerun — the explicit, on-demand version of what catchup=True would have done automatically on first deploy. In Airflow 3.3.1, triggered via airflow backfill create --from-date --to-date (the old airflow dags backfill command was removed). Only safe when the tasks being backfilled are idempotent — see Day 7's catchup entry and this section's own idempotent-task discussion.

Captures inserts, updates and deletes — including deletes, which a timestamp-polling query cannot see — as structured before/after events, with one Kafka topic created per captured table.

Day 25 — Airflow sensors, deferrable operators & deadline alerts

sensorgiữ nguyên "sensor" — operator Airflow chuyên để chờ: kiểm tra 1 điều kiện (file tồn tại, task khác đã xong, 1 row đã có trong bảng) và chỉ cho DAG tiếp tục khi điều kiện đó đúng, bản thân không xử lý dữ liệu gì cảAn Airflow operator whose only job is to wait: it checks a condition (a file exists, an upstream task finished, a row exists in a table) on an interval and only lets the DAG continue once that condition is true, instead of doing any data work itself. mode="poke" (default) blocks a worker slot the whole time; mode="reschedule" frees the slot between checks.
