1 · The gap Day 48 named directly, not a new idea

Day 48's own closing line was explicit: "a per-city breakdown of today's histogram … is the clearest direct next step if this mart needs more granularity later." That mart answers one global question — across every city combined, how many orders land in each 5-minute delivery-time band. A real operator asking "is Hanoi's distribution different from Da Nang's" can't get that answer from a single global histogram, the same way Day 36's original mart_delivery_sla couldn't answer "which specific city is breaching" until it carried city as part of its grain. Today gives the histogram that same per-city grain.

The naive fix — add group by city to Day 48's final query — would reintroduce exactly the bug Day 48 and Day 36 each already fixed once: a group by can only ever emit a row for a (city, bucket) pair that already had at least one order in it. A city with a fast, tight distribution — zero orders past the 40-minute bucket, genuinely good news — would simply have no rows there, indistinguishable from "this bucket was never checked for this city" to anyone reading the table cold. The fix has to be the same grid-first, left-join-second shape both of those lessons used, just crossed over two generated axes instead of one.

2 · cross join: the SQL keyword for "every combination," named explicitly

Day 36 already wrote a cross join — cities cross join dim_dates — without ever naming the keyword as its own concept, since that lesson's point was the join direction, not the join type. Today names it directly, because today's grid genuinely needs two independent axes crossed for the first time in this course: every city paired with every one of Day 48's twenty buckets, N cities times 20 buckets rows, before a single real order is involved. cross join has no on clause at all — there's nothing to match, because the whole point is pairing everything with everything, the base grid a left join can then be anchored onto.

Build it from pieces that already exist: Day 36's cities CTE shape (select distinct city from stg_restaurants) and Day 48's bucket_grid CTE, unchanged.

3 · Build: cities × buckets, then the real orders left-joined on top

In your food-delivery-pipeline repo, create models/marts/mart_delivery_time_histogram_by_city.sql in full:

-- models/marts/mart_delivery_time_histogram_by_city.sql
{{ config(materialized='table') }}

with order_durations as (
    -- identical to Day 48's CTE of the same name -- orders, restaurants,
    -- and the placed/delivered pair of stg_order_events rows per order
    select
        o.order_id,
        r.city,
        extract(epoch from (d.delivered_at - p.placed_at)) / 60 as minutes_to_deliver
    from {{ ref('stg_orders') }} as o
    inner join {{ ref('stg_restaurants') }} as r on o.restaurant_id = r.restaurant_id
    inner join {{ ref('stg_order_events') }} as p
        on o.order_id = p.order_id and p.status = 'placed'
    inner join {{ ref('stg_order_events') }} as d
        on o.order_id = d.order_id and d.status = 'delivered'
),

-- Day 36's exact CTE shape, reused verbatim
cities as (
    select distinct city from {{ ref('stg_restaurants') }}
),

-- Day 48's exact bucket_series/bucket_grid CTEs, reused verbatim
bucket_series as (
    {{ dbt_utils.generate_series(var('histogram_bucket_count')) }}
),

bucket_grid as (
    select
        (generated_number - 1) * {{ var('histogram_bucket_minutes') }} as bucket_start_minutes,
        generated_number * {{ var('histogram_bucket_minutes') }} as bucket_end_minutes
    from bucket_series
),

-- new today: the two grids crossed into one, N cities x 20 buckets rows,
-- before any real order is involved
city_bucket_grid as (
    select
        cities.city,
        bucket_grid.bucket_start_minutes,
        bucket_grid.bucket_end_minutes
    from cities
    cross join bucket_grid
),

bucketed_orders as (
    select
        city_bucket_grid.city,
        city_bucket_grid.bucket_start_minutes,
        city_bucket_grid.bucket_end_minutes,
        count(order_durations.order_id) as order_count
    from city_bucket_grid
    left join order_durations
        on order_durations.city = city_bucket_grid.city
        and order_durations.minutes_to_deliver >= city_bucket_grid.bucket_start_minutes
        and order_durations.minutes_to_deliver < city_bucket_grid.bucket_end_minutes
    group by city_bucket_grid.city, city_bucket_grid.bucket_start_minutes, city_bucket_grid.bucket_end_minutes
)

select
    {{ dbt_utils.generate_surrogate_key(['city', 'bucket_start_minutes']) }} as bucket_key,
    city,
    bucket_start_minutes,
    bucket_end_minutes,
    order_count
from bucketed_orders
order by city, bucket_start_minutes

Two join conditions carry today's entire fix. The cross join in city_bucket_grid builds the full city × bucket grid with no filtering at all — exactly (distinct city count) × 20 rows, independent of whether any order exists yet. Then bucketed_orders starts from city_bucket_grid and left joins the real durations onto it with both a city match and a bucket-range match in the on clause — not just the bucket-range condition Day 48 used alone, since today's grid has a second axis that has to line up too. count(order_durations.order_id), not count(*), is Day 48's same habit for the same reason: it reads a failed left join's nulls as a true 0, never a 1.

4 · Why this needed a new mart, not a city filter bolted onto the old one

It's worth being precise about why today is a third mart next to mart_delivery_sla and mart_delivery_time_histogram, not an edit to either. Adding a where city = 'hanoi' filter on top of Day 48's existing model would answer one city at a time, by hand, for whoever happens to type the filter — it would not change the mart's grain, and every other city would stay invisible unless someone re-ran the query once per city. Changing the grain itself, from "one row per bucket" to "one row per city per bucket," is a different table with a different surrogate key ([city, bucket_start_minutes] today, versus Day 48's [bucket_start_minutes] alone) — the same reason Day 11's sla_key had to become (city, order_date) rather than staying a bare date. A dashboard built on today's mart can facet by city natively; a dashboard built on a hand-filtered query cannot facet by anything it wasn't specifically asked for.

This also means the two histogram marts coexist on purpose, not as a stale duplicate: mart_delivery_time_histogram is still the right table for "what does delivery time look like platform-wide," a single clean distribution with no city noise in it, while mart_delivery_time_histogram_by_city is the right table the moment the question becomes "is one city different from the others." Keeping both, rather than deleting Day 48's in favor of today's, is the same judgment call Section 4 of Day 48 itself made about mart_delivery_sla: different questions earn separate marts instead of forcing one table to answer everything through filters.

Q: "You've got a platform-wide delivery-time histogram. The VP asks whether Hanoi's distribution looks different from the rest. What do you build, and why not just filter the existing table?" A strong answer, out loud: "Filtering the existing histogram by city answers one city at a time, by hand, and nobody else's distribution shows up until someone re-runs the query with a different filter — it doesn't change what the table actually represents. The real fix is changing the grain: instead of one row per time bucket, one row per city per time bucket. I build that by crossing two grids — a cross join of the distinct cities with the generated bucket ladder — before any real order touches the query, so every city gets all twenty buckets whether or not it has orders in every one. Then I left-join the real per-city, per-bucket order counts onto that grid, matching on both city and bucket range, and keep count() on a named column so an empty cell reads as a true zero. The surrogate key moves from just the bucket to the pair of city and bucket, the same way an SLA mart's key had to grow from just a date to city-plus-date once a per-city answer mattered. I'd keep the platform-wide histogram too — it's still the right table for a different question — rather than deleting it in favor of the new one." The signal: naming the grain change as the actual fix, describing the two-grid cross join precisely, and justifying keeping both marts instead of treating the new one as a strict upgrade.

Scope line

This lesson covers crossing two generated/looked-up grids (cities and Day 48's bucket ladder) via cross join to build a per-city delivery-time histogram. It does not add a per-restaurant or per-courier breakdown (same pattern, a different select distinct source, left for whenever that granularity is actually asked for), and it does not touch Day 48's global histogram or Day 6's mart_delivery_sla — all three marts stay in the project side by side, answering different questions at different grains.
