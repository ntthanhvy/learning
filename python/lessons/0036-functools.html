functools: memoizing, freezing arguments, and folding

Day 12 already introduced the functools module once, for exactly one job: @functools.wraps, fixing a decorated function's lost __name__. That's still the same module — a small toolbox of higher-order functions, ones that take or return other functions, for jobs common enough that the standard library ships them instead of everyone hand-rolling their own. Today covers the three left unopened: lru_cache, which remembers a function's past results so it never redoes the same work twice, partial, which pre-fills some of a function's arguments to make a narrower, ready-to-call version, and reduce, which collapses a whole iterable down to a single value by combining elements two at a time.

Bridge from SQL: lru_cache is a query result cache — the same statement with the same parameters gets served from memory instead of hitting the engine again. reduce is a hand-rolled aggregate: SUM(), MAX(), and COUNT() are each one fixed way of combining rows into one value; reduce is what those are all built from, with the combining rule spelled out instead of picked from a short list of names.

1 · lru_cache: never redo the same call twice

A pure function — same arguments in, same result out, no side effects — that gets called repeatedly with arguments it has already seen is wasting work. functools.lru_cache is a decorator (Day 12's mechanism, applied here rather than built) that wraps a function with a cache keyed on its arguments:

from functools import lru_cache

calls = 0

@lru_cache(maxsize=None)
def slow_square(n):
    global calls
    calls += 1
    return n * n

slow_square(4)   # runs the real function: calls == 1
slow_square(4)   # same argument again: served from cache, calls stays 1
slow_square(5)   # new argument: runs for real, calls == 2
print(calls)                  # 2 — not 3
print(slow_square.cache_info())   # CacheInfo(hits=1, misses=2, maxsize=None, currsize=2)

Verified live against this course's interpreter: the third call above is a cache hit, and calls stops at 2. cache_info() reports hits/misses/maxsize/currsize directly from the running cache, and cache_clear() empties it — both useful for confirming a cache is actually doing something rather than assuming it. maxsize caps how many distinct argument combinations get remembered before the least-recently-used entry is evicted to make room (the "LRU" in the name); maxsize=None, used above, means unbounded — fine for a small, fixed set of inputs, risky for a function called with unboundedly many distinct arguments over a long-running process, since nothing ever gets evicted.

Not free, and not for everything. The cache is keyed on the exact arguments passed, so every argument to a cached function must be hashable (Day 31's rule again — a list argument raises TypeError, a tuple doesn't). And caching only helps a pure function: one whose result depends only on its arguments. Decorating a function that reads a clock, hits a database, or depends on mutable global state with lru_cache silently serves stale answers instead of speeding anything up correctly.

2 · partial: pre-filling arguments to make a narrower function

functools.partial takes a function plus some of its arguments and returns a new callable that already has those arguments baked in — calling the result only needs whatever is left:

from functools import partial

def power(base, exp):
    return base ** exp

square = partial(power, exp=2)   # exp is fixed at 2 from here on
square(5)                       # 25 — same as power(5, exp=2)
square(9)                       # 81

basetwo = partial(int, base=2)   # works on any callable, not just your own functions
basetwo("10010")                # 18 — same as int("10010", base=2)

Both calls verified live to return exactly those values. This is the same shape Day 4's key= functions and Day 27's itertools recipes lean on constantly: something expects a plain one- or few-argument callable — a sorted(key=...), a callback, an event handler — but the function that does the real work needs more arguments than that slot provides. Writing a one-line lambda x: power(x, exp=2) works too; partial is the same idea without a lambda, and it keeps the original function's name and the fixed arguments inspectable on the result (square.func, square.keywords) rather than hiding them inside a closure.

3 · reduce: collapsing an iterable to one value, by hand

functools.reduce(function, iterable, initial) applies a two-argument function cumulatively across an iterable, left to right, until only one value is left:

from functools import reduce

nums = [1, 2, 3, 4, 5]
total = reduce(lambda acc, x: acc + x, nums)
# (((( 1+2 )+3 )+4 )+5) == 15 — acc carries the running result forward each step

reduce without a third argument uses the iterable's first element as the starting acc — which is also why an empty iterable with no initial value raises TypeError (confirmed live: "reduce() of empty iterable with no initial value"). Pass a third argument and it becomes both the starting value and the result for an empty iterable, sidestepping that crash: reduce(lambda acc, x: acc + x, [], 100) returns 100 without ever calling the lambda.

This is the general mechanism — sum(), any(), all(), and max() are each one fixed, named combining rule; reduce is what runs underneath when the combining rule doesn't already have a name. That generality is also the usual objection to it: reduce(lambda acc, x: acc + x, nums) says less clearly what it does than sum(nums) does, and a plain for loop building up acc is often just as short and reads top-to-bottom instead of inside-out. Reach for reduce when the combining step is genuinely custom and there's no sum/max/any already spelling it — not as a reflex replacement for a loop that already reads fine. (Need every intermediate running total, not just the final one? That's itertools.accumulate — Day 27's module, not today's.)

Q: "When would you reach for lru_cache, partial, or reduce?" A strong answer, out loud: "lru_cache when a pure function — no side effects, same output for the same input — gets called repeatedly with arguments I've already seen, and I'd check cache_info() to confirm it's actually paying off rather than assuming it. partial when something expects a plain callable with fewer arguments than the function that does the real work takes — a sorted(key=...), a callback — so I don't need a throwaway lambda just to fix a couple of arguments. reduce only when the combining rule is genuinely custom; if it's a sum, a max, or an any/all check, I'd use the named built-in instead, because it says what it does more clearly than a reduce call with a lambda inside it." The signal: knowing reduce is a last resort, not a first instinct, and that lru_cache requires hashable arguments and a pure function to be safe.

Where pandas goes from here: pandas has its own vectorized reductions — .sum(), .agg(), .apply() — that operate across a whole column at once rather than one Python-level call per element; functools.reduce is the plain-Python, one-value-at-a-time mechanism those are built on conceptually, not something you'd reach for on a DataFrame. Not covered here; that's data/'s territory, and this is the only sentence in this lesson that names it.
