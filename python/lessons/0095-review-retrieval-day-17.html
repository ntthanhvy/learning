1 · Three questions, in the original teaching order

Answer each out loud or on paper before reading the fold-out answer. If one is shaky, note it and go fix it in the practice file below rather than only rereading the old lesson.

Day 92 — weakref. After r = weakref.ref(obj) and then del obj, what does calling r() return, and why doesn't holding r itself keep obj alive?

Fold-out answer: calling r() after del obj returns None, confirmed live — the object is collected the moment every strong reference to it is gone, and a weakref.ref never counts as one of those. Holding r only gives a way to ask "is it still alive, and if so, what is it" on demand; it adds no reference that the garbage collector would ever treat as a reason to keep obj around.

Day 93 — sqlite3. Why does a ? placeholder protect a query against SQL injection where building the same query with an f-string does not, and what does with con: actually do to the connection once the block ends?

Fold-out answer: a ? placeholder passes the value through a separate argument, and sqlite3 escapes it correctly as data no matter what it contains — a string like "Ada' OR '1'='1" is searched for literally, confirmed live, instead of changing what the query means the way pasting that same text into an f-string would. with con: only wraps the transaction — it commits on a clean exit or rolls back if an exception escapes — and does not close the connection; con is still fully open and usable for more queries right after the block ends.

Day 94 — ast.literal_eval. Why does ast.literal_eval("1 + 2") raise ValueError instead of quietly returning 3, and what's the difference between that failure and what ast.literal_eval("[1, 2,") raises instead?

Fold-out answer: literal_eval walks the parsed syntax tree and accepts only literal nodes — numbers, strings, bytes, True/False/None, and lists/tuples/dicts/sets built from those. 1 + 2 parses as a BinOp node, not a literal, so it's rejected with ValueError even though evaluating it would be completely harmless — the function checks syntax shape, not whether a result would be safe. "[1, 2," isn't valid Python syntax at all (an unclosed bracket), so parsing itself fails first and raises SyntaxError instead — a parseable-but-disallowed expression and genuinely broken syntax are two different failure shapes, and code calling literal_eval() on uncontrolled input should catch both.
Where pandas/NumPy go from here: nothing pandas- or NumPy-specific today — this review only revisits Days 92-94's object-lifetime mechanics, embedded-database SQL, and safe literal parsing, none of which needs a DataFrame or array to demonstrate.

2 · Why these three, and why no new terms today

Same interleaving logic as every prior review day: a tool for letting an object be collected even while something still points at it, a tool for running real SQL with no server to stand up, and a tool for parsing Python-literal text without ever risking code execution — three different mental models pulled from three lessons, not one idea restated three ways. They also share a quieter throughline worth naming: all three are about a program refusing to trust something by default — a cache refusing to assume it should keep an object alive just because it saw it once, a query refusing to assume a value is safe to paste into SQL text, a parser refusing to assume a disallowed-but-parseable expression is harmless just because the result looks numeric. Recognizing which of those three "don't assume it's safe" shapes a given problem actually needs — not just recalling the function names — is the retrieval goal today.
