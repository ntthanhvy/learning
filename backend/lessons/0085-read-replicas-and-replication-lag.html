Read replicas: why the same query can return different answers a moment apart

Lesson 39 explained how one Postgres instance shows two transactions two different, both-correct versions of the same row without either blocking — MVCC, all inside one process, one disk. Five lessons have said the word "replica" in passing since (a failover, a reserved connection slot, a wrong quiz answer) without ever explaining what it is. Today names it: a second full copy of your database, on its own machine, kept in sync by copying changes across the network instead of sharing a disk — and the one new fact that copying introduces: it takes time.

1 · One database, then two copies of it

Every lesson so far has quietly assumed one Postgres process holding the only copy of the data. A primary is that one instance, the only one allowed to accept writes. A read replica is a second, separate Postgres instance holding a copy of that same data, that only ever answers read queries. The primary continuously ships its stream of changes over the network to the replica, which replays them locally to stay current. Nothing here is a new storage engine — a replica is an ordinary Postgres instance, running the exact MVCC machinery Lesson 39 covered, just fed its rows from another Postgres instance's change stream instead of from its own clients' writes.

Why bother? A single primary has a ceiling on how many read queries it can serve before reads start competing with writes for the same CPU and I/O. Pointing report generation, analytics, and other read-heavy traffic at one or more replicas gets that load off the primary entirely, without touching a single line of query code — the query itself doesn't change, only which instance answers it.

2 · The one fact that copying over a network introduces

Inside one instance, Lesson 39's snapshot rule is exact and instantaneous — a transaction either sees a committed version or it doesn't, decided the moment it takes its snapshot. Between two instances, that certainty is gone: a write commits on the primary, then has to travel over the network and get replayed before the replica's copy reflects it. That gap has a name: replication lag. It's normally a handful of milliseconds — small enough to ignore for most reads — but it is never guaranteed to be zero, and it can grow under heavy write traffic, a slow network link, or a replica temporarily falling behind.

The classic bug this causes: a user submits a form (a write, routed to the primary), the page immediately re-fetches to show the result (a read, routed to a replica to save load), and the replica hasn't replayed that write yet. The user sees their own just-submitted data vanish for a moment — not a bug in the write, not a bug in the read, just replication lag made visible at the worst possible instant.

3 · The guarantee that has a name, and the one that doesn't

The property the bug above breaks is read-your-own-writes: the specific, minimal promise that you at least see your own recent writes, even if you might momentarily see stale data written by someone else. It's Lesson 84's eventual consistency applied one layer earlier than sagas — same shape (a real, observable window where two copies of the truth briefly disagree), but living between a primary and its own replicas instead of between two independent services with two independent databases.

4 · The routing decision this actually is

Using replicas safely is a per-query routing choice, not a database setting: send a query to the primary or to a replica depending on what the query needs to see.

// A read that just needs "recent enough" data -- a public product listing,
// a dashboard refreshed every few seconds -- is exactly what a replica is for.
rows, err := replicaPool.Query(ctx, "SELECT id, name, price FROM products WHERE active")

// A read that must reflect a write this same request just made -- "show the
// order I just placed" -- has to go back to the primary, or it can lose the
// read-your-own-writes guarantee and show the user their own action vanished.
row := primaryPool.QueryRow(ctx, "SELECT status FROM orders WHERE id = $1", orderID)

Nothing about the SQL differs — the same SELECT is valid against either instance. The only decision is which connection pool a given query goes through, made query by query based on whether that specific read can tolerate a small lag window or not.

Scope line: this lesson stops at the vocabulary and the routing decision, matching MISSION.md's explicit exclusion of "distributed systems beyond vocabulary level" — the same line Lesson 84 drew for sagas. Standing up replicas, tuning replication itself, or handling a primary failing over to a promoted replica (Lesson 47 named that failover moment already, without explaining it) is operations work this course doesn't cover.

Q: "Your team wants to point read-heavy dashboard queries at a read replica to reduce load on the primary. What would you watch out for?" A strong answer, out loud: "The replica is a real Postgres instance running the same MVCC engine as the primary, just fed a stream of the primary's committed changes over the network instead of taking writes directly — so any query that's fine reading data that's a few milliseconds old is a good candidate. What I'd watch for is replication lag: if a user just wrote something and the very next request reads it back, and that read happens to land on a replica that hasn't replayed the write yet, they'll see their own change appear to vanish. I'd route anything that needs read-your-own-writes back to the primary explicitly, and only send replicas the reads that can genuinely tolerate a small lag window, like a dashboard or a public listing page." The signal: naming replication lag as the actual mechanism, not just "replicas can be stale," and knowing which specific reads are and aren't safe to route away from the primary.
