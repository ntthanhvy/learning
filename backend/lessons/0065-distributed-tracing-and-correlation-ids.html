Distributed tracing: one request ID, many services

Lesson 13 gave every log line a request_id and called it "the bridge that lets a support ticket be matched back to the exact server-side log entries" — but that bridge only spans one service's own logs. Lesson 64 closed naming distributed tracing as the standing next topic. Today: what happens to that same id once Lesson 31's world shows up — one request that fans out across several backends you operate — and why plain per-service logs stop being enough once it does.

1 · One request, several services, one story to reconstruct

Lesson 8 established that "the server" stops being one process the moment a second instance exists. Lesson 31 went further: a single user action — say, placing an order — often triggers your order service to call your billing service, which calls a payment provider, while a separate call goes to your inventory service. Four processes, four separate log streams, each written by a service that has no idea the other three even exist. If the payment call fails, "why did this order fail?" is really four questions across four log files, and nothing so far has said how to find the right four lines out of millions written that same minute.

Lesson 13's request_id already solved this shape of problem — inside one service. A correlation ID is exactly that value; the only change needed is to stop treating it as private to the service that minted it, and start treating it as something that travels with the request everywhere the request goes.

2 · Generate at the edge, or keep one you're handed

The rule is simple and has exactly one branch: the first service to see a request — the one sitting at the edge, directly facing the client — checks whether an inbound request already carries an id (a mobile app or another company's system might set one); if not, it generates a fresh one. Every service downstream of that first one does the opposite: it never generates its own id for a request that already has one. It reads the id it was handed, uses that same value in its own logs, and passes that same value on again to whatever it calls next. One id, minted once, threaded through the entire call graph unchanged.

Not a new concept — a wider radius. Nothing above changes what a correlation ID is. It changes where it's allowed to travel: out of one process's log lines, across an HTTP call, into another process's log lines, as many times as the call graph requires.

3 · The carrier inside one process: context.Context

Lesson 41 named the exact mechanism for this without spelling out the example: "small pieces of request-scoped metadata a whole call chain needs to see... attached once at the edge with context.WithValue and read by the logging middleware three layers down without every function in between needing it threaded as its own parameter." A correlation ID is the canonical case that sentence was written for. It gets attached to the context.Context once, in the first middleware that touches the request, and every function further down the call chain — the handler, the service layer, the code that eventually makes an outbound HTTP call — pulls it back out of the same context it already receives as its first parameter, no extra plumbing required.

4 · The carrier between processes: an HTTP header

context.Context only survives inside one running process — it cannot cross a network call by itself. So the moment a service makes an outbound HTTP request to another service, the correlation ID has to be pulled back out of the context and written onto that outbound request as a header, most simply X-Request-ID. The receiving service's own edge middleware reads that same header on the way in, and the cycle in section 2 repeats one hop further out: it already has an id, so it keeps it, attaches it to its own context, and logs with it.

// requestIDKey is the context.Context key; an unexported type prevents
// collisions with keys set by other packages (the exact risk Lesson 41
// flagged for WithValue misuse).
type ctxKey string

const requestIDKey ctxKey = "request_id"

// withRequestID is edge middleware: keep an inbound id if one arrived,
// otherwise mint a fresh one, then store it on the context for every
// handler and downstream call in this request's chain to read back.
func withRequestID(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        id := r.Header.Get("X-Request-ID")
        if id == "" {
            id = uuid.NewString()
        }
        ctx := context.WithValue(r.Context(), requestIDKey, id)
        w.Header().Set("X-Request-ID", id) // echo it back, per Lesson 13's client-visible bridge
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}

// chargeCard is deep in the call chain: it never received requestID as an
// explicit argument, only ctx, and still logs and forwards the same id.
func chargeCard(ctx context.Context, logger *slog.Logger, amountCents int) error {
    requestID, _ := ctx.Value(requestIDKey).(string)
    logger.Info("calling billing service", "request_id", requestID, "amount_cents", amountCents)

    req, err := http.NewRequestWithContext(ctx, http.MethodPost,
        "https://billing.internal/charges", nil)
    if err != nil {
        return fmt.Errorf("build billing request: %w", err)
    }
    req.Header.Set("X-Request-ID", requestID) // carries the id across the network hop

    resp, err := http.DefaultClient.Do(req)
    if err != nil {
        return fmt.Errorf("call billing service: %w", err)
    }
    defer resp.Body.Close()
    if resp.StatusCode != http.StatusOK {
        return fmt.Errorf("billing service returned %d", resp.StatusCode)
    }
    return nil
}

Every piece here is a lesson already taught, applied to a new radius: context.WithValue for the in-process carry (Lesson 41), a structured logger.Info call with a stable field (Lesson 13), and an outbound call authenticated the way Lesson 31 described — the correlation ID header sits alongside whatever service-to-service auth mechanism that lesson picked, not instead of it. A correlation ID proves nothing about identity; it only answers "which request was this."

6 · Where this grows into full distributed tracing

A single correlation ID answers "which log lines, across every service, belong to this one request" — and for most debugging that's already the win. It does not, by itself, show the shape of the call graph: which calls ran in parallel, which ran one after another waiting on the last, or how long each hop actually took relative to the others. Distributed tracing is the generalization that adds that shape: alongside one shared trace id (playing the same role as the correlation ID above), each individual unit of work — one HTTP call, one DB query, one function doing real work — gets its own span with its own start and end time and a pointer to whichever span called it. Collect enough spans sharing one trace id and a tracing backend — Jaeger and tools built on the vendor-neutral OpenTelemetry standard are the common choices today — can render the whole thing as a timeline: which service took 800ms of a 900ms request, and whether that 800ms was one slow call or ten calls run one after another that could have run in parallel instead.

None of that changes the propagation mechanism already shown above — a trace id still rides in context.Context inside a process and in a header (commonly the W3C's standardized traceparent header) between processes, exactly like the correlation ID in section 4. Full tracing is strictly more machinery for the same underlying idea: don't let a request's identity stop at a process boundary. This course stops at that concept-level understanding; wiring an actual OpenTelemetry SDK into a Go service is implementation detail for whenever a real system's debugging pain justifies adopting one.

Q: "A checkout request touches four of our services and one call is failing intermittently — how would you debug it?" A strong answer, out loud: "First thing I'd check is whether a correlation ID is actually propagating across all four — generated once at the edge, carried through context.Context inside each service, and forwarded as a header like X-Request-ID on every outbound call between them. If it is, I can grep that one id across all four services' logs and see exactly where the chain breaks, instead of correlating by rough timestamp. If it isn't propagating consistently, that's the first fix, before anything else — without it, four independent log streams are close to unreadable together. If the team needed to see relative timing across the hops too, not just 'which lines belong together,' that's the point where I'd bring up proper distributed tracing with spans, but the correlation ID alone usually answers 'what happened' well before that's necessary." The signal: reaching for the shared id first, and knowing the difference between "which lines belong to this request" (correlation ID) and "how long did each hop take relative to the others" (full tracing).
