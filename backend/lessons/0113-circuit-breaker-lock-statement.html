Circuit breaker, now in C# too

Lesson 112's own closing note named exactly one carried-over candidate: a circuit breaker's C# shape, the same kind of ecosystem-mirror gap Lesson 112 just closed for retry-with-backoff. Lesson 28 taught the full state machine in Go; today ports it to C#. The state machine doesn't change. One rule about where a lock is allowed to go, does.

1 · Same breaker, same three states — Lesson 28 already covers why

Nothing about why a circuit breaker exists changes between languages. Lesson 28 covers the full reasoning: a struggling dependency turns every naive retry into a pool exhaustion problem, and that is how one dependency's cascading failure becomes an outage of everything that calls it. The fix is still the same three-state machine — closed lets calls through and counts failures, open fails every call immediately for a cooldown instead of waiting out a timeout, and half-open lets exactly one probe through once the cooldown elapses. None of that is re-derived here; today is about what changes, and what doesn't, when the same state machine is written in C#.

2 · The state is still shared across every caller, so it still needs a guard

A circuit breaker's state — which of the three states it's in, how many consecutive failures it has counted, when it last tripped open — gets read and written on every single call through the breaker, and in a real service those calls happen concurrently. Go's version in Lesson 28 guarded that shared state with sync.Mutex; C# needs exactly the same guard for exactly the same reason — two concurrent callers checking and updating a failure counter at the same instant, unguarded, is a race condition no matter which language is doing it. C# reaches for the lock statement for this, not the Mutex class — per Microsoft's own class description, Mutex "can also be used for interprocess synchronization," i.e. coordinating separate processes or even separate applications, which is overkill for guarding a few fields inside one object within a single process.

3 · A minimal C# implementation

Same three fields Lesson 28's Go struct had — state, failure count plus threshold, and when it opened — plus the object the lock statement guards:

enum BreakerState { Closed, Open, HalfOpen }

class CircuitBreaker
{
    private readonly object gate = new();
    private BreakerState state = BreakerState.Closed;
    private int consecutiveFails;
    private readonly int failureThreshold;
    private readonly TimeSpan openTimeout;
    private DateTimeOffset openedAt;

    public CircuitBreaker(int failureThreshold, TimeSpan openTimeout)
    {
        this.failureThreshold = failureThreshold;
        this.openTimeout = openTimeout;
    }

    public async Task<T> CallAsync<T>(Func<Task<T>> operation)
    {
        if (!Allow())
            throw new InvalidOperationException("circuit open"); // fails in microseconds — no call attempted

        try
        {
            var result = await operation(); // no lock held anywhere near this line
            RecordResult(success: true);
            return result;
        }
        catch
        {
            RecordResult(success: false);
            throw;
        }
    }

    private bool Allow()
    {
        lock (gate)
        {
            switch (state)
            {
                case BreakerState.Closed:
                    return true;
                case BreakerState.Open:
                    if (DateTimeOffset.UtcNow - openedAt < openTimeout)
                        return false; // still cooling down
                    state = BreakerState.HalfOpen; // timeout elapsed — allow one probe
                    return true;
                default: // HalfOpen
                    return false; // a probe is already out; block the rest
            }
        }
    }

    private void RecordResult(bool success)
    {
        lock (gate)
        {
            if (success)
            {
                consecutiveFails = 0;
                state = BreakerState.Closed; // success (incl. the probe) fully resets
                return;
            }
            consecutiveFails++;
            if (state == BreakerState.HalfOpen || consecutiveFails >= failureThreshold)
            {
                state = BreakerState.Open;
                openedAt = DateTimeOffset.UtcNow;
            }
        }
    }
}

Every call to the dependency goes through breaker.CallAsync(() => CallInventoryServiceAsync(sku)) instead of calling it directly — same shape as Go's cb.Call(fn). Allow() is the gate, RecordResult is what actually moves the state, and CallAsync itself is the only place that ever awaits anything.

This isn't a style choice — the compiler enforces it. Per Microsoft's own language reference for the lock statement: "You can't use the await expression in the body of a lock statement." A plain lock desugars to Monitor.Enter paired with Monitor.Exit in a try/finally, and a monitor is tied to the thread that acquired it; suspending mid-await and resuming on a different pooled thread would leave that pairing broken, so the compiler refuses to let the two mix at all. That's why Allow() and RecordResult() are each their own small, synchronous, fully-locked method, and the await operation() line in CallAsync sits with no lock held anywhere near it. Go's version in Lesson 28 made the identical split — allow() and recordResult() each lock separately, fn() runs unlocked in between — but that was a deliberate design choice, not something go build would have rejected otherwise. C# just turns the same good habit into a compile error if you skip it.

4 · What the caller does when the circuit is open hasn't changed either

A breaker still only solves half the problem: failing fast instead of failing slow. The caller still has to decide what to return while the circuit is open — Lesson 28's fallback question, unchanged by language: a cached value that might be slightly stale, a "check back shortly" response, or an honest error returned immediately rather than after a timeout. That's a product decision in C# exactly as much as it was in Go.

Scope line

This lesson covers porting Lesson 28's circuit breaker (the closed/open/half-open state machine, why cascading failure makes blind retries worse, the fallback decision) to C#, plus the one genuinely new rule this port surfaces: a C# lock statement cannot contain an await, which is why the state-mutating methods stay separate, small, and synchronous. It does not re-derive the three states, cascading failure, or the rate-limiter-vs-breaker comparison — Lesson 28 already covers all three in full and nothing about them changes in C#. It does not cover Polly or any .NET resilience library's packaged breaker — the mechanism is taught here from first principles, same as Lesson 28 did in Go, per MISSION.md's "concepts first" rule.
