1 · Six questions, in the original teaching order

Answer each out loud or on paper before reading the fold-out answer. If one is shaky, note it and go fix it in the practice file below rather than only rereading the old lesson.

Day 15 — logging. A log call passes an f-string as the message, versus %s-style formatting with the value as a separate argument. Why does that choice matter for a DEBUG-level call in a program running at WARNING level?

Fold-out answer: an f-string is fully built before logging ever sees it, so the formatting cost is paid even if the record never clears the WARNING threshold and gets thrown away. %s-style formatting passes the raw value separately, and logging only interpolates it if the record actually clears the handler's level — so an expensive-to-format DEBUG message costs nothing at all when DEBUG output is filtered out, while the f-string version already paid the full cost regardless.

Day 28 — unpacking. header, *rows = lines peels one item off the front of a list. What type is rows afterward, and what happens if lines has only one element total?

Fold-out answer: rows is always a list, even if only zero or one items are "left over" — star-unpacking doesn't require any minimum count on its own side, it just collects however many remain. With a one-element lines, header gets that single item and rows comes back as an empty list, not an error — the exact-count ValueError rule only applies to the non-starred names, not the starred one.

Day 29 — writing a context manager. A hand-written __exit__ method has no explicit return statement at all. What happens to an exception raised inside that with block?

Fold-out answer: it propagates normally. A function with no return statement returns None, which is falsy — and __exit__ only suppresses an in-flight exception when it returns something truthy. Falling off the end silently is exactly equivalent to writing return False, so omitting return is safe here, not a bug, though writing return False explicitly is more obviously intentional to a reader.

Day 35 — __slots__. Base declares __slots__ = ("a",) and Child(Base) declares no __slots__ of its own. Does Child still get the memory and typo-safety benefit?

Fold-out answer: no — silently. A subclass that doesn't declare its own __slots__ gets a real instance __dict__ back, even though its parent declared slots, and nothing announces that the benefit is gone. The fix is for Child to declare its own __slots__ too, listing only the new fields it adds (not a, which already lives in Base's slots) — every class in the inheritance chain has to opt in separately.

Day 37 — descriptors. property and a plain @staticmethod are both descriptors. Which one wins when an instance's own __dict__ has an entry under the same attribute name, and why?

Fold-out answer: property wins, always, because it's a data descriptor — it defines both __get__ and __set__, and data descriptors are checked before the instance's own __dict__ in the attribute lookup order. A @staticmethod is a non-data descriptor — __get__ only, no __set__ — so a same-named instance __dict__ entry is found first and wins instead. That asymmetry is exactly what makes a validated @property setter impossible to bypass by writing straight into self.__dict__.

Day 40 — contextlib. Why can't a fixed with a, b, c: chain handle "close however many files happen to be in this list," and what closes them in the right order when the count is only known at runtime?

Fold-out answer: with a, b, c: requires every name to be written directly in the source, so the count is fixed at write time — there's no syntax for "however many, decided later." contextlib.ExitStack() solves it: call stack.enter_context(cm) once per item in a runtime-built list, and ExitStack guarantees every one of them gets __exit__ called, in reverse order of opening, even if the block raises partway through — the same all-or-nothing guarantee a fixed chain gives, just for a count decided at runtime.

2 · Closing the gap: string and textwrap, in one paragraph each

Two small stdlib corners were flagged as unexplored since Day 53's next-day note and confirmed still untaught by today's grep — thin enough for an aside rather than their own lesson, but worth naming so the gap actually closes. The string module is mostly a handful of ready-made character-class constants — string.ascii_letters, string.digits, string.punctuation — handy as the alphabet for random.choice()-based token generation (Day 54) instead of typing out "abcdefg..." by hand; most of its historical string-manipulation functions moved onto plain str methods (.strip(), .split(), .join()) long before this course started, which is exactly why it's never come up. The textwrap module reflows plain text to a fixed width — textwrap.fill(text, width=30) wraps a long string into multiple lines at word boundaries, textwrap.shorten(text, width=25, placeholder="...") truncates with a marker instead of cutting mid-word, and textwrap.dedent(text) strips a shared leading-whitespace prefix off every line — useful for a multi-line string written indented inside a function body, matching the surrounding code's indentation rather than starting at column zero.

import string, textwrap

print(string.ascii_letters[:10])   # 'abcdefghij'
print(string.digits)             # '0123456789'

print(textwrap.fill(
    "This is a long sentence that needs wrapping to a narrower width.",
    width=30,
))
# This is a long sentence that
# needs wrapping to a narrower
# width.

Both snippets above were run standalone before writing this paragraph, confirming the exact output shown.
