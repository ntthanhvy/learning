1 · The gap Day 21 named and deliberately left open

Day 21 built the real mechanics of an Asset-scheduled DAG — a task with outlets=[order_events_asset] firing an asset event on success, and a separate DAG scheduled by schedule=[order_events_asset] instead of a cron string — and proved the link was real by reading a row out of Airflow's own asset_event table. But it left check_order_events_grew's body as a bare ..., with a comment naming the exact risk out loud: an outlets= task fires its asset event on success, not on "did the data really change." A task that always returns without raising would mark the asset updated — and trigger dbt_build_on_events — every ten minutes, whether or not Kafka's consumer actually landed a single new row since the last check. That's not a hypothetical: Day 21's own schedule for order_events_landed is "*/10 * * * *", so a no-op "always succeed" version of this task would run dbt build against the warehouse 144 times a day for a stream that might see long quiet stretches overnight.

Fixing it needs exactly one thing Day 21 didn't reach for: somewhere to remember what the count was last time, so this run can compare against it. That's a one-row, one-number piece of state that lives in Airflow itself, not in the data warehouse — a job for Day 22's Variable, used today not as read-only config but as a tiny cursor a task reads from and writes back to on every single run.

2 · Why a Variable, and not Day 20's XCom

Day 20 drew a sharp line: XCom is for passing a small value between tasks inside one DAG run, and it is explicitly not a data transport for anything larger or longer-lived. A growth cursor is a different shape of problem — the same single task, in different DAG runs ten minutes apart, needs to read a value one of its own past runs wrote. XCom is keyed by (dag_id, task_id, run_id) by default, so reading "the previous run's XCom" from inside a running task means reaching across runs, which is exactly the kind of workaround that signals the wrong tool. A Variable has no run boundary at all — it's a single named value living in Airflow's metadata database, visible to any task in any DAG that asks for it by key, which is precisely "small persistent state that outlives one run" and nothing more.

from airflow.sdk import Variable

Variable.set("order_events_last_count", "42")
print(Variable.get("order_events_last_count", default="0"))

A real naming gotcha caught this round by actually calling it, not by assuming: the keyword that supplies a fallback for a missing key is default on the pinned apache-airflow==3.3.1's airflow.sdk.Variable.get() — not default_var, which several older Airflow 2.x blog posts and even some still-cached doc snippets use, and which raises a plain TypeError: Variable.get() got an unexpected keyword argument 'default_var' on this install, confirmed by calling it both ways against the real installed signature (inspect.signature(Variable.get) prints (key: 'str', default: 'Any' = NOTSET, deserialize_json: 'bool' = False)). That fallback matters for a cursor's very first run — no prior value has ever been written, and the task must not crash on a missing key, it must treat "never run before" as "last count was zero." Day 22 already surfaced the sharper gotcha this task depends on getting right: Variable.get() always returns a plain str, never an int, unless deserialize_json=True is passed. A first draft that writes Variable.set("order_events_last_count", new_count) (an int) and later compares Variable.get(...) > last_count without casting both sides to int first will compare a str to an int and raise TypeError the moment it actually runs — not on import, which is why Day 21's own DAG-parse checks never would have caught it.

3 · Build: finish check_order_events_grew

Replace the TODO body inside dags/order_events_landed.py (the file Day 21 built — only this one task's body changes, nothing else in that file or in dbt_build_on_events.py):

from __future__ import annotations

from datetime import datetime

import psycopg
from airflow.sdk import DAG, Asset, Variable, task

order_events_asset = Asset("postgres://fdp/raw.order_events")
PG_DSN = "host=localhost dbname=fdp user=fdp password=fdp"  # same DSN as Day 6's consumer
CURSOR_KEY = "order_events_last_count"

with DAG(
    dag_id="order_events_landed",
    schedule="*/10 * * * *",
    start_date=datetime(2026, 9, 21),
    catchup=False,
) as dag:
    @task(outlets=[order_events_asset])
    def check_order_events_grew() -> int:
        with psycopg.connect(PG_DSN) as conn, conn.cursor() as cur:
            cur.execute("SELECT count(*) FROM raw.order_events")
            current_count = cur.fetchone()[0]

        last_count = int(Variable.get(CURSOR_KEY, default="0"))

        if current_count <= last_count:
            # No growth since the last check: raise, so this task is marked
            # failed and outlets=[order_events_asset] never fires. A no-op
            # *success* here would trigger dbt_build_on_events every ten
            # minutes regardless of whether Kafka delivered anything new --
            # the exact risk Day 21's own comment named and left unbuilt.
            raise ValueError(
                f"no growth: {current_count} <= last checked {last_count}"
            )

        Variable.set(CURSOR_KEY, str(current_count))
        return current_count

    check_order_events_grew()

Two choices worth defending out loud, because both are easy to get wrong in a way that still parses and still runs. First, raising on no-growth rather than returning early with no asset-firing side effect: Airflow's outlets= mechanism fires strictly on task success, with no API for "succeeded but don't count it" — so "don't fire the asset" and "fail the task" are the same lever here, and a monitoring dashboard built later (Day 27's data-quality story) needs to know this DAG's expected failure rate is not zero, it's "however many ten-minute windows see no new orders," most likely every night. Second, writing the Variable after the growth check and not before: if this task raises, the cursor must stay at its old value, so the next run still compares against the last real count that grew — writing it unconditionally near the top would silently erase the ability to ever detect growth across a no-growth run.

This task's own correctness has nothing to do with Postgres or psycopg syntax — Day 6 already established that exact connection shape. The entire day's real skill is the cursor: read it as an int with a safe default, compare, raise instead of silently succeeding on no-growth, and only then overwrite it. Get that sequencing wrong and the DAG still parses, still runs, and still looks fine in the UI right up until someone checks whether dbt_build_on_events is actually running on every single schedule tick rather than only when data grew.

Q: "Your data-aware DAG checks every ten minutes. How do you stop it from triggering downstream work when nothing actually changed?" A strong answer, out loud: "Airflow's outlets= fires on task success, full stop — there's no 'succeeded but don't count it' option. So the task itself has to make 'no real change' a failure, not a successful no-op. I store the last-seen row count in an Airflow Variable, compare it against the current count on every run, and raise instead of returning if nothing grew — only on real growth do I update the stored cursor and let the task succeed, which is the only way outlets actually fires. The subtle bug to avoid is that Variable.get() always returns a string, so comparing it directly to an int silently does the wrong thing instead of crashing where you'd notice — I cast it explicitly on the way in." The signal: naming outlets' success-only semantics as the root constraint, not just "I added an if statement."
