1 · Six questions, in the original teaching order

Answer each out loud or on paper before reading the fold-out answer. If one is shaky, note it and go fix it in the practice file below rather than only rereading the old lesson.

Day 8 — exceptions. Why should a real except clause name an exact exception type, like except ValueError:, instead of a bare except:?

Fold-out answer: a bare except: catches literally everything — a typo'd variable name (NameError), a genuine bug elsewhere in the code, even KeyboardInterrupt — and silently turns all of them into the same quiet no-op, hiding real bugs behind whatever "recovery" code was meant for one specific, expected failure. Naming the exact type catches only what was actually planned for and lets everything else propagate loudly, where it can be noticed.

Day 11 — pytest. Inside a @pytest.fixture function that does yield some_value, what runs the code written after the yield, and when?

Fold-out answer: that code is teardown, and pytest itself runs it once the test using that fixture finishes — success or failure, the same always-runs guarantee Day 6's context-manager __exit__ and Day 8's finally both already made. Code before yield is setup, run once per test that names the fixture; code after it never runs until that one test is fully done.

Day 17 — pydantic models. A pydantic BaseModel field is typed price: float, and it's constructed with price="12.5" (a string). What happens, and is that the same thing a @dataclass would do?

Fold-out answer: pydantic coerces the string into a real float — 12.5, type float — because that conversion is safe and unambiguous; a @dataclass would instead store the string "12.5" completely unchanged, since Day 7 already established that type hints are documentation only and Python never enforces them at runtime. Same field, same hint, very different behavior at construction time.

Day 24 — ASGI middleware. A route raises an exception that has a registered @app.exception_handler. Does a middleware function's own try/except around await call_next(request) ever see that exception?

Fold-out answer: no. The exception handler resolves the exception into a finished Response before call_next() ever returns to middleware — so middleware only ever sees a normal, completed response, never the exception itself. Middleware that wants the request's true final status code should read response.status_code unconditionally after call_next() returns, not rely on a try/except that a handled exception will never reach.

Day 32 — @classmethod/@staticmethod. Why does a @classmethod alternative constructor call cls(...) instead of hardcoding the class's own name, like Money(...)?

Fold-out answer: so that a subclass inheriting the method unmodified still builds an instance of itself when called through the subclass, instead of always hardcoding back to the parent class. cls is whichever class the method was actually called through — the same idea behind stdlib alternative constructors like dict.fromkeys(...) and datetime.fromtimestamp(...).

Day 41 — typing extras. A class never inherits from a given Protocol and never imports it. Can it still satisfy that Protocol for a type checker?

Fold-out answer: yes — a Protocol is structural typing, not inheritance-based. Any class whose methods and signatures happen to match is considered to satisfy it, with zero coupling to the Protocol itself — confirmed in Day 41 with an Employee class that never mentions the Named protocol at all, yet still type-checks as one wherever Named is expected.
