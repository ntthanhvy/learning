groupby().apply() and multi-function .agg(): when built-in aggregations aren't enough

Lesson 4 covered .agg() with named aggregation and Lesson 55 used .agg({...}) with multiple functions per column in passing (in service of add_prefix()), but neither taught the dict-of-list shape as its own topic, and no lesson has covered groupby().apply() at all. Today closes both gaps: the multi-function .agg() pattern for stacking several built-in stats on one column, and .apply() for the harder case — a custom per-group calculation that .agg() genuinely cannot express.

1 · Multiple functions per column: .agg({col: [funcs]})

Lesson 4's .agg() took one function per column (via a plain dict or named aggregation). Give a column a list of function names instead, and every one of them runs on that column, all in a single pass over the data:

df2.groupby("customer").agg({"amount_clean": ["sum", "mean"], "order_id": "count"})
--           amount_clean         order_id
--                    sum    mean    count
-- customer
-- An                162.0   81.00        3
-- Binh              215.5  107.75        2
-- Chi                99.9   99.90        1

Confirmed directly against this course's real orders_raw.csv (coerced the same way as Lessons 2-4): mixing a list-of-functions column with a single-function column in the same dict works fine, and the result grows a two-level MultiIndex on the columns — one level names the source column, the other names the function that produced it. That's the same output shape Lesson 55 flattened with add_prefix()-adjacent tricks; the plain fix reached for most often is joining the levels by hand:

result = df2.groupby("customer").agg({"amount_clean": ["sum", "mean"], "order_id": "count"})
result.columns = ["_".join(c) for c in result.columns]
-- columns become: amount_clean_sum, amount_clean_mean, order_id_count

SQL bridge: this is exactly SELECT customer, SUM(amount), AVG(amount), COUNT(order_id) FROM orders GROUP BY customer — one SELECT, several aggregate expressions, same idea as naming several functions in one .agg() call instead of running three separate groupby()s.

2 · The wall .agg() hits: one function, one column, at a time

Every function .agg() accepts — built-in name or custom callable — receives one column's values for the group and returns one scalar. That's fine for "sum of amount" or "count of orders," but breaks down the moment the calculation needs to look at several columns of the same group together, or return more than one value from one pass over the group. Confirmed directly: a function that needs two columns at once from the same group has no clean home inside .agg()'s per-column contract.

3 · groupby().apply(): handing pandas a whole group at a time

groupby().apply(func) hands the whole per-group table to a custom function — every column, not just one — and combines whatever comes back:

def revenue_range(g):
    return g["amount_clean"].max() - g["amount_clean"].min()

df2.groupby("customer").apply(revenue_range, include_groups=False)
-- customer
-- An       78.0
-- Binh    144.5
-- Chi       0.0
-- dtype: float64

Confirmed directly: include_groups=False is required in this pandas version (3.0.5) to drop the grouping column from what the function receives — passing include_groups=True explicitly now raises ValueError: include_groups=True is no longer allowed outright, not merely a warning, so the grouping column is never silently re-included inside the function's view of the group.

The real payoff shows up once the custom function needs more than one column and returns more than one value — the exact shape .agg() cannot express:

def range_and_count(g):
    return pd.Series({
        "range": g["amount_clean"].max() - g["amount_clean"].min(),
        "n_orders": len(g),
    })

df2.groupby("customer").apply(range_and_count, include_groups=False)
--           range  n_orders
-- customer
-- An         78.0       3.0
-- Binh      144.5       2.0
-- Chi         0.0       1.0

Confirmed directly: returning a pd.Series from the function (one entry per desired output column) makes .apply() combine the per-group results into a DataFrame with those names as columns — len(g) reaches every row of the group directly, and g["amount_clean"].max() - g["amount_clean"].min() reads the same column twice in one pass, both impossible to express as a single named function inside .agg()'s dict.

4 · The cost: apply() is a Python-level loop, agg() usually isn't

This power has a price. Built-in .agg() function names ("sum", "mean", "count") run vectorized, compiled code across the whole column at once. groupby().apply() calls the Python function once per group, in a real Python-level loop under the hood — the exact cost Lesson 1's "think in tables, not loops" opened this course by warning against. The rule of thumb worth saying out loud in an interview: reach for .agg() (or .transform(), Lesson 16, when the shape needs to stay row-per-row) whenever a built-in or simple per-column function covers it, and drop to .apply() only when the calculation genuinely needs several columns of the same group together or a shape .agg() cannot produce.

5 · SQL bridge

.agg({"amount": ["sum", "mean"]}) is SELECT customer, SUM(amount), AVG(amount) FROM orders GROUP BY customer — plain aggregate functions, no procedural code needed. groupby().apply() has no clean SQL equivalent at all; the nearest real-world parallel is a stored procedure or a window-function-heavy CTE that computes several related values per partition in one procedural pass — the kind of per-group logic SQL pushes into either a UDF or a much longer query, and pandas expresses directly as an ordinary Python function.

6 · Why this earns its keep in an interview

"Give me the range of order values per customer" or "return the top N rows per group" are common follow-ups once the basic groupby().sum() answer lands — and both need .apply() (or nlargest() chained per group), not a one-line .agg(). Knowing the exact boundary — one column in, one scalar out for .agg(); whole group in, anything out for .apply() — signals real pandas fluency rather than pattern-matching from memorized snippets, and naming the performance tradeoff unprompted (vectorized vs. a per-group Python loop) is the senior-level version of that same answer.

Q: "How would you get, per customer, the difference between their highest and lowest order amount?" A strong answer, out loud: "That needs two values from the same column of the same group at once — max minus min — which `.agg()` can't do in one named function, so I'd reach for `groupby('customer').apply()` with a small function that takes the whole group's DataFrame and returns `g['amount'].max() - g['amount'].min()`. I'd pass `include_groups=False` so the grouping column itself doesn't leak into the function's view. It's slower than a built-in `.agg()` call since it's a real per-group Python loop under the hood, but for logic this specific there's no vectorized shortcut." The signal: knowing exactly where `.agg()`'s one-column-one-scalar contract ends and naming the performance tradeoff instead of treating `.apply()` as a free upgrade.
