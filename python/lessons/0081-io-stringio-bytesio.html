io.StringIO & io.BytesIO: a file-shaped object with no file on disk

Day 6's csv.reader(f) and Day 76's json.load(f) both expect f to be something with .read()/.write() — not necessarily a real file on disk. Day 15's logging practice already leaned on this once, quietly, to capture log output without touching the filesystem, but never named or taught the tool doing the work. The io module's StringIO and BytesIO are that tool: a value that behaves exactly like an open file to any code expecting one, without ever touching disk.

Why today, specifically: a fresh-gap grep across all 80 lessons and every practice file found zero hits for StringIO/BytesIO as a taught topic — the only two prior mentions are Day 15's practice file, which builds a logging.StreamHandler(io.StringIO()) purely as an invisible test fixture with no explanation in the lesson text, and the standing "worth a look" note carried across several review-day gap scans (Days 56, 68) that never won out against a stronger competing module. It is a genuine, clean gap, and it is squarely in scope: MISSION.md's pipeline goal is reading/writing CSV and JSON, and every format-handling lesson so far (Days 6, 66, 76) has assumed the data source is either a real file or an in-memory string/list — StringIO/BytesIO is the missing bridge between those two, letting a function written for files be tested, or reused, without disk I/O at all.

1 · The problem: a function written for files, tested without one

Suppose a function expects an already-open file object — exactly the shape csv.writer() and json.dump() both want:

import csv

def write_rows(f, rows):
    writer = csv.writer(f)
    for row in rows:
        writer.writerow(row)

Testing this for real means creating a temp file (Day 65's tempfile), writing to it, closing it, reopening it to read the result back, then deleting it — four extra steps around the one line actually being tested. csv.writer() never asked for a file specifically; it asked for anything with a .write() method that takes a string. io.StringIO is exactly that, held entirely in memory:

import io, csv

buf = io.StringIO()
write_rows(buf, [["name", "qty"], ["bolt", 10]])
print(buf.getvalue())
# 'name,qty\r\nbolt,10\r\n' -- the exact text that would have been written to a real file

write_rows() itself needed zero changes — it never knew its f wasn't a real file. .getvalue() is StringIO's own method for reading back everything written so far, as a plain str, with no open()/close()/temp-path bookkeeping anywhere.

(The \r\n in that output is Day 66's csv dialect doing its normal line-ending job, same as it would write to a real file — StringIO changed nothing about csv's own behavior, only where the bytes end up.)

2 · Reading, not just writing: StringIO as an input

StringIO works the other direction too — construct it with text, and anything that reads from a file reads that text instead:

import io, csv

text = "name,qty\nbolt,10\nnut,25\n"
reader = csv.reader(io.StringIO(text))
print(list(reader))
# [['name', 'qty'], ['bolt', '10'], ['nut', '25']]

This is the same pattern Day 6's csv.reader(f) used on a real open file — csv.reader() only ever needed something it could iterate line by line, and a StringIO wrapping a string satisfies that exactly like a file does. Useful whenever test data, or data that already arrived as a string (an HTTP response body, a string pulled from a database column), needs to go through file-shaped parsing code unchanged.

Bridge from SQL: this is the same idea as a SQL view over a derived table — the consuming query doesn't know or care that the "table" isn't a real stored one. StringIO is a view over a string that lets file-shaped code run against it as if it were a real file.

3 · BytesIO: the same idea for bytes, not text

StringIO holds str; BytesIO holds bytes — needed for binary formats like a zip archive (Day 64), a pickle stream (Day 72), or image data, none of which are valid text:

import io

buf = io.BytesIO()
buf.write(b"hello")
buf.write(b" world")
print(buf.getvalue())   # b'hello world'

buf.seek(0)             # rewind to the start -- same seek() a real binary file supports
print(buf.read())      # b'hello world' -- read from the current position, now position 0

.seek(0) is the detail that trips people up on both classes: after writing, the internal position sits at the end of what was written, so an immediate .read() returns nothing — exactly like a real file left open in write mode. Rewinding with .seek(0) first is what makes reading back what was just written actually work, on both StringIO and BytesIO.

Where this sits next to Day 65's tempfile: both exist to avoid naming a real path on disk, but for different reasons. tempfile still creates an actual file or directory — needed when some other program, or a function that insists on a real path string, has to open it too. StringIO/BytesIO create nothing on disk at all — the right choice whenever every reader and writer involved is Python code that only needs the file-like interface, never a path.
Where pandas goes from here: nothing pandas-specific today — pandas.read_csv() happens to also accept a StringIO/BytesIO in place of a path, but that is data/'s API to teach; no DataFrame code shown here, per MISSION.md.
