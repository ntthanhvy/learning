1 · A gap that's been sitting in this project since Day 6

mart_delivery_sla's own grain, stated out loud back on Day 6, is one row per city per order_date — but the only test on it, added that same day, is a lone not_null on city. Nothing has ever asserted that a (city, order_date) pair is actually unique, the same kind of grain guarantee Day 4 put on fct_orders.order_id and dim_restaurants.restaurant_id the moment each of those marts existed. The reason it was skipped is mechanical: dbt's built-in unique test takes exactly one column, and this mart's real identity is two columns together. Today's fix needs a single column that represents "this specific city + order_date combination" — which means manufacturing one, not finding one already sitting in the data.

2 · dbt packages: code someone else already wrote, into your project

Every model and macro in this project so far has been hand-written. A dbt package is the alternative for anything common enough that someone else has already solved it well: a bundle of macros and generic tests, distributed as a git repo, installed with a manifest file and one command — the dbt equivalent of adding a library to pyproject.toml rather than writing the function yourself. dbt_utils, maintained by dbt Labs itself and cited in RESOURCES.md's Phase 2a spine, is the most widely installed one — general-purpose SQL and testing helpers that don't belong to any one company's specific models.

Declare it in packages.yml, a new file at the project root, sibling to dbt_project.yml:

-- packages.yml
packages:
  - package: dbt-labs/dbt_utils
    version: [">=1.3.0", "<2.0.0"]

Install it — this is the one step in today's lesson that needs internet access, since it downloads from dbt Hub:

uv run --project ../dbt_env dbt deps

Expected — dbt resolves the version range, writes a lockfile, and drops the package's macros into dbt_packages/:

Installing dbt-labs/dbt_utils
Installed from version 1.4.1
Up to date!

dbt_packages/ and package-lock.yml are generated files — the lockfile is worth committing (it pins the exact resolved version for anyone else who clones the repo and runs dbt deps), dbt_packages/ itself is not, the same "generated, not source" distinction Day 1's .gitignore already drew around dbt's own target/ folder.

3 · Build: generate_surrogate_key gives the mart a real key

dbt_utils' generate_surrogate_key macro takes a list of column expressions, coalesces each to a placeholder if null, concatenates them, and hashes the result — one deterministic value standing in for "this exact combination." Add it to mart_delivery_sla.sql's final select, as the first column:

-- models/marts/mart_delivery_sla.sql -- inside the final select, as the new first column
select
    {{ dbt_utils.generate_surrogate_key(['city', "date_trunc('day', placed_at)::date"]) }} as sla_key,
    city,
    date_trunc('day', placed_at)::date as order_date,
    -- ...rest of the select is unchanged from Day 10

Note the package prefix: it's {{ dbt_utils.generate_surrogate_key(...) }}, not a bare {{ generate_surrogate_key(...) }} — every macro a package brings in is namespaced under that package's name, exactly so a project's own macro (like Day 10's is_sla_breach) can never silently collide with one an installed package defines. On Postgres, the macro resolves dbt.hash() to md5() and each column to varchar before concatenating with || — worth reading once with Day 10's dbt compile habit, since a macro from a package is still just Jinja producing plain SQL, no different from one you wrote yourself.

Add the grain test to models/marts/marts.yml, on the new column instead of the old single-column city test:

  - name: mart_delivery_sla
    columns:
      - name: sla_key
        tests:
          - unique
          - not_null
uv run --project ../dbt_env dbt build --select mart_delivery_sla

Why a hash, not just concatenating the two columns as text: city || order_date would work for uniqueness too, but a hash gives a fixed-width, opaque, join-friendly value that never needs quoting or escaping regardless of what's inside city — the same reason Day 5's Kafka messages used a generated event_id rather than concatenating fields into one string key. The tradeoff is real: a hash can't be reversed back into city and order_date by eye in a psql session the way a concatenated string could, which is exactly why city and order_date stay in the select as their own columns — sla_key is for uniqueness and joins, not for reading.

4 · When to write a test instead of importing one

dbt_utils also ships generic tests, not just macros — dbt_utils.accepted_range asserts a column's values fall inside a given bound, declared in YAML exactly like the built-in unique/not_null/relationships/accepted_values Day 3 used. This is worth comparing directly against Day 3's assert_positive_subtotal, a hand-written singular test asserting the exact same underlying business rule — subtotal can't be negative:

dbt_utils.accepted_rangeDay 3's assert_positive_subtotal
Shapegeneric test, one YAML linesingular test, a whole .sql file
Rule expresseda value bound: min_value: 0the same value bound, spelled the same way
Reusable across columns?yes, same line on any numeric columnno — one file, one column, one rule

For a plain range check like this one, dbt_utils.accepted_range is strictly less code for the identical result — today, replace the hand-written version to prove it:

-- models/staging/stg_orders.yml -- replace the singular test's job with a generic one
      - name: subtotal
        tests:
          - dbt_utils.accepted_range:
              arguments:
                min_value: 0

Delete tests/assert_positive_subtotal.sql — its job is now done by one YAML line pulled from a package instead of a whole separate hand-written SQL file. But the swap only works because this particular rule happens to be a plain range check. The moment a rule needs something dbt_utils' generic tests don't express — Day 9's whole point-in-time-join correctness, or "an order's delivered event must occur after its placed event," which needs a join across two rows of the same source rather than a bound on one column — no package test fits, and a singular test is the only option, same as Day 3 reached for one when no built-in test fit. The decision rule is the same one Day 10's callout used for macros, one layer up: reach for the package when the rule is truly generic and the package already expresses it; write it by hand the moment the rule is specific to this business or needs logic no generic test shape covers.

Q: "When would you reach for a dbt package instead of writing your own macro or test?" A strong answer, out loud: "Once a piece of logic is generic enough that it isn't really about my business at all — hashing a set of columns into a surrogate key, or checking a numeric column falls in a range, are the same problem in every dbt project that has them, so dbt_utils having already solved it well means I shouldn't solve it again. I'd install it with a packages.yml pinned to a version range and dbt deps, the same idea as pinning a library in a Python project. But the moment a rule is specific to my own data — a point-in-time join's correctness, or an order's delivered event needing to come after its placed event — no generic package test expresses that, and I write a singular test by hand instead, the same as I would before ever installing a package. Packages replace generic, reusable logic; they don't replace understanding what's actually specific to this pipeline's own business rules." The signal: naming a concrete package function by what problem it solves, and drawing the line at "generic vs. specific to my data" rather than treating a package as always better than hand-written SQL.
