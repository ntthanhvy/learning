Naming more than one query filter

Lesson 144 showed HasQueryFilter once per entity type — soft deletion, or a tenant check, never both. That wasn't a simplification for the lesson's sake: before EF Core 10, calling HasQueryFilter a second time on the same entity type doesn't add a second filter, it replaces the first one. A real app usually wants both soft deletion and tenant isolation on the same table at once. This lesson covers the two ways EF Core lets you get there: the old workaround, and the new first-class answer.

1 · The trap: the second call wins, silently

Lesson 144's two filters — soft deletion on IsDeleted, tenant isolation on TenantId — look like they'd stack if you just call the method twice:

modelBuilder.Entity<Blog>().HasQueryFilter(b => !b.IsDeleted);
// The following overwrites the previous query filter:
modelBuilder.Entity<Blog>().HasQueryFilter(b => b.TenantId == tenantId);

After both lines run, only the tenant check survives. The soft-deletion filter isn't combined with it, isn't kept as a fallback — it's gone, with no error or warning at build or run time. A deleted row from the correct tenant comes right back in a query result, because the one filter EF Core kept never mentions IsDeleted at all. This is exactly the kind of silent-replace bug Lesson 144's own "frontend-habit trap" callout warned about with a different mechanism: the API shape looks additive (two separate calls, like adding two CSS classes), but the actual behavior is last-write-wins.

2 · Before EF Core 10: one filter, joined by hand

The documented fix pre-dates named filters: don't call HasQueryFilter twice, call it once with both conditions joined by && in a single lambda:

modelBuilder.Entity<Blog>()
    .HasQueryFilter(b => !b.IsDeleted && b.TenantId == tenantId);

This works, and it's still the only option on EF Core versions before 10. But Microsoft's own docs name its real limitation: once the two conditions are merged into one && expression, they can't be addressed separately again. IgnoreQueryFilters() turns off both conditions for a query, because from EF Core's point of view there's only ever been one filter — it has no idea that a human reads it as two concerns. An admin tool that wants to see soft-deleted rows for the current tenant, without also leaking every other tenant's rows, has no way to ask for that.

3 · EF Core 10: give each filter a name

Named query filters, introduced in EF Core 10 (currently in preview per Microsoft's own docs), remove the overwrite trap entirely — each call gets a string name as its first argument, and both filters are kept, chained rather than replaced:

modelBuilder.Entity<Blog>()
    .HasQueryFilter("SoftDeletionFilter", b => !b.IsDeleted)
    .HasQueryFilter("TenantFilter", b => b.TenantId == tenantId);

Both conditions apply to every query against Blog, same as the && version — but now EF Core tracks them as two separate, independently addressable filters rather than one fused expression. The name is purely a label for managing the filter later; it has no effect on the generated SQL, which still ANDs every active filter's condition together the same way the manual && version did.

Frontend-habit trap: the string name doesn't look like it should matter — plenty of React/CSS APIs take a name purely for debugging (a component's displayName, say) with zero runtime effect beyond a label in dev tools. Here the name is the only handle you get for turning one filter off without turning off the other; skip naming a filter and you're back to the pre-EF-10 all-or-nothing behavior, even on EF Core 10.

4 · Disabling one filter, not both

Naming the filters is what makes selective disabling possible. IgnoreQueryFilters() with no arguments still turns off every filter on the entity type, named or not:

var allBlogs = await context.Blogs.IgnoreQueryFilters().ToListAsync();

Starting in EF Core 10, passing a list of names to the same method disables only those filters, leaving the rest active:

var allBlogs = await context.Blogs.IgnoreQueryFilters(["SoftDeletionFilter"]).ToListAsync();

This query sees soft-deleted rows — the named filter is off — but still only the current tenant's rows, because "TenantFilter" was never named in the list and keeps running. That's the admin-tool case section 2 couldn't express with a single merged && filter: see everything a normal query hides for one reason, while every other guardrail Lesson 78 and Lesson 144 put in place stays up.

5 · The other half: no context instance to reference

Lesson 144's tenant filter leaned on a constructor parameter the DbContext itself holds: MultitenancyContext(string tenantId), referenced directly from the filter lambda inside OnModelCreating. That works because OnModelCreating is a method on the context, with a live this available. Model configuration split out into its own IEntityTypeConfiguration<TEntity> class doesn't have that — Microsoft's docs call this out directly as "an additional complication": a query filter written inside Configure has no context instance to read a tenant ID from at all.

The documented workaround looks like it shouldn't work:

private sealed class CustomerEntityConfiguration : IEntityTypeConfiguration<Customer>
{
    private readonly SomeDbContext _context = null!;

    public void Configure(EntityTypeBuilder<Customer> builder)
    {
        builder.HasQueryFilter(d => d.TenantId == _context.TenantId);
    }
}

That null! field is never assigned a real context — it exists purely so the filter lambda has something typed to write _context.TenantId against. EF Core's query translator doesn't evaluate this lambda as ordinary C# that would throw a NullReferenceException on a null field; it reads the lambda as an expression tree and compiles _context.TenantId into a parameterized reference, resolved against the real, live context instance at query time — the same translate-don't-execute step that turns b => !b.IsDeleted into a SQL WHERE clause rather than running C# row by row. The dummy field is a syntax anchor for the expression tree, not a value that's ever read at runtime.
