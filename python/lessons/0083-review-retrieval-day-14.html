Day 80 — difflib. What can difflib.unified_diff() show you that a plain old == new comparison can't, and why is get_close_matches() a better fit than unified_diff() for a "did you mean…?" suggestion?

Fold-out answer: == only answers "are these the same, yes or no" — it gives no information about where two sequences differ when they aren't. unified_diff() walks line by line and marks exactly which lines were removed (-), added (+), or unchanged context (plain leading space), the same shape git diff prints. get_close_matches() suits "did you mean…?" better because it is built for exactly that: given one misspelled or unknown word and a list of known candidates, it ranks the candidates by similarity and returns the closest one(s) — unified_diff() instead expects two sequences that are already meant to line up position by position, and would just show the whole single word as entirely removed and the candidate as entirely added, with no ranking of "closeness" at all.

Day 81 — io.StringIO & io.BytesIO. Why does csv.writer() accept a StringIO in place of a real open file, and why does reading from a BytesIO immediately after writing to it come back empty?

Fold-out answer: csv.writer() only needs an object with a .write() method that accepts str — it never checks whether that object is backed by a real file on disk. io.StringIO implements that same file-like interface entirely in memory, so anything written to it (via csv, json, or plain print(..., file=buf)) is just as acceptable as a real file handle. Reading right after writing comes back empty because a stream tracks a single read/write position: after writing, that position sits at the end of what was just written, so an unseeked .read() starts from there and finds nothing left to read. .seek(0) rewinds the position back to the start before reading, which is why it has to run between the write and the read.

Day 82 — base64. Why does json.dumps() reject raw bytes outright, and why is calling base64.b64encode() a way of "hiding" or "securing" data a mistake?

Fold-out answer: JSON's own spec only defines a fixed set of value types — strings, numbers, booleans, null, objects, and arrays — and raw bytes is not one of them, so json.dumps() raises a TypeError the moment it meets a bytes value with no default= function to fall back on. base64.b64encode() re-encodes those bytes into a safe 64-character text alphabet that JSON's string type can hold, closing that gap. Calling it "hiding" or "securing" data is a mistake because base64 is encoding, not encryption: it uses a fixed, public, documented alphabet and no key at all, so anyone who recognizes base64-looking text (or simply runs base64.b64decode() on it) gets the original bytes back immediately — it protects nothing from anyone who wants to read it, it only makes binary data transportable through a text-only channel.
