base64: binary data as plain text

Day 81's io.BytesIO held raw bytes in memory instead of on disk — but JSON, a URL, an HTTP header, and plain text all still choke on raw bytes directly, because those formats only know a limited set of printable characters. The base64 module is the standard answer: encode bytes into that safe alphabet before handing them to a text-only format, and decode them back to the original bytes on the other end.

Why today, specifically: a fresh-gap grep across all 81 lessons and every practice file found zero hits for base64 as a taught topic — it surfaced as the runner-up in Day 81's own gap scan (that round picked io.StringIO/BytesIO instead, on relative priority, and explicitly flagged base64 as the standing candidate to take next). It is still a clean gap today, and it completes a real story: Day 81 taught holding bytes in memory; today teaches what to do when those bytes need to leave Python's world — into a JSON field, a URL, or a text-based log — without a byte lost or mangled.

1 · The problem: raw bytes don't survive a text-only format

Suppose a small PNG's raw bytes need to travel inside a JSON payload — maybe an API that returns an image thumbnail embedded directly in a response body instead of as a separate file:

import json

image_bytes = b"\x89PNG\r\n\x1a\n..."  # arbitrary binary, not text
try:
    json.dumps({"thumbnail": image_bytes})
except TypeError as e:
    print(e)
# Object of type bytes is not JSON serializable

Day 76's json.dumps() only knows str, int, float, bool, None, list, and dict — bytes is not on that list, and for good reason: JSON text itself is restricted to characters that can't represent an arbitrary byte like \x1a safely. The fix isn't a default= callback (Day 76) rewriting the bytes into some other shape; it's re-encoding the bytes themselves into text first, so they become a plain str JSON already knows how to hold.

2 · b64encode() / b64decode(): the core round trip

import base64

data = b"hello world"
encoded = base64.b64encode(data)
print(encoded)          # b'aGVsbG8gd29ybGQ='

decoded = base64.b64decode(encoded)
print(decoded)          # b'hello world'
print(decoded == data)  # True -- the exact original bytes, no loss

b64encode() takes bytes and returns bytes — notice the b'...' prefix on the output too. That output happens to contain only the 64 safe characters, so it's always safe to go one step further and turn it into a real str for embedding in JSON or text:

token = base64.b64encode(data).decode("ascii")
print(token, type(token))
# aGVsbG8gd29ybGQ= <class 'str'>

json.dumps({"payload": token})  # works now -- it's just a plain string

.decode("ascii") is safe here specifically because base64's output alphabet is pure ASCII by construction — unlike Day 76's general text-encoding concerns, there's no multi-byte character risk to worry about on this particular conversion.

The trailing = is padding, not noise: base64 packs every 3 input bytes into 4 output characters, and pads with = when the input isn't a multiple of 3 bytes, so a decoder always knows exactly where the real data ends:

for n in (1, 2, 3):
    print(n, base64.b64encode(b"x" * n))
# 1 b'eA=='   -- 1 byte in, padded to 4 chars
# 2 b'eHg='   -- 2 bytes in, padded to 4 chars
# 3 b'eHh4'   -- 3 bytes in, no padding needed

3 · urlsafe_b64encode(): when the text destination is a URL

Standard base64's 64-character alphabet includes + and / — both characters with their own special meaning inside a URL (space-encoding and path separators). Putting a raw base64 string into a URL query parameter risks it being misread:

data = bytes([251, 255, 191])
print(base64.b64encode(data))          # b'+/+/'
print(base64.urlsafe_b64encode(data))  # b'-_-_'

urlsafe_b64encode() does the exact same packing, just swapping + → - and / → _ in the output alphabet — safe to drop straight into a URL path segment or query string with no further escaping. urlsafe_b64decode() is its matching reader; mixing a string from one variant into the other's decoder silently produces wrong bytes or an error, so the pick has to match on both ends.

Not encryption: base64 is an encoding, not encryption. Anyone who sees a base64 string can decode it with zero effort and no secret key — base64.b64decode() is public knowledge, not a cipher. It hides nothing. If the actual goal is "keep this secret," Day 77's secrets module and a real encryption library are the right tools; base64 only solves "make these bytes survive a text-only pipe."
Where pandas/NumPy go from here: nothing library-specific today — base64 encoding is a plain-bytes operation with no connection to a DataFrame or array; this stays entirely in stdlib territory, per MISSION.md.
