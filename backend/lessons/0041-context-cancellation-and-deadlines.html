context.Context: the cancellation signal riding along with every request

Nineteen of this course's own Go snippets — Lessons 9 through 40 — take a ctx context.Context as their first parameter, and three of them even call ctx.Done() or ctx.Err(). Not one lesson has ever said what a context.Context actually is. Today closes that gap.

1 · The question every one of those snippets begged

Look back at Lesson 27's signal.NotifyContext, Lesson 32's ctx.Done() inside a retry loop, or literally any handler signature in this course — they all thread a ctx context.Context through, first argument, every call. It was treated as boilerplate: a parameter you pass along without asking why. It isn't boilerplate. A context.Context is Go's answer to one specific, very common problem: a single incoming HTTP request often triggers a whole tree of downstream work — a database query, an outbound HTTP call to another service, maybe both at once — and if the original caller gives up (closes the connection, or the request just times out), every one of those downstream calls is still sitting there working on behalf of nobody. A context.Context is the value that carries that signal down the chain, so every function on it can check "should I still be doing this?" without each layer having to invent its own cancellation channel.

The frontend equivalent you already own. This is the backend cousin of an AbortController passed into fetch() — call .abort() and the in-flight request stops, instead of the browser quietly finishing a fetch nobody's waiting on anymore. A context.Context is that same idea, generalized to an entire call chain of Go functions instead of one fetch() call.

2 · What actually rides inside it

A context.Context carries up to two things, and request-handling code almost always uses one or the other (rarely both by hand at once):

  • A cancellation signal. ctx.Done() returns a channel that's closed the moment the context is cancelled — by an explicit call, a deadline expiring, or a parent context being cancelled. Code that might run for a while selects on it: case <-ctx.Done(): return ctx.Err(), exactly the shape Lesson 32's backoff loop and Lesson 29's outbox relay both already used, one row above a real explanation of what it meant.
  • A deadline. context.WithTimeout(parent, 10*time.Second) (Lesson 27's shutdown sequence used exactly this) creates a context that cancels itself automatically once the duration elapses — no goroutine or timer needs to be written by hand to enforce it.

The key mechanical fact: a context is immutable and derived. You never modify one — context.WithTimeout, context.WithCancel, and signal.NotifyContext (Lesson 27) all take a parent context and return a brand-new child. Cancelling a parent cancels every child derived from it, automatically, all the way down — that's the entire propagation mechanism, no framework required.

// fetchOrderSummary demonstrates the propagation: ctx arrives from the HTTP
// handler already carrying the client's deadline. Deriving a *tighter* child
// deadline for the DB call means a slow query can't outlive the time budget
// the caller was willing to wait, even if the caller's own deadline is longer.
func fetchOrderSummary(ctx context.Context, db DB, orderID int64) (Summary, error) {
    dbCtx, cancel := context.WithTimeout(ctx, 2*time.Second)
    defer cancel()

    row := db.QueryRow(dbCtx, `SELECT total_cents, status FROM orders WHERE id = $1`, orderID)
    var s Summary
    if err := row.Scan(&s.TotalCents, &s.Status); err != nil {
        if ctx.Err() != nil {
            // the caller gave up (or the deadline passed) — don't wrap this as a
            // DB error, it's a cancellation, and callers should tell the two apart
            return Summary{}, fmt.Errorf("summary lookup abandoned: %w", ctx.Err())
        }
        return Summary{}, fmt.Errorf("query order %d: %w", orderID, err)
    }
    return s, nil
}

Note the defer cancel(): every context.With* call returns a cancel function, and it must always be called (even on the success path) once that context is no longer needed — skipping it leaks the small amount of state Go's runtime keeps to track the timer, one leak per call if this runs on every request.

3 · Why the database layer actually needs the ctx argument

pgx's Pool.QueryRow(ctx, ...), Exec(ctx, ...), and every other query method (already used, unexplained, in Lessons 33–40's own snippets) all take a context as their first argument for exactly this reason: if the HTTP client disconnects or the request's deadline passes while a query is running, pgx can use that same signal to abandon the query on the wire — cancelling the in-flight statement on the Postgres side too — instead of the connection sitting there computing a result nobody will ever read. This is a direct extension of Lesson 18's connection-pool story: a query that ignores cancellation doesn't just waste CPU, it holds a pooled connection open for the full query duration even after the caller is long gone, exactly the shape of pool exhaustion Lesson 18 described, just with an abandoned client instead of a bug as the cause.

4 · The one rule almost everyone breaks once

A context.Context is for cancellation and deadlines, and for small pieces of request-scoped metadata a whole call chain needs to see — the correlation ID from Lesson 13 is the canonical example, attached once at the edge with context.WithValue and read by the logging middleware three layers down without every function in between needing it threaded as its own parameter. It is not a general-purpose way to sneak optional parameters past a function signature, and it is never a substitute for a normal argument something actually depends on to do its job — if a function can't run correctly without a value, that value belongs in the signature, not buried in a context lookup that only fails at runtime if it's missing.

Q: "Why does almost every function in our Go services take a context.Context as its first parameter?" A strong answer, out loud: "It carries the cancellation signal and any deadline down the whole call chain from wherever the request started, so a database query or an outbound HTTP call can notice the original caller is gone and stop instead of finishing pointless work. It's derived, not mutated — WithTimeout or WithCancel returns a child, and cancelling a parent cancels every child under it automatically. The one thing I'd watch for in review is someone using it to smuggle a required argument through WithValue instead of putting it in the signature — that's the misuse, not the mechanism." The signal: naming propagation and derivation, not just "it's for timeouts."
