The middleware pipeline: order is the feature

Lesson 1 named middleware as "code wrapped around handlers for cross-cutting work." That was true but vague about one thing that turns out to matter a lot: middleware runs in a specific, visible order, and that order is not a style choice — it decides whether auth actually protects anything. Go makes you write the chain by hand, one wrap at a time. ASP.NET Core writes it as a literal, ordered list in Program.cs, and reading that list correctly is a real skill for reviewing .NET PRs.

1 · A pipeline, not a pile

Lesson 1 said middleware wraps a handler. The more precise picture: a request enters at the top of an ordered chain and passes through each piece in turn, in the order it was added, before ever reaching the route handler — then the response travels back out through the same chain, in reverse. Each piece gets to look at the request, do something, and decide whether to call the next piece or stop right there and answer immediately. That decision point is the whole mechanism; everything else is detail.

Go has no framework-owned pipeline, but idiomatic code builds the identical shape by hand, by wrapping one http.Handler in another:

func withLogging(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        next.ServeHTTP(w, r) // call the next link in the chain
        log.Printf("%s %s %v", r.Method, r.URL.Path, time.Since(start))
    })
}

func withAuth(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if !isAuthenticated(r) {
            w.WriteHeader(http.StatusUnauthorized)
            return // stop here -- next.ServeHTTP is never called
        }
        next.ServeHTTP(w, r)
    })
}

func main() {
    handler := withLogging(withAuth(orderHandler)) // the ORDER is written right here, by hand
    http.ListenAndServe(":8080", handler)
}

Read withLogging(withAuth(orderHandler)) from the outside in: logging wraps auth, auth wraps the real handler. A request hits logging first, then auth, then the handler — and the auth middleware's early return is the "stop right there" move: skip calling next.ServeHTTP, and nothing further in the chain, including the real handler, ever runs.

2 · ASP.NET Core's answer: the same chain, written as a list

ASP.NET Core takes the exact same wrap-and-call-next shape and gives it a dedicated, visible place: a sequence of app.Use... calls in Program.cs, each one a middleware pipeline link, in exactly the order they appear in the file:

// Program.cs -- this order is the entire pipeline, top to bottom
var app = builder.Build();

app.UseExceptionHandler("/error");  // 1: catch unhandled exceptions from everything below
app.UseHttpsRedirection();           // 2: redirect http:// to https://
app.UseAuthentication();             // 3: who is this request from?
app.UseAuthorization();              // 4: are they allowed to reach this route?
app.MapControllers();                // 5: terminal -- this is where a handler finally runs

app.Run();

Each registered piece receives a next delegate standing in for "everything registered after me," same role as Go's next.ServeHTTP above — the framework builds that chain of delegates automatically from the registration order, instead of you nesting function calls by hand.

Why order is the whole lesson, not a detail: swap lines 3 and 4 above — UseAuthorization() before UseAuthentication() — and authorization now runs against a request that has no identity attached yet, because authentication hasn't run. Every authorization check either silently fails closed (nobody gets in) or, worse, fails open depending on how the check is written. This isn't a hypothetical: it's the single most common ASP.NET Core middleware bug, and it compiles and starts up without any warning either way — nothing catches it except knowing the order matters and reading it.

3 · Short-circuiting: the deliberate "stop here"

A middleware component that never calls its next delegate is short-circuiting the pipeline, same as Go's withAuth returning early above. This is usually deliberate and correct — rejecting an unauthenticated request before it reaches anything that assumes one — but it means a component sitting late in the list silently never runs for requests a much earlier component already answered. Something that must run on every request, including rejected ones (request logging is the classic case) has to be registered before anything that might short-circuit, not after.

The route handler itself — MapControllers(), or MapGet("/orders", ...) — is terminal: it's where the chain of "pass it on" calls finally ends and a real response gets written, the equivalent of Go's innermost orderHandler.

4 · Where DI fits: middleware gets built by the same container

Lesson 103 covered the DI container resolving constructor parameters for controllers. Middleware is resolved the same way — a class-based middleware component's constructor can request any registered service, and the container supplies it, same AddScoped/AddSingleton/AddTransient rules from Lesson 103 apply:

public class RequestLoggingMiddleware {
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestLoggingMiddleware> _logger;

    public RequestLoggingMiddleware(RequestDelegate next, ILogger<RequestLoggingMiddleware> logger) {
        _next = next;       // the framework hands this in -- "the rest of the pipeline"
        _logger = logger;   // resolved by the DI container, same as Lesson 103's controllers
    }

    public async Task InvokeAsync(HttpContext context) {
        var start = DateTime.UtcNow;
        await _next(context);  // call the next link; awaiting lets it run, then returns here
        _logger.LogInformation("{Method} {Path} took {Ms}ms",
            context.Request.Method, context.Request.Path, (DateTime.UtcNow - start).TotalMilliseconds);
    }
}

This is the same constructor-injection shape Lesson 103 showed for controllers, just applied to a pipeline component instead of a route handler — one more thing Lesson 103's container resolves, exactly as that lesson's closing line anticipated.

Scope line

This lesson covers ordering, short-circuiting, and the DI connection — the mental model needed to read a Program.cs pipeline correctly in review. It does not cover: writing middleware as inline lambdas via app.Use(async (ctx, next) => ...) versus the class-based convention shown above (both exist; class-based is more common for anything beyond a few lines); endpoint routing's separate matching phase (how MapControllers itself decides which controller action runs, a routing-internals topic, not a pipeline-ordering one); and branching the pipeline per-path with app.MapWhen or UseWhen. These are natural follow-ons, not covered here.

Q: "A PR adds authorization middleware. What do you check first?" A strong answer, out loud: "Before anything about what the check itself does, I check where it's registered in Program.cs relative to UseAuthentication — authorization has to run after authentication, because it needs an identity already attached to decide anything, and ASP.NET Core won't warn you if you get the order backwards; it just silently authorizes against an empty identity. I'd also check whether anything upstream of it could short-circuit the request before this middleware ever runs, and whether this new middleware itself might unintentionally short-circuit something that was supposed to run after it, like response logging." The signal: naming that pipeline order is a correctness property, not cosmetic, and that the framework gives you zero compile-time protection against getting it wrong.
