Concurrency is not parallelism, and a goroutine is not a thread

Four words — concurrent, parallel, thread, coroutine — get used as if they were four names for one thing. They aren't. They're answers to two separate questions, and once you see which question each word answers, the whole vocabulary collapses into something you can hold in your head and defend in a review.

1 · The reframe: two questions, not one list

The confusion is structural. People try to line these four words up on a single scale from "slow" to "fast," and it never works, because two independent questions are being asked at once:

Question A — how is the work arranged? Is your program structured as independent pieces, and do those pieces actually execute at the same instant? → concurrency vs parallelism.

Question B — who decides when to switch between pieces? The operating system kernel, or your language's runtime? → thread vs coroutine.

Question A is about your design. Question B is about the mechanism underneath it. A single program answers both: "structured concurrently (A), using coroutines (B), running in parallel across 8 cores (A again)." That sentence is not redundant — it's three separate facts.

2 · Question A: concurrency vs parallelism

The canonical definitions come from Rob Pike, one of Go's designers, in a 2012 talk that exists more or less to kill this exact confusion:

Concurrency is "the composition of independently executing processes" — or in the short form, "dealing with lots of things at once." Parallelism is "the simultaneous execution of (possibly related) computations" — "doing lots of things at once." (go.dev/blog/waza-talk)

The test that makes it concrete: a single-core machine can be concurrent but can never be parallel. One core executes exactly one instruction stream at any instant. Yet a single-core server happily handles 500 open connections — it interleaves them, switching between them fast enough that all 500 make progress. That's concurrency with zero parallelism.

So the relationship isn't "concurrency is the slow version of parallelism." It's this: concurrency is a way of writing your program; parallelism is something the machine may or may not then do with it. You write concurrency. The runtime and the hardware grant parallelism. If you never structured the work concurrently, extra cores can't help you — there's nothing for them to pick up.

3 · Question B: thread vs coroutine — who does the switching

Now the mechanism. Both a thread and a coroutine are "a piece of work that can be paused and resumed." The difference is who pauses it.

An OS thread is scheduled by the kernel. The kernel can interrupt it at essentially any instruction and hand the core to something else — that's preemptive scheduling. Threads are the only thing an OS will actually place on separate cores, so threads are the unit of real parallelism. They're also comparatively expensive: a thread's stack is typically sized in megabytes, and creating one is a system call.

A coroutine is scheduled by the language runtime, in user space. The kernel doesn't know it exists. It suspends at points the runtime can see — an await, a channel operation, a network read — which is cooperative scheduling. Its stack starts at kilobytes, and creating one is a function call, not a syscall.

That last row of the coroutine column is the answer to "why does everyone use a different word?" They're the same idea with different names and different degrees of power. And notice the second-to-last row: coroutines do not compete with threads — they run on top of them. A runtime keeps a small pool of OS threads (roughly one per core) and multiplexes many coroutines onto them. That arrangement is called M:N scheduling.

Go's documentation is unusually direct about the naming, and it's worth reading as the resolution of your question rather than a footnote:

From Effective Go: "They're called goroutines because the existing terms — threads, coroutines, processes, and so on — convey inaccurate connotations. A goroutine has a simple model: it is a function executing concurrently with other goroutines in the same address space. It is lightweight, costing little more than the allocation of stack space." And: "Goroutines are multiplexed onto multiple OS threads so if one should block, such as while waiting for I/O, others continue to run." (go.dev/doc/effective_go)

So a goroutine is a coroutine in the broad family sense — runtime-scheduled, cheap, multiplexed M:N — but it's preemptible and it can block anywhere, without the async/await ceremony that Python or Rust require. That's why Go picked a new word.

4 · When to use which: the one question that decides it

Here is the rule that turns all of the above into a decision. Ask what your work is waiting on:

I/O-bound workCPU-bound work
Spends its timewaiting — on the network, the database, the diskcomputing — actually burning cycles
Backend examplesquerying Postgres, calling another service, reading a file, serving an idle connectionhashing a password, resizing an image, parsing a huge JSON body, compression
What you needconcurrency — a cheap way to hold thousands of waitsparallelism — more cores actually doing the work
Reach forcoroutines / goroutines — thousands of them, on a handful of threadsthreads or processes, roughly one per core, no more
Ceilingmemory and file descriptors, not coresyour physical core count. Full stop.

I/O-bound work is the overwhelming majority of what a backend service does, and that's why this vocabulary matters at all for backend work. A request handler that queries Postgres spends almost all of its wall-clock time doing nothing but waiting for a reply. During that wait, whatever was running it should be doing something else. If the unit of work is an expensive OS thread, 10,000 waiting requests means 10,000 mostly-idle threads, and you drown in memory and scheduler churn. If it's a cheap coroutine, 10,000 waits cost almost nothing — one thread per core stays busy, hopping between whichever coroutines have data ready.

CPU-bound work is the opposite, and here's the trap worth internalizing: concurrency does not speed up CPU-bound work. Splitting a computation into 100 coroutines on a 4-core machine does not make it faster — the same 4 cores do the same total work, plus scheduling overhead. Only parallelism helps, and parallelism is capped by your cores. Spawning 200 coroutines to hash 200 passwords is not a performance fix; it's the same CPU time with extra bookkeeping. Worse, in a cooperative runtime a long CPU-bound coroutine that never yields starves the others — the classic "why did all my request latencies spike" incident.

Where the language you're in changes the answer: In Go, the split is invisible — goroutines are cheap enough for I/O and the runtime spreads them across cores automatically (GOMAXPROCS defaults to the CPUs available), so one primitive covers both cases. In Python, the two cases need different tools, because the GIL means threads don't parallelize pure-Python computation: asyncio for I/O, multiprocessing for CPU. (Python 3.14 ships an officially supported free-threaded build, python3.14t, that removes the GIL — but it's opt-in, and the default build still has it. PEP 779.) In Node, there is one thread for your JavaScript, so CPU-bound work must leave it entirely — worker threads or a separate process.

Q: "What's the difference between concurrency and parallelism?" — a near-universal backend interview question. A strong answer, out loud: "Concurrency is a property of how I structure the program — independent pieces that can interleave. Parallelism is a property of the execution — those pieces literally running at the same instant, which needs multiple cores. A single-core box can be fully concurrent and never parallel: it handles a thousand connections by interleaving them. So I write concurrency, and the runtime plus hardware decide how much parallelism I get out of it. The practical consequence is that for I/O-bound work — which is most of a backend service, waiting on Postgres or another service — concurrency is what I need, and cheap runtime-scheduled tasks like goroutines are the right unit. For CPU-bound work, concurrency buys nothing; only parallelism helps, and it's capped by core count." The signal: naming that one is about structure and the other about execution, then connecting it to the I/O-bound vs CPU-bound decision rather than stopping at the definition.
