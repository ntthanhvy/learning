Descriptors: how @property and @classmethod actually work

Day 30 taught @property as "a method that reads like an attribute." Day 32 taught @classmethod/@staticmethod as "decorators that change the first argument." Both were true, and both stopped one level short of the mechanism: all three are built on one general protocol — the descriptor protocol — that any class can opt into. Today opens that box.

Bridge from SQL: a computed column and a stored column look identical in a SELECT * — the engine hides which one is really stored on disk versus derived on read. A descriptor is the same hidden switch for a Python attribute: obj.price reads exactly the same whether price is a plain stored value or a descriptor quietly running code on every access. The protocol below is what lets Python make that switch invisible at the call site.

1 · The protocol: __get__, __set__, __set_name__

A descriptor is any object whose class defines one or more of these three methods, and which is itself stored as a class attribute:

class Validated:
    def __set_name__(self, owner, name):
        # called once, when the *class* using this descriptor is created —
        # owner is that class, name is the attribute name assigned to it
        self.public_name = name
        self.private_name = "_" + name

    def __get__(self, obj, objtype=None):
        if obj is None:
            return self          # accessed on the class itself, e.g. Product.price
        return getattr(obj, self.private_name)

    def __set__(self, obj, value):
        if value < 0:
            raise ValueError(f"{self.public_name} can't be negative")
        setattr(obj, self.private_name, value)


class Product:
    price = Validated()      # the descriptor lives on the CLASS, once

    def __init__(self, price):
        self.price = price    # this line triggers Validated.__set__, not a plain dict write

Verified live: creating the Product class itself calls __set_name__(Validated_instance, Product, "price") immediately — before any Product is ever instantiated. Every later p.price read calls __get__; every p.price = ... write calls __set__. p.price = -5 raises ValueError exactly like Day 30's hand-written @dollars.setter did — because a @property setter is this same mechanism, one level down.

2 · @property is one specific descriptor, built in

Day 30 introduced @property as syntax; underneath, property is a built-in class whose instances are data descriptors — confirmed live: hasattr(property, "__get__") and hasattr(property, "__set__") are both True. Writing this Day-30-style class:

class Money:
    def __init__(self, cents):
        self.cents = cents

    @property
    def dollars(self):
        return self.cents / 100

is shorthand for storing a property instance built from the getter function: dollars = property(fget=<the function above>). Confirmed live: isinstance(Money.__dict__["dollars"], property) is True, and accessing Money.dollars (on the class, no instance) returns the property object itself rather than a number — that is the if obj is None: return self branch in __get__ above, the exact line that makes help(Money.dollars) and similar introspection work. @dollars.setter from Day 30 fills in that same property object's __set__ path. There is no separate "property mechanism" — it is one descriptor class, and Day 30's @property was always calling it.

3 · @classmethod and @staticmethod are descriptors too

Day 32's two method decorators use the same protocol, but as non-data descriptors — confirmed live: both classmethod and staticmethod have __get__ but no __set__. Their __get__ doesn't fetch a stored value at all; it returns a differently-bound callable:

class D:
    @classmethod
    def make(cls):
        return cls()      # classmethod.__get__ binds the CLASS as the first argument

    @staticmethod
    def helper(x):
        return x * 2       # staticmethod.__get__ returns the plain function, no binding at all

This is also why an ordinary method — a plain def with no decorator — works with dot-call syntax at all: a plain function is itself a non-data descriptor (functions define __get__), and instance.method() is that __get__ binding self as the first argument, the same protocol running underneath, invisibly, for the most ordinary method in the language.

4 · Data vs. non-data: who wins the lookup

The __set__-or-not distinction from section 3 has a direct, testable consequence for which value obj.attr actually returns when both an instance's own __dict__ and its class hold something under the same name. Verified live with a minimal pair — a data descriptor (has __set__) and a non-data descriptor (only __get__), both deliberately shadowed by writing straight into h.__dict__:

h.__dict__["data_attr"] = "instance value"
h.__dict__["nondata_attr"] = "instance value"

h.data_attr      # "from DataDesc.__get__" — the data descriptor still wins
h.nondata_attr   # "instance value" — the instance dict wins this time

The full lookup order Python actually runs, for obj.attr, checking type(obj) and its bases in MRO order (Day 32's inheritance chain) at each step:

  1. a data descriptor (defines __set__ and/or __delete__) found on the class — wins outright, even over the instance's own __dict__;
  2. otherwise, the instance's own __dict__, if the name is there;
  3. otherwise, a non-data descriptor (only __get__) or plain class attribute found on the class.

property deliberately sits at step 1 — that's the whole point of a validated @property setter: nothing an instance does can bypass it by sneaking a value straight into self.__dict__, because the data descriptor is checked first. A plain method or @staticmethod/@classmethod sits at step 3 precedence-wise, which is harmless for methods (nothing normally assigns over self.some_method) but is the exact reason a data descriptor is the right tool whenever an attribute must stay validated no matter what.

One more mechanical detail, confirmed live: a descriptor only intercepts access when it is found in a class's __dict__ during that MRO walk. Assigning a descriptor instance straight into an instance's own __dict__ (a.attr = Desc()) does nothing special — it's just a plain stored object, returned as-is, __get__ never called. The protocol only activates from the class side.

Q: "How does @property actually work under the hood?" A strong answer, out loud: "property is a built-in class implementing the descriptor protocol — __get__, __set__, and optionally __delete__ — and @property is just property() called as a decorator on the getter function, stored once on the class. Because it defines __set__, it's a data descriptor, which means it takes priority over anything in an instance's own __dict__ — that's what makes a validated setter actually unbypassable. classmethod and staticmethod use the same protocol but only define __get__, so they're non-data descriptors — classmethod.__get__ binds the class as the first argument instead of an instance, and staticmethod.__get__ just returns the plain function, unbound." The signal: naming the data-vs-non-data distinction specifically, and connecting it to lookup priority rather than just reciting "it makes methods read like attributes."

Where pandas goes from here: DataFrame.loc and .iloc are themselves descriptor-backed attributes — accessing df.loc returns a fresh indexer object via a __get__, the same protocol taught here, wired up to return something far more elaborate than a number. Not demonstrated here; that's data/'s job, and this is the only sentence in this lesson that names it.
