__slots__: trading dynamic attributes for memory and safety

Day 1 built the whole object model on one picture: a name is a label, an object lives in memory, and x.attr = value sticks a new label onto whatever x points at. What Day 1 didn't say is where those labels are kept — every plain instance carries its own private dict just to hold them. Today's mechanism, __slots__, tells Python to skip that dict entirely for a class whose fields are fixed — Day 7's @dataclass is exactly that kind of class.

Bridge from SQL: a table with a fixed set of typed columns doesn't let a row silently grow a new column mid-query — inserting into a nonexistent column is an error, not a quiet no-op. __slots__ gives a Python object that same guarantee at the instance level: only the declared attributes exist, and anything else raises immediately instead of quietly succeeding.

1 · What a plain instance actually carries

Go back to Day 1's picture: an object is data in memory, a name is a label stuck onto it. For a plain instance, part of that data is a hidden instance __dict__ — a small dict mapping each attribute name to its value. self.x = x in __init__ is really just writing into that dict.

class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

p = Point(1, 2)
print(p.__dict__)     # {'x': 1, 'y': 2} — this is where x and y actually live
p.z = 99              # dynamic attribute assignment: just adds a new key
print(p.__dict__)     # {'x': 1, 'y': 2, 'z': 99}

That dict is what makes Python attributes feel effortless — any name can be attached to any instance at any time, no declaration required. It's also two costs at once: every single instance pays for its own dict (real memory, one per object, even though every Point has exactly the same two field names), and nothing stops p.yz = 5 from silently succeeding when it should have been p.y = 5 — a typo that becomes a brand-new attribute instead of an error.

2 · __slots__: declare the fields, lose the dict

A class body can set __slots__ to a tuple of the exact attribute names instances are allowed to have. Do that, and Python stops giving instances a __dict__ at all — the named slots become the only place those values can live:

class Point:
    __slots__ = ("x", "y")

    def __init__(self, x, y):
        self.x = x
        self.y = y

p = Point(1, 2)
p.x, p.y                  # (1, 2) — reading and writing declared slots works exactly as before

p.__dict__                # AttributeError: 'Point' object has no attribute '__dict__'
p.z = 99                  # AttributeError: 'Point' object has no attribute 'z'

Everything about using p.x and p.y is unchanged — __slots__ doesn't touch how declared attributes work. What disappears is the escape hatch: no __dict__ exists to catch an undeclared name, so p.z = 99 — and, more usefully, a typo like p.yz = 5 — raises AttributeError immediately instead of quietly creating a new attribute nobody will ever read. This was verified live against this course's own interpreter (Python 3.12.3, not just read from docs): both the missing-__dict__ and the undeclared-attribute cases raise exactly that AttributeError, on the first attempt.

The real payoff isn't the error message — it's when it fires. Without __slots__, p.yz = 5 is indistinguishable from correct code right up until something later reads p.y and gets a stale or default value, far from where the typo was written. With __slots__, the same typo fails on the exact line that made it — the same "fail fast, fail where the mistake happened" win Day 33's Enum gave a misspelled status string.

3 · The memory case, measured

The saved __dict__ is not a small win at scale. Measured live in a scratch script against this course's interpreter — 100,000 plain instances versus 100,000 slotted instances of the same two-field class:

100000 plain instances:   13,600,000 bytes total, 136.0 bytes/instance
100000 slotted instances:  4,800,000 bytes total,  48.0 bytes/instance
ratio: 2.83x

Nearly a 3x reduction per instance, entirely from removing one small dict each object no longer needs. This matters exactly when a program holds a lot of small, fixed-shape objects at once — millions of parsed rows from Day 6's CSV pipeline, or graph nodes, or anything read from a large file and kept in memory rather than streamed. It's not a general "always add this" habit: a class with only a handful of live instances saves nothing worth mentioning, and __slots__ is one more thing to keep in sync if fields change later.

4 · __slots__ and inheritance: every class in the chain must opt in

This is the detail worth being careful with, and it was checked live rather than assumed: a subclass that doesn't declare its own __slots__ gets a __dict__ back anyway — even if its parent class declared slots.

class Base:
    __slots__ = ("a",)

class Child(Base):
    pass                  # no __slots__ declared here

c = Child()
c.a = 1
c.anything_at_all = 99   # works — Child instances have a __dict__ after all

Confirmed against docs.python.org's data model reference and reproduced live: Child here has a real __dict__, and the memory/typo-safety benefit is gone for it — silently, with no error telling you it happened. The fix is what you'd guess: every class in the inheritance chain that wants the guarantee must declare its own __slots__, listing only the fields that class adds (not the parent's, which stay in the parent's own slots):

class Base:
    __slots__ = ("a",)

class Child(Base):
    __slots__ = ("b",)    # only the NEW field — "a" is already in Base's slots

c = Child()
c.a, c.b = 1, 2       # fine — both slots exist, across two classes
c.z = 3                  # AttributeError — no __dict__ anywhere in the chain now

5 · With @dataclass: one keyword, same tradeoff

Day 7's @dataclass writes __init__, __repr__, and __eq__ from a list of typed fields. Since Python 3.10, it can write __slots__ from that same field list too — pass slots=True and the fields that were already being declared do double duty:

from dataclasses import dataclass

@dataclass(slots=True)
class Point:
    x: int
    y: int

p = Point(1, 2)
print(p)              # Point(x=1, y=2) — __repr__ still generated, unaffected
Point(1, 2) == Point(1, 2)   # True — __eq__ still generated, unaffected
p.z = 5                # AttributeError — no __dict__, exactly like a hand-written __slots__

Verified live rather than assumed from docs: dataclass(slots=True) runs cleanly on this course's Python (3.12.3), and __repr__/__eq__ behave exactly as they did without it — slots=True only removes the dict, nothing else about Day 7's generated methods changes. Nothing here is free forever, though: @dataclass(slots=True) was added in Python 3.10 specifically (confirmed against the dataclasses docs), so it's unavailable on anything older, and passing a class-level default like region: Optional[str] = None still works as before — the caveats worth knowing about but skipped today are around __init_subclass__ and weak references, both edge cases this course's data-shaped classes don't hit.

Q: "What does __slots__ actually do, and when would you use it?" A strong answer, out loud: "It replaces the per-instance __dict__ every plain object carries with a fixed set of named slots declared on the class. Two effects: less memory per instance, since there's no dict to allocate, and any attribute not in the list raises AttributeError immediately instead of silently succeeding — which turns a typo'd attribute name into a bug caught on the spot rather than a value that's quietly wrong somewhere downstream. I'd reach for it on a class I'm instantiating a lot of — parsed records, graph nodes — where the field list is genuinely fixed. I wouldn't bother for a handful of instances, and I'd remember that every subclass in the hierarchy needs its own __slots__ too, or the dict quietly comes back on that subclass." The signal: naming both effects (memory and the typo-safety win), not just one, and knowing the inheritance gotcha.

Where pandas goes from here: nothing to demonstrate — a DataFrame already stores every column in one shared, typed memory block rather than one dict per row, so pandas gets __slots__'s memory win for free at the table level, by a completely different mechanism. Not covered here; that's data/'s territory, and this is the only sentence in this lesson that names it.
