Delivery semantics: the three guarantees hiding behind every retry

Lesson 10 named at-least-once delivery for background jobs, and it already has its own glossary row — a job might run twice, but it's never silently dropped. Lessons 26, 29, and 87 all leaned on that same guarantee without ever naming its two siblings: the opposite failure mode, and the guarantee everyone secretly wishes they had. Ninety lessons in, "exactly-once" has appeared six times in passing, always as something a mechanism explicitly does not promise, and never once taught as its own term next to the other two. Today names all three side by side.

1 · Three answers to "what happens on a crash mid-delivery"

Every queue, every retry, every message handoff between two systems has to answer the same question: a crash or a network failure happens at the worst possible moment — right between "the work happened" and "the system was told the work happened" — so what does the receiver end up with? There are exactly three possible answers, and each has a name.

At-most-once delivery is what you get by doing nothing extra: send it, and if it fails, don't retry. Zero duplicates, ever — but a crash between "sent" and "confirmed" means the message is gone for good, silently. At-least-once delivery, Lesson 10's term, is the opposite trade: retry until confirmed, which means a crash in that same window produces a duplicate instead of a loss — the work happened, but the sender couldn't tell, so it tries again. And exactly-once delivery is the one everyone actually wants: never lost, never duplicated, no matter how many crashes happen along the way.

The uncomfortable fact: exactly-once delivery, in the strict sense — guaranteed by the network and the messaging system alone, across two fully independent processes — is not achievable in the general case. The sender can never be certain the receiver got a message without an acknowledgment, and that acknowledgment can itself be lost, which puts the sender right back at the same fork: retry (risking a duplicate) or don't (risking a loss). This isn't a tooling gap waiting on a smarter queue — it's a consequence of networks being unreliable, the same root cause behind Lesson 84's reason two-phase commit makes a poor practical fit for independent services.

2 · So what do systems that advertise "exactly-once" actually mean?

Lesson 29's outbox pattern said it outright: "no practical mechanism across two separate systems can promise [exactly-once] delivery." Lesson 87's CDC lesson and Lesson 72's event-driven vocabulary lesson both drew the same boundary. When a real system claims exactly-once, it almost never means exactly-once delivery in the strict network sense — it means exactly-once processing effect, built on top of ordinary at-least-once delivery plus one more ingredient this course already has a name for: an idempotent receiver. Lesson 26's idempotency key is exactly that ingredient. The message or job may physically arrive twice — delivery is still only at-least-once — but the receiver recognizes the duplicate and plays back the first result instead of redoing the work, so the observable effect is as if it happened exactly once.

The pattern repeats across three lessons: Lesson 10's job queue (retry until confirmed, handler checks a sent_at column first), Lesson 26's idempotency key (retry the POST, server replays the remembered result), and Lesson 29's outbox relay (retry the publish, subscriber checks "have I already shipped this order?" first) are the same shape three times. None of them achieve exactly-once delivery. All three achieve exactly-once effect, by pairing at-least-once delivery with an idempotent consumer. That pairing — not a smarter queue — is how "exactly-once" gets built in practice.

At-most-once is not a lesser, forgotten option — it's the correct choice for a specific class of work: a best-effort metrics ping, a non-critical log line, a cache-warming hint. Losing one occasionally is cheaper than the bookkeeping either of the other two guarantees demands. The mistake isn't choosing at-most-once; it's choosing it by accident, for something like a payment or an order, by writing a handler that doesn't retry and never noticing the silent-loss risk that choice carries.

Q: "Does your event system guarantee exactly-once delivery?" A strong answer, out loud: "No system I'd build claims strict exactly-once delivery, because across two independent processes connected by an unreliable network, that's not achievable in the general case — the sender can never be fully certain the receiver got a message, since the acknowledgment itself can be lost. What I'd actually build is at-least-once delivery, same as our outbox relay already does: retry until confirmed, which means an occasional duplicate instead of a silent loss. Then I'd make the consumer idempotent — check whether this message's effect already happened before applying it again, the same idempotency-key pattern we use for retried POSTs. The combination behaves like exactly-once from the outside, even though delivery itself is only at-least-once underneath. If a vendor claims true exactly-once delivery, I'd ask what they mean by it, because usually it's this same pairing with a different name." The signal: not treating "exactly-once" as a checkbox a tool provides, and correctly locating where the real work happens — the idempotent receiver, not the delivery mechanism.

Scope line

MISSION.md excludes distributed systems beyond vocabulary level, and the formal proof of why exactly-once delivery is impossible — the two-generals-problem framing, consensus-protocol depth, or how a specific message broker's "exactly-once" mode is actually implemented internally — drifts past that line. The point here is the vocabulary and the trade-off: three names for three failure modes, and the recognition that "exactly-once" in practice always means at-least-once delivery plus an idempotent receiver, not a fourth, better delivery mechanism.
