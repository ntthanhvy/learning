Configuration: what belongs in code, what belongs in the environment

1 · The frontend habit that doesn't survive

You already have a .env file. A Vite or Next.js project usually has one sitting at the project root with something like VITE_API_BASE_URL=https://api.example.com — and if it leaked into a public repo tomorrow, the damage would be someone learning your API's hostname. Low stakes, because anything in a frontend .env ships to the browser anyway; there's no real secret to keep, just build-time convenience.

The habit that doesn't survive the jump: on a backend, the file with the same name and the same shape routinely holds a database password, a signing key for session tokens, or a third-party API credential. Same filename, same instinct to "just put the value somewhere and read it" — completely different stakes if it ends up in git log instead of on the machine running the process. The question "did this get committed?" goes from a shrug to an incident.

2 · The Twelve-Factor rule: config is not code

The Twelve-Factor App states this as a strict rule, not a style preference: config must be separated from code. Its definition of config is specific — anything that varies between deploys. A database connection string that points at one host in dev and a different host in production is config. A per-environment feature toggle is config. Credentials are config. The application's logic — what a PATCH /orders/{id} handler actually does — is not config, because that code should behave identically whether it's running against the dev database or the production one; only where it points changes.

Environment variables are the standard mechanism for supplying config, precisely because they're outside the codebase by construction — nothing about setting DATABASE_URL in a deploy's process environment requires touching a file that's tracked in version control. The named anti-pattern is a checked-in configuration file with a block per environment — a config.yaml with a [dev] section, a [staging] section, a [production] section, all committed side by side. It looks organized, but two things go wrong with it in practice: someone deploying a change always has to remember which block is "live" right now, and a file that already holds real production values invites pasting a real secret into it out of habit, the exact moment a value that should never be committed gets committed. Env vars sidestep both — there is no "which block" to get wrong, because only one value exists per running process, supplied by whoever launched it.

3 · Secrets vs. non-secrets — and this exact course's own example

Not every config value is a secret. A port number, a log level (Lesson 13's DEBUG/INFO/WARN/ERROR), a feature flag that's on in staging and off in production — these vary between deploys, so they're config by the Twelve-Factor definition, but leaking one isn't a security incident. The other direction always holds, though: every secret — a database password, a JWT signing key, a third-party API token — is config, because it too varies (or should be rotatable) per environment, and it must never be hardcoded or committed regardless of how harmless it looks in a diff.

This isn't hypothetical — this exact course's own progress-tracking setup, described in NOTES.md, is a real, working instance of the pattern being taught, not a textbook example. The connection string that lets bin/record-progress write to this course's Neon database lives in ~/.config/learning/db.env, chmod 600 so only its owner can even read it, holding one line: LEARNING_DB_URL=postgres://.... It is never committed to this repository. bin/record-progress reads it with exactly the fallback this section describes:

if [ -z "${LEARNING_DB_URL:-}" ]; then
  source ~/.config/learning/db.env
fi

If the environment already has LEARNING_DB_URL set (true in CI), the script uses that; otherwise it falls back to sourcing the untracked, permission-locked file on disk. One script, two environments, zero copies of the credential inside version control — separation of config from code, running in this course's own toolchain every time a lesson gets recorded.

4 · Fail fast at startup, not deep inside a request handler

Reading config with os.Getenv is easy; deciding what to do when a required value is missing is where the design choice actually lives. The wrong version reads a blank string, doesn't check it, and lets it flow forward — the process starts up looking healthy, and minutes (or hours) later some unrelated line panics on a nil database handle, at a moment that has nothing to do with the actual cause. The right version checks at startup, before the process ever accepts a request, and refuses to boot if something required is missing:

type Config struct {
    DatabaseURL string
    Port        string
}

func loadConfig() (Config, error) {
    dbURL := os.Getenv("DATABASE_URL")
    if dbURL == "" {
        return Config{}, errors.New("DATABASE_URL is required but not set")
    }

    port := os.Getenv("PORT")
    if port == "" {
        port = "8080" // sane default, not a secret
    }

    return Config{DatabaseURL: dbURL, Port: port}, nil
}

func main() {
    cfg, err := loadConfig()
    if err != nil {
        fmt.Fprintln(os.Stderr, "startup failed:", err)
        os.Exit(1)
    }
    // ... use cfg.DatabaseURL, cfg.Port to start the server
}

PORT gets a default because a missing port number has an obviously reasonable fallback — 8080 is a fine guess, and guessing wrong just means a config value someone can override later. DATABASE_URL gets no default, because there is no reasonable guess for "which database" — an empty value there is always a misconfiguration, and loadConfig returns an error immediately so main can refuse to start rather than hand a broken Config to code that assumes it's valid. Fail fast: the failure happens at the earliest possible moment, with a message that names exactly what's missing, instead of surfacing later as a confusing symptom several layers away from the actual cause.

5 · Config values you've already met

This isn't the first config this course has touched — it's the first time naming it as one subject. Lesson 6/8's database connection string was this course's very first example of "a value that varies per environment": the same handler code runs against a different Postgres instance in dev, staging, and production, and only the connection string changes between them. Lesson 18's pgxpool knobs — MaxConns, MinConns, MaxConnLifetime, MaxConnIdleTime — were shown hardcoded directly in a newPool function for clarity, but by this lesson's rule they're config too: a pool sized for a low-traffic staging environment is very likely wrong for production, so those four numbers belong in the environment (or a config layer read from it) rather than baked into the binary, exactly like DATABASE_URL and PORT above.

The one-line version: if a value has to change when you deploy the same code somewhere else, it's config — it goes in the environment, never in a checked-in file with per-environment blocks, and a missing required one should stop the process at startup, loudly, not fail silently three requests later.

Q: "How do you handle configuration across environments?" A strong answer, out loud: "I keep config strictly separate from code — anything that varies between dev, staging, and production, like connection strings, credentials, or pool sizes, comes from the environment rather than being hardcoded or checked into a per-environment config file. Checked-in per-environment blocks are the pattern I avoid specifically, because it's easy to lose track of which block is actually live, and having real values sitting in a tracked file invites someone pasting a secret into it out of habit. At startup I validate that every required value is present and fail immediately with a clear error if something's missing, rather than letting a blank value propagate until it causes a confusing crash deep in a request handler. And secrets specifically never go in version control — they live in the environment or a secrets manager, read at runtime." The signal: naming the checked-in-file anti-pattern specifically, and fail-fast validation, not just "I use environment variables."
