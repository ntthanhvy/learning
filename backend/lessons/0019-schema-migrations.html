Schema migrations: evolving a table without breaking anything

MISSION.md's first success criterion promises designing a data model "entities, relationships, constraints, and a migration plan — and explain the trade-offs." Lesson 2 covered entities and relationships, Lesson 5 covered indexes as part of that model — but the migration plan itself has never been its own lesson. This is that lesson: how a schema changes after it's already live, without breaking the code currently running against it.

1 · What a migration actually is

A migration is a small, ordered SQL script that changes the schema — add a column, add an index, add a constraint — checked into the same git repository as the code that depends on it. A migration tool (in the Go ecosystem, golang-migrate is the standard) keeps a table in the database itself recording which migrations have already run, so it can apply exactly the ones a given environment is missing, in order, once each.

Think of it as the schema's equivalent of git commit history. You wouldn't hand-edit a colleague's checked-out working tree to match yours; you'd give them a commit to apply. A migration is the same idea for the shape of the database: instead of one person running ALTER TABLE by hand against production, the change is a file, reviewed in a PR (Lesson 14), and applied the same way in every environment — a teammate's laptop, staging, production — by running the same tool against the same script.

2 · The hazard: old code and new code, same database, at once

Lesson 8 established that a "stateless" server actually runs as many instances behind a load balancer, and a rolling deploy replaces them one at a time rather than all at once. For the length of that rollout — seconds to minutes — old code and new code are both handling live requests against the exact same database. A migration doesn't get that same grace period: it either hasn't run yet, or it has, for every instance, all at once.

That gap is where migrations break things. Add a required column — NOT NULL, no default — and every row written by an old-code instance that doesn't know the column exists will fail that constraint outright. Drop a column the old code still reads, and every one of its queries breaks the moment the column disappears, not when the old code is eventually retired. The migration ships instantly; the code doesn't.

3 · The safe recipe: expand/contract

Lesson 16 drew a line between backward-compatible changes (existing, correctly-written clients keep working) and breaking changes (they don't) for API contracts. Schema changes split the exact same way, and the fix is the same shape too: never take a single breaking step — take several backward-compatible ones in sequence, known as the expand/contract pattern.

To add a required column with zero downtime:

  1. Expand: a migration adds the column nullable, or with a DEFAULT. On its own this step is fully backward-compatible — old code doesn't know the column exists and keeps working exactly as before.
  2. Deploy new code that writes the column on every new row, but still tolerates it being NULL when reading an existing row (see the Go snippet below). This can roll out instance by instance same as any deploy.
  3. Backfill the existing rows — a script or background job (Lesson 10) that computes and writes a value for every row that predates the column.
  4. Contract: only once every instance is confirmed running the new code and the backfill is complete, a second migration adds the NOT NULL constraint.

Each step alone is backward-compatible. It's only the full sequence — expand, deploy, backfill, contract — that gets you to "required," and that's the trade-off worth naming out loud in review: a same-day "just add a required column" migration is fast to write and unsafe to run; the four-step version is slower but never breaks a request mid-rollout.

4 · Dropping a column: the same pattern, reversed

Removing a column safely runs the identical logic backwards. Drop the column first and every instance still reading it — old or new, doesn't matter which — breaks immediately. Instead: deploy code that stops reading the column, deploy code that stops writing it, confirm every instance is on that code, and only then run the migration that drops it. Write before read, when adding; read before write, when removing — in both directions, the migration that actually changes structure comes last, after the code no longer depends on the old shape.

The rule underneath both recipes: a migration is safe exactly when every currently-running version of the code — old and new alike — still works after it applies. If that's not true, split the change into more steps until it is.

5 · Building an index without blocking writes

Lesson 5 covered when an index is worth adding; it didn't cover how to add one to a table that's already taking live traffic. A plain CREATE INDEX takes a lock on the table for the entire build — every write to that table queues up and waits until the index finishes, which on a large table can be minutes of stalled writes in production. CREATE INDEX CONCURRENTLY builds the same index without holding that lock, so writes keep flowing the whole time.

The trade-off is real, not free: a concurrent index build takes noticeably longer than a locking one (it scans the table more than once to avoid holding the lock), and if it fails partway — a conflicting statement, a crash — it can leave behind an invalid index that Postgres won't use and won't clean up automatically; you have to notice, drop it, and retry by hand. For any table serving live traffic, that trade is almost always worth it anyway: a slower build beats a frozen table.

6 · Rollback vs. fix-forward

Migration tools like golang-migrate support paired files — a .up.sql that applies the change and a .down.sql that's meant to reverse it, so a bad migration can theoretically be rolled back. In practice, many production teams run a fix-forward policy instead: a bad migration is never rolled back — a new migration is written that corrects it, and history only ever moves forward.

The honest reason: a down migration only really works for changes that never destroyed anything. Reversing "add a nullable column" is trivial — drop it, no data lost. Reversing "drop a column" is not: the values that column held are already gone by the time anyone decides to roll back, and no .down.sql can conjure deleted data back into existence. Once a migration has destroyed or overwritten data, "rollback" is a script that looks reassuring but can't actually restore the pre-migration state — which is exactly why the expand/contract sequence in section 3 defers every destructive step (the final NOT NULL, the actual column drop) until it's provably safe, rather than leaning on rollback as the safety net.

7 · Reading a column that might still be NULL

Concretely, step 2 of the expand recipe means a store method has to handle the column not being populated yet. database/sql's sql.NullString makes that an explicit, compile-time-checked case instead of a runtime surprise:

func (s *Store) ShippingRegion(ctx context.Context, orderID int64) (string, error) {
    var region sql.NullString
    err := s.db.QueryRowContext(ctx,
        `SELECT shipping_region FROM orders WHERE id = $1`, orderID,
    ).Scan(®ion)
    if err != nil {
        return "", err
    }
    if !region.Valid {
        return "unknown", nil // old row, not backfilled yet — don't crash
    }
    return region.String, nil
}

region.Valid is false exactly for rows the backfill hasn't reached yet — an old row written before the column existed. Handling that case explicitly (falling back to a sentinel value here) is what makes the code in step 2 safe to deploy before the backfill in step 3 has even started.

Q: "Walk me through adding a required column to a table with live traffic, zero downtime." A strong answer, out loud: "I'd use the expand/contract pattern rather than one migration. First, expand: a migration adds the column nullable, or with a default — that alone is backward-compatible, since old code just ignores a column it doesn't know about. Then I'd deploy new code that writes the column on every new row but still tolerates NULL on read, so it's safe to roll out instance by instance during a normal deploy. Next, backfill the existing rows with a script or background job. Only once every instance is confirmed on the new code and the backfill's done would I ship a second migration adding the NOT NULL constraint — that's the contract step. Each individual step is backward-compatible on its own; it's the sequence that gets me to 'required' safely." The signal: naming expand/contract by name and explaining why the sequence matters, not just "add the column."
