Soft delete: keeping the row, hiding the record

Every lesson so far that touched a row's lifecycle — Lesson 2's entities, Lesson 12's ownership checks, Lesson 19's migrations — has quietly assumed "delete" means DELETE FROM and the row is gone. Lesson 19 even said it outright: once a migration destroys data, there's no getting it back. Today's the lesson on the alternative almost every real product actually uses instead — and the constraint-and-query cost of choosing it.

1 · Why a hard DELETE is often the wrong tool

Picture an accounts table with orders, invoices, and support tickets all holding a foreign key back to it (Lesson 2's join-table territory, just via a plain FK here). A user closes their account. Run DELETE FROM accounts WHERE id = $1 and one of two things happens: either the delete fails outright, because Postgres won't let you remove a row something else still points at, or — worse — it was allowed to CASCADE, and every order that account ever placed disappears with it. Neither is what "close my account" should mean. The order history, the invoices, the audit trail of what happened — a support agent, a finance report, or the user themselves reopening the account later still needs that data to exist.

Frontend-habit trap: a frontend "delete" almost always means "remove from my local list" — the item vanishes from the UI, and what happens server-side is someone else's problem. On the backend, you are that someone else, and "gone from the list" and "gone from the database" are two very different decisions with very different consequences.

The fix most products reach for is soft delete: instead of removing the row, mark it deleted and leave it exactly where it is.

2 · The shape: one column, one filter

The common version adds a single nullable timestamp column:

ALTER TABLE accounts ADD COLUMN deleted_at timestamptz;

NULL means "still active" — the default and normal state for every existing row. A non-null value means "deleted at this exact moment," and doubles as an answer to "when." DELETE FROM never runs; "deleting" a row becomes an UPDATE:

-- "deleting" an account
UPDATE accounts SET deleted_at = now() WHERE id = $1 AND deleted_at IS NULL;

-- every normal read has to say so explicitly
SELECT * FROM accounts WHERE id = $1 AND deleted_at IS NULL;

That second query is the entire cost of this pattern in one line: a soft-deleted row still physically exists, so every query that shouldn't return it needs its own WHERE deleted_at IS NULL. Forget it once, in one handler, in one report, in one admin script — and a "deleted" account quietly reappears somewhere it shouldn't. A hard delete never has this problem, because there's nothing left to accidentally select.

// GetAccount reads a single account, but only if it hasn't been soft-deleted.
// A plain SELECT with no deleted_at filter would happily return a "deleted"
// row to a caller who has no business seeing it.
func GetAccount(ctx context.Context, db DB, id int64) (name string, err error) {
    row := db.QueryRowContext(ctx, `
        SELECT name FROM accounts
        WHERE id = $1 AND deleted_at IS NULL`, id)
    if err := row.Scan(&name); err != nil {
        if errors.Is(err, sql.ErrNoRows) {
            return "", ErrNotFound // same 404 whether truly missing or soft-deleted
        }
        return "", err
    }
    return name, nil
}

// SoftDeleteAccount marks an account deleted instead of removing the row —
// existing foreign keys (orders.account_id, invoices.account_id) stay valid,
// and the row can still be read directly by id for audit/support purposes.
func SoftDeleteAccount(ctx context.Context, db DB, id int64, now time.Time) error {
    res, err := db.ExecContext(ctx, `
        UPDATE accounts SET deleted_at = $2
        WHERE id = $1 AND deleted_at IS NULL`, id, now)
    if err != nil {
        return err
    }
    n, err := res.RowsAffected()
    if err != nil {
        return err
    }
    if n == 0 {
        return ErrNotFound // already gone, or never existed — same response either way
    }
    return nil
}

Notice GetAccount returns the same ErrNotFound whether the row never existed or was soft-deleted — from the caller's side of the API contract, "deleted" and "never was" should usually look identical (a 404, per Lesson 3), even though internally the row is still sitting right there in the table.

3 · The constraint problem soft delete quietly creates

A plain UNIQUE constraint on email stops working the way you'd expect the moment soft delete enters the picture. Someone closes their account, then later signs up again with the same email — a completely normal thing for a user to do — and the second signup fails, because the first row, soft-deleted or not, still holds that email value and the constraint doesn't know or care about deleted_at. The fix is Lesson 5's indexing lesson coming back with a new use: a partial index:

CREATE UNIQUE INDEX accounts_email_unique_live
  ON accounts (email)
  WHERE deleted_at IS NULL;

This index only covers rows where deleted_at IS NULL — "live" rows. Two live rows still can't share an email, exactly as before. But a soft-deleted row's email is invisible to this index entirely, so a new signup with that same address is free to succeed. A plain table-wide UNIQUE constraint has no WHERE clause to give it this distinction — it protects every row equally, dead or alive, which is precisely the wrong rule once "dead" rows are still physically present.

4 · When soft delete is the wrong call too

Soft delete is not a universal default — it trades "deleted" for "always filtered," and that trade isn't free. Two cases where a real DELETE is still the right tool:

  • Legally required erasure. GDPR's "right to erasure" and similar regulations can require that personal data actually stop existing, not merely stop being queried by default — a deleted_at flag alone doesn't satisfy "erase this person's data," since the data is all still sitting right there in the table.
  • Data with no downstream reason to keep it. A password-reset token, an expired idempotency key (Lesson 26) — nothing reads these once they've served their purpose or expired, and nothing references them by foreign key. Soft-deleting something nobody will ever want back just grows the table forever for no benefit; a hard delete (often on a schedule, not per-request) is simpler and correct.

The deciding question is the same shape every time: does something else still legitimately need this row to exist — a foreign key, an audit trail, a "can I undo this" support request — or is a plain frontend-shaped "it's gone" actually true here too? Soft delete earns its cost only in the first case.

Q: "A user asks you to delete their account. Walk me through what actually happens in the database." A strong answer, out loud: "I wouldn't run a hard DELETE, because that account almost certainly has orders, invoices, or other rows pointing at it by foreign key — either the delete fails outright, or a CASCADE takes all that history down with it, which isn't what 'close my account' should mean. I'd add a deleted_at timestamp column, set it on 'delete' instead of removing the row, and make every normal read filter WHERE deleted_at IS NULL so the account stops appearing anywhere a live user should see it. The one thing I'd watch for is any UNIQUE constraint on a column like email — a plain table-wide UNIQUE would block the same email from signing up again later, so that needs to become a partial unique index scoped to deleted_at IS NULL instead. And if there's a legal erasure requirement involved, soft delete alone doesn't satisfy it — that's a real DELETE, possibly on a retention schedule." The subtext: naming the constraint problem unprompted is what separates "knows the deleted_at trick" from having actually shipped it.
