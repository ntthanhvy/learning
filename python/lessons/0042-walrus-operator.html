The walrus operator: :=

Day 38's regex lesson used if m := re.search(...): ... in passing, without stopping to explain the := itself. This short lesson closes that loose thread: what an assignment expression is, the two or three places it genuinely helps, and when to leave it alone.

Bridge from SQL: SQL has no equivalent — every SQL expression is already allowed to appear where it's needed, there's no separate "statement vs. expression" split to work around. The walrus operator exists purely to plug that gap in Python: it lets a name be bound to a value without leaving the expression context that needs it, such as inside a while or if condition.

1 · What := actually does

A plain name = value is a statement — it does not produce a value usable anywhere else, so it can never appear inside a while condition, an if condition, or a comprehension. name := value is an expression instead: it binds value to name, exactly like = does, but the whole thing also evaluates to that bound value — so it can sit anywhere an expression is allowed.

# plain assignment -- a statement, cannot be used inside an if/while test
n = 5

# assignment expression -- binds n AND is itself usable as a value
print(n := 5)   # prints 5 -- the := expression's value is 5, same as n

Outside of that one difference — usable inside a larger expression — a walrus binds a name into the surrounding scope exactly the way = would. It is not a new kind of variable or a special scope; it is the same assignment, just spelled so it fits where a statement can't go.

2 · Where it earns its keep: avoiding a repeated call

The clearest case is a while loop that needs to call something, test the result, and use that same result inside the loop body. Without a walrus this needs the call written out twice — once before the loop to prime it, once again at the end of the loop body to advance it:

# traditional shape -- the same call appears in two places
chunk = read_chunk()
while chunk != "":
    process(chunk)
    chunk = read_chunk()

# with walrus -- one call, one place, same behavior
while (chunk := read_chunk()) != "":
    process(chunk)

Verified live: both forms collect identical results, but the walrus version has the call site once instead of twice — one less place for the two copies to quietly drift apart after an edit. The same shape covers Day 38's exact example: if (m := re.search(pattern, text)) is not None: use(m) binds the match object and tests it in one line, instead of a separate m = re.search(...) line followed by the if.

3 · Where it earns its keep: avoiding a double computation in a comprehension

A comprehension that filters on a computed value and also uses that value in its output expression would otherwise compute it twice per passing element — once for the if, once for the result:

# without walrus -- expensive(x) runs twice for every x that passes the filter
result = [expensive(x) for x in nums if expensive(x) > 5]

# with walrus -- expensive(x) runs once per x, period
result = [y for x in nums if (y := expensive(x)) > 5]

Verified live with a print-tracing expensive(): the non-walrus version called it 8 times for a 5-element list (twice for each of the 4 elements that passed the filter after also being called once for the failing element); the walrus version called it exactly 5 times — once per element, full stop.

Gotcha, confirmed live: the bound name leaks past the comprehension. A comprehension normally has its own scope — a plain loop variable like x above does not exist after the comprehension finishes. A walrus-bound name is the one exception: y from the example above is still readable afterward, holding whatever it was last set to during the comprehension's run. This is intentional (the whole point is to make a computed value available outside the throwaway comprehension scope), but it means a walrus name inside a comprehension is not private the way the comprehension's own for variable is — pick a name that's fine to have hanging around afterward, or use it immediately and don't rely on the leaked value later.

4 · When not to use it

PEP 572, which introduced the walrus operator, is explicit that it should be used sparingly — only where it removes real duplication, not as a way to cram more logic onto one line. A plain = on its own line is almost always more readable than a walrus stuffed into an if or a comprehension just to save a line:

# harder to read -- walrus adds nothing here, there's no duplication to avoid
if (result := compute()) > threshold:
    log(result)

# plainer, and just as short -- prefer this when there's only one use of the value
result = compute()
if result > threshold:
    log(result)

The rule of thumb: reach for := only when the alternative is genuinely calling the same thing twice or computing the same thing twice — a while loop's advancing condition, or a comprehension's filter-and-use pattern from section 3. If a plain assignment on the line above already reads cleanly, leave it as a plain assignment.

Q: "What's the walrus operator for, and when would you avoid it?" A strong answer, out loud: "It's an assignment that's also an expression, so it can sit inside a while or if condition or a comprehension instead of needing a separate statement first. I'd use it to avoid calling or computing the same thing twice — priming and advancing a while loop with one call site instead of two, or a comprehension that filters on a computed value and reuses it in the output. I'd avoid it anywhere a plain assignment on its own line already reads fine — PEP 572 itself says to use it sparingly, and stacking it into already-dense lines just to save a line hurts readability for no real gain." The signal: knowing it's a readability tool for one specific duplication pattern, not a style default.

Where pandas goes from here: nothing pandas-specific — := is a general language feature, occasionally seen inside a pandas method chain's lambda for the same "avoid computing it twice" reason taught here. Not demonstrated; this is the only sentence in this lesson that names pandas.
