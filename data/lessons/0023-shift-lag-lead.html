shift(): pulling the previous (or next) row's value alongside

Lesson 22 closed with no single named next candidate, so today's topic comes from a fresh scan: Lesson 11's pct_change() was described as "hand-written as (curr - LAG(curr) OVER (...)) / LAG(curr) OVER (...), which is exactly what pct_change() is doing under the hood" — but the tool that actually IS that LAG()/LEAD(), shift(), was never taught on its own. It's a genuine gap: grepped every lesson body and the glossary, shift() appears nowhere as a taught concept.

1 · The SQL bridge: LAG() and LEAD()

SQL answers "what was this row's previous value" with a window function: LAG(amount) OVER (PARTITION BY customer ORDER BY order_date). pandas' direct equivalent is shift(): it moves every value down (or up) by N rows, in whatever order the DataFrame is currently in.

ordered = clean.sort_values(["customer", "order_date"])
ordered["prev_amount"] = ordered.groupby("customer")["amount"].shift(1)
#   customer  amount  order_date  prev_amount
#0        An   120.0  2026-01-05          NaN
#1        An    42.0  2026-01-10        120.0
#2      Binh    35.5  2026-01-06          NaN
#3      Binh   180.0  2026-01-09         35.5

shift(1) is LAG(amount) OVER (PARTITION BY customer ORDER BY order_date) — each row now carries the value from one row before it, per customer. The first order of each customer has nothing before it, so it comes back NaN — the same "genuinely doesn't exist yet" reasoning as Lesson 3's NaN-not-zero rule.

2 · The other direction: shift(-1) for LEAD()

A negative argument shifts values up instead of down — each row sees what comes next, not what came before:

ordered["next_amount"] = ordered.groupby("customer")["amount"].shift(-1)
#   customer  amount  order_date  next_amount
#0        An   120.0  2026-01-05         42.0
#1        An    42.0  2026-01-10          NaN
#2      Binh    35.5  2026-01-06        180.0
#3      Binh   180.0  2026-01-09          NaN

shift(-1) is LEAD(amount) OVER (PARTITION BY customer ORDER BY order_date). Same mechanism, opposite direction — now the last order of each customer is the one with nothing after it, so that row is NaN instead of the first.

3 · The sharp edge: shift() trusts row order only, same as everything in this family

shift() has no ORDER BY argument of its own — exactly the same warning Lessons 7, 11, and 13 already gave for cumsum(), pct_change(), and rolling(). It shifts whatever physical row order the DataFrame is currently in. Skip the grouping too, and it gets worse than "wrong order" — it bleeds values across customers, since shift() only looks at row position, not who the row belongs to:

## WRONG — no groupby(), just a plain shift on the sorted table
ordered["wrong_prev"] = ordered["amount"].shift(1)
#   customer  amount  order_date  wrong_prev
#0        An   120.0  2026-01-05         NaN
#1        An    42.0  2026-01-10        120.0
#2      Binh    35.5  2026-01-06         42.0   <-- An's amount, not Binh's!
#3      Binh   180.0  2026-01-09         35.5

Binh's first order silently inherits An's last amount (42.0) as its "previous" value — there's no error, no warning, just a quietly wrong number that looks perfectly plausible in a report. This is the single most common way shift() goes wrong in practice: always groupby(key) first when "previous" means "previous for this group," not "previous physical row."

4 · diff() is just shift(), pre-subtracted

ordered["amount"] - ordered["prev_amount"] and ordered.groupby("customer")["amount"].diff() compute the exact same numbers — diff() is a named shortcut for "current minus shift(1)," the same relationship Lesson 11 already showed between pct_change() and a hand-written (curr - LAG(curr)) / LAG(curr):

ordered.groupby("customer")["amount"].diff()
# An:  NaN, -78.0    (42.0 - 120.0)
# Binh: NaN, 144.5   (180.0 - 35.5)

Three related tools now sit side by side: shift() hands you the raw previous/next value, diff() hands you the difference, and Lesson 11's pct_change() hands you the fractional change — all three are the same "look one row over" idea, just returning a different shape of answer.

Rule of thumb: need the raw prior/next value itself (to compare against, to build a custom formula) → shift(). Just need the absolute difference → diff(). Need the percentage change → Lesson 11's pct_change(). All three: sort first, group by key first, or the answer is wrong in a way that won't raise an error.

Q: "How would you find each customer's order-over-order change in pandas, and how does that map to SQL?" A strong answer, out loud: "Sort by customer and date, then groupby(customer) chained with shift(1) for the raw previous value, diff() for the absolute change, or pct_change() for the percentage — they're all the same 'look at the previous row' idea, just returning a different shape of answer. In SQL that's LAG(amount) OVER (PARTITION BY customer ORDER BY order_date) — shift(1) is that window function directly, and shift(-1) is LEAD(). The pitfall I'd watch for is forgetting the groupby: shift() only knows physical row position, not which customer a row belongs to, so skipping the groupby silently pulls in another customer's value instead of raising an error." The signal: naming LAG/LEAD unprompted, and naming the silent-bleed failure mode instead of just the happy path.
