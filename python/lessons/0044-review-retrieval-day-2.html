Day 16 — FastAPI handlers. What one thing decides whether a handler parameter is a path parameter or a query parameter?

Fold-out answer: whether its name appears inside {} in the route decorator's URL string. A path parameter ({user_id} in the URL) is always required — no request missing it can match that route at all. A query parameter is a plain handler parameter not named in the URL, and becomes optional exactly when it carries a default value — the same default-argument rule Day 4 already taught for ordinary functions.

Day 19 — dependency injection. A handler parameter defaults to Depends(get_current_user), and get_current_user itself depends on Depends(get_db). How many times does get_db run for one incoming request?

Fold-out answer: exactly once. FastAPI resolves a whole sub-dependency chain before the handler runs and calls each shared dependency once per request, no matter how many other dependencies in that chain ask for it — confirmed in Day 19 by tracking call order and call count directly with TestClient.

Day 30 — dunder methods. A plain hand-written class defines no __eq__ at all. What does == compare on two of its instances?

Fold-out answer: identity, not value — the same fallback Day 1's is uses. Two separately constructed objects with equal field values compare unequal unless __eq__ is defined to compare by value instead; this is exactly what @dataclass was generating for you automatically back on Day 7.

Day 33 — Enum. Given class Status(Enum): SHIPPED = "shipped", is Status.SHIPPED == "shipped" ever True?

Fold-out answer: no. An Enum member is a distinct object of its own type, deliberately unequal to its underlying value — that's exactly what stops a bare string typo from being silently accepted anywhere a real member is expected, the whole reason to reach for Enum over a plain string in the first place.

Day 34 — match/case. A guard clause's condition (the trailing if on a case) evaluates to False. What happens to that case?

Fold-out answer: that whole case is skipped, and Python moves on to try the next case below it — a guard is only checked after the pattern itself has already structurally matched, and a failing guard rejects the case rather than raising an error or treating the pattern as still matched.

Day 38 — regular expressions. Why does re.match(r"super", "insuperable") return None while re.search(r"super", "insuperable") finds a match?

Fold-out answer: re.match() only checks for a match starting at index 0 of the string — "insuperable" starts with "in", not "super", so it fails even though "super" does occur later, at index 2. re.search() scans the whole string for the pattern occurring anywhere, which is why it succeeds on the same input.
