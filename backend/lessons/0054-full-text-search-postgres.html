Full-text search: why LIKE '%word%' doesn't scale

Every product eventually gets a search box — "find the order," "find the article," "find the user by bio." The reach-for-first tool is LIKE '%word%', and it works right up until the table has real volume. Today: why that query can't use a normal index no matter how you tune it, and the Postgres feature built specifically to fix it.

1 · Why an ordinary index can't help a %wildcard% query

Lesson 5 covered how an index works: a sorted structure the planner can jump into, the way a phone book lets you binary-search a last name. A WHERE title LIKE '%backend%' query breaks that completely. A leading % means "this substring could start anywhere inside the text" — there's no sorted prefix to jump to, so Postgres has no choice but to read every row and scan its full text byte by byte, a sequential scan regardless of how many indexes exist on that column. It gets slower, not faster, as the table grows; ordering "match anywhere" is a fundamentally different problem from ordering "match this exact value or range," which is all a standard B-tree index (Lesson 5's default) is built to answer.

LIKE also has no idea that "run" and "running" are the same idea, or that "the," "a," and "of" barely carry meaning. It's pure byte matching. A user searching "run" gets zero results against a row containing only "running" — technically correct, practically useless for anything called search.

2 · What full-text search actually is

Postgres ships a purpose-built answer: a pipeline that turns free text into a searchable, indexable value instead of treating it as an opaque string. A to_tsvector function does three things to a column's text: splits it into words, drops near-meaningless "stop words" (the, a, of, is), and stems every remaining word to a root form — "running," "runs," and "ran" all normalize toward "run". The output is a tsvector — a compact list of normalized word roots (called lexemes) plus their positions, ready to be matched or indexed. The search side gets the same treatment through to_tsquery, which parses a user's search terms the same way, so "Running" the query matches "runs" in the document — both reduce to the same root.

-- @@ is the full-text match operator: "does this tsvector match this tsquery"
SELECT to_tsvector('english', 'The quick runners are running fast')
       @@ to_tsquery('english', 'run');
-- true -- "running" stems to "run", "the"/"are" were dropped as stop words

3 · Making it fast: the GIN index

Computing to_tsvector on every row for every search would still mean scanning the whole table — the win only lands once that computed value is indexed. Lesson 44 already introduced the GIN index for JSONB's "does this contain that key" queries; full-text search is GIN's other classic use case, for exactly the same structural reason — a tsvector holds many lexemes per row, and GIN maps each lexeme back to every row containing it, an inverted index in the same sense a search engine builds one.

ALTER TABLE articles ADD COLUMN search_vec tsvector
  GENERATED ALWAYS AS (to_tsvector('english', title || ' ' || body)) STORED;

CREATE INDEX ON articles USING GIN (search_vec);

-- now this hits the index instead of scanning every row
SELECT id, title FROM articles
WHERE search_vec @@ to_tsquery('english', 'backend & postgres');

The GENERATED ALWAYS ... STORED column keeps the tsvector automatically in sync on every INSERT/UPDATE — no trigger to hand-write, no risk of the index searching stale text after an edit. That sync isn't free: like any index (Lesson 5's core trade-off), a GIN index on a generated tsvector column adds write-time cost — every insert or update to title/body now also recomputes and re-indexes the tsvector — in exchange for read-time speed on searches.

The mistake this retrains: reaching for LIKE '%word%' or, worse, doing a SELECT * and filtering matches in application code, because it "works" against a small dev database. Both approaches force a full scan on every search and get linearly slower as the table grows — the failure only shows up in production once the table is large enough to matter, the same shape as Lesson 5's "works fine locally, times out in prod" index lesson. If a column needs real text search, tsvector + GIN is the tool built for it, not a workaround.

4 · Where this stops being enough

Postgres full-text search covers a large share of real product search boxes — order notes, support tickets, article bodies, comments — without adding another service. It's not a replacement for a dedicated search engine (Elasticsearch, Typesense, Algolia) once requirements grow into fuzzy/typo-tolerant matching, faceted filtering across many fields, or relevance tuning beyond what ts_rank offers — that's a real architectural jump (a second system to keep in sync with Postgres), out of scope for this course per MISSION.md's own line on infra beyond vocabulary level. The instinct worth keeping: reach for Postgres's own full-text search first for anything that fits in one database, and justify a separate search service only once a concrete requirement — fuzzy matching, faceting, scale — actually demands it.
