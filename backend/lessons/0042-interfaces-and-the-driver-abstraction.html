Interfaces and the driver abstraction: what *pgxpool.Pool is actually standing in for

Lessons 18, 33–40, and last lesson's own snippet all pass a raw *pgxpool.Pool or a hand-named DB parameter into query functions, unexplained. Today: what a Go interface actually is, and why every one of those signatures is quietly an abstraction, not a concrete database.

1 · The parameter type nobody defined

Go back through this course's own snippets: Lesson 18's func leaky(ctx context.Context, pool *pgxpool.Pool) error, Lesson 41's func fetchOrderSummary(ctx context.Context, db DB, orderID int64). One takes a concrete pointer type; the other takes something called DB that was never shown. Both are doing the same thing: naming the shape of what they need, not a specific database. That shape has a name in Go — a interface. It's not a database, a struct, or a class — it's a list of methods. Any type possessing that exact method set satisfies the interface, full stop.

The frontend equivalent you already own. This is the same instinct as coding a component against a { data, loading, error } shape instead of a specific fetch library's response object — anything matching that shape works, whether it came from fetch, a mock in a test, or a different HTTP client entirely. A component that only reads props.items.map(...) doesn't care if items came from Redux, a REST call, or a hardcoded array in Storybook — it only cares that .map exists on it. A Go interface is that same "I only care about the shape" contract, enforced by the compiler instead of by convention.

2 · Implicit satisfaction: the part with no equivalent in most languages

In Java or C#, a class must write implements Queryable to satisfy an interface — the relationship is declared. Go interfaces are satisfied implicitly: if a type happens to have every method an interface requires, with matching signatures, it satisfies that interface automatically. Nothing links them by name; the compiler checks the method set structurally, wherever the interface is used.

// Row is a minimal stand-in for what pgx.Row / *sql.Row actually expose:
type Row interface {
    Scan(dest ...any) error
}

// Querier names the shape "something I can run a query against" —
// not a concrete database at all.
type Querier interface {
    QueryRow(ctx context.Context, sql string, args ...any) Row
}

// fetchOrder depends only on Querier. It has no idea whether the real
// type behind q is a live pgxpool.Pool, a single *pgx.Conn, a *pgx.Tx
// mid-transaction, or a fake with no network at all.
func fetchOrder(ctx context.Context, q Querier, id int64) (Order, error) {
    row := q.QueryRow(ctx, `SELECT id, total_cents FROM orders WHERE id = $1`, id)
    var o Order
    if err := row.Scan(&o.ID, &o.TotalCents); err != nil {
        return Order{}, fmt.Errorf("fetch order %d: %w", id, err)
    }
    return o, nil
}

*pgxpool.Pool (Lesson 18) happens to have a QueryRow method with a matching signature, so it satisfies Querier — nobody had to write that down anywhere in pgx's source or this file. Lesson 41's unexplained DB parameter was exactly this pattern, one level removed: a small interface named for what the function needed, not for the concrete database behind it.

3 · Why bother: the fake that never touches a network

The payoff shows up the moment you need to test fetchOrder without a running Postgres instance. Because the function depends on the Querier shape and not on *pgxpool.Pool specifically, a test can hand it any other type with a matching QueryRow method — including one that returns canned data from memory:

type fakeRow struct { id, total int64 }

func (r fakeRow) Scan(dest ...any) error {
    *(dest[0].(*int64)) = r.id
    *(dest[1].(*int64)) = r.total
    return nil
}

type fakePool struct{}

func (fakePool) QueryRow(ctx context.Context, sql string, args ...any) Row {
    return fakeRow{id: 42, total: 1999}
}

// fetchOrder(ctx, fakePool{}, 42) now runs in a unit test with zero
// network calls and zero running database — same function, same code path.

fakePool never declares any relationship to Querier or to *pgxpool.Pool — it satisfies the interface purely by having a method with the right name and signature. That's the entire reason query functions across this course take an interface parameter instead of *pgxpool.Pool directly: production code passes the real pool, a test passes a fake, and fetchOrder itself never changes.

4 · Where this stops paying off

This is not a call to wrap every parameter in an interface reflexively. If a function only ever runs against the real pool, is never unit-tested in isolation, and never needs to run inside a caller's transaction, a concrete *pgxpool.Pool parameter is simpler to read and just as correct — Lesson 18's own snippets do exactly that, for exhaustion-focused examples where swapping implementations was never the point. Reach for an interface parameter when a function's queries genuinely need to run against more than one thing in practice: the live pool in production, an in-progress *pgx.Tx from a caller composing a larger transaction, or a fake in a test. That is also the shape MISSION.md's "frameworks and ORMs" out-of-scope line is drawing a boundary around — this lesson is the plain interface mechanism underneath, not an introduction to any ORM's repository pattern built on top of it.

Q: "Why would you take an interface instead of *pgxpool.Pool as a function's parameter type?" A strong answer, out loud: "An interface names only the methods I actually call — QueryRow, say — so anything with a matching method set can be passed in: the real pool in production, a *pgx.Tx if this needs to run inside a caller's transaction, or a small fake in a unit test with no database at all. Go satisfies interfaces implicitly, so *pgxpool.Pool doesn't need to declare anything to qualify — it just needs the matching methods. I wouldn't do this everywhere, though — if a function only ever runs against the real pool and is never tested in isolation, a concrete pool parameter is simpler and just as correct." The signal: naming implicit satisfaction and knowing when the abstraction isn't worth it, not just "interfaces are for testing."
