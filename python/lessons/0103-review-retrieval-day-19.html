1 · Three questions, in the original teaching order

Answer each out loud or on paper before reading the fold-out answer. If one is shaky, note it and go fix it in the practice file below rather than only rereading the old lesson.

Day 100 — timeit. Why is timeit.timeit("sorted(data)", setup="data = list(range(1000, 0, -1))", number=1000) written with the list-building code in setup= instead of folded directly into the timed stmt, and what does the call actually return — a total or a per-call average?

Fold-out answer: setup= runs exactly once per call to timeit(), before any timed repetition begins, and its result (the data list) stays available to stmt without being counted toward the timed total — confirmed live, only sorted(data) itself showed up in the measured total, not the list construction repeated a thousand times over. The call returns the total elapsed seconds for all number runs added together, not a per-call average — dividing the returned float by number is on the caller, not something timeit() does automatically.

Day 101 — importlib. What can importlib.import_module(name) do that a plain import json statement cannot, and what does importlib.util.find_spec("nonexistent_name") return instead of raising, when no such module exists?

Fold-out answer: import_module(name) accepts the module's name as an ordinary runtime string — name could come from a config file, a CLI argument, or a dict lookup, decided while the program is running, something a plain import json statement can never do since its name is fixed, written literally in the source before the program ever runs. find_spec() on a missing name returns plain None, with no exception raised at all — confirmed live — letting code check importability before committing to an import_module() call that would otherwise raise ModuleNotFoundError.

Day 102 — array. Why did a measured 100,000-element list of plain ints use roughly 4.4x the total memory of the equivalent array.array('l', ...) holding the same values, and what happens the instant a mismatched-type value is appended to a typed array?

Fold-out answer: a list never stores its values directly — it stores a pointer to each one, and every int is its own separate Python object with its own header overhead on top of the list's own pointer array. An array stores the raw fixed-width value directly, packed back to back, with no per-element object at all — confirmed live, 3,600,056 bytes for the list against 816,640 bytes for the array, on the same 100,000 non-cached ints. Appending a value that doesn't match the array's declared typecode (3.5 into an 'i'-typed array) raises TypeError immediately, checked on every write — a plain list would have accepted the same float silently, mixed right in with the existing ints.
Where pandas/NumPy go from here: nothing pandas- or NumPy-specific today — this review only revisits Days 100-102's benchmarking discipline, runtime-string imports, and packed-storage trade-off, none of which needs a DataFrame or ndarray to demonstrate. Day 102's own boundary callout (NumPy's ndarray generalizing array.array's packed-storage idea to N dimensions plus vectorized math) is recalled by name only, not re-demonstrated.

2 · Why these three, and why no new terms today

Same interleaving logic as every prior review day: a tool for settling a performance claim with a measurement instead of a guess, a tool for deciding at runtime — not in the source — exactly which module or function to load, and a tool for trading a list's flexibility for an array's packed, type-checked storage. Three different mental models pulled from three lessons, not one idea restated three ways. They also share a quieter throughline worth naming: all three replace an assumption with something checked directly — timeit replacing "comprehensions are probably faster" with a measured total, importlib replacing a fixed if/elif chain of names with a lookup resolved at runtime, array replacing "every element is probably the right type" with a TypeError enforced on every single write. Recognizing which of those three "verify, don't assume" shapes a given problem actually needs — not just recalling the function names — is the retrieval goal today.
