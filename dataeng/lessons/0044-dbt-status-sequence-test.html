1 · A gap named on Day 27, never actually closed

Day 27's own data-quality story said this, plainly, about the Kafka consumer: it "never looks at whether status is a real status, whether occurred_at is a sane timestamp, or whether the same order's events arrive in a sensible order." Two of those three got a real fix since: Day 6's accepted_values test covers "is status a real status," and Day 42's assert_column_is_after covers "is occurred_at sane" for exactly one pair, placed_at before delivered_at. The third clause — "the same order's events arrive in a sensible order" — was never built. Grep this project's own test files and the word sequence never shows up next to status anywhere.

It's worth being precise about why Day 42's test doesn't already cover this. assert_column_is_after compares two named columns on one row of int_order_durations — one row per order, already collapsed down to just its placed_at and delivered_at timestamps. It has no way to see accepted or picked_up at all, because those statuses were never selected into that model in the first place, and it has no way to see a duplicate status, because duplicates don't make two columns compare wrong — they make two separate rows of raw.order_events exist, a problem about how many rows there are and what order they're in, not about two columns on the one row a model happened to keep.

A real, not hypothetical, way this bites: Day 6's own consumer is at-least-once, and Days 34/37 showed a rebalance can briefly reassign a partition mid-read. Nothing in this pipeline's design makes it impossible for a retried producer send, a replayed test message, or a redelivered-then-reprocessed event to land a picked_up row for an order that's already delivered, or two accepted rows for the same order. Every one of those rows is individually valid — a real event_id, a real status from the accepted set, a real timestamp — so not_null, unique and accepted_values all pass. Only looking at the sequence catches it.

2 · Build: rank each status, so "in order" becomes a comparable number

A status sequence is really an ordering problem in disguise: placed must come before accepted, which must come before picked_up, which must come before delivered or cancelled. Give that ordering an explicit number, the same way a CASE expression gives any categorical column a comparable rank, in a new intermediate model — one source, one reshape, dbt-internal only, the same shape Day 8 set for this layer:

-- models/intermediate/int_order_status_history.sql
select
    order_id,
    status,
    occurred_at,
    case status
        when 'placed'     then 1
        when 'accepted'   then 2
        when 'picked_up'  then 3
        when 'delivered'  then 4
        when 'cancelled'  then 4
        else null
    end as status_rank
from {{ ref('stg_order_events') }}

delivered and cancelled share rank 4 on purpose: both are terminal states an order reaches exactly once, and neither can legitimately come before the other for the same order — an order that's already delivered should never later show cancelled, or vice versa. Giving them the same rank means any second terminal-state event for one order reads as "no higher than the last one," which is exactly the failure this test needs to catch, not a special case it needs separate logic for.

Mark it ephemeral in dbt_project.yml's existing intermediate: block from Day 8 — nothing to add there, it already applies to every model in this folder.

3 · The test itself: a window function compares a row to the previous row, not another column

Day 42 already established the mechanics of a custom generic test — a {% test %} block in tests/generic/, model and column_name as the first two parameters, anything extra nested under YAML's arguments:. Today's test needs one new SQL idea on top of that: a window function, specifically lag(), to compare a row against the row before it — not another column on the same row, which is all Day 42's test ever needed.

-- tests/generic/test_assert_monotonic_by_group.sql
{% test assert_monotonic_by_group(model, column_name, partition_by_column, order_by_column) %}

with ranked as (

    select
        {{ partition_by_column }} as group_key,
        {{ order_by_column }} as position_column,
        {{ column_name }} as value_column,
        lag({{ column_name }}) over (
            partition by {{ partition_by_column }}
            order by {{ order_by_column }}
        ) as previous_value

    from {{ model }}

)

select *
from ranked
where previous_value is not null
  and value_column <= previous_value

{% endtest %}

partition by order_id is what keeps this test from ever comparing one order's status against a completely different order's — the same per-key isolation Day 5's Kafka partition key already gave this domain for free at the streaming layer; here it's the same idea expressed in SQL, at the warehouse layer, for a different purpose. previous_value is not null excludes each group's very first row, which has nothing before it to compare against and would otherwise always "fail" a <= check against a null it can never be true against anyway — the same null-handling instinct Day 9's point-in-time join and Day 27's own overlap test both already needed.

Wire it onto int_order_status_history.status_rank in a new models/intermediate/intermediate.yml (or add to the existing one from Day 42, if that file already exists in your project):

-- models/intermediate/intermediate.yml -- add alongside Day 42's int_order_durations entry
models:
  - name: int_order_status_history
    columns:
      - name: status_rank
        tests:
          - assert_monotonic_by_group:
              arguments:
                partition_by_column: order_id
                order_by_column: occurred_at
Why this couldn't be a package test either: dbt_utils ships sequential_values, which sounds close — but it checks that one column's own values step by a fixed amount with no gaps (consecutive integers, one row per calendar day), a property of a single ungrouped column. It has no notion of groups at all, so it can't express "monotonic within each order_id, reset for the next one." That's the same package-vs-hand-written line Day 42 already drew: generic enough to be worth checking for, and genuinely not covered once checked.

4 · Verify: it passes on real data, then catches a planted bad sequence

uv run --project ../dbt_env dbt build --select int_order_status_history

Expected, naming the test the same way dbt names every generic test (<macro>_<model>_<column>__<extra args>):

assert_monotonic_by_group_int_order_status_history_status_rank__occurred_at__order_id ... [PASS in 0.02s]

Now prove it has teeth, the same standard Day 3 and Day 42 both set — plant a real bad sequence rather than trust the SQL on faith. Pick an already-delivered order and insert a second picked_up event for it, landing after its own delivered row:

docker compose exec -T postgres psql -U fdp -d fdp -c \
  "INSERT INTO raw.order_events (event_id, order_id, status, occurred_at)
   SELECT gen_random_uuid(), 101, 'picked_up', max(occurred_at) + interval '1 hour'
   FROM raw.order_events WHERE order_id = 101;"
uv run --project ../dbt_env dbt build --select int_order_status_history

Expected — the planted row comes back as the exact failure, because the test's own select * returns the offending record, not just a count:

assert_monotonic_by_group_int_order_status_history_status_rank__occurred_at__order_id ... [FAIL 1 in 0.02s]

Done. PASS=0 WARN=0 ERROR=0 FAIL=1 SKIP=0 TOTAL=1

Order 101's already-delivered status has rank 4; the planted picked_up row also has rank 3, which is <= the previous row's rank (4) by the window's own order by occurred_at — caught, exactly as claimed. Undo the plant before moving on (DELETE FROM raw.order_events WHERE order_id = 101 AND status = 'picked_up' AND occurred_at > (SELECT min(occurred_at) FROM raw.order_events WHERE order_id = 101 AND status = 'picked_up'); — careful to delete only the one you just inserted), rerun, confirm PASS=1 again, then commit models/intermediate/int_order_status_history.sql, the intermediate.yml addition, and tests/generic/test_assert_monotonic_by_group.sql.

One case worth checking by hand before trusting the rank table: an order cancelled early — placed, accepted, cancelled, nothing after — must pass, not fail, even though it never reaches picked_up or delivered. Rank 1 → 2 → 4 is strictly increasing, so the test is correctly silent about it: a shorter-than-usual sequence isn't a sequence violation, and this test was never meant to enforce that every order reaches every status, only that whichever statuses do arrive for one order never go backward or repeat.

Q: "Your pipeline checks that an order's delivered_at comes after its placed_at. Does that cover your event data being in order?" A strong answer, out loud: "No, and it's worth being specific about why not. That test compares two named columns on one already-aggregated row — it can't see the statuses in between, like accepted or picked_up, because they were never selected into that model, and it can't see a duplicate or out-of-order event, because that's a row-count and row-order problem, not a two-column comparison. I closed that separately with a different generic test that ranks each status by where it sits in the order lifecycle, then uses a lag() window function partitioned by order_id and ordered by occurred_at to check that each event's rank is strictly higher than the one before it for that same order. That catches a duplicated status, a status arriving out of sequence, or any event landing after an order is already delivered or cancelled — failure modes that are real here specifically because the Kafka consumer is at-least-once and a rebalance can briefly reassign a partition mid-read, not something I'm testing against a hypothetical." The signal: naming precisely what the first test can and can't see, instead of assuming one timestamp-ordering test already covers "events are in order" in general.

Scope line

This lesson covers one new intermediate model and one new custom generic test using a window function, extending Day 42's custom-generic-test mechanism to a new shape — a cross-row sequence check, not a same-row column comparison. It does not re-derive why Kafka is at-least-once or how a consumer rebalance works (Days 6, 34, 37 already cover both); today only adds the test that would catch a sequence violation those mechanisms can produce, naming the connection once rather than re-teaching it.
