ipaddress: IP addresses as real objects, not strings

Day 116 parsed a URL's netloc out as a plain string — "api.example.com" or, just as often in real logs and configs, a bare IP like "192.168.1.10". A string like that looks fine to read but is easy to get wrong to validate: is it actually a valid address? Is it inside an allowed range? Hand-rolled string splitting and regex (Day 38) both get this wrong at the edges. ipaddress is the standard-library module that turns an IP address and a network range into real objects with the checks already built in.

Why today, specifically: a fresh case-insensitive grep across every lesson, practice file, reference/glossary.html, and RESOURCES.md confirmed ipaddress, mimetypes, binascii, textwrap, stat, tracemalloc, and platform are all zero-hit — genuinely untaught (zoneinfo, also on that watch-list, turned out to already be covered on Day 14 once checked directly, so it's off the list now, not a candidate). selectors, sched, and signal were re-confirmed zero-hit too but still skew toward the OS/event-loop internals MISSION.md's own async-depth scope boundary already excludes. ipaddress won over the other clean candidates because it connects directly to two already-taught lessons rather than standing alone: Day 116's urllib.parse (a netloc is sometimes a bare IP, never validated there) and Day 38's re (the module people reach for first to "validate an IP with a regex," and get wrong at the edges this lesson shows). calendar and socket remain the two longest-standing ruled-out candidates (thin content and scope-depth respectively) and stayed untouched again this round.

1 · Why a string is the wrong representation

A regex built to "validate an IP address" is a classic trap: it's easy to write one that accepts "999.999.999.999" (four groups of digits, but each one out of range) or rejects a perfectly legal shortened IPv6 address. ipaddress.ip_address() does the real parsing — not a pattern match, an actual check that each piece is a valid address — and raises on anything that isn't:

import ipaddress

addr = ipaddress.ip_address("192.168.1.10")
print(type(addr), addr)      # confirmed live: <class 'ipaddress.IPv4Address'> 192.168.1.10

try:
    ipaddress.ip_address("192.168.1.999")
except ValueError as e:
    print(e)   # confirmed live: '192.168.1.999' does not appear to be an IPv4 or IPv6 address

ipaddress.ip_address() picks IPv4Address or IPv6Address automatically from the string's shape — one function covers both, and the result is a real object, not text, so it supports ordering (<, confirmed live: ip_address("192.168.1.5") < ip_address("192.168.1.10") is True — something string comparison alone would get wrong, since "192.168.1.5" < "192.168.1.10" as plain strings is actually False) and useful attributes like .is_private:

print(ipaddress.ip_address("192.168.1.5") < ipaddress.ip_address("192.168.1.10"))  # confirmed live: True
print("192.168.1.5" < "192.168.1.10")        # confirmed live: False -- plain string comparison, wrong answer

print(ipaddress.ip_address("10.0.0.5").is_private)     # confirmed live: True
print(ipaddress.ip_address("1.1.1.1").is_private)      # confirmed live: False

2 · ip_network(): a whole range, with membership built in

Real config and firewall rules talk about ranges, written in CIDR form like 192.168.1.0/24 — the /24 says how many leading bits are the fixed network part, leaving the rest free for individual hosts. ipaddress.ip_network() parses that into an object supporting Python's own in operator for membership, so checking "is this address inside this range" is one readable line instead of manual octet math:

net = ipaddress.ip_network("192.168.1.0/24")
print(net.num_addresses)                              # confirmed live: 256
print(ipaddress.ip_address("192.168.1.10") in net)   # confirmed live: True
print(ipaddress.ip_address("192.168.2.1") in net)    # confirmed live: False -- outside the /24

ipaddress.ip_network() is strict by default about one easy-to-miss detail: the address part must actually be the start of the range, with no "host bits" left set, or it raises — confirmed live, ip_network("192.168.1.5/24") raises ValueError: 192.168.1.5/24 has host bits set, because .5 is a host inside the /24, not its start. Passing strict=False rounds it down to the network's actual start instead of raising, useful when the exact starting address genuinely doesn't matter yet:

try:
    ipaddress.ip_network("192.168.1.5/24")
except ValueError as e:
    print(e)   # confirmed live: 192.168.1.5/24 has host bits set

print(ipaddress.ip_network("192.168.1.5/24", strict=False))  # confirmed live: 192.168.1.0/24
Hosts vs. addresses: net.num_addresses counts every address in the range, including the network's own first address and its broadcast address at the end — neither of which is a usable host. net.hosts() is a generator (Day 5) yielding only the usable ones. Confirmed live on this same /24: num_addresses is 256, but len(list(net.hosts())) is 254 — the first (192.168.1.1) and last (192.168.1.254) usable hosts bracket the network/broadcast addresses that hosts() correctly excludes.
Where pandas/NumPy go from here: neither has any notion of an IP address or network as a type — a column of IP strings read with pd.read_csv() stays plain text, and checking range membership for a whole column means writing a small function with ipaddress and applying it, the same per-value logic this lesson just showed, one row at a time.
