np.trunc(): the fourth rounding direction, and np.fix()'s retirement

A real, twice-teased gap, not a narrowing of something already taught. np.trunc() is the pick: it completes the four-rounding-direction family (floor/ceil/trunc/round) Lessons 130 and 133 already built two-thirds of, and this round's own scratch check turned up a second, more current reason to teach it now — np.fix() is freshly deprecated in the installed numpy version.

1 · The fourth direction: toward zero, not toward a neighbor

Lesson 130 taught np.floor() (toward negative infinity) and np.ceil() (toward positive infinity); Lesson 133 taught np.round() (toward the nearest integer, ties to even). np.trunc(a) is the fourth direction: it rounds toward zero, confirmed directly (numpy 2.5.5) — it simply chops off the fractional part, with no neighbor comparison at all.

import numpy as np
import pandas as pd

np.trunc(1.7)    # 1.0  -- chops the fraction, doesn't round UP to 2 like ceil would
np.trunc(-1.7)   # -1.0 -- chops toward zero, doesn't round DOWN to -2 like floor would

Confirmed directly, the full four-way split only shows up on a negative number — on a positive number, trunc() and floor() happen to agree (both just drop the fraction when it's already headed toward zero):

x = -1.7
np.floor(x)   # -2.0 -- toward -infinity (away from zero)
np.ceil(x)    # -1.0 -- toward +infinity; happens to land on the same value as trunc here
np.trunc(x)   # -1.0 -- toward zero, chops the fraction
np.round(x)   # -2.0 -- toward the nearest integer (-1.7 is closer to -2 than to -1)

Confirmed directly, this is why ceil(-1.7) and trunc(-1.7) agree at -1.0 here but round(-1.7) disagrees at -2.0: nearest-integer and toward-zero are different rules that only sometimes land on the same answer, confirmed directly to diverge the moment the fractional part is closer to the far neighbor than the near one (checked separately on -1.2: trunc and round agree at -1.0 there, ceil also agrees — only floor splits off). Picking the right one is a real interview question, not a style choice: truncating a price to whole dollars silently loses the cents in the lost direction, flooring always costs the customer, rounding is "fair" on average.

Confirmed directly, int-dtype and Index rules match the rest of the family: an int64 Series under np.trunc() is a true no-op (values and dtype both unchanged, the same rule Lessons 130/133's floor()/ceil()/round() follow — there is no fraction to chop, so nothing happens). A Series' own Index is kept. NaN passes through unchanged. object-dtype input dispatches through Python and works; complex input raises TypeError immediately — all confirmed directly, all matching the established pattern from Lessons 129-133.

2 · np.fix(): same answer, but deprecated as of this numpy version

Confirmed directly (numpy 2.5.5), np.fix(a) returns bit-identical results to np.trunc(a) on every input tested — same toward-zero rule, same int no-op, same NaN passthrough. But calling it now raises a DeprecationWarning on every call, confirmed directly by capturing it with warnings.catch_warnings:

np.fix(2.5)
# DeprecationWarning: numpy.fix is deprecated. Use numpy.trunc instead,
# which is faster and follows the Array API standard.

Confirmed directly from the two functions' own types, this isn't cosmetic: np.trunc is a true ufunc (same family as np.floor/np.ceil/np.round), while np.fix is a plain Python function that calls np.trunc internally — one extra layer of overhead for a historical name that predates the Array API standard numpy is now aligning to. The deprecation message says exactly that: faster, and standard-compliant. Series.trunc() and Series.fix() both raise AttributeError, confirmed directly — pandas defines neither, continuing the naming-gap lineage from Lessons 126-131 (only Series.round(), Lesson 133's one exception, has a matching pandas method in this whole family).

prices = pd.Series([19.99, -4.50, 100.01])
np.trunc(prices)   # [19.0, -4.0, 100.0] -- Index kept, toward-zero on each
prices.trunc()      # AttributeError -- no pandas method; np.trunc(prices) is the only spelling

Q: "What's the difference between np.trunc() and np.fix(), and which should I use?" A strong answer, out loud: "They compute the same thing — both round toward zero, just chopping the fractional part, unlike floor (always toward negative infinity) or round (toward the nearest integer, ties to even). The difference is only that np.fix() is now deprecated in current NumPy — it's a thin Python wrapper around np.trunc() kept for backward compatibility, and the deprecation notice says to use np.trunc() directly because it's a true compiled ufunc and faster. I'd default to np.trunc() in any new code and only recognize np.fix() if I saw it in an older codebase." The signal: naming that they're numerically identical first, then correctly placing the real difference at "which one is current," not inventing a numeric difference that doesn't exist.
