1 · Three questions, in the original teaching order

Answer each out loud or on paper before reading the fold-out answer. If one is shaky, note it and go fix it in the practice file below rather than only rereading the old lesson.

Day 116 — urllib.parse. After parsed = urlparse(url), what type of value is parsed.query, and why does parse_qs() give every key a list of values even when a key appears only once in the URL?

Fold-out answer: parsed.query is still one raw, unsplit string — urlparse() only breaks a URL into its named top-level pieces (scheme, netloc, path, query), it never parses the query string's own key/value pairs. That is exactly parse_qs()'s job, run as a second step on .query's output. parse_qs() always maps every key to a list of values, even one appearing exactly once, because a query string may legally repeat the same key more than once (?tag=py&tag=web is valid and common) — confirmed live, qs["page"] came back as ['2'], a one-item list, never the bare string '2'.

Day 117 — unicodedata. Two strings print as identical text on screen, but s1 == s2 is False. What's the most likely cause, and what does unicodedata.normalize("NFC", s) actually do about it?

Fold-out answer: the most likely cause is that the same visible letter was built from a different number of underlying code points — one precomposed code point on one side (é as U+00E9), a base letter plus a separate combining mark on the other (e + U+0301). Both render identically, but == compares the actual code-point sequence, not the printed appearance — confirmed live, len(s1) was 4, len(s2) was 5, and s1 == s2 was False. normalize("NFC", s) rewrites a string into one standard shape (composing combining marks into a single code point wherever one exists), so two strings that only differed in how a character was built become identical once both sides are normalized the same way — confirmed live, both sides equal after normalizing.

Day 118 — ipaddress. Why does a hand-written regex often accept an invalid IP address like "192.168.1.999", and what does ipaddress.ip_network() give you that a plain string holding "192.168.1.0/24" does not?

Fold-out answer: a regex built to "validate an IP" typically only checks that each piece has the right digit shape (one to three digits, separated by dots) — it misses that a group like 999 is out of the valid 0–255 range unless the pattern explicitly encodes that. ipaddress.ip_address() does real parsing instead of a pattern match, confirmed live raising ValueError on "192.168.1.999". ipaddress.ip_network("192.168.1.0/24") returns an object supporting Python's own in operator for membership — confirmed live, ip_address("192.168.1.10") in net is True and ip_address("192.168.2.1") in net is False, with no manual octet math written by hand; a plain string gives you none of that, only text to split apart yourself.

Same interleaving logic as every prior review day: a tool for moving a URL between one string and its named pieces in both directions, a tool for recognizing that two identical-looking strings can carry a different code-point sequence underneath, and a tool for treating an IP address and a network range as real objects instead of risky hand-parsed text.
