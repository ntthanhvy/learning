searchsorted(): binary search on data you already sorted

Chào bạn — Lesson 74's teaser named searchsorted() as the one leftover zero-hit candidate, and framed the setup exactly: it needs a SORTED array to behave correctly, which is exactly what np.unique() always hands back. A fresh grep of all 74 lessons and the glossary reconfirms it is still genuinely untaught. Today closes that loop.

1 · What it answers: "where would this value go?" — not "is it there?"

searchsorted() answers a specific question: given a sorted array, at what integer position would a new value need to be inserted to keep it sorted? It is binary search — O(log n) per query — not a linear scan, and that speed is the entire reason it exists as its own method rather than a filter-and-count one-liner.

sorted_vals = np.unique(amt.to_numpy())     # [35.5, 42.0, 99.9, 120.0, 180.0] -- Lesson 74's guarantee
np.searchsorted(sorted_vals, 100)          # 3 -- 100 belongs at position 3 (between 99.9 and 120.0)

Confirmed directly (NumPy 2.5.3): calling it on today's real orders_raw.csv amount column, fed through Lesson 74's np.unique() to guarantee sorted input first, gives exactly this. Series.searchsorted() exists too, with the identical contract on a Series instead of a raw array.

SQL bridge: there is no single SQL keyword for this — the closest mental model is a window function like RANK() or a manual COUNT(*) WHERE right_col <= value correlated subquery, run once per lookup value. searchsorted() is the vectorized, binary-search version of that same "how many/which position" question, answered for an entire array of query values in one call instead of one row at a time.

2 · side="left" vs side="right": where ties land

When the query value already exists exactly in the array, side= decides whether the returned position is before or after the existing matches. Confirmed directly on sorted_vals above with the exact value 99.9 (at index 2):

np.searchsorted(sorted_vals, 99.9, side="left")   # 2 -- insert BEFORE the existing 99.9
np.searchsorted(sorted_vals, 99.9, side="right")  # 3 -- insert AFTER the existing 99.9

The default is side="left". This is not a cosmetic detail: side="right" is exactly "how many elements are <= value," confirmed directly by comparing it against a plain boolean-mask count ((sorted_vals <= 99.9).sum() also gives 3, matching side="right" exactly) — the vectorized binary-search version of a pattern you'd otherwise write as a mask-and-sum.

3 · The real gotcha: unsorted input gives a silently wrong answer, no error

The single most important fact about this method, confirmed directly with a deliberately-diverging case: searchsorted() never checks whether its input is actually sorted. Feed it the raw, unsorted amount column instead of np.unique()'s guaranteed-sorted output, and it returns a number every time — just the wrong one, with no exception, no warning:

unsorted = np.array([120.0, 35.5, 99.9, 180.0, 42.0])  # raw appearance order
sorted_vals = np.sort(unsorted)                             # [35.5, 42.0, 99.9, 120.0, 180.0]

np.searchsorted(unsorted, 40)   # 2  -- WRONG, no error
np.searchsorted(sorted_vals, 40) # 1  -- correct

Confirmed directly across six probe values (40, 50, 60, 100, 130, 150): three of the six (40, 130, 150) gave genuinely different — and wrong — positions on the unsorted array versus the correctly-sorted one, with zero indication anything went wrong. This is the sharp edge that makes this method dangerous in practice: np.unique() (Lesson 74), sort_values() (Lesson 31), or an explicit np.sort() must run first, every time, and there is no safety net if you forget.

4 · Two real uses: manual binning, and how merge_asof() works under the hood

First, manual bucketing without pd.cut(): given sorted bin edges, searchsorted(edges, values, side="right") - 1 gives the bucket index for each value in one vectorized call. Confirmed directly against pd.cut()'s own bucket codes on the same edges and values — both produced the identical bucket assignment array, byte-for-byte, on a 6-value test set spanning every edge case (including a value exactly on a boundary).

Second — and this is the payoff for having sat through Lesson 58's merge_asof() — its "nearest prior match" behavior is exactly a searchsorted() call under the hood. Confirmed directly by hand-replicating merge_asof(..., direction="backward") (the default) using nothing but np.searchsorted(right_times, left_times, side="right") - 1 to find each left row's matching right-row position: the manually-computed match and pd.merge_asof()'s own official output agreed exactly on a 3-row/4-row test case. merge_asof()'s core requirement — both sides must be sorted on the join key — is the exact same requirement searchsorted() has, because it's the same algorithm underneath.

Q: "When would you reach for searchsorted() instead of just filtering with a boolean mask?" A strong answer, out loud: "searchsorted() is binary search — O(log n) — versus a linear O(n) mask-and-count, so it matters once the array is large or I'm running many lookups against the same sorted reference array, like bucketing a big column into bins or replicating what merge_asof() does internally for an as-of join. The catch I'd flag immediately: it never checks that its input is actually sorted — feed it unsorted data and it returns a number with zero error, just the wrong one. I verified this myself: three out of six test values gave a different, wrong position on an unsorted array versus the same array correctly sorted first. So I'd always sort explicitly, or run np.unique() first if I also want deduplication, right before calling it — never assume upstream data is already sorted just because it looks that way." The signal: naming the silent-wrong-answer failure mode with a verified number, not just "make sure it's sorted" as a vague caveat — the same "know where the abstraction leaks" instinct as Lessons 73 and 74.
