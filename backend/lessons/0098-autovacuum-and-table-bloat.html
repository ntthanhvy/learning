Autovacuum and bloat: the cleanup Lesson 39 said was out of scope

Lesson 39 named VACUUM, explained why it exists, and then drew a line: "tuning autovacuum itself is operations work beyond this lesson's scope." Today crosses that line — what autovacuum actually is, why a table can bloat even though autovacuum is running, and the one failure mode that turns this from a disk-space nuisance into a production outage.

1 · VACUUM is a program; autovacuum is the scheduler that runs it

Lesson 39 was precise about why dead row versions need reclaiming — an old version stays on disk until no active snapshot could possibly still need it. It was looser about who actually does that reclaiming. VACUUM is a command you could, in principle, type yourself. autovacuum is the daemon that decides when: it watches every table's count of dead tuples against a threshold and launches a vacuum worker on its own, with no human or cron job involved. On any normal Postgres install it's on by default — the reason Lesson 39 could say "usually autovacuum, running on its own" without anyone having configured a thing.

That threshold is the whole story of why a table can still bloat with autovacuum fully enabled. By default autovacuum fires once dead rows cross roughly 20% of a table's live row count (autovacuum_vacuum_scale_factor, plus a small flat offset). That default was picked for an average table, not yours. A table that gets thousands of UPDATEs per minute can accumulate a 20%-sized pile of dead versions — and keep doing it faster than one autovacuum worker can clean a pile that size — long before the next run even finishes.

2 · Bloat is the pile outrunning the broom

Bloat is what Lesson 39 called "visibly bloat in size," named properly: dead row versions sitting between live ones faster than autovacuum reclaims them. Three things make a table a bloat risk specifically, not just an active one:

  • Heavy UPDATE/DELETE traffic — every one leaves a dead version behind (Lesson 39, Section 4); a table that's mostly INSERT-only barely bloats at all, since there's little to leave dead.
  • Long-running transactions elsewhere — a single open transaction, even one touching a completely different table, pins its own snapshot in place, and autovacuum can't reclaim any version that transaction's snapshot might still need, anywhere in the database, until it finally commits or rolls back.
  • Autovacuum falling behind — too few workers, a scale factor too loose for this table's write rate, or a vacuum run that keeps getting interrupted before it finishes a large table.

The fix for an already-bloated table (VACUUM FULL, which rewrites the whole table compactly) takes an exclusive lock for its entire duration — a cure that can cost more downtime than the disease. The cheaper fix is almost always further upstream: find the long-running transaction holding the old snapshot open, or tighten that one table's autovacuum_vacuum_scale_factor so it fires sooner, before the pile gets that large.

Frontend-habit trap: "the table is using more disk than I expect" reads like a memory leak — something to patch in application code. It isn't one. No bytes are unaccounted for and nothing is corrupted; every byte is either a live row or a dead version autovacuum hasn't reclaimed yet. The fix lives in Postgres configuration and transaction hygiene, not in the Go handler that issued the UPDATE.

3 · The failure mode that makes this urgent: wraparound

Disk space creeping up is an inconvenience. There's a second, sharper reason autovacuum tuning is a real operational concern and not just tidiness. Every transaction's id (Lesson 39's xmin/xmax) is a finite 32-bit number. Postgres reuses them in a circle, and a background vacuum pass is also what "freezes" old row versions so Postgres can tell a genuinely old xmin apart from a reused one that merely looks old after the counter wrapped. If autovacuum falls far enough behind — usually because of exactly the long-running-transaction or misconfigured-threshold causes above, left unaddressed for a long time — Postgres gets close enough to running out of fresh transaction ids that it protects itself the only way it safely can: it stops accepting new write transactions database-wide, in every table, until an emergency vacuum catches up. Reads still work. Every INSERT/UPDATE/DELETE anywhere in the database does not, until the cleanup finishes.

That's the actual stakes behind Lesson 39's one-line scope cut: autovacuum isn't only reclaiming disk space, it's the same mechanism standing between the database and a self-inflicted, database-wide write outage. Postgres ships monitoring views specifically so this never arrives as a surprise — age(datfrozenxid) in pg_database reports how close a database is to that wraparound limit, long before it becomes urgent.

4 · Seeing it from Go

Nothing about autovacuum is configured from application code — it's a server-side setting, not a pgx call. What application code does control is the one risk factor in Section 2 that a handler can actually create: a transaction opened and then left running far longer than its own work requires, because of a slow downstream call or a missing timeout.

// riskyTransfer holds a transaction open across a slow external call --
// every second this is open, autovacuum anywhere in the database cannot
// reclaim any row version that might still be visible to this snapshot.
func riskyTransfer(ctx context.Context, pool *pgxpool.Pool, from, to int, amount int) error {
    tx, err := pool.Begin(ctx)
    if err != nil {
        return err
    }
    defer tx.Rollback(ctx)

    _, err = tx.Exec(ctx, "UPDATE accounts SET balance = balance - $1 WHERE id = $2", amount, from)
    if err != nil {
        return err
    }

    // a slow fraud-check API call, still inside the open transaction --
    // this is the risk: the transaction's snapshot stays pinned for however
    // long this call takes, with no timeout bounding it
    if err := callFraudCheckAPI(ctx, from, to, amount); err != nil {
        return err
    }

    _, err = tx.Exec(ctx, "UPDATE accounts SET balance = balance + $1 WHERE id = $2", amount, to)
    if err != nil {
        return err
    }
    return tx.Commit(ctx)
}

The fix isn't a different vacuum setting — it's moving the slow call outside the transaction boundary (do the fraud check first, open the transaction only around the two fast UPDATEs), the same "keep transactions short" instinct Lesson 6 already taught for lock contention, now shown to matter for vacuum too. Lesson 41's context.Context deadline bounds the worst case, but doesn't replace actually shrinking what's inside the transaction.

Q: "One of our tables keeps growing in disk size even though row counts are flat. What's going on, and what would you check?" A strong answer, out loud: "That's almost always bloat, not a leak — Postgres never overwrites a row in place, UPDATE and DELETE leave dead versions behind, and autovacuum is supposed to reclaim that space in the background. If it's not keeping up, I'd check two things: is there a long-running transaction somewhere pinning an old snapshot and blocking reclamation, and is this specific table's autovacuum threshold too loose for how often it's written to. I'd also check pg_database's age(datfrozenxid) — if autovacuum has been falling behind long enough, the real risk isn't disk space, it's transaction id wraparound, which stops all writes database-wide until an emergency vacuum catches up." The signal: naming bloat as dead-version backlog rather than a leak, and knowing wraparound is the sharper failure mode behind it, not just disk pressure.

Scope line

This lesson covers only the operational layer Lesson 39 explicitly deferred: what autovacuum is, why a table bloats despite it running, and wraparound as the reason this matters beyond disk space. It doesn't cover tuning the full set of autovacuum parameters (cost delay, worker count, per-table overrides) or VACUUM FULL's mechanics in depth — both real operations topics, but a level past what a backend engineer needs to recognize the symptom and know what to check.
