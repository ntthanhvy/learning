1 · The question this repo has been quietly dodging since Day 6

mart_delivery_sla has had the same shape since Day 6: a Kafka consumer lands order_events into Postgres, and dbt computes "minutes from placed to delivered" and "share of orders over 45 min" later, on whatever schedule Day 7's DAG runs on. An order that goes placed → accepted → picked_up → delivered in three minutes and one that takes three hours are treated identically by this pipeline until the next scheduled dbt build runs. That gap — events arrive continuously, the answer updates in batches — is exactly the boundary this lesson names. The alternative is computing that same answer continuously, as each event lands, inside the stream itself. This course has never built that alternative, and today is about knowing precisely what it would buy and precisely what it would cost, not building it.

2 · Stream processing: compute on the stream itself, not after it lands

Kafka Streams and Flink are the two best-known answers to "I want to compute something continuously, as events arrive, not after they land somewhere." Both let a program hold running state — "this city's running count of orders over 45 minutes so far today" — and update that state one event at a time, instead of re-deriving it from scratch over a table. The core primitive both offer that a landed-then-queried table does not is windowing: grouping an endless stream into fixed time buckets so an aggregate has a well-defined moment to close and emit, something a batch query over a table does implicitly every time it runs, but a stream has to be told explicitly.

Kafka Streams is a library, not infrastructure: it links into an ordinary JVM application process and talks to the Kafka brokers this course already runs, no separate cluster. Flink is the heavier option — its own cluster of worker nodes, its own scheduler, and the ability to read from many sources beyond Kafka, with exactly-once state guarantees that survive a worker crashing mid-computation. Both exist specifically for problems where "wait for dbt's next scheduled run" is the wrong answer because the latency of waiting is itself the business problem — fraud detection that has to fire within seconds, not minutes; a live dashboard a dispatcher is staring at right now.

Right fit hereYes — nobody is paged the moment one city's SLA breach share ticks up; a dashboard refreshed hourly already serves the real decision this mart supportsWould be the right call if a dispatcher needed to see SLA breaches within seconds to act on them in real time, or if the aggregate itself needed to drive an automated action per event

The honest framing is not "streaming is advanced, batch is basic." It is that continuous computation earns its real cost — a new runtime, a new language, a new state store to operate — only when the latency of waiting for the next scheduled build is itself unacceptable to the business. mart_delivery_sla feeds a report a human reads periodically, not an automated action that needs to fire within the same second an event lands, so Day 6–7's land-then-batch path stays the right call, the same kind of named, revisitable decision as Day 23's "hand-written consumer over Debezium" and Day 7's "BashOperator over Cosmos."

6 · What's deliberately not here

Today is vocabulary and a diagram, not a build, for a concrete reason: standing up even the lighter of the two options (Kafka Streams) means writing and running a second application alongside the existing producer/consumer pair, in a different language ecosystem than the rest of this project, for a freshness requirement this portfolio's own domain doesn't have. Flink is further out of reach still — MISSION.md rules out a whole new cluster to operate locally, the same reasoning Day 17 applied to Schema Registry and Day 23 applied to Kafka Connect/Debezium: name the tool, know exactly what it buys and costs, and build it only when a real requirement — not a hypothetical one — shows up.

Q: "Your delivery-SLA mart is computed in dbt on a schedule. Why not compute it in a stream processor instead, since the data is already in Kafka?" A strong answer, out loud: "Because the real question isn't whether the data's in Kafka already, it's whether anyone needs the answer faster than my next scheduled dbt build gives it to them. mart_delivery_sla feeds a report a human checks periodically — nobody's paged the second one city's SLA-breach share ticks up — so the gap between batch runs is acceptable, and landing events then computing in dbt on a schedule costs me nothing beyond what I already run: Postgres and the Kafka broker. A stream processor like Kafka Streams or Flink would earn its real cost — a new runtime, in Kafka Streams' case a different language ecosystem, and for Flink a whole separate cluster with its own state store to operate — the moment this mart needed to drive something in real time: an alert that has to fire within seconds, or a dashboard that has to update per event instead of per batch. That's not a hypothetical I'm ignoring, it's a named threshold in my README I'd revisit the day it actually shows up." The signal: tying the decision to a specific latency requirement this project's domain does or doesn't have, not treating streaming as universally more advanced.
