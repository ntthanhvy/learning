np.broadcast_to(): making the implicit "stretch" an explicit, inspectable array

Lesson 96's teaser named exactly one standing candidate: np.broadcast_to(), deferred once at Lesson 94 (in favor of np.repeat()/np.tile()) and again at Lesson 95 (in favor of DataFrame.insert()/.pop()). A fresh grep across every lesson body and the glossary confirmed it's still a genuine zero-coverage gap — real hits only inside those two lessons' own teaser prose, never as a taught topic or a glossary row. Picking it today: it directly closes the loop Lesson 30 opened (broadcasting as an automatic, implicit rule) and Lesson 95 sharpened (tile() as the function that materializes a real copy) — broadcast_to() is the missing middle: the function that makes broadcasting's "stretching" an actual array you can look at, without ever paying for a copy.

1 · What broadcasting was doing invisibly all along

Lesson 30 named broadcasting as the rule that lets clean["amount"] * 1.1 apply one scalar to every row with no loop. That stretching is normally invisible — NumPy does it internally during the arithmetic and never hands you the stretched version as its own object. np.broadcast_to() makes that stretch explicit — it runs the exact same rule, but hands back the stretched array itself. Confirmed directly (numpy 2.5.4):

import numpy as np
arr = np.array([1, 2, 3])
b = np.broadcast_to(arr, (4, 3))
b
# [[1 2 3]
#  [1 2 3]
#  [1 2 3]
#  [1 2 3]]

# same numeric result as the implicit version from Lesson 30:
col = np.array([[1], [2], [3], [4]])
col + arr
# [[2 3 4]
#  [3 4 5]
#  [4 5 6]
#  [5 6 7]]   -- arr was stretched to (4,3) internally, same shape as b

The trap: an incompatible target shape raises ValueError, naming the exact mismatch — confirmed directly:

np.broadcast_to(arr, (4, 4))
# ValueError: operands could not be broadcast together with
# remapped shapes [original->remapped]: (3,) and requested shape (4,4)

2 · Read-only on purpose, and why

Confirmed directly against the official NumPy docs (which state this outright): the array broadcast_to() returns is a view, not a copy — np.shares_memory(b, arr) is True — and it is read-only. Writing to it raises immediately:

b[0, 0] = 99
# ValueError: assignment destination is read-only

That restriction isn't arbitrary — it protects you from a bug the array's own shape would otherwise hide. Confirmed directly: b.strides is (0, 8) — stride 0 on the first axis means all four "rows" are literally the same 24 bytes read four times, not four separate rows. Writing through b[0, 0] would silently corrupt every row at once, since there is only one row in memory. This is exactly how Lesson 95's np.tile() differs: tile() always allocates a real, independent, writeable copy (confirmed directly: np.shares_memory(np.tile(arr, (4, 1)), arr) is False) — strictly more memory, but safe to mutate. Needing to write into the result is the signal to reach for .copy() (or tile() directly) instead of broadcast_to():

writeable = np.broadcast_to(arr, (4, 3)).copy()
writeable[0, 0] = 99
# works fine now -- copy() made it a real, independent array
# arr itself is still untouched: [1 2 3]

3 · When to reach for it over plain arithmetic

For ordinary arithmetic (col + arr above), you never call broadcast_to() yourself — NumPy already does the equivalent stretch internally, for free, exactly as Lesson 30 taught. broadcast_to() earns its place when you need the stretched shape itself as a real object to pass elsewhere — feeding a fixed-shape function, building a cartesian-style mask, or just inspecting what a broadcast will actually produce before trusting it in a pipeline. A companion function, confirmed directly, computes the resulting shape with no array at all, useful for that same sanity check:

np.broadcast_shapes((4, 3), (3,))
# (4, 3)   -- answers "what shape would this broadcast to?" with zero data involved

Q: "What does np.broadcast_to() actually return, and why is it read-only?" A strong answer, out loud: "It returns a view, not a copy — same data, reshaped by the exact rule plain broadcasting arithmetic already uses internally, so no memory is duplicated. It's read-only because the view fakes extra rows or columns with stride tricks — stride 0 on the repeated axis — so every 'repeated' row is really the same bytes. Writing through one index would silently corrupt every other repeated row at once, so NumPy raises instead of allowing that. If I actually need to mutate the result, I call .copy() first, or reach for tile() instead, which always makes a real independent copy up front." The signal: naming view-not-copy, read-only, and the actual reason (shared memory via stride 0), not just "because NumPy says so."
