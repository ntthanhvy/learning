2 · try_number, confirmed straight from Airflow 3.3.1's own source

Reading TaskInstance's real class body this round (installed locally via uv run --with "apache-airflow==3.3.1", no live scheduler needed) turns up the exact mechanics, not the usual paraphrase:

try_number: Mapped[int] = mapped_column(Integer, default=0)
...
def is_eligible_to_retry(self):
    ...
    return bool(self.task.retries and self.try_number <= self.max_tries)

A try_number is a real counter on the task instance itself, not a derived guess — and is_eligible_to_retry() is the literal gate every failure passes through: a task only gets to retry if task.retries is truthy and try_number hasn't yet exceeded max_tries, which Airflow derives directly from the task's own configured retries. For Day 7's dbt_build (retries=2), that means three total attempts are possible: try_number 0, 1 and 2, each one checked against max_tries=2 before a fourth is ever considered.

The same source pass through airflow.sdk.execution_time.task_runner turned up something worth quoting directly, a comment explaining a real design decision rather than an assumption:

# We signal main() to sys.exit(1) AFTER finalize() runs, so
# on_failure_callback / on_retry_callback / listener hooks /
# email_on_failure / email_on_retry still fire. sys.exit(1) directly
# here would raise SystemExit, which is BaseException, not Exception --
# main()'s `except Exception:` would not catch it and finalize() at
# the call site would be skipped.

Two things confirmed directly from that comment, not inferred: on_retry_callback and on_failure_callback are two distinct hooks, chosen by which terminal state a failed attempt lands in (UP_FOR_RETRY fires the retry callback; a final, no-more-attempts failure fires the failure callback instead) — and both are guaranteed to run as part of finalize(), deliberately sequenced before the process actually exits, specifically so a crashing task still gets its callback.

3 · Build: add on_retry_callback to the real dbt_build task

In your food-delivery-pipeline repo, edit dags/food_delivery_pipeline.py — the exact file Day 7 wrote, not a copy. Add one function above the with DAG(...) block, and one keyword argument on dbt_build:

def log_dbt_build_retry(context: dict) -> None:
    # TODO: today's real skill -- this currently only prints. A real
    # deployment would call Slack/PagerDuty here, same as Day 25's
    # deadline-alert TODO did for a late run instead of a failed one.
    ti = context["task_instance"]
    print(
        f"RETRY: {ti.task_id} failed attempt try_number={ti.try_number} "
        f"of max_tries={ti.max_tries} -- retrying after retry_delay"
    )


# inside the existing `with DAG(...) as dag:` block, Day 7's dbt_build task:
dbt_build = BashOperator(
    task_id="dbt_build",
    bash_command=(
        f"cd {REPO_DIR}/warehouse && "
        "uv run --with 'dbt-postgres==1.11.0' dbt build --profiles-dir ."
    ),
    on_retry_callback=log_dbt_build_retry,  # new today
)

Nothing about retries=2 or retry_delay changes — both already exist on default_args since Day 7 and apply here exactly as before. on_retry_callback is additive: it observes a retry that was already going to happen, it doesn't cause one.

4 · Verify: force a real failure, watch try_number move

Proving this without waiting for a real transient Postgres hiccup needs a forced failure — this round built exactly that as a throwaway scratch DAG (not committed to your repo, just today's own verification), a single PythonOperator that raises on its first attempt and succeeds on its second, with the same on_retry_callback shape as Section 3:

def _fail_once_then_succeed(**context):
    ti = context["task_instance"]
    if ti.try_number < 2:
        raise RuntimeError("simulated transient failure")

Running this under a real scheduler would show the sequence Section 2's source confirms: attempt 0 executes, raises, lands in UP_FOR_RETRY, fires on_retry_callback with try_number=0; Airflow waits retry_delay; attempt 1 executes, try_number is now 1, which is <= max_tries (2), so the condition in _fail_once_then_succeed is false and it succeeds — no third attempt needed. 5 · Why this matters more than it looks like it should

A callback that only prints looks like a toy, but the mechanism underneath it is the same one a real on-call setup hangs its alerting on: on_retry_callback is where you'd page someone that dbt_build is struggling but not yet dead, and on_failure_callback (fired once try_number > max_tries, the attempt that doesn't get another chance) is where you'd page that it's actually down. Today's lesson is deliberately the smaller of the two — a retry is routine, a final failure is the one that should wake someone up — and naming that distinction out loud, backed by the exact source-level condition that decides between them, is worth more in an interview than either callback's own one-line body.

This is the same idempotent-retry idea Day 6's Kafka consumer and Day 7's own re-run proof already established — Airflow doesn't make a retry safe, it just calls the same thing again. Nothing about dbt_build's own safety changed today; today only makes visible the exact moment Airflow decides to call it again.
