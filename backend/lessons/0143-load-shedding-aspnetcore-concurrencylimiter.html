Load shedding, now in C# too (ConcurrencyLimiter)

Lesson 71's load shedder watched the server's own health (CPU, queue depth, latency) and rejected low-priority work once it crossed a threshold — a hand-written Shedder struct with no library backing it. Lesson 118 later covered ASP.NET Core's rate limiting middleware, but only its token bucket limiter: a per-client budget over a time period, not a server-wide overload signal. System.Threading.RateLimiting ships a fourth limiter type built for exactly Lesson 71's problem — ConcurrencyLimiter, which caps requests in flight right now instead of requests per second.

1 · A different question than "how many per second"

Lesson 118's token bucket answers "has this client used up its budget for this window." That's the right question for a client that sends too many requests. It is the wrong question for the problem Lesson 71 named: a service that is overloaded even though no single client has crossed any limit — a slow dependency, an expensive query, or many different well-behaved clients arriving at once can all drive the server into trouble while every individual rate-limit counter stays comfortably under its cap.

ConcurrencyLimiter answers the question Lesson 71's loadFn was reaching for, but with one specific, cheap-to-read signal: how many requests are in flight right now, server-wide (or per named policy) — not CPU, not a custom health function, just concurrency itself as the overload proxy.

2 · Registering it: the fourth limiter alongside Lesson 118's token bucket

Lesson 118's AddTokenBucketLimiter sits in the same AddRateLimiter call as this lesson's AddConcurrencyLimiter — same registration shape, same pattern, different algorithm:

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddRateLimiter(options =>
{
    options.AddConcurrencyLimiter("checkout-capacity", opt =>
    {
        opt.PermitLimit = 20;
        opt.QueueProcessingOrder = QueueProcessingOrder.OldestFirst;
        opt.QueueLimit = 5;
    });
});

var app = builder.Build();
app.UseRateLimiter();

app.MapPost("/checkout", HandleCheckout)
   .RequireRateLimiting("checkout-capacity");

PermitLimit here means something structurally different from Lesson 118's TokenLimit: it is not a bucket that refills over time, it is a count of permits currently on loan. Every request that enters /checkout takes one of the 20 permits and holds it for the request's entire duration; the permit returns to the pool only when that request finishes, not on a timer. A slow checkout holding its permit for three seconds blocks that same permit from a second request for those same three seconds — the exact "held resource" framing Lesson 71 used for an open connection, now expressed as a configuration option instead of a hand-rolled struct field.

3 · What this buys over Lesson 71's hand-written Shedder

Lesson 71's Go Shedder.Admit read a custom loadFn and compared it against two hand-chosen thresholds (0.80, 0.95). ConcurrencyLimiter replaces that whole decision with permit accounting the framework already does for every request: no health function to write, no threshold to tune by hand, no struct to maintain. QueueLimit plays the same role Lesson 71's thresholds did for borderline load — a request arriving when all 20 permits are out doesn't fail immediately, it waits in a queue up to QueueLimit deep (processed OldestFirst here, mirroring Lesson 118's same enum) before being rejected once the queue itself is full.

4 · What ConcurrencyLimiter does not give back

Lesson 71's whole second half was priority: shed the health check before the checkout. A bare ConcurrencyLimiter has no concept of priority at all — every request competing for those 20 permits is equal, so under sustained overload it sheds whichever requests happen to arrive once the queue is full, in arrival order, not by importance. Getting Lesson 71's priority behavior back means doing what Lesson 71's Go version did: assigning a separate, smaller PermitLimit policy to low-priority routes (health checks, background pings) via RequireRateLimiting on a different policy name, so they exhaust their own small pool before ever touching the pool that serves checkout. The limiter enforces whatever policy a route is assigned; deciding which routes get which policy — the actual priority judgment — is still the developer's call, exactly as it was in Lesson 71's hand-assigned Priority enum.

Frontend-habit trap: PermitLimit on a concurrency policy looks like a client-facing quota, the same shape as Lesson 118's per-API-key token bucket. It isn't partitioned by client at all unless wrapped in a PartitionedRateLimiter the way Lesson 118 did for tokens — a bare AddConcurrencyLimiter policy is one shared pool for every caller hitting that route, which is exactly the point: it protects the server's own capacity, not any one client's fair share.

5 · One real difference in what the rejected response can say

Lesson 71 recommended 503 with a Retry-After header so a well-behaved client knows the rejection is about capacity, not a bug. Microsoft's own rate-limiting docs name a specific limit here: time-based limiters like the token bucket can compute Retry-After because they know exactly when the next permit arrives (the next replenishment tick). ConcurrencyLimiter cannot — it has no timer, no schedule, just permits that free up whenever whichever in-flight request finishes first, at an unpredictable moment. A rejected response can still return 503, just without a trustworthy Retry-After value attached — the client learns "try later," not "try in exactly N seconds."

Q: "Your ASP.NET Core API falls over under a traffic spike even though no client is hitting its per-key rate limit. What do you reach for?" A strong answer, out loud: "That's the gap token-bucket rate limiting doesn't cover — it caps one client's requests per second, not the server's total in-flight load. I'd add a ConcurrencyLimiter policy capping how many requests can run at once, which is a direct port of the load-shedding idea: react to the server's own saturation, not a per-client count. The nuance is priority — a bare ConcurrencyLimiter treats every request equally, so I'd give low-priority routes like health checks their own smaller-permit policy so they exhaust their pool before touching checkout's. And since it's not time-based, I can't hand back a trustworthy Retry-After the way the token bucket limiter can — the client just hears 503, try again later, with no exact number attached." The signal: naming that concurrency and rate are different proxies for overload, and that priority still has to be designed in by routing, not assumed from the limiter.

Scope line

This lesson covers AddConcurrencyLimiter, its PermitLimit/QueueProcessingOrder/QueueLimit options, and the concurrency-vs-rate distinction against Lesson 118's token bucket. It does not cover chaining a concurrency limiter with a token bucket via RateLimiter.CreateChained (named in Microsoft's docs as a way to combine both signals on one endpoint), the rate-limiting metrics the middleware emits, or constructing a ConcurrencyLimiter directly rather than through AddConcurrencyLimiter — all left for a dedicated lesson if picked up later.
