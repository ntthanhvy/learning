COPY and bulk insert: loading a million rows without a million round trips

Every write this course has taught so far — Lesson 35's upsert, Lesson 6's transaction, Lesson 33's optimistic lock — assumes one row (or a handful) per statement, because that's what a request handler does. A CSV import, a nightly data sync, or a one-off backfill script is a different shape entirely: thousands to millions of rows, loaded once, with no client waiting on a response. Looping an INSERT per row is the naive answer, and it's slow for a specific, nameable reason.

1 · The cost a loop hides: one round trip per row

A single INSERT inside a request handler is fast because it's one row riding one network round trip between your app and Postgres — milliseconds, unnoticeable. A loop that calls INSERT once per row for 500,000 rows pays that same round-trip cost 500,000 times over, plus Postgres parsing and planning the same statement shape 500,000 times, plus (if each insert is its own implicit transaction) 500,000 separate commits each forcing a disk flush. None of that is a bug — it's the correct cost model for request/response traffic, applied to a workload it was never designed for.

Bulk insert is the general fix: pay the per-statement overhead once (or a handful of times), not once per row. Postgres offers two levels of this, and picking between them is today's actual decision.

2 · Level one: batch the INSERT itself

The first, smallest fix needs no new command — a single INSERT already accepts multiple VALUES rows:

INSERT INTO events (user_id, kind, occurred_at) VALUES
  (101, 'signup', '2026-09-16 08:00:00'),
  (102, 'signup', '2026-09-16 08:01:00'),
  (103, 'login',  '2026-09-16 08:02:00');
-- one round trip, one parse, one commit -- for all three rows, not three

This is the right move at the scale a Go handler naturally produces batches at — a few dozen to a few hundred rows per call, e.g. inserting all line items for one order at once instead of one INSERT per item in a loop. Past roughly a few thousand rows in a single statement, the win flattens out and the statement itself gets unwieldy (a huge parameter list, a large parse tree) — that's the point where the second level takes over.

3 · Level two: COPY, a different protocol entirely

COPY isn't a batched INSERT — it's a separate protocol path. Instead of Postgres parsing SQL syntax for every row, the client streams raw row data (commonly CSV or a binary format) straight into the table, and the server reads it as a stream rather than as N statements. From psql, loading a CSV file is one line:

\copy events (user_id, kind, occurred_at) FROM 'events.csv' WITH (FORMAT csv, HEADER true);

\copy (the psql client-side wrapper, backslash and all) reads the file from wherever psql is running and streams it to the server; the server-side COPY command reads a file path on the database server's own disk instead — \copy is almost always the one an application actually wants, since the app server and the database server are rarely the same machine.

4 · Doing it from Go: pgx's CopyFrom

An application loading rows it already has in memory — not a CSV file — uses the same underlying protocol through the driver. pgx exposes it as CopyFrom, taking a source that yields rows one at a time rather than a slice, so the whole batch is never required to sit fully materialized:

// rows is already in memory here for clarity; CopyFromSlice works the same
// way for any [][]any. For a truly large load, implement pgx.CopyFromSource
// yourself so rows stream from a file or channel instead of a slice.
rows := [][]any{
    {101, "signup", time.Now()},
    {102, "signup", time.Now()},
    {103, "login", time.Now()},
}

count, err := conn.CopyFrom(
    ctx,
    pgx.Identifier{"events"},
    []string{"user_id", "kind", "occurred_at"},
    pgx.CopyFromSlice(len(rows), func(i int) ([]any, error) {
        return rows[i], nil
    }),
)
// count == 3, err == nil on success; one round trip regardless of row count

The signature makes the trade explicit: CopyFrom takes a table name and a column list, not a query string — there's no SQL to parse per row because there is no per-row SQL at all.

5 · What COPY gives up to go this fast

Looped INSERTBatched INSERT (§2)COPY (§3–4)
Round tripsone per rowone per batchone for the whole load
ON CONFLICT / upsertyes, per rowyes, per statementno — plain load only
RETURNING generated idsyes, per rowyes, per statementno
Triggers, CHECK constraintsrun per rowrun per rowstill run per row

The missing row is the real decision: COPY has no ON CONFLICT clause and no RETURNING. If duplicate rows need to be skipped or merged (Lesson 35's upsert territory) or the caller needs the generated ids back, the standard pattern is COPYing into an empty staging table first, then a single set-based INSERT ... SELECT ... ON CONFLICT or MERGE from staging into the real table — full COPY speed for the load, full conflict handling for the merge, as two statements instead of one. CHECK constraints (Lesson 60) and triggers still fire per row either way — COPY skips SQL parsing overhead, not row-level rule enforcement, so a bad row still fails the whole COPY.

Frontend-habit bridge: this is the same trade as batching a hundred individual fetch() calls into one request with an array body — each network round trip has fixed overhead independent of payload size, so collapsing N round trips into one is a win long before the payload itself gets big. COPY takes that same idea one step further: not just fewer round trips, but a transfer format with no per-row parsing cost at all.

6 · When this actually comes up

Not in a request handler — a client waiting on an HTTP response for a 500,000-row COPY is its own problem (Lesson 10's background job is the right container for that work). This is the tool for: a one-off data migration, a nightly sync job pulling a vendor's export, a test-fixture loader seeding a database before an integration test suite runs. The signal that it's time to reach for COPY instead of a batched INSERT isn't a row-count threshold memorized in advance — it's noticing the load step, not the rest of the job, is what's slow.

Q: "How would you load a 2 million row CSV into Postgres?" A strong answer, out loud: "Not a loop of INSERTs — that pays a full round trip and statement parse per row, which at that scale dominates the run time. I'd use COPY, either \copy from psql for a one-off, or pgx's CopyFrom from Go if it's part of an application job, since both stream the data in over a dedicated protocol instead of parsing SQL per row. The catch is COPY has no ON CONFLICT and no RETURNING, so if I need to dedupe against existing rows or get generated ids back, I'd COPY into an empty staging table first and do a single set-based INSERT ... SELECT ... ON CONFLICT from staging into the real table — full COPY speed for the bulk load, full conflict handling in one final statement." The signal: naming COPY as a different protocol, not just "INSERT but faster," and knowing the staging-table pattern for when conflict handling is still required.
