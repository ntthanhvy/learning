dbt seeds vs. sources

Today's tangible win: a small, rarely-changing CSV — a four-row city-to-region lookup — gets checked into the dbt project itself and loaded by dbt seed, then joined into a new stg_restaurants_enriched model with ref(), the exact same function used for every other model dependency so far. The point isn't the join; it's seeing, hands-on, the one real line between data dbt loads itself and data dbt only ever reads.

1 · Every raw table so far has arrived the same way — from outside dbt

raw.restaurants, raw.couriers and raw.orders all share one trait: something outside dbt put them there. Day 1's generator script loaded them with plain psycopg, and Day 6 added raw.order_events the same way, landed by a Kafka consumer. dbt never writes to any of the four — it only ever declares them with source() (Day 2) and reads from them. That split is deliberate, not incidental: a source is dbt's declaration that a table is someone else's responsibility to populate.

But not every small table in a real project arrives that way. A city-to-region mapping, a list of valid order statuses, a currency-conversion table that changes twice a year — reference data nobody wants to stand up a whole batch job for, and that changes rarely enough to live as a plain file. For exactly that case, dbt ships a second kind of raw input, one it does load itself: a seed.

2 · A real seed: city → region, checked in as a CSV

PLAN.md's own generator script (Day 1) hardcodes four cities — Hanoi, Ho Chi Minh City, Da Nang, Hue — directly in Python, with no region grouping anywhere. Adding "region" to the raw generator would mean touching Day 1's scaffolding and re-running the whole load for four rows of lookup data that will almost never change. A seed is the right tool precisely because this data: lives nowhere else in the warehouse, changes on a timescale of "maybe once a year," and is small enough to read in one glance in a pull request diff.

-- food_delivery_pipeline/seeds/seed_cities.csv
city,region
Hanoi,North
Ho Chi Minh City,South
Da Nang,Central
Hue,Central

Load it:

uv run --project ../dbt_env dbt seed

Expected: Completed successfully, naming seed_cities — and a real table now exists at dbt_dev.seed_cities (or wherever today's active target's schema points, per Day 31), with exactly 4 rows, no source() declaration anywhere, because dbt itself just built it.

3 · ref() on a seed looks identical to ref() on a model — on purpose

This is the detail worth remembering over any syntax: once loaded, a seed is just another node in the project's DAG, referenced with the exact same ref() used for stg_restaurants or fct_orders since Day 2. There is no separate "seed-reading" function.

-- models/staging/stg_restaurants_enriched.sql
select
    r.restaurant_id,
    r.name,
    r.cuisine,
    r.city,
    c.region,
    r.commission_rate
from {{ ref('stg_restaurants') }} as r
left join {{ ref('seed_cities') }} as c
    on r.city = c.city

ref('stg_restaurants') points at a model built from a source()-declared raw table; ref('seed_cities') points at a seed built from a checked-in CSV. dbt's dependency graph treats both the same way — build order, dbt build --select stg_restaurants_enriched+, and the lineage graph all work identically whether the upstream node is a model, a source, or a seed. The only place the distinction actually matters is at the edge: how the data got into the warehouse in the first place, not how anything downstream reads it.

4 · The line, stated as a rule you can defend out loud

The question "seed or source?" has one real test: who is responsible for the file getting into the warehouse, and how often does the data change? raw.orders fails both — a Python script owns the load, and 500 new rows could land tomorrow — so it's a source, always. seed_cities.csv passes both — dbt owns the load via dbt seed, and a new city opening is a deploy, not a daily event. The size test matters too: a seed's whole file lives in git and gets fully reloaded (dropped and recreated) on every dbt seed run, which is fine for four rows and actively wrong for anything resembling production order volume.

The trap: reaching for a seed when the real answer is "write a test instead." A list of the five valid order statuses (placed, accepted, picked_up, delivered, cancelled) looks like seed material, but it's better enforced as an accepted_values data test on stg_order_events.status (dbt_utils or dbt-core's own generic test) — a rule about what's valid, not a table to join against. Reach for a seed only when the data is genuinely joined into a query's result, like today's region column. If nothing ever selects a column out of it, it's a constraint, not a seed.

Q: "When would you use a dbt seed instead of a source?" A strong answer, out loud: "A source is for a table something outside dbt is responsible for landing — a script, a Kafka consumer, a CDC tool — and dbt only ever reads it. A seed is for small, rarely-changing reference data I'm willing to check into the dbt project itself as a CSV and let dbt load with dbt seed — a city-to-region mapping is a good example, because it changes maybe once a year and is small enough to review in a pull request diff. Once loaded, both are referenced with ref(), so the DAG and build order don't care which one it is — the distinction is entirely about who owns getting the data in, not how it's read afterward. I'd never use a seed for anything an external pipeline process already lands, and I'd never use it for a fixed list of valid values either — that's a data test, not a table to join." The signal: naming the ownership test directly, and naming the test-instead-of-seed trap without being asked.
