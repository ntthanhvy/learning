collections.deque & namedtuple: the two corners collections left uncovered

Day 3 already spent defaultdict and Counter from the collections module on grouping and counting. Today closes the module out with its other two everyday exports: deque, a list that's fast at both ends instead of just one, and namedtuple, a tuple whose fields you can call by name instead of remembering their position.

Bridge from SQL: a deque is the plain-Python shape of a message queue or a sliding window over the last N rows — the two ends matter, not random access into the middle, the same way a queue table is only ever read from the front and written at the back. A namedtuple is the shape of a query result row before an ORM wraps it: fixed, named columns, read-only once built — exactly what cursor.fetchone() hands back from many database drivers.

1 · The problem deque solves: a list is only fast at one end

Appending to the right end of a list, lst.append(x), is O(1) — cheap, no matter how long the list is. But working at the left end is a different story: lst.insert(0, x) and lst.pop(0) are both O(n), because every remaining element has to shift over by one to close or open the gap at index 0. That cost is invisible on a short list and brutal on a long one:

import time
from collections import deque

big_list = list(range(200_000))
big_deque = deque(range(200_000))

# popping 20,000 items from the FRONT of each
# big_list.pop(0)      -- measured ~0.39s : every pop reshuffles ~200,000 items
# big_deque.popleft()  -- measured ~0.001s: no shifting, ends are O(1)

Verified live: popping 20,000 items from the front measured roughly 0.39s for list.pop(0) against roughly 0.001s for deque.popleft() — a ~400x gap on this run, growing with list size since list.pop(0) is O(n) per call and deque.popleft() stays O(1) regardless of length. A deque (say "deck") is built for exactly this: a sequence kept as a doubly-linked structure under the hood so both ends are equally cheap.

2 · Working at both ends

deque mirrors list's right-end methods and adds a left-end sibling for each one:

from collections import deque

queue = deque(["a", "b", "c"])
queue.append("d")        # deque(['a', 'b', 'c', 'd'])      -- right end, like list.append
queue.appendleft("z")    # deque(['z', 'a', 'b', 'c', 'd'])  -- left end, list has no equivalent
queue.popleft()          # 'z' -- removes and returns the left end
queue.pop()               # 'd' -- removes and returns the right end, same as list

Verified live: after both pops, queue == deque(['a', 'b', 'c']), matching the four-line trace above. Indexing (queue[1]) and iteration still work like a list, but random access into the middle — indexing or inserting anywhere except the two ends — is O(n) on a deque, same cost as a list; a deque is a trade, not a strict upgrade. Reach for it specifically when the two ends are what matter: a work queue (push tasks on the right, take them off the left, first in first out), a browser-history-style undo stack, or a sliding window.

3 · maxlen: a deque that forgets its own tail

A deque built with maxlen= caps its own size — once full, adding to one end silently drops from the other, no manual trimming needed:

from collections import deque

recent = deque(maxlen=3)
for i in [1, 2, 3, 4, 5]:
    recent.append(i)
    print(list(recent))
# [1]
# [1, 2]
# [1, 2, 3]
# [2, 3, 4]   -- 4 pushes out 1 to stay at maxlen 3
# [3, 4, 5]   -- 5 pushes out 2

Verified live: matches the comment exactly. This is the standard shape for "keep the last N log lines," "last N requests for a rolling error rate," or any fixed-size sliding window — no separate length check, no manual pop(0) to trim.

4 · namedtuple: a tuple you can read by name

Day 4's tuples already let you unpack (x, y) = point, but reading a field back later means remembering which position held what — point[0] means nothing on its own. namedtuple builds a tuple subclass with named fields, so both spellings work:

from collections import namedtuple

Point = namedtuple("Point", ["x", "y"])
p = Point(3, 4)

p.x, p.y      # (3, 4) -- by name
p[0], p[1]      # (3, 4) -- still a real tuple, positional access still works
x, y = p      # unpacking still works exactly like a plain tuple
p             # Point(x=3, y=4) -- readable repr for free

Verified live: all four lines match their comments. namedtuple("Point", ["x", "y"]) reads as "build a new tuple subclass named Point, with fields x and y, in that order" — the string name and the field list are both required, and the string name should match the variable it's assigned to (Python won't enforce that, but mismatched names make tracebacks confusing). Because it's still a genuine tuple, a namedtuple is immutable — p.x = 10 raises AttributeError: can't set attribute, the same guarantee Day 1's tuple immutability already promised.

Where this sits next to a dataclass: Day 7's dataclass is the heavier, more flexible tool — mutable by default, supports type hints, methods, and defaults. namedtuple is the lighter one: immutable, tuple-compatible (unpacks, compares, hashes, works anywhere a plain tuple is expected), and zero-boilerplate for a small fixed record. Reach for namedtuple when a function returns a small, immutable bundle of values — divmod()-style — and a dataclass when the record needs to change after creation or grow real behavior.
Where pandas goes from here: nothing pandas-specific — DataFrame.itertuples() happens to hand back each row as a namedtuple-like object, but that's a detail of iterating an existing DataFrame, not something to demonstrate here; today's deque/namedtuple are plain-list and plain-tuple tools with no DataFrame involved, per MISSION.md.

Q: "How would you implement a fixed-size cache of the last 100 events, most-recent-first, with cheap inserts?" A strong answer, out loud: "collections.deque(maxlen=100). Every new event goes in with appendleft() so the newest is always at index 0; once the deque fills up, each further appendleft() automatically drops the oldest event off the right end — no manual length check or trimming. Both ends are O(1), so this stays cheap no matter how many events flow through, unlike a plain list where trimming from one end would be O(n) per insert." The signal: naming maxlen specifically, not just "a deque," and knowing which end to push into to get "most-recent-first" for free.
