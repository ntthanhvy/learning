Writing your own output-cache policy

Both Lesson 128's and Lesson 129's scope lines named the same thing as a real, deliberately deferred feature: a custom IOutputCachePolicy. Everything so far — Expire(), Tag(), SetVaryByQuery() — composes existing policy-builder methods. This lesson is about the one rung up: writing the policy itself, for rules the builder has no method for at all.

1 · What the default policy can't express

Lesson 128's default caching policy is fixed: only HTTP 200, only GET/HEAD, never a response that sets a cookie, never a response to an authenticated request. The policy-builder methods from Lessons 128-129 adjust knobs within that shape — how long, which query keys, which tag — but none of them can change the shape itself. Nothing in OutputCachePolicyBuilder can say "also cache POST" or "also cache a 301." That rule isn't a missing method waiting to be added; it's deliberate, because allowing it by accident is how one tenant's cached response ends up served to another. Reaching past the builder means implementing the interface the builder itself is built on.

2 · The IOutputCachePolicy interface

IOutputCachePolicy has three methods, each called at a different point in the request:

public sealed class MyCustomPolicy : IOutputCachePolicy
{
    public static readonly MyCustomPolicy Instance = new();
    private MyCustomPolicy() { }

    ValueTask IOutputCachePolicy.CacheRequestAsync(
        OutputCacheContext context, CancellationToken cancellationToken)
    {
        var allow = AttemptOutputCaching(context);
        context.EnableOutputCaching = true;
        context.AllowCacheLookup = allow;
        context.AllowCacheStorage = allow;
        return ValueTask.CompletedTask;
    }

    ValueTask IOutputCachePolicy.ServeFromCacheAsync(
        OutputCacheContext context, CancellationToken cancellationToken)
        => ValueTask.CompletedTask;

    ValueTask IOutputCachePolicy.ServeResponseAsync(
        OutputCacheContext context, CancellationToken cancellationToken)
    {
        var response = context.HttpContext.Response;
        if (response.StatusCode != StatusCodes.Status200OK &&
            response.StatusCode != StatusCodes.Status301MovedPermanently)
        {
            context.AllowCacheStorage = false;
        }
        return ValueTask.CompletedTask;
    }

    private static bool AttemptOutputCaching(OutputCacheContext context)
    {
        var request = context.HttpContext.Request;
        return HttpMethods.IsGet(request.Method) || HttpMethods.IsHead(request.Method)
            || HttpMethods.IsPost(request.Method);
    }
}

CacheRequestAsync runs first, before a handler executes — this is where the policy decides, from the request alone, whether to even look in the cache or consider storing a result. ServeFromCacheAsync runs if a stored entry was found, right before it's served. ServeResponseAsync runs after the handler produced a fresh response, deciding whether that response is actually allowed into the store — the example above widens Lesson 128's default past GET/HEAD-only and past 200-only, to also allow POST requests and 301 responses, exactly the two rules the builder's methods have no knob for.

3 · Registering and selecting it

A singleton custom policy registers like any named policy, then selects the same way Expire20 did back in Lesson 128:

builder.Services.AddOutputCache(options =>
{
    options.AddPolicy("CachePost", MyCustomPolicy.Instance);
});

app.MapPost("/cachedpost", Gravatar.WriteGravatar)
    .CacheOutput("CachePost");

If the policy needs constructor-injected dependencies instead of being a parameterless singleton, drop the private constructor and Instance field, give it a public constructor, and register it through DI instead:

options.AddPolicy("CachePost", b => b.AddPolicy<MyCustomPolicy2>(), true);

One documented trap: a custom policy used as a base policy must never sit alongside a bare CacheOutput() or [OutputCache] with no policy name on the same endpoint — calling either with no arguments silently re-adds Lesson 128's default policy on top, which is exactly the shape rule the custom policy exists to override.

Frontend-habit trap: this looks like writing a custom React Query queryClient default — override one global rule, done. The gap is where the rule runs: a custom IOutputCachePolicy's three methods execute entirely server-side, in the request pipeline, before and after a handler most callers never see — there's no client-side equivalent moment to reach into, since the client never holds the cached entity in the first place.

Scope line

This lesson covers the IOutputCachePolicy interface's three methods, OutputCacheContext's EnableOutputCaching/AllowCacheLookup/AllowCacheStorage flags, and registering a custom policy by singleton or by DI. It does not cover IOutputCachePolicyProvider (resolving policies dynamically from a database or per tenant — a .NET 11+ addition), the SizeLimit/MaximumBodySize cache-wide limits, or SetLocking(false)'s resource-locking opt-out — each a reasonable follow-up, out of scope for a first custom policy specifically.
