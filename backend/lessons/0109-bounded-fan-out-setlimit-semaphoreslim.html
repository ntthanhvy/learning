Fan out to 3 is easy. Fan out to 3,000 needs a limit.

Lesson 108's fan-out pattern launched exactly three goroutines (or three Tasks) and waited for all of them. That works fine for three fixed downstream calls. It breaks the moment the list isn't three items but three thousand — a batch of rows to reprocess, a directory of files to upload, a page of user IDs to notify. Launching one goroutine or Task per item, unbounded, can open thousands of outbound connections or threads at once and take the downstream service down. Today's lesson: bounding how many of those fan-out tasks run at once, in Go and in C#.

1 · Unbounded fan-out is a different bug than the one Lesson 108 covered

Take Lesson 108's shape and swap "3 fixed services" for "N items from a slice":

for _, item := range items {   // items has 3,000 elements
    item := item
    g.Go(func() error {
        return processItem(ctx, item)   // opens an outbound call per item
    })
}
if err := g.Wait(); err != nil { return err }

This compiles, and it is still structured concurrency in Lesson 108's sense — nothing outlives g.Wait(), and a failure still cancels the group's ctx. But it now launches 3,000 goroutines immediately, each opening its own outbound connection to whatever processItem calls. A downstream service built to handle 20 concurrent requests sees 3,000 at once. This is a width problem, not a cancellation problem — Lesson 108's fail-fast gotcha and this lesson's width gotcha are independent bugs that can both be present in the same loop.

2 · Go: errgroup.Group.SetLimit bounds the group itself

The errgroup package's own answer is one method call, added directly to the Group used in Lesson 108:

g, ctx := errgroup.WithContext(parentCtx)
g.SetLimit(20)   // at most 20 goroutines active in this group at once

for _, item := range items {
    item := item
    g.Go(func() error {              // blocks here if 20 are already active
        return processItem(ctx, item)
    })
}
if err := g.Wait(); err != nil { return err }

Per the package's own docs, SetLimit() "limits the number of active goroutines in this group to at most n... any subsequent call to the Go method will block until it can add an active goroutine without exceeding the configured limit." A negative n means no limit (the Lesson 108 behavior); zero blocks every Go() call forever. One documented catch worth flagging explicitly: the limit must not be changed while goroutines in the group are already active — call SetLimit once, before the loop starts, not mid-flight.

3 · C#: no equivalent on Task.WhenAll — bring your own SemaphoreSlim

Task.WhenAll has no built-in width cap at all; calling it with 3,000 pending Tasks starts all 3,000 immediately, same as the naive Go loop. The standard .NET answer is a SemaphoreSlim, constructed with the width as its initial count, and a WaitAsync()/Release() pair wrapped around each task's body:

using var gate = new SemaphoreSlim(initialCount: 20, maxCount: 20);

var tasks = items.Select(async item => {
    await gate.WaitAsync(ct);           // suspends here if 20 slots are taken
    try { return await ProcessItemAsync(item, ct); }
    finally { gate.Release(); }       // always free the slot, success or throw
});

await Task.WhenAll(tasks);

Per Microsoft's own docs, WaitAsync() "asynchronously waits to enter the SemaphoreSlim" — when the count is already zero, the awaiting Task simply suspends (the same non-blocking suspension Lesson 107 covered for any await) until some other task calls Release() and frees a slot. The finally block matters as much as the call itself: a Release() left out of a finally means one thrown exception permanently leaks a slot, and the gate slowly starves down to zero over the app's lifetime.

Not the same thing as Lesson 50's bulkhead: a bulkhead partitions capacity between different dependencies (pricing gets its own pool, inventory gets its own, so one saturating can't starve the other). SetLimit/SemaphoreSlim here cap the width of one single fan-out against one dependency. The same semaphore pattern is in fact how a bulkhead's per-dependency slice is often implemented underneath — this lesson is the narrower, one-call-site version of that idea.

Scope line

This lesson covers capping how many fan-out tasks run concurrently, with errgroup.Group.SetLimit and a hand-wired SemaphoreSlim. It does not cover: picking the right width number for a given downstream service's actual capacity (an operational tuning question, not a mechanism one); Task.WhenAny's manual first-one-wins pattern (Lesson 108's other flagged follow-on, still open); or a worker-pool with a fixed set of long-lived goroutines reading from a channel, which Lesson 25 already named as the alternative shape to a cap-per-call-site.
