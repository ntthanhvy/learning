The output cache's own size limits and its locking switch

Lessons 129 through 134 named the same two knobs as "out of scope for now" every single time: the SizeLimit/MaximumBodySize cache-wide limits, and SetLocking(false)'s resource-locking opt-out. Both are real properties on the same OutputCacheOptions class Lesson 128 already introduced — not new concepts, just two settings a first pass at output caching had no room for yet. This lesson finally closes that gap.

1 · Two different questions, two different limits

"How big can the cache get?" and "how big can one cached response be?" sound like the same question. OutputCacheOptions answers them with two separate properties, because they fail differently. SizeLimit caps the whole cache's total storage at 100 MB by default; once that total is reached, Microsoft's own docs say "no new responses will be cached until older entries are evicted" — existing entries keep serving, but the cache simply stops growing. MaximumBodySize instead caps one response at 64 MB by default; the docs are direct about the consequence: "If the response body exceeds this limit, it will not be cached" — that one response is skipped outright, regardless of how much room the overall cache still has.

builder.Services.AddOutputCache(options =>
{
    options.SizeLimit = 100 * 1024 * 1024; // total cache budget; 100 MB is the default
    options.MaximumBodySize = 64 * 1024 * 1024; // per-response ceiling; 64 MB is the default
    options.DefaultExpirationTimeSpan = TimeSpan.FromSeconds(60); // Lesson 128's own default, same class
});

A large response that trips MaximumBodySize never gets the chance to count against SizeLimit at all — the per-response check runs first and rejects it before it ever reaches the shared storage budget. A busy, mostly-small-response cache is far more likely to fill up SizeLimit than to trip MaximumBodySize on any single entry; the two limits guard against two different failure shapes, not the same one at two scales.

Frontend-habit trap: this reads like a CDN's per-object size cap, and the per-response half genuinely is that. But SizeLimit has no browser-cache equivalent at all — a browser's HTTP cache is sized and evicted by the browser itself, never something application code configures. Here, both numbers are backend configuration the app owns directly, in the same options object as the expiration time from Lesson 128.

2 · Why locking is on by default, and what turning it off actually risks

Lesson 57 named the failure mode directly: a hot cache key expires, and every request arriving in that instant falls through to the origin at once — a cache stampede. Output caching ships a default defense against exactly that, and the docs say so in as many words: "By default, resource locking is enabled to mitigate the risk of cache stampede and thundering herd." Concretely, when many requests for the same not-yet-cached key arrive together, only the first acquires the lock and actually runs the handler; the rest wait for that result instead of each separately recomputing it — Lesson 57's request-coalescing fix, built into the middleware instead of hand-rolled.

Turning locking off is one call on a policy builder:

builder.Services.AddOutputCache(options =>
{
    options.AddPolicy("NoLock", builder => builder.SetLocking(false));
});

app.MapGet("/nolock", Gravatar.WriteGravatar)
    .CacheOutput("NoLock");

With locking off, every one of those simultaneous requests runs the handler independently the instant the key is missing — the exact pile-up Lesson 57 taught request coalescing to prevent. That trade only makes sense for a handler cheap enough that duplicate concurrent runs cost nothing worth guarding against; for anything that queries Postgres or calls a slow downstream service, leaving the default locking in place is the safer choice, and Lesson 129's eviction calls and Lesson 128's expiration times both already assume it's there.

Scope line

This lesson covers OutputCacheOptions.SizeLimit, OutputCacheOptions.MaximumBodySize, and SetLocking(false)'s resource-locking opt-out — the two limits and the one locking switch named out of scope across Lessons 129 through 134. It does not cover writing a custom eviction policy around SizeLimit pressure, nor benchmarking the actual cost of resource locking under real contention — both reasonable next steps, not today's.
