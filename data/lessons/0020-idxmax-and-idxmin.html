idxmax() and idxmin(): WHICH row, not just the value

Lesson 19's closing teaser named this pair directly — "idxmax()/idxmin(), finding WHICH row holds the max/min, not just the value." A distinction interview candidates fumble constantly: .max() hands you a number with no way back to the row it came from.

1 · .max() gives the VALUE, idxmax() gives the LABEL

Every lesson so far that touched a max/min used .max()/.min() — they return the value itself, with no memory of which row produced it. idxmax() and idxmin() answer a different question: "which ROW is that?" On the clean 4-row amount slice Lessons 6-19 have used (An/120.0/01-05, Binh/35.5/01-06, Binh/180.0/01-09, An/42.0/01-10):

clean["amount"].max()      # 180.0  -- just the number
clean["amount"].idxmax()   # 4      -- the INDEX LABEL of the row holding 180.0

clean["amount"].min()      # 35.5
clean["amount"].idxmin()   # 1      -- the row holding 35.5

.max() says "the biggest order was 180.0" — useful, but it can't tell you whose order that was or when it happened. .idxmax() says "row label 4 is the one" — the row's ADDRESS, not its content. Notice 4, not 2: this DataFrame's index still carries the original row positions from orders_raw.csv before the unparseable/missing rows were dropped, so the index label and the row's position in clean aren't the same number. That gap is exactly why idxmax() returns the LABEL — it always finds the row correctly by name, regardless of how the DataFrame got filtered or reordered beforehand.

2 · .loc[idx]: turning the label into the full row

An index label alone isn't very useful in an interview answer — the real move is feeding it straight into .loc[] to pull back the entire row, every column, not just the one you maxed on:

clean.loc[clean["amount"].idxmax()]
# order_id               5
# customer            Binh
# amount              180.0
# order_date    2026-01-09
# Name: 4, dtype: object

That's the whole point of returning a label instead of a value: .max() alone can never get you back to customer or order_date for the winning row — you'd need a separate filter (clean[clean["amount"] == clean["amount"].max()]) that's slower to write, and silently wrong if two rows happen to tie on the max value (it would return both). idxmax() + .loc[] is the direct, unambiguous path from "biggest value" to "everything about that row."

3 · groupby(...)["col"].idxmax(): the top row PER GROUP

Chained after groupby(), idxmax() answers one of the most common interview patterns there is: "find the top order per customer." Not the top amount — the whole top ROW, per customer:

top_idx = clean.groupby("customer")["amount"].idxmax()
# customer
# An      0
# Binh    4
# Name: amount, dtype: int64

clean.loc[top_idx]
#    order_id customer  amount  order_date
# 0         1       An   120.0  2026-01-05
# 4         5     Binh   180.0  2026-01-09

Each customer's idxmax() gives back the label of THEIR biggest order — An's is row 0 (120.0, their only other order was 42.0), Binh's is row 4 (180.0, beating their 35.5). Feeding that Series of labels straight into .loc[] pulls back one full row per customer in a single step: no separate merge, no manual sort-then-groupby().head(1) dance. This is the pattern to reach for anytime an interview question says "find the <top/latest/biggest> X per Y" and you need more than just the winning number.

4 · The SQL bridge: no single equivalent

This is worth naming explicitly, because it's where pandas is genuinely more concise than SQL, not just differently spelled. SQL has no single function that means "the row holding the max, per group" — you reach for one of two heavier constructs:

-- Option A: ORDER BY ... LIMIT 1 per group (subquery or LATERAL join)
SELECT c.customer, o.*
FROM (SELECT DISTINCT customer FROM orders) c
CROSS JOIN LATERAL (
  SELECT * FROM orders o
  WHERE o.customer = c.customer
  ORDER BY amount DESC LIMIT 1
) o;

-- Option B: window function, then filter to rank 1
SELECT * FROM (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY customer ORDER BY amount DESC) AS rn
  FROM orders
) ranked
WHERE rn = 1;

-- pandas: one line
clean.loc[clean.groupby("customer")["amount"].idxmax()]

Both SQL options need real ceremony — a correlated subquery/LATERAL join, or a window function wrapped in an outer WHERE rn = 1 filter. groupby(...)["col"].idxmax() collapses that entire shape into one call precisely because groupby() in pandas is already an object you can chain further operations onto, unlike a SQL GROUP BY clause, which only exists inside one aggregation query.

Ties, and NaN: if two rows in a group tie exactly on the max value, idxmax() returns only the FIRST one it encounters (by row order) — same "returns one winner" behavior as ROW_NUMBER() would need method="first"-style tie-breaking (Lesson 7) to guarantee reproducibly. And idxmax()/idxmin() raise a ValueError on an all-NaN Series or empty group — there's no "which row" answer when there's no data, so unlike .max() (which returns NaN quietly), idxmax() refuses to guess.

Q: "How would you find, for each customer, their single largest order — the full row, not just the amount?" A strong answer, out loud: "I'd use groupby('customer')['amount'].idxmax() — that gives me the index label of the max-amount row within each group, as a Series keyed by customer. Then I feed that straight into .loc[] on the original DataFrame to pull back the full row — every column, not just amount. I reach for idxmax() specifically over plain max() whenever I need to get BACK to the row, not just the number; max() alone throws away which row it came from. In SQL I'd need either a LATERAL join with ORDER BY ... LIMIT 1, or a ROW_NUMBER() OVER (PARTITION BY customer ORDER BY amount DESC) window function filtered to rank 1 — pandas collapses both of those into one line because groupby() there is a live object I can keep chaining, not just a clause." The signal: naming that SQL has no single equivalent, and being explicit that idxmax() returns a LABEL, not a value.
