contextlib: ready-made context managers beyond @contextmanager

Day 29 taught you to write a context manager, either as a class or with @contextmanager. Today is shorter: two context managers the standard library already wrote for you, for two problems that show up constantly — ignoring one specific, expected exception cleanly, and closing a variable, not-known-in-advance number of resources no matter how the middle fails.

Bridge from SQL: DROP TABLE IF EXISTS exists so you don't have to check whether the table is there before dropping it — the database swallows exactly one specific, expected failure and nothing else. contextlib.suppress() is that same narrow, named tolerance applied to Python's own exceptions.

1 · contextlib.suppress(): ignoring one named exception, cleanly

A common pattern: delete a file that might already be gone, and don't treat "already gone" as an error.

import os

try:
    os.remove("report.tmp")
except FileNotFoundError:
    pass

That works, but a bare except: pass-shaped block reads as "something is being silently ignored here" even when it's completely intentional and narrow. contextlib.suppress() says the same thing declaratively, naming exactly what's expected:

from contextlib import suppress
import os

with suppress(FileNotFoundError):
    os.remove("report.tmp")
# execution continues right here whether the file existed or not

Verified live: raising ValueError inside that same with suppress(FileNotFoundError): block does not get swallowed — it propagates out normally, exactly as if suppress weren't there. suppress() accepts multiple exception types as separate arguments (suppress(FileNotFoundError, PermissionError)), and only exactly those types are ignored. This is a different thing from Day 29's exception suppression (Day 29) — that was about what a hand-written __exit__ returns; suppress() is a ready-made context manager that does the narrow version of the same job without writing a class at all.

2 · contextlib.ExitStack(): a variable number of context managers

with handles a fixed number of resources fine — with open(a) as fa, open(b) as fb: — but that syntax can't handle "however many files happen to be in this list," decided at runtime. ExitStack is built for exactly that:

from contextlib import ExitStack

filenames = ["a.txt", "b.txt", "c.txt"]   # length only known at runtime

with ExitStack() as stack:
    files = [stack.enter_context(open(name)) for name in filenames]
    # ... use files ...
# every opened file is closed here, in reverse order, even if the loop raised partway through

stack.enter_context(cm) calls cm's __enter__ immediately (Day 29's protocol, called by hand instead of by with's own syntax) and remembers to call its __exit__ later. Verified live with a logging stand-in for three resources: opening all three then raising partway through the block still closed all three that had already opened, in reverse order (c, then b, then a) — ExitStack gives the same all-or-nothing cleanup guarantee as a fixed with a, b, c: chain, just for a list built at runtime instead of names typed in the source.

stack.callback(fn) queues a plain function, not just a context manager. Verified live: stack.callback(lambda: log.append("cleanup")) runs fn at the same point __exit__ would run — useful for one-off cleanup (deleting a temp file, closing a socket) that doesn't have its own context-manager class.

3 · One more corner, named not demonstrated: redirect_stdout

contextlib.redirect_stdout(target) temporarily points print()'s output at a different file-like object for the duration of a with block, then restores it — handy for capturing output from code that only knows how to print(). Named here for the module's shape, not built into today's practice file; the docs cover it in one short example if it's ever needed.

Q: "How would you clean up an unknown number of resources safely?" A strong answer, out loud: "contextlib.ExitStack — build the list of things to open at runtime, call stack.enter_context() on each inside a with ExitStack() as stack: block, and every one of them is guaranteed to close, in reverse order, even if something partway through raises. A fixed with a, b, c: chain only works when you know the count and names ahead of time; ExitStack is the version of that guarantee for a count decided at runtime." The signal: recognizing that with's multi-manager syntax has a real limit, and knowing the standard-library answer instead of hand-rolling a try/finally loop that closes already-opened resources on error.

Where pandas goes from here: nothing pandas-specific here — ExitStack and suppress() are plain Python plumbing that a pandas script would reach for exactly the same way, e.g. wrapping a variable number of open() calls before any pd.read_csv() runs.
