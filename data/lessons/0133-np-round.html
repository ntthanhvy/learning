np.round(): rounding to the nearest even digit, not the nearest half

Lesson 132 closed its own fresh scan with nothing pre-committed. Today's own fresh scan grepped every lesson body and every glossary row case-insensitively for np.round(, np.rint(, Series.round(: both np.round() and Series.round() had appeared only as one-line contrast points inside Lessons 130/131/132's own sections (never given their own exercise), and np.rint() had zero hits anywhere — a real gap, not a narrowing of something already taught. np.round() is the pick: it is the single most common "why did my number come out wrong" interview surprise in this whole elementwise-ufunc lineage.

1 · Banker's rounding: ties round to the nearest EVEN digit, not always up

np.round(a, decimals=0) rounds every element to the given number of decimal places. The trap, confirmed directly (numpy 2.5.5, pandas 3.1.1): on an exact .5 tie, it does NOT always round up or away from zero — it rounds to whichever neighbor is even, a rule called banker's rounding.

import numpy as np
import pandas as pd

np.round(0.5)   # 0.0  -- rounds DOWN to the even neighbor, not up to 1
np.round(1.5)   # 2.0  -- rounds UP to the even neighbor this time
np.round(2.5)   # 2.0  -- rounds DOWN again, 2 is even
np.round(-0.5)  # -0.0 -- same even-neighbor rule, mirrored for negatives

Confirmed directly, Series.round() follows the identical rule and both accept the same output: called on a Series, np.round(s) keeps the Series' own Index and matches s.round() value-for-value. This is deliberate, documented NumPy/IEEE 754 behavior (round-half-to-even), not a bug — but it is the opposite of the "always round .5 up" rule taught in most schools, and the one most people walk into an interview still assuming.

2 · decimals=: how many places, and the negative-decimals trick

Confirmed directly, decimals= (positional or keyword) controls how many digits after the decimal point survive; a negative value rounds to the left of the decimal point instead — tens, hundreds, thousands.

np.round(2.345, 2)      # 2.35 -- two decimal places
np.round(1234.5678, -2)  # 1200.0 -- negative decimals rounds to the nearest hundred

prices = pd.Series([19.995, 4.995, 100.004])
prices.round(2)   # two-decimal currency rounding, Index kept, same call either spelling

Confirmed directly, an int64 Series is a true no-op under np.round() — dtype and values both stay exactly unchanged, the same no-op rule Lesson 130's np.floor()/np.ceil() follow, not the always-upcast rule Lesson 129/131's np.sqrt()/np.log()/np.exp() follow (rounding an already-whole int to any number of decimal places changes nothing).

Confirmed directly, the sharper trap: np.round(2.675, 2) returns 2.68 — which looks like ordinary "round half up," not banker's-rounding-to-even (2.68 is even in the last digit either way, so this one doesn't disambiguate the rule). The real reason is underneath: 2.675 is not stored exactly in float64 at all. Its true stored value is 2.67499999999999982... — already slightly below the halfway point before rounding even starts. Any decimal literal with more digits than float64 can represent exactly is already a rounded value the moment it is typed — "the tie I thought I was rounding" may not be an exact tie in memory at all.
from decimal import Decimal
Decimal(2.675)   # Decimal('2.67499999999999982236431605997495353221893310546875')
np.round(2.675, 2)   # 2.68 -- still not what the stored value alone would predict; NumPy's own
                   # rounding algorithm does not simply chop the stored float and compare

3 · np.rint(): the no-decimals-argument sibling, and the missing Series.round() gap it doesn't have

Confirmed directly, np.rint(a) is np.round(a, decimals=0) with no decimals= parameter at all — always rounds to the nearest whole number, same banker's-rounding-to-even tie rule. Unlike every other elementwise ufunc in this lineage (Lessons 126-132), confirmed directly, pandas actually DOES define Series.round() — there is no naming gap here, the one case in this whole family where the pandas method and the NumPy function are both first-class and agree exactly. np.rint() has no equivalent pandas method name — calling Series.rint() raises AttributeError immediately, confirmed directly, so Series.round() (no arguments) is the pandas-idiomatic spelling instead.

Q: "If I round 2.5 and round 1.5, why don't I get the same pattern — shouldn't both round up?" A strong answer, out loud: "NumPy and pandas both use banker's rounding — IEEE 754's round-half-to-even — not the 'always round .5 up' rule taught in school. An exact tie rounds to whichever neighboring integer is even, so round(0.5) is 0, round(1.5) is 2, and round(2.5) is 2 again. The sharper trap underneath: most decimal literals like 2.675 aren't stored exactly in float64 at all — the true stored value is already 2.67499999...98, slightly below the tie — so what looks like a rounding-rule surprise is sometimes really a floating-point-representation surprise instead. For money or exact-decimal needs, I'd reach for Python's Decimal type rather than trusting float rounding at all." The signal: naming banker's rounding specifically, and not stopping at "floats are imprecise" without the concrete 2.675 example.
