1 · Seeing the race condition for real

Day 73 and Day 108 both described a race condition. Here it is actually happening. Four threads each run this 2,000 times on one shared counter, with a deliberate gap between reading and writing so a thread switch is almost certain to land in the middle:

import threading
import time

counter = 0

def bump(n):
    global counter
    for _ in range(n):
        temp = counter        # read
        time.sleep(0)         # yield to another thread -- widens the race window
        counter = temp + 1   # write

threads = [threading.Thread(target=bump, args=(2000,)) for _ in range(4)]
for t in threads: t.start()
for t in threads: t.join()
print(counter)   # expected 8000 -- confirmed live, actual result was 2003

Four threads each incrementing 2,000 times should land on exactly 8,000. It doesn't, confirmed live: most of the increments vanish, because two threads can both read the same temp before either writes it back — the second write overwrites the first's result instead of building on it. The simpler counter += 1 (no explicit time.sleep(0)) often happens to come out correct on a short loop like this, since the whole operation can fit inside one scheduler turn — which is the trap: a race condition that doesn't show up in your 3 test runs isn't fixed, it's just lucky. The gap here is deliberately widened to make the bug reliable instead of occasional.

2 · threading.Lock: one thread at a time, enforced

A lock fixes this by making every thread wait its turn around the risky lines — the critical section:

import threading
import time

counter = 0
lock = threading.Lock()

def bump(n):
    global counter
    for _ in range(n):
        with lock:              # acquire() on entry, release() on exit -- even if an exception escapes
            temp = counter
            time.sleep(0)
            counter = temp + 1

threads = [threading.Thread(target=bump, args=(2000,)) for _ in range(4)]
for t in threads: t.start()
for t in threads: t.join()
print(counter)   # 8000 -- confirmed live, exact every run, same bump() body as Section 1

with lock: is the idiom, the same context-manager shape Day 6 taught for files: it calls lock.acquire() on entry and lock.release() on exit, guaranteed, even if an exception escapes the block — confirmed live, a ValueError raised inside a with lock: block still leaves lock.locked() reporting False right after. The manual spelling, lock.acquire() ... lock.release(), works identically but a forgotten release() on an exception path leaves the lock stuck forever — the same "forgot to close it" risk Day 6 named for files, except a stuck lock freezes every other thread waiting on it, not just one leaked handle.

Confirmed live — a second acquire() genuinely blocks: one thread calls lock.acquire() and never releases it; a second thread's lock.acquire() call does not raise or return early — it sits there waiting. Only after the first thread calls .release() does the second thread's call return. lock.locked() reports whether a lock is currently held, without touching it — useful for a status check, never for deciding whether to acquire (another thread could acquire it in the gap between the check and the real acquire() call).

3 · The trap: acquiring the same Lock twice

A plain threading.Lock does not know which thread holds it — only whether it is held. Calling .acquire() a second time from the same thread that already holds it blocks exactly like a different thread would, waiting forever for a release that can now never come from anywhere:

import threading

lock = threading.Lock()
lock.acquire()
lock.acquire()   # deadlock -- this thread already holds it and now waits on itself, forever
print("never reached")

This is a deadlock: the program doesn't crash, it just hangs with no error to explain why — the same silent-hang shape Day 108 showed for a skipped task_done(). threading.RLock ("reentrant lock") is the escape hatch, confirmed live: the same thread can acquire it multiple times without blocking itself, as long as it calls .release() the same number of times before another thread can acquire it — useful when a function holding a lock needs to call another function that acquires the same lock, but not a default reach-for; a plain Lock catching this bug loudly (by hanging) is often more useful than an RLock quietly tolerating code that re-enters more than intended.

Where pandas/NumPy go from here: neither needs manual locking for this — a single-threaded pandas script has no competing threads to race, and NumPy's own C-level operations release the GIL internally for the duration of one call rather than asking the caller to manage a lock. Locks matter here because plain Python threads sharing plain Python objects is the case Day 73's ThreadPoolExecutor and this lesson both live in. Not covered further here, per MISSION.md.
