Server-Sent Events, now in C# too (TypedResults.ServerSentEvents, SseItem<T>)

Lesson 63 built SSE the hand-rolled way: grab the http.Flusher, set Content-Type: text/event-stream yourself, and format every event as a literal data: {...}\n\n string in a loop. Lesson 102 then covered SignalR, which uses SSE only as one of three automatic fallback transports underneath a different abstraction — never SSE on its own terms. As of .NET 10, ASP.NET Core Minimal APIs finally have a first-party way to return a plain SSE stream directly: TypedResults.ServerSentEvents, with a typed SseItem<T> wrapper instead of hand-formatted text.

1 · The gap Lesson 63 and 102 both left open

Lesson 63's Go handler worked, but every part of the wire format was the application's own responsibility: setting the header, writing the data: prefix, writing the blank line that ends an event, and flushing after each write so the browser doesn't wait on a buffer. Lesson 102 showed that SignalR already knows how to speak SSE — it's transport #2 in the fallback order behind WebSockets — but only as an internal detail of a hub connection, never exposed as "just give me an SSE endpoint." Until .NET 10, writing a plain SSE endpoint in ASP.NET Core meant doing exactly what Lesson 63's Go code did: set the header and write formatted strings to the response body by hand. Microsoft.AspNetCore.Http's new TypedResults.ServerSentEvents closes that gap: the handler hands over an async sequence of values, and the framework writes the stream.

2 · The same loop, now returned instead of written by hand

Lesson 63's Go handler pulled events off a channel inside a for/select loop and wrote each one itself. A Minimal API endpoint doing the same job returns an IAsyncEnumerable<T> and lets the framework drive the loop:

app.MapGet("/orders/{id}/updates", (int id, CancellationToken ct) =>
    TypedResults.ServerSentEvents(GetOrderUpdates(id, ct)));

async IAsyncEnumerable<OrderStatus> GetOrderUpdates(
    int id, [EnumeratorCancellation] CancellationToken ct)
{
    while (!ct.IsCancellationRequested)
    {
        var status = await _statusFeed.NextAsync(id, ct);
        yield return status;
    }
}

Binding a CancellationToken parameter in a Minimal API handler gives it HttpContext.RequestAborted automatically — the same signal Lesson 63's Go version read off r.Context().Done() inside its select — so the generator loop above stops the moment the client disconnects, without a separate disconnect check anywhere. yield return is doing the job Lesson 63's fmt.Fprintf plus flusher.Flush() did by hand: producing one value, handing it off, and waiting for the next. There is no header to set and no flush call to remember — TypedResults.ServerSentEvents owns both.

3 · SseItem<T>: an event is a typed value, not a formatted string

Section 2's example streams a plain OrderStatus value per event, serialized through the app's configured JSON options — a reasonable default, but it skips the three extra fields the SSE wire format itself defines: an event type, an id the browser echoes back on reconnect, and a server-chosen retry interval. Lesson 63's Go version had to splice those directly into the formatted string if it wanted them at all. In C#, they're named properties on SseItem<T>, constructed per event instead of written as string literals:

IAsyncEnumerable<SseItem<OrderStatus>> GetOrderUpdates(int id, CancellationToken ct)
{
    await foreach (var status in _statusFeed.Subscribe(id, ct))
    {
        yield return new SseItem<OrderStatus>(status, eventType: "order-status")
        {
            EventId = status.Version.ToString(),
            ReconnectionInterval = TimeSpan.FromSeconds(5)
        };
    }
}

That EventId is the C# side of a detail Lesson 63's browser-facing half mentioned only as "the browser reconnects automatically" without saying what it sends on the way back in: EventSource remembers the last event id it received and resends it as a Last-Event-ID request header on reconnect, so a server can resume a stream from where a dropped connection left off instead of replaying everything. ReconnectionInterval is the server telling the browser how long to wait before that reconnect attempt — a tuning knob Lesson 63's hand-rolled version had no field for at all, because it never wrote anything but data: lines.

Frontend-habit trap: Last-Event-ID looks like it should be something the frontend code reads and resends manually, the way you'd persist a cursor to localStorage. It isn't — EventSource tracks and resends it internally, with no application code touching it on either side of the connection unless you explicitly override it. The only decision left to the backend is whether to set a meaningful EventId at all; an endpoint that never sets one gives the browser nothing useful to resume from, and every reconnect effectively restarts the stream from scratch.

4 · What's unchanged, and what this still doesn't do

Every architectural limit Lesson 63 named stays exactly as true here: SSE is still one-way, server-to-client only — TypedResults.ServerSentEvents gives a handler a cleaner way to produce that one-way stream, not a second channel back. A chat app's outgoing messages still need an ordinary POST endpoint alongside the SSE one, in C# exactly as in Go. And Lesson 63's capacity warning carries over unchanged too: each open SSE connection is a held resource — in the C# version, an IAsyncEnumerable generator suspended on an await, not a blocked goroutine, but still something a server holding thousands of them at once has to plan for the same way Lesson 18 planned for connection-pool exhaustion. TypedResults.ServerSentEvents changes how much code the stream costs to write; it doesn't change the direction, or the fact that holding the connection open is still the whole feature.

Q: "We need live order-status updates in an ASP.NET Core API — build it with Minimal APIs, nothing fancier." A strong answer, out loud: "Since .NET 10, there's a first-party way to do this without hand-formatting anything: return TypedResults.ServerSentEvents from the endpoint, backed by an async method that yields SseItem<OrderStatus> values as the status changes. Binding a CancellationToken parameter gets me the client-disconnect signal for free, and setting EventId on each item means a client that reconnects after a drop sends Last-Event-ID back and I can resume instead of replaying the whole history. What I still need to decide myself is capacity — each open connection is a suspended generator held open for as long as the client stays connected, same cost as Lesson 63's Go version, just a different runtime primitive holding it." The signal: knowing what the framework now writes for free (the wire format, the reconnect id plumbing) versus what's still an application decision no library makes for you (how many of these a server can hold open, and whether resuming from Last-Event-ID is worth implementing).

Scope line

This lesson covers TypedResults.ServerSentEvents's IAsyncEnumerable<SseItem<T>> overload, SseItem<T>'s EventId/EventType/ReconnectionInterval properties, and the bound-CancellationToken disconnect signal. It does not cover the two simpler overloads (a bare IAsyncEnumerable<string>, or IAsyncEnumerable<T> with a single shared eventType), actually implementing Last-Event-ID-based resume server-side (the property exists; reading the incoming header back and replaying from it is application code this lesson doesn't write), or MVC-controller equivalents — every example above is a Minimal API endpoint, the shape Microsoft's own reference for this API uses throughout.
