gRPC: the other API shape

Lesson 69 said a load balancer "doesn't know or care whether the payload is HTTP, gRPC, or raw binary." Lesson 71 name-dropped "gRPC's ORCA load reporting" in a code comment. Both times, the word walked past without a definition. Today it gets one: what gRPC actually is, why a service team reaches for it instead of Lesson 3's REST contract, and where it still loses.

1 · Same job as Lesson 3, different contract

Lesson 3 built an API contract out of URLs, HTTP verbs, and hand-written JSON shapes — GET /orders/42 returns whatever JSON your handler happens to write, and the client has to already know (from docs, or from reading the code) what fields to expect back. gRPC starts from a different question: instead of "what resource lives at this URL," it asks "what function am I calling on that other service, with what typed arguments, getting back what typed result." A client doesn't build a URL and parse loose JSON; it calls client.GetOrder(ctx, &OrderRequest{Id: 42}) and gets back a *OrderResponse struct — generated code, not hand-parsed JSON, stands between the call site and the network.

That contract is written down once, in a .proto file:

// order.proto -- the contract both sides compile against
service OrderService {
  rpc GetOrder(OrderRequest) returns (OrderResponse);
}

message OrderRequest {
  int64 id = 1;
}

message OrderResponse {
  int64 id = 1;
  string status = 2;
  int64 total_cents = 3;
}

Run that file through gRPC's protoc compiler and both sides get generated Go (or Java, Python, whatever each service happens to be written in) with that exact shape baked in — a field renamed on one side and not the other fails at compile time, not as a silent undefined three services downstream. Lesson 3's JSON error contract solved the same "what shape am I getting back" problem by convention and discipline; gRPC solves it by generating code from a schema that can't drift out of sync without a build failing.

2 · What's actually different underneath: binary, not text

REST's JSON body is human-readable text you can paste into a browser tab or curl and eyeball. gRPC messages are protocol buffers on the wire: the same OrderResponse serializes to a compact binary blob, not {"id": 42, "status": "shipped", "total_cents": 4999}. Smaller payloads, faster to parse on both ends — real savings at the scale of thousands of internal calls per second between services — but you lose the "just read the response in the network tab" debugging habit Lesson 1 assumed; you need the schema (or a tool that already has it) to make sense of captured traffic.

gRPC also runs on HTTP/2 specifically, which is what lets one open connection carry many concurrent calls at once without them queuing behind each other — the same multiplexing Lesson 50's bulkhead lesson named in passing as "invisible infrastructure" on the browser side. A plain REST API can run on HTTP/2 too, but gRPC requires it; REST never did.

3 · Where each one actually wins

QuestionREST + JSONgRPC
Typical callerBrowsers, mobile apps, third-party integratorsYour own services calling each other internally
Readable off the wireYes — plain text JSONNo — binary, needs the schema to decode
Contract enforcementConvention + docs + discipline (Lesson 3)Compiled from a shared .proto, drift fails at build time
Browser supportNative — it's just HTTP + JSONNeeds a proxy (grpc-web) — browsers can't speak it directly
StreamingBolted on (SSE, WebSockets — Lesson 63)Built into the contract itself, both directions

The browser row is the one that decides most of it: gRPC's binary framing isn't something browser JavaScript can originate directly, so anything a web frontend calls straight from the browser is REST (or GraphQL) territory almost by default. gRPC shows up overwhelmingly on the service-to-service hop — Lesson 31's "caller isn't a person" case — where both ends are services you control, both get regenerated from the same .proto on every change, and the binary format's speed advantage actually compounds across thousands of internal calls.

Frontend-habit trap: "my API" at work is almost certainly the REST one a browser or mobile app calls directly. gRPC, if your company uses it at all, usually lives one hop further back — between backend services you never see from the browser's network tab. That's exactly why the word showed up twice in this course already (Lessons 69, 71) purely as "the other thing a load balancer might be routing," never as something a frontend-facing API needed to be.

4 · A minimal server in Go

The generated code does the serialization and routing; your job is the same business logic a REST handler would have, just behind a typed method instead of a parsed URL and body:

// Generated from order.proto by protoc; this is the part you write --
// the method body, same shape as any REST handler's core logic.
type orderServer struct {
    pb.UnimplementedOrderServiceServer
    db *sql.DB
}

func (s *orderServer) GetOrder(ctx context.Context, req *pb.OrderRequest) (*pb.OrderResponse, error) {
    var orderStatus string
    var totalCents int64
    err := s.db.QueryRowContext(ctx,
        "SELECT status, total_cents FROM orders WHERE id = $1", req.Id,
    ).Scan(&orderStatus, &totalCents)
    if err == sql.ErrNoRows {
        // gRPC has its own status codes -- NotFound here, not an HTTP 404
        return nil, status.Errorf(codes.NotFound, "order %d not found", req.Id)
    }
    if err != nil {
        return nil, status.Errorf(codes.Internal, "lookup failed")
    }
    return &pb.OrderResponse{Id: req.Id, Status: orderStatus, TotalCents: totalCents}, nil
}

Notice codes.NotFound and codes.Internal in place of Lesson 3's 404 and 500: gRPC has its own small fixed set of status codes, carried in the RPC response rather than an HTTP status line, but the same 4xx-vs-5xx instinct from Lesson 3 maps straight across — NotFound/InvalidArgument are the caller's problem to fix, Internal/Unavailable are yours.

Q: "When would you reach for gRPC instead of a REST API?" A strong answer, out loud: "For anything a browser or mobile client calls directly, I'd default to REST — it's human-readable, debuggable with curl, and browsers can't originate gRPC's binary framing without a proxy in front of it anyway. I'd reach for gRPC on the internal service-to-service hop, once I control both ends: the .proto file becomes the one contract both sides compile against, so a field rename that breaks the other service fails at build time instead of shipping a silent bug, and the binary wire format and HTTP/2 multiplexing actually pay off at the call volume internal services see. I wouldn't introduce it just because it's faster in a microbenchmark — the schema-driven contract and the build-time safety are the real reason, speed is a secondary benefit." The signal: picking the tool by who's calling and what breaks on drift, not by raw throughput alone.

Scope line

This lesson covers what gRPC is, its contract-first shape, and the REST-vs-gRPC decision at the level needed to recognize and discuss it in a review or an interview. It doesn't cover streaming RPCs (unary call shown here is one of four gRPC call shapes), protobuf's full type system and versioning rules (field numbers, reserved fields, backward compatibility), load balancing specifics for gRPC (Lesson 69's L4/L7 split applies differently to a protocol that multiplexes many calls over one connection), or GraphQL (Lesson 97's own deferred comparison point) — each is a real extension of today's model, not needed to have the vocabulary straight.
