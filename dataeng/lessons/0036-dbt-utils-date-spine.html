1 · The gap Day 11 named and never closed

mart_delivery_sla has reported "minutes from placed to delivered, and the share of orders over 45 min per city per day" since Day 6, and Day 11 gave it a real surrogate key over its true grain, (city, order_date). But the mart's own group by city, order_date can only ever produce a row for a combination that had at least one order. A city with zero orders on a given day — a slow Tuesday, a city that just launched and has three days of history — doesn't get a row showing "0 orders, 0 breaches." It gets no row at all, silently. Anyone querying mart_delivery_sla to ask "which cities are breaching SLA most this month" sees only days that had traffic, with no way to tell "0% breach rate" apart from "this city-day never happened" unless they already know the full calendar by heart. Day 11's own closing note named the fix directly — dbt_utils.date_spine — and left it unbuilt. Today closes it.

2 · date_spine: a calendar table generated from two dates, not a query

A date_spine macro takes a date part, a start expression and an end expression, and compiles to a recursive CTE that emits exactly one row per date in that range — nothing queried from any table, purely generated. It's the calendar-table pattern any warehouse eventually needs, written once by dbt Labs instead of by every project that needs one. Call it directly in a new model, models/marts/dim_dates.sql:

-- models/marts/dim_dates.sql
{{ dbt_utils.date_spine(
    datepart="day",
    start_date="cast('2024-01-01' as date)",
    end_date="cast(current_date as date)"
) }}

Build it alone first and read what comes out, before changing anything else:

uv run --project ../dbt_env dbt build --select dim_dates

The compiled SQL is a plain recursive CTE walking from start_date to end_date one day at a time, ending in a single date_day column — worth reading once, same as Day 11's reminder that a package macro is still just Jinja producing SQL, no different from hand-written SQL once compiled.

3 · Build: left join the spine onto every city, so absence becomes a visible zero

dim_dates alone only has dates — the real gap is (city, order_date) pairs, so today crosses the spine against the distinct cities this project already has in stg_restaurants, then left-joins the real order aggregation onto that full grid. Edit mart_delivery_sla.sql's structure: keep Day 6's order_durations CTE exactly as it is, and change only the final select to start from the full city/date grid instead of from the aggregated orders directly:

-- models/marts/mart_delivery_sla.sql -- new CTEs added above the existing final select
with order_durations as (
    -- ...unchanged from Day 6/Day 10: placed/delivered join through stg_order_events
),

cities as (
    select distinct city from {{ ref('stg_restaurants') }}
),

city_date_grid as (
    select cities.city, dim_dates.date_day as order_date
    from cities
    cross join {{ ref('dim_dates') }} as dim_dates
),

daily_city_stats as (
    select
        city,
        date_trunc('day', placed_at)::date as order_date,
        count(*) as order_count,
        sum(case when {{ is_sla_breach('minutes_to_deliver') }} then 1 else 0 end)::numeric as breach_count
    from order_durations
    group by city, date_trunc('day', placed_at)::date
)

select
    {{ dbt_utils.generate_surrogate_key(['city_date_grid.city', 'city_date_grid.order_date']) }} as sla_key,
    city_date_grid.city,
    city_date_grid.order_date,
    coalesce(daily_city_stats.order_count, 0) as order_count,
    coalesce(daily_city_stats.breach_count, 0) as breach_count,
    case when coalesce(daily_city_stats.order_count, 0) = 0
        then 0
        else daily_city_stats.breach_count / daily_city_stats.order_count
    end as share_over_sla
from city_date_grid
left join daily_city_stats
    on city_date_grid.city = daily_city_stats.city
    and city_date_grid.order_date = daily_city_stats.order_date

The join direction is the whole fix: starting from city_date_grid and left join-ing the real aggregation onto it means every grid row survives even when daily_city_stats has nothing for it, and the two coalesce() calls turn that missing row into an honest 0 instead of a null that would silently poison share_over_sla's division. Day 11's sla_key surrogate key moves with the grain — it's still exactly one column standing in for (city, order_date), now built from the grid's columns instead of the aggregation's, because the grid is what guarantees the pair exists at all.

4 · Why this is a real data-quality gap, not cosmetics

A dashboard built on top of yesterday's version of mart_delivery_sla has a silent failure mode: "average share of orders over SLA across all cities this week" computed by averaging share_over_sla across whatever rows exist quietly drops every zero-order city-day from the average instead of counting it as a true zero, which skews the number upward by exactly the amount of missing-data days. That's the same shape of bug as a dbt test that doesn't fire because the bad case never produces a row to test in the first place — Day 3's tests check rows that exist; nothing before today could ever check a (city, order_date) pair that was silently never created. date_spine doesn't add a new rule, it removes a blind spot: once the full grid exists, Day 3's existing not_null/unique tests on sla_key now actually test the grain they were always supposed to test, every city-day, not only the ones that happened to log traffic.

This generated-calendar idea has one bridge worth naming explicitly, not re-deriving: a Python-side calendar generator (pandas.date_range, say) would produce the identical set of dates. The reason today's fix lives in dbt rather than a Python script is the same reason Day 1 chose ELT over ETL — the grid is consumed by SQL joins immediately after, inside the same warehouse, by the same tool that already owns mart_delivery_sla's other transformations. (Bridged, not re-taught — pandas itself belongs to data/.)

Q: "Your delivery-SLA mart is grouped by city and day. How do you make sure a city with zero orders on some day still shows up as zero, instead of just not appearing?" A strong answer, out loud: "By building the full grid of every city crossed with every date in the reporting window first, as its own small model, using dbt_utils' date_spine macro to generate the date half of that — it's a recursive CTE that emits one row per day in a range, nothing queried from a table. Then I left-join my real orders-per-city-per-day aggregation onto that grid instead of starting from the aggregation itself, and coalesce the order count and breach count to zero wherever the join finds nothing. The join direction is what matters: starting from the grid guarantees every city-day survives even with zero real orders behind it, where starting from the aggregation — what I had before — can only ever produce rows for combinations that already happened to have at least one order. I caught this because an average computed downstream was silently skewed upward: every missing zero-order day was dropped from the average instead of counted as a real zero." The signal: naming the join direction as the actual fix, not just "I added a calendar table," and tying it to a concrete downstream consequence (a skewed average) rather than treating it as a cosmetic nicety.
