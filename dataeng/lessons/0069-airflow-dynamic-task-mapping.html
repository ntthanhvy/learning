2 · dynamic task mapping: one task definition, many task instances, decided at run time

Airflow's own fix for exactly this is .expand(): call a @task-decorated function's .expand() method with a keyword argument bound to a list, and Airflow creates one mapped task instance per element of that list — not at the moment the DAG file is parsed, but at the moment the DAG actually runs and the list's real length becomes known. Today's shape, built from pieces this course already has (Day 20's plain @task, Day 1's four-city domain):

from airflow.sdk import dag, task

CITIES = ["Hanoi", "Ho Chi Minh City", "Da Nang", "Hue"]

@dag(schedule="@daily", start_date=..., catchup=False)
def city_sla_check():
    @task
    def list_cities() -> list[str]:
        return CITIES

    @task
    def check_city_sla(city: str) -> dict:
        ...

    check_city_sla.expand(city=list_cities())

city_sla_check()

Confirmed this round with a real DagBag parse of exactly this shape (no live scheduler or metadata database needed — the same read-the-parsed-DAG-object technique Days 20/45/51 each used for their own structural claims, since bag.get_dag() itself queries the metadata database and fails without one, while bag.dags[...], read directly off the parsed DagBag object, does not):

check_city_sla -> is_mapped: True
list_cities -> is_mapped: False
check_city_sla upstream: ['list_cities']

check_city_sla comes back as a distinct kind of object entirely — DecoratedMappedOperator, not the plain operator class every non-mapped task in this course has used — and check_city_sla.expand(city=list_cities()) both declares the one upstream dependency (exactly Day 20's "the function call is the dependency" rule, with no >> anywhere) and tells Airflow the elements it maps over will come from that upstream task's own return value, not from a list written into the DAG file.

The number four — one mapped instance per city — is not a fact this round's parse can show. list_cities() hasn't run; nothing has. The parsed DAG only knows that check_city_sla is mapped and that its elements will come from list_cities's eventual output — the actual instance count, and each instance's own map_index (0 for Hanoi, 1 for Ho Chi Minh City, and so on), only exist once a real DAG run executes list_cities and Airflow's scheduler expands check_city_sla against its real return value. That is a live-run fact, named here rather than asserted.

3 · Why this is still "just" XCom underneath, same as Day 20

Nothing about .expand() invents a new data-passing mechanism. list_cities() returns a plain list; Airflow pushes that list to XCom exactly the way Day 20's count_raw_orders() pushed a plain integer — one row, keyed return_value, in Airflow's own metadata database. The only new behavior is what happens on the downstream side: instead of one task instance pulling that whole list as a single value, Airflow's scheduler reads the list's length and creates that many mapped instances of check_city_sla, each one pulling a single element at its own map_index. Day 20's own XCom-sizing warning still applies unchanged: list_cities returning four city names is a tiny, appropriate XCom value; it returning every row of raw.orders to map over would be exactly the dataset-through-XCom mistake Day 20 named, just dressed up as a list.

Q: "You need to run the same check against every row of a lookup table, and the number of rows can change. How would you structure that in Airflow?" A strong answer, out loud: "I'd use dynamic task mapping — one task definition, decorated with @task, calling .expand() with a keyword bound to another task's return value. Airflow creates one mapped task instance per element of that list at run time, each with its own map_index, instead of me hand-writing one task per row or looping at parse time. It's still built on the same XCom mechanism TaskFlow always uses — the list itself is a small XCom value, and the only genuinely new behavior is that the scheduler reads that list's length and expands the downstream task to match, so adding a new row to the source table changes the fan-out with zero code change." The signal: naming that .expand() defers the instance count to run time without inventing a new way to move data, and that each mapped instance fails or succeeds independently of its siblings.

Scope line

This lesson covers .expand() over a single keyword argument bound to an upstream task's return value, and the structural facts a DagBag parse can confirm without a live scheduler: is_mapped, the inferred upstream dependency, and the operator class change. It does not cover .expand_kwargs() (mapping over multiple paired arguments at once, vocabulary only), map_index_template (naming mapped instances something more readable than a bare integer), partial binding with .partial() (fixing some arguments while mapping others), or max_active_tis_per_dag-style concurrency limits on how many mapped instances run at once — real depth, left for if this course's own DAGs ever need a map large enough for concurrency to matter. The actual run-time fan-out (four real task instances, one per city, each with its own log and state) rests on Airflow's documented dynamic-mapping behavior, not a live airflow dags test run this round, since the airflow db migrate approval gate named every round since Day 35 was unavailable here too.
