Event-driven architecture: naming the paradigm behind the mechanisms

Lesson 29 built the outbox pattern, Lesson 30 verified a webhook's signature, and Lesson 63 chose between polling and a push channel — three lessons that all move an "X happened" notice from one system to another, without ever naming the paradigm they're all instances of. Today isn't a new mechanism. It's the vocabulary that was missing underneath three mechanisms you already have: event-driven architecture, message queue, and pub/sub.

1 · Two shapes a system can be built in

Every lesson so far has quietly assumed one shape: a client sends a request, a handler runs, a response comes back, done. Call that request-driven: the caller knows exactly who it's talking to. The other shape is event-driven architecture: a producer announces "this happened" into the system and moves on, with no idea who's listening or whether anyone is. Zero, one, or ten consumers might react. The producer's job ends at the announcement — that's the whole trade: request-driven couples the caller to a specific callee and gets a direct answer back; event-driven decouples them and gets no answer back, only a fact broadcast into the system for whoever cares to pick up.

2 · The word for what Lesson 29 built without naming it

An event is the unit that gets announced: "order 4471 was placed," not "please charge this card." Lesson 29's outbox table held events. The relay process that Lesson 29 taught was, without the name, a tiny publisher — it published rows into a message queue, and every downstream service that read from that queue was a subscriber. That publisher/subscriber relationship, generalized beyond any one outbox, is pub/sub. Lesson 30's webhook was one specific, narrow delivery mechanism for the same idea: a single subscriber, hard-coded as a URL, getting a direct HTTP push per event — pub/sub with the "many possible subscribers" part stripped down to exactly one.

3 · The thing events sit inside while nobody has read them yet

An event a publisher announces has to live somewhere between being published and being read — email works the same way, a message sits in your inbox between being sent and being opened. That holding structure is a message queue, and the piece of infrastructure that runs it — durably storing events, tracking which subscriber has read which, handling retries — is called a broker (Kafka, RabbitMQ, SQS, and Postgres itself — acting as a queue — are all brokers with different trade-offs; which one to run and operate is out of scope here, same as Lesson 8 named "the database is shared state" without teaching how to run one). The queue is what makes the decoupling in Section 1 actually durable: if every subscriber is offline, the events aren't lost, they're waiting.

4 · Same three mechanisms, now placed on the paradigm they belong to

The point of this table isn't that one mechanism beats another — it's that "outbox," "webhook," and "polling/SSE/WebSockets" were never competing solutions to the same problem. Outbox and webhook are both event-driven; polling/SSE/WS is request-driven (or its push variant) aimed at one specific, already-known client. Naming the paradigm is what lets you tell, in a design conversation, whether two options are actually alternatives or solving different problems wearing similar names.

Frontend-habit bridge: you already have pub/sub on the client — a DOM addEventListener("click", ...) is a subscriber registering interest in an event type without knowing or caring which code, if any, dispatched it, and the browser is the broker in between. Backend event-driven architecture is the identical relationship, just with a message queue standing in for the DOM's event loop, and "order placed" standing in for "click."

5 · Where MISSION.md draws the line here

This course's scope excludes distributed systems "beyond vocabulary level" — running a Kafka cluster, choosing partition counts, or reasoning about exactly-once delivery guarantees stays out. This lesson stops at exactly the line the outbox and webhook lessons already stood on: what to call the shape you're building, not how to operate the infrastructure underneath it. If a future PR review comment says "should this be event-driven instead of a direct call," today's vocabulary is what lets you evaluate the question instead of just nodding.

Q: "What's the difference between a webhook and a message queue?" A strong answer, out loud: "Both are event-driven — a publisher announces something happened without waiting for a reply. The difference is delivery. A webhook is a direct HTTP push to one hard-coded URL, so if that receiver is down the publisher has to retry the push itself. A message queue durably holds the event and lets any number of subscribers read it whenever they're ready, so a subscriber being offline doesn't lose anything — it just reads the backlog once it's back. I built the outbox pattern, which uses the database itself as a lightweight queue, and a webhook, which is really pub/sub narrowed down to a single fixed subscriber." The signal: naming pub/sub and message queue as the general vocabulary, then placing the two mechanisms you've actually built as specific points inside it, rather than treating them as unrelated tools.
