qcut(): binning by rank, not by value

Lesson 17's closing teaser named this directly — "qcut(), quantile-based binning, Lesson 12's cut() sibling, splitting by rank instead of fixed edges." Same "turn a number into a category" job Lesson 12 opened, one different, very interview-relevant assumption about what "even" means.

1 · Same question, different definition of "fair"

Lesson 12's pd.cut() splits a numeric column at fixed VALUE edges you choose (bins=[0, 40, 100, 200]) — every row lands wherever its value falls between those edges, no matter how many rows that turns out to be per bucket. pd.qcut() flips that: you choose how many bins, and pandas picks the value edges FOR you so that each bin ends up with (as close as possible to) an equal COUNT of rows. cut() answers "which fixed range is this value in?" — qcut() answers "which quarter (or third, or tenth) of the sorted data is this value in?"

Run both on the same clean 4-row amount slice Lessons 6-17 have used (An/120.0, Binh/35.5, Binh/180.0, An/42.0), reusing Lesson 12's exact bins for cut():

# cut() — Lesson 12's fixed edges: 0-40 Low, 40-100 Mid, 100-200 High
pd.cut(clean["amount"], bins=[0, 40, 100, 200], labels=["Low", "Mid", "High"]).value_counts()
# High    2    (120.0 and 180.0 both land here)
# Low     1    (35.5)
# Mid     1    (42.0)

# qcut() — 4 quantile bins, one per row on this small slice
pd.qcut(clean["amount"], q=4, labels=["Q1", "Q2", "Q3", "Q4"]).value_counts()
# Q1    1    (35.5)
# Q2    1    (42.0)
# Q3    1    (120.0)
# Q4    1    (180.0)

cut()'s fixed edges put both An's 120.0 and Binh's 180.0 into the same "High" bucket — a real, unequal 2/1/1 split, exactly what fixed edges produce whenever the underlying data isn't evenly spread across the range. qcut() instead sorts all four values and cuts at the boundaries that give each bucket exactly one row: Q1=35.5, Q2=42.0, Q3=120.0, Q4=180.0 — a guaranteed-even 1/1/1/1 split, because it never asks "where does 100 fall" — it asks "who's in the top quarter by rank."

Why this matters, concretely: if amount were heavily skewed — a handful of huge outlier orders and a long tail of small ones — cut()'s fixed-width bins would dump almost every row into one bucket and leave the others nearly empty. qcut() is immune to that by construction: it always finds edges that balance the COUNT, wherever the values actually sit. That's also its cost — the edges it picks are data-dependent and can look ugly/arbitrary (81.0, not a round number), whereas cut()'s edges are whatever meaningful business ranges you asked for (a real pricing tier, a real age bracket).

2 · q=: how many groups, not where they start

q= is the one argument that matters most: an integer number of equal-count bins (q=4 is quartiles, q=10 is deciles), or your own list of quantile cutpoints (q=[0, .5, 1] is an explicit median split). Try q=2 on the same slice — the plain median split:

pd.qcut(clean["amount"], q=2, labels=["Low", "High"])
-- An/120.0   -> High
-- Binh/35.5  -> Low
-- Binh/180.0 -> High
-- An/42.0    -> Low

The two smallest values (35.5, 42.0) become "Low," the two largest (120.0, 180.0) become "High" — a clean 2/2 split, because q=2 means "cut at the median," and the median of these four sorted values sits at 81.0. Under the hood qcut() is built on the same rank(pct=True) idea Lesson 7 introduced for plain ranking: it ranks every value as a percentile (0 to 1), then slices that 0-1 range into q equal-width percentile bands — equal-width in RANK space, not in value space, which is exactly the trade-off flip from cut().

3 · The SQL bridge: NTILE(n)

qcut()'s SQL cousin is a specific, well-known window function: NTILE(n) OVER (ORDER BY col) divides the ordered rows into n groups of as-equal-as-possible size, numbering each row 1 through n by which group it landed in — the exact same "equal COUNT, not equal value-range" contract as qcut(q=n).

-- SQL: quartile number per row, ordered by amount
SELECT customer, amount,
       NTILE(4) OVER (ORDER BY amount) AS quartile
FROM orders;

-- pandas equivalent
clean["quartile"] = pd.qcut(clean["amount"], q=4, labels=False) + 1

labels=False returns the bin number itself (0-indexed integers) instead of a category label, matching NTILE's plain integer output once you add 1 for 1-indexing. This is the pairing worth saying out loud in an interview: cut() ~ a CASE WHEN chain of fixed ranges, qcut() ~ NTILE(n) OVER (ORDER BY ...) — both already-familiar SQL shapes, just spelled differently.

Q: "What's the difference between cut() and qcut(), and when would you reach for each?" A strong answer, out loud: "cut() bins by fixed value edges you choose — good when the ranges themselves are meaningful, like real pricing tiers or age brackets, but the bucket sizes can end up wildly unequal if the data's skewed. qcut() bins by rank instead — you say how many buckets, and it finds edges that give each one roughly the same count of rows, like SQL's NTILE(n) OVER (ORDER BY col). I'd reach for qcut() when I specifically need balanced groups — quartile analysis, splitting a dataset into equal-sized cohorts for a report — and cut() when the boundaries themselves carry business meaning that shouldn't shift as the data changes." The signal: naming NTILE unprompted — it's the fastest proof this maps cleanly onto SQL knowledge already there.
