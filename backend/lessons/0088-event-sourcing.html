Event sourcing: when the log stops being a side effect and becomes the data

Lesson 87 read the WAL instead of polling a table to get a stream of changes out of Postgres — but the table was still the real thing; the stream was a side channel built on top of it. Today asks the more radical version of the same question: what if the log of changes wasn't a side channel at all, but the only thing actually stored — with every table you've ever queried in this course demoted to a cache you could delete and rebuild?

1 · The assumption every prior lesson made without saying so

Every lesson so far has assumed a table stores the current truth: an orders row has a status column, and when status changes, UPDATE overwrites it. The old value is gone — Lesson 46's audit log was the fix for exactly that loss, writing a second, append-only record of "what happened" alongside the mutable row, because the row itself couldn't be trusted to remember its own history. event sourcing takes the audit log's insight and makes it the whole design: don't keep a mutable row with a separate history table bolted on. Keep only the log. There is no UPDATE, ever — an order's status isn't a column that changes, it's a fact you derive by reading every event that ever happened to that order, in order, and folding them together: OrderPlaced → OrderPaid → OrderShipped tells you the current status is "shipped" without that word ever being stored as a status anywhere.

Lesson 46 vs. today: audit logging kept the row and added a history trail next to it — two things, one derived from watching the other. Event sourcing deletes the row's privileged status entirely. The log isn't evidence of what the row did. The log is the only thing that exists; the row, if one exists at all, is a disposable cache of it.

2 · Reading state means replaying, and nobody wants to replay from the beginning every time

Folding thousands of events every time you need to answer "what's this order's status?" is obviously too slow past a handful of events, so practical event-sourced systems keep a projection — an ordinary table that looks exactly like the orders table every earlier lesson assumed, rebuilt from the event log and refreshed as new events arrive. The projection is allowed to be wrong, stale, or missing entirely, because it holds zero information the log didn't already have; delete it and replaying every event from scratch regenerates the identical table. That's the actual trade event sourcing makes: the log is the single source of truth and is never lost or overwritten, at the cost of needing a projection (and the machinery to keep it current) just to get back the fast, simple table reads every other lesson in this course took for granted.

This is CDC's shape, inverted: Lesson 87's CDC starts from a table (the real thing) and derives a change stream (the side effect) by reading the WAL. Event sourcing starts from the event stream (the real thing) and derives a table — the projection — as the side effect. Same two artifacts, opposite direction of "which one is allowed to be rebuilt from the other."

3 · What you get, and what it costs

Ordinary table (Lessons 1–87)Event-sourced log
What's actually storedcurrent state, overwritten in place on every UPDATEevery event that ever happened, never overwritten or deleted
"What was the status yesterday?"impossible without a separate history table (Lesson 46)replay events up to yesterday's timestamp — built in, free
"Why did this change?"not stored at all unless logged separatelythe event itself usually carries the reason as a field
Fast "give me the current row" readone row lookup, immediateneeds a projection kept in sync — extra moving part
Changing your mind about what a "status" even meansa migration rewriting existing rowsrebuild the projection with new folding logic; the log itself never changes

That last row is the real payoff, not a minor one: because the log is immutable and holds raw facts rather than a pre-decided interpretation, you can change how you derive state from it — add a new projection, fix a bug in the folding logic, answer a question nobody thought to ask when the events were recorded — without ever touching old data, the same way Lesson 87's CDC consumer can start fresh from a replication slot without the source table knowing or caring. The cost is real too: every read either goes through a projection you now have to build and keep current, or replays a potentially long event history, and a bug in the folding logic doesn't corrupt the log (it's immutable) but does corrupt every projection built from that point forward until it's fixed and rebuilt.

Q: "What's the difference between event sourcing and just keeping an audit log next to your tables?" A strong answer, out loud: "An audit log, like the one in Lesson 46, is secondary — the real row still gets UPDATEd in place, and the audit trail is a best-effort record of what happened to it, usually written by a trigger or application code that could in principle be skipped. Event sourcing flips which one is authoritative: the event log is the only thing actually stored, and current state — the row you'd normally query — is a projection folded from that log, which can be deleted and rebuilt at any time because it holds no information the log didn't already have. The audit log describes a row's history; in event sourcing, there often isn't a privileged row at all, only the history, with a disposable table built on top of it for fast reads." The signal: naming which artifact is authoritative and which is derived, not just "event sourcing logs everything."

Scope line

MISSION.md excludes distributed systems "beyond vocabulary level," and event sourcing in real systems usually arrives bundled with CQRS (separate read/write models), event versioning across schema changes, and snapshotting strategies for logs too long to replay cheaply — all genuine operational depth this lesson stops short of. Today's goal is narrower and matches every prior pattern lesson in this course: know what the term means, recognize the trade when you see it in a design doc or a PR, and place it correctly next to CDC and audit logging rather than treating all three as the same idea with different names.
