CORS: why the browser blocks your own fetch()

You've hit a CORS error in DevTools more times than any other error in this course's scope — and probably "fixed" it by copy-pasting a header without knowing what it actually grants. Today: what the browser is protecting, who CORS is really for, and why it isn't the security feature most frontend devs assume it is.

1 · The rule that was already there: same-origin policy

Before CORS exists at all, browsers enforce something older and stricter: the same-origin policy. An origin is the scheme + host + port together, so https://app.example.com and https://api.example.com are different origins (different host), and https://app.example.com and http://app.example.com are different origins too (different scheme). By default, JavaScript running on one origin cannot read the response body of a request it makes to a different origin — the request can still go out and the browser will happily attach cookies to it, but the page's own JavaScript is blocked from reading what came back.

The distinction that trips people up: same-origin policy is enforced entirely by the browser, purely on the read side. Lesson 22's CSRF lesson already showed the other half of this: the browser attaches cookies and fires the request regardless of origin — that part was never blocked. Same-origin policy is what stops the attacker's own JavaScript from reading the response to that forged request. The two lessons are about opposite ends of the same request.

2 · CORS: the server's permission slip to relax that rule

CORS exists because same-origin policy, left alone, would break every legitimate case of one origin's frontend calling another origin's API — exactly your day job, where app.example.com calls api.example.com. CORS is the mechanism for the server to say, in the response itself, "this specific other origin is allowed to read this." The browser sends the request either way; CORS headers only control whether the calling page's JavaScript is allowed to see what came back.

GET /orders HTTP/1.1
Host: api.example.com
Origin: https://app.example.com

HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://app.example.com
Content-Type: application/json

[{"id":482,"status":"packed"}]

The browser sends Origin automatically on every cross-origin request — the page's JavaScript never sets it and cannot override it. The server reads that header, decides whether to trust it, and answers with Access-Control-Allow-Origin. If that header is missing, or names a different origin than the one that asked, the browser discards the response before the calling JavaScript ever sees it — the fetch() promise rejects, and DevTools prints the CORS error you've seen.

3 · The interview trap: CORS protects the client, not the server

This is the single most common misconception, and it's worth stating as bluntly as the mechanism deserves: CORS is not a server-side access control. It adds no protection against a non-browser caller at all — curl, a backend service, Postman, or an attacker's own script talking directly to your API never sends a real browser's enforcement layer along with it; they can read any response regardless of what Access-Control-Allow-Origin says, because CORS is enforced by browsers, not by your server. Your server was always the one deciding whether to answer a request in the first place — that's authentication (Lesson 4) and authorization (Lesson 12), the mechanisms that actually decide who is allowed to act. CORS headers only ever answer a narrower, additional question: which browser-hosted frontends are allowed to read this response. Getting CORS permissive (or even wide open with *) doesn't hand out any capability an authenticated, authorized request didn't already have — it only changes which websites' own JavaScript is allowed to see the result.

Frontend habit this retrains: "just add Access-Control-Allow-Origin: * to make the error go away" treats CORS as a bug to silence. Treat it instead as a real question your server is answering out loud: which other frontends should be allowed to read this data through a user's browser. Silencing the error without answering the question just picks the widest possible answer by default.

4 · Simple requests vs. preflight

Not every cross-origin request works the same way. A simple request — a plain GET, or a POST with only a plain content type like text/plain or form-encoded data, and no custom headers — goes out immediately, and the browser checks the CORS headers on the real response. But a request using PATCH/DELETE, a custom header like Authorization, or Content-Type: application/json (the normal shape of an API call from this course) triggers a preflight request first — the browser sends an OPTIONS request asking permission before sending the real one:

OPTIONS /orders/482 HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: PATCH
Access-Control-Request-Headers: content-type, authorization

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PATCH, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization

The point of the preflight is to ask before any side effect runs — the browser wants to know the server will accept this method/header/origin combination before it risks firing a real PATCH that changes data. Only if the preflight comes back with matching allowances does the browser send the actual request. This is why an endpoint using JSON bodies and an Authorization header — nearly everything built in this course from Lesson 3 onward — costs an extra round trip per unique method/origin combination the browser hasn't recently cached, not per request.

5 · Credentials: the one place * stops working

A cross-origin request only auto-attaches cookies if the calling JavaScript explicitly opts in (fetch(url, { credentials: "include" })), and if it does, the server must respond with Access-Control-Allow-Credentials: true plus a literal, specific origin in Access-Control-Allow-Origin — the wildcard * is rejected outright by the spec the moment credentials are involved. This isn't an arbitrary restriction: * paired with "also send my cookies" would mean any website on the internet could make the victim's browser send an authenticated, cookie-bearing request and read the answer — reintroducing exactly the credential-leaking risk same-origin policy exists to prevent. Ties directly back to Lesson 4's session cookies and Lesson 22's CSRF material: CORS's credentialed mode is the read-side counterpart to what SameSite defends on the write side.

6 · A minimal Go implementation

The CORS contract is entirely response headers plus one intercepted method — no new state, no database, just deciding what to set before the real handler runs (or, for OPTIONS, instead of it):

// allowedOrigins is the explicit allowlist of origins permitted to read
// responses from this API via a browser -- never "*" when credentials
// (cookies) are involved, since the two are mutually exclusive by spec.
var allowedOrigins = map[string]bool{
    "https://app.example.com": true,
}

// corsMiddleware inspects the Origin header the browser sends automatically
// on every cross-origin request, and if it's on the allowlist, echoes it
// back in Access-Control-Allow-Origin plus the other CORS response headers.
// A preflight OPTIONS request is answered here directly, never reaching the
// real handler.
func corsMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        origin := r.Header.Get("Origin")
        if allowedOrigins[origin] {
            w.Header().Set("Access-Control-Allow-Origin", origin)
            w.Header().Set("Access-Control-Allow-Credentials", "true")
            w.Header().Set("Vary", "Origin")
        }

        if r.Method == http.MethodOptions {
            w.Header().Set("Access-Control-Allow-Methods", "GET, POST, PATCH, DELETE")
            w.Header().Set("Access-Control-Allow-Headers", "Content-Type, Authorization")
            w.WriteHeader(http.StatusNoContent) // 204, preflight carries no body
            return
        }

        next.ServeHTTP(w, r)
    })
}

Two details worth naming: the origin is echoed back from the allowlist rather than hardcoded, because Access-Control-Allow-Origin can only ever hold one origin (or *) — supporting several real origins means checking the incoming Origin against a list and reflecting the match, exactly like this. And Vary: Origin matters the moment any caching layer (a CDN, a reverse proxy) sits in front of this handler — without it, a cache could serve one origin's allowed response to a different origin that should have been rejected.

Q: "Is CORS a security feature? What does it actually protect against?" A strong answer, out loud: "CORS doesn't protect the server — a non-browser client can ignore it entirely and read any response your server sends, since it's enforced by the browser, not the API. What it protects is the user: it stops a malicious website's JavaScript from using the victim's browser to read data from another site the victim happens to be logged into. The request still goes out either way — that's the same thing CSRF exploits — CORS is specifically about whether the calling page is allowed to read the answer. So authentication and authorization are still what decide whether a request is allowed to act at all; CORS only decides which other frontends are allowed to see the result through a browser." The signal: not confusing CORS with an access-control mechanism, and correctly separating "the request fired" from "the response was readable."
