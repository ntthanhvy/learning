mimetypes: guessing a file's type from its name

Day 116's urllib.parse pulled a path like /report.csv out of a URL as plain text — no step there said what kind of file that is. A web server answering an HTTP request, an email attaching a file, or an upload handler accepting a file all need to answer that question before they can do anything useful with the bytes: what Content-Type header goes with this filename? mimetypes is the standard-library module that answers it from the filename alone, no file contents required.

1 · guess_type(): a filename in, a MIME type out

A MIME type is the short, standardized string — "text/csv", "image/jpeg" — that labels what kind of content something is. mimetypes.guess_type() reads a filename's extension and looks it up against a built-in table, with no need to open the file or inspect its actual bytes:

import mimetypes

print(mimetypes.guess_type("report.csv"))     # confirmed live: ('text/csv', None)
print(mimetypes.guess_type("photo.JPG"))      # confirmed live: ('image/jpeg', None)
print(mimetypes.guess_type("noextension"))   # confirmed live: (None, None)

mimetypes.guess_type() always returns a 2-item tuple, not just a type string — confirmed live, "photo.JPG" matched despite the uppercase extension, and an extension-less name returned (None, None) rather than raising. Nothing here opens the file; a .csv extension on an empty or even corrupted file still guesses "text/csv", because the guess is purely about the name.

2 · The second tuple item: encoding, for compressed files

The tuple's second item answers a different question — is this file itself compressed, on top of its content type? Most files answer None, but a doubled extension like .tar.gz answers both parts at once:

print(mimetypes.guess_type("archive.tar.gz"))
# confirmed live: ('application/x-tar', 'gzip')
print(mimetypes.guess_type("notes.txt"))
# confirmed live: ('text/plain', None)

For "archive.tar.gz", the content underneath is a tar archive ("application/x-tar") and it has been gzip-compressed on top — two separate, true facts about the same file, which is exactly why guess_type() returns them as two separate values instead of inventing a single combined MIME type for every compression format.

3 · guess_extension(): the reverse direction

guess_extension() goes the other way — given a MIME type, what's a reasonable file extension for it? Useful when a script receives a type string (an HTTP response's Content-Type header, say) and needs to choose a filename to save under:

print(mimetypes.guess_extension("text/csv"))     # confirmed live: .csv
print(mimetypes.guess_extension("image/jpeg"))   # confirmed live: .jpg

mimetypes.guess_extension() picks one reasonable extension, not necessarily the only valid one — "image/jpeg" could just as legitimately be saved as .jpeg, but .jpg is what the built-in table returns by default. Treat it as a good default, not a guaranteed canonical answer.

Extending the table — add_type(): the built-in table doesn't know every extension a project might invent. mimetypes.add_type(mime_type, extension) registers a new mapping for the rest of the running program — confirmed live, before registering ".myapp", guess_type("thing.myapp") returned (None, None); after mimetypes.add_type("application/x-myapp", ".myapp"), the same call returned ('application/x-myapp', None). This only affects the current process's in-memory table, not any file on disk.

4 · It only ever looks at the name

This is the one trap worth naming directly: guess_type() is a name-based guess, not a content inspection. A file named "invoice.pdf" that is actually a renamed .txt file still guesses "application/pdf" — correctly reporting what the name claims, not what the bytes actually are. A full URL string works too, because guess_type() only looks at the trailing extension and ignores everything in front of it:

print(mimetypes.guess_type("https://example.com/path/report.CSV?x=1"))
# confirmed live: ('text/csv', None)

For anything security-sensitive — deciding whether to trust an upload, for instance — the filename's claimed type is not proof of the actual content; that needs inspecting the real bytes (a signature/"magic number" check), which is outside this module's job entirely.

Where pandas/NumPy go from here: neither has any notion of a MIME type — pd.read_csv() is told explicitly to read CSV by the function you call, not by asking mimetypes what a file's extension claims it is. Deciding *which* reader function to call based on an unknown file's extension is exactly the kind of small dispatch logic mimetypes is for, one level before any pandas call happens.
