pd.merge(how="cross"): every row paired with every row

Lesson 5 mapped how= onto the SQL joins already known — inner, left, right, outer. There's a fifth one SQL also has, and pandas added a dedicated spelling for it in 1.2: CROSS JOIN. It needs no shared key at all, because it isn't matching rows — it's pairing every row on one side with every row on the other. Zero lessons and zero glossary rows have covered it on its own merits so far; today closes that.

1 · No key, no matching — just every combination

Every how= Lesson 5 covered answers "which rows share a key value?" how="cross" asks a different question entirely: "what does every possible combination of a row from each side look like?" No on= needed, because there's no key to match — every left row is paired with every right row, full stop:

sizes = pd.DataFrame({"size": ["S", "M", "L"]})
colors = pd.DataFrame({"color": ["red", "blue"]})

pd.merge(sizes, colors, how="cross")
--   size color
-- 0    S   red
-- 1    S  blue
-- 2    M   red
-- 3    M  blue
-- 4    L   red
-- 5    L  blue

Confirmed directly (pandas 3.0.6): 3 rows × 2 rows produced exactly 6 rows — every size shown against every color, in the same order itertools.product() would generate it. The SQL equivalent is the literal CROSS JOIN keyword — SELECT * FROM sizes CROSS JOIN colors — or, just as commonly, the implicit version written as SELECT * FROM sizes, colors with no WHERE clause at all. The real-world use: generating every valid combination before filtering or scoring it (every product variant × every warehouse, every date in a range × every store ID) — the classic "I need a scaffold of all combinations, then I'll join real data onto it" interview task.

2 · on=, left_on=, right_on= are flatly incompatible with it

Because a cross join has no key, pandas doesn't silently ignore a key argument if one is passed — it raises. Confirmed directly:

pd.merge(sizes, colors, how="cross", on="size")
-- MergeError: Can not pass on, right_on, left_on or set
--             right_index=True or left_index=True

That's a fast, loud failure rather than a silent wrong answer — a reassuring contrast to several of this course's past traps (Lesson 57's row-multiplying merges, Lesson 89's loose equality checks). The one thing worth remembering going in: a cross join is the one how= value that is never spelled with on= at all — if a key genuinely matters, it isn't a cross join, it's an inner/left/right/outer merge with that key named.

3 · The real trap: row count multiplies, it doesn't add

Every other how= caps the output somewhere near the bigger input's row count (outer joins add unmatched rows; inner joins can only shrink). A cross join does neither — output rows = left rows × right rows, confirmed directly with two 1,000-row frames:

left  = pd.DataFrame({"a": range(1000)})
right = pd.DataFrame({"b": range(1000)})
len(pd.merge(left, right, how="cross"))
-- 1000000

1,000 rows joined to 1,000 rows produced one million — not 2,000, not 1,000. This is the sharpest version of Lesson 57's "row-multiplication" warning, except there's no validate= guard that applies here (that argument itself raises the same MergeError as on=, since it also implies a key). The only real defense is arithmetic done before running it: know both row counts, multiply them, and sanity-check that the product is actually the scaffold size wanted — not an accidental cross join from a dropped or mistyped on= elsewhere in a pipeline, which silently degrades into exactly this blowup with no key column to match against at all. Column-name collisions resolve exactly like any other merge, too — confirmed directly, two frames both named "x" cross-joined into columns named "x_x" and "x_y", the same default suffixes=("_x", "_y") from Lesson 5.

Q: "How would you generate a row for every combination of product size and color, before any real inventory data exists yet?" A strong answer, out loud: "pd.merge with how='cross' — it's the cartesian product of both frames' rows, no shared key needed, so it's the right tool specifically when I want every combination rather than every match. I'd build a sizes DataFrame and a colors DataFrame and cross-join them to get the full scaffold, then left-merge real inventory counts onto that scaffold afterward so missing combinations show up as NaN instead of silently not existing. The one thing I'd watch is the row count — it multiplies, not adds, so crossing two reasonably-sized frames can blow up fast, and pandas won't let me pass on= with it at all, which is actually a safety rail: if I think I need a key, that's a sign I don't actually want a cross join." The signal: naming the multiplicative row-count risk unprompted, and knowing a cross join is often step one of a two-step pipeline (scaffold, then fill), not the final answer by itself.
