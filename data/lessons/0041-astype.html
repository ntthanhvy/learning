astype(): converting a column's dtype on purpose

Lesson 40's teaser named no single dangling candidate, so this round is a fresh scan against the curriculum spine and glossary. astype() itself turned up: it has been used quietly inside code examples since Lesson 7 (.astype(int) on a rank) and Lesson 25 (.astype("category")), but never taught as its own tool — what it actually does, when it raises instead of coercing, and how it differs from Lesson 3's errors="coerce" functions. Today closes that gap directly.

1 · The problem: df.dtypes only shows you the type — it doesn't change it

Lesson 2 taught reading df.dtypes as the first-look ritual's second line. On the raw, uncleaned fixture:

raw = pd.read_csv("practice/data/orders_raw.csv")
raw.dtypes
-- order_id      int64
-- customer        str
-- amount          str   <- has a non-numeric "unknown" value, Lesson 2's own example
-- order_date      str
-- dtype: object

amount reads as text because of the one "unknown" row (Lesson 2's classic "one bad cell taints the whole column" finding). df.dtypes only reports that fact — it doesn't fix anything. astype() is the general-purpose tool that actually performs a conversion:

raw["order_id"].astype("int32").dtype
-- dtype('int32')   <- narrower int type, same values
raw["order_id"].astype(str).tolist()
-- ['1', '2', '3', '4', '5', '6']   <- numbers, now as text

2 · astype() raises on bad data — it does not coerce

This is the one fact that separates astype() from Lesson 3's cleaning tools. Try it directly on the messy amount column:

raw["amount"].astype(float)
-- ValueError: could not convert string to float: 'unknown'

No silent fallback, no partial result — the whole call fails the instant it hits one value it can't represent in the target dtype. That's the opposite of Lesson 2/3's pd.to_numeric(raw["amount"], errors="coerce"), which turns "unknown" into NaN and keeps every other value. Rule of thumb: reach for to_numeric()/to_datetime() with errors="coerce" when a column is genuinely messy and some values are expected to fail; reach for astype() when the column is already clean and a failure would mean something is actually wrong — the crash is a feature, not a bug, in that case.

Gotcha: astype(int) on a column containing NaN always raises, even if every other value is a perfectly good whole number — a plain int64 column has no way to represent a missing value at all: 
pd.Series([1.0, 2.0, None]).astype(int)
-- IntCastingNaNError: Cannot convert non-finite values (NA or inf) to integer
The fix is astype("Int64") (capital I) instead of astype(int) (lowercase built-in) — pandas' own nullable integer dtype, which reserves a real <NA> marker instead of demanding every value be finite: 
pd.Series([1.0, 2.0, None]).astype("Int64")
-- 0       1
-- 1       2
-- 2    <NA>
-- dtype: Int64

3 · Converting several columns at once, and revisiting category

A dict maps column name to target dtype, converting more than one column in a single call — the same shape as Lesson 4's named-aggregation dict, just for types instead of aggregations:

raw.astype({"order_id": "int32", "customer": "category"}).dtypes
-- order_id      int32
-- customer   category
-- amount          str
-- order_date      str
-- dtype: object

Lesson 25's astype("category") is a special case of exactly this: a memory-shrinking dtype conversion for a low-cardinality text column, not a numeric one. It follows the same raise-on-failure rule too — a column converted onto a fixed, explicit CategoricalDtype that's missing one of the real values in the data does something different again: it doesn't raise, it silently turns that value into NaN (Lesson 25 covered this gotcha directly; worth remembering it's the one common exception to today's "astype raises" rule).

4 · The SQL bridge: CAST, minus the silent truncation

Every SQL dialect has some spelling of CAST(col AS type) or col::type — astype() is that, applied to a whole pandas column at once:

-- SELECT CAST(order_id AS SMALLINT) FROM orders;
raw["order_id"].astype("int32")

-- SELECT amount::TEXT FROM orders;
raw["amount"].astype(str)

The behavior split lines up cleanly too: Postgres' plain CAST raises on a genuinely unconvertible value, same as astype(); TRY_CAST (or ::type wrapped in error handling in some engines) returns NULL instead of raising, same as pd.to_numeric(..., errors="coerce"). Same two-tool split, same two SQL/pandas pairs.

Q: "A column comes in from a CSV as text but should be numeric. Walk me through cleaning it." A strong answer, out loud: "First I'd check df.dtypes and look at a sample — if it's read as text/object, something in that column doesn't look numeric to pandas' inference. If I expect the column to be fully clean, astype(float) is the direct tool — it converts in one call and raises immediately if any value can't be represented, which is actually useful: the crash tells me my assumption about the data was wrong. If I expect some genuinely messy values, pd.to_numeric(col, errors='coerce') is the safer choice — same conversion, but unconvertible values become NaN instead of blowing up the whole pipeline, and then I'd check isna().sum() afterward to see how many rows that affected. One gotcha I'd flag either way: astype(int) specifically fails on any NaN in the column, even if the rest is clean integers, because plain int64 can't represent a missing value — the fix there is astype('Int64'), pandas' nullable integer type, if the NaNs are expected to stay." The signal: naming both tools and the deliberate choice between them (raise vs. coerce), not just reaching for whichever one comes to mind first.
