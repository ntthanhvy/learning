shelve: a dict that survives the process ending

Day 93's sqlite3 is a real database — a schema, SQL, typed columns. Most scripts never need that much ceremony; they just want a plain dict that is still there the next time the program runs. The standard-library shelve module is exactly that: a persistent dict, keyed by strings, holding almost any Python object as the value, backed by Day 72's pickle underneath.

1 · Opening one, and why it looks exactly like a dict

shelve.open(path) opens (or creates) a persistent store at that path and returns a Shelf — something that behaves like a dict for almost everything: [] lookup, in, .keys(), len(), del. Day 6's with block applies the same way it does to a file, closing the shelf (and flushing anything unwritten) when the block ends:

import shelve

with shelve.open("contacts") as db:
    db["ada"] = {"age": 30, "city": "Hanoi"}
    db["grace"] = {"age": 40, "city": "Hue"}

# a brand-new process, or just a later line, re-opening the same path:
with shelve.open("contacts") as db:
    print("ada" in db)        # True -- confirmed live, still there
    print(db["ada"])          # {'age': 30, 'city': 'Hanoi'} -- confirmed live
    print(sorted(db.keys()))  # ['ada', 'grace'] -- confirmed live

Nothing here is a new data structure to learn — it is Day 3's dict vocabulary, pointed at a file instead of memory. A missing key still raises a plain KeyError, confirmed live, exactly Day 3's lookup rule, unchanged.

2 · Keys must be strings; values go through pickle

shelve keys must be str — unlike a regular dict, which accepts any hashable key. Values have no such limit: almost anything pickle (Day 72) can serialize can be a shelf's value, including a dataclass instance, with no hand-conversion:

from dataclasses import dataclass

@dataclass
class Order:
    city: str
    amount: float

with shelve.open("orders") as db:
    db["o1"] = Order("Hanoi", 120.0)

with shelve.open("orders") as db:
    print(db["o1"])   # Order(city='Hanoi', amount=120.0) -- confirmed live, round-tripped intact

This is Day 72's gap, closed with lookup: pickle.dumps()/loads() round-trips one object at a time with no addressing scheme of its own; shelve is that same serialization wrapped in a key/value store, so a program can save and fetch many objects by name instead of managing separate files or one big list.

3 · The trap: mutating a value in place does nothing, unless writeback=True

Because a shelf writes a value back to disk only when it is assigned, mutating a mutable value already stored there — appending to a list that's a value, say — silently does not persist, confirmed live:

with shelve.open("recs") as db:
    db["rec"] = {"tags": ["a", "b"]}

with shelve.open("recs") as db:
    db["rec"]["tags"].append("c")   # mutates an in-memory copy only -- no assignment happened

with shelve.open("recs") as db:
    print(db["rec"])   # {'tags': ['a', 'b']} -- confirmed live, the append never saved

db["rec"] unpickles a fresh copy every time it's read; .append() changes that throwaway copy, not anything on disk. shelve.open(path, writeback=True) fixes this by caching every accessed entry in memory and writing all of them back on close — confirmed live, the identical code above persists the appended tag correctly once opened with writeback=True. The cost: every entry ever touched stays cached in memory until the shelf closes, which can use real memory on a shelf with many large values — the right trade only when in-place mutation is actually needed, not the default to reach for blindly.

Bridge from Day 93's sqlite3: both are "a database in a file with no server," but shelve has no schema, no SQL, and no query language — only key lookup, same as a dict. Reach for shelve for a script's own cache or saved state keyed by a simple name; reach for sqlite3 the moment the data needs filtering, joining, or any shape of query beyond "fetch by exact key."
