Day 53 named two composition keys as vocabulary and left them there — union and intersection — and its own TODO built exactly one exclude: block, nested a single level under definition:. Day 59 named the same gap again on its way out: "the union/intersection/multi-block exclude composition keys... remain the one standing, concrete dbt-selection gap." Both rounds were right to defer it — a single method/value pair, or one exclude: list, covers most real selectors, and piling on three new keys in one sitting would have buried either lesson. But the deferred question is real: Day 53's own nightly_marts_without_sla TODO excluded one node from one tag. What about excluding two, or selecting the union of two unrelated tags, or the intersection of a tag and a config? Those need union: and intersection: for real, not as a vocabulary word.

2 · Confirmed live: a real parse failure, then the actual rule

The natural first guess — put union: and exclude: as two sibling keys directly under one definition:, the same way Day 53's single exclude: sat next to nothing else — fails at dbt parse with a real runtime error, confirmed this round:

Runtime Error
  Could not read selector file data: Runtime Error
    Only a single 'union' or 'intersection' key is allowed in a root level selector definition; found union,exclude.

That error names the actual rule directly: a definition: block gets exactly one root composition key. exclude is not a second root key sitting beside union or intersection — it has to nest inside the list that key already defines, as its own list item, confirmed against the live docs page and then re-confirmed by a clean parse once reshaped that way:

definition:
  union:
    - method: tag
      value: nightly
    - exclude:
        - method: fqn
          value: mart_delivery_sla
        - method: fqn
          value: dim_couriers

Read as English, not YAML indentation: "everything tagged nightly, plus (then minus) whatever this nested exclude list removes." The docs state the rule for exactly where that removal applies: exclude always returns a set difference and is always applied last within its scope — here, last within the union list it sits inside, after every other item in that same list has already been combined.

Every row below is a real dbt list --selector <name> result against the six-model scratch project (staging tagged hourly, marts tagged nightly and materialized table, the same shape Day 52 onward has used), not predicted from the docs' prose:

Selector (definition: shape)Reading itConfirmed result
union: of tag:hourly and tag:nightlyevery node carrying either tag — a logical ORall seven models: three staging, four marts
intersection: of tag:nightly and config.materialized:tableonly nodes matching both — a logical ANDthe four marts (every nightly node here already is a table)
union: of tag:nightly plus a nested exclude: of two fqn blocksnightly marts, minus two named nodes, exclude applied lastdim_restaurants, fct_orders — the other two nightly marts dropped
A real finding, confirmed live, not assumed: the intersection row above doesn't narrow anything in this project, because every nightly-tagged model here already happens to be a table — the two sets are identical by coincidence of this project's own config, not because intersection: failed to narrow. intersection: is doing real AND logic; it just has nothing to cut in a six-model project where materialization and tag line up one-to-one. The operator earns its keep the moment that stops being true — say, a future nightly model left at the default view materialization on purpose.

3 · Confirmed live: default: true changes what a bare command does

Every selector so far, across Days 53, 59 and today, has needed --selector <name> typed explicitly. default: true on exactly one selector in the file changes that: a command with no --select, --exclude or --selector flag at all stops meaning "every node in the project" and instead resolves to whatever that one selector defines. Confirmed live this round — with a default: true selector pointed at path:models/staging added to the file, a completely bare dbt list --resource-type model (no flags) logged Using default selector default_selection and printed only the three staging models, not all seven:

Using default selector default_selection
stg_couriers
stg_orders
stg_restaurants
Worth knowing before reaching for this on a real project: the docs are explicit that only one selector may set default: true per invocation — a second one would be a config error, not a silent override — and they show a Jinja-conditional escape hatch (default: "{{ target.name == 'dev' | as_bool }}") for a project that wants a different default per target. Neither matters for this course's one-target project today, but both are worth knowing before reaching for this on a multi-target project: a careless default: true quietly changes what every bare dbt build in CI does, for everyone, the moment it's merged.

Q: "selectors.yml supports union, intersection and exclude. Walk me through combining them, and name one trap." A strong answer, out loud: "A definition: block takes exactly one root composition key -- union for OR, intersection for AND -- confirmed the hard way this round: putting union and exclude as two sibling keys under one definition failed to parse with a real error, 'only a single union or intersection key is allowed in a root level selector definition.' exclude isn't a third peer key; it nests inside the union or intersection list as its own item, and it's always applied last within whatever scope it sits in, after every other item in that same list has already been combined. The trap worth knowing is default: true -- setting it on one selector changes what a completely bare dbt build, with no flags at all, does for everyone the moment it's merged, and only one selector is allowed to claim it per invocation. I'd reach for union/intersection once a real selector needs an actual OR or AND, not by default, and I'd be deliberate about ever shipping a default: true on a shared project rather than treating it as a harmless convenience." The signal: naming the real parse error as something hit, not read about, and treating default: true as an operational risk rather than pure convenience.

Scope line

This lesson covers union, intersection, exclude nested inside either of them, and default: true (including the one-default-per-invocation rule and the Jinja-conditional escape hatch), confirmed live against a scratch project. It does not cover exclude as a per-method argument (method: tag, value: nightly, exclude: ["@tag:daily"] inline on the same block, a second documented shape distinct from today's nested-list-item form) or arbitrarily deep nesting of union inside intersection inside another union — both read as vocabulary in the primary source below, not built today.
