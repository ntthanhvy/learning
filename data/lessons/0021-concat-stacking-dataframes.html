pd.concat(): stacking DataFrames, merge()'s sibling for "just append rows"

Lesson 20's closing teaser named this directly — pd.concat(), merge()'s sibling from Lesson 5 for the "just append rows" case. Every join so far has matched rows by a shared key value. Today's tool doesn't match anything at all — it just stacks.

1 · concat() doesn't match anything — merge() does

Lesson 5's merge() answers "which row in table A corresponds to which row in table B?" by comparing key VALUES — customer_id in one table against customer_id in the other. pd.concat() asks a completely different question: "put these DataFrames together, one after another." No key, no matching, no lookup — just stacking. The two tools solve opposite halves of "combine two tables": merge() when rows need to be matched by what they mean; concat() when they just need to sit next to each other.

2 · axis=0 (the default): stacking rows

The most common case: two exports with the same columns that just need to become one table. Say a January batch and a February batch of orders, pulled separately:

batch_a = pd.DataFrame({"customer": ["An", "Binh"], "amount": [120.0, 35.5]})
batch_b = pd.DataFrame({"customer": ["Chi", "Danh"], "amount": [99.9, 200.0]})

pd.concat([batch_a, batch_b])
#   customer  amount
#0       An   120.0
#1     Binh    35.5
#0      Chi    99.9   <- index restarted at 0, collided with batch_a's row 0
#1     Danh   200.0

Notice the index: 0, 1, 0, 1 — each DataFrame kept its own original row labels, so two unrelated rows now share the label 0. That's rarely what you want once the batches are meant to become one logical table, and it's the first thing to fix:

pd.concat([batch_a, batch_b], ignore_index=True)
#   customer  amount
#0       An   120.0
#1     Binh    35.5
#2      Chi    99.9
#3     Danh   200.0

ignore_index=True throws away both original indexes and renumbers the result 0..N-1 — the right default whenever the old row labels carried no meaning worth keeping.

3 · keys=: keeping track of which batch a row came from

Sometimes the old labels — or at least which source they came from — is worth keeping, for debugging or for reporting "how many rows came from each batch." keys= builds exactly that, as a MultiIndex (Lesson 14's structure, reused here for a new purpose):

combined = pd.concat([batch_a, batch_b], keys=["jan", "feb"])
#         customer  amount
#jan 0          An   120.0
#    1        Binh    35.5
#feb 0         Chi    99.9
#    1        Danh   200.0

combined.loc["feb"]
#   customer  amount
#0       Chi    99.9
#1     Danh   200.0

The outer index level is the batch name, the inner level is each batch's own original row position — and .loc["feb"] slices straight back to just that batch, unchanged. This is the version to reach for when "which source did this row come from" is itself a question worth answering later, not just a one-time stack-and-forget.

4 · Mismatched columns: concat fills, it doesn't reject

Real batches don't always have identical columns. Say a later export adds a region column the earlier ones never had:

batch_c = pd.DataFrame({"customer": ["Danh"], "amount": [200.0], "region": ["West"]})

pd.concat([batch_a, batch_c], ignore_index=True)
#   customer  amount region
#0       An   120.0    NaN   <- batch_a never had a region column
#1     Binh    35.5    NaN
#2     Danh   200.0   West

concat() doesn't error and doesn't drop the extra column — it takes the union of every column seen across all inputs and fills whatever a given row's source DataFrame didn't have with NaN. That's Lesson 3's missing-data problem showing up in a new place: a successful concat can silently manufacture NaNs anywhere the input shapes didn't quite match, worth checking for with .isna().sum() right after, the same reflex Lesson 3 taught for any freshly loaded table.

5 · axis=1: stacking columns, aligned by index — not by key

Less common, but worth recognizing: axis=1 puts DataFrames side by side instead of one after another, lining rows up by INDEX LABEL rather than by any key column:

amount = pd.Series([120.0, 35.5, 180.0, 42.0], name="amount")
ranks = amount.rank(ascending=False).astype(int).rename("rank")  # Lesson 7

pd.concat([amount, ranks], axis=1)
#   amount  rank
#0   120.0     2
#1    35.5     4
#2   180.0     1
#3    42.0     3

This works because both Series already share the same index (0..3) — concat(axis=1) just glues columns together by matching those labels, the same alignment mechanism that made Lesson 20's .loc[idxmax()] work. It is not a substitute for merge(): if the two inputs' indexes don't already line up, this produces misaligned garbage or NaN-filled rows instead of an error — merge() is still the right tool anytime rows need to be matched by a key's VALUE rather than by already sharing the same index.

Rule of thumb: rows that mean the same thing across sources (another batch of the same kind of data) → concat(axis=0). Columns describing the SAME rows, already aligned by index → concat(axis=1). Rows that need to be matched by a key's value before they can be combined → merge(), not concat, regardless of axis.

6 · The SQL bridge

concat(axis=0) is UNION ALL — stack every row from both queries, keep duplicates, no matching required, exactly concat's behavior. Plain SQL UNION (which also de-duplicates) needs an explicit .drop_duplicates() call afterward in pandas, since concat() alone never removes anything. concat(axis=1) has no clean SQL equivalent, for the same reason Lesson 20 found none for grouped idxmax(): a SQL table has no inherent row order or position for a second table to align against the way a pandas index does — a SQL join always needs an explicit key to match on.

Q: "You have twelve monthly CSV exports with identical columns that need to become one DataFrame. What do you reach for?" A strong answer, out loud: "pd.concat() with a list of the twelve DataFrames, axis=0 since it's the default — this is a pure row-stacking problem, not a matching problem, so merge() would be the wrong tool entirely. I'd pass ignore_index=True unless keeping track of which month each row came from actually matters, in which case I'd use keys= instead to get a MultiIndex I can still slice by month later. And right after, I'd check columns and run isna().sum(), because if even one month's file has a differently-named or missing column, concat won't error — it'll silently NaN-fill instead." The signal: naming concat vs merge as a first branch — stacking rows needs no key, matching rows always does — before reaching for either.
