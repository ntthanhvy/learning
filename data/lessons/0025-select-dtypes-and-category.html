select_dtypes() and the category dtype: pulling columns by type, and shrinking repeated text

Lesson 24 closed by naming this exact candidate: select_dtypes()/category dtype, adjacent to Lesson 2's df.dtypes but never revisited as its own topic. Re-grepped every lesson body and the glossary before writing — still genuinely absent.

1 · Recap: df.dtypes tells you, select_dtypes() acts on it

Lesson 2 introduced df.dtypes as the first-look ritual's second line — one dtype per column, printed for you to read. That's fine for eyeballing six columns; it doesn't scale to "give me every numeric column" on a wide table without hand-typing every name. select_dtypes() is df.dtypes turned into a filter:

merged.dtypes
# order_id        int64
# customer          str
# amount        float64
# order_date        str
# region            str

merged.select_dtypes(include="number").columns.tolist()
# ['order_id', 'amount']

Read it like a SQL information_schema query: "give me every column whose declared type is numeric," without ever typing order_id or amount by name. That's the real interview use — a wrangling function that needs to scale a numeric transform (fill NaN, normalize, sum) across however many numeric columns a table happens to have, unknown until runtime.

2 · include= and exclude()

include= takes a dtype name (or a list of them) and keeps only matching columns; exclude= is its mirror — keep everything except matching columns:

merged.select_dtypes(exclude="number").columns.tolist()
# ['customer', 'order_date', 'region']  -- everything NOT numeric

merged.select_dtypes(include=["number", "datetime"]).columns.tolist()
# both numeric AND datetime columns, one call

"number" is a NumPy dtype-group alias — it matches int64 and float64 together without listing both. Both keywords return a brand-new DataFrame with only the matching columns (same "returns a copy" rule as everything else in pandas that isn't an in-place mutation) — chain .columns to get just the names, or keep the whole slice if that's what the next step needs.

3 · The category dtype: a lookup table hiding inside one column

SQL has two ways to store a repeated string: a free-text VARCHAR column, or an ENUM/foreign key into a small lookup table with an integer key underneath. pandas' text columns default to the first shape — Lesson 2's str dtype stores every value as its own separate string, even when only 2 or 3 distinct values actually repeat across thousands of rows (a region column with only "North"/"South", say). category dtype is pandas' second shape: it stores the small set of distinct values once, plus one small integer code per row pointing back into that set — the ENUM/lookup-table model, inside a single column.

merged["region"] = merged["region"].astype("category")
merged["region"].dtype
# category
merged["region"].cat.categories.tolist()
# ['North', 'South']  -- the lookup table, built automatically from the values seen

4 · Why it exists: memory, hand-verified

The pitch isn't theoretical — memory_usage(deep=True) proves it on this course's real 4-row fixture (merged with customers.csv, same as Lesson 5):

merged.memory_usage(deep=True)["region"]              # 216 bytes, as str
merged_cat.memory_usage(deep=True)["region"]          # 112 bytes, as category

Roughly half, on just 4 rows with 2 distinct values. The saving isn't fixed — it scales with row count relative to distinct-value count: the lookup table (categories) is paid for once no matter how many rows repeat it, while a plain str column pays the string-storage cost every single row. Repeat this same 4-row shape 250x to 1,000 rows and the gap opens far wider — region as str costs 54,000 bytes; as category, 1,108 bytes, since the lookup table barely grows while a thousand repeated "North"/"South" strings would have. Low-cardinality columns repeated over many rows (region, status, category, country code) are exactly where this pays off; a column that's almost all distinct values (an email address, a free-text comment) gains little or nothing, since there's no repetition for the lookup table to exploit.

The speed side follows from the same shape: groupby, value_counts, and comparisons on a category column work on small integer codes instead of comparing full strings row by row — the same reason an indexed foreign-key join beats comparing raw text in SQL.

5 · The gotcha: an out-of-category value doesn't just get added

A category column's categories are fixed once set — pandas won't silently grow the lookup table just because a new value shows up. The exact failure shape depends on how you write the new value in, and it's worth knowing both, hand-verified on pandas 3.0.5:

## Path A — direct scalar assignment into an existing category column: raises, doesn't silently corrupt
merged["region"].loc[0] = "Mars"
# TypeError: Cannot setitem on a Categorical with a new category (Mars), set the categories first

## Path B — converting a column to an EXPLICIT fixed set of categories that doesn't include a real value:
## this is the "no crash, quietly wrong" one
fixed = pd.CategoricalDtype(categories=["North", "South"])
pd.Series(["North", "Mars", "South"]).astype(fixed)
# 0    North
# 1      NaN     <-- "Mars" silently became missing, no error, no warning printed
# 2    South
# dtype: category

Same family as this course's other "no crash, quietly wrong" gotchas (Lessons 19-24): converting a column to a category dtype with an explicitly fixed category list is a real pattern — for example, forcing test data onto the same categories as training data — and any value outside that fixed list becomes NaN silently rather than raising. Always check .isna().sum() immediately after a fixed-category astype() conversion, the same reflex Lesson 2 taught for pd.to_numeric(..., errors="coerce").

SQL bridge: dtype overall ~ a column's declared type in a schema. category dtype ~ an ENUM, or a normalized foreign-keyed lookup table for a repeated value — same "store the small set once, reference it by a small code" idea, just living inside one pandas column instead of a separate joined table.

Q: "You've loaded a wide table and need to shrink its memory footprint. What do you check first?" A strong answer, out loud: "df.dtypes or select_dtypes() first, to see what's actually there — select_dtypes(include='number') or exclude='number' lets me grab a whole group of columns by type instead of hardcoding names, useful for any transform that needs to run across all the numeric columns regardless of how many there are. For the text columns, I'd check cardinality with nunique() relative to row count — a low-cardinality column like region or status repeated over many rows is a strong astype('category') candidate: pandas stores the distinct values once as a lookup table plus a small integer code per row, so memory_usage(deep=True) drops noticeably, and operations like groupby get faster since they're comparing small codes instead of full strings. The gotcha I'd flag: converting to an explicitly fixed category list and then feeding it a value outside that list silently produces NaN instead of raising — I'd always check isna().sum() right after that kind of conversion." The signal: naming the memory AND speed reasons, not just one, and flagging the silent-NaN trap unprompted.
