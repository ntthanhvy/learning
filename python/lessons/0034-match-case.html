match/case: structural pattern matching

An if/elif chain that checks one variable against several possibilities, then reaches inside it once it matches, is common enough that Python 3.10 added syntax for it directly. structural pattern matching — match/case — checks shape and content together in one place, instead of an if for the check and separate lines to unpack what was found.

Bridge from SQL: a CASE WHEN status = 'pending' THEN ... WHEN status = 'shipped' THEN ... block picks one branch out of several based on a value, and each branch's `THEN` only runs for that one condition. match/case is that same one-value-many-branches shape in Python — with the added trick that a branch can also reach inside the value (a tuple, a list, an object) and bind pieces of it to names, something SQL's CASE has no equivalent for.

1 · The problem: check, then unpack, as two separate steps

Handling a coordinate that might be a 1-, 2-, or 3-item tuple with if/elif means checking the length and then indexing into it, twice over:

def describe(point):
    if len(point) == 2:
        x, y = point
        return f"2D point at ({x}, {y})"
    elif len(point) == 3:
        x, y, z = point
        return f"3D point at ({x}, {y}, {z})"
    else:
        return "unknown shape"

The length check and the unpacking say the same thing twice — the second line only runs because the first line already promised a 2-tuple, but nothing ties them together as one statement.

2 · match/case: check shape and bind pieces at once

A sequence pattern checks length and unpacks in a single case line — no separate len() check, no separate unpacking assignment:

def describe(point):
    match point:
        case (x, y):
            return f"2D point at ({x}, {y})"
        case (x, y, z):
            return f"3D point at ({x}, {y}, {z})"
        case _:
            return "unknown shape"

match point: evaluates point once (the subject), then tries each case pattern top to bottom, running the first one that fits. case (x, y): only matches a 2-item sequence — and, if it matches, x and y are already bound to the two items, ready to use in that branch. The final case _: is the wildcard pattern — it matches anything and binds nothing, playing the role else plays in if/elif.

3 · Guards, OR-patterns, and matching class instances

A case pattern can add an if guard clause, combine alternatives with |, or match an object's type and pull out its attributes by name, using Day 33's Status enum and Day 7's dataclass together:

from dataclasses import dataclass
from enum import Enum

class Status(Enum):
    PENDING = "pending"
    SHIPPED = "shipped"
    CANCELLED = "cancelled"

@dataclass
class Order:
    status: Status
    total: float

def handle(order):
    match order:
        case Order(status=Status.PENDING, total=t) if t > 1000:
            return "needs manual approval"
        case Order(status=Status.PENDING | Status.SHIPPED):
            return "still active"
        case Order(status=Status.CANCELLED):
            return "no action needed"
        case _:
            return "unrecognized"

Order(status=Status.PENDING, total=t) — a class pattern — matches only an Order instance, only when its status attribute equals Status.PENDING, and binds its total attribute to t; the trailing if t > 1000 guard then further narrows that branch, so a small pending order falls through to check the next case instead. Status.PENDING | Status.SHIPPED is an OR-pattern — matches either member, one branch instead of two near-identical ones. Order matters: Python tries each case top to bottom and stops at the first match, exactly like if/elif.

4 · A capture pattern binds unconditionally — position it last

A bare name in a case, with no literal, no parentheses, always matches and binds the whole subject to that name — writing one before an intended case is a mistake Python actually catches, rather than a silent trap:

match command:
    case cmd:              # binds ANYTHING to cmd — always matches
        return f"got {cmd}"
    case "quit":          # SyntaxError: unreachable, caught before the code even runs
        return "bye"

A capture pattern (a bare name, with no guard) is irrefutable — it always succeeds — so it must be written last, the same role case _: plays. Unlike most Python mistakes, this one doesn't wait for a bug report: CPython's compiler statically proves the "quit" case below can never run and refuses to even start the program, raising SyntaxError: name capture 'cmd' makes remaining patterns unreachable at import time. Adding a guard changes the story — case cmd if cmd == "special": is no longer irrefutable, since the guard can fail, so it's allowed before other cases and Python falls through to try the next one exactly when the guard doesn't hold.

Q: "When would you reach for match/case over if/elif?" A strong answer, out loud: "When a branch depends on both the shape of a value and its contents — a tuple's length while also unpacking it, or an object's type while also reading its attributes. match checks and destructures in one pattern instead of a length or isinstance check followed by separate unpacking. For a flat comparison against one variable with no destructuring, if/elif is just as clear and there's no reason to reach for the newer syntax." The signal: naming the combined check-and-destructure benefit specifically, not just "it's the modern way to do it."

Where pandas goes from here: nothing directly — pandas has no equivalent to structural pattern matching; row-wise branching there is usually vectorized with np.select or .apply() instead of a per-row match. Not demonstrated here; that's data/'s territory, and this is the only sentence in this lesson that names it.
