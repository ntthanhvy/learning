Synthesis: the same "is this current?" check, three layers

Lesson 57's closing teaser named the sole remaining candidate: "the standing synthesis lesson through Lessons 9/33/51," open for several rounds now. Those three lessons taught three mechanisms that look unrelated — an HTTP header, a database column, a cache TTL — but they answer the exact same question at three different points in a request's path: is the copy of this data I'm holding still current? Today ties them together on one feature, so the pattern shows instead of just getting asserted.

1 · One feature, one bug, three places it can hide

The feature: an internal order-editing screen. A support agent opens order #482, sees status: "packed", and a moment later marks it "shipped". Nothing exotic — the same order Lesson 51 already used. The bug that can happen at each layer is always the same shape: someone writes based on a copy of the row that is no longer the newest one, and a newer change gets silently overwritten. Lesson 33 named this precisely — the lost update — and it turns out that same failure can occur three times over, once per layer, unless each layer separately guards against it.

2 · Layer 1 — the database row itself (Lesson 33)

Two support agents both open order #482 within the same second: agent A sees status = "packed", version = 4; agent B sees the identical row. Agent A submits "shipped" first — Postgres accepts it, the row becomes version = 5. A moment later agent B submits "cancelled", still holding version = 4 in memory. Without a check, that plain UPDATE would win too, silently erasing agent A's "shipped" write. Lesson 33's version-column pattern is exactly the guard: agent B's UPDATE requires version = 4 in its WHERE clause, which no longer matches — zero rows update, and the application surfaces the conflict instead of losing it.

UPDATE orders SET status = $1, version = version + 1
WHERE id = $2 AND version = $3;
-- agent B's $3 is 4, but the row is already at version 5 --
-- 0 rows updated, B's stale write is rejected, not silently applied.

This is the innermost layer: it protects the row no matter which client, which API, or which internal script tries to write it. Every write to this table, from any source, passes through this same guard.

3 · Layer 2 — the HTTP request/response (Lesson 51)

One layer out, the same race can happen before either write even reaches the database. Agent B's browser fetched order #482 a minute ago and cached the response body client-side; agent B edits the status in that stale view and submits a PATCH — no version conflict occurs at the database yet, because this is the very first write attempt this browser tab has made. Lesson 51's fix guards this specific handoff: the earlier GET response carried an ETag, and the PATCH must send it back as If-Match. The server compares that ETag to the order's current one before the request ever reaches the UPDATE statement above.

PATCH /orders/482 HTTP/1.1
If-Match: "etag-v4"
Content-Type: application/json

{"status":"cancelled"}

-- server's current ETag for #482 is now "etag-v5" (agent A's write) --
-- comparison fails before any SQL runs:
HTTP/1.1 412 Precondition Failed

Notice what this layer catches that Layer 1 alone would miss until the very last moment: a wasted round trip. Without If-Match, agent B's whole request — network hop, handler, serialization — would travel all the way to the database only to be rejected there. If-Match rejects it at the door, before any of that work runs, using the same underlying fact (the row moved past version 4) expressed as an HTTP precondition instead of a SQL WHERE clause.

4 · Layer 3 — the read path, before either write happens (Lesson 9)

Now go back one more step, to something neither Layer 1 nor Layer 2 touches at all: what agent B saw when they opened the order in the first place. If the order-detail endpoint sits behind an application cache (Lesson 9's cache-aside pattern) with, say, a five-minute TTL, agent A's "shipped" write can commit to Postgres and still leave the cached response — ETag and all — pointing at the old version = 4 state for up to five more minutes, unless the write path explicitly invalidates the cache entry for order:482. Until that invalidation happens, agent B's browser is handed a perfectly valid-looking ETag for data that Postgres itself has already moved past — a stale read handed out with full confidence.

The point of this section: Layer 3's bug isn't really a new bug — it's Layer 2's guard being fed a wrong input. If the cache in front of the GET handler isn't invalidated the instant Postgres's version changes, the ETag it serves is stale before the client ever makes a request — Layer 2 will still correctly compare the ETag it's given, it's just been given the wrong one to compare against.

5 · The same idea, seen three times

Line the three mechanisms up side by side and the pattern that was implicit in Lessons 9, 33, and 51 becomes explicit: every one of them is a cheap, comparable stand-in for "the full current state of this data," checked before trusting or acting on a copy.

Reading that table top to bottom instead of left to right shows the actual dependency chain: Layer 3 decides what Layer 2 gets to compare against, and Layer 2 decides whether Layer 1 ever gets asked to do anything. A gap at any single layer doesn't break the others — Layer 1's version check still protects Postgres even if the cache is stale — but it does mean the bug surfaces later and closer to the database than it needed to, instead of being caught at the cheapest possible point.

Frontend-habit trap: this three-layer shape already exists on the frontend, just under different names — a React Query cache entry going stale (Layer 3's problem), a fetch that should have sent If-Match but didn't (Layer 2's problem), and a form's "last write wins" bug if the backend never checks a version at all (Layer 1's problem). Recognizing "which layer is this staleness bug actually in" is the same diagnostic skill on both sides of the wire — only the vocabulary changes.

Q: "Users are reporting that a colleague's changes sometimes get overwritten on this edit screen. Where do you even start looking?" A strong answer, out loud: "I'd check for a staleness guard at each of the three places this can go wrong. First, does the UPDATE check a version or timestamp column in its WHERE clause — if not, that's the DB-level lost update Lesson 33 covers, and it's the most serious gap since nothing else would catch it either. Second, does the write endpoint require an If-Match header and reject a stale one with 412 — that catches it one layer earlier, before the DB is even touched. Third, is there a cache in front of the read that this same resource goes through, and does the write path invalidate it — because if the read itself hands out a stale ETag, the If-Match check downstream is being fed the wrong answer from the start. All three checks are the same question — is this copy still current — asked at three different points, and a bug report like this usually means one of the three was skipped, not that the whole approach is wrong." The signal: naming that it's one recurring question at three layers, not three unrelated debugging leads.
