value_counts(normalize=True): counts become percentages, and a silent denominator trap

Lesson 10 taught value_counts() as the one-column answer to "how many of each" — raw counts, sorted descending. Grepped every lesson body and the glossary for normalize=True first and found zero dedicated coverage: the only existing normalize= glossary row covers crosstab()/pivot_table()'s version of the same idea, never value_counts()'s own. The interview question is almost never "how many" alone — it's "what percentage" ("what share of orders came from each region?") — and today's trap is a real one: the default silently drops missing values from both the count and the denominator, so a "100%" breakdown can quietly describe fewer rows than the table actually has.

1 · normalize=True: counts become proportions of the whole

SQL answers "what percentage of rows have each value" with a COUNT(*) / SUM(COUNT(*)) OVER () window dance, or a second query for the grand total. value_counts(normalize=True) does it in one call — same split-count as before, each count divided by the total:

orders = pd.DataFrame({"region": ["North", "North", "North", "South", "South"]})
orders["region"].value_counts()
# region
# North    3
# South    2
# Name: count, dtype: int64

orders["region"].value_counts(normalize=True)
# region
# North    0.6
# South    0.4
# Name: proportion, dtype: float64

Confirmed directly (pandas 3.0.6): the result Series is literally named "proportion" instead of "count", and the values sum to exactly 1.0. Multiply by 100 and round for a human-facing percentage — (s.value_counts(normalize=True) * 100).round(1) — the result is still proportions underneath; the * 100 is purely a display choice, nothing pandas tracks as a separate mode.

2 · The trap: dropna=True is the default, and it changes the denominator too

This is the part that bites silently. value_counts() drops missing values by default — not surprising on its own — but with normalize=True, that same default also removes them from the denominator, not just the numerator:

s = pd.Series(["North", "South", "North", "North", "South", None])
# 6 rows total, 1 of them missing

s.value_counts(normalize=True)                  # dropna=True, the default
# region
# North    0.6
# South    0.4
# Name: proportion, dtype: float64   <- sums to 1.0, but only over the 5 non-null rows

s.value_counts(normalize=True, dropna=False)
# North    0.500000
# South    0.333333
# NaN      0.166667
# Name: proportion, dtype: float64   <- sums to 1.0 over all 6 rows, NaN gets its own share

Confirmed directly (pandas 3.0.6): the dropna=True default version reports North as 60% — true only of the 5 rows that have a region at all. If a caller reads that "60%" as "60% of all orders," they are wrong by a margin that grows with however much data is missing, and nothing about the output looks incomplete — the proportions still sum cleanly to 1.0, just over a smaller table than the one being described. The fix is the same habit as every other missing-data lesson in this course: check isna().sum() first, and pass dropna=False explicitly whenever "percentage of all rows" is the actual question being asked.

3 · Per-group percentages: groupby(...)[col].value_counts(normalize=True)

The single most common shape this gets asked in: "within each customer, what percentage of their orders came from each region" — a per-group breakdown, not a table-wide one. Chaining value_counts(normalize=True) straight onto a groupby selection normalizes within each group, not across the whole table:

df = pd.DataFrame({
    "customer": ["An", "An", "An", "Binh", "Binh"],
    "region":   ["North", "North", "South", "North", "South"],
})
df.groupby("customer")["region"].value_counts(normalize=True)
# customer  region
# An        North     0.666667
#           South     0.333333
# Binh      North     0.500000
#           South     0.500000
# Name: proportion, dtype: float64

Confirmed directly (pandas 3.0.6): each customer's own two rows sum to 1.0 independently — An's 0.667+0.333 and Binh's 0.5+0.5 are two separate totals, not one table-wide total of 2.0. This is groupby's split–apply–combine from Lesson 4 applying value_counts() as the per-group function, the same mental shift Lesson 16's transform() and Lesson 61's groupby().apply() both leaned on: the grouping changes what "the whole" means for normalize=True's denominator.

Q: "What percentage of orders came from each region, and does it change per customer?" A strong answer, out loud: "Table-wide, that's orders['region'].value_counts(normalize=True) — one call, proportions sum to 1. First thing I'd check before trusting it is whether region has any nulls, because normalize=True's default dropna=True quietly drops them from both the count and the denominator, so the percentages would describe only the non-null rows, not the whole table — I'd pass dropna=False if I actually want 'percentage of everything.' For the per-customer version, I'd chain groupby('customer')['region'].value_counts(normalize=True) — that normalizes within each customer's own group, so every customer's percentages sum to 1 independently rather than one table-wide total." The signal: naming the dropna=True denominator trap unprompted, and knowing groupby changes what "the whole" means for normalize=True.

4 · Where this fits

This is Lesson 10's value_counts() with one keyword added, but the keyword earns its own lesson because the trap is genuinely silent — no error, no warning, a result that still sums to a clean 1.0 either way. The habit from every prior missing-data lesson applies again: know whether nulls exist in the column before reading a normalize=True percentage as "of everything," and remember that a groupby in front of it resets the denominator to each group, not the whole table.
