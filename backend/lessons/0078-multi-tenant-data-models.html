Multi-tenant data models: one app, many customers, whose rows are whose

Lesson 59 named row-level security's strongest real case in passing: "a table shared by many tenants in one database, where 'which rows belong to this caller' is not a rare edge case but the central question every query has to get right." That lesson taught the enforcement mechanism. It never named the design question underneath it: when a feature request says "customers," what does "one app, many customers" actually look like as tables? This lesson is that design question — the three standard shapes, and which one a given feature request actually needs.

1 · The word this course has used loosely until now

Every schema this course has designed so far quietly assumed one thing: an orders table belongs to one business. A tenant is that business — one customer, organization, or account whose data must never leak into another tenant's view, even though every tenant runs on the same application code. A single-person to-do app has no tenants worth naming; a B2B SaaS product where Acme Corp and Globex Inc. both use the same deployed app, each managing their own users, orders, and settings, has two tenants from the moment the second customer signs up. Nothing about handlers, routing, or HTTP changes — the entire question lives in the schema.

2 · Three shapes, same feature

Take one feature request — "store each customer's orders" — and look at what changes underneath it:

ShapeWhat it looks like
shared schemaone orders table, every tenant's rows mixed together, each row carries a tenant_id column
schema-per-tenantone Postgres schema per tenant (acme.orders, globex.orders), same table definitions repeated per schema, one database
database-per-tenantone entire Postgres database per tenant, each with its own orders table, no cross-tenant query possible even by accident

All three answer the same feature request. They differ in where the isolation guarantee lives, and what that guarantee costs.

3 · Shared schema: the default, and Lesson 59's tenant_id

Shared schema is the shape Lesson 59 assumed without naming it: one orders table, one extra column, one index.

CREATE TABLE orders (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id   bigint NOT NULL REFERENCES tenants(id),
    customer_id bigint NOT NULL,
    total_cents bigint NOT NULL
);
CREATE INDEX ON orders (tenant_id);

Every query needs a WHERE tenant_id = ..., and every foreign key that used to just say "this row belongs to that customer" now silently also means "within the same tenant" — a fact easy to assume and easy to get wrong the first time two tenants' customer_id values collide because both started counting from 1. This is exactly the gap Lesson 59's row-level security policy closes: instead of trusting every handler, background job, and admin script to remember WHERE tenant_id = ..., a policy makes Postgres attach it automatically. Shared schema is the cheapest shape to run — one set of tables, one connection pool, one migration to apply — and the one place a forgotten WHERE clause is also the most catastrophic, since every tenant's rows sit in arm's reach of every query against that table.

4 · Schema-per-tenant and database-per-tenant: isolation moves outward

The other two shapes trade that cheapness for a guarantee that doesn't depend on any query, or any policy, being written correctly at all:

Schema-per-tenant gives each tenant its own Postgres schema (a namespace inside one database — Lesson 2's tables live inside the default public schema without this course ever naming it until now), so acme.orders and globex.orders are genuinely separate tables that happen to share a definition. A query that forgets to filter by tenant doesn't leak another tenant's rows — it simply can't see them, because the connection is scoped to one schema at a time. The cost shows up at migration time: adding a column to orders means running that migration once per tenant schema, not once, and a fleet of a few thousand tenants turns a one-statement migration into a loop.
Database-per-tenant goes one step further: a separate Postgres database per tenant, sometimes on separate physical instances entirely. No query can cross tenants even by a typo, because there is no shared connection through which to do it — and a single noisy tenant's queries can't degrade another tenant's performance by contending for the same table or the same buffer cache. The cost is the same multiplication problem Lesson 18 named for connection pools, now applied to whole databases: a thousand tenants can mean a thousand databases, a thousand sets of migrations to run, and a thousand times the fixed per-database overhead this course has never had to pay before.

5 · Picking a shape: what the feature request is actually asking

The three shapes sit on one line, cheap-and-shared to expensive-and-isolated, and the right one depends on what a specific feature request needs, not on which shape sounds more careful. A small number of large tenants who each expect their data physically separate for compliance reasons (a hospital system, a bank) points toward database-per-tenant, because "we can prove your data never touched shared infrastructure" is the actual requirement being satisfied. A product with thousands of small tenants — most SaaS signups — points toward shared schema with row-level security, because running thousands of databases for a majority of tenants who will never ask where their bytes live is cost with no matching benefit. Schema-per-tenant sits in between: a real, load-bearing choice for a mid-size tenant count that wants stronger isolation than a shared table but can't justify a full database per customer, though the per-tenant migration cost from section 4 tends to make it the least common of the three in practice once a fleet grows past a few hundred tenants.

Q: "We're building a new B2B feature. How should we decide whether to isolate tenant data with a shared table and a tenant_id, or give each tenant its own schema?" A strong answer, out loud: "I'd start from what's actually being promised to the customer, not from which shape feels safer. If a handful of large tenants need to prove their data is physically separate for compliance, that's a database-per-tenant requirement, full stop. If we're expecting hundreds or thousands of small tenants, a shared table with a tenant_id column is the only shape that keeps migrations and connection pooling sane at that scale — and I'd pair it with row-level security so the isolation doesn't depend on every handler remembering a WHERE clause. Schema-per-tenant is the one I'd reach for least often, because it multiplies migration work by tenant count without giving the hard guarantee a separate database gives." The signal: naming the actual constraint (compliance, tenant count, migration cost) driving the choice, not just picking the shape that sounds most secure.
