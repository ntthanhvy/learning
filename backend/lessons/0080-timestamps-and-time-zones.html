Timestamps: storing time without losing it

Lesson 74's CREATE TABLE snippets — and several lessons before it — have quietly used created_at TIMESTAMPTZ NOT NULL DEFAULT now() without ever explaining the type name. That's the whole column type Postgres actually recommends, and skipping the "tz" one character produces a table that silently stores the wrong thing the first time two servers in two time zones write to it. This lesson is the explanation those snippets were owed: what timestamptz actually stores, what it doesn't, and where the "which time zone is this?" question resurfaces even after the column type is right.

1 · Two types that look almost identical

Postgres has two datetime column types one letter apart, and the missing letters matter more than they look:

-- looks fine, is not:
started_at TIMESTAMP       -- no time zone
-- the one almost every table actually wants:
started_at TIMESTAMPTZ     -- "with time zone"

Per the PostgreSQL Manual's own datatype documentation, both are stored as the same 8 bytes with the same microsecond resolution — the difference isn't storage size, it's what Postgres does with a time zone on the way in and out. A timestamp without time zone does exactly what its name says: per the Manual, "PostgreSQL will silently ignore any time zone indication" in the input — not reject it, not convert it, just drop it. Write '2026-09-23 09:00 +07' into a plain timestamp column and Postgres keeps 2026-09-23 09:00 and throws the +07 away with no error and no warning.

2 · What timestamptz actually stores

A timestamptz behaves differently at both ends, and the Manual states both directions explicitly. On the way in: "an input string that includes an explicit time zone will be converted to UTC using the appropriate offset for that time zone. If no time zone is stated in the input string, then it is assumed to be in the time zone indicated by the system's TimeZone configuration parameter." On the way out: "it is always converted from UTC to the current timezone zone, and displayed as local time in that zone." Put together: Postgres never stores a time zone inside a timestamptz value. It stores one absolute instant in UTC — per the Manual, "all timezone-aware dates and times are stored internally in UTC" — and does the conversion arithmetic itself, both when a value comes in and again every time one goes out, based on whatever session setting is asking.

That's the part the type name misleads people into expecting: timestamptz does not remember "this happened at 9am Bangkok time." It remembers the one UTC instant that corresponds to 9am Bangkok time, and forgets Bangkok entirely. Two rows inserted at the same physical moment from a New York server and a Ho Chi Minh City server land on the identical stored value — which is exactly the property a column meant to answer "did A happen before B?" needs.

3 · Why "no time zone" breaks comparisons, not just display

The failure mode isn't cosmetic. Lesson 37's transaction-isolation lessons and Lesson 40's deadlock lesson both leaned on being able to order events correctly — which row was written first decides who wins a conflict. A timestamp (no tz) column can't answer that reliably across more than one time zone, because 2026-09-23 09:00 from a UTC+7 server and 2026-09-23 09:00 from a UTC-5 server compare as equal in the database, despite being twelve hours apart in reality. Every ORDER BY created_at, every WHERE created_at > $1 cursor from Lesson 15's pagination, and every audit-log ordering from Lesson 46 silently assumes every row was written from the same time zone the moment a table uses plain timestamp. That assumption holds by accident in a single-region app and breaks the day a second region, a second server's clock setting, or a client-supplied timestamp enters the picture.

4 · The client boundary: serializing time zone back out

Storing correctly is half the problem; the API boundary is the other half. A timestamptz value serialized to JSON should carry its own offset rather than assume the reader knows the server's zone — the standard shape is ISO 8601, e.g. "2026-09-23T09:00:00+07:00" or its UTC form "2026-09-23T02:00:00Z" — both name the identical instant unambiguously. The alternative some APIs use, a raw Unix epoch integer like 1790226000, is equally unambiguous — a count of seconds since a fixed UTC instant has no time zone to lose — but is unreadable without a converter and easy to accidentally mix seconds with milliseconds. What's never safe is a client-formatted string with no offset attached ("2026-09-23 09:00"): by the time it's serialized, whatever timezone-ness the original timestamptz carried is gone unless the serializer put it back in, so the receiving frontend has no way to tell which zone's 9am that even was.

Frontend-habit bridge: this is the same trap as new Date("2026-09-23 09:00") in JavaScript — no offset in the string means the JS engine guesses (usually the browser's local zone), silently, with no error. A backend that stores timestamptz correctly can still hand a frontend a broken time if the serialization layer strips the offset before it reaches JSON. The fix on both sides is the same instinct: never let a datetime value travel without its offset attached, from the database column all the way to the rendered string.

5 · Where local time still belongs

None of this means "always store UTC and never think about time zones again" — some data is genuinely about a time zone, not just an instant. A recurring meeting at "9am every weekday" or a restaurant's posted opening hours describes a local time that should shift with daylight saving changes in that place, not a frozen UTC instant that would drift relative to the wall clock twice a year. That case needs the zone stored as its own value (an IANA name like Asia/Ho_Chi_Minh, not a fixed offset like +07, since offsets change with daylight saving and countries occasionally change zones outright) alongside a local time or a recurrence rule, with the actual UTC instant computed at read time. The rule of thumb: if the fact is "this specific thing happened," store a timestamptz instant. If the fact is "this recurs at a local wall-clock time," store the zone name and the local time separately, and compute instants on demand.

Q: "Why does this table use TIMESTAMPTZ instead of TIMESTAMP for created_at?" A strong answer, out loud: "Because plain TIMESTAMP throws away whatever time zone the input had — Postgres silently ignores it — so two rows written from servers in different zones can end up with the same stored value even though they happened at different real moments, which breaks anything that orders or compares timestamps, like pagination cursors or audit-log ordering. TIMESTAMPTZ converts every input to one UTC instant and stores that, so comparisons are always correct regardless of which zone wrote the row. The one place I wouldn't reach for TIMESTAMPTZ is something like recurring opening hours, where the fact I actually want is 'runs at 9am local time' — that needs the zone name stored separately, since a frozen UTC instant would drift off 9am local once daylight saving shifts." The signal: naming the silent-data-loss behavior specifically, not just "timestamptz is more correct," and knowing the local-time exception exists instead of treating UTC-everywhere as an absolute rule.
