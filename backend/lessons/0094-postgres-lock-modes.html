Lock modes: why ALTER TABLE blocks reads that FOR UPDATE never touches

Lesson 6's SELECT ... FOR UPDATE blocks other writers but never blocks a plain read. Lesson 19 said a plain CREATE INDEX blocks writes for the whole build — and never mentioned that some DDL blocks reads too. Both lessons used the word "lock" as if there were only one kind. There isn't: Postgres has eight table-level lock strengths, and which one a statement takes decides exactly who it blocks.

1 · The same word, two very different blast radiuses

Lesson 40's funds transfer took a row lock with SELECT ... FOR UPDATE on two specific rows. While that lock is held, another transaction trying to UPDATE or FOR UPDATE those same two rows waits — but a plain SELECT * FROM accounts from a totally unrelated request sails straight through, unaffected. Now compare a routine deploy running this migration against the same table, live, in production:

ALTER TABLE accounts ADD COLUMN risk_score INT;

This one statement blocks every SELECT against accounts, anywhere in the app, for as long as it runs. Both statements "take a lock." One lets reads through; the other stops them cold. The difference isn't a bug in either lesson — it's that Postgres's locks come in a lock mode, each naming a different set of other modes it conflicts with.

2 · Four modes that cover almost everything you'll actually hit

Postgres defines eight table-level lock modes; four of them explain nearly every lock question that comes up in ordinary backend work:

ModeTaken byBlocks
ACCESS SHAREa plain SELECTonly conflicts with ACCESS EXCLUSIVE — the weakest mode there is
ROW EXCLUSIVEUPDATE, DELETE, INSERTother writers on the same rows — never blocks a plain SELECT
SHARE UPDATE EXCLUSIVEVACUUM, CREATE INDEX CONCURRENTLYother schema changes and itself — still lets reads and writes through
ACCESS EXCLUSIVEplain CREATE INDEX, most ALTER TABLE, DROP TABLE, TRUNCATEeverything — the only mode that blocks even a plain SELECT

Read that table as a strength ordering. ACCESS SHARE is so weak it only conflicts with the single strongest mode. ROW EXCLUSIVE — what every ordinary write takes — conflicts with other writers but still leaves every reader alone, which is exactly why Lesson 6's row lock never stops an unrelated SELECT. ACCESS EXCLUSIVE sits at the opposite end: it conflicts with literally every other mode, including ACCESS SHARE, which is the specific fact that makes a live ALTER TABLE freeze reads, not just writes.

Frontend-habit trap: "locked" sounds like one binary state — like a mutex, held or not. A Postgres table-level lock is a mode, not a boolean; the real question is never "is it locked" but "which mode, and does that mode conflict with what I'm trying to do." A row already under ROW EXCLUSIVE from an UPDATE is completely unlocked from a reader's point of view.

3 · Lesson 19's CONCURRENTLY, now with the actual mechanism

Lesson 19 said a plain CREATE INDEX blocks writes for the whole build, and CREATE INDEX CONCURRENTLY avoids that at the cost of a slower, retry-on-failure build. The lock table says exactly why: plain CREATE INDEX takes SHARE, which conflicts with ROW EXCLUSIVE — so every INSERT/UPDATE/DELETE queues up until the index finishes. CREATE INDEX CONCURRENTLY takes the weaker SHARE UPDATE EXCLUSIVE instead, which does not conflict with ROW EXCLUSIVE — writes keep flowing the entire time. Neither form ever takes ACCESS EXCLUSIVE, so reads were never blocked by either one; the trade Lesson 19 described was always about writes specifically, and the lock table is the reason.

The same lock table also explains the Lesson 19 symptom from the other direction: a plain ALTER TABLE ADD COLUMN takes ACCESS EXCLUSIVE by default — the PostgreSQL Manual states it directly: an ACCESS EXCLUSIVE lock is acquired for an ALTER TABLE statement "unless explicitly noted" otherwise for that specific subform. That's a stronger lock than CREATE INDEX ever takes, which is why adding a column to a live, high-traffic table is the riskier of the two operations — it stops reads, not just writes, for however long the statement takes.

4 · Checking it from Go before you ship a migration

A migration tool can't tell you which lock mode a statement will take, but Postgres can — pg_locks joined against pg_stat_activity shows exactly what mode is currently held or being waited for, which is the first thing to check when a deploy seems to be hanging:

// lockWaiters reports any session currently waiting to acquire a lock,
// along with the mode it wants and the query that's blocking it -- the
// first query to run when a migration or a deploy seems to be stuck.
func lockWaiters(ctx context.Context, db *sql.DB) ([]LockWait, error) {
    rows, err := db.QueryContext(ctx, `
        SELECT blocked.pid, blocked.mode, blocking.query
        FROM pg_locks blocked
        JOIN pg_locks blocking
          ON blocking.locktype = blocked.locktype
         AND blocking.relation = blocked.relation
         AND blocking.granted
        JOIN pg_stat_activity ON pg_stat_activity.pid = blocking.pid
        WHERE NOT blocked.granted`)
    if err != nil {
        return nil, fmt.Errorf("query lock waiters: %w", err)
    }
    defer rows.Close()

    var waits []LockWait
    for rows.Next() {
        var w LockWait
        if err := rows.Scan(&w.PID, &w.Mode, &w.BlockingQuery); err != nil {
            return nil, fmt.Errorf("scan lock wait: %w", err)
        }
        waits = append(waits, w)
    }
    return waits, rows.Err()
}

type LockWait struct {
    PID           int
    Mode          string
    BlockingQuery string
}

A waiting Mode of AccessExclusiveLock blocked behind an ordinary-looking SELECT is the signature of exactly today's trap: some earlier statement — an in-progress ALTER TABLE, or a transaction that opened one and never committed — is holding ACCESS EXCLUSIVE, and every read in the app is now queued behind it, not just the writes.

Q: "A routine ALTER TABLE ADD COLUMN migration took down read traffic on a busy table for thirty seconds during deploy. Someone says 'but it's just adding a column, it should be instant.' What actually happened?" A strong answer, out loud: "Adding a column itself is near-instant, but ALTER TABLE takes an ACCESS EXCLUSIVE lock by default, and that's the one lock mode that blocks even a plain SELECT, not just writes. If the table had any ongoing long-running query or transaction holding a weaker lock first, the ALTER had to queue up behind it, and then every read that arrived afterward queued up behind the ALTER in turn — so the thirty seconds wasn't the column add, it was every reader stacked up behind one ACCESS EXCLUSIVE lock. The fix is making sure nothing long-running touches that table around deploy time, and for add-column-with-default specifically, checking whether the Postgres version needs a full rewrite or not before assuming it's cheap." The signal: naming the specific lock mode and that it blocks reads, not reaching for "the database was just slow."

Scope line

This lesson covers table-level lock modes — the strength classification deciding which statements conflict with which. It doesn't cover row-level lock mechanics (Lesson 6's FOR UPDATE, Lesson 33's optimistic version columns), Postgres's deadlock detector (Lesson 40), or application-level advisory locks (Lesson 56) — all three are still correct as taught; today just names the table underneath the word "lock" that all of them were already using.
