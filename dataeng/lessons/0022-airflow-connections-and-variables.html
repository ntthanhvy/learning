1 · The credential this course has been hard-coding since Day 7

Every DAG this course has built carries a secret worth naming honestly: Day 7's two BashOperators run dbt and psycopg commands that reach your fdp Postgres over localhost:5432 using whatever credentials your shell environment or profiles.yml already had lying around — never passed through Airflow at all. That's fine for a single laptop with one database, but it's exactly the shape of thing that breaks the moment there's a second environment: a DAG hard-coding localhost:5432 can't also run against a staging warehouse without editing the DAG file itself and redeploying it, and a DAG with a password typed directly into its own source puts that password in your repo's git history forever, visible to anyone who can read the code. REPO_DIR = "/opt/airflow/food-delivery-pipeline" in Day 7's DAG is the same category of problem in miniature — a path baked into code that has to change by hand for every environment that isn't this one laptop.

Airflow has had an answer to this since well before version 3: a Connection: one named record holding everything needed to reach one external system, looked up by a short ID string instead of typed into every DAG that needs it.

2 · Defining a Connection without ever touching the Airflow UI

The UI's Admin → Connections form is the most commonly screenshotted way to create one, but it isn't the only way, and it's the wrong one for something you want checked into version control and reproduced identically on a teammate's machine or in CI. This round confirmed the environment-variable form works exactly as documented against a real 3.3.1 install: setting AIRFLOW_CONN_<CONN_ID> (the ID upper-cased) to a URI string makes that connection resolve with no database write and no UI click at all.

export AIRFLOW_CONN_FDP_PG="postgres://fdp_user:fdp_pass@localhost:5432/fdp"

Reading it back in Python, confirmed this round:

from airflow.sdk.bases.hook import BaseHook

conn = BaseHook.get_connection("fdp_pg")
print(conn.host, conn.port, conn.login, conn.schema)

Real output from this round's run, against that exact env var: localhost 5432 fdp_user fdp — the URI's pieces parsed into named fields (.host/.port/.login/.password/.schema), confirmed as a real, live object rather than the raw string handed back unparsed. The CLI gives the same lookup without writing any Python:

AIRFLOW_HOME="$(pwd)/airflow_home" AIRFLOW_CONN_FDP_PG="postgres://fdp_user:fdp_pass@localhost:5432/fdp" \
  uv run --with "apache-airflow==3.3.1" airflow connections get fdp_pg

Real output this round (abridged to the columns that matter):

conn_id | conn_type | host      | schema | login    | password | port
fdp_pg  | postgres  | localhost | fdp    | fdp_user | fdp_pass | 5432
A real caution this round's own output surfaced: airflow connections get prints the password in plain text by default. Airflow's secrets masker hides values it considers long/complex enough to be a real secret in task logs, but a short demo password like fdp_pass was explicitly skipped this round with the warning Skipping masking for a secret as it's too short — worth knowing before screenshotting a terminal, and a reason a real deployment uses a long, generated password rather than a short memorable one.

Nothing about this depends on where the environment variable actually comes from — a plain shell export today, a container's environment: block in docker-compose.yml tomorrow, or a secrets manager injecting it at deploy time later. The DAG code that reads the connection never changes across any of those; only where the value is set does.

3 · Variables: the same idea for a non-secret config value

A Variable is Airflow's matching mechanism for a config value that isn't a connection to an external system — a threshold, a feature flag, a file path. Day 10's dbt {{ var() }} (project-level, read by dbt at compile time) and today's Airflow Variable (orchestration-level, read by a task at run time) solve the same "don't hard-code a magic number" problem one layer apart; they don't share storage and a change to one never touches the other. Confirmed this round, the same environment-variable pattern as Connections, one level simpler (a plain value, not a parsed URI):

export AIRFLOW_VAR_SLA_THRESHOLD_MINUTES="45"
from airflow.sdk import Variable
minutes = Variable.get("sla_threshold_minutes")  # "45", always a str

Real CLI output this round: airflow variables get sla_threshold_minutes printed 45 directly, confirming the same env-var-first resolution Connections use. Variable.get() always returns a string unless deserialize_json=True is passed — a real gotcha if the TODO below forgets to cast it before comparing to an integer.

Q: "How do you keep database credentials out of your Airflow DAG code?" A strong answer, out loud: "Airflow Connections. Instead of writing a host, port, username and password directly into a DAG file, you define a Connection once — as an environment variable, through the UI, or via a secrets backend in a real deployment — keyed by a short ID, and the DAG looks it up at run time with BaseHook.get_connection. The DAG file itself never contains a credential; it contains a connection ID string, which isn't a secret. That means the exact same DAG code can run against a local Postgres, a staging warehouse or production just by changing which environment it's deployed into, with zero code changes and nothing sensitive ever committed to git. Non-secret config that still shouldn't be hard-coded — a threshold, a flag — gets the same treatment through Variables instead." The signal: naming environment-driven resolution as the actual mechanism, not just reciting "don't hard-code secrets" as a slogan.
