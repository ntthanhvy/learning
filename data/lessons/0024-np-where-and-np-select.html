np.where() and np.select(): vectorized if/else

Lesson 23's own teaser named two unconfirmed candidates: np.where()/np.select(), and select_dtypes()/category dtype. A fresh grep confirmed both were still genuinely absent, but np.where() wins today's slot — it's NumPy content MISSION.md explicitly calls in scope ("read NumPy-flavored code... predict its output"), and it directly replaces Lesson 12's apply() for the single most common reason people reach for apply() at all: an if/else per row.

1 · The SQL bridge: CASE WHEN

SQL answers "a new column whose value depends on a condition" with CASE WHEN ... THEN ... ELSE ... END. NumPy's direct equivalent is np.where(): pass it a condition, a value for True, a value for False.

import numpy as np

clean["tier"] = np.where(clean["amount"] >= 100, "High", "Low")
#   customer  amount  tier
#0        An   120.0  High
#1        An    42.0   Low
#2      Binh    35.5   Low
#3      Binh   180.0  High

Read it exactly like SQL: CASE WHEN amount >= 100 THEN 'High' ELSE 'Low' END. clean["amount"] >= 100 is a boolean mask (Lesson 1) — np.where() just gives you a way to turn that mask directly into two different output values instead of only using it to filter rows.

2 · Why not apply()? Because this is exactly the case it's slow for

Lesson 12 taught apply(axis=1) as the honest per-row escape hatch, and warned it's "still a Python-level loop under the hood — one Python function call per row." An if/else on one column is the textbook case that loop is unnecessary for:

# apply() version — works, but loops in Python
def tier(amount):
    return "High" if amount >= 100 else "Low"
clean["tier"] = clean["amount"].apply(tier)

# np.where() version — same result, no Python-level loop
clean["tier"] = np.where(clean["amount"] >= 100, "High", "Low")

Both produce the identical column. The difference is entirely how the work gets done: apply() re-enters the Python interpreter once per row (Lesson 1's core vectorization argument, again); np.where() evaluates the condition as one array operation and picks values from two arrays in compiled code, no per-row callback at all.

3 · More than two outcomes: np.select()

A plain if/elif/elif/.../else chain — SQL's CASE WHEN ... WHEN ... WHEN ... ELSE END — is np.select(), not nested np.where() calls:

conditions = [
    clean["amount"] >= 150,
    clean["amount"] >= 50,
]
choices = ["High", "Mid"]
clean["tier3"] = np.select(conditions, choices, default="Low")
#   customer  amount tier3
#0        An   120.0   Mid
#1        An    42.0   Low
#2      Binh    35.5   Low
#3      Binh   180.0  High

conditions and choices are two parallel lists (a general Python idiom, not pandas-specific): row by row, np.select() walks the conditions in order and uses the first one that's True, falling through to default if none match — exactly like SQL's CASE WHEN evaluating branches top to bottom and stopping at the first hit. An's 120.0 fails the first condition (not >= 150) but passes the second (>= 50), landing on "Mid".

Order matters, same as SQL: if the conditions overlap, np.select() picks the FIRST match, not the most specific one. Writing amount >= 50 before amount >= 150 would silently put every high-value row into "Mid" instead — no error, just a wrong bucket. Same discipline as ordering WHEN branches in SQL.

4 · NaN and dtype: what np.where() doesn't fix

Both functions are still built on ordinary comparisons, so Lesson 3's NaN rule still applies: comparing NaN >= 100 is False, not an error and not "unknown" — a row with a missing amount would silently land in the ELSE/default branch, the same "no crash, quietly wrong" shape as Lesson 23's ungrouped-shift() pitfall. Check for missing values explicitly first (isna()) if a missing input should mean something other than the default output.

Q: "How would you add a categorical column based on a numeric threshold, without a Python loop?" A strong answer, out loud: "np.where(condition, value_if_true, value_if_false) for a single yes/no split — it's CASE WHEN...ELSE...END, fully vectorized: the condition is a boolean mask evaluated once over the whole column, then values are picked from two arrays in compiled code, no per-row Python call. For three or more branches I'd reach for np.select() with a list of conditions and a matching list of choices, evaluated in order like SQL's CASE WHEN chain — first match wins. I'd avoid apply() here since a per-row Python function is the exact case np.where()/np.select() exist to replace, and Lesson 12 already showed apply() can be 10-100x slower at scale. One gotcha I'd flag: comparisons against NaN are always False, not an error, so a missing input silently falls into the default branch unless I check isna() first." The signal: naming CASE WHEN unprompted, explaining WHY it's vectorized (not just that it is), and flagging the NaN-into-default trap.
