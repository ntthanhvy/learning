np.intersect1d() / np.union1d() / np.setdiff1d(): SQL's INTERSECT/UNION/EXCEPT, as arrays

Lesson 98 closed with no standing candidate, so this round ran a fresh curriculum/glossary scan (same approach as Lesson 98's own). Found a genuinely surprising gap: this course has taught pd.merge()'s row-level joins (Lesson 5), the cartesian how="cross" (Lesson 92), and even named iterrows() as an anti-pattern in Lesson 1 — but the three NumPy functions that are the direct array equivalent of SQL's INTERSECT/UNION/EXCEPT set operations were never covered at all, despite being a clean, high-frequency interview pattern under MISSION.md's SQL-equivalence framing.

1 · Three functions, one shared shape: dedupe, sort, return a plain array

np.intersect1d() / np.union1d() / np.setdiff1d() are NumPy's set-theory trio. Confirmed directly (numpy 2.5.4), the direct SQL mapping:

import numpy as np
a = np.array([1, 2, 3, 4, 5])
b = np.array([3, 4, 5, 6, 7])

np.intersect1d(a, b)  # array([3, 4, 5])  -- SQL: a INTERSECT b
np.union1d(a, b)      # array([1, 2, 3, 4, 5, 6, 7])  -- SQL: a UNION b
np.setdiff1d(a, b)    # array([1, 2])  -- SQL: a EXCEPT b (order matters!)
np.setdiff1d(b, a)    # array([6, 7])  -- EXCEPT is NOT symmetric, unlike the other two

Confirmed directly: all three dedupe and sort the result even when an input has repeats or is unsorted (np.intersect1d([1,1,2,2,3], [2,3,3,4]) returns array([2, 3]), never [2, 2, 3]); every output is a plain, brand-new ndarray, never a view into either input. intersect1d and union1d are symmetric (order of the two arguments never changes the result) — setdiff1d is the one exception, exactly like SQL's EXCEPT: "a minus b" and "b minus a" are different questions.

2 · Two silent traps: assume_unique's wrong answer, and NaN never matching itself

Confirmed directly: all three accept an optional assume_unique= flag (default False) that skips the internal sort-and-dedupe step for speed — a real win on large, already-deduplicated input (a ~17x speedup confirmed directly on two 2M-element arrays pre-reduced with np.unique()), but it is a trust-me flag, not a check:

dup = np.array([1, 1, 2])
other = np.array([1, 2])
np.intersect1d(dup, other)                       # array([1, 2])  -- correct, default checks
np.intersect1d(dup, other, assume_unique=True)   # array([1, 1, 2])  -- WRONG, no error raised

Passing assume_unique=True on input that is not actually unique returns a silently wrong answer with duplicates still in it — no exception, no warning. It is only safe right after a step that already guarantees uniqueness (np.unique(), a groupby key, a primary key column).

The second trap, confirmed directly: intersect1d requires NaN to equal itself to count as "shared," and NaN != NaN — so two arrays that each contain a NaN never report it as an intersection, exactly like SQL's NULL never equaling NULL in a join or INTERSECT:

np.intersect1d([np.nan], [np.nan])   # array([], dtype=float64)  -- empty! NaN != NaN
np.union1d([1.0, np.nan, 3.0], [np.nan, 3.0, 4.0])
# array([ 1.,  3.,  4., nan])  -- union/setdiff just collect values, NaN passes through once

union1d and setdiff1d don't need an equality match to decide membership the same way, so a NaN that appears in the input simply passes through once — only intersect1d's "must match to survive" logic silently drops it.

3 · When to reach for this vs. pd.Index's own set methods

Confirmed directly: all three functions happily accept a pandas Series or Index as input (not just a raw array), but they always hand back a plain NumPy ndarray — the pandas type and its index are gone. If staying inside pandas types matters, pd.Index already has its own named methods doing the identical job while preserving dtype and Index-ness:

idx1 = pd.Index([1, 2, 3, 4])
idx2 = pd.Index([3, 4, 5, 6])
idx1.intersection(idx2)  # Index([3, 4], dtype='int64')  -- stays an Index
idx1.union(idx2)         # Index([1, 2, 3, 4, 5, 6], dtype='int64')
idx1.difference(idx2)    # Index([1, 2], dtype='int64')  -- EXCEPT, same asymmetry as setdiff1d

Same three operations, same asymmetric-difference rule — the choice is really just "do I need a plain array back, or do I need to keep working with pandas labels." A 2-D array handed to any of the np.*1d functions is silently flattened first rather than raising, confirmed directly — a reminder these are genuinely 1-D set tools, not a per-row comparison.

Q: "How would you find customer IDs present in both last month's and this month's active-user list?" A strong answer, out loud: "That's a set intersection — in SQL it's INTERSECT on the two ID columns. In pandas/NumPy, np.intersect1d(last_month_ids, this_month_ids) does exactly that: dedupes both sides, sorts, and returns the IDs present in both as a plain array. If I need the IDs only in one list — churned customers, say — that's setdiff1d, and I'd be careful about argument order since, like SQL's EXCEPT, a minus b isn't the same as b minus a." The signal: naming the SQL equivalent by name (INTERSECT/UNION/EXCEPT) and flagging setdiff1d's asymmetry unprompted, not just knowing the function exists.
