statement_timeout & lock_timeout: a query that should have died minutes ago

Lesson 18 covered a pool running dry because every connection was checked out and none came back. Lesson 40 covered two transactions stuck waiting on each other's locks forever, until Postgres's own deadlock detector stepped in. Neither lesson answered a simpler, more common version of both: one single query, or one single lock wait, that just never finishes — no deadlock cycle, no code bug, just a query that should have died minutes ago and didn't. By default, Postgres will let it run.

1 · Postgres's default patience is infinite

A missing WHERE clause on an UPDATE, an accidental cross join, a query against a table that grew ten times larger than when it was written, a row lock held by a transaction someone forgot to commit — none of these produce an error by default. Postgres will run the statement, or wait for the lock, for as long as it takes. There is no built-in ceiling.

That silence is expensive precisely because of Lesson 18's own connection pool: a query that runs for ten minutes holds its one checked-out connection for the full ten minutes, unavailable to every other request. A pool of 20 connections doesn't need 20 runaway queries to seize up — a handful is often enough to starve every other handler waiting on Acquire(), exactly the pool-exhaustion symptom Lesson 18 described, just caused by one slow query instead of a leaked one.

statement_timeout and lock_timeout exist to put a ceiling on both halves of that problem.

2 · Two different clocks, two different things they measure

These are easy to blur together because both abort a statement and both are configured the same way, but they start their clocks at different moments and measure different waiting:

statement_timeoutlock_timeout
Measurestotal time the statement runs, start to finishtime spent only while waiting to acquire a lock
Fires ona slow scan, a huge sort, any long-running querya SELECT ... FOR UPDATE or UPDATE blocked behind another transaction's lock
SQLSTATE on abort57014 (query_canceled)55P03 (lock_not_available)
Default value0 — disabled, no limit0 — disabled, no limit

A statement that never has to wait for a lock at all — a plain slow SELECT doing a full table scan — only ever risks hitting statement_timeout. A statement that runs instantly once it acquires its lock, but sits behind another transaction's row lock for nine minutes first, is the case lock_timeout exists for — statement_timeout would eventually catch that too, but lock_timeout lets you fail fast on lock contention specifically, with a much shorter budget than you'd want for genuinely heavy queries.

3 · Setting them: session, transaction, or query

Both are ordinary SET parameters — in milliseconds if no unit is given, or with an explicit unit like '3s':

-- for the rest of this session/connection
SET statement_timeout = '5s';
SET lock_timeout = '2s';

-- scoped to just this transaction -- reverts automatically at COMMIT/ROLLBACK,
-- the safer default for anything running over a pooled connection
BEGIN;
SET LOCAL statement_timeout = '5s';
SET LOCAL lock_timeout = '2s';
UPDATE accounts SET balance_cents = balance_cents - 500 WHERE id = 42;
COMMIT;

SET (without LOCAL) changes the setting for the rest of that connection — dangerous on a pooled connection, since the next unrelated request that happens to borrow it inherits a timeout it never asked for. SET LOCAL is scoped to the current transaction only and reverts automatically at COMMIT or ROLLBACK, which is why it's the shape worth reaching for by default when a value needs to differ per request rather than per whole database.

Because the value is just a session setting, a Go handler using pgx can set it once at the start of a request-scoped transaction, before running the actual query:

func updateBalance(ctx context.Context, pool *pgxpool.Pool, accountID int64, deltaCents int64) error {
    tx, err := pool.Begin(ctx)
    if err != nil {
        return fmt.Errorf("begin: %w", err)
    }
    defer tx.Rollback(ctx)

    // scoped to this transaction only -- never leaks onto the next request
    // that happens to reuse this pooled connection afterward
    if _, err := tx.Exec(ctx, `SET LOCAL lock_timeout = '2s'`); err != nil {
        return fmt.Errorf("set lock_timeout: %w", err)
    }
    _, err = tx.Exec(ctx, `UPDATE accounts SET balance_cents = balance_cents + $1 WHERE id = $2`, deltaCents, accountID)
    if err != nil {
        return fmt.Errorf("update balance: %w", err)
    }
    return tx.Commit(ctx)
}

This is a different mechanism from context.Context cancellation, worth naming explicitly since both can end a query early: ctx's deadline is enforced by the Go driver canceling the query from the client side; statement_timeout/lock_timeout are enforced by Postgres itself, server-side, regardless of what the client is doing. A generous or missing ctx deadline doesn't protect the database from a runaway statement — the two are complementary, not substitutes for each other.

Trap: setting either value in postgresql.conf applies it to every session on the whole server, including migrations, long analytical reports, and admin backfills that may legitimately need minutes. The Postgres manual itself calls this out — a global statement_timeout is generally not the recommended way to apply it; scope it per role, per session, or per transaction (as above) so a genuinely long-running job can opt out or set its own larger budget, instead of a database-wide value fighting every use case at once.

4 · Where this sits next to Lesson 40's deadlock detector

Lesson 40's deadlock detector and lock_timeout both end a stuck lock wait, but they catch different shapes of stuck. The deadlock detector only fires when there's an actual cycle — transaction A waiting on a lock B holds, while B waits on a lock A holds. It does nothing for a transaction waiting on a lock held by a perfectly healthy transaction that is just slow, or one some engineer left open in a debugger and forgot about — there's no cycle, so nothing detects it, and the wait is unbounded. lock_timeout catches that second case: it doesn't care whether a cycle exists, only how long this statement has been waiting for any lock. The two are complementary — a real deadlock trips the detector almost immediately regardless of any timeout setting, while a plain single-sided long wait is exactly what only lock_timeout catches.

Q: "An endpoint that updates a single row occasionally hangs for minutes with no error, then eventually succeeds. What would you check, and what would you change?" A strong answer, out loud: "No error and no deadlock message rules out Lesson 40's cycle case — this sounds like the endpoint is sitting in a lock queue behind some other transaction that's holding the row's lock and just being slow, or that never committed. First I'd check for neither a statement_timeout nor a lock_timeout set on that connection — with both at the default of zero, Postgres will wait indefinitely, and that lines up with the symptom exactly. I'd add a SET LOCAL lock_timeout scoped to the transaction, short — a couple seconds — so a stuck lock wait fails fast with SQLSTATE 55P03 instead of silently tying up a pooled connection for minutes, which is its own problem given how few runaway queries it takes to exhaust a pool." The signal: distinguishing this from a deadlock by the missing error, and reaching for SET LOCAL rather than a global config change.
