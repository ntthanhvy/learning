Clickjacking: the attack that never touches your API

Lesson 22 covered CSRF (a forged request) and Lesson 52 covered CORS (who can read a response). Both assume the attacker's page talks to your server directly. Clickjacking doesn't send your server anything unusual at all — it tricks a real, logged-in user into clicking your own legitimate page without realizing it. Today: the attack, and the one response header that kills it.

1 · The trick: your page is real, the click isn't what the user thinks it is

An attacker builds an ordinary-looking page — a "You won a prize, click to claim" button — and loads your actual site inside an invisible <iframe>, positioned exactly under that button and made transparent with CSS. The user sees the attacker's button. What their click actually lands on is your real page's real "Delete my account" or "Transfer funds" button, sitting invisibly on top. This is clickjacking (also called UI redress attack): the request that fires is completely genuine — same cookies, same origin, same session as if the user clicked it directly on your actual site — because it is the user, clicking your actual page. Nothing about the request itself looks forged.

Why CSRF defenses (Lesson 22) don't help here: a CSRF token still gets submitted correctly, because the form being submitted is your own real form, rendered by your own real page, inside that invisible frame — the token travels along with it exactly as designed. CSRF defends against a forged request from a different page; clickjacking doesn't forge anything, it just tricks the human into triggering a real one.

2 · The defense is refusing to be framed at all

Since the entire attack depends on your page loading inside someone else's <iframe>, the fix is a response header telling browsers to refuse that outright. X-Frame-Options is the older, simpler of the two headers that do this:

HTTP/1.1 200 OK
X-Frame-Options: DENY
Content-Type: text/html

DENY means no page, anywhere, including your own other pages, may load this response in a frame. SAMEORIGIN is the usual real-world choice — it still blocks every other origin, but allows your own site to frame its own pages (a settings page inside a dashboard's preview pane, for instance). Either value makes the invisible-iframe trick in Section 1 simply fail: the browser never renders your page inside the attacker's frame at all, so there's nothing for the fake button to sit on top of.

3 · The modern, more flexible version: CSP's frame-ancestors

Content-Security-Policy (CSP) is a broader header covering far more than framing — which origins scripts, styles, and images are allowed to load from at all, a defense mostly aimed at limiting what an injected script (Lesson 17's XSS-adjacent risk) can do even if one slips through. Its frame-ancestors directive does exactly what X-Frame-Options does, but can name multiple specific allowed origins instead of only all-or-same-origin:

Content-Security-Policy: frame-ancestors 'self' https://partner-dashboard.example.com

Where a real product needs to let one specific trusted partner embed a widget while blocking everyone else, X-Frame-Options genuinely cannot express that (it's binary: nobody, or only same-origin); frame-ancestors can. Shipping both together is standard practice today — frame-ancestors for browsers that respect CSP, X-Frame-Options as the fallback for the few that don't.

Frontend-habit trap: this looks like a client-side concern — "add a header in the frontend build config" — because the symptom (a page refusing to render in an iframe) shows up in the browser. It isn't a frontend fix. The header is set by the server on every response, the same place status codes and Content-Type come from; there's no client-side equivalent that protects anything, since the attacker's page is the one doing the framing, not yours.

4 · Setting it from Go

Like CORS (Lesson 52), this is pure response-header middleware — no state, no database, applied once to every response:

// securityHeaders sets response headers that are safe defaults for nearly
// every page this API serves -- X-Frame-Options blocks the classic
// clickjacking iframe trick, and the CSP frame-ancestors directive is the
// modern equivalent with finer-grained control over exactly who may embed.
func securityHeaders(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        w.Header().Set("X-Frame-Options", "DENY")
        w.Header().Set("Content-Security-Policy", "frame-ancestors 'none'")
        next.ServeHTTP(w, r)
    })
}

'none' in frame-ancestors is CSP's equivalent of DENY — no origin at all, including your own, may frame this response. Swap either value to allow same-origin or a named partner origin exactly as Sections 2–3 described, the same per-endpoint judgment call CORS required: most API JSON endpoints don't need this header at all (nothing meaningful renders from a bare JSON response in a frame), but any endpoint that returns an actual HTML page a logged-in user interacts with — a dashboard, a settings form, an account-deletion confirmation — is the exact shape of page this defends.

Q: "What's clickjacking, and why doesn't a CSRF token stop it?" A strong answer, out loud: "It's loading a real, legitimate page inside an invisible iframe, lining up a real button under a fake one on an attacker's page, so the user's genuine click triggers a genuine action on the real site without realizing it. A CSRF token doesn't help because nothing is forged — the form that submits is the real form from the real page, rendered normally inside that invisible frame, so the token goes along for the ride correctly. The actual defense is refusing to be framed at all: X-Frame-Options or CSP's frame-ancestors, set on the server's response, telling the browser this page can't be loaded in someone else's iframe in the first place." The signal: clearly separating "the request is forged" (CSRF) from "the click is misdirected" (clickjacking) — same-looking symptom, completely different mechanism and fix.

Scope line

This lesson covers the one CSP directive relevant to clickjacking (frame-ancestors) and X-Frame-Options. It doesn't cover CSP's full policy language (script-src, nonce/hash-based script allowlisting, report-uri violation reporting) — that's a deeper XSS-mitigation topic in its own right, one level past what's needed to recognize and close the clickjacking gap specifically.
