1 · The gap Day 66 named and left open

Day 66 proved static membership works for exactly one consumer: kill warehouse-loader-1, restart it inside session.timeout.ms, and the coordinator hands back the same three partitions with no rebalance in between. That lesson's own closing section named what it didn't test: "extending today's static ID to Day 34's two-consumer scenario, each with its own fixed group.instance.id, to show the grace window holding even when one of two members restarts while the other keeps serving its own partitions." Day 34 is the only lesson that ever ran two consumers in this group, and it did so with dynamic membership — every join or leave triggered a rebalance across both members, because neither carried a fixed identity the coordinator could recognize on rejoin. Today combines the two: two consumers, both statically identified, one of them restarting.

The question worth asking before running anything: with two members instead of one, does a restarting member's grace window affect the other member at all? Day 66's single-consumer version couldn't test this, because there was no other member to disturb.

2 · What changes, and what provably doesn't, with a second member in the room

The mechanism is unchanged from Day 66: each consumer's group.instance.id is a fixed identity the coordinator tracks independently per member. Adding a second statically-identified member doesn't make the coordinator track anything jointly — it tracks warehouse-loader-1's partitions and warehouse-loader-2's partitions as two separate bookkeeping entries, exactly as it would track two dynamic member IDs, except that a static entry survives that specific member's restart instead of being discarded the moment a heartbeat is missed.

That independence is the whole answer to Section 1's question: when warehouse-loader-2 is killed and restarts within its own session.timeout.ms, the coordinator's bookkeeping for warehouse-loader-1 never enters the picture. There is no group-wide rebalance to opt into or out of, because nothing about a per-member rebalance trigger changed group-wide: static membership turns off the *consequence* (reassignment) for a timely rejoin, it never turns the *trigger* into something shared. The surviving consumer, warehouse-loader-1, keeps consuming its own partitions throughout, never pausing, because from its point of view nothing in the group changed at all.

Bridge from Day 66: the trade-off is identical to the one-consumer case, just localized to whichever member is restarting. If warehouse-loader-2 were gone for good rather than restarting, its partitions would sit unread by anyone — including by warehouse-loader-1 — for the full session.timeout.ms grace window before the coordinator finally reassigns them. A second statically-identified member doesn't shrink that window or let the survivor opportunistically pick up the slack early; it only changes what happens if the same identity comes back in time.

3 · Build: two statically-identified consumers, kill one, restart it, watch the other never move

Edit scripts/consume_order_events.py so group.instance.id is read from an environment variable rather than hardcoded to Day 66's single "warehouse-loader-1", so the same file can run as either member:

# scripts/consume_order_events.py -- one line changed from Day 66's hardcoded string
import os

consumer = Consumer(
    {
        "bootstrap.servers": BOOTSTRAP,
        "group.id": GROUP_ID,
        "group.instance.id": os.environ["INSTANCE_ID"],  # was a literal string on Day 66
        "session.timeout.ms": 45000,
        "enable.auto.commit": False,
    }
)

Start both instances, each with its own fixed identity, confirm the 3-partition split, then kill and restart only the second one — well inside the 45-second grace window — while the first keeps running the whole time:

uv run --with confluent-kafka python3 scripts/produce_order_events.py

INSTANCE_ID=warehouse-loader-1 uv run --with confluent-kafka --with "psycopg[binary]" python3 scripts/consume_order_events.py &
CONSUMER_A=$!
INSTANCE_ID=warehouse-loader-2 uv run --with confluent-kafka --with "psycopg[binary]" python3 scripts/consume_order_events.py &
CONSUMER_B=$!
sleep 3
docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group warehouse-loader

kill -9 $CONSUMER_B
sleep 5    # well under the 45s session.timeout.ms
INSTANCE_ID=warehouse-loader-2 uv run --with confluent-kafka --with "psycopg[binary]" python3 scripts/consume_order_events.py &
CONSUMER_B=$!
sleep 3
docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group warehouse-loader

5 · What this still doesn't cover

Today only tested one member restarting while the other stays healthy the whole time. It says nothing about both members restarting at once, or about what happens if warehouse-loader-2's restart takes longer than its own grace window — that case degrades to exactly Day 34's dynamic rebalance for that one member's partitions, with warehouse-loader-1 still unaffected, since the coordinator's bookkeeping is per-member regardless of outcome. It also doesn't address what happens if two processes briefly carry the same group.instance.id at once — a deploy overlap where the old and new container both start with INSTANCE_ID=warehouse-loader-2 — which confluent-kafka's client fences with an error rather than letting both run; Day 66's scope line already named this as out of scope, and nothing here changes that, since this course's actual deploys are one process at a time.

Q: "If you've got two Kafka consumers in a group, both using static membership, and you restart just one of them, does the other one feel anything?" A strong answer, out loud: "No, and that's the point of static membership being per-member bookkeeping rather than group-wide. The coordinator tracks each group.instance.id's partition assignment independently. When one member's process restarts inside its own session.timeout.ms grace window, the coordinator recognizes the same identity rejoining and hands back exactly what it had — nothing about that touches the other member's own assignment, because there was never a group-wide rebalance to begin with, just one member's own bookkeeping entry being reused instead of discarded. I confirmed this by running two consumers with distinct group.instance.id values against the real topic, killing and restarting only one, and watching kafka-consumer-groups.sh --describe show the exact same partition split both before and after — the healthy consumer's partitions never moved. If that same member had actually died for good instead of restarting, only its own partitions would eventually get reassigned once the grace window expired — the other member still wouldn't have been touched any earlier by that fact alone." The signal: stating that static membership's bookkeeping is per-member, not group-wide, and that a healthy member's assignment is unaffected by a neighbor's restart regardless of whether that neighbor's own restart ultimately succeeds or times out.

Scope line

This lesson covers two statically-identified consumers in one group, one restarting inside its grace window while the other keeps running, confirmed live only as a valid two-identity config against the installed client — not against a real broker's actual multi-member rebalance behavior this round. It does not cover both members restarting simultaneously, a restart that overruns its own session.timeout.ms (which degrades to Day 34's ordinary dynamic-style reassignment for that member alone), fencing two processes sharing one group.instance.id (already out of scope per Day 66's own scope line, unchanged here), or the broker-side group.min.session.timeout.ms/group.max.session.timeout.ms bounds (broker tuning, past this course's working-level Kafka scope per MISSION.md).
