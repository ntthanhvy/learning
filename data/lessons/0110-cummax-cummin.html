Series.cummax() / Series.cummin(): the running best-so-far, and the NumPy function that doesn't exist

Lesson 109's own closing note carried forward one named candidate: cummax()/cummin(), confirmed uncovered since an earlier scan. Lesson 7 taught cumsum() as the pandas spelling of SQL's SUM() OVER (ORDER BY ...); today's pair is the exact same running-without-collapsing idea, swapped to "running biggest/smallest seen so far" — MAX()/MIN() OVER (ORDER BY ...), running instead of whole-window.

1 · Same shape as cumsum(), different question

cummax() and cummin() walk top to bottom exactly like cumsum() does, in whatever order the rows currently are — but instead of adding, each row reports the best (or worst) value seen by that point:

s = pd.Series([3, 1, 4, 1, 5, 9, 2, 6])

s.cummax()
# 0    3
# 1    3   -- 1 < 3, so the running max stays 3
# 2    4   -- 4 > 3, new running max
# 3    4
# 4    5
# 5    9
# 6    9   -- 2 < 9, stays 9
# 7    9
# dtype: int64

s.cummin()
# 0    3
# 1    1   -- new running min
# 2    1
# 3    1
# 4    1
# 5    1
# 6    1
# 7    1
# dtype: int64

Confirmed directly (pandas 3.1.0): the last value of s.cummax() always equals s.max(), and the last value of s.cummin() always equals s.min() — the running version converges to the plain aggregate by the final row, same relationship cumsum()'s last value has to sum().

2 · The one guarantee: it never moves the wrong way

Confirmed directly by diffing the result against itself: every step of cummax() is either flat or increases — it can never go down — and every step of cummin() is either flat or decreases — it can never go up. That single monotonic guarantee is the whole interview-answerable property, and it's what makes groupby("customer")["amount"].cummax() read naturally as "this customer's biggest order so far, as of this row," the running-record idea behind a leaderboard or a stock's running 52-week high:

df = pd.DataFrame({
    "customer": ["An", "An", "Binh", "Binh", "An"],
    "amount":   [10, 30, 5, 20, 15],
})
df["running_best"] = df.groupby("customer")["amount"].cummax()
# customer  amount  running_best
#       An      10            10
#       An      30            30   -- new personal best
#     Binh       5             5
#     Binh      20            20
#       An      15            30   -- still 30 -- 15 didn't beat it, group resets independently

Same gotcha as Lesson 7's cumsum(): there is no ORDER BY argument. If "so far" is meant to track order by date, the rows must be sort_values("order_date")'d first — cummax() only ever trusts the order the rows are already in.

3 · NaN: resumes by default, poisons on request

Confirmed directly, same shape as cumsum()'s own NaN handling: the default skipna=True leaves a NaN in place at its own row, but resumes tracking the running max/min right after it, as if that row were simply skipped:

s2 = pd.Series([3.0, np.nan, 1.0, 5.0, np.nan, 2.0])

s2.cummax()                     # default skipna=True
# 0    3.0
# 1    NaN   -- this row's own value IS NaN, stays NaN
# 2    3.0   -- resumes tracking: max(3, 1) = 3, the NaN was skipped
# 3    5.0
# 4    NaN
# 5    5.0
# dtype: float64

s2.cummax(skipna=False)
# 0    3.0
# 1    NaN   -- once skipna=False hits a NaN, EVERY row after turns NaN too
# 2    NaN
# 3    NaN
# 4    NaN
# 5    NaN
# dtype: float64

skipna=False is a one-way poison: the very first NaN permanently contaminates every row that follows, since "the running max including an unknown value" is itself unknown forever after. An all-NaN Series returns an all-NaN result either way, never raising.

4 · The NumPy layer: no np.cummax(), reach for np.maximum.accumulate() instead

Lesson 109 found a raw NumPy function under every pandas cumulative method so far: np.cumsum(), np.cumprod(), np.diff(). cummax()/cummin() break that pattern entirely — confirmed directly, there is no np.cummax() or np.cummin() function in NumPy at all; calling one raises AttributeError: module 'numpy' has no attribute 'cummax'. The actual NumPy equivalent lives under a different name, np.maximum.accumulate(), reached through the np.maximum ufunc's own .accumulate() method rather than a standalone function:

arr = np.array([3, 1, 4, 1, 5, 9, 2, 6])

np.cummax(arr)
# AttributeError: module 'numpy' has no attribute 'cummax'

np.maximum.accumulate(arr)
# array([3, 3, 4, 4, 5, 9, 9, 9])   -- same running max, different spelling

Confirmed directly, one more twist: called on a pandas Series instead of a plain array, np.maximum.accumulate() does dispatch and hands back a Series — the same recognizes-a-Series behavior Lesson 109 found for np.cumsum(), just reached through a ufunc method instead of a plain function name.

The trap: guessing np.cummax(arr) by analogy with np.cumsum(arr) is a reasonable guess that's simply wrong — NumPy never shipped a top-level cummax/cummin function, only the ufunc-accumulate spelling. pd.Series.cummax() itself is implemented on top of this exact ufunc machinery, so the pandas method and the "missing" NumPy function were never two different algorithms — only one has a short top-level name.

5 · One more contrast with cumprod(): dtype is never upgraded

Lesson 109 found cumprod() silently upgrades a narrow integer dtype (int8/int16/int32) to int64 to guard against overflow. Confirmed directly, cummax()/cummin() need no such guard and trigger none — taking the max or min of two int8 values can never overflow the way multiplying them can, so an int8 Series's cummax() stays int8, dtype unchanged.

Q: "How would you compute each stock's running 52-week high from a sorted price history?" A strong answer, out loud: "Sort by date within each stock first — cummax() trusts row order, it has no ORDER BY of its own, same gotcha as cumsum(). Then groupby(stock)['price'].cummax() gives the running high as of each row: it only ever holds steady or increases, by definition, so the last value in each group always equals that stock's plain max(). If I needed the NumPy-array version instead of a Series, I'd reach for np.maximum.accumulate() — NumPy never shipped a plain np.cummax() function, which is an easy wrong guess by analogy with np.cumsum()." The signal: naming the monotonic guarantee as the actual mechanism, not just the method name, and knowing the NumPy-layer gap exists instead of assuming every pandas cumulative method has a same-named NumPy twin.

Scope line

This lesson covers Series.cummax()/Series.cummin() as the running-best-so-far siblings of Lesson 7's cumsum(), their monotonic never-reverses guarantee, groupby(...).cummax() per-group behavior, the skipna NaN contrast (resume vs. permanently poison), and the missing-np.cummax() gap closed by np.maximum.accumulate(). It does not cover DataFrame.cummax(axis=) in depth, cummax()'s rarer sibling on non-numeric/categorical dtypes, or the wider family of NumPy ufunc .accumulate()/.reduce() methods beyond maximum/minimum — worth knowing the pattern exists, not today's focus.
