subprocess: running another program from Python

Every pipeline eventually needs something that already exists as a command-line tool — git, a shell script, a compiled binary, another language's interpreter — rather than a Python import. subprocess is the standard-library way to launch one, wait for it, capture what it printed, and check whether it actually succeeded, instead of shelling out blind and hoping.

1 · run(): launch, wait, get a result back

The one function used almost every time is subprocess.run(). It takes a list of strings — the program name, then each argument, exactly as they'd be typed at a shell, but split apart instead of joined into one string — starts that program, waits for it to finish, and returns a result object:

import subprocess

result = subprocess.run(["echo", "hello", "world"], capture_output=True, text=True)
print(result.returncode)   # 0 -- the process's exit status; 0 means success by convention
print(result.stdout)       # "hello world\n" -- captured because capture_output=True

subprocess.run() is a blocking call — the line after it doesn't execute until the external program exits, the same way a regular function call blocks until it returns. capture_output=True captures the program's printed output instead of letting it go straight to the terminal; text=True decodes that output as a string instead of raw bytes, the same decode step Day 6's file-reading lessons already covered for files.

2 · Argument lists, not one shell string

The list-of-strings form is the default for a reason: each element is passed to the program exactly as one argument, with no shell involved to reinterpret spaces, quotes, or special characters. Building a single command string instead and asking the shell to parse it is where real bugs — and real security holes — come from:

# SAFE: each argument is its own list element, no shell parsing involved
filename = "my file.txt"   # a space in the name -- no special-casing needed
subprocess.run(["cat", filename])

# DANGEROUS: shell=True hands a raw string to the shell to interpret,
# so untrusted input can inject extra commands
user_input = "file.txt; rm -rf ."
subprocess.run(f"cat {user_input}", shell=True)   # runs the rm too!

shell=True is sometimes needed for genuine shell features like pipes or wildcards, but it should never be combined with a string built from untrusted input — the rm -rf . above runs because the shell sees a ; and treats it as "command, then another command," not because cat did anything wrong. The list form sidesteps the whole class of bug: a filename containing ; is just a filename, with no shell around to notice.

3 · Checking success: returncode and check=True

A finished process almost always reports whether it worked via its exit code: returncode is 0 by convention for success, nonzero for failure. subprocess.run() never raises an exception on a nonzero exit by default — it just hands back the result and lets the caller decide. check=True changes that, raising if the command failed, the same "fail loud instead of silently continuing" instinct Day 8's exceptions lesson taught:

# default: silently returns, even if the command failed -- the caller must remember to check
result = subprocess.run(["ls", "/no/such/path"], capture_output=True, text=True)
if result.returncode != 0:
    print("ls failed:", result.stderr)

# check=True: raises CalledProcessError automatically on a nonzero exit
try:
    subprocess.run(["ls", "/no/such/path"], check=True, capture_output=True, text=True)
except subprocess.CalledProcessError as e:
    print("ls failed with code", e.returncode)

check=True is the right default for a pipeline step that can't sensibly continue if the external command failed — reading a nonzero returncode by hand is easy to forget in exactly the branch that matters least often and breaks loudest in production.

4 · Separating stdout from stderr

A process has two separate output streams: standard output for its actual result, and standard error for diagnostics and error messages. capture_output=True captures both, kept apart on result.stdout and result.stderr rather than merged into one blob — the same separation a well-behaved CLI tool keeps so a caller can use the real output while still seeing what went wrong:

result = subprocess.run(
    ["python3", "-c", "import sys; print('ok'); print('warn', file=sys.stderr)"],
    capture_output=True, text=True,
)
print("stdout:", repr(result.stdout))   # "ok\n"
print("stderr:", repr(result.stderr))   # "warn\n"

Without capture_output=True, both streams go straight to the terminal the Python process itself is running in, and result.stdout/result.stderr are None — fine for a script whose only goal is a side effect, wrong for a pipeline step that needs the external program's output as data to parse further.

Where pandas goes from here: nothing pandas-specific today — pandas has no subprocess-launching API of its own; a pipeline that shells out to another tool before or after a DataFrame step uses this exact module either way. Not covered further here, per MISSION.md.
