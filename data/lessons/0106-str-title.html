Series.str.title(): title-casing a column, and the apostrophe trap it shares with plain Python

Lesson 105 closed the standing .str.pad() pick and carried forward two named candidates from the same text-cleanup family: str.title()/str.join(). Re-grepped both case-insensitively across every lesson body and the glossary file before picking — both are still genuine zero-hit gaps, only ever named in past teaser text, never actually taught. Picked .str.title() over .str.join(): title-casing a names/addresses column for a report or export is a far more common real-task than joining list-valued cells, and direct probing turned up a sharp, easy-to-misdiagnose trap (apostrophes and digit boundaries) that looks pandas-specific at first glance but is actually inherited straight from Python's own built-in str.title() — a good "is this a pandas bug or a Python one?" interview-reasoning moment.

1 · Title-casing a whole column in one call

A names or address column pulled from a sloppy source often arrives as "JOHN SMITH", "john smith", or some other inconsistent casing. SQL has no single standard function for this (vendors differ: some offer INITCAP(), others nothing at all), so it is usually hand-rolled. Pandas ships Series.str.title() as a one-call fix:

import pandas as pd

s = pd.Series(["JOHN SMITH", "jane doe", "MaRy Jones"])

s.str.title()
# ['John Smith', 'Jane Doe', 'Mary Jones']    -- every word's first letter up, rest down

Confirmed directly (pandas 3.1.0): .str.title() uppercases the character right after every non-letter boundary — not just spaces, but punctuation and digits too — and lowercases every other letter. That "every boundary" rule is exactly where it stops matching the plain-English idea of "capitalize each word."

2 · The apostrophe and digit trap — inherited from Python, not a pandas bug

Confirmed directly, side by side with Python's own built-in str.title() (no pandas involved at all):

s = pd.Series(["o'brien's shop", "mcdonald's", "3rd street"])

s.str.title()
# ["O'Brien'S Shop", "Mcdonald'S", '3Rd Street']

# the exact same wrong-looking capitals come from plain Python, no pandas at all:
"o'brien's shop".title()
# "O'Brien'S Shop"    -- identical result

Confirmed directly: running s.str.title().tolist() == [v.title() for v in s] (the Python builtin applied one string at a time) returns True on every case tried — .str.title() is a thin, exact vectorized wrapper around Python's own str.title(), sharing its behavior byte for byte, not a separate pandas implementation with its own bugs. The apostrophe in "'s" counts as a non-letter boundary exactly like a space does, so the s right after it gets capitalized too — "Mcdonald'S", not the human-expected "McDonald's". The same rule hits digits: "3rd" becomes "3Rd", because the letter right after the digit boundary gets capitalized.

This is a genuinely useful interview distinction to name out loud: when a result looks buggy, check whether the behavior is coming from the pandas layer at all, or whether pandas is just a thin, faithful wrapper around a Python (or NumPy) primitive that already behaves this way. Here it is the latter — .str.title() is doing exactly what Python's str.title() does, just across a whole column at once. There is no cleaner built-in fix for the apostrophe case; the usual workaround is a regex that only capitalizes real word starts (s.str.replace(r"\w+", lambda m: m.group().capitalize(), regex=True)), which fixes the digit case ("3rd" stays "3rd") but still cannot fix "McDonald's" without a name-specific exception list — title-casing real names correctly is a known-hard problem, not a quick one-liner.

3 · capitalize() is a different method — don't reach for the wrong one

Confirmed directly: Series.str.capitalize() uppercases only the single first character of the entire string and lowercases everything else — it has no per-word logic at all, unlike .str.title():

s.str.capitalize()
# ["O'brien's shop", "Mcdonald's", '3rd street']    -- only the very first character is touched

NaN and non-string dtypes behave exactly like every other .str method probed so far (Lessons 102, 104, 105): confirmed directly (pandas 3.1.0) —

import numpy as np

pd.Series(["abc", np.nan, "def"]).str.title()
# 0    Abc
# 1    NaN      -- passes straight through untouched
# 2    Def
# dtype: str

pd.Series([1, 2, 3]).str.title()
# AttributeError: Can only use .str accessor with string values, not integer

Q: "A customer_name column came in as all-caps from an old system export. How would you normalize it, and what would you double-check?" A strong answer, out loud: "I'd start with df['customer_name'].str.title() — it's the vectorized equivalent of Python's own str.title(), one call for the whole column. But before shipping it I'd sample names with apostrophes, like O'Brien or McDonald, and names with embedded digits or hyphens — title() capitalizes after every non-letter boundary, not just spaces, so O'Brien becomes O'Brien'S and 3rd-floor-tenant becomes 3Rd-Floor-Tenant. For a small, known set of exceptions I'd follow up with a targeted .str.replace() or a mapping dict; there's no single built-in call that gets real names exactly right." The signal: knowing .str.title() isn't broken — it's doing exactly what Python's own str.title() does — and knowing where that stops being good enough for real names.
