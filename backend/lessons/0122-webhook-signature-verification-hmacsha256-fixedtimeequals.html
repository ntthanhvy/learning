Webhook signature verification, now in C# too

Lesson 30 built the HMAC verification check in Go: recompute a tag over the raw request body with a shared secret, compare it to the sender's tag in constant time, and only then parse the body. That lesson never got a C# mirror. Unlike Lesson 121's pair, this one doesn't need a framework feature at all — the whole mechanism lives in the base class library, in System.Security.Cryptography, the same place .NET keeps every other cryptographic primitive.

1 · Same two steps, now with BCL types instead of stdlib ones

Lesson 30's rule still holds exactly: verify the signature against the exact raw bytes before any JSON parsing, and compare tags in constant time, never with plain equality. Go's version reached for crypto/hmac and crypto/sha256 from the standard library; C#'s version reaches for HMACSHA256 and CryptographicOperations from the base class library — not a NuGet package, not a framework feature, just the BCL's own cryptography namespace.

public static class WebhookVerifier
{
    // webhookSecret: Lesson 21's "a secret is config too", loaded once at startup.
    private static readonly byte[] WebhookSecret =
        Encoding.UTF8.GetBytes(Environment.GetEnvironmentVariable("WEBHOOK_SECRET")!);

    // VerifySignature recomputes the HMAC-SHA256 over the raw body using the
    // shared secret, then compares it to the signature the sender attached --
    // in fixed time, so a timing side-channel can't leak the right value one
    // byte at a time.
    public static bool VerifySignature(byte[] body, string gotSignatureHex)
    {
        byte[] want = HMACSHA256.HashData(WebhookSecret, body);

        byte[] got;
        try { got = Convert.FromHexString(gotSignatureHex); }
        catch (FormatException) { return false; }

        return CryptographicOperations.FixedTimeEquals(want, got); // NOT want.SequenceEqual(got)
    }
}

app.MapPost("/webhooks/payments", async (HttpRequest req) =>
{
    using var ms = new MemoryStream();
    await req.Body.CopyToAsync(ms);
    byte[] body = ms.ToArray();

    string signature = req.Headers["X-Webhook-Signature"].ToString();
    if (string.IsNullOrEmpty(signature) || !WebhookVerifier.VerifySignature(body, signature))
        return Results.Unauthorized(); // unverified -- never reaches JsonSerializer.Deserialize

    // only now is it safe to parse and act on the body
    var evt = JsonSerializer.Deserialize<PaymentEvent>(body);
    return Results.Ok();
});

The handler reads the body as raw bytes first — req.Body.CopyToAsync into a buffer — for the exact reason Lesson 30 named in section 3: ASP.NET Core's own model binding would parse the JSON for you, but parsing and re-serializing can shift whitespace, key order, or number formatting, producing different bytes than what the sender actually signed. Verify first, parse second, same order as the Go version, same reason.

2 · The building blocks: a static hash method, and a comparison that can't leak timing

The first piece is HMACSHA256. Go's version built the tag in three explicit steps — construct an hmac.New hasher, Write the body into it, Sum to get the bytes out. HMACSHA256.HashData collapses that into one static call: hand it the key and the body, get the tag back, no hasher object to construct, write into, or dispose. The class still supports the Go-style streaming shape too (an instance plus ComputeHash) for large payloads read incrementally, but a webhook body is already fully buffered in memory by the time it's verified, so the one-shot static method is the right fit here, not the streaming one.

The one easy-to-miss detail, same as Lesson 30's: want.SequenceEqual(got) or want == got compiles, looks correct, and passes every functional test — and is exactly the naive comparison Lesson 30 warned about, since LINQ's SequenceEqual returns as soon as it finds a mismatched byte. CryptographicOperations.FixedTimeEquals is the one call that actually closes the timing side-channel; nothing else in the BCL's ordinary equality tooling does.

3 · What doesn't change crossing languages

Every correctness rule Lesson 30 named still applies untouched: the signature is computed over the exact raw bytes, not a reserialized copy; verification happens before parsing, never after; a mismatched signature is rejected outright with no partial trust; and real providers' concrete shapes — Stripe's timestamp + "." + body construction, GitHub's raw-body-only X-Hub-Signature-256 — are unchanged by which language receives them. None of that is Go-specific or C#-specific; HMACSHA256 and CryptographicOperations.FixedTimeEquals are just the two BCL pieces that carry it out in .NET instead of crypto/hmac and hmac.Equal.

Scope line

This lesson covers HMACSHA256.HashData as the C# mechanism for computing an HMAC tag, and CryptographicOperations.FixedTimeEquals as the constant-time comparison, for Lesson 30's webhook-signature pattern. It does not cover the streaming HMACSHA256 instance API, other hash algorithms, or key management/rotation in any depth — only the one static method and one comparison method this pattern needs. Lesson 30's own raw-bytes-first, provider-envelope, and replay-timestamp rules are not re-taught, only carried over unchanged.
