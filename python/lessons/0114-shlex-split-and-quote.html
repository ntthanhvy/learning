shlex: splitting and quoting shell-style strings

Day 68's subprocess.run() wants a list of strings, but a command often starts life as one string — typed by a person, read from a config file, pasted from a log. shlex is the standard-library module that turns a command-line-shaped string into that list the same way a shell would (respecting quotes), and does the reverse job too: making one value safe to drop into a shell command string in the first place.

1 · shlex.split(): a string to the argv list Day 68 wants

Day 68 built subprocess.run() calls by hand, one list element at a time: ["cp", filename, "/tmp/backup"]. But a command often arrives as a single string instead — a user types one line, a config file stores one field, a log records the exact command that ran. shlex.split() parses that string the way a POSIX shell would, splitting on whitespace but keeping a quoted substring together as one piece:

import shlex

command_line = 'cp "my file.txt" /tmp/backup --verbose'
argv = shlex.split(command_line)
print(argv)
# confirmed live: ['cp', 'my file.txt', '/tmp/backup', '--verbose']

shlex.split() is exactly the missing step between "a command as one string" and the list subprocess.run() takes — notice the quoted "my file.txt" became one list element, 'my file.txt', with the quote marks themselves stripped away, not a literal 4-character split on every space.

2 · shlex.quote(): the opposite direction, made safe

Day 68 flagged shell=True's danger: building one command string by hand (f"cat {user_input}") lets shell metacharacters like ; inject extra commands. Sometimes a single shell-string really is unavoidable — writing a shell script, logging the exact command for a human to copy-paste, building a line for os.system(). shlex.quote() makes one value safe to embed in that string, wrapping it in quotes (and escaping any quote characters inside it) only when it actually needs protection:

print(shlex.quote("hello"))            # confirmed live: hello  -- no special characters, left alone
print(shlex.quote("my file.txt"))    # confirmed live: 'my file.txt'  -- space forces quoting
print(shlex.quote("a; rm -rf /"))    # confirmed live: 'a; rm -rf /'  -- the whole thing becomes one literal argument

shlex.quote() is exactly the function that would have stopped Day 68's injection example: f"cat {shlex.quote(user_input)}" turns the dangerous "file.txt; rm -rf ." into one literal argument instead of two shell commands — the semicolon stops being special the moment it is inside quotes the shell itself put there.

The real fix is still the list form: shlex.quote() makes a shell *string* safer, but Day 68's list-of-arguments form to subprocess.run() avoids the shell parser entirely and needs no quoting at all. Reach for quote() only when a real shell string is unavoidable — a generated script, a log line, an os.system() call already committed to — not as a substitute for the list form in new subprocess code.

3 · shlex.join(): the exact inverse of split()

shlex.join(argv) takes a list of strings — the same shape subprocess.run() takes, or Day 39's argparse might have parsed apart — and joins them back into one shell-safe string, quoting each element with shlex.quote() wherever needed:

argv = ["cp", "my file.txt", "/tmp/backup"]
command_line = shlex.join(argv)
print(command_line)
# confirmed live: cp 'my file.txt' /tmp/backup

# confirmed live: splitting that string back apart reproduces the original list exactly
print(shlex.split(command_line) == argv)   # True

join() and split() round-trip cleanly, confirmed live above — useful for logging the exact command a script is about to run (or just ran) in a form a human could paste back into a terminal and get the identical result, spaces and all, without hand-rolling the quoting logic the shell itself uses.

Where pandas/NumPy go from here: neither has any notion of shell commands or quoting — a pandas pipeline that shells out to an external tool first builds the argument list with plain Python (or shlex, for a string it already has), runs it, then hands the resulting file to pd.read_csv(). Command construction is a stdlib/OS-level job, not a data-frame job. Not covered further here, per MISSION.md.
