1 · np.mod(): the % operator's NumPy twin, elementwise on arrays

Confirmed directly (numpy 2.5.5), np.mod(a, b) is literally the same function as np.remainder(a, b) — confirmed directly via np.mod is np.remainder, which returns True — and it matches Python's own % operator and pandas' Series.mod() exactly:

import numpy as np
import pandas as pd

np.mod(7, 3)     # 1  -- the ordinary case, no sign trap
np.mod(-7, 3)    # 2  -- NOT -1; result takes the SIGN OF THE DIVISOR (3, positive)
-7 % 3          # 2  -- plain Python % agrees exactly
np.mod(7, -3)    # -2 -- divisor is negative now, so the remainder flips negative too

Confirmed directly, this is the trap: anyone coming from C, Java, or JavaScript expects % to follow the sign of the dividend (the number being divided) — those languages compute truncated division, so -7 % 3 is -1 there. Python and NumPy instead compute floored division, where the remainder always has the divisor's sign. Both are "correct" by their own language's rule; the trap is assuming the C-style answer while reading or writing NumPy code.

2 · np.fmod(): the C-style sibling that disagrees on exactly this case

Confirmed directly, NumPy ships both rules as separate functions. np.fmod(a, b) disagrees with np.mod() on exactly the mixed-sign case above:

np.fmod(-7, 3)   # -1  -- takes the sign of -7 (the dividend), the C-style answer
np.mod(-7, 3)    # 2   -- takes the sign of 3 (the divisor) instead -- same inputs, different answer
Confirmed directly, divide-by-zero does not raise either: np.mod(5, 0) and np.fmod(5, 0) both return 0 (not NaN, not inf) with a RuntimeWarning ("divide by zero encountered in remainder"/"...in fmod") — confirmed directly via warnings.catch_warnings. On a float dividend, np.mod() works fine on fractions too (np.mod(5.5, 2) is 1.5), and NaN passes through unchanged with no warning. On an int64 array, the result dtype stays int64 — confirmed directly, no upcast to float, matching the floor()/ceil()/trunc()/round() family's int-preserving rule, not sqrt()/log()/exp()'s always-upcast rule.

3 · np.divmod() and np.power(): quotient-plus-remainder in one call, and the fractional-exponent NaN trap

Confirmed directly, np.divmod(a, b) returns a tuple of (floor_divide(a, b), mod(a, b)) in one call — the NumPy spelling of Python's built-in divmod(), elementwise:

np.divmod(-7, 3)   # (-3, 2) -- floor(-7/3) is -3, and mod(-7,3) is 2 from Section 1

np.power(a, b) is the elementwise sibling of ** (and Series.pow(), confirmed directly to match exactly). The trap, confirmed directly: a negative base with a fractional float exponent returns NaN, not the real-valued root someone might expect:

np.power(2, 10)        # 1024 -- the ordinary case
np.power(-8.0, 1/3)   # nan, RuntimeWarning: invalid value encountered in power
# -8 ** (1/3) "should" be -2 (the real cube root), but NumPy only ever
# evaluates a float exponent via the general a**b formula, which has no
# real solution for a negative base -- it does not special-case integer-
# valued roots like 1/3 to recover the real cube root

Q: "What does -7 % 3 give you in Python, and would that surprise someone coming from Java or C?" A strong answer, out loud: "It's 2, not -1. Python and NumPy's np.mod()/np.remainder() use floored division, where the remainder always takes the sign of the divisor — here the divisor is 3, positive, so the remainder is positive too. C, Java, and JavaScript instead use truncated division, where the remainder takes the sign of the dividend, so -7 % 3 would be -1 there. NumPy actually ships both: np.mod() for the Python-style answer, np.fmod() for the C-style one — so if I'm porting numeric code from C, I'd reach for np.fmod() to match the original behavior exactly, not assume np.mod() is a drop-in." The signal: naming the actual numeric answer first, then correctly attributing the difference to floored-vs-truncated division, not just "different rounding."
