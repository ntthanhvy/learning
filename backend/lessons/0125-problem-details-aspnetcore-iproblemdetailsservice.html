Problem Details, now in C# too

Lesson 83 covered RFC 7807/9457 Problem Details as a standard, language-agnostic JSON error shape — five fields, a registered media type, nothing tied to any one framework. ASP.NET Core happens to ship a first-party implementation of that exact standard: a ProblemDetails class, a service that writes it onto a response automatically, and middleware wiring that turns on by default. This lesson is that implementation, not a new concept.

1 · The same five fields, now a real class

Lesson 83's JSON shape (type, title, status, detail, instance) maps one-to-one onto ProblemDetails, a plain C# class the framework ships:

public class ProblemDetails
{
    public string? Type { get; set; }
    public string? Title { get; set; }
    public int? Status { get; set; }
    public string? Detail { get; set; }
    public string? Instance { get; set; }
    public IDictionary<string, object?> Extensions { get; }
}

Every name lines up with Lesson 83's table exactly — Type is still the stable category URI that never has to resolve to a real page, Detail is still the per-occurrence human text, and Extensions is the class's version of Lesson 83's "extensible" escape hatch: an IDictionary<string, object?> an API populates with its own fields, serialized alongside the standard five rather than replacing them.

2 · Turning it on: AddProblemDetails and two middlewares

Having the class is not the same as using it on every error response. ASP.NET Core writes a ProblemDetails body automatically only once a service is registered and the right middleware runs, through the IProblemDetailsService interface, registered with AddProblemDetails():

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddProblemDetails();

var app = builder.Build();

// Catches unhandled exceptions and writes a ProblemDetails body instead
// of a bare 500 with no content.
app.UseExceptionHandler();

// Catches client/server responses that already have a status code but
// no body yet (e.g. a bare Results.BadRequest()) and fills in a body.
app.UseStatusCodePages();

app.MapGet("/orders/{id:int}", (int id) =>
    id <= 0 ? Results.BadRequest() : Results.Ok(new { id }));

app.Run();

Both middlewares only act on a response that has a status code set but an empty body — a handler that already wrote its own JSON is left alone. UseExceptionHandler() covers the "an exception escaped the handler" case (where Lesson 7's rule about not leaking a stack trace to the client still applies); UseStatusCodePages() covers the "a handler returned a bare status code with no body" case, including routing failures like an unmatched 404. Minimal APIs and controllers wire this up the same way; controllers additionally auto-generate ProblemDetails for model-validation failures without any of this middleware, via MVC's built-in client-error handling.

3 · Extensions in practice: Lesson 83's "add your own code field," now typed

Lesson 83 showed a hand-written JSON body with an extra code, available, and requested field sitting next to the standard five. The C# equivalent populates Extensions from a CustomizeProblemDetails hook, run right before the body is written:

public class StockErrorFeature
{
    public int ProductId { get; set; }
    public int Available { get; set; }
    public int Requested { get; set; }
}

builder.Services.AddProblemDetails(options =>
{
    options.CustomizeProblemDetails = context =>
    {
        var feature = context.HttpContext.Features.Get<StockErrorFeature>();
        if (feature is null) return;

        context.ProblemDetails.Type = "https://example.com/errors/insufficient-stock";
        context.ProblemDetails.Title = "Insufficient stock";
        context.ProblemDetails.Detail =
            $"Only {feature.Available} units of product {feature.ProductId} remain, {feature.Requested} were requested.";

        // Lesson 83's extra fields, now strongly placed in Extensions --
        // still serialized alongside type/title/status/detail/instance, not
        // instead of them.
        context.ProblemDetails.Extensions["code"] = "insufficient_stock";
        context.ProblemDetails.Extensions["available"] = feature.Available;
        context.ProblemDetails.Extensions["requested"] = feature.Requested;
    };
});

This is Lesson 83's exact closing argument, now with a concrete hook: adopting Problem Details in ASP.NET Core doesn't mean giving up a short, stable, switch-on-able code field — it means that field moves into Extensions, still riding alongside the standard envelope and still served as application/problem+json by the registered IProblemDetailsWriter.

Default behavior worth knowing: once AddProblemDetails() is registered, these middlewares only respond with a ProblemDetails body when the request's Accept header is application/json, application/problem+json, or a wildcard like */*. A request asking for text/html or application/xml gets a fallback instead — the framework won't force a JSON shape onto a client that explicitly asked for something else.

4 · What doesn't change crossing the port

Lesson 83's full argument still holds: Problem Details standardizes the envelope and the Content-Type signal, not a domain's vocabulary, and it earns its keep once errors cross an organizational boundary rather than staying inside one team's closed API. The C# mechanism is new; the judgment call about whether to bother adopting the RFC at all is identical to Lesson 83's — and ASP.NET Core choosing to auto-generate this shape for its own built-in validation and routing errors is itself evidence of where Microsoft judged that boundary to sit: inside the framework and its ecosystem of API clients, gateways, and OpenAPI tooling, not just one team's frontend.

Scope line

This lesson covers the ProblemDetails class, IProblemDetailsService/AddProblemDetails(), the UseExceptionHandler()/UseStatusCodePages() pair, and CustomizeProblemDetails as the C# mechanism for Lesson 83's standard. It does not cover MVC's separate ProblemDetailsFactory extension point, ValidationProblemDetails's model-validation-specific shape, or ApiBehaviorOptions.ClientErrorMapping — all real, all controller-specific refinements of the same idea, out of scope for a first pass.
