Nullable boolean (BooleanDtype) and pd.NA: a third truth value

Lesson 83's teaser named two standing candidates left over from the memory/dtype family: sparse dtype and the nullable boolean (BooleanDtype/pd.NA). Grepped all 83 lesson bodies plus the glossary first — zero real hits on either. Nullable boolean wins today's pick: it plugs a genuine gap in Lesson 3's missing-data story (every fixture and gotcha so far has been numbers or text; a column of True/False with a gap has never been covered), and it directly extends the nullable Int64/Float64 pattern from Lesson 51 to booleans. Sparse dtype remains open for a future round.

1 · The gap: plain bool has no room for "missing"

Every dtype covered so far that can hold real data can also hold a gap for it: float64 has NaN, nullable Int64 (Lesson 51) has <NA>, the default str dtype (Lesson 79) has NaN. NumPy's plain bool is the one exception — there is no third bit pattern for "unknown," only True and False. Confirmed directly: building a Series from [True, False, None] with no dtype declared does not produce bool at all — it silently upcasts the whole column to object, the same "quietly gives up and falls back to a looser type" failure mode Lesson 51 already showed for numeric columns blocked by one bad string.

pd.Series([True, False, None])                  # dtype: object -- NOT bool, silently
pd.Series([True, False, None], dtype="boolean")  # dtype: boolean -- True, False, <NA>

BooleanDtype (its dtype string is lowercase "boolean") is the fix — the exact same shape of upgrade Lesson 51's nullable Int64/Float64 made for numbers, now for true/false columns. It shows up automatically too: convert_dtypes() (Lesson 51) already picks boolean on its own for an object column of real Python True/False/None — confirmed directly, no new syntax needed to trigger it.

2 · pd.NA: not the same as NaN, and not falsy either

The missing marker inside a boolean column is pd.NA, not the familiar float NaN from Lesson 3. Confirmed directly, and both results are easy to get wrong by assumption:

pd.NA == pd.NA   # <NA> -- NOT True. "unknown equals unknown" is itself unknown
pd.NA == 1        # <NA> -- comparisons involving NA always propagate NA, never True/False
bool(pd.NA)    # TypeError: boolean value of NA is ambiguous

That last line matters in practice: an if statement, a plain Python and/or, or anything else that calls bool() on a single pd.NA value crashes outright rather than silently treating it as falsy. This is deliberate — pd.NA refuses to let "unknown" get quietly coerced into a guessed side.

3 · Kleene logic: & and | on a boolean column with NA don't behave like plain Python and/or

Element-wise & and | on a boolean-dtype column follow three-valued (Kleene) logic instead of always propagating NA. Confirmed directly against a Series of [True, False, pd.NA]:

a = pd.Series([True, False, pd.NA], dtype="boolean")
a & False   # [False, False, False]  -- False wins regardless of the other side; NA never survives
a | True    # [True,  True,  True]   -- True wins regardless of the other side; NA never survives
a & True    # [True,  False, <NA>]   -- can't short-circuit, so the NA passes through
a | False   # [True,  False, <NA>]   -- same: nothing to short-circuit on, NA passes through

The rule: False & anything is always False, and True | anything is always True, even when "anything" is unknown — that side of the logic doesn't need to know the unknown value to be certain of the answer. Only the cases that genuinely depend on the unknown value (True & NA, False | NA) actually come back <NA>. .any() and .all() follow the identical short-circuit rule: confirmed directly, pd.Series([True, pd.NA], dtype="boolean").any() is True (one confirmed True is enough, the unknown value can't change that), while .all() on the same Series is <NA> in general — it only comes back a plain True/False once every non-NA value alone already decides the answer.

Gotcha, confirmed directly: filtering a DataFrame with a boolean mask that contains pd.NA silently DROPS those rows — no error, no NaN row in the output. df[mask] where mask is boolean-dtype and has an <NA> entry at some row simply excludes that row from the result, treating unknown as "leave it out" rather than raising or including it. This is different from Lesson 3's plain-NaN-in-numeric-column behavior and different from the legacy object-dtype str.contains() case (glossary's na= entry) where a stray NaN mixed into a boolean-looking mask raises ValueError: Cannot mask with non-boolean array containing NA instead. Nullable boolean masks fail silently by omission; legacy mixed-NaN masks fail loudly. Worth checking row counts before and after any filter built from a nullable boolean column, since a row can vanish with no error at all.

4 · The corruption case: astype(bool) silently turns None into False

The sharpest reason to reach for "boolean" deliberately rather than assuming plain bool is fine: converting an object column holding real None values straight to plain bool does not raise and does not produce a missing marker — it silently turns every None into False, a real, wrong value indistinguishable afterward from a genuine False. Confirmed directly:

s = pd.Series([True, False, None], dtype=object)
s.astype(bool)      # [True, False, False]  -- the None is GONE, silently became False. No warning.
s.astype("boolean")  # [True, False, <NA>]   -- the None survives as a real, visible missing marker

This is the same "no crash, quietly wrong" family the glossary's convert_dtypes() entry already names for numeric columns — except here the corruption is worse, because a silently-invented False looks like a completely ordinary, valid data point. A column of "is this customer a VIP" where the real answer was never recorded should never be allowed to become a hard, confident "no."

Q: "Why would you ever bother with the nullable boolean dtype instead of plain bool — isn't True/False already simple enough?" A strong answer, out loud: "Plain NumPy bool has no missing-value slot at all — if I build a Series from a list that has a real None in it and don't declare a dtype, pandas doesn't error and doesn't give me bool, it silently falls back to object, and if I then force astype(bool) on that, every None quietly becomes False with no warning, which is a real data-corruption risk for something like an is_vip or is_verified flag where 'never recorded' and 'confirmed no' are genuinely different facts. Nullable boolean dtype, dtype='boolean', keeps a real third state, pd.NA, that survives astype cleanly. The one gotcha I'd watch for: filtering a DataFrame with a boolean-dtype mask that has NA in it doesn't raise or include that row — it just silently drops it, so I'd check row counts before and after any filter like that rather than assume every original row is accounted for." The signal: naming the silent object-dtype fallback, the astype(bool)-corrupts-None trap, and the silent-row-drop filtering gotcha — three distinct failure modes, not just "it can hold NA."

5 · Where this fits: the nullable-dtype family is now complete for the common cases

Lesson 51 introduced nullable Int64/Float64/string via convert_dtypes(); today's boolean is the fourth member of that same family, sharing the same pd.NA marker across all of them — a genuine missing value means the exact same thing whether the column is numbers, text, or true/false. The practical rule going forward: reach for the nullable spelling ("Int64", "Float64", "boolean") any time a column's real-world meaning allows "we don't know yet," and keep the plain NumPy dtype only when a gap genuinely cannot occur.
