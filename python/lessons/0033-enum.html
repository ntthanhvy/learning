enum: naming a closed set of choices

Every field written so far has been a plain string, int, or bool. Some fields aren't really that — an order's status is not "any string," it's one of a fixed handful: pending, shipped, cancelled. Today's standard-library module, enum, gives that fixed set a name and a type, so "misspelled a magic string" becomes a startup-time error instead of a silent bug found in production.

Bridge from SQL: a column like status is often constrained to a known list — CHECK (status IN ('pending', 'shipped', 'cancelled')), or a small lookup table it foreign-keys against — precisely so 'shiped' (typo) can never land in the column. Plain Python strings have no such guardrail: order.status = "shiped" is accepted silently, and the bug surfaces later, wherever code checks == "shipped" and quietly never matches. enum.Enum is Python's version of that CHECK constraint — a closed set of named values, enforced by the type itself rather than by convention.

1 · The problem: magic strings with no guardrail

A plain string or int "status" field compiles and runs even when it's wrong — there's nothing to catch a typo, and nothing to list the valid options in one place:

class Order:
    def __init__(self, status):
        self.status = status

o = Order("shiped")     # typo — no error anywhere, ever
if o.status == "shipped":  # silently never True for this order
    ...

Nothing lists the valid values in one place either — a new teammate has to grep the codebase for every string literal ever compared against .status to reconstruct the set by hand.

2 · enum.Enum: a fixed, named set of values

An Enum subclass defines its members as class attributes; each member is a distinct object, accessed by name, never spelled as a raw string at the call site:

from enum import Enum

class Status(Enum):
    PENDING = "pending"
    SHIPPED = "shipped"
    CANCELLED = "cancelled"

Status.SHIPPED            # <Status.SHIPPED: 'shipped'>
Status.SHIPPED.name       # 'SHIPPED'
Status.SHIPPED.value      # 'shipped'
Status.SHIPPED == Status.SHIPPED   # True — same member
Status.SHIPPED == "shipped"       # False — a Status is not a str, on purpose

That last line is the entire point: Status.SHIPPED and the string "shipped" are deliberately not equal. A typo like Status.SHIPED is not a silent wrong string — it's an AttributeError raised immediately, at the line that made the mistake, the same "fail loudly and immediately" instinct Day 8's exceptions and Day 31's implicit-unhashable rule both already used.

3 · auto(), iteration, and lookup by value

When the specific underlying value doesn't matter — only that each member is distinct — auto() assigns one, so nothing has to be typed and re-typed by hand:

from enum import Enum, auto

class Status(Enum):
    PENDING = auto()      # 1
    SHIPPED = auto()      # 2
    CANCELLED = auto()    # 3

list(Status)                  # [Status.PENDING, Status.SHIPPED, Status.CANCELLED], definition order
Status(2)                     # Status.SHIPPED — look a member up by its value
Status["SHIPPED"]              # Status.SHIPPED — look a member up by its name (string)

An Enum is iterable in definition order — the same protocol Day 5's generators and every for loop already rely on — which makes "list every valid status" a one-line list(Status) instead of a comment someone has to keep in sync by hand. Status(2) (call syntax, by value) and Status["SHIPPED"] (index syntax, by name) are two different, deliberate lookup directions — mixing them up is a common first mistake.

4 · Where this replaces a pattern already half-used

A function parameter restricted to a handful of literal strings is exactly the shape an Enum replaces — the difference is whether typos are caught at the call site or not:

def ship(order, method):        # method: any string at all gets through
    if method == "ground":
        ...
    elif method == "air":
        ...

class ShipMethod(Enum):
    GROUND = "ground"
    AIR = "air"

def ship(order, method: ShipMethod):   # method: only a real ShipMethod member gets through
    if method == ShipMethod.GROUND:
        ...
    elif method == ShipMethod.AIR:
        ...

This is the same type-hint-as-contract idea Day 18 already used for pydantic request bodies — an Enum type hint on a FastAPI path or query parameter (Day 16) is validated automatically the same way, rejecting any value outside the named set with a 422 before the handler body ever runs, with no hand-written if/elif chain of string comparisons needed at all.

Q: "Why use enum.Enum instead of a plain string constant?" A strong answer, out loud: "A plain string has no guardrail — any string is accepted anywhere one is expected, so a typo like 'shiped' compiles, runs, and fails silently far from where the mistake happened. An Enum makes the valid set a real, closed type: Status.SHIPED raises AttributeError immediately, list(Status) always lists every valid option in one place, and a type-hinted parameter or pydantic field gets that validation for free, rejecting anything outside the set before the code that assumes it's valid ever runs." The signal: naming the immediate-AttributeError-versus-silent-typo contrast specifically, not just "it's more organized."

Where pandas goes from here: a pandas Categorical column enforces the same closed-set-of-values idea at the scale of an entire column of millions of rows, rather than one Python object at a time. Not demonstrated here; that's data/'s job, and this is the only sentence in this lesson that names it.
