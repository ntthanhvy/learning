.equals() and .compare(): checking whether two DataFrames match

Lesson 53's own teaser named three zero-hit candidates from a fresh curriculum/glossary scan: add_prefix()/add_suffix(), .equals()/.compare(), and json_normalize(). This round picks .equals()/.compare(): both answer "did this table change?" — a natural pairing for real interview/take-home work (checking a transform did what it should, diffing a before/after cleaning pass), and neither has ever appeared anywhere in the curriculum.

Recap, in one line

Every wrangling step since Lesson 3 has produced a new DataFrame — cleaned, merged, reshaped. A genuinely common next question is whether two of those tables actually match: did a refactor of the cleaning pipeline change any values? Did two data sources agree? .equals() answers that with one boolean; .compare() shows exactly which cells differ, when they don't.

1 · equals(): one True/False, but stricter than it looks

The real orders_raw.csv fixture, cleaned the same way as every lesson since Lesson 6:

clean
--   order_id customer  amount order_date
-- 0         1       An   120.0 2026-01-05
-- 1         6       An    42.0 2026-01-10
-- 2         2     Binh    35.5 2026-01-06
-- 3         5     Binh   180.0 2026-01-09

A genuine copy compares equal, as expected:

clean.equals(clean.copy())
-- True

The surprise: equals() is dtype-strict. Narrowing amount to float32 keeps every value numerically identical, but equals() says no:

narrowed = clean.copy()
narrowed["amount"] = narrowed["amount"].astype("float32")
clean.equals(narrowed)
-- False

Row order and column order both count as real differences too — a re-sorted or re-ordered copy of the exact same data compares unequal. equals() is asking "is this the same table, cell for cell, dtype for dtype, in this exact layout?" — not "does this data represent the same facts?"

2 · compare(): which cells, not just whether

equals() collapses everything to one boolean; compare() shows the actual differing cells. Change Binh's second order to 999.0:

changed = clean.copy()
changed.loc[3, "amount"] = 999.0
clean.compare(changed)
--   amount
--     self  other
-- 3  180.0  999.0

Only the one differing row and column survive, with self/other sub-columns holding each side's value — every unchanged cell is dropped entirely. On two genuinely identical DataFrames, compare() returns an empty DataFrame, not a boolean — checking "did anything change" from compare()'s result means checking .empty, not treating the return value itself as a yes/no answer.

3 · Two sharp edges

Edge 1 — shape/labels must already match. compare() requires both DataFrames to share the exact same index and columns going in; it has no merge-like key-matching step. Comparing against a DataFrame with a row dropped raises outright:

clean.compare(clean.drop(index=0))
-- ValueError: Can only compare identically-labeled (both index and columns) DataFrame objects

equals() takes the opposite approach on the same situation — a shape or column mismatch never raises, it just quietly returns False, the same "no crash, meaningful-looking result" shape as this course's other flagged gotchas, just landing on a boolean instead of a wrong value. Edge 2 — why not just ==? Plain == compares cell-by-cell and returns a same-shaped True/False DataFrame — but by IEEE float rules, NaN != NaN, so two otherwise-identical tables that both carry a real, matching NaN report as unequal:

a = pd.DataFrame({"x": [1.0, float("nan")]})
b = pd.DataFrame({"x": [1.0, float("nan")]})
(a == b).all().all()
-- False  -- wrong! these two frames ARE the same data
a.equals(b)
-- True   -- equals() treats matching NaN positions as equal

Any real-world table with missing values (which is most of them, per Lesson 3) makes plain ==-then-.all().all() an unreliable equality check. equals() exists specifically to handle this correctly.

4 · Shaping compare()'s output: keep_shape and keep_equal

The default trims everything unchanged away, which can hide context. keep_shape=True keeps every row, filling unchanged cells with NaN instead of dropping them:

clean.compare(changed, keep_shape=True)
-- (all 4 rows survive; unchanged cells and columns are NaN)

Adding keep_equal=True alongside it fills the unchanged cells back in with their real, matching value on both sides instead of NaN — a full side-by-side view of every cell, changed or not:

clean.compare(changed, keep_shape=True, keep_equal=True)
-- (all 4 rows, every column; unchanged cells show the same real value under self and other)

5 · The SQL bridge

Neither method has a clean single-statement SQL equivalent, because SQL has no notion of "two whole result sets, compared cell-by-cell in a fixed row order." The closest real-world parallel is EXCEPT (or MINUS): SELECT * FROM new EXCEPT SELECT * FROM old returns whole rows present in one side but not the other — set-based, order-independent, and row-level rather than cell-level. compare() is finer-grained than that: it can show that only one column of an otherwise-matching row changed, something EXCEPT can't express without hand-listing which columns to compare.

Q: "How would you verify that a refactored cleaning pipeline still produces the same output as the old one?" A strong answer, out loud: "Run both versions on the same input and call old_df.equals(new_df) first — one boolean, and it's stricter than it looks: it also checks dtype and row/column order, not just values, and it correctly treats matching NaN positions as equal, unlike a plain == comparison which would report a false mismatch on any shared missing value. If equals() comes back False, I'd switch to old_df.compare(new_df) to see exactly which cells changed — but only after confirming both frames share the same index and columns, since compare() raises ValueError on a shape mismatch instead of handling it. That combination — equals() as the yes/no gate, compare() for the diff when it's no — is faster than eyeballing two printed DataFrames." The signal: naming the dtype-strictness, the NaN-handling advantage over ==, and compare()'s shape-matching requirement.
