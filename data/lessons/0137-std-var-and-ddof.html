Series.std()/.var() vs np.std()/np.var(): the ddof=1 vs ddof=0 trap

This round's own fresh scan grepped every lesson body case-insensitively for .std(, .var(, np.std(, and np.var(: std only ever appeared as one column inside describe()'s output table (Lesson 49) or corr()'s own byline (Lesson 50) — never called directly, and .var()/np.std()/np.var() had zero hits anywhere across Lessons 1-136. A genuine, high-frequency interview gap: the two libraries compute a different number by default for the exact same column, with no error or warning to flag it.

1 · Same column, two different numbers by default

Confirmed directly (pandas 3.1.1, numpy 2.5.5) on one small Series:

import numpy as np
import pandas as pd

s = pd.Series([2, 4, 4, 4, 5, 5, 7, 9])

s.std()             # 2.138089935299395   -- pandas default
np.std(s.to_numpy()) # 2.0                 -- numpy default, SAME 8 numbers, different result

No crash, no warning — just two confirmed-different answers to what looks like the identical question. The cause is a single hidden parameter both functions compute with but default differently: ddof, short for Delta Degrees of Freedom.

2 · pandas defaults to ddof=1 (sample); NumPy defaults to ddof=0 (population)

Confirmed directly, every pandas statistics method (Series.std(), Series.var(), DataFrame.std()) defaults to ddof=1 — dividing the sum of squared deviations by count - 1, the sample variance formula, the correction Bessel's correction is named for, used because real data is almost always a sample of a larger population rather than the whole population itself. np.std() and np.var() default to ddof=0 instead — dividing by plain count, the population formula, treating the array as if it already contains every value that exists:

s.std(ddof=0)              # 2.0                 -- forcing pandas to ddof=0 now MATCHES numpy's default
np.std(s.to_numpy(), ddof=1)  # 2.138089935299395   -- forcing numpy to ddof=1 now MATCHES pandas' default
s.std(ddof=0) == np.std(s.to_numpy())             # True
s.std() == np.std(s.to_numpy(), ddof=1)              # True

Same formula family, same array — the two libraries simply ship opposite ddof defaults. .var() (the squared, un-rooted version .std() is the square root of) carries the identical split: pandas' Series.var() defaults to ddof=1, np.var() defaults to ddof=0.

Confirmed directly, why pandas picked ddof=1 as its default and NumPy picked ddof=0: pandas is built for tabular data analysis, where a loaded table is treated as a sample drawn from some larger real-world population — dividing by count - 1 is the standard statistical correction that makes the sample variance an unbiased estimator of the true population variance. NumPy is a general-purpose array library with no such analysis-flavored assumption baked in — it defaults to the plain mathematical population formula, dividing by count exactly, and leaves the sample correction to whoever calls ddof=1 explicitly.

3 · The silent single-row trap: pandas' default quietly returns NaN

Confirmed directly, a one-element Series's .std()/.var() under pandas' own ddof=1 default divides by count - 1 = 0 — not a ZeroDivisionError, a silent NaN:

pd.Series([5.0]).std()   # nan   -- count=1, ddof=1 -> divide by 0, silently NaN, no crash
pd.Series([5.0]).var()   # nan   -- same root cause
np.std(np.array([5.0]))  # 0.0   -- numpy's ddof=0 default divides by count=1, no trap here

A groupby().std() on any group that happens to land exactly one row wide reproduces this quietly — the output table still has the right shape, with a NaN sitting in that one group's cell instead of an error anywhere pointing at the real cause. The same "no crash, quietly wrong" family already flagged for describe() (Lesson 49) and reindex() (Lesson 47) — except here the quiet wrongness comes from a single-row group, not a dtype mismatch.

Q: "You compute df.std() in pandas and np.std() on the same column's values, and the two numbers don't match. What's going on?" A strong answer, out loud: "They're using different ddof defaults — pandas' std()/var() default to ddof=1, the sample-variance formula dividing by count minus 1, because pandas treats a loaded table as a sample of a bigger population. NumPy's std()/var() default to ddof=0, the population formula dividing by plain count, since NumPy makes no such assumption. Neither is a bug — I'd pass ddof= explicitly on whichever side to match the other once I know which formula the actual question calls for, and if a group's std() comes back NaN, my first guess is a group with only one row, since ddof=1 on a single value divides by zero silently instead of raising." The signal: naming both defaults by exact value, tying each to why that library chose it, and flagging the single-row NaN trap without being asked.
