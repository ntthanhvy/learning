Making your own objects behave like built-ins

Day 7 showed that @dataclass generates a readable __repr__ and a field-by-field __eq__ "for free," without explaining how. Today opens that box: the special methods (dunder methods, for the double underscores on both sides) that decide what print(obj) shows, what == and < do to your own objects, and @property — a way to make a method read like a plain attribute.

Bridge from SQL: a table's column order and a defined ORDER BY clause don't happen by accident — someone decided how rows print and how they sort. Python objects are the same: unless you say otherwise, printing a plain object shows its memory address, and < between two of them raises TypeError. The dunder methods below are how you tell Python "here is what printing and comparing this thing should mean" — the same decision a schema or a query's ORDER BY makes for a table.

1 · The problem, live

A plain class with no special methods at all:

class Money:
    def __init__(self, cents):
        self.cents = cents

m = Money(500)
print(m)                 # <__main__.Money object at 0x7f2a1c0a5d90> — useless for debugging
Money(500) == Money(500)  # False — compares identity (Day 1's `is`), not the cents value
Money(500) < Money(900)   # TypeError: '<' not supported between instances of 'Money'

Nothing is broken — Python simply has no idea what "printing" or "less than" should mean for a Money, so it falls back to identity for == (Day 1's is comparison in disguise) and refuses to guess for <. A dunder method (short for "double underscore") is how you fill that gap: define one with the right name, and Python calls it automatically whenever the matching syntax is used — you never call __repr__() or __eq__() by name yourself.

2 · __repr__: what printing means

__init__ is already a dunder method — the one Day 1 and Day 4 use constantly, called automatically when a class is invoked as Money(500). __repr__ works the same way, called automatically by print(), by repr(), and whenever a REPL echoes a value back without an explicit print:

class Money:
    def __init__(self, cents):
        self.cents = cents

    def __repr__(self):
        return f"Money({self.cents!r})"   # convention: valid Python that could rebuild the object

print(Money(500))       # Money(500) — not a memory address

The docs' convention (cited below) is that __repr__ should look like a valid Python expression that could recreate the object — Money(500), not a vague description — which is exactly the shape @dataclass auto-generates for you on Day 7. Writing it by hand on a plain class is what a dataclass was quietly doing all along.

3 · __eq__ and __lt__: what comparison means

Each comparison operator has its own dunder method — == calls __eq__, < calls __lt__, and there are four more (__le__, __ne__, __gt__, __ge__) covering the rest. Defining __eq__ and __lt__ compares by value instead of identity:

class Money:
    def __init__(self, cents):
        self.cents = cents

    def __repr__(self):
        return f"Money({self.cents!r})"

    def __eq__(self, other):
        if not isinstance(other, Money):
            return NotImplemented       # let Python try the other side, or fall back to False
        return self.cents == other.cents

    def __lt__(self, other):
        if not isinstance(other, Money):
            return NotImplemented
        return self.cents < other.cents

Money(500) == Money(500)   # True now — compares .cents, not identity
sorted([Money(900), Money(100)])  # [Money(100), Money(900)] — sorted() only needs __lt__

isinstance(other, Money) guards against comparing a Money to something unrelated, like an int. Returning the special value NotImplemented (not the exception NotImplementedError — a common mix-up) rather than False tells Python "I don't know how to compare these two — try the other object's method, or give up gracefully," instead of silently guessing wrong. The payoff: Day 4's sorted(rows, key=...) works on a list of Money with no key= at all once __lt__ exists, because sorted() itself is built on repeatedly calling <.

4 · Operator overloading beyond comparison

The same mechanism extends to arithmetic — + calls __add__, - calls __sub__, and so on. This is operator overloading — reusing an existing operator's syntax for a new type, rather than inventing a new method name like .add():

class Money:
    # ... __init__, __repr__, __eq__, __lt__ from above ...

    def __add__(self, other):
        return Money(self.cents + other.cents)

Money(500) + Money(300)   # Money(800) — + now means "combine two Money amounts"

The same caution SQL operator overloading never needs applies here: only overload an operator when its built-in meaning genuinely fits — + on two amounts of money is obvious, but overloading + to mean something unrelated (like merging two unrelated records) makes code that lies about what it does. When in doubt, a plainly named method reads better than a clever operator.

5 · @property: a method that reads like an attribute

A property is a method accessed without parentheses, computed fresh every time it's read:

class Money:
    def __init__(self, cents):
        self.cents = cents

    @property
    def dollars(self):
        return self.cents / 100

m = Money(550)
m.dollars              # 5.5 — read like a plain attribute, no m.dollars()

Without @property, dollars would be an ordinary method requiring m.dollars() — and Day 27's itertools functions, for contrast, are plain callables for exactly that reason, no properties involved. @property is worth reaching for when a value is fully derived from other attributes already stored (here, dollars from cents) — it guarantees dollars can never drift out of sync with cents, because nothing is stored twice.

A property can also guard writes with a paired setter, using the same name decorated with @dollars.setter:

class Money:
    def __init__(self, cents):
        self.cents = cents

    @property
    def dollars(self):
        return self.cents / 100

    @dollars.setter
    def dollars(self, value):
        if value < 0:
            raise ValueError("dollars can't be negative")
        self.cents = round(value * 100)

m.dollars = 12.50       # runs the setter — validates, then updates self.cents
m.dollars = -3          # ValueError — Day 8's raise, triggered through plain attribute-assignment syntax

This is the same validate-on-write idea Day 17's pydantic validators enforce on a whole model — @property is the plain-Python version of that same instinct, scoped to one derived attribute on a hand-written class instead of a whole request body.

Q: "How do you make a custom class printable and comparable in Python?" A strong answer, out loud: "Define __repr__ for how it prints — convention says it should look like valid Python that could rebuild the object. For comparison, __eq__ for == and __lt__ for <, each checking isinstance on the other side and returning NotImplemented, not False, for a type it doesn't know how to compare against. Once __lt__ exists, sorted() works with no key= needed, because sorted() is built on repeated < calls. And @dataclass generates exactly these two methods for you automatically — which is what it was doing under the hood the whole time." The signal: naming NotImplemented specifically, not just False — the detail most answers miss.

Where pandas/NumPy go from here: DataFrame.__eq__ and friends are exactly this same mechanism, overloaded to return an elementwise boolean array instead of one True/False — that's why df == 0 gives you a mask, not a single answer. Not demonstrated here; that's data/'s job, and this is the only sentence in this lesson that names it.
