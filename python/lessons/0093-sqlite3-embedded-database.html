sqlite3: a real database with no server to run

Day 21 talked to PostgreSQL — a separate server process, reached over a network connection. Today's module, sqlite3, is a embedded database built into the standard library: full SQL, zero setup, the whole thing a single file your script opens directly.

1 · connect(), a cursor, and the SQL the learner already knows

sqlite3.connect(path) opens a database file, creating it if it doesn't exist yet — or opens ":memory:" for a database that lives only in RAM and disappears when the connection closes, handy for scripts and tests that need a real database with nothing left behind on disk. A Connection doesn't run SQL directly; a Cursor, made with .cursor(), does:

import sqlite3

con = sqlite3.connect(":memory:")
cur = con.cursor()
cur.execute("CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT, age INTEGER)")
cur.execute("INSERT INTO users (name, age) VALUES (?, ?)", ("Ada", 30))
cur.execute("INSERT INTO users (name, age) VALUES (?, ?)", ("Grace", 40))
con.commit()

cur.execute("SELECT id, name, age FROM users WHERE age > ?", (20,))
print(cur.fetchall())
# [(1, 'Ada', 30), (2, 'Grace', 40)] -- confirmed live, each row a plain tuple

Every value that comes from outside the program — anything typed by a user, read from a file, pulled off the network — goes in through a ? placeholder and a separate tuple of values, never pasted straight into the SQL string with an f-string. sqlite3 escapes the value correctly no matter what it contains, so a name like "Ada' OR '1'='1" is searched for literally instead of breaking out of the query — confirmed live: that exact string as a parameter returns zero rows, not every row in the table. This is parameterized query, and it is the one correct way to build a query from a variable, in sqlite3 or any other database driver.

2 · Transactions: commit(), and the connection as a context manager

Changes made with INSERT/UPDATE/DELETE aren't durable until con.commit() runs; con.rollback() discards them instead. Using the connection itself as a with block wraps that for you — it commits automatically if the block finishes cleanly, or rolls back if an exception escapes:

try:
    with con:
        cur.execute("INSERT INTO users (name, age) VALUES (?, ?)", ("Temp", 1))
        raise ValueError("boom")
except ValueError:
    print("caught")

cur.execute("SELECT COUNT(*) FROM users")
print(cur.fetchone())
# (4,) -- confirmed live, the failed insert never committed; row count unchanged

That's a narrower job than Day 6's file context managers: with con: only manages the transaction — commit on success, rollback on an exception — it does not close the connection. The same con is still fully open and usable for more queries right after the block ends; only an explicit con.close() actually closes it, and a query attempted afterward raises sqlite3.ProgrammingError: Cannot operate on a closed database., confirmed live.

3 · Reading rows by name with sqlite3.Row

A plain row is a tuple — row[1] works, but says nothing about what column 1 means. Setting con.row_factory = sqlite3.Row switches every row fetched afterward to a tuple-like object that also supports lookup by column name:

con.row_factory = sqlite3.Row
cur = con.cursor()
cur.execute("SELECT id, name, age FROM users WHERE name = ?", ("Ada",))
row = cur.fetchone()
print(row["name"], row["age"])   # Ada 30 -- confirmed live, lookup by column name
print(row[0], row[1])         # 1 Ada  -- confirmed live, index access still works too
print(isinstance(row, tuple))   # False -- confirmed live, tuple-LIKE, not an actual tuple subclass

That one assignment on the connection affects every cursor made from it afterward — code reading a result by column name is far harder to break by reordering the SELECT list than code that counts on row[1] always meaning the same thing.

4 · When SQL itself rejects the data: IntegrityError

A constraint declared in the schema — UNIQUE, PRIMARY KEY, a foreign key — is enforced by SQLite itself, not by Python code checking first. A violation raises sqlite3.IntegrityError, a narrow, catchable exception distinct from a plain syntax mistake:

cur.execute("CREATE TABLE people (name TEXT UNIQUE)")
cur.execute("INSERT INTO people VALUES (?)", ("Ada",))
try:
    cur.execute("INSERT INTO people VALUES (?)", ("Ada",))
except sqlite3.IntegrityError as e:
    print(e)  # UNIQUE constraint failed: people.name -- confirmed live

Catching sqlite3.IntegrityError specifically — never a bare except: — lets a program tell "this exact row already exists" apart from every other way a query can fail, the same narrow-catching discipline Day 8 taught for exceptions generally.

Where pandas/NumPy go from here: pandas.read_sql()/DataFrame.to_sql() can move a whole table in or out of a DataFrame in one call — useful once data needs reshaping or aggregating at scale, exactly data/'s job.
