1 · The BashOperator style vs. writing a task as a function

Every task this course has built so far — Day 7's load_raw/dbt_build — is an instance of an operator class, wired together explicitly with >>. That's the classic style, and it's the right choice when a task is really "run this external command" with nothing Python-specific about it. The from airflow.providers.standard.operators.python import PythonOperator def _count(**context): context["ti"].xcom_push(key="order_count", value=500) def _report(**context): n = context["ti"].xcom_pull(task_ids="count_raw_orders", key="order_count") print(f"orders={n}") count_raw_orders = PythonOperator(task_id="count_raw_orders", python_callable=_count) report = PythonOperator(task_id="report", python_callable=_report) count_raw_orders >> report

TaskFlow style, verified this round against a real Airflow 3.3.1 install:

from airflow.sdk import dag, task

@dag(schedule="@daily", start_date=..., catchup=False)
def taskflow_demo():
    @task
    def count_raw_orders() -> int:
        return 500

    @task
    def report(order_count: int) -> str:
        return f"orders={order_count}"

    report(count_raw_orders())

taskflow_demo()

Both DAGs are identical once parsed. This round's own DagBag inspection of the TaskFlow version (Airflow 3's real loader, not just py_compile) confirms it:

tasks: ['count_raw_orders', 'report']
deps: [('count_raw_orders', 'report')]

Nowhere in the TaskFlow version is >> written, and nowhere is xcom_push/xcom_pull called by hand — report(count_raw_orders()) is a plain Python function call, and Airflow reads that call to build both the task dependency and the data hand-off between them. This is the whole value of TaskFlow: for a function-shaped task, it removes two kinds of boilerplate (manual XCom plumbing, manual >> wiring) that add nothing once the dependency is just "this function's argument is that function's return value."

2 · What TaskFlow is actually doing underneath: it's still XCom

TaskFlow does not invent a new way to move data between tasks — it is 100% sugar over the same mechanism Day 7's two BashOperators never needed, because they never passed Python values to each other. XCom ("cross-communication") is that one mechanism, and this round confirmed exactly what it stores by querying the scratch run's metadata database directly after airflow dags test taskflow_demo 2026-09-28:

sqlite3 airflow_home/airflow.db \
  "SELECT dag_id, task_id, key, value FROM xcom;"

Real output from this round's run:

taskflow_demo|count_raw_orders|return_value|500
taskflow_demo|report|return_value|"orders=500"

Two rows, one per @task-decorated function, each keyed return_value by default (the key a plain return uses; xcom_push's explicit key= argument is for anything named differently). report's own task log from the same run names the exact moment this happens:

Done. Returned value was: orders=500
Pushing xcom

The task finishes, Airflow serializes its return value, and writes it as a row in the same SQLite (or Postgres, in production) database that stores every DAG run, task state and log pointer Day 7 already called "bookkeeping about runs and tasks, never your actual data." XCom values live in exactly that bookkeeping database — not in a queue, not in object storage, not anywhere built for moving real datasets.

3 · Why that makes XCom the wrong tool for a dataset

This is the actual decision today's title is about, and it follows directly from Section 2 rather than being a rule to memorize: if XCom's value sits as one row in Airflow's own metadata table, then the size and shape of what you can put there is bounded by "something a database row and a web UI can reasonably hold," not by "whatever your pipeline needs to move." Airflow's own Best Practices doc is explicit that XCom is meant for small values — a count, an ID, a status string, a short file path — and names moving a large dataset through it as a mistake to avoid, not a scaling question.

Put concretely, against this project's own domain: Day 1's raw.orders is 500 rows; a real production day could be millions. A tempting-looking TaskFlow rewrite of Day 7's DAG might try dbt_build(load_raw()) where load_raw returns the loaded rows so dbt_build can "use" them directly in Python — that would serialize the entire orders table into one XCom row, bloating the metadata database, slowing down every webserver page that lists recent runs, and solving a problem that already has a correct answer: the data already lives in Postgres the moment load_raw finishes. The right shape, and the one Day 7 already uses, is for load_raw to return nothing (or a tiny confirmation), and for dbt_build to independently query the warehouse itself — the warehouse is the data transport, XCom is only for the small signal that one step finished and the next can start.

This is the same lesson as data/'s own warning against passing a whole DataFrame through a message queue, and backend/'s API-payload-size instincts, applied here to Airflow specifically: a pipe meant for coordination signals breaks down, often silently at first, the moment it's asked to carry the payload itself.

Q: "Your DAG needs task A's output in task B. Would you use XCom, and how do you decide?" A strong answer, out loud: "It depends entirely on the size and shape of what's being passed. XCom is a row in Airflow's own metadata database — fine for a count, an ID, a short status, anything a database column and the Airflow UI can hold comfortably. The moment it's an actual dataset — rows from a table, a file's contents — XCom is the wrong transport, because now the metadata database is holding the data payload instead of just bookkeeping about the run. The right pattern there is what my DAG already does: one task writes to the real data store, Postgres in this case, and the next task reads from that store itself. TaskFlow's @task syntax makes the small-value case nicer to write by inferring the XCom push/pull from a plain function call, but it doesn't change where the boundary is — it's still exactly XCom underneath, with the same size ceiling." The signal: naming XCom's actual storage location as the reason for the size boundary, not reciting "XCom is for small data" as an unexplained rule.
