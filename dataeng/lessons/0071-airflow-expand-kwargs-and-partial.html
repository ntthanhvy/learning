1 · The two gaps Day 69's own scope line named and left alone

Day 69 built one mapped task, check_city_sla, over one varying argument: city. Its own scope line named two real limits on that shape, straight from the official Dynamic Task Mapping doc it cited but didn't open past the first section: .expand_kwargs() for "mapping over multiple paired arguments at once," and .partial() for "fixing some arguments while mapping others." Both gaps are real the moment the per-city check needs more than one thing to vary. A food-delivery SLA floor isn't uniform across four cities of very different order volume — Hanoi and Ho Chi Minh City move far more orders than Da Nang or Hue, so a sensible min_orders floor per city (below which a day's SLA percentage is too noisy to act on) differs by city too. check_city_sla.expand(city=list_cities()) has no second slot for that: .expand() takes keyword arguments whose values are each a single list, one argument varying independently of any other, never two values arriving paired together per instance.

2 · .expand_kwargs(): one dict per instance, not one list per argument

Where .expand(city=list_cities()) takes one keyword bound to one list, .expand_kwargs() takes exactly one positional argument: a list of dicts (or an XComArg that will produce one), where each dict's keys become that one mapped instance's keyword arguments. Four cities, two arguments each, paired:

@task
def list_city_configs() -> list[dict]:
    return [
        {"city": "Hanoi", "min_orders": 50},
        {"city": "Ho Chi Minh City", "min_orders": 100},
        {"city": "Da Nang", "min_orders": 20},
        {"city": "Hue", "min_orders": 20},
    ]

@task
def check_city_sla(city: str, min_orders: int) -> dict:
    ...

check_city_sla.expand_kwargs(list_city_configs())

Confirmed this round by reading the installed apache-airflow==3.3.1 package's own expand_kwargs() method directly: it accepts only an XComArg or a Sequence of mappings — passing anything else (a plain list of strings, say) raises TypeError: expected XComArg or list[dict], not list immediately, at parse time, before the DAG is ever scheduled. Internally the mapped task's expand_input becomes a distinct type from Day 69's own, ListOfDictsExpandInput rather than DictOfListsExpandInput — the exact two names this course now has for "many arguments varying independently" versus "one bundle of arguments varying together, per instance."

3 · .partial(): the same value, every instance, no repeating it four times

A 45-minute SLA threshold belongs to the check itself, not to any one city — the same value for every mapped instance, the exact case .partial() exists for. Call it on the decorated task before .expand_kwargs(), chained:

@task
def check_city_sla(city: str, min_orders: int, threshold_minutes: int) -> dict:
    ...

check_city_sla.partial(threshold_minutes=45).expand_kwargs(list_city_configs())

.partial() on its own builds nothing — confirmed by reading the installed package's own OperatorPartial class directly: it is explicitly documented in its own docstring as "an intermediate state," existing only between DAG-parsing and the .expand()/.expand_kwargs() call that must follow it, and its __del__ method fires a real UserWarning — "Task ... was never mapped!" — if that chain is ever left incomplete. The value lands in the resulting mapped task's own partial_kwargs, confirmed live this round with a real DagBag parse printing partial_kwargs: {..., 'op_kwargs': {'threshold_minutes': 45}, ...} — one fixed value, shared by whatever number of mapped instances .expand_kwargs() ends up creating, not copied into each of the four dicts above.

A genuinely new finding this round, not assumed from Day 69's own .expand() behavior: mapping and fixing the same keyword with both calls — check.partial(city="fixed").expand_kwargs(list_configs()), where list_configs()'s dicts also set city — parsed with zero error, confirmed with a real DagBag parse against exactly that shape. Reading mappedoperator.py's own source directly explains why: .expand() calls a duplicate-key check, prevent_duplicates(), immediately against .partial()'s own kwargs, so a repeated keyword fails loudly at parse time with TypeError: unmappable or already specified argument: .... .expand_kwargs() skips that same check at parse time — it only runs inside _get_unmap_kwargs(), called once per mapped instance at actual task-execution time, with the exact same TypeError firing then instead. The DAG file you are about to commit looks clean either way; only a real run (or a live airflow tasks test, blocked here by the standing airflow db migrate gate) would surface a duplicate-key mistake made with .expand_kwargs(), where the identical mistake with .expand() would have been caught the moment the file was parsed.

Q: "When would you reach for .expand_kwargs() instead of .expand(), and what's one way the two aren't just syntactic variants of each other?" A strong answer, out loud: ".expand() takes separate keyword arguments, each bound to its own list, and every combination varies independently — it has no way to say 'these two values are paired, for the same instance.' .expand_kwargs() takes one list of dicts instead, so several arguments can vary together per mapped instance, which is what you need the moment two inputs are genuinely correlated, like a city and its own order-volume floor. They're not just two spellings of the same check, either: if you accidentally fix an argument with .partial() that a .expand() call also maps, Airflow catches that as a parse-time error immediately. The identical mistake with .expand_kwargs() parses clean, because that duplicate-key check only runs when a mapped instance is actually being unmapped at execution time — so a DAG using .expand_kwargs() needs a real run, not just a parse, to catch that specific class of bug." The signal: not treating .expand_kwargs() as a drop-in replacement for .expand() with more arguments, and naming the parse-time-versus-run-time gap in where the same mistake gets caught.
