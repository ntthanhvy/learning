Synthesis: reviewing one small feature end-to-end

Lesson 19 closed out the last named-but-untaught phrase in MISSION.md — all five success criteria now have at least one lesson behind them. Nothing new to bolt on today. Instead, this lesson does what Lesson 14 taught but hasn't been exercised on a feature built from scratch yet: take one small, concrete feature request, design it, then review the design the same way Lesson 14's five lenses would review a PR — data model, API contract, auth, concurrency, operations. One feature, all five tracks, tied together instead of taught apart.

1 · The feature request

"Let a customer mark their own order as urgent, so support can triage it faster." One sentence, one new capability. Small enough to hold in your head end-to-end — which is the point: most real backend work looks like this, not like a green-field service.

2 · Data model: one boolean column, added safely

Lesson 2 established that a table isn't a JSON blob — a new fact about an order needs a column, not a free-floating field. This fact is boolean, always applies to every order, and belongs on the row it describes: is_urgent boolean on the existing orders table, no new entity or join table (Lesson 2's join-table pattern is for many-to-many relationships; this is a single flag on a single row, so it doesn't apply here).

The migration itself is where Lesson 19 comes back directly. orders is a live table — adding is_urgent boolean NOT NULL in one step is exactly the hazard Lesson 19 named: an old-code instance mid-rollout doesn't know the column exists, and any INSERT it runs skips it, tripping the NOT NULL constraint instantly. The safe version is the expand step alone: ADD COLUMN is_urgent boolean NOT NULL DEFAULT false. A default makes this genuinely one-step-safe — old code's inserts get false automatically, no backfill or contract phase needed, because unlike Lesson 19's example this column has an honest default for every existing row (an order that already exists was, by definition, not marked urgent by this feature before it existed). No index either: Lesson 5's rule was index columns you filter or sort by at meaningful scale, and nothing in this feature queries "all urgent orders" yet.

3 · API: whose verb is this?

Lesson 3 named the temptation to reach for POST /markOrderUrgent — a verb dressed as a URL. The resource is still /orders/{id}; marking it urgent is a partial update to that resource, which is PATCH, the same verb Lesson 14's worked example used for shipping address. Reusing the existing endpoint rather than inventing a new one is itself an API-contract call: fewer surfaces for clients to learn, and it's already documented.

PATCH /orders/{id} with body {"is_urgent": true}, response {"is_urgent": true} and 200 OK on success. Two contract details worth naming out loud in review, both from earlier lessons: this call is idempotent — sending it twice leaves the same end state, satisfying Lesson 3's PUT/PATCH promise — and on failure it uses Lesson 3's error contract (a stable error.code, not a raw string) rather than inventing a one-off shape for this one field.

4 · Auth: two checks, not one

This is where Lesson 12 does the real work. "Let a customer mark their own order" has two separate requirements hiding in it, and Lesson 14's five-lens review named exactly why both matter: authentication (is anyone logged in) and authorization (does this specific order belong to this specific caller) are different checks, and a handler that only does the first is Lesson 12's IDOR — any logged-in customer could mark any order urgent by changing the id in the URL.

The fix isn't a second query "first fetch, then compare owner" — that's two round trips and a race between them. Fold the ownership check straight into the WHERE clause of the same statement, and check RowsAffected to tell "no such order" apart from "order isn't yours" — Lesson 14's own worked example named the same shape:

func (s *Server) markOrderUrgentHandler(w http.ResponseWriter, r *http.Request) {
    orderID := r.PathValue("id")
    userID := auth.UserIDFromContext(r.Context()) // Lesson 4: who is calling
    if userID == "" {
        http.Error(w, "unauthorized", http.StatusUnauthorized)
        return
    }

    // Lesson 12: ownership, not just authentication — the WHERE clause
    // only flips the row if this order actually belongs to this caller.
    tag, err := s.db.Exec(r.Context(),
        `UPDATE orders SET is_urgent = true WHERE id = $1 AND user_id = $2`,
        orderID, userID)
    if err != nil {
        http.Error(w, `{"error":{"code":"internal"}}`, http.StatusInternalServerError)
        return
    }
    rows, _ := tag.RowsAffected()
    if rows == 0 {
        // Lesson 14 §4: 404, not 403 — don't confirm the order exists
        // to a caller who doesn't own it.
        http.Error(w, `{"error":{"code":"not_found"}}`, http.StatusNotFound)
        return
    }

    w.Header().Set("Content-Type", "application/json")
    json.NewEncoder(w).Encode(map[string]bool{"is_urgent": true})
}

rows == 0 covers both "no such id" and "exists but isn't yours" with the same response — a real 404, not a 403 that would confirm the order exists to someone who shouldn't know that.

5 · Runtime: does this need a transaction, and does anything cache it?

Lesson 6's question — does this handler write to more than one place, or read-then-write the same row — applies here almost trivially: one UPDATE, one statement, nothing else changes alongside it. No transaction needed, and reaching for one anyway would be the wrong instinct to build; Lesson 14's PATCH example needed a transaction because it wrote to two tables (the order and an event log), this one doesn't. Running the concurrency lens is still worth doing explicitly rather than skipping it, because "no transaction needed" is a conclusion, not an assumption — the two are easy to mix up under time pressure.

The lens that does catch something: Lesson 9's caching rule. If order details are cached anywhere — a per-order cache entry, a list of "my orders" on a customer dashboard — this UPDATE has to invalidate it, or a customer who just flagged their order urgent reloads the page and sees the old, non-urgent version. Nothing in this feature request mentions caching, which is exactly why it's easy to ship a correct database write and a stale response — the review question is "what currently caches order data," not "does this handler cache anything," since the bug lives in a different piece of code than the one being changed.

The pattern underneath sections 2–5: none of these are new ideas — every one is a named lesson, applied to one concrete diff instead of taught in isolation. That's what makes this a review, not a fifth new topic.

6 · What "Go deeper" looks like for a feature this small

A one-column, one-endpoint feature doesn't need a design doc — but it's worth writing the two-sentence version anyway, because that's what turns into the PR description: what changes (schema + one endpoint), and what was deliberately left out (no index, no separate "urgent orders" list endpoint — not worth building until a real query needs one). Naming what you didn't build, and why, is itself a review-readiness habit Lesson 14 didn't cover explicitly: it pre-answers the reviewer's "why didn't you also do X" before they ask.

Q: "Design a small feature for me — anything, your choice — and walk me through it like you're about to open the PR." A strong answer, out loud: "I'd start with the smallest schema change that fits — here, one boolean column with a default, so the migration is safe in a single step with no backfill. Then the API: reuse an existing resource and verb if one already fits, rather than inventing a new endpoint — this is a PATCH on the order that already exists. For auth, I separate authentication from authorization explicitly and fold the ownership check into the query itself rather than a separate lookup, so there's no race between checking and acting. Then I ask whether this needs a transaction — usually no, for a single-statement change — and separately whether anything caches this data, because that's the bug that doesn't show up in the diff itself. Last, I write down what I deliberately didn't build, so the reviewer isn't left guessing whether I missed it or chose it." The signal: walking the same five lenses on a feature you designed, not just one someone handed you already broken.
