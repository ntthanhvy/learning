@classmethod and @staticmethod

Every method written so far takes self first and reads/writes one instance's state. Today's two decorators are for the other two shapes a method can be: one that builds an instance a different way (@classmethod), and one that is just a plain function living inside a class for organization, touching no instance at all (@staticmethod). Both are method decorators, the same general mechanism Day 30's @property already used.

Bridge from SQL: a table has exactly one CREATE TABLE shape, but real code builds rows several different ways — parsed from a CSV import, built from a form submission, copied from another row with one field changed. Each of those is a different construction path to the same row shape. Python's __init__ is one construction path; today's @classmethod is how a class offers several named alternatives to it — Money.from_dollars(5) alongside plain Money(cents=500) — without duplicating the class itself.

1 · The problem: one __init__, several ways to build

Day 30's Money class stores cents. Real input is not always cents — a CSV column might hold dollars as a string, like "5.00". Without today's tool, the conversion has to happen outside the class, at every call site:

class Money:
    def __init__(self, cents):
        self.cents = cents

# every caller repeats the dollars-to-cents conversion by hand
row_amount = "5.00"
m = Money(round(float(row_amount) * 100))

That conversion belongs with the class that knows what a cent is, not scattered across every caller — the same "one fixed shape, defined once" instinct Day 7's @dataclass and Day 30's __eq__ both already used, applied here to construction instead of comparison.

2 · @classmethod: an alternative constructor

A @classmethod receives the class itself as its first argument — conventionally named cls, playing the same role self plays for an instance method — instead of an instance. That lets it build and return a new instance using whatever conversion logic it needs, then hand back a normal, fully-formed object:

class Money:
    def __init__(self, cents):
        self.cents = cents

    def __repr__(self):
        return f"Money({self.cents})"

    @classmethod
    def from_dollars(cls, dollars_str):
        cents = round(float(dollars_str) * 100)
        return cls(cents)          # cls(...) is Money(...) here, but works for a subclass too

Money.from_dollars("5.00")   # Money(500) — called on the class, not an instance

Two details matter: it is called on the class (Money.from_dollars(...)), never on an instance, and it calls cls(cents) rather than Money(cents) by name — using cls means a subclass inheriting from_dollars unmodified still builds an instance of itself, not hardcoded back to Money. This is the same pattern behind stdlib constructors already used without a second thought: dict.fromkeys([...]) and datetime.fromtimestamp(...) are both @classmethods under the hood, named constructors standing beside the plain one.

3 · @staticmethod: a method with no instance and no class

Sometimes a piece of logic belongs conceptually inside a class — it is only ever used alongside it — but needs neither self nor cls. It doesn't read or write any instance state, and it doesn't build one either. That is what @staticmethod is for: a plain function, grouped inside the class purely for organization and lookup (Money.is_valid_dollars(...) reads clearly as "a Money-related check"), with no automatic first argument at all:

class Money:
    def __init__(self, cents):
        self.cents = cents

    @staticmethod
    def is_valid_dollars(dollars_str):
        try:
            return float(dollars_str) >= 0
        except ValueError:
            return False

Money.is_valid_dollars("5.00")    # True — called on the class, no instance needed
Money.is_valid_dollars("nope")    # False

The tell for "this should be a @staticmethod, not a plain instance method": try deleting self from the parameter list and the body. If nothing inside the method ever reads or writes self.anything, it was never really about one instance — it just lives near the class it supports.

4 · Telling the three apart

Three method shapes now exist, distinguished entirely by their first parameter — the same "look at what's actually being passed" instinct Day 4 used to tell positional from keyword arguments:

class Money:
    def as_dollars(self):           # instance method — needs one specific object's state
        return self.cents / 100

    @classmethod
    def from_dollars(cls, s):      # classmethod — builds a new instance, needs the class
        return cls(round(float(s) * 100))

    @staticmethod
    def is_valid_dollars(s):        # staticmethod — needs neither, just organized here
        try:
            return float(s) >= 0
        except ValueError:
            return False

An instance method needs a specific object's data to do its job (self.cents) — the shape every method through Day 31 has used. A @classmethod needs the class itself, to build a new instance a different way. A @staticmethod needs neither — if it did, it would already be one of the other two. Reaching for a free-floating module-level function instead of a @staticmethod is also completely fine when there is no strong reason to group it under the class; @staticmethod is a convenience for discoverability and namespacing, not a requirement.

Q: "What's the difference between @classmethod and @staticmethod?" A strong answer, out loud: "Both are called on the class rather than an instance, but a classmethod still receives the class itself as its first argument, conventionally called cls, which lets it build and return a new instance — that's the alternative-constructor pattern, like dict.fromkeys(). A staticmethod gets no automatic first argument at all; it's a plain function that happens to live inside the class for organization, and it never touches instance or class state. If a method doesn't read self and doesn't build a new instance, it's a staticmethod candidate; if it builds a new instance a different way than __init__, it's a classmethod candidate." The signal: naming cls specifically and giving dict.fromkeys/datetime.fromtimestamp as a stdlib example, not just reciting the decorator names.

Where pandas goes from here: pd.DataFrame.from_dict(...) and pd.DataFrame.from_records(...) are both @classmethod alternative constructors on DataFrame, the exact pattern taught here at bigger scale. Not demonstrated here; that's data/'s job, and this is the only sentence in this lesson that names it.
