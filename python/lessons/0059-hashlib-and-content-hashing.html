1 · The problem: "are these two files the same?" without reading both in full

Day 6 taught reading files with open() and Day 5 taught why a generator lets a huge file stream through constant memory. Neither answers a different, common question: given two files — or a file today versus the same file yesterday — are their contents identical? Comparing every byte works but means holding both files in memory at once, or reading both in lockstep; slow and wasteful once files are large, and pointless if the goal is just a single "did anything change?" flag stored in a database row.

# The byte-for-byte way — works, but doesn't scale and gives no compact answer to store
def same_contents(path_a, path_b):
    with open(path_a, "rb") as fa, open(path_b, "rb") as fb:
        return fa.read() == fb.read()   # both files fully in memory at once

hashlib answers a related but more useful question: given some bytes, produce a short, fixed-length "fingerprint" such that the same bytes always produce the same fingerprint, and any change to even one byte produces a completely different one. Store the fingerprint instead of the file, and "did this change?" becomes "do the two fingerprints match?" — one short string compared instead of two whole files.

2 · hashlib.sha256: deterministic, one-way, and sensitive to every bit

A hash function takes bytes of any length and returns a short, fixed-length digest. `hashlib.sha256()` is this course's default choice — build an empty hash object, feed it bytes, and read the digest back as a hex string:

import hashlib

data = b"hello world"
h = hashlib.sha256(data)
h.hexdigest()   # 'b94d27b9934d3e08a52e52d7da7dabfac484efe37a5380ee9088f7ace2efcde' -- 64 hex chars, always

hashlib.sha256(b"hello world").hexdigest() == h.hexdigest()   # True -- same bytes in, same digest out, every time
hashlib.sha256(b"hello worle").hexdigest() == h.hexdigest()   # False -- one changed letter, a completely different digest

Verified live: both comparisons match — identical bytes always produce an identical 64-character hex digest, and a single-character change produces a digest that shares no visible resemblance with the original. That second property (small input change, large unpredictable output change) is called the avalanche effect, and it's what makes a digest useless for "guess and check how close I am" — either two digests match exactly, or the inputs are considered different, with nothing in between.

3 · Hashing a file in chunks — the pattern that actually matters for Day 6-sized data

hashlib.sha256(data) above needed the whole data in memory first — fine for a short string, wrong for a multi-gigabyte file, and exactly the constant-memory problem Day 5's generators already solved once. The fix reuses that same idea: a hash object accepts bytes incrementally via .update(), so a file can be hashed one chunk at a time without ever holding it all in memory:

import hashlib

def hash_file(path, chunk_size=65536):
    h = hashlib.sha256()
    with open(path, "rb") as f:
        while chunk := f.read(chunk_size):   # Day 42's walrus -- read and check in one line
            h.update(chunk)
    return h.hexdigest()

Verified live: hashing a 1 MB in-memory buffer in 64 KB chunks via repeated .update() calls produced a digest identical to hashing the same bytes in one shot — .update() is cumulative, not a replace, so it makes no difference to the final digest whether the bytes arrive as one call or many. This is the standard shape for checksumming a real file on disk of any size, in constant memory, the same discipline Day 5 and Day 6 already established for reading — hashlib is just the first thing done with each chunk instead of yielding it onward.

Bridge from SQL: a content hash plays the role of a surrogate key computed from the row's own data instead of assigned by a sequence — two rows (or files) with identical content always get the identical key, so a UNIQUE constraint on a hash column is a cheap, storage-light way to reject an exact duplicate without comparing every other column.

4 · Two direct uses: change detection and de-duplication

Both uses follow from the same fact — identical bytes always produce identical digests, and different bytes (almost) never do:

# Change detection: store a hash instead of the whole file, compare hashes later
old_hash = "3f9a1c..."                      # saved from yesterday's run, e.g. in a database row
new_hash = hash_file("report.csv")
if new_hash != old_hash:
    print("file changed since last run -- reprocess it")

# De-duplication: group files (or records) by content hash to find exact duplicates
from collections import defaultdict   # Day 3

def find_duplicates(paths):
    by_hash = defaultdict(list)
    for p in paths:
        by_hash[hash_file(p)].append(p)
    return {h: ps for h, ps in by_hash.items() if len(ps) > 1}   # only groups with 2+ files

Verified live: two byte strings with identical content produced the identical sha256 digest, and a third with different content produced a different one — exactly the property find_duplicates relies on to group same-content files together by their shared hash, regardless of filename or location.

Not a password hasher: hashlib.sha256 is deliberately fast — good for checksums, bad for passwords, because "fast" means an attacker with a stolen password-hash database can try billions of guesses per second. Real password storage needs a deliberately slow, salted algorithm — hashlib.pbkdf2_hmac() is the standard library's own answer, or a dedicated library like bcrypt/argon2 in real backend code. That's a FastAPI-phase concern for a future lesson on authentication, not today's — today's sha256 use is entirely about detecting sameness, never about hiding a secret.
Where pandas goes from here: nothing pandas-specific today — pandas.util.hash_pandas_object() hashes DataFrame rows for pandas' own internal purposes (fast row comparison inside a DataFrame), but it isn't a general-purpose content-fingerprinting tool for arbitrary files or byte strings the way hashlib is, and this course doesn't teach pandas APIs regardless.
