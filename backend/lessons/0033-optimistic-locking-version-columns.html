Optimistic locking: the version-column alternative to FOR UPDATE

Lesson 6 fixed the lost-update race two ways: fold the check into the UPDATE, or take a row lock with SELECT ... FOR UPDATE and make the second transaction wait. Both assume the conflict is worth blocking for. Today's the case where it usually isn't — and the version-column pattern that handles it without ever holding a lock.

1 · Where FOR UPDATE stops being the right tool

Lesson 6's FOR UPDATE fix works well when a conflict is likely and the window is short — a flash-sale counter, two requests landing in the same millisecond. It works badly when the read and the write are far apart in time with a human in between: a user opens an "edit profile" form, reads the current bio, thinks for two minutes, then submits. Taking a row lock at the moment of the read and holding it open across two minutes of human typing would mean any other writer touching that row — even an unrelated admin action — blocks for the whole time the form sits open. That's not a rare edge case; it's most form-editing UIs.

Frontend-habit trap: a form's "last write wins" instinct — whoever clicks Save last silently overwrites whoever saved first — is exactly the lost update Lesson 6 named, just stretched across human-scale time instead of two requests racing in the same millisecond. The fix isn't a longer lock; it's not locking at all.

2 · Optimistic locking: don't lock, just check on write

Optimistic locking bets that two people editing the same row at the same time is rare enough not to pay for up front. Every table using it gets one extra column:

ALTER TABLE profiles ADD COLUMN version integer NOT NULL DEFAULT 1;

The read is a plain SELECT — no lock, no wait, no blocking any other reader or writer. The write is where the check happens: the UPDATE's WHERE clause demands the exact version the caller saw when it read the row, and bumps it by one on success.

UPDATE profiles SET bio = $1, version = version + 1
WHERE id = $2 AND version = $3;
-- $3 is the version this caller read earlier.
-- 1 row updated  = nobody else wrote in between, this write wins.
-- 0 rows updated = someone else already wrote and bumped the version —
--                   this caller's view is stale, and the app must decide
--                   what to do about it (see Section 3).

This is structurally the same trick as Lesson 6's first fix — fold the check into the WHERE clause of the write itself — just checking a version number instead of a stock quantity. The difference is what happens on conflict: Lesson 6's ticket counter check (remaining > 0) fails because there's truly nothing left to sell. A version mismatch here doesn't mean the row is unusable — it means someone else's write already landed, and it's an application-level decision what happens next, not a database-level dead end.

3 · Handling the conflict: it's not an error, it's a decision

Zero rows updated is not a bug and not something to silently swallow. Three honest options, in order of how often each is actually right:

  • Tell the user and let them decide. "This profile changed since you opened it — reload and reapply your edit." The HTTP-level version of this is a 409 Conflict, reusing Lesson 3's status-code vocabulary: the request was well-formed, but the state it assumed no longer holds.
  • Re-read and retry automatically, only when the write is commutative enough that blind reapplication is safe — incrementing a counter, appending to a list. Reapplying "set bio to exactly this string" over someone else's newer edit is just last-write-wins with extra steps; reapplying "increment view count by 1" is fine no matter who else wrote in between.
  • Merge, when the domain supports it (two people editing different fields of the same row) — the most work to build correctly, so reach for it last.
// updateProfile applies an optimistic-locking write: the UPDATE's WHERE
// clause requires the version the caller last read, so a concurrent writer
// who already bumped the version makes this UPDATE match zero rows instead
// of silently overwriting their change.
func updateProfile(ctx context.Context, db DB, id int64, newBio string, seenVersion int) error {
    var newVersion int
    err := db.QueryRowContext(ctx, `
        UPDATE profiles
        SET bio = $1, version = version + 1
        WHERE id = $2 AND version = $3
        RETURNING version`,
        newBio, id, seenVersion,
    ).Scan(&newVersion)

    if errors.Is(err, sql.ErrNoRows) {
        // Zero rows matched: either the id doesn't exist, or — the
        // interesting case — a concurrent writer already bumped the
        // version since this caller last read the row.
        return ErrStaleUpdate
    }
    return err
}

4 · Picking a side: optimistic vs. pessimistic

Pessimistic (FOR UPDATE, Lesson 6)Optimistic (version column)
Read costTakes a lock, blocks other writers immediatelyPlain read, blocks nobody
Best whenConflicts likely, gap between read and write is shortConflicts rare, gap includes human think-time
On conflictSecond transaction waits its turnSecond write fails fast — app decides what's next
Cost of being wrongUnrelated writers pile up waiting on a lock held too longA rare wasted round trip, retried or shown to the user

Neither one is "the correct concurrency control" in general — Lesson 6 already made that point about its own two fixes, and it holds here too. The actual question is where the time gap between read and write comes from: a few milliseconds inside one request favors locking; anything spanning a network round trip to a human favors optimistic.

Q: "Two users open the same settings page, both edit different fields, both hit Save a minute apart. How do you stop the second save from wiping out the first user's change?" A strong answer, out loud: "Taking a row lock on open would mean holding it for as long as the form stays open, which blocks unrelated writers for no good reason — that's a job for optimistic locking instead. Add a version column, have the read return it, and require the client to send it back on save. The UPDATE's WHERE clause checks version = $seen; if zero rows update, someone else already saved and I return a 409 so the second user can reload and reapply their change instead of silently overwriting it." The subtext: recognizing that a lock held across human time is the actual problem, not "add more locking."
