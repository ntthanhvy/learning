1 · The assumption every DAG so far has quietly made

Day 7's load_raw task runs a seed script that assumes the day's raw CSVs are simply there, ready, the instant the DAG fires. On a laptop running a deterministic generator, that assumption always holds. In a real deployment it rarely does: an upstream batch export finishes "sometime between 2am and 6am," not on your DAG's own clock, and a scheduled run that starts at a fixed time has no idea whether today's files have actually landed yet.

A sensor is Airflow's answer: an operator whose only job is to check a condition — repeatedly, on an interval — and let the DAG move on once it's true. Today builds one for exactly the gap Day 7 glossed over: wait for raw/orders.csv to actually exist before running dbt build against it.

2 · Two ways a sensor can wait, confirmed on a real install

The naive implementation of "check every 30 seconds" is a loop that blocks: the task holds a worker slot the entire time it's waiting, doing nothing but sleeping and re-checking. Airflow has had a cheaper option since well before version 3 — mode="reschedule" — where the sensor gives the worker slot back between checks and is simply rescheduled to try again later, instead of sitting there burning a slot. Confirmed directly from BaseSensorOperator's real constructor on a live 3.3.1 install:

poke_interval: timedelta | float = 60
timeout: timedelta | float | None = None
mode: str = 'poke'          # the default: blocks a worker slot the whole time
exponential_backoff: bool = False

mode="reschedule" is an improvement, but it still needs a worker process to wake up, re-check, and (if still false) go back to sleep — on a scheduler with hundreds of waiting sensors, that is hundreds of repeated wake-ups. Deferrable operators go one step further: the task suspends itself completely, freeing its worker slot entirely, and a separate, lightweight triggerer process (asyncio-based, can watch thousands of conditions in one process) does the actual waiting. The worker only gets woken back up once the condition is genuinely true.

Confirmed this round by reading FileSensor.execute's real source on a live 3.3.1 install, the exact branch that fires when deferrable=True:

elif not self.poke(context=context):
    self.defer(
        timeout=datetime.timedelta(seconds=self.timeout),
        trigger=FileTrigger(filepath=self.path, poke_interval=self.poke_interval),
        method_name="execute_complete",
    )

self.defer(...) is the real mechanism — it hands a Trigger object to the triggerer and tells Airflow which method to resume at once that trigger fires. The sensor's own worker slot is released the moment defer() is called, not held until the file shows up.

3 · The other half of today: what happened to "SLA"

Older Airflow tutorials (and plenty still live on the web) teach an sla=timedelta(...) argument on a task, checked by the scheduler and surfaced in a dedicated UI tab. Tried that directly against a real Airflow 3.3.1 install this round:

Dummy(task_id="t", sla=timedelta(minutes=5))
# warning: The SLA feature is removed in Airflow 3.0, replaced with Deadline Alerts in >=3.1
# AttributeError: 'Dummy' object has no attribute 'sla'

That is a real, current-version finding, not a hypothetical: the old per-task sla kwarg still parses without error (so an old DAG won't crash on import) but is silently inert — reading task.sla back afterward raises AttributeError, confirming nothing is actually checking it. The replacement, confirmed working end to end this round, is a Deadline Alert, declared on the DAG itself rather than one task:

from airflow.sdk import DAG, DeadlineAlert
from airflow.sdk.definitions.deadline import DeadlineReference, SyncCallback

def _alert_sla_breach(**context):
    print(f"SLA BREACH: dbt_build has not finished within 30 minutes")

with DAG(
    dag_id="raw_files_sensor_demo",
    deadline=DeadlineAlert(
        reference=DeadlineReference.DAGRUN_LOGICAL_DATE,
        interval=timedelta(minutes=30),
        callback=SyncCallback(_alert_sla_breach),
    ),
    ...
) as dag:
    ...

Confirmed directly against a live install: DeadlineReference.DAGRUN_LOGICAL_DATE measures from the run's logical date (other options exist for queued time or a fixed datetime); the callback must be wrapped in SyncCallback or AsyncCallback, and AsyncCallback specifically requires a real async def coroutine — passing it a plain function raised AttributeError: ... is not awaitable this round, a genuine gotcha worth knowing before picking the wrong wrapper. SyncCallback accepts an ordinary function, which is what today's build uses.

4 · Build: a sensor-gated, deadline-alerted DAG

In your food-delivery-pipeline repo, add dags/raw_files_sensor_demo.py alongside Day 7's DAG, not instead of it — same "second DAG, side by side" pattern Day 24 used for Cosmos. The sensor and the deadline wiring are given in full (new syntax today, not the day's skill); the day's actual skill is the TODO inside the callback, reading real run context instead of a bare print:

from datetime import datetime, timedelta

from airflow.providers.standard.operators.bash import BashOperator
from airflow.providers.standard.sensors.filesystem import FileSensor
from airflow.sdk import DAG, DeadlineAlert
from airflow.sdk.definitions.deadline import DeadlineReference, SyncCallback

REPO_DIR = "/opt/airflow/food-delivery-pipeline"  # same path Day 7 used


def _alert_sla_breach(**context) -> None:

    # state) and log which specific run missed the deadline, instead of this
    # bare print. A real deployment would call Slack/PagerDuty here; printing
    # proves the callback itself genuinely fires, which is the point today.
    print("SLA BREACH: dbt_build has not finished within 30 minutes of its logical date")


with DAG(
    dag_id="raw_files_sensor_demo",
    schedule="@daily",
    start_date=datetime(2026, 9, 21),
    catchup=False,
    deadline=DeadlineAlert(
        reference=DeadlineReference.DAGRUN_LOGICAL_DATE,
        interval=timedelta(minutes=30),
        callback=SyncCallback(_alert_sla_breach),
    ),
) as dag:
    wait_for_raw_files = FileSensor(
        task_id="wait_for_raw_files",
        filepath="/opt/airflow/data/raw/orders.csv",
        poke_interval=30,
        timeout=60 * 60,
        mode="reschedule",
        deferrable=True,
    )

    dbt_build = BashOperator(
        task_id="dbt_build",
        bash_command=f"cd {REPO_DIR}/warehouse && uv run --with 'dbt-postgres==1.11.0' dbt build",
        retries=2,
        retry_delay=timedelta(minutes=5),
    )

    wait_for_raw_files >> dbt_build

Fill in _alert_sla_breach's TODO. The sensor itself needs no edit — mode="reschedule" plus deferrable=True together are what make it cheap to leave running: the task gives up its worker slot both between reschedule attempts and while deferred, waiting on the triggerer instead.

deferrable=True needs a running triggerer process to actually resume the task once its trigger fires — airflow standalone (Day 7's setup) starts one automatically; a hand-assembled scheduler-only deployment would need to run airflow triggerer as its own process. Worth naming in an interview: a deferred task with no triggerer running simply never resumes, which looks identical to a stuck DAG from the UI alone.

5 · The retries this course already has, named precisely

Day 7's own retries=2/retry_delay=timedelta(minutes=5) on dbt_build (glossary Day 7) answers a different question than today's deadline alert: retries re-run a failed task automatically; a deadline alert fires on a task (or run) that is simply late, whether or not it ever fails. A `dbt_build` stuck waiting on a lock isn't failing — it's running, slowly — and no number of retries would ever catch that; only a deadline watching elapsed time does. The two are complementary, not alternatives: this project's real DAG should keep both.

Q: "When would you reach for a deferrable sensor instead of a plain poke-mode one?" A strong answer, out loud: "A plain sensor in poke mode blocks a worker slot the entire time it's waiting — fine for a handful of short waits, expensive at scale, since every waiting sensor ties up a slot doing nothing but sleeping and re-checking. mode='reschedule' helps by giving the slot back between checks, but a worker still has to wake up repeatedly to re-poll. A deferrable operator goes further: it suspends the task completely and hands the actual waiting to a separate triggerer process, which can watch thousands of conditions asynchronously in one lightweight process. I'd reach for deferrable whenever a wait is long or there are many of them running concurrently — exactly the shape of a pipeline waiting on upstream files or an external system's completion, not a two-second check." The signal: naming the worker-slot cost specifically, and the triggerer as the actual mechanism, not just "it's more efficient."
