np.nan_to_num(): replacing NaN AND infinity in one call, with a default that fillna() doesn't share

Lesson 122 closed with several standing candidates from its own fresh scan: np.nan_to_num(), np.take(), np.roll(), np.nonzero()/flatnonzero(), and np.corrcoef(). Today picks np.nan_to_num() — it looks like a plain NumPy cousin of fillna(), but it also silently handles inf/-inf, values fillna() never touches at all, and its default replacement for them is nowhere near zero.

1 · The gap: fillna() only ever sees NaN — infinity is invisible to it

Every missing-value lesson so far (fillna(), ffill()/bfill(), interpolate()) has handled exactly one bad value: NaN. But division and other float math can also produce inf or -inf — a real, non-missing float value that is still unusable in most downstream math (sums, means, and comparisons all break around it). np.nan_to_num(arr) replaces all three in one pass. Confirmed directly (numpy 2.5.4, pandas 3.1.1) that Series.fillna() genuinely does nothing to infinity — it is not a missing value to pandas, so there is nothing for fillna() to find:

import numpy as np
import pandas as pd

arr = np.array([1.0, np.nan, np.inf, -np.inf, 5.0])

pd.Series(arr).fillna(0).to_numpy()
# array([  1.,   0.,  inf, -inf,   5.])  -- only the NaN became 0; BOTH infinities are untouched

To clean infinities in pandas at all, Lesson 65's Series.replace() has to be reached for separately, by name, on top of fillna() — np.nan_to_num() does both jobs unprompted, in the same call, whether or not that is what was wanted.

2 · The trap: the default infinity replacement is not 0 — it's the dtype's max finite value

Confirmed directly against the official NumPy docs, which do spell this one out: np.nan_to_num(arr) defaults NaN to 0.0, same instinct as fillna(0) — but +inf becomes the largest finite number the array's dtype can represent (~1.7977e+308 for float64), and -inf becomes the most negative one. Not zero, not NaN, not a flag value — a huge, "looks like real data" number, documented but very easy to miss:

np.nan_to_num(arr)
# array([ 1.00000000e+000,  0.00000000e+000,  1.79769313e+308,
#        -1.79769313e+308,  5.00000000e+000])
# NaN -> 0.0, as expected -- but inf -> 1.7976931348623157e+308 (float64's own max), not 0 or NaN

np.nan_to_num(arr, nan=-1, posinf=999, neginf=-999)
# array([   1.,   -1.,  999., -999.,    5.])  -- nan=, posinf=, neginf= override all three independently

Confirmed directly: a single unguarded np.nan_to_num(some_ratio_column) on a column that happens to contain a divide-by-zero inf silently plants a ~1.8e308 value into later sums, means, and plots — no exception, no warning, and a number large enough to make every downstream aggregate meaningless, while looking superficially like "it worked." Lesson 60's str.contains NaN trap and Lesson 88's normalize=True trap share this course's running shape: no crash, quietly wrong. Pass nan=/posinf=/neginf= explicitly whenever infinities are a real possibility in the data, rather than trusting the default.

3 · What else differs: dtype preserved, copy= default, and object arrays are a silent no-op

Confirmed directly, three more edges worth knowing. The output dtype matches the input's exactly — a float32 array stays float32, so its own "largest finite value" ceiling is float32's, not float64's. copy=True is the default (a new array back); copy=False mutates and returns the same array object, confirmed via an identity check. And on an object-dtype array (for example one holding a Python None or mixed types rather than a native float array), np.nan_to_num() confirmed directly does nothing at all — no error, no replacement, the NaN passes straight through untouched, since the function's whole fast-path assumes a native float array to operate on:

arr_obj = np.array([1.0, np.nan], dtype=object)
np.nan_to_num(arr_obj)
# array([1.0, nan], dtype=object)  -- the NaN is STILL there; no error, no warning, silent no-op

A DataFrame column pulled out via .to_numpy() on an object dtype column (common after a mixed-type read) hits this exact no-op — confirm the dtype is a real float array first, or the "cleanup" step quietly cleans nothing.

Scope line

This lesson covers np.nan_to_num()'s three-value replacement contract (nan=, posinf=, neginf=), its confirmed default of the dtype's max/min finite float for infinities (documented, not a gap this time), the confirmed fillna()-never-touches-infinity contrast, and the confirmed object-dtype silent no-op. It does not cover complex-dtype arrays (NaN/inf handled separately per real/imaginary component, a documented but rare case for this course's tabular data) nor np.isnan()/np.isinf() as standalone detection functions, which are out of scope until a lesson needs them directly.
