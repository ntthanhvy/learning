Feature flags, now in C# too (FeatureGate, PercentageFilter)

Lesson 70 built a feature flag the hand-rolled way: a FlagSource interface with one Enabled(ctx, flagName, userID) method, an if statement at the call site, and a percentage rollout computed by hashing the user id mod 100 yourself. .NET has a first-party library for exactly this job — Microsoft's own Microsoft.FeatureManagement package, with declarative flag config, an attribute that gates a whole controller with zero if statements, and a percentage rollout filter that ships in the box instead of being hand-hashed.

1 · Same decoupling, declared instead of hand-checked

Lesson 70's point still holds without change: a feature flag separates deploying code from releasing a feature. What's different in .NET is where the if lives. Microsoft.FeatureManagement declares flags in config, not in a hand-written interface:

// appsettings.json
{
  "feature_management": {
    "feature_flags": [
      { "id": "NewCheckout", "enabled": true,
        "conditions": { "client_filters": [
          { "name": "Microsoft.Percentage", "parameters": { "Value": "5" } }
        ] } }
    ]
  }
}

services.AddFeatureManagement() reads this section by convention and registers an IVariantFeatureManager in DI. A handler asks it the same question Lesson 70's FlagSource.Enabled answered:

public class CheckoutController : Controller
{
    private readonly IVariantFeatureManager _featureManager;
    public CheckoutController(IVariantFeatureManager featureManager) => _featureManager = featureManager;

    public async Task<IActionResult> Checkout()
    {
        if (await _featureManager.IsEnabledAsync("NewCheckout"))
            return RunNewCheckout();
        return RunLegacyCheckout();
    }
}

Same shape as Go's flags.Enabled(ctx, "new-checkout-flow", userID) — an async bool check, injected rather than passed as a parameter. The flag's value still lives outside the binary (the JSON file, or a provider like Azure App Configuration sitting behind the same IConfiguration interface), so Lesson 70's "a constant in code is not a flag" rule is unchanged.

2 · [FeatureGate]: the if disappears entirely

.NET's distinct move, with no Go equivalent in Lesson 70's version: the Microsoft.FeatureManagement.Mvc package's [FeatureGate] attribute can gate an entire controller or action without any if inside the handler body at all:

[FeatureGate("NewCheckout")]
public class NewCheckoutController : Controller
{
    public IActionResult Index() => View();
}

When NewCheckout is off, ASP.NET Core's MVC pipeline rejects the request before the action method runs — a 404 by default, configurable to another status code — rather than the action running and immediately branching into an else. This is a structural difference, not cosmetic: Lesson 70's "flag debt" problem (an old flag's dead branch still sitting in the handler, forcing every reader to hold both paths in mind) can't happen the same way when the gate lives on the controller declaration instead of inside its body. Removing the flag later means deleting one attribute line and, eventually, the controller that's now unconditionally on — not untangling an if/else first.

Frontend-habit trap: [FeatureGate] looks like a route guard — a Vue/Angular route-level check that redirects before a component ever mounts. The comparison holds structurally (both reject at the boundary, before any body code runs) but the enforcement point differs: a frontend route guard is advisory, since a user can still call the underlying API directly; [FeatureGate] runs server-side in the same pipeline that serves the API itself, so there's no bypass route for a client to find.

3 · The percentage rollout: shipped, not hand-hashed

Lesson 70 section 3 built a percentage rollout by hand: hash a stable user id, reduce mod 100, compare against a threshold. Microsoft.FeatureManagement ships this as a filter instead of code to write: PercentageFilter is one of several built-in feature filters (alongside TimeWindowFilter) that are added automatically the moment AddFeatureManagement() runs — no extra registration, unlike the fourth built-in filter below. The appsettings.json snippet in section 1 already used it ("Microsoft.Percentage", Value: "5") — that's the entire 5% rollout from Lesson 70's worked example, with no hashing code anywhere in the application.

The one built-in filter that needs an extra line is TargetingFilter, registered with services.AddFeatureManagement().WithTargeting<MyTargetingContextAccessor>() — it evaluates a flag against a specific user id or named group (e.g. "beta testers") pulled from an ITargetingContextAccessor implementation, rather than a flat percentage of all traffic. Lesson 70's hashed-percentage rollout and .NET's TargetingFilter solve related but distinct problems: percentage rollout answers "how much traffic," targeting answers "which specific users," and a real system often wants both — requirement_type: "All" in the flag's conditions combines filters with AND logic, so a flag can require both a targeting match and a percentage roll in the same evaluation.

4 · What's unchanged, and what a flag never replaces

Lesson 70's kill-switch framing and flag-debt warning both carry over untouched — a flag whose job is "disable this path immediately in production" is exactly as valuable declared in appsettings.json as it was behind a hand-written FlagSource, and a [FeatureGate]'d controller nobody ever removes is still permanent complexity, just one attribute line instead of one dead if branch. Likewise unchanged: a feature flag is still a deploy-time risk knob a human moves on purpose, never a runtime defense that trips itself the way Lesson 28's circuit breaker does — Microsoft.FeatureManagement doesn't change who decides to widen a rollout, only how much hand-written code that decision costs to wire up.

Q: "We're building an ASP.NET Core service and want to roll out a risky change to 5% of users first. Do we need to build our own flag system?" A strong answer, out loud: "No — Microsoft.FeatureManagement already covers this. I'd declare the flag in config with the built-in Microsoft.Percentage filter at 5%, which needs no custom hashing code, and check it via IVariantFeatureManager.IsEnabledAsync, or gate the whole controller with [FeatureGate] if I want the rejected path to never even enter the action method. If we later need to target specific beta users instead of a flat percentage, TargetingFilter covers that too, with one extra WithTargeting() registration. What the library doesn't give us for free is discipline — we still need to decide, on paper, when the flag gets removed once it's fully rolled out, the same flag-debt risk as any hand-rolled version." The signal: knowing which parts the framework gives for free (the filter math, the attribute-level gate) versus which parts stay a team process problem no library solves (removing old flags).

Scope line

This lesson covers IVariantFeatureManager.IsEnabledAsync, services.AddFeatureManagement(), the [FeatureGate] attribute, and the built-in Microsoft.Percentage/TargetingFilter feature filters. It does not cover variants (the library's mechanism for returning more than a plain on/off value from one flag), telemetry emission for flag evaluations, dynamic feature providers backed by a database rather than appsettings.json, or Azure App Configuration's hosted flag management service — all named once in Microsoft's own docs but out of scope for a 20-minute concept lesson per this course's "concepts first" rule.
