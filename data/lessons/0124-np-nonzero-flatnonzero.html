np.nonzero() and np.flatnonzero(): finding WHERE, and a tuple that is always truthy

Lesson 123 closed with four standing candidates from Lesson 122's own fresh scan: np.take(), np.roll(), np.nonzero()/flatnonzero(), and np.corrcoef(). Today picks np.nonzero() and its simpler cousin np.flatnonzero() — both answer "which positions are non-zero," the raw-array layer under every boolean-mask trick this course has used since Lesson 22's query(), but np.nonzero()'s own return shape hides a genuine, confirmed correctness bug: the result is truthy in an if check even when nothing matched at all.

1 · The gap: boolean masks answer "which rows," but as a mask, not as positions

Every filter this course has written so far — df[mask], Series.isin(), query() — returns rows still shaped like the original table, found through a True/False mask. Sometimes what's actually wanted is the raw integer positions where a condition held, not a same-shaped mask or a filtered table. That is exactly what np.nonzero(arr) gives: not a mask, not filtered values, but the index positions themselves. Confirmed directly (numpy 2.5.4, pandas 3.1.1):

import numpy as np
import pandas as pd

arr = np.array([0, 5, 0, -3, 0, 8])

np.nonzero(arr)
# (array([1, 3, 5]),)  -- a ONE-ELEMENT TUPLE holding the index array, not the array itself

arr[np.nonzero(arr)]
# array([ 5, -3,  8])  -- using the tuple result to index straight back into the original array

ser = pd.Series(arr)
ser.index[(ser != 0).to_numpy()]
# Index([1, 3, 5])  -- the pandas-world equivalent: mask first, then ask the Index for positions

Same question Lesson 22's query() and Lesson 29's isin() answer with a mask, answered here as plain integer positions instead — the raw-array primitive this course's "name the NumPy function underneath an already-taught idiom" lineage has traced since Lessons 93, 100, 102, 109-112, 114, and 117-123.

2 · The trap: the tuple is always truthy, even when nothing matched

Confirmed directly (numpy 2.5.4) — not mentioned anywhere on the official docs page: np.nonzero(arr) always returns a tuple with exactly one element per dimension — for a 1-D array, always a 1-element tuple, whether or not any value actually matched. Python's truthiness of a tuple checks the tuple's own length, not what's inside it, so bool(np.nonzero(arr)) is True for every 1-D array, including one with zero matches at all:

all_zero = np.array([0, 0, 0])

result = np.nonzero(all_zero)
# (array([], dtype=int64),)  -- a 1-element tuple holding an EMPTY array; nothing matched

bool(result)
# True  -- the tuple itself has length 1, so it is truthy, regardless of the empty array inside it

if np.nonzero(all_zero):
    print("found a match")  # this line DOES run -- on an all-zero array, with zero real matches

A direct if np.nonzero(arr): guard, written by analogy with "an empty list/array is falsy," silently always takes the truthy branch — it is testing the wrong thing (a tuple's length, always 1 for a 1-D array) instead of the actual count of matches. This course's familiar "no crash, quietly wrong" shape (Lessons 19-29, 36, 60, 88, 122, 123): no exception, no warning, just the always-wrong branch. The real "how many matched" question has its own named function, np.count_nonzero(arr), confirmed directly to return the plain integer count (0 for the all-zero case above) — reach for that, or arr.any(), never a bare truth test on np.nonzero()'s own return value.

3 · The simpler cousin: np.flatnonzero(), and NaN counts as "non-zero" too

Confirmed directly, np.flatnonzero(arr) sidesteps the whole tuple trap: it returns one flat array directly, not a tuple, so len(), slicing, and truthiness on an empty result all behave as expected (though an empty array's own truthiness still raises ValueError rather than reading as False — confirmed directly, so .size or len() is still the right check, not a bare if):

np.flatnonzero(arr)
# array([1, 3, 5])  -- same three positions as np.nonzero(arr)[0], but as a plain array, no tuple wrapper

np.flatnonzero(all_zero)
# array([], dtype=int64)  -- empty array directly, no tuple wrapping it

len(np.flatnonzero(all_zero))
# 0  -- the correct count, straight from len(), no count_nonzero() needed for a 1-D array

On a 2-D array the two diverge on purpose: np.nonzero(arr2d) returns a 2-element tuple (row positions, column positions) ready to index back into the original shape, while np.flatnonzero(arr2d) returns positions into the flattened 1-D version instead — confirmed directly, np.nonzero is the one to reach for whenever the original shape still matters. One more confirmed trap both functions share equally: NaN has a non-zero bit pattern, so a NaN value counts as "non-zero" and is included in the result — "non-zero" means literally "not equal to the number 0," not "not missing," confirmed directly and confirmed absent from the official docs page as well:

arr_nan = np.array([0.0, np.nan, 1.0, 0.0])

np.flatnonzero(arr_nan)
# array([1, 2])  -- the NaN at position 1 IS included, right alongside the real 1.0 at position 2

Scope line

This lesson covers np.nonzero()'s confirmed tuple-of-arrays return shape and its confirmed always-truthy-tuple trap, np.flatnonzero() as its flat-array cousin and their confirmed 2-D divergence, np.count_nonzero() as the correct "how many" function, and the confirmed NaN-counts-as-non-zero behavior both share. It does not cover ndarray.nonzero() as an equivalent instance method (confirmed identical to the function form, mentioned only in passing) nor np.argwhere(), a closely related function returning positions as row-per-match coordinates instead of a per-dimension tuple — out of scope until a lesson needs that exact shape.
