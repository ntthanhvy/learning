traceback: capturing failure as text

Day 8 named the traceback as the report Python prints when an exception goes uncaught, and Day 15's logging used exc_info=True to attach one to a log record without ever seeing what that call does underneath. The traceback module is that underneath: it builds the exact same report on demand, inside a running except block, as a str a pipeline can log, save, or inspect — instead of losing it the instant the block moves on.

1 · The problem: an except block that only logs a message throws the detail away

Day 8 taught catching an exception narrowly. A common next step in a real pipeline is: don't crash the whole batch over one bad record — catch it, note the failure, and keep going. But a plain message loses exactly the detail needed to debug it later:

records = ["10", "20", "oops", "40"]
good, bad = [], []

for r in records:
    try:
        good.append(int(r))
    except ValueError as e:
        bad.append({"record": r, "error": str(e)})
# bad[0]["error"] == "invalid literal for int() with base 10: 'oops'"
# -- true, but it has no idea which function or line raised it

str(e) gives the exception's own message — useful, but it says nothing about where in the call chain the failure happened, which matters the moment the real parsing logic is more than one line deep.

2 · format_exc(): the full traceback, as a str

traceback.format_exc() called inside an active except block returns the exact text Python would have printed had nothing caught the exception — type, message, and the full chain of calls — as one ordinary string:

import traceback

for r in records:
    try:
        good.append(int(r))
    except ValueError:
        bad.append({"record": r, "error": traceback.format_exc()})

print(bad[0]["error"])
# Traceback (most recent call last):
#   File "pipeline.py", line 5, in <module>
#     good.append(int(r))
# ValueError: invalid literal for int() with base 10: 'oops'

That string is just data now — appendable to a list, writable to a file, insertable into a database column — the same shift Day 76's json.dumps() made for Python objects, applied here to a failure report. Because it returns a plain str, nothing stops a pipeline from keeping full failure detail for every bad record in one batch instead of only the last one Python happened to print.

One sharp edge: format_exc() only has something real to report while an exception is actively being handled. Called with no exception in flight, it returns the harmless-looking string "NoneType: None\n" instead of raising an error to flag the mistake — confirmed live. It belongs inside an except block, never outside one.

3 · print_exc(): the same report, written out directly

When the goal is simply to see the traceback rather than store it, traceback.print_exc() skips the string step and writes the report straight out — to stderr by default, the same stream an uncaught exception's own traceback goes to:

try:
    1 / 0
except ZeroDivisionError:
    traceback.print_exc()   # prints the full traceback to stderr, keeps running
print("still running")   # this line still executes -- the exception was caught

A file= keyword redirects it anywhere else a real file object can go — including Day 81's io.StringIO, which turns print_exc() back into exactly format_exc()'s string, just written instead of returned:

import io

buf = io.StringIO()
try:
    1 / 0
except ZeroDivisionError:
    traceback.print_exc(file=buf)

print(buf.getvalue().splitlines()[-1])   # ZeroDivisionError: division by zero -- confirmed live

This is the same job Day 15's logger.error(msg, exc_info=True) already does under the hood — logging calls this exact module to render the traceback text it attaches to a log record. Reach for logging directly when a logger is already set up; reach for traceback itself when the text needs to be stored, emailed, or inspected some other way a log record doesn't fit.

Where pandas/NumPy go from here: nothing library-specific today — capturing a traceback as text is a plain-Python exception-handling detail with no connection to a DataFrame or array; this stays entirely in stdlib territory, per MISSION.md.
