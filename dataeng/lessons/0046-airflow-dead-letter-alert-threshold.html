2 · The gap: a count with no judgment is not an alert

Day 45's stub printed one fixed string regardless of what Day 41's table actually held — zero rows or five hundred rows produced identical output. That's indistinguishable from a health check that was never wired to real data at all. A dead-letter table existing (Day 41) and something running after every build regardless of outcome (Day 45's all_done rule) are both necessary and neither is sufficient: the task still has to look at the actual number and decide whether it's fine. "Fine" here is simple, on purpose, for a single-operator portfolio pipeline with no real on-call rotation behind it: a handful of dead-lettered events sitting around between runs is expected — Day 41's own poison-message test plants a couple on purpose — but a pile climbing past a small fixed ceiling means something upstream is producing bad events continuously, not occasionally, and that is worth failing a task over.

This is not Day 25's territory. Day 25 covered SLAs and deadline alerting — a task or DAG run taking too long. Today is a data-quality threshold on a count a task itself computes, the same shape as Day 3's planted-bad-row tests but expressed as a live Airflow check instead of a dbt build failure. Both end the same way — a task goes red — for different reasons.

3 · Build: a real query and a alert threshold, replacing Day 45's stub

In your food-delivery-pipeline repo, edit dags/food_delivery_pipeline.py — the same file Day 7 wrote, Day 35 and Day 45 each added one thing to. Only check_dead_letters's body changes:

# new constant, module level, alongside the existing PG_DSN
DEAD_LETTER_ALERT_THRESHOLD = 5  # more than this between checks is a real upstream problem, not noise


def check_dead_letters(**context) -> None:
    import psycopg

    with psycopg.connect(PG_DSN) as conn, conn.cursor() as cur:
        cur.execute("SELECT count(*) FROM raw.dead_letter_events")
        count = cur.fetchone()[0]

    if count > DEAD_LETTER_ALERT_THRESHOLD:
        # Raising fails this task visibly in the UI and in `airflow dags test`'s
        # own output -- a human (or a future on_failure_callback, Day 35's
        # mechanism) has something concrete to act on instead of a silent log line.
        raise ValueError(
            f"dead-letter count {count} exceeds threshold {DEAD_LETTER_ALERT_THRESHOLD}"
        )

    print(f"checked raw.dead_letter_events: {count} row(s), within threshold")

Nothing about trigger_rule=TriggerRule.ALL_DONE changes — Day 45 already set that correctly, and it's still the reason this task runs at all on a failed dbt_build. Today's only job is giving the task body something real to decide with: query, compare, raise or don't.

Two choices worth defending out loud, because a plausible-looking first draft gets both wrong in ways that still parse. First, count > DEAD_LETTER_ALERT_THRESHOLD, not >=: the threshold is meant to read as "this many is still fine," so a count exactly at the limit should pass, not fail — an off-by-one here silently tightens the threshold by one without anyone choosing that. Second, the query counts every row in the table, not just rows since the last check. That's a deliberate simplification, not an oversight: Day 41's table has no "already seen" marker column, so today's check is a running total, not a per-run delta — it will alert exactly once, stay alerting on every run after until the dead-lettered rows are cleared or investigated, and that's named honestly here as a real limitation rather than implied as a windowed count it isn't.

Q: "Walk me through a monitoring check you built for your pipeline. Why does it fail sometimes, and is that a bug?" A strong answer, out loud: "After dbt build runs, no matter whether it passed or failed — I set trigger_rule=all_done for that — a task counts rows in a dead-letter table my Kafka consumer writes poison messages into. A couple of dead-lettered rows between checks is expected and fine, so the task only fails above a small fixed threshold, which turns a routine log line into a visible, actionable Airflow failure exactly when there's a real pattern of bad events, not a one-off. It's a running total, not a per-run delta, since the table has no seen-already marker — so once it trips, it keeps failing every run until someone clears or fixes the underlying cause, which is a real, named limitation, not a hidden one." The signal: stating the threshold's off-by-one direction and the running-total-not-delta limitation without being asked, not just "it checks a count."
