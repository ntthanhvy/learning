logging

Day 8 taught catching exceptions narrowly instead of letting them crash the program. But a caught exception that vanishes silently is its own bug — nobody finds out it happened until a customer complains. Today's module is how real programs keep a permanent, filterable record of what happened, including the failures Day 8 already knows how to catch. This closes out Phase 2a's last spine bullet, alongside Day 13's pathlib and Day 14's datetime/timezones, and is the third of the "most-used stdlib corners" trio.

Bridge from SQL: think of a busy production database — nobody tails a live SELECT stream to know if something broke; they check a log table of statement failures, each one stamped with a severity and a timestamp, and query it after the fact ordered by time or filtered by severity. Python's logging module is that log table for a running program: every entry gets a severity level, a timestamp, and a source, and can be filtered or routed without touching the code that produced it.

1 · Why print() isn't enough

print() has done fine as a debugging tool all course, but it breaks down the moment code needs to run unattended: a print() statement has no severity (a routine status line looks identical to "the database is unreachable"), always goes to the same place (there's no separating "warnings only" from "everything"), and can't be turned off per-module without deleting or commenting out every call. The standard library's logging module exists to fix exactly these three gaps at once.

2 · Levels: severity, not just text

Every log call carries a level, one of five standard names in increasing severity:

import logging

logging.debug("opened connection pool")     # fine-grained detail, dev only
logging.info("loaded 42 rows")             # routine, expected events
logging.warning("row 17 missing a currency")  # unexpected but recoverable
logging.error("could not write output file") # a real failure
logging.critical("database unreachable")    # the program likely can't continue

A level isn't decoration — it's the filter. Tell the logging system "only show me WARNING and above" and every debug()/info() call goes silent without deleting a single line of code, the exact per-module on/off switch print() can't give you.

3 · Logger, handler, formatter: who does what

Three objects cooperate on every log call, and keeping their jobs separate is the one idea this lesson spends most of its time on:

import logging

logger = logging.getLogger(__name__)      # 1. the logger — the thing your code calls
handler = logging.StreamHandler()         # 2. the handler — where records go
formatter = logging.Formatter(            # 3. the formatter — how a record renders
    "%(asctime)s %(levelname)s %(name)s: %(message)s"
)
handler.setFormatter(formatter)
logger.addHandler(handler)
logger.setLevel(logging.INFO)

logger.info("pipeline started")
# 2026-08-12 09:00:00,123 INFO __main__: pipeline started

A logger is what application code actually calls — created with logging.getLogger(name), almost always __name__ so the logger's name matches Day 9's module name exactly, making it obvious which file produced a given line. A handler owns the destination — a console stream, a file, or elsewhere — and a single logger can have several handlers, sending the same record to more than one place at once. A formatter owns how a record renders as text — attached to the handler, not the logger, so the exact same call can print two different-looking lines through two different handlers. Splitting these three jobs is what lets one logger.info(...) call end up on the console *and* in a file, formatted differently for each, with zero change to the calling code.

4 · basicConfig: the one-call setup for a script

Wiring a logger, handler, and formatter by hand every time is more than most scripts need. logging.basicConfig(...) does the same three-step setup from section 3 in one call, applied to the shared root logger every other logger reports up to by default:

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(name)s: %(message)s",
)

logger = logging.getLogger(__name__)
logger.info("pipeline started")
logger.warning("row 17 missing a currency")

basicConfig() must run once, before the first log call, and only the first call in a process has any effect — later calls are silently ignored, which is the standard-library's way of keeping one script's setup from clobbering another module's. This is the right tool for a single script; section 3's manual wiring is what a library module reaches for so it never forces its own format choices onto the program importing it.

5 · Logging a caught exception

This is where Day 8 and today meet. A narrow except block that swallows an error silently is exactly the kind of bug this course has warned against since Day 8 — the fix isn't to stop catching narrowly, it's to log inside the block before moving on:

logger = logging.getLogger(__name__)

def safe_int(text):
    try:
        return int(text)
    except ValueError:
        logger.error("could not parse %r as an int", text, exc_info=True)
        return None

exc_info=True tells the handler to attach the full traceback under the log line, the same traceback an uncaught exception would have printed — so the failure is still fully visible, just captured instead of crashing the program. Note the message uses %r with text passed as a separate argument rather than an f-string: logging only builds the final string if the record actually clears its handler's level, so an expensive-to-format DEBUG message costs nothing when DEBUG output is filtered out — an f-string would already have paid that cost before logging ever saw it.

Where pandas goes from here: pandas pipelines still log through this exact same stdlib module — there's no separate "pandas logging" — so everything here carries over directly once data/ pipelines get real, unattended.
