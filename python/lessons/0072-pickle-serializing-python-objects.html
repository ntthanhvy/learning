pickle: serializing Python objects

Day 6's json module round-trips dicts, lists, strings, and numbers to text — but a dataclass instance, a set, or a datetime all fail with TypeError: Object of type ... is not JSON serializable. The standard-library pickle module round-trips almost any Python object, by writing Python's own binary representation instead of text — at the cost of being Python-only, and dangerous to use on data you don't trust.

Why today, specifically: a fresh-gap grep across all 71 lessons and every practice file confirmed pickle has never been taught, despite being named as a standing candidate since Day 70's note. Of the other open candidates, configparser remains narrower work pathlib/plain dicts already cover, uuid is too thin alone for a full lesson, and concurrent.futures/threading sits closer to MISSION.md's explicit concurrency boundary than to data or backend work. pickle wins because it closes a real, concrete gap left wide open since Day 6: Day 7's own capstone builds a dataclass record, and nothing in the course has ever shown how to save one to disk and load it back, since json.dump cannot handle it directly.

1 · The gap: json can't hold a dataclass, a set, or a datetime

Try handing json.dump something Day 7's capstone already builds every day — a dataclass instance:

import json
from dataclasses import dataclass

@dataclass
class Order:
    city: str
    amount: float

order = Order("Hanoi", 120.0)
json.dumps(order)   # TypeError: Object of type Order is not JSON serializable

json only knows how to write the handful of types its format defines — strings, numbers, booleans, None, lists, and dicts of those. A dataclass instance, a set, a datetime, or a trained lookup structure built by hand are all invisible to it; writing one out means hand-converting it to a plain dict first (and remembering how to convert it back).

2 · pickle.dumps()/loads(): Python's own binary format

The pickle module instead writes Python's own internal representation of an object, as bytes, and can rebuild the exact same object from those bytes later — no hand-conversion required, because it isn't limited to a fixed set of types:

import pickle
from dataclasses import dataclass

@dataclass
class Order:
    city: str
    amount: float

order = Order("Hanoi", 120.0)

data = pickle.dumps(order)     # bytes -- Python's own binary format, not text
restored = pickle.loads(data)  # a brand-new Order, equal to the original

restored == order               # True
restored is order               # False -- a genuinely new object, not the same one

dumps() ("dump to a string of bytes") and loads() ("load from a string of bytes") mirror json.dumps()/json.loads() by name on purpose — same shape, different format underneath. A set, a datetime, or a nested mix of custom classes all round-trip the same way, with no extra code, because pickle is not reading a fixed text grammar — it is walking Python's own object structure directly.

3 · Writing to and reading from a file: dump()/load()

Just like json, pickle has a second pair of functions for an already-open file object instead of in-memory bytes — and the file must be opened in binary mode ("wb"/"rb"), since pickled data is bytes, not text:

import pickle

orders = [Order("Hanoi", 120.0), Order("Hue", 75.5)]

with open("orders.pkl", "wb") as f:   # "wb" -- write BINARY, not "w"
    pickle.dump(orders, f)

with open("orders.pkl", "rb") as f:   # "rb" -- read BINARY, not "r"
    restored = pickle.load(f)

restored == orders   # True -- the whole list of dataclass instances, back intact

Opening a pickle file with plain "w"/"r" instead of "wb"/"rb" is the most common first mistake — text mode tries to decode the bytes as a string and either raises a UnicodeDecodeError or corrupts the data. Day 6's with block is unchanged; only the mode string and the pair of functions differ from a json round trip.

Bridge from SQL: this is the same shape as storing a serialized blob in a BYTEA/BLOB column instead of normalized columns — convenient for an opaque payload you'll only ever read back in the same application, wrong the moment another system needs to query the fields inside it.

4 · Why not to pickle.load() data you don't trust

Unpickling is not just reading data back — it can execute arbitrary code. Rebuilding an object can call that class's own methods during construction, and a maliciously crafted pickle byte string can abuse that to run arbitrary code the instant pickle.load() touches it — there is no equivalent risk in parsing JSON text, which only ever produces the fixed handful of safe built-in types from section 1. The standard library's own documentation states this plainly: never unpickle data received from an untrusted or unauthenticated source.

The rule in practice: pickle is the right tool for a program's own cache, checkpoint, or scratch file — data it wrote itself and is reading back later, on the same trusted machine. It is the wrong tool the moment the bytes might have come from a network request, a file upload, or any other party you don't fully control; json (Day 6) is the safe default for anything crossing that boundary, which is also why JSON, not pickle, is the universal format for APIs.

Where pandas goes from here: a DataFrame has its own .to_pickle()/pd.read_pickle() methods, built on this same stdlib module, for caching a whole table faster than re-parsing a CSV each run — not demonstrated here; that choice belongs to data/.
