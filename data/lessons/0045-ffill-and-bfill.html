ffill() and bfill(): carrying a value across a gap

Lesson 3 taught three moves for missing data: drop, fill with a constant/median, or flag. Today adds a fourth fill strategy Lesson 3 deliberately left out — filling a gap with the nearest real value in row order instead of a computed constant. It's the move interviewers expect for time-series-shaped gaps (a sensor reading, a daily balance, a status column) where "the last known value" is a far more honest guess than a median ever is.

Recap, in one line

Lesson 3's fillna(value) always uses the same value for every gap, computed once up front (a median, a zero, a string). Today's tools instead look at each gap's neighbors in the current row order and copy one of those — a fundamentally different kind of fill, and one that inherits the same "trusts row order only" warning this course has given cumsum(), shift(), and rolling() before.

1 · ffill(): carry the last known value forward

ffill() replaces each NaN with the closest real value sitting above it:

s = pd.Series([120.0, None, 35.5, None, 180.0])
s.ffill()
-- 0    120.0
-- 1    120.0   <- carried down from row 0
-- 2     35.5
-- 3     35.5   <- carried down from row 2
-- 4    180.0

Each fill is a genuinely different number depending on where the gap sits — nothing like fillna(median)'s one constant everywhere. That's the entire pitch: for a "status as of now" or "last known reading" column, the truth actually is whatever the last real observation was, and a flat median would be a worse guess, not a safer one.

2 · bfill(): carry the next known value backward

bfill() is the mirror image — it looks downward instead of upward:

s.bfill()
-- 0    120.0
-- 1     35.5   <- pulled up from row 2
-- 2     35.5
-- 3    180.0   <- pulled up from row 4
-- 4    180.0

Row 1 differs between the two calls (120.0 via ffill vs 35.5 via bfill) — same gap, opposite direction, genuinely different answer. Neither is "more correct" in the abstract; the choice depends on what the gap actually means (was this value not yet recorded, or did recording stop?).

Gotcha — an edge gap stays NaN, no error: ffill() can't fill a leading NaN (nothing above it); bfill() can't fill a trailing one (nothing below it) — both silently leave that value as NaN rather than raising: 
pd.Series([None, 10.0, None, 20.0]).ffill()
-- 0     NaN   <- still NaN, nothing above row 0 to carry
-- 1    10.0
-- 2    10.0
-- 3    20.0
Always check .isna().sum() after an ffill/bfill pass — a table that starts (or ends) with a real gap won't be fully filled, and nothing announces that.

3 · The groupby gotcha: ffill() bleeds across group boundaries

Like cumsum(), shift(), and rolling() before it, plain ffill() only looks at physical row position — it has no idea one customer's rows just ended and another's just began. Run it on the whole table ungrouped, and a value can leak from the wrong customer entirely:

-- clean, sorted by customer then order_date -- Binh's FIRST row is missing:
--   customer order_date  amount
-- 0       An 2026-01-05   120.0
-- 1       An 2026-01-10    42.0
-- 2     Binh 2026-01-06     NaN   <- Binh's own first value, genuinely unknown
-- 3     Binh 2026-01-09   180.0
clean["amount"].ffill()
-- 0    120.0
-- 1     42.0
-- 2     42.0   <- WRONG: An's amount, not Binh's -- no error, just quietly wrong
-- 3    180.0

clean.groupby("customer")["amount"].ffill()
-- 0    120.0
-- 1     42.0
-- 2      NaN   <- correct: Binh has no earlier row of her own to carry from
-- 3    180.0

The fix is the same shape as every prior lesson in this "trusts row order only" family: sort correctly first, then chain groupby(key) before the fill so each group's gaps only ever look at that same group's own rows.

Q: "A time-ordered column has some missing values. When would you reach for ffill() instead of Lesson 3's median fill?" A strong answer, out loud: "It depends what 'missing' means for that column. A median fill assumes the true value is somewhere near the column's typical value, which is reasonable for something like a one-off missing order amount. But for a 'status as of right now' or 'last sensor reading' kind of column, the honest guess isn't the median — it's whatever the last real observation was, which is exactly what ffill() gives you. The two gotchas I'd flag unprompted: an edge gap with nothing to carry from stays NaN silently, so I always check isna().sum() after; and ffill() only looks at physical row position, so on a multi-entity table I have to sort correctly and chain groupby() first, or a value can quietly bleed from the wrong group with no error at all." The signal: naming the row-order dependency and the groupby fix without being prompted, the same reflex this course has built for cumsum()/shift()/rolling().

4 · limit=, and the retired fillna(method=) spelling

limit= caps how many consecutive gaps a single real value is allowed to fill, so a fill doesn't quietly paper over an unreasonably long stretch of missing data:

pd.Series([1.0, None, None, None, 5.0]).ffill()
-- [1.0, 1.0, 1.0, 1.0, 5.0]   <- one real value propped up 3 rows
pd.Series([1.0, None, None, None, 5.0]).ffill(limit=1)
-- [1.0, 1.0, NaN, NaN, 5.0]   <- only the FIRST gap gets filled, the rest stay NaN

One outdated spelling worth flagging directly, confirmed on this course's actually-installed pandas 3.0.5: older tutorials/Stack Overflow answers write fillna(method="ffill"). That keyword-argument form has been fully removed — it now raises TypeError: NDFrame.fillna() got an unexpected keyword argument 'method', not a deprecation warning. .ffill()/.bfill() as their own methods (used throughout this lesson) are the only current spelling.

5 · The SQL bridge

Plain SQL has no single built-in for "carry the last non-null value forward" — it needs a window function reaching back through prior rows:

-- Postgres/most engines: no direct LAG(), need the LAST non-null via a
-- window frame trick (a "last value ignore nulls" pattern):
-- SELECT *,
--   COALESCE(amount, MAX(amount) OVER (
--     PARTITION BY customer ORDER BY order_date
--     ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
--   )) AS amount_ffill
-- FROM orders;
-- (works here only because amount is never NaN-and-also-zero in a way
--  that would confuse the aggregate -- real ffill SQL patterns get messier)
clean.groupby("customer")["amount"].ffill()
-- one call, same intent, no window-frame gymnastics

This is a case where pandas is genuinely more concise than SQL, not just a different spelling of the same idea — worth naming directly if it comes up.
