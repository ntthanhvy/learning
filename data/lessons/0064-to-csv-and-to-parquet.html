to_csv() and to_parquet(): the ETL Load step, and its silent traps

Lesson 63's teaser named this round's candidate: the ETL "output" stage, flagged uncovered back in Lesson 8's to_csv/to_sql aside but never taught on its own. Confirmed still a real gap: grepped every lesson and the glossary for to_csv|to_parquet|index=False and found only that one passing mention. Today closes it — not the happy path (that's one line), but the three silent traps that bite the first time someone writes real output: the default extra index column, dtype loss on the CSV round-trip, and a header/append mistake that corrupts a whole column's dtype with zero errors.

1 · Where Load sits, and why it isn't "just one line"

Lesson 8 named the shape: Extract (read_csv) → Transform (everything since) → Load, writing the finished result to its destination. The methods themselves are short — df.to_csv(path), df.to_parquet(path) — which is exactly why this stage gets skipped over in practice: it looks too simple to have gotchas. It has three, and every one of them is silent — no exception, no warning, just a file that looks fine until something reads it back wrong.

2 · SQL bridge

to_csv() is the pandas equivalent of COPY table TO 'file.csv' WITH CSV HEADER (or \copy in psql) — dumping query results to a flat file. There's no SQL-standard equivalent for to_parquet(); the closer parallel is a warehouse's native columnar export (Postgres has no built-in Parquet writer at all — that's normally an external tool like pg_parquet or a Spark/dbt job). The gap matters: SQL people reach for CSV by reflex because it's what COPY gives them, but pandas makes Parquet just as easy to write, and it avoids every trap below.

3 · The first trap: to_csv()'s default writes an extra column

to_csv() defaults to index=True — it writes the row index as its own unnamed leading column, every single time, unless told otherwise:

df = pd.DataFrame({"a": [1, 2], "b": ["x", "y"]})
df.to_csv("out.csv")             # default index=True
-- ,a,b
-- 0,1,x
-- 1,2,y

pd.read_csv("out.csv").columns.tolist()
-- ['Unnamed: 0', 'a', 'b']   <- the index came back as a REAL data column

df.to_csv("out2.csv", index=False)   # the fix
-- a,b
-- 1,x
-- 2,y

Confirmed directly (pandas 3.0.5): Unnamed: 0 is not a warning label — it's a plain, usable-looking column name, so a careless downstream read_csv() just quietly gains a junk column instead of erroring. index=False is correct almost every time the index is the default RangeIndex (0, 1, 2…) rather than something meaningful, like a set_index() key worth keeping.

4 · The second trap: CSV has no dtype memory

A CSV file is plain text — every value round-trips as a string on disk, with no column-type header of any kind. read_csv() re-guesses each column's dtype from scratch on the way back in, and that guess is not always the original dtype:

df2 = pd.DataFrame({
    "order_id": [1, 2, 3],
    "order_date": pd.to_datetime(["2026-01-05", "2026-01-06", "2026-01-07"]),
    "amount": [120.0, 35.5, 99.9],
})
df2.dtypes
-- order_id        int64
-- order_date    datetime64[us]   <- a real datetime dtype
-- amount        float64

df2.to_csv("dates.csv", index=False)
pd.read_csv("dates.csv").dtypes
-- order_id        int64
-- order_date        str          <- SILENTLY demoted -- just text now
-- amount        float64

pd.read_csv("dates.csv", parse_dates=["order_date"]).dtypes
-- order_date    datetime64[us]   <- back to normal, but only because we asked again

Confirmed directly: no error, no warning — order_date just becomes a plain str column, and every .dt accessor call on it would now fail (Lesson 39's whole toolkit gone) until parse_dates= is passed again on read, re-declaring something the DataFrame already knew before it was written. The same blind spot applies to category dtype (Lesson 25/62) and nullable Int64/StringDtype (Lesson 41) — CSV forgets all of it, every time.

The fix: to_parquet(). to_parquet() writes a binary columnar format that stores each column's dtype alongside the data. Confirmed directly: df2.to_parquet("dates.parquet") then pd.read_parquet("dates.parquet") restores every dtype exactly — order_date comes back datetime64[us] with no parse_dates= needed, and pd.read_parquet(...).equals(df2) is True. It needs the optional pyarrow package (uv run --with pandas --with pyarrow), not part of a plain pandas install, and it isn't human-readable — the standard trade for an interview answer: CSV for a small file a human or another tool needs to open directly, Parquet for anything staying inside a data pipeline where dtype fidelity and file size (columnar + compressed) matter more.

5 · The third trap: appending without turning the header off

Writing output in batches means calling to_csv() more than once with mode="a" (append). header= still defaults to True on every call — including the second one — and nothing stops it from writing the column names again as a literal data row in the middle of the file:

df.to_csv("log.csv", index=False)                      # first batch
df.to_csv("log.csv", mode="a", index=False)          # second batch -- header=True by DEFAULT, still!
-- a,b
-- 1,x
-- 2,y
-- a,b        <- the header text, written again, as a DATA row this time
-- 1,x
-- 2,y

pd.read_csv("log.csv").dtypes
-- a    str    <- WRONG: whole column silently demoted from int64 to str
-- b    str       because "a"/"b" text is mixed into the numbers now

Confirmed directly (pandas 3.0.5): this raises nothing — the file parses fine, row count is simply larger than expected by one junk row per append, and the numeric column's dtype quietly becomes str because a text value now lives inside it. The fix is one keyword on every call after the first: header=False. This is the append-equivalent of Lesson 62's astype("int8") wraparound — a wrong-looking-but-plausible result with no error to catch it.

Q: "You're writing a cleaned DataFrame out to a file for the next pipeline stage to read. Walk me through it." A strong answer, out loud: "First question is the destination: is this a one-off a human or another tool opens directly, or does it stay inside a pipeline? For the former I'd use to_csv() with index=False explicitly — the default writes the row index as an unnamed extra column, which comes back on the next read_csv() as a real 'Unnamed: 0' column instead of an index. For the pipeline case I'd prefer to_parquet(): CSV is plain text with zero dtype memory, so anything not a plain int or float — datetime, category, nullable Int64 — round-trips as a demoted, wrong dtype unless the read side re-declares it, and that's a silent failure, not an error. Parquet stores the dtype with the data, so read_parquet() restores it exactly. And if I'm appending in batches rather than writing once, I'd flag the header= trap specifically: to_csv() defaults header=True on every call, so an append without header=False writes the column names again as a literal data row and can silently coerce a numeric column to string with no error at all." The signal: naming index=False, the dtype round-trip gap, and the append/header= trap unprompted — three separate silent-failure shapes, not one.

6 · Where this fits

Lesson 8 named the ETL shape in the abstract; today is the concrete Load step it pointed at but never taught. Nothing here is hard to write — to_csv(path, index=False) is the whole happy path — but every trap above produces a file that opens fine and looks right, which is precisely what makes this the stage worth double-checking before trusting a pipeline's final output.
