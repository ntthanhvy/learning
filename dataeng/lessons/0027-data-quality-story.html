The data-quality story: what is tested where, and why

Today's tangible win isn't new code — it's a one-page answer, written once and kept in the repo, to the interview question every one of the last 26 days was quietly building evidence for: "where is data quality actually enforced in this pipeline, and why there and not somewhere else?" Today pulls that answer out of 26 days of scattered lessons into a single table, and finds one real gap in the process.

1 · Why this needs writing down, not just knowing

Every lesson from Day 3 onward added one more piece of quality enforcement — a test, a freshness check, an idempotent write, a unit test — but each one landed in its own day's isolated context. Nothing in this repo has ever asked "across all of it, where does a bad row actually get caught, and where would it slip through?" That question is exactly what "walk me through your data-quality approach" means in an interview, and answering it well requires naming the layer a check lives at, not just that checks exist somewhere.

The honest version of this story has three data-quality layers, and the point of today is that they catch genuinely different failure modes — none of them is redundant with another, and none of them alone is enough.

2 · Layer 1 — the Kafka consumer: safety against repeats, not correctness of content

Day 6's consumer enforces exactly one property: an event delivered more than once lands exactly once, via ON CONFLICT (event_id) DO NOTHING plus committing the offset only after that write succeeds. That is a real, load-bearing guarantee — but notice what it does not check. It never looks at whether status is a real status, whether occurred_at is a sane timestamp, or whether the same order's events arrive in a sensible order. It only answers one question: "have I seen this exact event_id before?" Anything that passes that one check lands in raw.order_events, bad content and all.

That's a deliberate, correct division of labor, not an oversight: a consumer sitting in the hot path of every incoming message is the wrong place to run a expensive or judgment-heavy check. It protects the one property a hot path has to get right — no silent loss, no silent duplication — and leaves content correctness to a layer that can afford to look harder.

3 · Layer 2 — dbt tests and source freshness: content correctness, after the fact

Everything Day 6's consumer doesn't check is exactly what Day 3's tests and freshness checks pick up next, one layer downstream, in raw.* and the staging models built on top of it. Three different failure modes, three different mechanisms, deliberately not the same tool used three times:

Failure modeCaught byWhy that mechanism, specifically
A row's own value is wrong (orphan restaurant_id, negative subtotal)Day 3's relationships/singular data testsA data test runs a query against real rows and fails if any come back — exactly shaped for "is this specific row bad," nothing more.
The loader silently stopped running, row counts still look plausibleDay 6's source freshness on raw.restaurants/raw.ordersFreshness compares a timestamp to now; a data test on existing rows can never catch an absence of new rows, because there is nothing wrong with the rows that did arrive.
A model's own logic is wrong (wrong join, off-by-one, sign error) but today's real data never happens to exercise the bugDay 12's unit testsA data test can only ever fail on rows that currently exist; a unit test supplies the exact fixed input the bug needs to show itself, independent of what's really in the warehouse today.

The middle row is the one worth saying out loud in an interview, because it's the least obvious: a data test and a freshness check look similar (both live in sources.yml/schema.yml, both run via dbt build) but they're answering opposite questions — "is what arrived wrong?" versus "did anything arrive at all?" Conflating them is a real, common mistake; Day 6 added freshness as a second, distinct check specifically because Day 3's tests structurally cannot cover a stalled loader.

4 · Layer 3 — the point-in-time join: correctness that no test shape above covers

Day 9's snapshot-based point-in-time join (fct_orders_with_commission, joining each order to the commission_rate valid at placed_at) sits in neither layer above. It isn't a hot-path safety check and it isn't a named data test — it's a join condition whose correctness depends on getting a boundary right (dbt_valid_to is null or placed_at < dbt_valid_to) that no generic test shape (not_null, unique, relationships, accepted_range) can express, because the rule spans a window across two tables, not a property of one column. Day 11's own finding was the direct answer to why: packages and generic tests cover a column-level rule; a cross-row, cross-table windowing rule stays a hand-written singular test or, as here, correct SQL with no test watching it at all.

Naming that gap honestly is itself part of the data-quality story: this join's correctness today rests entirely on the SQL being written right once, not on anything that would catch a regression the way Day 3's tests would catch a reintroduced orphan restaurant_id. That's a real, currently-open weak point in this repo, not a hypothetical one.

5 · The day's actual skill: closing the one gap layer 3 exposed

Rather than leave Section 4's finding as prose, fix it with a tool this course already has. The boundary rule itself can be expressed as a data test — not on fct_orders_with_commission's final shape, but as a direct assertion on the snapshot: no two valid-time windows for the same restaurant_id should ever overlap, and every order's placed_at should land inside exactly one window. Write a new singular test, tests/assert_no_overlapping_commission_windows.sql, in your food-delivery-pipeline repo's warehouse/ directory:

-- tests/assert_no_overlapping_commission_windows.sql
-- Fails (returns rows) if any restaurant has two snapshot rows whose
-- [dbt_valid_from, dbt_valid_to) windows overlap -- the exact precondition
-- Day 9's point-in-time join silently assumes but never checks.
select
    a.restaurant_id,
    a.dbt_valid_from as a_from,
    a.dbt_valid_to as a_to,
    b.dbt_valid_from as b_from
from {{ ref('restaurants_snapshot') }} a
join {{ ref('restaurants_snapshot') }} b
    on a.restaurant_id = b.restaurant_id
    and a.dbt_valid_from < b.dbt_valid_from
where
    -- TODO: the actual overlap condition -- a's window must end at or before
    -- b's window starts. Remember dbt_valid_to is null for the current row:
    -- a null "end" never overlaps anything that starts after it, so get the
    -- null-safe comparison right (the exact gotcha Day 9 already named for
    -- the join itself, now showing up a second time in the test for it).
    -- a.dbt_valid_to is not null and a.dbt_valid_to > b.dbt_valid_from

This is deliberately the same dbt_valid_to is null boundary Day 9 flagged for the join itself, reappearing in the test written to guard it — proof that the gotcha wasn't a one-off, it's a structural property of every query touching this snapshot. Add the test to warehouse/tests/; no YAML registration is needed for a singular test, the same as Day 3's assert_positive_subtotal.sql.

6 · The honest answer to "what would you add next"

A complete data-quality story names its own remaining gaps, not just its coverage. Two worth stating plainly rather than building today: Phase 2b's schema evolution lesson (Day 17) covers the one failure mode none of today's three layers touch at all — a producer silently changing order_events's shape (a renamed field, a changed type) with nothing downstream rejecting it until some query breaks weeks later, since this project never adopted a Schema Registry. And Day 18's consumer lag is a liveness signal, not a correctness one: it tells you the consumer is falling behind, never whether what it already landed is right. Naming both out loud, unprompted, is a stronger interview answer than letting the interviewer find the gap first.

To prove the test actually has teeth rather than trivially passing, temporarily hand-edit one restaurant's snapshot history in a scratch copy so two windows overlap by a day, rerun the same command, and confirm it now returns that restaurant's row and fails — then discard the scratch edit. A test that has never been watched to fail hasn't proven anything, the same standard Day 3 set for assert_positive_subtotal.

Q: "Where is data quality enforced in your pipeline, and why there?" A strong answer, out loud: "Three layers, each catching something the others structurally can't. The Kafka consumer enforces exactly one thing in the hot path — no silent loss, no silent duplication of an event — and deliberately checks nothing about content, because that's the wrong place to do expensive validation. dbt's data tests and source freshness catch content problems and loader outages downstream, where I can afford to look harder, but a data test can only ever fail on rows that exist, so it can't catch a pure logic bug the data never happens to exercise — that's what unit tests are for. And one correctness rule, the point-in-time join's non-overlapping windows, didn't fit any of those shapes, so I wrote a dedicated singular test for exactly that boundary once I noticed nothing was watching it. The gaps I know about and haven't closed: schema evolution on the Kafka side, since there's no Schema Registry here, and consumer lag only tells me about speed, never correctness." The signal: naming which layer catches what and why that shape fits there, plus owning the gaps instead of implying full coverage.
