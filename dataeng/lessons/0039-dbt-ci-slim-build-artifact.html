2 · TODO #1: loading raw data into the CI database

Day 15 named the fix already — the exact command Day 1's own Verify block uses, pointed at localhost instead of docker compose's network name, since the service container is reachable the same way on a GitHub-hosted runner:

-- .github/workflows/dbt_ci.yml -- Section 2's TODO, filled in
      - name: Set up uv
        uses: astral-sh/setup-uv@v3

      - name: Load raw data
        env:
          PGHOST: localhost
          PGUSER: fdp
          PGPASSWORD: fdp_dev_password
          PGDATABASE: fdp
        run: uv run --with "psycopg[binary]" python3 scripts/generate_raw_data.py

      - name: dbt build
        working-directory: food_delivery_pipeline
        run: uv run --with "dbt-postgres==1.11.0" dbt build --profiles-dir .
        env:
          DBT_HOST: localhost
          DBT_USER: fdp
          DBT_PASSWORD: fdp_dev_password
          DBT_DBNAME: fdp

Nothing about generate_raw_data.py changes — it's Day 1's own deterministic seed script, planted bad rows and all, reading its connection fields from the same PG* environment variables psycopg and most Postgres tooling already honor by convention. The only new fact is that a GitHub Actions service container is reachable at localhost from every step in the job, the same property Day 15's own dbt build step already relied on.

3 · TODO #2: where prod-state/manifest.json actually comes from

Section 4's deferred TODO was more deliberately left open than Section 2's — Day 15 named the standard answer (actions/upload-artifact / actions/download-artifact, run on every successful main-branch build) without wiring it. That requires a second job, not just a second step: one job builds the full project on main and uploads its manifest.json; every PR job downloads the most recent one before running slim CI against it.

-- .github/workflows/dbt_ci.yml -- the full file, both jobs
name: dbt CI

on:
  push:
    branches: [main]
    paths: ['food_delivery_pipeline/**']
  pull_request:
    paths:
      - 'food_delivery_pipeline/**'
      - '.github/workflows/dbt_ci.yml'

jobs:
  build-main:
    # Runs only on pushes to main: a full build, then the resulting manifest.json
    # is uploaded as an artifact for every later PR job to defer against.
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:17
        env:
          POSTGRES_USER: fdp
          POSTGRES_PASSWORD: fdp_dev_password
          POSTGRES_DB: fdp
        ports: ['5432:5432']
        options: >-
          --health-cmd pg_isready
          --health-interval 5s
          --health-timeout 5s
          --health-retries 10
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v3
      - name: Load raw data
        env: { PGHOST: localhost, PGUSER: fdp, PGPASSWORD: fdp_dev_password, PGDATABASE: fdp }
        run: uv run --with "psycopg[binary]" python3 scripts/generate_raw_data.py
      - name: dbt build (full)
        working-directory: food_delivery_pipeline
        run: uv run --with "dbt-postgres==1.11.0" dbt build --profiles-dir .
        env: { DBT_HOST: localhost, DBT_USER: fdp, DBT_PASSWORD: fdp_dev_password, DBT_DBNAME: fdp }
      - name: Upload manifest for future PRs to defer against
        uses: actions/upload-artifact@v4
        with:
          name: prod-manifest
          path: food_delivery_pipeline/target/manifest.json
          retention-days: 30

  slim-ci-pr:
    # Runs on every PR: downloads the most recent main-branch manifest and
    # builds only state:modified+, deferring everything else to it.
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:17
        env: { POSTGRES_USER: fdp, POSTGRES_PASSWORD: fdp_dev_password, POSTGRES_DB: fdp }
        ports: ['5432:5432']
        options: >-
          --health-cmd pg_isready
          --health-interval 5s
          --health-timeout 5s
          --health-retries 10
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v3
      - name: Load raw data
        env: { PGHOST: localhost, PGUSER: fdp, PGPASSWORD: fdp_dev_password, PGDATABASE: fdp }
        run: uv run --with "psycopg[binary]" python3 scripts/generate_raw_data.py
      - name: Fetch prior manifest
        uses: actions/download-artifact@v4
        with:
          name: prod-manifest
          path: prod-state
      - name: dbt build (slim CI)
        working-directory: food_delivery_pipeline
        run: |
          uv run --with "dbt-postgres==1.11.0" dbt build \
            --select "state:modified+" \
            --defer --state ../prod-state \
            --profiles-dir .
        env: { DBT_HOST: localhost, DBT_USER: fdp, DBT_PASSWORD: fdp_dev_password, DBT_DBNAME: fdp }

Two mechanical details make this actually work, both easy to get backwards: actions/download-artifact defaults to the most recent successful upload of that artifact name across the whole repo, not something scoped to the current branch, so a PR genuinely compares against the latest real main build rather than against itself. And the two jobs are mutually exclusive by the if: guards, not by the trigger alone — push and pull_request both fire on a PR's own branch-push event on some repo configurations, so without the guard a PR could accidentally run the full-build job against its own unmerged code and upload that as if it were production's manifest.

The first real run after merging this will fail once, on purpose. download-artifact has nothing to fetch until build-main has succeeded at least once on main — so the very first PR opened after this workflow lands will see its slim-ci-pr job fail with an artifact-not-found error. That's expected, not a bug: merge this workflow file itself via the plain full-build path (or trigger build-main manually once), then every PR after that has a real manifest to defer against.

4 · Why this needed a second job, not a second step

Day 15's profiles.yml and --defer --state flags were already correct — the gap was entirely about where the comparison manifest lives between separate CI runs, which is exactly what a job boundary and an artifact exist to solve. A single job's own filesystem disappears when that job ends; nothing it writes is visible to a different job, let alone a different pull request opened days later. upload-artifact/download-artifact is GitHub Actions' own answer to "persist one file from one run so a later, unrelated run can read it" — the artifact store, not the runner's disk, is what makes prod-state/manifest.json outlive the job that produced it.

Q: "You said your dbt CI does slim builds with state:modified+. Where does the comparison manifest actually come from?" A strong answer, out loud: "A separate job, triggered only on pushes to main, runs a full dbt build and then uploads the resulting manifest.json as a GitHub Actions artifact. Every pull-request job downloads that same artifact — by name, which always resolves to the most recent successful upload across the repo — into a prod-state folder before running dbt build with --select state:modified+ --defer --state pointed at it. The two jobs are gated by if: conditions on the event type so a PR's own branch push can never accidentally run the full-build job and overwrite what main's manifest should mean. The real trade-off: the very first PR after this workflow ships has nothing to download yet, since build-main has to succeed on main at least once first — and if build-main ever starts failing silently, every PR after that keeps deferring to a manifest that's now stale, which is slim CI's whole known risk, not a new one I introduced." The signal: naming the artifact as what actually bridges two separate jobs/runs, not just reciting the dbt flags, and naming the bootstrap gap honestly instead of glossing over it.
