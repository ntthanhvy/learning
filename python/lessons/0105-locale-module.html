locale: formatting numbers the way a reader expects

An f-string's {n:,} always groups thousands with a comma and a period for the decimal point — fine for an English-speaking reader, wrong for plenty of others, who group with a period and use a comma for the decimal point instead. That grouping and punctuation choice is a locale, and the standard library's locale module is what reads data formatted a given locale's way and writes output formatted the same way back.

1 · Setting one, and why it is process-wide

By default a fresh Python process runs in the 'C' locale — no grouping, plain . decimal point. locale.setlocale() changes that, but confirmed live: it mutates global state for the entire process, not just the calling function or module — every later call anywhere in the program sees the new setting:

import locale

print(locale.getlocale())                          # ('C', 'UTF-8') -- confirmed live, before any change

locale.setlocale(locale.LC_ALL, "en_US.UTF-8")
print(locale.getlocale())                          # ('en_US', 'UTF-8') -- confirmed live

locale.LC_ALL sets every category at once (numbers, currency, dates, text sorting); narrower constants like LC_NUMERIC or LC_MONETARY exist to set just one. An unrecognized name raises locale.Error, not a silent fallback — confirmed live, requesting a made-up name raises it immediately rather than quietly keeping the old setting.

2 · Formatting numbers the locale's way

locale.format_string() and locale.currency() read the active locale's grouping and punctuation rules rather than hard-coding English conventions:

locale.setlocale(locale.LC_ALL, "en_US.UTF-8")

print(locale.format_string("%d", 1234567, grouping=True))
# 1,234,567 -- confirmed live

print(locale.currency(1234567.5, grouping=True))
# $1,234,567.50 -- confirmed live

grouping=True is required — without it, no thousands separator is inserted at all, confirmed live. These both read from locale.localeconv()'s table under the hood, which exposes the raw punctuation directly if a value needs custom formatting beyond what the two helpers cover:

conv = locale.localeconv()
print(conv["decimal_point"], conv["thousands_sep"])   # . , -- confirmed live, en_US

3 · Parsing numbers back the same way

locale.atof() is the reverse direction: given a string formatted the active locale's way, it parses it back into a float, correctly stripping whatever grouping character that locale uses before handing the rest to float(). Confirmed live, this genuinely strips the comma rather than tripping on it — a plain float() call could not do this:

print(locale.atof("12,345,678.9"))   # 12345678.9 -- confirmed live, comma stripped correctly

try:
    locale.atof("abc")
except ValueError as e:
    print(e)   # could not convert string to float: 'abc' -- confirmed live

This is the real reason the module exists beyond cosmetics: a number typed by a user, or read from a file produced by a locale-aware tool (a spreadsheet export, say), may already contain locale-specific grouping and decimal punctuation — locale.atof() is how a program undoes that correctly instead of a bespoke string-replace guess.

f-string {n:,} is not locale-aware — confirmed live. f"{1234567:,}" always inserts a comma and always means a period as the decimal point, in every locale, regardless of what locale.setlocale() was most recently called with. The comma-grouping mini-language in format specs is a fixed, English-style convention baked into the language itself — reaching for the locale module is the deliberate opt-in when output genuinely needs to match the user's own locale instead.
