API gateway & BFF: naming the layer in front of your services

This course has taught rate limiting (Lesson 11), circuit breakers (28), service-to-service auth (31), and correlation-ID generation "at the edge" (65) — each time saying "the first service to see a request" without ever naming what that first service usually is. Today: the edge layer itself, the two shapes it commonly comes in, and why "just put it in every service" stops working once there's more than one service.

1 · The thing four lessons already pointed at

Lesson 65 put it plainly: "the first service to see a request — the one sitting at the edge, directly facing the client." Lesson 31 assumed a fleet of backends calling each other. Lesson 11 assumed rate limiting happens "at the edge," not inside every handler. Lesson 28 assumed something is watching outbound calls fail. None of those lessons said where that logic actually lives. In a real system with more than one or two services, it rarely lives duplicated inside each one — it lives once, in a dedicated process every external request passes through first, before any of your actual business logic runs. That process is an API gateway.

2 · What moves into the gateway, and why "once" beats "everywhere"

Picture the fleet from Lesson 31: an order service, a billing service, an inventory service, a payment provider behind that. Without a gateway, a mobile app or web client would need to know all three internal hostnames, and each of those three services would need its own copy of: checking the client's auth token, rate-limiting per client, generating a correlation ID if none arrived yet (Lesson 65), and deciding whether to even accept the request under load (Lesson 11's backpressure). Every one of those is a cross-cutting concern — not specific to orders, or billing, or inventory — so writing it three times means three chances to get it slightly wrong, and three places to update when the rule changes.

An API gateway collapses that to one place. The client sends every request to one public hostname; the gateway terminates TLS, checks the auth token once, applies the rate limit once, mints the correlation ID once (exactly the "generate at the edge" rule from Lesson 65, now with a concrete home), and only then routes it to whichever internal service owns that path — the same route-matching concept from the glossary, now happening once at the gateway instead of inside each service's own router. The three backend services go back to trusting that anything reaching them already passed those checks — the same trust boundary Lesson 31 described between services, just drawn one hop further out, at the client boundary instead of between services.

Not a new mechanism — a new address for old ones. Nothing here invents a new concept. Rate limiting is still Lesson 11's token bucket. Auth is still Lesson 4/31's tokens. A correlation ID is still Lesson 65's generate-once rule. The gateway is just the one place all of them now run, instead of three or thirty places.

3 · The other question a gateway answers: whose shape is the response?

A plain gateway solves "one address, cross-cutting concerns handled once" but still hands back each backend's response mostly as-is. A second problem shows up once a product has more than one kind of client: a mobile app's order-history screen might need three fields from the order service and one from billing, stitched into a single small JSON payload to keep the phone's network usage low; the internal admin dashboard, hitting the same order data, might want fifteen fields across four services in one call, because the person using it is on a fast connection and wants everything visible at once. Neither shape is "the API" — they're two different client's needs pointed at the same backend data.

A backend-for-frontend (BFF) is the answer: not one shared gateway, but one small backend per client type, each calling whatever internal services it needs and reshaping the combined result into exactly what that one client wants — fewer round trips for the phone, richer payloads for the dashboard, without either client dictating the other's shape or the underlying services changing at all.

4 · Gateway vs. BFF: same position, different job

QuestionAPI gatewayBFF
How many, for how many clientsUsually one, shared by every client typeOne per client type (mobile BFF, web BFF, admin BFF)
Main jobCross-cutting: routing, auth, rate limiting, TLS terminationAggregation: call several services, reshape into one client-specific payload
Knows about client-specific shape?No — deliberately generic, forwards mostly as-isYes — its entire purpose is one client's ideal shape
Where request fan-out happensRare — one request in, one internal request outCommon — one request in, several internal calls out, merged

The two aren't mutually exclusive. A common real shape is a gateway at the very edge for TLS/auth/rate-limiting, with one or more BFFs sitting just behind it, each doing the aggregation work for one client type. Small systems often skip both and let clients call services directly; the trade-off matters once client count and service count both grow past what "everyone calls everything directly" can bear.

5 · A gateway in Go: the shape, not a framework

Real deployments usually reach for a dedicated product (Envoy, Kong, an API-management cloud service) rather than hand-rolling one, but the underlying shape is plain Go you already know: an http.Handler that checks a few things, then reverse-proxies to the right backend. This sketch composes ideas from Lessons 11, 65, and 41 into one entry point.

// routes maps a path prefix to the internal service that owns it --
// the routing decision at the heart of any gateway.
var routes = map[string]*url.URL{
    "/orders/":    mustParseURL("http://order-svc.internal:8080"),
    "/billing/":   mustParseURL("http://billing-svc.internal:8080"),
    "/inventory/": mustParseURL("http://inventory-svc.internal:8080"),
}

// gatewayHandler runs the cross-cutting checks once, at the one place
// every external request passes through, before any backend sees it.
func gatewayHandler(limiter *RateLimiter) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        // 1. correlation id, generate-at-the-edge rule from Lesson 65
        reqID := r.Header.Get("X-Request-ID")
        if reqID == "" {
            reqID = uuid.NewString()
        }
        r.Header.Set("X-Request-ID", reqID)

        // 2. auth, once, per Lesson 4/31 -- backends trust this already ran
        clientID, ok := verifyToken(r.Header.Get("Authorization"))
        if !ok {
            http.Error(w, "unauthorized", http.StatusUnauthorized)
            return
        }

        // 3. rate limit, once, per Lesson 11's token bucket
        if !limiter.Allow(clientID) {
            w.Header().Set("Retry-After", "1")
            http.Error(w, "rate limit exceeded", http.StatusTooManyRequests)
            return
        }

        // 4. route to the owning backend by longest matching prefix
        target, prefix := matchRoute(r.URL.Path)
        if target == nil {
            http.NotFound(w, r)
            return
        }
        r.URL.Path = strings.TrimPrefix(r.URL.Path, prefix)
        httputil.NewSingleHostReverseProxy(target).ServeHTTP(w, r)
    })
}

Every backend behind this gateway can now assume: a request that reaches it already carries a valid X-Request-ID, already passed auth, and already survived rate limiting. That assumption is exactly what lets Lessons 11, 31, and 65 be written once here instead of copy-pasted into the order service, the billing service, and the inventory service separately.

6 · The trade-off: one more hop, one more thing that can go down

A gateway adds a network hop to every single request, and it becomes a single point of failure by construction — if it's down, every backend behind it is unreachable even though each one is individually healthy. This is the same shape of trade-off Lesson 50's bulkhead pattern discussed for shared resources generally: centralizing something for consistency also centralizes its blast radius. Production gateways are run as a load-balanced fleet of identical instances for exactly this reason — the concern doesn't go away, it just gets addressed the same way Lesson 8 addressed it for any other stateless service: run more than one, behind a load balancer, none of them holding state the others don't have.

Q: "When would you introduce an API gateway, and would you also add a BFF?" A strong answer, out loud: "Once I have more than a couple of backend services and more than one kind of client, I'd want a gateway so auth, rate limiting, and request-id generation live in one place instead of being duplicated in every service — that's a pure infrastructure win, no product shape involved yet. I'd only add a BFF on top of that if different clients genuinely need different response shapes — say the mobile app wants a slim aggregated payload from three services in one round trip, and the internal dashboard wants a much richer one. If every client is happy with the same shape, a shared gateway alone is enough and a BFF would just be extra services to operate for no real benefit." The signal: treating the gateway and the BFF as answers to two different questions — "where do cross-cutting concerns live" versus "whose response shape is this" — not as the same thing with two names.
