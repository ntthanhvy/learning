Canary releases vs. blue-green deployments: small blast radius, one layer down

Lesson 70 built a feature flag's percentage rollout — widen a new code path from 5% to 25% to 100% while watching error rates — and dropped one term in passing, inside a callout, without ever teaching it: "a canary release watching error rates before widening a flag." Ninety-ish lessons in, that's still the only place the word appears anywhere in this course. Today names it properly, and names the thing people confuse it with, because they solve the same instinct at a different layer of the stack than a flag ever touches.

1 · A flag gates code inside one version; these gate which version is even running

Lesson 70's flag lived inside a single running binary: one version of the service was deployed everywhere, and an if statement decided, per request, which branch of already-deployed code to execute. Nothing about rolling a flag from 5% to 100% ever started a second process or shipped a second build — the artifact running in production never changed, only which path through it got used. A canary release answers a different question entirely: not "which branch runs inside this version," but "which version is running at all." A small slice of traffic or a small number of instances gets the new build; everyone else keeps running the old one; and a human or an automated gate watches the new build's metrics before deciding whether to send more traffic its way or pull it back out.

The instinct is identical to Lesson 70's percentage rollout — don't bet everything on an untested change at once, start small, watch, widen — but the thing being risked is different. A flag's 5% is 5% of requests choosing between two branches inside one deployed artifact. A canary's 5% is 5% of traffic (or instances, or both) hitting a genuinely different artifact — a different binary, built from a different commit, that could fail in ways the old binary structurally cannot, because the code itself changed, not just which path through unchanged code got taken.

Same instinct, different layer: a feature flag's percentage rollout gates which code path executes inside one running version. A canary release gates which version is running at all. You can have one without the other — a canary rollout of a build that happens to contain zero new flags, or a flag rollout with no new build involved — and plenty of real systems run both at once: canary the new build at the infrastructure layer, and inside that new build, keep its riskiest feature behind a flag defaulted off.

2 · What a canary actually needs underneath it

A canary release can't happen without something capable of sending some traffic one place and the rest somewhere else — which is exactly the job Lesson 69's load balancer already does, just aimed at a new target. Instead of splitting traffic across instances of the same version for capacity, a canary rollout points a small, deliberately chosen slice at instances running the new version and everything else at instances still running the old one. The mechanism — weighted routing across a pool of backends — is unchanged from Lesson 69; only the reason for the split (capacity vs. risk) and what's different between the backends (identical code vs. two different versions) changed. This routing behavior is usually called traffic shifting (or traffic splitting) — the same load-balancing layer Lesson 69 taught, now used to separate versions instead of just spreading load evenly.

Watching the canary is the other half, and nothing here is new either: error rates, latency percentiles, resource usage — the same metrics Lesson 68's error budget and Lesson 70's percentage rollout already watch. What's new is the decision those metrics feed: widen the canary's traffic share, hold it where it is for longer, or abort — pull all traffic back to the old version and treat the new build as a failed attempt, not a bug to patch forward from. That abort path is also just traffic shifting run in reverse: no data migration to undo, no second deploy to wait on, because the old version's instances never stopped running.

3 · Blue-green: skip the slow watch, keep an instant escape hatch instead

A canary's whole premise is patience: ramp slowly enough that a gradual regression — a memory leak that only shows up after an hour, a slow-growing error rate — gets caught before it reaches everyone. A blue-green deployment gives up on watching gradually in exchange for speed in both directions: two full, identical environments exist side by side — call them blue (currently live) and green (currently idle) — the new version is deployed and fully warmed up on green while blue keeps serving 100% of traffic untouched, and then the router flips, all at once, so green becomes live and blue becomes idle. There is no 5%-then-25%-then-100% ramp; it's 0% and 100%, switched in one move. Rollback is the same move backward: flip the router back to blue, instantly, because blue never stopped existing and never ran a single request from the new version.

What blue-green actually buys, and what it doesn't: the switch and the rollback are both as close to instant as this gets — no waiting for an old version's instances to drain or a new version's canary to prove itself over an hour. The cost is concrete: roughly double the infrastructure, since both environments have to exist, fully provisioned, at the same time, even though only one serves real traffic at any moment. And the switch catches only what a health check on green would have caught before the flip — a gradual regression that only shows up after green has carried real load for a while has already reached 100% of traffic by the time anyone notices, because nothing was watching a small slice first the way a canary does.

"Doing neither" — a rolling deploy with no canary and no blue-green, just replacing instances with the new version one at a time until all of them are updated — is the default most teams start from, and it's not free of either technique's safety net: a bad instance is serving some real traffic for however long it takes to notice and roll back, with no small-slice warning period and no instant full-environment escape hatch. Both canary and blue-green exist specifically to put a cheaper, faster decision point in front of that default.

Q: "What's the difference between a canary release and a blue-green deployment?" A strong answer, out loud: "Both put a new version in front of real traffic before fully committing to it, but they trade speed for coverage in opposite directions. A canary release sends a small slice of traffic to the new version first, watches error rates and latency, and widens gradually — that catches a regression that only shows up gradually, under sustained real load, at the cost of needing weighted traffic-splitting infrastructure and someone watching metrics over time before fully committing. Blue-green skips the gradual watch entirely: two full identical environments exist side by side, the new version gets fully deployed and health-checked on the idle one, and then all traffic switches over in one move, with rollback just as instant by switching back. That's fast in both directions but needs roughly double the infrastructure running at once, and it only catches what a health check would have caught before the switch — a slow leak that takes an hour to show up has already hit 100% of traffic by the time anyone notices. I'd reach for blue-green when the deploy itself is the risk and I want an instant undo; I'd reach for canary when the code change itself is the risk and I want to see it under real traffic before trusting it fully." The signal: naming the actual trade-off — gradual-and-cheap-per-instance vs. instant-and-double-infrastructure — rather than treating the two as interchangeable synonyms for "careful deploy."

5 · Not the same decision a circuit breaker makes

Lesson 28's circuit breaker trips itself automatically, mid-request, the instant a dependency's failure count crosses a threshold — no human in the loop, reacting in milliseconds to calls already failing right now. Widening a canary's traffic share, aborting it, or flipping a blue-green switch are not that: even when a metrics threshold triggers an automated promotion (some pipelines do exactly this), the decision is still "should this version serve more traffic going forward," made by watching a trend over minutes or hours — not "should this one call be allowed to happen," decided in microseconds by an open circuit. A circuit breaker protects callers from a dependency that's already failing right now. A canary or blue-green rollout decides whether a new version gets to exist in production at all. They can coexist in the same system without overlapping: the new canary build can have its own circuit breakers protecting its own outbound calls, same as any other version would.

Scope line

MISSION.md rules out Kubernetes and cloud-provider specifics as out of scope, and in a real production system that's almost always where canary releases and blue-green deployments actually get implemented — a Kubernetes Deployment's rolling-update controller, a cloud load balancer's weighted target groups, a managed traffic-splitting API. None of that is this lesson's job. The point here is the vocabulary and the trade-off underneath any of those tools: small-slice-and-watch versus two-environments-and-switch versus neither, and which layer (code path vs. running version) each risk-reduction technique in this course actually operates on. Knowing that is what lets a design discussion or a PR comment about "how are we rolling this out" make sense regardless of which specific platform ends up running it.
