1 · Every test so far has tested real data. Today tests logic instead.

Days 3, 9 and 11's tests all share one property: they run against whatever rows are actually sitting in the warehouse right now. not_null, relationships, dbt_utils.accepted_range — every one of them is a query over real, live data, and it either finds a violation or it doesn't. That's exactly the right tool for "is today's data clean," which is what a data test is for: Day 3's relationships test on stg_orders.restaurant_id caught a real orphan row because a real orphan row existed to catch.

But data tests have a blind spot: they can only fail on data that exists right now. mart_delivery_sla's share_over_45_min calculation — the case when {{ is_sla_breach(...) }} then 1 else 0 end divided by count(*) from Day 10 — could have an off-by-one bug, a wrong join direction, or a sign error, and no data test would ever notice, because a data test only checks properties like "is this null" or "is this in range," not "did this specific arithmetic produce the specific number it should have." Proving the *logic* is right needs inputs you control completely, with an answer you already know by hand — which is what a unit test (available since dbt-core 1.8) is built for.

2 · Anatomy of a unit test: given, fake inputs; expect, the answer

A unit test is declared in a model's schema YAML, under a top-level unit_tests: key — sibling to the models: key Day 3's stg_orders.yml used, not nested inside it. It names the model under test, supplies fake rows for each upstream ref()/source() that model reads via given, and states the exact output rows it should produce via expect. dbt substitutes the fake given rows for the model's real inputs, compiles and runs the model's actual SQL — the identical mart_delivery_sla.sql file, untouched — and diffs the result against expect.

Write one for mart_delivery_sla, in a new file models/marts/unit_tests.yml. Two delivered orders, same city and day, one inside the 45-minute SLA and one over it — an answer you can check by hand: 1 breach out of 2 orders is exactly 0.5.

-- models/marts/unit_tests.yml
version: 2

unit_tests:
  - name: test_mart_delivery_sla_share_over_threshold
    description: "One breach out of two delivered orders in the same city/day should compute a 0.5 share, using the default 45-minute var()."
    model: mart_delivery_sla
    given:
      - input: ref('stg_orders')
        rows:
          - {order_id: 1, restaurant_id: 1, courier_id: 1, subtotal: 20, delivery_fee: 3, placed_at: "2026-09-01 12:00:00"}
          - {order_id: 2, restaurant_id: 1, courier_id: 1, subtotal: 20, delivery_fee: 3, placed_at: "2026-09-01 12:00:00"}
      - input: ref('stg_restaurants')
        rows:
          - {restaurant_id: 1, city: "Hanoi"}
      - input: ref('stg_order_events')
        rows:
          - {order_id: 1, status: "delivered", occurred_at: "2026-09-01 12:20:00"}
          # order 1: 20 minutes to deliver -- inside the 45-minute SLA
          - {order_id: 2, status: "delivered", occurred_at: "2026-09-01 13:10:00"}
          # order 2: 70 minutes to deliver -- a breach
    expect:
      rows:
        - {city: "Hanoi", order_date: "2026-09-01", delivered_orders: 2, share_over_45_min: 0.5}

Only the columns each fake row actually needs are given — stg_orders' fake rows skip order_total entirely, since mart_delivery_sla.sql never reads it. Run it on its own with dbt test, the same command Day 3 used for data tests:

uv run --project ../dbt_env dbt test --select test_mart_delivery_sla_share_over_threshold

Expected:

1 of 1 PASS test_mart_delivery_sla_share_over_threshold ... [PASS in 0.08s]

Done. PASS=1 WARN=0 ERROR=0 SKIP=0 TOTAL=1
This proves nothing about today's real orders. The unit test would pass identically whether raw.orders currently has 500 rows or zero — it never queries raw.orders at all, since given replaces every upstream input with fakes. That's the whole point, not a limitation: a unit test asks "is this SQL correct," a data test asks "is this data correct," and mart_delivery_sla needs both, run for different reasons, not one instead of the other.

3 · Build: prove it actually catches a broken change

A test that has never failed hasn't proven anything yet — the same standard Day 3 held its relationships test to. Break mart_delivery_sla.sql on purpose: flip the aggregation from sum(...) to count(*) in the numerator, a realistic copy-paste slip that silently changes "how many orders breached" into "how many orders there are" — every order would count as a breach:

-- models/marts/mart_delivery_sla.sql -- TEMPORARY, to prove the unit test catches a break
-- change: sum(case when {{ is_sla_breach('minutes_to_deliver') }} then 1 else 0 end)::numeric
-- to:     count(*)::numeric  -- wrong: counts every order as a breach, not just late ones
uv run --project ../dbt_env dbt test --select test_mart_delivery_sla_share_over_threshold

Expected — the fixture's two fabricated orders now produce a share_over_45_min of 1.0 (2 counted as breaches out of 2) instead of the expected 0.5, so the unit test fails exactly where the bug is:

1 of 1 FAIL 1 test_mart_delivery_sla_share_over_threshold ... [FAIL 1 in 0.06s]

Done. PASS=0 WARN=0 ERROR=0 SKIP=0 TOTAL=1

dbt reports which expected row didn't match, not just pass/fail — read the mismatch with --store-failures or the console diff the way Day 3's failure output named the exact bad order_id. Revert the change back to {{ is_sla_breach('minutes_to_deliver') }} and confirm green again before moving on:

uv run --project ../dbt_env dbt test --select test_mart_delivery_sla_share_over_threshold
Done. PASS=1 WARN=0 ERROR=0 SKIP=0 TOTAL=1

Why not unit-test every model: stg_orders and the other staging models are close to pure passthroughs of raw.* — a unit test on a select with no branching or arithmetic mostly re-states the SQL in YAML, costing maintenance for no real bug-catching power. Unit tests earn their place on models with actual logic to get wrong: a case when, a join that could silently drop or duplicate rows, an aggregation, a threshold comparison like today's. That's also why mart_delivery_sla and mart_restaurant_sla got one today and the staging layer still has none — the same "does this specific piece earn its complexity" question Day 10 asked of macros, asked here of tests instead.

Q: "What's the difference between a dbt data test and a dbt unit test, and when do you reach for each?" A strong answer, out loud: "A data test — unique, not_null, relationships, or a custom one — runs a query against whatever rows are actually in the warehouse right now and flags a violation if it finds one. It's the right tool for 'is today's data clean,' but it has a blind spot: it can only fail on data that currently exists, so it can never catch a logic bug that just hasn't been exercised by today's rows yet. A unit test, available since dbt-core 1.8, fixes that by replacing a model's real ref() and source() inputs with small, hand-written fake rows and checking the output against a hand-written expected result — it runs the model's actual SQL, but on inputs I fully control, so I can prove an aggregation or a threshold comparison is correct independent of whatever's really in the warehouse today. I reach for a unit test on any model with real logic to get wrong — a case when, a join, an aggregation — and skip it on a near-passthrough staging model, where it would just restate the SQL in YAML for no real payoff. The two aren't redundant: a mart can have a unit test proving its math is right and a data test proving today's actual output still respects its grain, at the same time, for different reasons." The signal: naming the blind spot in data tests specifically ("can only fail on data that exists"), not just "one tests data, one tests logic" as a slogan.
