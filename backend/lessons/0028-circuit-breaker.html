Circuit breaker: stop calling what's already down

Lesson 27's closing teaser named two untaught candidates: circuit breaker and the outbox pattern. Today, the first one — a guard that notices a downstream dependency is failing and, for a while, simply stops calling it.

1 · Retrying a dead dependency makes the outage worse

Say your order service calls an inventory service on every checkout, and the inventory service starts timing out — overloaded, deploying, or just gone. The naive response feels correct: catch the error, retry. But every one of those calls still has to wait out its own timeout before it fails, and while it waits, it's holding a resource — the exact pool exhaustion shape Lesson 18 taught, except now the thing blocking every connection is a dependency that was never going to answer in time. More load arrives, more calls pile up waiting on the same dead dependency, and the order service — which was healthy — goes down too, just from trying to be polite to a service that already failed.

This is cascading failure: one dependency's outage, amplified by callers who never stop trying, becomes an outage of everything upstream of it too. A circuit breaker exists to break that chain: after enough consecutive failures calling a dependency, it stops attempting the call at all — failing immediately, in microseconds, instead of waiting out a timeout every single time — until the dependency has had a chance to recover.

Frontend-habit trap: a frontend retry (refetch on a failed request, react-query's default retry-with-backoff) assumes the network is what's unreliable and the server is fine — retrying is usually the right move. A circuit breaker assumes the opposite failure: the server side itself, or one dependency deep inside it, is the thing that's down. Retrying harder doesn't fix that; it adds load to something already struggling.

2 · Three states, not a binary on/off

The mechanism is a small state machine with three states:

  • Closed — the normal state. Calls pass through to the real dependency. Failures are counted; a run of consecutive failures crossing a threshold trips the breaker to open.
  • Open — calls fail immediately without even attempting the dependency, for a fixed cooldown window. This is the state that actually stops the cascade: no thread, goroutine, or pool connection is spent waiting on something known to be down.
  • Half-open — once the cooldown elapses, the breaker lets exactly one probe call through. Succeed, and it closes again — normal traffic resumes. Fail, and it reopens for another full cooldown, without ever letting a flood of retries hit the still-struggling dependency.

The names describe an electrical circuit deliberately: closed lets current (calls) flow; open breaks the circuit so nothing gets through; the breaker "trips" the same way a household circuit breaker does when a fault draws too much current, protecting the wiring behind it rather than the appliance that caused the fault.

3 · A minimal Go implementation

The whole mechanism fits in a small struct: a state, a failure counter and threshold, and the timestamp the breaker last tripped open:

type CircuitBreaker struct {
    mu               sync.Mutex
    st               state // closed, open, or halfOpen
    consecutiveFails int
    failureThreshold int
    openTimeout      time.Duration
    openedAt         time.Time
}

func (cb *CircuitBreaker) Call(fn func() error) error {
    if !cb.allow() {
        return ErrCircuitOpen // fails in microseconds — no call attempted
    }
    err := fn()
    cb.recordResult(err)
    return err
}

func (cb *CircuitBreaker) allow() bool {
    cb.mu.Lock()
    defer cb.mu.Unlock()
    switch cb.st {
    case closed:
        return true
    case open:
        if time.Since(cb.openedAt) < cb.openTimeout {
            return false // still cooling down
        }
        cb.st = halfOpen // timeout elapsed — allow one probe
        return true
    case halfOpen:
        return false // a probe is already out; block the rest
    }
    return false
}

func (cb *CircuitBreaker) recordResult(err error) {
    cb.mu.Lock()
    defer cb.mu.Unlock()
    if err == nil {
        cb.consecutiveFails = 0
        cb.st = closed // success (incl. the probe) fully resets
        return
    }
    cb.consecutiveFails++
    if cb.st == halfOpen || cb.consecutiveFails >= cb.failureThreshold {
        cb.st = open
        cb.openedAt = time.Now()
    }
}

Every call to the dependency goes through cb.Call(fn) instead of calling fn directly. allow() is the gate: closed always lets the call through; open blocks until openTimeout has elapsed, then flips to half-open and lets exactly one call through as a probe; half-open blocks every other caller until that one probe resolves. recordResult is what actually moves the state — a single failure while half-open reopens immediately (the dependency isn't back yet), while a success from any state fully resets the counter. This compiled clean as real, standalone Go — no framework, no external library, because the whole point is that the state machine is small enough to hold in your head.

4 · What the caller does when the circuit is open

A breaker only solves half the problem: failing fast instead of failing slow. The caller still has to decide what to return to its own caller while the circuit is open — this is the fallback: a cached inventory count that might be slightly stale, a "check back shortly" response, or, if there's truly nothing sensible to serve, an honest error returned immediately rather than after a timeout. Which fallback makes sense is a product decision, not a mechanical one — but an open circuit is exactly the signal that should trigger asking that question, instead of blindly propagating whatever error the dependency last returned.

5 · Not the same tool as rate limiting

Lesson 11's rate limiter and today's circuit breaker can look similar — both reject calls under certain conditions — but they protect opposite sides of a call, and mixing them up is a common interview stumble:

Rate limiter (Lesson 11)Circuit breaker (today)
Protectsthe callee, from too many callersthe caller, from a failing callee
Triggered byrequest volume crossing a capconsecutive failures crossing a threshold
Lives onthe service receiving trafficthe service making outbound calls
Recoverytoken bucket refills on a timerhalf-open probe tests real recovery

A single request can pass through both, in either order: your service might rate-limit its own incoming traffic and wrap its outbound call to inventory in a circuit breaker — one defends your capacity from the outside, the other defends your capacity from a dependency you don't control.

Q: "A downstream service you depend on starts timing out under load. What do you do?" A strong answer, out loud: "First, I wouldn't just add more retries — that adds load to something already struggling and can turn its outage into mine, since every retry still holds a connection or goroutine waiting. I'd wrap that call in a circuit breaker: after enough consecutive failures it trips open and fails immediately for a cooldown window, no network call attempted, instead of every caller waiting out a full timeout. After the cooldown it lets one probe call through — half-open — and only resumes normal traffic if that succeeds. And I'd decide up front what to return while it's open: a cached fallback if one makes sense, or a fast honest error if it doesn't, rather than letting the failure propagate after the slow way." The signal: naming the three states and the half-open probe specifically, and connecting it back to why blind retries make an outage worse.
