async/await: C#'s coroutine, named properly this time

Lesson 25 named the two questions — concurrent-or-not, thread-or-coroutine — and said Go skipped the async/await ceremony "that Python or Rust require." C# requires that ceremony too, and every C# snippet since Lesson 103 has used async Task<IActionResult> and await without ever stopping to say what they actually do. Today: what await really suspends, what Task<T> actually is, and the one C#-specific way to misuse both that creates a deadlock a Go goroutine cannot produce by the same mistake.

1 · Task<T> is a coroutine's "not finished yet, but here's where to check"

A C# method marked async that returns Task<T> does not return a T. It returns immediately with a Task<T> — an object representing "this work is running, and will eventually hold a T, or an exception, once it's done." Calling an async method starts the work and hands back that handle; it does not wait for the work to finish.

public async Task<Order> GetOrderAsync(int id) {
    var order = await db.Orders.FindAsync(id);   // suspend HERE until the DB answers
    return order;
}

Lesson 25 already named the mechanism this is: a async/await-marked method is C#'s coroutine — scheduled by the .NET runtime, not the OS kernel, suspending only at an await (a cooperative yield point, same word Lesson 25 used), and resuming later without ever needing its own OS thread while it waits. await db.Orders.FindAsync(id) suspends the method right there, hands the OS thread it was running on back to the thread pool to go serve some other request, and schedules the rest of the method to run once the database actually answers — on whatever thread happens to be free then, not necessarily the one that started it.

2 · Lining it up with Lesson 25's table: the same row, a different checkbox

This is not a new concept — it's a second entry in Lesson 25's "called" row, right next to goroutines, task/future, and Python's async def. The difference that actually matters day to day is one checkbox in that same table:

Go goroutineC# async/await
Scheduled byGo runtime, in user space.NET runtime, in user space
Switchingcooperative, but can suspend almost anywhere — a blocking call, a channel opcooperative, only at an explicit await — nowhere else, ever
Ceremony to write onego f() — no keyword needed on f itselfasync on the method, await at every suspend point
Calling it blocks the caller?no — go f() returns instantly, f runs independentlyno, if the caller also awaits — see section 3 if it doesn't

Go gave the compiler almost nothing to check — a goroutine can block inside any function, at any line, and the runtime copes. C# makes every suspend point visible in the method's own text as an await keyword, which is more ceremony to write but means a reviewer can see exactly where a method might hand its thread back, just by reading it top to bottom.

3 · The C#-specific trap: calling async code without awaiting it

Because Task<T> is a handle, not a value, C# lets you reach into it without await at all — and that's where a bug with no real Go equivalent shows up:

// Inside a synchronous method, calling an async one and blocking for the result:
public Order GetOrder(int id) {
    var order = GetOrderAsync(id).Result;  // BLOCKS this thread until the Task finishes
    return order;
}

.Result (and .Wait()) forces the calling thread to sit and block until the Task finishes — this is called sync-over-async, and it undoes the entire reason Task<T> exists: the calling thread is now blocked and unusable, exactly the cost goroutines and coroutines both exist to avoid. In modern ASP.NET Core this usually "only" wastes a thread-pool thread. But in a context that captures and resumes on the original context (classic ASP.NET's SynchronizationContext, or a WPF/WinForms UI thread) it can deadlock outright: the blocked thread is the exact same thread the awaited Task is waiting to resume on, so the Task can never finish and .Result never returns. No goroutine deadlocks this particular way, because Go never created a separate "blocking handle" object standing between a call and its result in the first place — calling a function and getting its value back is the only shape Go has.

The fix is almost always the same one word, propagated all the way up: await instead of .Result/.Wait(), on every method in the call chain, as far up as it needs to go — the rule sometimes called "async all the way." A library author one layer further down can also reduce the deadlock risk for synchronous callers they don't control with ConfigureAwait(false), but that's a mitigation for library code, not a substitute for the real fix in application code the team actually controls.

Where this shows up in review: a controller action or a test harness calling .Result on an async repository method "just to make it compile" is the single most common place this bug enters a C# codebase — it compiles cleanly, runs fine locally under light load, and only deadlocks or starves the thread pool under real concurrent traffic. Spotting a bare .Result or .Wait() anywhere outside test setup code is worth a comment every time.

Scope line

This lesson covers what async/await and Task<T> actually do, how that lines up with Lesson 25's thread-vs-coroutine vocabulary, and the sync-over-async deadlock trap. It does not cover: ValueTask<T> as a lower-allocation alternative to Task<T> for hot paths; Task.WhenAll/Task.WhenAny for running several awaits concurrently instead of one after another; or the compiler-generated state machine class each async method is actually rewritten into. Natural follow-ons, not covered here.
