# The concurrency vocabulary was never taught, under 14 Go lessons that assumed it

User asked, unprompted on 2026-07-30, to have "coroutine, parallel, concurrent, the difference, use case and when to use, also thread meaning" explained — after completing a Go course containing 14 concurrency lessons (`go/lessons/0004`, `0009`–`0014`: goroutines, channels, select, mutex, worker pools, context, errgroup, the memory model). A grep of the whole workspace confirmed the gap is real, not imagined: the word "coroutine" appeared nowhere in any course, and "parallelism" only in passing inside three lessons. The mechanism was taught thoroughly; the vocabulary underneath it never was.

**Implications:** Two things follow. (1) The four words were being held as one undifferentiated cluster, so any earlier lesson that said "runs concurrently" was landing on sand — the fix is Lesson 25's two-questions frame (structure vs execution; kernel-scheduled vs runtime-scheduled) plus the I/O-bound vs CPU-bound decision rule, now compressed into `reference/concurrency-vocabulary.html`. (2) More generally: this course and the Go course teach mechanisms well and can skip the naming layer, because a plausible-looking lesson can be followed end-to-end without the terms ever being pinned down. When a topic has a contested or overloaded vocabulary, teach the vocabulary explicitly rather than assuming it arrives with the mechanism. Worth probing whether the same gap exists for other clusters the user has "covered" — likely candidates: blocking/non-blocking/async/sync, and process vs container vs instance.

**Not yet evidence of learning** — this records the gap and the lesson written for it. Await the user's answers on Lesson 25's retrieval quiz (six questions) before treating the distinction as a new floor.
