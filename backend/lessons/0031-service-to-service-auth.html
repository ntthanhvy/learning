Service-to-service auth: when the caller isn't a person

Lesson 4's rule of thumb said "tokens when multiple independent services must verify identity without calling each other back" — but it never showed how one backend proves its identity to another, with no human, no login form, and no browser cookie anywhere in the picture. Today: three real mechanisms for that, and when each earns its place.

1 · Every auth mechanism so far assumed a human at a browser

Lesson 4 built authentication around a login form: a person types a password once, gets a cookie or JWT back, and the browser carries it on every later request. Lesson 30's webhook lesson broke one assumption — no session at all, just a signed claim — but a person was still, indirectly, the reason the call happened (a payment triggered it). This lesson breaks a second assumption: sometimes the caller is your own backend, calling another backend, on a schedule or in response to internal logic, with no request from any user anywhere upstream. Your order service calling your billing service to charge a card is the shape: two systems you both operate, one machine talking to another.

Not a new problem, a missing mechanism: the question is still "who is this request from" — Lesson 4's question exactly. What's different is the answer can't be "look up a session" or "ask a person to log in," because there's no session and no person. The three options below are just different ways to answer that same question for a machine caller.

2 · Option 1: a static API key — simple, and only as strong as its handling

The simplest mechanism: generate a long random string per calling service, give it to that service out-of-band (a secrets manager, Lesson 21's config layer), and have it send that string on every request. The receiving service checks it against the value it expects — in constant time, for the same reason Lesson 30's HMAC comparison had to be:

// requireServiceAPIKey checks a static, per-service API key on every request.
// Unlike a user password, this key is never hashed on the server side — it's
// compared directly because it's already a random, high-entropy secret, not
// something a human chose and might reuse elsewhere.
func requireServiceAPIKey(next http.Handler) http.Handler {
    want := []byte(os.Getenv("BILLING_SERVICE_API_KEY")) // Lesson 21: a secret is config too
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        got := []byte(r.Header.Get("X-Service-Key"))
        if len(got) == 0 || subtle.ConstantTimeCompare(got, want) != 1 {
            http.Error(w, "invalid service key", http.StatusUnauthorized)
            return
        }
        next.ServeHTTP(w, r)
    })
}

This is Lesson 30's hmac.Equal lesson applied to a plain shared secret instead of a signature — same timing-attack risk, same fix. Its weakness is exactly the one Lesson 30 named for a bare shared-secret header: the key is a single static string, so anyone who intercepts it (a log line, a misconfigured trace, a compromised service) can impersonate the calling service forever until it's rotated. Fine for a small number of internal services you fully control; risky as the only mechanism once more services, or less-trusted ones, are involved.

3 · Option 2: OAuth 2.0 client credentials — a short-lived token instead of a forever secret

The client credentials grant fixes the "forever secret" problem by adding a step: the calling service still holds a long-lived client id and secret, but instead of sending that secret on every request, it exchanges it once (or once per token lifetime) with an authorization server for a short-lived access token — typically a JWT, Lesson 4's other design — and sends that on each call. If a token leaks, it's only useful until it expires, often minutes; the long-lived secret itself is exchanged rarely, so it's exposed far less often.

Static API keyClient credentials grant
What travels on every callThe long-lived secret itselfA short-lived token derived from the secret
Blast radius of one leakValid until manually rotatedValid only until the token expires
Moving partsJust the two servicesAdds a third party: the authorization server
Typical fitA handful of internal services you ownThird-party integrations, many callers, compliance needs

The trade-off is real, not free: a third party (the authorization server) is now in the request path for every token refresh, and that's one more system that can be slow or down. This is why a static key is still a completely reasonable choice for two services inside the same team's infrastructure — the extra moving part has to earn its cost.

4 · Option 3: mutual TLS — proving identity below the HTTP layer entirely

Both options above send a secret inside the request — a header value the application code checks. mTLS moves the check a layer lower: the calling service presents a client certificate as part of the TLS handshake, and the server only completes that handshake if the certificate is signed by a certificate authority it's configured to trust. No secret ever travels inside a request body or header — the identity proof happens before a single byte of the HTTP request is read.

// newMTLSServer wires up mutual TLS: the server only completes the TLS
// handshake if the caller presents a certificate signed by a CA in
// caCertPool. No bearer secret travels in the request at all — the identity
// check happens below the HTTP layer, before a single byte of the request
// is read.
func newMTLSServer(handler http.Handler, caCertPool *x509.CertPool) *http.Server {
    return &http.Server{
        Addr:    ":8443",
        Handler: handler,
        TLSConfig: &tls.Config{
            ClientCAs:  caCertPool,
            ClientAuth: tls.RequireAndVerifyClientCert,
        },
    }
}

The strength is also the cost: nothing to leak in application logs (there's no header value to accidentally print), and revocation is a certificate-authority operation rather than an app-level rotation. But issuing, distributing, and rotating certificates for every service is real operational machinery — usually something a service mesh or platform team owns, not something one backend developer wires up by hand per service. Per MISSION.md's own scope, the certificate-management infrastructure itself (a private CA, a service mesh) is out of scope here — what matters at this level is recognizing the shape and knowing it exists as the strongest of the three options.

5 · Picking one

Rule of thumb going into an interview: static API key for a small number of internal services you fully control and can rotate easily; client credentials (OAuth) when a third party or many independent teams need to call you and you want short-lived, revocable tokens without owning certificate infrastructure; mTLS when the platform already provides it (many service meshes do this automatically) or the security bar genuinely requires no secret ever appearing in a request at all.

All three answer the same question Lesson 4 first asked — "who is this request from" — for a caller that isn't a person. None of them is "more secure" in the abstract, same as Lesson 4's session-vs-JWT verdict: each trades complexity for a different guarantee, and the right one depends on how many callers there are, who operates them, and what already exists in your infrastructure.

Q: "Two of our backend services need to talk to each other. How would you authenticate that call?" A strong answer, out loud: "First I'd ask how many callers and how much I trust them — for a couple of internal services on the same team, a static API key with a constant-time comparison is simple and enough, as long as it's stored as config and rotated occasionally. If it's a third-party integration or many independent callers, I'd lean toward OAuth's client credentials grant, so what travels on each request is a short-lived token instead of a forever secret. If the platform already supports mutual TLS, that's the strongest option since there's no secret in the request at all — the identity check happens in the TLS handshake itself, before the application even sees the request." The signal: naming the trade-off (fewer moving parts vs. shorter-lived exposure vs. no secret in the request path) instead of asserting one option is simply "the secure one."
