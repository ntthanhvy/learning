np.argmax() / np.argmin(): positions, flattening, and a NaN trap idxmax() doesn't have

Lessons 91 and 92 both mentioned np.argmax() in passing — once as the position-vs-label contrast to idxmax(axis=1), once as a carried-forward open candidate — but neither gave it its own depth. A fresh scan today confirmed it's still a real zero-coverage gap on its own merits, and it earns the slot: there are two behaviors here that have nothing to do with the axis=1 angle already taught, and one of them is a genuine silent-wrong-answer trap that idxmax() simply doesn't have.

1 · No axis= at all flattens the whole array first — a different default from idxmax()

Lesson 20's idxmax() defaults to axis=0 — one answer per column. np.argmax() has no such default at all — called with no axis=, it collapses the entire array into one flat sequence first, then returns a single integer position into that:

arr = np.array([[3, 7, 2],
                [5, 5, 1],
                [0, 0, 0]])

np.argmax(arr)
-- 1   (flattened: [3,7,2,5,5,1,0,0,0] -- position 1 is the 7)

np.argmax(arr, axis=1)
-- array([1, 0, 0])   -- NOW one answer per row, position within each row

Confirmed directly against the official NumPy docs (which state it plainly: "the index is into the flattened array") and by probing it: leaving off axis= on a 2-D array doesn't raise, doesn't error, and doesn't even look wrong at a glance — it just silently answers a completely different question than "which row/column." Translating a flat index back to a real (row, col) position needs np.unravel_index():

flat = np.argmax(arr)
np.unravel_index(flat, arr.shape)
-- (0, 1)   -- row 0, column 1 -- confirmed: arr[0, 1] is indeed 7, the true max

The interview-shaped trap: calling np.argmax(df.to_numpy()) on a DataFrame and expecting a per-row or per-column answer without ever typing axis= — it silently returns a flat position into the whole table instead, one number where several were expected, with no error to flag the mistake.

2 · Ties resolve to the first occurrence, by position — same rule as idxmax()

This part matches what Lessons 20 and 91 already established for idxmax()/idxmin(), confirmed directly here too so the rule can be trusted across both tools: a flat three-way tie resolves to the earliest position, not the largest or an arbitrary pick.

tie = np.array([4, 9, 9, 2])
np.argmax(tie)
-- 1   -- the FIRST 9 (index 1), not index 2

One tie rule, consistently applied across idxmax(), idxmin(), np.argmax(), and np.argmin() — nothing new to memorize here, just confirming it travels.

3 · The real trap: a NaN can silently win np.argmax(), where idxmax() would have skipped it

Lesson 91 taught that idxmax(axis=1)'s default skipna=True quietly skips NaN values and returns the best real value among what's left. np.argmax() has no skipna parameter at all — confirmed directly via inspect.signature(), its signature is only (a, axis=None, out=None, *, keepdims=<no value>) — and that absence isn't cosmetic, it changes the actual answer:

nan_arr = np.array([1.0, np.nan, 3.0])

np.argmax(nan_arr)
-- 1   -- points AT the NaN itself, not at 3.0, the real max

pd.Series(nan_arr).argmax()
-- 2   -- pandas' own Series.argmax() DOES skip the NaN, lands on 3.0

Confirmed directly: pd.Series.argmax() carries a real skipna=True keyword in its signature (inspect.signature() shows axis=None, skipna=True) and correctly returns position 2, the genuine maximum — but the plain NumPy array version, with no such keyword to reach for, lands on the NaN at position 1 instead, because NaN comparisons are never reliably ordered. That's the sharpest trap in this lesson: the exact same method name, .argmax(), gives two different answers on data that only differs in whether it's wrapped in a Series — no crash either way, just a silently different integer. The fix when NaN is a real possibility and a plain NumPy array (not a Series) is in hand: np.nanargmax(), confirmed directly to return 2 on the same array, skipping the NaN exactly like pandas does by default.

np.nanargmax(nan_arr)
-- 2   -- matches Series.argmax(); the NaN-safe NumPy sibling

Both an all-NaN array and an empty array raise rather than returning a meaningless position — confirmed directly, np.argmax(np.array([])) raises ValueError: attempt to get argmax of an empty sequence, and pd.Series([np.nan, np.nan]).argmax() raises ValueError: Encountered all NA values, the identical message Lesson 91 already met on idxmax()'s all-NA case. So the loud failure only shows up at the extreme (nothing left to compare); the quiet, wrong-answer failure shows up at the much more common case of "just one NaN mixed into real data."

Q: "What's the difference between np.argmax() and idxmax(), and when would a NaN bite me?" A strong answer, out loud: "np.argmax() returns a raw integer position in the underlying array, not a label — and if I call it with no axis= on a multi-dimensional array, it flattens the whole thing first and gives me one flat position, not a per-row or per-column answer, so I'd need np.unravel_index() to translate that back. idxmax() instead returns the real pandas label and respects axis= as 'per row' or 'per column' directly. The NaN trap is the one I'd watch hardest: np.argmax() has no skipna option at all, so if a NaN is sitting in the data, it can actually win — the position it returns points at the NaN itself, not the real maximum, silently, no error. pandas' own Series.argmax() does skip NaN by default because it has a real skipna=True keyword, so the exact same .argmax() name gives two different answers depending on whether the data's wrapped in a Series or sitting in a raw NumPy array. If I'm on a raw array and NaN is possible, np.nanargmax() is the NaN-safe fix." The signal: naming the flatten-by-default behavior and the NaN divergence as two separate, unrelated gotchas, not blurring them into one vague "be careful" — and knowing np.nanargmax() by name as the fix.
