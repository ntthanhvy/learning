Webhook signature verification: trusting a request from outside

Lessons 4, 17, 22, and 23 all guarded requests from your own users. A webhook flips that: a payment processor, a git host, a messaging API calls you, unprompted, claiming to be them. Today: why that claim can't be trusted on its own, and the one mechanism (HMAC signing) that lets you verify it.

1 · A webhook endpoint is a URL anyone can find and POST to

Lessons 24 and 29 both mentioned webhooks in passing — SSRF's "the server fetches whatever URL the client sent" and the outbox pattern's "publish to a message queue or webhook" — but neither taught the endpoint that receives one. That endpoint looks ordinary: POST /webhooks/payments, a JSON body, a 200 response expected back. Nothing about the URL itself is secret — it's often visible in your own dashboard config, sometimes guessable, and always just an HTTP endpoint like any other.

That's the problem. A normal request carries a session cookie or a bearer token proving which of your users is calling — Lesson 4's whole subject. A webhook has no user session at all; the caller claims to be Stripe, or GitHub, or Twilio, but anyone who finds the URL can send an identical-looking POST claiming the same thing. A handler that reads event.type == "payment.succeeded" and marks an order paid, with no check on where that claim came from, will happily mark an order paid because a stranger's curl command said so.

Not the same gap as IDOR: Lesson 12's IDOR was "authenticated as someone, but never checked it was the right someone." A webhook without signature verification is one step earlier — there's no authentication at all, just an unverified claim of identity sitting in the request body.

2 · Why a shared secret in a header isn't enough by itself

The obvious first fix — put a secret token in a custom header, check it matches — is close, but it's checking the wrong thing. A header value is just a string sitting in transit; if it ever leaks (a proxy log, a debugging screenshot, a misconfigured CORS setup echoing headers back), anyone holding that one static string can forge any body they like, forever, until the secret is rotated. What you actually want to prove is narrower: this exact body, unmodified, was produced by someone who holds the secret — not just "someone once knew a password."

That's what an HMAC (Hash-based Message Authentication Code) gives you: the sender computes a tag over the exact request body using the shared secret, attaches that tag as a header, and you recompute the same tag on your side over the bytes you actually received. If they match, two things are simultaneously proven — the body came from someone holding the secret, and it wasn't altered in transit, because changing even one byte of the body produces a completely different tag.

3 · Verifying against the raw bytes, not the parsed struct

The signature is computed over the request body's exact bytes — so verification has to happen before any JSON parsing, against those same raw bytes, not against a struct you decoded and could re-serialize slightly differently (key order, whitespace, number formatting all change the bytes without changing the meaning). Verify first, parse second — reversing that order defeats the whole point, since a forged body would already be trusted by the time you check it.

var webhookSecret = []byte(os.Getenv("WEBHOOK_SECRET")) // Lesson 21: a secret is config too

// verifySignature recomputes the HMAC-SHA256 over the raw body using the
// shared secret, then compares it to the signature the sender attached —
// in constant time, so a timing side-channel can't leak the right value
// one byte at a time.
func verifySignature(body []byte, gotSignatureHex string) bool {
    mac := hmac.New(sha256.New, webhookSecret)
    mac.Write(body)
    want := mac.Sum(nil)

    got, err := hex.DecodeString(gotSignatureHex)
    if err != nil {
        return false
    }
    return hmac.Equal(want, got) // NOT want == string(got) or bytes.Equal
}

func webhookHandler(w http.ResponseWriter, r *http.Request) {
    body, err := io.ReadAll(r.Body)
    if err != nil {
        http.Error(w, "cannot read body", http.StatusBadRequest)
        return
    }

    signature := r.Header.Get("X-Webhook-Signature")
    if signature == "" || !verifySignature(body, signature) {
        http.Error(w, "invalid signature", http.StatusUnauthorized)
        return // unverified — never reaches json.Unmarshal
    }

    // only now is it safe to parse and act on the body
    var event PaymentEvent
    json.Unmarshal(body, &event)
    w.WriteHeader(http.StatusOK)
}

The one deliberate, easy-to-miss detail: comparing tags with hmac.Equal, never == or a hand-rolled byte loop. A naive comparison returns as soon as it finds the first mismatched byte, so a forger measuring response times can learn the secret's tag one correct byte at a time — a timing attack. hmac.Equal always compares every byte in constant time regardless of where the first difference is, closing that leak.

4 · Real services do exactly this — same shape, different envelope

This isn't a hypothetical construction — it's what production webhook providers actually ship. Stripe sends a Stripe-Signature header containing a timestamp plus an HMAC-SHA256 tag computed over timestamp + "." + body (the timestamp defeats replaying an old, validly-signed request later); GitHub sends X-Hub-Signature-256, an HMAC-SHA256 tag over the raw body alone. Different header names, same core idea: a secret both sides know, a tag computed over exact bytes, compared in constant time.

Frontend-habit trap: there's no client-side equivalent to reach for here. A frontend never receives unsolicited server-to-server callbacks — every request it handles starts because it called something, or the user clicked. Webhook verification is a genuinely backend-only problem: proving the origin of a request nobody in your own UI ever asked for.

Q: "How do you make sure a webhook actually came from the provider that claims to have sent it?" A strong answer, out loud: "I'd verify an HMAC signature, not just check a static shared-secret header. The provider signs each request body with a secret only we both hold and sends that signature in a header; on my side I recompute the same HMAC over the exact raw bytes I received and compare it to theirs. If they match, I know the body wasn't tampered with in transit and came from someone holding the secret. Two details matter: I verify against the raw body before any JSON parsing, since parsing and re-serializing can change the bytes, and I compare the tags with a constant-time function like Go's hmac.Equal, not a plain equality check, so timing can't leak the correct value byte by byte." The signal: naming that it's the raw bytes being signed, and that comparison must be constant-time.
