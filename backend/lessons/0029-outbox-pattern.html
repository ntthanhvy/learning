The outbox pattern: making a DB write and an event atomic

Lesson 28's closing teaser named the last untaught candidate from Lesson 27's search: the outbox pattern. Circuit breaker (L28) and graceful shutdown (L27) are both done — this closes the set. Today: what happens when "update the row" and "tell everyone else about it" are two separate systems, and the trick that makes them act like one.

1 · Two systems, one moment, no shared transaction

Say createOrder does two things: insert the order row into Postgres, and publish an order.created event so a shipping service, an email service, and an analytics pipeline can react. Each of those two things talks to a different system — Postgres for the row, a message queue or webhook for the event — and nothing ties them together. That's the dual-write problem: whatever order you do the two writes in, a crash between them leaves the two systems disagreeing.

Insert the row, then crash before publishing: the order exists, but nobody downstream ever hears about it — a silently lost event. Publish first, then crash before the insert commits: a shipping service starts shipping an order that doesn't actually exist in the database yet, or ever will if the insert then fails. Retry your way out of the first case (publish again if you're not sure it went out) and you risk the opposite fault: publishing twice, which is Lesson 26's world — safe only if the subscriber also tolerates a duplicate. There is no ordering of "write to Postgres" and "call the queue" that is safe by itself, because they're two separate systems and only one of them is the one your code can wrap in a transaction.

Frontend-habit trap: in frontend code, "update the UI state and fire an analytics event" failing halfway is usually harmless — worst case, one dropped analytics ping. Here, the downstream event can be the trigger for shipping a physical order or charging a card again; a lost or duplicated event is a real business event, not a missing dot on a chart.

2 · The trick: write the event into the SAME database, in the SAME transaction

The fix doesn't make the two systems agree directly — it sidesteps the problem by turning "publish an event" into "write one more row," in the one database that already has transactions. Alongside the real orders table, add an outbox table — one row per event, holding a topic, a payload, and a processed timestamp that starts NULL. The handler inserts the order row and the outbox row inside one BEGIN…COMMIT:

func createOrder(ctx context.Context, db *sql.DB, o Order) error {
    tx, err := db.BeginTx(ctx, nil)
    if err != nil {
        return err
    }
    defer tx.Rollback() // no-op if Commit already ran

    _, err = tx.ExecContext(ctx,
        `INSERT INTO orders (id, customer_id, total_cents) VALUES ($1, $2, $3)`,
        o.ID, o.CustomerID, o.TotalCents,
    )
    if err != nil {
        return err
    }

    payload, err := json.Marshal(OrderShippedEvent{OrderID: o.ID, CustomerID: o.CustomerID})
    if err != nil {
        return err
    }

    // Same transaction, same connection, same all-or-nothing guarantee
    // as the INSERT above — this is the whole trick.
    _, err = tx.ExecContext(ctx,
        `INSERT INTO outbox (id, topic, payload, created_at, processed_at)
         VALUES (gen_random_uuid(), $1, $2, now(), NULL)`,
        "order.created", payload,
    )
    if err != nil {
        return err
    }

    return tx.Commit()
}

This is exactly Lesson 6's atomicity, applied to a business row and an "event to publish" instead of two business rows: either both INSERTs land, or neither does. There is no window where the order exists but the outbox row doesn't, or vice versa — the dual-write problem is solved not by making Postgres and the message queue agree, but by never writing to the message queue in the request path at all. The whole pattern is called the transactional outbox pattern for exactly this reason.

3 · The relay: a second process that actually publishes

The outbox table now holds a durable, ordered to-do list of events — but nothing has actually reached the message queue yet. That's the job of a separate relay (also called a poller): it reads unprocessed rows, calls the real publisher, and marks each row done once the call succeeds.

func outboxRelay(ctx context.Context, db *sql.DB, pub Publisher, pollEvery time.Duration) {
    ticker := time.NewTicker(pollEvery)
    defer ticker.Stop()

    for {
        select {
        case <-ctx.Done():
            return
        case <-ticker.C:
            if err := relayOnce(ctx, db, pub); err != nil {
                log.Printf("outbox relay: %v", err)
            }
        }
    }
}

func relayOnce(ctx context.Context, db *sql.DB, pub Publisher) error {
    rows, err := db.QueryContext(ctx,
        `SELECT id, topic, payload FROM outbox
         WHERE processed_at IS NULL
         ORDER BY created_at
         LIMIT 100`,
    )
    if err != nil {
        return err
    }
    defer rows.Close()

    var batch []outboxRow
    for rows.Next() {
        var r outboxRow
        if err := rows.Scan(&r.ID, &r.Topic, &r.Payload); err != nil {
            return err
        }
        batch = append(batch, r)
    }

    for _, r := range batch {
        // At-least-once: if Publish succeeds but the process dies before
        // the UPDATE below runs, this row gets published again next poll.
        if err := pub.Publish(ctx, r.Topic, r.Payload); err != nil {
            log.Printf("publish failed, will retry next poll: %v", err)
            continue
        }
        if _, err := db.ExecContext(ctx,
            `UPDATE outbox SET processed_at = now() WHERE id = $1`, r.ID,
        ); err != nil {
            return err
        }
    }
    return nil
}

Notice what the relay actually is: a standalone loop that wakes up on a timer, does work, and is never called from inside any HTTP handler — that's Lesson 10's background job definition, word for word. The relay is a background job; the outbox table is its job queue, "unprocessed rows" is the queue's pending set, and the relay is the worker.

4 · The relay's publish must survive being run twice

Look at the gap between pub.Publish(...) succeeding and the UPDATE ... SET processed_at that follows it. If the relay process dies in that gap — after the message genuinely reached the queue, before the row was marked processed — the next poll sees that row as still unprocessed and publishes it again. The event arrives twice.

Same shape as Lesson 26: this is exactly the "did it actually happen?" ambiguity Lesson 26 built idempotency keys to survive on the client's retry path, and Lesson 10 named outright for job queues: at-least-once delivery — a message might be delivered more than once, but it is never silently dropped. The relay can't promise exactly-once delivery to the queue any more than a background job worker could promise exactly-once execution; it can only promise at-least-once, which pushes the same requirement Lesson 26 and Lesson 10 both landed on onto whoever consumes the event: the subscriber's handling of order.created must be safe to run twice — check "have I already shipped this order?" before shipping, the same idempotency instinct applied one hop further down the chain.

This is why the transactional outbox pattern doesn't claim to solve dual-write by making delivery perfectly exactly-once — no practical mechanism across two separate systems can promise that. It solves the actual hazard: a crash can no longer silently lose the event (it's durably recorded in the same transaction as the business row), and a crash can at worst cause a harmless-if-idempotent duplicate — trading an unrecoverable loss for a recoverable, expected duplicate.

Q: "You need to update a row and publish an event when it changes. Why not just do both in the handler?" A strong answer, out loud: "Because the database write and the publish are two separate systems, and there's no ordering of the two calls that's safe on its own — a crash between them either loses the event or, if I retry to be safe, risks publishing it twice. I'd use the transactional outbox pattern instead: insert an outbox row in the same transaction as the business write, so they commit or roll back together — that's just Lesson 6's atomicity applied to an event instead of a second business row. A separate relay process polls that table, publishes each unprocessed row to the real queue, and marks it processed. The relay itself is a background job in the same sense as any other worker, and because a crash between publishing and marking-processed can cause a duplicate, the subscriber on the other end still has to tolerate at-least-once delivery — same idempotency requirement as any other queue consumer." The signal: naming the dual-write problem specifically, not just "queues can drop messages," and tying the relay's guarantee back to at-least-once rather than claiming it's perfect.
