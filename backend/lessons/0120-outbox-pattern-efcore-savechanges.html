The outbox pattern, now in C# too

Lesson 29 solved the dual-write problem in Postgres: insert the business row and an outbox row inside the same hand-written BEGIN…COMMIT, so a crash can't lose the event, only at-worst duplicate it. That lesson never got a C# mirror, even though the rest of the Lesson 11–50 resilience set — rate limiting, retry, circuit breaker, bulkhead, worker pools, graceful shutdown, health checks, optimistic locking — has been ported since Lesson 112. Today closes that gap: the same same-transaction trick, built from EF Core's own default SaveChanges() behavior instead of a hand-written transaction.

1 · Same idea, one call to SaveChanges instead of a hand-written transaction

Lesson 29's rule still holds exactly: the business row and the outbox row must commit or roll back together, or a crash between two separate writes either loses the event or risks duplicating it. What changes in EF Core is that nobody writes BeginTx/Commit by hand for the common case. Per Microsoft's own docs: "by default, if the database provider supports transactions, all changes in a single call to SaveChanges are applied in a transaction... SaveChanges is guaranteed to either completely succeed, or leave the database unmodified if an error occurs." Add both rows to the same tracked DbContext and call SaveChangesAsync() once:

public class OutboxMessage
{
    public Guid Id { get; set; }
    public string Topic { get; set; }
    public string Payload { get; set; }   // -- same role as Lesson 29's "payload" column
    public DateTime CreatedAt { get; set; }
    public DateTime? ProcessedAt { get; set; }  // null until the relay publishes it
}

public async Task CreateOrderAsync(Order order)
{
    db.Orders.Add(order);
    db.OutboxMessages.Add(new OutboxMessage
    {
        Id = Guid.NewGuid(),
        Topic = "order.created",
        Payload = JsonSerializer.Serialize(new { order.Id, order.CustomerId }),
        CreatedAt = DateTime.UtcNow,
    });

    // One call, one implicit transaction -- both rows commit or neither does.
    await db.SaveChangesAsync();
}

This is Lesson 29's exact guarantee, from a different source: there is no window where the order row exists but the outbox row doesn't, or vice versa, because both inserts are two pending changes inside one SaveChangesAsync() call rather than two separate statements the application has to wrap itself.

2 · The building block: EF Core's implicit SaveChanges transaction

The mechanism behind that guarantee is a plain EF Core feature, not anything outbox-specific — it is the same SaveChanges implicit transaction any multi-entity save already relies on. It applies here because the outbox row and the order row are just two more pending changes on the same DbContext — EF Core doesn't know or care that one of them happens to be an event waiting for a relay.

The one new rule it brings: the docs also flag that "manually controlling transactions... is incompatible with implicitly invoked retrying execution strategies" — if a resilient SQL provider retries a failed SaveChanges call under the hood, wrapping it in your own hand-written transaction can break that retry. The outbox write above avoids the problem entirely by staying inside the implicit default rather than opening a transaction by hand, same as Lesson 29's Go code did deliberately with its own explicit BeginTx.

3 · The relay: still a background job, same as Lesson 29's

Nothing about the relay's job changes crossing languages: poll the outbox table for unprocessed rows, publish each one, mark it processed. In C# the natural home for that loop is the BackgroundService base class already covered in Lesson 105 — a long-lived, timer-driven loop that starts with the host and is never called from inside a request:

public class OutboxRelay : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var batch = await db.OutboxMessages
                .Where(m => m.ProcessedAt == null)
                .OrderBy(m => m.CreatedAt)
                .Take(100)
                .ToListAsync(stoppingToken);

            foreach (var m in batch)
            {
                // At-least-once: dying between Publish and SaveChangesAsync below
                // republishes this same row next poll -- same gap Lesson 29 named.
                await publisher.PublishAsync(m.Topic, m.Payload, stoppingToken);
                m.ProcessedAt = DateTime.UtcNow;
                await db.SaveChangesAsync(stoppingToken);
            }

            await Task.Delay(TimeSpan.FromSeconds(5), stoppingToken);
        }
    }
}

Lesson 105's own vocabulary applies unchanged: this is an IHostedService (via the BackgroundService base class), registered once with AddHostedService<OutboxRelay>(), living for the process's whole lifetime rather than being created per request like a controller. The outbox table is still the queue, "unprocessed rows" is still the pending set, and the relay is still the worker — Lesson 29's framing, unchanged by which runtime is polling.

Scope line

This lesson covers EF Core's implicit SaveChanges transaction as the C# mechanism for Lesson 29's transactional outbox pattern, plus using Lesson 105's BackgroundService as the relay. It does not cover DbContext.Database.AutoTransactionBehavior's Always/Never settings or manual BeginTransactionAsync() control in any depth — only the one documented incompatibility with retrying execution strategies, flagged because it is the one new trap this port introduces; savepoints, which the same docs page covers as a separate feature for recovering mid-SaveChanges errors; or any message-broker-specific relay library (e.g. Debezium-style CDC from Lesson 87, MassTransit's own outbox support) — those are a deeper dive this lesson deliberately leaves for later, per MISSION.md's concepts-first rule.
