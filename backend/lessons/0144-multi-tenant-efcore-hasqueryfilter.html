Multi-tenant data, now in C# too (EF Core HasQueryFilter)

Lesson 78 picked a shape for multi-tenant data (shared schema with a tenant_id column, schema-per-tenant, or database-per-tenant) and leaned on Lesson 59's row-level security to make a shared table's isolation not depend on every handler remembering WHERE tenant_id = .... EF Core's shared-schema answer to that same forgotten-WHERE problem is a model-level setting, not a database policy: HasQueryFilter, a filter attached once to an entity type that EF Core then applies to every LINQ query against it automatically.

1 · The same gap, enforced one layer up

Lesson 59's row-level security policy lives in Postgres itself — it rewrites a query's WHERE clause inside the database, so even a raw psql session or a buggy script can't bypass it by accident. A global query filter lives one layer up, inside the application's own object-relational mapper — it rewrites the LINQ query before EF Core ever generates SQL, so any code going through that DbContext gets the filter, but code that bypasses EF Core entirely (raw ADO.NET, a different service hitting the same database) gets no protection at all. Same forgotten-WHERE problem Lesson 78 named for shared schema, same "make the framework remember it instead of the developer" fix Lesson 59 used — enforced at a different point in the stack, with a correspondingly different blast radius if something reaches the database some other way.

2 · Soft deletion first, because it's the filter with no moving parts

Microsoft's own docs introduce HasQueryFilter through soft deletion, not multi-tenancy, because it's the simplest case — the filter needs no outside information, just a column on the row itself:

public class Blog
{
    public int Id { get; set; }
    public bool IsDeleted { get; set; }
    public string Name { get; set; }
}

protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Blog>().HasQueryFilter(b => !b.IsDeleted);
}

From this point on, context.Blogs.ToListAsync() never returns a row where IsDeleted is true — EF Core adds that condition itself, the same way Lesson 139's SaveChanges override added an audit row without the caller asking for one. Nothing about the shape of the query changes; the filter is additive, invisible until a row disappears from a result set that should have had it.

3 · Multi-tenancy: the filter needs to know who's asking

Soft deletion's filter only reads a column. A tenant filter needs the current tenant — information that isn't on the row's own type, it's on whoever opened the DbContext. Microsoft's docs solve this by taking the tenant ID as a constructor parameter and referencing it directly from the filter lambda:

public class MultitenancyContext(string tenantId) : DbContext
{
    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Blog>().HasQueryFilter(b => b.TenantId == tenantId);
    }
}

This is Lesson 78's shared-schema shape, expressed as C# instead of a Postgres policy: every Blog carries a TenantId column, and this filter is the WHERE tenant_id = ... that section 3 of that lesson said every query needs, attached once instead of copy-pasted into every handler. Constructing MultitenancyContext without a tenant ID simply isn't possible — the constructor forces the caller to supply one, so there is no code path through this context type that can query without the filter already wired in.

Frontend-habit trap: it's tempting to read HasQueryFilter as something configured once at startup, the way AddDbContext is. It isn't — the filter lambda closes over tenantId, a value tied to one request, so a new MultitenancyContext gets built (and the filter re-evaluated against the current tenant) on every request, exactly like a React component re-rendering with new props rather than configuring itself once on mount.

4 · Escaping the filter on purpose, and the one place it quietly stops working

An admin tool or a background job legitimately needs to see every tenant's rows. IgnoreQueryFilters() is the documented escape hatch — one LINQ operator, applied per query, not a config flag flipped for the whole context:

var allBlogs = await context.Blogs.IgnoreQueryFilters().ToListAsync();

The sharper catch is Include(). Microsoft's docs show a required Blog–Post relationship where Blog carries a query filter: querying Posts directly returns every post, but Posts.Include(p => p.Blog) returns only the posts whose blog survives the filter — because a required navigation compiles to an INNER JOIN, and a filtered-out Blog row silently drops its Post rows out of the join too. The fix the docs name is either making the navigation optional (an EF-generated LEFT JOIN instead) or putting a matching filter on Post itself, so both entity types agree on which tenant's rows exist before any join runs.

Neither replaces the other's job description from Lesson 78: the choice of shape (shared schema, schema-per-tenant, database-per-tenant) is still a schema design decision made once, independent of which language queries it. HasQueryFilter is what a shared-schema choice looks like from inside an EF Core codebase specifically — the C# counterpart to Lesson 59's Postgres policy, not a fourth shape.

Q: "Our ASP.NET Core app uses EF Core against a shared multi-tenant table. How do we stop a forgotten tenant filter from leaking another tenant's rows?" A strong answer, out loud: "I'd put a global query filter on the entity type in OnModelCreating, referencing the current tenant ID from something the DbContext itself holds — a constructor parameter, typically — so the filter is attached once and applies to every query automatically instead of relying on every LINQ query remembering a Where clause by hand. I'd watch for Include() on a required navigation, though — that compiles to an inner join, and a filtered-out parent row can silently drop its children out of the result too, so I'd either make the navigation optional or filter the child type the same way. And for admin tooling that legitimately needs every tenant's rows, IgnoreQueryFilters() is the explicit, per-query escape hatch — not disabling the filter globally." The signal: naming where the filter lives, the join caveat as a real failure mode rather than an edge case, and that the escape hatch should be a deliberate per-query choice.

Scope line

This lesson covers HasQueryFilter's soft-deletion and multi-tenancy shapes, IgnoreQueryFilters(), and the required-navigation/Include() join caveat. It does not cover EF Core 10's named multiple-filters syntax (HasQueryFilter("Name", ...), allowing more than one filter per entity type and selective disabling), combining filters pre-EF-10 via && in one lambda, or the IEntityTypeConfiguration<TEntity> workaround for referencing a context-scoped value without an instance in scope — all named in the primary source but left for a dedicated lesson if picked up later.
