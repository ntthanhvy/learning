1 · Three questions, in the original teaching order

Answer each out loud or on paper before reading the fold-out answer. If one is shaky, note it and go fix it in the practice file below rather than only rereading the old lesson.

Day 88 — collections.ChainMap. A ChainMap never copies or merges its input dicts. What does that buy you that a one-time {**defaults, **user_config, **cli_flags} merge does not, and which dict actually changes when you assign through the ChainMap?

Fold-out answer: because a ChainMap holds a live reference to each original dict rather than a copy, editing one of those dicts later (say, the user's config file reloads) is visible through the ChainMap immediately — a one-time merge is a frozen snapshot that silently stops tracking the sources the moment it's built. Assigning through the ChainMap always writes into the first dict in the chain, confirmed live, regardless of which layer a key currently resolves from during lookup — it behaves like "record a new override at the highest-priority layer," never "edit wherever this key happens to live."

Day 89 — hmac. Why can't a plain hashlib.sha256(data) digest prove who sent a message, and why does hmac.new(key, msg) raise TypeError if digestmod is left out?

Fold-out answer: hashlib.sha256(data) takes no secret at all — it is a pure function of the bytes, so anyone holding the same data computes the identical digest with no special knowledge, attacker included; that proves content didn't change, not who produced it. hmac.new() has no default hash algorithm the way hashlib.sha256()'s own name already picks one, so per the standard library docs digestmod is required "despite its argument position" — confirmed live, omitting it raises TypeError: Missing required argument 'digestmod' rather than silently guessing an algorithm the other side might not expect.

Day 90 — graphlib. After ts.add("package", "test"), what does static_order() guarantee about the two, and what happens instead of a wrong-looking order when the dependencies contain a cycle?

Fold-out answer: ts.add(node, *predecessors) always reads as "node depends on each of predecessors," so static_order() guarantees "test" comes before "package" in its returned sequence, every time. A cycle means two or more nodes depend on each other, directly or through others, so no legal order exists at all — TopologicalSorter does not guess or quietly drop a node to manufacture one; confirmed live, it raises graphlib.CycleError naming the exact loop it found (('nodes are in a cycle', ['x', 'y', 'x']) for a two-node cycle).

2 · Why these three, and why no new terms today

Same interleaving logic as every prior review day: a tool for searching several dicts as layered priority without merging them, a tool for proving a message came from someone holding a shared secret, and a tool for ordering a set of tasks by "must happen before" instead of by value — three different mental models pulled from three lessons, not one idea restated three ways. They also share a quieter throughline worth naming: all three replace a hand-rolled version that looks right at first and then breaks in one specific, predictable way once real use pushes on it — a merged settings dict that stops tracking its sources, a concatenated hash that proves nothing about origin, a hand-written step order that silently drifts once dependencies change or loop back on themselves. Recognizing which of those three failure shapes a given problem is actually at risk of — not just recalling the function names — is the retrieval goal today.
