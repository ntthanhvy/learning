heapq & bisect: sorted order without re-sorting

Day 4 taught sorted(key=...) for "give me everything, in order, once." Today is the other half: what to reach for when the data keeps arriving, or the question is only ever "what's smallest?" or "where would this fit?" — a heap via heapq, and binary search on an already-sorted list via bisect.

Bridge from SQL: heapq's job is what ORDER BY x LIMIT 1 does incrementally — the database never fully sorts the table just to hand you the smallest row, and a heap gives Python the same trick as data streams in. bisect is closer to an index lookup on a sorted column: instead of scanning every row, it jumps straight to where a value belongs.

1 · The problem both modules solve: don't re-sort what's already (mostly) sorted

The obvious way to track "the 3 smallest values seen so far" is to keep appending to a list and calling sorted() every time a new value needs checking:

seen = [42, 17, 8, 91, 23]
seen.append(5)
seen.sort()               # re-sorts EVERYTHING, every single time
three_smallest = seen[:3]

That works, but it throws away the fact that the list was already in order a moment ago — sort() is O(n log n) on the whole collection, paid again on every insert. When data keeps arriving, or the collection is large and only the extreme values matter, that's wasted work repeated over and over.

2 · heapq: always know the smallest, without sorting the rest

heapq turns a plain list into a priority queue: a collection specialized for one question, "what's smallest right now?", answered fast even as items keep coming and going:

import heapq

tasks = []
heapq.heappush(tasks, (3, "write report"))
heapq.heappush(tasks, (1, "fix outage"))
heapq.heappush(tasks, (2, "review PR"))

tasks[0]                    # (1, 'fix outage') -- smallest is always at index 0
heapq.heappop(tasks)         # (1, 'fix outage') -- removes and returns it
heapq.heappop(tasks)         # (2, 'review PR')

Verified live: after the two pops, tasks == [(3, 'write report')]. Each heappush/heappop costs O(log n), not O(n log n) for a full re-sort — the list is kept in heap order (a weaker condition than fully sorted: only "each parent ≤ its children" holds), which is just enough structure to make "give me the smallest" and "put this back in order" both cheap. heapq is a min-heap only — the smallest item comes out first. Tuples like (priority, task) compare element-by-element (Day 28's unpacking, working in reverse here), so the first tuple slot doubles as the sort key without needing key= at all.

3 · Wanting the largest instead: negate, don't reinvent

There's no separate max-heap type in the standard library — the documented idiom is to push negated numbers, so the mathematically smallest negated value is the actual largest:

import heapq

scores = []
for s in [88, 95, 71, 99, 60]:
    heapq.heappush(scores, -s)   # push the negation

top_score = -heapq.heappop(scores)   # negate back on the way out -- 99

Verified live: top_score == 99. For the common case of just "the N largest/smallest of a collection I already have," skip manual pushing entirely — heapq.nlargest(n, iterable) and heapq.nsmallest(n, iterable) do this in one call, more efficiently than sorting the whole thing when n is small relative to the collection:

import heapq

scores = [88, 95, 71, 99, 60]
heapq.nlargest(2, scores)    # [99, 95]
heapq.nsmallest(2, scores)   # [60, 71]

4 · bisect: finding a spot in a sorted list without scanning it

bisect answers a different question: given a list that is already sorted, where does a new value belong, or where does an existing value live — without checking every element:

import bisect

grades = [60, 70, 80, 90]   # cutoffs, already sorted
labels = ["F", "D", "C", "B", "A"]

def grade_for(score):
    i = bisect.bisect_right(grades, score)
    return labels[i]

grade_for(85)   # "B" -- 85 falls in the (80, 90] bucket
grade_for(90)   # "A" -- bisect_right puts an exact match after equal values

Verified live: both calls match the comments. bisect_right(grades, score) returns how many cutoffs are <= score — a binary search over the list, O(log n) instead of checking each cutoff in turn. bisect_left is the sibling that breaks a tie the other way, putting an exact match before equal existing values; the difference only matters when duplicates are possible. bisect.insort(seq, value) inserts a value into a sorted list at the correct position in one call, keeping it sorted without a full re-sort:

import bisect

scores = [60, 75, 90]
bisect.insort(scores, 82)
scores   # [60, 75, 82, 90] -- inserted in place, still sorted

Verified live: matches the comment exactly.

5 · Picking between them

heapq is for a collection that keeps changing and where only the extreme end (smallest, or largest via negation) is ever asked for — a live leaderboard, a task queue, "top N so far" over a stream too large to hold sorted. bisect is for a collection that's sorted and mostly stable, where the question is "where does X belong" or "what's the closest cutoff to X" — grade bands, rate-limit tiers, keeping a sorted list of timestamps. Neither replaces sorted() for the everyday "give me the whole thing in order, once" case Day 4 already covers — both exist for the narrower jobs where re-sorting on every change would be wasted work.

Where pandas goes from here: nothing pandas-specific — a pandas Series has its own nlargest()/nsmallest() methods for the whole-column version of this question, backed by NumPy's sort rather than a heap; heapq/bisect are for plain Python lists and streaming data instead, not demonstrated here since that would mean showing a pandas API, out of scope per MISSION.md.

Q: "How would you efficiently track the top 3 values from a stream of numbers too large to hold in memory sorted?" A strong answer, out loud: "Keep a small min-heap of size 3 with heapq. For each new number, if the heap has fewer than 3 items, push it; otherwise compare it to the heap's smallest, at index 0, and only push-and-pop if the new number is bigger. That keeps the heap at exactly 3 items and each operation is O(log 3), so the whole stream costs O(n log k) for a stream of n and a top-k of k — never sorting the full stream, and never holding more than k items at once." The signal: naming that the heap size stays bounded at k, not growing with the stream, which is the actual memory win.
