SKIP LOCKED: claiming one job off a queue table without blocking the others

Lesson 10's worker called an unexplained dequeueJob(ctx) — "claim one pending row" — and moved on without saying how a claim actually works when several workers poll the same table at once. Lesson 94 named four table-level lock modes but stopped at row locks still being single-row, single-claimant tools. Today is the missing mechanism: the exact row-lock option that lets many workers claim different rows from the same queue table at the same time, none of them waiting on the others.

1 · What a naive claim actually does under two workers

The obvious way to "claim one pending row" is Lesson 6's own pattern: lock it, check it's still pending, mark it taken.

BEGIN;
SELECT id FROM jobs WHERE status = 'pending' ORDER BY id LIMIT 1 FOR UPDATE;
-- mark it running, do the work, COMMIT

With one worker, this is fine. With two workers polling the same table at the same instant, both run the identical SELECT ... FOR UPDATE. Postgres can only grant that row lock to one of them; Lesson 6 already established what happens next — the second transaction's FOR UPDATE blocks, waiting for the first to commit or roll back. It isn't stuck forever, and it isn't a deadlock (Lesson 40 — that needs a cycle, and there's only one lock here), but it is pure waste: the second worker sits idle for the entire first job's duration, just to discover — once it finally gets the lock — that row is no longer pending and it has to go find a different one. The table holds a hundred other pending rows that second worker could have claimed immediately; nothing about the correct behavior required it to queue up behind row 1 specifically.

2 · SKIP LOCKED: skip what's already taken, don't wait for it

Postgres's locking clause takes an option for exactly this: SKIP LOCKED. Added to the same query:

BEGIN;
SELECT id FROM jobs WHERE status = 'pending'
  ORDER BY id LIMIT 1
  FOR UPDATE SKIP LOCKED;
-- mark it running, do the work, COMMIT

Now the second worker's query doesn't block on row 1 at all. Postgres sees that row is already locked by another uncommitted transaction, silently omits it from the result, and moves on to consider the next pending row in order — handing the second worker row 2 immediately, no waiting. Both workers proceed in parallel, each with a different row genuinely locked, neither blocking the other. The ORDER BY id LIMIT 1 still picks the same "oldest pending" row deterministically for whichever worker gets there first; SKIP LOCKED only changes what happens when that row turns out to already be claimed.

Frontend-habit trap: this looks like it's "skipping" rows at the application level, the way you might filter an array — it isn't. The skip happens inside Postgres's own row visibility check, before any row data is even returned to the client; the application never sees the locked row at all, so there's no app-side branching to write for the skip itself.

3 · The sibling option, and why it's the wrong tool here

Postgres's locking clause has a second option, NOWAIT, that sounds similar but answers a different question. Where SKIP LOCKED quietly moves past a locked row to find a different one, NOWAIT makes the whole statement fail immediately with an error the moment any targeted row turns out to be already locked — no skipping, no substitute row, just an error the caller must catch.

A queue worker claiming "any one pending job, I don't care which" is squarely the third column: it has no reason to wait on a specific row (any pending row will do) and no reason to error out either (a locked row just means another worker already has something to do — not a failure). NOWAIT fits a narrower case this course hasn't needed yet: code that targets one specific row it actually requires, and wants to know immediately rather than queue behind it.

4 · Lesson 10's dequeueJob, finally shown

Lesson 10 enqueued jobs into a plain table and called an opaque dequeueJob(ctx) to "claim one pending row," without saying how. This is that function, for real, with multiple workers running it concurrently against the same table:

// dequeueJob claims exactly one pending job row and marks it running, in one
// transaction. SKIP LOCKED means a second worker calling this concurrently
// never waits behind a row a first worker already claimed -- it just gets
// handed the next pending row instead, so N workers polling in parallel
// each get distinct work with no contention between them.
func dequeueJob(ctx context.Context, db *pgxpool.Pool) (*Job, bool, error) {
    tx, err := db.Begin(ctx)
    if err != nil {
        return nil, false, err
    }
    defer tx.Rollback(ctx) // no-op once Commit succeeds below

    var j Job
    err = tx.QueryRow(ctx, `
        SELECT id, kind, payload FROM jobs
        WHERE status = 'pending'
        ORDER BY id
        LIMIT 1
        FOR UPDATE SKIP LOCKED`,
    ).Scan(&j.ID, &j.Kind, &j.Payload)
    if err == pgx.ErrNoRows {
        return nil, false, nil // nothing pending right now, not an error
    }
    if err != nil {
        return nil, false, err
    }

    if _, err := tx.Exec(ctx, `UPDATE jobs SET status = 'running' WHERE id = $1`, j.ID); err != nil {
        return nil, false, err
    }
    return &j, true, tx.Commit(ctx)
}

type Job struct {
    ID      int64
    Kind    string
    Payload []byte
}

The row lock is held only until this one transaction commits, right after marking the row running — by the time a second worker's own dequeueJob call runs its query, the first row is no longer even pending, so it's excluded by the WHERE clause rather than relying on the skip at all. SKIP LOCKED matters in the narrower window while that first transaction is still open: any worker racing in during that window skips straight past it instead of blocking.

Q: "We run four worker instances polling the same Postgres jobs table. Someone notices that under load, workers seem to be fighting over the same rows instead of spreading out the work. What would you check, and how would you fix it?" A strong answer, out loud: "First I'd check whether the claim query is a plain SELECT ... FOR UPDATE — if so, every worker that doesn't win the lock on a given row just blocks and waits for it, instead of moving on to a different pending row, which is the exact 'fighting over rows' symptom. The fix is adding SKIP LOCKED to that same query: a worker that hits a row another worker already has locked just skips it and keeps looking, so four workers polling at once each land on a different pending row instead of queuing up behind one. I'd specifically avoid NOWAIT here, since that errors out instead of looking further, which isn't what we want when any pending row is an acceptable claim." The signal: naming SKIP LOCKED specifically, not just "add retries" or "poll less often," and explaining why NOWAIT is the wrong option for this shape of problem.

Scope line

This lesson covers one locking-clause option for claiming rows out of a queue-like table without contention. It doesn't cover Lesson 56's advisory locks (coordinating logic with no row behind it at all, a different shape of problem), Lesson 94's table-level lock modes (this stays entirely inside row-level FOR UPDATE locking, never escalating to a table lock), or dedicated queue systems like SQS/RabbitMQ named in Lesson 10 as an alternative to a plain jobs table — SKIP LOCKED is specifically the Postgres-native answer when the queue is just a table.
