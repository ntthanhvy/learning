2 · The layer you've been skipping

Every mart so far has joined staging models directly: dim_restaurants joins stg_restaurants to stg_orders; fct_orders selects straight from stg_orders. That's fine at 2 marts. It stops being fine the moment a third mart needs the same join — say, a future courier-performance mart that also needs orders joined to restaurants for the commission rate. Without a middle layer, that join gets copy-pasted into a second file, and the two copies drift the moment one of them is edited and the other isn't.

dbt Labs' own house-style guide, "How we structure our dbt projects" — already this course's cited source for Day 2's staging layout — names the fix: an intermediate model layer sitting between staging and marts. Its rule is narrower than staging's "one source per model" — an intermediate model does one specific piece of reusable transformation logic, usually a join or a reshape that more than one downstream model needs — and narrower than a mart's "answer a real question": an intermediate model isn't meant to be queried by a dashboard at all, only by other dbt models.

LayerJoins across models?Queried by dashboards?Naming
stagingnever — one source per modelnostg_<source>
intermediateyes — that's its jobno, dbt-internal onlyint_<subject>_<verb>
martsyes, often via intermediate modelsyesfct_<grain> / dim_<entity>

The naming convention matters as much as the layer itself: int_orders_joined reads as "orders, with something joined on" before you open the file, the same way stg_ and fct_/dim_ already tell you a model's layer on sight.

3 · Build: models/intermediate/int_orders_joined.sql

This model pulls out exactly the join dim_restaurants already does — orders left-joined to restaurants — so it exists in one place. Give it in full; the day's actual skill is the refactor in Section 4, not this file:

-- models/intermediate/int_orders_joined.sql
select
    o.order_id,
    o.customer_id,
    o.restaurant_id,
    o.courier_id,
    o.subtotal,
    o.delivery_fee,
    o.order_total,
    o.placed_at,
    r.name as restaurant_name,
    r.cuisine,
    r.city,
    r.commission_rate
from {{ ref('stg_orders') }} as o
left join {{ ref('stg_restaurants') }} as r
    on o.restaurant_id = r.restaurant_id

Mark the intermediate folder ephemeral in dbt_project.yml, next to Day 4's staging/marts block — dbt inlines this SELECT directly into whatever queries it via a Jinja CTE, so it never becomes its own view or table in Postgres at all:

models:
  food_delivery_pipeline:
    staging:
      +materialized: view
    intermediate:
      +materialized: ephemeral
    marts:
      +materialized: table

Ephemeral is the house-style default for intermediate models specifically because nobody outside dbt ever queries them directly — paying for a real view or table would be storage and a lineage-graph node with no payoff. (Not free forever: an ephemeral model inlined into five different marts means that same join runs five separate times at query time. Fine at this project's size; Phase 2a's incremental-strategies lesson is where "reused often enough to materialize for real" becomes a live trade-off.)

4 · Refactor: point dim_restaurants at the new layer

Now the actual skill — dim_restaurants currently joins stg_orders to stg_restaurants itself. Rewrite it to select from int_orders_joined instead, so the join logic exists in exactly one file. The aggregation (one row per restaurant, count() of orders) still belongs in the mart — only the join moves:

-- models/marts/dim_restaurants.sql -- TODO: rewrite to select from int_orders_joined
-- instead of joining stg_restaurants + stg_orders directly. Keep the same
-- output columns and the same left-join behavior (a restaurant with zero
-- orders must still get a row with total_orders = 0).

Your rewritten version should still produce a group by over the restaurant's own columns with count(order_id) as total_orders — only the from/join changes, since int_orders_joined already carries every restaurant column dim_restaurants needs. One thing to get right: int_orders_joined's own join was a left join from orders to restaurants, so a restaurant with zero orders was already being dropped before it ever reached dim_restaurants in the naive rewrite — the fix is to keep joining from restaurants in the mart itself ({{ ref('stg_restaurants') }} as the left side, int_orders_joined as the right side), not to assume the intermediate model already preserved that direction for you.

Why this is worth noticing, not just fixing: an intermediate model built for one caller's join direction doesn't automatically serve a second caller with a different one. That's the real cost side of this layer MISSION.md's "depth where the mission says depth" doesn't spell out in one line: reuse only pays off when the reused piece is generic enough for every caller, and a mart-specific direction hiding inside a shared model is exactly the kind of thing PLAN.md's "when a macro/model makes a project worse" question is aimed at (Phase 2a comes back to this directly).

fct_orders does not change today — it already selects only order-grain columns straight from stg_orders, with no restaurant/courier join, so there is nothing in it for int_orders_joined to replace. Leave it as Day 4 built it.

Q: "Your dbt project has staging, intermediate and marts folders — what's actually different about the middle one?" A strong answer, out loud: "Staging is one model per raw source, no joins, ever — it exists so every downstream model has a clean, renamed starting point. Marts are the opposite end: they're allowed to join freely, because their job is to answer a real question a dashboard or analyst asks. Intermediate sits in between: it's allowed to join, same as marts, but it's not meant to be queried directly — it exists so one specific piece of reusable logic, usually a join or a reshape more than one mart needs, lives in exactly one file instead of being copy-pasted into every mart that needs it. In my project, int_orders_joined does the orders-to-restaurants join once, ephemeral so it costs nothing extra in the warehouse, and dim_restaurants builds on top of it instead of repeating that join itself." The signal: naming what intermediate is for — reuse, not just "another folder" — and being able to say it's dbt-internal only, never a dashboard's data source.
