Load shedding: choosing who gets turned away

Lesson 11 taught two ways a service says "no": rate limiting caps one client before its requests even start, and backpressure rejects new work once an internal queue is already full. Both react to a fixed limit decided in advance. Neither one asks the question a service actually needs answered mid-overload: given that some requests must be turned away right now, which ones should they be?

1 · A fixed limit and an overloaded server are two different problems

Lesson 11's bounded queue and token bucket both work off a number chosen ahead of time — 20 requests/second, 500 queued jobs. That number protects the service from a predictable ceiling being exceeded. But real overload rarely announces itself as "over the ceiling": a slow downstream dependency, a spike in expensive queries, or a burst of legitimate traffic from many different clients (so no single client's rate limit ever trips) can all drive CPU, memory, or latency into the danger zone while every individual client is still comfortably under its own cap. At that point the service isn't asking "did this one client exceed its budget" — it's asking "am I, right now, too loaded to keep serving everyone," and none of Lesson 11's per-client machinery answers that.

Load shedding is the service watching itself, not just watching each client, and dropping some work the instant its own signals say it's in trouble — before memory runs out, before every request's latency collapses together.

2 · Not the same tool as three lessons that sound related

Three earlier mechanisms all touch "rejecting work," and it's worth being precise about how load shedding differs from each one, since interview answers that blur them together read as not having actually built any of them.

The distinguishing question for load shedding: even if every client is behaving and every individual queue has room, is the service itself in enough trouble that it should refuse some work anyway? Rate limiting and backpressure both assume the fixed limit is the right proxy for "in trouble." Load shedding measures "in trouble" directly.

3 · The part that actually requires judgment: shedding by priority, not at random

Rejecting requests arbitrarily during overload still leaves a service worse off than it needs to be — a health check dropped at random can trigger Lesson 47's cascading restart, and a checkout request dropped at random costs revenue that a dropped analytics ping never would. The useful version of load shedding rejects the least important work first, keeping capacity for what matters most.

// A minimal priority-aware load shedder. Real systems (gRPC's ORCA load
// reporting, Envoy's overload manager) do this with richer signals, but the
// shape is the same: check load, then shed low-priority work first.
type Priority int

const (
    Low Priority = iota
    Normal
    Critical
)

type Shedder struct {
    loadFn func() float64 // e.g. current CPU or queue-depth ratio, 0.0-1.0
}

// Admit reports whether a request of the given priority should proceed.
// As load climbs past each threshold, lower-priority work is shed first --
// Critical is the last thing ever refused.
func (s *Shedder) Admit(p Priority) bool {
    load := s.loadFn()
    switch {
    case load > 0.95:
        return p == Critical
    case load > 0.80:
        return p >= Normal
    default:
        return true
    }
}

Two design choices carry the whole idea. First, the signal is the service's own measured load, not a per-client count — loadFn could read CPU, goroutine count, or the same queue depth Lesson 11's backpressure already tracks, just aimed inward instead of at one queue. Second, priority is assigned by the caller ahead of time, at the handler or route level (a health check and an internal cron job are usually Low; a logged-in user's checkout is usually Critical) — the shedder itself makes no judgment about what any single request is worth, it only enforces the ordering it's told.

Frontend-habit trap: this is the backend cousin of a low-end phone's browser deciding to skip a background image decode or pause an off-screen video to keep the main thread responsive — the page doesn't render nothing, it deliberately drops the least visible work first so scrolling and taps still feel instant. A loaded server makes the identical trade: shed the cron-job ping, keep the checkout request.

4 · The response has to say "try elsewhere," not "something is broken"

A shed request should return 503 Service Unavailable with a Retry-After header, the same pairing Lesson 11 used for a full queue — this tells a well-behaved client the rejection is about capacity, not a bug in the request, and gives it a concrete moment to retry rather than hammering immediately. Returning a generic 500 instead would send the client (and whoever's paging on error rates) chasing an application bug that doesn't exist; the request was fine, the server just chose not to do it right now.

Q: "Your service is falling over under a traffic spike even though no single client is hitting its rate limit. What do you do?" A strong answer, out loud: "That's the gap rate limiting doesn't cover — it protects against one bad client, not against the service being overloaded by many well-behaved ones at once. I'd add load shedding: watch the service's own signals, CPU, queue depth, or latency, and once they cross a threshold, start rejecting a chosen slice of incoming requests with 503 and Retry-After. The part that matters is shedding by priority, not randomly — tag routes ahead of time so health checks and background jobs get dropped before a logged-in user's checkout does. That way the service survives the spike serving its most important traffic, instead of every request degrading together until the process falls over." The signal: naming that load shedding reacts to the server's own measured state rather than a fixed per-client limit, and that priority-based shedding is what separates a useful implementation from randomly dropping requests.
