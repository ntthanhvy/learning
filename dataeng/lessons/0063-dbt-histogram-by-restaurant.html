1 · The gap two lessons named, from two different angles

Day 48 built the first histogram — one row per delivery-time bucket, platform-wide — and closed with a specific, named next step: "a per-city or per-restaurant breakdown... a cross join against stg_restaurants' distinct cities... is the direct next step." Day 49 picked up exactly half of that sentence, built the per-city version, and then re-named the other half on its own way out: "it does not add a per-restaurant or per-courier breakdown (same pattern, a different select distinct source, left for whenever that granularity is actually asked for)." Two lessons, two mentions, one piece of the original gap still open. Today closes it.

The reason this is worth a lesson of its own, not a two-line footnote on Day 49, is that city and restaurant sit at genuinely different grains in this project. raw.restaurants has many rows per city — Day 49's histogram already proved a city-wide number can hide which specific restaurant inside that city is actually the slow one, the identical blind spot Day 48 found in the city-wide SLA share one level up. "Hanoi is slow 12% of the time" could mean every restaurant in Hanoi runs a little behind, or it could mean nineteen restaurants are fine and one is consistently terrible. Only a restaurant-grain histogram can tell those apart, and nothing built so far in this course answers that question at this grain.

2 · Reusing Day 49's exact shape, crossed against a new axis

Day 49 already proved the pattern: build the full grid first (every axis value paired with every bucket, via cross join), then composite join condition left-join the real data onto it. Today's grid has the same two axes Day 49's did — a select distinct source crossed with Day 48's bucket ladder — just with restaurant_id standing in for city. The one genuine wrinkle: unlike city (a bare string with no separate ID), a restaurant has both an ID and a name, and the grid needs to carry both through to the final mart so a reader never has to join back to dim_restaurants just to know whose numbers they're looking at.

Carrying restaurant_name through the grid, not just restaurant_id, is a deliberate choice worth naming: joining it in once, at the grid-building step, means every downstream row already has a human-readable label, instead of forcing every future query against this mart to repeat a join dbt already knows how to avoid.

3 · Build: restaurants × buckets, then the real orders left-joined on top

In your food-delivery-pipeline repo, create models/marts/mart_delivery_time_histogram_by_restaurant.sql in full:

-- models/marts/mart_delivery_time_histogram_by_restaurant.sql
{{ config(materialized='table') }}

with order_durations as (
    -- identical to Day 48/49's CTE of the same name -- orders, restaurants,
    -- and the placed/delivered pair of stg_order_events rows per order
    select
        o.order_id,
        r.restaurant_id,
        r.restaurant_name,
        extract(epoch from (d.delivered_at - p.placed_at)) / 60 as minutes_to_deliver
    from {{ ref('stg_orders') }} as o
    inner join {{ ref('stg_restaurants') }} as r on o.restaurant_id = r.restaurant_id
    inner join {{ ref('stg_order_events') }} as p
        on o.order_id = p.order_id and p.status = 'placed'
    inner join {{ ref('stg_order_events') }} as d
        on o.order_id = d.order_id and d.status = 'delivered'
),

-- Day 49's cities CTE shape, reused -- restaurant_name carried through so
-- the final mart needs no further join to show a human-readable label
restaurants as (
    select distinct restaurant_id, restaurant_name from {{ ref('stg_restaurants') }}
),

-- Day 48's exact bucket_series/bucket_grid CTEs, reused verbatim
bucket_series as (
    {{ dbt_utils.generate_series(var('histogram_bucket_count')) }}
),

bucket_grid as (
    select
        (generated_number - 1) * {{ var('histogram_bucket_minutes') }} as bucket_start_minutes,
        generated_number * {{ var('histogram_bucket_minutes') }} as bucket_end_minutes
    from bucket_series
),

-- new today: the two grids crossed into one, N restaurants x 20 buckets
-- rows, before any real order is involved -- same shape as Day 49's
-- city_bucket_grid, just crossed against restaurants instead of cities
restaurant_bucket_grid as (
    select
        restaurants.restaurant_id,
        restaurants.restaurant_name,
        bucket_grid.bucket_start_minutes,
        bucket_grid.bucket_end_minutes
    from restaurants
    cross join bucket_grid
),

bucketed_orders as (
    select
        restaurant_bucket_grid.restaurant_id,
        restaurant_bucket_grid.restaurant_name,
        restaurant_bucket_grid.bucket_start_minutes,
        restaurant_bucket_grid.bucket_end_minutes,
        count(order_durations.order_id) as order_count
    from restaurant_bucket_grid
    left join order_durations
        on order_durations.restaurant_id = restaurant_bucket_grid.restaurant_id
        and order_durations.minutes_to_deliver >= restaurant_bucket_grid.bucket_start_minutes
        and order_durations.minutes_to_deliver < restaurant_bucket_grid.bucket_end_minutes
    group by restaurant_bucket_grid.restaurant_id, restaurant_bucket_grid.restaurant_name,
             restaurant_bucket_grid.bucket_start_minutes, restaurant_bucket_grid.bucket_end_minutes
)

select
    {{ dbt_utils.generate_surrogate_key(['restaurant_id', 'bucket_start_minutes']) }} as bucket_key,
    restaurant_id,
    restaurant_name,
    bucket_start_minutes,
    bucket_end_minutes,
    order_count
from bucketed_orders
order by restaurant_id, bucket_start_minutes

The left join's on clause carries three conditions, not Day 49's two — restaurant_id, the lower bucket bound, and the upper bucket bound all have to hold at once. Dropping the restaurant_id condition would silently attach every restaurant's orders to every other restaurant's bucket rows purely on timing, the same "the grid has two axes, both must match" lesson Day 49 drew about city — only here, missing the match is easier to get wrong by accident, since a bucket-range condition alone still looks like a plausible, complete on clause on its own.

4 · Why a restaurant grain finds what a city grain genuinely can't

Keeping all three histogram marts side by side — platform-wide (Day 48), per-city (Day 49), per-restaurant (today) — is the same judgment call Day 48 and Day 49 each already made about mart_delivery_sla: different questions earn separate marts rather than one table trying to answer all of them through a filter bolted on after the fact. But today's grain is worth being precise about, because it is the only one of the three that can actually answer "which specific restaurant is slow." A city average is a weighted blend of every restaurant in it — if one restaurant in a four-restaurant city runs catastrophically late and the other three are fast, the city's own number can still land close to the platform average, hiding the one real problem inside an average that looks fine. Querying today's mart grouped by restaurant_id and filtered to the slow buckets is the only one of the three marts that surfaces that restaurant by name, not just the city it happens to sit in.

This also means a restaurant with very few orders deserves a different read than one with many: a restaurant showing order_count = 1 in the 95-100 minute bucket could be one unlucky order, not a pattern, where the same shape at `order_count = 40` is a real problem. Today's mart doesn't make that judgment call for you — it's a grid of counts, not a verdict — but it is the table a real operator would actually look at before deciding whether a slow bucket means something.

Q: "Your dashboard shows city-level delivery SLA numbers, and every city looks roughly fine. An ops lead says one specific restaurant is getting complaints. How do you investigate, and why might the dashboard not have caught it already?" A strong answer, out loud: "A city-level number is a weighted average across every restaurant in that city, so one genuinely bad restaurant can get diluted into a city figure that still looks acceptable — the same blind spot a single SLA percentage has relative to a full distribution, just one grain further down. I'd build or query a mart at restaurant grain instead of city grain: the same bucket-histogram pattern, just crossed against distinct restaurants instead of distinct cities. The construction is identical either way — generate the full bucket ladder, cross join it against every restaurant so even a restaurant with zero slow orders still has a row showing zero, then left-join the real per-restaurant, per-bucket counts onto that grid matching on both restaurant and bucket range. That gives me a table where I can filter to one restaurant_id and see its actual shape, not a number blended with eleven other restaurants that are doing fine." The signal: naming averaging-across-grain as the actual blind spot, and describing the construction as the same reusable grid-then-left-join pattern rather than a bespoke restaurant-specific fix.

Scope line

This lesson covers crossing stg_restaurants' distinct (restaurant_id, restaurant_name) pairs against Day 48's bucket ladder via cross join, with a three-condition left join, to build a per-restaurant delivery-time histogram. It does not add a per-courier breakdown — the exact other half of Day 48's original named gap, same pattern, a select distinct against stg_couriers instead — left open since this project has not yet surfaced a real question that needs courier-level timing rather than restaurant-level. It does not touch Day 48's global histogram or Day 49's per-city one; all three marts stay in the project side by side, answering different questions at different grains. It also does not add any alerting or thresholding on top of today's grid (a restaurant crossing some "too many slow buckets" line) — Day 46's alerting pattern would transfer directly if that's ever asked for, not re-derived here.
