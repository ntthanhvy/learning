unittest.mock: faking the outside world in a test

Day 59's next-day note weighed a fresh gap against a second review pass and left the fresh case open. A closer look finds a genuine, load-bearing gap: Day 11 taught pytest, fixtures, and parametrize, and Day 22 tested a whole FastAPI app in-process — but nothing so far has answered "how do you test a function that calls something slow, flaky, or dangerous to actually run," like a network request, today's date, or a real database write. That's unittest.mock's job, and unlike pytest itself, it ships in the standard library.

Why today, specifically: a fresh-gap grep across all 59 lessons and every practice file confirmed zero hits for unittest.mock, Mock, MagicMock, patch, or monkeypatch. subprocess and configparser remain on the table from Day 58-59's notes but are still weaker: subprocess sits closer to MISSION.md's process/concurrency boundary, and configparser is a narrow format pathlib and plain dicts already cover. Mocking is different — it directly extends Day 11's testing material, it's the standard answer to "how do I test code with side effects" (exactly what a data pipeline's file/network/database calls are), and it sets up cleanly for testing the FastAPI-phase code from Days 16-26 once a handler needs to call something external. That makes it a stronger pick than a second review pass this round.

1 · The problem: some code is not safe or fast to actually run in a test

Day 11's tests all called real functions that did real, cheap, repeatable work — parsing a string, reading a temp file. Not every function is like that. A function that hits a real API over the network is slow and fails when there's no internet; a function that checks datetime.now() gives a different answer every run, so an assert against it can never be reliable; a function that sends a real email or writes a real production row has a side effect you don't want happening a hundred times a day just from running the test suite. All three share one shape: the function under test is fine, but something it calls is the problem.

def fetch_rate(currency):
    response = requests.get(f"https://api.example.com/rates/{currency}")   # real network call
    return response.json()["rate"]

def convert(amount, currency):
    return amount * fetch_rate(currency)   # the logic worth testing is this one line

Testing convert() honestly should not require a live network connection to a real API every time the test suite runs. What's needed is a way to run convert() for real while making fetch_rate() return a known, fixed value instead of actually calling the network — without editing convert()'s source code at all.

2 · Mock: an object that accepts anything and remembers what happened

A Mock is an object built for exactly this: it accepts any attribute access or method call, returns another Mock by default, and quietly records every call it received:

from unittest.mock import Mock

fake = Mock()
fake.anything(1, 2, name="x")     # works -- no AttributeError, no NameError, nothing defined ahead of time
fake.anything.called                # True -- Mock remembers it was called
fake.anything.call_args             # call(1, 2, name='x') -- and remembers exactly how

Verified live: creating a bare Mock() and calling an undefined method on it with arbitrary arguments raises nothing — it just works, and afterward .called is True and .call_args holds the exact arguments passed. A plain Mock is rarely used bare like this, though — its real job is standing in for a specific object your code already calls, with a controlled return value instead of another Mock.

3 · Controlling the return value: Mock(return_value=...)

Setting return_value makes every call to the mock return that fixed value instead of a fresh Mock:

from unittest.mock import Mock

fake_response = Mock()
fake_response.json = Mock(return_value={"rate": 1.1})   # .json() will now return this dict

fake_response.json()                        # {'rate': 1.1} -- every time, no network involved
fake_response.json() == fake_response.json()   # True -- same fixed value, called twice

This is the whole trick: build a Mock shaped like the real object convert() depends on (something with a .json() method returning a dict with a "rate" key), give it a fixed return_value, and the code under test can't tell the difference between it and a real network response — except it's instant and never flaky.

4 · patch: swapping in a Mock for the duration of one test only

fetch_rate() calls requests.get directly — there's no parameter to pass a fake response through. patch solves that by temporarily replacing a named function or object with a Mock, for the duration of a with block, then restoring the original automatically — Day 6's context-manager guarantee, applied to swapping code instead of closing a file:

from unittest.mock import patch, Mock

def test_convert_uses_the_fetched_rate():
    fake_response = Mock()
    fake_response.json = Mock(return_value={"rate": 1.1})
    with patch("requests.get", return_value=fake_response):
        assert convert(100, "eur") == 110.0
    # outside the with block, requests.get is back to the real function

patch("requests.get", ...) means "wherever requests.get is looked up during this block, hand back this Mock instead." Inside the block, fetch_rate() calls what it thinks is the real requests.get, gets fake_response back, calls .json() on it, and gets the fixed {"rate": 1.1} — no network, no flakiness, and the assertion runs in milliseconds. The moment the with block ends, requests.get is exactly what it was before, restored automatically even if the assert inside had failed — the identical unconditional-cleanup guarantee with already made for files.

Bridge from SQL: mocking a database call in a unit test plays the same role a disposable test schema plays for integration tests — both let you assert on your own logic's behavior without touching data that matters. The difference is scope: a mock replaces the call entirely (fastest, but proves nothing about the real database driver), while a real test database (Day 21) still executes real SQL against real rows. Most real projects use both — mocks for fast, frequent unit tests, and a real test database for a smaller number of slower integration tests.

5 · The one thing that silently defeats the whole test: patching the wrong path

patch()'s first argument is a string naming where a name is looked up, not where it's originally defined — a distinction that causes almost every real mocking bug. If convert() lives in a module called billing.py that did import requests at the top, then billing.py has its own local name requests pointing at the same module object. Patching "requests.get" patches the original requests module's attribute — but if billing.py imported it as from requests import get instead, billing.py now has its own separate name get, and patching "requests.get" never touches it:

# billing.py
from requests import get   # billing.get is now its OWN name, a separate reference to the same function

def fetch_rate(currency):
    return get(f".../{currency}").json()["rate"]

# test file -- WRONG, patches a path billing.py never looks up:
with patch("requests.get", return_value=fake_response):
    fetch_rate("eur")   # still calls the REAL get -- billing.get was never touched

# test file -- RIGHT, patches the name billing.py actually holds:
with patch("billing.get", return_value=fake_response):
    fetch_rate("eur")   # now uses the fake -- billing's own "get" name got replaced

Verified live: with a small billing-style module importing get by name, patching "requests.get" left the module still calling the real function (confirmed by the mock's .called staying False), while patching "billing.get" — the module's own local name — correctly redirected the call. The rule Day 9's import lesson already implied applies again here: from module import name binds a new local name in the importing module, so a patch has to target that module's name, not the name's original home. This one detail is the single most common reason a mock silently "doesn't work" — the test passes for the wrong reason (nothing was actually mocked) or fails confusingly because the real code path still ran.

6 · monkeypatch: pytest's built-in fixture for the same job

Day 11 taught pytest fixtures as a general mechanism — something decorated @pytest.fixture that a test asks for by parameter name. pytest ships one itself, called monkeypatch, that wraps exactly today's patch() pattern with automatic cleanup already wired to the test's lifetime, no with block needed:

def test_convert_uses_the_fetched_rate(monkeypatch):
    fake_response = Mock()
    fake_response.json = Mock(return_value={"rate": 1.1})
    monkeypatch.setattr("billing.get", Mock(return_value=fake_response))
    assert convert(100, "eur") == 110.0
    # no manual restore needed -- monkeypatch undoes it when the test ends, pass or fail

monkeypatch.setattr(path, value) does the same job as patch(path, ...) — same "path is a lookup location, not a definition site" rule from section 5 applies unchanged — but restores automatically when the test function returns, the same way Day 11's fixture teardown already ran after yield regardless of pass or fail. Reach for unittest.mock.patch directly outside a test (or when a plain with block reads more clearly than adding a fixture parameter); reach for monkeypatch inside a pytest test, since it's already there as a built-in fixture needing no import at all.

Where pandas goes from here: nothing pandas-specific today — mocking a pandas pipeline's I/O (a network call feeding pd.read_json(), say) uses the exact same patch/Mock mechanics taught today, just returning fake JSON bytes or a fake response object instead of a plain dict; the library itself stays data/'s job.
