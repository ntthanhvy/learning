WebSocket vs SignalR: a protocol and the library on top of it

"WebSocket vs SignalR" sounds like a choice between two rival technologies. It isn't: SignalR usually runs on WebSockets. The real question is "raw socket, or a library that handles the boring parts for me?" Once you see that, "why is SignalR used more now?" has a precise answer, and so does "when is it the wrong choice?"

1 · The frontend analogy you already own

Compare XMLHttpRequest with a data-fetching library like React Query. XHR is the browser primitive: it sends bytes and gives you bytes back. React Query is built on top of that primitive and adds retries, caching, loading states and deduplication. Nobody asks "XHR or React Query?" as if only one can exist. You pick the library because you'd otherwise write those features yourself, badly.

WebSocket vs SignalR is the same relationship, one layer down:

The primitiveThe library on top
FetchingXMLHttpRequest / fetchReact Query, SWR
Real-timeWebSocket (a protocol, RFC 6455)SignalR (.NET), Socket.IO (Node), Centrifugo (any backend)

2 · What a raw WebSocket gives you, and what it doesn't

Lesson 63 covered the protocol itself: an upgrade handshake, then a full-duplex pipe where either side can send a message at any time. That's all the protocol promises. Here is everything a real chat or live-dashboard feature still needs, which the protocol leaves to you:

  • Message meaning. A WebSocket message is just a string or bytes. You invent your own envelope ({"type":"chat","payload":…}) and a switch on type on both sides.
  • Reconnect. When Wi-Fi drops, the socket fires onclose and stays dead. Unlike SSE's EventSource, the browser does not reconnect for you.
  • Fallback. Some corporate proxies break the upgrade. With a raw socket, the feature simply fails there.
  • Audiences. "Send to user 42" or "send to everyone in room order-17" means keeping your own map of connections and cleaning it up on every disconnect.
  • Multiple instances. Lesson 63's trap: a socket is pinned to one instance, so a broadcast needs a cross-instance fan-out (Redis pub/sub or similar) that you build and run.

3 · What SignalR is: the same pipe, plus those five things

SignalR is Microsoft's real-time library for ASP.NET Core (docs). Each of the five gaps above maps to one feature:

Gap in raw WebSocketWhat SignalR does
Message meaningA hub: client and server call each other's methods by name, a form of RPC. Payloads are JSON or MessagePack.
ReconnectwithAutomaticReconnect() retries after 0, 2, 10 and 30 s. It's opt-in, not on by default.
FallbackTransport fallback: WebSockets, then SSE, then long polling, chosen automatically. These are the same three techniques from Lesson 63.
AudiencesClients.All, Clients.User(id), Clients.Group("order-17"), with no hand-written connection map.
Multiple instancesA backplane: plug in Redis, or let Azure SignalR Service hold the connections for you (scale docs).

The difference is visible in the code. Here is the same "broadcast a chat message" feature in each, client side:

// raw WebSocket: you invent the envelope, dispatch, and reconnect
const ws = new WebSocket("wss://api.example.com/ws");
ws.onmessage = (e) => {
  const msg = JSON.parse(e.data);
  if (msg.type === "chat") addMessage(msg.user, msg.text);
};
ws.onclose = () => { /* your backoff + reconnect logic here */ };
ws.send(JSON.stringify({ type: "chat", user, text }));

// SignalR: call methods by name; reconnect is one line
const conn = new signalR.HubConnectionBuilder()
  .withUrl("/chathub").withAutomaticReconnect().build();
conn.on("ReceiveMessage", (user, text) => addMessage(user, text));
await conn.start();
await conn.invoke("SendMessage", user, text);

And server side, the whole broadcast is one line in the hub: await Clients.All.SendAsync("ReceiveMessage", user, text);

4 · "Why is SignalR used more now?" The honest answer

Be precise here, because the question hides an assumption. SignalR hasn't replaced WebSockets; SignalR traffic usually is WebSocket traffic. What happened is that in the .NET world, the library became the default way to use WebSockets. Microsoft says so directly: "For most applications, we recommend SignalR rather than raw WebSockets", giving three reasons:

  1. it provides transport fallback where WebSockets aren't available;
  2. it provides a basic RPC app model (the hub);
  3. it has "no significant performance disadvantage compared to using raw WebSockets in most scenarios."

Reason 3 is the key one. If the library costs almost nothing extra and saves you from writing reconnect, dispatch, groups and scale-out, the raw socket only wins in narrow cases. Blazor Server is also built on SignalR, so many .NET teams ship it without ever choosing it.

Outside .NET, the same pattern shows up under other names: Node teams reach for Socket.IO. In Go, your course stack, there's no SignalR-equivalent in the standard library or from the Go team. Teams either use a WebSocket package and build the five pieces themselves, or run a separate real-time server like Centrifugo. So "SignalR is used more" is really a .NET-ecosystem fact, not a universal one.

Trap: the tension with Lesson 8. Lesson 8 called sticky sessions a band-aid to avoid. SignalR requires them on a multi-server farm, even with the Redis backplane. The reason: the negotiate request and the fallback transports are separate HTTP requests that must reach the same process. There are only two exceptions: Azure SignalR Service, or every client forced to WebSockets-only with SkipNegotiation. In a design review, "we'll add SignalR" should immediately raise "and how does our load balancer pin connections?"

5 · When to pick which

SituationReasonable pick
ASP.NET Core backend, browser clients, chat/notifications/dashboardsSignalR. That's the vendor's own recommendation.
Go backendA WebSocket library and your own envelope + reconnect, or SSE if the data only flows one way (Lesson 63).
Non-browser or third-party clients that speak "plain WebSocket" (IoT, another company's system)Raw WebSocket. A SignalR server expects the SignalR protocol, so a plain client can't just connect.
Ultra-tight, custom binary protocol (games, trading)Raw WebSocket. You want full control of every byte.

Q: "What's the difference between WebSockets and SignalR?" A strong answer, out loud: "WebSocket is the protocol: a full-duplex connection after an HTTP upgrade, nothing more. SignalR is an ASP.NET Core library that uses WebSockets when it can and falls back to SSE or long polling when it can't. On top of that it adds hubs, so you call methods by name instead of parsing messages yourself. It also gives you groups and per-user sends, optional auto-reconnect, and scale-out through a Redis backplane or Azure SignalR Service. Microsoft recommends it over raw WebSockets for most apps because the overhead is small. The catches: you need sticky sessions on a server farm, and every client has to speak the SignalR protocol." The signal: you call it "library on top of a protocol", not "alternative to", and you know at least one operational cost.
