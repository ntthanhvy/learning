groupby().filter(): keeping whole groups, not rows

Lesson 39's teaser named groupby().filter() as a real gap — not to be confused with Lesson 22's query() or Lesson 29's isin(), which both filter individual rows. Today's tool filters whole groups: every row of a group is kept or dropped together, based on a condition computed over the group as a whole. This is pandas' answer to SQL's HAVING.

1 · The problem: WHERE can't ask a per-group question

Back on the raw, uncleaned orders_raw.csv (Lesson 2's fixture, before any cleaning), each customer has a different number of orders:

raw = pd.read_csv("practice/data/orders_raw.csv")
--   order_id customer   amount  order_date
--  0        1       An    120.0  2026-01-05
--  1        2     Binh     35.5  2026-01-06
--  2        3       An  unknown  2026-01-07
--  3        4      Chi     99.9         NaN
--  4        5     Binh    180.0  2026-01-09
--  5        6       An     42.0  2026-01-10
raw.groupby("customer").size()
-- customer
-- An      3
-- Binh    2
-- Chi     1
-- dtype: int64

Suppose the task is "only keep orders from customers who placed at least 2 orders" — drop Chi's single row entirely, keep every row belonging to An and Binh. A boolean mask (raw[raw["amount"] > 100], Lesson 1) can only test each row against itself; it has no way to ask "how many rows does this row's group have in total?" That's exactly the gap groupby().filter() closes.

2 · groupby().filter(): a function per group, not per row

by_count = raw.groupby("customer").filter(lambda g: len(g) >= 2)
--   order_id customer   amount  order_date
--  0        1       An    120.0  2026-01-05
--  1        2     Binh     35.5  2026-01-06
--  2        3       An  unknown  2026-01-07
--  4        5     Binh    180.0  2026-01-09
--  5        6       An     42.0  2026-01-10

Chi's row (order_id 4) is gone; every row belonging to An and Binh survives, including the messy ones (Lesson 3's "unknown" amount, the missing order_date) — filter() doesn't clean anything, it only decides which whole groups stay. The lambda receives g, a real DataFrame holding just that one group's rows, and its return value must be a single True/False: truthy keeps every row of that group, falsy drops every row of that group. Notice the result's index ([0, 1, 2, 4, 5]) still carries the original row positions, not a fresh 0..n-1 — same "call reset_index() yourself if you want one" convention as every other row-selecting operation this course has covered.

The condition isn't limited to size — any per-group aggregate works, same as a HAVING clause can test any aggregate:

raw["amount_num"] = pd.to_numeric(raw["amount"], errors="coerce")  # "unknown" -> NaN
by_sum = raw.groupby("customer").filter(lambda g: g["amount_num"].sum(skipna=True) > 150)
-- same 5 rows as by_count -- Chi's total is only 99.9, An's is 162.0, Binh's is 215.5

3 · The SQL bridge: this is exactly HAVING

The name is deliberately parallel to how WHERE and HAVING divide labor in SQL: WHERE filters rows before grouping, HAVING filters whole groups after aggregating, using an aggregate in its condition. groupby().filter() plays exactly HAVING's role:

-- SELECT * FROM orders o
-- WHERE customer IN (
--   SELECT customer FROM orders GROUP BY customer HAVING COUNT(*) >= 2
-- );
raw.groupby("customer").filter(lambda g: len(g) >= 2)

SQL has no single-clause way to say "give me back every original row of the groups that pass HAVING" — HAVING alone only shrinks the aggregated result to one row per surviving group, which is why the SQL above needs a subquery wrapped in IN (...) to get back to row-level output. groupby().filter() does that whole subquery-and-IN dance in one call.

4 · Contrast with agg(): one row per group vs. every original row

It's easy to reach for the wrong tool here, because both start with groupby("customer"). Lesson 4's agg() collapses each group down to one summary row:

raw.groupby("customer")["amount_num"].sum()
-- customer
-- An      162.0
-- Binh    215.5
-- Chi      99.9
-- dtype: float64      <-- 3 rows: one per group, amounts only

filter() never collapses anything — it hands back a subset of the original DataFrame, every column intact, at full row-level detail:

by_count.shape   # (5, 4) -- still order_id, customer, amount, order_date

Rule of thumb: need a summary number per group → agg(). Need to keep (or drop) entire groups' worth of original rows, unsummarized → filter(). The two combine naturally in a chain too — filter first to drop small/thin groups, then aggregate the survivors, mirroring exactly how a real HAVING query is often followed by further row-level work downstream.

Two other "filter"-shaped tools this course already covered, and how they differ: Lesson 22's query() and Lesson 29's isin() both test one row at a time against a condition — they can drop individual rows out of a group while leaving the rest of that same group in place. groupby().filter() can only make an all-or-nothing decision per group — it either keeps every row of a group or drops every row of that group, never a partial group.

Q: "How would you find, say, customers with at least 3 orders, and return their original order rows — not just a count?" A strong answer, out loud: "In SQL that's a HAVING clause, but HAVING alone only gives me back one summarized row per group — to get the original rows I'd need a subquery: `SELECT * FROM orders WHERE customer IN (SELECT customer FROM orders GROUP BY customer HAVING COUNT(*) >= 3)`. In pandas, `groupby('customer').filter(lambda g: len(g) >= 3)` does that in one call — it evaluates my condition once per group and keeps every row of every group that passes, at full original detail, no aggregation applied. That's different from `groupby().agg()`, which always collapses each group to a single summary row — if I called `agg()` here I'd lose the individual order rows entirely. And it's different from `query()` or `isin()`, which decide row by row and can split a group apart; `filter()`'s decision is all-or-nothing per whole group." The signal: naming the SQL subquery pandas' one-liner replaces, and drawing the agg-vs-filter line precisely — collapse-to-summary vs. keep-original-detail-for-survivors.
