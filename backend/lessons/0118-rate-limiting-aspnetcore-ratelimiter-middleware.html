Rate limiting, now in C# too

Lesson 11 covered rate limiting in Go: a hand-rolled token-bucket struct, one bucket per API key stored in a sync.Map, and a middleware function that checks the bucket before calling the next handler. That lesson never got a C# mirror, even though every other Go-only resilience mechanism from this course — retry, circuit breaker, bulkhead, worker pools, graceful shutdown, health checks — has been ported since Lesson 112. Today closes that gap: the same token-bucket algorithm, built from ASP.NET Core's own rate-limiting middleware instead of a hand-written bucket and sync.Map.

1 · Same algorithm, one middleware instead of a hand-rolled struct

Lesson 11's rule still holds exactly: a bucket holds up to N tokens, refills at a steady rate, and every request spends one token to proceed — an empty bucket means the request is rejected until it refills. What changes in ASP.NET Core is that nobody writes the bucket, the mutex, or the refill math by hand. The building block is rate limiting middleware, and the specific algorithm Lesson 11 built by hand has its own extension method: AddTokenBucketLimiter().

using Microsoft.AspNetCore.RateLimiting;
using System.Threading.RateLimiting;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddRateLimiter(options =>
{
    options.AddTokenBucketLimiter("per-api-key", opt =>
    {
        opt.TokenLimit = 20;                              // bucket capacity -- same 20 as Lesson 11's struct literal
        opt.TokensPerPeriod = 10;                         // tokens added back each period
        opt.ReplenishmentPeriod = TimeSpan.FromSeconds(1);  // -- 10/sec, matching Lesson 11's refillPerSec
        opt.QueueLimit = 0;                               // 0 == reject immediately, no queueing
        opt.AutoReplenishment = true;                     // an internal timer refills; no manual TryReplenish() call needed
    });
});

var app = builder.Build();
app.UseRateLimiter();

app.MapGet("/orders", () => "ok").RequireRateLimiting("per-api-key");
app.Run();

Per Microsoft's own docs: "rather than adding back the requests taken from the expired segment, a fixed number of tokens are added each replenishment period" — the exact refill rule Lesson 11's allow() method computed by hand with time.Now().Sub(b.last) and math.Min(b.capacity, ...) every call. Here that math lives inside the framework; the app only states the three numbers.

2 · Per-client buckets: a partition instead of a sync.Map

Lesson 11's middleware kept one bucket per API key by storing them in a sync.Map keyed on the header value, created lazily with LoadOrStore. ASP.NET Core's equivalent is a partition, built once as the global limiter:

options.GlobalLimiter = PartitionedRateLimiter.Create<HttpContext, string>(httpContext =>
    RateLimitPartition.GetTokenBucketLimiter(
        partitionKey: httpContext.Request.Headers["X-API-Key"].ToString(),
        factory: _ => new TokenBucketRateLimiterOptions
        {
            TokenLimit = 20,
            TokensPerPeriod = 10,
            ReplenishmentPeriod = TimeSpan.FromSeconds(1),
            QueueLimit = 0,
            AutoReplenishment = true
        }));

Same shape as Lesson 11's buckets.LoadOrStore(key, &bucket{...}): the first request for a given key builds that key's limiter from the factory, every later request for the same key reuses it. The docs' own partitioning warning matches Lesson 11's implicit assumption too: partitioning on unbounded user-controlled input (an arbitrary header value, not an authenticated identity) risks a memory-exhaustion attack, since each distinct key caches its own limiter forever.

The frontend equivalent you already own. Lesson 11 already named this: a token bucket is the server-side version of debouncing a search box — refusing to do more work than the system can sustain, rather than accepting everything and falling behind. Nothing about that mental model changes here; only who writes the bucket does.

3 · Rejection: OnRejected instead of a manual WriteHeader call

Lesson 11's middleware, on an empty bucket, set Retry-After by hand and called w.WriteHeader(http.StatusTooManyRequests) directly. ASP.NET Core exposes the same two facts — the status code and the retry hint — through RateLimiterOptions.RejectionStatusCode (defaults to 429 already) and an OnRejected callback:

using System.Globalization;

options.OnRejected = async (context, token) =>
{
    if (context.Lease.TryGetMetadata(MetadataName.RetryAfter, out var retryAfter))
        context.HttpContext.Response.Headers.RetryAfter =
            ((int)retryAfter.TotalSeconds).ToString(NumberFormatInfo.InvariantInfo);

    context.HttpContext.Response.StatusCode = StatusCodes.Status429TooManyRequests;
    await context.HttpContext.Response.WriteAsync("rate limit exceeded", token);
};

context.Lease is the token-bucket limiter's own lease object — the same "did this succeed, and if not, how long until it might" answer Lesson 11's allow() returned as a plain bool plus a hardcoded "1"-second Retry-After. Here the limiter itself computes the real wait, exposed as metadata rather than guessed.

Scope line

This lesson covers ASP.NET Core's rate-limiting middleware's token-bucket limiter — AddRateLimiter(), AddTokenBucketLimiter()/TokenBucketRateLimiterOptions, UseRateLimiter(), RequireRateLimiting(), PartitionedRateLimiter partitioning, and OnRejected — as the C# mirror of Lesson 11's Go token bucket. It does not cover the fixed-window, sliding-window, or concurrency limiter algorithms the same middleware also ships (different shapes, future lesson if needed); chaining multiple limiters with CreateChained; the [EnableRateLimiting]/[DisableRateLimiting] MVC attributes beyond naming that they exist; or multi-instance rate limiting across a fleet (the docs are explicit that counters are per-instance, in-memory, and out of scope here per MISSION.md's distributed-systems boundary). It does not cover Go's select-statement arbitration rules — still deferred; see this round's NOTES.md entry for why.
