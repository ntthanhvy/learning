1 · Four questions, in the original teaching order

Answer each out loud or on paper before reading the fold-out answer. If one is shaky, note it and go fix it in the practice file below rather than only rereading the old lesson.

Day 57 — dataclasses.field() and frozen=True. Why does a dataclass field declared items: list = [] raise ValueError at class-definition time, and what does field(default_factory=list) do differently?

Fold-out answer: a plain = [] default would be built exactly once, at class-definition time, and every instance that omits the argument would share that one same list object — Day 1's mutable-default-argument trap, now hit inside a dataclass. @dataclass refuses to even define the class rather than let that bug happen later. field(default_factory=list) stores a zero-argument callable instead of a value; @dataclass calls it fresh for every instance that skips the argument, so no two instances ever share one list.

Day 59 — hashlib. Why does hashing a file in many small chunks via repeated .update() calls produce the exact same digest as hashing the whole file in one call, and why does that matter for a large file?

Fold-out answer: .update() is cumulative, not a replacement — each call feeds more bytes into the same running computation, so it makes no difference to the final digest whether the bytes arrive as one big call or many small ones. That matters because it lets a multi-gigabyte file be hashed one chunk at a time, in constant memory, the same discipline Day 5's generators already established for reading — without it, hashing would require holding the entire file in memory first.

Day 60 — unittest.mock. Why does patch("requests.get", ...) sometimes silently fail to mock a call at all, even though the code under test clearly calls a function named get from the requests library?

Fold-out answer: patch()'s target string names where a name is looked up, not where it was originally defined. If the module under test did from requests import get instead of import requests, that module now holds its own separate local name get — patching "requests.get" only ever touches the original requests module's attribute, never that module's own copy of the name. The fix is patching the name where it's actually looked up, e.g. "billing.get" if the module is called billing.py.

Day 62 — shutil. Why does shutil.copytree() refuse to run if the destination directory already exists, instead of just merging into it?

Fold-out answer: the destination-must-not-exist rule is deliberate, not a limitation to route around by pre-deleting the target. It exists so a typo in the destination path can never silently merge into — and corrupt — an existing directory that happened to already be there. dirs_exist_ok=True opts into merging only when that is genuinely the intent, rather than being the silent default.
