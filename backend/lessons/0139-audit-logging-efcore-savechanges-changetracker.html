Audit logging, now in C# too (ChangeTracker, SaveChangesAsync)

Lesson 46 built an audit log the hand-written way: a second INSERT, written out explicitly, in the same transaction as the state change it records. That works in any language, but it means remembering to write that second line at every single call site that changes something auditable — easy to forget once, and a forgotten audit row is a silent gap. EF Core's answer is different: instead of writing the audit insert by hand each time, override SaveChangesAsync once and let the framework's own change tracker tell you what just changed.

1 · ChangeTracker already knows what changed, before you ask

Every DbContext keeps a running list of every entity it has loaded or added, each tagged with an EntityState: Added, Modified, Deleted, or Unchanged. Microsoft's own change-detection reference is explicit about when this state is current: DbContext.SaveChanges and SaveChangesAsync call ChangeTracker.DetectChanges() automatically, "to ensure that all changes are detected before updating the database" — by the time SaveChangesAsync actually runs, every tracked entity's state already reflects exactly what's about to be written, no extra step required to ask for it.

That's the opening Lesson 46's Go version never had. A raw SQL UPDATE statement doesn't know, as a matter of language semantics, that it changed exactly the status column on account 42 — the Go code had to say so explicitly, by hand, building its own change JSON. EF Core's tracker already has that answer sitting in memory for every entity about to be saved, which is what makes writing the audit row automatically, once, actually possible.

2 · One override, not one insert per call site

Overriding SaveChangesAsync on the DbContext itself means every caller who already calls SaveChangesAsync — which is everyone, since that's the only way EF Core persists anything — gets audit rows for free, with no second statement to remember:

public class AppDbContext : DbContext
{
    private readonly ICurrentActor _actor; // Lesson 4's authenticated caller, injected once via the constructor

    public AppDbContext(DbContextOptions<AppDbContext> options, ICurrentActor actor) : base(options)
        => _actor = actor;

    public DbSet<Account> Accounts => Set<Account>();
    public DbSet<AuditLog> AuditLogs => Set<AuditLog>();

    public override async Task<int> SaveChangesAsync(CancellationToken ct = default)
    {
        var rows = new List<AuditLog>();
        foreach (var entry in ChangeTracker.Entries<Account>())
        {
            if (entry.State != EntityState.Modified) continue; // Added/Deleted skipped for this snippet's scope
            var changed = entry.Properties
                .Where(p => p.IsModified)
                .ToDictionary(p => p.Metadata.Name, p => p.CurrentValue);
            rows.Add(new AuditLog
            {
                ActorId = _actor.Id,
                Action = "account.update",
                EntityType = "account",
                EntityId = entry.Entity.Id,
                Change = JsonSerializer.Serialize(changed),
                CreatedAt = DateTimeOffset.UtcNow,
            });
        }
        AuditLogs.AddRange(rows); // queued into the SAME SaveChanges call, same transaction
        return await base.SaveChangesAsync(ct);
    }
}

Two details carry the whole idea. entry.Properties.Where(p => p.IsModified) is the C# answer to Lesson 46's hand-built change JSON — instead of the caller deciding what changed, PropertyEntry.IsModified reports it per property, read straight off the tracker. And calling AuditLogs.AddRange(rows) before base.SaveChangesAsync(ct) is what keeps Lesson 46's atomicity guarantee: the queued audit rows and the account update ride inside the exact same SaveChangesAsync call, so EF Core's own single implicit transaction covers both — nothing changes about why that matters, only how the two writes get queued together.

Frontend-habit trap: this is the same shape as a Redux middleware that inspects every dispatched action before it reaches the reducer, rather than every component remembering to log its own actions by hand. SaveChangesAsync is EF Core's one chokepoint every write passes through — overriding it once is the backend version of "put the logic in the middleware, not in every component."

3 · What this buys, and what it costs

The win over Lesson 46's version: nobody writing a new feature can forget the audit insert, because there's no insert left to remember — it happens inside the chokepoint every save already passes through. The cost is the one this override pattern always has: it only fires for changes that go through this DbContext's SaveChangesAsync. A bulk update run as raw SQL, or a migration, or a different service writing to the same table, bypasses the tracker entirely and produces no audit row — the same "only catches what goes through the one chokepoint" caveat Lesson 118's C# rate limiter already named for per-instance state. An automatic audit log is only as complete as the paths that are guaranteed to flow through it.

Q: "We're on EF Core — would you still hand-write an audit insert at every call site like our Go services do?" A strong answer, out loud: "No — I'd override SaveChangesAsync on the DbContext once, loop ChangeTracker.Entries for the entity types that need auditing, and read PropertyEntry.IsModified and CurrentValue to build the change record, the same way our Go code builds its change JSON by hand today. Queuing the audit rows before calling base.SaveChangesAsync keeps them in the same transaction, so the atomicity guarantee doesn't change. The real trade-off to flag: this only catches writes that go through this DbContext — a raw SQL bulk update or a migration would still bypass it silently, so it's not a substitute for checking where else the table gets written." The signal: naming the chokepoint-only limitation unprompted, not just describing the override.

Scope line

This lesson covers overriding SaveChangesAsync and reading ChangeTracker.Entries<TEntity>()/EntityEntry.State/PropertyEntry.IsModified to build an audit row automatically, for the Modified case specifically. It does not cover handling Added/Deleted states in the same loop (a straightforward extension of the same pattern, left out only for snippet length), EF Core's lower-level ISavingChangesInterceptor mechanism (a separate, more plumbing-heavy way to hook the same moment, useful when the audit logic needs to live outside the DbContext itself), or change-tracking proxies/notification entities (a different, opt-in change-detection strategy unrelated to audit logging specifically).
