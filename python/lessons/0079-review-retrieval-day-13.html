1 · Three questions, in the original teaching order

Answer each out loud or on paper before reading the fold-out answer. If one is shaky, note it and go fix it in the practice file below rather than only rereading the old lesson.

Day 76 — json.dumps/loads, indent=, default=. What is the actual difference between json.dump() and json.dumps(), and exactly when does json.dumps() call a function passed as default=?

Fold-out answer: dump/load always take an already-open file object and read or write it directly; dumps/loads work with a plain str already in memory, with no file involved at all — the trailing "s" means string, same conversion either way. dumps() tries its own built-in types first (str, int, float, bool, None, list, dict) and only calls default(value) on a value that is none of those, using whatever JSON-safe value that function returns in its place — a datetime turned into its .isoformat() string, or a dataclass turned into a dict via dataclasses.asdict().

Day 77 — secrets. Why is random the wrong module for generating a password-reset token, and why should a secret value be compared with secrets.compare_digest() instead of plain ==?

Fold-out answer: random builds its whole sequence from a seed using a deterministic formula — reproducible on purpose, which is exactly what Day 54 relied on for repeatable tests, and exactly why it's unsafe here: anyone who can guess or observe the seed can sometimes predict the rest of the sequence. secrets draws from the operating system's own cryptographically secure source instead, with no seed() at all. Plain == on strings typically stops comparing at the first mismatched character, so a wrong guess sharing more of the correct prefix takes measurably longer to reject than one that differs immediately — a timing attack can exploit that difference, measured over many attempts, to recover a secret character by character. compare_digest() always takes the same amount of time regardless of how much of the prefix matches, so the comparison itself leaks nothing.

Day 78 — pprint. What does pprint.pprint() actually change compared to plain print() on the same nested dict, and why might pprint() succeed on a value that json.dumps() rejects outright?

Fold-out answer: pprint() lays nested data out across multiple indented lines so the structure is visible at a glance, and — by default — sorts dict keys alphabetically so the same data always prints the same way regardless of insertion order; plain print() uses each object's default repr() with no such layout or ordering guarantee. json.dumps() only accepts JSON's own built-in types (dict/list/str/int/float/bool/None); pprint() accepts any Python object at all, including a set or a tuple used as a dict key, neither of which json.dumps() can serialize — because pprint()'s output is only for a human reading a terminal right now, never meant to be parsed back as data.
