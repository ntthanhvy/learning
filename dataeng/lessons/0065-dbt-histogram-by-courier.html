The reason courier grain earns its own lesson rather than a copy-paste of Day 63 with a different table name: stg_couriers has no name column. raw.restaurants carries both restaurant_id and a human-readable restaurant_name, which Day 63 carried through the grid so a reader never had to join back to see whose numbers they were looking at. raw.couriers (Day 1's schema: courier_id, vehicle, city, joined_at) has no equivalent — a courier in this project is identified by ID alone. Today's mart has to decide what to show instead of a name, and the honest answer is: nothing invented. vehicle and city are both real columns worth carrying through, because "which courier" is rarely the whole question a dispatcher asks — "which courier, on which vehicle, in which city" is closer to how a real operator would actually read this table.

2 · Reusing the same shape, crossed against a third axis with no name to carry

The construction is identical to Days 49 and 63: build the full grid first (every axis value paired with every bucket, via cross join), then left join the real data onto it with a composite join condition (Day 63's term — every matching axis, not just one, has to hold at once or a row can silently attach to the wrong group). Today's grid uses courier_id as the axis — but where Day 63 carried restaurant_name through for a human-readable label, today carries vehicle and city instead, because those are the real columns this raw table actually has, not a label invented to make the output look friendlier than the source data supports.

This is worth naming as a deliberate contrast, not an oversight: a mart should reflect the grain and the columns its source actually has. Faking a courier_name out of, say, "Courier " || courier_id would be a synthetic label — it would look nicer in a demo, but it carries zero information beyond the ID already sitting right next to it, dressed up to read like real data. vehicle and city, by contrast, are genuine attributes a dispatcher would ask about: "is it mostly the motorbike couriers running late, or is it one city's couriers specifically?"

3 · Build: couriers × buckets, then the real orders left-joined on top

In your food-delivery-pipeline repo, create models/marts/mart_delivery_time_histogram_by_courier.sql in full:

-- models/marts/mart_delivery_time_histogram_by_courier.sql
{{ config(materialized='table') }}

with order_durations as (
    -- orders joined to couriers (not restaurants, this time) and the
    -- placed/delivered pair of stg_order_events rows per order
    select
        o.order_id,
        c.courier_id,
        c.vehicle,
        c.city,
        extract(epoch from (d.delivered_at - p.placed_at)) / 60 as minutes_to_deliver
    from {{ ref('stg_orders') }} as o
    inner join {{ ref('stg_couriers') }} as c on o.courier_id = c.courier_id
    inner join {{ ref('stg_order_events') }} as p
        on o.order_id = p.order_id and p.status = 'placed'
    inner join {{ ref('stg_order_events') }} as d
        on o.order_id = d.order_id and d.status = 'delivered'
),

-- stg_couriers has no name column (unlike stg_restaurants) -- vehicle and
-- city are the real attributes carried through instead, not an invented label
couriers as (
    select distinct courier_id, vehicle, city from {{ ref('stg_couriers') }}
),

-- Day 48's exact bucket_series/bucket_grid CTEs, reused verbatim
bucket_series as (
    {{ dbt_utils.generate_series(var('histogram_bucket_count')) }}
),

bucket_grid as (
    select
        (generated_number - 1) * {{ var('histogram_bucket_minutes') }} as bucket_start_minutes,
        generated_number * {{ var('histogram_bucket_minutes') }} as bucket_end_minutes
    from bucket_series
),

-- new today: the two grids crossed into one, N couriers x 20 buckets
-- rows, before any real order is involved
courier_bucket_grid as (
    select
        couriers.courier_id,
        couriers.vehicle,
        couriers.city,
        bucket_grid.bucket_start_minutes,
        bucket_grid.bucket_end_minutes
    from couriers
    cross join bucket_grid
),

bucketed_orders as (
    select
        courier_bucket_grid.courier_id,
        courier_bucket_grid.vehicle,
        courier_bucket_grid.city,
        courier_bucket_grid.bucket_start_minutes,
        courier_bucket_grid.bucket_end_minutes,
        count(order_durations.order_id) as order_count
    from courier_bucket_grid
    left join order_durations
        on order_durations.courier_id = courier_bucket_grid.courier_id
        and order_durations.minutes_to_deliver >= courier_bucket_grid.bucket_start_minutes
        and order_durations.minutes_to_deliver < courier_bucket_grid.bucket_end_minutes
    group by courier_bucket_grid.courier_id, courier_bucket_grid.vehicle, courier_bucket_grid.city,
             courier_bucket_grid.bucket_start_minutes, courier_bucket_grid.bucket_end_minutes
)

select
    {{ dbt_utils.generate_surrogate_key(['courier_id', 'bucket_start_minutes']) }} as bucket_key,
    courier_id,
    vehicle,
    city,
    bucket_start_minutes,
    bucket_end_minutes,
    order_count
from bucketed_orders
order by courier_id, bucket_start_minutes

The left join's on clause carries the same three conditions Day 63's did — courier_id plus both bucket bounds — for the identical reason: dropping courier_id would silently let any courier's real orders attach to any other courier's bucket rows purely on timing. The one real difference from Day 63 is upstream of the join entirely: the couriers CTE selects vehicle and city because those are what stg_couriers actually has, not because they are the direct equivalent of restaurant_name — they aren't a label at all, just two more real attributes riding along for free once the grid-building join already has to touch that row.

4 · Four histograms, four grains, one pattern — and why courier timing answers a different question than restaurant timing

The project now carries four histogram marts side by side: platform-wide (Day 48), per-city (Day 49), per-restaurant (Day 63), per-courier (today). Each earns its place because each answers a question the others structurally cannot — the same judgment Days 48, 49 and 63 each already made about mart_delivery_sla. A restaurant-grain slow bucket points at something on the restaurant's side of the handoff: kitchen prep time, order-acceptance delay, how far the restaurant sits from its usual delivery zone. A courier-grain slow bucket points somewhere else entirely: a specific courier running behind across many different restaurants and cities, which a restaurant-grain table would never surface, because that courier's bad numbers get spread across however many different restaurants they deliver for.

That distinction is the practical reason this mart is worth building even though "a courier is slow" and "a restaurant is slow" can look identical from the mart_delivery_sla city rollup alone. Querying today's mart grouped by courier_id and filtered to the slow buckets answers "is this a kitchen problem or a delivery problem" in a way no city- or restaurant-grain table can, because it's the only one of the four that holds the restaurant side fixed and lets the courier side vary.

Q: "Your restaurant-level histogram looks fine for every restaurant, but ops is still getting complaints about late deliveries. What's missing, and what would you build?" A strong answer, out loud: "If every restaurant looks fine, the slowness probably isn't on the kitchen side of the handoff — it's worth checking the courier side instead, which a restaurant-grain table can't see at all, because a courier's own bad pattern gets spread across however many different restaurants they deliver for and diluted into each restaurant's own numbers. I'd build the same histogram construction one more time, crossed against distinct couriers instead of restaurants: generate the bucket ladder, cross join it against every courier so even a courier with zero slow orders still has a row showing zero, then left-join real per-courier, per-bucket counts onto that grid matching on courier id and bucket range. One wrinkle worth naming — couriers in this schema don't have a name column the way restaurants do, so I'd carry through the real attributes that do exist, vehicle and city, rather than inventing a label that looks like data but isn't. Filtering that mart to the slow buckets would show directly whether it's one courier running behind everywhere, or a vehicle type, or a city-specific pattern — three different root causes a restaurant-grain or city-grain table genuinely cannot tell apart." The signal: naming why restaurant-grain specifically can't see a courier-side problem, not just repeating "build another histogram," and flagging the missing-name wrinkle as a real data-honesty choice rather than skipping past it.
