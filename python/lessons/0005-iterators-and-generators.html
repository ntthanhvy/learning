Iterators & generators: lazy pipelines

Every for loop you've written since Day 1 has been looping over something built all at once — a full list in memory before the loop ever starts. Today's job: the mechanism that makes for work at all, and a way to produce a sequence one item at a time, on demand, so a script can process a file far bigger than memory without ever holding more than one piece of it. Day 3's callout promised this properly — here it is.

Bridge from SQL: a query plan doesn't materialize every intermediate table before the next operator runs — rows stream through WHERE, then the next stage, one at a time. A chain of generators is the same idea in Python: each stage pulls one item, does its bit, and hands it onward, instead of building a full intermediate list at every step.

1 · What actually makes a for loop work

A list is an iterable — you can write for x in a_list. So is a dict, a str, a range. What actually happens when Python runs that loop is two steps, normally hidden: first it calls iter() on the iterable to get an iterator, then it repeatedly calls next() on that iterator until there's nothing left:

nums = [10, 20, 30]

it = iter(nums)      # the iterator — remembers where it is
next(it)              # 10
next(it)              # 20 — same it, position advanced
next(it)              # 30
next(it)              # raises StopIteration — nothing left

A for loop is exactly that pattern, written for you: for x in nums calls iter(nums) once, then next() in a loop, catching StopIteration to know when to stop. The distinction worth holding onto: nums itself is iterable but has no memory of position — you can start a fresh loop over it any time. The iterator it, once created, is stateful — it remembers exactly where it left off, which is precisely the property today's generators exploit.

2 · A generator function: yield instead of building a list

Every function you've written up to now runs top to bottom and hands back one value with return — done, all at once. A generator function looks almost identical but uses yield instead of, or alongside, return:

def count_up_to(n):
    i = 1
    while i <= n:
        yield i        # pause here, hand back i, remember this exact spot
        i += 1

gen = count_up_to(3)   # calling it does NOT run the body at all yet
next(gen)              # 1 — body runs until the first yield, then pauses
next(gen)              # 2 — resumes right after that yield, runs to the next one
next(gen)              # 3
next(gen)              # raises StopIteration — loop condition finally false

Calling count_up_to(3) does not run any of the function's code — it immediately returns a generator, which is itself an iterator exactly per section 1 — it has a next(). The body only executes when something asks it to, and only up to the next yield, at which point it freezes with every local variable (here, i) intact until asked to resume. In practice you rarely call next() by hand — a plain for i in count_up_to(3): drives it exactly like any other iterable, one next() per loop turn, with StopIteration ending the loop silently the way it always does.

Compare that to the version that isn't lazy — a function returning a whole list:

def count_up_to_list(n):
    result = []
    i = 1
    while i <= n:
        result.append(i)
        i += 1
    return result      # the WHOLE list exists in memory before the caller sees any of it

Both loops over 3 print the same three numbers. The difference is entirely about when the values come into existence and how much memory is ever alive at once — which is exactly section 3's point.

3 · Why this matters: constant memory, not proportional to input size

count_up_to_list(10_000_000) builds a ten-million-element list, all of it resident in memory, before the first print ever runs. count_up_to(10_000_000) never holds more than the current i — each value is produced, used, and discarded before the next one is even computed. Scale that up to the real motivating case: a 10 GB log file, read and processed line by line.

def read_lines(path):
    with open(path) as f:
        for line in f:      # a file object is itself an iterator — one line in memory at a time
            yield line.strip()

# processing a 10 GB file: at any instant, exactly one line is alive in memory,
# never the whole file — the loop below never knows the file is huge
for line in read_lines("huge.log"):
    if "ERROR" in line:
        print(line)

An open file object is already a built-in iterator for this exact reason — looping it line by line, as read_lines does above, never reads the whole file at once either. Wrapping it in a generator here doesn't change that; it adds the .strip() step lazily, one line at a time, ready to feed the pipeline sections 4 and 5 build. (with open(...) as f is a context manager, properly Day 6's topic — read it today as "safely open and auto-close the file.")

4 · Generator expressions: the lazy sibling of a comprehension

Day 2's list comprehension, [x for x in nums], still builds the whole list immediately — same eagerness as count_up_to_list. Swap the square brackets for parentheses and you get a generator expression — the exact same three-slot grammar, but lazy:

nums = [1, 2, 3, 4, 5]

squares_list = [n * n for n in nums]     # list comprehension — builds all 5 values NOW
squares_gen  = (n * n for n in nums)     # generator expression — builds NONE yet

type(squares_gen)                          # <class 'generator'> — same kind of object section 2 built
next(squares_gen)                          # 1 — computed only now, on demand
next(squares_gen)                          # 4
sum(n * n for n in nums)              # 55 — no brackets at all needed as a lone function argument

That last line is the form Day 3's Counter(row["city"] for row in sales) already used, unexplained at the time — a generator expression passed straight into a function that consumes an iterable, with the parentheses of the function call doing double duty so the extra pair isn't needed. Reach for a generator expression over a list comprehension whenever the result is only ever going to be looped over once and thrown away — sum(...), max(...), feeding another loop — since there's no reason to pay for a full list nothing keeps.

5 · Chaining generators into a pipeline

The payoff: generators chain. Each stage takes an iterable and yields a transformed one, lazily — nothing runs until the final stage is actually consumed, and at that point values flow through every stage one at a time, the way section 1's bridge described a query plan streaming rows through operators.

from collections import defaultdict

def parse_rows(lines):
    for line in lines:
        city, amount = line.split(",")
        yield {"city": city, "amount": int(amount)}

def only_positive(rows):
    for row in rows:
        if row["amount"] > 0:
            yield row

raw_lines = ["Hanoi,120", "HCMC,-10", "Hanoi,45", "Danang,200"]

pipeline = only_positive(parse_rows(raw_lines))   # nothing has run yet — just wired stages together

totals = defaultdict(int)
for row in pipeline:                          # NOW values flow: one line parsed, filtered, grouped, per turn
    totals[row["city"]] += row["amount"]
# {'Hanoi': 165, 'Danang': 200} — HCMC's -10 row never even entered the dict

Read only_positive(parse_rows(raw_lines)) from the inside out: parse_rows yields parsed dicts one at a time, only_positive pulls from that lazily and yields only the ones that pass, and the final for loop's defaultdict grouping — Day 3's exact pattern — is what actually drives the whole chain, one row at a time, start to finish. Nothing is built in full at any stage; at most one row is "in flight" between any two stages at once. Swap raw_lines for read_lines("huge.log") from section 3 and this identical pipeline scales to a file far bigger than memory, unchanged.

Where pandas goes from here: pandas operations are eager and vectorized — df[df["amount"] > 0].groupby("city")["amount"].sum() computes each stage over the whole column at once rather than streaming row by row through lazy generators. Different tradeoff, same shape of question ("filter, then group"). Not covered here; that's data/'s job, and this is the only sentence in this lesson that mentions it.
