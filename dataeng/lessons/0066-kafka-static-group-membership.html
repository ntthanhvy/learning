1 · The cost Day 34 showed but didn't name

Day 34 ran two consumers in the same group, killed one, and watched the group coordinator hand its partitions to the survivor — a real rebalance, proven live with kafka-consumer-groups.sh --describe. That lesson's own build step waited a fixed 12 seconds after the kill specifically to clear session.timeout.ms (10 seconds, confluent-kafka's default), the point at which the coordinator judges a silent member dead. Nothing in that lesson asked the next question: what if the consumer that died comes right back — a deploy, a container restart, a crash-and-restart within a few seconds — rather than actually being gone for good?

By default, Kafka cannot tell those two cases apart. A consumer that stops sending heartbeats looks identical to the coordinator whether it is dead forever or just restarting — all the coordinator sees is silence past session.timeout.ms. So a routine restart of this course's one-instance warehouse-loader consumer pays the same price Day 34's kill-and-reassign did: every partition it owned gets rebalanced away and then, once the restarted process rejoins, rebalanced again to hand them back. Two rebalances, each briefly pausing consumption on every affected partition, to accomplish nothing — the exact same process ends up owning the exact same partitions it had before.

2 · Static membership: give the coordinator a name, not just a heartbeat

A static group membership consumer sets group.instance.id to a fixed string it chooses itself, instead of relying purely on the dynamic member ID Kafka assigns fresh every time a process joins. The coordinator remembers which partitions belong to which group.instance.id. When a process carrying that same ID disappears and reappears before its membership record expires, the coordinator treats it as the same member returning — not a new one joining — and hands back exactly what it already owned, no reassignment negotiation needed anywhere in the group.

The timing changed, too, and it's worth being precise about which timer does what now:

MembershipWhat session.timeout.ms governs
Dynamic (Day 34's default)The heartbeat-missed clock only — once it expires, the member is dropped and its partitions are reassigned immediately, for good.
Static (today, group.instance.id set)Both the heartbeat-missed clock and the full grace window to rejoin — the slot sits reserved, not reassigned, until this same timer also expires with no rejoin. There is no separate, longer timer for the grace window; raising this one value is the only lever.

That's why today's config widens session.timeout.ms from Day 34's 10-second default to something closer to a real restart's duration: too short, and a legitimate restart still misses its own grace window and rebalances anyway; too long, and a genuinely dead consumer's partitions sit unreassigned — reachable only by nobody — for that whole window. 45 seconds is a reasonable portfolio-scale number for a container restart; a production system would tune it against real deploy timing, not guess.

Bridge from Day 55: static membership is a different lever from partition.assignment.strategy. Day 55's cooperative-sticky assignor minimizes how many partitions move during a rebalance that is already happening. Static membership is about avoiding triggering that rebalance at all for a same-process restart. Both can run at once — they solve adjacent but different problems.

3 · Build: add group.instance.id, then restart and watch nothing move

Edit scripts/consume_order_events.py's Consumer({...}) call — the poll loop, INSERT_SQL and commit-after-write from Day 6 are unchanged, this is config only:

# scripts/consume_order_events.py -- two new keys on the existing Consumer()
consumer = Consumer(
    {
        "bootstrap.servers": BOOTSTRAP,
        "group.id": GROUP_ID,
        "group.instance.id": "warehouse-loader-1",
        "session.timeout.ms": 45000,
        "enable.auto.commit": False,
    }
)

Start the consumer, confirm its assignment, then kill and restart it quickly — well inside the new 45-second window — and compare the group's partition ownership before and after:

uv run --with confluent-kafka --with "psycopg[binary]" python3 scripts/consume_order_events.py &
CONSUMER_PID=$!
sleep 3
docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group warehouse-loader

kill -9 $CONSUMER_PID
sleep 5    # well under the new 45s session.timeout.ms
uv run --with confluent-kafka --with "psycopg[binary]" python3 scripts/consume_order_events.py &
CONSUMER_PID=$!
sleep 3
docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group warehouse-loader

5 · What this doesn't fix

Static membership only helps the case where the same process identity returns in time. It does nothing for a consumer that is actually gone for good — that still rebalances, exactly as Day 34 showed, once session.timeout.ms expires with no rejoin. It also doesn't shrink that expiry window's cost: for up to session.timeout.ms, a statically-assigned member's partitions are reserved but unread by anyone else, so lag can grow during a slow restart in a way it wouldn't if the group rebalanced immediately. The trade is explicit: fewer needless rebalances during ordinary restarts, in exchange for a longer window where a truly dead consumer's partitions sit idle before anyone else picks them up. For this course's single-consumer warehouse-loader group, that trade is clearly worth it — a routine restart is far more common here than a permanent failure, and nothing downstream is latency-sensitive enough to notice a 45-second gap.

Q: "Your Kafka consumer rebalances every time you redeploy it, even though it's the exact same consumer coming right back. How would you avoid that?" A strong answer, out loud: "By default, Kafka's coordinator can't distinguish a consumer that died for good from one that's about to restart — both just look like missed heartbeats past session.timeout.ms, so both trigger a full rebalance, even though a redeploy ends with the exact same process re-claiming the exact same partitions it already had. The fix is static group membership: set group.instance.id to a fixed value the consumer keeps across restarts. If that same instance ID rejoins before its membership expires, the coordinator rebinds it to its old partitions directly instead of running the join-and-sync rebalance protocol. I'd also widen session.timeout.ms to comfortably cover how long a real restart takes, since for a static member that's also the full grace window before the coordinator gives up and rebalances anyway. The trade-off is that a genuinely dead consumer's partitions now sit idle for that whole window before anyone else picks them up, so you don't set it arbitrarily high — you size it to the deploy, not to infinity." The signal: naming that the coordinator cannot distinguish "restarting" from "dead" without an explicit identity, and stating the trade-off (slower failover) rather than presenting static membership as a strictly free win.

Scope line

This lesson covers group.instance.id and its interaction with session.timeout.ms for a single-consumer group restarting quickly, confirmed live only as a valid, accepted config shape against the installed client — not against a real broker's actual rebalance behavior this round. It does not cover the coordinator-side group.min.session.timeout.ms/group.max.session.timeout.ms broker bounds that would clamp an unreasonable client-side value (a broker-tuning concern, past this course's working-level Kafka scope per MISSION.md), fencing a case where two processes briefly carry the same group.instance.id at once (confluent-kafka's client raises a fencing error in that case, but this course's single-process warehouse-loader never runs two copies with the same static ID, unlike Day 34's deliberately-different dynamic IDs), or extending today's single-instance change to Day 34's two-consumer scenario with two distinct static IDs — a natural follow-up, not required for today's one-consumer portfolio pipeline to benefit.
