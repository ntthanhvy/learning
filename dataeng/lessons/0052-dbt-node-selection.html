1 · The gap: every lesson so far has run the whole project

Every build command this course has shown — dbt run, dbt build, Day 7's Airflow BashOperator — has selected every single model and test in the project, every time. That was fine at six models. It stops being fine the moment one edit to stg_orders.sql means waiting on dim_restaurants, three histogram marts, two snapshots and a dozen tests that have nothing to do with the line that just changed. Day 15 already used a narrower selection once, state:modified+, to keep CI fast — but that lesson treated + as a detail of one specific selector, not as the general mechanism it actually is. Today is that mechanism, on its own, for the loop that matters most day to day: a human, at a terminal, wanting to rebuild exactly what one edit touched.

Every --select (and --exclude) argument is a node selection expression, not a filename glob. A bare model name (stg_orders) is the simplest form — it selects exactly that one model — but the real power is the handful of graph operators and methods layered on top of it.

2 · Confirmed live: five expressions, five exact node sets

Built a scratch project shaped exactly like the real one — stg_orders, stg_restaurants, stg_couriers feeding fct_orders, dim_restaurants, which both feed mart_delivery_sla — with +tags: ["hourly"] on every staging model and +tags: ["nightly"] on every mart, set once in dbt_project.yml the same way Day 31 configured generate_schema_name at the folder level. Ran dbt list --select "<expr>" --resource-type model for each, reading the resolved set back directly rather than trusting the docs' prose alone:

The last row is the one worth slowing down on, because it's the row most likely to surprise someone who assumes @ is just a fancier +. stg_orders+ (row 1) stays strictly downstream of stg_orders — three nodes, no dim_restaurants, no stg_restaurants. @stg_orders pulls in two more nodes neither of those is related to by any direct ancestor/descendant path from stg_orders alone: mart_delivery_sla (a descendant of stg_orders) also depends on dim_restaurants and stg_restaurants, and @'s whole job is to also pull in every ancestor of every descendant it finds — so building mart_delivery_sla for real means also having a fresh dim_restaurants underneath it, and @ is the operator that guarantees that, where plain + does not.

Confirmed the inverse too: --exclude "tag:nightly" combined with --select "stg_orders+" resolved to just stg_orders alone — fct_orders and mart_delivery_sla both carry the nightly tag inherited from the marts folder, and --exclude removes a node (and anything that node's own tests depend on) from whatever --select already produced, the same AND-NOT logic a Python set difference would give.

3 · Why @ exists at all: a build that references a stale table is not the same as a correct one

The gap @ closes is a real correctness bug, not a style preference. Say an edit lands in stg_orders.sql and the dev loop runs dbt build --select "stg_orders+" — the honest, minimal selection for "rebuild what I touched and its descendants." mart_delivery_sla gets rebuilt in that run, correctly, as a fresh select over fct_orders and dim_restaurants — but dim_restaurants itself was not selected, so its table in the warehouse is whatever was last built, possibly days ago, possibly before a restaurant's commission_rate changed. mart_delivery_sla runs cleanly and reports success; the row it produces can still be wrong, built against a stale dimension + never thought to touch because dim_restaurants isn't downstream of stg_orders at all — it's a sibling ancestor of the same descendant.

@stg_orders is the expression that actually guarantees a correct rebuild of everything stg_orders's change could affect: every descendant, and every ancestor those descendants need to be built correctly, recursively. It is less commonly reached for than plain + because it rebuilds more — the trade this course has made in every prior lesson (Day 15's CI, every manual dbt build) has been "rebuild everything" exactly to sidestep this exact gap, at the cost of speed. @ is the one operator that keeps the speed of a narrow selection without reintroducing it.

4 · Build: a Makefile target that uses this for real

In your food-delivery-pipeline repo, add one target to the Makefile Day 26 already created, right alongside demo:

build-changed: # usage: make build-changed MODEL=stg_orders
	cd food_delivery_pipeline && uv run --with "dbt-postgres==1.11.0" dbt build --select "@$(MODEL)" --profiles-dir .

This is deliberately the @ form, not $(MODEL)+ — a dev-loop target whose whole job is "rebuild everything a change to this one model could affect, correctly" should default to the operator that actually guarantees that, the same reasoning Section 3 just walked through. A faster, narrower stg_orders+-style run is still one plain dbt build --select "..." away any time the full correctness guarantee isn't needed — today's target is the safe default, not the only option.

Q: "Your dbt project has grown past 100 models. How do you avoid rebuilding all of them every time you touch one file locally?" A strong answer, out loud: "dbt's node selection syntax lets --select and --exclude take graph operators, not just model names. model+ selects a model and everything downstream of it — the obvious first move for a local edit. But the operator I actually default to for 'did my change break anything' is @model: it also pulls in every ancestor of each descendant it finds, which matters because a descendant with a second parent I didn't touch still needs that second parent freshly built to be correct, not just present. model+ can report a clean build on a mart that's secretly still reading a stale sibling table — @model is the one that doesn't let that happen. I only reach for the narrower, faster form when I specifically don't need that guarantee, like a quick syntax check on one model alone." The signal: naming @ as solving a real correctness gap plain + leaves open, not just "a faster version of the same thing."
