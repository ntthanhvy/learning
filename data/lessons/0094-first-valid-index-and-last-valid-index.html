first_valid_index() / last_valid_index(): trimming the NaN padding off a time series

A fresh scan today found a genuine zero-coverage gap: every lesson on missing data so far (Lessons 3, 45, 60, 65, 91, 93) has been about values missing inside a column. None of them answer a different, very common cleaning question: a sensor/report feed often starts recording late or stops early, leaving real NaN padding at the very start and end of a time series. dropna() would also delete real gaps in the middle — too blunt. Today's two methods find exactly where the real data begins and ends, so you can trim the edges and leave the middle alone.

1 · first_valid_index() / last_valid_index(): the label of the first and last non-NaN row

first_valid_index() and its mirror last_valid_index() scan a Series/DataFrame in its current row order and hand back the real label — confirmed directly (pandas 3.0.6), this is exactly equivalent to s.dropna().index[0] / [-1], just without building the intermediate dropped copy:

temp = pd.Series(
    [np.nan, np.nan, 20.1, 21.4, 19.8, np.nan, np.nan],
    index=pd.date_range("2026-01-01", periods=7, freq="D"),
)
-- 2026-01-01   NaN
-- 2026-01-02   NaN
-- 2026-01-03  20.1
-- 2026-01-04  21.4
-- 2026-01-05  19.8
-- 2026-01-06   NaN
-- 2026-01-07   NaN

temp.first_valid_index()
-- Timestamp('2026-01-03')   -- the real label, not position 2
temp.last_valid_index()
-- Timestamp('2026-01-05')

The actual win: slicing between the two trims the leading/trailing NaN padding while leaving any real gap in the middle of the series completely alone — something dropna() can't do without deleting that middle gap's row too:

trimmed = temp.loc[temp.first_valid_index():temp.last_valid_index()]
-- 2026-01-03  20.1
-- 2026-01-04  21.4
-- 2026-01-05  19.8   -- exactly the real 3 rows, nothing more

2 · No skipna, no axis, no arguments at all — and None instead of raising

Confirmed directly via inspect.signature(): both methods take no parameters besides self — no skipna= to turn off (there's nothing to turn off; skipping missing values is the whole point), no axis= either. On a DataFrame, confirmed directly, there's no per-column version at all: it looks across the entire row and returns one label for the first/last row where any column has a real value — a different shape of answer from Lesson 91's idxmax(axis=1), which always returns one label per row, not one label for the whole frame.

df = pd.DataFrame({
    "a": [np.nan, np.nan, 1, 2],
    "b": [np.nan, 3, np.nan, np.nan],
}, index=["w", "x", "y", "z"])

df.first_valid_index()
-- 'x'   -- row "w" is all-NaN; row "x" has b=3, so IT wins, even though a is still NaN there

And the sharpest contrast with this course's whole recent NaN-position thread (Lessons 20, 91, 93: idxmax() raises ValueError: Encountered all NA values on an all-NaN row/Series, and plain np.argmax() silently returns the NaN's own position): these two methods do neither. Confirmed directly — an all-NaN Series, and a genuinely empty one, both just return None, quietly, no exception at all:

pd.Series([np.nan, np.nan]).first_valid_index()
-- None   -- no ValueError, unlike idxmax() on the same data
pd.Series([], dtype=float).first_valid_index()
-- None

That's the trap worth naming out loud: code written assuming "it raises if nothing's there, like idxmax() does" will instead silently carry a None forward — and series.loc[None:last] doesn't raise either, it just does something other than what was intended. Always worth an explicit is None check before slicing with the result on data that might be entirely missing.

Q: "You're given a sensor feed that starts a day late and drops out early. How do you trim just the padding, keeping any real gap in the middle?" A strong answer, out loud: "dropna() is too blunt here — it would delete any real missing reading in the middle of the series too, not just the leading/trailing padding. Instead I'd use first_valid_index() and last_valid_index(): they scan in row order and return the actual index label of the first and last row with a real value, then I slice between them with .loc[first:last]. That keeps the middle exactly as-is and only trims the edges. One thing I'd check first: if the whole series could plausibly be empty or all-missing, both methods quietly return None instead of raising — unlike idxmax(), which raises ValueError on an all-NaN input — so I'd guard for None before slicing with it, not assume an exception would catch that case for me." The signal: naming dropna() as the wrong tool first (and why), knowing the None-not-raise behavior as a real trap, and contrasting it correctly against idxmax()'s raising behavior from memory.
