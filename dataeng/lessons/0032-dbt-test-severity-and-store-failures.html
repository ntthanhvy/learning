dbt test severity (warn/error) & store_failures

Today's tangible win: two of Day 3's existing tests get a config() block that changes what a failure actually does — one downgraded to warn so a known-messy column stops blocking the whole build, and one upgraded with store_failures: true so the exact offending rows land in a queryable table instead of only ever appearing once in a scrollback log.

1 · Every test so far has had exactly one setting: fail hard, or don't run

Since Day 3, every dbt test in this project has behaved the same way: its query runs, and if it returns any rows, dbt build reports ERROR for that test and the whole build's exit code goes non-zero. That is the right default — a relationships test catching an orphan restaurant_id should block a build, because downstream marts would silently carry a broken join. But not every test deserves the same reaction. A courier record with a null vehicle field is worth knowing about; it is not worth failing Day 7's whole nightly dbt build over, the way a CI pipeline failing a deploy over a lint warning instead of a real compile error wastes everyone's attention on the wrong signal. dbt's answer is severity: a per-test setting, warn or error, defaulting to error for every test written so far without anyone naming it explicitly.

2 · severity: warn on a test you want visible, not blocking

Day 3's stg_orders.yml added a relationships test on courier_id, asserting every order's courier exists in stg_couriers. In the real seed data that's always been true, but couriers who leave the platform are a real, expected business event this project hasn't modelled yet — an order placed while a courier was active, then that courier's row removed later, would orphan the join through no fault of the pipeline. Erroring the whole build over that is the wrong reaction until a courier-deactivation flow actually exists; today it becomes a warn, visible every run without blocking one:

-- models/staging/stg_orders.yml -- courier_id's relationships test, edited
      - name: courier_id
        tests:
          - not_null
          - relationships:
              arguments:
                to: ref('stg_couriers')
                field: courier_id
              config:
                severity: warn

The config: key nests under the test itself, same level as arguments: — not a sibling of tests:, and not something that applies to the whole column. restaurant_id's own relationships test, just above it in the same file, keeps its default error untouched: an orphan restaurant really would break fct_orders' join, so that one should still fail loud. Severity is a per-test decision, made on purpose, not a project-wide dial.

3 · store_failures: keep the offending rows, not just a count

Day 3's singular test, assert_positive_subtotal, selects the exact rows that break the rule — but only Postgres sees them, for the length of one test query, then they're gone. The scrollback log has the rows from whichever run you happened to be watching; a run two days from now with a new bad row shows new output you'd have to go find. store_failures fixes that: dbt writes the failing rows into a real table, rewritten fresh on every run, queryable any time with ordinary SQL instead of grepped out of a log you may not still have.

-- tests/assert_positive_subtotal.sql -- add a config() block at the top
{{ config(severity = 'error', store_failures = true) }}

select
    order_id,
    subtotal
from {{ ref('stg_orders') }}
where subtotal < 0

A singular test sets config via the {{ config(...) }} Jinja function at the top of its own .sql file, not YAML — there is no column or model to attach a tests: block to, since the whole file is the test. severity stays error here on purpose: a negative subtotal is exactly the kind of row that should still block a build. store_failures is independent of severity — an error test can store its failures just as a warn test can, the two settings answer different questions ("does this block the build" vs. "do I keep a queryable record of what failed").

4 · Where the stored rows actually land

By default, dbt creates failure tables in a schema named <target schema>_dbt_test__audit — on this project's dev target, that's dbt_dev_dbt_test__audit, a sibling of dbt_dev itself, not mixed into it. Each stored test gets one table, named after the test (dbt's own generated or custom test name). Query it like any other table:

uv run --project ../dbt_env dbt build --select assert_positive_subtotal
docker compose exec -T postgres psql -U fdp -d fdp -c \
  "select * from dbt_dev_dbt_test__audit.assert_positive_subtotal;"

Expected, assuming the seed data is already clean from Day 3's fix: 0 rows in both the build's own PASS line and this query — the audit table is overwritten empty on a passing run, not left holding a stale failure from before. Plant a bad row on purpose to see it work end to end:

docker compose exec -T postgres psql -U fdp -d fdp -c \
  "UPDATE raw.orders SET subtotal = -5.00 WHERE order_id = 1;"
uv run --project ../dbt_env dbt build --select assert_positive_subtotal

Expected: ERROR=1, naming assert_positive_subtotal — then re-run the same psql query above and expect exactly 1 row back: order_id 1, subtotal -5.00. Revert the row afterward (UPDATE raw.orders SET subtotal = <original value> WHERE order_id = 1; — check Day 1's seed script for the original) so the project returns to its known-clean baseline.

The real change isn't visible in today's numbers; it's in what happens the next time a courier goes missing: WARN=1 instead of a failed build, and a build that still completes.

This is still a deliberate, narrow choice — named honestly. Downgrading a test to warn is easy to misuse as a way to silence a real problem instead of fixing it. The only test touched this way today is one backed by a concrete, named reason (couriers leaving the platform is a real, not-yet-modelled event) — not "this test is annoying." A warn with no reason anyone could state out loud is a test slowly being ignored, not a test correctly scoped.

Q: "What's the difference between a test's severity and store_failures?" A strong answer, out loud: "Severity decides what a failing test does to the build — error fails dbt build with a non-zero exit code, warn logs it and lets the build keep going, still exiting zero. That's useful for a real but non-blocking signal, like a foreign key that can legitimately go stale before a cleanup process catches up. store_failures is a completely separate setting: it writes the exact failing rows into a real table in the warehouse, rewritten fresh every run, so you can query what failed with ordinary SQL instead of re-running the build and reading console output. The two combine independently — I've got one test that's error plus stored, because a negative subtotal should still block a build and I want the exact rows on hand, and one that's warn with no storage, because it's just a heads-up on a known, accepted gap." The signal: naming that the two configs answer different questions, not treating "softer" and "more visible" as the same axis.
