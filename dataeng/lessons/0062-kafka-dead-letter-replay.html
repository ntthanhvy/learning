1 · The gap Day 41 named and left open on purpose

Day 41's own scope line named this directly on its way out: "it does not cover replaying or reprocessing dead-lettered rows later (a real follow-up workflow, not today's)." That gap matters more than it first sounds, because a dead-letter table that only ever grows is barely better than silently dropping messages — a human can see the quarantined rows, but nothing in this course's pipeline ever does anything with them. Two real situations land a row in dead_letter_events and deserve different outcomes:

  • Permanently bad data: malformed JSON, or a required field truly never sent — Day 41's own two test cases. No amount of retrying fixes these; a human has to look.
  • Transiently bad timing: a message that is valid and complete, but failed for a reason that has nothing to do with the message itself — Postgres briefly unreachable, a constraint that didn't exist yet, a bug in consume_order_events.py that got fixed after the message was already dead-lettered. Re-running the exact same parse-and-insert logic against the exact same bytes now succeeds.

A replay script is exactly how a dead-letter table earns its name: a place items wait to be looked at again, not a graveyard.

2 · Reusing Day 6's idempotent insert, on purpose

The replay script doesn't invent new landing logic — it reuses Day 6's exact INSERT ... ON CONFLICT (event_id) DO NOTHING against raw.order_events, unchanged. That reuse is the whole safety argument, not a shortcut: Day 6 already made landing an event idempotent — bridge from backend: the same idempotency-key shape backend/ covers for an API request, applied here to a warehouse write — so replaying the identical bytes twice, by accident or by design, cannot create a duplicate row. That is what makes it safe to answer "what if I run the replay script twice?" with "nothing changes the second time," without adding a single new guard anywhere.

3 · Build: scripts/replay_dead_letters.py

In your food-delivery-pipeline repo, add a new script — it reads every row currently in dead_letter_events, re-parses the raw bytes, and either lands the event for real or records a fresh error on the same row:

"""Replay rows out of raw.dead_letter_events back into raw.order_events."""
import json

import psycopg

DSN = "postgresql://fdp:fdp@localhost:5432/fdp"

SELECT_SQL = "SELECT id, raw_value FROM raw.dead_letter_events ORDER BY id"

INSERT_SQL = """
    INSERT INTO raw.order_events (event_id, order_id, status, occurred_at)
    VALUES (%(event_id)s, %(order_id)s, %(status)s, %(occurred_at)s)
    ON CONFLICT (event_id) DO NOTHING
"""

DELETE_SQL = "DELETE FROM raw.dead_letter_events WHERE id = %(id)s"

UPDATE_ERROR_SQL = """
    UPDATE raw.dead_letter_events
       SET error = %(error)s, failed_at = now()
     WHERE id = %(id)s
"""


def main():
    conn = psycopg.connect(DSN)
    replayed, still_dead = 0, 0
    with conn:
        with conn.cursor() as cur:
            cur.execute(SELECT_SQL)
            rows = cur.fetchall()

        for row_id, raw_value in rows:
            try:
                event = json.loads(raw_value)   # bytea column loads as bytes; json.loads() takes bytes directly
                params = {
                    "event_id": event["event_id"], "order_id": event["order_id"],
                    "status": event["status"], "occurred_at": event["occurred_at"],
                }
                with conn.cursor() as cur:
                    cur.execute(INSERT_SQL, params)
                    cur.execute(DELETE_SQL, {"id": row_id})
                conn.commit()
                replayed += 1
                print(f"replayed dead_letter id={row_id} -> order_events event_id={params['event_id']}")
            except (json.JSONDecodeError, KeyError) as exc:
                conn.rollback()
                with conn.cursor() as cur:
                    cur.execute(UPDATE_ERROR_SQL, {"id": row_id, "error": str(exc)})
                conn.commit()
                still_dead += 1
                print(f"still dead id={row_id} error={exc}")

    print(f"REPLAYED={replayed} STILL_DEAD={still_dead}")


if __name__ == "__main__":
    main()

Two things worth noticing on purpose, not by accident: conn.rollback() on the failure path exists for exactly the reason Day 41's own consumer needed it — a failed statement leaves a Postgres transaction unusable until it's rolled back, so the next statement on that same connection (today, the UPDATE that records the fresh error) would fail too without it. And a still-broken row is UPDATEd, never DELETEd — the whole point is that nothing quarantined ever vanishes without a human deciding so.

Q: "Your pipeline has a dead-letter table for Kafka messages that failed to land. How do you handle the rows that pile up in it?" A strong answer, out loud: "A dead-letter table only buys you something if it's also a queue of work to come back to, not just a place things get dropped and forgotten. I'd write a separate replay process that re-reads each quarantined row's raw bytes and re-attempts the exact same parse-and-insert logic that failed originally. Some of those failures are permanent — bad JSON, a field that was genuinely never sent — and replaying changes nothing there, so the row stays, with its error refreshed. But some failures are transient: the database was briefly down, or a bug got fixed after the message was already dead-lettered, and replaying those lands them for real. The safety argument is that the replay's insert reuses the exact same idempotent ON CONFLICT DO NOTHING the original consumer used, so running the replay on a schedule, or by accident twice in a row, can never create a duplicate row — it either makes progress or it doesn't, and either way nothing downstream can tell the difference from a message that landed on the first try." The signal: distinguishing permanent from transient failure instead of treating every dead-lettered row the same, and naming idempotency as what makes repeated replay safe rather than something the replay script has to reinvent.

Scope line

This lesson covers a standalone replay script that re-parses every row currently in dead_letter_events and either lands it in order_events for real or updates its error in place. It does not cover scheduling the replay automatically (an Airflow task is the obvious next home for it, but this course's single DAG doesn't yet have a slot for a periodic maintenance task, and adding one without a real trigger would be scope creep for its own sake), alerting when the dead-letter table's row count crosses a threshold (Day 46 already built exactly that alerting shape for a different signal — the pattern transfers directly, not re-derived here), or automatically distinguishing "permanent" from "transient" failures ahead of time — today's script finds out empirically, by actually re-attempting the insert, rather than trying to classify the error text first.
