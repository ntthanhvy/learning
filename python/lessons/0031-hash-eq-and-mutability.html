__hash__: why a custom __eq__ can silently break dict and set

Day 30 wrote __eq__ by hand for the first time. Today shows the side effect nobody warns you about: defining __eq__ quietly disables the dunder method that lets an object be a dict key or a set element at all — __hash__ — unless you write that one too. Today explains what __hash__ does, why Python disables it the moment __eq__ appears, and why an object with mutable state should usually leave it disabled rather than fix it.

Bridge from SQL: a table's primary key has to stay put while it's being used as a lookup or a join key — UPDATE orders SET id = 999 WHERE id = 1 against a row still referenced elsewhere breaks every index and every foreign key pointing at the old value. Python's dict and set have the exact same requirement for whatever you use as a key: it has to produce the same lookup value for as long as it's stored, or the structure can no longer find it. Today's dunder method, __hash__, is what computes that lookup value — and Python's own safety rule for it is exactly "don't let a value that can change be used as a key."

1 · What __hash__ actually does

Day 3 said dict keys and set elements "must be immutable (hashable)" without explaining the mechanism. Here it is: hash(x) calls x.__hash__(), producing an integer Python uses to decide which internal bucket x belongs in — the reason dict/set lookup is direct instead of a scan through every entry. Every plain object already has one, inherited from the base object class:

class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

p = Point(1, 2)
hash(p)             # some integer — works, based on identity (Day 1's `is`), not on .x/.y
{p: "first point"}    # fine — a plain object is hashable by default

The default __hash__ is based on identity — the same object always hashes the same way, but two separately built Point(1, 2)s hash differently, because the default __eq__ (Day 30) also compares identity. The two stay in lockstep on purpose: x == y being true always implies hash(x) == hash(y) for the defaults, which is exactly the rule dict/set lookup depends on.

2 · Defining __eq__ breaks that lockstep

Day 30's Money defined __eq__ to compare .cents instead of identity — two different objects with the same cents now compare equal. But nothing told __hash__ about that change, so Python takes it away instead of leaving it wrong:

class Money:
    def __init__(self, cents):
        self.cents = cents

    def __eq__(self, other):
        if not isinstance(other, Money):
            return NotImplemented
        return self.cents == other.cents

hash(Money(500))          # TypeError: unhashable type: 'Money'
{Money(500): "five dollars"}  # same TypeError — a dict key must be hashable

This is not a bug to work around by accident — it is Python's documented behavior: "a class that overrides __eq__() and does not define __hash__() will have its __hash__() implicitly set to None." Leaving the old identity-based hash in place would have been actively wrong — it would let two "equal" Money objects land in different buckets of the same dict, so a lookup could miss a key that == says is right there. Python would rather refuse outright than let that silently corrupt a lookup.

3 · Fixing it — and the mutability trap

The fix looks like matching __hash__ to whatever field (or fields, wrapped in a tuple) __eq__ compares, passed through the built-in hash() function:

class Money:
    def __init__(self, cents):
        self.cents = cents

    def __eq__(self, other):
        if not isinstance(other, Money):
            return NotImplemented
        return self.cents == other.cents

    def __hash__(self):
        return hash(self.cents)   # same field __eq__ compares — equal Money now hash equal too

{Money(500): "five dollars"}   # works now — hashable again
Money(500) == Money(500)     # True, and hash(Money(500)) == hash(Money(500)) — back in lockstep

This is safe for Money only because nothing ever reassigns .cents after construction. If a class's fields can change after creation — the ordinary case for most hand-written classes — writing __hash__ this way opens the exact bug SQL's primary-key rule warns against: put a mutable object into a set, change the field __hash__ reads, and the object is now sitting in the wrong bucket. x in my_set can come back False for an object that is, by identity, still sitting inside my_set — the lookup structure and reality have split apart, and nothing raises an error to say so.

class Tag:
    def __init__(self, label):
        self.label = label

    def __eq__(self, other):
        if not isinstance(other, Tag):
            return NotImplemented
        return self.label == other.label

    def __hash__(self):
        return hash(self.label)   # dangerous: self.label is reassignable below

t = Tag("draft")
seen = {t}
t.label = "published"       # mutated after being hashed into `seen`
t in seen                  # False — wrong bucket now; `seen` still holds it, just unreachable by lookup

The documentation's own guidance (cited below) is direct about this: "if a class defines mutable objects and implements an __eq__() method, it should not implement __hash__()," precisely because a hashable collection's own correctness requires a key's hash to stay fixed for as long as it's stored. The safe default for a mutable class is exactly what Python already does automatically — leave __hash__ unset (None) once __eq__ is defined, so the class is correctly unhashable, and TypeError catches the mistake at the point of trying to use it as a key, rather than a silent wrong-bucket bug surfacing far away later. Only write __hash__ by hand for a class whose relevant fields are fixed for the object's whole lifetime — the same shape Day 7's @dataclass(frozen=True) takes advantage of, generating both a matching __eq__ and __hash__ together, safely, because frozen=True already guarantees nothing on it can change after construction.

Q: "Why would hash(my_object) suddenly raise TypeError after I added an __eq__ method?" A strong answer, out loud: "Python implicitly sets __hash__ to None the moment a class defines __eq__ without also defining __hash__, because the two have to stay in lockstep — objects that compare equal must hash equal, or dict/set lookup breaks. Rather than leave the old identity-based hash silently wrong, Python disables hashing entirely and makes you opt back in. I'd only write a matching __hash__ if the fields __eq__ compares can never change after construction — otherwise a mutated, already-stored object ends up in the wrong hash bucket and becomes unreachable by lookup, which is worse than a raised error because nothing tells you it happened." The signal: naming the lockstep requirement specifically, and knowing when leaving a class unhashable is the correct choice, not a gap to close.

Where pandas goes from here: a pandas DataFrame itself is unhashable for exactly this reason — its contents are mutable — while an individual cell value or a tuple used as a MultiIndex level follows the same hashable rule taught here. Not demonstrated here; that's data/'s job, and this is the only sentence in this lesson that names it.
