1 · The date on a DAG run isn't "when it ran"

Day 7's DAG has schedule="@daily" and start_date=datetime(2026, 9, 21), and every run so far has happened to execute on roughly the day it represents, so the distinction this lesson is about has been invisible. It stops being invisible the first time a DAG is deployed late, paused, or needs to reprocess a day that already happened — which is exactly backfilling.

Every Airflow DAG run is stamped with a logical_date, and a matching data_interval describing the window of data that run is responsible for. The run that executes at (roughly) 2026-09-29 00:05 UTC carries logical_date=2026-09-28 and data_interval=[2026-09-28, 2026-09-29) — it's named for the day of data it covers, not the moment the scheduler happened to trigger it. This round verified the exact values a real Airflow 3.3.1 task sees for one logical date, via {{ logical_date }}, {{ ds }}, {{ data_interval_start }} and {{ data_interval_end }} templated into a BashOperator:

logical_date=2026-09-28 00:00:00+00:00 ds=2026-09-28 data_interval_start=2026-09-28 00:00:00+00:00 data_interval_end=2026-09-28 00:00:00+00:00

The naming is deliberate, not an Airflow quirk to memorize: a daily batch job's whole point is to summarize a day that has already finished. Day 1's raw.orders load and Day 6's mart_delivery_sla both only make sense once a day's worth of events has fully landed — a run named for "now" would be ambiguous about which day's data it's actually summarizing. logical_date fixes that: it's always the answer to "what day of data is this run about," independent of whatever time the scheduler or a human actually triggered it.

If your own Airflow exposure (per the baseline learning record) was 2.x, the name changed: Airflow 2 called this same value execution_date, which this course deliberately hasn't used anywhere — Airflow 3 renamed it to logical_date specifically because "execution" implied "when it ran," which is exactly the wrong mental model.

2 · catchup, properly: what it actually decides

Day 7 set catchup=False with a one-line reason ("no real history to backfill yet") and moved on. Today names the mechanism underneath that flag: on every DAG parse, the scheduler asks "how many scheduled intervals exist between this DAG's start_date and now that have no DAG run yet?" Catchup controls what happens with the answer — create a run for every one of them (catchup=True, the default), or skip straight to only the most recent interval (catchup=False).

This round re-verified it for real rather than trusting Day 7's prose: a fresh scratch DAG with start_date=2026-09-28, schedule="@daily", catchup=False, reserialized today (2026-10-04), had its next scheduled run computed as exactly 2026-10-04T00:00:00+00:00 — not 2026-09-28, the start_date, which is what catchup=True would have produced instead (one queued run per missed day since 28 Sep). catchup is a one-time decision made the moment a DAG first exists in a scheduler's eyes; it says nothing about what happens afterward, which is where backfill comes in.

3 · Backfill: asking for the missed runs on purpose

Backfill is catchup's on-demand twin: instead of the scheduler deciding automatically at deploy time, a human asks explicitly for a specific date range, any time later. A real, concrete reason this pipeline would need one: suppose raw.orders for 28–30 September was corrupted at the source and re-loaded after a fix — the mart_delivery_sla rows for those three days need recomputing, and nothing about today's schedule will do that on its own.

Airflow 3 moved this to its own top-level command group — airflow dags backfill (the Airflow 2 spelling) no longer exists. This round confirmed the exact replacement and error message directly:

$ airflow dags backfill ...
airflow command error: argument COMMAND: Command `dags backfill` has been removed. Please use `airflow backfill create`, see help above.

A dry run shows exactly which logical dates a backfill would create, with no actual task execution:

AIRFLOW_HOME="$(pwd)/airflow_home" uv run --with "apache-airflow==3.3.1" airflow backfill create \
  --dag-id food_delivery_pipeline --from-date 2026-09-28 --to-date 2026-09-30 --dry-run

Expected, verified against a real Airflow 3.3.1 install this round against a scratch DAG on the same schedule shape:

Runs to be attempted:
+---------------------------+-----------------+------------------+
| logical_date              | partition_key   | partition_date   |
+===========================+=================+==================+
| 2026-09-28 00:00:00+00:00 |                 |                  |
+---------------------------+-----------------+------------------+
| 2026-09-29 00:00:00+00:00 |                 |                  |
+---------------------------+-----------------+------------------+
| 2026-09-30 00:00:00+00:00 |                 |                  |
+---------------------------+-----------------+------------------+

Drop --dry-run to actually create the runs. This round's real (non-dry) run confirmed backfilled DagRuns get their own distinct run_id naming — backfill__2026-09-29T00:00:00+00:00, not manual__<timestamp> (a one-off manual trigger) or scheduled__<timestamp> (the normal nightly run) — so the three kinds of run are always distinguishable later in airflow dags list-runs, exactly the kind of detail worth being able to name when an interviewer asks how you'd know a dashboard anomaly came from a backfill rather than a bad scheduled run.

4 · Why this is only safe because the tasks are idempotent

Here is the part Day 7 built but never said out loud: a backfill is only a good idea if re-running load_raw and dbt_build for an already-processed date produces the same end state as running it once. If either task instead appended on every run — inserting new rows rather than replacing or merging — backfilling three days would silently triple-count them. This is the same idempotent-task property backend/ calls an idempotency key, and the same one Day 6's Kafka consumer and Day 7's own fct_orders merge rely on; today is the third time this course applies it, now specifically to "reprocessing a past logical date," which is the exact scenario backfilling creates on purpose rather than by accident.

TaskWhat a backfilled re-run does for a given logical dateWhy it's still safe
load_rawDROP SCHEMA IF EXISTS raw CASCADE, then reload the same fixed seed (Day 1)Full replace, not append — a backfilled date reruns the identical deterministic load, never duplicates a row
dbt_buildfct_orders merges on unique_key='order_id' (Day 4/13); mart_delivery_sla is keyed by sla_key (Day 11) and rebuilds per-bucket, not append-onlyA reprocessed date's rows replace or merge into their own existing rows by key, instead of adding a second copy next to them
The gap this course's own demo loader still has: Day 7's generation log already found that generate_raw_data.py re-plants the same fixed 500 orders on every run rather than loading genuinely new per-day data — fine for a portfolio demo, but it means this particular DAG's load_raw task doesn't actually vary by logical date at all yet, so a real backfill test against it reprocesses identical data for every date rather than three distinct days' worth. A production loader would read each day's own file or API slice using data_interval_start/data_interval_end to know which rows belong to which run — worth naming as a real difference between this portfolio pipeline and a production one, the same honesty Day 7 flagged for its own loader.

5 · Build: run a real backfill against your own DAG

In your food-delivery-pipeline repo, with Day 7's AIRFLOW_HOME already set up:

AIRFLOW_HOME="$(pwd)/airflow_home" uv run --with "apache-airflow==3.3.1" airflow dags reserialize
AIRFLOW_HOME="$(pwd)/airflow_home" uv run --with "apache-airflow==3.3.1" airflow backfill create \
  --dag-id food_delivery_pipeline --from-date 2026-09-22 --to-date 2026-09-24 --dry-run

dags reserialize first is today's actual TODO to figure out why it's needed: a fresh backfill create looks up the DAG from Airflow's metadata database, not by re-parsing the file on the spot, so a DAG that was never synced there (a file sitting in dags/ that no scheduler or CLI command has touched yet) raises DagNotFound even though the file itself parses perfectly — confirmed directly this round by hitting exactly that error before running reserialize. Pick any 3-day window inside the DAG's own start_date..today range. Drop --dry-run once the dates printed look right, then confirm the three distinct backfill__... run IDs:

AIRFLOW_HOME="$(pwd)/airflow_home" uv run --with "apache-airflow==3.3.1" airflow dags list-runs food_delivery_pipeline

Q: "What's the difference between logical_date and the actual run time of a DAG, and why does Airflow bother with the distinction?" A strong answer, out loud: "logical_date is the start of the data interval a run is responsible for, not when the scheduler actually triggered it — a @daily run that executes just after midnight on the 29th carries logical_date 2026-09-28, because it's summarizing the 28th, a day that's just fully closed. The distinction matters the moment a run isn't exactly on time: if a DAG is paused for two days and then resumed, or a backfill reprocesses last month, every run still needs an unambiguous answer to 'what day of data is this,' completely independent of when it happened to execute. Airflow 2 called this execution_date, which conflated the two ideas; Airflow 3 renamed it to logical_date for exactly that reason." The signal: naming the failure mode the distinction prevents — an ambiguous "which day is this" the moment timing and data don't line up — rather than reciting the rename as trivia.
