np.log() and np.exp(): the skew-fix transform, and its undo button

Lesson 130 closed its own fresh scan with np.log()/np.exp() still open, the one pair left over from Lesson 128's own scan. Today's own fresh scan re-confirmed both are still genuinely untaught — grepped every lesson body and every glossary row case-insensitively for np.log(, np.exp(, np.log1p(, np.expm1(, np.log10(, np.log2(: the only hits were three prior "next lesson" teaser lines naming the pair in passing, never actual coverage. They win on their own merit too: np.log() is the standard fix for a right-skewed numeric column before summary stats or a model, and np.exp() is its undo button — together the most common transform/reverse-transform pair in the wrangling toolkit.

1 · Both keep the Series and its Index — and both always upcast to float64

np.log(x) and np.exp(x) both return a Series with the original Index intact when called directly on one — confirmed directly (numpy 2.5.5, pandas 3.1.1), matching the Lesson 127/129/130 pattern rather than Lesson 128's np.vectorize(). Unlike Lesson 130's np.floor()/np.ceil(), there is no int no-op case here:

import numpy as np
import pandas as pd

s_int = pd.Series([1, 10, 100], index=["a", "b", "c"])
np.log(s_int).dtype   # float64 -- always upcasts, even though every value is a clean integer
np.exp(s_int).dtype   # float64 -- same rule

Confirmed directly: both always return float64 regardless of the input dtype — the same always-upcast rule as Lesson 129's np.sqrt(), not the int-preserving rule of np.abs()/np.floor()/np.ceil(), since a logarithm or an exponential is almost never a whole number. Also confirmed directly, pandas defines neither Series.log() nor Series.exp() at all — both raise AttributeError immediately, continuing the naming-gap lineage Lessons 126-130 established for .roll()/.sign()/.sqrt()/.floor()/.ceil(). The pandas-idiomatic path is calling np.log()/np.exp() directly on the Series, confirmed directly to work identically to the plain-array case.

2 · The trap: log(0) is -inf with a warning, log(negative) is NaN with a different warning

Confirmed directly (numpy 2.5.5): np.log(0) returns -inf and raises RuntimeWarning: divide by zero encountered in log. np.log() on a negative real number returns NaN instead, with a different warning: RuntimeWarning: invalid value encountered in log. Neither crashes, both only warn — a silent -inf/NaN can ride all the way into a mean or a plot before anyone notices.
vals = pd.Series([0.0, -5.0, 10.0])
np.log(vals)
# RuntimeWarning: divide by zero encountered in log
# RuntimeWarning: invalid value encountered in log
# 0    -inf
# 1     NaN
# 2    2.302585
# dtype: float64

Confirmed directly: a plain NaN input (as opposed to a negative or zero one) passes straight through np.log() unchanged, with no warning at all — only an actual zero or negative value triggers the two warnings above. This matters for a real wrangling task: a "take the log of this revenue column" instruction silently breaks on any zero-revenue row (common for a brand-new product or a refunded order), producing -inf rather than an error. The standard fix is np.log1p(x) — confirmed directly identical to np.log(1 + x) for ordinary inputs but numerically more precise for very small x (confirmed directly on x = 1e-15: np.log(1 + x) loses precision to floating-point rounding before the addition even reaches np.log(), while np.log1p(x) computes the correct tiny result directly) — and, more importantly here, np.log1p(0) is a clean 0.0, no -inf, no warning, since it's really computing log(1 + 0) rather than log(0) directly.

3 · exp() can overflow to inf, and exp(log(x)) round-trips with float noise — never compare with ==

Confirmed directly: np.exp() on a large enough input overflows to inf with its own RuntimeWarning: overflow encountered in exp — np.exp(1000) returns inf, since e^1000 is far larger than float64 can represent (roughly 1.8e308 is the ceiling). Its companion np.expm1(x) (confirmed directly equal to np.exp(x) - 1 for ordinary inputs) is the precision-safe partner to np.log1p(), useful when reversing a log1p() transform on small values.

# the classic transform/reverse-transform pair: fix a right-skewed column, then undo it
skewed = pd.Series([10.0, 1000.0, 50000.0])
transformed = np.log(skewed)
back = np.exp(transformed)
back.tolist()
# [10.000000000000002, 999.9999999999998, 50000.00000000001]
# -- NOT exactly [10.0, 1000.0, 50000.0]: float round-trip noise, confirmed directly

Confirmed directly: np.exp(np.log(x)) does not reproduce x bit-for-bit — floating-point rounding during the two passes leaves a tiny residual error, the same "never compare floats with ==" lesson every prior numeric lesson in this course has flagged; use np.isclose() (Lesson 117) to check a round trip instead. The real wrangling use for the pair together: np.log(price / price.shift(1)) computes a log-return series directly — confirmed directly to match the standard financial log-return formula — and np.exp() is what reverses a log-transformed column back to its original scale once a model or aggregation has finished working in log-space.

Q: "Why would you log-transform a column before computing summary stats, and what has to be true of the data first?" A strong answer, out loud: "Log-transforming compresses a long right tail — a column with a few huge outliers and a lot of small values — so the mean and standard deviation aren't dominated by those extreme values, and it turns multiplicative relationships into additive ones, which is why log-returns are standard in finance. The catch is domain: np.log() is only defined for positive numbers. Zero gives negative infinity with a warning, not an error, and a negative value gives NaN with a different warning — both fail silently, so I'd check for non-positive values first, or use np.log1p() if zeros are expected and small. And the round trip back via np.exp() isn't exact — floating-point noise means I'd compare with np.isclose(), never ==." The signal: naming the domain restriction unprompted, not just the formula.
