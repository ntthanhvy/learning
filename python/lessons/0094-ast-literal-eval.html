ast.literal_eval: parsing Python literals safely

Day 76 taught json.loads() for text written in JSON's grammar. Some text isn't JSON at all — it's a string that looks like a Python literal: "[1, 2, 3]", "{'name': 'Ada', 'active': True}", a config value saved as repr() of the original value. eval() would parse that, but it would also run anything written there. ast.literal_eval() is the safe subset of that: it parses literal syntax only, and refuses everything else.

1 · What it parses, and what it flatly refuses

ast.literal_eval(text) accepts exactly the literal forms Python's own grammar defines: numbers, strings, bytes, True/False/None, and lists, tuples, dicts, or sets built only from those — nested as deep as needed. Anything else — a function call, a bare name, even plain arithmetic — is rejected:

import ast

print(ast.literal_eval("[1, 2, 3]"))
# [1, 2, 3] -- confirmed live, a real list
print(ast.literal_eval("{'name': 'Ada', 'active': True}"))
# {'name': 'Ada', 'active': True} -- confirmed live, a real dict
print(ast.literal_eval("(1, 2, 'x')"))
# (1, 2, 'x') -- confirmed live, a real tuple; JSON has no syntax for this at all

ast.literal_eval("1 + 2")
# confirmed live: ValueError: malformed node or string -- arithmetic is NOT a literal,
# even though the result would be harmless; literal_eval parses syntax, not semantics

That last line is the detail easy to assume away: literal_eval does not evaluate expressions at all, not even safe-looking arithmetic. It walks the parsed syntax tree and accepts only literal nodes — anything else is rejected before it would ever run.

2 · Why not just use eval()?

eval() runs arbitrary Python — any expression, including a function call. Given text from outside the program (a config file, a query parameter, a line from a log), that is a direct code-execution risk:

import ast

text = "__import__('os').system('echo pwned')"

try:
    ast.literal_eval(text)
except ValueError as e:
    print("blocked:", e)
# blocked: malformed node or string ... -- confirmed live, the call is rejected outright

# eval(text) would actually run it -- never call eval() on text you did not write yourself

This is the same shape as Day 72's pickle warning against untrusted data, applied to a different format: eval() is powerful exactly because it runs anything, which is precisely why it's the wrong tool for parsing. literal_eval() gives up that power on purpose — it can turn malicious-looking text into a result without ever executing a single function call hidden inside it.

3 · Where it fits next to json

Day 76's json.loads() is still the right choice for data that travels between systems — an HTTP body, a config file meant to be language-agnostic — because JSON's grammar is simple and universal. literal_eval() earns its place on a narrower job: text that is already Python-shaped, most often the output of repr() on a value, or a literal a person typed by hand expecting Python syntax:

import ast, json

try:
    json.loads("{'a': 1}")
except json.JSONDecodeError as e:
    print("json rejects single quotes:", e)
# confirmed live -- JSON's grammar requires double quotes; this text is not valid JSON

print(ast.literal_eval("{'a': 1}"))   # {'a': 1} -- fine, this is Python literal syntax

Neither module is a drop-in replacement for the other — they parse two different grammars that happen to overlap on simple cases.

4 · Malformed text: a different exception than "rejected on purpose"

A string that isn't valid Python syntax at all — not just disallowed, but actually broken — raises SyntaxError instead of the ValueError a disallowed-but-parseable expression raises:

ast.literal_eval("[1, 2,")
# confirmed live: SyntaxError: '[' was never closed -- broken syntax, not a disallowed literal

ast.literal_eval("some_name")
# confirmed live: ValueError: malformed node or string -- valid syntax (a name), but not a literal

Code calling literal_eval() on text it doesn't fully control should catch both: except (ValueError, SyntaxError): — catching only one leaves the other free to crash the program on ordinary bad input.

Where pandas/NumPy go from here: nothing pandas-specific today — literal_eval() is a plain-text parsing tool with no DataFrame or array counterpart; the closest pandas gets is reading a CSV cell that happens to contain a stringified list, which still needs a plain Python parsing step like this one before it becomes a real list.
