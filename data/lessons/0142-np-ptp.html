np.ptp(): max minus min in one call, and the narrow-dtype overflow trap

Lesson 141's own closing note named .mad() as the nearest surfaced-but-not-built candidate — checked directly in a scratch sandbox first: Series.mad() raises AttributeError on pandas 3.1.1, removed from the library entirely back in pandas 2.0, so it is dead API and a poor pick for an interview-prep lesson. Ran this round's own fresh scan instead: grepped every lesson body and the glossary case-insensitively for ptp( and found zero hits anywhere across Lessons 1-141. np.ptp() is still a live, documented NumPy function, closely related to this course's own .max()/.min() and np.percentile() (Lesson 111) lessons, and it hides a genuinely sharp dtype trap worth a full lesson.

1 · ptp() is "peak to peak" — max minus min, confirmed directly

Confirmed directly (pandas 3.1.1, numpy 2.5.5):

import numpy as np
import pandas as pd

arr = np.array([3, 7, 1, 9, 4])

np.ptp(arr)              # 8  -- same as arr.max() - arr.min()
arr.max() - arr.min()    # 8  -- confirmed identical

np.ptp() is short for "peak to peak" — the full range a column spans, from its lowest value to its highest. It is a convenience function only: nothing it computes is new, it just saves writing .max() - .min() as two separate calls. Confirmed directly, np.ptp() also runs directly on a pandas Series or DataFrame with no .to_numpy() conversion needed first, the same NumPy-function-on-pandas-data pattern Lesson 93's own np.argmax()/np.argmin() already confirmed:

s = pd.Series([3, 7, 1, 9, 4])
np.ptp(s)   # 8  -- works directly on a Series, no .to_numpy() needed

hasattr(s, "ptp")   # False -- confirmed: no Series.ptp() method exists

Confirmed directly: unlike .max() and .min() themselves, which exist as both a pandas method and a NumPy function, ptp only exists as the top-level np.ptp() function — calling .ptp() as a Series or DataFrame method raises AttributeError, removed from pandas in the same 2.0 cleanup that dropped .mad().

2 · axis= reduces one axis of a 2-D array or whole DataFrame, same pattern as np.median()

Confirmed directly, np.ptp() takes the same axis= parameter this course has used since np.percentile() (Lesson 111) and np.median() (Lesson 140):

df = pd.DataFrame({"a": [1, 2, 3], "b": [10, 20, 5]})

np.ptp(df, axis=0)   # a 2, b 15  -- range DOWN each column
np.ptp(df)           # 19         -- no axis: flattens first, one single number across the whole table

Confirmed directly, np.ptp(df, axis=0) matches column-by-column .max() - .min() exactly (df["a"].max() - df["a"].min() is 2, df["b"].max() - df["b"].min() is 15) — the same per-column reduction shape as np.median(arr, axis=0), just with a different formula underneath.

3 · The real trap: narrow integer dtypes can silently overflow

Unlike Lesson 140's np.median() trap (a cross-library NaN mismatch), np.ptp()'s sharpest trap is dtype-driven and happens inside a single call, with no second library involved. Confirmed directly:

arr_i8 = np.array([-128, 127], dtype=np.int8)

arr_i8.max(), arr_i8.min()   # (127, -128)  -- both look completely correct
np.ptp(arr_i8)                # -1  -- WRONG; the true range is 255
Confirmed directly, why this happens: np.ptp() computes max() - min() in the array's own dtype, not in a safely wide one. int8 can only hold -128 to 127 — the true range, 255, cannot fit in that dtype at all. The subtraction silently wraps around to -1 instead of raising an error, confirmed directly to reproduce a NumPy RuntimeWarning: overflow encountered in scalar subtract rather than an exception, easy to miss in a busy script. Confirmed directly, this trap survives even when the narrow-dtype array sits inside a pandas Series — np.ptp(pd.Series([-128, 127], dtype="int8")) returns the identical wrong -1. The fix is widening the dtype first: np.ptp(arr_i8.astype(np.int64)) confirmed directly returns the correct 255. This is exactly the kind of trap Lesson 62's own memory-optimization .astype() downcasting can set up unintentionally — shrinking a column to int8 to save memory, then calling np.ptp() on it later and getting a confidently wrong negative number back, no warning surfaced in most environments by default.

Confirmed directly, uint8 is not immune either, just differently bounded — a range that fits within 0..255 computes correctly (np.ptp(np.array([10, 250], dtype=np.uint8)) is 240, fits fine), but a float array never hits this trap at all, since floats do not wrap on overflow the way fixed-width integers do.

4 · NaN propagates, and an empty array raises instead of returning NaN

Confirmed directly, a NaN anywhere in the array poisons the whole result — the same propagation rule Lesson 140 confirmed for plain np.median(), not the pandas-side auto-skip behavior:

arr_nan = np.array([3.0, 7.0, np.nan, 9.0])
np.ptp(arr_nan)   # nan  -- one NaN poisons the whole range, no error

Confirmed directly, an empty array is where np.ptp() actually diverges from np.median()'s own quiet-NaN pattern: np.ptp(np.array([])) raises ValueError: zero-size array to reduction operation maximum which has no identity instead of returning NaN — because ptp is built directly from .max()/.min(), and neither has a sensible answer on zero elements, so it raises loudly rather than failing quietly this one time.

Q: "What's np.ptp(), and is there anything to watch out for when using it?" A strong answer, out loud: "ptp stands for peak-to-peak — it's just max() minus min() in one call, the full range a column spans. The one real trap is dtype: it computes the subtraction in the array's own dtype, so on a narrow type like int8, a genuinely wide range like -128 to 127 can silently overflow and come back as a small negative number instead of the correct 255 -- no error, just a wrong answer. That's exactly the kind of thing a prior memory-optimization pass that downcasts columns to save space can set up by accident. I'd widen the dtype with astype() before calling ptp() on anything that's been through aggressive downcasting, or just stick to max() - min() computed in a wider dtype if I'm not sure." The signal: naming the exact failure (silent overflow, not a crash) and connecting it to dtype-optimization work rather than treating ptp() as a trivial, risk-free convenience function.
