Names, objects & mutability: what = actually does

Day 1 of the intensive week. Before comprehensions, before generators, before any of it: what happens when you write x = something. Get this wrong and Python behaves like it has a poltergeist — a list changes when you never touched it, a function remembers data from a call an hour ago. Get it right and every one of those mysteries collapses into one rule.

Why this is Day 1: nearly every "Python is weird" bug traces back to this single idea. It is also the thing that makes the rest of the week make sense — why a comprehension builds a new list (Day 2), why dict keys must be immutable (Day 3), why a generator can't be replayed (Day 5). One rule, spent seven times.

1 · A name is a label, not a box

Most languages teach you to picture a variable as a box with a value inside. Python does not work that way, and carrying the box picture is the root of nearly every surprise ahead.

In Python, the data lives in an object. A name is just a label stuck onto that object. So = does not "put a value into a variable" — it attaches a label to an object that already exists. That attachment is called binding.

x = 5
y = x        # y now labels the SAME object as x
x = 6        # the label x is MOVED to a different object
print(y)     # 5 — y never moved, and the object 5 never changed

Read line 3 carefully. It did not "change x from 5 to 6." The object 5 is still there, unchanged, still labelled by y. All that happened is the label x was peeled off 5 and stuck onto 6. That is rebinding, and it is all that plain assignment ever does.

2 · Two labels, one object

So far so harmless — because integers can't be changed anyway. The picture starts to matter the moment two names label the same changeable object. That's called an alias:

a = [1, 2, 3]
b = a            # NOT a copy — b is a second label on the same list
b.append(4)

print(a)         # [1, 2, 3, 4]  <- a changed, and you never mentioned a
print(b)         # [1, 2, 3, 4]

There is only ever one list here. b = a copied nothing — it added a second label. append then changed the single shared object, and both labels see it because both point at the same thing.

You can prove there is only one object with is, which tests identity:

a = [1, 2]
b = a
c = [1, 2]      # a separate list that happens to look the same

print(a is b)   # True  — one object, two labels
print(a is c)   # False — two different objects
print(a == c)   # True  — different objects, equal contents
is vs ==: is asks "same object?", == asks "same value?". You almost always want ==. The one everyday use of is is comparing against None — write if x is None:, never if x == None:.

3 · The dividing line: mutable vs immutable

Whether aliasing can bite you depends entirely on one property of the object.

KindTypesCan it be changed in place?
mutablelist, dict, setYes — .append(), d[k] = v, .add()
immutableint, float, str, bool, tupleNo — every "change" builds a new object

This is why strings feel different from lists:

s = "hello"
t = s
s = s.upper()      # builds a NEW string, rebinds s to it
print(t)           # "hello" — untouched, because strings can't be mutated

nums = [1, 2]
other = nums
nums.append(3)   # MUTATES the one shared list
print(other)       # [1, 2, 3] — it changed underneath you

Same aliasing in both cases. Different outcome, and the only difference is whether the object could be mutated. Notice the tell: s.upper() returns a new string and you must assign it, while nums.append(3) returns None and changes the object. In Python, a method that returns None has almost always just mutated something.

4 · When you actually want a copy

If aliasing isn't what you want, ask for a copy explicitly:

original = [1, 2, 3]
copy1 = list(original)   # a new list
copy2 = original[:]      # same thing, older spelling

copy1.append(99)
print(original)         # [1, 2, 3] — safe

That is a shallow copy: the outer list is new, but the items inside are still the same objects. With flat data that is all you need. With nesting, the sharing is still there one level down:

rows = [["An", 120], ["Binh", 35]]
shallow = list(rows)
shallow[0].append("VN")     # mutating an INNER list
print(rows[0])              # ['An', 120, 'VN'] — still shared

import copy
deep = copy.deepcopy(rows)   # nothing shared at any depth

A deep copy is the sledgehammer: correct, slower, and usually a sign the data should have been rebuilt rather than copied. Reach for it only when you genuinely need an independent nested structure.

5 · The trap this all exists to explain

Here is the bug this lesson buys you immunity from. It catches every Python programmer exactly once:

# BROKEN — do not write this
def add_item(item, basket=[]):
    basket.append(item)
    return basket

print(add_item("apple"))    # ['apple']
print(add_item("banana"))   # ['apple', 'banana']  <- ???

The second call was supposed to start from an empty basket. It didn't, and now you know exactly why: Python evaluates default values once, when the def line runs — not on every call. That single list object is created at definition time and reused by every call forever, accumulating. This is the mutable default argument trap.

The fix is always the same shape:

# CORRECT
def add_item(item, basket=None):
    if basket is None:
        basket = []          # a fresh list per call
    basket.append(item)
    return basket

None is immutable, so sharing it is harmless, and the real list is built inside the body — once per call. Note the is None from section 2 doing real work here.

Rule of thumb: never put [], {}, or set() in a function's default arguments. Default to None and build the real thing in the body. Numbers, strings, and None as defaults are always safe, because they can't be mutated.

6 · Why the data track cares

This isn't trivia — it is the difference between a pipeline that's correct and one that's quietly wrong. A cleaning function that takes a list of records and mutates it has changed the caller's data too, so the "raw" records are no longer raw and the step can't be re-run or debugged. The safe habit, which the whole rest of this course builds on:

# mutates the caller's data — the original is now gone
def clean(records):
    for r in records:
        r["name"] = r["name"].strip()
    return records

# builds and returns something new — the original survives
def clean(records):
    out = []
    for r in records:
        out.append({**r, "name": r["name"].strip()})
    return out

The second shape — take input, return new output, never mutate — is what makes pipeline steps composable and testable. Day 2 rewrites that second version as a single readable line, and it will be obvious then why it produces a new list rather than editing the old one.

Q: "What does b = a do in Python?" A strong answer, out loud: "It binds a second name to the same object — it doesn't copy anything. If that object is mutable, like a list or dict, mutating it through either name is visible through both, because there's only one object. If it's immutable, like an int or a string, the question never comes up, since any 'change' rebinds the name to a new object and leaves the original alone. When I actually need independence I copy explicitly — list(a) for flat data, copy.deepcopy for nested." The signal: separating rebinding a name from mutating an object. That distinction is the whole answer, and it's what the mutable-default-argument question is really testing too.
