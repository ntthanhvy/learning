1 · Why this question, and why now

MISSION.md asks for a 10-minute walkthrough that includes "what would change at 100× volume" — a question every one of this repo's 27 prior lessons has been quietly setting up evidence for, without ever naming the number explicitly. "It would need more servers" is not an answer an interviewer accepts; naming which specific thing stops working first, at roughly what volume, and what the smallest real fix is, is. Today picks three concrete bottlenecks this pipeline actually has — not generic distributed-systems trivia — and does the arithmetic once, in writing, so it's ready before anyone asks.

"100×" here means roughly 50,000 orders/day instead of today's 500-order one-off seed (Day 1), and a proportional jump in order_events (12 events landed per Day 6's own test batch, so roughly 1.2M events/day at the same ratio) — round numbers for orientation, not a forecast to defend to the decimal place.

2 · Bottleneck 1 — Kafka: partition count as a parallelism ceiling

Day 5 fixed order_events at 3 partitions, keyed by order_id so one order's own status events stay in order. That key choice still holds at 100× — ordering per order never needed to change — but the partition count is the part that stops scaling: Kafka guarantees at most one consumer, per consumer group, can read a given partition at a time. Three partitions means at most three consumer processes in inspect-group (or any single group) can ever work in parallel, no matter how many you start — a fourth sits idle, assigned nothing, confirmed behavior straight from Day 5's own partition-assignment claim.

At 500 orders/day with ~12 events each, Day 6's single consumer drained a batch with room to spare. At 1.2M events/day, three partitions cap this topic's own total consumer throughput at whatever three single-threaded consumers can do — and the fix is not "add a fourth consumer," it's kafka-topics.sh --alter --partitions N to raise the ceiling itself, done before the volume arrives, because partition count can only go up, never down, on a live topic, and existing keys don't automatically remap to new partitions, only new messages do.

3 · Bottleneck 2 — dbt: an incremental filter that still re-scans everything

Day 13 gave fct_orders a real is_incremental() filter on placed_at, and that's the part of "incremental" that actually saves work: each run only reads rows newer than what's already landed, not all 500 (or 50,000,000) historical orders. The part that does not scale automatically is mart_delivery_sla's delete+insert lookback from the same lesson — its HAVING filter recomputes "the last couple of days' buckets" on every single run, which is a fixed, small cost at 500 orders/day and stays a fixed, small cost at 50,000 orders/day too, as long as the lookback window itself doesn't have to widen. The real 100× risk here isn't the row count, it's whether whatever is producing delivered events starts arriving later under load — a lookback sized for "usually within a day" silently stops being enough if load pushes typical delivery-event lag past it, and the fix is the same diagnostic Day 13 already taught (widen the filter, or --full-refresh once to catch up), not a different incremental strategy.

The other real 100× question for dbt specifically is materialization choice, not incremental logic: dim_restaurants (Day 4) is a full table rebuild every run, fine at 40 restaurants, still fine at 4,000 — restaurant counts don't scale with order volume the way orders do, so this one deliberately stays a plain table rather than being converted to incremental for no reason, a direct answer to Day 10's own "does this earn its complexity" bar applied to materialization instead of macros.

4 · Bottleneck 3 — the warehouse: one Postgres node, not a cluster

Every dbt model and every landed event in this project writes to one postgres:17 container (Day 1), with no read replica and no partitioning on any table. At 500 orders/day this is irrelevant; at 50,000 orders/day, raw.order_events alone is roughly 600,000 new rows/day, and the two places that feel it first are concrete, not abstract: Day 6's consumer does one INSERT ... ON CONFLICT per event, so insert throughput on that one table becomes the hot path's own ceiling long before query performance does; and mart_delivery_sla's delete+insert rewrites whole day-buckets on every run, which is cheap against a day's worth of orders today and still cheap against a day's worth of orders at 100×, since the lookback window's row count doesn't grow with total history — the actual warehouse risk at scale is unindexed growth on raw.order_events itself making every downstream staging/mart select slower over time, not any one run's incremental cost. The single-node answer this course's own constraints (MISSION.md: Postgres only, no cloud account) actually supports first is table partitioning raw.order_events by date and adding the index Day 1 never needed at 500 rows — before reaching for a managed warehouse at all, since MISSION.md rules those out by name and the real first bottleneck is indexing, not engine choice.

6 · What's deliberately not here

Three real scaling levers are named and set aside on purpose, not forgotten: Kafka Streams/Flink-style stream processing (MISSION.md's own out-of-scope list — "land it and let dbt do it" stays the right call at this project's scale), a managed cloud warehouse (also explicitly out of scope — Postgres is the warehouse here by design), and multi-broker Kafka tuning (out of scope per MISSION.md's constraints list). Naming a lever and correctly setting it aside is itself part of a strong "what breaks at 100×" answer — an interviewer is listening for judgment about what's actually needed at this scale, not a list of every tool that exists.

Q: "What would break first if this pipeline ran at 100× its current volume?" A strong answer, out loud: "Three things, in the order I'd expect to hit them. First, Kafka's partition count — order_events has 3 partitions today, which caps how many consumers in one group can ever run in parallel at exactly 3, no matter how many I start; the fix is raising the partition count ahead of the volume, not adding more consumer processes past that ceiling. Second, dbt's incremental models themselves mostly scale fine — fct_orders only reads new rows, and mart_delivery_sla's delete+insert lookback stays a small, fixed-size rewrite regardless of total history — but the lookback window's size assumption could break if delivery events start arriving later under load than my current window accounts for. Third, the warehouse: one Postgres node with no partitioning on raw.order_events means insert throughput on that one table becomes the real hot-path ceiling, and the first fix is table partitioning by date plus proper indexing, not switching engines — this project is intentionally Postgres-only. What I'd explicitly not reach for yet: Kafka Streams, a managed warehouse, or multi-broker tuning — none of those are needed at this scale, and reaching for them early is its own kind of mistake." The signal: naming which bottleneck hits first, the actual mechanism (not just "it would be slow"), and which heavier tools are deliberately not needed yet.
