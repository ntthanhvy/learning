1 · Three questions, in the original teaching order

Answer each out loud or on paper before reading the fold-out answer. If one is shaky, note it and go fix it in the practice file below rather than only rereading the old lesson.

Day 72 — pickle. Why can pickle serialize a dataclass instance that makes json.dumps() raise TypeError, and what is the one rule about calling pickle.load() that has nothing to do with syntax at all?

Fold-out answer: json only knows how to write the fixed set of types its text format defines — strings, numbers, booleans, None, lists, and dicts of those — so a custom type like a dataclass instance is invisible to it. pickle writes Python's own internal binary representation of an object instead of a fixed text grammar, so it can round-trip almost any Python object with no hand-conversion step. The non-syntax rule: never call pickle.load()/loads() on data from an untrusted or unauthenticated source — reconstructing an object during unpickling can invoke that object's own code, so a maliciously crafted pickle byte string can run arbitrary code the instant it's loaded, a risk json parsing simply has no path to.

Day 73 — concurrent.futures. Why does ThreadPoolExecutor.map() finish five one-second simulated calls in about one second instead of five, and why does that same trick do nothing for a pure CPU-bound computation?

Fold-out answer: each simulated call is I/O-bound — nearly all of its time is spent waiting, not computing — so running the five waits concurrently overlaps the idle time instead of stacking it, and total time tracks the slowest single call rather than the sum of all five. CPython's GIL only releases automatically during a blocking I/O wait; a thread doing pure arithmetic never blocks on I/O, so it never releases the GIL, and running the same computation across several threads provides no speedup (ProcessPoolExecutor, using separate processes instead of threads, is the tool for that case instead).

Day 74 — uuid & configparser. Why can two independent processes both call uuid.uuid4() with zero risk of colliding, and why does plain config["database"]["port"] hand back the string "5432" rather than the integer 5432 even though the file reads port = 5432?

Fold-out answer: uuid4() generates a 128-bit random value, not a number handed out by any central counter — the randomness is large enough that two independent calls colliding is not a practical concern, which is exactly why no coordination between callers is ever needed (unlike an auto-increment integer primary key, which needs the database itself to hand out the next number). configparser reads every raw value out of an INI file as a plain string, with no concept of int or bool built in anywhere — getint(), getfloat(), and getboolean() are the separate typed readers that convert that string on the way out, not on the way in.

2 · Why these three, and why no new terms today

Same interleaving logic as every prior review day: a serialization-format tradeoff, then a concurrency model, then two small but genuinely different "know it exists, reach for it correctly" tools — four different mental models pulled from three lessons, not one idea restated four ways. They also share a quieter throughline worth naming: all three are about a tool drawing a hard line around what it will and won't do automatically — pickle will serialize almost anything but trusts the caller completely on safety, ThreadPoolExecutor will overlap waits but can't speed up computation the GIL still serializes, and configparser will move values between a file and a dict but never silently guesses their type. Recognizing which guarantees a tool is actually making, versus which it explicitly leaves to the caller, is the retrieval goal today more than recalling exact method names alone.
