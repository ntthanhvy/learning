Optimistic locking, now in C# too

Lesson 33 covered optimistic locking in Postgres: a hand-added version column, an UPDATE whose WHERE clause demands the version the caller last read, and a zero-rows-affected result that means someone else wrote first. That lesson never got a C# mirror, even though every other Go-only mechanism from the Lesson 11–50 stretch — rate limiting, retry, circuit breaker, bulkhead, worker pools, graceful shutdown, health checks — has been ported since Lesson 112. Today closes that gap: the same version-check-on-write idea, built from EF Core's own concurrency-token feature instead of a hand-written WHERE version = $3.

1 · Same idea, a column attribute instead of a WHERE clause

Lesson 33's rule still holds exactly: no lock on read, and the write only succeeds if the row hasn't changed since it was read. What changes in EF Core is that nobody writes the WHERE version = $3 clause by hand. The building block is a concurrency token: a property EF Core loads and tracks like any other, but checks against the database's current value on every SaveChanges().

public class Profile
{
    public int Id { get; set; }
    public string Bio { get; set; }

    [ConcurrencyCheck]
    public int Version { get; set; }  // -- same role as Lesson 33's "version integer" column
}

Per Microsoft's own docs: "the concurrency token is loaded and tracked when an entity is queried — just like any other property. Then, when an update or delete operation is performed during SaveChanges(), the value of the concurrency token on the database is compared against the original value read by EF Core." That's Lesson 33's WHERE id = $2 AND version = $3 — EF Core just generates it from the attribute instead of a hand-written query:

var profile = await db.Profiles.SingleAsync(p => p.Id == 1);
profile.Bio = "new bio";
profile.Version++;                 // app-managed token: caller bumps it, same as Lesson 33's "+ 1"
await db.SaveChangesAsync();  // EF emits: UPDATE ... WHERE Id = @p AND Version = @originalVersion

2 · A second flavor: let the database generate the token

Lesson 33's version column only moves because the app's SET version = version + 1 says so. EF Core also supports the database doing that work on its own, via [Timestamp]:

public class Profile
{
    public int Id { get; set; }
    public string Bio { get; set; }

    [Timestamp]
    public byte[] Version { get; set; }  // DB bumps this itself -- app never assigns it
}

This is the one piece with no Postgres equivalent named in Lesson 33: SQL Server's rowversion column type changes itself on every write, so there's nothing to increment by hand and nothing to forget to increment. Postgres has no built-in auto-incrementing row-version type — Lesson 33's app-managed integer column (or EF Core's [ConcurrencyCheck] flavor above) is the equivalent there, per the docs' own note that "the details... differ across databases, and some databases don't support these at all."

The frontend equivalent you already own. Lesson 33 already named this: a version check on write is the server-side version of a form warning "this record changed since you opened it, reload?" instead of silently letting the second Save overwrite the first. Nothing about that mental model changes here; only who writes the version-matching WHERE clause does.

3 · The conflict: an exception instead of a row count

Lesson 33's Go code checked for zero rows affected (sql.ErrNoRows on the RETURNING clause) and returned a sentinel ErrStaleUpdate. EF Core surfaces the identical zero-rows-matched fact as a thrown exception instead:

try
{
    await db.SaveChangesAsync();
}
catch (DbUpdateConcurrencyException ex)
{
    // Same meaning as Lesson 33's zero-rows-affected: the UPDATE's own
    // WHERE ... AND Version = @original matched no rows -- someone else
    // already wrote and changed the token since this caller read the row.
    foreach (var entry in ex.Entries)
    {
        var databaseValues = await entry.GetDatabaseValuesAsync();
        if (databaseValues == null)
            throw; // row was deleted, not just updated -- a different decision

        // Lesson 33's three honest options apply unchanged here: tell the
        // user (409 Conflict), retry if commutative, or merge. Whichever
        // is chosen, re-arming the original values is what lets a retry
        // pass the next concurrency check instead of failing again.
        entry.OriginalValues.SetValues(databaseValues);
    }
}

DbUpdateConcurrencyException.Entries gives one entry per conflicting row; entry.GetDatabaseValuesAsync() fetches what's actually in the database right now — Lesson 33's "someone else already wrote and bumped the version" fact, available here as data instead of just a boolean. entry.OriginalValues.SetValues(databaseValues) is the retry-enabling step: without it, a second SaveChangesAsync() would compare against the same stale original value and fail again.

Scope line

This lesson covers EF Core's optimistic-concurrency feature — [ConcurrencyCheck]/IsConcurrencyToken(), [Timestamp]/IsRowVersion(), DbUpdateConcurrencyException, and the Entries/GetDatabaseValuesAsync()/OriginalValues.SetValues() resolution pattern — as the C# mirror of Lesson 33's Postgres version column. It does not cover using transaction isolation levels (repeatable read / snapshot) as an alternative concurrency-control mechanism, which the same docs page discusses as a separate approach with its own trade-offs; multi-property concurrency tokens (checking several columns at once, briefly shown in the docs' merge example); or SQL Server's exact rowversion byte layout. It does not cover Go's select-statement arbitration rules — still deferred; see this round's NOTES.md entry for why.
