1 · What Airflow actually adds here

Every build step this week, you've been the orchestrator: you typed the seed command, waited, then typed dbt build. That's fine for building a pipeline, but it's not what runs a pipeline in production — nobody wants to SSH in every morning and type two commands by hand. Airflow's whole job, as Day 1 named it, is to be that hand: it runs a fixed sequence of steps on a schedule, retries the ones that fail, and keeps a record of whether each run succeeded — without doing any of the actual data work itself.

An Airflow DAG is the same idea as dbt's DAG from Day 2 — a directed graph of things and their dependencies — just one level up: instead of models depending on other models via ref(), Airflow tasks depend on other tasks via >>. Today's DAG has exactly two tasks and one dependency: load_raw >> dbt_build. dbt build's own internal DAG (Day 2's model graph) still runs entirely inside that second task — Airflow doesn't know or care that dbt has its own dependency graph, it only sees "run this one command, then that one."

2 · Choosing the lightest setup, on purpose

Airflow's own "Running Airflow in Docker" page ships a reference docker-compose.yaml with a webserver, scheduler, triggerer, dag-processor, a dedicated Postgres for Airflow's own metadata, Redis and multiple workers — a real multi-service stack sized for demoing CeleryExecutor, not for adding a scheduler next to one existing Postgres. That page says so itself: it's a reference for exploring Airflow's moving parts, "not applicable for a production setup" and heavier than a laptop pipeline needs.

The Quick Start is the one this course actually follows: airflow standalone. It runs the webserver, scheduler and a database migration in a single command, defaulting to SQLite for Airflow's own metadata (a completely separate database from your fdp Postgres — Airflow's metadata is bookkeeping about runs and tasks, never your actual data) and LocalExecutor for running tasks as local subprocesses. No Redis, no Celery, no second container. This round's verification confirmed the default executor a fresh AIRFLOW_HOME resolves to is exactly LocalExecutor, and airflow db migrate against that fresh home created a working SQLite-backed metadata store in under a second — the "lightest setup that runs Airflow 3.3.1 next to the existing compose stack" PLAN.md asks for. Your two containers (postgres, kafka) keep running exactly as they are; Airflow runs as a plain process alongside them, talking to fdp Postgres over localhost:5432 the same way your terminal has been doing all week.

If your Airflow exposure was 2.x: the biggest visible change here is the import path. Airflow 3 moved the DAG-authoring surface into airflow.sdk (from airflow.sdk import DAG, not from airflow import DAG), and standard operators like BashOperator now live in a separate provider package, airflow.providers.standard.operators.bash, not in Airflow core. Both are confirmed-working imports against this course's pinned 3.3.1 below — an older tutorial's from airflow.operators.bash import BashOperator will not resolve on Airflow 3.

4 · Build: dags/food_delivery_pipeline.py

Create dags/ inside airflow_home/ (Airflow's default dags_folder, confirmed by this round's airflow config get-value core dags_folder) and add this DAG in full — it's scaffolding, in the same sense Day 5's producer was: the Python syntax is nothing new from python/, so today's actual skill is the three Airflow-specific choices named below, not the code itself:

"""Daily batch DAG: load raw.* data, then run dbt build on top of it.

Both tasks are safe to re-run: generate_raw_data.py drops and recreates the
raw schema deterministically (Day 1), and dbt build's models/tests are pure
SELECTs plus idempotent incremental logic (Day 4/6) -- so a manual re-run,
or Airflow retrying a failed task, produces the same end state as a single
successful run.
"""
from datetime import datetime, timedelta

from airflow.sdk import DAG
from airflow.providers.standard.operators.bash import BashOperator

REPO_DIR = "/opt/airflow/food-delivery-pipeline"  # mount your repo checkout here, or edit to an absolute local path

default_args = {
    "retries": 2,
    "retry_delay": timedelta(minutes=5),
}

with DAG(
    dag_id="food_delivery_pipeline",
    description="Load raw.* tables, then dbt build the staging/marts layers",
    schedule="@daily",
    start_date=datetime(2026, 9, 21),
    catchup=False,
    default_args=default_args,
    tags=["food-delivery-pipeline"],
) as dag:

    load_raw = BashOperator(
        task_id="load_raw",
        bash_command=(
            f"cd {REPO_DIR} && "
            "uv run --with 'psycopg[binary]' python3 scripts/generate_raw_data.py"
        ),
    )

    dbt_build = BashOperator(
        task_id="dbt_build",
        bash_command=(
            f"cd {REPO_DIR}/warehouse && "
            "uv run --with 'dbt-postgres==1.11.0' dbt build --profiles-dir ."
        ),
    )

    load_raw >> dbt_build

Three choices worth naming out loud, because an interviewer will ask "why does this DAG look the way it does," not just "does it work":

  • retries=2, retry_delay=timedelta(minutes=5): a retries transient failure — Postgres not accepting connections yet, a momentary network blip — shouldn't need a human to notice and re-trigger. Two retries, five minutes apart, absorbs exactly that class of failure without masking a real one (a genuinely broken model still fails all three attempts and alerts).
  • catchup=False: per the Airflow Best Practices doc, a DAG with catchup left on (the default) will, on first deploy, try to run once for every day between start_date and now. This pipeline has no history to backfill — Day 1's data didn't exist before today's week — so backfilling would just re-run today's logic against today's data, repeatedly, for no reason. Phase 2c covers when catchup is exactly what you want.
  • BashOperator, not a Python function calling dbt's Python API: per PLAN.md, this is deliberately the simplest thing that works. BashOperator runs each step as its own subprocess, in its own shell, exactly like typing the command yourself — nothing dbt-specific in Airflow's own code. Astronomer Cosmos (Phase 2c) turns every individual dbt model into its own Airflow task instead of one opaque dbt build block, trading simplicity for per-model visibility and retry granularity — a real upgrade, but not a Day 7 prerequisite.

5 · Why a manual re-run is safe — traced through both tasks

"Retries are safe" isn't a property Airflow adds — it's a property each task underneath either has or doesn't, and Airflow just calls the same idempotent thing again. Trace it through both of today's tasks:

TaskWhat a re-run actually doesWhy that's safe
load_rawDROP SCHEMA IF EXISTS raw CASCADE, then rebuild from the same fixed seed (Day 1)Deterministic seed, same rows every time — a second run overwrites, never duplicates
dbt_buildviews recreate fully; dim_restaurants (table) rebuilds fully; fct_orders (incremental) merges on unique_key='order_id'; data tests re-run against whatever's in raw.* right nowNo step here appends blindly — a view/table rebuild replaces its own output, and Day 4's unique_key is exactly what stops an incremental merge from duplicating a row on a repeated run
This is the same idempotent-write idea Day 6's Kafka consumer used, and the same idempotency-key concept from backend/ before that — applied a third time, now to a scheduled batch task instead of a message or an API request. Same principle, three different layers of this stack.

This round's verification traced this for real rather than asserting it — and surfaced something worth knowing about your own repo, not a flaw in the argument above. Running load_raw's exact command against a live scratch Postgres gave Day 1's exact output:

raw.restaurants: 40
raw.couriers:    15
raw.orders:      500  (2 bad rows planted: order 13 orphan restaurant_id, order 27 negative subtotal)

Running dbt_build's exact command straight afterward reproduced Day 3's two named test failures — because Day 1's seed script re-plants those two demo rows every single time it runs, on purpose, so this course always has something for Day 3's tests to catch:

Done. PASS=9 WARN=0 ERROR=2 SKIP=8 NO-OP=0 REUSED=0 TOTAL=19

Fixing those two rows by hand (Day 3's one-time UPDATE) and re-running dbt_build gave a clean build:

13 of 19 OK created sql incremental model dbt_dev.fct_orders .................. [SELECT 500 in 0.11s]
12 of 19 OK created sql table model dbt_dev.dim_restaurants ................... [SELECT 40 in 0.13s]
...
Done. PASS=19 WARN=0 ERROR=0 SKIP=0 NO-OP=0 REUSED=0 TOTAL=19

Re-running both tasks again from there — a second full load_raw >> dbt_build pass, simulating what Airflow does on every scheduled run — confirmed the actual safety claim: fct_orders held exactly 500 total rows, 500 distinct order_id afterward, no duplicates, even though load_raw had just reset and reloaded every raw row underneath it.

The honest gap this exposes: generate_raw_data.py is a portfolio demo generator, not a production loader — it exists to give this course deterministic, replayable data, and replanting Day 3's two bad rows every run is a deliberate feature of that demo, not of a real pipeline. A real daily loader would append genuinely new rows and never reintroduce fixed old ones, so this specific test failure would not recur once fixed. Today's DAG orchestrates exactly the two commands this course has taught; swapping the demo loader for a real incremental one is real-world follow-up work outside Phase 1's scope, and is worth being able to say out loud in an interview as the difference between a portfolio pipeline and a production one.

7 · Ship it: README, architecture diagram, decisions

Day 1 asked for two or three sentences in README.md. Today it becomes the write-up an interviewer actually reads before talking to you. Replace it with, at minimum, these two sections:

Architecture diagram — Day 1's pipeline map, now describing what's actually built and running, not what's planned:

generate_raw_data.py ──▶ raw.restaurants / raw.couriers / raw.orders
      (batch, Airflow load_raw task)

Kafka producer ──▶ topic:order_events (3 partitions, keyed by order_id)
      (stream)          │
                         ▼
          Kafka consumer ──────────▶ raw.order_events
   (at-least-once, ON CONFLICT DO NOTHING,      │
    manual offset commit after write)           │
                                                 ▼
                                        dbt build (Airflow dbt_build task)
                                        raw → staging → marts
                                        (fct_orders, dim_restaurants,
                                         mart_delivery_sla)
                                                 │
                                                 ▼
                                   Airflow DAG: food_delivery_pipeline
                                   load_raw >> dbt_build, @daily, retries=2

Decisions — the section that actually answers "walk me through this repo," one line per decision, each with the *why* rather than just the *what*:

  • ELT over ETL — raw data lands untransformed first, so a bad load is always recoverable by re-running the transform, never by re-extracting from a source that may have moved on. (Day 1)
  • One topic, keyed by order_id — Kafka guarantees order only within a partition, so keying by order_id is the minimum needed to keep one order's own status changes in sequence, and deliberately promises nothing about ordering across different orders. (Day 5)
  • At-least-once delivery, made safe by an idempotent write — ON CONFLICT (event_id) DO NOTHING plus committing the Kafka offset only after the Postgres write, so a crash mid-stream can redeliver a message but never loses one or double-counts it. Verified by an actual kill-and-restart test, not just asserted. (Day 6)
  • fct_orders is incremental, dim_restaurants isn't — raw.orders only grows; restaurants barely change. Incremental logic is only worth its complexity where reprocessing everything every run would actually cost something. (Day 4)
  • Orchestration is BashOperator, not Cosmos — two coarse-grained tasks are enough to make a nightly run schedulable and retryable; per-model task granularity is a real upgrade for later, not a Day 7 requirement. (Day 7)
  • What breaks at 100× volume — order_events's 3 partitions cap Kafka's parallelism at 3 consumers per group; fct_orders' incremental filter would need a watermark strategy more robust than a simple max-timestamp scan once late-arriving events are common; a single-node Postgres warehouse would need to become a column-store or a managed warehouse. None of these are urgent at this data's actual size — naming them anyway is what a design review is checking for.

Push both files. This is the artifact PLAN.md calls Phase 1's ship step — a repo a stranger, or an interviewer, could clone and run in under ten minutes.

Q: "Why does your Airflow DAG only have two tasks — isn't that too coarse?" A strong answer, out loud: "For this repo's size, yes, two tasks is the right amount of granularity — load_raw and dbt_build are the only two things that actually need independent retry semantics, since dbt already has its own internal DAG that decides model build order and skips downstream models when an upstream one fails. Going finer — one Airflow task per dbt model, which is what Cosmos does — buys per-model retry and a graph view inside Airflow's own UI, at the cost of one task per model instead of one task per logical stage. That's a real trade I'd make once the dbt project is big enough that a single failing model shouldn't block investigating the others independently, but for seven models it would be complexity with no payoff yet." The signal: naming the trade-off explicitly, with a concrete threshold for when the answer would flip, instead of treating "more granular is always better" as a fact.
