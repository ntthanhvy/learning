After the timeout fires: retry-with-backoff, now in C# too

Lesson 111's own Scope line drew the boundary deliberately: "a timeout tells you to give up on this attempt, not whether to try again." Today picks up exactly there. Lesson 32 already taught the strategy — exponential backoff plus jitter — but only in Go. Every C# lesson since 107 has had a Go-side twin; this is the one place where the gap ran the other way. Today closes it.

1 · A timeout firing is an answer to one question, not two

context.WithTimeout and CancellationTokenSource(TimeSpan) — Lesson 111's whole lesson — answer exactly one question: should this specific attempt keep running? Once the deadline passes, the answer is no, and the call returns an error. What that error means next is a completely separate question the timeout mechanism has no opinion on at all: was this a one-off hiccup worth trying again, or a dependency that's actually down, where trying again just adds load to something already struggling? Lesson 32 named that second question for Go. Today asks it again, in C#, reusing the exact same strategy rather than inventing a new one.

2 · The strategy doesn't change between ecosystems — only the vocabulary does

Lesson 32's shape still holds completely: wait after a failure, double the wait each subsequent failure (exponential backoff), randomize that wait so many clients failing together don't retry together (jitter), skip retrying a 4xx since the request itself was wrong, and stop immediately if the caller's own outer deadline has already passed. None of that is Go-specific; it's a statement about distributed systems. What's different in C# is only the shape of two things: how a single attempt gets its own deadline (Lesson 111's CancellationTokenSource(TimeSpan), not Go's context.WithTimeout), and how "wait without blocking a thread" is spelled.

3 · C#'s wait-without-blocking is Task.Delay, not time.Sleep

Go's backoff loop in Lesson 32 waited with a select over time.After and ctx.Done() — never time.Sleep, because Sleep can't be interrupted by a cancelled context. C# has the exact same trap and the exact same fix: Thread.Sleep blocks the OS thread outright (the sync-over-async mistake Lesson 107 already named), so the backoff wait has to be await Task.Delay(delay, cancellationToken) instead — a delay that is itself cancellable, and that releases the thread back to the pool while waiting, the same cooperative-yield Lesson 107 described for every other await:

async Task<Price> FetchPricingWithRetryAsync(string sku, CancellationToken outerToken)
{
    var rng = new Random();
    var baseDelay = TimeSpan.FromMilliseconds(200);
    var capDelay = TimeSpan.FromSeconds(5);
    Exception lastError = null;

    for (int attempt = 0; attempt < 4; attempt++)
    {
        using var attemptCts = CancellationTokenSource.CreateLinkedTokenSource(outerToken);
        attemptCts.CancelAfter(TimeSpan.FromSeconds(3)); // Lesson 111's per-attempt deadline
        try
        {
            return await CallPricingServiceAsync(sku, attemptCts.Token);
        }
        catch (Exception ex) when (IsRetriable(ex))
        {
            lastError = ex;
            if (attempt == 3) break; // last attempt already used, no point waiting again

            var backoff = TimeSpan.FromMilliseconds(Math.Min(
                capDelay.TotalMilliseconds, baseDelay.TotalMilliseconds * Math.Pow(2, attempt)));
            var jittered = TimeSpan.FromMilliseconds(rng.NextDouble() * backoff.TotalMilliseconds);
            await Task.Delay(jittered, outerToken); // outer token: caller's own deadline can still cut this short
        }
    }
    throw new Exception($"giving up after 4 attempts", lastError);
}

Two tokens are doing two different jobs, deliberately not collapsed into one: attemptCts.Token (linked to outerToken, with its own 3-second CancelAfter) bounds a single attempt exactly the way Lesson 111 taught; the bare outerToken passed straight into Task.Delay bounds the whole retry loop, so a caller who cancels the entire operation doesn't have to wait out a queued backoff sleep first.

CreateLinkedTokenSource is new, and it's the only genuinely new mechanism today. CancellationTokenSource.CreateLinkedTokenSource() combines the caller's outer token and this attempt's own timeout into a single token: the attempt stops if either the whole operation was cancelled or this one attempt's 3 seconds ran out — whichever comes first. Go's equivalent is unglamorous by comparison: nesting context.WithTimeout(outerCtx, 3*time.Second) already does this for free, since a child context Lesson 41 taught is cancelled whenever its parent is, with no separate linking step needed.

4 · Idempotency still isn't optional

Lesson 32's closing warning carries over unchanged: a timeout on the client side doesn't prove the server side didn't finish the work before the response was lost. Retrying a non-idempotent write after a timeout can double-create, in C# exactly as much as in Go. Lesson 26's Idempotency-Key is still the thing that makes retrying safe; today's loop only decides the timing, not the safety.

Scope line

This lesson covers composing retry-with-backoff (Lesson 32's strategy: exponential backoff, full jitter, a retriable-error check, respecting an outer deadline) on top of a single-call timeout (Lesson 111), now shown in C# for the first time using Task.Delay and CancellationTokenSource.CreateLinkedTokenSource(). It does not re-derive the backoff math or the retry-storm problem — Lesson 32 already covers both in full and nothing about them changes in C#. It does not cover a circuit breaker (Lesson 28) as the outer stop-retrying-entirely guard, nor Polly or any .NET resilience library's packaged version of this same loop — the mechanism is taught here from first principles, same as Lesson 32 did in Go, per MISSION.md's "concepts first" rule.
