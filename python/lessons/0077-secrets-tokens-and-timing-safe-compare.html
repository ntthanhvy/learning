1 · Why random is the wrong tool here

Day 54 built random on a deterministic formula seeded from a starting number — reproducible on purpose, which is exactly what makes it unsafe for anything secret. If an attacker can observe enough of a random-generated sequence (or guess roughly when a process started, which often supplies the seed), the rest of the sequence can sometimes be predicted. A password-reset token or a session ID generated that way is a guessable token, not a secret one.

import random
import secrets

random.seed(0)
guessable = str(random.randint(100000, 999999))   # reproducible from a known seed -- never do this for a real token

safe = secrets.token_hex(16)   # e.g. 'e3b0c44298fc1c149afbf4c8996fb92c' -- drawn from the OS's own secure randomness source

secrets draws from the operating system's own cryptographically secure random source instead of a seedable formula. There is no secrets.seed() at all — reproducibility is precisely the property a secret token must never have, so the module simply doesn't offer it.

2 · Generating tokens: token_hex and token_urlsafe

Two functions cover almost every real token need, differing only in the alphabet of the output:

import secrets

secrets.token_hex(16)       # e.g. '9f86d081884c7d659a2feaa0c55ad015' -- 32 hex chars from 16 random bytes
secrets.token_urlsafe(16)   # e.g. 'E1F6k2cQqbG6w6-N9d5mTA' -- shorter, URL-safe characters from the same 16 bytes

Both take the number of random bytes as their argument, not the length of the output string — token_hex(16) always returns 32 characters (two hex digits per byte), while token_urlsafe(16) returns a shorter string using a wider alphabet (letters, digits, -, and _) that is safe to drop directly into a URL query string with no escaping. Reach for token_hex when the token goes into a database column or a header value; reach for token_urlsafe when it goes into a URL, such as a password-reset link.

Verified live: calling either function twice in a row produces two different strings every time — unlike Day 54's seeded random.seed(42) example, there is no way to reset secrets back to a prior starting point and reproduce the same sequence, by design.

Bridge from Day 74's uuid: both generate unlikely-to-collide values with no coordination needed, but for different purposes. uuid.uuid4() optimizes for uniqueness as an identifier (a request ID, a primary key) and is not secret — it's often logged or shown in a URL path. secrets.token_urlsafe() optimizes for unpredictability as a credential — something an attacker must not be able to guess. A session ID should be a secrets token, not a uuid4(), even though both "look like" a random string.

3 · Picking from a fixed set: secrets.choice

Sometimes the token needs to come from a specific alphabet instead of raw hex or URL-safe bytes — a one-time numeric PIN, or a short human-readable code. secrets.choice() is the module's secure replacement for random.choice(), picking one element from a sequence using the same secure source as the token functions:

import secrets
import string   # Day 69's "already closed" module, reused here for its letter/digit constants

alphabet = string.ascii_uppercase + string.digits
code = "".join(secrets.choice(alphabet) for _ in range(6))
print(code)   # e.g. 'K3P9QZ' -- a 6-character code, each character drawn securely

This is the right tool for a one-time PIN or a short invite code that a human has to type in — something token_urlsafe()'s mixed-case-plus-punctuation alphabet is awkward to read aloud or retype correctly. random.choice() would work syntactically here too, which is exactly the trap: nothing stops the wrong, predictable function from compiling and running — only the choice of module makes the output actually safe to hand out as a credential.

4 · Comparing secrets safely: secrets.compare_digest

A plain == comparison between two strings is not just functionally fine — in most code it is exactly right. But comparing a secret value — a token, a password hash, an API key — against user-supplied input has one extra risk == doesn't protect against: Python's string == typically stops comparing at the first mismatched character, so a wrong guess that happens to share a long correct prefix takes measurably longer to reject than a wrong guess that differs immediately. Repeated over many attempts, that tiny timing difference is a real, documented attack (a timing attack) used to recover secrets character by character:

import secrets

real_token = secrets.token_hex(16)
guess = "0000000000000000000000000000000"

guess == real_token                            # False -- correct answer, but took a data-dependent amount of time to get there
secrets.compare_digest(guess, real_token)       # False -- same answer, constant time regardless of how much of the prefix matched

compare_digest() always takes the same amount of time to return, no matter how many leading characters match — it is built specifically so the comparison itself leaks nothing. Reach for it only when comparing a secret against untrusted input (verifying an API key header, a webhook signature, a password-reset token from a URL); an ordinary == between two values that aren't secrets, like comparing two filenames, needs no such protection and should stay plain ==.

Where this sits next to Day 59's hashlib: Day 59 named pbkdf2_hmac() as the right tool for storing a password (a slow, salted hash) and deferred it as a future topic — that is still deferred today. secrets answers a different pair of questions that come before and after storage: generating the random token in the first place (token_hex/token_urlsafe), and safely checking a supplied value against a stored one (compare_digest) without a timing leak. All three — generating, hashing-for-storage, and comparing — are distinct jobs that real authentication code needs; today closes the first and third.
Where pandas goes from here: nothing pandas-specific today — token generation and constant-time comparison have no DataFrame equivalent; a generated token might end up stored in a DataFrame column downstream, but no DataFrame code is shown here, per MISSION.md.
