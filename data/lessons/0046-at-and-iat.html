.at[] and .iat[]: fast single-scalar access

.loc[] and .iloc[] (used constantly since Lesson 1) can pull out a whole row, a whole column, or a rectangular block of both. Today's two methods do only ONE job — get or set exactly one cell — and trade away every one of those other abilities for real speed and a narrower, more honest contract.

Recap, in one line

.loc[row_label, col_label] and .iloc[row_pos, col_pos] both accept a single label/position OR a list/slice of them, so pandas has to check which shape you gave it every time, even when you only ever wanted one cell. .at[]/.iat[] skip that check entirely by refusing anything but a single scalar.

1 · .at[]: one cell, by label

.at[] reads or writes a single cell, addressed the same way .loc[] addresses one:

--   order_id customer  amount order_date
-- 0        1       An   120.0 2026-01-05
-- 1        6       An    42.0 2026-01-10
-- 2        2     Binh    35.5 2026-01-06
-- 3        5     Binh   180.0 2026-01-09
clean.at[1, "amount"]
-- 42.0 -- identical result to clean.loc[1, "amount"]

clean.at[0, "amount"] = 999.0
-- sets exactly that one cell, same effect as clean.loc[0, "amount"] = 999.0

Every value .at[] produces is one .loc[] would also produce — nothing new to learn about the result. The difference is entirely in what it's willing to accept as an argument.

2 · .iat[]: one cell, by position

.iat[] is .at[]'s positional twin, the same relationship .iloc[] has to .loc[]:

clean.iat[1, 2]
-- 42.0 -- row position 1, column position 2 ("amount") -- ignores the label entirely
-- identical result to clean.iloc[1, 2]

clean.iat[-1, -1]
-- 2026-01-09 -- negative positions work exactly like .iloc[], counting from the end

3 · The one real restriction: scalar only, no exceptions

This is the entire trade — try to hand .at[]/.iat[] anything but a single label/position pair and it refuses, loudly, rather than silently doing something close enough:

clean.at[1, ["amount", "customer"]]
-- InvalidIndexError: ['amount', 'customer']
-- .loc[] would have happily returned a 2-value row slice here -- .at[] won't

No row slices, no column lists, no boolean masks, no : — if the answer isn't exactly one cell, .at[]/.iat[] are the wrong tool, full stop. That narrowness is the whole point: it's a promise to both pandas and the next reader of the code that this line touches exactly one value.

Gotcha — a missing label still raises, just like .loc[]: .at[] is not more forgiving than .loc[] about label lookups — reading a label that doesn't exist raises the same KeyError either way: 
clean.at[999, "amount"]
-- KeyError: 999   (clean.loc[999, "amount"] raises the identical KeyError)
And on the write side, both behave identically too — assigning to a row label that doesn't exist yet creates a brand-new row, padding every other column with NaN, for both .at[] and .loc[] alike. Nothing about that behavior changes between them; only the accepted shape of the argument differs.

4 · Why bother: speed on a single-cell hot path

Hand-timed on this course's own 4-row fixture, 20,000 repeated lookups of the same cell: .at[] took about 1.3x less time than the equivalent .loc[] call. That gap is real but modest on a table this small — the honest reason to reach for .at[]/.iat[] isn't "always use it," it's a targeted swap on a genuine hot path: single-cell lookups repeated many times inside a loop (rare in idiomatic pandas, but it happens — e.g. building up a result cell-by-cell after a vectorized approach hits a real dead end) is where the per-call overhead .loc[]/.iloc[] pay for shape-checking actually adds up.

A realistic single-cell pattern that reads naturally with .at[]: pairing it with Lesson 20's idxmax() to pull one specific value once the row label is already known —

top_idx = clean.groupby("customer")["amount"].idxmax()
-- An -> 0, Binh -> 3   (the row LABEL holding each customer's max, from Lesson 20)
clean.at[top_idx["An"], "amount"]
-- 120.0 -- one cell, by the label idxmax() already found

Q: "When would you use .at[] instead of .loc[]?" A strong answer, out loud: "They return identical results for a single-cell lookup — .at[] and .iat[] are strictly narrower versions of .loc[] and .iloc[], accepting only one row label/position and one column label/position, nothing list- or slice-shaped. That narrowness buys two things: a real but modest speed edge on repeated single-cell access, since pandas skips the shape-checking .loc[]/.iloc[] do on every call; and a clearer signal in the code itself that this line touches exactly one value, not a range. I wouldn't reach for it by default — .loc[]/.iloc[] read fine for one-off lookups — but I'd use it in a tight loop over individual cells, or anywhere I want the type system-adjacent guarantee that a typo can't accidentally turn into a silent multi-cell operation." The signal: naming both the real (but bounded) speed reason and the narrower-contract reason, not just parroting "it's faster."

5 · The SQL bridge

SQL has no real equivalent distinction here — a scalar subquery like SELECT amount FROM orders WHERE order_id = 6 always returns exactly one value by construction (or errors if it matches more than one row); there's no separate "fast single-value" syntax versus a general row/range query the way pandas splits .at[] from .loc[]. This distinction is pandas-specific plumbing, not a transferable SQL concept — worth naming as exactly that if it comes up.
