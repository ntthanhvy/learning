pprint: making nested data readable without reaching for json

A plain print() on a dict of lists of dicts comes out as one long, hard-to-scan line. Day 76 showed one fix — json.dumps(obj, indent=2) — but that only works on JSON-shaped data (no sets, no custom objects, no tuples as dict keys) and always produces a string you then have to print yourself. The pprint module is the simpler, more general tool for exactly this job: readable nested data, printed directly, for a human looking at a terminal — not for serialization at all.

1 · The problem: nested data on one unreadable line

A plain print() call uses each object's default repr(), laid out however it fits — for a short flat list that's fine, but a dict of lists of dicts becomes one dense, bracket-heavy line with no indentation to show where one record ends and the next begins:

record = {
    "user": {"id": 42, "name": "An", "roles": ["admin", "billing"]},
    "orders": [{"sku": "A1", "qty": 3}, {"sku": "B2", "qty": 1}],
}
print(record)
# {'user': {'id': 42, 'name': 'An', 'roles': ['admin', 'billing']}, 'orders': [{'sku': 'A1', 'qty': 3}, {'sku': 'B2', 'qty': 1}]}

That single line is correct but slow to scan — finding where "orders" starts means counting brackets by eye. This is exactly the shape of problem pprint exists to solve.

2 · pprint(): the direct replacement for print()

pprint.pprint() takes the same single object print() would take, and lays it out across multiple lines with indentation showing the nesting:

from pprint import pprint

pprint(record)
# {'orders': [{'qty': 3, 'sku': 'A1'}, {'qty': 1, 'sku': 'B2'}],
#  'user': {'id': 42, 'name': 'An', 'roles': ['admin', 'billing']}}

Two things change from plain print(): the multi-line indentation, and — by default — dict keys are sorted alphabetically before printing ("orders" now comes before "user", reversed from insertion order), specifically so the same data always prints the same way regardless of what order its keys happened to be built in. Passing sort_dicts=False turns that off and preserves insertion order instead, when the original order is the point.

3 · width= and pformat(): controlling layout, and getting a string back

pprint() only breaks a line once it would exceed a target width — 80 characters by default — so short structures still print on one line, same as plain print() would. width= changes that threshold directly:

from pprint import pprint

short = {"id": 1, "name": "An"}
pprint(short)                 # {'id': 1, 'name': 'An'} -- fits on one line, stays on one line
pprint(record, width=40)    # forces more, narrower lines than the default-width call above

Sometimes the readable text is needed as a string — to write into a log line, or embed in an error message — rather than printed immediately. pprint.pformat() ("pretty-format") does the identical layout work and returns the result as a str instead of printing it, the same split json.dumps()/print(json.dumps(...)) has:

from pprint import pformat
import logging

logging.warning("bad record: %s", pformat(record))   # the formatted text becomes part of a log message, not stdout
Bridge from Day 76's json.dumps(indent=): both produce readable, multi-line nested output, but for different inputs and different purposes. json.dumps(obj, indent=2) only accepts JSON-shaped data (dict/list/str/int/float/bool/None) and produces valid JSON text meant to be sent, stored, or parsed back by something else. pprint() accepts any Python object — including set, tuple, and a dict with a tuple as a key, none of which json.dumps() can serialize at all — and its output is for a human to read right now, never meant to be parsed back. Reach for json.dumps(indent=) when the readable text might also need to travel somewhere as data; reach for pprint() when it's purely a debugging or logging aid.
Where pandas goes from here: nothing pandas-specific today — pprint formats plain Python dicts/lists/sets for terminal reading; a DataFrame already has its own readable __repr__ for the same job on tabular data, no DataFrame code shown here, per MISSION.md.
