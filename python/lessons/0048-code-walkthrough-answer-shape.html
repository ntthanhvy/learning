Reading someone else's code out loud

Day 47 taught the four-part shape for answering a conceptual question from memory — claim, mechanism, example, contrast. That covers half of technical-interview performance: producing an explanation for a claim already held. The other half is the mirror image and gets far less practice: handed a block of unfamiliar code someone else wrote, walk through it out loud and explain what it does before being asked a single question about it. This is a code walkthrough, and — like Day 47's answer shape — it has a reusable order that turns "let me look at this" panic into a rehearsed move.

Bridge from the baseline: learning-records/0001-… names a reading/writing asymmetry — this course can read simple Python already, so a code walkthrough is close to the strong half of the baseline. The trap is different from Day 47's: it isn't recall pressure, it's narration pressure — silently understanding a function is not the same skill as producing a spoken explanation of it in real time, in an order a listener can actually follow. Interviewers rarely hand over blank-file problems only; "here's a snippet, talk me through it" is at least as common, and untrained narration tends to default to reading the code aloud line by line, which explains syntax but never states purpose.

1 · Three moves, in a fixed order — outside in, not top to bottom

A strong code walkthrough does not start at line 1 and read downward. It goes from the outside of the code toward its riskiest inside detail, in three moves:

  1. Purpose. One sentence on what the code is for — the job it does for a caller — inferred from its name, its signature, and what it returns, before explaining a single line of its body. A listener who only hears this sentence should know why the code exists.
  2. Shape. One or two sentences on the control flow that gets from input to output: is it a loop, a recursion, an early return, a generator that yields instead of returning, a context manager guarding a resource? Name the mechanism, not each line.
  3. Sharp edge. The one detail in this specific code that a careless reading would get wrong — a mutable default, a generator that only runs once, a decorator changing what the function name is bound to, an except clause narrower or wider than it looks. This is the payoff: it proves the code was actually understood, not just paraphrased.

Notice the shape: purpose first is the same instinct as Day 47's claim-first rule — state the conclusion before the supporting detail, so a listener who stops listening early still walked away with the right idea. The two shapes are mirror images of the same discipline aimed at opposite directions: Day 47 builds an answer outward from a claim already held; a walkthrough builds an explanation outward from code just seen for the first time.

2 · Walking through unfamiliar code, live

Here is a function built entirely from mechanisms already taught (Day 12 decorators, Day 5 generators, Day 4 key=) but never shown together this way before — exactly the kind of "seen the pieces, not this exact shape" snippet a walkthrough needs to handle:

from functools import wraps

def skip_empty(fn):
    @wraps(fn)
    def wrapper(*args, **kwargs):
        for item in fn(*args, **kwargs):
            if item:
                yield item
    return wrapper

@skip_empty
def top_scores(rows, n=3):
    ranked = sorted(rows, key=lambda r: r["score"], reverse=True)
    for row in ranked[:n]:
        yield row.get("name", "")

Three moves, out loud:

# Purpose
"top_scores takes a list of row-dicts and gives back the names of the
top n by score, skipping any row whose name is blank."

# Shape
"It's two generators stacked: top_scores itself sorts rows by score
descending with key=, slices the top n, and yields each one's name;
skip_empty wraps it and re-yields only the truthy ones, so an empty
string never comes out the other end."

# Sharp edge
"skip_empty makes wrapper a generator function too, not a plain
function - it can only do that because it uses yield instead of return,
looping over whatever fn(*args, **kwargs) produces. And @wraps(fn) is
doing real work here: without it, top_scores.__name__ would report
'wrapper' instead, which matters the moment something introspects or
logs the function by name."

Notice the sharp edge is not "here is a fact I memorized about decorators" — it is specific to this code: a decorator that turns a generator's caller-facing name into the wrapper's own, on a function that itself only works because wrapper contains a yield. Reading it top to bottom line by line would explain the syntax and miss both points.

3 · Why this is a language skill, not a Python skill

Exactly like Day 47's shape, the three-move order (purpose, shape, sharp edge) is not Python-specific — it works for reading a walkthrough of Go, SQL, or Rust too, which is why it isn't a dedicated PLAN.md spine item either. What is Python-specific is the vocabulary needed to name the shape accurately: without Day 5's generators, Day 12's decorators, and Day 4's key=, the shape step above would collapse into "it loops and sorts things," which is true but explains nothing a listener couldn't see by reading the code themselves. The walkthrough skill is worthless without the vocabulary; the vocabulary is inert without the walkthrough skill to deploy it under time pressure.

Where pandas goes from here: nothing pandas-specific — the same three-move order applies identically to walking through a pandas groupby chain someone else wrote, but building that example here would mean writing worked pandas code, which stays out of scope per MISSION.md. Not demonstrated.

Q: "Here's a function you've never seen before — walk me through it." A strong answer, out loud, before touching any specific line: "Let me start with what it's for, based on the name and what it returns, then how it gets there, then anything that looks like it could bite someone — rather than reading it top to bottom." Then apply the three moves. The signal: the candidate has a plan for unfamiliar code, not just the ability to eventually understand it after a long silence.
