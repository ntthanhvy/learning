unicodedata: when two identical-looking strings aren't equal

Day 1 taught that == on two str objects compares their actual characters, not their printed appearance — and that has always been true, byte for byte. What Day 1 didn't need yet is a case where two strings print identically on screen, character for character to the human eye, and still fail ==. Unicode makes that possible: the same visible letter can be built from a different number of underlying code points. unicodedata is the standard-library module that explains why, and normalize() is the fix.

Why today, specifically: a fresh case-insensitive grep across every lesson, practice file, reference/glossary.html, and RESOURCES.md confirmed unicodedata, normalize, NFC, and NFD are all zero-hit — genuinely untaught. selectors, signal, sched, stat, tracemalloc, platform, ipaddress, mimetypes, binascii, and codecs were also confirmed zero-hit this round (Day 116's own closing note had flagged all eleven as candidates), but most of those skew toward OS/event-loop internals this course's own scope boundary already excludes (MISSION.md's "no deep asyncio event-loop internals," extended here to the sibling OS-signal/socket territory), or are thin single-function asides. unicodedata won because it is a genuine language-level gotcha about str identity and equality — directly extending Day 1's "names, objects, mutability" rather than standing alone — and because it is a real bug class: usernames, filenames, and search queries that look identical can silently fail an == check or a dict/set lookup depending on which app or OS last touched the string. calendar and socket remain the two longest-standing ruled-out candidates (thin content and scope-depth respectively). 1 · The same letter, built two different ways

A letter like é can exist in a Python str as a single code point — U+00E9, "LATIN SMALL LETTER E WITH ACUTE" — or as two code points stacked together: a plain e (U+0065) followed by a separate "combining acute accent" mark (U+0301) that visually lands on top of whatever comes before it. Both render identically on screen. Neither is wrong; Unicode allows both on purpose, because some scripts need combining marks that have no single precomposed character at all.

s1 = "café"                      # precomposed: e-acute is ONE code point, U+00E9
s2 = "cafe" + "́"           # plain e + a SEPARATE combining acute accent, U+0301

print(s1, "|", s2)          # confirmed live: café | café  -- look identical
print(len(s1), len(s2))     # confirmed live: 4 5  -- but NOT the same length
print(s1 == s2)            # confirmed live: False

That's not a display bug and not a Python bug — == on strings compares code points exactly, the same rule Day 1 relied on everywhere else, and these two strings genuinely contain a different sequence of code points. The trap is that nothing on screen hints at it. A value pasted from one app, a filename saved by one OS, or a username typed on one keyboard layout can carry a different code-point sequence than another that looks pixel-for-pixel the same, and ==, dict lookups, and set membership will all quietly disagree.

2 · unicodedata.normalize(): picking one shape to compare by

unicodedata.normalize(form, s) rewrites a string into one of a small number of standard shapes, so two strings that only differ in how a character was built end up identical after normalizing both the same way. The two forms this course needs: "NFC" (compose combining marks into a single code point wherever one exists) and "NFD" (decompose the other way, splitting every precomposed character back into its base + combining marks). Either direction works as a comparison key, as long as both sides use the same one:

import unicodedata

nfc1 = unicodedata.normalize("NFC", s1)
nfc2 = unicodedata.normalize("NFC", s2)
print(nfc1 == nfc2)                 # confirmed live: True
print(len(nfc1), len(nfc2))        # confirmed live: 4 4  -- both composed down to the same 4 code points

nfd1 = unicodedata.normalize("NFD", s1)
nfd2 = unicodedata.normalize("NFD", s2)
print(nfd1 == nfd2)                 # confirmed live: True
print(len(nfd1), len(nfd2))        # confirmed live: 5 5  -- both decomposed to the same 5 code points

unicodedata.normalize() is the fix: pick one form, apply it to every string before comparing, storing, or hashing it, and the "built differently, looks the same" trap disappears — exactly the way Day 1's mutable-default-argument trap disappeared once the actual rule behind it was named instead of guessed at.

The lookup trap, made concrete: a set or dict key check uses == internally (via __hash__/__eq__, Day 31), so it inherits the exact same blind spot. Confirmed live: {s1} as a set does not contain s2 (s2 in {s1} is False), even though they print identically — but normalizing both sides first fixes it, unicodedata.normalize("NFC", s2) in {unicodedata.normalize("NFC", s1)} is True. Any code that deduplicates usernames, filenames, or free-text input by putting them in a set or using them as a dict key needs to normalize first, or it will silently treat two "same" values as different.

3 · unicodedata.name() and .category(): asking what a character actually is

Two more small, frequently useful lookups from the same module: unicodedata.name(char) returns a character's official Unicode name as a string — useful for debugging exactly which invisible character snuck into a string — and unicodedata.category(char) returns a short code classifying what kind of character it is (letter, digit, punctuation, space, and so on), handy for a validation check that needs to reason about character kind rather than hand-writing a list of allowed characters:

print(unicodedata.name("A"))          # confirmed live: LATIN CAPITAL LETTER A
print(unicodedata.category("A"))      # confirmed live: Lu  -- Letter, uppercase
print(unicodedata.category("5"))      # confirmed live: Nd  -- Number, decimal digit
print(unicodedata.category(" "))      # confirmed live: Zs  -- Separator, space

name() turns a mystery character copy-pasted from somewhere into a readable label instead of a blank space or a box on screen — exactly the debugging move for "why does this string that looks fine fail every check." category() is a one-call way to ask "is this a letter?" or "is this punctuation?" without hand-writing a range of acceptable code points.

Where pandas/NumPy go from here: neither has a notion of Unicode normalization at all — a column of strings read with pd.read_csv() that silently mixes NFC and NFD text keeps that inconsistency straight through any pandas operation, including .groupby() and .drop_duplicates(), which both compare using the same ==-based rule this lesson just showed breaking. Normalizing is still a plain-Python, per-string job, typically done once while cleaning raw text before it ever reaches a DataFrame. Not covered further here, per MISSION.md.
