1 · The gap Day 34 left open: what decided the split, and what paying for it a second time felt like

Day 34 ran two copies of the Day 6 consumer under one group.id, watched Kafka split order_events's 3 partitions across them, then killed one and watched the coordinator hand its partition to the survivor. That lesson named that a rebalance happens and that exactly one consumer owns a partition at a time — it never asked which rule decided partitions 0 and 2 → consumer A, partition 1 → consumer B specifically, or what the survivor was actually doing for those several seconds while session.timeout.ms ran out. Both questions have the same one-word answer: the partition assignment strategy every consumer in a group agrees to run.

Day 34's two consumers never set partition.assignment.strategy, so they ran on librdkafka's default, range — confirmed this round directly against the installed client, which is why the partition numbers it printed (0,2 to one consumer, 1 to the other) were range's own deterministic output, not a coin flip. range belongs to a family called eager rebalancing: on every single rebalance, every member's partitions are revoked and the whole group's assignment is recomputed from zero — which is exactly why, when Day 34 killed one consumer, the surviving one also briefly stopped consuming its own untouched partitions, not just the orphaned one. That pause never showed up as a visible bug in Day 34 because its own verification only checked the final row count, not consumption latency during the gap — but at 1,000 events/sec instead of a dozen, "every consumer in the group stalls on every join or leave" is a real, measurable cost this course's portfolio conversation should be able to name.

2 · The fix: an assignor that only moves what actually moved

cooperative-sticky fixes exactly this. On a rebalance, it computes the new assignment the same way, but only revokes partitions from members whose ownership is actually changing — a consumer keeping all the partitions it already had never stops consuming at all, and the few partitions genuinely moving go through one short revoke-then-reassign instead of the whole group's partitions doing so. "Sticky" names the other half: when a rebalance does need to move a partition, it prefers leaving it with a consumer that already held it recently, rather than redistributing everything from scratch the way range does — fewer partitions change hands overall, not just a faster pause for the ones that don't need to.

The config is one string, set identically on every consumer that will ever join the group — confirmed live this round that a mismatched set (some consumers range, others cooperative-sticky) is a documented misconfiguration the client itself warns about, so the whole group moves together or not at all:

consumer = Consumer(
    {
        "bootstrap.servers": BOOTSTRAP,
        "group.id": GROUP_ID,
        "auto.offset.reset": "earliest",
        "enable.auto.commit": False,
        "partition.assignment.strategy": "cooperative-sticky",
    }
)

Bridge from backend: this is the same shape as a backend rolling-deploy question — "can you replace instances one at a time without a full-fleet outage?" — applied to Kafka consumers instead of API servers. cooperative-sticky is what makes a consumer-group deploy (bring up a new version, retire the old one) behave like a rolling deploy instead of a brief all-hands-stop; the deploy-strategy reasoning itself belongs to backend/, this lesson only applies it.

3 · Seeing the split happen, not just the final state

subscribe() already accepts two optional callbacks that fire exactly when a rebalance touches this specific consumer — on_assign when it gains partitions, on_revoke when it loses them. Day 6 and Day 34 never passed them, so nothing printed when ownership actually changed; today wires them in so a rebalance is visible in this consumer's own log, not only in a separate kafka-consumer-groups.sh --describe call run from another terminal:

def on_assign(consumer, partitions):
    print(f"assigned: {[p.partition for p in partitions]}")


def on_revoke(consumer, partitions):
    print(f"revoked: {[p.partition for p in partitions]}")

Confirmed live this round: both are plain functions taking (consumer, partitions), where partitions is a list of TopicPartition objects — p.partition for the partition number is the same attribute Day 34's own glossary entries already relied on reading off a kafka-consumer-groups.sh row, just reached from Python instead of a CLI table.

In your food-delivery-pipeline repo, edit scripts/consume_order_events.py. Add the new config line to the existing Consumer({...}) call, and the two callback functions, then pass them to subscribe():

def on_assign(consumer, partitions):
    print(f"assigned: {[p.partition for p in partitions]}")


def on_revoke(consumer, partitions):
    print(f"revoked: {[p.partition for p in partitions]}")

    )
    consumer.subscribe([TOPIC], on_assign=on_assign, on_revoke=on_revoke)  # callbacks new today

    # the commit-after-write ordering -- is untouched from Day 6
    ...

Nothing about the INSERT ... ON CONFLICT write or the write-then-commit ordering from Day 6 changes — today only changes how the group decides who owns which partition, not what a consumer does once it owns one.

Q: "A teammate says adding a new consumer to a busy consumer group briefly stalled every existing consumer, not just the one gaining a partition. Why would that happen, and what would you change?" A strong answer, out loud: "That's the default partition-assignment strategy, range or roundrobin, both of which are eager — on every rebalance the coordinator revokes every partition from every member first, recomputes the whole assignment from scratch, then hands it back out. A consumer whose own partitions end up unchanged still stops consuming for that full revoke-and-reassign round trip, because the protocol doesn't distinguish 'your assignment changed' from 'your assignment is being recomputed anyway.' The fix is switching every consumer in the group to the cooperative-sticky assignor, which only revokes partitions from members whose ownership is actually changing, and tries to keep a partition with whoever already had it rather than redistributing everything. I'd verify it by wiring on_assign/on_revoke callbacks into the consumer and confirming that a rebalance only logs a revoke for partitions that truly changed hands, not every partition the group owns." The signal: naming eager rebalancing's revoke-everything behavior as the actual mechanism causing the stall, not just "rebalancing is slow," and knowing the fix is a one-line config shared by the whole group, not application retry logic.

Scope line

This lesson covers partition.assignment.strategy, the range vs. cooperative-sticky contrast, and the on_assign/on_revoke callbacks confirmed live against the installed client. It does not cover writing a custom assignor (a Kafka Streams/Java-ecosystem concern, well past this course's working-level Kafka scope per MISSION.md), roundrobin specifically (the other eager strategy, vocabulary-only here since it shares range's stop-the-world behavior and the distinction between the two eager strategies themselves doesn't change today's argument), or on_lost (the third callback, firing when this consumer's session has already expired and its partitions are presumed lost rather than cleanly revoked — a corner case closer to Day 50's crash-handling thread than today's assignment-strategy focus).
