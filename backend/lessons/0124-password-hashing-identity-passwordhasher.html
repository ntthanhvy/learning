Password hashing, now in C# too

Lesson 48 built the password-hashing rule in Go: never store the plaintext, never just hash it with something fast like SHA-256, reach for a slow, tunable, self-salting function like bcrypt instead. That lesson never got a C# mirror. ASP.NET Core Identity ships a first-party class that does the whole job — and adds one thing Go's bcrypt package never offered: a built-in signal for "this hash is old, upgrade it."

1 · Same two rules, one first-party class instead of a third-party package

Lesson 48's rule still holds exactly: store a hash, never the password; use a slow, tunable, automatically-salted algorithm, never a fast general-purpose one. Go's version reached for golang.org/x/crypto/bcrypt, a package outside the standard library. C#'s version reaches for PasswordHasher<TUser>, a first-party class in Microsoft.AspNetCore.Identity — not a NuGet add-on bolted on afterward, the same package that backs ASP.NET Core's own built-in user system.

public class AppUser { public string Id { get; set; } = ""; }

public class AccountService
{
    private readonly PasswordHasher<AppUser> _hasher = new();

    // SignUp: HashPassword embeds its own random salt and iteration count
    // inside the returned string -- there is no separate salt column, same
    // as bcrypt's packed "$2a$10$..." output in Lesson 48.
    public string HashForStorage(AppUser user, string plain) =>
        _hasher.HashPassword(user, plain);

    // Login: VerifyHashedPassword does the comparison in constant time --
    // Lesson 30's timing-attack defense, built into the framework call here.
    public bool CheckLogin(AppUser user, string storedHash, string attempt)
    {
        var result = _hasher.VerifyHashedPassword(user, storedHash, attempt);
        return result is PasswordVerificationResult.Success
            or PasswordVerificationResult.SuccessRehashNeeded;
    }
}

Nothing about the underlying problem changes crossing languages: HashPassword generates a fresh random salt per call and packs it, along with the algorithm's parameters, inside the single string it returns — the same "no separate salt column to manage" property Lesson 48 named for bcrypt's output. VerifyHashedPassword reads the salt back out of that string automatically and compares in an amount of time that doesn't leak how close a guess was, the same guarantee Lesson 122's CryptographicOperations.FixedTimeEquals gave webhook signatures.

2 · The one new piece: SuccessRehashNeeded

Here is where the two languages genuinely diverge. Go's bcrypt.CompareHashAndPassword returns only an error or nil — correct password, or not; nothing in between. C#'s VerifyHashedPassword returns a three-way PasswordVerificationResult: Failed, Success, or SuccessRehashNeeded.

public (bool ok, string? newHashToSave) VerifyAndMaybeUpgrade(
    AppUser user, string storedHash, string attempt)
{
    var result = _hasher.VerifyHashedPassword(user, storedHash, attempt);

    if (result == PasswordVerificationResult.Failed)
        return (false, null);

    if (result == PasswordVerificationResult.SuccessRehashNeeded)
        // correct password, but hashed under an older iteration count or
        // compatibility mode -- rehash now, while the plaintext is in hand,
        // and the caller persists newHashToSave over the old column value.
        return (true, _hasher.HashPassword(user, attempt));

    return (true, null); // Success -- already current, nothing to rewrite
}

SuccessRehashNeeded fires when the stored hash's own embedded parameters (iteration count, or an older "compatibility mode" format) have fallen behind the hasher's current defaults — the exact situation Lesson 48 described in the abstract, "a work factor tuned upward over time as hardware gets faster." bcrypt's cost factor can be raised the same way in Go, but nothing in bcrypt.CompareHashAndPassword's return value tells the caller a given row is still on the old cost — that check has to be built by hand, usually by parsing the cost out of the hash string yourself. PasswordHasher<TUser> makes the upgrade-on-next-login pattern a first-class return value instead of a DIY parse.

The one easy-to-miss detail: a login handler should check for SuccessRehashNeeded and persist the new hash on that same request, immediately after a successful login — this is the only moment the plaintext password is in hand at all; there is no batch job that can "upgrade everyone's hash" later, since the plaintext was never stored anywhere to upgrade from.

3 · What doesn't change crossing languages

Lesson 48's full checklist still applies untouched: never store plaintext, never reach for encryption instead of hashing (a password should never be recoverable, not even by the backend itself), never use a fast general-purpose hash, and always use something slow and tunable with salting built in. The default algorithm differs — bcrypt in Go, PBKDF2-HMACSHA256 in PasswordHasher<TUser>'s default compatibility mode — but both are OWASP-acceptable, tunable, self-salting choices; neither is "more secure" in the abstract, same verdict as Lesson 48's bcrypt-vs-Argon2id comparison.

Scope line

This lesson covers PasswordHasher<TUser>'s two methods and the PasswordVerificationResult enum as the C# mechanism for Lesson 48's hash-don't-encrypt, slow-not-fast rule. It does not cover PBKDF2's own internals, Argon2id support in .NET, or ASP.NET Core Identity's full user-management system (sign-in cookies, lockout, two-factor) — only the one class this pattern needs. The lower-level KeyDerivation.Pbkdf2 primitive is deliberately not shown either: Microsoft's own docs warn it "shouldn't be used in new apps that... store hashed passwords," precisely because PasswordHasher<TUser> is the higher-level, correct-by-default replacement.
