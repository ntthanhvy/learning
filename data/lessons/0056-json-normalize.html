json_normalize(): flattening nested JSON into a table

Lesson 55's own teaser named the last remaining zero-hit candidate from Lesson 53's original scan: json_normalize(). Every lesson through 55 started from a flat CSV — but a real interview take-home, or an actual API response, just as often arrives as nested JSON (an object inside an object, a list of line items inside an order). This lesson covers the tool built for exactly that gap.

Recap, in one line

Every fixture since Lesson 2 loaded flat via pd.read_csv() — one row, one dict-of-scalars, no nesting. json_normalize() is what handles the other common shape: a list of dicts where some values are themselves dicts or lists, the shape a JSON API almost always actually returns.

1 · Why plain pd.DataFrame() isn't enough

Feeding nested dicts straight to the regular DataFrame constructor doesn't flatten anything — the nested value just becomes one object cell holding the raw Python dict, unusable for any vectorized column operation:

records[0]
-- {'order_id': 1, 'amount': 120.0, 'order_date': '2026-01-05',
--  'customer': {'name': 'An', 'region': 'North'},
--  'items': [{'sku': 'A1', 'qty': 2}, {'sku': 'A2', 'qty': 1}]}
pd.DataFrame(records)["customer"].iloc[0]
-- {'name': 'An', 'region': 'North'}   (still a plain dict, dtype object)

Confirmed directly against the real fixture: the customer column's dtype stays object, and nothing like df["customer.region"] exists yet — the nested structure is just carried along untouched, not flattened.

2 · json_normalize(): nested dicts become dotted columns

pd.json_normalize() is a top-level function (pd.json_normalize(records), not records.json_normalize()) that walks every nested dict and turns each nested key into its own column, joined with a dot by default:

flat = pd.json_normalize(records)
flat.columns.tolist()
-- ['order_id', 'amount', 'order_date', 'items', 'customer.name', 'customer.region']
flat[["order_id", "customer.name", "customer.region"]]
--    order_id customer.name customer.region
-- 0         1            An           North
-- 1         2          Binh           South
-- 2         5          Binh           South
-- 3         6            An           North

Confirmed directly: the nested customer dict becomes two real, independently-selectable columns — customer.name and customer.region — ordinary str dtype columns, filterable and groupable like any other. The items column is left alone here (still one list-of-dicts per row) — flattening a nested list, rather than a nested dict, needs the separate tool in the next section. The joiner is configurable: sep="_" gives customer_name/customer_region instead of the dotted default.

3 · record_path + meta: exploding a nested list into its own rows

Each order's items is a nested list of line items, a different shape from a nested dict — flattening it means one output row per item, not one output column. record_path= names the list to explode; meta= names which outer fields to carry along on every resulting row, confirmed directly against the real fixture:

items = pd.json_normalize(
    records,
    record_path="items",
    meta=["order_id", ["customer", "name"]],
)
--   sku  qty  order_id customer.name
-- 0  A1    2         1            An
-- 1  A2    1         1            An
-- 2  B1    1         2          Binh
-- 3  B1    3         5          Binh
-- 4  B2    2         5          Binh
-- 5  A1    1         6            An

4 orders became 6 item rows — order 1 had 2 items, order 5 had 2 items, orders 2 and 6 had 1 each — with order_id and the nested customer.name (a two-element path list, since it's nested one level deep in the source) copied onto every row that item belongs to. This is the pandas shape of a SQL one-to-many join: orders joined to order_items on order_id, except the "join" is really just un-nesting a list that was already embedded in the source JSON.

4 · Two sharp edges, both confirmed directly

A raw JSON string is NOT accepted. json_normalize() expects already-parsed Python objects (a list of dicts, or a dict) — not the text of a JSON document. Passing the raw string genuinely raises, confirmed directly against the real fixture:

raw_text = json.dumps(records)
pd.json_normalize(raw_text)
-- NotImplementedError
-- (the fix: parse first)
pd.json_normalize(json.loads(raw_text)).columns.tolist()
-- ['order_id', 'amount', 'order_date', 'items', 'customer.name', 'customer.region']

A real crash, not a silent wrong answer — the same "loudly refuses on a type it wasn't built for" family as .compare()'s ValueError on mismatched shapes (Lesson 54), not the quieter "no crash, quietly wrong" family most of this course's other gotchas have fallen into.

A missing meta key raises by default, unlike a missing dict key elsewhere in pandas. If some record in the list is missing a field named in meta=, the default behavior is a hard KeyError — not a quiet NaN, confirmed directly:

-- one record has no "order_id" key at all
pd.json_normalize(records_missing, record_path="items", meta=["order_id"])
-- KeyError: "Key 'order_id' not found. To replace missing values
--            of 'order_id' with np.nan, pass in errors='ignore'"

The error message names its own fix: errors="ignore" switches that record's missing meta value to NaN instead of raising — the opposite default from str.extract()'s "non-match becomes NaN, never raises" (Lesson 42), worth naming explicitly if asked in an interview, since guessing the wrong default here means a crash the first time real-world data has a gap.

5 · The SQL bridge

There's no single SQL equivalent, because SQL tables can't hold nested values in a column to begin with — a JSON or JSONB column is the closest cousin, and json_normalize()'s two behaviors map onto two different SQL operators: flattening a nested dict (Section 2) is like Postgres's ->> operator pulling a named field out of a jsonb column into its own column, while record_path= exploding a nested list (Section 3) is like Postgres's jsonb_array_elements() combined with a join back to the parent row — one input row becomes several output rows, carrying the parent's key along on each.

Q: "You're handed a REST API response — a list of orders, each with a nested customer object and a nested list of line items. How do you get this into a usable DataFrame?" A strong answer, out loud: "First json.loads() it if it's still raw text — json_normalize() only accepts already-parsed Python objects, not a JSON string directly, and it genuinely raises NotImplementedError if you skip that step. Then pd.json_normalize() on the list flattens every nested dict into dotted columns automatically — customer.name, customer.region. For the nested items list, that's a different shape: I'd use record_path='items' with meta=['order_id', ...] to explode it into one row per line item, carrying the order-level fields along — basically un-nesting a one-to-many relationship that was embedded directly in the JSON, the same shape as a SQL join to a child table." The signal: distinguishing dict-flattening from list-exploding as two different problems, and knowing the raw-string gotcha instead of assuming json_normalize() reads text directly.
