1 · A third option this course has never shown

By now you've written a test three different ways, and it's worth lining them up before adding a fourth: Day 3's assert_positive_subtotal was a singular test, one file, one rule, not reusable. Day 11's dbt_utils.accepted_range was a package's generic test — reusable, but someone else wrote the SQL; you only ever supplied arguments in YAML. Day 12's unit tests check model logic against fake rows, a different axis entirely (logic vs. real data), not a mechanism for writing a new kind of real-data check at all.

What's never come up: dbt lets you write a brand-new generic test, with the exact same reusable, parameterized shape as a package's — declared in YAML, applied to any column, written once and reused everywhere — except the SQL inside it is yours. That's today's actual skill, and it closes a real gap: nothing in this project has ever tested that delivered_at comes after placed_at for the same order, a rule no built-in test and no installed package expresses, because it's a comparison between two columns on the same row, not a bound on one column alone.

2 · Build: promote the join into its own model first

Day 6's mart_delivery_sla.sql computes placed_at, delivered_at and minutes_to_deliver inside its own CTEs, then immediately aggregates them away into a city/day grain — there's no column left afterward to test the raw per-order comparison against. Pull that join into its own intermediate model first, the same layering move Day 8 made for the restaurant/courier join, so the per-order columns exist somewhere testable:

-- models/intermediate/int_order_durations.sql
with placed as (
    select order_id, occurred_at as placed_at
    from {{ ref('stg_order_events') }}
    where status = 'placed'
),

delivered as (
    select order_id, occurred_at as delivered_at
    from {{ ref('stg_order_events') }}
    where status = 'delivered'
)

select
    o.order_id,
    o.restaurant_id,
    r.city,
    p.placed_at,
    d.delivered_at,
    extract(epoch from (d.delivered_at - p.placed_at)) / 60 as minutes_to_deliver
from {{ ref('stg_orders') }} as o
inner join placed as p on p.order_id = o.order_id
inner join delivered as d on d.order_id = o.order_id
inner join {{ ref('stg_restaurants') }} as r on r.restaurant_id = o.restaurant_id

This is a line-for-line move of Day 6's own CTEs into their own file, materialized ephemeral per Day 8's convention (dbt-internal only, inlined at compile time, no extra storage). Rewrite models/marts/mart_delivery_sla.sql to select from it instead of repeating the join:

3 · Write the generic test itself

A custom generic test lives in a .sql file under tests/generic/ — a special subfolder dbt recognizes alongside the singular tests you already have directly in tests/ — and is defined with a {% test %} block, the same Jinja block shape as any macro. Every generic test's first two parameters are always named model and column_name, whether built into dbt, shipped by a package, or written here; the column being tested is one of them (column_name), and any other column it needs to compare against is just another named argument:

-- tests/generic/test_assert_column_is_after.sql
{% test assert_column_is_after(model, column_name, after_column) %}

select *
from {{ model }}
where {{ column_name }} < {{ after_column }}

{% endtest %}

Read this the same way Day 3 read its own singular test: a dbt data test fails when its select returns any row at all, and the returned rows are the specific offenders. {{ model }} renders to whatever model this test is attached to in YAML — here, int_order_durations — and {{ column_name }}/{{ after_column }} render to whichever two columns that YAML names. Nothing about this SQL hardcodes placed_at or delivered_at anywhere; that's the entire point of the generic shape, identical in spirit to Day 11's dbt_utils.accepted_range taking a min_value argument instead of a hardcoded bound.

Wire it onto int_order_durations.delivered_at in a new models/intermediate/intermediate.yml:

version: 2

models:
  - name: int_order_durations
    columns:
      - name: delivered_at
        tests:
          - assert_column_is_after:
              arguments:
                after_column: placed_at

arguments: is the current dbt syntax for any extra, test-specific parameter beyond model/column_name — the same nesting Day 3 already flagged for relationships' to:/field:, not something new to today's test specifically. column_name itself never appears under arguments:: dbt supplies it automatically from the - name: delivered_at line the test is nested under.

Expected — the new test runs and passes against today's real data, named exactly the way dbt names every generic test: <test macro name>_<model>_<column_name>__<extra args>:

Now prove it actually catches something, the same style of proof Day 3 used on the planted bad rows — hand-corrupt one event directly, moving a delivered timestamp before its own order's placed timestamp:

docker compose exec -T postgres psql -U fdp -d fdp -c \
  "UPDATE raw.order_events SET occurred_at = occurred_at - interval '2 days'
   WHERE order_id = 101 AND status = 'delivered';"
uv run --project ../dbt_env dbt build --select int_order_durations mart_delivery_sla

Expected — the exact row for order 101 comes back as the failure, because the test's own select * returns the offending record itself, not just a count:

assert_column_is_after_int_order_durations_placed_at__delivered_at ... [FAIL 1 in 0.02s]

Done. PASS=0 WARN=0 ERROR=0 FAIL=1 SKIP=0 TOTAL=1

Undo the corruption before moving on (UPDATE raw.order_events SET occurred_at = occurred_at + interval '2 days' WHERE order_id = 101 AND status = 'delivered';), rerun, confirm PASS=1 again, then commit tests/generic/test_assert_column_is_after.sql, models/intermediate/int_order_durations.sql, models/intermediate/intermediate.yml, and the rewritten mart_delivery_sla.sql.

Where this would actually have caught something real: Kafka's at-least-once delivery (Day 6) and the consumer lag/rebalancing work since (Days 34, 37) never guarantee a producer sends statuses in order, only that each one eventually lands. A clock skew bug, a replayed test message, or a producer retrying out of order could all produce a real delivered_at earlier than its own placed_at — not a hypothetical, the exact shape of bug a grain-level not_null/unique test is structurally blind to, because both timestamps are individually valid, non-null values. Only a test that compares the two columns to each other catches it.

5 · When this was worth writing, and when it wouldn't be

Day 11 already drew the package-vs-hand-written line: reach for a package when a rule is generic enough that it isn't really about your business at all, write it by hand when it's specific to your own data. Today's rule sits one level more generic than that line suggests at first glance — "one timestamp column must come after another" has nothing food-delivery-specific in it, which raises a fair question: why not check whether a package already has this?

dbt_utils does not ship a two-column ordering test — its generic tests bound a single column (accepted_range) or check relationships to another model (relationships, extended), not a same-row comparison between two columns. That gap is common enough that it's worth checking a package first every time, and real enough here that writing five lines yourself beat adding a second package dependency for one test. The deciding question isn't "is this rule generic" alone — it's "generic, and does an already-installed, already-trusted package actually express it." When both are true, import it. When only the first is true, five lines in tests/generic/ gets you a real package-grade test without a new dependency to track.

Q: "You've used dbt's built-in tests and a package's tests — when would you write your own generic test instead of either?" A strong answer, out loud: "Built-in tests and package tests both cover genuinely generic rules — not_null, uniqueness, a value range — where someone else has already solved the exact shape I need and I'd just be re-solving it myself for no reason. I write my own generic test when the rule is still generic enough to be reusable across columns or models, but no built-in or installed package actually expresses it. In my project, nothing checks that a delivered_at timestamp comes after its own order's placed_at — that's a same-row, two-column comparison, which dbt_utils doesn't ship a test for. I wrote a five-line {% test %} macro, assert_column_is_after(model, column_name, after_column), that takes any two column names as arguments, so it's reusable the next time I add a pair of timestamps that need the same ordering guarantee — not a one-off singular test tied to this one column pair forever. The signal I'd want to give here is knowing there are really three tiers — built-in, package, and custom generic — and picking between them by how generic the rule is and whether something trustworthy already expresses it, not jumping straight to a singular test the moment a built-in test doesn't fit." The signal: naming the three-tier structure explicitly and the real reason this rule needed the custom tier — a same-row column comparison no installed test covers.

Scope line

This lesson covers writing one new custom dbt generic test ({% test %} in tests/generic/), applying it via YAML's arguments: block, and the intermediate-model refactor needed to give it a real column to test. It does not cover dbt's full macro/Jinja control-flow surface beyond the {% test %}/{% endtest %} block itself (Day 10 already covers Jinja and macros in depth), nor does it re-derive Kafka ordering/delivery guarantees (Days 6, 16, 34) beyond the one callout naming why this rule is worth having — this lesson only adds the test that would catch a violation, not the mechanism that could cause one.
