Problem Details: the error contract someone already standardized

Lesson 3 had you invent an error contract from scratch: {"error":{"code","message"}}. Lesson 7 reused it for 500s. Neither ever mentioned that the industry ran into the exact same "every API's error body looks different" problem and shipped an actual internet standard for it. Today's lesson is that standard, and the honest question of whether it should have replaced Lesson 3's shape all along.

1 · The problem Lesson 3 solved locally, and RFC 7807 solved globally

Lesson 3's framing was right: pick one error shape and use it everywhere in your API. But "everywhere in your API" is one API. A frontend calling three different backend services — yours, a payments provider, an internal auth service — meets three different bespoke error shapes, each invented the same way Lesson 3 walked you through: reasonably, in isolation, with no coordination between teams. That's the wider version of the exact problem Lesson 3 opened with ("sometimes a string, sometimes HTML, sometimes {message}") — just one level up, across organizations instead of across handlers in one codebase.

Problem Details is that coordination: one JSON shape, standardized once, so any client that already knows the standard can parse any compliant API's errors without learning that API's custom shape first.

2 · The five fields

A Problem Details body is still just JSON — nothing exotic — with a small fixed set of optional-but-conventional fields:

{
  "type": "https://example.com/errors/insufficient-stock",
  "title": "Insufficient stock",
  "status": 409,
  "detail": "Only 3 units of product 42 remain, 5 were requested.",
  "instance": "/orders/42"
}
FieldMeaning
typea URI naming the error category — the machine-readable part a client branches on, playing the same role as Lesson 3's code
titlea short, human-readable summary of that category, stable across occurrences
statusthe same HTTP status code as the response's own status line, repeated in the body so it survives a proxy or log that only kept the JSON
detaila human-readable explanation of this specific occurrence — the part that can safely mention "3 units of product 42," unlike title
instancea URI identifying this specific occurrence, often just the request path

The type field is the load-bearing one, and it's worth being precise about what kind of value it holds. It doesn't have to resolve to a real, fetchable page — the RFC explicitly allows a URI that's never dereferenced, used purely as a stable, globally-unique-by-convention name (the same trick a Go import path or an XML namespace URI plays: a URL shape chosen for its namespacing guarantee, not because anything lives there). What matters is that it's a stable identifier for "this category of problem," precise enough that https://example.com/errors/insufficient-stock can never mean two different things, the way a short string like "conflict" might drift in meaning across a codebase over months.

3 · The part that's actually new: a registered media type

Lesson 3's contract was a JSON shape, served with the same Content-Type: application/json as every success response. A client had no way to tell "this is an error in our agreed shape" from "this is just some JSON" without first parsing the body and checking for an error key. RFC 7807 registers its own media type, application/problem+json, so the Content-Type header itself announces "this body is a Problem Details error" before a single byte of JSON gets parsed. A generic HTTP client, proxy, or logging tool that has never heard of your API can still tell an error response from a success response by header alone.

Frontend-habit bridge: this is the same instinct as checking response.ok before touching response.json() — except pushed one layer earlier, into content negotiation instead of a status-code check you write yourself. A client that understands application/problem+json gets that signal for free from a header a proxy can also read, without any body-shape convention it has to already know.

4 · What it doesn't replace: your own machine-readable code

Problem Details standardizes the envelope, not your domain's vocabulary. Lesson 3's "code": "order_not_found" — a short, stable string a frontend does exact-match branching on — has no required equivalent in the five fields above; type is a URI, not a short enum string, and matching on a full URI string is clunkier for a client's switch statement than Lesson 3's bare code. The RFC's answer is that Problem Details is explicitly extensible: an API is free to add its own fields alongside the standard five.

{
  "type": "https://example.com/errors/insufficient-stock",
  "title": "Insufficient stock",
  "status": 409,
  "detail": "Only 3 units of product 42 remain, 5 were requested.",
  "code": "insufficient_stock",
  "available": 3,
  "requested": 5
}

That last block is exactly Lesson 3's instinct, unharmed: a short stable code plus whatever structured detail the specific error needs (available, requested) — just sitting inside a body whose envelope, and whose Content-Type, are now a standard instead of a one-off invention. Adopting Problem Details isn't "throw out Lesson 3's contract"; it's "wrap the same contract in a shape and header a wider ecosystem already recognizes."

5 · Where this is actually worth the switch

A single frontend talking only to one backend team's API gets little from adopting the RFC verbatim — Lesson 3's homegrown shape already does the job inside that closed pair, and rewriting every handler's error body for a standard nobody outside the team will ever check is not a strong trade. The RFC earns its keep when errors cross an organizational boundary: a public API with third-party integrators, a service mesh where a generic API gateway (Lesson 66) needs to make routing or retry decisions from error shape alone without knowing every backend's bespoke contract, or tooling (API gateways, generic HTTP client libraries, some framework error handlers) that already understands application/problem+json out of the box and can surface a useful error automatically. The decision rule is the same shape as Lesson 82's ENUM-vs-CHECK call: adopt the standard when the audience for your error format is wider than the one team that wrote it; keep the lightweight local convention when it isn't.

Q: "Have you seen or used RFC 7807 Problem Details?" A strong answer, out loud: "It's a standard JSON shape for API errors — type, title, status, detail, instance — served with its own media type, application/problem+json, so a client or proxy can tell it's a structured error before parsing the body. It doesn't replace an API's own machine-readable error code; the spec is explicitly extensible, so you'd still add your own code field and any domain-specific detail alongside the standard fields. I'd reach for it when errors cross an organizational boundary — a public API, or tooling that already expects that media type — and stick with a simpler homegrown contract for an API only my own frontend calls." The signal: knowing it's an envelope standard that coexists with your own error codes, not a replacement for them.
