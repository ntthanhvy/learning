Savepoints: rolling back part of a transaction, not all of it

Lesson 6 taught a transaction as all-or-nothing: COMMIT keeps everything, ROLLBACK discards everything, no middle option. Lesson 40's deadlock retry backstop throws away the whole transaction and starts over. Ninety-one lessons in, one real middle option between those two has never come up: undoing just the last few statements of a transaction while keeping everything before them. Today names it.

1 · The gap between "commit everything" and "discard everything"

Picture a handler that processes a batch: insert a parent order row, then loop over ten line items inserting each one. Item 7 violates a CHECK constraint (Lesson 60) — bad quantity, say. Lesson 6's transaction model gives exactly two outcomes: let the whole transaction fail and ROLLBACK, losing the order and the six good line items with it, or catch the error and keep going, which Postgres won't actually let you do — once a statement inside a transaction errors, Postgres marks the entire transaction aborted, and every statement after that point fails too, even an otherwise-valid one, until a ROLLBACK clears it.

Frontend-habit trap: a try/catch around one bad array item, skipping it and continuing the loop, is the instinctive fix — and it silently does not work inside a Postgres transaction. Catching the error in your Go code stops your program from crashing, but it does not un-abort the transaction on the database side; the very next statement you send still comes back current transaction is aborted, commands ignored until end of transaction block.

A savepoint is the actual middle option: a named marker set inside the still-open transaction, which a later rollback can return to without discarding anything issued before it.

BEGIN;
INSERT INTO orders (id, customer_id) VALUES (501, 42);

SAVEPOINT before_item;
INSERT INTO order_items (order_id, qty) VALUES (501, -3);  -- fails the CHECK constraint
-- transaction is now aborted, but only back to the savepoint
ROLLBACK TO SAVEPOINT before_item;
-- the order row is still there; try the item again correctly, or skip it
INSERT INTO order_items (order_id, qty) VALUES (501, 3);

COMMIT;  -- order row + the one good item both land; the failed attempt never did

2 · What a savepoint actually buys, and what it costs

ROLLBACK TO SAVEPOINT before_item undoes every statement issued after that marker — exactly the failed INSERT, nothing more — and leaves the transaction itself still open, still holding the order row, still committable. A plain ROLLBACK with no savepoint is the all-or-nothing option Lesson 6 already taught: it discards the entire transaction back to BEGIN, order row included. A savepoint doesn't replace that option; it adds a second, narrower one.

Plain ROLLBACKROLLBACK TO SAVEPOINT
What's undoneevery statement since BEGINevery statement since that SAVEPOINT only
What survivesnothing — transaction endseverything before the savepoint; transaction stays open
Can you still COMMIT afterno — there's nothing left to commityes — commit whatever's left once ready
Typical usethe operation as a whole failedone sub-step failed; the rest should still land

A savepoint isn't free, and it isn't a second transaction. Postgres has to keep enough bookkeeping to undo back to that exact point, which means every open savepoint holds a small amount of extra internal state for as long as the transaction stays open — cheap for a handful of savepoints in a short-lived handler, but not something to set in a loop running thousands of times inside one transaction without a reason. And it's strictly a single-transaction trick: once you call COMMIT or ROLLBACK on the outer transaction, every savepoint inside it is gone along with it. There's no such thing as a savepoint that outlives its own transaction.

3 · Where this actually shows up: a Go batch handler

A worker inserting a batch of line items, skipping any row that fails validation instead of discarding the whole batch, is the shape this earns its keep in — the sql.Tx equivalent of the manual SQL above, using SAVEPOINT/RELEASE SAVEPOINT/ROLLBACK TO SAVEPOINT as plain SQL statements sent through the same connection:

// insertItemsSkippingBad inserts each item inside its own savepoint, so one
// row failing a CHECK constraint only loses that row -- the transaction as a
// whole, and every already-inserted item, survives.
func insertItemsSkippingBad(ctx context.Context, tx *sql.Tx, orderID int64, items []Item) (inserted, skipped int, err error) {
    for _, it := range items {
        if _, err := tx.ExecContext(ctx, `SAVEPOINT before_item`); err != nil {
            return inserted, skipped, fmt.Errorf("set savepoint: %w", err)
        }
        _, insErr := tx.ExecContext(ctx,
            `INSERT INTO order_items (order_id, qty) VALUES ($1, $2)`, orderID, it.Qty)
        if insErr != nil {
            // this item's statement failed -- roll back only to the savepoint,
            // not the whole transaction, then move on to the next item
            if _, rbErr := tx.ExecContext(ctx, `ROLLBACK TO SAVEPOINT before_item`); rbErr != nil {
                return inserted, skipped, fmt.Errorf("rollback to savepoint: %w", rbErr)
            }
            skipped++
            continue
        }
        if _, err := tx.ExecContext(ctx, `RELEASE SAVEPOINT before_item`); err != nil {
            return inserted, skipped, fmt.Errorf("release savepoint: %w", err)
        }
        inserted++
    }
    return inserted, skipped, nil
}

RELEASE SAVEPOINT on the success path discards the marker itself (there's nothing left to roll back to, so keeping it around would be pure waste) without touching the row it just inserted. The caller still decides whether to Commit() or Rollback() the outer transaction once the loop finishes — a savepoint changes what one bad statement does to everything around it, not who makes the final call.

Q: "Your batch-import job inserts a thousand rows inside one transaction. Row 400 fails a constraint, and right now that kills the whole import. How would you fix it?" A strong answer, out loud: "Postgres aborts the entire transaction the instant one statement inside it errors — catching that error in application code doesn't undo the abort, the very next statement on that connection still fails until something rolls back. The fix is wrapping each row's insert in its own SAVEPOINT: if that row's statement fails, ROLLBACK TO SAVEPOINT undoes just that one insert and leaves every earlier row, and the open transaction, intact. RELEASE SAVEPOINT cleans up the marker on the success path. I'd still decide separately whether the whole import commits or rolls back at the end — savepoints control what one bad row does, not the final commit decision." The signal: naming that a transaction-wide abort is Postgres's actual behavior on any statement error, not a configuration choice, and that a savepoint is the fix at the per-statement level, not a replacement for the outer transaction.

Scope line

Postgres implements nested-transaction-like behavior as explicit SAVEPOINT/RELEASE/ROLLBACK TO statements rather than true nested transactions — some ORMs simulate "nested transactions" by generating savepoints under the hood automatically, but that's a library convenience layered on this same mechanism, not a different database feature, and MISSION.md's ORM exclusion means this lesson stops at the plain SQL. Multi-statement locking order (Lesson 40) and isolation-level conflicts (Lesson 37) still apply exactly as before inside a transaction that also uses savepoints — a savepoint changes what gets undone on a per-statement failure, not how concurrent transactions see each other.
