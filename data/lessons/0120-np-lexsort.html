np.lexsort(): multi-key sort positions, keys passed in a backwards-looking order

Lesson 119 closed with two standing candidates from a fresh curriculum/glossary scan: np.lexsort() and np.partition()/argpartition(). A fresh grep of every lesson, practice file, and the glossary reconfirms both are still genuinely untaught — today picks np.lexsort(): it is the direct multi-key sibling of Lesson 73's single-key argsort(), and a first probe turned up a parameter-order convention sharp enough to get backwards in an interview without ever triggering an error.

1 · The gap: argsort() answers "where" for one key, lexsort() answers it for several

Lesson 73's argsort() returns the positions that would sort a single array. Real sorting tasks often need a tiebreaker — sort by last name, and within matching last names, by first name. np.lexsort() is that function — it takes a tuple of same-length key arrays and returns one array of positions, exactly like argsort(), but resolving ties across however many keys are given. Confirmed directly (numpy 2.5.4), sorting a small name table by last name, then first name as tiebreaker:

import numpy as np
import pandas as pd

last_name  = np.array(["Tran", "Tran", "Le", "Le"])
first_name = np.array(["Binh", "An", "Chi", "An"])

order = np.lexsort((first_name, last_name))
# order = array([3, 2, 1, 0])
last_name[order]   # array(['Le', 'Le', 'Tran', 'Tran'])
first_name[order]  # array(['An', 'Chi', 'An', 'Binh'])  -- within "Le": "An" before "Chi"

The result groups both "Le" rows together, both "Tran" rows together, and breaks the "Le" tie correctly by first name ("An" before "Chi") — exactly the split-ties-by-the-next-key behavior a multi-column sort needs.

2 · The sharp catch: the LAST key passed is the PRIMARY sort key

Confirmed directly against the official NumPy docs, matching its own worked example exactly: np.lexsort((first_name, last_name)) sorted by last_name first — but last_name was the second item in the tuple, not the first. The rule, stated plainly in the official docs: "the last key in the sequence is used for the primary sort order; ties are broken by the second-to-last key, and so on." The tuple order is backwards from how most people would guess reading it left to right. Confirmed directly by swapping the tuple order and watching the sort key flip:

# swapped tuple order: first_name is now LAST -> first_name becomes PRIMARY
wrong_for_our_goal = np.lexsort((last_name, first_name))
first_name[wrong_for_our_goal]  # array(['An', 'An', 'Binh', 'Chi'])  -- sorted by FIRST name now, not last

Confirmed directly, this exact tuple order matches pandas.DataFrame.sort_values(by=[...])'s own left-to-right reading exactly — once the tuple is built right-to-left (primary key last):

df = pd.DataFrame({"last_name": last_name, "first_name": first_name})
sv = df.sort_values(by=["last_name", "first_name"])
sv.index.tolist()        # [3, 2, 1, 0]
order.tolist()            # [3, 2, 1, 0]  -- IDENTICAL positions

sort_values(by=["last_name", "first_name"]) reads primary-first, left to right — the natural order. np.lexsort((first_name, last_name)) needs the identical two keys passed in the opposite order to produce the same result. Getting this backwards never raises an error; it silently sorts by the wrong column first, which is exactly what makes it an interview-worthy trap rather than a one-line footnote.

3 · Single key: lexsort() collapses to exactly argsort()

Confirmed directly: wrapping a single array in a one-element tuple gives byte-identical output to Lesson 73's argsort() on that same array — lexsort() is a strict generalization, not a different algorithm:

x = np.array([30.0, 10.0, 20.0])

np.lexsort((x,))   # array([1, 2, 0])
np.argsort(x)        # array([1, 2, 0])  -- IDENTICAL

The trailing comma inside (x,) is required — Python's own single-element-tuple syntax, not a lexsort() quirk — since lexsort() always expects a sequence of keys, even a sequence of one.

4 · No ascending= keyword, and strings can't use argsort()'s negation trick

Confirmed directly: like argsort(), lexsort() takes no ascending= parameter at all — passing one raises TypeError: lexsort() got an unexpected keyword argument 'ascending'. Lesson 73's fix for argsort() was negating the numeric values first. That trick fails outright on strings: -last_name raises UFuncTypeError, since negation has no meaning for text. The confirmed working alternative for a string key: pd.factorize(..., sort=True) turns the strings into sorted dense integer codes first (Lesson 68), and those codes negate cleanly:

codes, uniques = pd.factorize(last_name, sort=True)
# codes = array([1, 1, 0, 0]), uniques = Index(['Le', 'Tran'])

order_desc = np.lexsort((first_name, -codes))   # descending last_name, ascending first_name tiebreak
last_name[order_desc]   # array(['Tran', 'Tran', 'Le', 'Le'])
first_name[order_desc]  # array(['An', 'Binh', 'An', 'Chi'])

df.sort_values(by=["last_name", "first_name"], ascending=[False, True]).index.tolist()
# [1, 0, 3, 2]  -- IDENTICAL positions to order_desc above

5 · NaN sorts to the end, matching sort_values() exactly — and mismatched shapes raise ValueError

Confirmed directly, and confirmed absent from the official docs page (no mention of NaN handling at all): a NaN in any key sorts to the end of that key's ordering, the same placement argsort() already uses (Lesson 73) and the same placement DataFrame.sort_values() uses by default — all three agree, so this is not a trap the way Lessons 118/119's NaN findings were:

primary = np.array([1.0, np.nan, 1.0, np.nan, 2.0])
secondary = np.array([5, 1, 3, 9, 0])

np.lexsort((secondary, primary)).tolist()   # [2, 0, 4, 1, 3]
pd.DataFrame({"primary": primary, "secondary": secondary}) \
  .sort_values(by=["primary", "secondary"]).index.tolist()
# [2, 0, 4, 1, 3]  -- IDENTICAL, NaN rows pushed last in both

Confirmed directly: keys of mismatched length raise ValueError: all keys need to be the same shape immediately — never a silent broadcast or truncation.
