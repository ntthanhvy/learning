struct: packing and unpacking binary data

Every format lesson so far has been text-shaped: CSV rows, JSON objects, Python literals. Some data isn't text at all — a sensor log, a network protocol header, a legacy file format — just a fixed sequence of raw bytes, no delimiters, no quotes. The struct module is the stdlib's answer to that: it packs Python values into exact bytes, and unpacks them back, with byte-for-byte control over the layout.

1 · A format string describes the byte layout

struct.pack(fmt, *values) takes a short format string and the values to encode, and returns a bytes object laid out exactly as the format says. struct.unpack(fmt, data) reverses it, always returning a tuple:

import struct

packed = struct.pack(">ihb", 1000, -5, 3)
print(packed)              # b'\x00\x00\x03\xe8\xff\xfb\x03' -- confirmed live, 7 raw bytes
print(struct.unpack(">ihb", packed))
# (1000, -5, 3) -- confirmed live, exact values back as a tuple

Each letter in "ihb" names one field's type and fixed width: i is a 4-byte signed int, h a 2-byte signed short, b a 1-byte signed char — the exact same single-letter codes C uses for these widths. The leading > is a byte-order marker, covered next. struct.calcsize(fmt) answers "how many bytes will this format take?" without packing anything — calcsize(">ihb") returns 7, matching the length of packed above exactly.

2 · Byte order: the same number, two different byte sequences

The same integer can be laid out two ways: most-significant byte first (big-endian), or least-significant byte first (little-endian). The same Python integer produces visibly different bytes depending on which one the format string picks:

print(struct.pack("<i", 1))   # b'\x01\x00\x00\x00' -- confirmed live, little-endian: low byte first
print(struct.pack(">i", 1))   # b'\x00\x00\x00\x01' -- confirmed live, big-endian: high byte first

Network protocols and most file formats fix big-endian (>) as "network byte order," precisely so two machines with different native byte orders still agree on what the bytes mean. Omitting the prefix uses the machine's own native order instead — fine for a file this same program will read back, risky for anything written on one machine and read on another.

3 · Native mode also adds padding — "=" turns it off

Leaving the prefix off doesn't just pick native byte order — it also lets the C compiler's alignment rules insert padding bytes between fields, the same padding a C struct gets for faster memory access. That padding can make the packed size bigger than the fields' widths add up to:

print(struct.calcsize("ci"))    # 8 -- confirmed live: 1-byte char + 3 padding bytes + 4-byte int
print(struct.calcsize("=ci"))   # 5 -- confirmed live: "=" forces standard size, no padding at all

This is the detail easiest to get burned by: a format string that works while reading back a file on the same machine can silently include padding bytes a different machine's compiler wouldn't add. A format prefix — >, <, or = — always selects standard size with no padding — any format string meant to be read back portably should always start with one of the three.

4 · A realistic shape: decoding a tiny binary record

Put together, this is enough to read a small fixed-layout record — a 4-byte magic tag, a version byte, a count, and a float average, the shape a simple binary log format might use:

FMT = ">4sBHf"   # magic(4 bytes) + version(1) + count(2) + average(4), big-endian, no padding
print(struct.calcsize(FMT))   # 11 -- confirmed live

record = struct.pack(FMT, b"TEMP", 1, 42, 21.5)
magic, version, count, avg = struct.unpack(FMT, record)
print(magic, version, count, avg)
# b'TEMP' 1 42 21.5 -- confirmed live, exact round trip

4s means "4 raw bytes, fixed width" — not a Python string, a bytes slice padded or truncated to exactly that length. A mismatched buffer size is the most common failure here, and struct is explicit about it rather than returning silently wrong data:

try:
    struct.unpack(">i", b"\x00\x00")   # only 2 bytes given, format needs 4
except struct.error as e:
    print("rejected:", e)
# rejected: unpack requires a buffer of 4 bytes -- confirmed live, struct.error, not silent garbage

struct.error is the one exception type this module raises, for both a bad format string and a wrong-sized buffer — worth catching specifically around any unpack() call fed bytes read from a file or a socket, since real-world data gets truncated.

Where pandas/NumPy go from here: NumPy has its own, much richer answer to "describe a fixed byte layout" — the dtype system backing every array, including structured dtypes with named fields. Not demonstrated here; building or reading one is data/'s job, and this is the only sentence in this lesson naming it.
