Kafka static membership: when both members overrun their windows at once

Today's tangible win: Day 72's single-overrun test, rerun with both statically-identified consumers kept down past their own session.timeout.ms at the same time — and your own kafka-consumer-groups.sh --describe output proving the case Day 72 couldn't show: no survivor left to absorb anything, every partition sitting fully unconsumed for the whole gap, then one ordinary rebalance (not two) once the first consumer rejoins.

Before today — confirm Day 72's single-overrun shape still works: today reruns Day 68's two-consumer script with both sleeps lengthened past the grace window instead of just one. It edits no file. Start from a clean check:

docker compose exec kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --describe --topic order_events

1 · The gap Day 72 named and left open

Day 72 proved one precise thing: when warehouse-loader-2 stays down past its own 45-second session.timeout.ms, the coordinator reassigns its partition(s) to warehouse-loader-1 — the surviving consumer never pauses, because the coordinator's bookkeeping is per-member, not group-wide. That lesson's own scope line named exactly what it didn't run: "both members overrunning their windows at the same time." The question matters because Day 72's reassuring result — a healthy neighbor keeps the lights on while one member times out — quietly depends on there being a healthy neighbor at all. What does "per-member bookkeeping" actually mean when there is no survivor, even briefly?

This isn't a new mechanism to learn. Day 66 already established that each static member's session.timeout.ms is its own independent clock, with no group-wide timer sitting above it. Today just takes that fact seriously and runs two of those clocks out at once instead of one.

2 ·

Chain three already-confirmed facts instead of guessing at a new one:

Already confirmedSource
Each static member's session.timeout.ms is its own independent clock — there is no shared, group-wide grace timer.Day 66, Section 2
A member's expiry only ever reassigns that member's own partitions, to whichever members are currently present.Day 72, Section 2
Static membership changes the outcome of a timely rejoin only; it never reserves a slot forever once the window has actually closed.Day 72, Section 2

Run those three facts forward to the case where both members are down past their own windows. warehouse-loader-1's window expires first (say it was killed first); the coordinator reassigns its partitions — but the only other "member" is warehouse-loader-2, which by then is also already dead or about to expire. There is nothing present to reassign to. The second expiry doesn't trigger a second, symmetric reassignment either, for the same reason: reassignment hands a partition to a currently-present member, and there is no currently-present member left. The group's own membership count has dropped to zero, and a partition with no consumer isn't reassigned to nobody — it just sits, fully unconsumed, until somebody shows up.

Bridge from Day 72: Day 72's key sentence was "there is no sense in which a second static member's presence buys more time for a first one that's running late." Today's finding is the sharper, specific case of that: a second member doesn't just fail to buy time for the first — once both are gone, there's no member left for the coordinator to even hand a partition to. "Per-member bookkeeping" was never a promise that the group stays available; it only ever promised that one member's own fate doesn't leak into a different member's own entry. With zero members, there's no entry left that isn't affected.

3 · Build: kill both consumers, let both windows expire, watch the single rejoin that follows

Reuse Day 68's script and env-var shape exactly — same INSTANCE_ID environment variable, same 45-second session.timeout.ms. The only change from Day 72: kill both processes, and bring back only one of them after both windows have closed, to see what a single rejoin into an empty group actually produces:

uv run --with confluent-kafka python3 scripts/produce_order_events.py

INSTANCE_ID=warehouse-loader-1 uv run --with confluent-kafka --with "psycopg[binary]" python3 scripts/consume_order_events.py &
CONSUMER_A=$!
INSTANCE_ID=warehouse-loader-2 uv run --with confluent-kafka --with "psycopg[binary]" python3 scripts/consume_order_events.py &
CONSUMER_B=$!
sleep 3
docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group warehouse-loader

kill -9 $CONSUMER_A $CONSUMER_B
sleep 50   # past the 45s session.timeout.ms for BOTH members this time
docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group warehouse-loader

INSTANCE_ID=warehouse-loader-1 uv run --with confluent-kafka --with "psycopg[binary]" python3 scripts/consume_order_events.py &
CONSUMER_A=$!
sleep 3
uv run --with confluent-kafka python3 scripts/produce_order_events.py   # fresh traffic to prove the lone rejoin now owns everything
sleep 3
docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group warehouse-loader

Expected across the three --describe calls — the ordinary split, then a group with no current owner for any partition, then a single rejoin claiming all three:

Read call 2 as today's actual new evidence: every CURRENT-OFFSET is frozen exactly where call 1 left it, and every CONSUMER-ID/HOST/CLIENT-ID column is blank — not "reassigned to nobody," literally no owner recorded, because the coordinator has nobody present to record. Read call 3 against call 2: a single rejoin produces a single rebalance that hands the lone rejoiner all three partitions at once, including partition 1, which it never owned before today. LAG on partition 1 (4, in the row above) is the direct cost of the empty-group gap: four events arrived while nobody was consuming anything, and warehouse-loader-1 only catches up to them after claiming ownership it never had under Day 68's or Day 72's single-overrun version of this test. 4 · The genuinely new finding: availability, not just ownership bookkeeping, is group-wide

Days 66, 68 and 72 each confirmed that ownership bookkeeping is per-member — one member's expiry, reassignment or late rejoin never touches a healthy neighbor's own entry. Today's result doesn't contradict that; it sits one level below it. Bookkeeping can stay perfectly per-member while availability collapses group-wide, for the simple reason that availability was never a property any single member's entry carried on its own — it was always a count across every member's entry at once. Per-member bookkeeping only guarantees a healthy member's own slot is undisturbed by a neighbor; it says nothing about what happens when there are no healthy slots left to disturb.

This is the same shape as Day 50's producer-side finding, from the other end of the pipe: BufferError showed that one slow consumer's backpressure becomes the producer's problem, not a fact contained entirely on the consumer side. Today shows the mirror case on the consumer-group side — one member's expiry is contained, but every member expiring at once is not a sum of contained events, it's a genuinely different condition (zero coverage) that none of the per-member facts individually predicted.

Checked live this round, not against a real broker (no reachable Kafka this sandbox round, the same standing gap every recent Kafka round has named): two scratch Consumer({...}) configs, one per static identity (warehouse-loader-1, warehouse-loader-2), both sharing group.id: "warehouse-loader" and session.timeout.ms: 45000, were constructed for real this round against a freshly-installed confluent-kafka==2.16.2 client (librdkafka 2.16.0) in a scratch directory — both Consumer() calls succeeded with no config-rejection error, confirming two static identities sharing one group still construct cleanly with no special handling needed for the "both might expire" case; the client itself has no concept of "how many other members are currently down" at construction time. uv run python3 -m py_compile on that scratch file was clean. The actual claims this lesson rests on — that an empty group leaves every partition with no recorded owner until a rejoin, and that a lone rejoin into an empty group claims every partition in one rebalance rather than waiting for a second member — are Kafka's own documented group-coordinator behavior (a partition's owner is whichever member the coordinator's last rebalance assigned it to; with zero members present, the last rebalance assigned it to nobody) applied to the two-static-member case, not a live multi-process, multi-minute test this round, since no broker was reachable to run Section 3's sequence for real. Confirm all three of Section 3's --describe outputs, especially call 2's blank CONSUMER-ID columns, in your own environment before quoting the "no owner recorded" claim verbatim in an interview.

Q: "You've shown that static membership's bookkeeping is per-member, so one consumer's restart doesn't disturb another's. Does that mean the group stays available as long as each member's own window is short enough?" A strong answer, out loud: "Not quite — per-member bookkeeping and group availability are two different claims. Bookkeeping being per-member means one member's own expiry or rejoin never touches a different member's own assignment, and I confirmed that back on Day 72 with one survivor staying untouched while its neighbor timed out. But if every member's window expires at the same time, there's no survivor left for bookkeeping to protect — the coordinator just has zero members present, and every partition sits with no recorded owner until somebody rejoins. I ran exactly that: killed both statically-identified consumers, let both windows expire, and the describe output showed every partition with a blank consumer column, offsets frozen, until one consumer came back and claimed all three partitions in a single rebalance. The lesson is that per-member isolation protects a healthy member from a sick one — it was never a promise that the group has a healthy member at all. Sizing session.timeout.ms generously helps any one member survive a slow restart, but it doesn't help if your deploy process kills every member at once." The signal: distinguishing bookkeeping isolation (per-member, already proven) from availability (a property of the whole group's current membership count, which can hit zero regardless of how isolated the bookkeeping is).

Scope line

This lesson covers two statically-identified consumers both overrunning their own session.timeout.ms at the same time, in the same group Days 66/68/72 built, reasoned from Kafka's documented per-member expiry behavior chained across both members and confirmed live only as valid consumer configs against the installed client — not against a real broker's actual empty-group and single-rejoin timing this round. It does not cover more than two members (the chain of reasoning generalizes, but this project's warehouse-loader group has never run a third instance), the broker-side group.max.session.timeout.ms bound that could clamp an unreasonably large client-side value (broker tuning, past this course's working-level Kafka scope per MISSION.md), or what a consumer mid-transaction on its Postgres write does during the gap — this project's ON CONFLICT (event_id) DO NOTHING write (Day 6) is a single statement, not a multi-step transaction, so there is no partially-committed state for an empty-group gap to interact with here, but a pipeline with a longer transaction per batch would need to ask that question for real.
