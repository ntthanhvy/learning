Unit vs. integration tests: where the line actually is

Lesson 42 built a Querier interface and a fake so a query function could run in a test with zero network calls — but never said which of your functions deserve that treatment versus a real database. Today: the actual line between a unit test and an integration test on the backend, and why frontend testing habits don't transfer cleanly across it.

1 · The frontend habit that doesn't map cleanly

Frontend testing mostly asks one question: does this component render the right thing for these props? The unit is the component; a fake API response is just a JSON fixture, and almost every test looks the same shape. Backend code splits into two genuinely different kinds of logic, and treating them the same way is the actual mistake — not "not writing tests," which Lesson 1 already assumed the reader wouldn't need convincing about.

Some backend code is a decision with no I/O in it at all: is this account eligible for suspension, does this discount apply, is this the terminal state for an order. Other backend code's entire job is talking to Postgres correctly: does this query return the right rows, does this constraint actually reject what it should, does this transaction actually roll back on error. A unit test is the right tool for the first kind; it is structurally the wrong tool for the second, no matter how cleverly the fake is written.

The frontend equivalent you already own. This is the same split as testing a pure formatCurrency(cents) helper with Jest versus testing that a Cypress flow actually submits a form and updates a real page — one needs no browser at all, the other needs the real thing or nothing meaningful is verified. Backend code has the identical split; it's just less visible because "the real thing" is a database instead of a rendered DOM.

2 · The concrete line: does correctness live inside SQL?

Lesson 45's version of the question Lesson 42 left open: give SuspendDelinquentAccount below an AccountStore interface exactly like Lesson 42's Querier. Its own logic — the 30-day eligibility rule — has no SQL in it at all, so a fake satisfying the interface is not a shortcut, it's the correct test for that logic specifically.

// AccountStore names only the methods the business logic actually needs --
// the same Lesson 42 interface shape, here used to draw the unit/
// integration boundary instead of the pool-vs-transaction one.
type AccountStore interface {
    Suspend(ctx context.Context, accountID int64) error
}

var ErrAlreadySuspended = errors.New("account already suspended")

// SuspendDelinquentAccount is the business logic under test: real logic
// worth a fast unit test, with no SQL of its own.
func SuspendDelinquentAccount(ctx context.Context, store AccountStore, accountID int64, overdueDays int) error {
    if overdueDays < 30 {
        return fmt.Errorf("account %d not yet eligible: %d days overdue", accountID, overdueDays)
    }
    if err := store.Suspend(ctx, accountID); err != nil {
        return fmt.Errorf("suspend account %d: %w", accountID, err)
    }
    return nil
}

// fakeAccountStore is the in-memory double a unit test hands
// SuspendDelinquentAccount -- no network, no real database, per Lesson 42.
type fakeAccountStore struct {
    suspended map[int64]bool
}

func (f *fakeAccountStore) Suspend(ctx context.Context, accountID int64) error {
    if f.suspended[accountID] {
        return ErrAlreadySuspended
    }
    f.suspended[accountID] = true
    return nil
}

A unit test of SuspendDelinquentAccount catches a wrong eligibility cutoff (29 vs. 30 days) instantly, on every commit, with no database running. But it proves nothing about whether the real Suspend implementation's SQL actually works — that method's whole job is the SQL, and a fake can't verify SQL, only agree to return whatever the test told it to return. That's the line: if the correctness question is "did I write the right SQL / does this constraint fire / does this transaction commit atomically (Lesson 6)," a fake can only hide the answer, not test it.

3 · Integration tests: a real database, on purpose

An integration test runs the real pgAccountStore.Suspend against a real Postgres instance — not production, a disposable test database — and checks the row actually changed. It's slower (a real connection, Lesson 18's pool machinery, a real round trip) and needs infrastructure a pure unit test doesn't, but it's the only test that can catch a typo'd column name, a constraint (Lesson 38) firing when it shouldn't, or an isolation-level surprise (Lesson 37) — none of which a fake, however carefully written, has any way to know about.

type Querier interface {
    Exec(ctx context.Context, sql string, args ...any) error
}

type pgAccountStore struct {
    db Querier
}

// Suspend's entire job IS the SQL -- exactly the part a fake cannot verify.
func (s *pgAccountStore) Suspend(ctx context.Context, accountID int64) error {
    return s.db.Exec(ctx, `UPDATE accounts SET status = 'suspended' WHERE id = $1`, accountID)
}

The standard trick for keeping these fast and independent: wrap each integration test in a real transaction (Lesson 6) and roll it back at the end instead of committing — the test writes real rows through real SQL, sees real constraint behavior, and leaves the database exactly as it found it, so a second test run never trips over leftover data from the first. Only the outer test process ever calls ROLLBACK instead of COMMIT; the code under test has no idea it's being tested at all.

Unit testIntegration test
What it needsNothing but the process itself — a fake satisfies the interfaceA real (test) Postgres instance, a real connection
SpeedMilliseconds, runs on every saveSeconds, usually runs in CI or on demand
What it actually provesThe decision logic is correct, given whatever the fake returnsThe SQL, constraints, and driver calls are correct against a real engine
What it cannot catchA wrong query, a missing constraint, a transaction bugNothing structurally — but a wrong eligibility rule still needs a unit test to isolate cheaply

4 · The ratio, and the mistake to avoid

Real backend code is usually mostly decisions with a thin data-access layer underneath — so most tests should be unit tests against fakes, with a smaller number of integration tests specifically targeting the query/constraint/transaction layer where correctness genuinely depends on the real engine. The mistake in both directions is real: unit-testing everything with a mocked database (Lesson 42's fake stops being a testing shortcut and starts silently asserting "my mock behaves like Postgres," which nobody verified), or integration-testing everything against a real database (every eligibility-rule test now needs a live Postgres connection, turning a millisecond check into a multi-second one for logic that never touched SQL). Neither extreme is really about correctness — it's about which line a piece of code sits on, decided once per function, not once per test suite.

Q: "How do you decide whether a piece of backend code needs a unit test or an integration test?" A strong answer, out loud: "I look at where the correctness question actually lives. If it's a decision — is this account eligible, does this discount apply — a unit test against a fake dependency is faster and just as trustworthy, because the fake only needs to satisfy an interface, not behave like Postgres. If the function's whole job is the SQL itself — a query, a constraint, a transaction boundary — a fake can't verify that at all, so it needs an integration test against a real, disposable test database, usually wrapped in a transaction that gets rolled back instead of committed so tests stay independent. Most of a codebase is the first kind, with integration tests concentrated on the data-access layer specifically." The signal: naming what a fake cannot prove, not just "unit tests are fast, integration tests are slow."
