Environments & pyproject.toml

Every practice file so far has run with uv run python3 practice/NN_x.py without a second thought. Today: what that command is actually doing, why it never touches a system-wide Python install, and how to read the one file — pyproject.toml — that names a project and its dependencies. Direct follow-on to Day 9's project-layout sketch, which left pyproject.toml as "tomorrow's job."

Bridge from SQL: think of a Python virtual environment the way you'd think of a separate database per project instead of one shared schema everyone writes tables into — isolating dependencies is the same motivation as isolating data: two projects wanting different, conflicting versions of the same thing must never collide.

1 · Why isolation: the collision problem

Suppose Project A needs requests version 2.10 and Project B, on the same machine, needs version 2.31 with breaking changes since 2.10. Installing packages "globally" — one shared location for the whole machine — means only one version of requests can exist at a time; installing B's version breaks A. A package manager like uv solves this by giving every project its own private directory holding its own interpreter and its own installed packages — nothing is shared, so nothing collides.

2 · uv run: what actually happens

Every practice file in this course has been launched the same way:

cd ~/learning/python && uv run python3 practice/09_modules_imports_and_layout.py

uv run does three things before your code ever executes: (1) finds or creates a virtual environment for this project — a .venv/ folder, created the first time it's needed; (2) makes sure every dependency the project declares is installed inside that .venv/, installing anything missing; (3) runs python3 from inside that environment, not whatever python3 the operating system happens to have on its own path. This is exactly why every practice file so far has needed no separate "install first" step — uv run already did it, and because these files are standard-library only, step 2 has had nothing to install.

3 · pyproject.toml: the project's own name tag

A pyproject.toml file sits at a project's root and answers one question: what is this project, and what does it need to run? A minimal one looks like:

[project]
name = "sales-pipeline"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = [
    "httpx>=0.27",
    "pydantic>=2.0",
]

[dependency-groups]
dev = ["pytest>=8.0"]

dependencies lists what the running program itself needs — the two packages Phase 2b's backend work will add. A separate dev group holds tools only a developer needs, like pytest, never installed for an end user running the finished program. This course's own practice files have had an empty dependencies list the whole time, which is precisely why uv run python3 practice/x.py has never needed a --with flag — there was nothing to add.

4 · Adding a dependency and reading the lock file

uv add httpx does two things: appends "httpx>=0.27" (or whatever the current version resolves to) into pyproject.toml's dependencies list, and writes the exact resolved versions of httpx and everything it depends on into a second file, uv.lock. pyproject.toml states loose, human-chosen constraints ("0.27 or newer"); uv.lock pins the precise versions actually installed, so a teammate — or CI — running uv sync against the same lock file gets byte-identical dependency versions, not just "something matching the constraint." pyproject.toml is meant to be hand-edited occasionally; uv.lock is generated and normally left alone.

5 · uv run --with: a one-off dependency, no file changes

Occasionally a script needs a package without committing to it project-wide — uv run --with rich python3 scratch.py installs rich into a temporary environment for that one run only, touching neither pyproject.toml nor uv.lock. Every practice file's documented run command in this course has deliberately never used --with, which is itself a signal: standard-library-only code needs nothing beyond what uv run python3 already provides on its own.

6 · Where this lands in the layout Day 9 sketched

Day 9 ended with an unmanaged picture of a project folder. Today fills in the piece it deliberately left blank:

myproject/
    pyproject.toml      # today: name, version, dependencies — read/write with uv
    uv.lock              # today: exact resolved versions — generated, don't hand-edit
    .venv/                # today: the isolated environment uv run uses automatically
    src/
        mypkg/
            __init__.py
            parsing.py
    tests/
        test_parsing.py
Where pandas goes from here: adding pandas to a real project is exactly uv add pandas — one line in dependencies, resolved and locked the same way as any other package. Not demonstrated further here; using the library itself stays data/'s job.
