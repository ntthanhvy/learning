between(): a readable range filter, clip()'s filtering sibling

Lesson 35's teaser named two remaining candidates from Lesson 34's original scan: between() and combine_first(). Picked between(): it's the higher interview-frequency of the two (a range-filter one-liner comes up constantly, while combine_first() is a niche fillna-from-another-Series variant closer to Lesson 3's/Lesson 21's territory already covered), and it pairs directly with Lesson 35's clip() — same "is this value inside [lower, upper]" shape, but between() answers it as a boolean mask for filtering instead of bounding the value itself.

1 · The problem: a range check people write longer than it needs to be

"Orders between $50 and $150" is one of the most common filter shapes in any wrangling task — and the boolean-mask spelling for it, (s >= 50) & (s <= 150), is correct but easy to get wrong (missing parens around each comparison is a classic bug, since & binds tighter than >= in Python). between() is the named shortcut for exactly this: one call, both bounds, no parens to get wrong.

On this course's cleaned 4-row slice (An 120.0/01-05, An 42.0/01-10, Binh 35.5/01-06, Binh 180.0/01-09):

clean["amount"]
# 0    120.0
# 1     42.0
# 2     35.5
# 3    180.0

2 · between(lower, upper): a boolean mask, not a filtered result

clean["amount"].between(50, 150)
# 0     True   # 120.0 is inside [50, 150]
# 1    False   # 42.0 is below 50
# 2    False   # 35.5 is below 50
# 3    False  # 180.0 is above 150

Unlike clip() (Lesson 35), which returns the SAME shape with values pulled inside the range, between() returns a boolean mask — you still filter with it, exactly like any other comparison:

clean[clean["amount"].between(50, 150)]
#   order_id customer  amount  order_date
# 0        1       An   120.0  2026-01-05

This is the direct pandas spelling of SQL's WHERE amount BETWEEN 50 AND 150 — same name, same inclusive-both-ends default, same meaning.

3 · Exactly the same mask as the two-comparison version

series.between(a, b) is confirmed identical, element for element, to (series >= a) & (series <= b) — hand-verified on this slice, both give [True, False, False, False] for between(50, 150). between() doesn't do anything the boolean-mask version couldn't already do; it's purely a readability and typo-safety win, the same relationship Lesson 35's clip() has to a hand-written nested np.where().

4 · inclusive=: which end(s) count as "in range"

The default includes both bounds (inclusive="both"). Three other modes narrow that, useful when a range boundary is exclusive on purpose (a discount tier that starts strictly ABOVE a threshold, for example):

amounts = clean["amount"]  # [120.0, 42.0, 35.5, 180.0]
amounts.between(42, 120, inclusive="both")     # [True, True, False, False]  -- 42 and 120 both count
amounts.between(42, 120, inclusive="neither")  # [False, False, False, False] -- neither 42 nor 120 counts
amounts.between(42, 120, inclusive="left")     # [False, True, False, False]  -- only the 42 (lower) match counts
amounts.between(42, 120, inclusive="right")    # [True, False, False, False]  -- only the 120 (upper) match counts

SQL has no built-in equivalent to inclusive= — BETWEEN is always both-inclusive in standard SQL, so an exclusive-bound range there has to fall back to plain >/< comparisons instead.

5 · between() works on dates too

between() isn't limited to numbers — it works on any orderable dtype, including datetime columns (Lesson 32's .dt territory), for a "date range" filter:

dates = pd.to_datetime(clean["order_date"])
dates.between("2026-01-06", "2026-01-09")
# 0    False   # 01-05 is before the range
# 1    False   # 01-10 is after the range
# 2     True   # 01-06 -- Binh's first order
# 3     True  # 01-09 -- Binh's second order

pandas parses the string bounds against the Series' own datetime dtype automatically — no separate pd.to_datetime() call needed on the bounds themselves.

6 · The gotcha: NaN never matches, in or out

Continuing this course's "no crash, quietly wrong" family since Lesson 19: a NaN value in the Series being tested is neither inside nor outside the range — between() quietly returns False for it, same as any other comparison against NaN, never raising and never separately flagging it:

s = pd.Series([10.0, np.nan, 100.0])
s.between(0, 200)
# 0     True
# 1    False   # NaN -- not "in range", not "out of range" either -- just False
# 2     True

A row with a missing value silently disappears from a between()-filtered result — indistinguishable, by looking at the filtered output alone, from a row that was genuinely outside the range. Same reflex as every gotcha since Lesson 19: know your NaN count before filtering, don't assume a shorter result means "fewer matches," it might mean "some rows were unmeasurable."

Q: "How would you filter a column to a value range, and what's a subtlety to watch for?" A strong answer, out loud: "series.between(lower, upper) — it's the readable, harder-to-typo spelling of (series >= lower) & (series <= upper), both give the identical boolean mask, so I'd still wrap it in df[...] to actually filter. It defaults to inclusive on both ends, same as SQL's BETWEEN, but inclusive= lets me drop either or both ends if the range is meant to be exclusive there — SQL has no direct equivalent for that, you'd fall back to plain > / < comparisons. It also works on datetime columns for a date-range filter, not just numbers. One gotcha: NaN never matches, in or out — it silently comes back False, so a shorter filtered result doesn't necessarily mean fewer real matches, it might mean some rows were missing data entirely." The signal: naming the inclusive= modes and the NaN-is-always-False gotcha unprompted, not just describing the two-bound mechanic.
