1 · The name for something Day 24 already showed without naming it

Day 24's Cosmos task IDs looked like dbt_models.stg_restaurants_run and dbt_models.dim_restaurants_run — every one of them prefixed with dbt_models.. That prefix was never explained at the time, because Cosmos generates it as a side effect of a mechanism this course hadn't covered yet: a TaskGroup. Cosmos's DbtTaskGroup, confirmed this round by reading its own import, is literally a subclass of Airflow's plain TaskGroup — Day 24 was already looking at this mechanism, just through a package that builds one automatically instead of a DAG author writing one by hand.

The food_delivery_pipeline DAG has grown three real tasks since Day 7 — load_raw, dbt_build, check_dead_letters — and will likely grow more (Day 45's own closing note named a real threshold check as the next open loop on that same task). A flat list of a dozen tasks in the Airflow UI's Graph view is unreadable at a glance; a TaskGroup around the dbt-shaped tasks keeps the warehouse-build step visually and logically together without changing what actually runs.

2 · Confirmed live: grouping changes task_id, and dependency edges resolve to roots and leaves only

Built a scratch DAG shaped like a slightly larger version of this course's own — load_raw, a TaskGroup named dbt_models holding four tasks (stg_orders, stg_restaurants both feeding fct_orders, which feeds mart_delivery_sla), then check_dead_letters — and parsed it for real with Airflow's own DagBag:

all task ids:
  check_dead_letters
  dbt_models.fct_orders
  dbt_models.mart_delivery_sla
  dbt_models.stg_orders
  dbt_models.stg_restaurants
  load_raw

check_dead_letters upstream ids: ['dbt_models.mart_delivery_sla']
fct_orders upstream ids: ['dbt_models.stg_orders', 'dbt_models.stg_restaurants']

Two things confirmed directly, not assumed from the docs: every task inside the with TaskGroup(group_id="dbt_models") as dbt_models: block really does gain a dbt_models. prefix on its own task_id — exactly Day 24's dbt_models.stg_restaurants_run shape. And wiring load_raw >> dbt_models >> check_dead_letters at the DAG level does not make check_dead_letters depend on all four tasks inside the group — it resolves to a dependency on mart_delivery_sla alone, because that is the group's only task with no downstream edge inside the group (its one leaf). Airflow walks a group's internal graph to find its real roots (what load_raw actually points at) and leaves (what check_dead_letters actually waits on), and wires the outside edges to those specific tasks, not to the group as a monolithic unit.

This matters for exactly the dead-letter check Day 45 built. If check_dead_letters needs to run after the whole warehouse build, not just after one mart, the group's leaf is what it should actually depend on — today's grouping doesn't change which task that is, it only changes how the graph is drawn and labelled.

3 · Build: wrap the DAG's dbt-shaped tasks in a TaskGroup

In your food-delivery-pipeline repo, edit dags/food_delivery_pipeline.py once more. Today only changes dbt_build's placement — nothing about Day 35's on_retry_callback or Day 45's trigger_rule changes:

# new import, alongside the existing DAG and operator imports
from airflow.sdk import TaskGroup

# inside the existing `with DAG(...) as dag:` block, replacing the bare
# dbt_build = BashOperator(...) with the same task wrapped in a group:
with TaskGroup(group_id="dbt_models") as dbt_models:
    dbt_build = BashOperator(
        task_id="dbt_build",
        bash_command=f"cd {REPO_DIR}/warehouse && uv run --with 'dbt-postgres==1.11.0' dbt build --profiles-dir .",
        retries=3,
        retry_delay=timedelta(minutes=2),
        on_retry_callback=on_retry_callback,  # Day 35, unchanged
    )

# the DAG's own dependency line is unchanged in form -- dbt_models now
# stands in for dbt_build, but resolves to the same single task either way
load_raw >> dbt_models >> check_dead_letters_task

With only one task inside the group today, this round's change is mostly cosmetic — the real payoff is that check_dead_letters_task already depends on the group's one leaf, dbt_build, exactly as before, and adding a second dbt-shaped task later (a real per-model split, or a second dbt build --select step) slots into the same group without touching check_dead_letters_task's own wiring at all.

Q: "Your DAG has grown to a dozen tasks across ingestion, transformation and monitoring. How do you keep the Airflow UI readable without changing what actually runs?" A strong answer, out loud: "I'd group related tasks with a TaskGroup — it's purely an organizational and visual layer, not a scheduling one. Tasks inside the group get their task_id prefixed with the group_id, and the Graph view collapses the whole group into one expandable box. The part that actually matters for correctness is that an edge drawn to or from the group resolves to the group's real roots and leaves, not to every task inside it — so wrapping tasks in a group never silently changes a dependency that was already correct, it just makes the graph legible." The signal: naming that a TaskGroup changes presentation and the task_id namespace, not scheduling semantics — and that root/leaf resolution is the one behavior worth actually confirming rather than assuming.

Scope line

This lesson covers a plain Airflow TaskGroup: the task_id prefix it applies and how an outside edge resolves to its roots and leaves. It does not cover nested TaskGroups (a group inside a group — the same root/leaf resolution applies recursively, vocabulary only), @task_group's TaskFlow-decorator form (a thin wrapper over the same context-manager class, not a different mechanism), or Cosmos's own DbtTaskGroup internals beyond the subclass relationship already named in Section 1 — Day 24 is still the primary source for what Cosmos itself builds.
