ETags and conditional requests: a fingerprint for "did this change?"

Lesson 50's closing teaser named this as the last standing candidate from Lesson 49's search: ETag/conditional-request headers. Today — the one HTTP header that answers two different questions at once: "is my cached copy still good?" on GET, and "is the version I'm about to overwrite still current?" on PUT/PATCH/DELETE.

1 · A fingerprint of a resource's current state

An ETag ("entity tag") is a short, opaque string a server attaches to a response identifying exactly which version of that resource this is. It is usually a hash of the response body or a version number, and the server is free to choose the format — clients must never try to parse it, only compare it for equality.

GET /orders/482 HTTP/1.1

HTTP/1.1 200 OK
ETag: "a1b2c3d4"
Content-Type: application/json

{"id":482,"status":"packed","total_cents":4599}

That's the whole mechanism at its core: a fingerprint of "this resource, right now." Anything that changes the resource's content must change its ETag. Two requests that get back the same ETag are guaranteed to have seen the same state; two different ETags mean the state differs somehow, though not necessarily how.

Frontend habit: this is the backend-native version of a frontend cache key or a React Query/SWR staleTime check — except instead of the client guessing how long data stays fresh, the server states a precise fingerprint and the client asks it directly.

2 · GET + If-None-Match: "only send the body if it changed"

Once a client has an ETag from a previous response, it can send it back on the next GET using the If-None-Match header. The server recomputes the resource's current ETag and compares it to the one the client sent:

GET /orders/482 HTTP/1.1
If-None-Match: "a1b2c3d4"

HTTP/1.1 304 Not Modified
ETag: "a1b2c3d4"

If the ETags match, the resource hasn't changed since the client last saw it — the server replies 304 Not Modified with no body at all — the client already has the current data, it just keeps using its cached copy. If the resource has changed, the ETags won't match, and the server responds normally with 200 OK and the full new body plus a new ETag. This directly extends Lesson 9's caching lesson: Cache-Control tells a client how long it may trust a cached copy without asking; ETag + If-None-Match is for when that trust period is up but re-downloading the whole body anyway would be wasteful — the client still asks, but the answer can be "nothing to send."

3 · PUT/PATCH/DELETE + If-Match: "only write if it's still the version I saw"

The second half of conditional requests protects writes instead of reads, using a companion header:

PATCH /orders/482 HTTP/1.1
If-Match: "a1b2c3d4"
Content-Type: application/json

{"status":"shipped"}

If-Match tells the server: only perform this write if the resource's current ETag is exactly this value. If someone else has updated the order since the client last fetched it, the current ETag has moved on, the comparison fails, and the server rejects the write with 412 Precondition Failed instead of silently overwriting a version the client never actually saw.

This should feel familiar: it is the exact lost-update problem Lesson 33 solved with a version integer column and a WHERE ... AND version = $seen clause. If-Match is the same optimistic-concurrency idea moved up one layer, expressed in HTTP instead of SQL:

Same problem, same no-locking-on-read strategy, same "reject a stale write instead of silently losing an update" outcome — just moved from an app-level column check to an HTTP-native mechanism that any client, not just this one codebase, can rely on without knowing the schema has a version column at all.

4 · A minimal Go implementation

An ETag is only trustworthy if it's derived from the same data the client is comparing against — a hash of the current row is the simplest honest source, though reusing an existing version or updated_at column works too and avoids hashing on every request.

type Order struct {
    ID         int
    Status     string
    TotalCents int
}

// etag derives a fingerprint from the fields that define this resource's
// current state -- any change to Status or TotalCents changes the hash.
func etag(o Order) string {
    sum := sha256.Sum256([]byte(fmt.Sprintf("%d:%s:%d", o.ID, o.Status, o.TotalCents)))
    return fmt.Sprintf(`"%x"`, sum[:8])
}

// getOrderHandler answers a conditional GET: if the client's If-None-Match
// already matches the current ETag, it gets 304 and no body at all.
func getOrderHandler(w http.ResponseWriter, r *http.Request, o Order) {
    tag := etag(o)
    w.Header().Set("ETag", tag)
    if r.Header.Get("If-None-Match") == tag {
        w.WriteHeader(http.StatusNotModified) // 304, no body
        return
    }
    w.Header().Set("Content-Type", "application/json")
    json.NewEncoder(w).Encode(o)
}

// patchOrderHandler answers a conditional write: If-Match must equal the
// current ETag, or the write is rejected with 412 before touching the DB.
func patchOrderHandler(w http.ResponseWriter, r *http.Request, current Order, newStatus string) {
    if want := r.Header.Get("If-Match"); want != "" && want != etag(current) {
        http.Error(w, "order changed since you last read it", http.StatusPreconditionFailed) // 412
        return
    }
    current.Status = newStatus
    // ... persist current, same shape as Lesson 33's version-column UPDATE
    w.Header().Set("ETag", etag(current))
    json.NewEncoder(w).Encode(current)
}

Notice patchOrderHandler checks If-Match before doing any database write — the same "fail the precondition before the side effect runs" shape as Lesson 33's WHERE version = $seen, just checked in application code instead of the SQL WHERE clause. A real implementation would still want the actual persistence step to be atomic (a transaction, or the same version-column WHERE guard underneath), since two concurrent requests could both pass this check a moment apart — the HTTP-level check narrows the window, it doesn't replace a DB-level guarantee for cases where that race actually matters.

5 · Where each one actually pays off

If-None-Match is a bandwidth and latency optimization: an API polled every few seconds (a dashboard, a mobile app checking for updates) can send the last-seen ETag and get back a tiny 304 instead of the same multi-KB JSON body over and over, exactly the "don't resend if nothing changed" instinct behind Lesson 9's caching lesson. If-Match is a correctness guarantee: any client editing a resource that might be edited by someone else concurrently — a shared document, an admin panel, an order two support agents might both touch — should read the ETag first and send it back on the write, turning a possible silent lost update into an explicit, handleable 412.

Q: "What's the difference between If-None-Match and If-Match, and when would you use each?" A strong answer, out loud: "Both compare a client-supplied ETag against the resource's current one, but they're used on opposite operations for opposite reasons. If-None-Match goes on a GET — it's a bandwidth optimization, the server returns 304 with no body when the client's cached copy is already current. If-Match goes on a write, PUT or PATCH or DELETE — it's a correctness guarantee, the server returns 412 and refuses the write if the resource changed since the client last read it, so you can't silently overwrite someone else's update. It's the same problem Lesson 33's version column solves at the database layer, just expressed as an HTTP-native mechanism instead of an app-level WHERE clause." The signal: naming both directions correctly and connecting If-Match back to optimistic concurrency rather than describing it as just another caching header.
