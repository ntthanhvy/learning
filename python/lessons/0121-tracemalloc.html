tracemalloc: watching where memory actually goes

Day 1 named the mutable-default-argument trap and showed it produce a wrong answer. It never showed the other half of that bug: the shared default list also keeps growing, forever, as long as the program runs — a silent memory leak with no exception to catch it. tracemalloc is the standard-library module that answers "which line of code is actually responsible for this memory," turning that kind of leak from a guess into a measured fact.

1 · Turning tracing on, and why a snapshot needs it first

tracemalloc is off by default — tracking every allocation has a real cost, so Python only pays it once tracemalloc.start() is called. Calling tracemalloc.take_snapshot() before that raises, confirmed live:

import tracemalloc

print(tracemalloc.is_tracing())      # confirmed live: False
tracemalloc.take_snapshot()         # confirmed live: raises RuntimeError
# "the tracemalloc module must be tracing memory allocations to take a snapshot"

tracemalloc.start()
print(tracemalloc.is_tracing())      # confirmed live: True

tracemalloc.start() is the one-time setup step every example below assumes has already run.

2 · A snapshot, and comparing two of them

A Snapshot is a frozen record of every traced allocation at one moment, tagged with the file and line that created it. One snapshot alone is rarely useful — the real move is taking two, before and after some suspect code, and comparing them:

tracemalloc.start()

def make_big_list():
    return [i * i for i in range(50000)]

before = tracemalloc.take_snapshot()
big = make_big_list()
after = tracemalloc.take_snapshot()

diff = after.compare_to(before, "lineno")
print(diff[0])
# confirmed live: ".../file.py:4: size=1996 KiB (+1996 KiB), count=49986 (+49986), average=41 B"

snapshot.compare_to() points at line 4 — exactly the comprehension inside make_big_list() — not a vague "memory went up somewhere" guess. The top entry is sorted first because it's the single biggest contributor to the growth between the two snapshots.

3 · Proving Day 1's trap live: the leak behind the wrong answer

Day 1 showed def add_item(item, basket=[]): producing an accumulating basket across calls — a correctness bug. tracemalloc shows the same function is also a memory leak, confirmed live, by pointing straight at the .append() line as the thing still growing 10,000 calls later:

def add_item(item, basket=[]):
    basket.append(item)   # line 2 -- this is what compare_to() points at
    return basket

before = tracemalloc.take_snapshot()
for i in range(10000):
    add_item(i)
after = tracemalloc.take_snapshot()

top = after.compare_to(before, "lineno")[0]
print(top)
# confirmed live: ".../file.py:2: size=304 KiB (+304 KiB), count=9743 (+9743), average=32 B"
print(len(add_item.__defaults__[0]))
# confirmed live: 10000

Nothing here is special to tracemalloc's own bookkeeping — line 2 is the real .append() call, growing by one entry every single call, exactly matching the default list's own length of 10000 read straight off the function object. This is the difference between suspecting a leak from a slowly climbing memory graph and pointing at the exact line causing it.

4 · Current and peak usage, without a diff

For a quick "how much am I using right now" check, get_traced_memory() skips the two-snapshot dance entirely:

current, peak = tracemalloc.get_traced_memory()
print(current, peak)   # confirmed live: 2046698 2047192 (bytes)

tracemalloc.reset_peak()
current, peak = tracemalloc.get_traced_memory()
print(current, peak)   # confirmed live: 2046767 2046767 -- peak now equals current

tracemalloc.get_traced_memory() only counts memory tracemalloc itself is tracking — allocations from before start() was called, or memory a C extension allocated outside Python's own allocator, don't show up here at all.

Turning tracing off: tracemalloc.stop() clears all recorded traces and stops the overhead — confirmed live, is_tracing() reports False right after, and calling get_traced_memory() again after stop() raises the same RuntimeError shape Section 1 showed for take_snapshot() before start(). There's no "pause," only on or off.
Where pandas/NumPy go from here: pandas and NumPy have their own memory profile entirely — a DataFrame's columns live in contiguous typed buffers, and tracemalloc reports that underlying buffer allocation as one block, not broken down per row the way it breaks down a plain Python list. Profiling that buffer-level picture is a data/-side topic, if it comes up at all; this lesson is about Python-level object allocation, which every script makes regardless of which libraries it imports.
