ASGI middleware: wrapping every request/response

Day 22 named middleware in one recognition-level sentence and moved on — never built, never run. Today it gets the worked lesson: a function that wraps every request/response passing through the app, running code before the route handler and again after it returns — with a concrete, load-bearing example (request timing + structured logging) and the one real gotcha worth naming up front: middleware sits outside Day 23's exception handlers in FastAPI's stack, so it can't assume its own try/except will ever see a handled exception.

Bridge from SQL: a database trigger that fires on every table's INSERT/UPDATE — auditing who changed what, when — without touching any single table's own definition. Middleware is that same idea moved to HTTP: one function wired in once, seeing every request and every response the app produces, with no route handler aware it's even running.

1 · What middleware actually is

Every lesson since Day 16 has written a route handler as a plain function: FastAPI calls it, the function returns a value, FastAPI turns that into a response. middleware (named already, recognition-only, back in Day 22's glossary) sits one layer further out: it wraps every route the app has, running before the matching handler starts and after it finishes — the same shape as Day 6's with block (setup, then the wrapped work, then guaranteed cleanup), except the "wrapped work" here is however FastAPI resolves the whole rest of the request, handler included.

Nothing about a route handler changes to support this. A handler written exactly like Day 16's still just reads its parameters and returns a value — middleware is bolted on separately, once, and applies to routes that already existed before it was added and any written afterward.

2 · @app.middleware("http") and call_next

FastAPI's simplest way to add middleware is a decorator on an async def function taking two parameters: the incoming Request, and a callable named call_next that represents "everything downstream" — routing, dependencies, the matching handler, all of it:

import time
from fastapi import FastAPI, Request

app = FastAPI()

@app.middleware("http")
async def add_timing_header(request: Request, call_next):
    start = time.perf_counter()
    response = await call_next(request)          # everything downstream runs here
    duration_ms = (time.perf_counter() - start) * 1000
    response.headers["X-Process-Time-ms"] = str(round(duration_ms, 1))
    return response

@app.get("/items/{item_id}")
def get_item(item_id: int):
    return {"item_id": item_id}

Reading top to bottom: everything before await call_next(request) runs before the route handler — here, recording a start time. await call_next(request) is the handoff: it runs the rest of FastAPI's request handling (routing, any Depends() from Day 19, the handler itself) and returns the real Response object once all of that is done. Everything after that line runs after the handler returns but before the client actually receives the response — here, computing elapsed time and stamping it onto a response header. Confirmed directly: a plain GET /items/7 through TestClient comes back with an X-Process-Time-ms header attached, even though get_item itself never mentions timing or headers at all.

call_next must be awaited — this is Day 20's checkpoint idea applied to middleware itself: the middleware function pauses at that line, hands control to the rest of the app, and resumes exactly where it left off once a response comes back, the same pause-and-resume relationship await always has.

3 · A concrete example: timing + structured logging

Stamping a header is a toy. A middleware most real services actually run logs one structured line per request — method, path, status code, duration — the same shape a production log aggregator expects, built once and applying to every route the app will ever grow:

import logging, time
from fastapi import FastAPI, Request

logger = logging.getLogger("requests")
app = FastAPI()

@app.middleware("http")
async def log_requests(request: Request, call_next):
    start = time.perf_counter()
    response = await call_next(request)
    duration_ms = (time.perf_counter() - start) * 1000
    logger.info(
        "request handled",
        extra={
            "method": request.method,
            "path": request.url.path,
            "status_code": response.status_code,
            "duration_ms": round(duration_ms, 1),
        },
    )
    return response

This is Day 15's logging module and its extra= structured-fields pattern, unchanged — the only new piece is where the log call lives: one middleware function instead of a line inside every single handler. Every route the app has, present and future, gets a request-handled log line with zero changes to any handler's own code, the same "write it once, every caller benefits" idea Day 19's Depends() already established for shared setup — middleware is that same idea for wrapping, not just providing a value.

BaseHTTPMiddleware (from starlette.middleware.base, the ASGI toolkit FastAPI is built on) is the class-based alternative to @app.middleware("http") — same call_next shape, wrapped in a class instead of a decorated function, useful mainly when a middleware needs constructor arguments or several apps need to share one middleware class. This course sticks to the decorator form, since it covers everything today's example needs.

4 · The gotcha: middleware runs outside Day 23's exception handlers

Day 23 taught @app.exception_handler(SomeException): register it once, and any route that raises SomeException gets converted into a chosen response before that exception ever reaches a caller. The gotcha: an exception handler resolves the exception before middleware's own call_next() returns — so by the time middleware sees anything, it only ever sees a finished Response, never the exception itself.

class OutOfStock(Exception):
    ...

@app.exception_handler(OutOfStock)
def handle_out_of_stock(request, exc):
    from fastapi.responses import JSONResponse
    return JSONResponse(status_code=409, content={"error": "out_of_stock"})

@app.middleware("http")
async def log_requests(request: Request, call_next):
    try:
        response = await call_next(request)
    except Exception:
        # never runs for OutOfStock - the handler already resolved it
        logger.error("unhandled exception")
        raise
    logger.info("request handled", extra={"status_code": response.status_code})
    return response

Confirmed directly with TestClient against this exact shape: a route raising OutOfStock makes call_next() return normally with response.status_code == 409 — the except Exception: branch never fires, because OutOfStock never escapes as far as middleware; Day 23's handler already turned it into a response one layer further in. Only a truly unhandled exception — one with no registered @app.exception_handler anywhere — actually propagates out of call_next() as a real exception middleware's try/except can catch.

The practical rule: middleware that wants to log the request's final status code should read response.status_code unconditionally after await call_next(request), exactly like section 3's example already does — not assume a try/except around call_next() will ever see the business exceptions Day 23 taught handlers for. That try/except still has a real job (catching the rare exception nobody registered a handler for, to log it before FastAPI's own default 500 response goes out), just not the job of observing every error path.

Where pandas goes from here: a pandas pipeline has no request/response cycle to wrap — timing or logging a transform step means calling time.perf_counter() around that one call directly in the script, not registering anything app-wide; middleware is specifically a web-service answer to "run this for every request," which a one-shot script has no equivalent of.
