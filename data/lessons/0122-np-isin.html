np.isin(): the array primitive under Series.isin(), and two traps it doesn't share

Lesson 121 closed with no standing candidate, so this round did a fresh curriculum/glossary scan. The clearest gap: np.isin(), the raw-array function underneath Lesson 29's Series.isin() — the exact "name the NumPy function underneath an already-taught idiom" lineage this course has run since Lessons 93, 100, 102, 109-112, 114, and 117-121. A first probe found it diverges from Series.isin() in two sharp, confirmed ways: a bare string no longer raises, and NaN no longer matches NaN.

1 · The gap: isin() has a NumPy layer underneath it, same shape as clip() and argsort()

Lesson 29 taught Series.isin(candidates) as the pandas spelling of SQL's WHERE col IN (...). Underneath it sits np.isin(arr, test_elements), the same raw-array layer relationship Lesson 102's np.clip() has to Series.clip() and Lesson 93's np.argmax() has to idxmax(). Confirmed directly (numpy 2.5.4), element-for-element identical to Series.isin() on the happy path:

import numpy as np
import pandas as pd

customer = np.array(["An", "Chi", "Binh", "An"])
candidates = ["An", "Chi"]

np.isin(customer, candidates)
# array([ True,  True, False,  True])
pd.Series(customer).isin(candidates).to_numpy()
# array([ True,  True, False,  True])  -- IDENTICAL

Same Lesson 29 Section 3 anti-join trick works directly on raw arrays too, no Series needed: customers[~np.isin(customers, orders_customers)] finds every customer with no matching order, confirmed directly against this course's fixture. So far, a pure rename with an array in, an array out.

2 · The first divergence: a bare string does NOT raise

Confirmed directly (numpy 2.5.4, pandas 3.1.1): Lesson 29 confirmed current pandas raises TypeError when Series.isin() gets a bare string instead of a list — a real guard pandas added. np.isin() has no such guard: a bare string is accepted as one scalar candidate, matched exactly, with no character-by-character iteration either (the old iterate-the-characters folklore Lesson 29 already debunked for Series.isin() doesn't apply here, confirmed directly):

small = np.array(["An", "Chi"])

np.isin(small, "An")
# array([ True, False])  -- no error; "An" treated as ONE scalar candidate, matched whole

pd.Series(small).isin("An")
# TypeError: only list-like objects are allowed to be passed to isin(), you passed a `str`

The official NumPy docs page for isin() doesn't spell this out explicitly either (confirmed via WebFetch) — it only notes that a set gets converted to a one-element object array, a related but separate gotcha, not the bare-string case. Two functions sharing almost the same name, opposite behavior on the exact same bad input: one raises loudly, the other silently does something plausible-looking. Always wrap candidates in [...] for both, regardless of which one happens to guard against it today.

3 · The sharper divergence: NaN does NOT match NaN

Confirmed directly, and confirmed absent from the official docs (fetched via WebFetch — no mention of NaN handling at all): Series.isin() treats a missing value as matching another missing value for membership purposes — a real, deliberate pandas convenience. np.isin() does not: it falls back to plain float equality, and under IEEE rules NaN != NaN, so no row ever matches a NaN candidate at all:

xn = np.array([1.0, np.nan, 3.0, np.nan])
nan_candidates = [np.nan, 3.0]

np.isin(xn, nan_candidates)
# array([False, False,  True, False])  -- only the real 3.0 matched; BOTH NaN rows stayed False

pd.Series(xn).isin(nan_candidates)
# array([False,  True,  True,  True])  -- BOTH NaN rows matched True, plus the real 3.0

Confirmed directly across both single- and multi-NaN inputs: this is not a one-off fluke of this particular array — Series.isin([np.nan]) alone matches every NaN row in the Series, while np.isin(arr, [np.nan]) alone matches nothing, ever. This is this course's familiar "no crash, quietly wrong" shape (Lessons 19-29, 36): swapping one of these functions for the other on data with missing values silently changes which rows count as a match, with no exception and no warning either way.

4 · What stays the same: invert=, any shape, and the np.in1d() rename

Confirmed directly, three things that do carry over cleanly: invert=True is the np.isin()-native way to spell ~np.isin(...) (same result, one less negation); np.isin() works on any array shape, not just 1-D — a 2-D array gets an element-wise mask of the same shape, since there is no pandas "column" concept to stay inside; and np.isin() is the current, documented replacement for the older np.in1d(), which the official docs now point away from in favor of isin().

np.isin(customer, candidates, invert=True) == ~np.isin(customer, candidates)
# array([ True,  True,  True,  True]) -- identical either way, just phrased differently

Scope line

This lesson covers np.isin()'s basic mask contract and its match to Series.isin() on the happy path, the confirmed bare-string divergence (no TypeError guard), the confirmed NaN-matching divergence (no NaN-to-NaN match, unlike Series.isin()), and the invert= parameter. It does not cover np.isin()'s kind= parameter (an internal algorithm-selection hint between a sort-based and a hash-based implementation — out of scope per MISSION.md's "deep NumPy / C-level internals" exclusion) nor its behavior on a DataFrame's multi-column isin() form (pandas-only, no np.isin() equivalent).
