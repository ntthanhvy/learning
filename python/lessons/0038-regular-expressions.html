Regular expressions: pattern-matching text with re

Day 6 read and wrote whole files; Day 4's str.split()/str.replace() handle fixed, exact text. Neither answers "does this string look like an email address," "pull every number out of this log line," or "is this field a 3-letter code followed by 4 digits, and nothing else." That's a regular expression job, and Python's standard-library re module is where that pattern language plugs in: one small, sharp tool for "does this text have a certain shape," not a replacement for plain string methods when an exact match already does the job.

Bridge from SQL: this is LIKE/ILIKE and Postgres's ~ operator, with a much richer pattern language. WHERE email ~ '^[a-z]+@[a-z]+\.com$' and Python's re.fullmatch(r"[a-z]+@[a-z]+\.com", email) are the same idea — "check the whole value against a shape" — just spelled differently, and the metacharacters below (., *, +, character classes) carry over almost unchanged between the two.

1 · A pattern is a shape, not exact text

A plain string compared with == or found with in only ever matches itself. A regex pattern describes a shape instead — "one or more digits," "an @ surrounded by word characters" — checked against a target string. The core functions:

import re

re.search(r"super", "insuperable")   # found at index 2 -> a Match object
re.match(r"super", "insuperable")    # None -- match() only checks the very start
re.fullmatch(r"\d+", "123")         # the *whole* string must fit the pattern -> matches
re.fullmatch(r"\d+", "123a")        # None -- the trailing "a" breaks a full match

Verified live: all four lines above return exactly what's commented. search() scans the whole string for the pattern anywhere inside it; match() only checks starting at index 0; fullmatch() demands the entire string, start to end, fit the pattern — the one to reach for when validating a whole field like a SKU or postal code, since search() would happily approve a valid pattern buried inside garbage on either side.

A miss is None, not an exception. No match found means search()/match()/fullmatch() return None — they never raise. Calling .group() on that None without checking first raises AttributeError: 'NoneType' object has no attribute 'group' (confirmed live), a common first bug. Always test the result before using it: if m := re.search(...): ... or a plain if m is not None:.

2 · The metacharacters that cover most real patterns

A small vocabulary of special characters builds almost every pattern seen in practice:

# \d  any digit           \w  any "word" char (letter/digit/_)   \s  whitespace
# .   any char (not \n)   *   0 or more of the last thing         +   1 or more
# ?   0 or 1 (optional)   {m,n}  between m and n times            |   OR
# []  one char from a set          ^  start of string    $  end of string
# ()  a capturing group -- pulls that piece out of the match separately

re.findall(r"\d+", "room 12, row 4, seat 100")
# ['12', '4', '100'] -- every non-overlapping match, as plain strings

Character classes narrow "any character" to a specific set: [A-Z] is one uppercase letter, [a-z0-9_] is one lowercase letter, digit, or underscore, and [^0-9] (a ^ right after [) negates the set — anything except a digit. Combine a class with a quantifier for "how many": [A-Z]{3} is exactly three uppercase letters, \d{4} is exactly four digits. Anchor with ^/$ to pin a pattern to the start/end of a string when using search() instead of fullmatch().

Greedy by default. */+/{m,n} grab as much text as they can while still letting the overall pattern match — verified live: re.match(r"<.*>", "<html><title>").group() returns the whole "<html><title>", not just "<html>", because .* greedily eats past the first > looking for the last one. Add a ? right after the quantifier — .*? — to make it lazy instead: re.match(r"<.*?>", "<html><title>").group() then stops at the first "<html>", confirmed live.

3 · Raw strings: why every pattern here starts with r"…"

Python's own string escapes and regex's escapes both use backslash, and they collide. "\d" as a plain string tries to interpret \d as a Python escape sequence first (there isn't one, so newer Python versions warn about it); r"\d" — a raw string — passes the two literal characters \ and d straight through to re, which is what the regex engine actually expects. Confirmed live: r"\d" == "\\d" is True — a raw string is just a shorthand for double-backslashing by hand. Always write regex patterns as raw strings; it's the one habit that avoids an entire category of "why doesn't my pattern match" bugs.

4 · Pulling pieces out: groups, findall, and sub

Parentheses in a pattern mark a capturing group — a piece of the match retrievable on its own:

m = re.search(r"(\w+)@(\w+)\.com", "contact: alice@example.com today")
m.group(0)   # 'alice@example.com' -- group 0 is always the whole match
m.group(1)   # 'alice'   -- first parenthesized piece
m.group(2)   # 'example' -- second parenthesized piece
m.groups()  # ('alice', 'example') -- every captured group as one tuple

# named groups read better than counting parentheses
m2 = re.search(r"(?P<user>\w+)@(?P<domain>\w+)\.com", "bob@site.com")
m2.group("user")   # 'bob'
m2.groupdict()      # {'user': 'bob', 'domain': 'site'}

All six results above verified live. re.sub(pattern, replacement, string) is the find-and-replace counterpart — re.sub(r"\d+", "#", "room 12, row 4") returns "room #, row #" (confirmed live), replacing every match rather than one fixed substring the way str.replace() does. re.split(pattern, string) splits on a pattern instead of a fixed separator — re.split(r"[,;]\s*", "a, b;c, d") returns ['a', 'b', 'c', 'd'] (confirmed live), handling a comma-or-semicolon-plus-any-amount-of-space separator that str.split() alone can't express in one call.

Compile once, reuse many times. re.compile(pattern) returns a pattern object with the same .search()/.match()/.findall() methods, letting a pattern used in a loop be parsed once instead of on every call: pat = re.compile(r"\d+"); pat.findall("a1 b22 c333") returns ['1', '22', '333'] (confirmed live) — the module-level re.findall(pattern, s) functions do this compiling internally anyway and cache a handful of recent patterns, so the difference is mostly clarity and avoiding repeated work in a tight loop, not a hard requirement.

Q: "When would you reach for re instead of plain string methods?" A strong answer, out loud: "When the thing I'm matching is a shape rather than an exact value — 'looks like an email,' 'starts with three letters then four digits,' 'pull every number out of this line' — not when a fixed substring or prefix check already does the job; str.split()/.replace()/in are faster and clearer for those. I'd reach for fullmatch() specifically when validating that an entire field matches a shape, not just that the shape appears somewhere inside it, and I'd always write patterns as raw strings to avoid backslash collisions with Python's own string escapes." The signal: knowing regex is a targeted tool, not a default, and knowing the match/search/fullmatch distinction cold.

Where pandas goes from here: Series.str.contains(), .str.extract(), and .str.replace() accept the same regex patterns taught here, applied across a whole column at once instead of one Python-level re.search() call per value. Not covered here; that's data/'s territory, and this is the only sentence in this lesson that names it.
