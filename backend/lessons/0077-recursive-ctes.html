Recursive CTEs: querying a tree without knowing how deep it goes

Lesson 76 named the plain WITH ... AS (...) CTE and deliberately stopped one step short: what happens when the thing you're querying is a tree — a manager's whole reporting chain, a category and every subcategory beneath it, a comment and every reply to a reply to a reply — and you don't know in advance how many levels deep it goes? A plain CTE names one fixed step. This lesson covers the variant built for "keep going until there's nothing left to find."

1 · Why a fixed number of joins doesn't work

Lesson 76's CTE ran once and stopped: name a step, use it, done. A self-referencing table — an employees table where each row has a manager_id pointing at another row in the same table — breaks that assumption. "Everyone who reports up to Alice, at any depth" could be one join (her direct reports) or six (a report's report's report...), and the query can't hardcode a join count without silently going wrong the day the org chart grows one level deeper.

-- employees(id, name, manager_id) -- manager_id is NULL for the top of the chart
SELECT id, name, manager_id FROM employees WHERE manager_id = 1;
-- only Alice's direct reports -- their own reports are still invisible

A recursive CTE fixes exactly this: instead of naming one step, it names a step that can refer to its own prior output, and Postgres reruns it until a run produces nothing new.

2 · The two-part shape every recursive CTE has

Every WITH RECURSIVE query has exactly two parts joined by UNION or UNION ALL, and the split is not optional:

PartJob
base case (non-recursive term)runs once — the starting row(s), e.g. "the employee with no manager"
recursive case (recursive term)runs repeatedly, joining the CTE's own name against the base table — "find rows whose manager_id matches a row already found"
 
WITH RECURSIVE org_chart AS (
    -- base case: the top of the chart, runs once
    SELECT id, name, manager_id, 1 AS depth
    FROM employees WHERE manager_id IS NULL

    UNION ALL

    -- recursive case: joins org_chart's own growing output against employees
    SELECT e.id, e.name, e.manager_id, oc.depth + 1
    FROM employees e
    JOIN org_chart oc ON e.manager_id = oc.id
)
SELECT * FROM org_chart ORDER BY depth;
-- every employee at every depth, no fixed join count written anywhere

Only the recursive term is allowed to reference org_chart by name — that self-reference is what makes it recursive at all. Postgres runs the base case once, then reruns the recursive case using only the rows the previous run added, stopping automatically the first time a run adds zero new rows.

3 · UNION vs UNION ALL here means something sharper than usual

Lesson 76 never needed this distinction, but a recursive CTE lives or dies by it. UNION discards duplicate rows every single run, which costs a comparison against everything found so far — UNION ALL keeps every row, no comparison. For a real tree (an org chart, a category tree) rows never repeat anyway, so UNION ALL is both correct and cheaper. UNION only earns its cost when the underlying data could cycle back to a row already seen — and in that case, deduplication is doing real work, not just tidying: it's the only thing standing between the query and an infinite loop.

4 · The termination condition is your job, not Postgres's

Postgres stops a recursive CTE automatically once a run adds zero new rows — but nothing forces that to happen quickly, or ever. A self-referencing table with a cycle in it (row A points to B, B points back to A) paired with UNION ALL will run forever, since a row that points back around always looks "new" to a query that never checks for duplicates. This is the one place a query bug becomes an availability incident instead of a wrong answer: a runaway recursive CTE consumes a connection and keeps producing rows until something outside the query kills it. Real production usage adds an explicit depth cap as insurance regardless of whether the data is expected to have cycles:

SELECT e.id, e.name, e.manager_id, oc.depth + 1
FROM employees e
JOIN org_chart oc ON e.manager_id = oc.id
WHERE oc.depth < 20;  -- insurance: stop even if the data has an unexpected cycle

5 · Where this fits what the course already covers

Ties to Lessons 60 and 75: a CHECK constraint (Lesson 60) or a trigger (Lesson 75) could enforce "no cycles allowed" at write time — but neither can answer "show me everyone under Alice" at read time; that's a query-shape problem, and a recursive CTE is the query shape built for it. It's also the direct answer to a gap Lesson 76 left open on purpose: that lesson's plain CTE named one fixed intermediate step precisely because "top 3 per group" only needed one step — a self-referencing hierarchy is the case where one step was never going to be enough, at any fixed number.
