.xs() and droplevel(): slicing and simplifying a MultiIndex

Lesson 51's own closing teaser named these as the last two names on the Lesson-47-flagged batch — both MultiIndex-specific, deliberately deferred until a MultiIndex-heavy topic was due. Lessons 14/15/39 already built and lived inside a MultiIndex (grouped rows, stacked columns, two-aggfunc pivots) without ever showing the two tools built for working inside one once it exists — today closes that gap using the exact same fixtures.

Recap, in one line

A MultiIndex is something Lessons 14/15/39 already built more than once — groupby() on two columns, stack()/unstack(), a pivot_table with two aggfuncs at once. Every one of those lessons reached for reset_index() to flatten it back to something ordinary. Today's tools are for the case where you don't want to flatten yet — you just want one slice (.xs()) or to drop one whole level (droplevel()) while the rest of the structure stays put.

1 · .xs(): pull out one label's slice, on any level

Lesson 15's exact grouped Series, a two-level row MultiIndex (customer outer, order_date inner):

by_customer_date = clean.groupby(["customer", "order_date"])["amount"].sum()
-- customer  order_date
-- An        2026-01-05    120.0
--           2026-01-10     42.0
-- Binh      2026-01-06     35.5
--           2026-01-09    180.0
-- Name: amount, dtype: float64

.xs() pulls out the cross-section for one label — on the outer level by default, matching a plain .loc["An"] lookup:

by_customer_date.xs("An")
-- order_date
-- 2026-01-05    120.0
-- 2026-01-10     42.0
-- Name: amount, dtype: float64

The real reason to reach for .xs() instead of .loc[]: it can also cross-section an inner level directly, something .loc[] can't do without first supplying the outer level's key too. Naming level="order_date" pulls every customer's value for one date at once:

by_customer_date.xs(pd.Timestamp("2026-01-05"), level="order_date")
-- customer
-- An    120.0
-- Name: amount, dtype: float64

Only An ordered on that date, so only An's row survives — .xs() filters across every outer-level group at once, matching whichever rows have that inner-level label, wherever they sit. A missing label raises loudly, the same as .loc[]: by_customer_date.xs("Danh") raises KeyError: 'Danh', no silent empty result.

2 · .xs() also works on columns, via axis=

Lesson 39's two-aggfunc pivot has a MultiIndex on the columns, not the rows:

pv = clean.pivot_table(
    index="customer", columns="order_date", values="amount",
    aggfunc=["sum", "count"], fill_value=0,
)
-- columns: MultiIndex [("sum", 2026-01-05), ..., ("count", 2026-01-10)]

axis=1 tells .xs() to cross-section the columns instead of the rows — pulling just the "sum" half back out to a plain, single-level-column table:

pv.xs("sum", axis=1, level=0)
-- order_date  2026-01-05  2026-01-06  2026-01-09  2026-01-10
-- customer
-- An               120.0         0.0         0.0        42.0
-- Binh               0.0        35.5       180.0         0.0

Same idea as Section 1, just the other axis: level=0 names the outer column level (the aggfunc name), and every remaining column level (order_date) stays exactly as it was — .xs() only ever removes the one level it matched on.

3 · drop_level=False: keep the matched level instead of removing it

By default .xs() drops the level it just matched (that's why by_customer_date.xs("An") came back with only order_date left). drop_level=False keeps it, as a single-value level rather than removing it — useful right before a pd.concat() (Lesson 21) with other slices that still need that level to line up:

by_customer_date.xs("An", drop_level=False)
-- customer  order_date
-- An        2026-01-05    120.0
--           2026-01-10     42.0
-- Name: amount, dtype: float64

4 · droplevel(): remove a level outright, no filtering

droplevel() solves a different problem than .xs(): it doesn't filter anything down to one label — it removes an entire level and keeps every row/column that was already there, whatever labels they carry. Stack Lesson 39's two-aggfunc pivot down one level to get a genuinely two-level row MultiIndex to work with:

stacked = pv.stack(level=0)
-- order_date      2026-01-05  2026-01-06  2026-01-09  2026-01-10
-- customer
-- An       sum         120.0         0.0         0.0        42.0
--          count         1.0         0.0         0.0         1.0
-- Binh     sum           0.0        35.5       180.0         0.0
--          count         0.0         1.0         1.0         0.0

droplevel(0) (or the equivalent name, "customer") removes the outer level, leaving every row's aggfunc label behind with no customer information at all — 0 counts from the outside in, same convention as every other positional level= argument this course has used:

stacked.droplevel(0)
-- order_date  2026-01-05  2026-01-06  2026-01-09  2026-01-10
-- sum              120.0         0.0         0.0        42.0
-- count              1.0         0.0         0.0         1.0
-- sum                0.0        35.5       180.0         0.0
-- count              0.0         1.0         1.0         0.0

droplevel(1) does the opposite — drops the inner (aggfunc) level, leaving customer repeated once per aggfunc row instead:

stacked.droplevel(1)
-- order_date  2026-01-05  2026-01-06  2026-01-09  2026-01-10
-- customer
-- An               120.0         0.0         0.0        42.0
-- An                 1.0         0.0         0.0         1.0
-- Binh               0.0        35.5       180.0         0.0
-- Binh               0.0         1.0         1.0         0.0

Notice both results still have four rows — nothing was filtered out, unlike every .xs() example above. The only thing that changed is which level of the label is still visible; the underlying data is untouched. axis=1 does the same job on columns, pulling the aggfunc level straight off pv without stacking first: pv.droplevel(0, axis=1) leaves 8 columns with just the date, one "sum" block and one "count" block sitting side by side under matching date labels.

5 · The gotcha: droplevel() on a level with duplicate values silently produces a non-unique index

Both results in Section 4 have repeated labels now — "sum"/"count" appear twice, and An/Binh appear twice. droplevel() never checks for this and never raises: it happily returns an index with duplicate labels, and the very next .loc[] lookup against it inherits the same silent multi-row-instead-of-one-row behavior Lesson 33's set_index() entry already warned about:

result = stacked.droplevel(1)
result.loc["An"]  # both An rows come back, not an error, not one row

This is the same "no crash, quietly wrong" family flagged since Lesson 19 (most recently convert_dtypes() in Lesson 51): droplevel() did exactly what it was asked — remove a level — and it is genuinely not droplevel()'s job to notice the result is now ambiguous to look up by label. Check result.index.is_unique after a droplevel() before relying on single-row .loc[] lookups against the result. A plain, single-level Index has no level to drop at all: calling droplevel() on one raises ValueError: Cannot remove 1 levels from an index with 1 levels: at least one level must be left — the one case this method does refuse outright.

6 · The SQL bridge

.xs() reads like a WHERE clause pinned to one part of a composite key — WHERE customer = 'An' when matching the outer level, or WHERE order_date = '2026-01-05' alone when matching the inner one without needing to also specify customer, something a composite PRIMARY KEY lookup in SQL can't do partially either (an index on (customer, order_date) can't be probed by order_date alone without a full scan). droplevel() has no real SQL equivalent — SQL rows don't carry a structured, leveled key the way a MultiIndex does, so there's no operation that "removes one column from every row's identity while keeping every row" in quite the same sense; the closest analogy is simply SELECTing a narrower column list and accepting that the result may now have duplicate rows where it didn't before.

Q: "What's the difference between .xs() and droplevel() on a MultiIndex, and when would each one produce duplicate labels?" A strong answer, out loud: "They solve opposite problems. .xs() filters down to one label's cross-section on a chosen level — it can reach an inner level directly, which plain .loc[] can't do without the outer key too — and it never introduces duplicates, since it's narrowing the data, not renaming its index. droplevel() does the reverse: it keeps every row or column exactly as it was and just removes one level of the label outright, so if that dropped level was what made two rows distinguishable, droplevel() happily hands back a non-unique index with no warning — I'd check index.is_unique right after, before trusting a single-row .loc[] lookup against the result. In one sentence: .xs() can shrink the data but keeps labels unique; droplevel() keeps the data but can make labels stop being unique." The signal: naming the axis= flexibility, the inner-level reach .loc[] lacks, and the specific duplicate-label risk droplevel() introduces silently.
