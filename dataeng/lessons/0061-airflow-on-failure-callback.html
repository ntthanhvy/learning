1 · The gap: two rounds named this hook, neither built it

Day 35 wired on_retry_callback onto dbt_build and named its sibling directly on the way out: "on_failure_callback (fired once try_number > max_tries, the attempt that doesn't get another chance) is where you'd page that it's actually down." Day 56 named it again while building max_consecutive_failed_dag_runs: "Day 35's on_failure_callback remains the right hook, still named rather than built." Two rounds, one unbuilt mechanism, both pointing at the same gap. Today closes it — the same close-a-named-TODO move Day 58 made for Day 55's deferred on_lost.

The distinction actually matters, not just by name. Day 35's own retry attempt and today's failure callback fire from the exact same place in Airflow's source — airflow.sdk.execution_time.task_runner.finalize() — but on two different terminal states a task instance can land in after an attempt ends:

if state == TaskInstanceState.SUCCESS:
    _run_task_state_change_callbacks(task, "on_success_callback", context, log)
elif state == TaskInstanceState.SKIPPED:
    _run_task_state_change_callbacks(task, "on_skipped_callback", context, log)
elif state == TaskInstanceState.UP_FOR_RETRY:
    _run_task_state_change_callbacks(task, "on_retry_callback", context, log)
    # ... if error and task.email_on_retry and task.email: _send_error_email_notification(...)
elif state == TaskInstanceState.FAILED:
    _run_task_state_change_callbacks(task, "on_failure_callback", context, log)
    # ... if error and task.email_on_failure and task.email: _send_error_email_notification(...)

Read directly out of the installed apache-airflow==3.3.1 package this round (airflow.sdk.execution_time.task_runner, the same module Day 35's own primary source already named): UP_FOR_RETRY and FAILED are mutually exclusive terminal states for one attempt, decided earlier by is_eligible_to_retry() — Day 35's try_number <= max_tries check. An attempt that still has tries left lands in UP_FOR_RETRY and only ever fires on_retry_callback; only the attempt that has genuinely run out of retries lands in FAILED and fires on_failure_callback. A dbt_build with retries=2 (Day 7's own setting, untouched since) can fire on_retry_callback up to twice before it ever fires on_failure_callback at most once — the two hooks don't compete for the same event.

2 · Confirmed live this round: what the callback actually receives, and what happens if it breaks

Day 35 and Day 56 both read the surrounding logic from the installed source without running it. This round went one step further: finalize() was called directly, by hand, with a real TaskInstanceState.FAILED and a real ValueError, bypassing the still-blocked airflow db migrate/airflow dags test approval gate entirely (one attempt made this round, same result as every round since Day 35 — blocked). The callback fired with a dict carrying, among other keys, exception:

ON_FAILURE_CALLBACK fired with context keys: ['exception', 'outlet_events', 'task_instance']
ON_FAILURE_CALLBACK saw exception: ValueError('planted dbt_build failure')

context["exception"] is the real exception object dbt_build's own BashOperator raised, not a string — whatever the callback does with it (log it, format it into a message) gets the real repr(), not a guess. Then a second, separate run proved something neither prior round claimed: a callback that itself raises doesn't crash finalize() or the task-runner process around it.

def broken_callback(context):
    raise RuntimeError("the callback itself is buggy")

# ... wired as dbt_build's only on_failure_callback, then finalize() forced
# with a real FAILED state and a real exception ...
finalize() returned normally -- the raising callback did NOT propagate.

Reading _run_task_state_change_callbacks explains exactly why, line by line:

for i, callback in enumerate(getattr(task, kind)):
    try:
        create_executable_runner(callback, ...).run(context)
    except Exception:
        log.exception("Failed to run task callback", kind=kind, index=i, callback=callback)

Every callback in the list gets its own try/except Exception. A broken on_failure_callback gets logged — "Failed to run task callback", with the callback's own name and index — and Airflow moves on to the next finalizer (the listener hooks, the optional failure email) exactly as if that callback had never existed. The task's own FAILED state, already decided before any callback ran, is completely unaffected either way.

5 · Why "fire and forget" is the right default for an alert callback

Section 2's broken-callback proof isn't a curiosity — it's the actual design reason on_failure_callback is safe to hand a real alert integration later (Slack webhook, PagerDuty, email) without a second layer of error handling around it. If a notification call itself throws — a timeout, a bad webhook URL, a expired token — that exception dies inside _run_task_state_change_callbacks's own try/except, gets logged with the callback's name and index, and the task's own FAILED state, Day 56's max_consecutive_failed_dag_runs count, and every other finalizer still run untouched. The failure that actually matters — dbt_build didn't run — is never masked by a second, unrelated failure in the thing meant to report it.

Scope line

This lesson covers on_failure_callback's firing condition (the FAILED terminal state, mutually exclusive with on_retry_callback's UP_FOR_RETRY), its exact context argument, and the confirmed-live fact that a raising callback is caught and logged rather than propagated. It does not cover actually sending a notification anywhere — today's log_dbt_build_failure stays a print, the same honest TODO shape Day 45 left on check_dead_letters, because this course has no paid notification service in scope per MISSION.md.
