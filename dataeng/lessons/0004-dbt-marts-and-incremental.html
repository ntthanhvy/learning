1 · What a mart actually is

Staging is one model per raw table, no joins. A mart is the opposite: it's allowed — expected — to join across staging models, because a mart's job is to answer a real question ("which restaurant is this order from, and what's that restaurant's commission rate?"), not to mirror one raw table. Today's two marts sit directly on top of Day 2's staging layer:

raw.restaurants ──▶ stg_restaurants ──┐
raw.couriers    ──▶ stg_couriers      ├──▶ fct_orders
raw.orders      ──▶ stg_orders      ──┘
                     stg_restaurants ────▶ dim_restaurants

This is the first time in the course two staging models feed the same downstream model — the DAG stops being flat siblings (Day 2's dbt docs serve picture) and starts actually branching.

2 · Facts vs. dimensions

Dimensional modelling splits a warehouse into two kinds of table, a distinction from Kimball's data warehouse toolkit that predates dbt by two decades and still organizes almost every analytics warehouse built today:

  • A fact table holds one row per business event, at a declared grain, carrying foreign keys to its dimensions plus the numeric measures people aggregate. fct_orders' grain is one row per order — subtotal, delivery_fee and order_total are its measures, restaurant_id and courier_id are its foreign keys.
  • A dimension table holds one row per real-world entity, with the descriptive attributes people filter or group by. dim_restaurants' grain is one row per restaurant — cuisine and city are exactly the columns a "top cuisines by city" query groups by.

Naming the grain out loud before writing a single line of SQL is the actual skill here — Kimball's own framing is "declare the grain first," and getting it wrong (say, accidentally producing two rows per order) is the single most common mart bug, always caught by a unique test on the grain column, which is exactly why both models below get one.

3 · Materialization, the third option: incremental

Day 2 covered view and mentioned table in passing. A table stores its result at build time — faster to query than a view, since nothing re-runs on read, but it goes stale until the next full rebuild, and a full rebuild means re-running the SELECT over every row, every time, even the 499 that haven't changed since yesterday.

An incremental model fixes exactly that: after the first build, dbt only processes rows that are new or changed, appending or merging them into the existing table instead of rebuilding it from scratch. That trade costs something too — incremental logic is more code to get right, and a badly written incremental filter can silently miss late-arriving rows — so it's not the default for every table, only for ones where "reprocess everything, every time" actually hurts.

raw.orders is the one table in this domain that only grows — restaurants and couriers barely change, but every day adds new orders. That append-heavy shape is exactly the signal to reach for incremental, and it's why fct_orders, not dim_restaurants, is today's incremental model.

4 · Build: dim_restaurants as a table

Create models/marts/dim_restaurants.sql. It's a dimension: one row per restaurant, joining in a measure worth denormalizing onto it (how many orders it's had), computed with a left join so a restaurant with zero orders still gets a row:

-- models/marts/dim_restaurants.sql
select
    r.restaurant_id,
    r.name,
    r.cuisine,
    r.city,
    r.commission_rate,
    count(o.order_id) as total_orders
from {{ ref('stg_restaurants') }} as r
left join {{ ref('stg_orders') }} as o
    on o.restaurant_id = r.restaurant_id
group by
    r.restaurant_id,
    r.name,
    r.cuisine,
    r.city,
    r.commission_rate

Note the two ref() calls: this is the first model in the project that depends on two staging models at once — the branch Section 1's DAG sketch showed.

5 · Build: fct_orders, incremental with a unique_key

Now write models/marts/fct_orders.sql yourself. Requirements:

  • a config() block at the top setting materialized='incremental' and unique_key='order_id' — the grain column, so dbt knows which existing row a re-run's new data should replace rather than duplicate;
  • select order_id, customer_id, restaurant_id, courier_id, subtotal, delivery_fee, order_total and placed_at from {{ ref('stg_orders') }};
  • an {% if is_incremental() %} block that filters to only rows placed after the current max placed_at already in {{ this }} — on the very first run the table doesn't exist yet, so this whole block is skipped and every row is selected; on every later run, it's skipped only for rows already loaded.
-- models/marts/fct_orders.sql -- fill in the config() and the incremental filter
{{
    config(
        materialized='TODO',
        unique_key='TODO'
    )
}}

select
    order_id,
    customer_id,
    restaurant_id,
    courier_id,
    subtotal,
    delivery_fee,
    order_total,
    placed_at
from {{ ref('stg_orders') }}

-- TODO: {% if is_incremental() %} ... {% endif %}, filtering to placed_at
-- newer than the current max already in {{ this }}

{{ this }} is dbt's name for "the table this model itself is building" — the only way an incremental model's own SQL can refer to what it already contains, since ref() only points at other models. is_incremental() is true only when the target table already exists and this isn't a --full-refresh, which is exactly the condition under which "only new rows" is the correct thing to ask for.

Why unique_key, specifically: without it, an incremental run just INSERTs whatever the SELECT returns — if a late-arriving update to an existing order slipped past the placed_at filter, or you ever ran the model twice on the same new data by accident, that order_id would appear in the table twice. With unique_key='order_id' set, dbt instead merges: a row whose key already exists gets updated in place, not duplicated. This is the exact same idea as backend/'s idempotency keys — same input processed twice, same end state — just applied to a batch model's re-run instead of an API request. One-line bridge only; that concept isn't re-derived here.

Q: "Walk me through view vs. table vs. incremental — how do you choose?" A strong answer, out loud: "Start with view, because it's free — no storage, always current, and fine for anything cheap to compute, which is why every staging model in this project is a view. Move to table when a model is either expensive to recompute or queried often enough that paying the query cost on every single read stops being worth it — table trades staleness (it's only as fresh as the last run) for read speed. Move to incremental when a table's inputs are large and append-heavy enough that rebuilding the whole thing every run wastes real time — it needs a unique_key so a re-run merges into existing rows instead of duplicating them, and an is_incremental() filter so it only processes what's actually new. In this project, raw.orders only grows, so fct_orders is incremental; raw.restaurants barely changes and is small, so dim_restaurants stays a plain table." The signal: choosing based on data shape and query pattern, not defaulting to incremental because it sounds more advanced — Kimball's own dimensional modelling guidance treats most dimensions as small enough that a full rebuild is simply not a problem worth solving.
