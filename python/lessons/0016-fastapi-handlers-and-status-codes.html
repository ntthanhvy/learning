FastAPI handlers, path/query params & status codes

Day 12 already showed you @app.get("/users/{id}") and told you it's a decorator exactly like the ones you'd built by hand — nothing new to learn about @ itself. Today that preview becomes real: FastAPI is installed for the first time, one route is written end to end, and you learn how a URL's moving parts and a response's status code fit together. This opens Phase 2b — the backend phase — and is the first lesson whose practice file needs anything beyond the standard library.

Bridge from SQL: think of a route as a stored procedure with a name (the URL) instead of a function name — a client "calls" GET /users/42 the way code calls get_user(42), and what comes back is a result set of exactly one row, serialized as JSON instead of printed as a table. A path parameter is like a procedure's required argument; a query parameter is like an optional one with a default, the same distinction Day 4 already drew between positional and keyword-with-default arguments.

1 · Installing FastAPI, and a first route

Every practice file through Day 15 ran on the standard library alone. Today is a deliberate, permanent exception, flagged explicitly because it's the first one: FastAPI is a third-party package, installed the same one-off way Day 11 first installed pytest — via uv run --with, no pyproject.toml anywhere in this course yet:

from fastapi import FastAPI

app = FastAPI()

@app.get("/ping")
def ping():
    return {"status": "ok"}

app is a single FastAPI instance representing the whole application — every route registers itself onto that one object. @app.get("/ping") is Day 12's decorator mechanism, applied: it takes the plain function ping and wraps it with the machinery that says "when a GET request arrives at /ping, call this function and turn its return value into an HTTP response" — exactly the shape Day 12 previewed, with no new decorator concept to learn today. A function registered this way is called a handler. Returning a plain dict is enough — FastAPI serializes it to a JSON response body automatically, no json.dump call needed even though Day 6 taught exactly that module for the same job by hand.

2 · Path parameters: part of the URL itself

Most real routes need input, and the first way to take it is inside the URL:

@app.get("/users/{user_id}")
def get_user(user_id: int):
    return {"user_id": user_id, "name": f"user-{user_id}"}

The {user_id} segment in the decorator's URL string is a path parameter — a placeholder FastAPI fills from the real URL and matches, by name, to the handler's own parameter user_id. Day 7's type hints are doing real work here, not just documentation: user_id: int tells FastAPI to convert the URL's text ("42") into a real int before the handler ever runs, and to reject the request automatically if the text isn't a valid integer — a request to /users/abc never reaches your code at all. A path parameter is never optional; a route with {user_id} in its URL simply doesn't match any request that doesn't supply one.

3 · Query parameters: optional, after the ?

The second way to take input is a plain function parameter that isn't named inside the URL string:

@app.get("/users")
def list_users(active: bool = True, limit: int = 10):
    return {"active": active, "limit": limit}

A request to /users?active=false&limit=5 calls list_users(active=False, limit=5) — FastAPI reads everything after the URL's ?, matches each key=value pair to a parameter by name, and converts it using the same type-hint mechanism section 2 just showed. This is exactly Day 4's default-argument rule, reused rather than reinvented: a handler parameter with a default (active: bool = True) becomes a query parameter, optional in the request exactly because omitting a default argument in a normal function call is already legal. A parameter with no default becomes a *required* query parameter instead — same rule, just no fallback to reach for. The only thing that decides path vs. query is whether the name appears inside {} in the URL string: everything else uses the identical parameter syntax.

4 · Status codes: telling the client what happened, not just what came back

Every HTTP response carries a three-digit status code alongside its body, grouped by leading digit: 2xx success, 4xx the client's fault (bad input, missing resource), 5xx the server's fault. FastAPI defaults every handler to 200 OK on a normal return, but real APIs need to say more than "it worked":

from fastapi import FastAPI, HTTPException

app = FastAPI()
_users = {1: "an", 2: "binh"}

@app.get("/users/{user_id}")
def get_user(user_id: int):
    if user_id not in _users:
        raise HTTPException(status_code=404, detail="user not found")
    return {"user_id": user_id, "name": _users[user_id]}

@app.post("/users", status_code=201)
def create_user(name: str):
    new_id = max(_users) + 1
    _users[new_id] = name
    return {"user_id": new_id, "name": name}

Two mechanisms, one for each direction: raise HTTPException(status_code=404, ...) is Day 8's raise, reused unchanged — a built-in exception type FastAPI specifically knows to catch and turn into an error response instead of a crash, so a missing user becomes a clean 404, never a 500 traceback. Going the other way, @app.post("/users", status_code=201) sets the *success* code up front, in the decorator, since 201 Created (not the default 200) is the correct code for "a new resource now exists" — the HTTP convention behind every REST API you'll ever call. @app.post itself is the same decorator family as @app.get, just bound to a different HTTP method, matched the same way GET requests match @app.get routes.

5 · Testing a handler without running a server

A route is still just a function underneath the decorator — Day 12's whole point — so testing one doesn't require starting a real server and sending real network requests. FastAPI's TestClient, built on httpx, calls routes in-process:

from fastapi.testclient import TestClient

client = TestClient(app)

response = client.get("/users/1")
assert response.status_code == 200
assert response.json() == {"user_id": 1, "name": "an"}

missing = client.get("/users/999")
assert missing.status_code == 404

This is Day 11's plain assert again, aimed at .status_code and .json() instead of a plain function's return value — the same retrieval-practice idiom, a new target. Today's practice file uses this pattern directly rather than pytest's fixture/parametrize machinery, since the goal right now is reading a response, not pytest mechanics Day 11 already covered.

Where pandas goes from here: a FastAPI handler's return value is one JSON object per request — never a DataFrame; if an endpoint needs to hand back tabular data, it converts a DataFrame to records first (df.to_dict("records"), named only, not demonstrated) rather than returning the DataFrame itself.
