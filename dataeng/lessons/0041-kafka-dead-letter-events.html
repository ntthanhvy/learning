1 · The bug a manual commit doesn't protect against

Day 6's consumer loop does exactly one thing per message: parse it, write it, commit the Postgres transaction, then commit the Kafka offset. That order is correct for a good message — Day 6 named it "write first, commit second." It says nothing about a message that can never be written at all: malformed JSON, or valid JSON missing a field the INSERT needs. Confirmed directly, no broker needed to see the shape of this bug — it's in the code itself:

event = json.loads(msg.value())        # raises JSONDecodeError on bad bytes
with conn.cursor() as cur:
    cur.execute(INSERT_SQL, event)      # raises KeyError if a required field is missing
conn.commit()
consumer.commit(message=msg, asynchronous=False)   # never reached if either line above raised

Nothing in that loop catches either exception. The whole process dies, enable.auto.commit=False means the Kafka offset for that message was never committed, and auto.offset.reset: "earliest" plus this consumer group's own last-committed position means the next start re-polls the exact same message — and dies on it again. The pipeline doesn't just drop one event; it stops making forward progress at all, forever, until a human finds and manually skips the offset.

2 · Two wrong fixes before the right one

A bare try/except: continue around the whole loop "fixes" the crash by silently discarding the poison message — no row, no log line a human will ever see, no trace it existed. A bare try/except: pass with no continue is worse: it skips the INSERT but falls through to consumer.commit() anyway, which happens to avoid the stall but is accidental, not designed — nothing about that code says on purpose "committing past a message we didn't actually process is fine here." Bridge from backend: this is the same shape backend's Lesson 49 named for a job queue — retrying forever and silently dropping are the two wrong answers, and a dead-letter table is the third option: quarantine the payload somewhere a human can see it, then make forward progress anyway.

3 · Build: a dead-letter table, and a consumer that uses it

Add one table — same database, no second Kafka topic, keeping today's infra cost at zero:

docker compose exec -T postgres psql -U fdp -d fdp -c \
  "CREATE TABLE raw.dead_letter_events (
       id              BIGSERIAL PRIMARY KEY,
       topic           TEXT NOT NULL,
       kafka_partition INT NOT NULL,
       kafka_offset    BIGINT NOT NULL,
       raw_value       BYTEA NOT NULL,
       error           TEXT NOT NULL,
       failed_at       TIMESTAMPTZ NOT NULL DEFAULT now()
   );"

Then edit scripts/consume_order_events.py: wrap the parse-and-write in its own try/except, and move consumer.commit() to run after either outcome, not just the success path:

DEAD_LETTER_SQL = """
    INSERT INTO raw.dead_letter_events
        (topic, kafka_partition, kafka_offset, raw_value, error, failed_at)
    VALUES (%(topic)s, %(partition)s, %(offset)s, %(raw_value)s, %(error)s, now())
"""

# ...inside the while loop, replacing Day 6's bare parse-and-write block:
try:
    event = json.loads(msg.value())
    with conn.cursor() as cur:
        cur.execute(INSERT_SQL, event)
    conn.commit()
    print(f"landed event_id={event['event_id']} ...")
except Exception as exc:
    conn.rollback()
    with conn.cursor() as cur:
        cur.execute(DEAD_LETTER_SQL, {
            "topic": msg.topic(), "partition": msg.partition(),
            "offset": msg.offset(), "raw_value": msg.value(),
            "error": str(exc),
        })
    conn.commit()
    print(f"dead-lettered offset={msg.offset()} error={exc}")

# Runs after EITHER branch above -- a clean land or a dead-letter write
# both count as "handled." If this line only ran inside the try block's
# success path, a poison message would still stall the consumer: quarantined
# but never committed, so the next poll reads the exact same message again.
consumer.commit(message=msg, asynchronous=False)

conn.rollback() on the failure path matters as much as the dead-letter insert itself: whatever partial work the failed INSERT_SQL attempt left on the connection must clear before the next transaction (the dead-letter insert itself) can run cleanly on the same connection.

4 · Verify: send one poison message, watch it get quarantined, not lose the stream

Publish one malformed event directly, bypassing the producer's own JSON encoding on purpose:

uv run --with confluent-kafka python3 -c "
from confluent_kafka import Producer
p = Producer({'bootstrap.servers': 'localhost:9092'})
p.produce('order_events', key=b'bad-1', value=b'not-valid-json{{{')
p.produce('order_events', key=b'102', value=b'{\"order_id\": 102, \"status\": \"placed\"}')  # missing event_id
p.flush()

uv run --with confluent-kafka --with "psycopg[binary]" python3 scripts/consume_order_events.py

Expected — two dead-letter lines, zero crashes, and the process still exits cleanly once caught up, exactly like every prior consumer run:

Q: "Your Kafka consumer just crashed in production on a message in the middle of the topic. What's your first move, and how do you stop it happening again?" A strong answer, out loud: "First I'd check whether the offset for that message ever committed — if auto-commit is off and the crash happened before the commit call, restarting just re-reads the same message and crashes again, so the pipeline is fully stalled, not just missing one event. The actual fix is wrapping the per-message processing in its own try/except: on failure, write the raw payload and the error into a dead-letter table, then commit the offset anyway, since quarantining it counts as handling it. That gets you back to forward progress immediately, and nothing is silently lost — the bad message is sitting in a table with its exact bytes and error, waiting for someone to look at it, the same shape as a dead-letter queue for a job system, just landed in the warehouse instead of a second queue." The signal: naming that the stall, not just the one lost message, is the real production risk, and that committing past a dead-lettered message is a deliberate decision, not an accident.

Scope line

This lesson covers wrapping per-message Kafka consumer processing in try/except, landing the raw payload and error into a same-database dead_letter_events table, and committing the Kafka offset after quarantining so the consumer keeps making forward progress. It does not cover replaying or reprocessing dead-lettered rows later (a real follow-up workflow, not today's), a second Kafka topic as the dead-letter destination (Kafka Connect's own DLQ convention uses one; today stays in Postgres to keep infra cost at zero, per this course's own scope), or backend's Lesson 49 job-queue dead-letter pattern beyond the one-line naming bridge above — that lesson's retry-budget-then-dead-letter shape is a different mechanism for a different kind of queue, not re-derived here.
