Sagas: what replaces a transaction once two services are involved

Lesson 29's outbox pattern solved atomicity for one database and one event — insert the row, insert the outbox row, both commit together or neither does. That trick only works because both writes stay inside the same Postgres instance. What happens once step two of a business process lives in a second service, with its own database, that your transaction can never reach? Today: the vocabulary for that exact situation, and the pattern that replaces "wrap it in a transaction" once one transaction can no longer cover the whole story.

1 · The order-placement process, one service at a time

Say placing an order means three separate services each doing their own write: an orders service creates the order row, a payments service charges the card, and an inventory service decrements stock. Each service owns its own database on purpose — the same boundary reason Lesson 66's API gateway sits in front of a fleet instead of one shared schema: no team's internal table changes should force another team's redeploy. But it means Lesson 6's BEGIN…COMMIT is no longer an option for "all three happen or none do." Postgres's atomicity guarantee stops at the edge of one database connection, and these are three different databases behind three different services. If the payment charge succeeds but the inventory decrement then fails — card charged while stock silently oversold is the boring version, a service crashing mid-process is the scarier one — there is no single ROLLBACK that can undo work that already committed somewhere else.

Same shape as Lesson 29, one level up: Lesson 29 named this exact hazard for two systems (a database and a queue) and fixed it by keeping both writes inside one database, in one transaction. That fix runs out of road the moment the two things that need to agree are two independently-committing services with no shared database at all — the dual-write problem, generalized past the point Lesson 29's trick can reach.

2 · Why there's no cross-service ROLLBACK

The textbook answer to "make several systems commit together" is two-phase commit (2PC): a coordinator asks every participant "can you commit?", waits for a unanimous yes, then tells everyone to commit for real. Postgres can technically speak this protocol, but it's a poor fit for independently-run services on purpose — every participant must hold its locks and stay blocked the entire time it waits on the coordinator, so one slow or crashed service stalls all the others, which defeats the independent-failure boundary microservices are usually drawn for in the first place. This course's scope (MISSION.md excludes "distributed systems beyond vocabulary level") stops right here: naming 2PC as the theoretical answer almost nobody reaches for in this situation, not teaching how to operate it.

3 · The saga: local transactions plus a planned undo for each

The pattern actually used instead accepts that no cross-service lock will ever exist, and designs for what happens after a later step fails instead of trying to prevent that from ever being possible. A saga splits the process into a sequence of ordinary local transactions — each one exactly the single-database, single-service kind Lesson 6 already covers, nothing new there — plus, for every step, a pre-written compensating transaction that undoes that step's effect if a later step fails. "Undo" here means semantically, not literally rolling back a commit that already happened elsewhere — chargeCard's compensation is refundCard, not an impossible cross-service ROLLBACK.

// The happy path: three local transactions, one per service, run in order.
// If a later step fails, run compensations for every step that already committed,
// in reverse order.
func placeOrderSaga(ctx context.Context, o Order) error {
    if err := ordersSvc.CreateOrder(ctx, o); err != nil {
        return err // nothing committed anywhere yet -- nothing to undo
    }
    if err := paymentsSvc.ChargeCard(ctx, o.CustomerID, o.TotalCents); err != nil {
        ordersSvc.CancelOrder(ctx, o.ID) // compensate step 1
        return err
    }
    if err := inventorySvc.DecrementStock(ctx, o.Items); err != nil {
        paymentsSvc.RefundCard(ctx, o.CustomerID, o.TotalCents) // compensate step 2
        ordersSvc.CancelOrder(ctx, o.ID)                        // compensate step 1
        return err
    }
    return nil
}

Nothing about any individual step is new: each call is a normal local transaction inside one service's own database, exactly Lesson 6's guarantee. What's new is the explicit unwind list — every step that already succeeded gets a matching compensation, run in reverse order, the moment a later step fails.

4 · The cost: a window where the world is visibly inconsistent

Between step 2 committing (card charged) and step 3 failing and its compensation running (card refunded), a real customer's balance shows the charge. Anyone reading the payments database in that window sees state that the business process itself considers temporary and about to be corrected. This is eventual consistency: given enough time and no new writes, every service's state converges to correct — but unlike Lesson 6's single-database transaction, which never lets a partial state become visible to any other query in the first place, a saga's in-between window is real and observable. That's the trade a saga makes explicitly: give up "no partial state is ever visible" in exchange for "no cross-service lock is ever required."

Frontend-habit bridge: this is the backend version of an optimistic UI update that sometimes has to roll back — you show the new state immediately, then reconcile if the server rejects it, rather than blocking every pixel until a round trip confirms success. A saga is the same bet at the scale of a whole business process: move forward assuming each step will succeed, and have a real, tested undo ready for when one doesn't.

5 · Two ways to trigger the compensations

Nothing above says who decides "step 3 failed, now run compensations 2 and 1." Two shapes exist, and this course's scope stops at naming them rather than teaching how to run either one in production. An orchestration saga has one coordinator calling each step directly and deciding what to compensate — close to the placeOrderSaga function above, just one explicit piece of code owning the whole sequence. A choreography saga has no coordinator at all — each service reacts to the previous service's event (Lesson 72's publisher/subscriber vocabulary, applied here) and publishes its own event in turn, including a failure event that tells earlier services to compensate themselves. Orchestration keeps the sequence readable in one place at the cost of a new central dependency; choreography removes that dependency at the cost of the overall sequence no longer being visible anywhere but the event log itself.

6 · Where this actually earns its keep

A saga is real complexity — hand-written compensations, an observable inconsistency window, a coordination style to pick — and it only pays for itself once a business process genuinely spans services with separate databases and no shared transaction is possible. A process confined to one service and one database should stay exactly what Lesson 6 already covers: a plain transaction, ROLLBACK included for free. Reach for a saga only once that option is structurally gone.

Q: "How would you handle a business process that touches three different microservices, if one step can fail after an earlier one already succeeded?" A strong answer, out loud: "A regular database transaction can't help here — Postgres's atomicity stops at one connection, and these are three separate databases. Two-phase commit exists on paper, but it means every service blocks and holds locks while waiting on a coordinator, which fights the whole point of running independent services. What's actually used is a saga: each step is its own ordinary local transaction, and every step also has a compensating action defined in advance — a refund to undo a charge, for instance — that runs if a later step fails. That does mean there's a real window where the system looks inconsistent, like a charge that hasn't been refunded yet, which is a genuine trade-off, not a bug — you're choosing eventual consistency over a lock you can't actually get across services. I'd pick orchestration, one coordinator calling each step and deciding what to compensate, if I wanted the sequence readable in one place, or choreography, each service reacting to the previous one's event, if I wanted to avoid adding that coordinator as a new dependency." The signal: naming why 2PC is avoided in practice, not just that a saga exists, and being explicit that the inconsistency window is an accepted trade-off, not an oversight.
