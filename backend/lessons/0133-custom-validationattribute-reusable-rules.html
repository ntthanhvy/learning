Writing a reusable validation rule once

Lesson 132 closed by naming its own gap: [Required], [Range], and the rest are rules Microsoft already wrote, and IValidatableObject.Validate only ever lives on one model class, so it can't be reused across different classes. This lesson writes the missing piece — a custom, reusable single-property rule, as its own attribute class, the same shape as [Range] itself.

1 · A rule becomes reusable by becoming a class

IValidatableObject.Validate (Lesson 132) is tied to the one model class that implements it: copy the rule to a second class and the copy drifts the moment one gets fixed and the other doesn't. A ValidationAttribute subclass is a rule declared exactly once, as a class, usable on any property of any class from then on — the same leverage Lesson 81's shared JSON Schema document had over copy-pasted handler checks, just spelled as a C# class instead of a schema file.

public class ClassicMovieAttribute : ValidationAttribute
{
    public ClassicMovieAttribute(int year) => Year = year;

    public int Year { get; }

    protected override ValidationResult? IsValid(
        object? value, ValidationContext validationContext)
    {
        var movie = (Movie)validationContext.ObjectInstance;
        var releaseYear = ((DateTime)value!).Year;

        if (movie.Genre == Genre.Classic && releaseYear > Year)
            return new ValidationResult(
                $"Classic movies must have a release year no later than {Year}.");

        return ValidationResult.Success;
    }
}

Applied exactly like a built-in attribute: [ClassicMovie(1960)] public DateTime ReleaseDate { get; set; }.

2 · The method every subclass must override: IsValid

The one method a ValidationAttribute subclass overrides is protected override ValidationResult? IsValid(object? value, ValidationContext validationContext). value is the decorated property's own current value, boxed as object? — the attribute has no idea at compile time whether it is sitting on a DateTime, a string, or an int, which is exactly why the body casts it. Returning ValidationResult.Success means the rule passed; returning a new ValidationResult(message) means it failed, with message becoming that property's reported error text, read the same way [Range]'s own failure message is.

3 · Seeing the rest of the object: ValidationContext.ObjectInstance

A built-in attribute like [Range] only ever sees the one property it decorates. ClassicMovieAttribute needs more: whether this same object's Genre is Classic. ValidationContext carries that wider view — its ObjectInstance property is the whole model object currently being validated, cast back to the concrete class to reach any other property on it. This is the one way a single-property attribute class can still read a sibling property, without becoming a full IValidatableObject.Validate override tied to one class.

4 · Where the error message text actually comes from

The worked example above builds its own message inline with $"Classic movies must have a release year no later than {Year}.". ValidationAttribute also exposes an ErrorMessage property, settable from the attribute usage site itself ([ClassicMovie(1960, ErrorMessage = "...")]) the same way every built-in attribute accepts one, plus a FormatErrorMessage(string name) method a subclass can override to weave the failing property's display name into a templated message rather than hand-building the string inside IsValid every time.

Frontend-habit trap: this looks like writing a custom Zod .refine() or Yup .test() function — same "one reusable predicate, parameterized" instinct. The gap that doesn't carry over: a Zod refine callback gets the whole parsed object handed to it directly as an argument. A C# ValidationAttribute only receives the one decorated property's value directly — reaching any other property requires the extra step through validationContext.ObjectInstance, because the attribute class itself is written once, generically, with no compile-time knowledge of which model it will eventually decorate.

Scope line

This lesson covers subclassing ValidationAttribute, the IsValid(object? value, ValidationContext validationContext) signature, reading a sibling property through ValidationContext.ObjectInstance, and the ErrorMessage/FormatErrorMessage message path. It does not cover client-side validation adapters (IClientModelValidator, the jQuery-validation/unobtrusive-validation wiring a custom attribute needs to also run in the browser) — a reasonable next step, not today's — nor FluentValidation or any other third-party validation library, which stays out of scope for the same framework-comparison reason Lesson 132 named.
