MVCC: how Postgres actually does isolation

Lesson 37 named the mechanism behind every isolation level twice, in passing, and moved on: "Postgres's row-versioning storage engine (MVCC) makes them nearly free" and "a side effect of how its snapshot mechanism works." Today opens that box — what MVCC actually keeps on disk, and why it's the real reason Lesson 6's readers and writers never blocked each other in the first place.

1 · The question Lessons 6 and 37 both dodged

Lesson 6 said a plain SELECT "sees whatever was committed at the moment it runs." Lesson 37 said REPEATABLE READ "pins a transaction's reads to a single consistent snapshot." Both sentences assume something neither explained: how can Postgres show two different transactions two different, both-correct versions of the *same row*, at the *same instant*, without either one blocking the other? A naive single-copy database can't — if transaction A is mid-write on a row, transaction B's read has to either wait or read A's half-finished change. Postgres does neither. The answer is MVCC: multi-version concurrency control.

2 · Postgres never overwrites a row — it adds a new one

The mental model a frontend dev brings to UPDATE is "find the row, change its bytes in place" — the same way you'd mutate a JS object. Postgres does something different: an UPDATE leaves the old row physically on disk, unchanged, and inserts a brand-new row version next to it. A DELETE doesn't erase bytes either — it just marks the existing version as no longer current. Every row secretly carries two hidden system columns that make this work:

-- not columns you SELECT normally, but every row has them:
-- xmin: the id of the transaction that created this row version
-- xmax: the id of the transaction that deleted/replaced this row version
--       (0 / null while the version is still the current one)

An UPDATE, under the hood, is really "set xmax on the old version to my transaction id, then INSERT a new version with my transaction id as its xmin." Both versions sit in the table at once, at least for a while. This is exactly what "row-versioning" in Lesson 37's parenthetical meant: multiple versions of one logical row, coexisting.

3 · A snapshot is just a rule for which versions to see

Once you know rows come in versions, "what a transaction sees" stops being mysterious. At the moment a transaction takes its snapshot — once per statement under READ COMMITTED, once for the whole transaction under REPEATABLE READ/SERIALIZABLE — Postgres fixes a simple visibility rule: a row version is visible only if its xmin transaction had already committed by that point, and its xmax either doesn't exist yet or belongs to a transaction that hadn't committed by that point. Everything else on disk is invisible to this transaction, as if it didn't exist.

That single rule is the whole trick. A writer creating a new version never has to block a reader — the reader's snapshot rule simply skips the not-yet-committed version and keeps seeing the old one. A reader never has to block a writer either — the writer just adds another version. No locks are needed for ordinary reads at all, which is why Lesson 6's SELECTs never contended with each other, only the two competing writes did.

Ties to Lesson 37: this is what actually explains both footnotes. Postgres skips READ UNCOMMITTED's dirty reads for free because the visibility rule above already excludes any uncommitted xmin — there is no code path that would show you another transaction's in-progress write even if you asked for the loosest level. And REPEATABLE READ blocking phantom reads (stricter than the SQL standard requires) is a direct consequence of taking the snapshot once, at the transaction's first statement, instead of once per statement — a row inserted by another transaction after that point simply has no visible version yet, no matter what later query asks for it.

4 · Why old versions don't pile up forever: VACUUM

Every UPDATE or DELETE leaves a dead row version behind — invisible to new transactions, but still physically occupying disk space, because some already-running transaction might still need it for its own snapshot. Postgres reclaims that space with VACUUM, a background process (usually autovacuum, running on its own) that periodically scans for dead versions no visible transaction still needs and marks that space reusable. This is why a table that gets heavy UPDATE traffic but rarely runs autovacuum can visibly bloat in size — it isn't a leak in your application, it's row versions Postgres hasn't reclaimed yet. Tuning autovacuum itself is operations work beyond this lesson's scope; the point here is only the causal link — why dead versions exist at all traces straight back to Section 2.

5 · Seeing it from Go

Nothing about MVCC changes how you write Go against Postgres — pgx never touches xmin/xmax directly. What it does explain is a behavior that otherwise looks like a mystery: setting REPEATABLE READ genuinely freezes what a transaction sees, even of rows other transactions commit while it's still open, because the snapshot was fixed at the start and never moves.

// withRepeatableRead opens a transaction pinned to one snapshot for its
// whole lifetime (Lesson 37's isolation level), which MVCC is what actually
// makes possible: every read inside fn sees the same row versions, no
// matter what other transactions commit in the meantime.
func withRepeatableRead(ctx context.Context, pool *pgxpool.Pool, fn func(pgx.Tx) error) error {
    tx, err := pool.BeginTx(ctx, pgx.TxOptions{
        IsoLevel: pgx.RepeatableRead,
    })
    if err != nil {
        return fmt.Errorf("begin repeatable read: %w", err)
    }
    defer tx.Rollback(ctx) // no-op if fn already committed

    if err := fn(tx); err != nil {
        return err
    }
    return tx.Commit(ctx)
}

Two back-to-back SELECTs inside fn return identical results even if another transaction commits a change to that exact row in between — not because Postgres blocks the other writer, but because this transaction's snapshot never advances to see the new version. Same MVCC mechanism, now visible in application code instead of buried in the isolation-level table.

Q: "How does Postgres let a long-running report query read consistent data without blocking every write that happens while it runs?" A strong answer, out loud: "Postgres uses MVCC — an UPDATE never overwrites a row in place, it writes a new version and keeps the old one around. My report's transaction took a snapshot at the start, so it just keeps seeing the row versions that were visible then; new writes create newer versions the report's snapshot doesn't know about yet. Nobody blocks anybody — the tradeoff is Postgres has to eventually clean up those old versions with vacuum, and a long-running transaction can delay that cleanup by keeping old versions 'possibly still needed' for longer." The signal: naming MVCC as the actual mechanism, not just "Postgres handles it."
