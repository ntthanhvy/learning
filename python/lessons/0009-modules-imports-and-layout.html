Modules, packages & imports

Every practice file so far has been a single script, run alone. Real projects — the capstone included — split across several files that need to call each other. Today: what a Python file becomes the moment another file imports it, why if __name__ == "__main__": exists, how a folder becomes an importable package, and a minimal project layout so tomorrow's uv/pyproject.toml lesson has something concrete to sit on top of.

Bridge from SQL: think of a module the way you'd think of a VIEW or a stored function library — a named, reusable unit that other queries reference by name instead of copy-pasting its definition inline. import parsing is the Python version of "use whatever's defined over there," not a copy of the code.

1 · A file is a module the moment something imports it

Every Day-1-through-8 practice file has run as a lone script: uv run python3 practice/08_exceptions.py. But any .py file is also a module — a unit another file can pull code from by name:

# parsing.py
def safe_int(text):
    try:
        return int(text)
    except ValueError:
        return None
# main.py, same folder
import parsing
parsing.safe_int("42")          # 42 — call anything via module.name

from parsing import safe_int
safe_int("42")                   # 42 — pull the name in directly

Both forms run parsing.py top to bottom exactly once, the first time it's imported anywhere in a program, then cache the result — a second import parsing elsewhere reuses that same already-run module instead of re-running the file. import parsing keeps everything behind the parsing. prefix (no name clashes); from parsing import safe_int pulls just that one name into the current file directly.

2 · if __name__ == "__main__":: script vs. import

Every module has a built-in variable called __name__. Python sets it to "__main__" when the file is run directly, or to the module's own name ("parsing") when the file is imported instead:

# parsing.py
def safe_int(text):
    ...

if __name__ == "__main__":
    # only runs when this file is executed directly —
    # NOT when another file does `import parsing`
    print(safe_int("42"))

Without that guard, any quick self-test or demo code at the bottom of parsing.py would also run every single time any other file imports it — surprising side effects triggered by the mere act of importing. The guard makes a file work both ways on purpose: a runnable script by itself, and a clean, side-effect-free library when imported elsewhere. Every practice file in this course already ends this way, right before its own check() calls — that block only prints its ✓/✗ tally when you run the file directly.

3 · import variants and where Python looks

Four spellings cover nearly everything:

import csv                       # stdlib module, use as csv.reader(...)
import csv as c                  # alias — c.reader(...)
from csv import DictReader      # pull one name in directly
from csv import DictReader as DR # pull in, renamed

When Python sees import csv, it searches, in order: (1) already-imported modules (the cache from section 1), (2) the directory of the file doing the importing, (3) installed packages (what uv manages — tomorrow's topic), (4) the standard library. That search order is why a local file named csv.py in your own project would silently shadow the real csv module — one more reason not to name a file after a stdlib module.

4 · Packages: a folder of modules

A package is a directory containing an __init__.py file — often empty — which tells Python "treat this folder as an importable namespace":

mypkg/
    __init__.py
    parsing.py
    loading.py
from mypkg import parsing
parsing.safe_int("42")

from mypkg.parsing import safe_int
safe_int("42")

This is the exact mechanism behind every stdlib import so far — csv, json, dataclasses, collections are each either a single module or a package, and import csv has been doing this same lookup the whole course. Modern Python (3.3+) technically allows a package directory without __init__.py at all (an "implicit namespace package"), but writing the file explicitly, even empty, remains the clearer, more common convention and is what this course uses.

5 · A minimal project layout

Tomorrow's lesson formalizes this with uv and pyproject.toml; today's job is just to recognize the shape it will manage:

myproject/
    pyproject.toml      # tomorrow: project metadata + dependencies
    src/
        mypkg/
            __init__.py
            parsing.py
            loading.py
    tests/
        test_parsing.py # pytest, coming later this week

Splitting extract/transform/load from Day 7's capstone into three separate modules (extract.py, transform.py, load.py) inside a package like this is the natural next step once a single-file script outgrows itself — each stage becomes independently importable and independently testable, which matters once pytest enters the picture.

Where pandas goes from here: import pandas as pd is this exact mechanism, aliased — pandas itself is just a (very large) package following the same __init__.py/module rules taught today. Not covered here beyond that one sentence; the library itself is data/'s job.
