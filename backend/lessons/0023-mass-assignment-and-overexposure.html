Mass assignment: what your API accidentally lets clients set

Lesson 12 taught the record-level check: does this user own this row? Today's bug passes that check completely — the caller really does own the row — and still lets them write a field nobody meant to expose. It's the OWASP risk that gets skipped precisely because authorization already looks handled.

1 · The convenient trap: one struct, two jobs

A Go struct that mirrors a database row is genuinely convenient — pgx can scan a row straight into it, and encoding/json can decode a request body straight into the same one. Reusing it for both is the default move, and it's exactly the bug:

type User struct {
    ID          int    `json:"id"`
    Email       string `json:"email"`
    Name        string `json:"name"`
    IsAdmin     bool   `json:"is_admin"`
    BalanceCent int    `json:"balance_cents"`
}

func updateProfileHandler(w http.ResponseWriter, r *http.Request) {
    userID := UserFromContext(r.Context()).ID
    var update User
    if err := json.NewDecoder(r.Body).Decode(&update); err != nil {
        http.Error(w, "bad request", http.StatusBadRequest)
        return
    }
    update.ID = userID // "safety": force the id... but every other field is still client-controlled
    store.UpdateUser(r.Context(), update)
}

This is mass assignment: the handler is authenticated (Lesson 4), it's checking the right record (Lesson 12's ownership check would pass — this is the caller's own row), and it still lets the request body decide IsAdmin and BalanceCent, because those fields exist on the struct json.Decode was pointed at. Forcing update.ID = userID only guards the one field someone remembered to think about.

2 · The attack, spelled out

A client sends exactly the request the UI would send for a normal profile edit — plus two extra keys the UI never sends but the API never rejects:

PATCH /me
{"name": "Kim", "email": "kim@example.com", "is_admin": true, "balance_cents": 999999}

Nothing here trips authentication or the record-level check from Lesson 12 — this really is Kim, editing Kim's own row, exactly as allowed. The bug is one level down: which fields an already-authorized write is allowed to touch was never decided. That's the distinction worth holding onto — Lesson 12 answered "can this user write to this row at all," and mass assignment is "which columns of that row," a separate question with no shared middleware to answer it either.

3 · The fix: an explicit allowlist struct

Lesson 17 named the general principle already, for values: allowlist over blocklist — accept only what you've explicitly decided is fine, rather than trying to enumerate everything bad. The same principle applies to fields, not just values. The fix isn't a filter that strips is_admin out after decoding — it's a struct that never had a slot for it to land in:

type ProfileUpdate struct {
    Name  string `json:"name"`
    Email string `json:"email"`
}

func updateProfileHandler(w http.ResponseWriter, r *http.Request) {
    userID := UserFromContext(r.Context()).ID
    var in ProfileUpdate
    if err := json.NewDecoder(r.Body).Decode(&in); err != nil {
        http.Error(w, "bad request", http.StatusBadRequest)
        return
    }
    store.UpdateProfile(r.Context(), userID, in.Name, in.Email) // only these two columns, ever — nothing else CAN bind
}

Send the exact same attacker payload from section 2 at this version: is_admin and balance_cents are simply dropped by json.Decode, silently, because ProfileUpdate has no field for them. There's no list of dangerous fields to remember and keep in sync — the struct's shape is the allowlist. The one-time cost is a second struct per write endpoint instead of reusing the DB model; the payoff is that adding a new sensitive column to User later can never accidentally become client-writable, because nothing wires it up until someone deliberately does.

Not just Go: this bug has hit production systems built in every language — a well-known 2012 GitHub incident let a user set public_key on someone else's account this exact way, back when Rails' ActiveRecord bound request params onto models by default. The language changes; the shape of the mistake — model convenience reused as the request boundary — doesn't.

4 · The read-side twin: excessive data exposure

The same convenience cuts the other way too. A handler that does json.NewEncoder(w).Encode(user) straight off the User struct sends every field back to the client — including ones like a password hash or an internal risk score that were only ever meant to live in the database:

DirectionBugFix
Write (request → model)Mass assignment — client sets fields it shouldn'tA request struct with only the settable fields
Read (model → response)Excessive data exposure — response leaks internal fieldsA response struct with only the public fields

Same root cause, mirrored: one struct, reused past the boundary it was safe inside. The fix is the same shape too — a dedicated struct for what crosses the wire, separate from the one that mirrors the table.

Q: "You've added authentication and an ownership check to a PATCH endpoint. What else would you check before calling it safe?" A strong answer, out loud: "Which specific fields the request body is allowed to set. If the handler decodes JSON straight into the same struct the database row uses, any field on that struct becomes client-writable the moment it exists — even ones nobody intended, like a role flag or a balance. I'd use a separate request struct with only the fields this endpoint should ever change, so it's not a filter I have to remember, it's a type that structurally can't hold anything else. I'd apply the same idea to the response side — encoding the internal model back out can leak fields like a password hash the same way." The signal: authentication and ownership are necessary but not sufficient — field-level access is a third, separate check.
