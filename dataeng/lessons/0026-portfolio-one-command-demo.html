2 · A Makefile is the plainest fix, not the fanciest

A Makefile predates every tool this course has taught by decades, and that's the point: it needs no new install (make ships with every macOS and Linux box already), and every target is just a named shortcut for a shell command this repo's own lessons already wrote. Today doesn't introduce a new orchestration concept — Day 7's Airflow DAG already runs two of these same steps on a schedule, inside Postgres and Kafka containers that exist. make demo is for a human (or an interviewer) who wants to see the whole thing work once, right now, without standing up Airflow first.

A Makefile target can declare other targets as its own prerequisites — demo: up seed kafka-topic produce consume dbt-build means running make demo runs all six, strictly in that left-to-right order, before demo's own one-line recipe ever executes. That ordering guarantee is the entire value here: it's the one thing a human typing commands from memory is most likely to get wrong under time pressure, and it's exactly what a stranger cloning this repo for the first time has no way to know on their own.

3 · Build: Makefile at the repo root

In your food-delivery-pipeline repo, add a Makefile at the top level, next to docker-compose.yml. Every recipe line below is a command this course's own lessons already taught — Day 1's seed script, Day 5's topic creation and producer, Day 6's consumer, Day 7's dbt build — copied verbatim, not rewritten:

.PHONY: up seed kafka-topic produce consume dbt-build demo down

up:
	docker compose up -d
	docker compose ps

seed:
	uv run --with "psycopg[binary]" python3 scripts/generate_raw_data.py

kafka-topic:
	# kafka-topics.sh --create has no --if-not-exists flag; it throws
	# TopicExistsException and a non-zero exit on a topic that's already
	# there, which is exactly what happens on a second "make demo" run --
	# the `|| true` is what keeps this target safe to run again.
	docker compose exec -T kafka /opt/kafka/bin/kafka-topics.sh \
	  --bootstrap-server localhost:9092 \
	  --create --topic order_events \
	  --partitions 3 --replication-factor 1 || true

produce:
	uv run --with confluent-kafka python3 scripts/produce_order_events.py

consume:
	timeout 20 uv run --with confluent-kafka --with "psycopg[binary]" \
	  python3 scripts/consume_order_events.py || true

dbt-build:
	cd warehouse && uv run --with "dbt-postgres==1.11.0" dbt build --profiles-dir .

demo: up seed kafka-topic produce consume dbt-build
	@echo "Demo pipeline ran end to end. See README.md for what each step did."

down:
	docker compose down -v
Two things worth naming about consume specifically: Day 6's consumer is a long-running loop by design (it keeps polling for new messages), which is correct for a real deployment but wrong for a one-shot demo that has to finish and hand control back. timeout 20 gives it 20 seconds to drain whatever produce just wrote, then kills it — the || true stops make from treating that timeout's own non-zero exit as a failure of the whole demo chain. This is a demo-script concession, not a change to Day 6's actual consumer code or its at-least-once/idempotent-write design — nothing about the landing logic itself is touched today.

6 · Build: bring Day 7's decisions section current

Day 7's decisions list was written on 2026-09-21, the end of Phase 1 — it doesn't yet mention anything from Days 8–25. Rather than rewrite it, append one line per Phase 2 theme actually shipped, in the same "what, then why" shape Day 7 already established:

  • Snapshots for commission_rate — restaurants_snapshot keeps every historical rate with a validity window, so a mart joining on the rate at order time doesn't silently use today's rate for last month's orders. (Day 9)
  • An intermediate layer, used once — int_orders_joined exists because dim_restaurants and nothing else needed that exact join; a single-caller macro or intermediate model is pure indirection, so this layer only grew when a second real caller justified it. (Day 8, Day 10)
  • A macro over a second hand-written case when — is_sla_breach() exists because mart_restaurant_sla gave the SLA threshold logic a second real caller; before that, Day 6's inline comparison was the right amount of complexity. (Day 10)
  • delete+insert on dbt-postgres's own default, not merge — Postgres only gained a real MERGE in version 15, and dbt-postgres still defaults to delete+insert once unique_key is set; mart_delivery_sla's late-arriving-event lookback needed delete+insert specifically, since a late event recomputes a whole city+day bucket, not one row's own columns. (Day 13)
  • Cosmos evaluated, not adopted — per-model Airflow tasks are a real upgrade once "which model failed" stops being obvious from one log; for this project's seven models, one BashOperator and a readable dbt log still wins on setup cost. (Day 24)
  • Deferrable sensors over polling — a FileSensor with deferrable=True hands a wait to the triggerer process instead of blocking a worker slot, and a DeadlineAlert catches "running, just too slowly" the way a retry structurally cannot. (Day 25)
