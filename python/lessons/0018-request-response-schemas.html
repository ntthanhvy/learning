Request/response schemas: the type hints ARE the contract

Day 16's handlers took input as loose path/query parameters — an int here, a str there. Day 17 built the pydantic model that validates a whole shaped record at once, but only ever constructed one by hand, in plain Python. Today those two ideas merge: a pydantic model becomes a handler's parameter type for a JSON body, and a second model becomes its response_model. Once both ends of a route are pydantic models, the handler's signature — its parameter types and its response_model — is a full, machine-checked description of the endpoint: a schema, with nothing else to keep in sync.

Bridge from SQL: a request schema is an INSERT statement's column list with types and CHECK constraints — reject the row before it touches anything. A response schema is a VIEW's declared output columns: it decides what a caller is allowed to see, even if the underlying object (like a query's full result row) carries more. Neither is optional the way an untyped API leaves both open to guesswork.

1 · A pydantic model as a handler's parameter: the request body

Day 16's create_user(name: str) only ever took one flat value from a query parameter. A real POST body is usually a whole record — exactly what Day 17's BaseModel already validates. Give a handler parameter a pydantic-model type hint, with no default, and FastAPI stops treating it as a query parameter and starts reading it from the request's JSON body instead:

from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class ItemIn(BaseModel):
    name: str
    price: float

@app.post("/items")
def create_item(item: ItemIn):
    return {"name": item.name, "total": item.price}

Nothing here is a new mechanism — it's Day 16's "a type hint decides how a value is read" rule, plus Day 17's BaseModel, combined. A JSON body of {"name": "pen", "price": "12.5"} gets parsed and handed to ItemIn's constructor before create_item ever runs, with the exact same coercion Day 17 showed (the string "12.5" becomes a real float). A body missing price, or with a price that can't coerce at all, never reaches your code: FastAPI catches the ValidationError itself and returns HTTP 422 Unprocessable Entity with the same field-by-field detail Day 17's ValidationError message carried, automatically — no try/except written in the handler at all.

2 · response_model: the same enforcement, on the way out

A handler is still free to return a plain dict, an ORM row, or anything else JSON-serializable — but nothing stops it from leaking a field that shouldn't leave the server, like an internal cost or a password hash. response_model puts a second pydantic model on the outbound side, shaping (and filtering) whatever the handler returns:

class ItemOut(BaseModel):
    id: int
    name: str
    price: float

_items = {}
_next_id = 1

@app.post("/items", response_model=ItemOut, status_code=201)
def create_item(item: ItemIn):
    global _next_id
    new_id = _next_id
    _next_id += 1
    _items[new_id] = item
    return {"id": new_id, "name": item.name, "price": item.price, "secret_cost": 999}

The handler's own return includes secret_cost, but the JSON a client actually receives is {"id": 1, "name": "pen", "price": 12.5} — confirmed by running this exact route through TestClient. response_model=ItemOut builds an ItemOut from whatever the handler returned, the same construction-time validation and coercion as any other BaseModel, and only fields ItemOut declares survive into the response. A returned value missing a field ItemOut requires is a server bug, not a client one — FastAPI raises its own error rather than shipping a response that breaks its declared shape, because response_model is a promise about every response, not just a filter applied when convenient.

3 · Two models, one route: request and response rarely match

ItemIn and ItemOut are deliberately two different models sharing two fields, not one model reused twice — and that split is the normal shape of a real route, not a special case:

class ItemIn(BaseModel):     # what a client is allowed to send
    name: str
    price: float

class ItemOut(BaseModel):    # what a client is allowed to see back
    id: int              # server-assigned — a client never sends this
    name: str
    price: float

id exists only in ItemOut because it's assigned by the server, after the fact — a client sending an id in the request body would be pointless (and ItemIn without that field simply ignores any extra key sent). The reverse gap matters just as much: if ItemIn grew a password: str field for some other endpoint, a handler that carelessly returned the whole model instead of building an explicit ItemOut would leak it straight into a response. Two schemas per route — one named ...In, one named ...Out, by convention rather than any language rule — is how a FastAPI codebase keeps "what a client may send" and "what a client may see" independently correct, even when most of their fields overlap.

Where pandas goes from here: a request/response schema validates and shapes exactly one JSON record per call — never a whole table; if a handler needs to hand back many rows built from a DataFrame, it converts each row to a plain dict first and lets a list[ItemOut] response model validate the list, one record at a time, the same single-record contract this lesson taught, just repeated.
