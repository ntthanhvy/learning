pydantic models: validation, coercion & settings

Day 16's handlers already trusted a type hint like user_id: int to reject a bad URL segment before the handler ran. Today that same trust gets a name and a shape of its own: pydantic model. You'll build one from a plain class first, watch it reject and coerce input on its own, write a custom validation rule, and read settings from the environment the same way.

Bridge from SQL: a pydantic model is close to a CREATE TABLE with CHECK constraints, enforced on the client side instead of the database — Day 7's dataclass already gave you the fixed, named, typed columns; today's model adds the constraint-checking a plain dataclass never does, rejecting a bad row before it's ever "inserted" (constructed) at all.

1 · What a plain class and a dataclass don't do

Day 7 taught @dataclass as a fixed, named, typed shape with free __init__/__repr__/__eq__. But type hints, Day 7 also said plainly, are documentation only — Python never enforces them at runtime:

from dataclasses import dataclass

@dataclass
class Item:
    name: str
    price: float

bad = Item(name="pen", price="twelve")  # no error at all
print(bad.price + 1)              # crashes later, far from the real mistake

price: str being passed where price: float was promised raises nothing at construction — the dataclass happily stores the string, and the program crashes minutes later at an unrelated line that assumed the hint was true. This is exactly the gap a pydantic model closes.

2 · A pydantic model: validation and coercion, for free

A pydantic model looks like a dataclass with one change — it subclasses BaseModel — and behaves completely differently at construction time:

from pydantic import BaseModel

class Item(BaseModel):
    name: str
    price: float
    qty: int = 1

item = Item(name="pen", price="12.5", qty="3")
print(item.price, type(item.price))  # 12.5 <class 'float'>
print(item.qty, type(item.qty))      # 3 <class 'int'>

Two things happened, and they're different mechanisms even though one line triggered both. Coercion is the string "12.5" being converted into a real float because that conversion is safe and unambiguous — pydantic doesn't just check the type, it tries to *produce* the declared type from what it was given. validation is the check that makes coercion possible or, when it isn't, stops construction cold:

from pydantic import ValidationError

try:
    Item(name="pen", price="not-a-number")
except ValidationError as e:
    print(e)
# 1 validation error for Item
# price
#   Input should be a valid number, unable to parse string as a number [...]

A ValidationError names every failing field and exactly why, in one message, listing all failures at once rather than stopping at the first — this is Day 8's raise mechanism, just raised by pydantic's own code instead of yours. This is also precisely the mechanism Day 16 already relied on for user_id: int in a path parameter — FastAPI builds a pydantic model behind the scenes for every typed handler parameter, so today names the machinery that lesson was already using.

3 · Custom validators: rules pydantic can't infer from a type

A type hint alone can say "this must be a string," but not "this string must have no spaces." For rules like that, a field gets its own function:

from pydantic import BaseModel, field_validator

class SignUp(BaseModel):
    username: str
    age: int

    @field_validator("username")
    @classmethod
    def username_no_spaces(cls, v):
        if " " in v:
            raise ValueError("username must not contain spaces")
        return v.lower()

SignUp(username="Anh Tuan", age=20)  # ValidationError: username must not contain spaces
SignUp(username="AnhTuan", age=20).username  # "anhtuan" — lowercased by the same function

Two Day-12 ideas are doing the work here, stacked: @field_validator("username") is a decorator wrapping username_no_spaces so pydantic calls it during construction with the field's value; @classmethod is new syntax but not a new idea — it just means the function receives the model class (cls) instead of an instance, since validation runs before any instance fully exists. Inside, a plain raise ValueError(...) — Day 8's mechanism again — is caught by pydantic and folded into the same ValidationError section 2 showed, with your message attached. Returning a value from a validator matters too: whatever it returns becomes the field's final value, which is how username_no_spaces both rejects bad input and normalizes good input (lower-casing it) in one function.

4 · Settings: the same model, reading the environment

Configuration — a database URL, a debug flag, an API key — usually comes from environment variables, not a request body. Pydantic's settings package is the same model idea, pointed at os.environ instead:

from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    app_name: str = "myapp"
    debug: bool = False

settings = Settings()  # reads APP_NAME / DEBUG from the environment, falls back to the defaults above

BaseSettings is a separate package (pydantic-settings, installed one-off exactly like Day 16's fastapi/httpx) built on the exact same BaseModel mechanics as sections 2–3 — same coercion, same validators, same ValidationError — the only difference is where a field's value comes from when the constructor doesn't supply one: instead of a plain Python default, it checks an environment variable matching the field's name (case-insensitively — APP_NAME or app_name both work) before falling back to the code's own default. Setting DEBUG=true in the shell and calling Settings() with no arguments coerces that string into debug=True, the identical string-to-bool coercion section 2 already showed for numbers.

Where pandas goes from here: pydantic validates one record's *shape* before it's used — a single row's fields, checked once, at the boundary; a DataFrame's dtypes instead describe an entire column's type across every row at once, which is a table-wide concern pandas owns, not something pydantic models are for.
