1 · Every model so far has been private. Today one becomes an API.

Thirteen days of models, and not one of them has told dbt about anything outside dbt itself. ref() and source() only ever point at other dbt nodes — staging, intermediate, marts, snapshots. But fct_orders and mart_delivery_sla are exactly the kind of table MISSION.md's own "walk through the architecture" goal has in mind: something a real dashboard, a data scientist's notebook, or another team's own pipeline reads directly, with no dbt in between on their side. The moment that's true, those two models stop being "just SQL this project happens to run" and become something closer to a contract: change a column's name or type without warning, and something downstream — code you may never see — breaks silently, weeks after the change shipped.

dbt has three separate features for exactly this shift from private SQL to a relied-upon interface, and today builds all three on fct_orders, the mart the rest of this project already depends on most:

FeatureWhat it actually doesEnforced how?
docs (description)human-readable documentation on a model/column, rendered into a browsable sitenever — pure documentation, dbt does not check it against anything
exposuredeclares a non-dbt downstream consumer (dashboard, notebook, pipeline) as a real node in dbt's own DAGa broken ref() inside an exposure fails dbt parse, same as a broken ref() in a model
model contractpins a model's column names and types up front; dbt checks the compiled SELECT against that list before letting a build finishonly at compile/run time, against a real warehouse connection — not at dbt parse

2 · Docs: descriptions a generated site can actually show

dbt docs generate has been available since Day 1 without ever being used — it reads every model, column and test in the project and builds a static, browsable site with the full lineage graph. Today's build step gives it something worth showing: fct_orders gets a model-level description and a description on every column, in models/marts/marts.yml, alongside the tests already there:

-- models/marts/marts.yml -- fct_orders section, replacing the bare "columns:" block from Day 4
models:
  - name: fct_orders
    description: "One row per order, at the grain the whole downstream pipeline depends on. Contracted: column names, types and the order_id not-null/unique guarantee are enforced at build time, not just tested after the fact."
    columns:
      - name: order_id
        description: "Primary key. One row per order; never null, never duplicated."
        tests:
          - not_null
          - unique
      # ...customer_id, restaurant_id, courier_id, subtotal, delivery_fee,
      # order_total, placed_at -- one description: line each, TODO below

Fill in a one-line description for the remaining seven columns yourself — the day's first real skill is just writing them accurately, since a wrong or stale description is worse than none: it tells a future reader (possibly you, in six months) something false with total confidence. Generate the site and open it:

uv run --project ../dbt_env dbt docs generate
uv run --project ../dbt_env dbt docs serve

Expected — dbt docs serve starts a local webserver (default port 8080) and opens the generated site; click fct_orders in the left-hand model tree and every description you wrote appears next to its column, with the full lineage graph (stg_orders → fct_orders, and now fct_orders → delivery_ops_dashboard once Section 4 adds the exposure) one click away via the graph icon.

Docs are pure documentation, not a guarantee. Nothing in dbt checks a description against anything — write "the customer's email address" on a column that's actually an integer ID, and dbt build passes without a single warning. That's the real difference from what Section 3 builds next: descriptions inform a human reader; a contract is checked by dbt itself, every build.

3 · Model contracts: pin the shape, not just test it after the fact

Every test this project has wired since Day 3 — not_null, relationships, dbt_utils.accepted_range, Day 12's unit tests — runs after a model is built, checking whether the output happens to be correct. A model contract works the other way round: declare the exact shape a model must produce — column names, types, and column-level constraints — before it's built, and dbt refuses to finish the build if the compiled SELECT doesn't match. It's the difference between a promise checked after the fact and a promise dbt enforces on the way in.

Turn it on for fct_orders — contract: {enforced: true} as a model config, plus a data_type on every column (required once a contract is enforced; a column dbt can't type-check is a contract with a hole in it):

-- models/marts/marts.yml -- fct_orders, extending Section 2's block
models:
  - name: fct_orders
    description: "..."  # from Section 2
    config:
      contract:
        enforced: true
      on_schema_change: 'TODO'
    columns:
      - name: order_id
        data_type: bigint
        description: "..."
        constraints:
          - type: not_null
          - type: unique
        tests:
          - not_null
          - unique
      - name: customer_id
        data_type: bigint
      # ...restaurant_id, courier_id: bigint; subtotal, delivery_fee, order_total: numeric;
      # placed_at: timestamp -- match each to what stg_orders/fct_orders.sql actually selects

Keep Day 4's not_null/unique tests on order_id alongside the new constraints block — they check two different things, at two different times. A constraints entry becomes a real DDL constraint dbt writes into the create table statement itself (a Postgres not null column and a unique index), enforced by the database on every single write, contract or no contract test — worth being specific about, since this isn't true on every warehouse dbt supports: dbt Labs' own docs list Postgres as actually enforcing not_null, unique, primary_key and foreign_key constraints at the database level, while Snowflake, BigQuery and Redshift only let you declare most of them as metadata the warehouse never checks — a real difference worth naming if this pipeline's warehouse ever changed. The pre-existing tests: entries are still ordinary dbt data tests, run after the build via a select that fails if it finds any violating rows. Dropping the tests: block because the constraints: block "does the same thing" would be a mistake — a constraint stops a write from violating it; a test tells you, with a named, readable failure, whether one already has.

Fill in on_schema_change and run a plain build first, before guessing:

uv run --project ../dbt_env dbt build --select fct_orders

With on_schema_change: 'ignore' (dbt's own incremental default since Day 4, never named explicitly until now), that build refuses to even start — fct_orders is materialized='incremental', and dbt's own contract validation rejects the combination outright:

Invalid value for on_schema_change: ignore. Models materialized as incremental
with contracts enabled must set on_schema_change to 'append_new_columns' or 'fail'

Worth sitting with why: a contract is a promise about columns that never silently appear or disappear. ignore — Day 4's implicit default, that a schema drift between runs just gets quietly absorbed — is the exact opposite promise. Fill in on_schema_change: 'fail' — the stricter of the two options dbt allows here, and the right one for a mart other things depend on: if fct_orders.sql ever changes shape unexpectedly, the build stops loudly instead of a downstream dashboard finding out days later that a column vanished.

uv run --project ../dbt_env dbt build --select fct_orders

Expected — identical output to every prior day, since the contract matches what the model already produces:

1 of 1 OK created sql incremental model dbt_dev.fct_orders ...... [MERGE 0 in 0.11s]

Done. PASS=1 WARN=0 ERROR=0 SKIP=0 TOTAL=1
What a contract actually catches, checked this round, not assumed: a data_type typo (bigin for bigint) and a declared column that doesn't exist in the model's own select both parsed clean under dbt parse — a contract's real shape-check only happens when dbt compiles the model against a live connection and compares the result, the identical "parse doesn't reach this far, compile/run does" limit Day 13 found for an invalid incremental_strategy string. An exposure's broken ref() is different — Section 4 checks that one, and it fails at dbt parse itself, no connection needed, because a ref() is resolved against the manifest directly rather than against a compiled column list.

4 · Exposures: tell dbt's own graph about the dashboard reading this

An exposure is dbt's way of naming the other side of today's shift: something that reads a dbt model's output but isn't itself a dbt model. Declare the city-ops dashboard this course's own domain implies — the one built on mart_delivery_sla's SLA numbers and fct_orders' order-level detail — as a new file, models/marts/exposures.yml:

-- models/marts/exposures.yml
version: 2

exposures:
  - name: delivery_ops_dashboard
    label: "Delivery Ops Dashboard"
    type: dashboard
    maturity: medium
    url: https://example.com/dashboards/delivery-ops
    description: "The city-ops dashboard reading mart_delivery_sla and fct_orders directly. Not a dbt model -- a downstream consumer dbt now knows about."
    depends_on:
      - ref('fct_orders')
      - ref('mart_delivery_sla')
    owner:
      name: "Data Platform"
      email: data-platform@example.com

type is one of a fixed vocabulary (dashboard, notebook, analysis, ml, application) — pick the one closest to reality, not a free-text label. depends_on's ref() calls are the whole payoff: they make delivery_ops_dashboard a real node in dbt's DAG, exactly like Day 9's snapshot became a node any model could ref() right back. Confirm it resolves as its own resource type, distinct from a model:

uv run --project ../dbt_env dbt list --resource-type exposure
exposure.food_delivery_pipeline.delivery_ops_dashboard

Now break it on purpose, the same "prove the check has teeth" standard Day 3 and Day 12 both held their own tests to — point depends_on at a model that doesn't exist:

uv run --project ../dbt_env dbt parse

With ref('mart_does_not_exist') temporarily swapped in, this fails immediately, no database needed:

Compilation Error

Revert to the real ref()s and regenerate the docs site — delivery_ops_dashboard now shows up as a downstream node on both fct_orders' and mart_delivery_sla's own lineage graphs, a real answer to "what actually reads this mart" that used to live only in someone's memory or a wiki page nobody kept current:

Q: "What's the difference between a dbt model's description, an exposure, and a model contract — and when would you reach for each?" A strong answer, out loud: "All three exist because the moment a dbt model gets a consumer outside dbt — a dashboard, another team's pipeline — it stops being private SQL and starts being something people rely on without reading the code. A description is pure documentation: dbt renders it into the generated docs site, but never checks it against anything, so a stale or wrong description costs nothing to dbt itself, only to whoever trusts it. An exposure is different — it's a real node in dbt's own DAG, naming a non-dbt consumer and the models it depends on via ref(), so a broken dependency fails dbt parse immediately, no live connection needed, the same way a broken ref() between two models always has. A model contract is the strictest of the three: it pins exact column names and types up front, and dbt checks the compiled model against that declaration before letting the build finish — though that check only actually happens at compile or run time against a real connection, not at parse, which matters if you're trying to catch a contract break in CI without spinning up a database. I'd reach for a description on anything worth a human explanation, an exposure the moment a real non-dbt consumer exists, and a contract specifically on a model where an accidental type or column change would break something outside my control to fix quickly." The signal: naming exactly which check runs when — parse-time for exposures, compile/run-time for contracts, never for descriptions — instead of treating all three as interchangeable "governance" features.
