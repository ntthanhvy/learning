Health checks: why checking the DB in the wrong one causes cascading restarts

Lesson 13 introduced liveness and readiness in one paragraph, with two small handlers, and moved on. That was enough to define the words — it was never enough to explain why getting them backwards is one of the most common ways a small database blip turns into a full outage. Today: the one mistake that causes it, worked all the way through.

1 · Two different questions, asked by two different endpoints

Lesson 13 already named the split: a liveness check answers "is this process alive and not deadlocked," and a readiness check answers "can this instance serve real traffic right now." What that lesson didn't dwell on is why the split matters, or what happens when a team implements both endpoints correctly by name but puts the wrong logic in each one.

Liveness should be nearly free to answer — return 200, done, no I/O. It exists to catch one specific failure: the process is still running as an OS process, but something inside it has wedged (a deadlock, an infinite loop holding every worker) so it can no longer make progress on anything, ever, without outside help. The only fix for that is a restart, so liveness failing should trigger one.

Readiness is allowed to be expensive-ish and specific: ping the database with a short timeout, check that a required downstream service responds, whatever "can I actually do my job" means for this service. It exists to catch a completely different failure: the process is fine, but one of its dependencies currently isn't — so this instance should be pulled out of rotation temporarily, not killed.

2 · The mistake: one handler, one meaning, used for both

The failure this lesson is really about starts from something that looks harmless: reusing the readiness logic — "ping the DB" — as the liveness check too, either by literally wiring the same handler to both endpoints, or by writing a liveness handler that "just to be safe" also checks the database. It reads as extra caution. It is the opposite.

Whatever process supervisor is polling these endpoints — a load balancer's health-check config, a container orchestrator, an old-school process manager like systemd or a hand-rolled watchdog script — treats a liveness failure the same way no matter which product it is: kill the process, start a new one. That response is correct for a deadlocked process. It is the worst possible response to "the database had a two-second blip," and a liveness check that pings the database cannot tell those two situations apart.

The frontend equivalent you already own. Think of a React error boundary that's scoped too broadly — one flaky child component throwing during render takes down the entire page instead of just that widget, because the boundary was placed one level too high. A liveness check that includes a DB ping has the same shape: a failure that should be scoped to "this one dependency is unavailable" instead gets treated as "this whole process must die," because the check was written one layer too broad.

3 · Walking through the blip

Say a fleet of 10 instances sits behind a load balancer, all pointed at one Postgres primary, and liveness on every instance pings that database. Postgres has a two-second hiccup — a long-running migration takes a lock, a failover briefly promotes a replica, anything Lesson 28's circuit-breaker lesson would call a transient dependency failure.

  1. All 10 instances poll the database at roughly the same interval, so all 10 liveness checks time out at roughly the same moment — not one instance, all of them, because they share the one thing that just broke.
  2. The supervisor sees 10 simultaneous liveness failures and does exactly what liveness failing means: kill and restart all 10 processes, roughly together.
  3. Every restarted process reconnects to Postgres on startup — reopening its connection pool from zero (Lesson 18's pool-sizing lesson covers what a pool actually costs to establish: a TCP handshake plus authentication per connection, not a cheap operation). Ten processes doing that within the same few seconds is a burst of new-connection load landing on a database that had, at most, a two-second problem to begin with.
  4. That reconnect burst is real additional load on top of whatever caused the original blip — it can extend an outage that would otherwise have cleared in two seconds into one that takes much longer, purely because the fleet's own recovery behavior became the second failure.

Every step after step 1 was avoidable. Nothing about "the database was briefly unavailable" required killing a single process — every one of those 10 processes was alive, healthy, and would have recovered on its own the moment Postgres answered again. The only thing that needed to happen was the load balancer routing around them for two seconds, which is exactly what readiness — not liveness — is for.

4 · The fix is which endpoint fails, not new logic

Getting this right doesn't require inventing anything — it requires putting the database ping behind the correct endpoint and leaving the other one trivial. This is generic across whatever polls it: any health check endpoint works the same way whether the thing polling it is a cloud load balancer, a container orchestrator, or a homegrown supervisor script — the endpoint design doesn't change, only the caller's name does.

func (h *Health) livenessHandler(w http.ResponseWriter, r *http.Request) {
    // No I/O, no dependency checks. If this process can run this
    // handler at all, it is alive -- that's the entire question.
    w.WriteHeader(http.StatusOK)
}

func (h *Health) readinessHandler(w http.ResponseWriter, r *http.Request) {
    // A short, bounded check of what a real request would need.
    // A timeout here means "not ready," never "kill me".
    ctx, cancel := context.WithTimeout(r.Context(), 2*time.Second)
    defer cancel()

    if err := h.db.PingContext(ctx); err != nil {
        http.Error(w, "database unreachable", http.StatusServiceUnavailable)
        return // pulled from rotation -- process keeps running
    }
    w.WriteHeader(http.StatusOK)
}

func main() {
    h := &Health{db: db} // db is a *sql.DB or pgxpool.Pool, opened at startup
    mux := http.NewServeMux()
    mux.HandleFunc("/healthz", h.livenessHandler)  // process-alive only
    mux.HandleFunc("/readyz", h.readinessHandler)  // dependency-aware
    // ...register the real application routes on mux too...
}

Two details worth naming explicitly. First, the timeout on the readiness DB check has to be short and bounded — an unbounded Ping would just hang the readiness check itself, defeating the point, which is why context.WithTimeout is doing real work here and not decoration. Second, a failing readiness check is expected to flip back to healthy on its own with zero intervention the moment the dependency recovers — no restart, no redeploy, nothing to clean up — which is exactly the property Lesson 27's graceful-shutdown lesson relied on from the other direction: readiness is the same lever a shutting-down process flips first to stop receiving new work, before it ever touches liveness.

Q: "A teammate wants to add a database ping to the liveness endpoint 'to be extra safe.' What do you say?" A strong answer, out loud: "I'd push back. Liveness failing means 'kill and restart this process' to whatever's polling it — that's the right response to a deadlock, but it's the wrong response to the database having a blip, because every instance in the fleet shares that same database and would fail liveness at the same moment. You'd get a fleet-wide simultaneous restart over a problem that had nothing to do with any individual process being broken, and the restart itself adds a burst of reconnection load right when the database can least afford it — turning a two-second blip into a longer outage. The database check belongs on readiness: it pulls the instance out of the load balancer's rotation without killing it, and it recovers on its own the moment the database answers again." The signal: naming the simultaneous-failure mechanism and the reconnect-load consequence, not just reciting "liveness shouldn't check dependencies" as a rule with no reason behind it.
