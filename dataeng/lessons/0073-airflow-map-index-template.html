2 · map_index_template: one Jinja string, rendered per instance from that instance's own arguments

Add it as a keyword on the @task decorator itself, not on .expand()/.expand_kwargs():

@task(map_index_template="{{ task.op_kwargs['city'] }}")
def check_city_sla(city: str, min_orders: int, threshold_minutes: int) -> dict:
    ...

Confirmed this round with a real DagBag parse against exactly this change: the string lands untouched in partial_kwargs['map_index_template'], the DAG imports with zero errors, and is_mapped, upstream and the rest of Day 71's already-confirmed structure are all unaffected — this keyword changes a label only, nothing about scheduling.

Reading the installed apache-airflow==3.3.1 package's own execution-time code directly (airflow.sdk.execution_time.task_runner, the module that actually runs a task once the scheduler has handed it off) shows exactly when and how the string turns into a real label:

  • task.map_index_template is added to the Jinja template context under the key map_index_template, alongside the usual dag, task, ti and params every templated field already gets.
  • A private function, _render_map_index(context, ti, log), does the actual work: jinja_env.from_string(template).render(context) — plain Jinja, the same engine and environment every other templated field in this course (Day 10's {{ var() }}, Day 19's {{ ds }}) already uses.
  • At render time, context["task"] is set to ti.task — and for a mapped task instance, that is the unmapped, per-instance operator Day 71 already confirmed exists (the one .expand_kwargs() produces one of, per dict). Its op_kwargs is that one instance's own resolved arguments, not the full list — so {{ task.op_kwargs['city'] }} reads "Hanoi" on the Hanoi instance and "Hue" on the Hue instance, never the other three.
  • The render happens twice: once early, right before the task body executes, with whatever context is available then (best-effort — if it fails, the error is swallowed and logged at debug level, since a partial label beats a crashed task), and once again right after the task body finishes, with the fuller post-execution context. The second render overwrites the first only if it produces a different, non-empty string — so a template that only needs op_kwargs, like today's, settles on its final value from the first render already.
  • The result lands on ti.rendered_map_index, a dedicated field threaded through every task-instance state-change call this round's source read found (running, success, failed, retry) and sent back to the API server as its own value — not reused from any existing templated field, confirming it is a first-class label, not a side effect of logging.
A genuinely new finding this round, not assumed from Day 69's or Day 71's own text: the double-render exists specifically so a template referencing the task's own return value (via {{ ti.xcom_pull(...) }}-style access, not used in today's build) can still produce a correct label — the early render is a best-effort placeholder visible while the task is still running, and the real label is only guaranteed accurate after the task finishes and the second render runs. Today's template only reads op_kwargs, available before the task body ever runs, so both renders would already agree in this specific case — but the two-pass design is there for templates that need more than that.

Q: "Your DAG has a mapped task with a dozen instances. How do you make a failure in the Airflow UI actually actionable without opening every log?" A strong answer, out loud: "By default a mapped instance shows up as a bare integer index, so a failure just tells you 'instance 7 failed' — you have to go cross-reference the upstream list by hand to know what that even means. map_index_template fixes that: it's a Jinja string set on the task itself, rendered once per instance against that instance's own op_kwargs, and the result replaces the integer everywhere Airflow shows that instance — the Grid view, the logs, the task-instance API. For a task mapped over cities, something like task.op_kwargs['city'] turns 'instance 7 failed' into 'Da Nang failed,' which is immediately actionable. It's purely a label, though — it doesn't change scheduling, retries or dependencies, and it's rendered twice internally, once as a best-effort early guess and once for real after the task finishes, so a template that depends on the task's own output still resolves correctly." The signal: naming it as a readability fix with zero effect on scheduling semantics, and knowing it's rendered from the instance's own resolved arguments, not the full mapped list.
