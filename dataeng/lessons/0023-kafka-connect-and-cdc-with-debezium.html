1 · Day 6's consumer, named for what it actually is: a polling CDC pipeline you wrote by hand

Day 6 built a real, working path from a change in the business ("an order was placed") to a row in raw.order_events: a Python producer publishes a JSON event to Kafka, a Python consumer reads it and does INSERT ... ON CONFLICT (event_id) DO NOTHING. That pipeline works today because every status change already has an explicit "please tell Kafka about this" step written into the application code producing orders. raw.restaurants and raw.couriers have no such step — Day 1's loader writes them straight into Postgres with a plain batch CSV load, and nothing announces a change to anyone. If a restaurant's commission_rate changes tomorrow, Kafka never hears about it; only Day 9's dbt snapshot, run on dbt's own schedule, would ever notice.

Change data capture (CDC) is the general name for closing that gap: turning row-level changes a database is already making into a stream of events, without touching the code that made them. Day 6's producer is hand-written CDC for exactly one table's worth of logic (order status), wired in on purpose. The alternative this lesson covers is a framework that does CDC for any table, including ones like raw.restaurants that nobody instrumented.

2 · Kafka Connect: a framework for moving data in and out of Kafka without writing a producer or consumer

Kafka Connect is a framework, shipped with Kafka itself, whose whole job is moving data into or out of Kafka through configuration rather than code. You don't write a producer loop or a consumer loop; you write (or more often, just fill in) a JSON config for a connector, and a Connect worker process runs it. A source connector reads from an external system (a database, an API, a filesystem) and writes to a Kafka topic; a sink connector reads from a topic and writes to an external system (Postgres, Elasticsearch, S3). Day 6's hand-written consumer is, structurally, a sink you built from scratch — Connect's pitch is that most of that plumbing (retries, offset tracking, scaling across more workers, restart-on-crash) is already solved once, by the framework, for every connector that uses it.

Connect itself knows nothing about any particular database or API — that logic lives in the connector plugin. Debezium is the best-known source connector for CDC specifically.

3 · Debezium: a source connector that tails the database's own log instead of asking it questions

The naive way to notice "something changed in raw.restaurants" is polling: run SELECT * FROM raw.restaurants WHERE updated_at > :last_check on a timer. That requires a reliable updated_at column (a deleted row leaves no trace to poll for at all), and it either checks too often (wasted load) or too rarely (stale data). Debezium instead reads the database's own internal replication log — Postgres's write-ahead log (WAL) via logical replication, MySQL's binlog, and so on — the same mechanism a read replica uses to stay in sync. Every row-level insert, update and delete the database already recorded for its own replication purposes becomes a structured Debezium event, with no extra query load on the table and no missed deletes, because a delete is a real entry in that log even though it leaves no row behind to poll for.

A Debezium change event isn't just "something changed" — it carries the actual data, structured as before (the row's prior state, or null on insert) and after (the row's new state, or null on delete), plus an op field (c/u/d/r for create/update/delete/read-during-initial-snapshot). One Kafka topic gets created per captured table automatically — a hypothetical Debezium setup on this portfolio's own Postgres would produce something like fdp.public.restaurants, one topic, with every row change to that one table landing there in order.

5 · The trade-off: why this portfolio keeps the hand-written consumer

Day 6's hand-written consumerKafka Connect + Debezium
What it capturesOnly what the application explicitly publishes — exactly order_events' four statuses, on purpose, nothing elseEvery row-level change to every captured table, including ones nobody thought to instrument
New infrastructureNone beyond the Kafka broker this course already runsA Connect worker process (its own JVM, its own config store) plus Postgres logical replication enabled and a replication slot per connector
Code to writeOne producer script, one consumer script — both already written, both debuggable with a Python stack traceNone (a connector is configuration, not code) — but debugging a stuck connector means reading Connect's own logs and replication-slot state, a different skill
Right fit hereYes — one topic, one event shape, a single developer who can read the two scripts end to end in five minutesWould be the right call if restaurants/couriers needed real-time change capture too, or if there were many source tables and writing a hand-rolled producer for each stopped scaling

The honest decision isn't "hand-written is worse" or "Debezium is overkill" in the abstract — it's that CDC earns its operational cost (a Connect cluster, replication slots to monitor, one more moving part that can fall behind or fail silently) when there are enough source tables, or a strict enough real-time requirement on tables nobody controls the write path for, that hand-writing a producer per table stops being the cheaper option. This portfolio has exactly one event-producing concern (order_events) with full control over the producer's code, so Day 6's approach stays correct — but a `raw.restaurants`-style table whose commission_rate needed to reach a mart within seconds of changing, not whenever dbt's next snapshot run happens, is precisely the shape of problem Debezium exists for.

Q: "Your order events come from a hand-written Kafka producer. Why not just use CDC off the orders table directly?" A strong answer, out loud: "Those are solving different problems. CDC with something like Debezium captures row-level changes already happening in a database — inserts, updates, deletes — by reading the database's own replication log, with no code change required from whatever's writing those rows. My order_events topic isn't a row changing in a table; it's a domain event — 'this order was accepted' — that the application explicitly decides to publish, with a shape I control, at the moment that matters to the business, not at the moment a row happens to change. If I had a table changing underneath me that I didn't control the write path for, or needed change capture on many tables without writing a producer for each one, Debezium is exactly the right tool, because it trades a new piece of infrastructure — a Kafka Connect worker and a replication slot — for not having to instrument the write side at all. For one table with one producer I already own, hand-writing it is simpler and more debuggable, and that's the actual trade-off, not 'CDC is advanced' versus 'manual is basic.'" The signal: distinguishing a domain event from a row-change event, and naming the real infrastructure cost CDC trades away rather than treating it as strictly superior.
