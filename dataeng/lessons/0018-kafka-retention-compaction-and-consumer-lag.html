1 · A log isn't a queue: nothing deletes a message because you read it

Every queue a backend developer has used — SQS, RabbitMQ, a Postgres-table-as-queue — deletes or marks a message consumed the moment some consumer finishes with it. Kafka does not work that way, and this is worth being precise about out loud because it's the single most common wrong assumption carried over from queue experience. order_events is an append-only log: a message sits in a partition whether every consumer group has read it, half of them have, or none have. The only two things that remove a message from a Kafka topic are a retention policy aging it out, or a compaction pass deciding a newer message under the same key supersedes it — never "a consumer read this."

That independence is the point. Day 6's consumer and Day 16/17's producer runs all read from order_events without coordinating with each other at all, and a brand-new consumer group starting today could still read Day 5's very first message, if it's still within retention. A queue can't offer that; a log can, because deleting on read was never part of the deal.

2 · Retention: time and size limits, enforced regardless of who's read what

Kafka ages messages out on a per-topic schedule controlled by two settings, retention.ms (how long, default 7 days at the broker level) and retention.bytes (how big the partition's log is allowed to grow before older segments get dropped, default unbounded). Whichever limit is hit first wins. Neither setting looks at consumer offsets at all — a message past its retention window is deleted whether or not any consumer group, including one that's been down for a week, has ever read it.

Check what order_events is actually running under right now. No topic-level override means it's inheriting the broker's default:

docker compose exec kafka /opt/kafka/bin/kafka-configs.sh \
  --bootstrap-server localhost:9092 --entity-type topics \
  --entity-name order_events --describe

Expected on a topic with no override yet — an empty line, meaning no dynamic (topic-level) config exists, only the broker-wide default underneath it:

Dynamic configs for topic order_events are:

Set an explicit 7-day retention on order_events directly, rather than relying on an implicit broker default this portfolio doesn't control elsewhere in its own compose file:

docker compose exec kafka /opt/kafka/bin/kafka-configs.sh \
  --bootstrap-server localhost:9092 --entity-type topics \
  --entity-name order_events --alter \
  --add-config retention.ms=604800000
Completed updating config for topic order_events.

Confirm it stuck:

docker compose exec kafka /opt/kafka/bin/kafka-configs.sh \
  --bootstrap-server localhost:9092 --entity-type topics \
  --entity-name order_events --describe
Dynamic configs for topic order_events are:
  retention.ms=604800000 sensitive=false synonyms={DYNAMIC_TOPIC_CONFIG:retention.ms=604800000}

604800000 ms is exactly 7 days — the same number the broker was already defaulting to, made explicit on purpose. A message produced today is guaranteed to still be there in 7 days regardless of whether inspect-group, the course's own consumer group from Day 5, or a brand-new group has read it yet. retention.ms is the setting; retention.bytes is the sibling cap most teams leave unbounded unless disk is the actual constraint, not time.

3 · Log compaction: for a keyed topic, keep the latest per key instead of everything

order_events has been keyed by order_id since Day 5 specifically so every status transition for one order lands in the same partition, in order. That key makes order_events look, on the surface, like a textbook candidate for Kafka's other cleanup mode: log compaction. Compaction doesn't age messages out by time or size at all — it periodically rewrites each partition's log and, for every key, throws away every message except the newest one. The topic becomes a changelog of "current value per key," not a record of every event that ever happened.

Prove it rather than take the definition on faith. Create a small scratch topic with compaction on — not order_events itself, just to see the mechanism:

docker compose exec kafka /opt/kafka/bin/kafka-topics.sh \
  --create --bootstrap-server localhost:9092 \
  --topic scratch_compacted --partitions 1 --replication-factor 1 \
  --config cleanup.policy=compact

Confirm the config landed, and notice what it's overriding — the broker's own default cleanup policy is delete (time/size retention), the mode every topic gets unless told otherwise:

docker compose exec kafka /opt/kafka/bin/kafka-configs.sh \
  --bootstrap-server localhost:9092 --entity-type topics \
  --entity-name scratch_compacted --describe
Dynamic configs for topic scratch_compacted are:
  cleanup.policy=compact sensitive=false synonyms={DYNAMIC_TOPIC_CONFIG:cleanup.policy=compact, DEFAULT_CONFIG:log.cleanup.policy=delete}

That one line is the entire contrast in a single config value: cleanup.policy=delete (the default — age out by time/size, keep everything until then) versus cleanup.policy=compact (keep one row's worth per key, forever, regardless of age). Produce the same kind of status-transition sequence this portfolio already writes to order_events — four messages, same key, each one a later status for order 101 — into the compacted topic, then read it back after compaction has had a chance to run. A compaction pass isn't instant and isn't guaranteed to have run the moment you check, but the eventual, steady-state result for key 101 is exactly one message: whichever status was written most recently, with every earlier status for that key gone. That's not a bug to work around — it's the entire feature compaction sells.

4 · The actual decision: why order_events stays on time-based retention

This is the part worth being able to defend out loud, not just define both terms and move on. order_events being keyed by order_id is necessary for compaction to make sense, but it is not sufficient reason to turn it on — the question compaction answers is "do I only ever need the latest value per key," and for this portfolio's own consumer, the answer is no.

Time/size retention (cleanup.policy=delete, today's choice)Compaction (cleanup.policy=compact)
What the topic holdsEvery message ever written, until it ages out by time or sizeOne message per key — the latest — regardless of age
Reading order 101's historyAll four status transitions, in order: placed → accepted → picked_up → deliveredOnly the current status; the other three are gone once compaction runs
What it suitsAn event log a consumer needs to replay in full — exactly Day 6's consumer, which processes every transition to build delivery-SLA historyA changelog of current state per key — e.g. "what's restaurant 9's current commission rate," not "every rate it's ever had"

Day 6's consumer inserts one row per event into raw.order_events, not one row per order — it relies on seeing placed, accepted, picked_up and delivered as four distinct, ordered messages to compute anything about delivery time between them, the way mart_delivery_sla does. If order_events were compacted, every order would eventually collapse to whatever status it's currently in; the three earlier transitions would be gone, and this course's own event-sourcing-style replay — the thing that makes Kafka worth using here instead of Postgres updating a status column in place — would quietly stop being possible. Compaction isn't a safer or more modern setting than retention; it's a different contract about what the topic promises to still have later, and for an event-history topic, that contract is wrong on purpose if applied. The honest rule: compact a topic when you've decided you only need "current state per key" (a dimension-style changelog); retain-by-time a topic when you need "everything that happened," which is what order_events is for, structurally, since Day 5.

Where compaction would actually fit in this pipeline, if it ever did: a hypothetical restaurant_commission_rates topic, keyed by restaurant_id, whose only job is "what's the current rate" — not a history of every rate change — is the shape compaction is built for. order_events is not that shape, and renaming or restructuring it to fit compaction isn't on the table; Day 2a's dbt snapshots already cover the "track every change over time" need for restaurant attributes a different way, on the batch side.

5 · Consumer lag: the one number worth watching in production

Everything above is about what the topic keeps. Consumer lag is about whether a consumer is keeping up with it, and it is the single most-checked Kafka health metric in a running production system — more than broker CPU, more than disk, because it's the most direct signal that something downstream is actually falling behind. Consumer lag for one partition is high-water mark (the log-end offset — "how far the producer has written") minus the group's own committed offset on that partition ("how far this consumer group has confirmed it's processed"). Zero lag means a consumer group is fully caught up; nonzero and shrinking means it's catching up; nonzero and growing is the signal that something's wrong — either the consumer is processing slower than the producer is writing, or it's stuck or crashed outright and nothing is being committed at all.

Check it against a real consumer group right now, the same CLI Day 5's inspector and Day 6's consumer already used --describe on for offsets. If you haven't run a consumer in a while, produce a fresh batch first so there's something to be behind on:

uv run --with confluent-kafka python3 scripts/produce_order_events.py

Then check lag for whichever group your consumer has been using (inspect-group from Day 5, or your Day 6 consumer's own group if you gave it one):

docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group inspect-group

Expected shape — this round's own live run, deliberately stopped a consumer partway through 12 messages to make lag nonzero on purpose, is shown verbatim so the columns are unmistakable rather than described in the abstract:

GROUP           TOPIC         PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG  CONSUMER-ID  HOST  CLIENT-ID
lag-demo-group  order_events  0          3               8               5    -            -     -
lag-demo-group  order_events  2          4               4               0    -            -     -

Consumer group 'lag-demo-group' has no active members.

Read the columns left to right: LOG-END-OFFSET is the high-water mark (partition 0 has received 8 messages total), CURRENT-OFFSET is this group's committed offset (it's confirmed 3), and LAG is the subtraction Kafka does for you — 8 − 3 = 5, five messages this group has not yet processed on that partition. Partition 2 shows LAG 0: that partition is fully caught up. "No active members" is not an error here — it means no consumer process from this group is connected right now, which is itself useful information: a group with real lag and no active members is a crashed or stopped consumer, exactly the second failure mode lag is built to surface. A group with real lag and an active member connected is the other case — processing slower than the producer, worth checking CPU, Postgres write latency, or whatever the consumer's own bottleneck is before assuming anything about Kafka itself.

In production, this is the number an on-call alert watches, not disk usage or broker uptime: a dashboard tracking LAG per partition per group, alerting when it crosses a threshold or keeps climbing instead of shrinking. This portfolio's own consumer, run manually so far across Days 6/16/17, has never had the chance to show real lag before today, because nothing's ever been both running continuously and falling behind — the gap above was created on purpose to make the column non-zero once, the same way Day 16's verification waited for a genuine retry rather than faking one.

Q: "How would you know if a Kafka consumer in production is unhealthy?" A strong answer, out loud: "The first thing I'd check is consumer lag — the difference between a partition's high-water mark, how far the producer has written, and the consumer group's committed offset, how far it's confirmed processing. kafka-consumer-groups.sh --describe shows it directly in the LAG column, per partition. Zero or shrinking lag means healthy. Lag that's growing means one of two things: the consumer is alive but processing slower than messages are arriving, which points at a downstream bottleneck like a slow database write, not Kafka itself; or the consumer has crashed or stalled entirely, which the same command shows as lag that's nonzero with no active members listed. I wouldn't reach for broker metrics first — a broker can be perfectly healthy while a specific consumer group falls behind, and lag is the metric that's actually about the consumer's own health, not the cluster's." The signal: naming the subtraction precisely (high-water mark minus committed offset) and distinguishing "stuck" lag from "slow" lag, since the fix for each is completely different.
