dbt retry: resuming a failed build instead of rerunning it whole

Today's tangible win: when dbt build fails partway through — one bad model, everything after it skipped — dbt retry re-runs only the nodes that didn't succeed last time, using the exact same command and flags as the run it's resuming, instead of either rerunning the whole project or hand-picking --select survivors from memory. Confirmed this round straight from the installed dbt-core 1.12 source: retry reads target/run_results.json from the failed run, keeps only the nodes whose status was error, fail, skipped, runtime error or partial success, and replays whichever original command produced that file — build, run, or test — against exactly that set.

cd dbt_env && uv run dbt parse

1 · The gap: a partial failure has always meant "start over" or "guess by hand"

Every build failure this project has shipped on purpose — Day 1's two planted bad rows, Day 3's negative-subtotal test, Day 13's late-arriving correction, Day 45's dead-letter threshold — has been fixed by either a full dbt build rerun (cheap here, at a few hundred rows; expensive on a real warehouse with a year of history) or a hand-written --select bad_model+ that only works if you remember exactly which nodes failed and which ones got skipped as a result. Neither is really dbt's own memory of what happened — it's you, reconstructing the failure from the terminal scrollback or the CI log. dbt build already writes that memory to disk on every single invocation, success or failure, as target/run_results.json; today's lesson is the command that reads it back.

This matters most exactly where Day 15 and Day 39 already live: a CI pipeline building forty models where node 23 fails on a flaky warehouse connection, not a real bug. Without retry, a human either reruns everything (slow, and risks a second flake somewhere else) or digs through CI logs to build a manual --select list. With retry, the fix is "run it again, same command" — dbt already knows node 23 is the only thing that needs to happen.

2 · Confirmed from the installed package: retry replays the original command, not always build

Reading dbt.task.retry.RetryTask directly (installed locally via uv run --with "dbt-postgres==1.11.0", no live database needed to read source — the same approach Days 20-22, 25, 35, 45, 46, 54 and 56 already used) shows the actual mechanism:

RETRYABLE_STATUSES = {
    NodeStatus.Error, NodeStatus.Fail, NodeStatus.Skipped,
    NodeStatus.RuntimeErr, NodeStatus.PartialSuccess,
}

# in RetryTask.__init__: load the previous run's own results file
state_path = args.state or config.target_path
previous_results = load_result_state(
    Path(config.project_root) / Path(state_path) / "run_results.json"
)
previous_command_name = previous_results.args.get("which")  # "build", "run", "test", ...

# in RetryTask.run(): keep only nodes whose last status was retryable
unique_ids = {
    result.unique_id for result in previous_results.results
    if result.status in RETRYABLE_STATUSES
}

Three details worth more than the headline. First, retry looks in target/ by default — the same directory a normal run already writes to, not the separate --state comparison directory Day 15's callout warned never to collide with target-path. A second dbt build between the failure and the retry overwrites that file with a new, probably-all-success result, and retry would then find nothing left to retry — the failure record is only good until the next run clobbers it. Second, previous_command_name is read from the saved results, not chosen by the retry invocation: a failed dbt test gets retried as test, a failed dbt build as build, even though the command typed on the terminal is just dbt retry both times. Third, skipped is itself retryable — every node dbt skipped as a consequence of an upstream failure (not just the node that actually errored) gets a second attempt automatically, with no manual dependency-tracing required.

What dbt retry does not do: it does not re-decide anything about why a node failed. If bad_model.sql still divides by zero, retry reruns it, it fails again, identically — this is a resumption mechanism for the build's own progress, not a self-healing one. Fix the actual cause first; retry only saves you from re-doing the parts that already worked.

3 · Why this is a different claim than Day 15's slim CI or Day 13's --full-refresh

It's easy to blur this with other "run less than everything" dbt features already in this project, so naming the boundary matters. Day 15's state:modified+ asks "what changed since a prior git commit's manifest?" — a diff against a different project state, used to skip work that's definitely still correct. Day 13's --full-refresh asks the opposite question, "ignore what's already built and recompute everything for this one incremental model" — more work, not less. Today's retry asks neither: "what, in the single most recent invocation, did not finish successfully?" — a diff against this project's own last attempt, not against git history and not against an incremental model's own prior state. All three read a file from a previous run, but a different file, for a different purpose: state:modified+ reads a copied-aside manifest.json, retry reads target/run_results.json in place, and --full-refresh reads nothing — it's a flag that tells one model's own compiled SQL to ignore its usual incremental filter.

They compose, too: a CI job can run dbt build --select state:modified+ to scope a build to what changed, have one of those nodes fail on a transient warehouse hiccup, and retry that same scoped build with a plain dbt retry — the node set retry resumes from is whatever the prior invocation actually attempted, state-selection and all, not the whole project.

4 · Build: wire retry into the CI job Day 15 already wrote

In your food-delivery-pipeline repo, open the GitHub Actions workflow Day 15 added (the one running dbt build against a Postgres service container). Add one step immediately after the existing build step, running only if that step failed:

# .github/workflows/dbt-ci.yml -- add right after the existing "dbt build" step
      - name: dbt build
        id: dbt_build
        run: dbt build --profiles-dir . --select state:modified+ --state ./prod-manifest
        continue-on-error: true

      - name: dbt retry (resume a transient failure once)
        if: steps.dbt_build.outcome == 'failure'
        run: dbt retry --profiles-dir .

Note that retry itself takes no --select — the node set is already fixed by whatever run_results.json the build step just wrote. One retry, not a loop: a real bug fails the same way twice, and two straight failures should surface to a human rather than retry forever, the identical reasoning behind Day 56's max_consecutive_failed_dag_runs choosing 3 over an unbounded retry loop.

That confirms every status name used in Section 2's RETRYABLE_STATUSES set against the real enum — error, fail, skipped, runtime error and partial success are retryable; warn is retryable only when the original run passed --warn-error (confirmed in the same source read); success, pass, no-op and reused are never retried, correctly, since nothing about them needs resuming. With a real Postgres available, confirm the full cycle directly:

uv run --with "dbt-postgres==1.11.0" dbt build --profiles-dir .
# expect: ok_model succeeds, bad_model errors (division by zero)
# fix bad_model.sql, then:
uv run --with "dbt-postgres==1.11.0" dbt retry --profiles-dir .
# expect: only bad_model runs this time -- ok_model is not rebuilt

Expected on that second command: dbt's own log names exactly one node selected (bad_model), skipping ok_model entirely — the concrete, visible proof that retry is scoped to the prior failure, not a second full build wearing a different command name.

Scope line

This lesson covers dbt retry as a node-resumption command reading target/run_results.json, confirmed via the installed package's own RetryTask source and a scratch-project parse. It does not cover retry's interaction with microbatch models' per-batch retry (a dbt 1.9+ feature tracking which date batches of a microbatch-incremental model succeeded independently) — named as existing in the source read (batch_map in RetryTask.run) but out of scope, since this project has no microbatch model and Day 13 already covers this project's actual incremental strategy (merge/delete+insert) in depth. It also does not cover automatic retry loops or exponential backoff — Section 4's one-retry-then-surface choice is deliberate, the same reasoning Day 56 used to pick 3 over an unbounded auto-pause threshold.
