str.split(): breaking one text column into several

Chào bạn — the argsort/np.unique/searchsorted trio Lesson 72 opened is now fully taught, so today's a fresh scan. A fresh grep across all 75 lessons and the glossary turned up a real gap hiding in plain sight: Lessons 42/43 taught str.extract()/str.extractall() (regex-based) and Lesson 60 taught str.contains() (a filter), but the plain, no-regex-needed workhorse for "one messy column, several real fields" — str.split() — never got its own lesson. It's one of the most common live-coding asks ("this column has name and region jammed together with a dash, split it"), so it closes that gap today.

1 · The default: one string in, one Python list out

.str.split(sep) breaks each string at every occurrence of sep. Its default shape surprises people coming from SQL: not a new table, but a Series where every cell holds a plain Python list.

orders["customer_full"]
# 0    An Nguyen-North
# 1    Binh Tran-South
# 2        Chi Le-East
# ...
orders["customer_full"].str.split(" ")
# 0    [An, Nguyen-North]
# 1    [Binh, Tran-South]
# 2        [Chi, Le-East]
# ...  -- dtype: object, each cell is a real Python list

Confirmed directly (pandas 3.0.6): the result's dtype is object, and type() on any individual cell is Python's built-in list, not a Series or array. This list form is the right shape when you only need to index one piece out with .str[i] (Section 3) — it is the wrong shape the moment you want the pieces as real separate columns.

2 · expand=True: turn the split into real columns — and watch it pad ragged rows with NaN

expand=True is the fix — one real column per piece, ready to assign back onto the DataFrame. But it hides a real trap: if rows don't all split into the same number of pieces, the shorter rows get padded with NaN, silently, no warning:

orders["sku_path"]
# 0      ELEC/PHONE/CASE-01
# 1     HOME/KITCHEN/MUG-02
# ...
# 4           TOYS/BLOCK-05   -- only ONE "/" here, not two
orders["sku_path"].str.split("/", expand=True)
#         0         1        2
# 0    ELEC     PHONE  CASE-01
# ...
# 4    TOYS  BLOCK-05      NaN   -- row 4 padded, no dept/subdept split like the others

Confirmed directly on this course's own fixture: 4 of 5 rows in sku_path follow a dept/subdept/sku pattern, but one row ("TOYS/BLOCK-05") only has two segments. expand=True returns a DataFrame shaped by the WIDEST row (3 columns here), and every narrower row's missing tail column becomes NaN — the same "coerce a mismatch into NaN rather than raise" instinct as str.extract()'s no-match rows (Lesson 42) or pd.to_numeric(errors="coerce"). Naming this unprompted — "check for unexpected NaNs after an expand=True split, since it means a row had a different piece-count than expected" — is the interview-grade instinct here.

3 · n=: capping how many cuts happen, so the remainder stays whole

n= limits the split count directly, useful whenever only the FIRST separator actually matters and the rest of the string should stay intact:

orders["customer_full"].str.split("-", n=1, expand=True)
#            0        1
# 0  An Nguyen    North
# 1  Binh Tran    South
# ...  -- exactly ONE cut, no matter how many "-" a name might contain

Confirmed directly: without n=1, a row like a hypothetical "An Nguyen-Van-North" (two dashes) would split into three pieces instead of the intended two — n= is the guardrail against that. rsplit() is the mirror method: same signature, but counts n cuts from the RIGHT end instead of the left — the natural choice for "keep everything up to the last separator together," e.g. pulling a file extension or the final path segment off sku_path without disturbing the rest.

SQL bridge: there's no single built-in SQL SPLIT that returns multiple columns cleanly across dialects — Postgres has split_part(col, sep, n), called once PER desired piece, or string_to_array(col, sep) for the list form. str.split(sep, expand=True) is the vectorized version of calling split_part() for every piece in one shot; str.split(sep) without expand is the pandas equivalent of string_to_array().

4 · .str[i]: indexing into the list form, safely, even on ragged rows

The list form (Section 1) supports positional indexing with .str[i] — and unlike indexing a plain Python list, it never raises IndexError on a row whose list happens to be too short for that position:

parts = orders["sku_path"].str.split("/")   # list form, ragged lengths (3, 3, 3, 3, 2)
parts.str[2]
# 0    CASE-01
# ...
# 4        NaN   -- row 4's list only has 2 elements, position 2 doesn't exist -- NaN, not a crash

Confirmed directly: parts.iloc[4][2] (plain Python list indexing) raises IndexError: list index out of range, but parts.str[2] (the vectorized accessor) returns NaN for that same row instead — the whole point of the .str accessor family is exactly this kind of per-row safety net that raw Python list/string operations don't give you for free.

Q: "You need to split a 'name-region' column into two real columns. Walk me through it." A strong answer, out loud: "str.split('-', n=1, expand=True) — n=1 caps it at one cut so a name that happens to contain another dash doesn't get split further than intended, and expand=True gives me back a real two-column DataFrame instead of a Series of lists, ready to assign column names and merge back onto the original frame. The thing I'd check immediately after: whether any row produced an unexpected NaN in a column that should be fully populated — that means a row didn't actually contain the separator the number of times I assumed, the same silent-mismatch risk as str.extract()'s no-match rows. I'd run isna().sum() on the result before trusting it." The signal: naming n= and expand=True together with their actual reasons, and flagging the ragged-row NaN risk unprompted.
