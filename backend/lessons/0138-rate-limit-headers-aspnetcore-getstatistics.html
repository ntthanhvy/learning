Rate-limit headers, now in C# too (GetStatistics, CurrentAvailablePermits)

Lesson 96 added three headers to Lesson 11's Go token bucket — RateLimit-Limit, RateLimit-Remaining, RateLimit-Reset — so a client could see its quota trending toward zero on ordinary successful responses, not just learn about it the moment it gets a 429. Lesson 118 ported the bucket itself to ASP.NET Core's rate limiting middleware, but never the headers. Today closes that gap — and the honest version of this port is a little surprising: the framework doesn't hand you those headers for free.

1 · What OnRejected actually exposes, and what it doesn't

Lesson 118's OnRejected callback reads context.Lease.TryGetMetadata(MetadataName.RetryAfter, ...) to copy a real retry hint onto a rejected response. It's tempting to assume a sibling call exists for the successful case — some MetadataName.Remaining you could read on every response the same way. It doesn't. The MetadataName class ships exactly two members, and Microsoft's own reference is explicit about when each applies: ReasonPhrase is "metadata put on a failed lease acquisition to specify the reason the lease failed," and RetryAfter is "metadata put on a failed lease acquisition to specify when to retry acquiring a lease." Both are failure-only. A successful RateLimitLease — the object you get back when a request is allowed through — carries no remaining-count metadata at all.

Frontend-habit trap: it's natural to assume a mature framework feature "obviously" has a one-line accessor for something this common — the same instinct that reaches for a prop no component actually exposes. ASP.NET Core's rate limiting middleware was built to answer "allow or reject, and if rejected, when to retry" — a yes/no gate, not a quota-reporting API. Lesson 96's headers were never that gate's job in Go either; they were a deliberate addition wrapped around it. The C# port needs the same deliberate addition, just with a different building block underneath.

2 · The real gauge: GetStatistics(), not lease metadata

The number does exist — just on the limiter itself, not the lease. Every RateLimiter (the type backing each partition) exposes a GetStatistics() method, returning a snapshot whose CurrentAvailablePermits is exactly Lesson 96's "tokens left right now" — read straight off the limiter, no lease required:

public class RateLimitHeadersFilter : IEndpointFilter
{
    private readonly PartitionedRateLimiter<HttpContext> _limiter;
    private readonly int _configuredLimit; // TokenLimit from the same AddTokenBucketLimiter call, kept alongside
    public RateLimitHeadersFilter(PartitionedRateLimiter<HttpContext> limiter, int configuredLimit)
        => (_limiter, _configuredLimit) = (limiter, configuredLimit);

    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext ctx, EndpointFilterDelegate next)
    {
        var response = ctx.HttpContext.Response;
        var stats = _limiter.GetStatistics(ctx.HttpContext); // snapshot for this request's own partition

        if (stats is not null)
        {
            response.Headers["RateLimit-Limit"] = _configuredLimit.ToString();
            response.Headers["RateLimit-Remaining"] = stats.CurrentAvailablePermits.ToString();
        }
        return await next(ctx); // runs after UseRateLimiter already decided allow/reject
    }
}

Two things fall out of this shape that Lesson 96's Go version never had to think about. First, GetStatistics takes the partition's resource key as a parameter (here, the HttpContext the global limiter partitions on) — it reports one partition's numbers, the same per-API-key split Lesson 118's PartitionedRateLimiter already keeps separately per key. Second, RateLimit-Reset has no GetStatistics equivalent at all: the token bucket limiter's reset timing is derived from its own ReplenishmentPeriod configuration — a value the app already set when calling AddTokenBucketLimiter, computed at the call site rather than read off any live object.

3 · Why this sits in a filter, not inside OnRejected

OnRejected only runs on the request that gets turned away — Lesson 96's own point about Retry-After exactly repeats here one layer up: anything that fires only at rejection is already too late to help a client pace itself beforehand. Setting these two headers has to happen on every response, success or not, which means it belongs in something that always runs — an IEndpointFilter registered after UseRateLimiter, the same filter shape Lesson 121's idempotency port used for a different "wrap every call" need. GetStatistics() being decoupled from any single lease is what makes that possible: the filter can ask "what's the state right now" on a response that was never rejected at all, something OnRejected's lease-scoped metadata could never answer.

Q: "Our C# API has a 429 with Retry-After, but partners say they get no warning before it. Why can't we just read the remaining count off OnRejected?" A strong answer, out loud: "OnRejected only fires on the one request that already got rejected — by definition too late to warn anyone. ASP.NET Core's MetadataName type only has RetryAfter and ReasonPhrase, and both docs say explicitly those are failed-lease-only; there's no remaining-count metadata on a successful lease at all. The actual number lives on the limiter itself — RateLimiter.GetStatistics() returns CurrentAvailablePermits — so I'd add a small endpoint filter that reads that on every response, win or lose, and sets RateLimit-Limit/RateLimit-Remaining the way Lesson 96 already does by hand in our Go services." The signal: naming that the gap is lease-scoped versus limiter-scoped state, not a missing callback.

Scope line

This lesson covers RateLimiter.GetStatistics() and RateLimiterStatistics.CurrentAvailablePermits as the C# source for Lesson 96's RateLimit-Remaining/RateLimit-Limit headers, read inside an IEndpointFilter running after UseRateLimiter. It does not cover a working RateLimit-Reset port (no runtime accessor exists for it; the lesson only names where that number would have to come from instead), RateLimiterStatistics's CurrentQueuedCount/TotalSuccessfulLeases/TotalFailedLeases fields beyond naming them, or the IETF RateLimit header-field draft's exact reset-timestamp format (Lesson 96's own open item, still unresolved).
