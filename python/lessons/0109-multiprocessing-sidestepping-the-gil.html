multiprocessing: sidestepping the GIL for real CPU work

Day 73 named the boundary and stopped there: CPython's GIL lets only one thread run Python bytecode at a time, so threads never speed up pure number-crunching — only I/O waits. multiprocessing is the module Day 73 pointed at but never opened: instead of several threads inside one interpreter sharing one GIL, it runs several separate Python interpreters as separate OS processes, each with its own GIL, actually running Python bytecode at the same time on different CPU cores.

1 · Process: a whole separate interpreter, not another thread

multiprocessing.Process looks almost identical to Day 73's thread-pool shape — target=, args=, .start(), .join() — but .start() here launches an entire new OS process, with its own memory and its own Python interpreter, rather than another thread inside the current one:

from multiprocessing import Process
import os

def f(name):
    print(f"hello {name}, pid={os.getpid()}")

if __name__ == "__main__":
    print(f"parent pid={os.getpid()}")
    p = Process(target=f, args=("bob",))
    p.start()
    p.join()
    print("joined, exitcode =", p.exitcode)
# confirmed live:
# parent pid=34503
# hello bob, pid=34504   -- a genuinely different process ID
# joined, exitcode = 0

.start() launches the child and returns immediately; .join() blocks until it finishes, same as Day 73's threads. The difference that matters is underneath: a thread shares the same memory as every other thread in its process, but a Process gets its own separate memory entirely, confirmed live below.

The if __name__ == "__main__": guard is not optional style. The official docs state it directly: starting a child process needs the __main__ module to be safely importable by that child. On this sandbox's Linux default (the fork start method, confirmed live via multiprocessing.get_start_method()), the child inherits the parent's already-loaded code, so skipping the guard happens not to break anything here — but on Windows and macOS, where spawn is the default, the child starts a brand-new interpreter that re-imports __main__ from scratch. Without the guard, that re-import re-runs the Process(...)/.start() call itself, which spawns another child, which re-imports again — runaway recursion. The guard is what makes the same script correct everywhere, not just on whichever platform happens to run it first.

2 · No shared memory: confirmed live

A thread mutating a shared list is visible to every other thread immediately — that was the whole race-condition risk Day 73 named. A child process mutating what looks like the same variable is not visible to the parent at all, because fork/spawn gives the child its own private copy of the parent's memory at the moment it starts:

from multiprocessing import Process

counter = []

def bump():
    counter.append(1)
    print("inside child, counter =", counter)

if __name__ == "__main__":
    p = Process(target=bump)
    p.start()
    p.join()
    print("in parent after join, counter =", counter)
# confirmed live:
# inside child, counter = [1]
# in parent after join, counter = []   -- parent's list never changed

This is the opposite trap from Day 73's: threads risk a race condition on shared state nobody meant to share; processes have zero shared state by default, so code that assumes a child's changes land back in the parent silently loses that data. Getting a result back out requires deliberately passing it through something built for that, like the Queue below — never a plain shared variable.

3 · multiprocessing.Queue: handing results back across the process boundary

Day 108's queue.Queue only works between threads in the same process — it relies on memory they already share. multiprocessing.Queue has the same .put()/.get() interface but works across the process boundary: every item placed on it is pickled (serialized, Day 72's module) on the way out and unpickled on the way in, since the two processes cannot see each other's memory directly:

from multiprocessing import Process, Queue

def worker(q):
    q.put([42, None, "hello"])

if __name__ == "__main__":
    q = Queue()
    p = Process(target=worker, args=(q,))
    p.start()
    print("got:", q.get())   # [42, None, 'hello'] -- confirmed live, round-tripped intact
    p.join()

Because every item goes through pickle, the same restriction applies: whatever is put() onto a multiprocessing.Queue, and every argument passed via args= to a Process, must be picklable. A plain function defined at module level qualifies; a lambda or a function defined inside another function generally does not — pickle needs to be able to look the function up by name in an importable module to reconstruct it in the other process.

4 · Pool: running one function across many inputs, and the measured payoff

Pool is the batch-shaped tool, the Process-based equivalent of Day 73's thread pool: .map() applies a function to every item of an iterable across a fixed number of worker processes, collecting results in input order:

from multiprocessing import Pool

def square(x):
    return x * x

if __name__ == "__main__":
    with Pool(4) as p:
        print(p.map(square, [1, 2, 3, 4, 5]))   # [1, 4, 9, 16, 25]
        res = p.apply_async(square, (20,))
        print(res.get(timeout=1))                   # 400 -- confirmed live

apply_async() is Pool's one-call-at-a-time equivalent of Day 73's submit() — it returns immediately, and .get() (not .result() this time) blocks until that one call finishes. Measured live on this sandbox (4 CPU cores, via os.cpu_count()), running the same CPU-bound loop four times through Day 73's ThreadPoolExecutor took 2.85s; the identical work through multiprocessing.Pool took 1.50s — a 1.9× speedup, because four real processes genuinely ran Python bytecode at the same time on four separate cores, instead of four threads taking turns behind one shared GIL.

Bridge from Day 73: same mental model, opposite trade-off. Threads are cheap to start and share memory freely, which is exactly right for I/O waits and exactly wrong for CPU-bound work under the GIL. Processes are heavier to start (a whole interpreter each) and share nothing by default, which is exactly wrong for a quick I/O-bound fetch and exactly right for CPU-bound work that needs more than one core actually computing at once.
Where pandas/NumPy go from here: NumPy's own array operations already release the GIL internally for many calls and often use multiple cores through its own C code, without needing this module at all — a different mechanism for a similar goal. Not covered further here, per MISSION.md; this course teaches the standard-library mechanism, not NumPy's internals.
