Writing the client-side rule itself (jQuery Unobtrusive Validation adapters)

Lesson 134 got ClassicMovieAttribute to emit data-val-classicmovie and data-val-classicmovie-year onto the rendered form field, then stopped — that lesson's own scope line named the missing piece explicitly: "the matching JavaScript adapter itself." Markup alone checks nothing. This lesson writes the two jQuery calls that turn those attributes into an actual in-browser check.

1 · A rule, and the adapter that wires it to markup

Two separate calls do two separate jobs. The first registers the actual check, by name, with jQuery Validation itself — the generic engine Lesson 134 named as the thing that "runs named rules against form fields":

$.validator.addMethod('classicmovie', function (value, element, params) {
    var genre = $(params[0]).val(), year = params[1], date = new Date(value);

    // The Classic genre has a value of '0'.
    if (genre && genre.length > 0 && genre[0] === '0') {
        // The release date for a Classic is valid if it's no greater than the given year.
        return date.getUTCFullYear() <= year;
    }

    return true;
});

Nothing here mentions HTML attributes at all — addMethod just teaches jQuery Validation a function named 'classicmovie' that takes the field's current value, its DOM element, and a params array, and returns true or false. On its own, nothing on the page would ever call it.

2 · $.validator.unobtrusive.adapters.add() reads the markup

The second call is the bridge Lesson 134's own markup needed. It tells jQuery Unobtrusive Validation — the adapter Lesson 134 described as scanning the page for data-val-* and feeding them to jQuery Validation — exactly how to read the classicmovie attributes and activate the rule just registered above:

$.validator.unobtrusive.adapters.add('classicmovie', ['year'], function (options) {
    var element = $(options.form).find('select#Movie_Genre')[0];

    options.rules['classicmovie'] = [element, parseInt(options.params['year'])];
    options.messages['classicmovie'] = options.message;
});

Three arguments, three jobs. 'classicmovie' is the rule name — it has to match both the data-val-classicmovie attribute Lesson 134's AddValidation wrote and the name just given to addMethod above. ['year'] lists which extra parameters to pull off the markup — Microsoft's own docs describe this as "additional parameters the validator needs," read here from data-val-classicmovie-year. The callback receives an options object: options.params['year'] holds that attribute's value as a string, so the adapter parses it with parseInt; options.rules['classicmovie'] is set to the exact [element, year] array the rule function's own params parameter expects; and options.messages['classicmovie'] carries over the error text the server already rendered into data-val-classicmovie, so the browser's error message matches the server's without being retyped.

Frontend-habit trap: this is still just jQuery form-validation code — nothing here should feel unfamiliar as JavaScript. The new part is the contract, not the syntax: the rule name, the params array, and the options.rules/options.messages assignments all have to line up exactly with what the C# AddValidation method wrote as HTML attributes. Rename one side without the other and the rule silently never fires — no error, no console warning, the checkbox or date field just stops being validated client-side.

Scope line

This lesson covers $.validator.addMethod for registering a named client-side rule function, and $.validator.unobtrusive.adapters.add for reading a rule's data-val-* parameters and activating it — the one piece Lesson 134's own scope line named as not yet covered. It does not cover writing this same check without jQuery (a vanilla-JS or framework-native client validator), nor shipping this adapter file project-wide via a bundler — both reasonable next steps, not today's.
