Files, formats & context managers

Day 5 ended with a throwaway line: "a file object is already a built-in iterator." Today that claim gets made precise, plus the safety mechanism around it (with) and the two structured formats you'll actually read and write — csv and json. By the end, you'll be able to open a real CSV lazily, line by line, into structured dicts — exactly what tomorrow's ETL capstone builds on.

Bridge from SQL: a CSV file is the closest thing Python sees to a raw, un-typed database export — rows of text, one line per record, comma-separated columns. Today's job is turning that text into the same row-of-values shape SQL already gives you for free, by hand.

1 · open() and file modes

open(path, mode) returns a file object connected to a file on disk. The mode string says what you intend to do with it: "r" reads (the file must already exist), "w" writes from scratch (creates the file if missing, erases it first if it already has content), and "a" appends (creates if missing, adds to the end if not):

f = open("notes.txt", "w")   # create/overwrite, ready to write
f.write("first line\n")
f.write("second line\n")
f.close()                        # flush to disk and release the file handle

f = open("notes.txt", "r")   # read what's there
f.read()                         # "first line\nsecond line\n" — the whole file as one string
f.close()

Forgetting the mode's effect is a common early mistake: opening an existing file with "w" to just "add a line" silently destroys everything already in it. When in doubt about whether a file exists yet, "a" is the safer default for adding to a log-like file.

2 · Why a file object is an iterator — not a new mechanism

Day 5 built the iterator protocol: iter() gets you an iterator, next() pulls one item, StopIteration ends it, and a for loop is exactly that pattern automated. A file object opened for reading already is such an iterator — each call to next() on it returns the next line, so for line in f is not a special file-reading trick, it's the identical mechanism Day 5 taught, applied to a source that happens to be a file:

f = open("notes.txt", "r")
for line in f:              # same iter()/next()/StopIteration protocol as Day 5's lists and generators
    print(line.strip())    # .strip() drops the trailing "\n" each line keeps
f.close()

This is also why a file scales to sizes far bigger than memory the same way a generator does: for line in f never reads the whole file into one string first — it pulls one line at a time, exactly the constant-memory argument Day 5 made for yield. A file object is Python's own built-in generator-like iterator, not a look-alike.

3 · The problem with solves: a leaked or locked file on exception

Every file object opened with open() holds a real operating-system resource — a file handle — until .close() runs. Calling .close() by hand works fine as long as nothing goes wrong in between. The moment an exception is raised between open() and the matching .close(), the close line is skipped, and the handle stays open for the rest of the program — unflushed writes can be lost, and on some platforms the file stays locked to other processes:

# manual open/close — LEAKS the handle if process_line() raises
f = open("notes.txt", "r")
for line in f:
    process_line(line)          # if this raises, the line below never runs
f.close()                        # SKIPPED on exception — handle stays open, leaked

The with statement fixes exactly this. with open(...) as f: guarantees the file gets closed when the block ends, whether it ends normally or via an exception:

# with — guaranteed to close even if process_line() raises
with open("notes.txt", "r") as f:
    for line in f:
        process_line(line)      # if this raises, close() STILL runs before the exception propagates
# f is already closed here, exception or not — no line of cleanup code to forget

Nothing about reading the file changed between the two versions — only the guarantee around cleanup. That guarantee is why with is the only spelling of open() you should reach for from here on.

4 · The context manager protocol: __enter__ and __exit__

with is not special-cased for files — it's a general protocol any object can support. A context manager is any object with two special methods: __enter__, called when the with block starts, and __exit__, called when it ends — normally or via exception:

with open("notes.txt") as f:
    ...
# roughly equivalent to, but exception-safe the way manual code above wasn't:
f = open("notes.txt").__enter__()
try:
    ...
finally:
    f.__exit__(None, None, None)   # __exit__ always runs, exception or not — this line is what .close() needs

You won't write __enter__/__exit__ yourself yet — that's a later lesson on writing your own classes. What matters today is recognizing the shape: as f binds whatever __enter__ returns (the file object itself, for open()), and the finally-like guarantee on __exit__ is precisely what made section 3's second version safe. Whenever you see with X() as name: in someone else's code, read it as "acquire a resource, guaranteed to release it no matter what happens inside."

5 · Reading CSV: csv.reader and csv.DictReader

A CSV file is just text — comma-separated values, one record per line — but hand-splitting on "," breaks the moment a field contains a comma inside quotes. The standard library's csv module handles that correctly. csv.reader gives each row as a plain list of strings:

import csv

with open("sales.csv") as f:
    reader = csv.reader(f)
    header = next(reader)         # ['city', 'amount'] — first row, pulled like Day 5's next()
    for row in reader:            # each row: ['Hanoi', '120'] — a list, strings, no header attached
        print(row[0], row[1])

csv.reader(f) wraps the file's own line-by-line iteration (section 2) with comma-and-quote-aware splitting — it's still lazy, one row per next(), nothing pre-loaded. Indexing by position (row[0], row[1]) works but reads poorly and breaks silently if a column is ever reordered. csv.DictReader fixes that by using the first row as field names automatically, handing back each row as a dict:

with open("sales.csv") as f:
    reader = csv.DictReader(f)      # first line consumed automatically as the header
    for row in reader:
        print(row["city"], row["amount"])   # {'city': 'Hanoi', 'amount': '120'} — keyed by column name

Every value out of either reader is a str — CSV has no number type, so row["amount"] is the string "120", not the int 120; converting it (int(row["amount"])) is the reader's job, same as Day 5's parse_rows already did by hand for its comma-split lines.

6 · JSON: json.load, json.dump, and why it maps onto dict/list for free

CSV is flat — rows and columns, nothing nested. JSON is the standard text format for nested data — objects ({...}) and arrays ([...]) that can hold each other arbitrarily deep. The reason it's easy in Python specifically: JSON's {...} and [...] are, syntactically, the exact shapes Day 1 already called dict and list literals. The json module reads a JSON file straight into real Python dict/list objects, and writes them back out the same way:

import json

data = {"city": "Hanoi", "amount": 120, "tags": ["retail", "q3"]}

with open("record.json", "w") as f:
    json.dump(data, f)               # writes {"city": "Hanoi", "amount": 120, "tags": ["retail", "q3"]}

with open("record.json") as f:
    loaded = json.load(f)            # reads it straight back into a real dict, ints stay ints

loaded == data                       # True — same shape, same types, no strings-for-everything like CSV

Unlike CSV, JSON keeps types: 120 loads back as an int, not a string, and ["retail", "q3"] loads back as a real list nested inside the dict. That's the whole appeal — no re-parsing numbers by hand the way CSV always requires. Both with blocks above are exactly section 3's pattern; json.load/json.dump always take an already-open file object, never a path string directly.

Where pandas goes from here: pd.read_csv("sales.csv") does the open, read, split, and type-conversion of section 5 in one eager call, loading every row into memory as a DataFrame at once. Not covered here; that's data/'s job, and this is the only sentence in this lesson that mentions it.

7 · Setting up tomorrow: lazy CSV rows, ready for structure

Sections 2 and 5 already combine into exactly what the capstone needs: a file is an iterator (section 2), csv.DictReader turns each line into a dict lazily (section 5), and Day 5's generator functions can wrap that in a further lazy transform — no new mechanism, just today's and Day 5's tools chained:

import csv

def read_sales(path):
    with open(path) as f:
        reader = csv.DictReader(f)
        for row in reader:
            yield {"city": row["city"], "amount": int(row["amount"])}   # str -> int, once per row

for record in read_sales("sales.csv"):   # one row in memory at a time, all the way from disk
    print(record)

read_sales is a generator function exactly like Day 5's parse_rows, except its source is a real CSV file instead of a hardcoded list of strings, and its rows arrive already comma-split and keyed by csv.DictReader instead of hand-split on ",". Tomorrow's capstone takes this exact dict-per-row shape and gives each row a proper structure — a dataclass — instead of a loose dict with no guarantee of which keys exist.
