Dead-letter queues: what happens to a job that never succeeds

Lesson 10 taught that jobs get retried, so they must be safe to run twice. It never asked the other question: what if a job keeps failing no matter how many times it's retried? Today: the failure mode a plain retry loop can't fix on its own, and the queue-level fix for it.

1 · Retries assume the failure is temporary

Lesson 10's worker loop and Lesson 32's backoff both share the same quiet assumption: if a job fails, trying again will eventually work, because the failure was transient — a dependency blipped, a network call timed out. Most failures really are like that. Some aren't. A job can fail for a reason that no amount of retrying fixes: a corrupted or malformed payload that the handler can never parse, a permanently-invalid foreign key the row it references was hard-deleted, a bug in the handler itself that throws on every single attempt. This is a poison message: a job that fails every time, forever.

Left alone, a plain retry loop treats a poison message exactly like a transient one — it just keeps trying. Depending on how the queue is built, that produces one of two bad outcomes: the same job is dequeued and retried forever, burning worker time on work that will never succeed, or — worse in a queue that processes jobs roughly in order — that one broken job sits at the front and blocks every job queued behind it from ever being tried.

Frontend-habit trap: this is the backend version of an infinite retry loop in a useEffect that never gives up on a failed fetch — except here the "loop" is a whole worker process, and the "blocked UI" is every other job waiting in line behind it.

2 · The fix: stop retrying after N attempts, but don't lose the job

The naive fix — just give up and delete the job after a few failures — trades one problem for a worse one: Lesson 10's whole point was that a job must never be silently dropped. Deleting a failed job after its last retry is exactly the silent drop Lesson 10 built the entire queue-based design to avoid.

The actual fix keeps Lesson 10's "never silently lose it" promise while still refusing to retry forever: after a bounded number of failed attempts, move the job out of the live queue into a separate holding table — a dead-letter queue (DLQ) — instead of leaving it to retry indefinitely or deleting it outright. The job still exists, in full, with its payload and its last error, waiting for a human to look at it. It's off the live queue, so it can no longer block or waste attempts on work behind it, but nothing about it was thrown away.

// moveToDeadLetter copies a permanently-failed job into a separate holding
// table for manual inspection, then removes it from the live queue so it
// stops blocking work behind it -- same transaction, so neither write can
// happen without the other (Lesson 6's atomicity, applied here).
func moveToDeadLetter(ctx context.Context, db *sql.DB, j job, lastErr error) error {
    tx, err := db.BeginTx(ctx, nil)
    if err != nil {
        return err
    }
    defer tx.Rollback() // no-op if Commit already ran

    _, err = tx.ExecContext(ctx,
        `INSERT INTO dead_letter_jobs (id, kind, payload, attempts, last_error, failed_at)
         VALUES ($1, $2, $3, $4, $5, now())`,
        j.ID, j.Kind, j.Payload, j.Attempts, lastErr.Error(),
    )
    if err != nil {
        return err
    }
    _, err = tx.ExecContext(ctx, `DELETE FROM jobs WHERE id = $1`, j.ID)
    if err != nil {
        return err
    }
    return tx.Commit()
}

// runWorker processes jobs, retrying failures up to MaxAttempts before
// routing a permanently-failing job to the dead-letter table instead of
// leaving it to retry forever and block the jobs behind it.
func runWorker(ctx context.Context, db *sql.DB) {
    for {
        j, ok := dequeueJob(ctx, db)
        if !ok {
            time.Sleep(time.Second)
            continue
        }

        err := processJob(ctx, j)
        if err == nil {
            continue // success; real code marks it done here
        }

        j.Attempts++
        if j.Attempts >= j.MaxAttempts {
            if dlErr := moveToDeadLetter(ctx, db, j, err); dlErr != nil {
                log.Printf("dead-letter move failed for job %d: %v", j.ID, dlErr)
            }
            continue
        }
        // real code re-enqueues with backoff here -- Lesson 32's territory,
        // not repeated here since the retry-spacing decision was already taught
    }
}

3 · Choosing "retry again" vs. "dead-letter it" reuses a rule you already have

Lesson 32 already drew the line this decision needs: its retriable check separated failures worth retrying (a 5xx, a network blip) from ones that aren't (a 4xx — the request itself was wrong, and retrying repeats the identical mistake). The same split applies here, one level up: a job attempt count reaching its max isn't the only reason to dead-letter something. If processJob can classify its own error the way Lesson 32's HTTP client could — "this is structurally wrong and will never succeed, no matter how many times I try" — a poison message can be dead-lettered on the first failure instead of wasting its whole retry budget finding out the slow way. Both routes end in the same place: the DLQ, not silent deletion.

4 · A DLQ is not a fix by itself — it's a place to notice the problem

Moving a job to a dead-letter table doesn't repair whatever was wrong with it. If nothing ever reads that table, dead-lettering a job is just a slower, more polite way of losing it — the jobs pile up, unseen, and the underlying bug (the bad payload, the missing foreign key, the handler crash) never gets fixed. A dead-letter queue only pays off paired with two things: an alert when a row lands in it (Lesson 13's monitoring territory — "is this happening now," not just "what happened"), and someone actually looking at the payload and the stored error to decide whether to fix and re-enqueue the job or discard it for good. The table is a queue for human attention, not a second automatic retry mechanism.

Plain retry (Lesson 10/32)Dead-letter queue
Assumes the failure isTransient — will likely clear upPossibly permanent — may never clear up
What happens after max attemptsNothing built-in — risks retrying foreverJob is moved out of the live queue
Is the job lost?No, if retried; yes, if deleted on give-upNo — kept in full for inspection
Blocks jobs behind it?Can, in an ordered queueNo — removed from the live queue
Needs a human eventually?No, if it succeeds on retryYes — someone has to triage it

Q: "Your job queue has one job that's been failing for an hour and blocking everything behind it. What went wrong, and how would you prevent it?" A strong answer, out loud: "The queue is treating a permanent failure the same way it treats a transient one — retrying forever instead of recognizing this job will never succeed. I'd cap the retry attempts, and once a job exhausts them, move it into a separate dead-letter table in the same transaction as removing it from the live queue, rather than deleting it outright — that keeps Lesson 10's 'never silently lose a job' guarantee while stopping it from blocking work behind it. That table needs an alert wired to it, though — a DLQ that nobody watches just delays the data loss instead of preventing it." The signal: naming that a DLQ preserves the job rather than discarding it, and that it only works paired with someone actually watching it.
