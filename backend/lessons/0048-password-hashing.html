Password hashing: storing a secret you should never be able to read back

Lesson 4 showed a request proving "this is Lan, still logged in" via a session or a JWT — but both start from the same first moment: a login handler checking a password against something stored in the database. What's actually stored there, and why it must never be the password itself, was left unsaid. Today: the one column every backend has and almost never explains.

1 · The wrong answer, and why it's tempting

The naive version works on day one: a users table with a password column, INSERT the value the signup form sent, SELECT ... WHERE password = $1 to check a login. It's the same instinct as storing any other form field — nothing about the schema stops you. The problem isn't correctness today; it's what happens the day your database leaks. Breaches happen to careful teams, not just careless ones — a misconfigured backup, a compromised replica, a subpoenaed snapshot. The only question that matters is what an attacker holding a full copy of the users table can do with it. If the password column holds the actual password, the answer is: log in as everyone, immediately, and — because most people reuse passwords — try the same values against every other site that user has an account on, an attack with its own name: credential stuffing. Your breach becomes every user's breach, everywhere they reused that password.

2 · Hashing is not encryption

The fix is to never store the password at all — store something derived from it that's useless on its own. That means reaching for a hash function, not encryption. The distinction is the entire lesson: encryption is meant to be reversed by whoever holds the key — exactly the property you want for data you'll need back later, like Lesson 30's webhook payloads or a credit card number a payment processor tokenizes. A password should never come back. Nobody, including your own backend, ever needs to answer "what was this user's password" — only "does this new guess match." Reaching for encryption on a password column is a common but serious mistake: it means whoever holds the encryption key (a config file, an environment variable, Lesson 21's territory) can decrypt every password in the table at will. A hash has no key to steal — the one-way property is the whole point.

3 · Why a plain hash still isn't enough

So: hash the password, store the hash, compare hashes on login. Better — but reaching for a fast, general-purpose hash like SHA-256 is still wrong, for a reason that has nothing to do with SHA-256 being broken. It's too fast. Modern hardware computes billions of SHA-256 hashes per second, which is exactly what you want for verifying a file download and exactly what you don't want for a password: an attacker with a stolen hash column can try billions of guesses per second against it, offline, with no rate limit to stop them — Lesson 11's rate limiting only defends the login endpoint, and it's irrelevant once the hashes are already stolen.

Two more problems stack on top of raw speed. First, identical passwords produce identical hashes — so an attacker who precomputes hashes for the most common million passwords (a rainbow table) can reverse thousands of stolen hashes by lookup alone, no guessing required. The fix for that half is a salt: a random value, unique per user, mixed into the input before hashing, so two users who both chose "password123" end up with two unrelated hashes. Second, even salted, SHA-256 is still fast — so the real fix has to also slow the function down.

4 · The actual answer: a slow, tunable, self-salting hash

Password hashing calls for a purpose-built function that is deliberately expensive to compute, with a work factor you can dial up as hardware gets faster, and salting built in automatically so nobody forgets it. Two names cover nearly every real system: bcrypt, older and everywhere; and Argon2id, newer and OWASP's current top recommendation because it also makes memory expensive, not just time — a GPU has thousands of cheap compute cores but nowhere near that much fast memory per core, so a memory-hard function narrows the attacker's hardware advantage far more than bcrypt's time-only cost does. Both remain acceptable; bcrypt is a completely reasonable default if that's what your language's ecosystem makes easiest.

import "golang.org/x/crypto/bcrypt"

func hashPassword(plain string) (string, error) {
    // bcrypt generates its own random salt and embeds it in the output --
    // there is no separate salt column to manage.
    hash, err := bcrypt.GenerateFromPassword([]byte(plain), bcrypt.DefaultCost)
    return string(hash), err
}

func checkPassword(plain, storedHash string) bool {
    // Constant-time comparison happens inside this call -- the same
    // timing-attack defense Lesson 30 named for webhook signatures,
    // bcrypt just does it for you here.
    err := bcrypt.CompareHashAndPassword([]byte(storedHash), []byte(plain))
    return err == nil
}

Note what never appears anywhere in this code: a separate salt column, or a secret key to protect. bcrypt.GenerateFromPassword generates a fresh random salt per call and stores it packed inside the returned hash string itself — $2a$10$N9qo8uLOickgx2ZMRZoMy..., where the cost factor and salt are both embedded, human-readable, right there in the value you'd store in the password_hash column. CompareHashAndPassword reads the salt back out of that string automatically; nothing about verifying a login ever needs to know the salt as a separate piece of data.

Frontend-habit trap. A "never send the password back to the client" instinct probably already feels obvious — you'd never render user.password in a response, the same instinct Lesson 23's excessive-data-exposure lesson named. This lesson is that same instinct pushed one layer deeper: the backend itself should never be able to produce the plaintext password either, not just refuse to send it. If your own server can answer "what is this user's password," something upstream of the hash is already wrong.

Q: "Why not just encrypt passwords instead of hashing them — isn't encryption stronger?" A strong answer, out loud: "Stronger isn't the axis that matters here — reversibility is. Encryption is designed to be reversed by whoever holds the key, which is exactly wrong for a password: nobody, including our own backend, should ever be able to recover a user's plaintext password, because if we can, so can anyone who steals the key. Hashing is one-way by design — there's no key to steal, because there's nothing to decrypt. And a general-purpose hash like SHA-256 still isn't enough on its own, since it's fast enough to brute-force billions of guesses a second against a stolen table — that's why we use bcrypt or Argon2id specifically: they're deliberately slow, salted automatically, and tunable as hardware gets faster." The signal: naming reversibility as the actual axis, not reaching for "encryption sounds more secure" as a gut reaction.
