array: typed sequences without a list's per-item overhead

A plain list never actually stores its values directly — it stores a pointer to each one, and every int or float it points at is its own separate Python object with its own header overhead. That is flexible (a list can mix any types at all) but wasteful the moment every element is the same primitive kind — a million sensor readings, a column of integer IDs, a buffer of raw samples. The standard-library array module is the plain-Python answer: a sequence that behaves like a list but packs its values directly, at the cost of allowing only one declared type.

1 · Declaring one: a typecode, then values

array.array(typecode, iterable) takes a one-character typecode fixing what every element must be, then builds the array from any iterable of matching values:

import array

ids = array.array('i', [101, 102, 103])   # 'i' = signed int, platform-dependent width (commonly 4 bytes)
print(ids.typecode, ids.itemsize)        # i 4 -- confirmed live
print(list(ids))                      # [101, 102, 103]

Most of a list's API works unchanged — indexing, slicing, append(), extend(), pop(), iteration, even slice assignment with another array of the same typecode — confirmed live. The difference that matters is typecode choice: 'i'/'l' for signed integers of different guaranteed minimum widths, 'f'/'d' for single- and double-precision floats. The full table of typecodes and their guaranteed minimum sizes is in the docs linked below; reaching for 'i' or 'd' covers the overwhelming majority of real use.

2 · The one restriction, enforced at every write

Every element must match the declared typecode — not "close enough," checked on every append(), every construction, every assignment:

nums = array.array('i', [1, 2, 3])
try:
    nums.append(3.5)
except TypeError as e:
    print(e)   # 'float' object cannot be interpreted as an integer -- confirmed live

A list would have silently accepted 3.5 sitting right next to three ints, no complaint. This is the trade a list never makes: an array gives up mixed-type flexibility and gets, in exchange, an early, specific TypeError the moment a value doesn't belong — the same "fail loudly near the mistake" instinct Day 8's narrow exception handling already taught, applied here to data shape instead of control flow.

3 · Why bother: the packed-storage payoff, measured

A list of int stores one pointer per element, each pointing at a separate full Python int object elsewhere in memory. An array stores the raw fixed-width value directly, back to back, with no per-element object at all. Measured directly rather than assumed, for 100,000 integers outside Python's small-int cache (so each one is genuinely a distinct object, not a shared cached value):

import array, sys

n = 100_000
values = range(1000, 1000 + n)

lst = list(values)
arr = array.array('l', values)

list_total = sys.getsizeof(lst) + sum(sys.getsizeof(x) for x in lst)
array_total = sys.getsizeof(arr)

print(list_total, array_total)       # 3600056 816640 -- confirmed live
print(list_total / array_total)      # ~4.4 -- the list uses about 4.4x the memory, for the same 100,000 values

That gap is array's whole reason to exist: once every element genuinely is the same primitive numeric type, paying for a full object per element buys nothing. Two round-trip methods move an array's raw bytes in and out directly — tobytes() returns the packed bytes, and frombytes() (called on an empty array of the matching typecode) rebuilds one from them, confirmed live to round-trip exactly — handy for writing a buffer straight to a binary file or socket without going through Day 96's struct format strings one field at a time.

Where pandas/NumPy go from here: array.array is one-dimensional, plain Python, and has no vectorized math — arr + arr raises TypeError, not element-wise addition. NumPy's ndarray generalizes this exact packed-storage idea to N dimensions plus a huge vectorized operation set, and is data/'s territory entirely — not demonstrated here.
