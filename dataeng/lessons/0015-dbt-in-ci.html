1 · Fourteen days of "run it on my laptop." Today it runs on every PR.

Every build step so far has had the same weak point: it only proves the pipeline works on the one machine that just ran it. A teammate — or a future you, six months on — opens a pull request that changes fct_orders.sql, and nothing stops a typo from merging straight to main until someone happens to run dbt build by hand and notices. CI is dbt's answer: a server builds the project on every pull request, using a database that exists only for the duration of that one check.

GitHub Actions is the natural choice here since the repo already lives on GitHub — no new host, no new account. Today's first workflow does exactly what Day 1 through Day 14 did locally, just on GitHub's own runner instead of a laptop: bring up Postgres, load raw data, run dbt build.

2 · A disposable Postgres, alive only for one CI run

GitHub Actions can start a service container alongside a job — the same postgres:17 image Day 1's docker-compose.yml already pins, started fresh for this one job and thrown away when it finishes. No state carries over between runs, which is exactly the property a CI database should have: every PR gets built against a known-clean warehouse, never one some previous run left dirty.

-- .github/workflows/dbt_ci.yml
name: dbt CI

on:
  pull_request:
    paths:
      - 'food_delivery_pipeline/**'
      - '.github/workflows/dbt_ci.yml'

jobs:
  dbt-build:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:17
        env:
          POSTGRES_USER: fdp
          POSTGRES_PASSWORD: fdp_dev_password
          POSTGRES_DB: fdp
        ports:
          - 5432:5432
        options: >-
          --health-cmd pg_isready
          --health-interval 5s
          --health-timeout 5s
          --health-retries 10

    steps:
      - uses: actions/checkout@v4

      - name: Set up uv
        uses: astral-sh/setup-uv@v3

      - name: Load raw data
        run: TODO -- the same command Day 1's Verify block uses, against localhost instead of docker compose's network

      - name: dbt build
        working-directory: food_delivery_pipeline
        run: uv run --with "dbt-postgres==1.11.0" dbt build --profiles-dir .
        env:
          DBT_HOST: localhost
          DBT_USER: fdp
          DBT_PASSWORD: fdp_dev_password
          DBT_DBNAME: fdp

The TODO is today's first real skill: fill in uv run --with "psycopg[binary]" python3 scripts/generate_raw_data.py, the exact command Day 1 already verified — the service container is reachable at localhost:5432 from every step in the job, the same way docker compose's network made postgres reachable by service name locally. The env: block feeds Day 2's connection fields in as environment variables rather than a committed profiles.yml — a CI runner has no ~/.dbt/ of your own, and a profiles.yml checked into the repo would be the first real secret this course has ever risked leaking. A minimal profiles.yml committed alongside the workflow, reading each field from env_var(), is what makes this resolve:

-- food_delivery_pipeline/profiles.yml -- committed; no real secret lives in this file
food_delivery_pipeline:
  target: dev
  outputs:
    dev:
      type: postgres
      host: "{{ env_var('DBT_HOST', 'localhost') }}"
      port: 5432
      user: "{{ env_var('DBT_USER') }}"
      password: "{{ env_var('DBT_PASSWORD') }}"
      dbname: "{{ env_var('DBT_DBNAME') }}"
      schema: dbt_dev
      threads: 4

The default falls back to localhost, so nothing changes for local runs — Day 2's ~/.dbt/profiles.yml still works unmodified, since DBT_HOST is simply unset there. Push this workflow, open a throwaway PR (even a one-line comment change inside food_delivery_pipeline/ is enough to trigger it), and watch the Actions tab.

3 · state:modified+: build only what a PR actually touched

A full dbt build re-creates every model and re-runs every test, every single PR — fine at 10 models, wasteful at 200, where most PRs touch one file. dbt has a selector built exactly for this: state: compares the current project against a previous run's manifest.json and can select just what changed.

SelectorWhat it selects
state:modifiedevery model, test, source, macro-dependent node etc. whose SQL, config, columns or contract differ from the comparison manifest — plus anything brand new
state:modified+the same, plus everything downstream of each modified node (the + is the same downstream-graph operator any --select already understands)

A change to a config (materialized, incremental_strategy), a column's data_type in a contract, or a source's freshness block all count as "modified" — not just SQL text. tags and meta are deliberately excluded, since those are pure labels with no effect on what actually gets built.

state: needs something to compare against: a manifest.json from a prior dbt parse/run/build, passed via --state. Confirm the selector works before touching CI — save today's clean manifest as a stand-in "production" state, then make a real edit and see what gets picked up:

uv run --project ../dbt_env dbt parse
mkdir -p ../prod-state
cp target/manifest.json ../prod-state/manifest.json

Now add one harmless column to fct_orders.sql — TODO, add a real column your project can support without breaking Day 14's contract, such as current_timestamp as built_at — and check what state:modified+ finds, without building anything yet:

uv run --project ../dbt_env dbt ls --select "state:modified+" --resource-type model --state ../prod-state

Expected: exactly one line, food_delivery_pipeline.fct_orders — the only model whose compiled SQL actually differs from the saved manifest. (Drop --resource-type model and its two data tests, not_null and unique on order_id, show up too — state:modified+ selects every affected resource type, not just models.) Revert the column before continuing; Section 4 wires this selector into the workflow rather than leaving it as a one-off check.

Don't point --state and --target-path at the same folder. A normal dbt build overwrites target/manifest.json as part of parsing — before dbt gets a chance to diff against it — silently turning every run into a no-op comparison against itself. Keep the comparison manifest in its own directory, copied there deliberately, exactly as above.

4 · Deferral: don't rebuild what you're not testing

Selecting only fct_orders creates a new problem: fct_orders still has a real ref('stg_orders'), and stg_orders was never built in this CI run's schema, because it wasn't selected. A plain --select state:modified+ build would fail the moment it tries to query a table that doesn't exist. --defer is the fix: for any ref() that points outside the selected set, dbt resolves it against the comparison manifest's schema instead of failing — stg_orders reads from wherever the last full "production" build actually put it, not from an empty CI schema.

-- the slim-CI pattern: select only what changed, defer everything else to prod's own build
uv run --with "dbt-postgres==1.11.0" dbt build \
  --select "state:modified+" \
  --defer --state ../prod-state \
  --profiles-dir .

This is the pattern dbt's own docs call slim CI: a PR that touches one model builds and tests that model plus whatever depends on it, while every unrelated model is trusted from the last known-good build rather than rebuilt for no reason. The trade-off is real and worth naming out loud: slim CI is only as trustworthy as the manifest it defers to — if prod-state/manifest.json is stale or was built from a broken commit, a PR can pass CI against a schema that no longer reflects reality.

For today's repo, with 10 models, a full dbt build already finishes in seconds — slim CI's payoff shows up later, at the scale where a full rebuild takes minutes and most PRs touch one model. Wire it in now anyway, since the mechanism doesn't change with project size, only the time it saves:

-- .github/workflows/dbt_ci.yml -- new step, after checkout, replacing the "dbt build" step from Section 2
      - name: Fetch prior manifest
        run: TODO -- download prod-state/manifest.json from wherever the last main-branch build stored it (a release asset, an artifact from the last successful main-branch run, or a committed path -- pick one and say why)

      - name: dbt build (slim CI)
        working-directory: food_delivery_pipeline
        run: |
          uv run --with "dbt-postgres==1.11.0" dbt build \
            --select "state:modified+" \
            --defer --state ../prod-state \
            --profiles-dir .
        env:
          DBT_HOST: localhost
          DBT_USER: fdp
          DBT_PASSWORD: fdp_dev_password
          DBT_DBNAME: fdp

The second TODO is deliberately open — GitHub Actions' own actions/upload-artifact/actions/download-artifact pair, run on every successful main-branch build and fetched here, is the standard answer — worth reading before picking a different one, since a hand-rolled alternative (committing the manifest, a release asset) works but adds its own upkeep.

Q: "Walk me through what happens when a PR changes one dbt model, from push to a green check." A strong answer, out loud: "GitHub Actions starts a job with a disposable Postgres service container — same image as production, but empty and thrown away after the run. The workflow checks out the PR's code, loads whatever raw data the tests need, and instead of running a full dbt build, it runs dbt build --select state:modified+ --defer --state, pointing at a manifest.json saved from the last successful main-branch build. state:modified+ diffs the PR's compiled project against that manifest and selects only the models that actually changed plus anything downstream of them — could be config, contract, or SQL, not just text. Everything the PR didn't touch is deferred: any ref() pointing outside the selected set resolves against production's own already-built tables instead of failing on an empty CI schema. The whole thing only builds and tests what's actually at risk from this PR, and it only works because the comparison manifest is kept current — if that manifest were stale, slim CI would pass PRs against a picture of the warehouse that's already wrong." The signal: naming why defer is needed (an unselected node's ref() would otherwise hit an empty schema) rather than reciting the flag combination from memory.
