Primary key design: choosing what identifies a row

Lesson 2's glossary entry for primary key has sat unchanged since day two: "the column that uniquely identifies one row — usually an id." Every lesson since has used one without ever asking which kind. Lesson 15 built cursor pagination on the assumption that a row's key is naturally ordered; Lesson 39 explained MVCC's insert-a-new-version-never-overwrite storage without asking where in the table that new version lands. Both questions trace back to one decision made once, at table-creation time, that this course never actually taught: what should the key be?

1 · The default nobody questions: a sequential integer

The unglamorous default is a database-generated counter — Postgres calls it an identity column:

CREATE TABLE orders (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- INSERT never names id; Postgres hands back 1, 2, 3, ... in insert order

(The older SERIAL pseudo-type does the same thing through a backing sequence; GENERATED ALWAYS AS IDENTITY is the SQL-standard spelling and the one current Postgres docs recommend.) Three properties fall out of "the database just counts": the value is small (8 bytes as BIGINT), it's dense and ascending — row 1,000,001 was inserted right after row 1,000,000 — and it's guessable. That last property is usually harmless and occasionally isn't, which is where the alternative enters.

2 · The alternative: a UUID

A UUID is generated independently, by the application, the database, or even the client, with no shared counter to check in with:

CREATE TABLE orders (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    customer_id BIGINT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- e.g. 8f14e45f-ceea-467e-bd3c-33bd8e6ee2d0 -- unrelated to insertion order

That independence is the whole appeal: a client can generate an order's id before ever talking to the server (useful for Lesson 26's idempotency keys, and for offline-first writes that sync later), and merging rows from two databases never collides the way two counters both starting at 1 would. The classic gen_random_uuid() flavor (UUIDv4) pays for that independence with pure randomness — and randomness in a primary key is a cost, not a neutral fact, once you look at what the key touches.

3 · What randomness costs: index locality

Lesson 39 established that Postgres never overwrites a row — an INSERT adds a new version, and the table's primary-key index has to record where every version lives. A B-tree index (Lesson 5) stores its entries in key order across fixed-size pages. A sequential integer key inserts its entries in the same order the index already stores them in — every new row lands on the same "rightmost" page until it fills, then a fresh page opens. A UUIDv4 key inserts in effectively random order across the entire keyspace — every new row has to land on a random existing page, scattered across however many pages the table already has.

Ties to Lesson 39: this is the same "new version, not overwrite" mechanism, viewed from the index's side. An ascending key keeps writes concentrated on whichever page is currently the newest — that page tends to already be in memory (cache-hot) from the last insert. A random key spreads writes across pages that were written long ago and likely aren't in memory anymore, forcing Postgres to read a cold page off disk before it can insert into it. Same storage engine, same row-versioning; the key's ordering decides whether an index insert is a cache hit or a disk read.

Concretely, that means a UUIDv4-keyed table's primary-key index grows more fragmented and cache-unfriendly than a sequential-keyed one at the same row count — a real, measurable write-throughput cost, not a theoretical one. It doesn't make UUIDs wrong; it means "UUID vs. integer" is a genuine trade-off, not a style preference.

4 · What sequential keys cost: guessability

The cost runs the other way too. Lesson 23 named excessive data exposure as an internal model's fields leaking into a response body it was never meant to reach. A guessable primary key opens a narrower but related door: ID enumeration. GET /orders/1048 tells anyone watching the network tab that order 1048 exists, and that trying 1047 or 1049 will very likely hit a real row too — the id is a hint about how many orders exist in total and an open invitation to enumerate every one of them. Lesson 12's authorization check (does this caller own order 1048?) still has to run either way, so a guessable id is never a substitute for that check — but it turns a single missing authorization check into a table-scan-by-hand vulnerability instead of a one-off mistake, and it hands a competitor your order volume for free just by watching one response header. A UUID closes that specific leak: seeing id 8f14e45f-... gives an attacker nothing to increment.

5 · The newer answer: sortable UUIDs

The two costs above — an index that likes ascending keys, an API that dislikes guessable ones — used to be a real either/or choice. UUIDv7 (and the similar, non-UUID-standard ULID) split the difference: the leading bits are a millisecond timestamp, the trailing bits are random. The result sorts in creation order — restoring the index locality that section 1's sequential key had — while staying unguessable enough in the trailing bits that an attacker can't enumerate neighboring rows the way a bare counter allows. It isn't a strict win: a UUIDv7 still costs 16 bytes against an 8-byte BIGINT, and its leading timestamp bits do reveal roughly when a row was created, which a pure UUIDv4 doesn't. It's the option worth defaulting to today for a new table where both index write-locality (restoring section 1's ascending, cache-hot insert pattern) and id guessability (section 4's concern) both matter, which in practice is most public-facing tables.

Frontend-habit bridge: this is the same trade-off as choosing a React key prop. An array index is free and already ordered, but it's meaningless once the list reorders or an item is removed from the middle. A stable, content-derived id costs a little more to generate and carries no ordering information of its own — exactly like a UUIDv4's randomness. UUIDv7 is the "best of both" option a key prop rarely gets: stable identity and an ordering baked in for free.

6 · Where this actually gets decided

This is a schema-design call made once, at CREATE TABLE time, and expensive to reverse later — Lesson 19's migration lesson covers the mechanics of changing a column's type on a live table, and a primary key's type is exactly the kind of column that touches every foreign key pointing at it. The practical default: an internal, request-scoped table with no public-facing id (an audit log row, an internal join table) rarely needs anything more than a plain sequential key — nobody outside the service ever sees the value. A table whose id appears in a URL, a webhook payload, or any response body a client can inspect is the one where guessability and sortability both start to matter, and UUIDv7 earns its extra 8 bytes.

Q: "Would you use an auto-increment integer or a UUID for a new table's primary key?" A strong answer, out loud: "It depends on whether the id is ever exposed outside the service. A sequential integer is smaller and inserts are cache-friendly — Postgres's B-tree just appends to the newest page — but it's guessable, so if this id shows up in a URL or API response, a caller can enumerate neighboring rows just by incrementing it, which turns any missed authorization check into an easy scan. A UUIDv4 fixes the guessability but inserts in random order, which fragments the index and turns cache-hot writes into cold disk reads at scale. My default for anything public-facing now is UUIDv7 — it sorts in creation order like the integer does, so the index stays cache-friendly, while the random trailing bits keep it unguessable. I'd only reach for a plain sequential key on a purely internal table nothing outside the service ever sees." The signal: naming the index-locality cost specifically, not just "UUIDs are more secure," and knowing UUIDv7 exists as the answer to both costs at once.
