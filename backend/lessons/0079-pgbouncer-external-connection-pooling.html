PgBouncer: pooling the pools

Lesson 18 named the fix for the multiplication problem — MaxConns per instance times instance count outrunning Postgres's max_connections — in one sentence: "put an external pooler like PgBouncer in front of Postgres." It linked the tool and moved on. This lesson is the sentence that was owed: what PgBouncer actually is, how it multiplexes many app-side connections onto few real ones, and the trade-off its three pooling modes make.

1 · The gap Lesson 18's own pool can't close

pgxpool's pool (Lesson 18) is per-process. Each instance opens its own set of real Postgres connections and keeps them warm — that's the pool a handler borrows from. It solves "don't reopen a connection every request." It cannot solve the multiplication problem, because that pool has no visibility into any other instance's pool; scaling from three instances to thirty just multiplies the same per-instance MaxConns by thirty, and Postgres's max_connections (100 by default, per the PostgreSQL Manual, minus a handful reserved for superusers) doesn't move. A per-process pool can be sized carefully and still lose this fight the moment autoscaling adds instances.

A connection pooler like PgBouncer sits between every instance's pool and Postgres itself, as its own separate process. Every instance now points its DSN at PgBouncer instead of Postgres directly; PgBouncer holds a small, fixed number of real Postgres connections and hands them out to however many client connections actually show up, whether that's 3 instances or 300.

2 · What "multiplexing" means here

The word doing the real work is multiplexing: many client connections share few real ones over time, not all at once. A client connection to PgBouncer isn't the same object as a real Postgres backend process — PgBouncer decides, per some unit of work, which real connection a given client borrows next, then takes it back. That unit of work is the pooling mode, and it's the one setting that actually decides how safely this can be done.

Pool modeReal connection returned to the poolSafe with
sessionwhen the client disconnectsanything, including session-level features (advisory locks from Lesson 56, SET variables)
transactionwhen the current transaction commits or rolls backmost application code — one request, one transaction, one borrow
statementafter each individual statementonly autocommit, single-statement traffic — no multi-statement transactions at all

Session mode is the least aggressive multiplexing — it barely improves on not pooling at all, since a client that opens a connection and does nothing for a while still occupies a real backend the whole time. Transaction mode is where most of PgBouncer's actual value lives: a real connection is only tied up for the length of one transaction, then it's free for a different client's request, which is how a fixed pool of, say, 20 real connections can serve hundreds of app-side connections that are mostly idle between requests — exactly the mismatch Lesson 18 named ("most services need far fewer concurrent connections than requests-per-second").

3 · The cost transaction mode charges for that reuse

Transaction mode's speed comes from breaking an assumption Lesson 18's own pool never had to break: that a single client connection maps to a single, stable real connection for its whole lifetime. Session-level state — a SET search_path, a temp table, an advisory lock taken with pg_advisory_lock and expected to still be held later — lives on whichever real connection happened to run it, and the next statement from that same client might land on a completely different real connection with none of that state. Lesson 56's advisory locks assumed one session held a lock across multiple statements; that assumption breaks under transaction-mode pooling unless the lock and its release both happen inside one transaction.

This is the trade transaction mode makes explicit: give up per-connection session state, get to run far more app-side connections than max_connections would otherwise allow. It is not a free multiplier — it is the same "isolation moves outward, cost shows up somewhere else" shape Lesson 78 walked through for multi-tenant schemas, just applied to connections instead of tenants.

4 · Where it actually sits

Nothing about the instance's own code changes — the DSN just points at PgBouncer's port instead of Postgres's, and pgxpool keeps working exactly as Lesson 18 described, borrowing and releasing from its own per-instance pool. PgBouncer is the second, outer layer: instance pools multiplex handlers onto a modest number of app-side connections; PgBouncer multiplexes every instance's app-side connections onto a small, fixed number of real Postgres ones. Two pools, two different problems — per-instance pooling saves the connect-handshake cost per request; PgBouncer saves Postgres from the instance-count multiplication that no amount of per-instance tuning alone can fix.

Q: "We autoscaled to handle a traffic spike, and now the database is refusing connections. What's going on, and what would you check?" A strong answer, out loud: "I'd check whether the new instance count times each instance's pool size has pushed total connections past max_connections — that's the classic multiplication problem, and autoscaling is exactly when it bites, since instance count grows without anyone revisiting pool math. If instance count is genuinely going to keep growing, I'd put PgBouncer in front of Postgres in transaction pooling mode, so every instance talks to a small fixed number of real connections instead of each one claiming its own slice of max_connections. I'd also check the codebase for anything relying on session-level state — advisory locks, SET commands — since transaction mode breaks that unless it's scoped to one transaction." The signal: naming the multiplication problem first, then the specific pooling-mode trade-off, not just "add a pooler" with no cost attached.
