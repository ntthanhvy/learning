.ewm(): the moving average that never forgets, just discounts

Chào bạn — Lesson 71's teaser named no single dangling candidate, so this round is a fresh curriculum/glossary scan again. Lesson 13 taught .rolling() (a fixed-size sliding window) and .expanding() (a window that grows from the start) — but a fresh grep of all 71 lessons and the glossary confirms their third sibling, .ewm() (exponentially weighted moving average), is still genuinely zero-hit. It closes that trio, and it is the actual smoothing method behind "EWMA" in time-series and finance interview questions.

1 · The gap: rolling forgets sharply, expanding never forgets at all

Lesson 13's .rolling(window=N) only looks at the last N rows — row N+1 falls off a cliff, weighted zero, the instant it exits the window. Lesson 13's .expanding() is the opposite extreme: every row ever seen counts equally forever, no matter how old. Real smoothing (a stock's moving average, a rolling conversion-rate estimate) usually wants a middle ground: recent rows should matter MORE than old ones, but old rows should never be discarded outright — just discounted. Neither .rolling() nor .expanding() can express that.

2 · .ewm(): a running average where every past row still counts, less and less

.ewm() ("exponentially weighted moving average," often shortened to EWMA in interviews) is that middle ground: every row ever seen keeps some weight forever, but the weight shrinks geometrically the further back it is — recent rows dominate, ancient rows fade toward (but never quite reach) zero. Confirmed directly (pandas 3.0.6), on this course's real orders_raw.csv fixture, An's two cleaned orders (120.0 on 01-05, 42.0 on 01-10):

an["amount"].ewm(span=2, adjust=False).mean()
# 0    120.0   -- first row: nothing to average yet, so it's just itself
# 1     68.0   -- NOT a plain average of 120 and 42 (that would be 81.0,
#               -- rolling(2).mean()'s answer); 42 counts more than 120 here

Exactly one of com=, span=, halflife=, or alpha= must be passed to pick the decay rate — span=2 above means "decay roughly like a 2-row rolling window would," internally converted to alpha = 2 / (span + 1). Confirmed directly: passing two of them together, or none at all, both raise ValueError — pandas will not guess which decay parameterization you meant.

SQL bridge: plain SQL has no built-in EWMA — it isn't expressible as a fixed window frame like ROWS BETWEEN N PRECEDING AND CURRENT ROW (Lesson 13's .rolling() analog), because every prior row contributes forever, just at a shrinking weight. The honest answer in an interview: "SQL doesn't have a direct equivalent; you'd hand-roll the recursive formula with a window function and a running product, or just do this step in pandas/Python instead." Naming that gap accurately is itself a signal.

3 · The gap-filling nuance: adjust=True vs adjust=False give DIFFERENT numbers

Confirmed directly, and the sharpest interview point in this lesson: adjust= is not cosmetic — it changes the actual output on early rows. With span=2 (so alpha = 2/3) on An's two values (120.0, 42.0):

an["amount"].ewm(span=2, adjust=True).mean()   # default
# 0    120.0
# 1     61.5   -- bias-corrected: divides by the sum of weights SEEN so far

an["amount"].ewm(span=2, adjust=False).mean()
# 0    120.0
# 1     68.0   -- pure recursive form: y_t = (1-alpha)*y_(t-1) + alpha*x_t

adjust=False is the textbook recursive EWMA formula, unrolled one row at a time from the actual previous OUTPUT. adjust=True (the default) instead computes a weighted average of every raw INPUT seen so far, dividing by the sum of the weights actually present — a bias correction that matters most on the first few rows, before the weights have "caught up." The two formulas converge as more rows accumulate, but on a short Series — exactly the kind an interview fixture uses — the gap is large: 61.5 vs 68.0, over 10% apart, from the identical two input numbers.

4 · No leading NaN by default, and it still chains after groupby()

Confirmed directly: unlike .rolling(window=N), whose first N-1 rows are NaN because fewer than N rows exist yet, .ewm() never has that problem — the very first row's output is just itself (there's nothing to discount against yet), so row 0 is never NaN by default. min_periods= can reintroduce a leading NaN on purpose, if a report shouldn't trust an average built from just one data point. And exactly like every other row-order-sensitive method this course has covered, .ewm() chains cleanly after groupby() to keep each entity's smoothing separate:

clean.groupby("customer")["amount"].apply(lambda s: s.ewm(span=2, adjust=False).mean())
# customer
# An    0    120.000000
#       1     68.000000
# Binh  2     35.500000
#       3    131.833333

Skipping groupby() on a multi-entity table has the same failure mode Lesson 23's shift() and Lesson 13's .rolling() already warned about: it silently bleeds one customer's early weight into another customer's smoothed average, computed on whatever the current row order happens to be — .ewm() trusts row order only, with no ORDER BY argument of its own.

Q: "How would you compute a smoothed 30-day moving average that doesn't just drop old data the instant it exits a window?" A strong answer, out loud: "That's exactly what .ewm() is for — an exponentially weighted moving average. Unlike rolling(window=30), which gives full weight to the last 30 rows and zero weight the instant a row falls outside that window, ewm() lets every row ever seen keep some weight forever, just shrinking geometrically the further back it is — so it never has a hard cliff. I'd pick the decay with span= to match roughly the same feel as a 30-row rolling window, or halflife= if I want to reason directly in 'time to decay to half weight.' One thing I'd flag: adjust=True, the default, and adjust=False give genuinely different numbers on the early rows — adjust=False is the textbook recursive formula, adjust=True bias-corrects by dividing by the weights actually accumulated so far — so I'd pick one deliberately and say which, not leave it as an unexamined default, especially since they can differ by 10%+ near the start of a short series." The signal: naming that .ewm() has no fixed-window cliff (most candidates only know .rolling()), and specifically flagging that adjust= changes actual numbers, not just style.
