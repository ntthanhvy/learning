Dataclasses, typing & an ETL capstone

Six days built six separate tools: Day 1's names/objects, Day 2's comprehensions, Day 3's dict/set grouping, Day 4's key= functions, Day 5's generators, Day 6's csv.DictReader and json. Today adds the last piece — giving a loose dict a real shape — then spends everything at once on a working ETL script: Extract a CSV, Transform it into structured records, Load a summary out as JSON. This is Phase 1's tangible proof: a script, built from an empty file, standard library only.

Bridge from SQL: a dataclass is close to a CREATE TABLE statement — a fixed set of named, typed columns every row must have. Where SQL enforces that shape at the database, a dataclass enforces it (loosely — Python doesn't check types at runtime) at the object level: every instance is guaranteed to have exactly these fields.

1 · The problem: a dict has no guaranteed shape

Day 6's read_sales() yielded rows shaped like {"city": "Hanoi", "amount": 120} — a plain dict. That works, but nothing stops a typo (row["citty"] silently raises KeyError instead of catching itself earlier) or an inconsistent record (one row missing "amount" entirely, unnoticed until it's used). A dict's keys are just strings chosen at runtime; there's no fixed list of "the fields a sales record has."

row = {"city": "Hanoi", "amount": 120}
row["citty"]              # KeyError — typo caught only when this line runs, if it ever runs

def total_for(row):
    return row["amount"] * 1.1
total_for({"city": "Hanoi"})   # KeyError: 'amount' — this row is missing a field, found late

A plain class fixes the missing-field problem — __init__ forces every instance to supply required fields — but costs boilerplate for things you'd want by default: printing a plain class instance shows <__main__.SalesRow object at 0x7f...>, not its data, and comparing two instances with == checks identity, not field values, unless you write __repr__ and __eq__ by hand.

class SalesRowPlain:
    def __init__(self, city, amount):
        self.city = city
        self.amount = amount

a = SalesRowPlain("Hanoi", 120)
b = SalesRowPlain("Hanoi", 120)
print(a)          # <__main__.SalesRowPlain object at 0x7f2b1c0a4d90> — useless for debugging
a == b            # False — different objects, even though every field matches

2 · @dataclass: fields with __repr__/__eq__ for free

A dataclass is a normal class with one decorator and a list of typed fields — no __init__ to write by hand:

from dataclasses import dataclass

@dataclass
class SalesRow:
    city: str
    amount: int

a = SalesRow("Hanoi", 120)
b = SalesRow("Hanoi", 120)
print(a)          # SalesRow(city='Hanoi', amount=120) — readable, generated for free
a == b            # True — compares field by field, generated for free
a.city            # 'Hanoi' — attribute access, same as any object

Each line under the class header — city: str, amount: int — declares a field: a name plus its type hint (section 3 explains the : str part precisely). @dataclass reads that list and generates __init__(self, city, amount), __repr__, and __eq__ automatically, so SalesRow("Hanoi", 120) works immediately with no method written by hand. A field can carry a default exactly like Day 4's default arguments:

@dataclass
class SalesRow:
    city: str
    amount: int
    currency: str = "VND"    # default — same rule as Day 4's def f(x, rate=0.1)

SalesRow("Hanoi", 120)              # SalesRow(city='Hanoi', amount=120, currency='VND')
SalesRow("HCMC", 80, "USD")          # SalesRow(city='HCMC', amount=80, currency='USD')

Day 1's mutable-default-argument trap still applies here — a field default of [] or {} raises an error at class-definition time specifically to stop you from hitting it; the fix (dataclasses.field(default_factory=list)) is worth knowing exists but is out of scope for today's records, which need only str/int/float fields.

3 · Type hints: reading (and writing) an annotated signature

The : str and : int above are type hints — Python has had them since 3.5, and they show up everywhere from here on, including every dataclass field. A hint on a plain variable or a function signature uses the same colon syntax:

city: str = "Hanoi"              # variable annotation — city is meant to hold a str

def total_for(row: SalesRow) -> float:  # row must be a SalesRow, function returns a float
    return row.amount * 1.1

Critically: Python never checks these at runtime. total_for("not a SalesRow") still runs — it just breaks (or silently misbehaves) somewhere inside, exactly as if the hint weren't there. A type hint is documentation with structure, read by humans and by external tools (editors, mypy), not a guard Python enforces itself. That's precisely why they're worth writing anyway: they turn "what does this function expect?" from a question you answer by reading the body into one the signature already answers.

Two hints from the typing module cover most real signatures. list[X] means "a list whose elements are all type X":

def total_amount(rows: list[SalesRow]) -> int:   # rows: a list of SalesRow objects
    return sum(row.amount for row in rows)     # Day 5's generator expression, straight into sum()

Optional[X] (from typing, or the newer X | None spelling) means "either type X, or literally None" — the hint for a field or parameter that might legitimately be missing:

from typing import Optional

@dataclass
class SalesRow:
    city: str
    amount: int
    region: Optional[str] = None   # region: str | None = None — same meaning, newer spelling

Today's goal is recognition and practical use for exactly these shapes — plain types, list[X], Optional[X] — not the rest of the typing module. That's enough to read almost any real-world annotated function and to write today's capstone.

Where pandas goes from here: a dataclass's fixed, typed fields are close in spirit to a DataFrame's typed columns (df.dtypes) — both are a fixed schema over rows — but a dataclass describes one row at a time in plain Python objects, not a whole columnar table. Not covered here; that's data/'s job, and this is the only sentence in this lesson that mentions it.

4 · The capstone: Extract → Transform → Load, standard library only

Every tool for this already exists across Days 1–6. ETL just names the three-stage shape the capstone script follows: Extract (read the raw CSV), Transform (turn rows into typed records and aggregate), Load (write a summary out as JSON).

Extract — Day 6's exact read_sales() generator, chaining with open() (Day 6 §3) over csv.DictReader (Day 6 §5) the way Day 5's generator functions chained stages, except now it yields a dataclass instance instead of a loose dict:

import csv
from dataclasses import dataclass

@dataclass
class SalesRow:
    city: str
    amount: int

def extract(path: str):
    with open(path) as f:               # Day 6 §3 — with guarantees the file closes
        reader = csv.DictReader(f)       # Day 6 §5 — rows as dicts keyed by column name
        for row in reader:
            yield SalesRow(city=row["city"], amount=int(row["amount"]))   # dict -> dataclass, str -> int

Transform — Day 2's comprehensions filter and reshape, Day 3's defaultdict groups by key, Day 4's key= sorts the result:

from collections import defaultdict

def transform(rows) -> list[tuple]:
    positive = [r for r in rows if r.amount > 0]    # Day 2 — list comprehension, drop bad rows
    totals = defaultdict(int)
    for r in positive:
        totals[r.city] += r.amount             # Day 3 — grouping by key, by hand
    return sorted(totals.items(), key=lambda pair: pair[1], reverse=True)  # Day 4 — key=

Load — Day 6's json.dump, writing the summary a fresh consumer (a dashboard, another script) can read back with json.load:

import json

def load(totals: list[tuple], path: str) -> None:
    summary = [{"city": city, "total": total} for city, total in totals]  # Day 2 comprehension again
    with open(path, "w") as f:
        json.dump(summary, f, indent=2)      # Day 6 §6 — Python objects out as JSON text

Wired together, the whole script is three function calls — extract stays lazy (a generator, Day 5) right up until transform's list comprehension is the first thing that actually consumes it:

def run(csv_path: str, json_path: str) -> None:
    rows = extract(csv_path)        # Extract — a generator, nothing read yet (Day 5)
    totals = transform(rows)        # Transform — comprehension + grouping + key= (Days 2-4)
    load(totals, json_path)         # Load — json.dump (Day 6)

run("sales.csv", "summary.json")
# summary.json: [{"city": "Danang", "total": 200}, {"city": "Hanoi", "total": 165}]
