binascii: bytes as hex text, and a fast checksum

Day 82's base64 turned raw bytes into text safe for JSON or a URL. There's a second, plainer way to write bytes as text that shows up constantly in logs and debug output: hex — "48656c6c6f" instead of a wall of base64. binascii is the standard-library module underneath both base64 and bytes.hex(), and it also carries a fast, non-cryptographic checksum — crc32() — a different tool from Day 59's hashlib digests.

1 · hexlify / unhexlify: bytes as a hex string, and back

binascii.hexlify() turns a bytes value into its hex-digit representation, two characters per byte — confirmed live:

import binascii

data = b"Hello, Python!"
hexed = binascii.hexlify(data)
print(hexed)       # confirmed live: b'48656c6c6f2c20507974686f6e21'
print(type(hexed))  # confirmed live: <class 'bytes'>

back = binascii.unhexlify(hexed)
print(back == data)  # confirmed live: True

binascii.hexlify() is exactly what bytes.hex() calls underneath, just returning bytes instead of str — this is the module that has existed since before bytes grew its own convenience methods, and it's still what base64 itself is built on.

2 · A readable separator, and what breaks unhexlify

hexlify() takes an optional separator and a group size, for output a human can actually scan:

print(binascii.hexlify(data, "-", 2))
# confirmed live: b'4865-6c6c-6f2c-2050-7974-686f-6e21'

try:
    binascii.unhexlify(b"abc")       # odd number of hex digits
except binascii.Error as e:
    print(e)  # confirmed live: Odd-length string

try:
    binascii.unhexlify(b"zz")       # not valid hex digits
except binascii.Error as e:
    print(e)  # confirmed live: Non-hexadecimal digit found

binascii.Error is a real, documented exception — confirmed directly as a subclass of ValueError — not a bare string check the caller has to write by hand.

3 · crc32: a fast checksum, not a security hash

Day 59 taught hashlib for content hashing and explicitly ruled out a fast general-purpose digest for anything security-sensitive. binascii.crc32() goes further the other direction: it's not cryptographic at all, it's a small, fast integer checksum meant for catching accidental corruption — in a zip entry, a network packet, a saved file — cheaply:

print(binascii.crc32(data))         # confirmed live: 1944741392
print(binascii.crc32(b""))           # confirmed live: 0

# chunked, like hashlib's .update() -- pass the running value back in
checksum = 0
for chunk in [b"Hello, ", b"Python", b"!"]:
    checksum = binascii.crc32(chunk, checksum)
print(checksum == binascii.crc32(data))  # confirmed live: True

binascii.crc32() takes the running checksum back as its second argument on each call, the same shape as Day 59's chunked .update() — but it answers "did this get corrupted by accident," never "can this be trusted," the line Day 59 already drew around hashlib.

Where this connects to Day 82: binascii.b2a_base64()/a2b_base64() are the exact functions base64.b64encode()/b64decode() call underneath — confirmed live, binascii.b2a_base64(data).rstrip(b"\n") == base64.b64encode(data) is True. Reach for base64 directly for that job; binascii is the layer below it, worth knowing exists but rarely called for base64 work by name.
Where pandas/NumPy go from here: neither library uses binascii for anything in its public API — hex dumps and checksums here are a plain-bytes, protocol-level concern, not a data-table one. Not covered further here, per MISSION.md.
