np.unique(): sorted, richer, and a stricter cousin of Series.unique()

Chào bạn — Lesson 73's teaser named two leftover zero-hit candidates: np.unique and searchsorted. A fresh grep of all 73 lessons and the glossary reconfirms both are still genuinely untaught. np.unique() is the pick today: Lesson 19 already taught Series.unique() and nunique(), but never its NumPy-level cousin — same name, genuinely different contract, and a natural setup for searchsorted() next time (which needs a SORTED array to work correctly, exactly what np.unique() always hands back).

1 · The gap: Series.unique() keeps appearance order, np.unique() always sorts

Lesson 19's Series.unique() answers "what are the distinct values" and returns them in the order they FIRST appear in the data — it never sorts. np.unique() looks like the same question but answers it differently: it always returns the distinct values SORTED, and it always returns a plain NumPy ndarray, never a Series or Index, even when called directly on a Series.

s = pd.Series(["Chi", "An", "Chi", "Binh", "An"])
s.unique()          # ['Chi' 'An' 'Binh']  -- order of FIRST APPEARANCE
np.unique(s)        # ['An' 'Binh' 'Chi']  -- always SORTED, plain ndarray

np.unique() is genuinely the NumPy-level version of the same idea — confirmed directly (NumPy 2.5.3) that it accepts a Series directly (no .to_numpy() needed), but always hands back a plain ndarray, dropping any pandas-specific wrapper.

SQL bridge: both Series.unique() and np.unique() answer the same question plain SELECT DISTINCT col answers, with no guaranteed row order in SQL either — but SQL gives you no built-in way to ask "and which original row was each distinct value's first occurrence," which is exactly what np.unique()'s return_index= adds for free, closer to a windowed ROW_NUMBER() trick than to plain DISTINCT.

2 · The four extra returns: index, inverse, counts — and how inverse differs from factorize()

Confirmed directly on this course's real orders_raw.csv customer column (['An','Binh','An','Chi','Binh','An']):

vals, idx, inverse, counts = np.unique(
    df["customer"].to_numpy(),
    return_index=True, return_inverse=True, return_counts=True,
)
vals      # ['An' 'Binh' 'Chi']      -- sorted distinct values
idx       # [0, 1, 3]                -- FIRST position each value appears at
inverse   # [0, 1, 0, 2, 1, 0]       -- codes that rebuild the original array
counts    # [3, 2, 1]                -- how many times each value occurs

return_inverse= looks identical to Lesson 68's factorize() — both hand back integer codes plus the distinct values they point into — but they disagree on ORDER whenever appearance order and sorted order differ. Confirmed directly with a case built specifically to diverge (['Chi','An','Chi','Binh','An'], where "Chi" appears first but sorts last):

pd.factorize(s)                          # uniques ['Chi','An','Binh'], codes [0,1,0,2,1] -- FIRST-APPEARANCE order
np.unique(s.to_numpy(), return_inverse=True)  # uniques ['An','Binh','Chi'], codes [2,0,2,1,0] -- SORTED order

The codes are genuinely different arrays, not just relabeled — confirmed directly, byte-for-byte unequal. They only match when factorize(s, sort=True) is used instead: confirmed directly that factorize(sort=True)'s uniques and codes then equal np.unique(..., return_inverse=True)'s output exactly. The practical rule: default factorize() and Series.unique() agree with each other (both appearance order); np.unique() and factorize(sort=True) agree with each other (both sorted) — never assume the two families' plain defaults match.

3 · NaN handling: collapsed to one, and a real crash on mixed object arrays

Confirmed directly (NumPy 2.5.3) on the real fixture's amount column (coerced with pd.to_numeric(errors="coerce"), one real NaN): np.unique() pushes NaN to the very END of the sorted output, same placement argsort() used in Lesson 73 — and collapses EVERY NaN down to a single occurrence, even though NaN != NaN normally. Confirmed with a synthetic array containing two separate NaNs ([3.0, 1.0, nan, 2.0, nan, 1.0]): the output contains exactly one nan, not two, controlled by the equal_nan=True default.

The real gotcha, confirmed directly: on an object-dtype array — a pandas string column containing a genuine Python None, not a numeric NaN — np.unique() raises outright: TypeError: '<' not supported between instances of 'float' and 'str', because sorting mixed types is undefined. Series.unique() handles the exact same data without complaint (it never sorts, so it never needs to compare a float NaN against a string). This is the sharpest practical reason to reach for Series.unique() over np.unique() on real messy string columns: sorting is not optional in np.unique(), and messy columns are exactly where that assumption breaks.

Q: "Series.unique() and np.unique() sound like the same thing — what's actually different, and when would picking the wrong one bite you?" A strong answer, out loud: "They answer the same question — what are the distinct values — but with two real differences I've verified hands-on. First, order: Series.unique() keeps first-appearance order, np.unique() always sorts, so if I need appearance order preserved I can't just swap one for the other. Second, and the one that's actually bitten real code: np.unique() has to sort to do its job, so on an object-dtype column with mixed types — say a string column with a real None in it rather than a numeric NaN — it raises a TypeError trying to compare a float to a string. Series.unique() never sorts, so it sails through the same data fine. I'd default to Series.unique() on raw, possibly-messy columns, and reach for np.unique() specifically when I want the sorted order, or need return_counts=/return_index=/return_inverse= in one call instead of chaining separate methods." The signal: naming the sort-triggered TypeError as a concrete failure mode, not just reciting "one sorts, one doesn't" — that's the same "know where the abstraction leaks" instinct as Lesson 73's stale-docstring catch.
