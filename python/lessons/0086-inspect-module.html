inspect: asking a function about its own signature

Day 12's decorators and Day 19's Depends() both rely on something never explained: how does a wrapper, or a framework, know what parameters a function takes without calling it — their names, their defaults, whether they're positional or keyword-only? The inspect module is that answer — the same mechanism FastAPI itself uses to read a route function's parameters and decide what to inject.

1 · The problem: a wrapper that doesn't know what it's wrapping

Day 12's generic decorator shape — def wrapper(*args, **kwargs): return func(*args, **kwargs) — works precisely because it never needs to know func's parameter names. But plenty of real code does need to know them: a framework that validates arguments before calling a function, a debugger printing "called with x=1, y=2," or a library deciding which of a function's parameters to fill in automatically. Hand-parsing a function's text for this would be fragile and wrong half the time. Python instead keeps that information live, on the function object itself, and inspect is the standard way to read it back out:

import inspect

def greet(name, greeting="Hello", *, loud=False):
    return f"{greeting}, {name}!"

print(inspect.signature(greet))
# (name, greeting='Hello', *, loud=False) -- confirmed live

inspect.signature(greet) never calls greet — it reads the function object's own stored metadata and hands back a description of its parameters, as data you can walk through in code.

2 · Signature and Parameter: the shape as data, not text

inspect.signature() returns a a Signature object whose .parameters is an ordered mapping from each parameter's name to a Parameter describing it — looping over it reads the same thing print() showed, but as data a program can act on:

sig = inspect.signature(greet)
for pname, p in sig.parameters.items():
    print(pname, "default:", p.default, "kind:", p.kind)
# name default: <class 'inspect._empty'> kind: POSITIONAL_OR_KEYWORD
# greeting default: Hello kind: POSITIONAL_OR_KEYWORD
# loud default: False kind: KEYWORD_ONLY        -- confirmed live

Confirmed live: a parameter with no default (name) reports its .default as the sentinel inspect.Parameter.empty, not None — None is a perfectly valid real default, so a separate sentinel is needed to mean "this parameter truly has none." loud reports kind: KEYWORD_ONLY because Day 4's * syntax marked it so — the same distinction Day 4 taught is readable back out as data here, not just enforced at call time.

3 · bind(): matching real arguments against the signature

A Signature can also check a specific set of arguments against itself — sig.bind(*args, **kwargs) matches them to parameter names exactly as a real call would, raising TypeError on a mismatch, without ever calling the function:

bound = sig.bind("Alice")
bound.apply_defaults()
print(bound.arguments)
# {'name': 'Alice', 'greeting': 'Hello', 'loud': False} -- confirmed live

.apply_defaults() fills in every parameter bind() left out with its declared default, so bound.arguments ends up a complete name-to-value mapping for the call — exactly the kind of lookup a framework needs before deciding what to pass each parameter. This is the actual mechanism behind Day 19's Depends(): FastAPI inspects a route function's signature once, at startup, to learn each parameter's name and type hint, then uses that information on every request to work out what value to supply for each one — no magic, just inspect run ahead of time.

4 · The is* family: what kind of object is this, really

inspect also answers a plainer question — not "what does this take," but "what is this" — with a family of boolean checks, useful when code receives an object of unknown origin (a plugin, a dynamically loaded callable) and needs to branch on its kind safely:

inspect.isfunction(greet)      # True -- a plain def
inspect.isclass(int)          # True -- int is a class
inspect.isbuiltin(len)         # True -- implemented in C, not Python
# all three confirmed live

These matter because callable(x) alone (seen informally in earlier lessons) only answers "can this be called with ()" — it's True for a function, a class, and an object with __call__ all alike. The is* checks tell them apart when the distinction changes what to do next.

Where pandas/NumPy go from here: neither library is introspected this way in normal use — inspect is a language/framework tool, not a data-analysis one, so there is nothing to contrast today; this callout exists only to confirm the absence, per MISSION.md's no-pandas rule.
