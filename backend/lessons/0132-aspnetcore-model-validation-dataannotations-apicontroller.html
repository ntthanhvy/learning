Request validation, now in C# too

Lesson 81 drew the line between syntactic validation (is this shaped like an email) and semantic validation (does this product id actually exist), and showed the Go shape: a JSON Schema document checked by a general-purpose validator before the handler runs. The C#-port arc since Lesson 103 has covered DI, middleware, EF Core, async, resilience, auth, and caching — but never came back for this one. This lesson is that return trip: the same syntactic gate, built into the framework instead of a separate schema document.

1 · The rule lives on the model, not in the handler

Where Lesson 81's JSON Schema was a separate document describing CreateOrderInput, ASP.NET Core's DataAnnotations attributes put the same rule directly on the class the request body deserializes into:

public class CreateOrderInput
{
    [Required]
    public Guid ProductId { get; set; }

    [Range(1, 1000)]
    public int Quantity { get; set; }

    [Required, EmailAddress]
    public string Email { get; set; } = "";
}

Nothing here is a handler-level if. The rule is declared once, on the shape itself, the same instinct Lesson 81 named — "write the rule down once, as data" — just spelled as attributes on a class instead of keys in a JSON object.

2 · Who actually runs the check: ModelState and ModelStateInvalidFilter

Model binding and model validation both run before a controller action executes. The result lands in ModelState.IsValid, checked by hand in plain MVC/Razor Pages actions:

public async Task<IActionResult> Create(CreateOrderInput input)
{
    if (!ModelState.IsValid)
        return BadRequest(ModelState);
    // ...
}

A controller marked with [ApiController] never needs that if. Microsoft's own docs state it plainly: "Web API controllers don't have to check ModelState.IsValid if they have the [ApiController] attribute. In that case, an automatic HTTP 400 response containing error details is returned when model state is invalid." The check itself runs as a ModelStateInvalidFilter action filter, wired in automatically by [ApiController] — and the action method body never executes at all when it trips, the same short-circuit Lesson 81's schema gate performed before auth or a query ever ran.

3 · The default response is a typed ValidationProblemDetails

The automatic 400 is not a bare string. Its documented shape is ValidationProblemDetails — the same RFC 7807-shaped type Lesson 125's ProblemDetails gave a Type/Title/Status/Detail/Instance shape to, with one addition: an errors dictionary keyed by field name, each value a list of that field's failed rules:

{
  "type": "https://tools.ietf.org/html/rfc7231#section-6.5.1",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "errors": { "Quantity": ["The field Quantity must be between 1 and 1000."] }
}

Building that object is itself delegated: ApiBehaviorOptions.InvalidModelStateResponseFactory is the delegate property responsible, and by default it "uses ProblemDetailsFactory to create an instance of ValidationProblemDetails." Overriding that factory — via ConfigureApiBehaviorOptions — is how a team adds logging to every automatic 400 without touching a single action, and setting options.SuppressModelStateInvalidFilter = true is the documented way to turn the whole automatic behavior off and go back to a hand-written if (!ModelState.IsValid) per action.

4 · What DataAnnotations still can't check: the same semantic line

Every attribute in section 1 answers "is this shaped right" — Lesson 81's syntactic validation, unchanged by the move to C#. None of them can ask "does this product id exist" or "is there enough stock," because none of them can see a database. For a rule spanning more than one property — released date must precede a discontinued date, say — a model implements IValidatableObject instead of adding another attribute:

public IEnumerable<ValidationResult> Validate(ValidationContext validationContext)
{
    if (Quantity > 1000 && string.IsNullOrEmpty(ApprovalCode))
        yield return new ValidationResult(
            "orders over 1000 units need an approval code",
            new[] { nameof(ApprovalCode) });
}

Validate runs after every property-level attribute already passed, and it still only sees the object itself — no injected DbContext, no query. The line Lesson 81 drew stands exactly where it stood in Go: a product id that doesn't exist, or a quantity that exceeds real stock, is still a handler-level lookup against the database, after both the attributes and IValidatableObject have already said yes.

Frontend-habit trap: this looks like a Zod or Yup schema wired to a form's onSubmit — same "declare the shape once" instinct. The gap that doesn't carry over: a frontend schema only ever protects the one form that imports it. A C# model's DataAnnotations fire for every action that binds to that class, and because [ApiController] wires the check in automatically, a developer can forget it exists entirely and the 400 still happens — there's no missed if to forget, which is also why skipping it on purpose needs its own explicit opt-out.

Scope line

This lesson covers DataAnnotations attributes on a model class, ModelState.IsValid and the two kinds of error it summarizes, [ApiController]'s automatic 400 via ModelStateInvalidFilter, the default ValidationProblemDetails response shape, InvalidModelStateResponseFactory/SuppressModelStateInvalidFilter, and IValidatableObject for cross-field rules. It does not cover FluentValidation or any third-party validation library (a framework-comparison deep-dive past this lesson's one concept), nor custom ValidationAttribute subclasses for reusable single-property rules — a natural next step, not today's.
