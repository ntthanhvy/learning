Row-level security: the database enforces the same rule your handler does

Lesson 12 fixed IDOR with one line in the handler: if order.UserID != user.ID && !user.HasRole("admin"). That line works — as long as every handler that ever queries orders remembers to write it. Today's question: what if a query gets there without going through that handler at all — a new endpoint someone forgets to check, an admin script, a background job with a typo'd WHERE clause? Postgres has a mechanism that answers "no row leaks" at the table itself, not per query.

1 · The gap Lesson 12's fix doesn't close

Lesson 12's ownership check is correct and it belongs in the handler — but it's an application-level guarantee, which means it only holds where that code actually runs. Picture the same orders table three months later: a teammate adds an internal /admin/export endpoint and forgets the ownership check because "it's just for us"; a new background job queries orders directly to build a report and nobody thought to add the same if; someone runs an ad-hoc query in a database console while debugging a ticket. None of these go through the handler Lesson 12 fixed. Every one of them can see every row, because the guarantee lived in application code, and application code is exactly the thing that gets skipped, forgotten, or bypassed.

Row-level security (RLS) moves the same "does this caller own this row?" question down one layer, from the handler into Postgres itself. Once RLS is enabled on a table and a policy is defined, every query against that table — from the handler, the export endpoint, the report job, the console — gets the same filter applied automatically, before any rows come back.

2 · How it actually works: enable, then define a policy

Two steps. First, turn RLS on for the table — this alone doesn't grant access, it flips the table from "open" to "deny by default":

ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
-- from this point on, a role with no matching policy sees zero rows,
-- not an error -- queries still run, they just return nothing.

Second, define a policy — a boolean expression Postgres silently ANDs onto the WHERE clause of every query that role runs:

CREATE POLICY orders_owner_only ON orders
  USING (user_id = current_setting('app.current_user_id')::int);
-- app.current_user_id is a session-local setting the application sets
-- once per connection/transaction, right after authenticating the caller.

The application still has to say who's asking — RLS doesn't skip authentication, it consumes the result of it. Right after Lesson 4's middleware identifies the caller, the handler sets a session variable, and every query on that connection is filtered from then on without needing its own WHERE user_id = ...:

SET app.current_user_id = '42';
SELECT * FROM orders; -- only rows where user_id = 42 come back --
-- no WHERE clause needed here: the policy supplies it.

3 · What changes for the handler that already had the check

Lesson 12's fixed handler still works fine, and RLS doesn't ask you to delete that if — the two are complementary, not competing, guarantees. What changes is what happens when a query doesn't have the check:

App-level check (Lesson 12)Row-level security (today)
Enforced bythe handler's own ifPostgres, on every query against the table
Applies toonly code paths that remembered to write itevery code path, including ones written later
Fails howsilently returns another user's row (IDOR)query runs, matching rows simply aren't there
Costone if per handler, easy to forgetone policy per table, plus a session variable to set

Neither replaces the other. The handler's check can return a clean 403 with a message; a database that just returns zero rows can't distinguish "doesn't exist" from "exists, not yours" without extra work, and a 403 is a better response than a confusing 404. RLS's value isn't a nicer error — it's that the guarantee holds even where nobody wrote an if at all. Layering both is the actual production pattern: the handler for a good client-facing error, RLS as the backstop that catches everything the handler didn't.

4 · The most common real mistake: forgetting to set the session variable

RLS policies typically read a session-local value like app.current_user_id — and if the application forgets to set it on a given connection (a pooled connection reused from a prior request, a background worker that never authenticates a "user" at all), current_setting either errors or returns an empty string, and the policy's comparison fails for every row. The practical effect is usually not a security hole — it's the opposite failure, a caller silently seeing zero rows they should see, which shows up as a confusing bug report rather than a leak. This is exactly the kind of per-connection state Lesson 18 already flagged as dangerous: a session variable set on a pooled connection must be reset (or the connection discarded) before it's handed to the next request, or one caller's current_user_id can leak into another caller's query.

Trap: RLS policies are bypassed by default for a table's owner role and any role with the BYPASSRLS attribute — including, commonly, whatever role your migration tool or admin scripts connect as. This is by design (someone has to be able to do a full backup), but it means "I enabled RLS" is not automatically true for every connection your system makes; check which role the application actually connects as day to day, and confirm that role is not the table owner and does not have BYPASSRLS.

5 · Where this earns its keep: defense in depth, not a replacement

RLS is not a substitute for Lesson 17's parameterized queries — a policy is itself SQL evaluated by Postgres, so it doesn't stop SQL injection in application code that builds queries by string concatenation; injected SQL still runs as that role, and the policy still applies to it, but the underlying vulnerability is unrelated and still needs fixing at the query-building layer. What RLS adds is a second, independent layer that holds even when the first layer (a correct handler) has a bug or a gap — the same "don't rely on one layer" instinct Lesson 58's three-layer synthesis lesson taught for staleness checks, applied here to access control instead. The strongest real-world case for it: a table shared by many tenants in one database, where "which rows belong to this caller" is not a rare edge case but the central question every single query against that table has to get right, forever, across every future engineer who touches the codebase.

Q: "We had an incident where an internal script exposed another customer's data. How would row-level security have helped?" A strong answer, out loud: "The script bypassed our usual API handlers, so whatever ownership check we'd written in the handler layer never ran — that's the actual root cause, not that anyone wrote bad SQL. Row-level security moves the same check into Postgres itself: once it's enabled on the table and a policy is defined, every query against that table gets the ownership filter applied automatically, whether it comes from the API, a background job, or someone's ad-hoc script. I'd still keep the handler-level check too, because it gives a clean 403 instead of a silent empty result — but RLS is the backstop for every code path we didn't think to check by hand. The one thing I'd flag: it only helps for the roles it actually applies to, so I'd also confirm our application doesn't connect as the table owner or a BYPASSRLS role, which skip policies entirely." The signal: naming RLS as a second, independent layer rather than a replacement for the existing handler check, and knowing the bypass caveat exists.
