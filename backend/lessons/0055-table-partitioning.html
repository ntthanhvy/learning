Table partitioning: one logical table, many physical ones

Lesson 54's closing teaser named table partitioning as a fresh, confirmed-untaught PostgreSQL gap, alongside a standing synthesis-lesson candidate. Today's the sharper, more concrete pick: what happens once a single table's rows number in the hundreds of millions — an index alone stops being enough, and Postgres has a purpose-built answer for splitting one logical table into many physical pieces.

1 · What an index can't fix

Lesson 5 covered indexes as the fix for "find matching rows without scanning everything." That still holds at huge scale — a B-tree index on created_at finds last week's orders rows fine whether the table has a million rows or ten billion. What indexes don't fix is the other cost of a huge table: routine maintenance (Lesson 39's VACUUM, a full-table backup, an index rebuild) still has to walk the whole physical table, and deleting "everything older than two years" is still millions of individual row deletes — one transaction, one WAL entry per row, regardless of how well-indexed the WHERE clause is. The table's logical size and its physical size are the same thing as far as Postgres storage is concerned — one giant heap file (or set of 1GB segment files) that every maintenance operation has to touch in full.

2 · Partitioning: one table, split into many

A partitioned table looks like one ordinary table to every query — same name, same columns, same constraints — but Postgres physically stores its rows across several separate child tables called partitions. Every partition is declared with a rule about which rows it owns — a range partition owns a contiguous span of values (orders from March 2026), a list partition owns an explicit set of values (orders from a named region), and a hash partition owns rows by a hash remainder when there's no natural range or list at all, just a desire to spread rows evenly. Time-range partitioning on a timestamp column is by far the most common shape for backend data — most tables that grow without bound (orders, events, audit logs — Lesson 46) grow by time.

CREATE TABLE orders (
  id bigint GENERATED ALWAYS AS IDENTITY,
  created_at timestamptz NOT NULL,
  customer_id bigint NOT NULL,
  PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_2026_07 PARTITION OF orders
  FOR VALUES FROM ('2026-07-01') TO ('2026-08-01');

CREATE TABLE orders_2026_08 PARTITION OF orders
  FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');

-- application code still just does this -- Postgres routes the row internally
INSERT INTO orders (created_at, customer_id) VALUES (now(), 42);

Note the primary key: Postgres requires the partition key (created_at) to be part of any unique constraint on a partitioned table, since uniqueness can only be enforced within a partition, not cheaply across all of them at once — a real constraint to design around, not a formality.

3 · Why splitting the table actually helps

Two distinct wins, and it matters which one a given query gets. First, partition pruning: a query filtered on the partition key (WHERE created_at >= '2026-08-01') only touches the one or two partitions that could possibly contain a match — the planner rules out every other partition before scanning anything, the same instinct as Lesson 5's selectivity, applied at the whole-partition level instead of the row level. Second — and often the bigger real-world win — maintenance operations become per-partition instead of whole-table: dropping two-year-old data is DROP TABLE orders_2024_07 (near-instant, no row-by-row DELETE, no bloat left for VACUUM to clean up later), and a VACUUM or index rebuild on one month's partition doesn't have to walk every other month's rows at all.

The trap this retrains: assuming partitioning is primarily a query-speed feature, then being disappointed. A query that doesn't filter on the partition key at all (WHERE customer_id = 42 with no date bound, against a table partitioned by created_at) gets no pruning — Postgres must check every partition, which can be slower than one big well-indexed table due to the per-partition planning overhead. Partitioning is a maintenance and lifecycle tool first, a query-speed tool second, and only for queries that actually filter on the partition key.

4 · When it's worth reaching for

Partitioning adds real operational complexity — every new month needs a new partition created ahead of time (or an automation job that does it), and retrofitting an existing large table onto partitions is itself a nontrivial migration (Lesson 19), not a single ALTER TABLE. It earns that cost specifically when a table both (a) grows without bound and (b) has an old-data lifecycle — archive, cheaper storage, or delete — that "just drop the old partition" answers cleanly. A few-million-row users table that never needs bulk-aged-out deletes doesn't need it; a fast-growing events or audit_log table that must purge anything older than 90 days is the textbook case. This is squarely a PostgreSQL data-modeling decision — not the sharded/distributed-systems territory MISSION.md scopes out — the table still lives on one Postgres instance; partitioning only changes how that one instance stores and maintains it internally.
