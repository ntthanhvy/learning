np.sign(): the three-way bucket code underneath a positive/negative/zero flag column

Lesson 126 closed with its own standing-candidate list fully used up, so today ran a genuinely fresh scan rather than taking a pre-committed pick (this course's own "fresh scan each round" convention). The scan surfaced a whole family of untaught elementwise math ufuncs (np.abs(), np.sqrt(), np.floor()/np.ceil(), np.sign()) — np.sign() won because it collapses a verbose np.where()/np.select() chain (Lesson 24) into one call, a genuinely common "flag the direction of a delta" interview task.

1 · One call instead of a nested np.where() chain

Lesson 24 taught np.where() for a single yes/no split and np.select() for several named conditions. A three-way "negative / zero / positive" bucket is exactly the kind of thing that tempts a nested np.where() inside another np.where(). np.sign(x) replaces that whole chain with one call, confirmed directly (numpy 2.5.4, pandas 3.1.1):

import numpy as np
import pandas as pd

delta = pd.Series([-5, 0, 3, -2, 7])

# The verbose way, chaining Lesson 24's np.where():
np.where(delta > 0, 1, np.where(delta < 0, -1, 0))
# array([-1,  0,  1, -1,  1])

# The direct way:
np.sign(delta)
# 0   -1
# 1    0
# 2    1
# 3   -1
# 4    1
# dtype: int64

Confirmed directly: called on a Series, np.sign() returns a Series with the original index kept intact, not a bare ndarray — assigning it straight to a new column, df["sign_code"] = np.sign(df["delta"]), lines up row-for-row with no reindexing needed. The result dtype follows the input: an integer Series in produces int64 out, a float Series in produces float64 out (confirmed directly) — unlike Series.shift() (Lesson 23), np.sign() never upcasts int to float on its own.

2 · The trap: NaN passes straight through, it is not bucketed

Confirmed directly (numpy 2.5.4), and confirmed exactly matching the official docs' own wording ("nan is returned for nan inputs"): a NaN in the input is not coerced into any of the three buckets — it comes back as NaN, untouched:

arrf = np.array([-5.0, 0.0, 3.0, np.nan])

np.sign(arrf)
# array([-1.,  0.,  1., nan])  -- the NaN survives, it is not bucketed as 0 or any other code

This is the opposite failure mode from Lesson 123's np.nan_to_num(), which replaces NaN with a chosen finite value by design. Here, a downstream groupby("sign_code") or value_counts() on the result silently gets a real NaN key mixed in with the -1/0/1 codes — plausible-looking output, no error, but a bucketing bug if the NaN rows were supposed to be excluded or filled first. Also confirmed directly, a detail the official docs page does not mention at all: a signed zero, -0.0, returns plain 0.0 — not -1 — so the sign bit on a float zero is not what decides the bucket.

3 · No Series.sign() — and complex input means something else entirely

Confirmed directly: pandas defines no Series.sign() or DataFrame.sign() method at all — calling .sign() on a Series raises AttributeError immediately, the same naming gap Lesson 126 found for np.roll(). np.sign() stays a NumPy-only function; the pandas-idiomatic spelling is calling it directly on the Series' own values, as in Section 1, not reaching for a method that does not exist.

pd.Series([-5, 0, 3]).sign()
# AttributeError: 'Series' object has no attribute 'sign'

# Confirmed directly from the official docs: complex input means something unrelated --
# x / abs(x) (the "unit direction" of the complex number), not a -1/0/1 code at all.
np.sign(np.array([3 + 4j]))
# array([0.6+0.8j])  -- out of scope for this lesson's wrangling use case, mentioned only to avoid the trap

Confirmed directly via np.shares_memory(): np.sign() always returns a new array, never a view into the input — mutating the result never touches the original column. Confirmed directly, it also runs without error on an object-dtype array of plain Python ints, unlike Lesson 123's np.nan_to_num(), which silently no-ops on object dtype.

Scope line

This lesson covers np.sign()'s confirmed -1/0/1 bucketing of real numbers versus a nested np.where() chain; the confirmed NaN-passes-through behavior (not bucketed, not an error) and the confirmed-absent-from-docs -0.0 → 0.0 detail; and the confirmed absence of any pandas .sign() method. It does not cover the complex-number form in any depth, or np.copysign()/np.signbit(), both legitimate but out-of-scope siblings per MISSION.md's "no deep NumPy" line — named only in passing.
