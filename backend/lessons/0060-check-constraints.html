CHECK constraints: teaching the row its own rules

Lesson 17 put input validation in the handler: reject a negative price before it ever reaches SQL. Lesson 59 showed the same instinct applied to authorization — push the rule into Postgres itself, so it holds even where the handler check doesn't run. Today's question: what stops a negative price from landing in the orders table via a background job, a migration's own UPDATE, or a teammate's one-off fix six months from now, none of which ever call your handler?

1 · The gap handler validation doesn't close

Lesson 17's input validation is correct and it belongs in the handler — checking that price is a positive number before an INSERT ever runs. But like Lesson 12's ownership check, it's an application-level guarantee: it only holds for code that actually calls that validation function. A data-backfill script writing straight SQL, a teammate's quick fix in a database console, an admin tool built eight months later by someone who never read the original handler — none of them re-run your validation, and none of them are stopped from writing price = -5.

A CHECK constraint moves the same "is this value even legal?" question down into the table definition itself. Once it's declared, every write to that table — from the handler, the backfill script, the console, next year's admin tool — gets the same rule enforced, because the rule now lives on the row, not in any one code path.

2 · Syntax: per-column and per-table

A CHECK constraint is a boolean expression attached to a column or to the whole table. Per-column, right after the type:

CREATE TABLE products (
  id SERIAL PRIMARY KEY,
  name TEXT NOT NULL,
  price NUMERIC CHECK (price > 0)
);

Give it a name so a future violation error is readable instead of a generated string like products_price_check:

CREATE TABLE products (
  id SERIAL PRIMARY KEY,
  name TEXT NOT NULL,
  price NUMERIC CONSTRAINT positive_price CHECK (price > 0)
);

A table-level CHECK can reference more than one column — this is the only place a cross-column rule like "discounted price must actually be lower" can live at all:

CREATE TABLE products (
  id SERIAL PRIMARY KEY,
  price NUMERIC CHECK (price > 0),
  discounted_price NUMERIC CHECK (discounted_price > 0),
  -- table-level: compares two columns, so it can't be written per-column
  CHECK (discounted_price < price)
);

Adding one to an existing table works the same as any other constraint — see Lesson 19's migration pattern:

ALTER TABLE products
  ADD CONSTRAINT positive_price CHECK (price > 0);
-- Postgres checks every EXISTING row against the new rule immediately;
-- the ALTER fails if even one current row already violates it.

3 · The trap: CHECK says nothing about NULL

Trap: a CHECK constraint passes if its expression evaluates to TRUE or to NULL — only an explicit FALSE is rejected. price > 0 evaluated against a NULL price yields NULL, not FALSE, so the row is allowed through with no price at all. CHECK (price > 0) guards against a wrong price; it does nothing to guard against a missing one. If a price is mandatory, that still needs its own NOT NULL alongside the CHECK — the two constraints answer different questions and neither substitutes for the other.

5 · Where this earns its keep over handler validation

A CHECK constraint isn't a replacement for Lesson 17's handler-level validation — keep both, for the same reason Lesson 59 kept the handler's ownership check alongside RLS. The handler can return a clean 400 with a field-specific message before a query even runs, which is a far better experience than parsing a raw Postgres error. What the constraint adds is the backstop: it holds even when a code path skips the handler, and it holds forever, across every future engineer who writes a query against that table without reading the original validation code first. The strongest case for reaching for one: any rule that must never be false regardless of which code wrote the row — a price that can never go negative, a status column limited to a fixed set of strings, an end date that can never precede its start date.

Q: "When would you use a CHECK constraint instead of just validating in the application?" A strong answer, out loud: "I'd keep the application-level validation regardless, because it gives a clean 400 with a useful message before a query even runs. A CHECK constraint is for rules that have to hold no matter which code path writes the row — a background job, a migration, someone's one-off fix in a console next year. If a rule like 'price can't be negative' is only enforced in one handler, it's one refactor away from a bad row landing in the table. I'd add the constraint for anything that would be a real data-integrity problem if it slipped through, and I'd remember it isn't a NOT NULL substitute — a CHECK passes on NULL unless I add that separately." The signal: layering the constraint alongside application validation rather than picking one, and knowing the NULL caveat without being asked.
