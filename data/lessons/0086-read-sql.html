pd.read_sql(): the ETL Extract step via SQL, and its dtype traps

Lesson 8's ETL aside named to_csv/to_sql as the Load step in passing; Lesson 64 later closed to_csv/to_parquet as their own lesson but left the SQL side alone. Grepped every lesson and the glossary for to_sql|read_sql and found exactly those two passing mentions, never a dedicated lesson — the same gap shape Lesson 64 itself closed for file output. Today closes the mirror image on the Extract side: loading a query result straight into a DataFrame, and the one dtype surprise that trips up nearly everyone moving from SQL into pandas for the first time.

1 · The SQL bridge: this is just SELECT, with the result landing in a DataFrame

If a SQL query already returns the exact shape of table you want, there is no reason to export it to a file first. pd.read_sql(sql, conn) runs the query and hands back a DataFrame directly:

orders = pd.read_sql("SELECT * FROM orders WHERE amount > 100", conn)
orders.dtypes  # one column per SELECTed column, dtype guessed from the data that came back

Mentally this is psql -c "SELECT ..." piped straight into a table object instead of to a terminal or a file — the Extract half of the ETL shape Lesson 8 named, now spelled out on its own. Everything downstream (filter, groupby, merge) is unchanged from every prior lesson; only the loading step is new.

2 · read_sql() vs read_sql_query() vs read_sql_table()

pd.read_sql() is a dispatcher, not its own implementation — it looks at what was passed and forwards to one of two stricter functions:

FunctionTakesSQL equivalent
read_sql_query()a SQL query stringSELECT ... with any WHERE/JOIN/GROUP BY
read_sql_table()a bare table nameSELECT * FROM table, nothing else possible
read_sql()either oneguesses which of the two above to call

Confirmed directly (pandas 3.0.5): read_sql_table() additionally requires a SQLAlchemy engine specifically — it needs to introspect the table's real column types through SQLAlchemy's reflection, which a plain DB-API connection can't provide. For anything with a WHERE clause, a JOIN, or an aggregation — which in practice is almost every real pull — reach for read_sql_query() directly rather than the bare table name, and read_sql() simply becomes convenient shorthand once the habit is to always pass a query string.

3 · Why conn must be a connection/engine object, not a raw cursor

The conn argument is not the live, already-executing cursor object a lower-level DB-API library hands back — it's a connection-like object pandas can introspect and run its own query through: a connection, or for a full-featured setup, a SQLAlchemy engine. Confirmed directly: pandas' own docs recommend a SQLAlchemy engine for every backend except sqlite3, which is special-cased to also accept a plain stdlib sqlite3.Connection directly, no SQLAlchemy required.

from sqlalchemy import create_engine
engine = create_engine("postgresql://user:pass@host/dbname")
orders = pd.read_sql("SELECT * FROM orders", engine)   # engine, not a raw psycopg cursor

import sqlite3
conn = sqlite3.connect("local.db")
orders2 = pd.read_sql("SELECT * FROM orders", conn)      # sqlite3 is the one special case

A raw DB-API cursor already mid-query doesn't fit this shape at all — read_sql() wants to run the query itself and manage fetching every row, not consume a cursor someone else already advanced.

4 · params=: never f-string a SQL query

Anyone coming from a backend/SQL background who's internalized the injection lesson already knows the rule: never splice a variable into a SQL string directly. The exact same rule applies here, and it's just as easy to forget because it feels like harmless Python string formatting rather than a query being sent to a server:

# WRONG -- the same SQL-injection shape as any raw DB-API call
min_amount = 100
pd.read_sql(f"SELECT * FROM orders WHERE amount > {min_amount}", conn)

# RIGHT -- bind parameters, same idea as a parameterized query anywhere else
pd.read_sql(
    "SELECT * FROM orders WHERE amount > %(min_amount)s",
    conn,
    params={"min_amount": min_amount},
)

params= passes bind values through the underlying driver the same way any parameterized query would — the input is sent as data, never concatenated into the SQL text, so a value like "100; DROP TABLE orders;" is just treated as a literal string to compare, not executable SQL. This is the identical defense the backend course's SQL-injection lesson teaches for any raw query — pd.read_sql() isn't exempt from it just because the caller is pandas instead of a web framework. The exact placeholder style (%(name)s vs :name vs ?) depends on the underlying driver/dialect, not on pandas.

5 · The real interview trap: a nullable INTEGER column comes back as float64, not Int64

This is the dtype surprise worth knowing cold. A SQL INTEGER column that allows NULL and actually has at least one NULL row does not come back from read_sql() as a nullable integer — it silently gets upcast to plain float64, with every NULL becoming NaN:

-- SQL table: quantity INTEGER, one NULL row
pd.read_sql("SELECT order_id, quantity FROM orders", conn).dtypes
-- order_id      int64
-- quantity    float64    <- an INTEGER column, silently turned into float!

Confirmed directly (pandas 3.0.5): the reasoning is identical to Lesson 51's plain-int64-can't-hold-NaN story — NumPy's default integer dtype has no missing-value slot, so the moment a whole-number column has even one gap, pandas must widen it to something that can represent "missing," and the historical default for that has always been float64, not the nullable Int64 this course has used since Lesson 51. A quantity of 3 silently reads back as 3.0 — correct in value, but the wrong dtype for anything downstream expecting whole numbers, and a genuine .0-vs-missing ambiguity disappears into "it's a float now, trust the NaNs."

The fix is the same nullable-dtype opt-in this course has used repeatedly: pass dtype_backend="numpy_nullable", or cast the column afterward:

pd.read_sql("SELECT order_id, quantity FROM orders", conn, dtype_backend="numpy_nullable").dtypes
-- order_id      Int64    <- nullable, matches the SQL schema's real intent
-- quantity      Int64    <- NULL rows become pd.NA, not NaN -- no silent float upcast

# or cast after the fact, same result for one column:
df["quantity"] = df["quantity"].astype("Int64")

This is exactly the Lesson 84/51 nullable-dtype pattern, just arriving through a different door: a database round trip, instead of a CSV read or an object-column conversion. Same marker (pd.NA), same reason (NumPy's plain integer/boolean have no room for "missing"), new source.

6 · chunksize=: streaming a big result instead of loading it all at once

A query that returns millions of rows materialized all at once as one DataFrame can blow past available memory before any processing even starts. chunksize= turns the return value into an iterator of smaller DataFrames instead of one big one:

for batch in pd.read_sql("SELECT * FROM orders", conn, chunksize=10_000):
    process(batch)   # each `batch` is a DataFrame of at most 10,000 rows

This is the one legitimate place a for loop belongs in this course's pandas style — the loop is over batches, not rows; every batch is still processed with ordinary vectorized pandas code inside it. The SQL-side cousin is a server-side cursor fetching in pages rather than one giant resultset; chunksize= is pandas doing the same thing on the client side, trading one big spike in memory for many smaller, bounded ones.

Q: "Walk me through pulling data from a database into pandas for a pipeline." A strong answer, out loud: "I'd use read_sql_query() with an explicit SQL string rather than the bare-table read_sql_table(), since almost any real pull has a WHERE or JOIN. The conn= argument needs to be a real connection or engine object — a SQLAlchemy engine for anything beyond SQLite, since pandas needs to run the query itself, not consume an already-executing cursor. Any value coming from outside the code goes through params=, never an f-string — splicing a variable into the SQL text is the exact same injection risk as any raw query, pandas isn't special-cased out of that rule. The dtype gotcha I'd watch for: a nullable INTEGER column in the source table comes back as float64 if even one row is NULL, because plain NumPy int64 has no missing-value slot — I'd pass dtype_backend='numpy_nullable' to get real nullable Int64 back instead of a silent float upcast. And if the result set is large, I'd reach for chunksize= to stream it in bounded batches instead of materializing the whole query in memory at once." The signal: naming the params= injection risk and the INTEGER-to-float64 dtype trap unprompted — the two places this bites someone who's only ever tested against a small, NULL-free sample table.
