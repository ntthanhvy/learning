EF Core's own flavor of N+1

Lesson 36 taught the N+1 query problem in the abstract: one query for a list, then one more query per row in a loop. It even named lazy-loading as the ORM disguise for that same bug. Today: exactly how EF Core's DbContext — Lesson 103's Scoped service, the one with change tracking — turns that disguise into something that looks like perfectly normal C#, and the two different fixes for the two different ways it happens.

1 · The loop is still there, it's just hidden behind a property

Here's code that looks like it does nothing wrong — no visible loop issuing queries, just reading data off objects already in hand:

foreach (var order in db.Orders.ToList()) {
    Console.WriteLine($"Order {order.Id}: {order.Items.Count} items");
}

If Order.Items is a navigation property and lazy-loading is enabled, that one-line order.Items.Count fires a fresh SELECT the first time it's touched for each order — Lesson 36's 1,001-query shape, except nothing in this code looks like a loop firing queries. It looks like reading a field. That's exactly the disguise Lesson 36's section 6 named, and it's the normal way this bug gets into a C# codebase: nobody wrote a query inside the loop on purpose, the navigation property wrote it for them.

2 · Fix #1: tell EF Core to fetch the relation up front

The fix is the same "eager load" idea Lesson 36 named generically, with a concrete EF Core method: Include():

var orders = await db.Orders
    .Include(o => o.Items)   // fetch Items in the SAME query, via JOIN
    .ToListAsync();

foreach (var order in orders) {
    Console.WriteLine($"Order {order.Id}: {order.Items.Count} items");  // no extra query now
}

Include(o => o.Items) turns the query into one SQL statement with a JOIN, so every order's items arrive in the same round trip as the orders themselves. By the time the foreach runs, order.Items is already populated — reading it doesn't ask the database anything, because EF Core's change tracking already has it in memory. This is Lesson 36's JOIN-or-batch fix, just spelled as a LINQ method instead of hand-written SQL.

3 · The second, EF-Core-specific flavor: change tracking itself is the cost

Lesson 103 already named it: change tracking is DbContext remembering every entity it has loaded, so SaveChanges() knows which fields changed and can generate the right UPDATE. That bookkeeping isn't free — and it runs whether or not you intend to modify anything:

// A read-only report endpoint -- nothing here is ever going to be saved
[HttpGet("reports/orders")]
public async Task<IActionResult> GetOrderReport() {
    var orders = await db.Orders.Include(o => o.Items).ToListAsync();
    return Ok(orders.Select(o => new { o.Id, o.Items.Count }));
}

This isn't Lesson 36's round-trip-count problem — Include already fixed that part, it's one query. The cost here is different: every one of those entities gets a tracked-entity snapshot allocated and kept in the DbContext's change tracker, purely in case something changes it later — memory and CPU spent on bookkeeping a read-only report endpoint will never use. On a large result set, that overhead is real and avoidable.

The fix is a different method than Include, because it's a different problem: AsNoTracking():

var orders = await db.Orders
    .AsNoTracking()           // skip the change-tracker snapshot entirely
    .Include(o => o.Items)
    .ToListAsync();

Include and AsNoTracking answer two different questions, and this lesson's whole point is not to confuse them: Include fixes how many queries run (Lesson 36's round-trip problem); AsNoTracking fixes how much bookkeeping each returned row carries (an EF-Core-only cost with no Go/raw-SQL equivalent, because hand-written SQL never tracked anything to begin with). A report endpoint that never calls SaveChanges should almost always use both.

Go side-by-side: the Go/pgx code in Lesson 36 never had either problem by construction. A hand-written SELECT ... JOIN ... or batched WHERE id = ANY(...) query is the only round trip there is — there's no navigation property to lazily fire a second query, and there's no change tracker silently snapshotting every scanned row, because pgx.Rows.Scan just copies columns into a struct and stops. The trade-off runs the other way too: that same hand-written code gets no free UPDATE-diffing from a change tracker either — Go/pgx code must build its own UPDATE statement by hand, field by field, every time. EF Core's convenience and its two N+1-adjacent costs are the same trade-off, not two separate things to avoid.

Scope line

This lesson covers EF Core's lazy-loading navigation-property flavor of Lesson 36's N+1 problem, the Include() fix for it, and the separate change-tracking overhead AsNoTracking() fixes. It does not cover: split queries (AsSplitQuery()) for when a single big JOIN itself becomes the bottleneck on multiple collection includes; explicit loading (Entry().Collection().Load()) as a third loading strategy; or EF Core's query compilation/caching internals. Natural follow-ons, not covered here.
