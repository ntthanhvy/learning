np.percentile() and np.quantile(): same math, two scales, and a NaN trap pandas doesn't have

This round's fresh scan confirmed np.ravel()/.flatten() was still open (named three rounds running since Lesson 108), but it also turned up a sharper gap: Lesson 18 taught qcut() to bin rows by quantile, but the raw NumPy functions underneath — np.percentile() and np.quantile() — were never covered on their own. They continue the "raw NumPy layer under a pandas method" family Lessons 93/95/97/99-102/109/110 have been building, and this one hides a genuinely sharp NaN contrast with Series.quantile().

1 · Same computation, two different scales

np.percentile() and np.quantile() compute the exact same statistic — "the value below which q% (or fraction q) of the data falls" — the only difference is which scale q is written on:

arr = np.array([3, 1, 4, 1, 5, 9, 2, 6])

np.percentile(arr, 50)     # 3.5  -- 50 out of 100
np.quantile(arr, 0.5)      # 3.5  -- 0.5 out of 1, identical result

np.percentile(arr, [25, 50, 75])
# array([1.75, 3.5 , 5.25])   -- multiple q values at once, one array back

Confirmed directly (numpy 2.5.4): passing a value outside each function's own valid range raises ValueError immediately rather than silently clamping — np.percentile(arr, 150) raises "Percentiles must be in the range [0, 100]", and np.quantile(arr, 1.5) raises the 0-1 equivalent. Mixing the two scales up — passing 0.5 to np.percentile() expecting a median — doesn't raise at all; it silently computes the 0.5th percentile (essentially the minimum), the easiest wrong-guess mistake with this pair.

2 · The NumPy-layer gap: it does NOT dispatch to a Series back

Lessons 109/110 found a mixed pattern: np.cumsum()/np.clip() dispatch to the pandas method and hand a Series back when called on a Series, but np.cummax() doesn't even exist as a top-level function. np.percentile()/np.quantile() add a third shape to that pattern: confirmed directly, calling either one on a pandas Series does not dispatch to Series.quantile() — it always returns a bare numpy.float64 scalar (or a plain ndarray for multiple q values), with the Index gone entirely, same "index disappears" behavior np.diff() had in Lesson 109:

s = pd.Series(arr)

np.percentile(s, 50)          # 3.5, type numpy.float64 -- a bare scalar, no Index
s.quantile(0.5)                # 3.5, same value, but via the pandas method instead

s.quantile([0.25, 0.5, 0.75])
# 0.25    1.75
# 0.50    3.50
# 0.75    5.25
# dtype: float64   -- pandas keeps the q values as a labeled Index; NumPy never does

The groupby-friendly version only exists on the pandas side, confirmed directly: df.groupby("g")["v"].quantile(0.5) returns one quantile per group with the group labels as Index — there is no NumPy-level equivalent that understands groups at all, since np.quantile() only ever sees a flat array.

The trap: reaching for np.percentile()/np.quantile() inside a pandas pipeline expecting a Series back (to assign into a new column, say) silently breaks — it hands back a bare scalar or array with no row alignment at all. Series.quantile()/DataFrame.quantile() are the pandas-native spelling precisely because this NumPy pair never learned to carry index/group context.

3 · NaN: np.percentile() poisons silently, Series.quantile() just drops it

Confirmed directly, this is the sharpest trap in the pair: unlike every pandas method probed so far in this course (which default to skipna=True, Lessons 7/109/110), np.percentile()/np.quantile() have no skipna concept at all — a single NaN anywhere in the input poisons the entire result to NaN, with no warning:

arr_nan = np.array([1.0, 2.0, np.nan, 4.0])

np.percentile(arr_nan, 50)      # nan -- one NaN anywhere wrecks the whole computation
np.nanpercentile(arr_nan, 50)   # 2.0 -- the NaN-aware sibling function, ignores NaN entirely

pd.Series(arr_nan).quantile(0.5)
# 2.0  -- Series.quantile() drops NaN automatically, matching np.nanpercentile(), NOT np.percentile()

So Series.quantile()'s default behavior actually matches np.nanpercentile(), not the plain np.percentile() it looks like the obvious NumPy counterpart of — calling the wrong one of the pair on NaN-containing data is a silent, no-exception, wrong-number bug.

4 · method=, not interpolation= — a hard break, not just a rename

Confirmed directly against the official NumPy docs: the parameter controlling how a percentile that falls between two data points gets computed is method= (default "linear"), offering choices like "nearest", "lower", "higher", and several statistical variants. It used to be called interpolation= — but in the installed version this course uses, that old name is fully removed, not merely deprecated: passing interpolation= now raises TypeError: percentile() got an unexpected keyword argument 'interpolation' outright, the same hard-break pattern Lesson 103 found with pd.to_timedelta()'s removed errors="ignore".

np.percentile(arr, 50, method="nearest")
# 4  -- snaps to the nearest actual data point instead of interpolating

np.percentile(arr, 50, interpolation="linear")
# TypeError: percentile() got an unexpected keyword argument 'interpolation'

Q: "What's the difference between np.percentile() and np.quantile()?" A strong answer, out loud: "Same algorithm, different scale for q — percentile takes 0 to 100, quantile takes 0 to 1, so percentile(arr, 50) and quantile(arr, 0.5) give the identical number. Neither one dispatches on a Series the way cumsum() does — you get a bare NumPy scalar back with no index, so inside a pandas pipeline I'd reach for Series.quantile() instead. And the NaN behavior is the trap: the plain NumPy versions let one NaN poison the whole result silently, while Series.quantile() quietly drops NaN by default — closer to np.nanpercentile() than to np.percentile() itself, even though the names look like direct counterparts." The signal: naming the scale difference correctly, knowing neither dispatches to a Series, and catching the NaN mismatch between the "obvious" NumPy counterpart and what pandas actually does by default.
