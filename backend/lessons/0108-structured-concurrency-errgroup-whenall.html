Fan out to 3 services, get all results or the first error

Lesson 107 covered one await at a time. Real handlers often need three downstream calls at once — pricing, inventory, shipping — and then one of two outcomes: all three answers, or the first error, with the other two stopped rather than left running pointlessly. Lesson 25 named the vocabulary (goroutine, coroutine, cooperative scheduling); today is the pattern for coordinating several of them together, in Go and in C#, and the one place the two stacks quietly disagree on what "first error" should do to its siblings.

1 · The shape: fan out, then one of two outcomes

Three independent calls, started together, not one after another:

priceResult, invResult, shipResult := callPricing(), callInventory(), callShipping()
// sequential: ~300ms if each call takes ~100ms

Run sequentially, three 100ms calls cost 300ms. Run concurrently, they cost roughly 100ms — the slowest one. That's the whole motivation. But concurrent fan-out raises a question sequential code never had to answer: if the inventory call fails, should the pricing and shipping calls keep running anyway? Usually not — their answers are about to be discarded, so every extra millisecond they run is wasted work and wasted downstream load. The pattern this lesson covers is structured concurrency: fan out, wait for the whole group to finish, and make sure no sibling call outlives the point where its result stopped mattering.

2 · Go: errgroup.Group ties "wait for all" to "cancel on first error"

Go's standard library gives you sync.WaitGroup for "wait for all goroutines," but it says nothing about errors or cancellation. golang.org/x/sync/errgroup is the de facto standard answer, built on exactly the Lesson 41 context.Context you already know:

g, ctx := errgroup.WithContext(parentCtx)

var price Price
var inv Inventory
var ship ShipEstimate

g.Go(func() error {
    var err error
    price, err = callPricing(ctx)   // ctx -- cancelled if a sibling fails
    return err
})
g.Go(func() error {
    var err error
    inv, err = callInventory(ctx)
    return err
})
g.Go(func() error {
    var err error
    ship, err = callShipping(ctx)
    return err
})

if err := g.Wait(); err != nil {
    return err   // the FIRST error any goroutine returned
}
// all three succeeded; price, inv, ship are all populated

errgroup.WithContext(parentCtx) returns a errgroup.Group and a derived ctx. Each g.Go() call runs one of the three calls in its own goroutine. The moment any one of them returns a non-nil error, the derived ctx is cancelled — the exact same cancellation signal Lesson 41 already taught you to check for. The other two goroutines, mid-flight, see that cancellation inside callInventory(ctx) or wherever they're blocked and can stop early, instead of running to completion for no reason. g.Wait() blocks until every goroutine in the group has returned, then hands back only the first non-nil error any of them produced — not a list of all three.

3 · C#: Task.WhenAll does "wait for all," not "cancel on first error"

C#'s equivalent fan-out looks almost identical on the surface, and that similarity is exactly what hides the gotcha:

var priceTask = CallPricingAsync(ct);
var invTask = CallInventoryAsync(ct);
var shipTask = CallShippingAsync(ct);

await Task.WhenAll(priceTask, invTask, shipTask);
// all three awaited Tasks are done -- or WhenAll threw

Task.WhenAll returns a Task that, per Microsoft's own docs, "will complete when all of the supplied tasks have completed" — every single one, always, whether they succeeded or faulted. If invTask throws almost immediately while priceTask and shipTask are still running, Task.WhenAll does not stop them. It just keeps waiting for all three to finish before it lets the await on its own line continue — the opposite of errgroup's behavior, using code that looks like a direct translation of it.

The gotcha, stated plainly: errgroup cancels siblings automatically, because g.Go()'s functions and g.Wait() are wired to the same derived ctx. Task.WhenAll has no such wiring — passing the same CancellationToken into all three calls does not make one task's failure cancel the token. Nothing cancels the token unless something explicitly calls Cancel() on it.

Getting errgroup's fail-fast behavior in .NET takes one extra, explicit piece: a CancellationTokenSource (cts) that every task's call is given the CancellationToken (cts.Token) from, with the catch block for each task calling cts.Cancel() the moment that task fails:

using var cts = new CancellationTokenSource();

async Task<Price> RunPricing() {
    try { return await CallPricingAsync(cts.Token); }
    catch { cts.Cancel(); throw; }   // signal siblings, then rethrow
}
// RunInventory() / RunShipping() follow the same try/catch-and-cancel shape

try {
    await Task.WhenAll(RunPricing(), RunInventory(), RunShipping());
} catch (Exception) {
    // Task.WhenAll's exception only carries ONE rethrown exception from .Result,
    // even though ALL faulted exceptions are aggregated inside the Task itself
    throw;
}

Each wrapper method catches its own failure, calls cts.Cancel(), then rethrows. The other two calls, which were given cts.Token, see the cancellation and can stop early inside whatever await they're sitting on — the same early-exit callInventory(ctx) got for free in the Go version, here wired by hand through one shared CancellationTokenSource. The alternative some teams use instead of this try/catch wiring is Task.WhenAny — await just the first task to finish, inspect whether it faulted, and manually cancel the rest if it did — but that needs its own manual loop to collect the remaining results on success, so the try/catch-and-cancel shape above is usually the smaller change from a naive Task.WhenAll call.

Scope line

This lesson covers fanning out independent concurrent calls with errgroup and Task.WhenAll, and the fail-fast cancellation gap between them. It does not cover: errgroup.Group.SetLimit for bounding how many goroutines run at once (Lesson 25's worker-pool idea, applied to errgroup specifically); Task.WhenAny's full manual-cancellation pattern in detail; or retry/backoff on an individual failed call before giving up (Lesson 32's territory, one layer below this one).
