factorize(): the integer codes hiding under category dtype

Named as a standing zero-hit candidate since Lesson 66, reconfirmed by Lesson 67's closing teaser and by a fresh grep of all 67 lessons and the glossary this round — still genuinely uncovered. Picked over the round's other zero-hit candidates (.sample(), .align()) because it sits precisely next to a lesson already taught: Lesson 25 named category dtype as "a lookup table hiding inside one column," storing distinct values once plus a small integer code per row — factorize() is the plain NumPy-flavored function that produces exactly that codes/uniques pair directly, without going through a dtype conversion first.

1 · category dtype's mechanism, pulled out as a standalone function

Lesson 25 showed .astype("category") building a small lookup table under the hood: distinct values stored once, plus one small integer code per row pointing back into it. factorize() is that exact mechanism, exposed directly as a function you can call on any array-like — no dtype conversion required:

clean["customer"].tolist()
# ['An', 'An', 'Binh', 'Binh']

codes, uniques = pd.factorize(clean["customer"])
codes     # array([0, 0, 1, 1])          -- numpy.ndarray, one int per row
uniques   # Index(['An', 'Binh'])        -- the distinct values, in ORDER OF APPEARANCE

Confirmed directly (pandas 3.0.5) on the real orders_raw.csv clean 4-row slice. factorize() always returns exactly two pieces: codes, a plain NumPy integer array the same length as the input, and uniques, the distinct values each code points into. It also exists as a method — clean["customer"].factorize() — confirmed to return byte-identical output to the top-level pd.factorize(clean["customer"]) call.

2 · The one real difference from category dtype: appearance order, not sorted order

category dtype's .cat.categories sorts its lookup table alphabetically by default. factorize() does not — its uniques are ordered by when each value FIRST appears in the data, confirmed directly with a case where the two orders diverge:

s = pd.Series(["Chi", "An", "Chi", "Binh", "An"])

# factorize(): order of FIRST APPEARANCE -- Chi, An, Binh
codes, uniques = pd.factorize(s)
codes     # [0, 1, 0, 2, 1]
uniques   # ['Chi', 'An', 'Binh']

# category dtype: ALPHABETICAL by default -- An, Binh, Chi
s.astype("category").cat.codes.tolist()        # [2, 0, 2, 1, 0]
s.astype("category").cat.categories.tolist()  # ['An', 'Binh', 'Chi']

# sort=True makes factorize() match category dtype's codes EXACTLY
codes, uniques = pd.factorize(s, sort=True)
codes     # [2, 0, 2, 1, 0]   -- identical to .cat.codes
uniques   # ['An', 'Binh', 'Chi']  -- identical to .cat.categories

Confirmed directly: with sort=True, factorize()'s codes and uniques become element-for-element identical to that same Series' category-dtype .cat.codes and .cat.categories. They are the same underlying algorithm — factorize() just defaults to the cheaper appearance-order pass (no sort step needed) rather than category dtype's alphabetical default.

SQL bridge: both are the same "surrogate key" idea — assign a small integer to stand in for a repeated value, the way a normalized lookup table replaces a repeated VARCHAR with a small foreign key. category dtype keeps that mapping attached to the column as a dtype, ready for repeated use (groupby, comparisons, memory savings from Lesson 25). factorize() hands you the raw codes/uniques pair once, as plain NumPy/pandas objects, for a one-off encoding task — feeding a machine-learning input, or building a fast integer-keyed lookup by hand.

3 · The gotcha: NaN's -1 sentinel is a silent wrong-answer trap, not a crash

A missing value doesn't get its own row in uniques — factorize() gives it the sentinel code -1 instead, confirmed directly:

s = pd.Series(["An", None, "Binh", "An", np.nan])

codes, uniques = pd.factorize(s)
codes     # [0, -1, 1, 0, -1]     -- NaN rows get -1, not their own code
uniques   # ['An', 'Binh']        -- NaN never appears here at all

That -1 looks harmless until you try the natural reconstruction move, uniques[codes] — confirmed directly, this is a genuine "no crash, quietly wrong" trap, the same family as this course's other silent-failure gotchas (category dtype's fixed-list NaN from Lesson 25, ffill()'s bleed-across-groups):

uniques[codes]
# array(['An', 'Binh', 'Binh', 'An', 'Binh'], dtype=object)
#           ^^^^                     ^^^^
#      WRONG -- should be missing, not "Binh"!

NumPy/Python indexing treats -1 as "the last element," not "missing" — so uniques[-1] silently returns uniques's last real entry (here, "Binh") for every row that was actually NaN. No exception, no warning, and the array even keeps a plausible-looking dtype. The safe reconstruction checks for -1 first: pd.Series(uniques[codes]).mask(codes == -1), or pass use_na_sentinel=False to factorize() so NaN gets a real code and its own slot in uniques instead of -1.

Q: "What does factorize() do, and how does it relate to category dtype?" A strong answer, out loud: "factorize() encodes an array-like into two pieces: an integer numpy array of codes, one per row, and a uniques array of the distinct values each code points into — the exact same surrogate-key idea as category dtype's codes/categories pair from Lesson 25, just returned directly as a function result instead of living on a dtype. The one real difference is ordering: factorize() defaults to order of first appearance, while category dtype sorts alphabetically by default — passing sort=True to factorize() makes its output match category dtype's codes and categories exactly, so they're genuinely the same algorithm underneath. The gotcha I'd flag: missing values get the sentinel code -1, not a real code, and naively reconstructing with uniques[codes] silently returns the WRONG real value for every missing row, because -1 is valid negative indexing into the last element — no crash, no warning. I'd either check for -1 before indexing, or pass use_na_sentinel=False so NaN gets its own real slot in uniques." The signal: naming the category-dtype connection unprompted, the appearance-order-vs-sorted distinction, and specifically the -1 reconstruction trap — that's the part almost everyone misses on first contact.

4 · Where this actually gets used

factorize() shows up whenever something downstream needs small dense integers instead of repeated strings/objects — feeding a NumPy/ML routine that only accepts numeric arrays, building a fast integer-keyed groupby-like count by hand (np.bincount(codes), confirmed directly to match a value_counts() tally in appearance order), or de-duplicating a large low-cardinality column's storage the same way category dtype does, but as a one-off pass rather than an attached dtype. For anything that stays inside pandas and gets reused (repeated groupby, memory savings, filtering) — reach for category dtype (Lesson 25) instead; it keeps the mapping attached to the column so you never have to carry codes/uniques around by hand. Confirmed directly: a plain Python list raises TypeError: factorize requires a Series, Index, ExtensionArray, np.ndarray or NumpyExtensionArray got list on pandas 3.0.5 — wrap it in np.array(...) or a pd.Series first if the input isn't already array-like.
