1 · What dbt actually adds on top of SQL you already know

A dbt model is a file with a SELECT in it. That's it — no new query language, no new joins, nothing about SQL itself changes. What dbt adds is everything around that SELECT:

  • a way to declare "this raw table is my starting point" — source() — so dbt knows what's upstream of everything;
  • a way to say "this model depends on that other model" — ref() — instead of hardcoding schema-qualified table names, so dbt can figure out build order and draw a graph;
  • a choice of how each model gets materialized — view, table, or (Day 4) incremental — decoupled from the SQL itself;
  • and, from that web of ref()/source() calls, a DAG — a picture of the whole project's dependencies that dbt draws for you, instead of you tracking it in your head or in a README.

Today builds the first layer of that graph: staging models: one per raw table, doing light cleanup and nothing else. No joins yet — that's intermediate models, later in the course.

3 · Declare the sources

A source tells dbt "this table already exists, I didn't build it, here's its name." Create models/staging/sources.yml:

version: 2

sources:
  - name: raw
    schema: raw
    tables:
      - name: restaurants
      - name: couriers
      - name: orders

This is a declaration, not a query — it doesn't create or move any data. It's what makes {{ source('raw', 'orders') }} in a model resolve to raw.orders, and it's the anchor Day 3's source freshness checks attach to.

4 · Build the three staging models

Per dbt Labs's "How we structure our dbt projects" — this course's house style per RESOURCES.md — staging models are one-per-source-table, named stg_<table>, doing only renames/casts/light derived columns, never a join. Create models/staging/stg_restaurants.sql and models/staging/stg_couriers.sql with exactly this (scaffolding — the columns just pass through Day 1's raw schema):

-- models/staging/stg_restaurants.sql
select
    restaurant_id,
    name,
    cuisine,
    city,
    commission_rate,
    updated_at
from {{ source('raw', 'restaurants') }}
-- models/staging/stg_couriers.sql
select
    courier_id,
    vehicle,
    city,
    joined_at
from {{ source('raw', 'couriers') }}

Now write models/staging/stg_orders.sql yourself. Requirements:

  • select every column from raw.orders via {{ source('raw', 'orders') }} — order_id, customer_id, restaurant_id, courier_id, subtotal, delivery_fee, placed_at;
  • add one derived column, order_total, as subtotal + delivery_fee — this is the "light derivation" staging is allowed to do;
  • do not join to stg_restaurants or stg_couriers here — that join is an intermediate model, not staging, and is out of scope until later in the course.
-- models/staging/stg_orders.sql -- fill in the SELECT
select
    order_id,
    -- TODO: the rest of the columns, plus order_total
from {{ source('raw', 'orders') }}

5 · Materialize as views, and set it project-wide

A materialization is how dbt turns a SELECT into a real warehouse object. A view stores no data — every read re-runs the query — which is exactly right for staging: cheap to build, always reflects the current raw data, and there's no meaningful storage cost for a thin pass-through. Set it once for the whole staging folder in dbt_project.yml, rather than repeating a config block in every model:

models:
  food_delivery_pipeline:
    staging:
      +materialized: view

Marts (Day 4) will override this to table at the folder level — different trade-off, same mechanism.

Now look at the graph dbt built from your three source() calls — no joins between models yet, so it's flat, but the mechanism is what matters:

uv run --project ../dbt_env dbt list --resource-type model --output path
uv run --project ../dbt_env dbt docs generate
uv run --project ../dbt_env dbt docs serve

dbt list prints the three models dbt found. dbt docs generate builds a static site describing the project — including a DAG viewer — and dbt docs serve opens it at localhost:8080. Click a model node and look for two things: the Sources node feeding each stg_ model (that's your source() call, drawn as an edge), and the fact that stg_restaurants, stg_couriers and stg_orders currently have no edges to each other — they're siblings, not a chain, because nothing has joined them yet. That changes on Day 4 when marts ref() more than one staging model at once.

Why ref() over a hardcoded table name: today's models only use source(), but every model you write from Day 4 onward will call {{ ref('stg_orders') }} instead of writing dbt_dev.stg_orders directly. ref() is how dbt knows the dependency exists at all — write the schema name by hand instead, and dbt has no way to know one model must run before another, and no way to draw the edge in dbt docs serve.

Q: "What's the difference between source() and ref()?" A strong answer, out loud: "source() points at a table dbt didn't build — raw data that landed some other way, in this project a batch script or Kafka. ref() points at a table another dbt model built. Both compile down to a schema-qualified table name, but only by going through one of them does dbt learn the dependency exists, which is what lets it compute build order and draw the DAG. If I write the table name by hand instead, the SQL still runs, but dbt has no idea one model needs to run before another — the graph just silently loses that edge." The signal: dbt's dependency tracking is opt-in per reference, not automatic from the SQL alone.
