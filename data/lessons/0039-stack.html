stack(): pulling columns down into the row index

Lesson 38's teaser named stack() as its own topic — mentioned in passing back in Lessons 6 and 14 as unstack()'s inverse, but never taught directly (only unstack() itself got a full lesson, in Lesson 15). Today closes that gap from the other direction: start from a wide table, not a groupby, and watch stack() turn it long.

1 · What stack() does: columns become the innermost row-index level

Lesson 15 built a wide customer-by-date table with unstack(). Run it again here as today's starting point:

by_customer_date = clean.groupby(["customer", "order_date"])["amount"].sum()
wide_by_date = by_customer_date.unstack("order_date", fill_value=0)
-- order_date  2026-01-05  2026-01-06  2026-01-09  2026-01-10
-- customer
-- An               120.0         0.0         0.0        42.0
-- Binh               0.0        35.5       180.0         0.0

stack() undoes exactly this: it takes the column labels and moves them down to become the innermost level of the row index.

restacked = wide_by_date.stack()
-- customer  order_date
-- An        2026-01-05    120.0
--           2026-01-06      0.0
--           2026-01-09      0.0
--           2026-01-10     42.0
-- Binh      2026-01-05      0.0
--           2026-01-06     35.5
--           2026-01-09    180.0
--           2026-01-10      0.0
-- dtype: float64

restacked is exactly by_customer_date back again, value for value — stack() and unstack() are true inverses of each other on this round trip, the same "long ↔ wide" pair Lesson 15 described from the unstack side. Where unstack() read "spread a row-index level across new columns," stack() reads "collapse the columns back down into a row-index level" — same operation, opposite direction.

2 · The SQL bridge: this is UNPIVOT, or a manual long rebuild via UNION ALL

A SQL-comfortable way to picture stack(): it's what UNPIVOT does in databases that support it (SQL Server, Snowflake), or what a manual long rebuild does everywhere else — one SELECT customer, '2026-01-05' AS order_date, "2026-01-05" AS amount FROM wide_table UNION ALL SELECT customer, '2026-01-06', "2026-01-06" FROM wide_table UNION ALL ... per column, stacking every column's values underneath each other with the original column name carried along as a new value column. stack() does that same UNION-ALL-per-column rebuild in one call, and — unlike hand-writing it — never needs the column list typed out twice.

3 · Difference from melt(): index level vs. plain column

Lesson 6 taught melt() for the same wide-to-long direction. Both get to the same destination, but they don't leave the result in the same shape:

melted = wide_by_date.reset_index().melt(
    id_vars="customer", var_name="order_date", value_name="amount"
)
--   customer order_date  amount
-- 0       An 2026-01-05   120.0
-- 1     Binh 2026-01-05     0.0
-- 2       An 2026-01-06     0.0
-- ... (8 rows, plain flat columns, arbitrary row order)

melt() hands back a flat DataFrame with order_date as an ordinary column — no index gymnastics needed, and the row order is whatever melt() chooses (column-major, not sorted by customer). stack() hands back a Series (or DataFrame, for MultiIndex columns — Section 4) with order_date sitting as a row-index level instead, sorted by the outer level first — usually followed by its own reset_index() to reach melt()'s flat shape. In practice: reach for melt() on an ordinary flat wide table (it's the more portable habit — works no matter how the wide table was built); reach for stack() when the table already has, or should keep, a meaningful row-index structure, since it preserves that structure natively instead of flattening it away.

4 · dropna behavior: this pandas version keeps every combination

Older pandas versions defaulted to silently dropping rows that stack() newly creates and that come out entirely NaN — a real gotcha the docs still warn about. The pandas version this course runs on (checked directly: uv run --with pandas python3 -c "import pandas; print(pandas.__version__)" reports 3.0.5) uses the newer stacking implementation, where that auto-drop no longer happens at all — every row survives, NaN included:

wide_nan = by_customer_date.unstack("order_date")  # no fill_value -- real NaN gaps
wide_nan.stack()
-- customer  order_date
-- An        2026-01-05    120.0
--           2026-01-06      NaN   <- kept, not dropped
--           2026-01-09      NaN
--           2026-01-10     42.0
-- Binh      2026-01-05      NaN
--           2026-01-06     35.5
--           2026-01-09    180.0
--           2026-01-10      NaN
-- dtype: float64
Version gotcha: if a tutorial, Stack Overflow answer, or interviewer's mental model says "stack() drops the all-NaN rows it creates by default" — that was true under the legacy implementation, and is exactly what dropna=True used to control. On current pandas, passing dropna= explicitly at all now raises a ValueError ("dropna must be unspecified") — the argument is being phased out because the new implementation never drops rows in the first place. Always check pd.__version__ before trusting a remembered default; this is exactly the kind of version-drift trap interviewers like to probe ("does that still hold on the version you'd actually be running?").

5 · MultiIndex columns: stack(level=...) picks which level moves

Lesson 14's two-aggfunc pivot_table produced MultiIndex columns (one level for the aggfunc, one for the date) and used flatten-then-melt to reshape it. stack(level=...) is the native alternative Lesson 14 flagged but didn't demonstrate — it needs no flattening step, because it already understands MultiIndex columns:

pv = clean.pivot_table(
    index="customer", columns="order_date", values="amount",
    aggfunc=["sum", "count"], fill_value=0,
)
-- columns: MultiIndex [("sum", 2026-01-05), ("sum", 2026-01-06), ..., ("count", 2026-01-10)]
pv.stack(level=0)
-- order_date       2026-01-05  2026-01-06  2026-01-09  2026-01-10
-- customer
-- An        sum         120.0         0.0         0.0        42.0
--           count         1.0         0.0         0.0         1.0
-- Binh      sum           0.0        35.5       180.0         0.0
--           count         0.0         1.0         1.0         0.0

level=0 names the outermost column level (the aggfunc name) to pull down; it lands as a new innermost row-index level right under customer, leaving order_date in place as the columns — the exact move Lesson 14 described in words ("wide.stack(level=0) pulls the aggfunc level directly down into the row index") without ever showing the output. Same trade-off as Section 3: no flatten-string step needed, but the aggfunc name is now an index level, not a plain column, so a reset_index() still usually follows.

Q: "When would you reach for stack()/unstack() instead of melt()/pivot_table(), and what's a common mistake with stack()?" A strong answer, out loud: "They solve the same long-vs-wide problem, but melt/pivot_table are the more general, portable habit — they work on any flat wide table and don't require me to think about index levels. stack/unstack are the right call when the table already has, or should keep, a meaningful MultiIndex — say, a groupby result I want to reshape without flattening column names into strings first, or a pivot_table with multiple aggfuncs where stack(level=0) pulls the aggfunc level down natively. The mistake I'd watch for: older pandas silently dropped newly-created all-NaN rows when stacking, controlled by a dropna argument — current pandas dropped that behavior entirely, so relying on a remembered default without checking pandas.__version__ against what's actually installed is a real way to get surprised in production, and it's also a good thing to flag out loud in an interview to show I know the API isn't static." The signal: naming stack/unstack and melt/pivot_table as solving the same problem at different levels of index-awareness, not two unrelated tool families — and knowing to double-check version-dependent defaults rather than trusting memory.
