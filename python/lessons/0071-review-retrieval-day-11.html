1 · Three questions, in the original teaching order

Answer each out loud or on paper before reading the fold-out answer. If one is shaky, note it and go fix it in the practice file below rather than only rereading the old lesson.

Day 68 — subprocess. Why is passing a list of arguments to subprocess.run() safer than building one string and passing shell=True, and what does check=True actually change?

Fold-out answer: the list form passes each element to the program as exactly one argument, with no shell involved to reinterpret spaces, quotes, or special characters like ;. shell=True hands a raw string to the system shell to parse instead, so untrusted input containing shell metacharacters can inject extra commands. check=True changes subprocess.run() from silently returning a result on a nonzero exit code (leaving the caller to remember to check returncode by hand) to raising CalledProcessError automatically whenever the command fails.

Day 69 — statistics. Why can mean() and median() disagree sharply on the same list, and what is the specific bug risk in hand-rolling a median() instead of calling statistics.median()?

Fold-out answer: mean() sums every value and divides by the count, so one extreme outlier drags it far from where most of the data sits. median() sorts first and takes the middle, so that same outlier barely moves it. A hand-rolled median() commonly gets the even-length case wrong — picking one of the two middle values instead of averaging them — the exact off-by-one the standard library has already gotten right so no one has to re-solve it per pipeline.

Day 70 — decimal. Why does 0.1 + 0.2 == 0.3 evaluate to False in plain Python, and why doesn't wrapping a float literal in Decimal() fix that?

Fold-out answer: float stores numbers in base 2, and most decimal fractions — including 0.1, 0.2, and 0.3 — have no exact, finite binary representation, so each is stored as the closest approximation; adding two approximations produces a result that is extremely close to, but not exactly, 0.3. Decimal(0.1) doesn't fix this because the float literal has already lost precision the moment Python parsed it — Decimal just displays that already-imprecise binary value in full exact digits. The fix is constructing Decimal from a string (or int), never from a float, so no float step ever gets a chance to lose precision first.
