pivot_table() vs .pivot(): the duplicate-key gotcha, plus margins=True

Lesson 6 already reached straight for pivot_table() to build a wide report, and it just worked. Today explains why that was the right instinct rather than luck: pandas actually has a second, stricter pivot method — .pivot() — that Lesson 6 skipped past on purpose. Today meets it, watches it crash on real data, and comes back to pivot_table() with a clearer picture of what it's buying you — plus one feature Lesson 6 never used: margins=True.

Recap, in one line

Lesson 6: pivot_table(index=, columns=, values=, aggfunc=) reshapes long data wide, one row per index value, one column per distinct columns value. Today's question: what happens when more than one row shares the same index/columns pair — and what a plain .pivot() does differently.

1 · .pivot(): pivot_table's stricter, aggregation-free sibling

pandas actually ships two pivot methods. .pivot() is the plain one: same index=/columns=/values= shape as pivot_table, but no aggfunc argument at all — because it assumes there's nothing to aggregate. Every index/columns combination is assumed to map to exactly one row already:

orders = pd.DataFrame({
    "order_id": [1, 2, 3, 4, 5],
    "customer": ["An", "Binh", "An", "Binh", "An"],
    "order_date": ["2026-01-05", "2026-01-06", "2026-01-05", "2026-01-06", "2026-01-10"],
    "amount": [120.0, 35.5, 60.0, 180.0, 42.0],
})
orders.pivot(index="customer", columns="order_date", values="amount")
-- ValueError: Index contains duplicate entries, cannot reshape

An placed two orders on 2026-01-05 (order_id 1 and 3 — a re-submitted or corrected order, the kind of thing that happens constantly in real order data). .pivot() has no way to decide what a single An/2026-01-05 cell should hold when two rows want to fill it, so it refuses outright rather than silently pick one. This is exactly the row Lesson 6's clean 4-row slice never had — every customer/date pair there was already unique, which is why .pivot() would have worked fine on it too, and why Lesson 6 never had to explain the difference.

Gotcha: .pivot()'s error only fires at reshape time, on the FULL combination of index + columns — it says nothing about which rows collided or what values were involved. In a real pipeline this shows up as a crash several steps downstream of wherever the actual duplicate got introduced (a re-run, a late correction row, a join that fanned out) — the traceback points at the pivot call, not the cause.

2 · pivot_table(): the same reshape, but aggfunc decides the collision

This is the one difference that matters: pivot_table() takes everything .pivot() takes, plus aggfunc — and when two or more rows land on the same cell, it runs aggfunc over all of them instead of raising. Same duplicate data, no crash:

orders.pivot_table(index="customer", columns="order_date", values="amount", fill_value=0)
-- order_date  2026-01-05  2026-01-06  2026-01-10
-- customer
-- An                90.0        0.00        42.0   <- mean(120.0, 60.0), the DEFAULT aggfunc
-- Binh               0.0      107.75         0.0

orders.pivot_table(index="customer", columns="order_date", values="amount", aggfunc="sum", fill_value=0)
-- order_date  2026-01-05  2026-01-06  2026-01-10
-- customer
-- An               180.0         0.0        42.0   <- sum(120.0, 60.0) instead
-- Binh               0.0       215.5         0.0

Notice the first call didn't pass aggfunc at all — pivot_table's default is aggfunc="mean", silently. An's 2026-01-05 cell became 90.0, the average of 120.0 and 60.0, not an error and not either original value. That default is easy to miss precisely because nothing crashes: the output looks completely reasonable, and unless the numbers are checked against a known total, an accidental mean-instead-of-sum bug can ship silently. Lesson 6's own examples always passed aggfunc="sum" explicitly for exactly this reason — worth calling out now that the reason is visible.

Rule of thumb for interviews: "does every index/columns pair already map to one row?" — if yes, .pivot() is a fine, slightly stricter choice (it documents that assumption and enforces it). If that's ever in doubt — real order data, event logs, anything from a source that can retry or correct itself — reach for pivot_table() and pass aggfunc explicitly rather than trusting the mean default.

3 · margins=True: row and column subtotals, for free

pivot_table has one more argument .pivot() doesn't: margins=True. It adds one extra row and one extra column, each holding aggfunc run across that whole row or column — a grand-total row and column, computed with the same aggregation as everything else:

orders.pivot_table(
    index="customer", columns="order_date", values="amount",
    aggfunc="sum", fill_value=0, margins=True, margins_name="All",
)
-- order_date  2026-01-05  2026-01-06  2026-01-10    All
-- customer
-- An               180.0         0.0        42.0  222.0   <- An's row total
-- Binh               0.0       215.5         0.0  215.5   <- Binh's row total
-- All              180.0       215.5        42.0  437.5   <- column totals, and the grand total

margins_name="All" (default is literally the string "All" already, named here for clarity) labels that extra row/column — pick something that can't collide with a real customer or order_date value. The bottom-right corner (437.5) is the grand total either way you'd sum it: down An's row, or across the All column — both reach the same number, which is a good sanity check that nothing else went wrong.

SQL bridge: margins=True is pandas' answer to GROUP BY ROLLUP(...) or a UNION ALL with a subtotal query bolted on — both real SQL patterns for "grand total row/column alongside the detail," both noticeably more ceremony than one keyword argument. There's no SQL keyword that adds a margin to a pivoted report shape directly, since SQL has no pivot primitive of its own either (Lesson 6's opening point).

4 · Putting it together: pivot_table is pivot + collision handling + optional totals

One sentence worth having ready for an interview: pivot_table is what .pivot() would be if it also handled duplicate keys (via aggfunc, default mean) and could add grand-total rows/columns on request (margins=True). Reaching for pivot_table by default — the way Lesson 6 quietly already did — is the safer habit; knowing .pivot() exists, what it assumes, and exactly which error it throws when that assumption breaks is what separates "used pivot_table once" from "understands why."

Q: "What's the difference between .pivot() and pivot_table(), and when would .pivot() actually fail?" A strong answer, out loud: ".pivot() assumes every index/columns combination already maps to exactly one row — it has no aggfunc at all. If two rows share the same index/columns pair, .pivot() raises ValueError: Index contains duplicate entries, rather than guessing which one to keep. pivot_table() is the more general version: same index/columns/values shape, but it adds an aggfunc — mean by default, so I always pass aggfunc explicitly rather than trust that default — that runs over however many rows land on each cell, so duplicates get aggregated instead of crashing. pivot_table() also supports margins=True, which adds a grand-total row and column computed with that same aggfunc, without a separate groupby step. In practice I default to pivot_table() any time the source data could plausibly have a repeat key — re-submitted orders, retried events — and only reach for plain .pivot() when I specifically want that duplicate-key assumption enforced as a check." The signal: naming the exact ValueError, naming the mean default as a real gotcha (not just "it aggregates"), and framing margins=True as a grand total, not a new concept.
