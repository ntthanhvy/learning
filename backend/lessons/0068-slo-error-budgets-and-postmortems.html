SLOs, error budgets, and postmortems: what you do with the signal once monitoring finds it

Lesson 13 built the tools that answer "is it happening now" and "what happened" — metrics and logs. It never answered a harder pair of questions: how bad is bad enough to page someone at 3am, and what happens organizationally after that page fires? Today closes that loop: the number that defines "good enough," the budget derived from it that turns a philosophical debate into an engineering decision, and the document a team writes afterward so the same outage doesn't teach the same lesson twice.

1 · A promise, a number, and a budget

Three related terms get used almost interchangeably in casual conversation, but they answer three different questions. An SLA (service level agreement) is a contract, often with real financial penalties, promising a customer some level of reliability — "99.9% uptime or you get a credit." An SLI (service level indicator) is the actual measured number backing that promise — the same kind of metric Lesson 13 already taught you to graph, like "percentage of requests completed under 300ms" or "percentage of requests that didn't 5xx." A SLO (service level objective) is the internal target set against that SLI — "99.9% of requests succeed in a rolling 30-day window."

The SLO is deliberately the tightest of the three, and that's the whole point: if the external SLA promises 99.9% and the internal SLO also targets exactly 99.9%, the team finds out about a problem at the exact same moment the customer already has grounds for a refund. Setting the SLO stricter — or measuring it over a shorter, faster-moving window — buys the team time to notice and fix an issue before the contractual promise is actually broken. This is the same "leave headroom before the hard limit" instinct Lesson 61's statement_timeout already taught for one query and Lesson 18's pool sizing taught for a whole service — here applied to the reliability target itself.

2 · The error budget: turning "how careful should we be" into a number

A 99.9% SLO isn't a demand for perfection — it's an explicit admission that 0.1% of requests are allowed to fail, on purpose. Multiply that allowance out over the SLO's window and it becomes a real, spendable quantity: at 1,000,000 requests a month, a 99.9% SLO permits 1,000 failed requests before the SLO itself is breached. That permitted quantity is the error budget.

// A rolling error budget check -- the same shape as a rate limiter's
// bucket (Lesson 11), spent by failures instead of by requests.
type errorBudget struct {
    windowRequests int64 // total requests in the rolling window
    windowFailures int64 // failed requests in that same window
    sloTarget      float64 // e.g. 0.999 for a 99.9% SLO
}

// remaining reports how much budget is left, as a fraction from 1.0 (fresh)
// down to 0.0 (fully spent) and below (SLO already breached).
func (b errorBudget) remaining() float64 {
    allowed := (1.0 - b.sloTarget) * float64(b.windowRequests)
    if allowed == 0 {
        return 1.0
    }
    return 1.0 - float64(b.windowFailures)/allowed
}

The budget's real job is turning a values argument into a math problem. "Should we ship this risky migration today?" is a debate that can go in circles forever on instinct alone. "We've spent 85% of this month's error budget already, and the migration has a known failure mode" is a number two people can agree on without agreeing on much else — spend the rest of the budget shipping features and taking calculated risks; once it's gone, the team's own rule is to stop taking on new risk and spend engineering time on reliability instead, until the window rolls forward and the budget refills.

Not the same shape as a rate limiter, despite the code above. Lesson 11's token bucket rejects requests in real time to protect the service right now. An error budget rejects nothing automatically — it's a retrospective, rolling count that a team consults to make a deploy/no-deploy or hire-more-SREs/ship-more-features decision. Nobody's request gets a 429 because the error budget is low; a human reads the number and changes behavior.

3 · When the budget runs out anyway: on-call and the runbook

Monitoring (Lesson 13) is what pages someone in the first place — a metric crossing an SLO-derived alert threshold, not just any blip. The person who gets paged is on-call: a rotating responsibility, not a permanent job, precisely so the 3am pages don't always land on the same person. What that person does next is where most of the actual value of preparation shows up: a runbook is a pre-written, step-by-step guide for a specific, recognized failure mode — "connection pool exhausted: check X, restart Y, escalate to Z if that doesn't help" — written calmly in advance instead of improvised at 3am under pressure with a page blaring.

A runbook works because most incidents aren't actually novel. Lesson 47's cascading-restart failure, Lesson 18's pool exhaustion, and Lesson 57's stampede are exactly the kind of recurring, nameable failure a runbook exists for — the first time any of them happens it's a fire; the second time, it should be a checklist.

4 · After the fire is out: the blameless postmortem

Fixing the immediate outage and understanding why it happened are two different jobs, done at two different times. A postmortem is written after the incident is resolved, reconstructing the timeline, the root cause, the impact, and — critically — a list of concrete action items, not vague resolutions. The word "blameless" isn't a soft HR add-on: a postmortem that names which engineer to blame teaches every other engineer to hide problems and route around monitoring rather than report them, which produces a team with worse signal exactly when it needs better signal most. A blameless postmortem asks what let the failure happen — a missing runbook, an alert threshold set wrong, a migration that shipped without review — because those are the things a team can actually fix.

Q: "Your team keeps missing its uptime target. How would you approach fixing that?" A strong answer, out loud: "First I'd check whether we even have an SLO distinct from the customer-facing SLA — if the internal target isn't stricter than the promise, we're finding out about problems at the same moment the customer has grounds for a complaint. I'd want an error budget tracked against that SLO, because it turns 'should we ship this risky change' from a values argument into a number the team can actually agree on — spend the budget on calculated risk, and once it's gone, prioritize reliability work over new features until it refills. For the incidents that do happen, I'd want runbooks for the recurring, nameable failure modes so on-call isn't improvising under pressure, and a blameless postmortem after anything serious — blameless specifically so people report problems honestly instead of hiding them to avoid blame." The signal: naming the SLA/SLO/error-budget chain as a decision-making tool, not just reliability trivia, and knowing why "blameless" is a functional requirement, not a nicety.
