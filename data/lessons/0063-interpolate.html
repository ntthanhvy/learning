interpolate(): filling a gap by estimating between real neighbors

Fresh curriculum/glossary scan this round, as Lesson 62's teaser asked for: grepped every lesson for interpolate and found only a single "not needed today" aside in Lesson 38 — the same gap Lesson 47's and 48's scans already flagged and nobody picked up since. Lesson 3 taught drop/constant-fill/flag; Lesson 45 added ffill()/bfill() (copy the nearest real neighbor). Today adds the fourth missing-data move none of them cover: estimating a gap's value FROM its real neighbors via straight-line math, rather than copying one of them outright.

1 · Recap: three fill strategies down, one to go

Lesson 3: fillna(value) — one constant (a median, a zero) for every gap, computed once up front. Lesson 45: ffill()/bfill() — copy the nearest real value, unchanged, from above or below. Both are honest about what they do: a constant, or an exact copy. interpolate() is different in kind — for a numeric column, it draws a straight line between the two real values on either side of a gap and reads off the value the line would have at the gap's position. Same family of problem, a genuinely different guess.

2 · SQL bridge: no built-in for this at all

SQL has COALESCE for a constant fill and window-function tricks for "the last non-null value" (Lesson 45 showed the ROWS BETWEEN UNBOUNDED PRECEDING pattern) — but straight-line interpolation between two real rows has no standard SQL equivalent; it usually needs a correlated subquery finding the nearest real value on each side, then hand-writing the linear formula. interpolate() is one of the clearer cases where pandas is doing genuinely more than a one-line SQL translation, not just re-spelling something SQL already has a keyword for.

3 · The default: linear interpolation

interpolate() with no arguments assumes evenly-spaced rows and fits a straight line between each gap's real neighbors:

s = pd.Series([10.0, None, None, 40.0, None, 60.0])
s.interpolate()
-- 0    10.0
-- 1    20.0   <- 1/3 of the way from 10 to 40
-- 2    30.0   <- 2/3 of the way from 10 to 40
-- 3    40.0
-- 4    50.0   <- halfway from 40 to 60
-- 5    60.0

s.ffill()   -- for contrast: every gap just copies the value above it
-- 0    10.0
-- 1    10.0
-- 2    10.0
-- 3    40.0
-- 4    40.0
-- 5    60.0

Confirmed directly: rows 1 and 2 each get a genuinely different, computed value (20.0, 30.0) — never seen anywhere in the original data — while ffill() on the same Series just repeats 10.0 twice. Neither is "more correct" in the abstract; it depends on what the column actually measures. A steadily-changing quantity (a thermometer reading, a running balance drifting between two known checkpoints) is well modeled by a straight line; a "status as of now" column (Lesson 45's use case) is not — there's no meaningful "60% of the way between 'active' and 'cancelled.'"

4 · The edge gotcha: a leading NaN still stays NaN, same family as ffill()

A straight line needs a real value on both sides — a gap with nothing above it (or nothing below it) has no line to draw, so the default leaves it as NaN, silently, exactly like Lesson 45's ffill()/bfill() edge case:

s2 = pd.Series([None, 10.0, None, 30.0])
s2.interpolate()                        # default limit_direction="forward"
-- 0     NaN   <- nothing above it -- no line possible, stays NaN
-- 1    10.0
-- 2    20.0
-- 3    30.0

s2.interpolate(limit_direction="both")   # fills the leading edge too
-- 0    10.0   <- carried flat from the nearest real value, not a true line
-- 1    10.0
-- 2    20.0
-- 3    30.0

Confirmed directly: limit_direction="both" fills the leading edge, but not with a genuine interpolation — with nothing on one side, it just extends the single available neighbor flat (functionally an ffill/bfill for that one edge cell only). Always check .isna().sum() after, the same standing habit Lesson 45 already established — a table starting or ending with a real gap can still come out of interpolate() not fully filled.

5 · The groupby gotcha: worse than ffill(), because there's no groupby().interpolate() at all

Like every row-order-trusting tool before it (cumsum(), shift(), rolling(), ffill()), plain interpolate() only sees physical row position — it has no idea one customer's rows just ended and another's just began, so a gap sitting right at that boundary gets a line drawn straight through it from the wrong customer's data:

-- sorted by customer then order_date -- Binh's FIRST row is missing:
--   customer order_date  amount
-- 0       An 2026-01-05   120.0
-- 1       An 2026-01-10    42.0
-- 2     Binh 2026-01-06     NaN   <- Binh's own first value, genuinely unknown
-- 3     Binh 2026-01-09   180.0
clean["amount"].interpolate()
-- 0    120.0
-- 1     42.0
-- 2    111.0   <- WRONG: a straight line from An's 42.0 to Binh's 180.0
-- 3    180.0

Lesson 45's fix for ffill() was one word: chain groupby("customer") before the call. That fix does NOT exist here — confirmed directly, df.groupby("customer")["amount"].interpolate() raises AttributeError: 'SeriesGroupBy' object has no attribute 'interpolate' outright. interpolate() is not a recognized groupby-aggregation method the way ffill()/bfill()/sum()/cumsum() are. The working fix reaches back to Lesson 16's transform():

clean.groupby("customer")["amount"].transform(lambda s: s.interpolate())
-- 0    120.0
-- 1     42.0
-- 2      NaN   <- correct: Binh has no earlier row of her own to draw a line from
-- 3    180.0

transform() runs the lambda once per group and hands back a result broadcast to each group's own rows (same row count, same order) — exactly the shape interpolate() needs but doesn't provide a direct per-group entry point for. groupby().apply() (Lesson 61) would also work here, but transform() is the narrower, more idiomatic tool for a same-length numeric result.

A crash, not a silent-wrong trap this time: interpolate() only works on numeric dtypes. Confirmed directly: calling it on a text/object column raises TypeError: Series cannot interpolate with object dtype immediately — no NaN, no guess, no partial result. This is the opposite failure mode from the groupby gap above; check the column's dtype first (select_dtypes, Lesson 25) rather than discovering it mid-pipeline.

6 · method="time": respecting real elapsed time, not just row position

Plain interpolate() (method "linear", the default) treats every row as equally spaced, regardless of the actual gap between timestamps. On a DatetimeIndex with irregular spacing, that can misjudge how far along the line a gap actually sits — method="time" fixes it by weighting the interpolation by real elapsed time instead of row count:

-- index: Jan 1, Jan 2, Jan 5, Jan 6 -- NOT evenly spaced (3-day gap in the middle)
s.interpolate()                 # default "linear" -- ignores the date gap, treats rows as evenly spaced
-- Jan 1    10.0
-- Jan 2    20.0   <- 1/3 of the way, by ROW count only
-- Jan 5    30.0   <- 2/3 of the way, by ROW count only
-- Jan 6    40.0

s.interpolate(method="time")   # weights by ACTUAL days elapsed
-- Jan 1    10.0
-- Jan 2    16.0   <- only 1 of 5 total days elapsed -- closer to 10 than row-based guessed
-- Jan 5    34.0   <- 4 of 5 total days elapsed
-- Jan 6    40.0

Confirmed directly on an index spanning Jan 1/2/5/6: the two methods disagree (20.0/30.0 vs. 16.0/34.0) precisely because the middle gap spans 3 real days while the outer gaps span only 1 — method="time" requires the object to have a real DatetimeIndex to measure elapsed time against; plain method="linear" works on any numeric index, including a default RangeIndex.

Q: "A numeric time series has some missing readings. Why reach for interpolate() instead of ffill() or a median fill?" A strong answer, out loud: "It depends on what kind of quantity is missing. A median fill assumes the true value is close to typical, which throws away any trend. ffill() assumes nothing changed since the last reading, which is right for a 'status as of now' column but wrong for something that's steadily drifting, like a sensor value or a running balance between two known checkpoints — there, a straight-line estimate between the real value before and after the gap is a more honest guess than either a flat copy or a global average. Two things I'd flag unprompted: interpolate() only works on numeric dtypes, it raises immediately on text; and unlike ffill()/bfill(), there's no groupby().interpolate() at all — on a multi-entity table I have to use groupby(key)['col'].transform(lambda s: s.interpolate()), or a gap at a group boundary silently draws a line straight through into the wrong entity's data, same family of bug as every other row-order-trusting tool in this course." The signal: picking the right fill strategy for what the column actually means, and naming the missing groupby-native method as a specific, confirmed gotcha rather than assuming it works like ffill().

7 · Where this fits in the missing-data toolkit

Four tools, four different assumptions about what a gap means: dropna() (Lesson 3, the value truly can't be recovered), fillna(constant) (Lesson 3, the honest guess is one typical value), ffill()/bfill() (Lesson 45, the honest guess is whatever was last/next observed, unchanged), and interpolate() (today, the honest guess is a computed point on the trend between two real neighbors). None replaces the others — picking correctly, out loud, based on what the column represents is the actual interview skill; the mechanical syntax is the easy part.
