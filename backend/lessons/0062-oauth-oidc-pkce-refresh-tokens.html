OAuth, OpenID Connect, PKCE, and refresh tokens: "Sign in with Google," properly named

Lesson 4 built login for a user proving their own identity to your own backend. Lesson 31 built one backend proving its identity to another, with no human involved at all. Neither covers the case sitting between them: a human, at your app, wants your app to act on their behalf against someone else's API — their Google Calendar, their GitHub repos — without ever handing your app their Google password. That specific problem is what OAuth 2.0 exists to solve, and it's been a named, deferred candidate since Lesson 60's round for exactly this reason: it's large enough to deserve its own lesson rather than a rushed mention.

1 · The problem: delegated access, not your own login

Your app wants to read a user's Google Calendar to suggest meeting times. The wrong design is obvious once stated: ask the user to type their Google password into your login form, store it, and use it to call Google's API yourself. That fails the moment you think about it — your app now holds a credential that unlocks the user's entire Google account, forever, with no way for the user to revoke just your app's access without changing their password everywhere else.

OAuth 2.0 is the fix: the user proves who they are directly to Google (never to your app), then Google hands your app a narrow, revocable token — not the password, and not full account access, just "calendar read, for this app, until it expires." Three distinct parties are worth naming precisely, because the rest of this lesson refers to them by role: the client (your app), the authorization server (Google's login/consent screen), and the resource server (the Google Calendar API itself) — often the same company operates both the authorization server and resource server, but the roles are still distinct.

2 · The authorization code flow, step by step

The dominant flow for a backend web app is the authorization code flow:

1. Your app redirects the browser to Google:
   GET https://accounts.google.com/o/oauth2/auth
     ?client_id=...&redirect_uri=https://yourapp.com/callback
     &scope=calendar.readonly&response_type=code&state=xyz123

2. User logs into Google (if not already) and approves the requested scope
3. Google redirects back: GET https://yourapp.com/callback?code=AUTH_CODE&state=xyz123
4. Your BACKEND (never the browser) exchanges the code, server-to-server:
   POST https://oauth2.googleapis.com/token
     grant_type=authorization_code&code=AUTH_CODE&client_secret=...
5. Google responds: { access_token, refresh_token, expires_in }

Two details carry real weight. First, the code from step 3 is a one-time-use, short-lived value — it is not itself the access token, only something exchangeable for one, and only from the backend, since only the backend holds the client_secret the exchange requires. Second, state is not decoration: it's a random value your app generated before the redirect and must check for an exact match on the way back, closing off a CSRF-shaped attack where a forged callback with someone else's code gets linked to the wrong account. scope is the other load-bearing parameter — it names exactly what access is being requested (calendar.readonly, not the whole account), and it's what the user actually sees and approves on Google's own consent screen, not something your app can silently widen later without the user approving again.

3 · Access tokens vs. refresh tokens: why there are two

Step 5's response carries two different tokens with two different jobs:

Access tokenRefresh token
Used forcalling the resource server's API directly, on every requestgetting a new access token once the old one expires
Typical lifetimeminutes to about an hourdays, months, or until revoked
Sent tothe resource server (e.g. the Calendar API)only back to the authorization server's token endpoint
If leakeduseful only until it expires soonuseful until revoked — the higher-value target

This is the same short-lived-credential shape Lesson 31's client credentials grant used for service-to-service calls, applied here to a human's delegated access instead: a short-lived access token is what actually travels on every API call, while a longer-lived refresh token is kept server-side and never sent to the resource server at all — only back to the authorization server's own token endpoint. That split exists because the two are exposed in different places with different risk: an access token rides along on every one of potentially thousands of API calls, so keeping it short-lived caps the damage of any single leaked copy; a refresh token is used rarely and only against one trusted endpoint, so it's allowed to live much longer without the same exposure.

4 · PKCE: the fix for a flow that can't keep a secret

Step 4's exchange assumed the client holds a client_secret — fine for a backend web app, since the secret never leaves your server. A mobile app or a single-page app has no such place to hide one: decompile the app or read the JS bundle and the "secret" is right there, not secret at all. PKCE (pronounced "pixy") fixes this without a shared secret at all:

1. Client generates a random code_verifier, keeps it in memory only
2. Client derives code_challenge = BASE64URL(SHA256(code_verifier))
3. Authorization redirect includes code_challenge (not the verifier)
4. Authorization server stores code_challenge alongside the issued code
5. Token exchange sends the original code_verifier (not the challenge)
6. Authorization server hashes the received verifier and checks it
   matches the challenge stored in step 4 -- proves same client, no secret needed

The trick is a one-way function: anyone who intercepts the authorization code in step 3's redirect (a real risk on mobile, where another app can sometimes register the same custom URL scheme) only ever sees the hashed challenge, never the verifier — and a hash can't be reversed to recover the value that produced it. Only the client that generated the original code_verifier can produce a match in step 6, so a stolen authorization code alone is useless to an attacker without also holding the verifier that never left the legitimate client's memory. PKCE was designed for public clients but is now recommended for confidential (backend) clients too, as defense-in-depth alongside the client_secret — the same "don't rely on one layer" instinct Lesson 58's synthesis lesson and Lesson 59's RLS lesson both already made for other problems.

5 · OpenID Connect: OAuth answers "can this app act," not "who is this"

A subtle trap: OAuth's access token only proves the client was granted some scope of access — it was never designed to answer "who is the user," and treating it as an identity proof is a well-documented misuse. OpenID Connect (OIDC) is the layer built on top of OAuth specifically to answer that question properly: the same authorization-code exchange also returns an id_token — a ID token, literally Lesson 4's JWT design, reused — carrying signed claims (a stable subject id, email, name) your app verifies and reads to establish the session, exactly the way "Sign in with Google" buttons work in practice. The rule of thumb: an access token is a key that opens a specific door on someone else's API; an ID token is a signed statement of who's asking. Confusing the two — using an access token as if it proved identity — is a real, named class of implementation bug, not a pedantic distinction.

6 · A PKCE code-verifier pair and the callback exchange, in Go

The verifier/challenge pair from section 4, plus the callback handler that reads the returned code and would exchange it server-side:

// newPKCEVerifier generates a cryptographically random code_verifier and its
// derived code_challenge (S256), the pair PKCE uses to bind an authorization
// code to the same client that started the flow.
func newPKCEVerifier() (verifier, challenge string, err error) {
    raw := make([]byte, 32)
    if _, err := rand.Read(raw); err != nil {
        return "", "", err
    }
    verifier = base64.RawURLEncoding.EncodeToString(raw)

    sum := sha256.Sum256([]byte(verifier))
    challenge = base64.RawURLEncoding.EncodeToString(sum[:])
    return verifier, challenge, nil
}

// callbackHandler is the OAuth redirect target: it reads the authorization
// code Google appended to the redirect URI, looks up the code_verifier this
// browser stashed before the redirect (keyed by the state value), then
// exchanges code + verifier for tokens -- never the browser's job, always
// the backend's, since only the backend should ever see the tokens.
func callbackHandler(exchange func(code, verifier string) (*tokenResponse, error), verifierForState func(state string) string) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        code := r.URL.Query().Get("code")
        state := r.URL.Query().Get("state")
        if code == "" {
            http.Error(w, "missing code parameter", http.StatusBadRequest)
            return
        }
        verifier := verifierForState(state) // looked up, never re-derived
        tok, err := exchange(code, verifier)
        if err != nil {
            http.Error(w, "token exchange failed", http.StatusBadGateway)
            return
        }
        _ = tok // store access/refresh tokens server-side; never send to the browser
    }
}
Trap: the last line's comment is the part worth internalizing, not just the code — both tokens belong in your backend's storage (encrypted at rest), never in a cookie or response body the browser can read. The browser only ever needed the authorization code, briefly, to get here; once your backend has exchanged it, the browser's job in this flow is done.

7 · Where this sits next to Lessons 4 and 31

All three "who/what is this request" lessons now cover a distinct shape of the same underlying question, and it's worth lining them up explicitly so they don't blur together:

LessonWho's proving what, to whom
Lesson 4a user proves their identity directly to your own backend (sessions or JWT)
Lesson 31your backend proves its own identity to another backend, no human involved
Lesson 62 (this one)a user grants your app limited, revocable access to someone else's API, without sharing a password

OAuth is not a replacement for Lesson 4's own login — most apps still run their own session or JWT for "is this user logged into my app," and separately hold OAuth tokens for whichever third-party APIs the user has connected. The two systems commonly coexist in the same app for entirely different jobs.

Q: "Walk me through what happens when a user clicks 'Connect your Google Calendar' in our app." A strong answer, out loud: "We'd redirect the browser to Google's authorization endpoint with our client_id, the exact scope we need — calendar.readonly, not broader — a state value we generate and will check on return, and if this is a public client like a mobile app, a PKCE code_challenge too. The user approves on Google's own consent screen, never our login form, so we never see their Google password. Google redirects back to our callback with a one-time authorization code; our backend, not the browser, exchanges that code server-side for an access token and a refresh token. We store both server-side, use the short-lived access token on actual Calendar API calls, and use the refresh token — only against Google's token endpoint — to get a new access token once the old one expires, without asking the user to reconnect." The signal: naming the code-for-token exchange as strictly server-side, distinguishing access vs. refresh token lifetimes and where each travels, and treating scope as something the user actually approved rather than an implementation detail.
