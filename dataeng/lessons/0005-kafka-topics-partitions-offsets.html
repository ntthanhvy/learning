1 · Why a log, not a queue and not a table

Every table in this course so far — raw.orders, stg_orders, fct_orders — is something you can UPDATE or re-query at any offset into its rows and get the current truth. A log is different on purpose: it only ever appends. Nothing already written is edited or deleted in place (retention aside, which is Phase 2b). Order status changes are a perfect fit for that shape — placed doesn't get overwritten by accepted, it's a new fact that happened after placed and should stay on the record next to it.

Kafka is a distributed system built entirely around this one idea. A topic is a named feed — this course has exactly one, order_events, matching the domain table in PLAN.md. A producer appends records to a topic; a consumer reads them back, one at a time, tracking its own position. Nobody deletes a record when it's read — unlike a queue such as RabbitMQ or SQS, a Kafka record can be read by many different consumers, each keeping its own separate position in the same log.

2 · A topic is actually several logs: partitions

A topic isn't one giant log — it's split into a fixed number of partitions, decided when the topic is created. Splitting matters for two reasons: it's how Kafka distributes a topic's throughput across multiple brokers in a real cluster (out of scope here — this course runs one broker), and it's the unit Kafka's ordering guarantee actually applies to. Kafka promises order within one partition, full stop. It makes zero promise about order across partitions of the same topic.

That single sentence is the crux of today. If order_events had 3 partitions and every event were scattered across them at random, an order's placed event could land on partition 0 and its delivered event could land on partition 2 — and nothing would guarantee the consumer sees placed first. For a status sequence, that's not a subtle bug, it's the whole thing broken.

3 · The key decides the partition

Kafka's fix is the key: a string attached to every produced message. Kafka hashes the key and uses that hash to pick the partition — deterministically, so the exact same key always maps to the exact same partition, every time, for as long as the partition count doesn't change. This course's rule, matching PLAN.md's domain table exactly: key every order_events message with order_id. Every status change for order 101 — placed, accepted, picked_up, delivered — hashes to the same partition and is written there in send order, so a consumer reading that partition sees them in the order they happened. A message with no key (or a null key) round-robins across partitions instead — fine for data with no ordering requirement, wrong for this topic.

What the key does not do: it says nothing about order across different orders. Order 101's events and order 102's events can interleave freely, land on different partitions, arrive in any relative sequence — and that's fine, because nothing in this domain ever needs to compare order 101's status to order 102's. The key's job is narrow and exact: keep one order's own events in order. That's the whole guarantee, not a stronger one.

4 · Offsets: a partition's bookmark

Every record in a partition gets a permanent, ever-increasing position number: its offset, starting at 0. Offsets are local to a partition — partition 0's offset 5 and partition 2's offset 5 are two unrelated records. A consumer's job is to remember, per partition, the next offset it hasn't read yet, and that remembered position is called a committed offset. This should feel familiar: it's the same idea as keyset pagination's cursor from earlier courses — "give me everything after this bookmark," not "give me page 6."

Consumers don't commit offsets alone — they belong to a consumer group, identified by a group.id. Kafka assigns each partition in a topic to exactly one consumer within a group at a time, and the group's committed offsets are what let a consumer that dies and restarts — or a brand-new process that takes over — resume exactly where the group left off, instead of re-reading everything or skipping ahead. Day 6's consumer will lean on this directly: killing it mid-stream and restarting it must not create duplicate warehouse rows, and committed offsets are half of how that's arranged (the other half is the ON CONFLICT write itself).

6 · Build: create the order_events topic, with 3 partitions

Topics aren't created implicitly here — create it explicitly so the partition count is a deliberate choice, not whatever a default happens to be:

docker compose exec kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --create --topic order_events \
  --partitions 3 --replication-factor 1

Expected: Created topic order_events. (Replication factor 1 because this is a single broker — real clusters use 3, out of scope per MISSION.md's "running Kafka in production" exclusion.) Confirm the partition layout:

7 · Build: a Python producer, keyed by order_id

Create scripts/produce_order_events.py using confluent-kafka (this course's pinned client — no pandas, plain Python plus this one library, per the overlap rule). It's scaffolding: read it, then run it as-is today — Day 6 is where you'll adapt a version of this shape into the consumer's counterpart:

"""Produce a batch of order_events messages, keyed by order_id.

Keying by order_id (not event_id) is today's point: every event for one
order lands on the same partition, in send order.
"""
import json
import uuid
from datetime import datetime, timezone

from confluent_kafka import Producer

BOOTSTRAP = "localhost:9092"
TOPIC = "order_events"

# One order's full lifecycle, in the order it actually happened -- this is
# the sequence that must arrive at the consumer in this exact order.
STATUSES = ["placed", "accepted", "picked_up", "delivered"]


def delivery_report(err, msg):
    if err is not None:
        print(f"delivery failed: {err}")
    else:
        print(
            f"delivered to {msg.topic()} [partition {msg.partition()}] "
            f"@ offset {msg.offset()}, key={msg.key().decode()}"
        )


def make_event(order_id: int, status: str) -> dict:
    return {
        "event_id": str(uuid.uuid4()),
        "order_id": order_id,
        "status": status,
        "occurred_at": datetime.now(timezone.utc).isoformat(),
    }


def main():
    producer = Producer({"bootstrap.servers": BOOTSTRAP})

    for order_id in (101, 102, 103):
        for status in STATUSES:
            event = make_event(order_id, status)
            producer.produce(
                TOPIC,
                key=str(order_id),
                value=json.dumps(event),
                callback=delivery_report,
            )
            producer.poll(0)

    producer.flush()


if __name__ == "__main__":
    main()

The key=str(order_id) argument on producer.produce() is the one line that matters today — everything else is the confluent-kafka boilerplate any producer needs (a delivery_report callback confirming each write, flush() blocking until every message is actually sent). Run it:

uv run --with confluent-kafka python3 scripts/produce_order_events.py

Expected — read the partition column carefully, it's the whole lesson in one terminal output: every event for the same order_id lands on the same partition number, and within that partition the offsets are sequential:

delivered to order_events [partition 2] @ offset 1, key=101
delivered to order_events [partition 2] @ offset 2, key=101
delivered to order_events [partition 2] @ offset 3, key=101
delivered to order_events [partition 0] @ offset 0, key=102
delivered to order_events [partition 0] @ offset 1, key=102
delivered to order_events [partition 0] @ offset 2, key=102
delivered to order_events [partition 0] @ offset 3, key=102
delivered to order_events [partition 0] @ offset 4, key=103
delivered to order_events [partition 0] @ offset 5, key=103
delivered to order_events [partition 0] @ offset 6, key=103
delivered to order_events [partition 0] @ offset 7, key=103

Your own partition numbers may differ from this listing (the hash-to-partition mapping depends on the key's hash, not on run order) — what must match is that every row for key=101 shares one partition number, every row for key=102 shares one (possibly the same one 103 lands on, as above — two different keys can legally hash to the same partition), and each partition's own offsets count up without gaps.

8 · Build: a Python consumer, and read the ordering back

Create scripts/inspect_order_events.py — a small consumer that joins a named group and prints what it reads, so the ordering claim is something you see, not just something you're told:

"""Consume a few order_events messages to see per-partition ordering."""
import json

from confluent_kafka import Consumer

BOOTSTRAP = "localhost:9092"
TOPIC = "order_events"
GROUP_ID = "inspect-group"


def main():
    consumer = Consumer(
        {
            "bootstrap.servers": BOOTSTRAP,
            "group.id": GROUP_ID,
            "auto.offset.reset": "earliest",
            "enable.auto.commit": True,
        }
    )
    consumer.subscribe([TOPIC])

    try:
        seen = 0
        while seen < 12:
            msg = consumer.poll(timeout=5.0)
            if msg is None:
                break
            if msg.error():
                print(f"consumer error: {msg.error()}")
                continue
            event = json.loads(msg.value())
            print(
                f"partition={msg.partition()} offset={msg.offset()} "
                f"key={msg.key().decode()} status={event['status']}"
            )
            seen += 1
    finally:
        consumer.close()


if __name__ == "__main__":
    main()

auto.offset.reset: "earliest" tells this consumer to start from the beginning of the topic the first time inspect-group has ever run (a group with no prior committed offset has nowhere else to start from). enable.auto.commit: True means the client library commits offsets for you periodically — fine for today's read-only inspection; Day 6 turns this off and commits manually, on purpose, right after the warehouse write succeeds, not before.

uv run --with confluent-kafka python3 scripts/inspect_order_events.py

Expected — key=101's four rows appear consecutively with consecutive offsets on one partition, and likewise for 102/103, matching whatever partition layout section 7 printed for your run:

9 · Verify: inspect the consumer group's offsets from the CLI

The Kafka CLI can describe any consumer group's committed offsets without writing a line of Python — this is the tool you'll reach for on Day 6 to check whether a restarted consumer resumed where it should have:

docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group inspect-group

Expected — one row per partition inspect-group has touched, CURRENT-OFFSET equal to LOG-END-OFFSET (it has read everything currently in the topic) and LAG of 0 on each:

GROUP           TOPIC           PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG   CONSUMER-ID  HOST  CLIENT-ID
inspect-group   order_events    0          8               8               0     -            -     -
inspect-group   order_events    2          4               4               0     -            -     -

Consumer group 'inspect-group' has no active members.

Only the partitions that actually received messages appear (here, 0 and 2 — partition 1 never got a key that hashed to it in this run, which is fine and expected with only 3 keys produced). "No active members" just means the consumer process already exited — the group and its committed offsets persist in Kafka regardless, which is the entire point: nothing about this bookmark depends on the consumer still running.

LAG is the metric to watch going forward. LAG = LOG-END-OFFSET − CURRENT-OFFSET: how many records a group hasn't caught up to yet. Zero lag means fully caught up. A consistently growing lag on Day 6's consumer would mean the warehouse write is falling behind the producer — the single most useful health signal for any real Kafka consumer, and out of scope to alert on today, but worth knowing where it comes from.

Q: "Why key Kafka messages by order_id here, and what does that actually buy you?" A strong answer, out loud: "Kafka only guarantees message order within a single partition, never across partitions of the same topic. A topic's partition count is chosen for throughput, but that means a topic with more than one partition needs some way to keep related messages together, in order — that's what the key is for. Kafka hashes the key to deterministically pick a partition, so every message with the same key always lands on the same partition, in send order. For order_events, keying by order_id means every status change for one order — placed, accepted, picked_up, delivered — is guaranteed to arrive at any consumer in that same order, because they're all on one partition's one append-only log. It says nothing about ordering between different orders, which this domain never needs anyway." The signal: naming the guarantee precisely — per-partition order, not global order — rather than a vague "keys keep things in order."
