pathlib

Every lesson through Day 12 has handed open() a path already written as a plain string — "notes.txt", a fixture built with tempfile.mkdtemp(). Today looks at where those strings actually come from once a program has to build one out of pieces itself: joining a directory to a filename, checking whether something exists first, listing files that match a pattern. Doing that with string concatenation breaks in ways that are easy to miss until they don't — pathlib is the standard-library fix.

Bridge from SQL: a file path is a lookup key into the filesystem, the same role a primary key plays for a table row — you don't rebuild a row from its individual column values by hand every time you need it, you SELECT ... WHERE id = ? and let the database resolve the key to the row. pathlib gives paths the same treatment: a path is a real object with operations on it (does this key resolve to something? what "columns" — name, parent, extension — does it decompose into?), not a string you re-parse by hand every time.

1 · The problem: paths built by string concatenation

Nothing stops you from building a path with plain string operations — it is exactly what beginners reach for first:

directory = "data"
filename = "sales.csv"
full_path = directory + "/" + filename   # "data/sales.csv"

This works, right up until it doesn't. Three concrete failure modes, all structural rather than typos: the hardcoded "/" is wrong on Windows, which expects \ — code that works on your machine breaks for a teammate; if directory already ends in "/" (easy to do by accident, e.g. from a config value), the concatenation produces "data//sales.csv", a double slash that some tools tolerate and others don't; and every other question about the path — does it exist, is it a file or a folder, what's its extension — needs its own separate string-slicing or os.path function call, each with its own edge cases. None of this is a Python weakness so much as strings being the wrong representation for something that isn't fundamentally text — it's a location, with real operations (join, exists, list contents) that a plain string has no way to expose.

2 · Path and the / operator

pathlib.Path represents a filesystem path as an object instead of a string, and overloads the division operator, /, to mean "join this path with the next piece" instead of arithmetic division. It looks unusual the first time you see it — an operator doing something other than math — but it is no stranger a mechanism than the fact that + means concatenation for two strings and addition for two numbers: Python always asks the object on the left what an operator should do, and Path answers that / means "join":

from pathlib import Path

directory = Path("data")
full_path = directory / "sales.csv"   # Path("data/sales.csv") — correct separator, always
print(full_path)                    # "data/sales.csv" on Linux/macOS, "data\sales.csv" on Windows

directory / "sales.csv" never produces a double slash and never hardcodes the wrong separator — Path decides the correct one for whatever operating system the code is actually running on, structurally, not by remembering to write it correctly every time. Chaining works too: Path("data") / "raw" / "2026" / "sales.csv" builds up a nested path the same way, one join at a time.

3 · Checking what's actually there: .exists(), .is_file(), .is_dir(), .mkdir()

A Path object can point at something that doesn't exist yet — building one with / never touches the filesystem, it just describes a location. Asking whether that location is real is a separate, explicit step:

p = Path("data") / "sales.csv"
p.exists()      # True/False — is there anything at all at this path?
p.is_file()     # True only if it exists AND is a regular file
p.is_dir()      # True only if it exists AND is a directory

out_dir = Path("data") / "processed"
out_dir.mkdir(parents=True, exist_ok=True)   # create it (and any missing parents), don't error if it's already there

mkdir(parents=True, exist_ok=True) is the combination worth remembering as one unit: plain .mkdir() raises FileNotFoundError if data/ itself doesn't exist yet, and raises FileExistsError if processed/ is already there — parents=True creates any missing ancestor directories along the way, and exist_ok=True makes an already-existing target a no-op instead of an error, which is almost always what you actually want when preparing an output directory.

4 · .read_text() / .write_text(): shortcuts over Day 6's with open(...)

Day 6 taught open() plus with as the safe way to read or write a file, and none of that material is being replaced today — a Path object works as a drop-in argument to open(), and supports with identically:

p = Path("notes.txt")
with open(p, "r") as f:      # Path works directly where Day 6 used a string
    text = f.read()

What pathlib adds on top is a shortcut for the common case where the whole file is small enough to read or write in one call, collapsing open() + with + .read()/.write() + the implicit close into a single method:

p.write_text("first line\nsecond line\n")   # opens "w", writes, closes — one call
p.read_text()                                # opens "r", reads the whole file, closes — one call

.read_text()/.write_text() still open and close a real file underneath — they are not a different I/O mechanism, just Day 6's pattern written once instead of three lines. For anything that needs a mode other than whole-file read/write (appending, streaming line by line, binary mode), reach back for open(path, mode) with with exactly as Day 6 taught, passing the Path straight in.

5 · Listing files: .glob() and .rglob()

.glob(pattern) returns every path inside a directory matching a shell-style wildcard pattern, lazily (Day 5's generator idea — it yields matches one at a time rather than building the whole list up front before returning):

data_dir = Path("data")
for csv_path in data_dir.glob("*.csv"):   # every *.csv directly inside data/, not subfolders
    print(csv_path)

for csv_path in data_dir.rglob("*.csv"):  # same, but recurses into every subfolder too
    print(csv_path)

* matches any run of characters within one path segment, so "*.csv" means "any name ending in .csv." .glob() stays in the one directory you called it on; .rglob() ("recursive glob") walks every nested subdirectory too — the difference to reach for depends entirely on whether the files you want could live in subfolders.

6 · Decomposing a path: .name, .stem, .suffix, .parent

The same questions string-slicing used to answer by hand — find the last /, find the last . — are plain properties on a Path, computed correctly regardless of platform:

p = Path("data/raw/sales.csv")
p.name      # "sales.csv"      — the final component, filename + extension
p.stem      # "sales"          — the filename with the extension removed
p.suffix    # ".csv"           — just the extension, dot included
p.parent    # Path("data/raw") — the directory one level up, itself a Path

.parent returning a real Path (not a string) is what makes it chain: p.parent.parent walks up two levels, and p.parent / "processed.csv" builds a sibling path next to the original, both using the exact same / join from section 2.

Where pandas goes from here: pandas accepts a path (string or Path, either works) as the first argument to pd.read_csv(path) without caring which one you hand it — mentioned here by name only, not demonstrated, matching the hard rule above.
