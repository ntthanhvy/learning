1 · The thing Day 7 already named as a trade-off

Day 7 built dags/food_delivery_pipeline.py deliberately coarse: one BashOperator runs dbt build as a single shell command, and Airflow only ever sees whether that one subprocess's exit code was zero or not. That is a real limit, named honestly back then rather than discovered now: if dim_restaurants fails but every staging model succeeded, Airflow's own graph view shows exactly one red box — dbt_build — with no visibility into which of today's eight models actually broke, and no way to retry just that one model without re-running the whole command.

Cosmos is the fix PLAN.md named back on Day 7 as "a real upgrade, but not a Day 7 prerequisite": it reads your dbt project the same way dbt ls does, and turns every model and every model's tests into its own Airflow task, wired together by the exact dependency edges your ref() calls already declare.

2 · What Cosmos actually builds — confirmed against a real project, not a toy

This round built a scratch dbt project shaped like this course's own (stg_restaurants, stg_orders with a unique/not_null test on order_id, dim_restaurants joining both) and ran it through Cosmos's DbtTaskGroup for real, parsed with Airflow's own DagBag. The resulting tasks, read directly off that parse:

dbt_models.stg_restaurants_run
dbt_models.stg_orders.run
dbt_models.stg_orders.test
dbt_models.dim_restaurants_run

dim_restaurants_run upstream = [stg_orders.test, stg_restaurants_run]
stg_orders.test      upstream = [stg_orders.run]

Three things worth naming from that real output, not from the docs: a model with no test gets one task (<model>_run); a model with a test gets two tasks, .run then .test; and dim_restaurants_run waits on stg_orders.test, not just stg_orders.run — Cosmos makes a downstream model wait for its upstream's tests to pass, which a single dbt build call also does internally, but today you can see that exact dependency as a real edge in Airflow's own graph view instead of it being invisible inside one task.

3 · The one gotcha this round found by actually running it

Every BashOperator this course has written since Day 7 invokes dbt the same way: uv run --with "dbt-postgres==1.11.0" dbt build, a self-contained command that needs nothing pre-installed. Cosmos's default execution mode, ExecutionMode.LOCAL, works differently — it shells out to a literal dbt executable path, resolved once at DAG-parse time, not re-installed by uv on every run. Confirmed this round directly from a live install:

from cosmos import ExecutionConfig
ExecutionConfig().dbt_executable_path
# /path/to/some/temp/venv/bin/dbt — whatever's on PATH right now

That default is a real, current-version finding (astronomer-cosmos 1.15.1, pinned in RESOURCES.md), not a hypothetical: on a fresh machine with no persistent dbt install, Cosmos's LOCAL mode has nothing to find, and a DAG using it will fail to parse with a "no such file" style error — uv run --with's whole appeal all week has been never needing a persistent install, and this is the one place in this course that assumption breaks.

The practical fix, matching this course's tooling: create one persistent virtual environment with dbt installed once (uv venv dbt_venv && uv pip install --python dbt_venv/bin/python "dbt-postgres==1.11.0"), then pass that environment's real dbt path to ExecutionConfig explicitly rather than relying on the default. This round confirmed ExecutionConfig(execution_mode=ExecutionMode.LOCAL, dbt_executable_path=<path>) is accepted and genuinely used — Cosmos's own dbt ls call (what discovers your models and builds the task list) ran through that exact path and returned real nodes. Creating the persistent venv itself was not re-exercised against a live Postgres this round (this sandbox's own policy blocks creating a new persistent virtualenv outside a scratch cleanup), so test that one command on your own machine before trusting it blindly.

5 · The actual trade-off, stated as a threshold

BashOperator (Day 7)Cosmos DbtTaskGroup (today)
Airflow tasks1, for the whole dbt build1 per model, 1 per model's tests
Retry granularitywhole command re-runsjust the failed model/test re-runs
Graph viewone box, no model-level detailfull per-model graph, matches dbt docs
Setup costnone — uv run --with is self-containedone persistent dbt install, pinned and maintained
Parse-time costnone — nothing runs at DAG-parse timedbt ls runs on every DAG parse to build the task list

For this project's size — seven models, one failure mode anyone debugging would just read the dbt log for anyway — Day 7's own call stands: the setup cost (a maintained, persistent dbt venv instead of zero infrastructure) isn't paid back yet. The threshold where it flips is concrete, not a vibe: enough models that "which one failed" stops being obvious from one log, or enough runtime that retrying one model instead of the whole build actually saves meaningful time. Name that threshold out loud rather than treating either choice as universally correct.

Q: "Your dbt project runs inside Airflow as one BashOperator. When would you switch to Cosmos instead?" A strong answer, out loud: "Cosmos parses the dbt project at DAG-parse time and renders one Airflow task per model, with dependency edges taken straight from the project's own ref() graph — so a failure shows up as one red box for the model that actually broke, and a retry only re-runs that model, not the whole build. The cost is real: Cosmos needs a persistent dbt install Airflow can shell out to, not the uv run --with pattern that makes every other script in this project self-contained, and dbt ls runs on every single DAG parse to rebuild the task list. For a project with a handful of models, that setup cost isn't worth it — one BashOperator and a readable dbt log tells you everything. I'd switch once the project is big enough that 'which model failed' stops being obvious from one log, or once retry time on the whole build starts actually costing something." The signal: stating Cosmos's real mechanism (parses the project, builds real per-model tasks) and a concrete switch condition, not just "Cosmos is more production-grade."
