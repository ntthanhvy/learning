query(): filtering with a WHERE-shaped string instead of a boolean mask

Lesson 21's closing teaser named this directly — query(), used without explanation back in Lesson 8's method chain (.query("amount_rank == 1")) but never taught on its own. Today gives that call a name and a mental model: a second way to spell filtering, sitting right next to the boolean mask from Lesson 1.

1 · Same filter, two spellings

Lesson 1 taught filtering with a boolean mask: df[df["amount"] > 100]. That's still the right default — it's explicit and it's everywhere in real pandas code. But repeat the column name enough times in a chain and it gets noisy fast, especially with several conditions. query() does the exact same filtering, spelled as a string:

# boolean mask (Lesson 1)
clean[clean["amount"] > 100]

# query() — same result
clean.query("amount > 100")
#   order_id customer  amount  order_date
#0         1       An   120.0  2026-01-05
#2         5     Binh   180.0  2026-01-09

Both return identical DataFrames. The difference is entirely about how the condition is written: repeated df[...]/clean[...] noise versus one plain-looking expression. That expression is exactly what makes it feel familiar: a query() string reads like a SQL WHERE clause, because that's precisely the gap it closes.

2 · The SQL bridge

This is the whole pitch: clean.query("amount > 100") is WHERE amount > 100, spelled as a pandas method call. String equality, multiple conditions, the works — all read close to their SQL originals:

clean.query("customer == 'An'")          # WHERE customer = 'An'
clean.query("amount > 50 and customer != 'An'")  # WHERE amount > 50 AND customer != 'An'
#   order_id customer  amount  order_date
#2         5     Binh   180.0  2026-01-09

Note the keywords: and/or/not, not &/|/~ — inside a query string you write them like Python's own boolean keywords (which happen to match SQL's), not like the bitwise operators a boolean mask forces you into. That operator swap is the one real syntax difference worth remembering.

3 · @variable: pulling a Python value into the expression

A hardcoded number in the string works, but real filters usually depend on a variable computed earlier in the script. Prefix it with @ inside the query string to reach into the surrounding Python scope:

threshold = 100
clean.query("amount > @threshold")
#   order_id customer  amount  order_date
#0         1       An   120.0  2026-01-05
#2         5     Binh   180.0  2026-01-09

Without @, query() looks for a column literally named threshold and raises UndefinedVariableError since no such column exists. @ is what tells it "this is a Python name from outside the DataFrame, not a column."

4 · Why it exists: readable chains

The real payoff shows up inside a method chain (Lesson 8) — a boolean mask can't be written mid-chain at all, since there's no DataFrame name yet to index into:

# can't do this mid-chain — `merged` doesn't exist until the chain finishes
merged = clean.merge(customers, on="customer", how="left")
merged[merged["region"] == "South"]

# query() reads naturally as one more link in the chain
(
    clean
    .merge(customers, on="customer", how="left")
    .query("region == 'South'")
)
#   order_id customer  amount  order_date region
#1         2     Binh    35.5  2026-01-06  South
#2         5     Binh   180.0  2026-01-09  South

That's exactly the shape Lesson 8's own example used .query("amount_rank == 1") for — filtering to one row per group right after a rank() step, with no intermediate variable needed to hold the mask.

Rule of thumb: boolean mask is still the right default for a single simple condition, and it's the form you'll see most in other people's code. Reach for query() when a chain needs a filter step with no natural variable name to mask against, or when several conditions in one boolean mask are getting hard to read.

5 · One sharp edge: column names that aren't valid identifiers

A query string is parsed as an expression, so a column name with a space or a symbol needs backticks to be recognized inside it: df.query("`order date` > '2026-01-01'"). It's rare in practice — most real column names are already valid identifiers — but worth recognizing the error if it comes up, rather than assuming query() is broken.

Q: "When would you use query() instead of a boolean mask?" A strong answer, out loud: "They filter identically — query() is just a string-expression spelling of the same WHERE-clause idea as a boolean mask. I reach for it inside a method chain, where there's no intermediate DataFrame name yet to build a mask against, or when a mask has enough conditions that repeating df[...] on each one hurts readability. For a single simple filter I'd still default to the boolean mask, since it's more common in the codebases I've seen and doesn't need the @ prefix to pull in outside variables." The signal: naming the real trade-off — chain-friendliness versus the ubiquity and directness of a plain mask — instead of claiming one is simply better.
