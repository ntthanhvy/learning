.map(): recoding a Series value-by-value

Lesson 26's own teaser named two candidates — .map() and pd.wide_to_long() — re-grepped every lesson body and the glossary before writing, both still genuinely absent. This one wins: it's the tool people reach for apply() (Lesson 12) instead of, for the single most common recoding task — swapping one value for another across a whole column.

1 · The task: recode a column of values into other values

You've seen this shape already: a customer's region lives in a lookup table (customers.csv), and Lessons 5/22 pulled it in via merge(). But sometimes the lookup is small and already in your head — a handful of codes to labels, a handful of raw category strings to cleaned-up ones — and setting up a whole second DataFrame just to merge() against it is overkill. .map() is built exactly for this: a Series method, one value in, one value out, per row.

# customer -> region, as a plain dict, no second DataFrame needed
region_map = {"An": "North", "Binh": "South"}
clean["customer"].map(region_map)
# 0    North
# 1    North
# 2    South
# 3    South

SQL bridge: this is a CASE WHEN col = 'An' THEN 'North' WHEN col = 'Binh' THEN 'South' END written as data instead of branches — or, if the lookup already lived in a table, exactly what a small dimension-table JOIN gives you. .map() is the "the lookup fits in a dict" shortcut for that same idea.

2 · Three things you can pass .map() — dict, Series, or function

A dict (shown above) is the most common case: a fixed, small lookup. A Series works identically — its index becomes the lookup key, its values become the replacement, which matters if the mapping itself came from computed data (e.g. a groupby() result) rather than something you typed by hand:

region_series = pd.Series({"An": "North", "Binh": "South"})
clean["customer"].map(region_series)  # identical result to the dict above

A function works too — this is where .map() and apply() genuinely overlap on a single Series:

clean["amount"].map(lambda x: "High" if x >= 100 else "Low")
# 0    High
# 1     Low
# 2     Low
# 3    High

3 · .map() vs apply(): same Series-with-a-function case, different intent

Lesson 12 taught apply() as the honest per-row escape hatch, on rows spanning multiple columns (axis=1) with no vectorized shortcut. .map() only ever runs on one Series — it can't see other columns at all. When the transform genuinely is "one column's values, translated one at a time," .map() says that intent directly; apply() works too (a Series has .apply() as well) but reads as "run this arbitrary function," not "recode these values."

## Both give the identical result here -- .map() just names the intent:
clean["customer"].map(region_map)                         # "I'm recoding values"
clean["customer"].apply(lambda c: region_map.get(c))     # "I'm running a function"

The dict/Series form has no apply() equivalent at all without writing a lambda around .get() yourself — .map() takes the lookup directly, no wrapping needed.

4 · The gotcha: unmatched values become NaN, silently

If a value in the Series has no matching key in the dict/Series, .map() does not raise — it fills in NaN for that row and moves on, same "no crash, quietly wrong" shape this course has flagged since Lesson 19 (nunique()'s truthy Ellipsis, Lesson 24's NaN-into-default-branch, Lesson 25's fixed-category NaN, Lesson 26's silent no-op). Hand-verified on this course's fixture:

partial_map = {"An": "North"}  # Binh is missing on purpose
clean["customer"].map(partial_map)
# 0    North
# 1    North
# 2      NaN     <- Binh had no key in partial_map -- no error, just NaN
# 3      NaN

This is a real interview trap: a lookup dict that's missing an entry silently NaNs those rows out instead of failing loudly. Always check .isna().sum() after a .map() call against an external/hand-built dict, the same reflex Lesson 3 built for missing data generally — a value count of unexpected NaNs after a recode is the tell.

Bonus, not the main lesson: a plain DataFrame also has its own .map() (the modern name for what used to be called applymap(), now deprecated) — it applies a function to every cell across the whole table at once, not one column: small.map(lambda v: str(v).upper()). Reach for the Series version taught above for recoding one column; the DataFrame version is rare in practice and mentioned here only so the name doesn't surprise you if you meet it.

Q: "When would you use .map() instead of apply()?" A strong answer, out loud: "map() is for recoding a single Series, value by value — I pass it a dict, a Series, or a function, and it looks up or computes one replacement per element. apply() is more general: it runs a function per row across multiple columns, or per column, and doesn't have a built-in dict-lookup shorthand. If I'm translating one column's codes into labels — a status code to a status name, say — map() says that intent directly and is the more idiomatic choice. The gotcha I watch for: map() doesn't raise on an unmatched value, it silently fills NaN, so I always check isna().sum() afterward against an external lookup dict to catch missing keys before they become silent data loss." The signal: naming map() as Series-only and intent-revealing, not just "a synonym for apply()," and knowing the silent-NaN gotcha without being prompted.
