1 · The gap Day 14 named and never closed

Day 14 turned on contract: {enforced: true} for fct_orders and declared two column-level constraints on order_id: not_null and unique. That lesson's own text went further than it built, naming a fact worth rereading: dbt Labs' Model contracts page lists four constraint types a contract can declare at the column level — not_null, unique, primary_key, foreign_key — and names Postgres specifically as the adapter that enforces every one of them as a real database-level constraint, not metadata a build can silently violate. Day 14 built the first two and stopped. restaurant_id sat on both dim_restaurants (where it's the natural primary key) and fct_orders (where it's a foreign key into that same table) the whole time, contract-enforced in name only.

The gap matters because this project already has a relationship it checks the slow way. Day 4's relationships test on fct_orders.restaurant_id runs after a build, as a select that fails if it finds an order pointing at a restaurant that doesn't exist — useful, but it only catches the problem once bad rows already landed in the table. A real foreign key constraint, enforced by Postgres itself, refuses the bad row's insert or merge outright, at write time, before it is ever a row dbt's own test has to go looking for.

2 · primary_key constraint on dim_restaurants

Add one line to the existing restaurant_id column entry in models/marts/marts.yml, under dim_restaurants:

# models/marts/marts.yml -- dim_restaurants, extending Day 14's shape
models:
  - name: dim_restaurants
    config:
      contract:
        enforced: true
    columns:
      - name: restaurant_id
        data_type: bigint
        constraints:
          - type: primary_key
        tests:
          - unique
          - not_null
      # ...name, cuisine, city, commission_rate -- unchanged from Day 14

Keep the unique/not_null tests alongside the new constraints entry, the same "two different checks, two different times" reasoning Day 14 already gave for fct_orders.order_id. A primary_key constraint folds not_null and unique into one declared concept — "this column identifies the row" — but on dbt's own CONSTRAINT_SUPPORT table a primary_key entry is distinct from either, and the pre-existing tests: block is what still gives a readable, named failure if it's ever violated. Checked directly against the installed Postgres adapter's own source this round, not assumed: PostgresAdapter.CONSTRAINT_SUPPORT[ConstraintType.primary_key] is ConstraintSupport.ENFORCED, and the base adapter class every other adapter inherits from marks the same entry NOT_ENFORCED by default — Postgres is overriding the default, not merely matching it.

3 · foreign_key constraint on fct_orders

Now the half that references dim_restaurants. Add to fct_orders' restaurant_id column, alongside its existing relationships test:

# models/marts/marts.yml -- fct_orders, extending Day 14's shape
  - name: fct_orders
    config:
      contract:
        enforced: true
      on_schema_change: 'fail'
    columns:
      - name: order_id
        data_type: bigint
        constraints:
          - type: not_null
          - type: unique
        tests:
          - not_null
          - unique
      - name: customer_id
        data_type: bigint
      - name: restaurant_id
        data_type: bigint
        constraints:
          - type: foreign_key
            to: ref('dim_restaurants')
            to_columns: [restaurant_id]
        tests:
          - relationships:
              arguments:
                to: ref('dim_restaurants')
                field: restaurant_id
      # ...courier_id, subtotal, delivery_fee, order_total, placed_at -- unchanged

to and to_columns are the two fields a foreign_key constraint needs that not_null/unique/primary_key never did: to is a ref() (or source()) pointing at the referenced model, and to_columns is the list of columns over there holding the matching key — dim_restaurants.restaurant_id, dim_restaurants' own new primary_key column from Section 2. Using ref() rather than a bare schema-qualified table name matters for the same reason it always has in this course: it resolves to whatever schema the active target actually builds into, so the constraint survives a move between dev, CI and prod targets unchanged.

Confirmed live this round, not assumed: a scratch dbt project with exactly this shape — Day 1's four tables, Day 14's contract: {enforced: true}, today's two new constraints — parsed clean with dbt parse, zero warnings tied to the constraints themselves. Reading the resulting manifest directly showed dbt keeps to as the literal string "ref('dim_restaurants')" at parse time, not yet resolved to a real relation name — the same "parse doesn't reach this far, compile/run does" limit Day 14 and Day 13 each found for their own constraint and config checks. The real DDL — a Postgres references dim_restaurants (restaurant_id) clause on the column — only gets rendered when the model actually compiles against a live connection, which this sandbox still can't reach (no running Postgres container). Reading dbt.adapters.base.impl's own render_column_constraint method directly confirmed the exact rendering rule instead: a foreign_key constraint with both to and to_columns set renders as f"references {constraint.to} ({', '.join(constraint.to_columns)})".

4 · What a foreign_key constraint catches that Day 4's test already caught — and what it catches earlier

Nothing here replaces Day 4's relationships test, kept unchanged above in the same column entry. The two checks run at different times against a different failure: the test is a select dbt runs after fct_orders is built, searching the finished table for any restaurant_id with no match in dim_restaurants and failing with a named, readable count if it finds one. The constraint is enforced by Postgres itself, inside the insert/merge statement dbt's own incremental materialization writes — a row with a bad restaurant_id never makes it into the table in the first place, the database refuses the write outright. For an incremental model like fct_orders, built with Day 4's own merge strategy, that distinction is the same at-the-door-versus-after-the-fact gap this course has drawn before: Day 6's ON CONFLICT (event_id) DO NOTHING stops a duplicate write at the door; Day 4's own relationships test only ever tells you, afterward, that a door was left open.

One ordering fact worth naming explicitly: Day 14's own build order means dim_restaurants must exist with its primary_key constraint already in place before fct_orders' foreign_key constraint can be enforced against it — the same dependency ref('dim_restaurants') already encodes in dbt's DAG, just now carrying a database-level consequence too, not only a build-order one.

Confirm the constraints really landed as DDL, not just YAML, by reading Postgres' own catalog directly — this is the check that actually distinguishes today's work from a no-op YAML edit:

docker compose exec -T postgres psql -U postgres -d food_delivery -c "
  SELECT conrelid::regclass AS table_name, conname, contype
  FROM pg_constraint
  WHERE conrelid IN ('dbt_dev.dim_restaurants'::regclass, 'dbt_dev.fct_orders'::regclass)
  ORDER BY table_name, contype;
"

Expected: one row for dim_restaurants with contype = 'p' (primary key) and one row for fct_orders with contype = 'f' (foreign key) — Postgres' own two-letter constraint-type codes, proof the constraint is sitting in pg_constraint as a real, database-enforced rule, not a line of YAML dbt only ever reasons about internally. Prove it has teeth the same way Day 3 and Day 12 both held their own checks to: try to insert an order for a restaurant that doesn't exist and confirm Postgres itself refuses it, not a dbt test catching it later:

docker compose exec -T postgres psql -U postgres -d food_delivery -c "
  INSERT INTO dbt_dev.fct_orders (order_id, customer_id, restaurant_id, courier_id, subtotal, delivery_fee, order_total, placed_at)
  VALUES (999999, 1, 999999, 1, 10.00, 2.00, 12.00, now());
"

Q: "Your dbt project has a relationships test on a foreign key column. Why would you also add a foreign_key constraint, since the test already catches orphaned rows?" A strong answer, out loud: "They catch the same mistake at different times. A relationships test is a select dbt runs after the model is built, so it tells me, with a readable failure message, that a bad row already landed — useful for visibility and CI, but the damage is already in the table. A foreign_key constraint, on an adapter that actually enforces it — Postgres is one of a short list dbt Labs documents, most warehouses only let you declare it as metadata — becomes a real database-level constraint in the model's own DDL. That means the insert or merge itself gets rejected by the database, at write time, before a bad row ever exists to go looking for. I'd keep both: the constraint as the hard stop, the test as the named, debuggable signal when something upstream is producing bad keys in the first place. And I'd be explicit in an interview that this only has real teeth on Postgres — the same contract on Snowflake or BigQuery would parse and declare the same YAML but never actually stop a bad write." The signal: naming the enforcement-vs-metadata split by adapter, not treating "I added a foreign_key constraint" as uniformly meaningful everywhere dbt runs.

Scope line

This lesson covers column-level primary_key and foreign_key constraints inside a contract already enforced since Day 14, on Postgres specifically, where dbt Labs' own documentation and the installed adapter's CONSTRAINT_SUPPORT table agree both are genuinely ENFORCED as real DDL. It does not cover model-level constraints (declared under a model's own top-level constraints: key rather than per-column — needed for a composite primary key spanning more than one column, which this project's tables never do), check constraints (an arbitrary SQL predicate, vocabulary only here), or what happens to either constraint on an adapter that only declares them as metadata (Snowflake, BigQuery, Redshift) — named in Section 2 and 4 as a real difference, not built, since this course's warehouse is Postgres by design. No live Postgres connection was reachable this sandbox round, so the actual DDL rendering, the pg_constraint catalog check, and the rejected insert in Section 5 rest on the installed adapter's own documented rendering rule, not a live psql run this round — flagged here rather than asserted as directly observed.
