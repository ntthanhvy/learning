glob & fnmatch: filename pattern matching

Day 13 built pathlib.Path objects and walked a directory with .iterdir(), checking each name by hand. That works, but "every file ending in .csv" or "every file nested at any depth under logs/" is common enough to deserve its own syntax — the shell-style wildcard pattern every shell already uses for ls *.csv. Python has two matching layers built on the same pattern syntax: Path.glob() searches the filesystem for you, and fnmatch tests one name you already have against a pattern.

1 · Path.glob(): searching a directory by pattern

Day 13's .iterdir() lists everything in one directory, no filtering. Path.glob(pattern) filters as it lists, using the same wildcard characters a shell uses: * for any run of characters (never crossing a /), ? for exactly one character, and [abc] for one character out of a set.

from pathlib import Path

root = Path("logs")
for p in sorted(root.glob("*.csv")):
    print(p.name)
# confirmed live, against logs/app.csv, logs/2024.csv, logs/notes.txt, logs/archive/old.csv:
# 2024.csv
# app.csv
# -- archive/old.csv is NOT listed: glob("*.csv") only looks one level deep

glob() returns an iterator (Day 5's lazy-pipeline idea again), not a list — wrap it in sorted() or list() to see every result at once, since directory listing order is not guaranteed to be consistent across runs or platforms.

2 · rglob(): the same pattern, every depth

Path.rglob(pattern) ("recursive glob") is glob("**/" + pattern) written out — it walks into every subdirectory, no matter how deep, applying the same pattern at each level:

for p in sorted(root.rglob("*.csv")):
    print(p)
# confirmed live, same logs/ tree as above:
# logs/2024.csv
# logs/app.csv
# logs/archive/old.csv   -- rglob() found the nested one glob() skipped

The ** segment itself is a recursive wildcard — the one piece of glob syntax allowed to cross a / boundary, which is exactly why a plain * in Section 1 stayed confined to one directory. root.glob("**/*.csv") and root.rglob("*.csv") are confirmed live to return the identical set.

Confirmed live — glob() never raises on zero matches: list(root.glob("*.xyz")) for a pattern matching nothing returns [], not an exception — unlike Day 13's Path.read_text() on a missing file, which raises FileNotFoundError immediately. A pattern search finding nothing is a normal, expected outcome, not a failure.

3 · fnmatch: testing one name you already have

glob() searches a real filesystem. Sometimes the names are already in hand — read from a zipfile listing (Day 64), a database row, an API response — and the question is just "does this one name match the pattern?" That's fnmatch:

from fnmatch import fnmatch

names = ["report_2024.csv", "report_2024.tmp", "README.md"]
matches = [n for n in names if fnmatch(n, "report_*.csv")]
print(matches)   # confirmed live: ['report_2024.csv']

print(fnmatch("REPORT.CSV", "*.csv"))   # confirmed live on this Linux machine: False
from fnmatch import fnmatchcase
print(fnmatchcase("REPORT.CSV", "*.csv"))   # confirmed live: False as well -- identical result here

fnmatch() is documented to normalize case the same way the operating system's own filesystem does before comparing — case-insensitive on Windows and default macOS, but case-sensitive on Linux, confirmed live above: both calls return False on this machine, because Linux's normalization step is a no-op. fnmatchcase() skips that OS-dependent normalization entirely and always compares exactly as written — on Linux the two functions happen to agree, but on Windows fnmatch("REPORT.CSV", "*.csv") would return True while fnmatchcase() stays False on every platform. Reach for fnmatchcase() whenever the result needs to be the same regardless of what OS runs the code — matching a label from a CSV column, say, rather than an actual filesystem path.

Where pandas/NumPy go from here: neither has a filename-pattern matcher of its own — a pandas pipeline that needs "every CSV under this folder" still reaches for Path.glob() or pathlib first, then hands each matched path to pd.read_csv() one at a time. Pattern matching over filenames is a stdlib/OS-level job, not a data-frame job. Not covered further here, per MISSION.md.
