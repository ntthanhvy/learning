Series.str.strip(): the whitespace bug hiding in every merge key

Lesson 103 closed the standing pd.to_timedelta() pick and carried forward one named candidate: the str.pad()/str.strip()/str.title()/str.join() text-cleanup family. Re-grepped strip case-insensitively across every lesson body and the glossary file before picking — the only hit was Lesson 55's plain Python "_".join(...).strip("_") call on an already-joined label, never the pandas .str.strip() accessor itself, so this is a genuine zero-hit gap. Picked .str.strip() over its three siblings: it is the single most common and most-skipped real-CSV cleanup step, and it directly explains a class of bug (silent extra groupby groups, silent missed merge rows) this course hasn't named yet.

1 · The bug: whitespace you can't see, breaking a key you trust

SQL's TRIM()/LTRIM()/RTRIM() strip leading/trailing whitespace from a text column. Pandas' column-wide equivalent is Series.str.strip() — same idea, run once over the whole column instead of row by row:

import pandas as pd

df = pd.DataFrame({
    "name": ["Binh", "Binh ", " Binh", "An"],
    "amount": [100, 50, 30, 20],
})
df.groupby("name")["amount"].sum()
# name
#  Binh     30
# An        20
# Binh     100
# Binh      50      -- "Binh" split into THREE separate groups!

df["name"].str.strip().pipe(lambda s: df.groupby(s)["amount"].sum())
# name
# An       20
# Binh    180        -- all three Binh rows now correctly merged

Confirmed directly: "Binh" == "Binh " is False — Python string equality is exact, character for character, and pandas' groupby key matching uses that same exact equality. A trailing or leading space is invisible when a human eyeballs a printed DataFrame, but it is a completely different key to the machine, so groupby() silently produces extra groups instead of raising anything. The identical trap breaks a merge() the same way — rows that should match on a text key silently don't, with no error, no warning, just fewer joined rows than expected:

left = pd.DataFrame({"key": ["Binh ", "An", " Chi"], "val": [1, 2, 3]})
right = pd.DataFrame({"key": ["Binh", "An", "Chi"], "other": [10, 20, 30]})
pd.merge(left, right, on="key").shape[0]
# 1   -- only "An" matched; "Binh " and " Chi" silently dropped

pd.merge(left.assign(key=left["key"].str.strip()), right, on="key").shape[0]
# 3   -- all three rows match once the key is stripped first

2 · lstrip() / rstrip(): the one-sided siblings

Confirmed directly: str.lstrip() removes only leading whitespace and str.rstrip() removes only trailing whitespace — exactly SQL's LTRIM()/RTRIM() split:

s = pd.Series([" Binh ", "  An", "Chi  "])
s.str.strip()   # ['Binh', 'An', 'Chi']        -- both sides
s.str.lstrip()  # ['Binh ', 'An', 'Chi  ']     -- left only, trailing spaces survive
s.str.rstrip()  # [' Binh', '  An', 'Chi']     -- right only, leading spaces survive

All three also take an optional to_strip= string of characters instead of whitespace — confirmed directly, pd.Series(["--Binh--", "**An**"]).str.strip("-*") returns ['Binh', 'An'], stripping any combination of the given characters from both ends, not a literal substring match.

3 · Two traps worth naming

Confirmed directly, pandas 3.0.6:

# Trap 1: NaN passes straight through untouched, same shape as every
# other .str method and as np.clip()'s NaN behavior (Lesson 102).
pd.Series([" Binh ", np.nan, "  An  "]).str.strip()
# 0    Binh
# 1     NaN
# 2      An
# dtype: str

# Trap 2: a Series with NO string values at all raises AttributeError
# outright -- the .str accessor refuses a non-string dtype up front.
pd.Series([1, 2, 3]).str.strip()
# AttributeError: Can only use .str accessor with string values, not integer

Trap 1 means .str.strip() is safe to call on a column that already has missing values — no extra .fillna() dance needed first. Trap 2 is a dtype check, not a per-value one: confirmed against the official pandas docs, a mixed object-dtype Series with a few non-string entries mixed among real strings instead turns those specific non-string entries into NaN rather than raising — the hard AttributeError only fires when pandas can tell upfront, from the column's own dtype, that there are no strings in it at all.

This is MISSION.md's ETL "clean" step applied to the single most-skipped real-CSV problem: a text column read from a CSV, a copy-pasted spreadsheet, or a user-entered form field almost always has inconsistent leading/trailing whitespace somewhere. It costs nothing to call .str.strip() on every text key column right after load, right alongside the dtype fixes from Lesson 2 — and it costs a confusing, silent, hard-to-notice bug later if skipped: a groupby() with one extra group that looks almost right, or a merge() quietly missing rows, both with zero error message pointing at the real cause.

Q: "Your groupby('customer_name') is producing more groups than there are actual customers. What's your first guess?" A strong answer, out loud: "Before anything fancier, I'd check for invisible whitespace or casing differences in the key column — 'Binh' and 'Binh ' look identical printed out but are different strings, so groupby silently treats them as two separate groups instead of raising any error. I'd run df['customer_name'].str.strip() (and probably .str.lower() too) across the whole column before grouping, which is vectorized and needs no loop, then re-check the group count. The same invisible-whitespace issue breaks merge() the same way — rows that should join on a text key silently don't, with fewer rows in the result and no warning at all." The signal: naming whitespace/casing as the first suspect for a key that "should" match but doesn't, not jumping straight to something more exotic.
