1 · Parsing durations: strings and numbers, not just datetime subtraction

Every timedelta this course has produced so far came from subtracting two parsed datetimes (Lesson 23's shift(), Lesson 32's .dt accessor). Real source data often hands over a duration directly instead — a string like "1 day 2 hours", or a bare number of seconds. pd.to_timedelta() is that parser:

import pandas as pd

pd.to_timedelta("1 day 2 hours")
# Timedelta('1 days 02:00:00')

pd.to_timedelta(5, unit="h")
# Timedelta('0 days 05:00:00')

df = pd.DataFrame({"dur": ["1 days 00:00:05", "2 days 00:01:00"]})
pd.to_timedelta(df["dur"])
# 0   1 days 00:00:05
# 1   2 days 00:01:00
# Name: dur, dtype: timedelta64[us]

Confirmed directly (pandas 3.0.6): a single string returns a Timedelta scalar; a Series of duration strings returns a Series with a real timedelta64[us] dtype — not object/string — ready for arithmetic against a datetime column exactly like Lesson 23's own subtraction-derived timedeltas. A bare number needs unit= to say what it counts (seconds, hours, days, ...); with no unit= given on a bare number, it defaults to nanoseconds, confirmed directly (pd.to_timedelta(1_000_000_000) → exactly 1 second).

2 · Two traps, one shared with to_datetime, one new

Confirmed directly, both against the official pandas docs:

# Trap 1 (shared with pd.to_datetime, Lesson 81): unit= is rejected
# outright when the input is a string -- not silently ignored.
pd.to_timedelta("1 day", unit="h")
# ValueError: unit must not be specified if the input is/contains a str

# Trap 2 (new here): errors="ignore" was removed in this pandas version --
# only "raise" (the default) and "coerce" remain valid at all.
pd.to_timedelta(["1 days", "bad"], errors="ignore")
# ValueError: errors must be one of 'raise', or 'coerce'.

pd.to_timedelta(["1 days", "bad"], errors="coerce")
# TimedeltaIndex(['1 days', NaT], dtype='timedelta64[us]', freq=None)

Trap 1 is Lesson 81's exact format=-vs-string rule, reappearing on the sibling function: a string already states its own units in words ("day", "hours"), so pairing it with a numeric unit= is a contradiction pandas refuses outright rather than silently picking one side. Trap 2 is specific to this pandas version (3.0.6) and worth naming because older code or tutorials may still show errors="ignore" — it now raises ValueError immediately, confirmed directly and cross-checked against the official docs, which document only 'raise' and 'coerce' as valid values. errors="coerce" behaves exactly like Lesson 2/81's pattern: unparseable entries become NaT, parseable ones pass through untouched.

3 · Why it matters: enables real duration arithmetic

Confirmed directly: a parsed timedelta adds/subtracts against a parsed datetime exactly like any Lesson-23-derived one, since both end up as the same underlying timedelta64/datetime64 dtypes regardless of which function produced them:

order_date = pd.to_datetime("2026-01-01")
sla = pd.to_timedelta("3 days")
order_date + sla
# Timestamp('2026-01-04 00:00:00')
This is the ETL "clean dtypes" step from MISSION.md applied to durations specifically: a source column holding "3 days" or "PT3H"-style text as raw strings/objects can't be added, compared, or resampled against a datetime column until it's parsed into a real timedelta64 — exactly the same reason Lesson 81's pd.to_datetime() matters for point-in-time columns. A SQL equivalent: casting a text column to an INTERVAL type before doing date arithmetic against it, rather than leaving it as a string the database can't add to anything.

Q: "You have a CSV column called 'processing_time' with values like '2 days 04:30:00'. How would you work with it?" A strong answer, out loud: "First parse it with pd.to_timedelta() rather than leaving it as a string or object dtype — that gives a real timedelta64 column I can add or subtract against a datetime64 column, sort, or compare with <, exactly like any duration derived from subtracting two timestamps directly. I'd watch two things: unit= can't be passed alongside a string input, since the string already states its own unit in words; and in recent pandas, errors='ignore' isn't valid anymore — only 'raise' or 'coerce' — so coerce is what I'd reach for if some rows might be malformed, same as to_datetime." The signal: naming it as the duration-parsing counterpart to to_datetime, not a brand-new unrelated function.
