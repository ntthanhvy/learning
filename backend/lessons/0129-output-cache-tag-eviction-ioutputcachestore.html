Evicting an output cache on purpose

Lesson 128's own scope line named exactly this as the next gap: tag-based eviction and the storage question behind IOutputCacheStore, both deliberately left out of that first pass at AddOutputCache(). A ten-second expiry (Lesson 128's Expire()) eventually clears a stale cached response on its own, but "a blog post just got edited, purge it now" can't wait ten seconds — it needs a way to reach in and evict specific entries on demand.

1 · Tagging a group of endpoints

A tag is just a label attached to a policy, applied to one endpoint directly or to a whole group through a base policy. CacheOutput() takes a builder lambda the same way AddPolicy does, so tagging a single endpoint needs no named policy at all:

app.MapGet("/blog", GetBlogIndex)
    .CacheOutput(b => b.Tag("tag-blog"));
app.MapGet("/blog/post/{id}", GetBlogPost)
    .CacheOutput(b => b.Tag("tag-blog"));

Both endpoints now carry tag-blog, even though they cache two completely different shapes of response. A tag doesn't change what gets cached or for how long — Expire() and SetVaryByQuery() from Lesson 128 still control that. It only gives a later eviction call something to reference.

2 · The eviction call itself

Eviction happens through IOutputCacheStore, injected like any other service and called directly from a handler:

app.MapPost("/purge/{tag}", async (IOutputCacheStore cache, string tag) =>
{
    await cache.EvictByTagAsync(tag, default);
});

A POST /purge/tag-blog removes every entry either of Lesson 1's two endpoints wrote, immediately — not after whatever Expire() happened to be set to. The natural place to call this isn't a dedicated purge endpoint, though: it's the same handler that just edited the blog post, right after its write to Postgres succeeds, so the cache and the database change together instead of the cache catching up on its own schedule.

A base policy can tag everything at once, which is the shape a blanket "flush the whole output cache" button needs:

options.AddBasePolicy(b => b.Tag("tag-all"));

Calling EvictByTagAsync("tag-all", default) then clears every cached entry in the app, the same one-call shape as purging a single tag — no special "clear everything" method exists, because tagging everything with one shared tag already gets there.

3 · Why eviction needs its own storage question

Lesson 121's idempotency-key pattern already introduced a shared cache interface, IDistributedCache, and it would be reasonable to expect output caching to reuse it. It doesn't, and Microsoft's own docs give a specific reason: EvictByTagAsync needs to find and remove every entry sharing a tag as one atomic operation, and IDistributedCache's plain key-value Get/Set/Remove contract has no operation shaped like that at all. IOutputCacheStore exists as its own interface precisely because tagging demands something IDistributedCache was never designed to do.

The default IOutputCacheStore implementation sits on top of .NET's in-memory MemoryCache — fine for one instance, but Lesson 8's stateless-handler problem shows up again immediately: a tag evicted on instance A leaves instance B still serving the old cached response, since each instance's MemoryCache is its own separate copy. The documented fix is a Redis-backed store, wired in before AddOutputCache():

builder.Services.AddStackExchangeRedisOutputCache(options =>
{
    options.Configuration = builder.Configuration.GetConnectionString("Redis");
});

builder.Services.AddOutputCache();

AddStackExchangeRedisOutputCache is a different method from Lesson 121's IDistributedCache-flavored AddStackExchangeRedisCache — same backing store, two separate registrations, because the two interfaces solve different problems with different contracts on top of it.

Frontend-habit trap: this reads like invalidating a React Query key after a mutation — call a purge after the write, name what it affects precisely, done. The difference is scope: React Query's cache lives in one browser tab and dies when the tab closes. EvictByTagAsync against the default in-memory store only clears one server instance's copy; clearing every instance behind a load balancer needs the shared Redis store, the same "state has to live somewhere every instance can see" rule Lesson 8 raised for sessions and rate-limit counters.

Scope line

This lesson covers Tag() on a policy builder, IOutputCacheStore.EvictByTagAsync, and AddStackExchangeRedisOutputCache as the documented multi-instance fix. It does not cover writing a custom IOutputCacheStore implementation against a different backing store, the SizeLimit/MaximumBodySize cache-wide limits, or SetLocking(false)'s resource-locking opt-out — real knobs on the same options class, out of scope for a first pass at eviction specifically.
