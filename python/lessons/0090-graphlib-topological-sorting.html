1 · The problem: an order that respects "must happen before"

Some lists don't have one correct order — any permutation works. Others do: a build script can't run its "package" step before its "compile" step; a database migration can't add a foreign key before the table it points to exists. The naive fix is writing the order by hand, but that only works until the dependencies change, and a hand-written order can't notice if someone introduces a cycle — a loop where nothing can legally go first:

# hand-written order, easy to get subtly wrong once there are many steps
steps = ["compile", "test", "package", "deploy"]
# if "package" quietly grows a new dependency on a step added later,
# nothing here notices -- the list just silently runs in the wrong order

graphlib.TopologicalSorter, added to the standard library specifically for this, takes the dependencies as data instead and computes a valid order — or tells you plainly there isn't one:

from graphlib import TopologicalSorter

ts = TopologicalSorter()
ts.add("test", "compile")       # "test" needs "compile" done first
ts.add("package", "test")      # "package" needs "test" done first
ts.add("deploy", "package")   # "deploy" needs "package" done first

print(list(ts.static_order()))
# ['compile', 'test', 'package', 'deploy'] -- confirmed live

ts.add(node, *predecessors) reads as "node depends on each of predecessors." static_order() returns every node exactly once, each one after all of its own predecessors — a node with no predecessors at all (like "compile" here, added only as someone else's predecessor) is included automatically, with nothing to wait for.

2 · Building the graph from a dict, and the cycle error

For a graph that's already known up front, passing a dict straight to the constructor is shorter than calling .add() repeatedly — keys map to a list of their own predecessors, the same direction as .add():

graph = {"a": [], "b": ["a"], "c": ["a", "b"]}
ts = TopologicalSorter(graph)
print(list(ts.static_order()))   # ['a', 'b', 'c'] -- confirmed live

If the dependencies describe a cycle — two steps that each (directly or through others) depend on one another — there is no valid order, and graphlib says so with a dedicated exception rather than silently returning something wrong:

ts = TopologicalSorter()
ts.add("x", "y")
ts.add("y", "x")   # x needs y, and y needs x -- a cycle

list(ts.static_order())
# graphlib.CycleError: ('nodes are in a cycle', ['x', 'y', 'x']) -- confirmed live

That error is the entire point of using graphlib over a hand-rolled sort: a cycle in a hand-written list just produces a wrong-looking order that someone has to notice; a cycle fed to TopologicalSorter raises CycleError immediately, naming the exact loop it found.

3 · When steps can run at the same time: the manual protocol

static_order() is a flat sequence — fine for running steps one at a time, but it throws away information a scheduler running steps concurrently needs: which steps have no dependency on each other and could start together right now. prepare()/get_ready()/done() expose that, batch by batch:

ts = TopologicalSorter({"b": ["a"], "c": ["a"], "d": ["b", "c"]})
ts.prepare()
while ts.is_active():
    ready = ts.get_ready()         # every node whose predecessors are all done
    print("ready:", ready)
    ts.done(*ready)                # mark them finished, unlocking their dependents
# ready: ('a',)
# ready: ('b', 'c')   -- b and c both only needed a, so both are ready together
# ready: ('d',)
# confirmed live

get_ready() returns a tuple, which may hold more than one node — exactly the steps a thread pool (Day 73's ThreadPoolExecutor) could hand out to run at once, since none of them is waiting on any of the others. done(*ready) tells the sorter those nodes finished, which is what unlocks the next batch. One rule to know: once prepare() has run, .add() raises ValueError — the graph is locked in before execution starts, so it can't be edited out from under a scheduler already consuming it. static_order(), under the hood, is calling exactly this protocol and flattening its batches into one sequence — it also can only be consumed once per sorter.

Where pandas/NumPy go from here: neither library has an equivalent — graphlib orders discrete named steps by dependency, not rows or columns of tabular data, so there is nothing to contrast; this callout exists only to confirm the absence, per MISSION.md's no-pandas rule.
