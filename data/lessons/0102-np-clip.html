np.clip(): the array-level clamp underneath Series.clip()

Lesson 101 closed its own standing candidate with none carried forward, so this round ran a fresh curriculum/glossary scan (same situation Lessons 98/99 started from). Lesson 35 taught Series.clip() and even hand-derived its logic as a nested np.where() floor-then-ceiling check — but never named the actual NumPy sibling, np.clip(), that Series.clip() itself calls down to. A clean, genuinely surprising gap closing a loop Lesson 35 opened, same lineage shape as Lesson 100 closing Lesson 21's pd.concat() thread.

1 · Same clamp, one level lower

np.clip() does exactly what Lesson 35's Series.clip() does — just one layer lower, on any array-like, not only a Series:

import numpy as np
import pandas as pd

arr = np.array([120.0, 5.0, 999.0, 50.0])
np.clip(arr, 50, 150)
# array([120.,  50., 150.,  50.])

s = pd.Series([120.0, 5.0, 999.0, 50.0])
np.clip(s, 50, 150)
# 0    120.0
# 1     50.0
# 2    150.0
# 3     50.0
# dtype: float64

Confirmed directly (pandas 3.0.6, numpy 2.5.4): calling np.clip() on a Series returns a Series back, not a bare array — NumPy's dispatch machinery recognizes pandas objects and hands the result back in the same type, byte-for-byte identical to calling s.clip(lower=50, upper=150) directly (checked with np.array_equal()). The two aren't just similar — Series.clip() calls down to this exact same NumPy routine under the hood, the same relationship Lesson 100 found between pd.concat() and the raw np.vstack()/np.hstack() family underneath it.

2 · Three traps the Series method doesn't have

Confirmed directly, three behaviors specific to the plain-array function, none of which Series.clip() exposes the same way:

# Trap 1: lower > upper doesn't raise -- every value silently becomes
# the upper bound, no warning at all.
np.clip(arr, 150, 50)
# array([50., 50., 50., 50.])  -- all four values, whatever they were

# Trap 2: an int array clipped with float bounds silently upcasts to
# float64 -- same silent-upcast shape as Lesson 100's stacking family.
ints = np.array([1, 200, 300], dtype=np.int64)
np.clip(ints, 10.5, 100.5).dtype
# dtype('float64')  -- even though every input value was a plain int

# Trap 3: NaN passes straight through, same as Series.clip() -- NOT
# pulled to either bound, because NaN can't be compared with < or >.
np.clip(np.array([np.nan, 5.0, 999.0]), 50, 150)
# array([ nan,  50., 150.])  -- the NaN survives untouched

Trap 1 is the one worth saying out loud in an interview: passing bounds in the wrong order is a typo any time of day, and np.clip() gives zero feedback that something went wrong — it just quietly returns an array of one repeated value. Cross-checked against the official NumPy docs, which confirm this exact rule in the signature's own example: when a_min > a_max, every output value becomes a_max. Trap 2's silent int-to-float upcast on mismatched bound/array dtypes is the same no-warning pattern Lesson 100 found stacking an int array with a float one. Trap 3 matches Lesson 35's own glossary note almost exactly — NaN passes through both the Series and the array version untouched, since clipping requires a </> comparison and NaN fails every comparison by IEEE float rules (Lesson 1's NaN entry).

3 · Why reach for np.clip() at all, given Series.clip() exists

Confirmed directly, timing both over an identical 2,000,000-row column: Series.clip() measured several times slower than calling np.clip() on the Series' own .to_numpy() array directly, run repeated three times to rule out a one-off fluke (results varied run to run, from roughly 6x to roughly 36x — the exact ratio is noisy, but the direction never flipped). The gap traces to the same source as every pandas-vs-NumPy timing difference this course has found before: Series.clip() carries pandas' index-alignment and missing-value-handling machinery on top of the same underlying NumPy call, while np.clip() on a raw array skips all of it.

In practice this almost never matters — one clip() call on a column is not the bottleneck in a real pipeline, and Series.clip()'s Index-aware behavior (per-row bounds via a same-length Series, from Lesson 35) is usually exactly what's wanted. The real reason to know np.clip() by name: it is what a NumPy-only function signature or a third-party library expects when it asks for an array, not a Series — and it is the term that shows up when reading NumPy-flavored code that has no pandas import at all, directly matching this course's own "read NumPy-flavored code and predict its output" goal.

Q: "What's the difference between Series.clip() and np.clip()?" A strong answer, out loud: "Functionally almost nothing on a Series — Series.clip() actually dispatches down to np.clip() under the hood, confirmed by getting byte-identical results either way. np.clip() works on any array-like, not just a Series, and it's a bit faster on a raw array since it skips pandas' index-alignment overhead. The one trap I'd watch for either way: passing the bounds in the wrong order doesn't raise — it silently clips everything to the upper bound, no warning." The signal: knowing they're the same operation at different layers, not two unrelated functions, and naming the lower-order-than-upper trap unprompted.
