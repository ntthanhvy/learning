sort_values() and reset_index() edge cases

Lesson 30's teaser named this exactly: sort_values() and reset_index() have been called in almost every practice file since Lesson 6, always as setup, never as the lesson. Today is the edge cases that actually bite in an interview — what the index looks like after a sort, and the silent traps in .loc[] that follow.

1 · sort_values() moves rows, not labels

The one fact this whole lesson hangs on: sort_values() reorders the rows, but each row keeps carrying its original Index label along with it. Watch the labels on the left column after sorting clean (the same cleaned 4-row slice as Lessons 6-30) by amount:

sorted_clean = clean.sort_values("amount")
#    order_id customer  amount  order_date
# 1         2     Binh    35.5  2026-01-06
# 5         6       An    42.0  2026-01-10
# 0         1       An   120.0  2026-01-05
# 4         5     Binh   180.0  2026-01-09
sorted_clean.index.tolist()   # [1, 5, 0, 4] -- NOT [0, 1, 2, 3]

The rows are in the right order now, but the index still says 1, 5, 0, 4 — the position each row held before the sort. That mismatch between "row order" and "index label" is where every edge case below comes from.

2 · The trap: .iloc[0] and .loc[0] now disagree

This is the concrete gotcha worth rehearsing out loud. After the sort above, .iloc[0] (position 0 — the actual first row) and .loc[0] (the row still labeled 0) point to two different rows:

sorted_clean.iloc[0]["amount"]   # 35.5  -- Binh, the true smallest amount, position 0
sorted_clean.loc[0]["amount"]    # 120.0 -- An, whatever row was originally at position 0

Neither call raises an error — both return a perfectly valid row, just not the same one. Reaching for .loc[0] out of habit right after a sort is a real "no crash, quietly wrong" trap, the same family this course has flagged since Lesson 19: it looks like "give me the first row" but it actually means "give me whatever row happens to still be labeled 0."

3 · reset_index(): renumber the labels to match the new order

reset_index() is the fix: it replaces the index with a fresh 0, 1, 2, 3 that matches the DataFrame's current row order, so .loc[0] and .iloc[0] agree again. But its default behavior surprises people the first time:

sorted_clean.reset_index()
#    index  order_id customer  amount  order_date
# 0      1         2     Binh    35.5  2026-01-06
# 1      5         6       An    42.0  2026-01-10
# 2      0         1       An   120.0  2026-01-05
# 3      4         5     Binh   180.0  2026-01-09

The old labels didn't vanish — they became a brand-new column literally called index. That's rarely what you want mid-pipeline; drop=True is the version people actually mean almost every time:

sorted_clean.reset_index(drop=True)
#    order_id customer  amount  order_date
# 0         2     Binh    35.5  2026-01-06
# 1         6       An    42.0  2026-01-10
# 2         1       An   120.0  2026-01-05
# 3         5       Binh  180.0  2026-01-09

Rule of thumb worth saying out loud in an interview: "if I don't need the old positions kept around as data, I always pass drop=True."

4 · The shortcut: sort_values(..., ignore_index=True)

sort_values() takes its own ignore_index=True keyword, which does the sort and the reset in one call — hand-verified to produce an identical result to chaining the two:

clean.sort_values("amount", ignore_index=True).equals(
    clean.sort_values("amount").reset_index(drop=True)
)  # True

Same result, one call instead of two chained ones — a small method-chaining (Lesson 8) win when the old labels are never needed.

5 · na_position: where do missing values sort to?

Coercing the raw fixture's non-numeric "unknown" amount to NaN (Lesson 3's errors="coerce") and sorting shows pandas' default: NaN always sorts last, regardless of ascending/descending:

raw["amount_num"] = pd.to_numeric(raw["amount"], errors="coerce")
raw.sort_values("amount_num")[["customer", "amount_num"]]
#   35.5, 42.0, 99.9, 120.0, 180.0, NaN   <- NaN last even in ascending order

raw.sort_values("amount_num", na_position="first")[["customer", "amount_num"]]
#   NaN, 35.5, 42.0, 99.9, 120.0, 180.0   <- na_position="first" moves it to the front instead

SQL's default is implementation-defined here (Postgres sorts NaN/NULL last in ascending order by default too, but not every database agrees) — na_position= makes pandas' choice explicit either way instead of leaving it to a default someone has to look up.

6 · Multiple sort keys, independent directions

by= takes a list of columns, and ascending= takes a matching list — each key can sort its own direction:

clean.sort_values(["customer", "amount"], ascending=[True, False])
#   customer  amount
#   An         120.0    <- customer A-Z, but amount high-to-low WITHIN each customer
#   An          42.0
#   Binh       180.0
#   Binh        35.5

Same idea as SQL's ORDER BY customer ASC, amount DESC — each column in the list gets paired with the ascending value at the same position.

7 · sort_index(): the inverse operation

Since the original labels survive a sort (Section 1), they're still usable to get back to the pre-sort row order — sort_index() sorts by the index labels themselves, not by any column:

sorted_clean.sort_index().equals(clean)   # True -- exactly restores the original row order

Worth knowing this exists, mostly so you recognize it when reading someone else's code — it's a much rarer interview ask than sort_values().

8 · reset_index() after groupby: Series becomes a DataFrame

This is the single most common place reset_index() actually shows up in real pipelines. A groupby() aggregation like Lesson 4's .sum() returns a Series indexed by the group key, not a DataFrame:

g = clean.groupby("customer")["amount"].sum()
# customer
# An      162.0
# Binh    215.5
# Name: amount, dtype: float64      <- a Series; "customer" IS the index, not a column
type(g)   # pandas.Series

reset_index() turns that grouped Series back into an ordinary DataFrame with the group key as a real column again — the shape most downstream code (another merge(), writing to CSV) actually expects:

g.reset_index()
#   customer  amount
# 0       An   162.0
# 1     Binh   215.5
type(g.reset_index())   # pandas.DataFrame

g.reset_index(name="total_amount")   # rename the value column while resetting, in one call
#   customer  total_amount
# 0       An         162.0
# 1     Binh         215.5

name= only applies to a Series (there's no single "the value column" to rename on a multi-column DataFrame) — it's the one reset_index() keyword worth remembering specifically for this groupby pattern.

9 · Downstream operations that quietly reset the index for you

Not every operation leaves gappy index labels lying around — worth knowing which ones already hand you a clean 0..n-1 index so an extra reset_index() isn't needed. A boolean filter does not renumber:

clean[clean["amount"] > 50].index.tolist()   # [0, 4] -- gaps, not [0, 1]

...but merge() (Lesson 5) always returns a fresh 0..n-1 index on its result, regardless of what the inputs' indexes looked like:

clean.sort_values("amount").merge(customers, on="customer", how="left").index.tolist()
# [0, 1, 2, 3] -- merge() re-indexes the result even though the left side was unreset

The row order from the sort survives the merge — merge just doesn't carry the old labels forward. Don't assume every DataFrame method leaves the index as-is; check the one you're using rather than guessing.

Q: "You sorted a DataFrame and then indexed into row 0 — but got the wrong row. What happened?" A strong answer, out loud: "sort_values() reorders the rows but keeps each row's original index label attached — it doesn't renumber. So .loc[0] still means 'the row labeled 0', which after a sort is whatever row used to be first, not the row that's first now. .iloc[0] is what I actually wanted — position, not label. The fix going forward is reset_index(drop=True), or sort_values(..., ignore_index=True) to do both in one call, so the labels match the new row order and .loc[] and .iloc[] agree again." The signal: naming .loc/.iloc as the actual mechanism, not just "I added reset_index() and it worked."
