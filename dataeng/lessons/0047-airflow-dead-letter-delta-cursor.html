1 · The limitation Day 46 named honestly instead of hiding

Day 46's scope line said it directly: check_dead_letters's COUNT(*) FROM raw.dead_letter_events is a running total over every row ever inserted, not new rows since the last run, because Day 41's table has no "already seen" marker column. The consequence is exactly what a running total always does to a fixed threshold: once the total crosses DEAD_LETTER_ALERT_THRESHOLD once, it keeps failing on every run after, forever, even with zero new poison events, until someone clears or fixes the table by hand. A monitoring check that keeps alerting after the actual problem stopped is worse than noise — it teaches whoever's on call to ignore it, which is the opposite of what Day 46 Section 2 argued a real alert should do.

Day 46's own closing section named two concrete next steps rather than a vague "improve this." One was a real notification via Day 35's on_failure_callback — a good pick, but it needs an actual Slack/email/PagerDuty target to call, which this course has deliberately kept out of scope (no paid services, per MISSION.md's constraints). The other was "a per-run delta via a Day-38-style Variable cursor instead of a running total" — fully buildable with nothing new, since Day 38 already solved this exact shape of problem for a different table. Today builds that one.

2 · Same cursor shape as Day 38, different table, same reason

Day 38's check_order_events_grew needed to remember last run's row count for raw.order_events so it could tell "grew" from "didn't," and it stored that single number in an Airflow Variable because a Variable, unlike Day 20's XCom, has no run-boundary: the same key is visible to the same task across separate, later DAG runs, which is exactly "small state that outlives one run." Today's problem is the mirror image on a different table: check_dead_letters needs to remember last check's dead-letter count so it can alert on new poison events, not the pile that already triggered an alert last time. Same tool, same reason, different number being tracked.

The one real difference from Day 38 worth naming: Day 38's task raised on no-growth, because its job was to suppress a downstream Asset trigger, and raising was the only lever outlets= respects. Today's task has no outlet and no downstream trigger to suppress — its only job is deciding whether to alert — so it raises on the opposite condition: too much new bad data, not too little growth. Both tasks write their cursor only after a successful comparison, for the same reason Day 38 Section 3 argued: a run that itself raises must leave the cursor exactly where it was, so the next run still compares against the last count a check actually completed against.

3 · Build: a delta instead of a running total

In your food-delivery-pipeline repo, edit dags/food_delivery_pipeline.py — the same file Day 7 wrote and Days 35/45/46 each added one thing to. Add one import, one constant, and replace check_dead_letters's body:

# new import, alongside the existing psycopg import
from airflow.sdk import Variable

# new constant, module level, alongside the existing DEAD_LETTER_ALERT_THRESHOLD
DEAD_LETTER_CURSOR_KEY = "dead_letter_last_count"


def check_dead_letters(**context) -> None:
    import psycopg

    with psycopg.connect(PG_DSN) as conn, conn.cursor() as cur:
        cur.execute("SELECT count(*) FROM raw.dead_letter_events")
        current_count = cur.fetchone()[0]

    # Day 38's exact pattern: a str default for a cursor that has never run
    # before, cast to int immediately -- Variable.get() only ever returns str.
    last_count = int(Variable.get(DEAD_LETTER_CURSOR_KEY, default="0"))
    new_since_last_check = current_count - last_count

    # Write the cursor forward unconditionally, success or alert -- this run
    # really did check up to current_count, so the next run's delta should
    # start from here regardless of whether today's count trips the alert.
    Variable.set(DEAD_LETTER_CURSOR_KEY, str(current_count))

    if new_since_last_check > DEAD_LETTER_ALERT_THRESHOLD:
        raise ValueError(
            f"{new_since_last_check} new dead-lettered event(s) since the last "
            f"check exceeds threshold {DEAD_LETTER_ALERT_THRESHOLD} "
            f"(total now {current_count})"
        )

    print(
        f"checked raw.dead_letter_events: {new_since_last_check} new since last "
        f"check, {current_count} total, within threshold"
    )

One choice worth defending out loud, because it looks backwards at a glance: the cursor is written before the raise, not after. That's the opposite order from Day 38's growth check, and on purpose — Day 38's cursor had to stay put on a failed run, because that run's own comparison was never trusted (no real growth, so there's nothing new worth remembering). Today's cursor should move forward even on an alerting run, because the COUNT(*) itself is real and current regardless of whether it crosses the threshold; moving it forward is exactly what turns "alert on the same pile forever" into "alert once per burst of new events." Writing it only on the non-alerting path would silently resurrect Day 46's original bug: a true but already-reported pile-up would keep re-triggering against a last_count that forever points back to before the alert first fired. trigger_rule=TriggerRule.ALL_DONE from Day 45 and DEAD_LETTER_ALERT_THRESHOLD from Day 46 are both untouched.

4 · Verify: a mocked cursor, then the real DAG module

The algorithm's correctness doesn't depend on Postgres or Airflow's metadata database at all — it's six numbers compared against each other. This round verified it that way first, the same mocked-cursor approach Day 46 used for its own threshold boundary, with the one case that actually distinguishes today's delta from Day 46's running total:

def decide(last_count: int, current_count: int) -> tuple[int, bool]:
    delta = current_count - last_count
    return delta, delta > 5

# (last_count, current_count) -> (delta, alert)
decide(0, 0)    # -> (0, False)  -- nothing ever landed
decide(0, 5)    # -> (5, False)  -- exactly at threshold, still fine
decide(0, 6)    # -> (6, True)   -- one past threshold, alert
decide(10, 12)  # -> (2, False)  -- small delta; current_count=12 alone would NOT mislead here
decide(10, 50)  # -> (40, True)  -- real burst, alert
decide(50, 50)  # -> (0, False)  -- Day 46's exact bug case: huge total, zero new -- must NOT alert

Run live this round, all six cases matched the comment exactly — the last case is the one Day 46's running-total version gets wrong: a table sitting at 50 rows from a burst three days ago would alert on every single run forever under Day 46's logic, and correctly stays quiet under today's delta once nothing new has landed.

Q: "Your dead-letter alert fired once last week. It's still failing every run today even though nothing new has landed. What's wrong, and how would you fix it?" A strong answer, out loud: "The check was comparing a running total against a fixed threshold instead of new rows since the last check — once the total crosses the line once, it never goes back down on its own, so it alerts forever until someone manually clears the table. I fixed it the same way I'd already fixed an analogous problem for a different Airflow task: store the last-seen count in an Airflow Variable, compute the delta against the current count on every run, and alert on the delta, not the total. The cursor has to advance every run regardless of whether that run alerts, or the next run compares against a stale baseline and the exact same bug comes back in a different shape." The signal: recognizing this as the same root cause in a new place, not a brand-new bug, and stating the cursor-write-timing reasoning without being asked.
