typing extras: Protocol, TypedDict & generics

Day 7 covered enough typing to read most function signatures: plain types, list[X], Optional[X]. Today adds three more shapes that show up constantly once code grows past single functions — duck-typing without inheritance, a dict with a fixed known shape, and a class or function that works the same way for any type while staying type-checkable.

Bridge from SQL: a TypedDict is close to a table schema written in Python instead of SQL — fixed column names, fixed column types, checked by tooling before the code ever runs, but (unlike a real table) not enforced by anything at runtime.

1 · Protocol: structural typing, no inheritance required

Normal type hints usually mean "an instance of this class or a subclass of it." A Protocol hints something different: "any object shaped like this," regardless of what it inherits from. This is duck-typing made checkable.

from typing import Protocol

class Named(Protocol):
    def name(self) -> str: ...

class Employee:
    def name(self) -> str:
        return "Ada"

def greet(item: Named) -> str:
    return f"Hello, {item.name()}!"

greet(Employee())   # fine — Employee never mentions Named at all

Employee does not inherit from Named and never imports it — it just happens to have a name() method with a matching signature, and that's enough. Any other class with the same method — Product, Customer, whatever — satisfies the same Protocol with zero coupling between them. This is the same shape SQL never needs a name for: two unrelated tables can each have a name column without one "inheriting" from the other.

isinstance() against a Protocol needs an extra decorator. Verified live: plain isinstance(emp, Named) raises TypeError: Instance and class checks can only be used with @runtime_checkable protocols. Add @runtime_checkable above class Named(Protocol): and isinstance() works — confirmed live returning True for a class with a matching name() method and False for one without. It only checks that the names exist, not that the signatures actually match — that deeper check is still a static type checker's job, not isinstance()'s.

2 · TypedDict: a dict with a fixed, named, typed shape

A plain dict[str, object] hint says "some string keys, values of unknown type" — true, but useless for catching a typo'd key or a wrong value type. TypedDict declares the exact keys and types a dict is supposed to have:

from typing import TypedDict

class Order(TypedDict):
    sku: str
    qty: int
    unit_price: float

def order_total(order: Order) -> float:
    return order["qty"] * order["unit_price"]

order: Order = {"sku": "A1", "qty": 3, "unit_price": 2.5}

Verified live: an Order value is a completely ordinary dict at runtime — order["qty"], order.keys(), everything works exactly as it would without the hint. TypedDict buys nothing at runtime by itself; the payoff is a type checker (or a careful reader) catching order["qyt"] or order["qty"] = "three" before the code ever runs, the same way a table schema catches a bad column name at the database, not in application logic.

3 · Generics: one class or function, any type, still checkable

Without generics, "a box that holds one item" either loses its item's type entirely (class Box: def __init__(self, item): ... — item is typed as Any, effectively untyped) or needs a separate class per type (IntBox, StrBox, ...). A TypeVar plus Generic keeps one definition and the type information both:

from typing import TypeVar, Generic

T = TypeVar("T")

class Box(Generic[T]):
    def __init__(self, item: T):
        self.item = item

    def get(self) -> T:
        return self.item

int_box: Box[int] = Box(42)      # get() is known to return int
str_box: Box[str] = Box("hi")   # get() is known to return str, same class

Verified live: Box is one class, and int_box.get()/str_box.get() return 42 and "hi" respectively — the same code path for both, no per-type subclass written. A TypeVar works the same way directly on a plain function, with no class involved:

def first_or_default(items: list[T], default: T) -> T:
    return items[0] if items else default

One TypeVar ties the return type to whichever type was actually passed as items'/default's type at each call — a checker knows first_or_default([1, 2], 0) returns int and first_or_default(["a"], "z") returns str, from the exact same function body.

Python 3.12 added a shorter built-in syntax for the same idea — class Box[T]: instead of T = TypeVar("T"); class Box(Generic[T]):. Named here so it's recognizable if seen; today's practice file uses the explicit TypeVar/Generic form because it works on every Python version this course targets and makes the underlying mechanism visible rather than hidden behind new syntax.

Q: "What's the difference between a Protocol and inheriting from an abstract base class?" A strong answer, out loud: "Inheritance is explicit — a class has to say up front which base it implements. A Protocol is structural: any class with matching method names and signatures satisfies it automatically, with zero coupling and no import needed in the implementing class at all. It's static duck-typing — useful when you don't own the class you're passing in, or don't want to force unrelated classes into a shared hierarchy just to satisfy one type hint." The signal: knowing Python has both nominal (inheritance-based) and structural (shape-based) typing, and picking the right one instead of reaching for inheritance by default.

Where pandas goes from here: nothing pandas-specific — these three are general Python typing tools a pandas-adjacent codebase would use identically, e.g. a TypedDict describing one row's shape before it ever becomes a DataFrame. This is the only sentence in this lesson that names pandas.
