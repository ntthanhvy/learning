Cache stampede: when the cache itself causes the outage

Lesson 56 named this as its own closing teaser: a second confirmed-untaught gap tying directly to Lesson 9's cache-aside pattern and Lesson 32's retry-storm material. Lesson 9 taught the cache as the fix for repeated reads hitting Postgres. Today's lesson is the failure mode where that exact fix backfires the moment the cached value expires while it's popular.

1 · The gap in Lesson 9's cache-aside pattern

Lesson 9's cache-aside flow was: check the cache, and on a miss, read the real source and write the result back with a TTL. That flow quietly assumes misses arrive one at a time. It doesn't say what happens when a single hot key — a trending product page, a popular user's profile, a homepage feed — expires while thousands of requests per second are asking for exactly that key. Every one of those requests sees a miss at the same instant, and every one of them independently falls through to Postgres to recompute the same value.

Frontend-habit trap: this looks identical to Lesson 32's retry storm at first glance — many clients doing the same expensive thing at once — but the trigger is different. A retry storm needs a prior failure to synchronize clients around. A cache stampede (also called the dogpile effect or thundering herd problem) needs no failure at all — a perfectly healthy cache expiring on schedule is enough to trigger it, because popularity, not breakage, is the fuel.

2 · Why this is worse than an ordinary cache miss

An ordinary cache miss costs one expensive read. A stampede costs N simultaneous expensive reads for the same key, where N is however many requests arrived in the gap between "the old value expired" and "the new value finished being written back." If the origin computation is a slow aggregate query or a call to a third-party API, that gap might be hundreds of milliseconds — long enough, on a hot key, for thousands of duplicate requests to land on Postgres or the downstream API at once. The cache, whose entire job was to protect the origin from repeated load, becomes the mechanism that synchronizes an overload against it. Worse, if that overload makes the origin slow enough to blow past the caller's own timeout, some of those N callers retry — turning a stampede into the retry storm Lesson 32 already named, now stacked on top.

3 · Three fixes, each closing a different part of the gap

The first fix is request coalescing: on a miss, the first caller to arrive takes a short-lived lock keyed to that cache key (a Redis SETNX, or Lesson 56's Postgres advisory lock repurposed for exactly this) and is the only one that actually recomputes the value. Every other caller that misses while the lock is held either waits briefly for the winner to finish and populate the cache, or — if the old value is still around — serves that slightly stale copy instead of joining the recomputation. N simultaneous origin hits collapses to 1.

// coalesced recompute: only the lock winner actually queries Postgres;
// everyone else waits on the same result instead of duplicating the work
func getProductPage(ctx context.Context, id string) (*Page, error) {
    if p, ok := cache.Get(id); ok {
        return p, nil
    }
    // only one goroutine per key actually calls the function below;
    // concurrent callers for the same id block here and share its result
    v, err, _ := group.Do(id, func() (any, error) {
        p, err := loadFromPostgres(ctx, id)
        if err != nil {
            return nil, err
        }
        cache.Set(id, p, 10*time.Minute)
        return p, nil
    })
    if err != nil {
        return nil, err
    }
    return v.(*Page), nil
}

The group.Do call above is the shape of Go's golang.org/x/sync/singleflight package — one in-process call per key, with every concurrent caller for that same key blocking on and sharing the single result, no explicit lock code needed. It only coalesces callers within one process, though: across multiple instances, an external lock (Redis or a Postgres advisory lock) is still needed to get the same one-recompute guarantee.

The second fix is early refresh: recompute a hot key's value slightly before its TTL actually expires — deterministically, or probabilistically with rising odds as expiry approaches — so requests never observe a real miss on it at all. The third fix is simplest and often good enough: serve the stale value while recomputing in the background (stale-while-revalidate), trading a few seconds of staleness — the same staleness-tolerance judgment call Lesson 9 already asked for every cache — for zero synchronized origin hits.

4 · The trap: this only fires on hot keys

A cache holding a million rarely-read keys essentially never stampedes — misses on cold keys are already spread out in time, so nothing synchronizes. The failure mode is specific to popularity: the more callers share one key, the more of them land in the exact same expiry gap. That's also why it's easy to miss in testing — a staging environment with light, spread-out traffic will never reproduce it, and the first real evidence is often an on-call page the moment a homepage or trending-item cache entry expires under real production load.

Q: "Your cache TTL is 10 minutes and every 10 minutes you see a latency spike on Postgres. Why, and what would you do?" A strong answer, out loud: "That's a classic cache stampede — the TTL expiring on a hot key means every concurrent request for it misses at once and all fall through to Postgres simultaneously, not because anything broke but because the value was popular. I'd add request coalescing so only one caller per key actually recomputes and the rest share that result — Go's singleflight package does this in-process, or a Redis lock across instances. If the data tolerates a few seconds of staleness, serving the old value while refreshing in the background is often simpler and just as effective." The subtext: naming that this is a popularity problem, not a bug, and knowing there's more than one valid fix depending on staleness tolerance.
