.assign(): adding columns without ever risking SettingWithCopy

Chào bạn — Lesson 77 closed the core .str accessor family, so today's a fresh scan. Grepping every lesson body and the glossary turned up a real gap hiding in plain sight: .assign() has quietly appeared in code since Lesson 8's method-chaining lesson (.assign(amount=lambda d: ...)) and kept showing up ever since (Lessons 53, 67), but it has never gotten its own lesson explaining its own mechanics — what its multiple keyword arguments actually do, in what order, and why it's the one column-creation tool that sidesteps Lesson 26's whole SettingWithCopy question entirely.

1 · The basic shape: keyword name becomes the new column

.assign(col=value) returns a new DataFrame with col set to value — the keyword's own name becomes the column name:

df = pd.DataFrame({
    "customer": ["An", "Binh", "Chi"],
    "amount": [120.0, 215.5, 99.9],
    "qty": [3, 2, 1],
})
out = df.assign(unit_price=df["amount"] / df["qty"])
# customer  amount  qty  unit_price
#       An   120.0    3       40.00
#     Binh   215.5    2      107.75
#      Chi    99.9    1       99.90
"unit_price" in df.columns   # False -- df itself was never touched

Confirmed directly (pandas 3.0.6): out is a brand-new DataFrame; df keeps exactly its original three columns. This is functionally the same result as df["unit_price"] = df["amount"] / df["qty"], but that spelling mutates df in place — .assign() never does, by design.

2 · Multiple columns in one call, later ones referencing earlier ones via lambda

Passing several keyword arguments builds several columns in a single call. When a later column needs a column an earlier keyword in the same call just created, that value must be a lambda d: ... rather than a plain expression — the lambda receives the in-progress DataFrame (with the earlier keywords already applied) as d:

out = df.assign(
    unit_price=lambda d: d["amount"] / d["qty"],
    unit_price_rounded=lambda d: d["unit_price"].round(1),
)
# customer  amount  qty  unit_price  unit_price_rounded
#       An   120.0    3       40.00                40.0
#     Binh   215.5    2      107.75               107.8

Confirmed directly: keyword arguments are guaranteed to run in the exact order written (a documented behavior, not incidental), so unit_price_rounded's lambda genuinely sees unit_price already present on d. Swapping the plain (non-lambda) form in for the second keyword — unit_price_rounded=df["unit_price"].round(1) — was confirmed to raise KeyError: 'unit_price', because a plain expression evaluates immediately against the ORIGINAL df, which never had unit_price at all. The lambda form is not just style — it is the only way to chain a new column off one created earlier in the same call.

Rule of thumb: if a keyword's value only reads columns that already exist on the original DataFrame, a plain expression is fine. The moment it needs a column being created by an earlier keyword in the same .assign() call, it must be lambda d: ... — same reason Lesson 8 introduced the lambda form in the first place, now with the mechanism spelled out explicitly.

3 · Overwriting an existing column works the same way

The keyword name doesn't have to be new — reusing an existing column's name overwrites it in the returned DataFrame, and still leaves the original untouched:

out = df.assign(amount=lambda d: d["amount"] * 2)
out["amount"].tolist()   # [240.0, 431.0, 199.8]
df["amount"].tolist()    # [120.0, 215.5, 99.9]  -- original amounts, unchanged

Confirmed directly: this is a genuine overwrite in the result, with zero risk to df — useful for "clean this column" steps inside a chain (coercing dtype, rounding, clipping) without needing a second variable name.

4 · Why .assign() never triggers Lesson 26's SettingWithCopy question

Lesson 26 warned that writing into a filtered slice — sub["col"] = value after sub = df[mask] — is ambiguous: it might silently fail to update anything, might raise, or might mutate something unintended, depending on whether sub is a view or a copy. .assign() sidesteps that whole question, because it never writes into an existing object at all — it always returns a fresh, independent DataFrame:

sub = df[df["amount"] > 100]
sub_flagged = sub.assign(flag=True)   # no warning, no ambiguity -- sub_flagged is simply new

Confirmed directly: calling .assign() on a filtered slice raises nothing and produces a correct, independent result, with no .copy() needed first — because .assign() was never going to write into sub's own memory in the first place. This is exactly why it is the standard tool inside a method chain (Lesson 8): every intermediate DataFrame is disposable, so there is nothing to accidentally mutate.

SQL bridge: df.assign(new_col=expr) is the pandas spelling of adding a computed column to a SELECT list — SELECT *, amount / qty AS unit_price FROM orders. Chaining several keyword arguments in one .assign() call, where a later one reads an earlier one, mirrors a query building one derived column on top of another within the same SELECT (or a chain of WITH CTEs) — each step sees the previous step's output, nothing upstream is ever mutated.

Q: "Why use df.assign(col=...) instead of just df['col'] = ...?" A strong answer, out loud: "Both produce the same values, but assign() never mutates the original DataFrame — it always returns a new one, which is what makes it safe to drop into the middle of a method chain without worrying about Lesson 26's whole view-versus-copy question, since there's no in-place write happening at all. It also reads better inside a chain: df.query(...).assign(unit_price=lambda d: d['amount']/d['qty']).sort_values('unit_price') stays one expression, no intermediate variable needed. The one thing I'd watch for: if I'm creating two columns in the same assign() call and the second depends on the first, the second has to be a lambda — a plain expression there evaluates against the original DataFrame, before the first new column existed, and raises a KeyError." The signal: naming the immutability as the actual reason (not just "it's the fancy way"), and knowing the lambda-dependency rule cold rather than guessing at it live.
