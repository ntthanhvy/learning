to_dict() and to_records(): handing a table back to plain Python

Lesson 52 closed out the whole Lesson-47-flagged batch, so this round did a fresh scan of the curriculum and glossary for the next genuinely-uncovered pattern (per its own teaser). Every lesson so far has ended with a DataFrame or Series still inside pandas — MISSION.md's own wrangling path ends in "output," and nothing has taught the step of handing the finished table back out as plain Python objects. That's today's gap.

Recap, in one line

Lesson 1's whole pitch was "think in tables" — stay inside DataFrames and Series instead of looping. Eventually something outside pandas needs the result: a JSON API response, a plain dict for a unit test fixture, a loop-friendly list of rows. to_dict() and to_records() are today's two answers to "how do I get this out."

1 · to_dict(orient="records"): a list of row-dicts

The real orders_raw.csv fixture, cleaned the same way as every lesson since Lesson 6:

clean
--   order_id customer  amount order_date
-- 0         1       An   120.0 2026-01-05
-- 1         6       An    42.0 2026-01-10
-- 2         2     Binh    35.5 2026-01-06
-- 3         5     Binh   180.0 2026-01-09

orient="records" is the shape most interview take-homes and API responses actually want: one dict per row, in a plain Python list — the exact reverse of building a DataFrame from a list of dicts in the first place.

clean.to_dict(orient="records")
-- [{'order_id': 1, 'customer': 'An', 'amount': 120.0, 'order_date': Timestamp('2026-01-05 00:00:00')},
--  {'order_id': 6, 'customer': 'An', 'amount': 42.0,  'order_date': Timestamp('2026-01-10 00:00:00')},
--  {'order_id': 2, 'customer': 'Binh', 'amount': 35.5, 'order_date': Timestamp('2026-01-06 00:00:00')},
--  {'order_id': 5, 'customer': 'Binh', 'amount': 180.0, 'order_date': Timestamp('2026-01-09 00:00:00')}]

4 rows in, 4 dicts out, same order. Plain numeric and text columns come back as ordinary Python int/float/str — but notice order_date came back as a pandas Timestamp, not a plain Python value. That matters in Section 4.

2 · Other orient= shapes, and Series.to_dict()

The default orient (no argument at all) is "columns" — a dict of dicts, outer keys are column names, inner keys are the row index:

clean.to_dict()  # same as orient="columns"
-- {'order_id': {0: 1, 1: 6, 2: 2, 3: 5},
--  'customer': {0: 'An', 1: 'An', 2: 'Binh', 3: 'Binh'}, ...}

orient="list" is column-oriented too, but each column becomes a plain Python list instead of an index-keyed dict — the shape a plotting library or a bulk-insert call usually wants:

clean.to_dict(orient="list")
-- {'order_id': [1, 6, 2, 5], 'customer': ['An', 'An', 'Binh', 'Binh'], ...}

A Series has its own simpler to_dict(), no orient= needed — the index becomes the keys directly:

clean.groupby("customer")["amount"].sum().to_dict()
-- {'An': 162.0, 'Binh': 215.5}

That's Lesson 4's exact groupby total, now a plain dict — no DataFrame, no Index object, just two key-value pairs.

3 · to_records(): a NumPy structured array instead

to_records() answers the same "get it out" question but for NumPy/C-level consumers instead of plain Python — its output is a numpy.rec.recarray, not a dict or list:

clean.to_records(index=False)
-- rec.array([(1, 'An', 120. , '2026-01-05T00:00:00.000000'),
--            (6, 'An',  42. , '2026-01-10T00:00:00.000000'),
--            (2, 'Binh',  35.5, '2026-01-06T00:00:00.000000'),
--            (5, 'Binh', 180. , '2026-01-09T00:00:00.000000')],
--           dtype=[('order_id', '<i8'), ('customer', 'O'), ('amount', '<f8'), ('order_date', '<M8[us]')])

Each row is a fixed-layout record with named, typed fields — rec[0].amount and rec[0]["amount"] both work. index=False drops the row Index from the output entirely; the default index=True adds it back as the first field, named "index" (or the index's real name, if it was set_index()'d first) — the same default-keeps-the-index instinct as Lesson 31's reset_index().

4 · The gotcha: to_dict() output is NOT automatically JSON-safe

The most common reason to reach for to_dict(orient="records") is to hand a result to json.dumps() for an API response. This is where Section 1's Timestamp value bites — json only knows how to serialize plain Python types, and a pandas Timestamp is not one of them:

import json
json.dumps(clean.to_dict(orient="records"))
-- TypeError: Object of type Timestamp is not JSON serializable

This is a real crash, not a quiet wrong answer — a genuinely different failure shape from this course's usual "no crash, quietly wrong" family (describe(), corr(), convert_dtypes()). The int/float/str columns above serialize fine on their own; only the datetime column needs help. The fix is to convert the datetime column to a plain string before calling to_dict(), using Lesson 32's .dt accessor:

fixed = clean.assign(order_date=clean["order_date"].dt.strftime("%Y-%m-%d"))
json.dumps(fixed.to_dict(orient="records"))
-- '[{"order_id": 1, "customer": "An", "amount": 120.0, "order_date": "2026-01-05"}, ...]'

pandas does have its own to_json() method that sidesteps this by writing a JSON string directly — but its default date format is a raw millisecond epoch integer (1767571200000 for 2026-01-05), not a readable date string, so it trades one surprise for another unless date_format="iso" is passed explicitly. Knowing why the plain to_dict() + json.dumps() path fails is the more broadly useful interview answer, since it explains the same root cause even when the eventual output isn't JSON at all.

5 · The SQL bridge

Neither method has a direct SQL equivalent — a SQL result set is already row-oriented and client libraries (e.g. psycopg, an ORM) handle the "give me plain objects" step automatically when a query returns. The closest mental model is a driver's cursor.fetchall() paired with cursor.description for column names: to_dict(orient="records") is pandas doing that zip-into-named-dicts step for you in one call, and to_records() is the lower-level, fixed-schema cousin — closer to the raw tuples fetchall() returns before any naming happens at all.

Q: "You've cleaned a DataFrame — how do you hand the result to a downstream API as JSON?" A strong answer, out loud: "to_dict(orient='records') gives me a list of one dict per row, which is the shape most JSON APIs expect. The catch is that pandas types like Timestamp aren't JSON-serializable on their own — json.dumps raises a TypeError on any datetime column — so I'd convert those columns to plain strings with .dt.strftime() first, or use pandas' own to_json() with date_format='iso' if I want it to write the JSON string directly. I'd pick to_dict() when I still need to touch the data in Python afterward, and to_json() when I just need the final string." The signal: naming the specific TypeError, not just "it doesn't always work," and knowing there are two real fixes with a real tradeoff between them.
