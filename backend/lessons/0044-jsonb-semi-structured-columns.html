JSONB: when one column is allowed to be a schema of its own

Lesson 2 opened this course with a rule: tables are not JSON, break the blob into columns and rows. That rule still holds — but Postgres also ships a column type that stores JSON directly. Today: what JSONB actually is, why it isn't a loophole around Lesson 2, and the one honest reason to reach for it.

1 · Not a loophole — a different problem

Lesson 2's rule was about data with a known, fixed shape: an order has a total, a status, a customer id — every order has the same fields, so they become columns, and normalization (Lesson 2 again) keeps each fact in one place. A JSONB column exists for the opposite case: data whose shape genuinely varies row to row, or changes often enough that a migration (Lesson 19) for every new field would be constant churn — a product's attributes (a shirt has size and color, a laptop has RAM and screen size), a webhook's raw payload (Lesson 30), or a user's arbitrary settings blob.

CREATE TABLE products (
  id            bigserial PRIMARY KEY,
  name          text NOT NULL,
  price_cents   integer NOT NULL,
  attributes    jsonb NOT NULL DEFAULT '{}'
);

INSERT INTO products (name, price_cents, attributes) VALUES
  ('T-Shirt', 1999, '{"size": "M", "color": "blue"}'),
  ('Laptop',  129999, '{"ram_gb": 16, "screen_in": 14}');

name and price_cents stay real columns — every product has both, and Lesson 2's reasoning still wins there. Only the genuinely variable part moves into attributes. That split, not an all-or-nothing choice, is the actual skill this lesson teaches.

The frontend equivalent you already own. This is the same instinct as a TypeScript interface with a few required fields plus one metadata: Record<string, unknown> catch-all — the fields every consumer relies on stay typed and named, and the genuinely-varies-per-item data goes in the escape hatch instead of forcing every possible field to exist on every object. JSONB is that escape hatch, enforced by the database instead of a type checker.

2 · JSONB vs. a plain text column: it's actually queryable

Postgres has two JSON types: json stores the exact text you sent, byte for byte; jsonb parses it into a binary form on write. That parse cost buys real capability — jsonb supports operators that reach inside the value without pulling the whole blob into application code and parsing it there:

-- ->> gets a top-level key as text
SELECT name FROM products WHERE attributes ->> 'color' = 'blue';

-- @> checks "does this JSONB contain this JSONB" -- the operator a GIN index speeds up
SELECT name FROM products WHERE attributes @> '{"size": "M"}';

-- an index on the whole column, so @> queries don't scan every row
CREATE INDEX ON products USING GIN (attributes);

Almost nobody reaches for plain json in new code for exactly this reason: it re-parses the text on every single access, and nothing inside it can be indexed the way @> above can. jsonb is the default any current guide recommends unless byte-for-byte input preservation is the actual requirement (rare — auditing raw webhook payloads is one of the few real cases).

3 · What you give up: everything Lesson 2's structure bought you

A JSONB column has no schema Postgres enforces. Nothing stops one row's attributes from having "ram_gb": 16 as a number and another's from having "ram_gb": "16GB" as a string in the same column — a foreign key (Lesson 38), a NOT NULL, a CHECK constraint, none of that reaches inside a JSONB value. A CHECK (attributes ? 'sku') can require a key to exist, but it can't require a specific type or range the way a real column's constraint can. This is the actual trade, stated plainly rather than left implicit: JSONB moves shape enforcement out of the database and into application code, the same "who validates this" question Lesson 17 raised for request bodies — except here the untrusted-shape risk is now sitting in the database itself, not just at the API boundary.

Real columnsJSONB column
Shape enforcementPostgres enforces types, NOT NULL, CHECK, foreign keysNothing enforced inside the value — any shape can be written
When the shape is known and sharedThe right default — every row has the same fieldsForces every consumer to defensively check for missing/wrong-typed keys
When the shape genuinely varies per rowNeeds a migration per new field, or a sparse table of unused columnsNew fields need no migration at all
Querying/filtering by a fieldA plain indexed WHERE, no operators to learnNeeds ->>/@> operators and usually a GIN index to stay fast

The rule of thumb: if you can name the field and every row needs it, it's a column — Lesson 2's rule hasn't changed. Reach for JSONB only for the part that's genuinely per-row-variable, and only after checking whether a join table (also Lesson 2) fits better — a product_attributes table with product_id, key, value rows is fully queryable and indexable with plain SQL, at the cost of being more verbose to read and write than one JSONB blob. JSONB wins when the variation is wide (many different keys across rows) and rarely needs to be queried by individual key; a join table wins when a specific key needs to be filtered, joined, or aggregated on often.

// ProductAttrs is deliberately untyped at the Go layer — attributes vary
// per row, so there's no single struct that fits every product. Callers
// look up only the keys they care about and handle a missing/wrong-typed
// key explicitly, the same defensive shape Lesson 17 taught for any
// untrusted input.
type ProductAttrs map[string]any

type Product struct {
    ID         int64
    Name       string
    PriceCents int64
    Attrs      ProductAttrs
}

// fetchProduct scans the jsonb column straight into a Go map -- pgx/
// encoding/json both do this unmarshal automatically for a []byte/map
// destination, no manual parsing step needed.
func fetchProduct(ctx context.Context, q Querier, id int64) (Product, error) {
    row := q.QueryRow(ctx,
        `SELECT id, name, price_cents, attributes FROM products WHERE id = $1`, id)
    var p Product
    if err := row.Scan(&p.ID, &p.Name, &p.PriceCents, &p.Attrs); err != nil {
        return Product{}, fmt.Errorf("fetch product %d: %w", id, err)
    }
    return p, nil
}

// screenSizeInches reads one specific key defensively -- exactly what
// "nothing enforced inside the value" (section 3) means in application code.
func screenSizeInches(p Product) (float64, bool) {
    v, ok := p.Attrs["screen_in"]
    if !ok {
        return 0, false
    }
    f, ok := v.(float64) // encoding/json decodes every JSON number as float64
    return f, ok
}

Q: "When would you use a JSONB column instead of normal columns?" A strong answer, out loud: "When the shape genuinely varies per row and doesn't share a fixed set of fields — product attributes across totally different categories, or a raw webhook payload I want to keep intact. If every row has the same fields, those stay real columns with real constraints; JSONB gives up type checking, NOT NULL, and foreign keys inside the value, so I'm choosing to push that validation into application code. I'd also check whether a join table fits better first — JSONB wins when I rarely need to filter by a specific inner key, a join table wins when I do." The signal: naming the enforcement trade-off explicitly, not just "JSONB is flexible."
