Retries: exponential backoff and jitter

Lesson 28's circuit breaker named "retry-with-backoff" in passing and moved on. Today's the lesson that was always the other half of that sentence: how a caller should actually retry a failed call — how long to wait, why doubling the wait isn't quite enough, and why every client waiting the exact same amount of time is itself a bug.

1 · The frontend habit, and where it stops being enough

A frontend retry is usually simple: refetch on failure, maybe with a fixed one-second delay, because the assumption is the network hiccuped and the server is fine. Lesson 28 named the case where that assumption breaks — the server side, or a dependency behind it, is genuinely struggling — and built a circuit breaker to stop hammering it. But a circuit breaker only decides whether to call at all. It doesn't decide how a caller should space out the retries it's still allowed to make. That's a separate, smaller decision, and getting it wrong causes real outages on its own.

Not a replacement for Lesson 28, a companion to it: a circuit breaker trips after repeated failures and stops calling entirely for a while. A backoff strategy governs the spacing of the calls made before that threshold is hit. A well-built client caller uses both — backoff between attempts, a breaker as the outer safety net once attempts keep failing.

2 · Fixed-delay retries synchronize into a wave

Picture 500 client instances that all just got the same 503 from an overloaded service, each retrying after exactly one fixed second. All 500 land back on the service at nearly the same instant — a second wave shaped exactly like the first. If the service was struggling under the original load, it now takes a second hit at full force, right as it was trying to recover. This is the actual failure mode retry storm names, and it's why "just retry" is not, by itself, a safe default.

3 · Exponential backoff: wait longer after each failure

exponential backoff fixes the "hit it again immediately" half of the problem: instead of a fixed delay, each retry waits roughly double the previous one (200ms, 400ms, 800ms, 1.6s, capped at some maximum so it doesn't grow forever). A dependency that's down for a few seconds gets far fewer requests during that window than a fixed-delay strategy would send, and a client backs off harder the longer the trouble lasts — matching effort to how bad things actually are.

But doubling alone doesn't fix the synchronization problem from Section 2. If every one of those 500 clients started at the same moment and doubles the same way, they're still all retrying in lockstep — just at 200ms, then 400ms, then 800ms instead of every second. The wave got taller intervals, not less of a wave.

4 · Jitter: make the wave stop being a wave

jitter is the fix: instead of waiting exactly the computed backoff value, each client waits a random amount up to that value. The specific version used below is full jitter — AWS's own backoff writeup (cited below) found it outperforms smaller "add a little randomness" variants, because spreading the wait across the entire range, not just wobbling near the edge, is what actually breaks up the synchronized wave. 500 clients that failed together now retry spread smoothly across the whole window instead of arriving in one spike.

// callWithBackoff retries fn up to maxAttempts times, waiting between
// attempts with exponential backoff (doubling each time) plus full jitter
// (a random value between 0 and the computed delay), and gives up early if
// ctx is cancelled or its deadline passes.
func callWithBackoff(ctx context.Context, maxAttempts int, fn func() error) error {
    base := 200 * time.Millisecond
    cap := 5 * time.Second

    var lastErr error
    for attempt := 0; attempt < maxAttempts; attempt++ {
        lastErr = fn()
        if lastErr == nil {
            return nil // success, stop retrying
        }
        if !retriable(lastErr) {
            return lastErr // don't retry a client error like 400
        }
        if attempt == maxAttempts-1 {
            break // last attempt already used, no point sleeping again
        }

        backoff := time.Duration(math.Min(
            float64(cap),
            float64(base)*math.Pow(2, float64(attempt)),
        ))
        jittered := time.Duration(rand.Int63n(int64(backoff) + 1)) // full jitter: [0, backoff]

        select {
        case <-time.After(jittered):
        case <-ctx.Done():
            return ctx.Err() // caller's deadline won — stop waiting
        }
    }
    return fmt.Errorf("giving up after %d attempts: %w", maxAttempts, lastErr)
}

5 · Not every failure deserves a retry

The retriable check above is doing real work, not boilerplate. A 5xx or a network-level error (connection reset, timeout) might succeed on a second try — the failure could be transient. A 4xx won't: if the server rejected the request because it was malformed or unauthorized, retrying sends the exact same wrong request again and wastes an attempt for nothing. This is the same status-code line Lesson 3 first drew (4xx is the caller's problem, 5xx is the server's) — here it decides which failures are even worth a second attempt.

// retriable reports whether an error is worth retrying at all — a 5xx or a
// network-level failure might succeed next time, but a 4xx won't, since the
// request itself was wrong and retrying just repeats the same mistake.
func retriable(err error) bool {
    var httpErr *statusError
    if errors.As(err, &httpErr) {
        return httpErr.code >= 500
    }
    return true // treat unknown errors (timeouts, connection resets) as worth retrying
}

6 · The piece this whole strategy assumes: Lesson 26

Retries are only safe if the handler tolerates running twice: everything in this lesson controls when a retry happens. It says nothing about what happens if the first attempt actually succeeded on the server side but the response was lost before the client saw it — a client-side timeout doesn't mean the server-side write didn't happen. Retrying blind in that case can double-create. Lesson 26's Idempotency-Key is what makes a retried POST safe rather than merely "spaced out nicely" — backoff and jitter decide the timing; idempotency decides the safety. Both matter together.
