Worker pools: the other way to bound fan-out

Lesson 109 bounded a fan-out loop with a cap at the call site: errgroup.Group.SetLimit or a SemaphoreSlim, one slot acquired per item, released when that item's work finishes. There's a second, older shape for the same problem — a fixed set of long-lived workers that read items off a queue themselves, rather than a cap that stops new launches. Lesson 25 named this shape in passing as Go's "worker pool" and deferred it; today builds it for real, in Go and in C#'s own purpose-built version of the same idea.

1 · Same goal, a different mechanic

Lesson 109's cap and today's pool both answer "how many of these run at once?" — but they get there differently. SetLimit/SemaphoreSlim still launches one task per item; the cap only blocks the next launch once the limit is full, so under the hood the program still creates as many goroutines or Tasks as there are items, just throttled. A worker pool flips that: a small, fixed number of workers are started once, and every item — however many thousands arrive — gets pulled off one shared queue by whichever worker is free next. No per-item goroutine or Task ever gets created; the workers themselves are the only concurrent units that exist for the whole run.

The two shapes suit different inputs. A fixed list of N known calls (Lesson 108's three services) or a one-off burst (Lesson 109's batch) fits a cap just fine — launch, throttle, done. A queue that work keeps arriving on indefinitely — a job table, an incoming request stream, a message broker — fits a worker pool better: the workers just keep running, pulling the next item whenever one appears, with no "loop over N items" to even write.

2 · Go: workers reading off one channel

A Go worker pool is a fixed number of goroutines, each running the same for range loop over one shared channel. The channel itself is what Go calls a queue here — no separate queue data structure is needed, since a channel already serializes handoff between goroutines:

func runWorkerPool(ctx context.Context, jobs <-chan Job, workerCount int) <-chan Result {
    results := make(chan Result)
    done := make(chan struct{})

    for w := 0; w < workerCount; w++ {
        go func() {
            for j := range jobs {          // blocks here until a job arrives or jobs closes
                err := processJob(ctx, j)
                results <- Result{ID: j.ID, Err: err}
            }
            done <- struct{}{}         // this worker drained the queue, signal exit
        }()
    }

    go func() {
        for i := 0; i < workerCount; i++ { <-done }
        close(results)
    }()
    return results
}

Exactly workerCount goroutines exist for the life of this call, no matter whether jobs carries 20 items or 20,000 — each worker's for range jobs simply blocks on an empty channel and wakes up the instant the next item is sent, until the sender calls close(jobs) and every worker's range loop ends on its own. Lesson 11's backpressure shows up here for free: if jobs is an unbuffered or small-buffered channel, a producer sending faster than the pool drains simply blocks on its own send, with no separate throttling code required.

3 · C#: the same shape has a name, Channel<T>

C# doesn't ask you to hand-roll a queue plus a lock the way Go pre-channels did — System.Threading.Channels is the BCL's own purpose-built answer, and Microsoft's own docs describe it plainly: it provides "synchronization data structures for passing data between producers and consumers asynchronously," implementing "the producer/consumer conceptual programming model." A Channel<T> is created once, and a fixed number of consumer Tasks each loop over its Reader, same shape as Go's goroutines over a shared channel:

var jobs = Channel.CreateBounded<Job>(1_000);

var workers = Enumerable.Range(0, workerCount)
    .Select(_ => Task.Run(async () => {
        await foreach (var job in jobs.Reader.ReadAllAsync())
            await ProcessJobAsync(job);
    }))
    .ToArray();

await Task.WhenAll(workers);  // after the producer calls jobs.Writer.Complete()

Fixed number of worker Tasks, same as the fixed goroutine count — the only thing that scales with the number of jobs is how long ReadAllAsync() keeps yielding items, never how many workers exist. Microsoft's own docs confirm ReadAllAsync() is exactly built for this: it "creates an IAsyncEnumerable<T> that enables reading all of the data from the channel," meant to be driven by await foreach until the writer signals it's done.

4 · The one knob Channel<T> has that a bare Go channel doesn't name explicitly

A bounded Go channel just blocks a sender once full — that's the only behavior, full stop. Channel.CreateBounded makes that choice a named, explicit option: BoundedChannelFullMode. Per Microsoft's own table, the default, Wait, matches Go's only behavior verbatim — "calls to WriteAsync wait for space to be available in order to complete the write operation" — but three other values exist precisely because sometimes blocking the producer is the wrong trade-off: DropOldest/DropNewest silently discard a queued item to make room, and DropWrite silently discards the newly written one instead, trading "producer never blocks" for "some items never get processed."

Pick deliberately, not by accident: a job queue that must process every row (an outbox relay, a billing event) belongs on the default Wait — the same guarantee a bounded Go channel gives for free, since it has no drop modes to misconfigure. A live-metrics or position feed, where only the newest reading matters and a stale queued one is actively wrong to keep, is the rare case where DropOldest is the correct choice, not a bug. The trap is reaching for a drop mode out of habit "to be safe against blocking" on a queue where every dropped item is actually lost real work — Go's bounded channel never tempts you into that choice, because it was never offered.

5 · What stays identical to Lesson 109's cap, in both languages

Sizing the pool is the same judgment call Lesson 109 already taught for SetLimit/SemaphoreSlim: too few workers and the queue backs up under load; too many and the downstream dependency the workers call gets hit with more concurrent load than it can take, the exact failure Lesson 109's own opening section described. A worker pool doesn't remove that judgment call — it just changes where the limit lives: not "how many launches are in flight," but "how many workers exist," fixed once at startup either way.

Scope line

This lesson covers the worker-pool shape (a fixed number of long-lived consumers reading off one shared queue) as the alternative to Lesson 109's per-call-site cap, in Go (goroutines over a chan) and C# (System.Threading.Channels' Channel<T>, Channel.CreateBounded/CreateUnbounded, BoundedChannelFullMode).
