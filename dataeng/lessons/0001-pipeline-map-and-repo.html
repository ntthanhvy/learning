3 · Why ELT, not ETL

Older data platforms did ETL: pull data out, transform it in a dedicated processing engine, then load only the finished result. This course does ELT instead: land the raw rows in Postgres exactly as they arrived — messy rows and all — and transform them afterward, in place, using Postgres's own query engine. That's literally what dbt is: SQL SELECTs that run inside the warehouse and materialize their results as new tables or views.

Why this order wins here: the raw layer becomes a permanent, replayable source of truth. If a transformation has a bug, the raw data is still sitting there untouched — rerun the transform, don't re-extract from the source. This is also why Day 3's planted bad rows matter: in ETL they'd get caught (or silently dropped) before landing anywhere; in ELT they land in raw.orders on purpose, and it's dbt's tests, not the loader, that are responsible for catching them.

The raw layer you build today is the foundation everything else in this course sits on top of.

4 · Where each tool actually sits

Three new names, three narrow jobs — depth comes later, but the job of each is fixed from today:

  • dbt transforms. It never extracts and never loads — it only turns raw tables into tested, modeled ones, entirely with SQL that runs inside Postgres.
  • Kafka moves continuously-arriving events (order status changes) from where they happen to the warehouse. It's the only piece in this course that isn't Postgres-shaped — a topic is a log, not a table.
  • Airflow orchestrates. It doesn't transform or move data itself — it runs other things (the loader, dbt build) on a schedule and retries them when they fail.

One-line bridges, so today doesn't re-teach courses you've already done: the Python you'll write below is exactly the Python Intensive language, no new syntax. The idempotent write pattern Day 6's Kafka consumer uses is the same idempotent idea from Backend Foundations's idempotency keys, applied to a consumer instead of an API. And this course never uses pandas — that stays in Data Wrangling; the loader and consumer here are plain Python plus psycopg.

7 · Build: seed the raw schema

Create scripts/generate_raw_data.py with exactly this. It's scaffolding, not the day's skill — read it once so you know what it does, but there are no TODOs here:

"""Seed the raw.* tables in the food-delivery-pipeline warehouse.

Deterministic (fixed seed) so re-running produces the exact same rows --
including the two planted bad rows Day 3's dbt tests are built to catch.
Drops and recreates the `raw` schema each time, so it is always safe to
run again from scratch.
"""
import random
from datetime import datetime, timedelta, timezone

import psycopg

DSN = "postgresql://fdp:fdp_dev_password@localhost:5432/fdp"
SEED = 20260915

CITIES = ["Hanoi", "Ho Chi Minh City", "Da Nang", "Hue"]
CUISINES = ["Vietnamese", "Japanese", "Italian", "Korean", "Fast Food", "Vegetarian"]
VEHICLES = ["motorbike", "bicycle", "car"]


def build_schema(cur):
    cur.execute("DROP SCHEMA IF EXISTS raw CASCADE")
    cur.execute("CREATE SCHEMA raw")
    cur.execute("""
        CREATE TABLE raw.restaurants (
            restaurant_id   INT PRIMARY KEY,
            name            TEXT NOT NULL,
            cuisine         TEXT NOT NULL,
            city            TEXT NOT NULL,
            commission_rate NUMERIC(4,3) NOT NULL,
            updated_at      TIMESTAMPTZ NOT NULL
        )
    """)
    cur.execute("""
        CREATE TABLE raw.couriers (
            courier_id INT PRIMARY KEY,
            vehicle    TEXT NOT NULL,
            city       TEXT NOT NULL,
            joined_at  TIMESTAMPTZ NOT NULL
        )
    """)
    cur.execute("""
        CREATE TABLE raw.orders (
            order_id      INT PRIMARY KEY,
            customer_id   INT NOT NULL,
            restaurant_id INT NOT NULL,
            courier_id    INT NOT NULL,
            subtotal      NUMERIC(10,2) NOT NULL,
            delivery_fee  NUMERIC(10,2) NOT NULL,
            placed_at     TIMESTAMPTZ NOT NULL
        )
    """)
    # Day 5's Kafka consumer is what actually inserts rows here -- Day 1
    # only creates the empty table so the warehouse shape is complete.
    cur.execute("""
        CREATE TABLE raw.order_events (
            event_id    TEXT PRIMARY KEY,
            order_id    INT NOT NULL,
            status      TEXT NOT NULL,
            occurred_at TIMESTAMPTZ NOT NULL
        )
    """)


def seed_restaurants(cur, rng, n=40):
    now = datetime.now(timezone.utc)
    rows = [
        (
            rid,
            f"Restaurant {rid}",
            rng.choice(CUISINES),
            rng.choice(CITIES),
            round(rng.uniform(0.10, 0.25), 3),
            now - timedelta(days=rng.randint(0, 400)),
        )
        for rid in range(1, n + 1)
    ]
    cur.executemany("INSERT INTO raw.restaurants VALUES (%s,%s,%s,%s,%s,%s)", rows)
    return n


def seed_couriers(cur, rng, n=15):
    now = datetime.now(timezone.utc)
    rows = [
        (cid, rng.choice(VEHICLES), rng.choice(CITIES), now - timedelta(days=rng.randint(0, 300)))
        for cid in range(1, n + 1)
    ]
    cur.executemany("INSERT INTO raw.couriers VALUES (%s,%s,%s,%s)", rows)
    return n


def seed_orders(cur, rng, n_restaurants, n_couriers, n=500):
    now = datetime.now(timezone.utc)
    rows = []
    for oid in range(1, n + 1):
        restaurant_id = rng.randint(1, n_restaurants)
        subtotal = round(rng.uniform(3.0, 40.0), 2)

        # Plant a few bad rows on purpose -- Day 3's dbt tests exist to
        # catch exactly these two.
        if oid == 13:
            restaurant_id = 9999  # orphan: no such restaurant
        if oid == 27:
            subtotal = -subtotal  # negative subtotal

        rows.append((
            oid,
            rng.randint(1000, 1999),
            restaurant_id,
            rng.randint(1, n_couriers),
            subtotal,
            round(rng.uniform(0.5, 3.0), 2),
            now - timedelta(hours=rng.randint(0, 24 * 14)),
        ))
    cur.executemany("INSERT INTO raw.orders VALUES (%s,%s,%s,%s,%s,%s,%s)", rows)
    return n


def main():
    rng = random.Random(SEED)
    with psycopg.connect(DSN, autocommit=True) as conn:
        with conn.cursor() as cur:
            build_schema(cur)
            n_r = seed_restaurants(cur, rng)
            n_c = seed_couriers(cur, rng)
            n_o = seed_orders(cur, rng, n_r, n_c)
            print(f"raw.restaurants: {n_r}")
            print(f"raw.couriers:    {n_c}")
            print(
                f"raw.orders:      {n_o}  "
                "(2 bad rows planted: order 13 orphan restaurant_id, order 27 negative subtotal)"
            )


if __name__ == "__main__":
    main()

Run it (no project setup needed — uv run --with installs psycopg on the fly for this one command):

uv run --with "psycopg[binary]" python3 scripts/generate_raw_data.py

Expected output, exactly:

----------+---------------+----------
       13 |          9999 |     9.32

(2 rows)

(Your own subtotal values will match exactly, since the seed is fixed — restaurant_id 9999 and the negative number are the two intentional breaks, not bugs.)

Re-run the seed script once more — same output both times is the point: a script you can re-run without fear is what "safe to re-run" (Day 7's Airflow requirement) actually means in practice.

Q: "Walk me through this pipeline's architecture." A strong answer, out loud: "It's ELT, not ETL — raw restaurant, courier and order data lands in Postgres untransformed, either by batch script or, for order status events, through Kafka. dbt then transforms that raw layer into tested staging models and marts entirely with SQL running inside the warehouse. Airflow's only job is orchestration: it runs the loader and dbt build on a schedule and retries on failure. Nothing here is a general-purpose ETL engine — each tool does exactly one job, and Postgres is where the actual transformation compute happens." The signal: naming what each tool does not do is as important as what it does — that's what shows you understand the boundaries, not just the buzzwords.
