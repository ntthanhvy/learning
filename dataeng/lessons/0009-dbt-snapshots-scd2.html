1 · The problem: raw.restaurants only ever shows "now"

raw.restaurants.commission_rate is a single column with a single value per restaurant. Every dbt model you've built so far — stg_restaurants, dim_restaurants, int_orders_joined — reads that column and gets whatever it currently is. That's fine for "what's this restaurant's rate today," and wrong for anything that asks about the past: if a restaurant renegotiated its rate from 15% to 12% last month, every one of this course's marts would silently apply 12% to an order placed back when the real rate was 15%. fct_orders would still show the right order_total, but any commission-revenue number derived from multiplying order_total by today's rate would be wrong for every historical order — not a crash, not a failing test, just a quietly incorrect number that would only get caught (if it ever did) by someone reconciling against an old invoice.

This is a data-warehousing problem old enough to have a name from the Kimball Group's own dimensional-modelling vocabulary, cited in RESOURCES.md as this course's primary source for facts, dimensions and grain: a slowly changing dimension (SCD). raw.restaurants as it stands is what Kimball calls SCD Type 1 — every update overwrites the old value, no history kept. Today's fix is SCD Type 2: keep every value a column has ever had, each stamped with the window of time it was actually true for.

2 · dbt's tool for this: snapshots

dbt's Snapshots feature (cited in RESOURCES.md, today's primary source) implements SCD Type 2 directly: point it at a source or model that changes over time, and on every dbt snapshot run it compares the current row to what it already recorded, and if the value changed, it closes out the old row and inserts a new one — never updating a row in place, only ever appending. Two columns dbt adds automatically make the history queryable:

ColumnMeaning
dbt_valid_fromthe timestamp this version of the row started being true
dbt_valid_tothe timestamp it stopped being true — null for the row that is still current

A snapshot needs a snapshot strategy to decide "did this row change": timestamp trusts a column like updated_at and treats any change to it as a new version; check instead compares a named list of columns directly, useful when no reliable updated_at exists. raw.restaurants already has updated_at (per PLAN.md's domain table), so today uses timestamp — cheaper to evaluate and exactly the case that column exists for.

3 · Build: snapshots/restaurants_snapshot.sql

Snapshots live in their own top-level snapshots/ folder, declared in dbt_project.yml's snapshot-paths — sibling to models/, not inside it, because a snapshot isn't a transformation of existing data the way a model is; it's the thing recording history that models will later read. Give this one in full, since the syntax itself (the {% snapshot %} block, the config() keys) is new today and isn't the day's actual skill:

-- snapshots/restaurants_snapshot.sql
{% snapshot restaurants_snapshot %}

{{
    config(
        target_schema='dbt_dev_snapshots',
        unique_key='restaurant_id',
        strategy='timestamp',
        updated_at='updated_at',
    )
}}

select
    restaurant_id,
    name,
    cuisine,
    city,
    commission_rate,
    updated_at
from {{ source('raw', 'restaurants') }}

{% endsnapshot %}

unique_key here means the same thing it meant for Day 4's incremental fct_orders: the column identifying "which real-world row is this a version of," so dbt knows to close out restaurant 7's old row rather than confusing it with restaurant 12's. target_schema puts the snapshot table somewhere separate from dbt_dev's regular models — snapshot tables aren't staging or marts, they're their own thing, and a distinct schema keeps that visible in psql.

Run it with its own command, not dbt build — snapshots are invoked separately from models and tests:

uv run --project ../dbt_env dbt snapshot

Expected, on the very first run — every restaurant gets exactly one row, all with the same dbt_valid_from (whenever you ran this) and a null dbt_valid_to, since nothing has changed yet from dbt's point of view:

1 of 1 START snapshot dbt_dev_snapshots.restaurants_snapshot .. [RUN]
1 of 1 OK snapshot dbt_dev_snapshots.restaurants_snapshot ...... [INSERT 0 40 in 0.08s]

Done. PASS=1 WARN=0 ERROR=0 SKIP=0 TOTAL=1

Now simulate the actual scenario this whole lesson is about — a restaurant renegotiating its rate. Pick one restaurant and update it directly in raw.restaurants (a one-time manual step to prove the mechanism, the same kind of hand-edit Day 3 used to fix the two planted bad rows, not the normal pattern going forward):

docker compose exec -T postgres psql -U fdp -d fdp -c \
  "UPDATE raw.restaurants SET commission_rate = 0.12, updated_at = now()
   WHERE restaurant_id = 7;"

Run dbt snapshot again. Because restaurant 7's updated_at moved forward, the timestamp strategy detects a change: it closes out restaurant 7's original row (dbt_valid_to now set to this run's timestamp) and inserts a brand-new row for restaurant 7 with the new commission_rate and a null dbt_valid_to. Every other restaurant is untouched:

1 of 1 OK snapshot dbt_dev_snapshots.restaurants_snapshot ...... [INSERT 0 1 in 0.06s]
docker compose exec -T postgres psql -U fdp -d fdp -c \
  "SELECT restaurant_id, commission_rate, dbt_valid_from, dbt_valid_to
   FROM dbt_dev_snapshots.restaurants_snapshot
   WHERE restaurant_id = 7 ORDER BY dbt_valid_from;"
 restaurant_id | commission_rate |       dbt_valid_from       |        dbt_valid_to
---------------+------------------+-----------------------------+-----------------------------
             7 |             0.15 | 2026-09-15 09:03:11.20+00   | 2026-09-23 06:00:04.51+00
             7 |             0.12 | 2026-09-23 06:00:04.51+00   |
(2 rows)

Two rows for one restaurant, each true for a different window — the old 0.15 rate valid from Day 1's seed until the moment you ran today's second snapshot, and the new 0.12 rate valid from that moment on, with dbt_valid_to left null because it's still current. This table now has exactly what a Type-1 raw.restaurants can never give you: the ability to ask "what rate was true on some specific past date."

4 · Build: join a fact to the version valid at order time — fct_orders_with_commission

Now the actual skill. fct_orders has one row per order with its own placed_at. restaurants_snapshot has one row per version of a restaurant, each with a [dbt_valid_from, dbt_valid_to) window. Joining them correctly means matching each order not just on restaurant_id, but on placed_at falling inside that specific version's window — a point-in-time join, not the plain equi-join every prior mart in this course has used:

-- models/marts/fct_orders_with_commission.sql -- TODO: write the join
-- Select order_id, restaurant_id, placed_at, order_total from fct_orders,
-- and commission_rate from restaurants_snapshot (ref it like any other
-- model -- a snapshot is just another node dbt's DAG can depend on).
-- The join must match on restaurant_id AND on placed_at falling inside
-- the snapshot row's [dbt_valid_from, dbt_valid_to) window. Remember
-- dbt_valid_to is null for the row that is still current -- your
-- condition must still match that row for orders placed after the last
-- change, or every recent order will silently get no match at all.
-- Add a derived column, commission_amount, as order_total * commission_rate.

Two things worth getting right before you write it: first, {{ ref('restaurants_snapshot') }} is the correct way to read a snapshot from a model — dbt treats a snapshot as a node in the same DAG as everything else, exactly like Day 2's ref() between staging models, not a special separate mechanism. Second, the boundary condition: a naive placed_at < dbt_valid_to comparison quietly drops every order placed after the most recent change, because that row's dbt_valid_to is null and comparing anything to null is never true in SQL — the fix is an explicit or dbt_valid_to is null alongside it, the same "don't forget the open-ended case" instinct Day 4's zero-order-restaurant left join already asked for.

One thing to say out loud about cost: a snapshot only records history from the moment you start running it — running dbt snapshot for the first time today does not retroactively know what commission_rate was a year ago if it changed before today. History starts accruing the day the snapshot starts running, which is exactly why Day 1's seed script back-dated raw.restaurants.updated_at for every restaurant, giving today's very first snapshot run a believable-looking starting dbt_valid_from instead of "the moment this lesson happened to run."

Q: "How would you track a slowly changing dimension in dbt, and why not just let the column update in place?" A strong answer, out loud: "Updating a column in place is SCD Type 1 — you lose the old value the moment it changes, which is fine for a typo fix but wrong for anything like a commission rate or a price that's genuinely different at different points in time. dbt's snapshot feature implements SCD Type 2: instead of updating a row, it closes out the old version with a dbt_valid_to timestamp and inserts a new one with a fresh dbt_valid_from, so every version that ever existed stays queryable. The strategy is either timestamp, comparing an updated_at column, or check, comparing a list of columns directly when there's no reliable timestamp. The payoff only shows up once something downstream needs to ask 'what was true back then' — in my project, joining orders to the restaurant's commission rate at the time each order was placed, not whatever the rate is today, which needs a point-in-time join on the validity window instead of a plain equi-join." The signal: naming Type 1 vs. Type 2 explicitly, and knowing the join needs the validity window, not just the foreign key.
