pd.date_range(): building the calendar grid, instead of trusting the one you were sent

Lesson 97 closed the last of three carried-forward candidates, leaving no standing pick — this round ran its own fresh curriculum/glossary scan from scratch. Datetime itself is well covered (Lessons 32's .dt accessor, 38's resample(), 58's merge_asof(), 59's to_period(), 71's Grouper(), 81's to_datetime(format=), 94's first_valid_index()), but one function those lessons all quietly leaned on as test-data setup was never itself the subject of a lesson: pd.date_range(). A genuine gap, and a common one — the SQL cousin, generate_series() over a date range, is a frequent interview pattern for "find the missing days."

1 · Four knobs, exactly three required

pd.date_range() is pandas' calendar-grid builder — the direct equivalent of writing out a SQL generate_series(start, end, interval) yourself instead of trusting whatever dates happen to already be in a table. Confirmed directly (pandas 3.0.6):

import pandas as pd
pd.date_range("2026-01-01", periods=5, freq="D")
# DatetimeIndex(['2026-01-01', '2026-01-02', '2026-01-03',
#                '2026-01-04', '2026-01-05'], dtype='datetime64[ns]', freq='D')

pd.date_range("2026-01-01", "2026-01-10", freq="3D")
# every 3rd day between the two dates:
# ['2026-01-01', '2026-01-04', '2026-01-07', '2026-01-10']

Only start/end/periods/freq exist, and the function needs exactly three of them live to pin the grid down — confirmed directly, both too few and too many raise the identical message:

pd.date_range("2026-01-01")  # only 1 given
# ValueError: Of the four parameters: start, end, periods, and
# freq, exactly three must be specified

pd.date_range("2026-01-01", "2026-01-10", periods=5, freq="D")  # all 4 given
# ValueError: Of the four parameters... exactly three must be specified

The official docs phrase the rule more loosely — "a maximum of three can be specified at once," plus "at least two of start, end, periods" separately. Confirmed directly, the sharper, simpler way to say it in practice: give any two of start/end/periods, and leave freq out — it quietly defaults to "D" (daily), which is why that case doesn't look like "three" but passes anyway:

pd.date_range("2026-01-01", "2026-01-05")  # no freq/periods -- defaults to daily
# ['2026-01-01', '2026-01-02', '2026-01-03', '2026-01-04', '2026-01-05']

2 · freq= strings changed under pandas 3.0 — old aliases now raise

Confirmed directly: the single-letter month/hour aliases long used in older pandas code and tutorials are gone as of pandas 3.0, not merely deprecated — they now raise ValueError outright, the same removed-not-deprecated pattern as Lesson 45's fillna(method=):

pd.date_range("2026-01-01", periods=3, freq="M")
# ValueError: 'M' is no longer supported for offsets.
# Please use 'ME' instead.

pd.date_range("2026-01-01", periods=3, freq="H")
# ValueError: Invalid frequency: H ... Did you mean h?

pd.date_range("2026-01-01", periods=3, freq="ME")  # month-END, current spelling
# ['2026-01-31', '2026-02-28', '2026-03-31']

pd.date_range("2026-01-01", periods=3, freq="B")  # business day -- still valid, unchanged
# ['2026-01-01', '2026-01-02', '2026-01-05']  -- Sat/Sun 1/3-1/4 skipped

Code copied from an older tutorial that still says freq="M" or freq="H" will crash on current pandas, not silently misbehave — the interview-safe habit is naming the current alias ("ME", "h", "D", "B") out loud rather than the one half-remembered from older material.

3 · The real ETL use: finding the missing days a sparse table hides

The practical reason this function earns its own lesson: a feed is rarely sent with every calendar day already present — rows just silently don't exist for the days with no activity. date_range() is how you build the true calendar grid and expose those gaps instead of pretending they don't exist, using Lesson 47's reindex():

sparse = pd.Series(
    [10, 20, 30],
    index=pd.to_datetime(["2026-01-01", "2026-01-03", "2026-01-05"]),
)
full_grid = pd.date_range(sparse.index.min(), sparse.index.max(), freq="D")
sparse.reindex(full_grid)
# 2026-01-01    10.0
# 2026-01-02     NaN   -- a real missing day, now visible
# 2026-01-03    20.0
# 2026-01-04     NaN   -- another real missing day
# 2026-01-05    30.0
# Freq: D, dtype: float64

Without building full_grid first, the sparse Series simply looks complete — three rows, no NaN anywhere, no sign that two days never arrived at all.

Q: "How would you find which days are missing from a sparse time-series table?" A strong answer, out loud: "Build the real calendar with pd.date_range() from the table's own min and max date, then reindex() the table onto that full range. Any day the original table didn't have becomes NaN after the reindex, so isna() on that result tells me exactly which days are missing — the table on its own never reveals that, since a missing day just isn't a row, there's nothing to flag." The signal: naming date_range() plus reindex() together, not date_range() alone — generating the grid is only half the pattern.
