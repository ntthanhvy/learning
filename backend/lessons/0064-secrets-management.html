Secrets management: the credential that isn't a password

Lesson 21 drew one line already: config belongs in the environment, not in code. A database password, an API key, a signing key are all "config" by that definition — but they're a special kind, one that leaks catastrophically if handled the same casual way as a timeout value or a feature flag. Lessons 21 and 31 both touched this in passing, pointing at ".env files" and "rotate it" without ever naming the machinery underneath. Today names it.

1 · Why a secret is not just another config value

A secret is any credential where possession equals power: a database password lets you read every row; an API key lets you spend someone else's account limit or send email as their domain; a signing key lets you mint tokens indistinguishable from the real ones Lesson 48 and Lesson 62 already covered. A wrong port number in config causes a bug. A leaked secret causes an incident — data exfiltration, spend fraud, or forged authentication — often silently, discovered only after damage. That asymmetry is the whole reason secrets get their own handling, separate from ordinary environment variables.

The most common real-world leak path isn't a sophisticated attack — it's a secret committed straight into git history, pasted into a Slack message, or printed to a log line by an over-eager fmt.Printf("config: %+v", cfg) during debugging. Every technique below exists to make that class of mistake structurally harder, not just discouraged by policy.

2 · Baseline: environment variables are necessary but not sufficient

Lesson 21 already established that a secret's value should live in the environment, never hardcoded in a source file. That's still true and still the floor, not the ceiling. Plain environment variables have real limits once a team and its footprint grow: anyone with read access to the deploy config can see the raw value forever; there's no audit trail of who read it or when; rotating a leaked key means manually finding and updating it everywhere it was pasted; and a .env file sitting in a repo (even a "private" one) is one misconfigured .gitignore away from being committed. None of that is a flaw in environment variables themselves — it's what's missing once you need more than "keep it out of the source file."

3 · The secrets manager: one system of record, not N copies

A secrets manager flips the model: instead of every service's deploy config holding its own copy of a database password, each service asks the secrets manager for it at startup (or on demand), over an authenticated call, and the manager decides whether that specific caller is allowed to have it. The value is stored in exactly one place instead of N copies scattered across config files, CI variables, and someone's laptop `.env`. Two things fall out of that centralization almost for free: an audit log of every access (who or what read this secret, and when), and the ability to revoke or rotate a value in one place and have every dependent service pick up the new one, instead of hunting down every file that pasted the old one.

Not magic, just indirection: a secrets manager doesn't make the underlying credential any less powerful if leaked — it reduces how many places a copy of it can leak from, and adds a record of who touched it. The database password is still a database password.

4 · Rotation: a secret is safest with a short, enforced lifetime

Rotation is the answer to a question every secret eventually faces: what happens if this already leaked and nobody noticed? A secret that never changes is a secret whose blast radius, once leaked, lasts forever — the exact failure mode Lesson 48 named for passwords and Lesson 62 named for long-lived access tokens, generalized to every kind of credential a backend holds. Rotating on a schedule (say, database credentials every 30-90 days) bounds that window even when a leak is never detected: an old, stolen copy simply stops working at the next rotation, without anyone needing to know it was ever stolen in the first place.

The operational catch is that rotation must not cause an outage the instant the old value stops working. The standard fix is a brief overlap window where both the old and new value are valid at once — the secrets manager issues the new credential, every service picks it up on its own schedule (a periodic refresh, or a restart), and only once nothing is still using the old one does it actually get revoked. Rotating a secret and revoking the old value in the same instant is how a routine rotation turns into a self-inflicted incident.

5 · Least privilege applies to secrets too

The same least privilege principle Lesson 12's authorization lesson applied to users applies just as directly to services: the order service should hold a database credential scoped to the orders schema, not a superuser password that happens to also work against the payments schema. One shared "god" credential used everywhere is convenient right up until one service is compromised — at which point the attacker has everything, because the credential itself never distinguished between services. Scoping credentials narrowly means a single compromised service leaks only what that service could already touch, not the whole system.

6 · What this looks like day to day

// Bad: secret value baked into a struct literal, now permanently in git history
var cfg = Config{
    DBPassword: "hunter2-prod-final", // visible to anyone who can read this file, forever
}

// Better: read from the environment at startup (Lesson 21's floor)
var cfg = Config{
    DBPassword: os.Getenv("DB_PASSWORD"),
}

// Better still: fetch from a secrets manager, short-lived, auditable, rotatable
func loadDBPassword(ctx context.Context, sm SecretsClient) (string, error) {
    return sm.GetSecret(ctx, "prod/orders-service/db-password")
}

The middle version is a legitimate stopping point for a small system — it's exactly what Lesson 21 recommended, and it's a real improvement over the first line. The third version is what "the pace can deepen" looks like once a system has enough services, enough people, and enough blast radius that "grep the deploy config" is no longer an acceptable way to find out who has a credential.

Q: "How would you handle the database credentials for a new service?" A strong answer, out loud: "At minimum, the password comes from the environment, never hardcoded — that's non-negotiable regardless of scale. If the team already runs a secrets manager, I'd fetch it from there instead, scoped to only what this service needs, not a shared superuser credential. I'd also want it on a rotation schedule with an overlap window, so a leak that goes undetected still has a bounded lifetime instead of being valid forever. The goal isn't paranoia — it's making sure a single leaked value, or a single compromised service, doesn't hand over more than that one service ever needed." The signal: naming the environment-variable floor without treating it as the ceiling, and connecting rotation and least privilege back to bounding blast radius rather than reciting tool names.
