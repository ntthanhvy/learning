Advisory locks: coordinating processes without a new row

"Distributed locks" has been this course's own standing out-of-scope teaser for 25+ rounds — real distributed coordination (Redis/Zookeeper/etcd-based) is beyond MISSION.md's single-instance scope. But the actual question behind that teaser usually isn't distributed at all: "how do I stop two of my own processes from doing the same thing at once?" Postgres already answers that, in-scope, with a lock that isn't attached to any row.

1 · The problem Lessons 6 and 33 don't quite cover

Lesson 6's row lock (SELECT ... FOR UPDATE) and Lesson 33's optimistic version column both protect a specific row someone is about to write. But plenty of coordination problems have no row to lock at all: "only one instance should run the nightly cleanup job," "don't let two workers pick up the same un-rowed batch of work at once," "run this migration step exactly once even if three instances start up simultaneously." There's nothing to SELECT ... FOR UPDATE — the thing being protected is a piece of logic, not a database record.

Frontend-habit trap: the instinct is often "add a jobs table with an is_running boolean and check it first" — but that's a fresh check-then-act race of its own (Lesson 6's exact bug), now one level up: two instances can both read is_running = false before either writes true. Coordinating processes with an ordinary row needs the same atomic-check discipline the row itself was supposed to provide.

2 · Advisory locks: a lock keyed by a number, not a row

An advisory lock is Postgres's answer: a lock keyed by an integer the application chooses, with no row, no table, and no data behind it at all — the "resource" being locked is whatever meaning the application assigns to that number. Postgres just tracks, for each key, whether it's currently held and by whom; every session in the same database can ask about the same key and get a consistent answer, which is exactly the coordination signal "only one of us do this" needs.

-- pick any bigint as the lock key -- often a hash of a string like 'nightly-cleanup'
SELECT pg_try_advisory_lock(hashtext('nightly-cleanup')::bigint);
-- true  = lock acquired, this session is the one that should run the job
-- false = someone else already holds it, this session should skip and exit

pg_try_advisory_lock never blocks — it returns immediately with true or false, which is the shape almost every real "only one of us should do this" scenario wants: a losing instance doesn't wait around, it just skips this run and tries again next cycle. Postgres also offers pg_advisory_lock (blocks until the key is free) for the rarer case where waiting is actually the right behavior.

3 · Session-level vs. transaction-level: the detail that causes real bugs

An advisory lock comes in two lifetimes, and picking the wrong one is the single most common mistake with this feature. A session-level lock (pg_advisory_lock / pg_try_advisory_lock) stays held until the session explicitly releases it with pg_advisory_unlock or the connection closes — it survives across multiple transactions on that connection. A transaction-level lock (pg_advisory_xact_lock) is released automatically the instant the current transaction commits or rolls back, with no unlock call needed at all.

-- transaction-scoped: released automatically at COMMIT/ROLLBACK, nothing to forget
BEGIN;
SELECT pg_try_advisory_xact_lock(hashtext('nightly-cleanup')::bigint);
-- ... do the guarded work inside this same transaction ...
COMMIT; -- lock released here, automatically

Session-level locks are the sharper tool but the one that leaks: since they live on the pooled connection (Lesson 18) rather than the transaction, returning that connection to the pool without calling pg_advisory_unlock leaves the lock held indefinitely — the next request that happens to borrow the same pooled connection inherits a lock it never asked for, and every other session trying that key gets stuck behind a lock nobody remembers taking. The transaction-scoped variant exists specifically to make that mistake impossible: there's no unlock call to forget, because commit or rollback always releases it.

4 · A Go worker using it to avoid double-running a job

This is the shape Lesson 10's background-jobs lesson left implicit: at-least-once delivery means a job handler must tolerate running twice, but for something like a scheduled cleanup, the cleaner fix is often just making sure only one instance starts it in the first place.

// runNightlyCleanup only proceeds if this instance wins the advisory lock for
// this named job -- every other instance's attempt returns false and exits
// immediately instead of doing (or waiting to do) the same work twice.
func runNightlyCleanup(ctx context.Context, db *pgxpool.Pool) error {
    const jobName = "nightly-cleanup"
    var acquired bool
    err := db.QueryRow(ctx,
        `SELECT pg_try_advisory_lock(hashtext($1)::bigint)`, jobName,
    ).Scan(&acquired)
    if err != nil {
        return err
    }
    if !acquired {
        return nil // another instance already has it -- skip this run, not an error
    }
    defer db.Exec(ctx, `SELECT pg_advisory_unlock(hashtext($1)::bigint)`, jobName)

    return doCleanup(ctx, db)
}

Notice this snippet uses the session-level pair deliberately, with an explicit defer unlock right next to the acquire — the discipline Section 3 named, made concrete: the unlock call exists in the same breath as the lock call, so it can't be forgotten later. A version scoped to one transaction (pg_try_advisory_xact_lock wrapped in a BEGIN/COMMIT) would drop the defer entirely and rely on the transaction's own end instead — the safer default whenever the guarded work naturally fits inside one transaction.

Q: "Three instances of your service start up at the same time and each tries to run a one-time migration step. How do you make sure it only runs once?" A strong answer, out loud: "A jobs table with an is_running flag has the same check-then-act race Lesson 6 covers — two instances can both read false before either writes true. I'd use a Postgres advisory lock instead: each instance calls pg_try_advisory_lock with the same key on startup. Exactly one gets true and runs the migration step; the other two get false and skip it immediately, no waiting, no extra table. If the guarded work fits inside one transaction, I'd reach for the transaction-scoped variant instead, so there's no explicit unlock call to forget." The subtext: naming the row-based alternative's exact failure mode, and knowing the two lock lifetimes are a real choice, not an implementation detail.

5 · Why this isn't the "distributed lock" this course kept deferring

This is genuinely narrower than what "distributed lock" usually means, and worth being precise about the difference rather than quietly renaming the same thing. An advisory lock only coordinates sessions connected to the same Postgres instance — it says nothing about, and doesn't help with, coordination across multiple independent databases or services with no shared Postgres to ask. That broader problem — consensus across genuinely separate systems, the Redis/Zookeeper/etcd territory this course's teasers have named since Lesson 30 — stays out of scope per MISSION.md's distributed-systems exclusion. What today closes out is the much more common version of that question a single-instance Postgres-backed service actually has: "stop two of my own processes, that already share one database, from doing the same thing at once" — narrowed to exactly the vocabulary level MISSION.md allows, using a mechanism this course's own stack already ships.
