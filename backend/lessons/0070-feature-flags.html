Feature flags: separating "deployed" from "on"

Lesson 19 walked through expand/deploy/backfill/contract because a migration and a rolling deploy can't be trusted to land at the same instant. Lesson 21 mentioned "a feature flag" once, in passing, next to a timeout value, without ever naming what it actually is. Lesson 68 built the error budget for deciding whether to ship something risky. None of that closes the actual gap: the one mechanism that makes "ship the code" and "turn the feature on" two separate, independently reversible decisions.

1 · The habit a frontend dev already half-has, named properly

A conditional render behind a boolean prop — {isBetaUser && <NewCheckout />} — is a feature flag's shape already sitting in frontend muscle memory. The backend version does the same job for a handler instead of a component: a runtime check that decides which code path actually runs, read from somewhere other than the code itself. A feature flag is exactly that check, formalized: a name, a boolean or a small set of values, read from config or a database row rather than hardcoded, gating whether new code executes for a given request.

The point isn't the if statement — every team already has those. It's what the flag buys structurally: deploying code and releasing a feature become two different events. Lesson 19's whole four-step dance existed because a schema change and a rolling deploy can't be trusted to land at the same instant across every instance. A feature flag sidesteps that class of problem for application logic entirely — the new code can sit deployed, disabled, on every instance for days, and "turning it on" becomes a config change, not a deploy, with no rollout window where some instances have the behavior and others don't.

2 · What actually reads the flag, and where the value lives

// A minimal flag check -- the interface every richer flag system
// (LaunchDarkly, Unleash, a home-grown table) still boils down to.
type FlagSource interface {
    // Enabled reports whether flagName is on for this specific request's
    // context (user id, cohort) -- not just globally on or off.
    Enabled(ctx context.Context, flagName string, userID string) bool
}

func checkoutHandler(w http.ResponseWriter, r *http.Request, flags FlagSource) {
    userID := userIDFromContext(r.Context())
    if flags.Enabled(r.Context(), "new-checkout-flow", userID) {
        runNewCheckout(w, r)
        return
    }
    runLegacyCheckout(w, r)
}

Two design choices matter more than the syntax. First, Enabled takes a userID, not just a flag name — a real flag system decides per request, not once at process start, which is what makes a percentage rollout possible at all (below). Second, the flag's value lives outside the binary: a database row, a small managed service, a config file re-read on an interval — anything an operator can change without asking Go to recompile and every instance to restart. A constant declared in code that a deploy still has to ship is not a feature flag; it's just an early return with extra ceremony.

3 · Percentage rollout: the same idea Lesson 69 taught for traffic, aimed at risk instead

The plainest flag is all-or-nothing: every user gets the old path, or every user gets the new one. A percentage rollout sits between those two extremes: enable the new path for, say, 5% of users, watch error rates and latency, then widen to 25%, then 100% — the same instinct Lesson 69's weighted load balancing applied to traffic capacity, now applied to blast radius instead. The 5% isn't picked per request at random, either; it's usually a hash of a stable id (the user id) reduced mod 100, so the same user consistently lands on the same side of the flag across requests instead of flickering between old and new checkout mid-session.

This is a deploy-time risk knob, not a runtime defense. Lesson 28's circuit breaker trips itself, automatically, the instant a dependency's failure count crosses a threshold — no human in the loop, reacting in milliseconds. A feature flag's rollout percentage only moves because an engineer watching a dashboard decided to move it. They can work together (a canary release watching error rates before widening a flag) but a flag is not a substitute for a breaker, and a breaker doesn't decouple deploy from release the way a flag does.

4 · The kill switch: a flag whose whole job is going backwards fast

Flip the percentage-rollout framing around and there's a second, distinct use: a kill switch is a flag whose sole purpose is turning something off immediately, in production, without a deploy. This is where Lesson 68's material comes back directly: an on-call engineer who's just paged for a bad deploy has, in order of speed, three options — revert the deploy (minutes, needs CI), roll back a migration (Lesson 19's contract step made this safe, but it's still not instant), or flip a kill switch (seconds, a config write). A kill switch is deliberately built and wired up before the incident it might be needed for, the same "written calmly in advance" spirit as Lesson 68's runbook — the worst time to add a kill switch to a risky code path is during the incident that just proved you needed one.

Circuit breaker (Lesson 28)Kill switch (today)
Who flips itthe code itself, automaticallya human, deliberately
Triggera counted run of consecutive failuresa judgment call during an incident
Scopeone dependency's outbound callsany code path a team chose to wire one to
Resetson its own, via the half-open probeonly when a human flips it back

5 · Flag debt: the cost that shows up in review, not at runtime

A flag that's been at 100% for two months and never removed is a specific, recognizable form of decay: the if branch is still there, the old path is still there, and every future reader has to hold both in their head to know which one actually runs — a permanent scar in the code, similar in shape to Lesson 34's soft-delete row that never gets purged, except here it's a live branch, not a dead row. This is exactly the kind of thing Lesson 14's PR-review lens should catch and usually doesn't, because "add a flag" reads as a small, safe diff and "the flag from three months ago is still here" is nobody's diff at all — it's not new work, so it never shows up for review on its own. A team that treats flag removal as a real, trackable follow-up (not "someday") is the difference between flags as a temporary safety mechanism and flags as permanent, silently multiplying branches no test suite fully covers.

Q: "How would you ship a risky change to a high-traffic checkout flow?" A strong answer, out loud: "I'd put the new logic behind a feature flag rather than shipping it live on merge — that separates deploying the code from releasing the feature, so the rollout isn't tied to a deploy window at all. I'd start it at a small percentage, hashed on user id so the same user doesn't flip back and forth between old and new mid-session, and widen it as error rates and latency stay clean. I'd also wire up a kill switch on the new path specifically, before enabling it, not after — if something goes wrong at 2am, flipping a flag is a config write that takes seconds, versus reverting a deploy or rolling back a migration, which both take longer. And I'd put a concrete date or trigger on removing the flag once it's fully rolled out, since an old flag nobody removes is just permanent branching complexity with no test coverage guarantee." The signal: naming deploy/release decoupling as the actual point, distinguishing a kill switch's human trigger from a circuit breaker's automatic one, and treating flag removal as real, trackable work instead of an afterthought.
