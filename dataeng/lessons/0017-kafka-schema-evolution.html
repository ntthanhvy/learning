Schema evolution: why JSON-without-a-schema bites

1 · The question every producer eventually asks: can I change the shape?

Every order_events message since Day 5 has had exactly four fields: event_id, order_id, status, occurred_at. Today the business wants a fifth — which channel the order came through, app or web — because a product question just came up that the current data can't answer. This is an ordinary, permanent fact about any event stream that outlives a single producer deploy: the shape of the message changes, but the topic doesn't get rewritten. Every message already sitting in order_events from Days 5, 6 and 16's runs has only four fields, forever. Only messages produced after today's change will have five.

A relational table has a schema Postgres enforces on every row, every time — ALTER TABLE is the one place shape changes happen, and every row obeys it from then on. A Kafka topic enforces nothing at all about message shape by default: it's an append-only log of bytes, and order_events happens to carry JSON today only because Day 5's producer chose json.dumps(). Nothing stops tomorrow's producer from writing a message missing a field, renaming one, or changing a type — and nothing tells today's consumer that happened until it crashes on a field that isn't there.

2 · Two kinds of change: one is safe, one isn't

Not every shape change is equally dangerous. The distinction that matters is whether a reader written against the old shape can still make sense of a message in the new shape, and vice versa:

ChangeOld consumer reads a new messageNew consumer reads an old message
Add an optional field with a sensible default (today's channel)Fine — old consumer code never looks for the new key, ignores itFine, if the new consumer treats a missing key as "use the default" rather than a required field
Rename a field (e.g. status → order_status)Breaks — old consumer looks for a key that's goneBreaks the other direction too — nothing links the old and new names
Change a field's type (e.g. order_id int → string)Breaks — old consumer's parsing/comparison logic assumed a type that's goneBreaks — same problem, reversed

The first row is called a backward-compatible change: new data doesn't break old readers. Renaming and retyping a field are neither backward- nor forward-compatible — they break readers on both sides of the change, which is exactly why they're the two moves to avoid on a live topic, not just today's moves to avoid.

3 · Build: add channel the backward-compatible way

Add one key to make_event() in scripts/produce_order_events.py — the rest of the file, including Day 16's idempotence config, is unchanged:

# scripts/produce_order_events.py -- make_event() grows one new field
def make_event(order_id: int, status: str) -> dict:
    return {
        "event_id": str(uuid.uuid4()),
        "order_id": order_id,
        "status": status,
        "occurred_at": datetime.now(timezone.utc).isoformat(),
        "channel": "app",
    }

That alone is a trap half-finished: every message produced from now on has channel, but Day 6's consumer still reads event["channel"]-style dict access nowhere — it only ever reads fields it explicitly listed in its INSERT. The real risk is the opposite direction, and it's easy to miss: once raw.order_events gets a channel column and the consumer's INSERT expects a channel key on every event dict, what happens when it reads one of the dozens of four-field messages Days 5, 6 and 16 already wrote into the topic? Plain dict indexing — event["channel"] — raises KeyError the instant it hits the first old message, and the consumer crashes on data that was perfectly valid when it was written. Fix it with .get() and a default, read as "if this key is missing, assume the oldest known value" rather than "require it":

# scripts/consume_order_events.py -- inside the message loop, right after json.loads()
event = json.loads(msg.value())
event["channel"] = event.get("channel", "unknown")

Then widen INSERT_SQL and the warehouse table to match. Add the column — nullable, so existing rows need no backfill:

docker compose exec -T postgres psql -U fdp -d fdp -c \
  "ALTER TABLE raw.order_events ADD COLUMN channel TEXT;"
# scripts/consume_order_events.py -- INSERT_SQL gains one column and one placeholder
INSERT_SQL = """
    INSERT INTO raw.order_events (event_id, order_id, status, occurred_at, channel)
    VALUES (%(event_id)s, %(order_id)s, %(status)s, %(occurred_at)s, %(channel)s)
    ON CONFLICT (event_id) DO NOTHING
"""
Why .get("channel", "unknown") and not a required field: the moment a consumer requires every message to carry a field, it has silently taken a dependency on every producer that has ever written to this topic agreeing on the current shape — including every message already written in the past, which it cannot change. A default makes old data a known, labelled case ("unknown") instead of a crash. This is the same shape of lesson as backend/'s API versioning: a v2 client reading a v1 response (or vice versa) needs a defined fallback for a field that might not be there, not an assumption that it always will be.

(2 rows)

Both counts in one table, from one unchanged consumer, is the actual demonstration: the schema changed mid-stream and nothing broke on either side of the change. 5 · What a Schema Registry buys over what you just did by hand

Today's fix works, and it's exactly the kind of thing a small team does by hand for a while. It has a real cost that doesn't show up until the team is bigger than one person: the backward-compatibility rule from Section 2 lived entirely in a developer's head and a careful code review. Nothing stopped tomorrow's producer change from renaming status to order_status and shipping it — the topic would accept it happily, and every consumer would break in production, discovered only when it did.

A Schema Registry is the tool that moves this check from "a human remembers" to "the infrastructure refuses." A producer registers its message schema before publishing; if a new version of that schema would break a configured compatibility rule — BACKWARD (new schema can read old data, today's rule), FORWARD (old schema can read new data), or FULL (both) — the registry rejects the registration outright, and the bad change never reaches the topic at all. Confluent's Schema Registry is the common implementation; it isn't part of Apache Kafka itself.

Schema Registry is usually paired with a binary serialization format instead of raw JSON — Avro or Protobuf. Both buy two things JSON-with-a-schema-in-your-head doesn't give you: field types and required/optional-ness are checked mechanically against a real schema definition rather than inferred from whatever example payloads a developer happened to look at, and messages on the wire carry a compact schema ID instead of repeating every field name in every message — smaller, and impossible to typo a field name into silently accepting.

Vocabulary today, not a build step. Per this course's Kafka depth rule, a Schema Registry is a new container and a new serialization format across the whole pipeline — real infrastructure cost for a single-developer portfolio where one disciplined convention (additive fields, sensible defaults, no renames) covers today's actual risk. Know what it is, what compatibility mode it would enforce here (BACKWARD), and why real multi-team Kafka deployments reach for it; the hands-on half of today's lesson is Section 3–4, not this one.

Q: "Your team wants to add a field to a Kafka topic's message schema that's already in production. Walk me through how you'd do it safely." A strong answer, out loud: "The question I'd ask first is which direction of compatibility I need — can new messages still be read by consumers running old code, or do I also need old messages to be readable by new code. For adding a field, backward compatibility is usually what matters: I'd add it as optional with a sensible default, never required, so a consumer that doesn't know about it yet just ignores it. The part people miss is the other direction — once a consumer is updated to expect that field, it still has to handle every message already sitting in the topic from before the field existed, which will never have it. I'd read it with a default — event.get('channel', 'unknown') in Python, not event['channel'] — so a KeyError on old data never happens. What I wouldn't do is rename or retype an existing field on a live topic; that breaks both directions at once, for both old and new consumers, and there's no default that fixes it. At scale, a Schema Registry with a BACKWARD compatibility rule enforces exactly this at publish time instead of relying on code review to catch it, but the underlying discipline — additive fields, defaults for absence, no renames — is the same thing I'd do by hand on a smaller system." The signal: naming backward vs. forward precisely, and catching that the harder direction is making the new consumer tolerate old data, not the other way around.
