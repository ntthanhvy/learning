Polling, long polling, SSE, and WebSockets: how "real-time" actually gets to the browser

Every lesson so far has assumed the shape Lesson 1 laid out: the browser asks, the backend answers, the connection ends. That shape has no way for the server to say "something changed" on its own — a new chat message, a price update, a job finishing — without the browser asking again first. Four different fixes exist for that gap, and picking the wrong one is a genuinely common design mistake, not a style preference. You already know the client side of at least two of these from the DOM; today is the backend side.

1 · The gap: HTTP only answers, it never volunteers

A plain fetch() is a question-then-answer: the browser opens a connection, sends a request, the server sends exactly one response, and the connection's job is done. Lesson 1 built the whole mental model of this course on that shape. It works perfectly for "load my orders" — but it has no mechanism at all for "tell me the moment a new order arrives," because the server has no way to speak first. The server can only ever respond to a question it was just asked.

Four different techniques close that gap, each trading away a different thing to do it. None of them is strictly "the modern one" that replaced the others — each is still the right choice in specific, nameable situations, which is exactly why picking blind is the actual mistake.

2 · Polling: the honest, wasteful default

Polling is just a setInterval around a normal fetch() — nothing new architecturally, every request is a complete, ordinary request-response pair, and the server answers instantly every time, even when the honest answer is "nothing changed." That simplicity is real: no new backend infrastructure, works through every proxy and firewall, and a stateless handler (Lesson 8) handles it exactly like any other endpoint. The cost is just as real: an interval short enough to feel responsive (every 2-3 seconds) means most requests are wasted round trips answering "no," multiplied by every client polling at once — a chat app with 10,000 open tabs polling every 3 seconds is 3,300+ requests per second asking a question whose answer is "no" the overwhelming majority of the time.

3 · Long polling: making the wasted request wait instead

Long polling fixes polling's core waste with one change: the server doesn't answer immediately. It holds the request open — no response sent — until either new data actually exists or a timeout passes (say, 30 seconds), then responds and the client immediately opens a fresh request to resume waiting. From the client's side the code looks almost identical to polling; from the server's side, a handler goroutine now blocks for up to 30 seconds per open connection instead of returning in milliseconds, which is the trade being made: far fewer wasted "no" answers, at the cost of holding far more connections (and their goroutines, and their memory) open at once. It's still ordinary HTTP request-response underneath — nothing about the protocol changed, only how long the server chooses to wait before using it.

4 · SSE: the server keeps one connection open and just keeps talking

SSE (Server-Sent Events) keeps a single connection open indefinitely and the server pushes new events down it as they happen, instead of the client re-asking on any schedule. It's still plain HTTP — one request, one response — except the response never formally ends; the server just keeps writing to it, formatted as a simple text stream (data: {...}\n\n per event). The browser side is a few lines you may already recognize: new EventSource("/updates") fires an onmessage callback per event and, notably, reconnects automatically if the connection drops — that reconnection logic is built into the browser API, not something you write yourself. The real constraint is architectural, not code-level: this is one-way only, server-to-client. A chat app's incoming messages fit SSE well; a chat app's outgoing messages still need a normal POST alongside it, because SSE has no channel back.

// sseHandler keeps one HTTP response open and writes events to it as they occur,
// instead of returning immediately -- the defining shape of Server-Sent Events.
func sseHandler(events <-chan Event) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        w.Header().Set("Content-Type", "text/event-stream")
        w.Header().Set("Cache-Control", "no-cache")

        flusher, ok := w.(http.Flusher) // must flush per event, not buffer until the end
        if !ok {
            http.Error(w, "streaming unsupported", http.StatusInternalServerError)
            return
        }

        for {
            select {
            case ev := <-events:
                fmt.Fprintf(w, "data: %s\n\n", ev.JSON())
                flusher.Flush() // push this event now, don't wait for more
            case <-r.Context().Done(): // Lesson 41: client disconnected, stop writing
                return
            }
        }
    }
}
Trap: that handler goroutine blocks in its own select loop for as long as the client stays connected — potentially hours. A server holding thousands of these open at once needs to plan for that connection count the same way Lesson 18 planned for connection-pool exhaustion: an open SSE connection is a held resource, not a fire-and-forget response.

5 · WebSockets: when the server needs to listen back

SSE's one-way limit is exactly what WebSockets exist to remove: after an initial HTTP request that asks to upgrade the protocol, the same TCP connection stops speaking HTTP entirely and becomes a raw, full-duplex channel: either side can send a message at any time, with no request/response pairing at all. A multiplayer cursor position, a live collaborative document edit, a game's input stream — anything genuinely bidirectional and frequent belongs here, not on SSE plus a workaround POST channel.

The cost is the one this course has been building toward since Lesson 8: a WebSocket connection is inherently stateful and pinned to whichever single instance accepted the upgrade. Lesson 8's whole point was that any instance should be able to handle any request because nothing lived only in one process's memory — a live WebSocket connection breaks that assumption on purpose, by design, because the whole feature requires one instance to hold one specific open socket for one specific client for the life of that connection. Broadcasting a message to "every connected client" behind multiple instances then needs its own fan-out mechanism (commonly Redis pub/sub) so instance B can tell instance A "forward this to the socket you're holding" — a real piece of infrastructure SSE and polling never require at all.

The decision rule worth saying out loud in review: start from how often things actually change and which direction data needs to flow, not from which technique sounds newest. A dashboard that refreshes real numbers once a minute has no business holding a WebSocket open all day just because it sounds more "real-time" — polling is the honestly simpler, cheaper, correct answer there. A live multiplayer whiteboard has no business polling every 2 seconds hoping to catch up — the lag alone breaks the feature. Reaching for WebSockets by default, the way this course has flagged similar reflexes before (Lesson 36's N+1, Lesson 57's cache stampede), tends to add real operational cost — connection-count capacity planning, the cross-instance fan-out problem, reconnect/backoff logic — to solve a problem a cheaper technique already solved.

Q: "A client wants live updates when an order's status changes. How would you build that?" A strong answer, out loud: "First I'd ask how often status actually changes and whether the client ever needs to send anything back mid-stream. If it's occasional — a few times over an order's life — long polling or even plain polling every few seconds is honestly fine and needs zero new infrastructure. If updates are frequent and strictly server-to-client, I'd reach for SSE: one open connection, the browser's EventSource handles reconnects for me, and I don't need a fan-out system unless I'm behind multiple instances, in which case I'd add Redis pub/sub so any instance can push to any connected client. I'd only reach for a full WebSocket if the client also needs to send frequent messages back on the same channel — status updates alone don't need that." The signal: naming the actual constraint (direction, frequency) before naming a technology, and knowing that a live connection is stateful and pinned to one instance, which Lesson 8's stateless-handler assumption doesn't cover for free.
