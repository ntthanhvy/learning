importlib: imports as data, not syntax

Day 9 fixed one thing about every import statement so far: the module name is written literally in the source, decided before the program ever runs. A plugin system, a CLI that loads a handler by name from a config file, or a FastAPI app picking a database driver by an environment variable all need the opposite — the name arrives as a plain string while the program is running, and import whatever_the_string_says is not legal Python syntax. importlib is the module that closes that gap.

Why today, specifically: a fresh case-insensitive grep across every lesson title, every lesson body, every practice file, reference/glossary.html, and RESOURCES.md confirmed importlib is still genuinely zero-hit as a dedicated topic (Day 100's own gap list carried it forward alongside array, types.SimpleNamespace, locale, and socket). Day 9 taught import/packages/__name__ thoroughly but only the static form, written as source code before the program runs — this lesson is the direct continuation, not a new unrelated corner, and every behavior below was confirmed live in a scratch run rather than assumed. Zero pandas/NumPy surface: dynamic module loading is a language mechanism, not a library either course teaches.

1 · importlib.import_module(): the name is a runtime string

import json only works because json is typed literally in the source. importlib.import_module(name) takes that same name as an ordinary string value — anything that can produce a string at runtime (a config file, a CLI argument, a dict lookup) can now choose the module:

import importlib

name = "json"          # could just as easily come from a config file or argv
mod = importlib.import_module(name)
mod.dumps({"a": 1})     # '{"a": 1}' -- confirmed live, mod is the real json module

It returns the actual module object, exactly like import json would bind to the name json — there is nothing special about the result, only about how its name was decided. A name that doesn't exist raises the same ModuleNotFoundError a plain import statement would:

try:
    importlib.import_module("definitely_not_a_real_module")
except ModuleNotFoundError as e:
    print(type(e).__name__)   # ModuleNotFoundError -- confirmed live

Once a module is loaded this way, pulling out a specific function is a plain attribute lookup — getattr(mod, "mean") works exactly like mod.mean, except the attribute name "mean" can also be a runtime string. That pairing — pick the module by string, pick the function by string — is the whole mechanism behind a plugin registry: a dict mapping short names ("csv", "json") to a module+function pair, built entirely from data instead of a chain of if/elif on every known option.

2 · Checking before loading: importlib.util.find_spec()

Calling import_module() on a name that might not exist means catching ModuleNotFoundError every time — reasonable for one lookup, noisy for scanning many candidate names. importlib.util.find_spec(name) asks "would this import succeed?" without actually running the module's code, returning None when the answer is no:

import importlib.util

spec = importlib.util.find_spec("os")
print(spec is None)              # False -- confirmed live, os is found

missing = importlib.util.find_spec("definitely_not_a_real_module")
print(missing)                    # None -- confirmed live, no exception raised

A found spec is a small object describing where the module lives and how it would be loaded — rarely inspected directly, but its mere existence (or None) is enough to decide, cleanly, whether a later import_module() call is worth making.

3 · importlib.reload(): re-running an already-imported module

Day 9 established that a module's top-level code runs exactly once, no matter how many times it's imported — the second import reuses the cached result. importlib.reload(module) is the deliberate escape hatch: it re-runs that module's code in place and returns the same module object, updated:

import math
import importlib

refreshed = importlib.reload(math)
print(refreshed is math)        # True -- confirmed live, same object, re-run in place

This matters almost exclusively in long-lived interactive sessions or a dev server picking up an edited file without a full restart — reaching for it inside normal application code is rare and usually a sign something else (a factory function, a fresh object per request) would be the more direct fix.

4 · importlib.metadata: reading a package's own version

A FastAPI app that logs its dependency versions at startup, or a CLI's --version flag, needs installed-package metadata — not the module's code, but data about it. importlib.metadata.version(name) reads that straight from what uv/pip already recorded when the package was installed, no import of the package's own code required:

import importlib.metadata as metadata

print(metadata.version("pip"))   # e.g. "24.0" -- confirmed live, read from install metadata

An unknown distribution name raises importlib.metadata.PackageNotFoundError rather than ModuleNotFoundError — a different exception on purpose, because "no such installed package" and "no such importable module" are genuinely different failures (a package can ship multiple importable module names, or none matching its own distribution name).

Where pandas/NumPy go from here: nowhere directly — importlib is how Python loads any package, pandas and NumPy included, but neither library changes how the mechanism itself works. The one realistic crossover, a plugin system that dynamically loads either a stdlib parser or a pandas reader by name, is data/'s territory and isn't demonstrated here.
