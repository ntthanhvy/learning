1 · The service: a tiny task list, in five pieces

Today's app is a task list with two routes: create a task, read one back by id. Small on purpose — the point is to see every piece land in a real, runnable file, not to build something elaborate. Five pieces, each a direct reuse of an earlier lesson:

  • Day 17 — pydantic request model. TaskIn(BaseModel) with a title: str and a done: bool = False default, plus a @field_validator("title") rejecting a blank string — the exact custom-validator shape Day 17 taught, applied to a new field.
  • Day 18 — pydantic response model. TaskOut(BaseModel) with id, title, done, attached to the route as response_model=TaskOut — the type hint is the contract, same as Day 18's own framing.
  • Day 23 — a custom exception and its handler. class TaskNotFound(Exception) plus @app.exception_handler(TaskNotFound), returning a consistent {"error": "task_not_found", "id": ...} shape — Day 23's exact pattern, not a fresh one.
  • Day 19 — a dependency. get_task_or_404(task_id: int), used as task: dict = Depends(get_task_or_404) on the read route — looks the task up once, raises TaskNotFound if it's missing, and the route body never has to check for that case itself.
  • Day 20 — a real await checkpoint. The create route is async def and does await asyncio.sleep(0) before writing the record — standing in for the real await a database insert would need, so the route is genuinely async, not async def in name only.

Here is the whole thing, in the order above:

from fastapi import Depends, FastAPI
from fastapi.responses import JSONResponse
from pydantic import BaseModel, field_validator
import asyncio

app = FastAPI()
_DB: dict[int, dict] = {}
_NEXT_ID = 1

class TaskIn(BaseModel):
    title: str
    done: bool = False

    @field_validator("title")
    @classmethod
    def title_not_blank(cls, v: str) -> str:
        if not v.strip():
            raise ValueError("title must not be blank")
        return v

class TaskOut(BaseModel):
    id: int
    title: str
    done: bool

class TaskNotFound(Exception):
    def __init__(self, task_id: int):
        self.task_id = task_id

@app.exception_handler(TaskNotFound)
async def task_not_found_handler(request, exc: TaskNotFound):
    return JSONResponse(status_code=404, content={"error": "task_not_found", "id": exc.task_id})

def get_task_or_404(task_id: int) -> dict:
    if task_id not in _DB:
        raise TaskNotFound(task_id)
    return _DB[task_id]

@app.post("/tasks", response_model=TaskOut, status_code=201)
async def create_task(task: TaskIn):
    global _NEXT_ID
    await asyncio.sleep(0)
    record = {"id": _NEXT_ID, "title": task.title, "done": task.done}
    _DB[_NEXT_ID] = record
    _NEXT_ID += 1
    return record

@app.get("/tasks/{task_id}", response_model=TaskOut)
async def read_task(task: dict = Depends(get_task_or_404)):
    return task

36 lines, and every one of them is a mechanism from a lesson already taught. Nothing here is new syntax — today's win is seeing them compose without friction.

2 · Day 22's testing pattern, aimed at all of it at once

Day 22 tested one route at a time via TestClient. Today's tests exercise the whole flow — create, then read the created thing back, then hit the failure path:

from fastapi.testclient import TestClient
client = TestClient(app)

r = client.post("/tasks", json={"title": "write lesson"})
assert r.status_code == 201
task_id = r.json()["id"]

r2 = client.get(f"/tasks/{task_id}")
assert r2.status_code == 200 and r2.json()["title"] == "write lesson"

r3 = client.get("/tasks/999999")
assert r3.status_code == 404 and r3.json()["error"] == "task_not_found"

Confirmed directly in-process against this exact app: POST /tasks with a real title returns 201 with a body matching TaskOut's three fields; a blank title (" ") is rejected with pydantic's 422, no route code needed to check for it; a missing id returns the custom 404 shape from section 1's handler, not FastAPI's default error page. No real socket opens anywhere — the identical in-process discipline every FastAPI practice file has used since Day 16.

3 · What "wired together" actually bought

Notice what each route body does not contain: no manual type-checking of task.title (pydantic did it before the function ran), no if task_id not in _DB: return error repeated in every route that needs a task (the dependency did it once), no bare dict shape hoping the client sends the right keys back (response_model enforces the shape on the way out too). Each lesson from Days 17–20 removed one specific category of hand-written code from the route bodies — today is the first time all of those removals are visible stacked on top of each other in one file.

Where pandas goes from here: none of today's five pieces has a pandas equivalent to contrast against — pydantic validation, dependency injection, and exception handlers are service-shape concerns a one-shot data pipeline never has, since nothing is waiting to accept a next request. This is the same point Day 25's own closing callout made about deployability, one layer up.
