np.floor() and np.ceil(): rounding toward infinity, not toward zero

Lesson 129 closed its own fresh scan with np.floor()/np.ceil() and np.log()/np.exp() still open. Today's own fresh scan re-confirmed both pairs are still genuinely untaught (grepped every lesson body and every glossary row; zero dedicated coverage for either pair). Picked np.floor() and np.ceil() as one coherent pair: together they are the two calls behind the classic "round down/up to a whole dollar/unit" wrangling task, and, confirmed directly below, they break the int-upcasts-to-float pattern Lesson 129 just established for np.sqrt() — a genuinely different dtype story worth contrasting on its own.

1 · Both keep the Series and its Index — and, unlike np.sqrt(), int input is a true no-op

np.floor(x) and np.ceil(x) both return a Series with the original Index intact when called directly on one — confirmed directly (numpy 2.5.5, pandas 3.1.1), same as Lesson 129's np.abs()/np.sqrt(). The dtype story is different, though:

import numpy as np
import pandas as pd

s_int = pd.Series([1, -1, 3, 7])
np.floor(s_int).dtype   # int64 -- a genuine no-op, values completely untouched
np.floor(s_int).tolist() # [1, -1, 3, 7] -- identical to s_int itself

s_float = pd.Series([1.2, -1.2, 2.7])
np.floor(s_float).dtype # float64 -- stays float on float input

Confirmed directly: an integer is already a whole number, so np.floor()/np.ceil() on an int64 Series return the exact same values, untouched, still int64 — a true no-op, not an upcast. This is a sharper rule than Lesson 129's np.sqrt(), which always upcasts to float64 even on a clean int input; np.floor()/np.ceil() only ever produce float64 when the input was already float. Confirmed directly, pandas defines no Series.floor() or Series.ceil() method at all — calling either raises AttributeError immediately, the same naming gap Lessons 126–129 found for np.roll()/np.sign()/np.sqrt(). The pandas-idiomatic path is calling np.floor()/np.ceil() directly on the Series, confirmed directly to work identically to the plain-array case.

2 · The trap: "round down" means toward negative infinity, not toward zero

Confirmed directly (numpy 2.5.5): on a negative number, np.floor() rounds away from zero, not toward it — np.floor(-1.2) is -2.0, not -1.0. The function that rounds toward zero instead is np.trunc(), a different, unrelated function.
np.floor(-1.2)   # -2.0  -- rounds DOWN, i.e. toward -infinity, past -1
np.trunc(-1.2)   # -1.0  -- rounds TOWARD zero instead, a different function entirely
np.ceil(-1.2)    # -1.0  -- rounds UP, i.e. toward +infinity, back toward zero

Confirmed directly: "floor" always means toward negative infinity and "ceil" always means toward positive infinity, regardless of the input's own sign — on a negative number this makes floor() look like it rounds "away from zero" and ceil() look like it rounds "toward zero," the reverse of the positive-number intuition most people build first. This is also confirmed directly to differ from Series.round(), which rounds to the nearest whole number (using banker's rounding on exact halves — round(2.5) is 2.0, confirmed directly, not 3.0) rather than committing to a single direction at all. A wrangling task that says "round down to the nearest whole dollar" means np.floor(), never Series.round() — confirmed directly they disagree on every non-whole input: np.floor(2.7) is 2.0 but pd.Series([2.7]).round() is 3.0.

3 · NaN, complex, object dtype, and a same-named but unrelated datetime method

Confirmed directly: a NaN input passes straight through both functions unchanged, still NaN — neither one raises or warns, the same pass-through behavior Lesson 127's np.sign() has for NaN. Confirmed directly, both run on an object-dtype array of plain Python floats without error (dispatching through Python's own math-level rounding), but both raise TypeError immediately on complex input — confirmed directly against the real error message ("ufunc 'floor' not supported for the input types") — because "round down" has no single meaning for a 2-D complex number, unlike Lesson 129's np.abs(), which has a well-defined complex magnitude. One naming trap to flag explicitly: pandas does define Series.dt.floor() — but only on datetime data, rounding a timestamp down to the start of a given frequency bucket (e.g. .dt.floor("h") rounds down to the start of the hour). It is unrelated to np.floor() in every way except the shared English word; confirmed directly, calling plain .floor() on a non-datetime Series still raises the same AttributeError as before.

# the classic wrangling task: round prices down to the nearest whole dollar
prices = pd.Series([19.99, 20.01, 5.00, 100.0])
np.floor(prices)
# 0     19.0
# 1     20.0
# 2      5.0
# 3    100.0  -- confirmed directly: a whole float input is its own floor

# unrelated: rounding a TIMESTAMP down to the hour -- a different method entirely
ts = pd.Series(pd.to_datetime(["2026-01-01 10:45:00"]))
ts.dt.floor("h")   # 2026-01-01 10:00:00
