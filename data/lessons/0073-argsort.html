argsort(): positions, not values — and a stale docstring to catch

Chào bạn — Lesson 72's teaser named three leftover zero-hit candidates: np.unique, argsort, searchsorted. A fresh grep of all 72 lessons and the glossary reconfirms all three are still genuinely untaught. argsort() is the pick today: it closes a real gap next to Lesson 7's rank() and Lesson 31's sort_values(), and — the reason it earns its own lesson rather than a footnote — its own official docstring turns out to describe behavior pandas no longer has.

1 · The gap: rank() and sort_values() answer "what," argsort() answers "where"

Lesson 7's rank() gives each row its own position number, in the row's own place. Lesson 31's sort_values() rearranges the actual rows into sorted order. argsort() does neither — it returns, for each OUTPUT position, which ORIGINAL row index belongs there. It never touches the values or the row order itself; it only computes the recipe for sorting them.

s = pd.Series([30, 10, 20])
s.rank()          # 0  3.0   1  1.0   2  2.0   -- each row's OWN rank
s.argsort()        # 0  1     1  2     2  0     -- position 0 in sorted order is ORIGINAL row 1

argsort() is genuinely the mechanism sort_values() and rank() build on internally — confirmed directly: the two are exact inverses of each other on the same data (rank() - 1 equals the inverse permutation of argsort(), both giving [2, 0, 1] for [30, 10, 20]). Reaching for argsort() directly matters when you need the POSITIONS themselves as data — e.g. to apply the same sort order to a second, unrelated array — not just the sorted values.

SQL bridge: plain SQL has no equivalent to asking for "the positions that would sort this," because SQL never exposes row position as a first-class value to compute with — the closest SQL gets is ROW_NUMBER() OVER (ORDER BY col), which is actually closer to pandas' rank(method="first") (each row's own new position) than to argsort() (which output position holds which original row). In an interview, naming that argsort() is the "reverse direction" of ROW_NUMBER() is the sharp, correct distinction.

2 · Using it on this course's real fixture: sort by amount without sort_values()

Confirmed directly (pandas 3.0.6) on this course's real orders_raw.csv, using the raw amount column coerced with pd.to_numeric(errors="coerce") (the "unknown" string in row 2 becomes NaN, untouched by dropna() here on purpose):

amt = pd.to_numeric(df["amount"], errors="coerce")
order = amt.argsort()
order.tolist()          # [1, 5, 3, 0, 4, 2]
df.iloc[order]["order_id"].tolist()   # [2, 6, 4, 1, 5, 3] -- ascending by amount

Reading rows back out needs .iloc[order], never .loc[order] — argsort() returns raw integer POSITIONS, not the DataFrame's own index labels, so .loc would silently look up the wrong rows (or raise KeyError) the moment the index isn't a plain 0, 1, 2, ... range.

3 · The catch: the official docstring says "-1 indicating nan values" — it does not, anymore

This is the round's central, non-obvious finding, and the reason this lesson exists rather than a one-line glossary entry. Pandas' own help(pd.Series.argsort) states, verbatim: "Positions of values within the sort order with -1 indicating nan values." Confirmed directly (pandas 3.0.6) that this is stale — no -1 appears anywhere in the actual output:

s = pd.Series([30.0, float("nan"), 10.0, float("nan"), 20.0])
s.argsort().tolist()     # [2, 4, 0, 1, 3] -- NOT [2, -1, 0, -1, 1]
-1 in s.argsort().to_numpy()   # False

Actual current behavior: NaN rows are pushed to the END of the sort order (same as NumPy's own default), and their real original position appears in the output completely normally — no -1 sentinel anywhere. On this course's fixture, the NaN row (order_id 4, the missing amount) ends up last in order above, at real position 2, not flagged with any special value. Trusting the docstring's literal wording — writing code that checks if pos == -1: skip it — would silently never trigger, because that branch is unreachable on this pandas version. The correct, verified statement for an interview: "NaNs sort to the end and keep an ordinary integer position — don't rely on -1 as a NaN marker; check the source Series for NaN directly if you need to filter it out."

4 · No ascending= keyword — negate the values instead

Confirmed directly: unlike sort_values() and rank(), argsort() takes no ascending= argument at all — passing one raises TypeError: Series.argsort() got an unexpected keyword argument 'ascending'. Simply reversing the output array afterward (argsort()[::-1]) is a common but wrong instinct: it also flips the NaN-last placement to NaN-first, and flips tie order, neither of which is the same as a genuine descending sort. The standard, correct trick — confirmed directly to give the right order on this fixture — is to negate the numeric values first, then argsort the negation:

(-amt).argsort().tolist()   # [4, 0, 3, 5, 1, 2] -- descending by amount, NaN still last

Q: "What's the difference between rank(), sort_values(), and argsort() — and when would you reach for argsort() specifically?" A strong answer, out loud: "All three are related to ordering, but they answer different questions. sort_values() rearranges the actual rows into sorted order — I'd use it when I want the sorted DATA. rank() gives each row its own position number, in place — I'd use it for 'what percentile/place is this row in its group,' often after a groupby(). argsort() is the odd one out: it doesn't touch the data at all, it returns the POSITIONS that would sort it — I'd reach for it specifically when I need to apply the same computed order to a second, separate array or column, not just re-sort the one I called it on. One thing I'd flag from hands-on testing: its own docstring says NaN gets encoded as -1, but on the pandas version I checked that's not actually true anymore — NaNs just sort to the end with an ordinary position, so I wouldn't trust that detail without verifying it directly first." The signal: distinguishing "reorder the data" from "compute the reorder recipe," and specifically flagging a stale docs claim instead of repeating it — that's the same "verify, don't assume" instinct interviewers want to see applied to any library, not just this one.
