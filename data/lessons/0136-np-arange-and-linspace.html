1 · np.arange(): count by step size, stop is exclusive

Confirmed directly (numpy 2.5.5), np.arange(start, stop, step) is the array-building sibling of Python's own range() — same exclusive-stop convention, but it accepts float arguments where range() only accepts integers:

import numpy as np
import pandas as pd

np.arange(5)           # [0 1 2 3 4]      -- one arg: stop only, start defaults to 0
np.arange(1, 5)        # [1 2 3 4]        -- stop (5) is excluded, same as range(1, 5)
np.arange(0, 1, 0.1)   # [0.  0.1 ... 0.9] -- float step works; range() would raise TypeError here

Confirmed directly against the official docs' own wording, this is the documented trap: when step is a non-integer float, "the length of the output... is not always obvious," because the actual number of elements is computed from dividing (stop - start) by step, and that division is subject to ordinary floating-point rounding error. On this machine, np.arange(0, 1.1, 0.1) happened to come out to the expected 11 elements, and np.arange(0, 0.7, 0.1) to the expected 7 — but the individual values inside already show the imprecision that causes the trap elsewhere: np.arange(0, 0.7, 0.1)[-1] prints as 0.6000000000000001, not the clean 0.6 someone would expect, because 0.1 itself has no exact binary floating-point representation.

2 · np.linspace(): count by total points, stop is inclusive by default

Confirmed directly, np.linspace(start, stop, num) flips the question: instead of "what step size, stopping before some value," it asks "how many points, including both ends":

np.linspace(0, 1, 5)                 # [0.   0.25 0.5  0.75 1.  ] -- 5 points, 1.0 IS included (inclusive stop)
np.linspace(0, 1, 5, endpoint=False)  # [0.  0.2 0.4 0.6 0.8]      -- excludes 1.0, now matches arange()'s convention
np.linspace(0, 1, 5, retstep=True)   # (array([...]), np.float64(0.25)) -- also returns the step size used
Confirmed directly against the official docs' own recommendation: the docs for numpy.arange() state plainly, "it is best to use numpy.linspace" whenever a non-integer step is involved, specifically because linspace() computes its step size exactly once (dividing the total span by num - 1) rather than accumulating it by repeated addition the way arange() effectively does — so rounding error cannot compound across many steps. The two functions answer different questions on purpose: reach for arange() when the step size is what matters (e.g. "every 5th row index"), and linspace() when the total count of points matters (e.g. "20 evenly spaced bin edges for a histogram").

3 · np.zeros()/np.ones()/np.full(): placeholder arrays, and np.empty()'s uninitialized-memory trap

Confirmed directly, np.zeros(shape) and np.ones(shape) both default to float64 even though every value is a whole number, and shape can be a plain int (1-D) or a tuple (N-D):

np.zeros(3)           # array([0., 0., 0.]), dtype float64 -- NOT int, even though values are whole
np.ones((2, 3))       # 2x3 array of 1.0s, dtype float64
np.full((2, 2), 7)    # 2x2 array of 7, dtype int64 -- full() infers dtype FROM the fill value instead
np.full((2, 2), 7.0)  # 2x2 array of 7.0, dtype float64 -- same shape, fill value's dtype flips it

Confirmed directly, this is the sharper trap: np.empty(shape) does not fill the array with zeros the way its name might suggest by analogy to np.zeros() — it only reserves memory of the right size and dtype, leaving whatever garbage bytes were already there:

np.empty(3)  # array([6.77313745e-310, 6.77313745e-310, 1.58101007e-322]) -- garbage, re-run and it may differ
# np.empty() exists purely as a speed optimization: skipping the zero-fill
# write is marginally faster when every element will be overwritten anyway
# (e.g. inside a loop) -- reading before writing is undefined behavior

Q: "I need 50 evenly spaced points between 0 and 10, inclusive of both ends. Would you use arange() or linspace(), and why?" A strong answer, out loud: "linspace(0, 10, 50) — I know the exact count I want (50), and linspace's stop is inclusive by default, so both endpoints land in the array exactly. If I used arange() instead, I'd have to reverse-engineer a step size from the count, which is exactly the case NumPy's own docs warn produces unpredictable lengths once that step isn't a clean integer — arange()'s stop is also exclusive, so I'd need to nudge the stop value up slightly just to include 10. arange() is the right tool when the step size itself is the meaningful unit, like 'every 0.5 seconds'; linspace() is right when the point count is the meaningful unit." The signal: picking based on which quantity (step vs. count) is actually fixed by the problem, not just defaulting to whichever function is more familiar.
