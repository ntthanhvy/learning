Idempotency keys: making POST safe to retry

Lesson 3 taught you that POST makes no idempotency promise — "retrying a POST creates something new each time" was the whole point of that table. Today: the concrete mechanism that lets a client retry a POST anyway, without your server creating the thing twice.

1 · The gap Lesson 3 left open

Lesson 3's verb table was honest about POST: no promise, the one verb allowed side effects, so only it needs "special protection (dedup tokens, disabled buttons)" against the double-click-fires-two-orders problem. That line named the problem and gestured at a fix, but never built one. The same gap shows up from the network side, not just double-clicks: a client fires POST /orders, the server creates the order and starts writing the response, and the connection drops before the client ever sees 201 Created. From the client's side this is indistinguishable from "the request never arrived" — the only reasonable move is to retry. But the order was already created. Retry naively and the customer gets charged twice.

Same shape as Lesson 10: background job queues promise at-least-once delivery for exactly this reason — a worker can crash after finishing work but before marking the job done, so the job runs again. That lesson's answer was "the handler must tolerate running more than once." Today's lesson is the concrete tool for tolerating it at the API layer.

2 · The idea: let the client name the attempt, not the row

The fix is a client-generated idempotency key, sent as a request header: Idempotency-Key: 7c9e-.... The client generates this once, when the user clicks "Place order" — not once per HTTP attempt. If the request needs retrying (timeout, dropped connection, 5xx), the client sends the exact same key again. The server's job: the first time it sees a key, do the work and remember the result; every later request with that same key gets the remembered result played back, without doing the work again.

This inverts where the "have I done this before?" question gets answered. Without a key, the server has no way to distinguish "a new order" from "the same order, asked twice" — both just look like a POST with a body. The key gives the server something stable to check before touching the database.

3 · A minimal implementation

The mechanism: a small store mapping key → the response that was already sent for it, checked before the real handler runs and filled in after:

type IdempotencyStore struct {
    mu      sync.Mutex
    records map[string]idempotencyRecord
}

func (s *IdempotencyStore) Get(key string) (idempotencyRecord, bool) {
    s.mu.Lock()
    defer s.mu.Unlock()
    rec, ok := s.records[key]
    return rec, ok
}

func withIdempotency(store *IdempotencyStore, next http.HandlerFunc) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        key := r.Header.Get("Idempotency-Key")
        if key == "" {
            http.Error(w, "Idempotency-Key header required", http.StatusBadRequest)
            return
        }
        if rec, ok := store.Get(key); ok {
            w.Header().Set("Content-Type", "application/json")
            w.WriteHeader(rec.statusCode)
            w.Write(rec.body) // replay — never calls next()
            return
        }
        rw := &recordingWriter{ResponseWriter: w, status: http.StatusOK}
        next(rw, r) // first time: run the real handler
        store.Put(key, rw.status, rw.body) // remember exactly what it sent
    }
}

The middleware wraps createOrderHandler from Lesson 3's shape unchanged — the handler itself never learns about retries. recordingWriter (the full version compiles clean, elided here for space) just captures whatever status and body the real handler wrote, so the exact same bytes can be replayed later. A production version swaps the in-memory map for a database table with a unique constraint on the key, so the "check, then remember" step is itself safe under two near-simultaneous retries — but the shape is identical.

4 · Why replay the stored response instead of just re-running the handler

It's tempting to think the fix is simpler than this — "just check if an order with this key already exists, and skip creating it." That's most of the idea, but replaying the exact stored response matters for a reason beyond convenience: re-running any part of the original logic risks a second real side effect (a second charge to the payment provider inside that handler, a second email queued), even if the order row itself doesn't duplicate. The safe version does zero application logic on a replay — it recognizes the key before the handler runs at all and returns bytes that were already sent once.

5 · What the key doesn't fix by itself

Three details that turn a naive version into a correct one: the key must be scoped per client (usually per API credential/customer), never global — otherwise one customer's retry could theoretically collide with another's key and leak their order back. It should be checked against the same request body it was first used with — reusing a key with a different payload is a client bug, and a careful implementation flags that with a 422 rather than silently returning the old response for new data. And it needs an expiry — Stripe's own docs (below) keep keys for 24 hours, long enough to cover realistic retries without the store growing forever.

Q: "How would you make a payment-creation endpoint safe to retry?" A strong answer, out loud: "POST doesn't promise idempotency on its own, so I'd require an Idempotency-Key header the client generates once per user action. First time the server sees a key, it runs the real handler and stores exactly what it returned, keyed by that value. Any later request with the same key gets that stored response replayed — the handler never runs again — so a dropped connection and a client-side retry can't double-charge. I'd scope the key per customer, validate the retried body matches the first one, and expire old keys after a day or so." The signal: replaying the stored response instead of re-running logic, and naming the per-client scoping detail unprompted.
