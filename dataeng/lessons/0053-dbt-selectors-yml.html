1 · The gap: a correct expression is still something to remember and retype

Day 52 ended with a real, working dev-loop command: dbt build --select "@stg_orders", and the reasoning for why @ specifically is the safe default. That reasoning doesn't change today. What's missing is durability — the expression lives only inside one Makefile recipe line and inside whoever's head remembers why @ and not +. A second person on this project (or the same person in six months) has no way to discover that reasoning from the CLI alone, and a long or multi-part expression — several tag: methods, an --exclude, a graph operator — gets error-prone to retype correctly every time. dbt's answer is a selectors.yml: one file, at the project root, where a selection expression gets a name and a description field explaining why it's shaped the way it is.

2 · Confirmed live: the YAML shape is not the CLI string

The natural first guess — paste "@stg_orders" straight into a YAML value: field — fails at dbt parse with a real compilation error, confirmed this round:

Compilation Error
  Could not render @{{ var('changed_model') }}: Required var 'changed_model' not found in config

That error came from a different, broken attempt (templating the model name via var() inside the selector), but the underlying lesson holds either way: selectors.yml's definition: block is a structured object, not a string dbt re-parses as CLI syntax. A graph operator becomes its own key, sitting next to method and value rather than folded into either of them. The table below is dbt's actual mapping from CLI syntax to YAML keys, every row confirmed by running the equivalent dbt list both ways and diffing the node sets:

CLI syntaxYAML definition: equivalentConfirmed resolves to
stg_ordersmethod: fqn
value: stg_orders		just that one model
stg_orders+add children: truestg_orders plus its descendants
+stg_ordersadd parents: truestg_orders plus its ancestors
@stg_ordersadd childrens_parents: truestg_orders, its descendants, and every ancestor those descendants need
tag:nightlymethod: tag
value: nightly		every node carrying that tag

Built food_delivery_pipeline/selectors.yml against the same scratch project shaped like this course's real one (Day 52's six models), naming the two expressions actually worth keeping around:

selectors:
  - name: build_changed_orders
    description: "Rebuild stg_orders's full correctness closure: it, every descendant, and every ancestor those descendants need."
    definition:
      method: fqn
      value: stg_orders
      childrens_parents: true

  - name: nightly_marts
    description: "Every model tagged nightly -- the marts, rebuilt together after order_events lands for the day."
    definition:
      method: tag
      value: nightly

Running dbt list --selector build_changed_orders --resource-type model against the scratch project printed exactly the five nodes Day 52's @stg_orders printed — stg_orders, fct_orders, mart_delivery_sla, dim_restaurants, stg_restaurants — confirming the YAML form and the CLI form are the same selection, just named.

A real trap, confirmed live: --selector and --select/--exclude cannot be combined. Passing both — dbt list --selector build_changed_orders --exclude "tag:nightly" — doesn't error; it silently keeps the selector's result and drops the --exclude entirely, logging only The --select and --exclude arguments are being ignored for node selection because --selector is provided at the default log level, easy to miss in a long CI log. If an expression needs a narrower cut than a named selector provides, that narrowing belongs inside the selector's own YAML (a second selector, or dbt's union/intersection composition — vocabulary only here, not built today), not bolted onto the CLI call.

3 · Build: name it, then point the Makefile target at the name

In your food-delivery-pipeline repo, add food_delivery_pipeline/selectors.yml with the two selectors above, adjusted to this project's real shape if Day 48/49's histogram marts changed which models carry the nightly tag. Then edit Day 52's build-changed target to call the name instead of the raw string:

build-changed: # usage: make build-changed MODEL=stg_orders
	cd food_delivery_pipeline && uv run --with "dbt-postgres==1.11.0" dbt build --selector build_changed_$(MODEL) --profiles-dir .

This trades flexibility for discoverability on purpose: the old target worked for any model name via $(MODEL); a named selector is fixed to exactly the model it was written for. That's the right trade once an expression is reused often enough to be worth a name — today's repo has exactly one model whose change ripples wide enough to matter this way, stg_orders, so one named selector plus the still-flexible raw --select "@$(MODEL)" form (keep both, per the TODO below) covers it without overbuilding.

Q: "What's a dbt selectors.yml for, and when would you actually reach for one?" A strong answer, out loud: "It names a --select/--exclude expression in a YAML file at the project root, invoked with --selector instead of retyping the raw string. The shape isn't the same as the CLI string, though — a graph operator like @ or + becomes its own boolean key next to method and value, like childrens_parents: true, not text folded into the value field; I confirmed that the hard way, pasting a literal @ into a value string fails to parse. I reach for one once an expression is long enough, or load-bearing enough, that retyping it correctly every time is a real risk, and the description field lets me write down why it's shaped that way right next to the team that maintains it — version-controlled reasoning, not something living only in one person's head or one Makefile comment. One real trap worth knowing: --selector can't be combined with --select or --exclude on the same command; passing both silently drops the extra flag with only a log line, not an error, so any narrowing has to live inside the selector's own YAML instead." The signal: naming the YAML-vs-CLI shape mismatch as something confirmed, not assumed, and surfacing the silent --selector/--select conflict as a real operational trap rather than treating selectors.yml as pure syntactic sugar.

Scope line

This lesson covers selectors.yml's basic shape (method, value, the three graph-operator boolean keys) and the --selector flag, confirmed live against a scratch project. It does not cover dbt's full selector composition syntax (union, intersection, multi-block exclude beyond today's TODO, default: true for a selector that runs without being named at all) — read as vocabulary in the primary source below, not built today — nor the path:/source:/config: selection methods Day 52 also named but left unbuilt, which remain open for a future round.
