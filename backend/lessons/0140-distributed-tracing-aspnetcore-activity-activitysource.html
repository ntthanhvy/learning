Distributed tracing, now in C# too (Activity, ActivitySource)

Lesson 65 built a correlation ID the hand-written way: generate it at the edge, carry it through context.Context inside one process, then manually copy it onto an outbound header at every call site that talks to another service — remembering to do that last step is on the caller, every single time. .NET's answer removes that last step from the caller's job entirely. The runtime itself, plus its in-box HTTP server and client, already know how to carry a trace's identity across both an await and a network hop — no header copy-paste required.

1 · Activity is .NET's name for what Lesson 65 called a span

Lesson 65's section 6 named the generalization beyond a single correlation ID: a full trace is a tree of timed units of work, each one pointing at whichever unit called it. .NET's distributed-tracing docs confirm that .NET has had exactly this model built into the runtime for years, under its own name: "units of work in a trace are represented by instances of System.Diagnostics.Activity... Another common industry name for units of work in a distributed trace are 'Spans'. .NET adopted the term 'Activity' many years ago, before the name 'Span' was well established for this concept." Same tree, same idea as OpenTelemetry's span — .NET just had its own word first.

Every Activity records a globally unique Activity.TraceId shared by the whole tree, its own Activity.SpanId, and Activity.ParentSpanId pointing at whichever Activity started it — the exact three fields Lesson 65 described a span needing, just under .NET's own property names.

2 · Activity.Current flows across await on its own

Lesson 65's Go snippet needed an explicit ctx context.Context parameter threaded through every function in the call chain, because that's the only way a value rides along in Go — nothing flows automatically. .NET's docs describe a different default: "Each thread in a process may have a corresponding Activity object that tracks the work occurring on that thread, accessible via Activity.Current. The current activity automatically flows along all synchronous calls on a thread and follows async calls that are processed on different threads." Start a child ActivitySource's activity anywhere inside a request's async call chain, and it becomes the new Activity.Current for every awaited call underneath it — no parameter to remember to pass, because the runtime's own async machinery carries it.

private static readonly ActivitySource Source = new("OrderService");

public async Task<ChargeResult> ChargeCardAsync(int amountCents, HttpClient billingClient, CancellationToken ct)
{
    using var activity = Source.StartActivity("charge-card");
    activity?.SetTag("amount_cents", amountCents); // Lesson 13's structured log field, as an Activity tag instead

    // billingClient is a plain HttpClient; no header set here by hand --
    // HttpClient already knows how to encode Activity.Current as a
    // traceparent header on the way out.
    var resp = await billingClient.PostAsync("https://billing.internal/charges", null, ct);
    if (!resp.IsSuccessStatusCode)
    {
        activity?.SetStatus(ActivityStatusCode.Error, $"billing returned {resp.StatusCode}");
        throw new InvalidOperationException($"call billing service: {resp.StatusCode}");
    }
    return ChargeResult.Success;
}

Compare this to Lesson 65's chargeCard: no ctx.Value(requestIDKey) lookup, no explicit req.Header.Set("X-Request-ID", requestID) line. The using block's disposal also restores whatever Activity.Current was before this method started, matching Lesson 65's own stack-like call-graph shape automatically rather than by convention.

Frontend-habit trap: this is the same shape as React's Context API threading a value down automatically versus prop-drilling it through every intermediate component by hand. Lesson 65's Go version is the prop-drilling story — every function signature carries ctx on purpose. .NET's Activity.Current is closer to a context provider that the async runtime itself already wired up, so nothing in between has to touch it.

3 · The network hop: still a header, but nobody writes it by hand

Lesson 65 section 4 established the real constraint this doesn't change: no in-process carrier survives a network call on its own. .NET's docs are explicit that the header still has to travel, just not by the app developer's own code: "Unlike many other language runtimes, .NET in-box libraries such as the ASP.NET web server and System.Net.Http natively understand how to decode and encode Activity IDs on HTTP messages... This means that .NET applications that receive and emit HTTP messages participate in flowing distributed trace IDs automatically, with no special coding by the app developer." The header itself is the W3C standard's own traceparent — the same header format Lesson 65 named as the eventual standardized choice — and ASP.NET Core's request pipeline reads it on the way in, starts an Activity whose ParentSpanId points at whatever arrived in that header, and HttpClient writes the current Activity back out as traceparent on any outbound call, both directions handled by the framework rather than application code.

4 · What this buys, and what it costs

The win over Lesson 65's version: a forgotten header copy is no longer possible for any call made through HttpClient inside an ASP.NET Core app, because there's no header-copying code left for a new call site to omit. The cost mirrors Lesson 139's own audit-log caveat exactly: this automatic propagation only covers HTTP calls made through .NET's own in-box client and server. A call to a non-HTTP transport (a message queue, a raw socket), or an outbound call made by some other library that doesn't know about Activity, carries nothing automatically — the trace tree simply stops at that edge, silently, unless something explicitly reads Activity.Current and forwards it by hand the way Lesson 65's Go code always had to.

Q: "Our Go services propagate a request ID by hand through context.Context and a header. We're adding a .NET service to the same call graph — does it need the same wiring?" A strong answer, out loud: "Less than you'd think. .NET's HttpClient and ASP.NET Core already know how to decode and encode the W3C traceparent header automatically, and Activity.Current flows across await on its own, so a plain HTTP call between our .NET service and anything else that understands traceparent needs no extra code. Where it still needs the same care as our Go services is anything that isn't a standard in-box HTTP call — a message queue hop, or a call through a library that doesn't touch Activity — there, I'd read Activity.Current explicitly and forward its TraceId/SpanId by hand, the same discipline the Go code already has everywhere." The signal: knowing exactly where the automation stops, not just that it exists.

Scope line

This lesson covers Activity/ActivitySource.StartActivity, Activity.Current's automatic flow across synchronous and async/await calls, and the in-box ASP.NET Core/HttpClient encoding and decoding of the W3C traceparent header. It does not cover actually wiring an OpenTelemetry exporter to collect and visualize these Activities (Lesson 65's own stopping point for the Go side too), ActivityListener/DiagnosticListener (the lower-level collection mechanisms a telemetry library builds on), sampling (ActivityListener.Sample, named in the docs but not explored here), or the older Hierarchical ID format (superseded by W3C TraceContext as .NET's default since .NET 5).
