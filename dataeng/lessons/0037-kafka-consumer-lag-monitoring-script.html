1 · What Day 18 actually did, and the gap it left

Day 18 defined lag correctly and read it once: consumer lag is high-water mark minus committed offset, read straight off the LAG column of kafka-consumer-groups.sh --describe. That's the right definition and the right first command, but it's a human reading a terminal once. Nothing from that day can run on a schedule, raise an alert, or feed a dashboard — it was concept-plus-one-CLI-read, which is exactly how PLAN.md's own Phase 2b bullet frames this topic ("consumer lag as the key health metric") without specifying a build. The gap is mechanical, not conceptual: turn the one-off shell read into a script that returns a real exit code, because that's the actual interface a monitoring system or an orchestrator needs.

This also bridges directly to MISSION.md's own Kafka bullet about the landing step being at-least-once: lag is the metric that tells you *when* to worry about that consumer, not just that it's theoretically safe. A consumer that's stopped committing entirely — crashed, OOM-killed, stuck in a retry loop — is invisible from the warehouse side until lag makes it visible.

2 · Why the CLI output alone doesn't compose into an alert

kafka-consumer-groups.sh --describe is a Java tool shelling out through the broker's admin protocol; its output is text meant for a terminal, not a return value a Python process (or an Airflow task) can branch on. Getting the same number programmatically needs two separate broker calls, because Kafka itself exposes "how far the group has committed" and "how far the log currently extends" through two different APIs:

What you needWhere it comes from
The group's committed offset per partitionAdminClient.list_consumer_group_offsets() — an admin-level call, no need to join the group
The partition's current high-water markA real Consumer's get_watermark_offsets() — asks the broker directly for a partition's low/high offsets

Lag itself is just the subtraction between those two numbers, same as Day 18 — today's actual work is calling both APIs correctly and treating the result as a value a script can act on, not a line to read.

3 · Build: scripts/check_consumer_lag.py

Adapted from Day 6's own consumer shape (same BOOTSTRAP/GROUP_ID constants, same "give the exact shape in full" rule for a script whose correctness depends on getting two admin calls right, not on something safe to leave as an exercise):

"""Compute consumer lag per partition for one group, in Python instead of
reading kafka-consumer-groups.sh --describe by eye.

Lag = high-water mark (log-end offset, from a real Consumer's own
get_watermark_offsets) minus the group's committed offset (from
AdminClient.list_consumer_group_offsets). Exits non-zero if any
partition's lag exceeds LAG_THRESHOLD -- the shape a monitoring check or
an Airflow sensor actually calls, not a line a human reads once.
"""
import sys

from confluent_kafka import Consumer, TopicPartition
from confluent_kafka.admin import AdminClient
from confluent_kafka._model import ConsumerGroupTopicPartitions

BOOTSTRAP = "localhost:9092"
TOPIC = "order_events"
GROUP_ID = "warehouse-loader"
LAG_THRESHOLD = 1000


def main():
    admin = AdminClient({"bootstrap.servers": BOOTSTRAP})

    request = ConsumerGroupTopicPartitions(GROUP_ID)
    group_future = admin.list_consumer_group_offsets([request])[GROUP_ID]
    committed = group_future.result()  # ConsumerGroupTopicPartitions

    # A throwaway consumer, never subscribed or joined to any group, used
    # only to ask the broker for each partition's current high-water mark.
    watermark_reader = Consumer(
        {"bootstrap.servers": BOOTSTRAP, "group.id": "lag-checker-throwaway"}
    )

    worst_lag = 0
    print(f"{'PARTITION':<10}{'COMMITTED':<12}{'LOG-END':<10}{'LAG':<8}")
    for tp in committed.topic_partitions:
        if tp.topic != TOPIC:
            continue
        _, high = watermark_reader.get_watermark_offsets(
            TopicPartition(tp.topic, tp.partition), timeout=10.0
        )
        committed_offset = tp.offset if tp.offset is not None and tp.offset >= 0 else 0
        lag = high - committed_offset
        worst_lag = max(worst_lag, lag)
        print(f"{tp.partition:<10}{committed_offset:<12}{high:<10}{lag:<8}")

    watermark_reader.close()

    if worst_lag > LAG_THRESHOLD:
        print(f"ALERT: lag {worst_lag} exceeds threshold {LAG_THRESHOLD}")
        sys.exit(1)
    print(f"OK: worst partition lag is {worst_lag}")


if __name__ == "__main__":
    main()

Two things worth naming out loud, because both are the kind of detail that looks like a typo until you've hit it once. First, confluent_kafka.admin does not re-export ConsumerGroupTopicPartitions in this installed version — it has to come from confluent_kafka._model, confirmed directly against the installed package this round rather than assumed, since the obvious `from confluent_kafka.admin import ConsumerGroupTopicPartitions` raises AttributeError. A leading underscore in a module path is usually a sign to stay away, but here it's the only working import for a class the public admin module's own docstring tells you to use — worth a one-line code comment in your repo so a future you doesn't "fix" it back to the import that fails. Second, list_consumer_group_offsets returns futures, one per group, because the admin API is async under the hood; .result() is what blocks for the real answer, same pattern confluent-kafka uses everywhere in the admin client.

With LAG_THRESHOLD = 1000 that's still OK — four messages behind is normal between batches, not an incident. The threshold is a judgment call tied to how often the consumer actually runs and how large a "normal" gap between runs is, the same kind of threshold-tuning conversation as an SLA breach minutes cutoff (Day 10's sla_threshold_minutes); a consumer that runs continuously might alert past a lag of 50, while one that only runs once an hour might reasonably sit at a few thousand between runs and alert only past a much higher number.

4 · Where this plugs in, without building new infrastructure today

This script is deliberately a leaf, not a new service. Two realistic next steps exist without writing a line of new monitoring code today: a cron-style call from outside Airflow entirely (the honest MVP), or — the shape that actually fits this course's own stack — an Airflow task that runs this script via BashOperator before dbt_build in the real food_delivery_pipeline DAG from Day 7, failing fast with a clear message if the Kafka side is badly behind, rather than letting dbt build run against a warehouse known to be stale. That wiring is a future day's work, explicitly not today's — today's scope is the check itself returning a trustworthy exit code, since an Airflow task calling a script that always exits 0 would be worse than no check at all.

Scope check: no new Docker service, no Prometheus/Grafana, no new topic. One script, two broker calls, one threshold. Exactly the "working level" Kafka depth this course commits to — a real dashboard behind a real alert is an interesting follow-on, not today's build.

Q: "Walk me through how you'd actually monitor Kafka consumer lag in production, not just define it." A strong answer, out loud: "Lag is high-water mark minus committed offset, per partition, and I'd get both numbers programmatically rather than reading a CLI table by hand — AdminClient.list_consumer_group_offsets for the committed side, a real Consumer's get_watermark_offsets for the log-end side. I'd wrap that in a script that exits non-zero past a threshold, because the moment lag monitoring is just a number a human reads occasionally, it doesn't actually catch anything at 2am. The threshold itself depends on how the consumer runs — continuous versus scheduled batches — so it's a judgment call, not a universal constant. And I'd wire the check to run before anything downstream trusts the data it's watching, not as a separate dashboard nobody checks until something's already broken." The signal: naming both actual API calls, not just the subtraction, and connecting the check to a concrete failure mode (stale data silently feeding a report) rather than treating monitoring as a checkbox.
