1 · The SQL you've already been writing has a template language underneath

Every {{ ref('stg_orders') }} and {{ source('raw', 'restaurants') }} you've typed since Day 2 is a call into Jinja, the templating language dbt compiles every model through before a single query reaches Postgres. ref() and source() are just Jinja functions dbt provides — {{ }} drops in a value, {% %} runs control flow like if or for, and it all happens at compile time, on your laptop, before Postgres ever sees a query. Day 8's {% if is_incremental() %} in fct_orders was already this — you were writing Jinja without it being named yet. Today names it and gives you two more tools built on top: a project-wide variable, and a macro.

One habit worth building now: dbt compile renders every model's Jinja to plain SQL without running it, and writes the result to target/compiled/. Whenever a Jinja construct's output isn't obvious, compiling and reading the plain SQL beats guessing:

uv run --project ../dbt_env dbt compile --select mart_delivery_sla

2 · {{ var() }}: pull a magic number out of SQL

mart_delivery_sla.sql (Day 6) has a bare 45 sitting inside a case when — the SLA threshold, in minutes, hardcoded into the query text. That's a real problem the moment anyone asks "what if we measured against 30 minutes instead," because answering means editing SQL and redeploying, not changing a setting. dbt's fix is var(): a named project variable, declared with a default in dbt_project.yml, read from any model with {{ var('name') }}, and overridable per-run from the command line with --vars — no SQL file touched either way.

Declare the default in dbt_project.yml, alongside the models: block Day 8 added:

vars:
  sla_threshold_minutes: 45

Replace the bare 45 in mart_delivery_sla.sql with {{ var('sla_threshold_minutes') }}:

-- models/marts/mart_delivery_sla.sql -- inside the final select
    sum(case when minutes_to_deliver > {{ var('sla_threshold_minutes') }} then 1 else 0 end)::numeric
        / count(*) as share_over_45_min

The column is still named share_over_45_min — renaming it today would ripple into any downstream query already reading that column name, and this lesson's job is making the threshold configurable, not renaming a shipped column. Note that in your head, not in the SQL, for now.

Build normally and the default (45) applies, identical output to before:

uv run --project ../dbt_env dbt build --select mart_delivery_sla

Now override it for one run, with no file edited — this is the entire payoff:

uv run --project ../dbt_env dbt build --select mart_delivery_sla --vars '{sla_threshold_minutes: 30}'

Compile it to see exactly what changed, per Section 1's habit — the rendered SQL should show a literal 30 where {{ var(...) }} was:

uv run --project ../dbt_env dbt compile --select mart_delivery_sla --vars '{sla_threshold_minutes: 30}'
grep -B1 "share_over" target/compiled/food_delivery_pipeline/models/marts/mart_delivery_sla.sql
    sum(case when minutes_to_deliver > 30 then 1 else 0 end)::numeric
        / count(*) as share_over_45_min

{{ target }} is the same idea, one level up: instead of a value you name, dbt exposes the active connection itself as an object — {{ target.name }}, {{ target.schema }}. It's how a project tells dev and CI apart inside SQL without a separate var() for it, since dbt already knows which profile target is active from the --target flag or profile default. This project only has one target so far (dbt_dev), so there's nothing to branch on yet — worth knowing the name for the day a CI profile shows up, which Phase 2a's own spine has coming.

3 · Macros: a Jinja function you define once, call from anywhere

A macro is a reusable Jinja function: define it once in macros/ with {% macro %}...{% endmacro %}, call it from any model with {{ macro_name(args) }}. It's dbt's answer to "this exact SQL fragment appears in two files" — the same DRY instinct Day 8's intermediate layer applied to a whole join, aimed here at a smaller, expression-level piece of logic.

The SLA breach check — "is this duration over the threshold" — is exactly that kind of fragment: mart_delivery_sla.sql needs it today, and a courier-scorecard mart would need the identical check tomorrow if one gets built. Write it once as a macro, give it in full since the {% macro %} syntax itself is new today:

-- macros/is_sla_breach.sql
{% macro is_sla_breach(minutes_column) -%}
{{ minutes_column }} > {{ var('sla_threshold_minutes') }}
{%- endmacro %}

The -%}/{%- whitespace-trim markers matter here, not just style: without them Jinja leaves the newlines and indentation from inside the {% macro %} block in the rendered output, so a call like {{ is_sla_breach('minutes_to_deliver') }} would compile to SQL with a line break in the middle of a case when expression. Still valid SQL either way, but worth trimming so compiled output reads the way you wrote it — the "compile and read the plain SQL" habit from Section 1 is exactly how this gets caught.

Notice the macro itself calls {{ var(...) }} — macros and var() compose, the macro doesn't hardcode the threshold either, it just centralizes the *comparison*, while var() keeps centralizing the *number*. Call it from mart_delivery_sla.sql in place of the raw comparison:

-- models/marts/mart_delivery_sla.sql -- inside the final select
    sum(case when {{ is_sla_breach('minutes_to_deliver') }} then 1 else 0 end)::numeric
        / count(*) as share_over_45_min

Compile and confirm it renders to the exact same plain SQL as Section 2's direct comparison — a macro must be invisible in its output, or something's wrong:

uv run --project ../dbt_env dbt compile --select mart_delivery_sla
grep -B1 "share_over" target/compiled/food_delivery_pipeline/models/marts/mart_delivery_sla.sql
    sum(case when minutes_to_deliver > 45 then 1 else 0 end)::numeric
        / count(*) as share_over_45_min

When a macro makes a project worse: per PLAN.md's own framing of this topic, a macro isn't free. is_sla_breach() earns its place because two real models call it with the identical comparison. A macro with exactly one caller is indirection with no payoff — anyone reading that one model now has to open a second file to understand a one-line comparison, which is strictly worse than reading it inline. And a macro that branches heavily on {% if %} to serve very different callers stops being "one job reused" and starts being an undocumented mini-language only the macro's author can safely edit — Day 8's own "reuse only pays off when the reused piece is generic enough for every caller" finding, applied one layer down from a whole model to a single expression. Before writing a macro, name the second real caller first; if there isn't one yet, write the SQL inline and wait.

Q: "When would you reach for a dbt macro instead of just writing the SQL twice?" A strong answer, out loud: "Only once there's a second real caller — not in anticipation of one. dbt compiles every model through Jinja already, so a macro is just a named, reusable Jinja function, called with curly-brace syntax like ref() or source() are. I'd pull a comparison or expression into a macro when two or more models need the exact same logic, so a change to the rule happens in one file instead of drifting between copies. But a macro with only one caller is pure indirection — it makes the one model harder to read for no reuse payoff. I'd pair it with var() when the thing that's actually varying isn't the logic but a number or threshold inside it, like an SLA minutes cutoff — var() centralizes the value with a project-level default, overridable per run with --vars, without touching SQL at all. The two compose: the macro can call var() internally, so a model reads as one clean line while both the comparison and the number it compares against are each defined in exactly one place." The signal: naming the "second real caller" bar explicitly, not treating macros as always-good DRY.
