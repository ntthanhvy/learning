Foreign key referential actions: what happens to the children

Lesson 2 defined a foreign key as "this row belongs to that row" and stopped there. Lesson 34 leaned on the missing half without explaining it: "either the delete fails outright... or — worse — it was allowed to CASCADE, and every order that account ever placed disappears with it." Today closes that gap — the four things Postgres can do to a child row when its parent disappears, and why picking the wrong one is a design bug, not a syntax detail.

1 · A foreign key is silent about deletes by default

Lesson 2's foreign key only says a child row points at a parent row. It says nothing about what should happen when that parent row is deleted or its key changes — and Postgres won't let you skip the question. Every REFERENCES clause has an answer, whether you wrote one or not:

CREATE TABLE orders (
    id INT PRIMARY KEY,
    account_id INT REFERENCES accounts(id) -- no ON DELETE clause...
);

...silently means ON DELETE RESTRICT: Postgres refuses to delete an accounts row while any orders row still points at it. That's exactly the "delete fails outright" half of Lesson 34's sentence — not a bug, the default behavior nobody named. The referential action is the explicit version of that same choice, spelled out per relationship instead of left to the default.

2 · The four actions, and what each one actually does

ActionWhen the parent row is deletedReach for it when
RESTRICT (default)delete is refused with an errorthe parent must never disappear while dependents exist — force a deliberate decision first
CASCADEevery referencing child row is deleted toothe child has no meaning without its exact parent — it dies with it by definition
SET NULLthe child row's FK column becomes NULLthe child should outlive the parent, just un-link it — the FK column must be nullable
SET DEFAULTthe FK column resets to its declared DEFAULT valuerare — a "fallback parent" must already exist as a real row (e.g. an "Unassigned" category)

Each is written on the foreign key itself:

-- order_items has no meaning without its order — it dies with it
CREATE TABLE order_items (
    order_id INT REFERENCES orders(id) ON DELETE CASCADE,
    product_id INT NOT NULL,
    qty INT NOT NULL
);

-- a comment should survive its author leaving; just show "deleted user"
CREATE TABLE comments (
    id INT PRIMARY KEY,
    author_id INT REFERENCES accounts(id) ON DELETE SET NULL,
    body TEXT NOT NULL
);

ON UPDATE takes the same four actions, for the rarer case where a parent's primary key value itself changes (almost never, if you use a stable generated id) — the same reasoning applies, so this lesson focuses on ON DELETE, the one you'll actually decide on regularly.

Ties to Lesson 34: that lesson picked soft delete for accounts specifically because neither RESTRICT nor CASCADE was the right answer — RESTRICT blocks the "close my account" feature outright, and CASCADE would erase order history a finance report still needs. Soft delete sidesteps the referential-action question entirely: the parent row never actually goes away, so nothing downstream ever fires. That's not a coincidence — soft delete and referential actions are two different answers to the same question ("what happens to the children"), and real schemas mix both depending on the relationship.

3 · A per-relationship judgment call, not one rule for the whole schema

The mistake is treating this as one setting for the whole database instead of one decision per relationship. Lesson 2's own order example has both shapes sitting right next to each other:

  • order_items.order_id → CASCADE. A line item with no order is meaningless — it can't exist independently, so it shouldn't outlive the row it belongs to.
  • orders.account_id → RESTRICT (or soft delete on accounts, per Lesson 34). An order is a legal/financial record — it must never silently vanish just because someone closed their account.

The test that separates them: does the child row mean anything without this exact parent? Yes → CASCADE is honest, not dangerous. No, but the link itself is optional → SET NULL. No, and the child must never lose its parent silently → RESTRICT, and force whoever's deleting to make an explicit decision (soft delete, reassign, or a confirmed cascade in application code).

4 · Handling RESTRICT in application code

A RESTRICT violation isn't a bug to fix — it's Postgres correctly refusing an unsafe delete. The handler's job is to catch that specific error and turn it into a clear response, the same "translate the database error into a named sentinel" shape Lesson 37's translateSerializationFailure used for a different Postgres error code:

// ErrAccountHasOrders is returned when a RESTRICT-protected foreign key
// blocks the delete — checked via errors.Is at the call site, same pattern
// as every other sentinel error in this course.
var ErrAccountHasOrders = errors.New("account still has orders: cannot close")

// closeAccount attempts to delete an account row. If accounts.id is still
// referenced by a RESTRICT foreign key (e.g. orders.account_id), Postgres
// returns a foreign_key_violation (SQLSTATE 23503) instead of deleting —
// translated here into a clear, expected error instead of a raw DB message
// leaking to the caller (Lesson 7's information-disclosure rule, applied
// to a constraint error instead of a 500).
func closeAccount(ctx context.Context, db DB, accountID int64) error {
    _, err := db.ExecContext(ctx, `DELETE FROM accounts WHERE id = $1`, accountID)
    if err == nil {
        return nil
    }
    if isForeignKeyViolation(err) { // checks pgconn.PgError.Code == "23503" in real pgx code
        return ErrAccountHasOrders
    }
    return fmt.Errorf("close account: %w", err)
}

That's the same fold-the-database's-own-guarantee-into-a-named-error move this course keeps returning to: Lesson 35's unique violation, Lesson 37's serialization failure, and now a foreign-key violation — three different Postgres error codes, one shared habit of translating them into sentinels the caller can branch on instead of a raw driver error.

Q: "Your team is designing a `documents` table where each document belongs to a `folder`. What FK behavior would you pick for `documents.folder_id` when a folder is deleted, and why?" A strong answer, out loud: "It depends what deleting a folder is supposed to mean to the user. If 'delete this folder' should delete everything in it — the way a filesystem trash works — CASCADE is honest: the documents genuinely have no home without it. If instead the product wants 'delete this folder' to just ungroup the documents back to some root level, SET NULL is closer, as long as folder_id is nullable and the UI already handles a document with no folder. What I wouldn't do is default to RESTRICT and let users hit a confusing error the first time they try to delete a folder with anything in it — that's a product decision hiding behind a database error." The signal: treating it as a product question first, a constraint syntax question second.
