df.to_sql(): the ETL Load step's SQL half, and its silent traps

Lesson 86 taught pd.read_sql(), the Extract side of moving data between pandas and a database. to_sql() is its write-side mirror — named in the exact same Lesson 8 aside as to_csv, and in Lesson 64's own teaser, but never taught on its own. Re-grepped every lesson body and the glossary for to_sql first and confirmed only those passing mentions exist, zero dedicated coverage. Today closes it: not the happy path (one line), but the three silent traps — an existing-table collision, a default extra index column, and a dtype round-trip that quietly loses information — that mirror Lesson 64's to_csv() traps and Lesson 86's read_sql() trap, now on the Load side.

1 · The SQL bridge: to_sql() is CREATE TABLE + INSERT, in one call

Writing a DataFrame into a database table is the Load half of the ETL shape Lesson 8 named — the destination this time is a table, not a file. df.to_sql(name, conn) does the equivalent of a SQL CREATE TABLE (if the table is new) followed by one INSERT per row, inferring each column's SQL type from its pandas dtype:

orders = pd.DataFrame({"order_id": [1, 2, 3], "amount": [120.0, 35.5, 99.9]})
orders.to_sql("orders", conn, index=False)   # CREATE TABLE orders (...) ; INSERT INTO orders VALUES (...), ...

Mentally this is the write-side cousin of psql's \copy table FROM 'file.csv', except the source is already a DataFrame in memory rather than a file on disk — no intermediate CSV needed, the same no-intermediate-file framing Lesson 86 used for the read direction. Confirmed directly (pandas 3.0.6): to_sql() returns the integer number of rows written, useful for a quick sanity check in a pipeline without a separate SELECT COUNT(*).

2 · if_exists=: the table-already-there decision pandas refuses to guess

The second call to to_sql() against the same table name is where the real decision lives — pandas will not silently guess what to do about a table that's already there:

if_exists=BehaviorSQL equivalent
"fail" (default)raises ValueError, writes nothingCREATE TABLE with no IF NOT EXISTS
"replace"drops the whole table, recreates it, then insertsDROP TABLE + CREATE TABLE + INSERT
"append"keeps the existing table and schema, inserts new rowsplain INSERT INTO

Confirmed directly (pandas 3.0.6): calling to_sql() a second time with no if_exists= at all raises ValueError: Table 'orders' already exists. immediately — the if_exists="fail" default is a deliberate fail-loudly choice, not an oversight — it forces an explicit choice every time rather than silently picking one of the two very different behaviors below. "replace" and "append" look similar in a quick test with identical data, but they are not interchangeable in a real pipeline: "replace" destroys the table's existing schema and any rows a different process put there, while "append" keeps both and can duplicate rows if the same batch is written twice — confirmed directly, re-running an identical to_sql(if_exists="append") call doubles every row with zero complaint, no uniqueness check of any kind.

3 · The first trap: to_sql()'s default also writes an extra index column

This is the exact same trap Lesson 64 named for to_csv(), now on the SQL side: index= defaults to True, writing the DataFrame's row index as its own real column:

df = pd.DataFrame({"amount": [120.0, 35.5, 99.9]}, index=["a", "b", "c"])
df.to_sql("t1", conn)              # default index=True
pd.read_sql("SELECT * FROM t1", conn).columns.tolist()
-- ['index', 'amount']    <- the row index came back as a REAL column named "index"

df.to_sql("t2", conn, index=False)   # the fix
pd.read_sql("SELECT * FROM t2", conn).columns.tolist()
-- ['amount']

Confirmed directly (pandas 3.0.6): the column is literally named index in the created table — plausible-looking, easy to miss in a wide table, and a problem the moment something downstream runs SELECT * expecting only the real business columns. Exactly the same shape as to_csv()'s default Unnamed: 0 column from Lesson 64, just a different literal name because SQL table columns need a real identifier rather than CSV's blank header slot. index=False is correct almost every time the index is still the default RangeIndex; keep index=True (or pass index_label=) only when the index is a real, meaningful key worth persisting as its own column.

4 · The second trap: the dtype round-trip quietly loses information

A SQL column type is a coarser bucket than a pandas dtype, so writing then reading back doesn't always return the same dtype that went in:

df3 = pd.DataFrame({
    "order_id": pd.array([1, 2, None], dtype="Int64"),
    "status": pd.Categorical(["paid", "paid", "refunded"]),
})
df3.dtypes
-- order_id      Int64
-- status     category

df3.to_sql("t3", conn, index=False)
pd.read_sql("SELECT * FROM t3", conn).dtypes
-- order_id    float64   <- nullable Int64 demoted to plain float64
-- status          str   <- category demoted to plain string, no categories remembered

Confirmed directly (pandas 3.0.6): this is Lesson 86's exact trap arriving from the opposite direction — the nullable Int64 with a real gap gets written as a SQL INTEGER column, and reading it back with no dtype_backend="numpy_nullable" on the read_sql() side upcasts it to float64 again, the identical "NumPy's default integer has no missing-value slot" story from Lessons 51/84/86. category fares worse — SQL has no categorical column type at all, so it's written as plain text and the category labels/ordering are gone the moment it round-trips; nothing on the read side can bring that back except re-declaring astype("category") manually afterward. Neither loss raises an error or a warning — both are silent, and both are fixed the same way Lesson 86 already taught: declare the wanted dtype explicitly on the way back out with dtype_backend= or astype(), since to_sql()/read_sql() round-trips never restore it on their own.

5 · method="multi" and chunksize=: writing a large DataFrame efficiently

The default to_sql() write issues one INSERT statement per row, which is slow at real scale. method="multi" batches many rows into a single multi-row INSERT statement instead, pairing naturally with chunksize= to cap how many rows go into each batch:

df.to_sql("big_table", conn, index=False, if_exists="append",
          method="multi", chunksize=1_000)

Confirmed directly (pandas 3.0.6, 20,000-row test): method="multi" with chunksize=1_000 ran noticeably faster than the row-by-row default on identical data, with the same final row count — the SQL-side cousin of Lesson 86's own chunksize= on the read side, except here it batches the write instead of streaming the read. The trade-off worth naming out loud in an interview: a multi-row batch commits or fails as one unit, so a bad value deep in a 1,000-row batch rolls back that whole batch, not just the one bad row — a different failure granularity than the slower one-row-at-a-time default.

Q: "You've got a cleaned DataFrame ready to land in a database table. Walk me through to_sql()." A strong answer, out loud: "First decision is if_exists= — it defaults to 'fail' and raises ValueError if the table's already there, which is deliberate: pandas won't guess between replace, which drops and recreates the whole table, and append, which keeps the schema and existing rows but has no uniqueness check, so re-running the same append blindly duplicates every row. Second, I'd pass index=False explicitly unless the index is a real meaningful key — the default writes it as a literal extra column named 'index', the same trap to_csv() has with its default 'Unnamed: 0' column. Third, I'd expect dtype loss on the round-trip: a nullable Int64 column with a gap comes back as float64 unless I ask for dtype_backend='numpy_nullable' on the read side, and a category column loses its categories entirely since SQL has no categorical type at all — both silent, no error. And if the write is large, I'd use method='multi' with a chunksize= to batch the inserts instead of one row at a time, knowing a bad row now fails its whole batch rather than just itself." The signal: naming the if_exists='fail' default, the index='index' column, and the dtype round-trip loss unprompted — the three places a first-time to_sql() call looks fine and isn't.
