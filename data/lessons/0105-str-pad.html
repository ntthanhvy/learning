Series.str.pad(): fixed-width alignment, and the sign trap zfill() doesn't have

Lesson 104 closed the standing .str.strip() pick and carried forward three named candidates from the same text-cleanup family: str.pad()/str.title()/str.join(). Re-grepped all three case-insensitively across every lesson body and the glossary file before picking — all three are still genuine zero-hit gaps, never taught. Picked .str.pad() over its siblings: it is the direct SQL LPAD()/RPAD() equivalent (a classic interview ask — zero-padding IDs, zip codes, invoice numbers to a fixed width), and direct probing turned up a sharp, docs-contradicting trap involving its zfill() sibling that neither .str.title() nor .str.join() has an equivalent of.

1 · Fixed-width alignment: SQL's LPAD()/RPAD(), vectorized

SQL's LPAD(col, width, fillchar) and RPAD(col, width, fillchar) pad a text column out to a fixed width. Pandas' equivalent is Series.str.pad() — one call pads the whole column at once:

import pandas as pd

s = pd.Series(["7", "42", "123"])

s.str.pad(width=5)
# ['    7', '   42', '  123']    -- side="left" is the default, pads with spaces

s.str.pad(width=5, side="right")
# ['7    ', '42   ', '123  ']    -- SQL's RPAD()

s.str.pad(width=5, side="both")
# ['  7  ', '  42 ', ' 123 ']    -- centers the string, extra space goes right when odd

s.str.pad(width=5, fillchar="0")
# ['00007', '00042', '00123']    -- zero-padding an ID column, a common interview ask

Confirmed directly (pandas 3.0.6): width= is a minimum width, not an exact one — a string already as long as or longer than width passes through completely unchanged, confirmed with pd.Series(["123"]).str.pad(width=1) returning "123" untouched rather than truncating. fillchar= must be exactly one character — passing a multi-character string like "00" raises TypeError: fillchar must be a character, not str rather than repeating or truncating it. An invalid side= value (anything other than "left"/"right"/"both") raises ValueError: Invalid side.

2 · The zfill() trap: the docs call it "equivalent", direct testing says otherwise

Pandas also ships Series.str.zfill(), a dedicated zero-pad shortcut. The official pandas docs describe it as "equivalent to Series.str.pad(side='left', fillchar='0')" — confirmed directly, that equivalence holds for plain positive-looking strings, but breaks exactly on a leading minus sign:

s = pd.Series(["-7", "42"])

s.str.zfill(5)
# ['-0007', '00042']    -- sign-aware: the '-' stays first, zeros go between sign and digits

s.str.pad(width=5, side="left", fillchar="0")
# ['000-7', '00042']    -- NOT sign-aware: '-' is just another character, pushed rightward

Confirmed directly and cross-checked against the official docs page for Series.str.pad() (which names zfill() as the documented "equivalent" call) and the docs page for Series.str.zfill() itself: the two calls agree on every plain numeric-looking string, but disagree specifically the moment a string starts with "-" — zfill() treats the sign as special and keeps it in front of the padding, exactly like Python's own built-in str.zfill(), while str.pad(fillchar="0") has no concept of a sign at all and simply fills from the left, producing a nonsensical "000-7" that no longer reads as a negative number at a glance.

This is MISSION.md's "read code and predict its output" skill, applied to a case where the official docs' own wording ("equivalent to") is only true for the common case. If a source column can ever hold a negative number represented as a zero-padded string — a signed ID, a temperature, an accounting adjustment — reach for .str.zfill(), not .str.pad(fillchar="0"), specifically because of the sign. For everything else (non-numeric fixed-width alignment, custom fill characters, centering), .str.pad() is the general tool and zfill() is just its sign-aware zero-fill special case.

3 · NaN and non-string dtypes: the same shape as every other .str method

Confirmed directly, pandas 3.0.6 — the same pass-through/raise split as .str.strip() (Lesson 104) and np.clip() (Lesson 102):

pd.Series(["7", np.nan, "42"]).str.pad(width=5, fillchar="0")
# 0    00007
# 1     NaN      -- passes straight through untouched, never padded or an error
# 2    00042
# dtype: str

pd.Series([1, 2, 3]).str.pad(width=5)
# AttributeError: Can only use .str accessor with string values, not integer

Q: "You need to zero-pad an account_id column to 8 digits for an export file. How would you do it, and what would you watch for?" A strong answer, out loud: "I'd use df['account_id'].astype(str).str.pad(width=8, fillchar='0') — or just .str.zfill(8), which is the dedicated shortcut for exactly this case. The one thing I'd watch for is sign: if account_id could ever be a signed number represented as a string, like '-42', str.pad(fillchar='0') isn't sign-aware and would produce '000-042' — garbage — while str.zfill() specifically keeps the minus sign in front. So for pure zero-padding of possibly-signed values I'd reach for zfill(), and save str.pad() for everything else: custom fill characters, right-padding, or centering a column for a fixed-width report." The signal: knowing zfill() isn't just a shorter spelling of pad() — it is a genuinely different, sign-aware behavior for the one case that matters most for IDs.
