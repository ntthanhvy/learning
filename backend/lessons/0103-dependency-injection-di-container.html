Dependency injection: who hands a handler its database?

Every handler needs things it didn't create itself: a database connection, an HTTP client, a logger. Someone has to hand those over. Dependency injection is just a name for that handover. Go does it by hand, in plain code you can read top to bottom. .NET builds a whole subsystem around it — the DI container — and once you can name what it's doing, ASP.NET Core startup code stops looking like magic.

1 · The frontend version of this problem

You've solved this exact problem before. A deeply nested component needs the current user, or a theme, or an API client. Passing it down as props through five layers that don't use it is prop drilling. React Context exists so a component can declare "I need this" and have it appear, without every layer in between forwarding it manually. The provider at the top decides what gets supplied; the component in the middle just says what it needs and leaves it at that.

Backend code has the same shape. A handler needs a database connection. Something, somewhere, has to create that connection and get it to the handler. "Who creates it, and how does it arrive?" is the whole question dependency injection answers — Context is one answer for the frontend tree; constructor injection is the backend answer, by hand in Go or via a container in .NET.

2 · Go's answer: write the wiring yourself

Go has no DI container in the standard library, and idiomatic Go rarely reaches for one. The pattern is constructor injection: a struct declares what it needs as fields, a constructor function takes those as parameters, and main() is where everything actually gets built and connected.

type OrderHandler struct {
    db     *sql.DB
    logger *slog.Logger
}

func NewOrderHandler(db *sql.DB, logger *slog.Logger) *OrderHandler {
    return &OrderHandler{db: db, logger: logger}
}

func (h *OrderHandler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
    // h.db and h.logger are already there -- handler never built them itself
}

func main() {
    db := mustOpenDB()
    logger := slog.Default()
    handler := NewOrderHandler(db, logger) // the wiring happens here, once, by hand
    http.Handle("/orders/", handler)
    http.ListenAndServe(":8080", nil)
}

Nothing here is hidden. If you want to know where db came from, you read main(). The cost shows up as the app grows: every new handler means another line in main() wiring its dependencies by hand, and if ten handlers all need the same db and logger, you're passing the same two values ten times.

3 · .NET's answer: register once, let the container resolve

ASP.NET Core ships a DI container as a core framework piece, not an add-on. Startup code registers each service once; the container resolves it automatically wherever it's asked for — usually as a constructor parameter, same shape as the Go example, just filled in by the framework instead of by you.

// Program.cs -- registration happens once, at startup
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddDbContext<AppDbContext>(opts =>
    opts.UseNpgsql(connectionString));
builder.Services.AddScoped<IOrderRepository, OrderRepository>();
var app = builder.Build();

// OrderController.cs -- ASP.NET Core resolves both constructor params for you
public class OrderController : ControllerBase {
    private readonly IOrderRepository _repo;
    public OrderController(IOrderRepository repo) { _repo = repo; }

    [HttpGet("{id}")]
    public IActionResult Get(int id) {
        var order = _repo.Find(id);
        return order is null ? NotFound() : Ok(order);
    }
}

Nobody calls new OrderController(...) anywhere. The framework sees an incoming request, needs an OrderController, looks at its constructor, sees it needs an IOrderRepository, checks the registration from Program.cs, and builds the chain automatically. This is why ASP.NET Core constructors are full of interface parameters with no visible caller — the container is the invisible caller.

4 · The part that actually matters: lifetime

The registration call name — AddScoped, AddSingleton, AddTransient — isn't decoration. It's a service lifetime, and picking the wrong one is a real, reviewable bug class in .NET PRs.

LifetimeOne instance lives for...Go equivalent
Transienta single resolution — a new one every time it's requested, even twice in the same requestcalling NewThing() fresh, inline, every time
Scopedone HTTP request — shared by everything resolved during that request, then discardeda value created once near the top of a handler, passed down to whatever it calls within that same request
Singletonthe whole application process — created once, reused forevera package-level variable set up once in main(), like the db above

EF Core's DbContext is registered Scoped by default, and that default is load-bearing: a DbContext tracks the entities it's loaded during one request (change tracking), and that record should not leak into the next, unrelated request or get shared across concurrent requests touching the same instance.

Trap: the captive dependency. The container will let you register a Singleton that takes a Scoped service (like DbContext) as a constructor parameter. The first time that singleton is built, it captures whichever request's scoped instance happened to be around — then holds onto it forever, handing that one stale, eventually-disposed DbContext to every future request. This is called a captive dependency, and it fails in production in a way that's hard to reproduce locally (works fine on the first request, degrades or crashes later). In review: any Singleton constructor taking a Scoped or Transient parameter is worth a second look.

5 · Why Go skips the container and .NET doesn't

This isn't one ecosystem being "better" — it's a trade-off, and both sides know it.

  • Go's bet: explicitness over convenience. A small number of long-lived services (one db, one logger) rarely justifies a container; reading main() should tell you the whole dependency graph.
  • .NET's bet: ASP.NET Core apps tend to have many more moving pieces wired through middleware, filters, and framework internals (auth handlers, EF Core, logging providers, SignalR hubs from Lesson 102) — enough that hand-wiring every constructor call would be its own maintenance burden. The container also lets the framework itself register things you never see, like HttpContext accessors.

Both ecosystems still do constructor injection — the difference is only who calls the constructor: you, by hand, in Go; the container, automatically, in .NET.

Q: "What's dependency injection, and what do the DI container lifetimes mean?" A strong answer, out loud: "Dependency injection means a piece of code receives what it needs through its constructor instead of creating it itself — Go does that by hand in main(); ASP.NET Core automates it with a container you register services into once at startup. The lifetime you register a service with controls how long one instance lives: Transient is a new instance every time, Scoped is one per HTTP request — that's EF Core's DbContext default, because of change tracking — and Singleton is one for the app's whole lifetime. The bug to watch for is a captive dependency: a Singleton holding onto a Scoped instance it captured once, serving that same stale instance to every later request." The signal: you can name the three lifetimes without hesitating, and you know a real failure mode, not just the vocabulary.
