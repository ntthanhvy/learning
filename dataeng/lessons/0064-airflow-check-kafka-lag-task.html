1 · The gap: a correct script with nowhere to run

Day 37 built scripts/check_consumer_lag.py deliberately as "a leaf, not a new service" — a script that computes consumer lag the same way Day 18 defined it, and exits non-zero past a threshold, specifically so something else could call it. Its own Section 4 named the realistic next step and stopped short of building it: wire it into the real DAG via BashOperator, before dbt_build, so a consumer that's stopped committing — crashed, OOM-killed, stuck in a retry loop, Day 37's own examples — fails the pipeline fast instead of letting dbt build run its full test suite against raw.order_events that nothing has actually confirmed is current.

That gap sat unbuilt for twenty-seven days while this DAG grew around it: Day 45 added check_dead_letters after dbt_build, Day 54 added max_active_runs/dagrun_timeout, Day 56 added max_consecutive_failed_dag_runs. Every one of those changes assumed the DAG's shape was load_raw >> dbt_build >> check_dead_letters_task and left it there. Today is the first lesson to insert a task in the middle of that chain rather than appending to either end, which is worth noticing as its own small design question: where a check belongs in a DAG is not just "does it work," it's "what should it block if it fails."

2 · Why the lag check belongs before dbt_build, not after it

Day 45's check_dead_letters and Day 46's real threshold on it both run after dbt_build, on purpose, with trigger_rule="all_done" — a health check that should report the same way whether the build it's reporting on passed or failed. Today's task is a different shape entirely: a quality gate: lag measures whether the Kafka consumer has actually kept the warehouse's raw.order_events table current before any dbt model reads from it. Running the lag check after dbt_build would mean dbt has already built fct_orders and mart_delivery_sla against data nothing yet confirmed was fresh — the check would tell you the problem one step too late, after the stale marts already exist and dbt's own tests have already passed against rows that were simply incomplete, not wrong.

Placed before dbt_build instead, with Airflow's default all_success trigger rule (unchanged — today adds a task, it doesn't touch any existing trigger rule), a failing lag check stops dbt_build from running at all, the same "don't build marts on data that failed to load" argument Day 45 already made about load_raw itself, just one step later in the chain and checking freshness instead of presence. check_dead_letters and check_kafka_lag now sit on either side of dbt_build in this DAG, naming the same distinction two different ways: a gate upstream prevents, a report downstream only describes.

3 · Build: check_kafka_lag, a BashOperator calling Day 37's script unchanged

In your food-delivery-pipeline repo, edit dags/food_delivery_pipeline.py — the same file Day 7 wrote and Days 35, 45, 46, 47, 51, 54, 56 and 61 each added to. Add one new task, and one line changing how the existing tasks connect:

# inside the existing `with DAG(...) as dag:` block, between load_raw and dbt_build:
check_kafka_lag = BashOperator(
    task_id="check_kafka_lag",
    bash_command="uv run --with confluent-kafka python3 /opt/scripts/check_consumer_lag.py",
    # no retries, no callback, no trigger_rule override -- Day 37's script
    # is unchanged, and the default all_success is exactly what's wanted:
    # dbt_build should never run if this task doesn't exit 0 first.
)

# was: load_raw >> dbt_build >> check_dead_letters_task  (Day 45)
load_raw >> check_kafka_lag >> dbt_build >> check_dead_letters_task

Two choices worth defending out loud, because both look arbitrary until named. First, no retries on check_kafka_lag, unlike dbt_build's retries=2 from Day 35: lag doesn't usually self-heal in the seconds a retry would wait, and retrying a slow-but-correct consumer's lag check a couple of times before giving up would just delay discovering a real problem, not fix one — Day 35's retry logic bridges to backend's transient-vs-permanent-failure framing, and a stuck consumer is the permanent case here, not the transient one. Second, check_kafka_lag gets no on_failure_callback of its own; Day 61's callback mechanism is already proven out on dbt_build and would attach to this task exactly the same way if this portfolio ever wires a real alert, so today doesn't re-derive it — the task's own non-zero exit code, visible in the Airflow UI the moment all_success stops dbt_build from starting, is the whole signal this round needs.

uv run --with confluent-kafka python3 /opt/scripts/check_consumer_lag.py assumes the script is mounted into whatever container actually runs this BashOperator, at /opt/scripts/ — the same mount-path convention Day 7's own dbt_build task already uses for /opt/dbt. Adjust the path to wherever your compose setup actually bind-mounts scripts/; the task itself doesn't care, as long as the container it runs in can reach both the script and the Kafka broker.

5 · What this closes, and what it still doesn't

This is the same move Day 58 made for Day 55's deferred on_lost, Day 61 made for Day 35's deferred on_failure_callback, and Day 62 made for Day 41's deferred replay workflow: find a lesson's own named, concrete, unbuilt next step and build exactly that, rather than scanning for a brand-new topic. The difference today is that the gap crossed threads — Day 37 is a Kafka lesson, and closing its own named gap meant editing the Airflow DAG, not writing more Kafka code. That is itself a fact worth saying in an interview: a working pipeline's actual seams are where one tool's output becomes another tool's precondition, and "which tool teaches this" stops mattering once the two are wired together in one DAG.

What's still open: check_kafka_lag's failure is visible in the Airflow UI and in dbt_build simply never starting, but nothing pages a human yet — Day 61's on_failure_callback mechanism would attach here directly if that's ever wanted, the same "named, not built" shape this course has used honestly several times now rather than bolting on a second feature this round. LAG_THRESHOLD = 1000 also still lives as a hardcoded constant inside Day 37's script, not an Airflow Variable the way Day 38's growth-check cursor is — tunable without a redeploy is a real improvement, just not today's.

Q: "You have a Kafka consumer landing events into a warehouse, and a daily dbt job that builds marts off that warehouse. What stops dbt from quietly building on stale data if the consumer falls behind or dies?" A strong answer, out loud: "Nothing, by default — dbt has no way to know the consumer even exists, it just reads whatever rows are sitting in the table. I'd add a task before the dbt build step that checks consumer lag programmatically — high-water mark minus committed offset, per partition — and exits non-zero past a threshold. Wired with Airflow's default all_success trigger rule, a failing lag check stops the dbt task from ever starting, so a dead or badly-behind consumer fails the pipeline visibly and early, instead of letting a full dbt build run, pass its own tests, and publish marts built on data that was simply incomplete. The key design choice is where that check sits in the DAG: after the build, like a dead-letter count, it's a health report; before the build, like this one, it's a gate that actually prevents bad output rather than just describing it after the fact." The signal: naming trigger-rule placement as a deliberate decision with two different right answers for two different kinds of check, not treating "add a check somewhere" as sufficient.
