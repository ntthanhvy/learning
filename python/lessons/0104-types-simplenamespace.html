types.SimpleNamespace: attribute access without a class

A plain dict loaded from JSON reads awkwardly — record["name"], record["address"]["city"] — every field wrapped in brackets and quotes. Day 7's dataclass fixes that with real record.name dot access, but it demands a class declared up front, with every field named and typed before any data exists. Sometimes there is no fixed shape worth declaring — a one-off script unpacking whatever a config file happens to contain, or a quick object to pass a handful of named values around. The types.SimpleNamespace class is exactly that: dot access on arbitrary data, with no class declaration at all.

1 · Building one: any keywords become attributes

types.SimpleNamespace(**kwargs) takes any set of keyword arguments and stores each one as a plain attribute, immediately readable with dot syntax:

import types

ns = types.SimpleNamespace(name="Ana", age=30)
print(ns.name, ns.age)      # Ana 30 -- confirmed live
print(ns)                   # namespace(name='Ana', age=30) -- confirmed live

There is no class to define first and no fixed set of expected names — any keyword at all becomes an attribute. New ones can be added, changed, or removed after construction too, exactly like any other plain object's instance instance __dict__ (Day 1's object model, not a new rule):

ns.city = "Hanoi"          # add a new attribute after construction
print(ns)                        # namespace(name='Ana', age=30, city='Hanoi') -- confirmed live
print(vars(ns))                  # {'name': 'Ana', 'age': 30, 'city': 'Hanoi'} -- confirmed live

del ns.city
print(ns)                        # namespace(name='Ana', age=30) -- confirmed live, city removed

vars(ns) (or ns.__dict__ directly) exposes the exact backing dict — types.SimpleNamespace genuinely is "a dict with dot access," confirmed live, not just an analogy.

2 · Reaching into it wrong: a plain AttributeError

Asking for an attribute that was never set raises the same error any ordinary object raises for a missing attribute — not KeyError, since there is no bracket lookup involved at all:

try:
    ns.missing
except AttributeError as e:
    print(e)   # 'types.SimpleNamespace' object has no attribute 'missing' -- confirmed live

That is the trade against a plain dict: a typo'd key like record["nmae"] is also a KeyError, same category of failure, but a dict offers .get(key, default) for a graceful fallback (Day 3) — SimpleNamespace has no equivalent; a missing attribute is always an outright error, never a quiet default.

3 · The real use: JSON without declaring a class first

json.loads() accepts an object_hook — a function called on every JSON object as it's parsed. Passing types.SimpleNamespace itself turns every nested JSON object into dot-accessible attributes, recursively, with zero class declarations anywhere:

import json, types

raw = '{"name": "Ana", "address": {"city": "Hanoi"}}'
person = json.loads(raw, object_hook=lambda d: types.SimpleNamespace(**d))

print(person.name)            # Ana -- confirmed live
print(person.address.city)    # Hanoi -- confirmed live, the nested object too

This is the whole reason the class exists: a dataclass needs name, age, and every other field named and typed before any JSON arrives — exactly right when the shape is known and worth enforcing (an API's request body, Day 7's records). SimpleNamespace is right when the shape is whatever today's data happens to contain, and declaring it up front would be pure overhead for a one-off script.

4 · Where it stops: no enforcement at all

Confirmed directly, side by side: a @dataclass built with no special options still allows a brand-new attribute after construction, same as SimpleNamespace — that freedom is not what tells them apart. What does tell them apart is required fields. A dataclass's __init__ demands every declared field or raises TypeError immediately:

from dataclasses import dataclass

@dataclass
class Person:
    name: str
    age: int

try:
    Person(name="Ana")     # age is missing
except TypeError as e:
    print(e)   # missing 1 required positional argument: 'age' -- confirmed live

ns_empty = types.SimpleNamespace()   # confirmed live -- no error, no fields required at all

A SimpleNamespace() with zero keywords is perfectly valid. There is no required shape, no type checking on any value, and no way to list "what fields does this have" without just inspecting one live instance's __dict__ — the price of skipping the declaration entirely.

Where pandas/NumPy go from here: nowhere directly — types.SimpleNamespace is a single plain object, not a collection, and has no row/column structure of any kind. The nearest pandas analog, a Series exposing its values by attribute-style access in some cases, is a different mechanism entirely (backed by an index, not a fixed set of keyword names) and is data/'s territory, not demonstrated here.
