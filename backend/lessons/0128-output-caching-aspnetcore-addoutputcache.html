Output caching, now in C# too

Lesson 127's own scope line named two things it deliberately skipped: ASP.NET Core's Response Caching Middleware and its newer Output Caching Middleware, calling both "a separate, higher-level concern — a server-side cache that actually stores and serves response bodies, built on top of these same header values rather than being the header mechanism itself." Today picks up that thread: not the Cache-Control header itself anymore, but a middleware that decides, stores, and serves whole responses.

1 · Two middlewares, two different questions

ASP.NET Core actually ships two separate answers to "cache this response server-side," and they ask different questions:

  • Response Caching Middleware (AddResponseCaching()/UseResponseCaching()) asks: "does this response's own Cache-Control header say it's cacheable?" It only stores a response if the response itself is marked public, respects max-age/no-store/private the same way a compliant HTTP proxy would, and refuses anything with an Authorization or Set-Cookie header. It is Lesson 127's CacheControlHeaderValue given a place to actually land, enforced by code instead of trusted to whatever a downstream proxy chooses to honor.
  • Output Caching Middleware (AddOutputCache()/UseOutputCache()) asks a completely different question: "does my own app-configured policy say to cache this?" It ignores the response's Cache-Control header entirely and instead stores whatever a policy written in C# tells it to, independent of HTTP semantics. Microsoft's own docs are blunt about which one to reach for in a typical API or UI app: output caching is "a better approach," because "the configuration determines what to cache independent of HTTP headers" — no fighting a browser that sends Cache-Control: no-cache on every refresh.

Lesson 9's three caching layers (HTTP header, application cache, DB buffer cache) didn't have a slot for either of these — both middlewares sit inside the server process, between routing and the handler, which makes them a fourth shape: a server-side cache of entire response bodies, configured by the app rather than negotiated over HTTP.

2 · Wiring it up and picking an endpoint

Output caching needs both a service registration and a pipeline step, then an explicit opt-in per endpoint — nothing is cached just because the middleware is present:

builder.Services.AddOutputCache();
// ... later, after building the app:
app.UseOutputCache();

app.MapGet("/products/{id}", GetProduct).CacheOutput();

That single .CacheOutput() call opts one endpoint in, using the default caching policy: only 200 responses, only GET/HEAD, never a response that sets a cookie, never a response to an authenticated request. The same [OutputCache] attribute does the same thing on a controller action.

3 · Policies: expiry, and controlling the cache key

A single default expiry (one minute) rarely fits every endpoint, so named policies configured once at startup let different endpoints opt into different rules:

builder.Services.AddOutputCache(options =>
{
    options.AddBasePolicy(b => b.Expire(TimeSpan.FromSeconds(10)));
    options.AddPolicy("ByCulture", b => b.SetVaryByQuery("culture"));
});

app.MapGet("/catalog", GetCatalog).CacheOutput("ByCulture");

SetVaryByQuery is the policy-builder answer to a problem Lesson 127's own typed headers never had to solve: by default the whole URL — including every query string — is part of the cache key, so /catalog?culture=en and /catalog?culture=vi are correctly cached as two separate entries. Naming culture explicitly keeps the key scoped to the one query parameter that actually changes the response, instead of accidentally fragmenting the cache over every unrelated query string a client happens to send.

4 · Where Lesson 126's ETag comes back

Output caching doesn't replace Lesson 126's ETag/If-None-Match pattern — it reuses it. If a handler sets an ETag header before CacheOutput() returns the response, a later request carrying a matching If-None-Match gets a 304 Not Modified instead of the cached body being resent in full:

app.MapGet("/report", (context) =>
{
    context.Response.Headers.ETag = $"\"{reportVersion}\"";
    return WriteReport(context);
}).CacheOutput();

This is the same ETag-driven revalidation Lesson 126 covered — output caching just adds that the 304 can now be served without even running the handler again, since the response is already sitting in the cache store.

Frontend-habit trap: a frontend dev reaching for stale-while-revalidate in React Query or a service worker is solving the same "serve something now, verify freshness in the background" problem — but that's a client-side cache deciding what it trusts. Output caching is the server deciding, for every client, what it's willing to hand out without recomputing — the two aren't the same cache and don't need to agree with each other.

Scope line

This lesson covers AddOutputCache()/UseOutputCache(), the default caching policy, CacheOutput()/[OutputCache], and policy-level Expire()/SetVaryByQuery() — plus naming Response Caching Middleware as the sibling that keys off the Cache-Control header instead. It does not cover tag-based eviction (Tag()/IOutputCacheStore.EvictByTagAsync), the Redis-backed IOutputCacheStore for multi-instance consistency, or writing a custom IOutputCachePolicy — real features, each a reasonable future lesson, out of scope for a first pass at the middleware's basic shape.
