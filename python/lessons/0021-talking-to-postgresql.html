Talking to PostgreSQL from Python

Day 19's get_db() dependency returned a fake {"conn": "fake-db"} stand-in, on purpose — the real thing needed Day 20's async/await underneath it first. Today get_db() becomes real: a DB-API connection and cursor talking to a real PostgreSQL server through psycopg, wired into FastAPI the exact way Day 19 already showed — one dependency, resolved once per request, that every handler needing the database can share.

Bridge from SQL: you already know the language spoken over this connection — SELECT/INSERT/WHERE haven't changed. What's new is the Python side of the wire: opening the connection, sending a query with placeholders instead of pasted-in values, and pulling rows back out as Python tuples or dicts.

1 · Connecting and running a query

psycopg.connect(...) opens one connection to a running PostgreSQL server; a cursor pulled from that connection is what actually sends SQL and reads rows back:

import psycopg

with psycopg.connect("postgresql://user:pw@localhost/mydb") as conn:
    with conn.cursor() as cur:
        cur.execute("SELECT id, name FROM users WHERE id = %s", (7,))
        row = cur.fetchone()          # one tuple, or None
        print(row)                     # (7, 'alice')

Both with blocks are Day 6's context manager, doing exactly what it always does: the cursor closes when its block ends, and the connection closes — releasing the network socket — when its own block ends, guaranteed even if execute() raises partway through. fetchone() reads a single row (or None if there isn't one); fetchall() reads every remaining row as a list of tuples. Nothing here is a new idea — it's Day 6's file-handle pattern, aimed at a network connection instead of a file on disk.

2 · Placeholders, not string-building — this is where injection lives

The %s in cur.execute("... WHERE id = %s", (7,)) is a placeholder, not Python string formatting — execute() sends the query text and the values tuple to the server as two separate pieces, so a value can never be interpreted as SQL syntax, no matter what characters it contains. This is exactly the defense the backend/ course's own SQL injection lesson names abstractly (parameterized queries over pasted-in values) — today is where that concept lands in actual Python code, not new theory.

# DANGEROUS - never do this: builds SQL out of untrusted input
cur.execute(f"SELECT * FROM users WHERE name = '{name}'")

# SAFE - the placeholder, always
cur.execute("SELECT * FROM users WHERE name = %s", (name,))

Confirmed directly against a real table: passing name = "x' OR '1'='1" through the f-string version rewrites the query into matching every row; the same value through the placeholder version is sent as one literal string to compare against name, matching zero rows — the input never touches the query's grammar. The rule from the earlier line: the SQL string passed to execute() is written once, by you, and never contains anything read from a request.

3 · A connection as a Depends() dependency

Day 19's get_db() returned {"conn": "fake-db"} specifically so today could swap in the real thing without changing anything else about how handlers use it — same Depends(get_db) call, same one-per-request guarantee:

from fastapi import FastAPI, Depends
import psycopg

app = FastAPI()

def get_db():
    with psycopg.connect("postgresql://user:pw@localhost/mydb") as conn:
        yield conn              # handler runs here, using conn
                                # conn closes when the request ends

@app.get("/users/{user_id}")
def get_user(user_id: int, conn = Depends(get_db)):
    with conn.cursor() as cur:
        cur.execute("SELECT id, name FROM users WHERE id = %s", (user_id,))
        row = cur.fetchone()
        return {"id": row[0], "name": row[1]}

A yield-based dependency is Day 11's pytest fixture idea again, one layer down: the code before yield is setup (open the connection), get_user runs while paused at yield, and the code after yield — here, the with block simply ending — is teardown (close the connection), guaranteed to run after the handler finishes, success or exception. Every handler needing the database just adds conn = Depends(get_db); none of them opens a connection by hand.

4 · Real production code uses a pool, and goes async

Opening a fresh TCP connection to PostgreSQL on every single request is slow and wastes server resources — real services keep a connection pool of already-open connections ready and hand one out per request instead, exactly the resource-reuse idea Day 19's callout named without building it. psycopg_pool.ConnectionPool does this: created once at startup, its .connection() gives out an existing connection instead of opening a new socket each time. And since a query is pure I/O — the exact case Day 20 said async def pays off for — psycopg ships an async-native pair, AsyncConnection and AsyncConnectionPool, so a query awaits the network round trip instead of blocking the whole event loop while PostgreSQL thinks:

import psycopg

async def get_user_async(user_id: int):
    async with await psycopg.AsyncConnection.connect("postgresql://...") as conn:
        async with conn.cursor() as cur:
            await cur.execute("SELECT id, name FROM users WHERE id = %s", (user_id,))
            return await cur.fetchone()

async with is with for an object whose __aenter__/__aexit__ need to await something (opening or closing the connection is itself I/O); otherwise every idea here is identical to section 1 — connect, get a cursor, execute with placeholders, fetch rows — just each blocking step replaced by its awaitable twin, exactly Day 20 section 3's fix for the blocking-call trap applied to a real driver instead of time.sleep().

Where pandas goes from here: pd.read_sql("SELECT ...", conn) takes a connection exactly like today's and returns a whole DataFrame in one call — convenient for a one-shot analysis script, but it opens and holds one connection for the life of that script; a backend service instead needs many short-lived queries sharing a pool across concurrent requests, which is what today's dependency and pool solve.
