Deadlocks: when two transactions wait on each other forever

Lesson 6's own quiz used "a deadlock" as a wrong answer to a different question — the word shown, never explained. Lesson 6 taught SELECT ... FOR UPDATE as a fix for lost updates; today covers the failure mode that same row lock can introduce once a transaction takes more than one lock.

1 · Why one row lock was safe, and two can not be

Lesson 6's fix for a lost update was SELECT ... FOR UPDATE: lock the row, do your work, commit — a second transaction wanting the same row simply waits. That's safe as long as a transaction only ever locks one row before committing. The moment a transaction needs to lock two rows — a funds transfer touching both the sending and receiving account — a new failure becomes possible that never came up with a single lock.

Picture two transfers running at the same time, in opposite directions, between accounts A and B:

Transaction 1: transfer A -> B         Transaction 2: transfer B -> A
  LOCK account A   (FOR UPDATE)          LOCK account B   (FOR UPDATE)
  ... now wants to LOCK account B        ... now wants to LOCK account A
  -- but Transaction 2 already holds B   -- but Transaction 1 already holds A
  -- so Transaction 1 WAITS              -- so Transaction 2 WAITS

Transaction 1 holds A and waits for B. Transaction 2 holds B and waits for A. Neither can ever proceed — each is waiting on a lock the other is holding, and neither will release its lock until it gets the other. This is a deadlock. Notice this is a genuinely different bug from Lesson 6's lost update: a lost update happens with no locks at all and produces a silently wrong number; a deadlock happens because of locks and produces two transactions stuck, not a wrong result.

Postgres doesn't let this hang forever. Postgres runs a background deadlock detector that periodically checks for exactly this circular-wait pattern. When it finds one, it picks one of the two transactions as the victim, aborts it with an error (SQLSTATE 40P01, "deadlock detected"), and releases its locks — letting the other transaction proceed. The aborted transaction gets nothing; its work is rolled back exactly as if it had called ROLLBACK itself. Nothing hangs forever, but the aborted transaction's caller has to notice the failure and decide what to do about it.

2 · The fix: always take locks in the same order

The deadlock above only happens because the two transactions locked the accounts in opposite order — one went A-then-B, the other went B-then-A. If both transactions always lock the lower account id first, the circular wait becomes structurally impossible: whichever transaction gets there first locks the lower id, the second transaction blocks waiting for it (not the reverse), and once the first commits and releases, the second proceeds normally. No cycle can form.

// transferFunds locks BOTH account rows involved in a transfer, always in
// ascending account id order — regardless of which account is "from" and
// which is "to" — so two concurrent transfers between the same two accounts
// can never each hold one row and wait for the other's.
func transferFunds(ctx context.Context, tx Tx, fromID, toID int64, amountCents int64) error {
    first, second := fromID, toID
    if second < first {
        first, second = second, first
    }
    if err := tx.Exec(ctx, `SELECT id FROM accounts WHERE id = $1 FOR UPDATE`, first); err != nil {
        return fmt.Errorf("lock account %d: %w", first, err)
    }
    if err := tx.Exec(ctx, `SELECT id FROM accounts WHERE id = $1 FOR UPDATE`, second); err != nil {
        return fmt.Errorf("lock account %d: %w", second, err)
    }
    if err := tx.Exec(ctx, `UPDATE accounts SET balance_cents = balance_cents - $1 WHERE id = $2`, amountCents, fromID); err != nil {
        return err
    }
    return tx.Exec(ctx, `UPDATE accounts SET balance_cents = balance_cents + $1 WHERE id = $2`, amountCents, toID)
}

Notice the lock order (by account id, ascending) is completely independent of the transfer's direction (from/to) — that independence is the whole trick. Any two transactions calling this same function, transferring in whichever direction, always agree on which row to lock first.

3 · When ordering isn't enough: retry on 40P01

Consistent lock ordering prevents deadlocks between transactions that all go through the same code path, like every call to transferFunds above. It doesn't cover every case — a hand-written report query taking locks in a different sequence, or a bug in a rarely-hit branch, can still produce one occasionally. Because Postgres's detector always aborts one side rather than hanging, a deadlock is always safe to retry — this is the same bounded-retry shape Lesson 37 used for a SERIALIZABLE transaction's serialization failure, just triggered by a different SQLSTATE:

// runWithDeadlockRetry retries the whole transaction once Postgres aborts one
// side of a deadlock with SQLSTATE 40P01 — the same bounded-retry shape
// Lesson 37 used for a SERIALIZABLE serialization failure (40001), applied to
// a different SQLSTATE.
func runWithDeadlockRetry(ctx context.Context, attempts int, fn func(context.Context) error) error {
    var err error
    for i := 0; i < attempts; i++ {
        err = fn(ctx)
        if err == nil {
            return nil
        }
        if !isDeadlock(err) {
            return err
        }
        time.Sleep(time.Duration(i+1) * 5 * time.Millisecond)
    }
    return fmt.Errorf("gave up after %d deadlock retries: %w", attempts, err)
}

The order of priorities matters here: fix the lock ordering first, because it prevents the deadlock from ever happening for the common path. Retry-on-40P01 is the safety net underneath, for the cases ordering doesn't reach — the same "prevent, then retry as a backstop" layering Lesson 32's backoff sat underneath Lesson 28's circuit breaker.

Q: "Your funds-transfer endpoint occasionally fails with a Postgres error about a deadlock. What's happening, and what would you check?" A strong answer, out loud: "A deadlock means two transactions each hold a lock the other one is waiting for — Postgres's deadlock detector caught the cycle and aborted one side rather than let both hang forever. First thing I'd check is whether the transfer code locks the two accounts in a consistent order regardless of transfer direction — if a transfer from A to B locks A first, but a transfer from B to A locks B first, two concurrent transfers between the same pair can deadlock. The fix is ordering the locks by something stable, like account id, so every transaction agrees on which row to lock first. I'd also wrap the call in a bounded retry on the deadlock SQLSTATE as a backstop, since Postgres guarantees the aborted side is a clean rollback, safe to retry." The signal: naming the lock-ordering fix first, retry only as the backstop — not the other way around.
