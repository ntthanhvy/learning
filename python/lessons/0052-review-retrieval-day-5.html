1 · Six questions, in the original teaching order

Answer each out loud or on paper before reading the fold-out answer. If one is shaky, note it and go fix it in the practice file below rather than only rereading the old lesson.

Day 10 — environments & pyproject.toml. What's the practical difference between pyproject.toml and uv.lock, and why does a project need both?

Fold-out answer: pyproject.toml states loose, human-editable constraints — "httpx>=0.27" — that a person chooses and occasionally hand-edits; uv.lock records the exact resolved versions of that package and everything it depends on, generated by the tool and normally left alone. A teammate or CI running uv sync against the same lock file gets byte-identical dependency versions, not just "something matching the constraint" — the lock file is what makes a build reproducible, not just installable.

Day 14 — datetime & timezones. Why does subtracting a naive datetime from an aware one raise TypeError instead of just computing a duration?

Fold-out answer: a naive datetime has no tzinfo — its zone is unstated, exactly SQL's plain TIMESTAMP — so Python has no safe way to guess whether it means the same zone as the aware value or a different one entirely. Rather than silently compute a wrong, plausible-looking duration, Python refuses outright, surfacing the ambiguity at the point of comparison instead of letting a wrong number flow downstream into a report.

Day 27 — itertools. itertools.groupby can silently produce two separate groups for the same key. Why, and what's the fix?

Fold-out answer: groupby only merges items that are already consecutive and share a key — it never sorts the input first, unlike Day 3's defaultdict(list)-based grouping. If a repeated key is separated by a different key in between, that's two runs, not one, and groupby reports them as two groups. The fix is to sort by the same key first (sorted(rows, key=...)) before grouping, or reach for defaultdict instead if the input can't be guaranteed sorted.

Day 31 — __hash__. A class defines __eq__ but not __hash__. What happens the moment code calls hash() on an instance, or tries to use it as a dict key?

Fold-out answer: TypeError — Python implicitly sets __hash__ to None the instant a class overrides __eq__ without also defining __hash__, because the two must stay in lockstep (objects that compare equal must hash equal, or dict/set lookup breaks). Rather than leave the old identity-based hash silently wrong, Python disables hashing entirely and makes the class correctly unhashable until __hash__ is written by hand to match.

Day 39 — argparse. Why doesn't a plain except Exception: around parser.parse_args() catch a bad command-line argument?

Fold-out answer: bad input doesn't raise a normal, catchable exception — argparse prints a usage line and an error to stderr, then calls sys.exit(2), which raises SystemExit. SystemExit deliberately inherits from BaseException, not Exception, specifically so a program-ending exit isn't accidentally swallowed by an ordinary broad except Exception: — the same narrow-catch discipline Day 8 already taught, just showing the one common exception that's designed to slip past it on purpose.

Day 42 — the walrus operator. What happens to a name bound with := inside a list comprehension, once the comprehension finishes running?

Fold-out answer: unlike the comprehension's own throwaway for variable, which stops existing once the comprehension is done, a walrus-bound name leaks into the enclosing scope and stays readable afterward, holding whatever it was last set to. That's intentional — the whole point of := in a comprehension is making a computed value available outside that scope — but it means the bound name isn't private the way the loop variable is, so it's worth picking a name that's fine to have hanging around.
