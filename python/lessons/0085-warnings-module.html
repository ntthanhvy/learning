warnings: flagging trouble without stopping

Day 8's raise stops a function cold. Day 15's logging writes an observation to a record, but never changes whether the program keeps going. Between those two sits a real gap: a function that notices something is probably wrong — a deprecated argument, a suspicious value it can still limp through — and needs to say so loudly, without crashing the caller over it. 1 · The problem: not every problem deserves a crash

A function parsing a "rate" field might get 50 when it expected a fraction like 0.5 — probably a percent typed by mistake. Raising stops the whole batch over one likely-fixable value; silently "fixing" it and saying nothing hides a real data problem from whoever's debugging later:

def parse_rate(value):
    if value > 1:
        value = value / 100   # guesses it was a percent -- but tells no one
    return value

print(parse_rate(50))   # 0.5 -- quietly "fixed", no trace it happened

This is the exact middle ground raise and a plain return both miss: keep running, but make the guess visible.

2 · warnings.warn(): a signal that doesn't stop anything

warnings.warn(message, category) prints a one-line notice — by default once per distinct call site, to stderr — and then execution continues normally on the very next line:

import warnings

def parse_rate(value):
    if value > 1:
        warnings.warn(
            f"rate {value} looks like a percent, not a fraction -- dividing by 100",
            UserWarning,
        )
        value = value / 100
    return value

print(parse_rate(50))
# <stdin>:1: UserWarning: rate 50 looks like a percent, not a fraction -- dividing by 100
# 0.5

Confirmed live: the function's return value (0.5) and the warning text both appear — nothing about calling warn() changed control flow at all. UserWarning is the default, general-purpose category; DeprecationWarning (for "this still works, but stop using it") and RuntimeWarning (an unusual runtime condition) are the two other most common built-in categories, used the same way.

warnings.warn() vs. logging.warning(): both signal "something's off" without stopping. Day 15's logging.warning() just writes a line to wherever logging is configured to send it — no special handling available. warnings.warn() is built to be programmatically acted on by the caller: filtered, deduplicated, collected in a test, or turned into a real exception, as the next two sections show. Library code (e.g. "this argument is deprecated") reaches for warnings; application logging of routine events reaches for logging.

3 · Catching warnings in a test, and escalating one into an exception

A test that wants to confirm a warning actually fired needs to catch it rather than let it print — warnings.catch_warnings(record=True) plus simplefilter("always") collects every warning raised inside the with block into a plain list instead of printing it:

with warnings.catch_warnings(record=True) as caught:
    warnings.simplefilter("always")
    parse_rate(50)
    assert len(caught) == 1
    assert "looks like a percent" in str(caught[0].message)
    assert caught[0].category is UserWarning
# all three asserts pass -- confirmed live, no print reached stderr

simplefilter("always") matters here: Python's default filter only shows each distinct warning once per location, which would hide a second identical call in the same test run. The opposite direction also exists — warnings.filterwarnings("error", category=UserWarning) turns every matching warning into a real raised exception instead of a printed line, letting a test (or a strict pipeline) fail loudly on a condition that's normally survivable:

warnings.filterwarnings("error", category=UserWarning)
try:
    warnings.warn("bad input", UserWarning)
except UserWarning as e:
    print("caught as exception:", e)
# caught as exception: bad input -- confirmed live

Same warn() call both times; the filter in effect decides whether it prints once and moves on, or stops the program like any other exception.

Where pandas/NumPy go from here: nothing library-specific today — both libraries use exactly this module under the hood for their own deprecation notices (the "FutureWarning: ..." lines a pandas upgrade sometimes prints), but today's lesson stays in plain stdlib territory, per MISSION.md.
