IHostedService: a worker living inside your app process

Lesson 10 drew a hard line: a handler enqueues work, a separate, independent process dequeues and runs it. That's still the right model for real job queues. But ASP.NET Core has a lighter-weight shape for recurring or long-running work that doesn't need its own process — a background task registered to start and stop alongside the web app itself. Today: what that shape is, when it's the right call, and where it stops being enough.

1 · Not every background task needs Lesson 10's whole machine

Lesson 10's queue-and-worker pattern earns its complexity when jobs must survive a crash, retry safely, and scale independently of the web tier. But plenty of recurring backend work is smaller than that: expire stale sessions every hour, flush an in-memory metrics buffer every 30 seconds, warm a cache on startup. None of that needs a durable queue or a second deployable — it just needs some code running continuously, started once, stopped cleanly when the app shuts down.

ASP.NET Core's answer is an IHostedService: a class the DI container starts once, when the app starts, and stops once, when the app shuts down — living for the whole process lifetime, same lifetime shape as Lesson 103's Singleton, but with actual code to run instead of just state to hold.

2 · The shape: BackgroundService and a loop

Nobody implements IHostedService directly in practice — the framework ships BackgroundService, an abstract base class that does the start/stop plumbing and leaves one method to fill in:

public class ExpiredSessionCleanupService : BackgroundService {
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly ILogger<ExpiredSessionCleanupService> _logger;

    public ExpiredSessionCleanupService(IServiceScopeFactory scopeFactory,
                                       ILogger<ExpiredSessionCleanupService> logger) {
        _scopeFactory = scopeFactory; // see section 4 -- NOT a scoped DbContext injected directly
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken) {
        while (!stoppingToken.IsCancellationRequested) {
            using (var scope = _scopeFactory.CreateScope()) {
                var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
                await db.Sessions.Where(s => s.ExpiresAt < DateTime.UtcNow)
                               .ExecuteDeleteAsync(stoppingToken);
            }
            _logger.LogInformation("expired sessions cleaned");
            await Task.Delay(TimeSpan.FromHours(1), stoppingToken); // wait, respecting shutdown
        }
    }
}

// Program.cs
builder.Services.AddHostedService<ExpiredSessionCleanupService>(); // registered once, not per-request

ExecuteAsync runs for the life of the app: the while loop is the entire job, not one iteration of it. stoppingToken is how the host says "shut down now" — Task.Delay and the loop condition both honor it, so the app can stop within roughly one tick instead of being killed mid-work.

3 · Go has no registered-service concept — the shape is the same goroutine Lesson 10 already used

Go never needed a dedicated interface for this because starting a long-lived goroutine alongside the server already is the pattern — no framework registration step exists to compare against:

// worker: a goroutine started once at process startup, running for the process's entire life
func runCleanupWorker(ctx context.Context) {
    ticker := time.NewTicker(time.Hour)
    defer ticker.Stop()
    for {
        select {
        case <-ctx.Done(): // process is shutting down -- stop cleanly
            log.Println("cleanup worker: shutting down")
            return
        case <-ticker.C:
            deleteExpiredSessions(ctx) // the actual recurring work
        }
    }
}

func main() {
    ctx, cancel := context.WithCancel(context.Background())
    defer cancel()
    go runCleanupWorker(ctx) // started once, alongside the HTTP server, not per-request
    // ... start http.ListenAndServe, etc.
}

Line up the two: ExecuteAsync's while (!stoppingToken.IsCancellationRequested) is runCleanupWorker's select loop; stoppingToken is ctx.Done(); AddHostedService is just go runCleanupWorker(ctx) made into a declared, container-managed registration instead of a line written by hand in main. ASP.NET Core didn't invent a new capability here — it gave Go's already-familiar shape a name, a base class, and a place in Program.cs where every other registered background task is visible in one list.

Where this stops being enough: an IHostedService dies with its process. Restart the app, redeploy, scale to three instances — and either the task vanishes until the app comes back, or it runs three times at once with no coordination between instances (nothing stops all three from firing the same cleanup query simultaneously). Lesson 10's queue-and-worker pattern exists specifically for work that must survive exactly that: a durable queue outlives any one process, and Lesson 95's SKIP LOCKED is exactly the mechanism that lets several worker instances claim jobs without claiming the same one twice. An IHostedService for the session-cleanup example above is fine precisely because running it zero or three times in a given hour costs nothing worse than a slightly stale row.

4 · Why a scope, not a straight constructor injection

Notice the cleanup service's constructor takes IServiceScopeFactory, not AppDbContext directly. AddHostedService registers the service itself as a Singleton — it's built once and lives for the app's whole lifetime, same as Lesson 103 covered — but AppDbContext is normally registered Scoped, meant to live for one HTTP request. Injecting a Scoped service straight into a Singleton's constructor is exactly Lesson 104's glossary term captive dependency waiting to happen: the one instance created at startup would be held for the service's entire lifetime, never refreshed, likely holding a stale or disposed database connection by the second loop iteration. Calling _scopeFactory.CreateScope() inside the loop creates a fresh scope — and a fresh AppDbContext — every iteration, then disposes it at the end of the using block, which is the correct way for a Singleton to borrow something Scoped for a moment without trapping it.

Q: "Why does this ExecuteAsync create a scope instead of just injecting AppDbContext into the constructor?" A strong answer, out loud: "AddHostedService registers the service as a Singleton, built once for the app's whole life, but AppDbContext is Scoped, meant to live one request at a time. Injecting it straight into the constructor would be a captive dependency — one DbContext instance held for the entire app lifetime instead of a fresh one per unit of work. Creating a scope inside the loop and resolving AppDbContext from that scope gives each iteration its own instance, disposed right after, which is the supported way for a Singleton to use something Scoped." The signal: connecting a specific registration mismatch to the concrete bug it causes, not just naming "captive dependency" as a term.

Scope line

This lesson covers what IHostedService/BackgroundService is, when it's the right-sized tool versus Lesson 10's queue pattern, and the scope-factory detail that keeps it from becoming a captive-dependency bug. It does not cover: IHostedLifecycleService's extra startup/shutdown hook ordering; Quartz.NET or Hangfire as dedicated scheduling libraries people reach for once cron-like scheduling needs grow past a simple Task.Delay loop; or Go's own ecosystem equivalents for cron-style scheduling (e.g. robfig/cron).
