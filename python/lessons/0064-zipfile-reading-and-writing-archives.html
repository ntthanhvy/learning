1 · The problem: a directory is not a file

Day 62's shutil moves and copies whole directory trees on the same filesystem, but it has no answer for "send this directory to someone else as one attachment" or "here's a .zip a vendor sent — get the records out of it." A zip archive packages any number of files and folders into one compressed, portable container — the same format behind .zip downloads, a Java .jar, or a docx file's internals. zipfile reads and writes that format directly, no external program required.

2 · Reading an archive: ZipFile, namelist(), extractall()

import zipfile

with zipfile.ZipFile("data/drop.zip") as zf:
    zf.namelist()                    # ["orders.csv", "customers.csv", "readme.txt"]
    with zf.open("orders.csv") as f:
        first_line = f.readline()    # read one member's bytes without extracting anything to disk
    zf.extractall("data/extracted")  # unpack every member into this directory

ZipFile is a context manager (Day 6) just like open() — the with block closes it automatically. namelist() lists every member's path inside the archive without extracting anything, which matters for a large archive: checking what's inside, or reading just one member with zf.open(name), never touches disk for the other members. extractall() is the shortcut for "I want everything, written out as real files" — the same escape hatch Day 62's copytree() covers for a plain directory, but starting from a compressed container instead.

Only extract archives from a source that's trusted: a crafted zip entry can contain a path like ../../etc/passwd, and older Python versions would write straight through it. Modern extractall() guards against that specific escape, but it is still the same discipline Day 62's rmtree() callout applied to unvalidated paths — treat an archive from an untrusted source the way any other unvalidated input is treated, not as automatically safe just because it went through the standard library.

3 · Writing an archive: ZipFile in write mode

import zipfile
from pathlib import Path

with zipfile.ZipFile("archive/2026-09-30.zip", "w") as zf:
    zf.write("output/report.csv", arcname="report.csv")  # add one file
    for path in Path("output/logs").rglob("*.txt"):
        zf.write(path, arcname=path.relative_to("output"))    # add each file at a chosen internal path

The mode string works the same way Day 6's open() modes do: "w" creates a new archive (overwriting one that exists), "a" appends members to an existing archive. arcname controls the path stored inside the archive, which usually should not be the same as the full source path — without it, zipping /home/user/output/report.csv would store that entire absolute path inside the archive instead of just report.csv. Combining Path.rglob() (Day 13) with a loop is the idiom for "zip this whole directory, one file at a time, with clean internal paths."

4 · One-shot helpers: shutil.make_archive()

When the whole point is "zip this entire directory, keep its structure, no per-file control needed," shutil — Day 62's module — has a shortcut built on top of zipfile:

import shutil

shutil.make_archive("archive/2026-09-30", "zip", "output")  # writes archive/2026-09-30.zip from the whole output/ tree
shutil.unpack_archive("data/drop.zip", "data/extracted")   # the extractall() shortcut, format auto-detected

make_archive()/unpack_archive() are the right tool for "the whole directory, nothing fancy" — reach for zipfile directly instead when only some files belong in the archive, when internal paths need renaming, or when a member needs reading without extracting the rest, as in section 2.

Where pandas goes from here: nothing pandas-specific today — pandas.read_csv() can in fact read directly from a path inside a zip (via its own compression= handling), but building, inspecting, or selectively extracting the archive itself is never a DataFrame's job; that stays zipfile's (or shutil's, for the whole-tree shortcut).
