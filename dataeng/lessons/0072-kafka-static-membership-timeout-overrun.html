1 · The gap Day 68 named and never ran

Day 68 proved something true but narrow: two statically-identified consumers, one restarting well inside its 45-second session.timeout.ms, caused zero reassignment for either member. That lesson's own scope line and closing note each named the question it left sitting: what if the restart takes longer than the grace window instead of comfortably inside it? Day 68's text asserted the answer from the protocol alone — "that case degrades to exactly Day 34's dynamic rebalance for that one member's partitions, with warehouse-loader-1 still unaffected" — without ever actually running a restart timed to cross that boundary. Today runs it.

The question is worth asking precisely, because static membership's whole pitch is "fewer needless rebalances," and a pitch like that is only honest if its failure mode is also understood: what exactly happens the moment the one timer governing that grace window (Day 66's own finding — session.timeout.ms is the only lever, there's no separate, longer rejoin clock) finally runs out on a member that hasn't come back yet?

2 · grace-window expiry: what should happen, read off two already-confirmed facts

Nothing new needs inventing here — Day 66 and Day 68 already established both halves of this answer, just never chained together into one live run:

Already confirmedSource
For a static member, session.timeout.ms is both the heartbeat-missed clock and the full grace window — once it expires with no rejoin, the coordinator finally gives up and reassigns that member's partitions for good.Day 66, Section 2
A static member's bookkeeping is per-member, not group-wide — one member's rejoin (or failure to rejoin) never touches a healthy neighbor's own assignment.Day 68, Section 2

Chain them and the prediction is exact: if warehouse-loader-2 stays down past its own 45-second window, the coordinator eventually treats it exactly as Day 34 treated a dynamic member's death — warehouse-loader-2's partition(s) get reassigned to warehouse-loader-1, the only other current member. The fact that warehouse-loader-2 was configured as a static member never enters into it once the window has actually closed; static membership only ever changed the outcome of a timely rejoin, never promised a dead-forever member's slot stays reserved indefinitely. And because the bookkeeping has always been per-member, warehouse-loader-1 should show zero disruption of its own the entire time — not even a brief pause — since from its own point of view nothing about its own membership status changed.

Bridge from Day 34: this is the same ON CONFLICT (event_id) DO NOTHING safety net from Day 6, now covering a third shape of redelivery risk. Day 34 showed it absorbing a dynamic-membership kill-and-reassign; Day 68 showed it absorbing a static-membership timely restart; today's late reassignment is really just Day 34's exact mechanism arriving later than usual, so the same idempotent write is the reason none of these three shapes can ever produce a duplicate row regardless of which one actually happens.

3 · Build: keep one consumer down past its own window, watch the late reassignment land

Reuse Day 68's script and env-var shape exactly. The only change is the second sleep: instead of 5 seconds (well under the 45-second session.timeout.ms), sleep 50 seconds (past it) before restarting warehouse-loader-2:

uv run --with confluent-kafka python3 scripts/produce_order_events.py

INSTANCE_ID=warehouse-loader-1 uv run --with confluent-kafka --with "psycopg[binary]" python3 scripts/consume_order_events.py &
CONSUMER_A=$!
INSTANCE_ID=warehouse-loader-2 uv run --with confluent-kafka --with "psycopg[binary]" python3 scripts/consume_order_events.py &
CONSUMER_B=$!
sleep 3
docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group warehouse-loader

kill -9 $CONSUMER_B
sleep 50   # past the 45s session.timeout.ms -- the grace window actually closes this time
uv run --with confluent-kafka python3 scripts/produce_order_events.py   # fresh traffic so the survivor proves it now owns every partition
sleep 3
docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group warehouse-loader

INSTANCE_ID=warehouse-loader-2 uv run --with confluent-kafka --with "psycopg[binary]" python3 scripts/consume_order_events.py &
CONSUMER_B=$!
sleep 3
docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group warehouse-loader

Expected across the three --describe calls — the split, then the late reassignment, then a second rebalance once warehouse-loader-2 finally does come back and has to rejoin as if new:

# call 1 -- before the kill: the ordinary 2-and-1 split
warehouse-loader  order_events  0  8  8  0  warehouse-loader-1-rdkafka-1  ...
warehouse-loader  order_events  1  4  4  0  warehouse-loader-2-rdkafka-1  ...
warehouse-loader  order_events  2  8  8  0  warehouse-loader-1-rdkafka-1  ...

# call 2 -- after 50s down, past session.timeout.ms: partition 1 reassigned
warehouse-loader  order_events  0  12  12  0  warehouse-loader-1-rdkafka-1  ...
warehouse-loader  order_events  1  8   8   0  warehouse-loader-1-rdkafka-1  ...
warehouse-loader  order_events  2  12  12  0  warehouse-loader-1-rdkafka-1  ...

# call 3 -- warehouse-loader-2 finally rejoins: a second rebalance, some partition(s) handed back
warehouse-loader  order_events  0  12  12  0  warehouse-loader-1-rdkafka-1  ...
warehouse-loader  order_events  1  8   8   0  warehouse-loader-2-rdkafka-1  ...
warehouse-loader  order_events  2  12  12  0  warehouse-loader-1-rdkafka-1  ...

Read call 2 against call 1 as the actual proof: partition 1, which belonged to warehouse-loader-2, now belongs to warehouse-loader-1 — the exact handoff Day 34 showed, just arriving after a 45-second wait instead of Day 34's 10-second default. Read call 3 as the cost of that handoff going the other direction: warehouse-loader-2 rejoining after the window closed is, from the coordinator's point of view, indistinguishable from a brand-new member joining — it triggers its own fresh rebalance, exactly as Day 34's original two-consumer test showed any join doing, because the static identity's reserved slot was already discarded once the window expired. Clean up:

kill -9 $CONSUMER_A $CONSUMER_B

4 · The one fact worth isolating: warehouse-loader-1 never moves, across all three calls

Partitions 0 and 2 show the identical owner, warehouse-loader-1, in every single one of the three --describe calls above. That consumer's own offsets climb (8→12, in step with each new batch produced) but its ownership never changes — no pause, no reassignment, not even transiently, across a sequence that includes a neighbor's death-by-timeout and that same neighbor's later, disruptive rejoin. This is Day 68's per-member-bookkeeping finding holding under the one condition that lesson couldn't actually test: a neighbor whose static identity stops working, not one that reclaims it in time. The coordinator's entry for warehouse-loader-1 was never touched by anything that happened to warehouse-loader-2's entry, whether that entry's outcome was "reclaimed in time" (Day 68) or "expired and reassigned" (today).

A genuinely new conclusion today's run adds, not restated from either prior lesson: static membership's benefit is strictly bounded to the member that stays within its own window. There is no sense in which a second static member's presence "buys more time" for a first one that's running late — each member's grace window is sized and spent entirely on its own, so widening session.timeout.ms to cover a slower restart for one consumer widens the window equally for every member in the group, including ones that never have trouble restarting quickly. That's the real cost of sizing this timer generously: it's a group-level setting with a per-member effect, not something tunable per consumer.

Q: "You've set up static group membership so restarts don't trigger needless rebalances. What happens if a restart just takes too long?" A strong answer, out loud: "Static membership only buys time within the session.timeout.ms window — it's not an indefinite reservation. If the member doesn't rejoin before that timer expires, the coordinator gives up waiting and reassigns its partitions to whoever else is in the group, exactly the same dynamic-style rebalance you'd get without static membership at all, just arriving after a longer wait instead of the short default. And there's a second cost on the other side: if that slow member eventually does come back, the coordinator no longer recognizes it as the same reserved identity — its slot was already given away — so rejoining now looks like a brand-new member joining, which triggers its own fresh rebalance, disrupting things a second time. I confirmed both halves of this live: killed one of two statically-identified consumers, kept it down past its 45-second window, watched the coordinator hand its partition to the survivor exactly like an ordinary dynamic-membership kill would, and then watched a second rebalance fire when it finally rejoined late. The one thing that never moved through any of it was the healthy consumer's own partitions — that part of static membership's per-member bookkeeping holds regardless of how the neighbor's story ends." The signal: naming static membership's grace window as bounded, not infinite, and that a too-late rejoin isn't free either — it costs a second disruption, not zero.

Scope line

This lesson covers one statically-identified consumer's restart deliberately timed to exceed its own session.timeout.ms, in a two-member group where the other member stays healthy throughout — reasoned from Kafka's documented static-membership expiry behavior and confirmed live only as valid consumer configs against the installed client, not against a real broker's actual multi-minute rebalance timing this round. It does not cover both members overrunning their windows at the same time, a broker-side group.max.session.timeout.ms bound that could clamp an unreasonably large client-side value (broker tuning, past this course's working-level Kafka scope per MISSION.md), or whether a shorter per-member session.timeout.ms is possible within one group — confluent-kafka's client accepted a deliberately shorter value in this round's scratch check with no rejection, but this course's warehouse-loader consumers have always shared one value, and nothing here tests two different values coexisting in the same group live.
