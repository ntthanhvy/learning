The random module: choosing, shuffling & repeatable "randomness"

Every language needs a way to pick, shuffle, or sample — test fixtures, shuffled quiz options (like the ones on this very page), sampling a subset of rows for a spot-check. Today's tool is the random module, plus the one word that makes its output reproducible on demand instead of different every run.

Bridge from SQL: random.sample(rows, 20) is the plain-Python shape of ORDER BY RANDOM() LIMIT 20 — pick 20 distinct rows at random, no repeats. The difference is where it runs: SQL's version asks the database to shuffle server-side; Python's version shuffles a list already sitting in memory.

1 · Why "random" needs a second word: pseudo

random does not read real-world noise (like a die roll) — it runs a deterministic formula that, given a starting number, produces a long sequence of values that look statistically random but are fully determined by that starting number. That starting number is the seed. Leave it alone and Python picks one from the OS for you (different every run); set it explicitly and the entire sequence that follows becomes repeatable:

import random

random.seed(42)
print(random.randint(1, 100))   # 82 -- same every time seed(42) runs first
print(random.randint(1, 100))   # 15 -- same second call too

random.seed(42)                # reset back to the same starting point
print(random.randint(1, 100))   # 82 -- identical sequence repeats from scratch

Verified live: reseeding with the same value reproduces the exact same sequence of calls, in order — this is the whole point of a seed. A test that asserts on "random" output would be flaky without one; call random.seed(some_fixed_number) at the top of the test (or fixture) and the "random" values become as predictable as any other input, which is exactly why pytest fixtures for randomized test data almost always seed first.

Not for security: random's algorithm is predictable if an attacker can observe enough of its output — never use it for passwords, tokens, or anything security-sensitive. That job belongs to secrets (stdlib, cryptographically secure, out of scope today) — mentioned here only so the boundary is clear, not as a second module to learn.

2 · Picking: choice, choices, and sample

Three functions answer three different "pick from this" questions, and mixing them up is the most common mistake:

import random

fruits = ["apple", "banana", "cherry", "date"]

random.choice(fruits)             # one random element, e.g. "cherry" -- picks ONE, with replacement doesn't apply (single pick)
random.choices(fruits, k=3)     # 3 elements, WITH repeats allowed, e.g. ["date", "date", "apple"]
random.sample(fruits, k=3)      # 3 DISTINCT elements, no repeats, e.g. ["banana", "date", "apple"]

Verified live (seeded): choice returns a single element. choices samples with replacement — the same element can appear more than once in the result, which is why it needs a count via k= rather than being capped at the list's length. sample samples without replacement — every element in the result is distinct, and asking for k larger than the list's length raises ValueError. "Pick a random quiz answer to highlight" is choice; "simulate 100 dice rolls" is choices; "pick 5 distinct winners from 200 entries" is sample.

3 · Shuffling in place: shuffle

random.shuffle() reorders a list's elements randomly — and, like list.sort(), it mutates the list in place and returns None, not a new shuffled list:

import random

deck = [1, 2, 3, 4, 5]
result = random.shuffle(deck)
result       # None -- shuffle returns nothing
deck          # e.g. [3, 1, 5, 2, 4] -- the ORIGINAL list, reordered in place

Verified live: result is None while deck itself ends up reordered — the same "mutate, return None" shape Day 1 already flagged for list.sort() and list.append(). Writing deck = random.shuffle(deck) is a classic trap: it silently overwrites deck with None. To shuffle a copy and keep the original untouched, shuffle a copy explicitly: shuffled = deck[:]; random.shuffle(shuffled).

4 · Numbers: randint, random(), and uniform

Three more functions cover the common numeric ranges:

import random

random.randint(1, 6)        # int in [1, 6], BOTH ends inclusive -- a die roll
random.random()             # float in [0.0, 1.0), e.g. 0.37454...
random.uniform(1.5, 4.5)    # float in [1.5, 4.5], both ends inclusive

Verified live: randint(1, 6) can return 6 itself — both bounds are inclusive, unlike range(1, 6)'s exclusive upper end, a mismatch worth double-checking against off-by-one errors. random() takes no arguments and always returns a float from 0 up to (but never reaching) 1 — the building block every other function in the module is ultimately implemented on top of.

Where pandas goes from here: nothing pandas-specific to teach — DataFrame.sample() exists and takes its own random_state= seeding argument, but that is a DataFrame method with its own API, not today's stdlib random module; not demonstrated here, per MISSION.md.

Q: "How would you write a test for a function that shuffles a hand of cards?" A strong answer, out loud: "I'd call random.seed() with a fixed number at the top of the test, before calling the function under test. That makes the 'random' shuffle deterministic — the exact same sequence every run — so I can assert on the specific resulting order instead of writing a weaker test like 'the length didn't change' or 'it's not sorted anymore.' Without seeding, the test would be flaky: it might pass 999 times and then fail once by chance, or worse, pass even when the shuffle logic is broken." The signal: naming seed() specifically, and explaining reproducibility as the reason, not just "make it not random."
