Memory/dtype optimization: measuring with memory_usage(deep=True) and downcasting on purpose

Lesson 60's teaser named this as one of two remaining candidates; Lesson 61 took the other (groupby/agg patterns), so this closes the loop. Re-grepped every lesson before writing: Lesson 25 already taught select_dtypes(), the category dtype, and a single-column memory_usage(deep=True) comparison; Lesson 41 taught astype()'s raise-on-failure behavior and nullable Int64/Float64; Lesson 51 taught convert_dtypes()'s best-guess pass. None of them taught memory_usage(deep=True) as a whole-table profiling workflow, or numeric downcasting (pd.to_numeric(..., downcast=), explicit astype("int32")/"float32") and its overflow/precision-loss risk — today closes exactly that gap, the numeric half of memory optimization that the text-focused Lesson 25 didn't cover.

1 · Recap: what's already covered, and what's new today

Three earlier lessons touched dtypes from three different angles: Lesson 25 shrank a low-cardinality text column with astype("category"); Lesson 41 taught astype()'s general raise-on-bad-data conversion; Lesson 51 taught convert_dtypes()'s best-guess pass across a whole table. None of them asked "how much memory does this whole table actually use, column by column, and can the numeric columns be shrunk the same way category shrinks text?" That's today's question, and it needs one measuring tool plus one shrinking technique: df.memory_usage(deep=True) to see where the bytes actually go, and downcasting (pd.to_numeric(..., downcast=) or explicit astype("int32")) to shrink numeric columns whose actual value range doesn't need the wide default type.

2 · SQL bridge: you already choose column widths in a schema — pandas doesn't, by default

Writing a CREATE TABLE, choosing SMALLINT vs INTEGER vs BIGINT, or REAL vs DOUBLE PRECISION, is a deliberate, upfront decision — the schema fixes the width once and every row is stored that way from the start. pandas' read_csv() has no schema to consult, so it defaults every numeric column to the widest practical type — int64, float64 — regardless of whether the actual values would fit in a SMALLINT. An order_id column that will never exceed a few thousand rows still costs 8 bytes per value by default, the same width as a value near 9 quintillion. Today's tools are how you retroactively do, in pandas, what a well-designed schema would have done upfront in SQL: pick the narrowest type that actually fits the data.

3 · Measuring first: memory_usage(deep=True), not just df.info()

Lesson 2's df.dtypes tells you the type; it says nothing about bytes. df.memory_usage() reports per-column memory — but its default, deep=False, silently undercounts any column holding Python strings, because it reports only the fixed-size pointer array, not what each string object itself costs:

df2.memory_usage()                 # deep=False (the default) -- shallow, cheap, WRONG for text columns
-- Index            40
-- order_id         40
-- customer         40    <- looks identical to a numeric column's cost. it is not.
-- order_date       40
-- amount_clean     40

df2.memory_usage(deep=True)   # actually walks every string object
-- Index            40
-- order_id         40
-- customer        260    <- the real cost
-- order_date      268
-- amount_clean     40

Confirmed directly on this course's real (cleaned) orders_raw.csv: the shallow total across the whole frame is 240 bytes; the deep total is 915 — 3.8x higher, entirely hidden in the two text columns. This is the same "looks like an answer, quietly wrong" family as Lesson 25's own gotcha: deep=False never raises or warns, it just reports a number that's true for numeric/bool/datetime columns and false for anything holding Python objects/strings. deep=True is the one rule worth internalizing: always pass it when text/object columns are present, and chain .sum() for a table-wide total or .sort_values(ascending=False) to find which column is actually the biggest cost before optimizing the wrong one.

4 · category dtype, revisited at scale

Lesson 25 showed the category win on a 4-row fixture (216 → 112 bytes). Repeated to 2,500 rows (still only 3 distinct customer names), the same conversion goes from 130,000 bytes to 2,656 — the gap widens with row count, not narrows, since the lookup table barely grows while the plain-string cost scales linearly with rows:

big["customer"].memory_usage(deep=True)                          # 130000, as str
big["customer"].astype("category").memory_usage(deep=True)      # 2656, as category

Nothing new here beyond Lesson 25's own mechanism — it's the same tool, re-confirmed at a scale where the payoff is dramatic rather than marginal, which is closer to what a real "shrink this table" interview task looks like than a 4-row toy.

5 · Downcasting numeric columns: pd.to_numeric(..., downcast=)

pd.to_numeric(col, downcast="integer") converts a column AND automatically picks the smallest safe integer type for the values actually present:

big["order_id"].dtype                                     # int64, values only ever 1-6
pd.to_numeric(big["order_id"], downcast="integer").dtype  # int8 -- picked automatically, safely
-- memory: 20132 bytes -> 2632 bytes, same values, zero risk

Confirmed directly: downcast="integer" checks the real min/max of the column against each integer type's range and picks the smallest one that fits — it never produces a wrong value, because it refuses to pick a type too narrow for what's actually there. downcast="float" does the same for floats, landing on float32 before falling back to float64 if precision genuinely requires it. This is the safe, recommended path: let pandas check the range for you rather than guessing a target type by hand.

6 · The gotcha: explicit astype("int8") does NOT check the range — it wraps silently

The interview-relevant trap is reaching for plain astype() to downcast instead of to_numeric(downcast=). astype() (Lesson 41) raises on a type it genuinely cannot represent (like text into float) — but a too-narrow integer type is not one of those cases; it silently wraps around instead:

s = pd.Series([100, 200, 300], dtype="int64")
s.astype("int8").tolist()
-- [100, -56, 44]     <- 200 and 300 both silently WRAPPED, no error, no warning

pd.to_numeric(s, downcast="integer").tolist()
-- [100, 200, 300]    <- same data, but downcast= checked the range first and landed on int16

Confirmed directly on pandas 3.0.5: np.iinfo(np.int8) reports a valid range of -128 to 127; forcing 200 and 300 into int8 via plain astype() doesn't raise OverflowError — it wraps modulo the type's range, producing believable-looking but completely wrong integers, with no exception and no warning printed. This is the same "no crash, quietly wrong" family as Lesson 25's fixed-category gotcha and Lesson 51's string-not-Float64 trap. The fix is the same lesson every time: prefer pd.to_numeric(col, downcast=...), which checks the real range first, over hand-picking an astype() target type from a guess about what the values "probably" look like. If astype() is the right tool for another reason (e.g. converting several differently-typed columns via a dict, Lesson 41), check col.min()/col.max() against np.iinfo("int8")/np.finfo("float32") by hand first.

Precision loss, the float-specific version of the same trap: downcasting a float column can also silently lose precision rather than overflow — pd.Series([123456789.123456]).astype("float32") becomes 123456792.0, a different number, with no error. float32 has roughly 7 significant decimal digits versus float64's ~15-17; a column of large or high-precision values (financial totals needing exact cents, scientific measurements) can genuinely change value under a careless float32 downcast. downcast="float" doesn't prevent this the way it prevents integer overflow — floats are inherently approximate, so "safe" here just means picking the narrowest type that round-trips the SAME rounded value, not that no rounding ever happens. Check a sample of before/after values with .equals() (Lesson 54) or a tolerance-based comparison before trusting a float downcast on precision-sensitive data.

Q: "A DataFrame is using more memory than expected. Walk me through shrinking it." A strong answer, out loud: "First I'd measure, not guess — df.memory_usage(deep=True).sort_values(ascending=False) to see which columns actually cost the most, since the default deep=False silently undercounts any text/object column by only reporting a fixed-size pointer array, not the real string cost. For low-cardinality text columns repeated across many rows — status, region, category codes — astype('category') stores the distinct values once plus a small integer code per row, the same idea as a SQL ENUM or lookup table. For numeric columns, I'd check whether the actual value range needs the full int64/float64 default — pd.to_numeric(col, downcast='integer') or downcast='float' checks the real min/max and picks the smallest safe type automatically. The gotcha I'd flag: plain astype('int8') on a column with out-of-range values doesn't raise, it silently wraps around to a wrong-looking-but-plausible number, and astype('float32') can silently lose precision on large or high-precision values — so I'd always prefer to_numeric(downcast=), which checks the range first, over guessing a narrow type by hand with astype()." The signal: measuring before optimizing, naming both the text (category) and numeric (downcast) halves of the technique, and flagging the silent-wraparound trap unprompted.

7 · Why this matters beyond a single interview answer

This closes the loop on every prior dtype lesson: Lesson 25 (category for text), Lesson 41 (astype's raise-on-failure contract), and Lesson 51 (convert_dtypes' best-guess pass) all touch dtypes, but none of them measured whole-table memory or addressed numeric downcasting specifically. A realistic interview "optimize this pipeline" task often combines all four: profile with memory_usage(deep=True), convert low-cardinality text to category, downcast numeric columns that don't need their default width, and use convert_dtypes() as a final best-guess polish — in that order, since (per Lesson 51) polishing before the real cleaning step just upgrades the container without fixing the values.
