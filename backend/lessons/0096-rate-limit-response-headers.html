Rate-limit headers: telling a client its quota before it gets rejected

Lesson 11 gave the token bucket a voice for exactly one moment: the instant it rejects a request, via 429 and Retry-After. Every request before that moment — including the one that empties the bucket — goes out silent, with no way for the client to know it was close to the limit at all. Today: the response headers that make a client's remaining quota visible on every single response, rejected or not.

1 · Retry-After only speaks after the damage is done

Lesson 11's middleware sets Retry-After on the one response that gets rejected. That's genuinely useful — it tells an already-blocked client when retrying is worth attempting — but it only fires once the bucket is already empty. A well-behaved client calling the API in a loop has no visibility before that point: it can't tell the difference between "20 requests left" and "1 request left" on any of the successful calls leading up to the rejection, because nothing on those responses says anything about the bucket at all. The first signal it ever gets is the 429 itself.

A client that could see its own remaining quota on every response could slow itself down voluntarily, before hitting the wall — exactly the way a gas gauge lets a driver plan a stop before the tank is empty, not after the engine cuts out.

2 · Three headers, one on every response

The fix is a small family of rate-limit response headers, attached to every response the token bucket middleware touches, success or rejection alike:

HeaderMeaning
RateLimit-Limitthe bucket's total capacity in this window (Lesson 11's capacity)
RateLimit-Remainingtokens left right now, after this request's own cost was taken
RateLimit-Resetseconds until the bucket is back to full capacity

(Many existing APIs — GitHub, Twitter/X, Stripe among them — ship the older, non-standardized X-RateLimit-Limit / X-RateLimit-Remaining / X-RateLimit-Reset spelling, from the now-deprecated general convention of prefixing custom headers with X-. The unprefixed RateLimit-* family is the newer, standardization-track naming; the three fields mean the same thing either way, and a client should check for whichever spelling an API actually documents.)

Extending Lesson 11's middleware to set all three on every response, not just the rejected one:

func rateLimit(next http.Handler, buckets *sync.Map) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        key := r.Header.Get("X-API-Key")
        raw, _ := buckets.LoadOrStore(key, &bucket{tokens: 20, capacity: 20, refillPerSec: 10, last: time.Now()})
        b := raw.(*bucket)

        allowed, remaining, resetSecs := b.check() // same bucket math, now reporting state

        w.Header().Set("RateLimit-Limit", strconv.Itoa(int(b.capacity)))
        w.Header().Set("RateLimit-Remaining", strconv.Itoa(remaining))
        w.Header().Set("RateLimit-Reset", strconv.Itoa(resetSecs))

        if !allowed {
            w.Header().Set("Retry-After", "1")
            w.WriteHeader(http.StatusTooManyRequests) // 429
            return
        }
        next.ServeHTTP(w, r)
    })
}

The headers now ride along on the 19th successful request the same as the 21st rejected one. A client reading RateLimit-Remaining: 1 on an ordinary 200 OK has everything it needs to pause itself for a beat, entirely on its own initiative, with no 429 ever having to happen at all.

Frontend-habit trap: this looks like it belongs in the response body — {"remaining": 1} added to the JSON — the way a frontend dev is used to surfacing app-level state. It deliberately doesn't live there. Quota is metadata about the HTTP exchange itself, not about the resource being fetched, which is exactly the same header-vs-body line Lesson 51's ETag drew: the thing being described sits in the body, information about the response describing it sits in a header. A generic HTTP client, proxy, or logging middleware can read a header without knowing anything about this particular API's JSON shape.

3 · Why every response, not just the rejected one

It would be simpler to only set these headers on the 429 — that's the one request that actually needs an explanation. The reason to set them on every response instead is the same reason Lesson 11's token bucket allows bursts in the first place: a client that only ever sees its quota at the moment of rejection has no way to behave any better than a client that saw nothing at all, because by definition it's already too late. Reporting the quota continuously turns a hard stop into a visible, approaching one — a client library can watch RateLimit-Remaining trend toward zero across several calls and start spacing out its own requests well before the server ever has to say no.

Q: "A partner team integrating with our API keeps getting surprised by 429s. What would you add?" A strong answer, out loud: "Right now the only signal we send is the 429 itself, with Retry-After telling them when to try again — but that's after they've already been rejected. I'd add RateLimit-Limit, RateLimit-Remaining, and RateLimit-Reset headers to every response, not just the rejected ones, so their client can see its quota trending down on ordinary successful calls and throttle itself before ever hitting the wall. It's the same token bucket and the same 429 underneath — this is purely about making the existing state visible earlier, so the partner's own client can be well-behaved instead of just reactive." The signal: naming that the fix is visibility on successful responses, not a change to the limiting logic itself.

Scope line

This lesson covers only making an existing rate limiter's state visible to the client on every response. It doesn't revisit Lesson 11's token-bucket algorithm itself (still the same bucket, same refill math) or Lesson 71's load shedding (a different trigger — server-side capacity signals, not a per-client quota — and these headers don't apply there, since a shed request was never about that client's own limit).
