1 · Three questions, in the original teaching order

Answer each out loud or on paper before reading the fold-out answer. If one is shaky, note it and go fix it in the practice file below rather than only rereading the old lesson.

Day 96 — struct. Why does struct.calcsize("ci") return 8 while struct.calcsize("=ci") returns 5, and why should a format string meant to be read back on a different machine always start with >, <, or =?

Fold-out answer: leaving the prefix off selects native mode, which follows the C compiler's own alignment rules and can insert padding bytes between fields for faster memory access — confirmed live, a 1-byte char plus a 4-byte int costs 8 bytes natively (3 padding bytes hidden inside), but only 5 under "=ci", which forces standard size with zero padding. Native mode's padding rules (and sometimes its byte order) are compiler- and machine-dependent, so a file packed on one machine and unpacked on another can silently disagree about the layout unless the format string pins down >, <, or = explicitly instead of trusting the default.

Day 97 — getpass. Why does getpass.getpass() fall back to plain, visible input instead of raising an error when stdin is redirected from a file, and what warns that the fallback happened?

Fold-out answer: suppressing terminal echo is something only a real terminal (a tty) can do — there's no OS-level echo setting to turn off on a redirected file or pipe. Rather than crash outright, getpass.getpass() falls back to reading the line visibly, the same way input() would, confirmed live with stdin swapped for a StringIO. GetPassWarning — a real, catchable subclass of UserWarning — fires at that moment specifically so calling code can notice the silent downgrade and react, rather than assuming a password was hidden when it wasn't.

Day 98 — string.Template. Why is Template("$name owes $amount") safe to fill with text that came from outside the program, in a way an f-string built the same way is not?

Fold-out answer: an f-string's {...} slot is a real Python expression, evaluated by the interpreter — powerful when a developer writes it, dangerous when the template text itself is untrusted. Template's $name syntax has no expression grammar at all: .substitute() only ever does a plain key lookup against the names given, confirmed live by feeding "untrusted" template text through it and watching a plain string value come back inert — there is no way to smuggle a function call or attribute lookup through a placeholder, which is exactly the gap an f-string can't close.
Where pandas/NumPy go from here: nothing pandas- or NumPy-specific today — this review only revisits Days 96-98's binary byte layouts, terminal-echo suppression, and safe string substitution, none of which needs a DataFrame or array to demonstrate.

2 · Why these three, and why no new terms today

Same interleaving logic as every prior review day: a tool for describing an exact byte layout when data isn't text-shaped at all, a tool for getting a secret from a human's keyboard into a running program without it ever appearing on screen, and a tool for filling a template with untrusted text without ever risking code execution — three different mental models pulled from three lessons, not one idea restated three ways. They also share a quieter throughline worth naming: all three are about a program being explicit instead of trusting a convenient default — struct refusing to assume native padding travels safely between machines, getpass refusing to silently claim a password was hidden when the fallback made it visible, Template refusing to treat a placeholder as anything more than a plain string lookup. Recognizing which of those three "say what you mean, don't assume" shapes a given problem actually needs — not just recalling the function names — is the retrieval goal today.
