CSRF: the other half of cookie auth

Lesson 4 named CSRF as the trade-off of storing a session in an HttpOnly cookie instead of localStorage — then said it was "handled separately" and moved on. It never actually was. Today it gets the lesson Lesson 4 deferred, the same way Lesson 12 later delivered the authorization half of "auth" that Lesson 4 had also put off.

1 · What CSRF actually is

Go back to Lesson 4's own quiz: it already made you tell XSS and CSRF apart, but only as "these are different, XSS is the one HttpOnly defends against." Here's the CSRF half spelled out. XSS is about which code runs — an attacker gets their own JavaScript executing inside your page's own origin, so it can read anything your page can read. CSRF has nothing to do with running code on your site at all. It's a request forged from a completely different site:

1. You log in to bank.example — browser gets Set-Cookie: session_id=abc123; HttpOnly
2. You open evil.example in another tab (a phishing link, an ad, whatever)
3. evil.example's HTML contains: <form action="https://bank.example/transfer" method="POST">
                                    <input name="to" value="attacker-account">
                                    <input name="amount" value="9999">
                                  </form>
   <script>document.forms[0].submit()</script>
4. Your browser POSTs to bank.example ──▶  auto-attaches session_id=abc123, same as any request to bank.example
5. bank.example's server sees a valid, authenticated session ──▶  processes the transfer

Nothing was stolen. The attacker never read your cookie, never ran code on bank.example, and an HttpOnly flag does nothing here — it only stops JavaScript from reading the cookie, and this attack never tries to read it. It relies on the one property every cookie has by design: the browser attaches it to any request to that domain, regardless of which page's HTML triggered the request. Your own browser is the one making the forged request, using your own valid session, and the server has no way to tell "the user clicked a button on my site" apart from "a form on some other site auto-submitted itself" — both arrive as an identical, validly-authenticated POST.

2 · Why this is specifically a cookie problem

This is the piece Lesson 4 asserted without justifying: "put the JWT in an Authorization header instead of a cookie" isn't just a storage preference, it's a structural CSRF fix. Walk through why. A cross-site <form> submission, or an <img src="evil-url">, or a background fetch from another origin — the browser will happily fire all of these at your domain and auto-attach any cookie that matches it. What the browser will not do is reach into evil.example's JavaScript and hand it the Authorization header value your app set on bank.example's own page. A custom header only gets attached by JavaScript that explicitly sets it, and that JavaScript would have to be running on your own origin to have the token available in the first place — which is exactly the XSS scenario, a different attack with a different defense.

So the two designs Lesson 4 compared land on opposite sides of this specific risk: a bearer token in a header is naturally immune to CSRF, because forging a cross-origin request doesn't forge the header. A session cookie is naturally exposed to CSRF, because forging a cross-origin request gets the cookie for free — that's what cookies are for. Neither is "more secure" overall (Lesson 4's XSS-vs-CSRF trade-off table still holds), but this is the concrete mechanism behind that one throwaway line.

The one-line version: CSRF exists because cookies attach themselves; it only threatens auth that lives in a cookie. Auth that lives in a header you set yourself was never exposed to it in the first place.

3 · Defense 1: the SameSite cookie attribute

If the entire attack depends on the browser attaching a cookie to a cross-site request, the simplest fix is telling the browser not to do that. That's what SameSite does — a third cookie attribute alongside the HttpOnly and Secure flags Lesson 4 already used:

ValueSent on cross-site request?When you'd use it
StrictNever — not even clicking a link in from another siteHighly sensitive actions; costs you: clicking an email link to your own site arrives logged out
LaxOnly top-level navigations (clicking a link), never a cross-site form POST or fetchThe sane default for session cookies — most browsers already default new cookies to this
NoneAlways, on every cross-site request — must be paired with SecureA cookie genuinely meant to be shared across sites, e.g. a third-party embed

Lax is the default worth reaching for because it draws the line exactly where the risk lives: clicking a link to your site is a normal, harmless user action that should arrive logged in, but a hidden cross-site <form> auto-submitting a POST — the actual forgery from section 1 — is blocked before it ever reaches your server, cookie and all. Note the honest limit though: SameSite=Lax is a browser-enforced default, not a contract every browser is guaranteed to honor identically forever, and it says nothing about a same-site attack (e.g. an XSS bug on your own domain triggering the same request) — which is why it's a strong first layer, not the only layer.

4 · Defense 2: a token the attacker can't produce

For state-changing requests specifically, the more explicit defense stops relying on the cookie alone and requires a second, unguessable value the request must carry — one a cross-site form has no way to obtain. Two common shapes of this:

  • Double-submit cookie: the server sets a random token as a cookie, and the client's own JavaScript (which can read a non-HttpOnly cookie) copies that value into a custom header on every state-changing request. The server checks the header value against the cookie value. A cross-site attacker's forged form can make the browser attach the cookie, but has no way to read its value to also put it in the header — it can only guess.
  • Synchronizer token pattern: the server embeds a random token as a hidden form field when rendering the page, and stores the same value server-side against that session. A forged cross-site form has no way to know or embed that token, so a submission without a matching one is rejected. This is the older, more traditional pattern (used by classic server-rendered apps); double-submit is the more common shape for an API + SPA split.

Both patterns share the same idea: forging the request is easy (any page can make the browser fire a POST), but forging the token is not, because the attacker's page can never read a value scoped to your origin. Here's the double-submit check as a Go middleware — the shape most REST APIs actually reach for:

func requireCSRFToken(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if r.Method == http.MethodGet || r.Method == http.MethodHead {
            next.ServeHTTP(w, r) // safe methods don't change state, nothing to check
            return
        }

        cookie, err := r.Cookie("csrf_token")
        if err != nil {
            http.Error(w, "missing csrf cookie", http.StatusForbidden)
            return
        }

        header := r.Header.Get("X-CSRF-Token")
        if header == "" || subtle.ConstantTimeCompare([]byte(header), []byte(cookie.Value)) != 1 {
            http.Error(w, "csrf token mismatch", http.StatusForbidden)
            return
        }

        next.ServeHTTP(w, r)
    })
}

Two details worth naming: only unsafe methods (POST/PUT/PATCH/DELETE) are checked — a GET is expected to be side-effect-free, so there's nothing for a forged GET to change (this is also why GET handlers must never mutate state, a rule worth holding regardless of CSRF). And the comparison uses subtle.ConstantTimeCompare rather than ==, the same timing-attack-resistant comparison used for password hashes — not because the token is secret from the legitimate client, but because a byte-by-byte == comparison leaks how many leading bytes matched through response timing, handing an attacker a way to guess the token one byte at a time.

5 · Layered, not either/or

SameSite=Lax and a double-submit token aren't competing options — production systems commonly run both. SameSite is a cheap, broad first layer enforced by the browser itself with zero server-side state to manage. A token check is the explicit, server-verified backstop for the specific requests that matter (state-changing ones), and it keeps working even against an older browser or a misconfigured cookie that skipped the SameSite attribute entirely. Defense in depth, not a choice between them.

Q: "Does your API need CSRF protection?" A strong answer, out loud: "It depends entirely on how auth travels. If the client sends a bearer token in an Authorization header, no — a cross-site page can't make the browser attach a header it never set, so CSRF isn't a risk there. If auth travels in a cookie, then yes: I'd set SameSite=Lax as the baseline, since it blocks the classic forged-form-POST case for free with no server-side state, and add a double-submit or synchronizer token check on top for state-changing endpoints specifically, since SameSite alone depends on browser behavior I don't fully control. I wouldn't bother protecting GET requests — those should never mutate state in the first place, CSRF or not." The signal: tying the defense to which auth mechanism is in play, not reciting "add CSRF tokens" as a rule that applies everywhere uniformly.
