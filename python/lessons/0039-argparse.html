argparse: turning a script into a real command-line tool

Day 7's capstone hardcoded its CSV path at the top of the file. Every script so far has, one way or another — change what it does, and you edit the source. A CLI tool takes its input from the command line instead — wordcount report.txt --top 3 — and Python's standard-library argparse module is the standard way to build one, without hand-parsing sys.argv yourself.

Bridge from SQL: think of argparse's declared arguments as a stored procedure's typed parameter list (CREATE PROCEDURE report(top_n INT DEFAULT 5, unit TEXT DEFAULT 'words')) — declare the names, types, and defaults once, and every call is checked and coerced against that shape before the body ever runs, instead of the body defensively parsing raw text itself.

1 · The problem: sys.argv is just a list of strings

Every command-line invocation lands in sys.argv — a plain list, index 0 is the script's own name, everything after is whatever the caller typed, and all of it is a string, untyped and unvalidated:

# python3 report.py report.txt --top 3 -v
# sys.argv == ['report.py', 'report.txt', '--top', '3', '-v']

Hand-parsing that means writing your own loop to find "--top", grab the next element, convert it with int(), handle it missing, handle a typo like --to, and write your own --help text — all before the script's actual job starts. argparse replaces that loop: declare what arguments exist, once, and it handles finding, converting, defaulting, rejecting bad input, and --help for free.

2 · Declaring arguments: positional, optional, flags

An ArgumentParser is built once, then told about each argument via add_argument():

import argparse

parser = argparse.ArgumentParser(
    prog="wordcount",
    description="Count top words in a text file",
)
parser.add_argument("infile", help="path to the text file")          # positional -- required, no --
parser.add_argument("-n", "--top", type=int, default=5,      # optional -- has a default
                    help="how many top words to show")
parser.add_argument("-v", "--verbose", action="store_true",   # a flag -- no value, just on/off
                    help="print extra detail")

args = parser.parse_args()   # reads sys.argv[1:] automatically
print(args.infile, args.top, args.verbose)

A name with no leading dash ("infile") is a positional argument — required, matched purely by order. A name starting with -/-- is an optional argument — has a default, and the caller can skip it entirely. action="store_true" makes an option a pure on/off switch: present on the command line means True, absent means the flag's default (False here), with no value to type after it.

3 · What comes back: a Namespace, already typed

Verified live: calling parser.parse_args(["report.txt", "--top", "3", "-v"]) directly (bypassing real sys.argv for a repeatable check) returns Namespace(infile='report.txt', top=3, verbose=True, unit='words') — args.top is a real int, 3, not the string "3" that was typed, because type=int already ran the conversion. Omitting --top entirely and re-parsing confirms the declared default takes over: args.top == 5, still an int. Every declared argument becomes one attribute on the returned Namespace object — args.infile, args.top — not a dict to key into, though vars(args) converts it to one if a dict is genuinely needed.

choices= narrows valid values. parser.add_argument("--unit", choices=["words", "lines"], default="words") restricts that option to exactly those two strings — verified live, calling it with --unit bytes is rejected before args is even built, with no code needed to check the value by hand.

4 · Bad input doesn't raise — it prints usage and exits

This is the one behavior most worth getting right before shipping a CLI: parse_args() does not raise a catchable Python exception on bad input. Verified live against three failure cases — a non-integer passed where type=int expected one, a value outside choices=, and a missing required positional — all three print a usage line plus a one-line error to stderr, then call sys.exit(2), which raises SystemExit. A bare try/except Exception: around parse_args() (Day 8's narrow-catch habit) will not catch this, because SystemExit deliberately does not inherit from Exception — it inherits directly from BaseException, precisely so a normal except Exception lets a program-ending exit through rather than swallowing it. Confirmed live: -h/--help takes the same SystemExit path but with code 0 — success, not failure — after printing the auto-generated help text argparse builds from every help= string supplied.

5 · Reading a real argument list end to end

Put together, a small tool looks like this — no more hand-rolled string comparisons against sys.argv:

import argparse

def build_parser():
    parser = argparse.ArgumentParser(prog="wordcount")
    parser.add_argument("infile")
    parser.add_argument("-n", "--top", type=int, default=5)
    parser.add_argument("-v", "--verbose", action="store_true")
    return parser

def main(argv=None):
    args = build_parser().parse_args(argv)   # argv=None -> real sys.argv[1:]
    if args.verbose:
        print(f"reading {args.infile}, top {args.top}")
    # ... real work here, using args.infile / args.top ...

build_parser() split out as its own function, and main(argv=None) taking an explicit (optional) argument list rather than always reading real sys.argv, is what makes a CLI testable — a test calls main(["fixture.txt", "--top", "2"]) directly with a fake argument list, no subprocess needed, tying straight back to Day 11's pytest.

Where pandas goes from here: a pandas-based script still typically takes its input path and options from argparse exactly this way — argparse is the CLI layer regardless of whether the body underneath is plain Python or pd.read_csv(args.infile); nothing here is pandas-specific, and this is the only sentence in this lesson that names it.

Q: "How would you turn a one-off script into a command-line tool?" A strong answer, out loud: "I'd reach for the standard library's argparse rather than hand-parsing sys.argv — declare each argument once with add_argument(), including its type, default, and help text, and parse_args() gives back a typed Namespace with validation, --help, and clear error messages for free. One thing I'd watch for: bad input doesn't raise a normal exception, it calls sys.exit() under the hood, so a broad except Exception around parsing won't catch it — and that's deliberate, not a bug, since SystemExit inherits from BaseException specifically so it isn't accidentally swallowed." The signal: knowing the module exists and reaching for it by default, plus understanding the exit-not-raise behavior instead of being surprised by it in production.
