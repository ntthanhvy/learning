np.abs() and np.sqrt(): the two building blocks under every error-metric column

Lesson 128 closed its own fresh scan with np.abs(), np.sqrt(), and np.floor()/np.ceil() open from Lesson 127's scan, plus np.log()/np.exp() newly confirmed untaught. Today's own fresh scan re-confirmed all four candidates are still genuinely untaught (grepped every lesson body and glossary row; the names only ever appeared in passing inside two prior "next lesson" teaser lines, never as a lesson's own topic). np.abs() and np.sqrt() win as one coherent pair: together they are the two calls behind the single most common interview error-metric task — turning a signed delta column into mean absolute error or RMSE — and, confirmed directly below, they disagree sharply on dtype handling and overflow safety despite looking like two equally "simple" math functions.

1 · Both keep the Series and its Index — but handle dtype differently

np.abs(x) and np.sqrt(x) both return a Series with the original Index intact when called directly on one — confirmed directly (numpy 2.5.4, pandas 3.1.1), neither one flattens to a bare ndarray the way Lesson 128's np.vectorize() does. They part ways on dtype, though:

import numpy as np
import pandas as pd

s_int = pd.Series([-5, 3, -2], index=["a", "b", "c"])

np.abs(s_int).dtype    # int64  -- stays in the input's own dtype family
np.sqrt(s_int).dtype   # float64 -- ALWAYS upcasts to float, even on a clean int input

Confirmed directly: np.abs() follows the same dtype-preserving rule as Lesson 127's np.sign() — int in, int64 out; float in, float64 out. np.sqrt() never preserves an integer dtype at all, because a square root is almost never a whole number; it always returns float64, confirmed directly, even when every input value happens to be a perfect square. Also confirmed directly: pandas defines Series.abs() as a real method — s_int.abs() works and matches np.abs(s_int) exactly — but there is no Series.sqrt() at all; calling it raises AttributeError immediately, the same naming gap Lessons 126 and 127 found for np.roll() and np.sign(). The pandas-idiomatic square root is Series.pow(0.5) or calling np.sqrt() directly on the Series, confirmed directly to produce identical results.

2 · The trap: np.sqrt() on a negative warns and returns NaN — np.abs() on INT64_MIN silently returns the wrong sign

Confirmed directly (numpy 2.5.4): np.sqrt() on a negative real number returns NaN and raises a RuntimeWarning — loud and visible. np.abs() on the single most negative possible int64 value returns the same negative number back, unchanged, with no warning at all — silent and wrong.
# np.sqrt() on a negative: NaN, with a visible warning
np.sqrt(np.array([-4.0, 9.0]))
# RuntimeWarning: invalid value encountered in sqrt
# array([nan,  3.])

# np.abs() on INT64_MIN: silently wrong, no warning at all
minval = np.iinfo(np.int64).min   # -9223372036854775808
np.abs(np.array([minval], dtype=np.int64))
# array([-9223372036854775808])  -- still negative! the true magnitude doesn't fit in int64

Confirmed directly: that second result is two's-complement integer overflow, not a bug report — the positive magnitude of int64's most negative value is one larger than int64's own maximum, so it wraps straight back around to the original negative number, and NumPy raises nothing. Series.abs() reproduces the identical silent wraparound on the same value. np.sqrt()'s NaN-plus-warning on a negative input is the safer failure mode of the two — it is visible in a test run or a notebook's own warning output; the np.abs() overflow produces a plausible-looking negative number that passes every downstream check silently. This specific input (int64's absolute minimum) is rare in real data, but any column read in as a narrower signed int dtype near its own floor carries the same risk.

3 · Complex input, object dtype, and no views

Confirmed directly from the official docs: np.abs() on a complex number returns its magnitude — np.abs(3 + 4j) is 5.0 (Pythagorean distance from zero), a genuinely useful result, unlike Lesson 127's np.sign() on complex input, which returns a unit-direction value that is a trap to misread as a -1/0/1 code. Confirmed directly, both functions run on an object-dtype array of plain Python numbers without error — np.abs() dispatches to each element's own abs(), and Series.abs() does the same — but np.sqrt() raises a TypeError immediately on object dtype, since a plain Python int/float has no .sqrt() method for the ufunc to call. Confirmed directly via np.shares_memory(): both functions always return an independent new array, never a view into the input, regardless of dtype.

np.abs(3 + 4j)       # 5.0  -- magnitude, a real / useful answer
np.sqrt(np.array([-1, 4, 9], dtype=object))
# TypeError: loop of ufunc does not support argument 0 of type int
# which has no callable sqrt method

Put together, this is the real building block behind an error-metric column: abs_err = np.abs(actual - predicted) for mean absolute error, and rmse = np.sqrt((err ** 2).mean()) for root-mean-squared error — confirmed directly to run clean end to end, no loop, no apply().
