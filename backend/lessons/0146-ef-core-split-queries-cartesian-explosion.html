Two Includes, one JOIN, way too many rows

Lesson 106 fixed EF Core's N+1 problem with Include(): fold every related table into one query, one round trip, instead of a query per row. It also named the one case where Include() itself becomes the bottleneck, and left it for later: calling it twice for two sibling collections. Today's lesson is that follow-up — the problem is called cartesian explosion, and EF Core's fix is a method named exactly for what it does: AsSplitQuery().

1 · One JOIN, two sibling collections, a cross product

Lesson 106's fix folded Order.Items into one query via Include(). That stays true for one collection. Add a second, sibling collection on the same entity and the shape changes:

var blogs = await ctx.Blogs
    .Include(b => b.Posts)
    .Include(b => b.Contributors)
    .ToListAsync();

Posts and Contributors are both collection navigations hanging directly off Blog — siblings, same level. SQL has no way to JOIN two sibling one-to-many relationships into one result set without multiplying them: a blog with 10 posts and 10 contributors gets every post paired with every contributor, 100 rows back for that one blog instead of the 20 you'd expect from "10 posts plus 10 contributors." Microsoft's own docs name this exact 10-and-10-becomes-100 case. The bigger the lists, the worse the multiplication — three sibling collections of 10 each would multiply to 1,000 rows for one blog.

Frontend-habit trap: this looks like the kind of thing a GROUP BY or a smarter SELECT shape should just avoid, the way a well-written GraphQL resolver avoids over-fetching. It's not a query-writing mistake — it's what a JOIN is, structurally, once two independent one-to-many relationships sit at the same level. The fix isn't a smarter JOIN; it's not using one JOIN for both.

2 · The nested case doesn't explode the same way

Not every two-Include query has this problem. Chaining a second Include through ThenInclude — nesting one level deeper rather than adding a sibling — stays linear:

var blogs = await ctx.Blogs
    .Include(b => b.Posts)
    .ThenInclude(p => p.Comments)
    .ToListAsync();

Here Comments belongs to Post, not to Blog directly — there's exactly one row per comment, no cross product, because the second JOIN walks further down the same chain instead of branching sideways. The rule worth keeping: cartesian explosion is about sibling collections on the same parent, not about the number of Include calls in a query.

3 · A quieter cost: duplicated columns, even with one collection

A single Include() has its own, smaller version of the same row-duplication idea. ctx.Blogs.Include(b => b.Posts) still returns one row per post, and every one of those rows repeats the parent blog's columns — Id, Name, and any other column on Blog included in the projection. Usually that's negligible. It stops being negligible if Blog happens to carry a large column (binary data, a long text field) — that column now travels over the wire once per post, not once per blog. The documented fix for that narrower case is a plain projection that leaves the big column out, not AsSplitQuery():

var blogs = await ctx.Blogs
    .Select(b => new { b.Id, b.Name, b.Posts })
    .ToListAsync();

That trades away change tracking on the result (Lesson 106's distinction again — a projection to an anonymous type isn't a tracked entity, so it can't be saved back through SaveChanges), the same trade AsNoTracking() makes on purpose.

4 · AsSplitQuery(): stop joining, issue one query per collection instead

For the sibling-collection case, EF Core's answer is a method that does exactly what its name says — split one query with multiple JOINs into multiple queries with none of the cross-product problem:

var blogs = await ctx.Blogs
    .Include(b => b.Posts)
    .AsSplitQuery()
    .ToListAsync();

This generates two separate SELECT statements instead of one JOINed query — one for Blogs, one for Posts filtered down to the matching blogs, matched back up in memory on the client side once both results arrive:

-- query 1
SELECT [b].[BlogId], [b].[Url] FROM [Blogs] AS [b] ORDER BY [b].[BlogId]
-- query 2
SELECT [p].[PostId], [p].[BlogId], [p].[Title]
FROM [Blogs] AS [b]
INNER JOIN [Posts] AS [p] ON [b].[BlogId] = [p].[BlogId]
ORDER BY [b].[BlogId]

No sibling collection multiplies against another, because there's no longer a single result set for them to multiply inside. Each collection gets its own round trip, and each round trip returns exactly the rows that collection actually has.

5 · What split queries cost instead

Split queries trade one performance problem for a different set of trade-offs Microsoft's docs name explicitly, not a strictly-better option:

Single query (JOIN, default)Split query (AsSplitQuery())
Row multiplicationsibling collections cross-multiplynone — each collection is its own query
Round tripsoneone per included collection
Consistency under concurrent writesguaranteed by the single querynot guaranteed — a write between the two queries can leave results inconsistent
Client-side memoryone buffered resultearlier query's results held in memory until later queries finish

The consistency row is the one worth not skipping past: a single JOIN-based query is one round trip to a database that answers it from one consistent point in time. Two separate queries are two separate round trips — if another transaction commits a new post in the gap between them, the Blogs query and the Posts query can reflect two different moments, something a single query structurally cannot do. Microsoft's docs call out wrapping split queries in a serializable or snapshot transaction as the mitigation, with the caveat that doing so brings back a performance cost of its own.

There's a second documented trap, specific to pairing split queries with pagination: ordering must be fully unique across all the split queries, not just the primary one. Ordering only by a non-unique column (date, say) can let each split query's database execution pick a different arbitrary row when ties exist, so Skip/Take on EF Core versions before 10 can return mismatched pages across queries that were supposed to describe the same window. Ordering by date and a unique id together closes that gap.

6 · Choosing per query, or globally

AsSplitQuery() and its opposite, AsSingleQuery(), are both per-query operators — call one on a specific query to override whatever the context's default is:

var blogs = await ctx.Blogs
    .Include(b => b.Posts)
    .AsSingleQuery()   // force the JOIN shape, even if split is the context default
    .ToListAsync();

The default, with no configuration at all, is single query — the JOIN shape Lesson 106 already covered. EF Core knows this default can be the wrong call, though: it emits a warning whenever a query loads multiple collections and neither a global default nor a per-query AsSingleQuery()/AsSplitQuery() has been set, precisely so the cartesian-explosion case in section 1 doesn't ship unnoticed. The global default can be set once, on the provider options, if most of the app's multi-collection queries should split:

protected override void OnConfiguring(DbContextOptionsBuilder optionsBuilder) {
    optionsBuilder.UseSqlServer(connectionString,
        o => o.UseQuerySplittingBehavior(QuerySplittingBehavior.SplitQuery));
}

Q: "A list endpoint does ctx.Orders.Include(o => o.Items).Include(o => o.Tags).ToListAsync() and is returning way more rows than expected for a small number of orders. What's going on?" A strong answer, out loud: "Items and Tags are both sibling collection navigations on Order, so that single query's JOINs produce a cross product — an order with 5 items and 5 tags comes back as 25 duplicated rows for that one order, not 10. I'd fix it with AsSplitQuery(), which issues one SQL query per included collection instead of one big JOIN, so neither collection multiplies against the other. I'd watch two things before shipping that: whether this endpoint also does Skip/Take pagination, since ordering has to be fully unique across the split queries or pages can mismatch, and whether concurrent writes between the split queries' round trips could leave the response inconsistent, since a single JOIN query doesn't have that gap." The signal: naming cartesian explosion as a sibling-collection JOIN problem specifically (not "JOINs are slow"), and naming both AsSplitQuery() trade-offs rather than treating it as a free fix.

Scope line

This lesson covers cartesian explosion from sibling Include() calls, AsSplitQuery()/AsSingleQuery(), the consistency and round-trip trade-offs, the Skip/Take ordering caveat, and the global UseQuerySplittingBehavior default. It does not cover explicit loading (Entry().Collection().Load()) as a third loading strategy, one-to-one navigations (always loaded via JOIN regardless of split/single mode, per the same source), or query compilation/caching internals — named in the primary source but out of scope here.
