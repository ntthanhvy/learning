pandas 3.0's default str dtype, and the select_dtypes gotcha it causes

Lesson 78 left two open leads — more groupby/agg beyond Lessons 4/40/48/61/66, or memory/dtype beyond Lessons 25/41/51/62 — but neither survived a fresh scan untouched: grepping all 78 lesson bodies plus the glossary found the groupby/agg lead nearly exhausted, while re-reading Lesson 62 (memory/dtype) in full turned up a real gap one level underneath it. Lesson 60's own quiz already mentioned, in passing, that str.contains()'s na= default depends on "the modern str dtype" versus "legacy object dtype" — but no lesson ever explained what that modern str dtype actually IS, why every text column here has quietly been one since Lesson 62 ran on pandas 3.0.6, or the deprecation trap it sets for Lesson 25's own select_dtypes(). That's today's topic.

1 · Confirmed directly: read_csv() no longer gives you plain object dtype

Every earlier lesson describing a text column as "object dtype" was accurate on older pandas, but current pandas changed the default. Loading this course's own orders_raw.csv fixture:

df = pd.read_csv("orders_raw.csv")
df.dtypes
-- order_id      int64
-- customer        str
-- amount          str
-- order_date      str
-- dtype: object

Confirmed directly (pandas 3.0.6): every text column's dtype now prints as str, not object — isinstance(df["customer"].dtype, pd.StringDtype) is True. This is a pandas 3.0 default-inference change, not something this course's fixture did differently; older code and older pandas tutorials describing text columns as "object dtype" are describing the previous default, still reachable today via .astype(object) but no longer what you get for free.

2 · Does the new default change memory usage? Confirmed: no

Lesson 62 taught measuring memory with memory_usage(deep=True) and shrinking low-cardinality text with category. It's tempting to assume the new str dtype is itself a memory optimization — it is not:

big["customer"].memory_usage(deep=True)                     # 155632, default "str" dtype
big["customer"].astype(object).memory_usage(deep=True)     # 155632, legacy "object" dtype -- IDENTICAL
big["customer"].astype("category").memory_usage(deep=True)   # 3288, still the real win

Confirmed directly on the 500x-repeated fixture (Lesson 62's own scaling technique): default str and legacy object cost the exact same bytes. The new default is about type safety and consistency — a dedicated string type instead of a generic bucket that could hold literally anything — not about memory. Lesson 62's own advice is unchanged: category is still the tool that actually shrinks a low-cardinality text column, regardless of whether it starts as str or object.

Two different things named "string," worth keeping straight: lowercase str (today's topic) is the new automatic default — you get it for free, no opt-in. Lesson 51's string (via convert_dtypes()) is pandas' older nullable string dtype, opt-in only. Confirmed directly they're the same underlying StringDtype class with the same .storage value — but their .na_value differs: the default str column's missing marker is plain float NaN, while the nullable string column's is pd.NA. Same class, different missing-value contract — worth checking .dtype.na_value directly rather than assuming, especially before an == NaN comparison (Lesson 3's own NaN rule still applies to either).

3 · The gotcha: select_dtypes("object") still works today — with a warning

Lesson 25 taught select_dtypes(include="object") to find text columns. It still finds them — but only through a deprecated backward-compatibility shim:

df.select_dtypes(include="object").columns.tolist()
-- ['customer', 'amount', 'order_date']   -- still works, but:
-- Pandas4Warning: For backward compatibility, 'str' dtypes are included
-- by select_dtypes when 'object' dtype is specified. This behavior is
-- deprecated and will be removed in a future version.

df.select_dtypes(include="str").columns.tolist()
-- ['customer', 'amount', 'order_date']   -- identical result, ZERO warning

Confirmed directly: both calls return the exact same three columns today, but only include="object" raises Pandas4Warning — include="str" gets there silently. This is the same "still runs, quietly outdated" family as Lesson 73's stale argsort() docstring and Lesson 29's removed isin() folklore: code written against the old default keeps working for now, on borrowed time, while the forward-compatible spelling is one word different and already available.

Q: "Why would df.select_dtypes(include='object') print a deprecation warning on current pandas?" A strong answer, out loud: "pandas 3.0 changed the default dtype read_csv() gives text columns — it's now a dedicated str dtype (pandas.StringDtype), not the old generic object dtype. select_dtypes(include='object') still catches those str columns today, but only through a backward-compatibility shim that pandas has already flagged for removal, so it warns every time. The fix is just passing include='str' instead, which matches the same columns with no warning. The bigger point I'd make: the new str dtype doesn't change memory usage at all versus the old object dtype — it's the same bytes — so Lesson-level advice about using category for low-cardinality text is completely unaffected; this is a type-identity change, not a memory optimization." The signal: naming the actual pandas-version cause instead of guessing, and correctly scoping what did and didn't change (identity, not memory).
