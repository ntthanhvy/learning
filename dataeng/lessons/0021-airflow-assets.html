1 · The gap a @daily schedule can't close

Day 7's food_delivery_pipeline DAG runs dbt_build on a fixed clock, schedule="@daily". That's a real limitation this course has carried since Day 7 without naming it: raw.order_events doesn't fill up once a day on a schedule — Day 6's Kafka consumer lands rows continuously, whenever the stream has something to deliver, as its own long-running process entirely outside Airflow. A clock-scheduled dbt_build is always either early (today's events haven't all landed yet) or late (new events sat unprocessed for hours before the next midnight run) — it has no way to know when raw.order_events actually changed, because nothing tells it.

An Asset fixes exactly this: it's Airflow's own object for "a piece of data exists," and a task can declare it produces one (outlets=), while a separate DAG can be scheduled to run the moment that Asset is marked updated (schedule=[asset]), instead of on a clock. This round confirmed the class is real and importable against the pinned 3.3.1 install:

from airflow.sdk import Asset
order_events_asset = Asset("postgres://fdp/raw.order_events")

The string is a name/URI, not a live connection — Airflow never actually reads raw.order_events itself to check this. It's an identifier a task declares against, nothing more; the actual proof that the data changed still has to come from a task that checked.

2 · Two roles: producing an Asset, scheduling on one

This round built both halves as two small, real scratch DAGs — a task that marks the Asset updated, and a separate DAG scheduled by it — to see the actual mechanics before writing today's build step. Producing is a task-level outlets= argument, confirmed against a real BashOperator:

from airflow.sdk import DAG, Asset
from airflow.providers.standard.operators.bash import BashOperator

order_events_asset = Asset("postgres://fdp/raw.order_events")

with DAG(dag_id="producer_dag", schedule="@daily", start_date=..., catchup=False) as dag:
    check = BashOperator(task_id="check_events", bash_command="...", outlets=[order_events_asset])

Scheduling on it is a DAG-level schedule= argument taking a list of Assets instead of a cron string:

with DAG(dag_id="dbt_build_on_events", schedule=[order_events_asset], start_date=..., catchup=False) as dag:
    dbt_build = BashOperator(task_id="dbt_build", bash_command="...")

This round's own DagBag parse of the scheduled-side DAG confirms schedule=[asset] compiles to a real, named timetable rather than silently falling back to something else:

consumer schedule: AssetTriggeredTimetable(asset_condition=AssetAll(Asset(name='postgres://fdp/raw.order_events', ...)))

AssetAll is the condition class Airflow uses even for a single asset — it reads as "wait until every asset in this list has a fresh event," and composing two assets with Python's own &/| operators (confirmed this round) produces AssetAll/AssetAny respectively, for a DAG that should wait on more than one upstream. Today's build only needs one asset, so this is vocabulary for now — worth knowing the names exist the day a mart depends on two independently-updating sources.

3 · The real link, read out of Airflow's own database

Declaring the same Asset("postgres://fdp/raw.order_events") string in two different DAG files is what connects them — Airflow matches assets by that identifier, not by Python object identity, so the producer and scheduled DAGs never import each other. This round confirmed the link is a real, queryable relationship, not just inferred from matching strings, via airflow assets details run against the live scratch metadata database after both DAGs were parsed:

uri              | postgres://fdp/raw.order_events
scheduled_dags   | {'dag_id': 'dbt_build_on_events', ...}
producing_tasks  | {'dag_id': 'order_events_landed', 'task_id': 'check_order_events_grew', ...}

Both sides of the relationship are visible from either DAG's perspective, confirmed by inspecting the exact same asset after running the producing task for real: airflow dags test order_events_landed 2026-10-06 produced a genuine new row in Airflow's asset_event table —

sqlite3 airflow_home/airflow.db \
  "SELECT a.name, ae.source_dag_id, ae.source_task_id, ae.timestamp FROM asset_event ae JOIN asset a ON a.id = ae.asset_id;"
postgres://fdp/raw.order_events|order_events_landed|check_order_events_grew|2026-10-06 02:52:39.516831

That's the actual mechanism underneath "data-aware scheduling": a task finishes, Airflow writes one row recording which asset it touched and when, and a DAG scheduled on that asset is queued the next time the (here, otherwise idle) scheduler looks for new asset events — the same metadata-database pattern Day 20 found XCom uses, now storing "this asset changed" instead of "here's a small value," and still not a place to put the actual order_events rows themselves.

An honest limit of this round's verification: airflow dags test runs a DAG directly and skips the scheduler's own loop entirely (the same thing Day 7 and Day 19 found for other commands) — it does write the real asset_event row shown above, but airflow assets details's own last_asset_event field stayed None afterward rather than reflecting it, because that particular summary field is only updated by the scheduler's asset manager, a code path dags test doesn't run through. The event row itself (and therefore the trigger a live scheduler would act on) is real and confirmed; that one convenience field in the CLI's own summary output is not, and this round says so rather than papering over it.

4 · Why this isn't just Day 19's catchup in disguise

It's worth being precise about what changed, since both topics are about "when does a run happen": catchup/backfill (Day 19) is still entirely clock-driven — every run corresponds to some calendar interval, whether created automatically or requested on demand. An Asset-scheduled DAG has no calendar interval behind it at all; it runs purely because an event fired, whenever that happens to be, and catchup/logical_date questions don't really apply the same way. The two features solve different problems and can combine (a clock-scheduled producer whose output triggers an event-scheduled consumer, exactly today's shape), but naming them as the same idea would be wrong.

from datetime import datetime

from airflow.sdk import DAG, Asset
from airflow.providers.standard.operators.bash import BashOperator

order_events_asset = Asset("postgres://fdp/raw.order_events")
REPO_DIR = "/opt/airflow/food-delivery-pipeline"  # same path Day 7 used

with DAG(
    dag_id="dbt_build_on_events",
    schedule=[order_events_asset],
    start_date=datetime(2026, 9, 21),
    catchup=False,
) as dag:
    dbt_build = BashOperator(
        task_id="dbt_build",
        bash_command=(
            f"cd {REPO_DIR}/warehouse && "
            "uv run --with 'dbt-postgres==1.11.0' dbt build --profiles-dir ."

Q: "Your batch dbt job runs nightly, but your streaming data lands continuously. How would you fix the mismatch?" A strong answer, out loud: "A clock schedule is the wrong trigger when the thing you're reacting to doesn't happen on a clock — Kafka delivers order events continuously, so a nightly dbt_build is always either early or stale by hours. Airflow's Assets feature fixes this directly: one task declares, via outlets, that it produced a specific piece of data, and a separate DAG is scheduled on that asset instead of a cron string, so it only runs when there's actually something new. In my pipeline, a small scheduled check watches raw.order_events for real growth and marks the asset updated only then, and the dbt_build DAG is scheduled on that asset instead of @daily. The nightly dbt_build for the batch-loaded restaurant/courier/order tables stays exactly as it was, because those really do only change once a day — the fix is scoped to the table that doesn't behave that way, not a wholesale rewrite." The signal: scoping the fix to the actual mismatch (one table, not the whole DAG) rather than claiming Assets replace clock scheduling everywhere.
