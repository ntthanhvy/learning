1 · Three questions, in the original teaching order

Answer each out loud or on paper before reading the fold-out answer. If one is shaky, note it and go fix it in the practice file below rather than only rereading the old lesson.

Day 108 — queue. Why can two threads safely share one queue.Queue with no threading.Lock written by hand, and what does a plain q.get() do by default when the queue is currently empty?

Fold-out answer: queue.Queue's own put()/get() methods already acquire and release an internal lock on every single call, confirmed live — no manual threading.Lock is needed to avoid the race condition Day 73 named. A plain q.get() on an empty queue blocks by default, waiting until some other thread puts an item in, rather than raising right away; get_nowait() is the deliberate non-blocking alternative, raising queue.Empty immediately instead.

Day 109 — multiprocessing. After a child Process appends to what looks like a shared list, what does the parent see in that same list once the child finishes and is joined — and why does that differ from Day 73's threads?

Fold-out answer: no change at all, confirmed live — the parent's list stays exactly as it was before the child ran. A child process gets its own separate copy of memory the moment it starts, so mutating what looks like a shared variable inside the child never changes the parent's copy. This is the opposite risk from Day 73's threads, which all share the same memory and can race on it; getting a value back out of a child process requires something built for crossing that boundary, like a multiprocessing.Queue, never a plain shared variable.

Day 110 — fractions. Why does Fraction(1, 3) + Fraction(1, 3) + Fraction(1, 3) equal exactly 1, when the equivalent float math can land on a near-miss — and why does Fraction(0.1) print a large, unexpected-looking fraction instead of 1/10?

Fold-out answer: Fraction stores a numerator and denominator as two integers directly, with no binary or decimal rounding step at all, confirmed live — so the three thirds reduce to exactly Fraction(3, 3), which is exactly 1. Fraction(0.1) prints something like 3602879701896397/36028797018963968 because it faithfully reports the float 0.1's own pre-existing binary approximation — that float was never exactly one-tenth to begin with. Building from a string instead, Fraction("0.1"), never passes through float at all and lands on the exact 1/10.
Where pandas/NumPy go from here: nothing pandas- or NumPy-specific today — this review only revisits Days 108-110's thread-safe queuing, process-based concurrency, and exact rational arithmetic, none of which needs a DataFrame or ndarray to demonstrate. Day 109's own boundary callout (NumPy releasing the GIL internally via its own C code) and Day 110's own boundary callout (no dedicated exact-rational dtype in either library) are recalled by name only, not re-demonstrated.

2 · Why these three, and why no new terms today

Same interleaving logic as every prior review day: a tool for handing work safely between threads inside one process, a tool for running separate processes that genuinely compute at the same time on different cores, and a tool for exact ratio arithmetic that no float or Decimal can match. Three different mental models pulled from three lessons, not one idea restated three ways. They also share a quieter throughline worth naming: Days 108 and 109 are two halves of the same concurrency story Day 73 opened and never finished — threads share memory and need coordination (queue.Queue supplies it safely), while processes share nothing and need a deliberate hand-off to get anything back out (multiprocessing.Queue supplies that instead) — and Day 110 is a reminder that "exact" is not one fixed idea: Day 70's Decimal is exact for base-10 money, Day 110's Fraction is exact for ratios neither base-10 nor base-2 can finish writing out.
