Database views and materialized views: saving a query, not a table

Lesson 2 called the schema "the truth, shared by every feature" and the JSON response "a view, rebuilt per request." Postgres has a literal feature with that exact name. Today: what a VIEW actually is, why it doesn't store anything, and the one case — a materialized view — where it does.

1 · A view is a saved query, not a copy of data

Lesson 36 (N+1) fixed a repeated join-per-row pattern with one real JOIN. Lesson 2 taught denormalization: deliberately storing a fact twice, as a trade-off you must justify. A view sits between those two: it's neither a copy nor a fix for slow joins — it's a name for a query.

CREATE VIEW order_summaries AS
SELECT
  o.id AS order_id,
  COUNT(oi.id) AS item_count,
  SUM(oi.unit_price * oi.quantity) AS total_cents
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
GROUP BY o.id;

After that runs once, SELECT * FROM order_summaries WHERE order_id = 42 works exactly like querying a table — but Postgres stores none of those rows anywhere. Every time the view is queried, it re-runs the JOIN and GROUP BY behind the name, against the current orders/order_items data, right then. A view holds zero storage of its own; drop the underlying tables and the view breaks, because there was never anything in it to keep.

The frontend equivalent you already own. This is a saved query the same way a named, reusable SQL fragment or a derived Redux selector is a saved computation — selectCartTotal(state) doesn't store a total anywhere; it recomputes from the current store every time it's called. A Postgres view is that same "always recomputed, never stale, no cache" contract, just written once in SQL instead of once in JS and imported everywhere a component needs it.

2 · What a view is actually for

Two honest reasons to reach for one, neither about speed:

  • Hiding a query's complexity behind a name. Once order_summaries exists, every handler that needs an order's item count and total just selects from it — nobody re-derives the JOIN and GROUP BY in five different places, and nobody has to relearn the schema's join path to write a new report.
  • Narrowing what a caller can see, without a second copy of the data. A view can select a subset of columns or rows — CREATE VIEW active_accounts AS SELECT id, email FROM accounts WHERE deleted_at IS NULL reuses Lesson 34's soft-delete filter in one place, and a role granted access only to that view never sees a column it selects out, like password_hash.

What a view does not do: make a slow JOIN fast. Wrapping a query in CREATE VIEW changes nothing about how Postgres executes it — the same query plan runs either way. If Lesson 5's indexing lesson would have helped the underlying JOIN, it still needs to; the view is a name, not a query optimizer.

3 · When "recomputed every time" is the wrong trade — materialized views

A view that scans and joins two large tables on every single read starts to cost real time once it's queried often. Postgres's second form trades the "always current" guarantee for speed by actually storing the result:

CREATE MATERIALIZED VIEW order_summaries AS
SELECT o.id AS order_id, COUNT(oi.id) AS item_count,
  SUM(oi.unit_price * oi.quantity) AS total_cents
FROM orders o JOIN order_items oi ON oi.order_id = o.id
GROUP BY o.id;

CREATE UNIQUE INDEX ON order_summaries (order_id);
REFRESH MATERIALIZED VIEW CONCURRENTLY order_summaries;

A materialized view is a plain view's opposite trade: the query runs once, its result is written to disk like a real table, and reads afterward are just table reads — no JOIN, no GROUP BY, every time. The cost moves from every read to whoever runs REFRESH, and the data between refreshes can be stale, the exact risk Lesson 9's caching lesson named for any cached value. CONCURRENTLY (a name Lesson 19 already used for index builds) lets reads keep hitting the old data while the refresh runs, instead of locking readers out — it requires the unique index shown above to work at all.

Plain VIEWMATERIALIZED VIEW
StorageNone — a saved query, re-run every timeActual rows on disk, written at refresh time
FreshnessAlways current, no staleness possibleStale until the next REFRESH runs
Read costFull underlying query, every single readA plain table read, no recomputation
Who pays the query costEvery caller, on every readWhoever triggers REFRESH, once per refresh

That freshness gap is why a refresh belongs in a background job (Lesson 10's shape) — a scheduled worker, or a job enqueued after the write that changed the underlying data — never inline inside the request that triggered the change, the same "don't make the client wait for work it didn't ask to wait for" reasoning Lesson 10 already established.

// Row/Querier mirror Lesson 42's minimal interface pair — the point here
// is the query shape, not the interface mechanism again.
type Row interface {
    Scan(dest ...any) error
}
type Querier interface {
    QueryRow(ctx context.Context, sql string, args ...any) Row
}

type OrderSummary struct {
    OrderID, ItemCount, TotalCents int64
}

// fetchOrderSummary queries the materialized view exactly like a table —
// one row in, one row out, no JOIN or GROUP BY in this function at all.
func fetchOrderSummary(ctx context.Context, q Querier, orderID int64) (OrderSummary, error) {
    row := q.QueryRow(ctx,
        `SELECT order_id, item_count, total_cents FROM order_summaries WHERE order_id = $1`,
        orderID)
    var s OrderSummary
    if err := row.Scan(&s.OrderID, &s.ItemCount, &s.TotalCents); err != nil {
        return OrderSummary{}, fmt.Errorf("fetch order summary %d: %w", orderID, err)
    }
    return s, nil
}

// refreshOrderSummaries runs in a background job (Lesson 10), never inline
// in a request — CONCURRENTLY needs the unique index created above. It
// reuses Querier's QueryRow only because REFRESH here returns no rows;
// a real handler would use pgx's Exec for a statement with no result set.
func refreshOrderSummaries(ctx context.Context, exec Querier) error {
    _ = exec.QueryRow(ctx, `REFRESH MATERIALIZED VIEW CONCURRENTLY order_summaries`)
    return nil
}

fetchOrderSummary has no idea whether order_summaries is a table, a view, or a materialized view — the query text and the Querier interface look identical either way. That's the actual point of naming the query at all: callers depend on a name and a row shape, not on how the data behind it is produced.

Q: "What's the difference between a view and a materialized view?" A strong answer, out loud: "A plain view is just a saved SELECT — it stores nothing, so every read re-runs the underlying query and always sees current data, but it's exactly as slow as that query. A materialized view actually writes the result to disk at creation or refresh time, so reads are cheap table reads afterward, but the data is only as fresh as the last REFRESH — someone has to run that, usually a background job, not inline in a request. I'd reach for a materialized view specifically when a query is read often, expensive to compute, and okay being slightly stale — not as a default replacement for a plain view or an index." The signal: naming the storage/freshness trade explicitly, not just "materialized views are the fast ones."
