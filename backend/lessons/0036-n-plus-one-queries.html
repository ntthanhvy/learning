The N+1 query problem

Lesson 5 named this in passing while answering a different question ("should I add an index?") — one paragraph, no code, no fix worked through. Today it gets the full treatment: the concrete shape in real Go+pgx code, why it's invisible in the diff, and both fix patterns worked all the way through.

1 · The shape: 1 query becomes 1 + N

A list endpoint needs each order's line items too. Written the way it reads naturally — fetch the orders, then loop and fetch each one's items — looks like this:

orders := SELECT id FROM orders WHERE user_id = $1        -- 1 query
for each order:
    SELECT * FROM order_items WHERE order_id = order.id   -- N more queries, one per order

One query fetches the list. Then the loop fires one more query per row. Ten orders means 11 round trips to Postgres instead of 1 or 2; a thousand orders means 1,001. That's the N+1 query problem: the total isn't proportional to how much data comes back, it's proportional to how many round trips it took to get it — and round trips are the expensive part, not the query itself.

2 · Why it's invisible in the diff

Nothing here is wrong Go. There's no error, no panic, no lint warning — a `for` loop calling store.GetItems(order.ID) is exactly what "fetch related data for each item" looks like in ordinary application code:

// naiveGetOrdersWithItems fetches N orders, then loops and issues one
// more query per order to fetch that order's line items: 1 + N round
// trips. Nothing here looks wrong — it reads like straightforward Go.
func naiveGetOrdersWithItems(ctx context.Context, db *pgxpool.Pool, userID int64) ([]Order, error) {
    rows, err := db.Query(ctx, `SELECT id FROM orders WHERE user_id = $1`, userID)
    if err != nil {
        return nil, err
    }
    defer rows.Close()

    var orders []Order
    for rows.Next() {
        var o Order
        if err := rows.Scan(&o.ID); err != nil {
            return nil, err
        }
        orders = append(orders, o)
    }

    for i := range orders {
        // one query per order — this is the +N
        itemRows, err := db.Query(ctx, `SELECT order_id, sku, qty FROM order_items WHERE order_id = $1`, orders[i].ID)
        if err != nil {
            return nil, err
        }
        for itemRows.Next() {
            var it Item
            if err := itemRows.Scan(&it.OrderID, &it.SKU, &it.Qty); err != nil {
                itemRows.Close()
                return nil, err
            }
            orders[i].Items = append(orders[i].Items, it)
        }
        itemRows.Close()
    }
    return orders, nil
}

It compiles, it passes every test written against a handful of fixture rows, and it returns the right data. The only thing wrong with it is a runtime property that doesn't show up until the list is long and the database is one network hop away instead of on localhost — exactly the class of bug Lesson 13's "it works on my machine" framing warned about for logs, now showing up for query count instead.

Ties to Lesson 18: N+1 doesn't just multiply round trips, it multiplies concurrently held pool connections under load. Each in-flight request running this handler holds a connection from Lesson 18's pgxpool for the entire 1 + N sequence, not just for one quick query — ten concurrent requests against a 1,000-row list each hold a connection through roughly 1,001 round trips apiece. That's exactly the pool-exhaustion shape Lesson 18 taught (Acquire without a fast Release starves everyone else), except here it's not a leaked Release() causing it — connections come back fine, they're just held far longer than the work actually requires.

3 · The misconception: an index doesn't fix this

Lesson 5 named this directly and it's worth repeating on its own, because it's a genuinely common reflex: seeing a slow list endpoint and reaching for an index on order_items.order_id. An index there is not wrong — each of the individual N queries does get faster, from a table scan down to an index lookup. But an index makes each of the N queries fast; it does nothing to reduce N. 1,001 fast round trips is still 1,001 round trips, still paying full network latency and connection-acquisition cost on every single one. The bug is the shape of the access pattern, not the speed of any one query in it — the fix has to change how many queries run, not how fast each one runs.

4 · Fix pattern one: a single JOIN

When the goal is one flat combined result, a JOIN collapses the whole thing into one query and one round trip:

SELECT o.id, i.sku, i.qty
FROM orders o
JOIN order_items i ON i.order_id = o.id
WHERE o.user_id = $1;

Postgres does the matching server-side; the client reads one result set with a row per (order, item) pair instead of orchestrating N separate connections. The trade-off: each order's own columns repeat once per item row, and reassembling "one order object with a slice of items" from that flat shape takes a little scan-and-group logic in the handler — a fine cost for a genuinely flat, single-purpose result.

5 · Fix pattern two: one batched query + in-memory grouping

When the parent/child shape should stay separate in the application — orders as one slice, each with its own Items field, same as the naive version's return type — the fix is a single batched query using WHERE id = ANY($1), covering every order's items in one round trip, then grouping the results back onto their parent in Go:

// batchedGetOrdersWithItems fetches the same orders, then fetches every
// order's line items in ONE additional query using ANY($1), and assembles
// the parent/child shape back together in application code: 2 round trips
// total, no matter how many orders there are.
func batchedGetOrdersWithItems(ctx context.Context, db *pgxpool.Pool, userID int64) ([]Order, error) {
    rows, err := db.Query(ctx, `SELECT id FROM orders WHERE user_id = $1`, userID)
    if err != nil {
        return nil, err
    }
    defer rows.Close()

    var orders []Order
    ids := make([]int64, 0)
    byID := make(map[int64]*Order)
    for rows.Next() {
        var o Order
        if err := rows.Scan(&o.ID); err != nil {
            return nil, err
        }
        orders = append(orders, o)
        ids = append(ids, o.ID)
    }
    for i := range orders {
        byID[orders[i].ID] = &orders[i]
    }
    if len(ids) == 0 {
        return orders, nil // nothing to batch-fetch
    }

    // one query for every order's items, not one query per order
    itemRows, err := db.Query(ctx, `SELECT order_id, sku, qty FROM order_items WHERE order_id = ANY($1)`, ids)
    if err != nil {
        return nil, err
    }
    defer itemRows.Close()

    for itemRows.Next() {
        var it Item
        if err := itemRows.Scan(&it.OrderID, &it.SKU, &it.Qty); err != nil {
            return nil, err
        }
        if o, ok := byID[it.OrderID]; ok {
            o.Items = append(o.Items, it)
        }
    }
    return orders, nil
}

This is the same batched query Lesson 5 called "a batched WHERE id IN (...)" in passing — ANY($1) is pgx's idiomatic form, passing a Go slice as one parameter instead of building an IN (...) list by hand. Two round trips total: one for the orders, one for every order's items together, regardless of whether the list has 10 rows or 10,000.

Q: "You added an index on order_items.order_id but the list endpoint is still slow. What would you check?" A strong answer, out loud: "I'd suspect the index didn't fix the actual problem — an index makes each individual query faster, but if the code is running one query per row in a loop, the count of round trips is still N, index or not. I'd check the handler for a loop that calls the store once per item instead of once total. The fix isn't a better index, it's collapsing the loop into one query — a JOIN if I want one flat result, or a single WHERE id = ANY($1) batched query plus in-memory grouping if I want to keep the parent/child shape the handler already returns." The signal: naming that an index doesn't reduce query count, and naming both fix patterns, not just "add caching" or "add an index" as a reflex.

6 · Where it sneaks in silently: ORMs and query builders

This course doesn't teach any specific ORM — the Go/pgx examples above are hand-written SQL on purpose. But it's worth knowing the vocabulary for where N+1 is the single most common bug ORMs and query builders introduce: lazy-loading an association. order.Items reading like a plain field access, but secretly firing a fresh query the first time it's touched, is exactly this bug wearing a disguise — the loop in section 2 is still there, it's just hidden behind property syntax instead of an explicit method call. The fix vocabulary carries over unchanged: ORMs generally expose an "eager load" or "prefetch related rows" option that turns the hidden per-row query into one of the two patterns above, JOIN or batched fetch, run up front instead of lazily inside the loop.
