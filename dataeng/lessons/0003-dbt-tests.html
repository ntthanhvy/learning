dbt: tests catch bad data

1 · Two bad rows, still sitting in the warehouse

Day 1's seed script planted two bad rows in raw.orders on purpose, and Day 2 confirmed they pass straight through stg_orders unchanged, because staging only reshapes columns:

OrderWhat's wrong
order_id = 13restaurant_id = 9999 — no restaurant with that id exists in raw.restaurants
order_id = 27subtotal is negative — a subtotal can never be less than zero

Nothing has caught either one yet. In ELT that's expected — the raw layer takes data exactly as it arrived, mess included. Today's job is to give dbt a way to notice the mess: a data test is a query that should return zero rows; if it returns any, the test fails. That's the entire mechanism — no new query language, same as Day 2's "a dbt model is just a SELECT."

2 · Generic tests: not_null, unique, relationships

A generic test is written once and reused across columns by declaring it in YAML — you never write the underlying SQL yourself. dbt ships four built in; the one that catches order 13's orphan restaurant_id is relationships, dbt's foreign-key check: every value in the child column must exist in the parent column, or the test fails and names the orphan.

Create models/staging/stg_orders.yml (a schema file — declares tests and docs for an existing model, doesn't change the model's SQL):

-- models/staging/stg_orders.yml
version: 2

models:
  - name: stg_orders
    columns:
      - name: order_id
        tests:
          - unique
          - not_null
      - name: restaurant_id
        tests:
          - not_null
          - relationships:
              arguments:
                to: ref('stg_restaurants')
                field: restaurant_id
      - name: courier_id
        tests:
          - not_null
          - relationships:
              arguments:
                to: ref('stg_couriers')
                field: courier_id

not_null and unique are the other two in play here: order_id should be both, since it's the grain of the model. Note two things about relationships: its options nest under arguments: (current dbt syntax — older tutorials show to:/field: unnested, which now prints a deprecation warning), and to: takes a ref(), not a hardcoded table name — same reasoning as Day 2's ref() vs. hand-written names, so dbt can order tests after the models they depend on.

3 · Singular tests: one SQL file, one specific rule

Not every rule fits the four generic shapes. Order 27's negative subtotal needs a rule specific to this business: subtotal can never be less than zero. That's a singular test: a plain .sql file in the tests/ directory, containing a SELECT that should return nothing. No YAML wiring needed — dbt discovers any .sql file under tests/ automatically and treats it as a test.

Create tests/assert_positive_subtotal.sql yourself. Requirements:

  • select from {{ ref('stg_orders') }} — never query raw.orders directly in a test, same ref()-over-hardcoded-name reasoning as everywhere else in the project;
  • return the rows that are wrong, not a count — a test fails when its query returns any row, and returning the actual offending rows makes a failure's output tell you exactly which order broke it;
  • the rule: subtotal must not be less than zero.
-- tests/assert_positive_subtotal.sql -- fill in the WHERE
select
    order_id,
    subtotal
from {{ ref('stg_orders') }}
-- TODO: filter down to rows where subtotal is negative

4 · dbt build vs dbt run

Day 2 only ever ran dbt run, which builds models and nothing else — tests don't run, so a test failure would never have shown up even if one existed. dbt build runs models and tests and snapshots and seeds, in dependency order, and — critically — if a test on a model fails, dbt still finishes building everything that doesn't depend on the bad result, then reports the failure clearly at the end. From today on, use dbt build, not dbt run: a green dbt run only proves the SQL compiled, not that the data is trustworthy.

uv run --project ../dbt_env dbt build

5 · Source freshness: is the raw data even current?

Tests catch bad values. source freshness catches a different failure mode entirely: the loader silently stopped running, and nobody noticed because the row counts still look plausible. Freshness compares a source's most-recent timestamp to now and warns or errors if it's stale. Add a freshness: block plus loaded_at_field to Day 2's models/staging/sources.yml:

-- models/staging/sources.yml
version: 2

sources:
  - name: raw
    schema: raw
    tables:
      - name: restaurants
        loaded_at_field: updated_at
        freshness:
          warn_after: {count: 24, period: hour}
          error_after: {count: 48, period: hour}
      - name: couriers
      - name: orders
        loaded_at_field: placed_at
        freshness:
          warn_after: {count: 24, period: hour}
          error_after: {count: 48, period: hour}

loaded_at_field names which column holds "when did this row show up" — updated_at for restaurants, placed_at for orders. couriers has no freshness block: not every source needs one, and a batch dimension that barely changes isn't worth alerting on yet. Check it separately from dbt build:

uv run --project ../dbt_env dbt source freshness

Expected, since Day 1's seed data is recent: both configured sources report PASS. If you don't touch the warehouse for a couple of days, re-running this will start reporting WARN on orders — that's the mechanism doing its job, not a bug.

docker compose exec -T postgres psql -U fdp -d fdp -c \

   UPDATE raw.orders SET subtotal = 9.32 WHERE order_id = 27;"

Editing raw data by hand won't happen again after today: this is a one-time fix to prove the tests work end to end. From Day 5 onward, bad rows get caught by the Kafka consumer's own checks before landing, and dbt's tests stay as the last line of defense, not the first — the same "defense in depth" idea, applied at each stage a row passes through.

Q: "How would you catch bad data in a dbt project?" A strong answer, out loud: "Two kinds of test. Generic tests — not_null, unique, relationships, accepted_values — are declared in YAML against a column and cover the common shapes, especially referential integrity between models. Singular tests are a one-off SQL file for a business rule specific to this data, like a subtotal that can never go negative — the query returns the offending rows, and any row returned is a failure. Run both together with dbt build, not dbt run, since run only builds models and never executes a single test. On top of that, source freshness checks whether the raw data is even current, which catches a stalled loader that tests on the data itself can't — the rows that did land might all be perfectly valid, and freshness is the only thing that notices new ones stopped arriving." The signal: naming both test kinds without being asked, plus knowing freshness solves a different problem than a data test.
