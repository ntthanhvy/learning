pd.testing.assert_frame_equal(): comparing tables for a real test, not a printout

Lesson 54 taught .equals() (one True/False) and .compare() (which cells differ) for checking whether two DataFrames match. A fresh curriculum/glossary scan today confirmed neither lesson, nor any other, ever mentions pandas.testing itself — the module built specifically for writing an automated test that a transform's output is correct, the exact skill a take-home "clean this dataset" interview exercise is graded on. The gap it closes: .equals() is all-or-nothing strict (a float32 vs float64 column fails even when every value matches), which makes it a poor fit for testing numeric pipelines where small floating-point rounding is expected and fine.

1 · assert_frame_equal(): pass silently, fail with a readable diff

SQL has no built-in "assert these two result sets match" statement — that check normally lives in whatever test framework wraps the query. pandas ships its own equivalent for DataFrames: assert_frame_equal() from pandas.testing. Confirmed directly (pandas 3.0.6): on a genuine copy, it returns None and prints nothing — the same "silent on success" convention as Python's own assert keyword:

import pandas as pd
import pandas.testing as pdt

clean = pd.DataFrame({
    "customer": ["An", "Binh"],
    "amount":   [120.0, 35.5],
})

pdt.assert_frame_equal(clean, clean.copy())
# (nothing printed -- the check passed)

Change one value and the failure is loud, specific, and tells you exactly where to look — this is the real reason to reach for it over .equals() inside a test: .equals() only ever tells you whether two frames match; assert_frame_equal() tells you why they don't, in the same call:

changed = clean.copy()
changed.loc[1, "amount"] = 999.0
pdt.assert_frame_equal(clean, changed)
# AssertionError: DataFrame.iloc[:, 1] (column name="amount") are different
#
# DataFrame.iloc[:, 1] (column name="amount") values are different (50.0 %)
# [index]: [0, 1]
# [left]:  [120.0, 35.5]
# [right]: [120.0, 999.0]
# At positional index 1, first diff: 35.5 != 999.0

2 · Floats are compared with tolerance by default — unlike .equals()

This is the behavior that actually earns assert_frame_equal() its own lesson rather than being a footnote on Lesson 54. Confirmed directly: a difference of 1e-9 in a float column passes with no error at all — floats are compared with a small default relative/absolute tolerance (the same idea as NumPy's allclose), not bit-for-bit:

drifted = clean.copy()
drifted["amount"] = drifted["amount"] + 1e-9
pdt.assert_frame_equal(clean, drifted)
# (nothing printed -- passes; 1e-9 is well inside the default tolerance)

clean.equals(drifted)
# False  -- .equals() has no tolerance concept at all, any difference fails

A real-world difference — say 0.01 off, the kind a rounding or re-aggregation bug actually produces — is big enough to fail even with the default tolerance, exactly as it should. For a case that genuinely needs a looser tolerance (comparing results from two different floating-point code paths that are expected to round slightly differently), rtol=/atol= widen it explicitly, or check_exact=True tightens it to bit-for-bit — the opposite knob, useful once a pipeline is expected to produce byte-identical output and any drift at all is itself a bug worth catching.

3 · check_dtype and check_like: two more strictness knobs

Two keywords make assert_frame_equal() flexible about exactly what "matching" means, each confirmed directly against the real behavior rather than assumed:

KeywordDefaultWhat it relaxes
check_dtype=TrueSet False to let a float32 column match an equal-valued float64 column — the exact case Lesson 54's .equals() could never do.
check_like=FalseSet True to sort both frames by their index and column labels before comparing, so row/column order stops mattering — the labels still have to match, just not their on-disk order.

Confirmed directly: with check_dtype=False, the float32-vs-float64 comparison from Lesson 54 that made .equals() return False now passes cleanly through assert_frame_equal(). And confirmed: a DataFrame whose rows were shuffled but still carry the same index labels ([0, 1, 2, 3] rearranged, not reset to a fresh default range) fails under the default row-order-sensitive comparison, but passes with check_like=True once both sides are label-sorted first.

Q: "How would you write an automated test confirming your cleaning function's output is correct?" A strong answer, out loud: "I'd build the expected DataFrame by hand for a small known input, run the real function, and call pandas.testing.assert_frame_equal(expected, actual) — it raises AssertionError with a readable cell-level diff on any mismatch, and returns None silently when it passes, same convention as a plain assert. The one thing I'd decide deliberately is check_dtype and check_exact: floats get a small default tolerance, which is usually right for a numeric pipeline, but I'd set check_exact=True if even tiny drift should count as a bug, or check_dtype=False if I only care about the values matching, not the exact bit-width." The signal: naming the default float tolerance unprompted, and knowing it's the reason to prefer this over .equals() inside an actual test.

4 · Where this fits

Lesson 54's .equals()/.compare() are for interactive checking — "did this change, and where?" — read at a REPL or notebook cell. assert_frame_equal() is the same idea aimed at an automated test: it raises instead of returning a value, which is exactly what a test runner (or a plain assert-driven script, like this course's own practice files) needs to fail loudly. assert_series_equal() is the identical tool one level down, for comparing two Series directly rather than whole DataFrames.
