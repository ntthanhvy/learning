Graceful shutdown, now in C# too

Lesson 27 covered graceful shutdown in Go: catch SIGTERM, flip readiness to unhealthy first, then let http.Server.Shutdown drain in-flight requests up to a deadline. That lesson never got a C# mirror, even though every other Go-only mechanism from the same stretch of the course — retry, circuit breaker, bulkhead, worker pool — has been ported since Lesson 112. Today closes that gap: the same two-step shutdown sequence, as ASP.NET Core's own generic host actually implements it.

1 · The same two steps, a different owner

Lesson 27's rule still holds exactly: stop accepting new work, then let work already in flight finish up to a deadline, in that order. What changes in ASP.NET Core is who performs each step. In Go, the two lines of signal-catching code in Lesson 27's snippet are the whole mechanism — nothing else is watching for SIGTERM unless that code is written. In ASP.NET Core, a built-in component called ConsoleLifetime already does the signal-catching for you — the wiring Lesson 27 had to hand-write in Go is on by default the moment a host is built.

Per Microsoft's own docs, before .NET 6 there was no clean way to intercept SIGTERM at all — ConsoleLifetime worked around it by subscribing to AppDomain.ProcessExit, which also fires when code calls Environment.Exit, causing real deadlocks the docs describe outright. Since .NET 6, POSIX signals are handled directly, and ConsoleLifetime "handles SIGTERM gracefully" without that workaround. The practical rule the docs state plainly: call IHostApplicationLifetime.StopApplication() to shut down on purpose, never Environment.Exit — the latter skips the graceful path entirely.

2 · IHostApplicationLifetime: the events Lesson 27's single ctx.Done() fans out into

Go's snippet blocked on one channel, ctx.Done(), and ran the whole shutdown sequence linearly after it. ASP.NET Core instead exposes IHostApplicationLifetime, injectable into any class, with ApplicationStopping as the direct equivalent of Lesson 27's ctx.Done() firing — the moment to start step 1, stop accepting new work:

public class DrainOnShutdown {
    public DrainOnShutdown(IHostApplicationLifetime lifetime, HealthState health) {
        lifetime.ApplicationStopping.Register(() => {
            health.MarkUnready();                       // step 1: readiness flips first
            Console.WriteLine("shutdown signal received, draining in-flight requests");
        });
        lifetime.ApplicationStopped.Register(() =>
            Console.WriteLine("shutdown complete"));
    }
}

ApplicationStopping fires when ConsoleLifetime catches SIGTERM/SIGINT/SIGQUIT — no hand-written signal handler required, unlike Go's signal.NotifyContext line. ApplicationStopped fires once every hosted service's StopAsync has returned, the direct equivalent of Go's "shutdown complete" log line after srv.Shutdown returns.

3 · Who does step 2's actual draining — Kestrel, not your code

In Go, step 2 is one explicit call: srv.Shutdown(shutdownCtx), written by hand with its own timeout. In ASP.NET Core, the generic host calls this for you: once ApplicationStopping fires, the host calls the web server's own StopAsync "with a shutdown timeout that you can configure (default 30s)." Per Microsoft's own docs, Kestrel then "close[s] their port bindings and stop[s] accepting new connections," and tells already-open connections to stop processing new requests — for HTTP/2, by sending a GOAWAY frame; for HTTP/1.1, by simply ending the connection's request loop once the current request finishes. Configuring the timeout is one line, the C# equivalent of Go's context.WithTimeout(..., 10*time.Second):

builder.Host.ConfigureHostOptions(opts =>
    opts.ShutdownTimeout = TimeSpan.FromSeconds(10));   // same knob as Go's shutdownCtx deadline

If every active request finishes first, the host returns early, same as Go's srv.Shutdown returning before its deadline. If the timeout expires first, the docs are explicit about the cost: "pending connections and requests are aborted forcefully, which can cause errors in the logs and to the clients" — the same trade-off Lesson 27 named for a Go handler still running when shutdownCtx expires.

Readiness-first still isn't automatic: Lesson 27's ordering bug — the load balancer still routing new traffic in because nothing told it the instance is leaving — is just as possible in ASP.NET Core. ConsoleLifetime catching the signal and Kestrel draining connections says nothing about a separate /health/ready endpoint a load balancer polls. The docs' own load-balancer checklist spells out the same order Lesson 27 taught: bring up the new instance, stop sending traffic to the old one, then signal it to shut down. Wiring ApplicationStopping to flip readiness unhealthy (as the snippet in section 2 does) is still something you write — the framework automates the signal-catching and the connection-draining, not the readiness flip itself.

Scope line

This lesson covers ASP.NET Core's graceful-shutdown sequence — ConsoleLifetime's signal handling, IHostApplicationLifetime's three events plus StopApplication(), Kestrel's connection-draining under HostOptions.ShutdownTimeout — as the C# mirror of Lesson 27's Go sequence. It does not cover Kestrel's HTTP/1.1 vs HTTP/2 vs HTTP/3 draining differences beyond the one `GOAWAY` fact already stated; IIS's distinct 503-based shutdown behavior, mentioned once in the source but not a concept this course tracks; or IHostedLifecycleService's extra Starting/Started/Stopping/Stopped hooks around IHostedService itself, already flagged as out of scope by Lesson 105. It does not cover Go's select-statement arbitration rules — still deferred, not attempted this round; see this round's NOTES.md entry for why.
