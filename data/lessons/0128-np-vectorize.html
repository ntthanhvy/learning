np.vectorize(): a name that promises vectorization and does not deliver it

Lesson 127 closed its own fresh scan with np.abs(), np.sqrt(), and np.floor()/np.ceil() as other open elementwise-ufunc candidates, none pre-committed. This round's own fresh scan re-checked those plus np.vectorize() — flagged untaught across at least five prior scan rounds (back through Lessons 93-126's history) but always passed over for a sharper same-round pick. It wins today: it directly continues Lesson 12's own "apply() is a Python loop under the hood" warning, and its name is the trap — it sounds like the vectorized escape hatch from that warning, but it is not one.

1 · It matches apply() exactly — including the part that is not actually vectorized

Lesson 12 taught that DataFrame.apply(fn, axis=1) is "pandas' escape hatch back to per-row Python" — still a loop underneath, just spelled as a method call. np.vectorize(fn) looks, from its name alone, like the fix for exactly that problem. Confirmed directly against the official NumPy docs' own wording, it is the opposite: "The function is provided primarily for convenience, not for performance. The implementation is essentially a for loop."

import numpy as np
import pandas as pd
import timeit

def classify(x):
    if x > 100: return "high"
    elif x > 50: return "mid"
    else: return "low"

vec_classify = np.vectorize(classify)
big = np.random.randint(0, 200, size=200_000)
big_series = pd.Series(big)

# Confirmed directly, timed on this machine (200k rows, 3 runs each):
timeit.timeit(lambda: [classify(x) for x in big], number=3)   # ~0.077s -- plain list comprehension
timeit.timeit(lambda: vec_classify(big), number=3)             # ~0.117s -- np.vectorize() -- SLOWER
timeit.timeit(lambda: big_series.apply(classify), number=3)   # ~0.058s -- Series.apply()

Confirmed directly: on this machine, np.vectorize() was the slowest of the three — even slower than the plain Python list comprehension it dresses up, because it pays extra bookkeeping overhead (broadcasting setup, one calibration call to detect the output dtype) on top of the same per-element Python calls. The name is the whole trap: it is a convenience wrapper for broadcasting a scalar function over array shapes, not a performance tool — never reach for it believing it will out-run a real vectorized column expression or even beat a bare loop.

2 · What it is actually for: broadcasting a scalar function, not speed

The genuine use case: a function written for two plain scalars, made to accept arrays of different shapes and broadcast between them the way a real ufunc (np.add, Lesson 127's np.sign()) already does natively.

def addxy(x, y):
    return x + y

v = np.vectorize(addxy)
v(np.array([[1], [2], [3]]), np.array([10, 20, 30]))
# array([[11, 21, 31],
#        [12, 22, 32],
#        [13, 23, 33]])  -- (3,1) and (3,) broadcast together, confirmed directly

Confirmed directly: called on a pandas Series, it returns a bare ndarray, not a Series — the opposite of Lesson 127's np.sign(), which keeps the Series and its Index intact. Confirmed directly from the official docs' own wording, the otypes= parameter fixes the output dtype explicitly; left unset, "the data type of the output... is determined by calling the function with the first element of the input," one extra calibration call confirmed directly to happen before the real pass starts. The excluded= parameter marks an argument (by position or keyword name) to pass through unmodified rather than broadcasting it — useful for a constant option flag the scalar function takes alongside its array inputs.

3 · The cache= trap: it is not memoization

Confirmed directly, and confirmed matching the official docs' own wording: cache=True sounds like it memoizes repeated input values, but the docs say precisely: "if neither otypes nor signature are provided, and cache is True, then cache the number of outputs" — it only skips the one extra dtype-calibration call, nothing about the values themselves.
calls = []
def counting(x):
    calls.append(x)
    return x * 2

v = np.vectorize(counting, cache=True)
v(np.array([5, 5, 5, 7]))
print(calls)
# [5, 5, 5, 7]  -- all four values called, including the three repeats of 5 -- NOT memoized

Confirmed directly: with cache=False (the default), the exact same input produces five calls, not four — one throwaway calibration call on the first element plus all four real calls. cache=True saves exactly that one extra call; repeated values such as the three 5s are still recomputed every time either way. Confirmed directly, errors inside the wrapped function propagate normally, with no silent NaN substitution the way some ufuncs behave on bad input — dividing by a zero inside the wrapped function raises a plain ZeroDivisionError, exactly as calling the scalar function directly would.
