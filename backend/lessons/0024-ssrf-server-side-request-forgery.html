SSRF: when your server is the attacker's proxy

Every security lesson so far (Lessons 12, 17, 22, 23) has been about a request arriving at your server. This one flips the direction: a feature that makes your server send a request out, to a URL a client got to influence. That single design shape is its own OWASP Top 10 risk, never covered here yet.

1 · The feature that quietly opens a hole

Plenty of ordinary features need the server to fetch a URL on the caller's behalf: a webhook target, an "import from URL" button, a link-preview thumbnail, an avatar pulled from a profile link. The natural implementation just fetches whatever URL the client sent:

func fetchAvatarVulnerable(w http.ResponseWriter, r *http.Request) {
    imageURL := r.URL.Query().Get("url")
    resp, err := http.Get(imageURL) // fetches whatever the client asked for
    if err != nil {
        http.Error(w, "fetch failed", http.StatusBadGateway)
        return
    }
    defer resp.Body.Close()
    io.Copy(w, resp.Body)
}

This works perfectly for its intended use — a client passes a public image URL, the server fetches it, everyone's happy. The bug is what else it accepts. Nothing here checks where the URL points, only that it's a URL.

2 · The attack: your server as a proxy into your own network

This is SSRF: instead of a normal image URL, the attacker sends a URL pointing at somewhere the public internet can't normally reach, but the server can:

GET /fetch-avatar?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/
GET /fetch-avatar?url=http://localhost:6379/
GET /fetch-avatar?url=http://10.0.4.12:5432/

Three real targets, three real outcomes: 169.254.169.254 is the cloud metadata endpoint (AWS/GCP/Azure all use it) — reachable only from inside the instance, and it can hand back live cloud credentials. localhost:6379 is a Redis instance that was never exposed publicly because "only the server talks to it." 10.0.4.12:5432 is a Postgres instance sitting on a private subnet, unreachable from outside — except the app server sits inside that same network and has a route to it. None of these addresses were ever meant to be public. The attacker never touches them directly; they get your server to touch them, and the response gets copied straight back into the HTTP response the attacker receives. The server's network position — and often its credentials — become the attacker's.

Why this isn't just "another IDOR": Lesson 12's IDOR is about a request that arrives and reads the wrong row. SSRF is about a request your own server sends, to a destination it never meant to reach — the trust boundary being crossed is the network perimeter around internal services, not a database row's ownership.

3 · Why "just block private IP ranges from the URL string" isn't enough

The obvious first fix is to reject any URL whose hostname parses to a private-looking address before fetching it. That's necessary, but checking the URL string alone misses the actual attack surface: a hostname is resolved by DNS, and DNS is attacker-controlled the moment the attacker controls the domain. http://evil-but-looks-fine.example.com/ can have a DNS record pointing straight at 169.254.169.254 — the string in the URL never mentions a private IP at all, so a check that only inspects the URL text passes it through. Worse, an attacker with a slightly more patient setup can even make the DNS answer differ between the moment it's checked and the moment it's actually connected to (a DNS rebinding attack) — checking the URL, or even resolving it once ahead of time, and then fetching separately leaves that gap open.

The fix has to sit at the actual network connection, not the URL string: resolve the hostname, inspect the IP that connection is about to use, and refuse to dial it if it's private/loopback/link-local — every single time a connection is made, not once earlier in the request.

4 · The fix: validate the connection, not the string

In Go, http.Client takes a custom Transport, and the transport's DialContext is the one place that sees the literal IP a connection is about to use — the right place to enforce this:

func safeDialContext(ctx context.Context, network, addr string) (net.Conn, error) {
    host, port, err := net.SplitHostPort(addr)
    if err != nil {
        return nil, err
    }
    ips, err := net.DefaultResolver.LookupIP(ctx, "ip", host)
    if err != nil {
        return nil, err
    }
    for _, ip := range ips {
        if ip.IsPrivate() || ip.IsLoopback() || ip.IsLinkLocalUnicast() {
            return nil, errBlockedHost // refuse to dial it, no exceptions
        }
    }
    dialer := net.Dialer{Timeout: 5 * time.Second}
    return dialer.DialContext(ctx, network, net.JoinHostPort(ips[0].String(), port))
}

var safeClient = &http.Client{
    Timeout:   5 * time.Second,
    Transport: &http.Transport{DialContext: safeDialContext},
}

Because DialContext runs at the moment of the actual TCP connection — after DNS resolution, right before the socket opens — this closes both problems at once: a hostname that resolves to a private IP is caught regardless of what the URL string looked like, and there's no earlier "check now, connect later" gap for DNS rebinding to slip through, because the check and the connection are the same step. safeClient.Get(url) replaces the bare http.Get(url) from section 1, and every outbound fetch in the feature now goes through it.

Q: "A code review shows a handler doing http.Get(userSuppliedURL) for a webhook feature. What do you flag?" A strong answer, out loud: "That's SSRF — the server will fetch whatever URL the request contains, including internal addresses like the cloud metadata endpoint or an internal Postgres instance that were never meant to be reachable from outside. I'd flag it as blocking, not a nit. The fix isn't a regex check on the URL string, since DNS can point an innocent-looking hostname at a private IP — it needs to validate the actual IP at connection time, in the HTTP client's dial step, so a hostname that resolves to a private or loopback address gets refused right when the connection is made, not earlier when it's easier to spoof." The signal: naming that the check has to happen at dial time against the resolved IP, not as a one-time string check on the URL.
