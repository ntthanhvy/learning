Idempotency keys, now in C# too

Lesson 26 built a hand-rolled Go middleware that checks an Idempotency-Key header before the real handler runs, and replays a stored response on a retry instead of running the handler twice. That lesson never got a C# mirror, unlike most of the Lesson 11-50 resilience set. Two first-party ASP.NET Core building blocks turn out to cover the exact same shape: an IEndpointFilter to intercept the call before the handler, and IDistributedCache as the key-to-response store.

1 · Same idea, two framework pieces instead of one hand-written map

Lesson 26's rule still holds exactly: the first request with a given key runs the real handler and remembers exactly what it returned; every later request with that same key gets the remembered response played back, and the handler never runs a second time. The Go version built both halves by hand — a mutex-guarded map, and a wrapper function around http.HandlerFunc. ASP.NET Core already ships a named piece for each half:

public class IdempotencyFilter : IEndpointFilter
{
    private readonly IDistributedCache _cache;
    public IdempotencyFilter(IDistributedCache cache) => _cache = cache;

    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext ctx, EndpointFilterDelegate next)
    {
        var key = ctx.HttpContext.Request.Headers["Idempotency-Key"].ToString();
        if (string.IsNullOrEmpty(key))
            return Results.Problem("Idempotency-Key header required", statusCode: 400);

        var stored = await _cache.GetStringAsync(key);
        if (stored != null)
            return Results.Content(stored, "application/json"); // replay -- next() never runs

        var result = await next(ctx); // first time: run the real handler
        var body = JsonSerializer.Serialize(result);
        await _cache.SetStringAsync(key, body,
            new DistributedCacheEntryOptions { AbsoluteExpirationRelativeToNow = TimeSpan.FromHours(24) });
        return result;
    }
}

app.MapPost("/orders", CreateOrderAsync).AddEndpointFilter<IdempotencyFilter>();

The handler, CreateOrderAsync, never learns about retries — exactly like Lesson 26's wrapped Go handler. A production version keys the cache entry per client, same as the Go version's scoping rule in section 5, and swaps the simplified Results.Content replay above for storing and replaying the real status code and headers too; elided here for space, same as Lesson 26's own elided recordingWriter.

2 · The building blocks: a short-circuiting filter, and a cache that isn't just in-process

The first piece is an IEndpointFilter. Its shape is exactly what Lesson 26's hand-written withIdempotency wrapper did in Go: run code before the handler, and decide whether next (the handler) gets called at all. Returning early from InvokeAsync without awaiting next(ctx) is the C# version of the Go middleware's early return after w.Write(rec.body) — both skip the handler entirely on a replay.

The second piece is IDistributedCache. Lesson 26's own in-memory map[string]idempotencyRecord only works correctly on a single instance — exactly the "stateless server" problem Lesson 8 raised, since two instances behind a load balancer would each have their own map, and a retry landing on the other instance wouldn't find the first instance's stored response at all. IDistributedCache names that gap directly: it's an interface over a cache store shared across every instance (Redis in production, SQL Server, or an in-memory stand-in for local dev only), so the replay check works no matter which instance answers the retry.

The one new rule it brings: IDistributedCache stores byte[] (or, via GetStringAsync/SetStringAsync, UTF-8 strings) — not arbitrary objects — so a stored response has to be serialized going in and deserialized coming out, same as any cache value that crosses a process boundary. DistributedCacheEntryOptions.AbsoluteExpirationRelativeToNow is the C# way to say what Lesson 26's own "expire after 24 hours, matching Stripe" rule said in Go: an entry that outlives its usefulness should age out on its own, not accumulate forever.

3 · What doesn't change crossing languages

Every correctness rule Lesson 26 named still applies untouched: the key must be generated once by the client per logical action, not per HTTP attempt; it must be scoped per client, never shared globally; a retried body that doesn't match the first one is a client bug worth flagging rather than silently replaying old data over new; and replaying the exact stored response — not re-running any part of the handler's logic — is still what avoids a second real side effect (a second charge, a second email) on a retry. None of that is Go-specific or C#-specific; IEndpointFilter and IDistributedCache are just the two named framework pieces that carry it out in ASP.NET Core instead of a hand-rolled map and wrapper function.

Scope line

This lesson covers IEndpointFilter as the C# mechanism for intercepting a request before the handler runs, and IDistributedCache as the shared key-to-response store, for Lesson 26's idempotency-key pattern. It does not cover endpoint filter factories, controller-action filter registration, or the full set of IDistributedCache backing-store implementations (Redis setup, SQL Server cache tables) in any depth — only the two methods and the one options type this pattern needs. Lesson 26's own scoping, same-body, and expiry rules are not re-taught, only carried over unchanged.
