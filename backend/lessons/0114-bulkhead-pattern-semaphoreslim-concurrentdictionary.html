The bulkhead pattern, now in C# too

Lesson 50 taught the bulkhead pattern — giving each dependency its own fixed slice of a shared resource — in Go only. Lesson 109 already named the C# building block this needs, in passing: "the same semaphore pattern is in fact how a bulkhead's per-dependency slice is often implemented underneath." Today builds that underneath, for real, and hits one concurrency trap on the way that Go's version never has to think about.

1 · Same wall, same reason — Lesson 50 already covers why

Nothing about why a bulkhead exists changes between languages. Lesson 50 covers the full reasoning: one shared pool means one slow dependency can hold every slot in it, starving requests that never even called that dependency — the same cross-dependency starvation, just wearing a different ecosystem's connection type. The fix is still the same: stop sharing the resource, and give each dependency its own fixed-size partition that the others can never borrow from, even while it sits idle. None of that is re-derived here; today is about what the partition itself is made of in C#, and the one new trap that shows up assembling it.

2 · Go's map of pools becomes a ConcurrentDictionary of semaphores

Lesson 50's Go Bulkhead struct was a map[string]*Pool — one small custom pool per dependency name, built once up front in NewBulkhead and never touched again. C# has a ready-made width-limiter already introduced in Lesson 109: SemaphoreSlim. The dictionary holding one per dependency name needs to be safe for concurrent reads and writes too, so it's a ConcurrentDictionary, not a plain Dictionary. So a C# bulkhead is a ConcurrentDictionary from dependency name to its own SemaphoreSlim, and each call acquires a slot from the one matching its dependency before doing any work:

class Bulkhead
{
    private readonly ConcurrentDictionary<string, SemaphoreSlim> partitions = new();

    public void Configure(string dependency, int limit) =>
        partitions[dependency] = new SemaphoreSlim(initialCount: limit, maxCount: limit);

    public async Task<T> CallAsync<T>(string dependency, Func<Task<T>> operation)
    {
        if (!partitions.TryGetValue(dependency, out var gate))
            throw new InvalidOperationException($"no bulkhead partition configured for '{dependency}'");

        await gate.WaitAsync();  // this dependency's own slice only -- others untouched
        try { return await operation(); }
        finally { gate.Release(); }
    }
}

Set up once at startup — Configure("inventory", 8), Configure("shipping", 4), Configure("reports", 2) — exactly like Lesson 50's NewBulkhead(map[string]int{...}). A reporting call that finds its 2-slot semaphore already at zero suspends on WaitAsync() until a slot frees, with no visibility into whether inventory's or shipping's semaphores have room — because it can't touch them.

3 · The trap: building partitions lazily races, if you're not careful

Lesson 50's Go map was built once, entirely, before any call could reach it — so there was nothing to race. A C# bulkhead that instead creates each dependency's SemaphoreSlim lazily, on first use, reaches for the obvious-looking one-liner:

var gate = partitions.GetOrAdd(dependency, _ => new SemaphoreSlim(limit, limit));

This looks safe — ConcurrentDictionary is, per Microsoft's own docs, "a thread-safe collection of key/value pairs that can be accessed by multiple threads concurrently." But the same docs carry a sharper remark specifically about GetOrAdd and AddOrUpdate: their value-factory delegates "are called outside the locks to avoid the problems that can arise from executing unknown code under a lock. Therefore, the code executed by these delegates is not subject to the atomicity of the operation." In plain terms: if two calls for the same brand-new dependency name race in at the same instant, new SemaphoreSlim(...) can run twice — the dictionary itself stays correct and keeps only one winning entry, but the losing SemaphoreSlim was still fully constructed and then silently discarded, un-disposed.

Why this one's forgivable, but worth knowing: a throwaway SemaphoreSlim holds no unmanaged handle unless its wait handle was ever requested, so the leak here is small — but the same GetOrAdd gotcha is far sharper for a value factory with real side effects (opening a connection, starting a background task), where "ran more than once, most results discarded" is a genuine bug, not just acceptable waste. The fix, when it matters: build every partition up front during Configure, the way Lesson 50's Go code always did, so CallAsync only ever reads an already-built dictionary and GetOrAdd's race never gets a chance to fire.

4 · What doesn't change: the partition is still a hard wall

Lesson 50's trade-off carries over untouched: a dependency's semaphore sitting at full count while another dependency's semaphore is stuck at zero is correct, not wasteful — the moment one partition could lend a slot to another under pressure, the isolation the whole pattern exists for is gone. Sizing each SemaphoreSlim's maxCount still comes from watching that one dependency's actual concurrent usage, same as Lesson 18 taught for a single shared pool and Lesson 50 taught for partitioning it.

Scope line

This lesson covers porting Lesson 50's bulkhead pattern (per-dependency resource partitioning, why it protects other dependencies rather than the callee or the caller, why partitions can't lend capacity to each other) to C#, built from SemaphoreSlim (Lesson 109) plus ConcurrentDictionary, and the one C#-specific trap GetOrAdd's outside-the-lock value factory creates for lazy partition creation. It does not re-derive the bulkhead-vs-circuit-breaker-vs-rate-limiter comparison table — Lesson 50 already covers that in full and nothing about it changes in C#. It does not cover Polly's bulkhead isolation policy or any other .NET resilience library's packaged version — the mechanism is taught here from first principles, same as every prior C#-port lesson in this run, per MISSION.md's "concepts first" rule.
