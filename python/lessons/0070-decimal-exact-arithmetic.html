decimal: exact arithmetic for money

Day 69's statistics module computed correct summary numbers from already-correct input. Today's gap is upstream of that: plain Python float cannot represent most decimal fractions exactly, so a pipeline that sums prices or amounts in float silently accumulates tiny errors — the standard-library decimal module fixes exactly this, with no pandas involved.

Why today, specifically: a fresh-gap grep across all 69 lessons and every practice file found zero mentions of decimal, floating-point rounding error, or any float-precision caveat anywhere in the course — a genuine gap, not a previously-set-aside candidate like configparser (still untaught, but narrower: one config-file format pathlib/plain dicts already cover adequately). decimal also answers directly to MISSION.md's own "read, clean, reshape, aggregate, write" pipeline framing — summing or aggregating money is a realistic pipeline task this course has never once gotten numerically right.

1 · 0.1 + 0.2 != 0.3: why float lies about decimals

Try this in any Python shell:

print(0.1 + 0.2)          # 0.30000000000000004 -- not 0.3
print(0.1 + 0.2 == 0.3)   # False

This is not a Python bug — it is how every mainstream language's float works under the hood: it stores numbers in base 2, and most decimal fractions — 0.1, 0.2, 0.3 — have no exact, finite binary representation, the same way 1/3 has no exact finite decimal representation. The error is tiny, a fraction of a cent, but pipelines that sum thousands of such values accumulate it, and on money, "slightly off" is a bug, not a rounding footnote.

Bridge from SQL: this is exactly why SQL's DECIMAL/NUMERIC column types exist alongside FLOAT/REAL — a schema storing prices as NUMERIC(10,2) is making the same choice Python's decimal module makes, and for the same reason.

2 · decimal.Decimal: exact base-10 arithmetic

The standard-library Decimal type stores numbers in base 10 instead of binary, so the fractions that matter for money are exact, not approximated:

from decimal import Decimal

# construct from a string -- NOT from a float, which already lost precision
a = Decimal("0.1")
b = Decimal("0.2")
print(a + b)             # 0.3 -- exact
print(a + b == Decimal("0.3"))   # True

# the float trap: Decimal(0.1) still carries float's existing error
print(Decimal(0.1))     # 0.1000000000000000055511151231257827021181583404541015625

That last line is the single most common decimal mistake: passing a float literal into Decimal() does not fix anything, because the float has already lost precision before Decimal ever sees it — the imprecise binary value is just displayed exactly. The fix is to always construct Decimal from a str (or an int), never from a float, so the exact decimal digits are what gets stored.

3 · A pipeline summing prices correctly

This is the realistic shape: read a list of prices (as they'd arrive from a CSV or JSON — strings, not floats) and total them exactly.

from decimal import Decimal

# prices as they arrive from a CSV row -- strings, never cast to float first
raw_prices = ["19.99", "5.01", "3.33", "0.10", "0.10", "0.10"]

total_float = sum(float(p) for p in raw_prices)
total_decimal = sum(Decimal(p) for p in raw_prices)

print(total_float)      # 28.63000000000001 -- a stray trailing error, visible the moment it's printed
print(total_decimal)    # 28.63 -- exact

Six ordinary prices, summed with float, already print a visibly wrong trailing digit. Decimal never does, because every step of the addition stays in exact base-10 arithmetic. quantize() rounds a Decimal to a fixed number of places with an explicit, named rounding rule — the right way to round money to cents, since it states the rounding behavior instead of relying on float's harder-to-predict rounding at exact halfway points:

from decimal import Decimal, ROUND_HALF_UP

price = Decimal("19.995")
print(price.quantize(Decimal("0.01"), rounding=ROUND_HALF_UP))   # 20.00
Where pandas goes from here: a DataFrame column can hold Decimal objects via dtype=object, but pandas' real strength — vectorized math — works on float64/int64 columns, not Decimal; choosing exactness over speed at the column level is a data/-side design decision, not demonstrated here.
