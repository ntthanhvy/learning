Testing with pytest

Every practice file so far has checked itself with a hand-rolled check() function printing ✓/✗. That was never a coincidence — it's a small, homemade version of what a real Python project uses pytest for. Today: the one deliberate exception to "standard library only" in this course, why it's worth it, and the three pieces that make it work — plain assert, fixtures, and parametrize.

Bridge from SQL: think of a test suite the way you'd think of a set of query-result assertions you'd run after every schema migration — "this SELECT must return exactly these rows, every time, or something broke." pytest is that same idea for functions: run the function, assert the output is what it should be, and re-run automatically on every change instead of eyeballing it by hand.

1 · The one deliberate exception to "standard library only"

pytest is not part of the standard library — it's a third-party package. Every prior lesson's practice file avoided third-party packages on purpose (MISSION.md's constraint: uv run python3 …, no --with needed). Today breaks that rule deliberately, because testing is common enough, and pytest good enough, that avoiding it would teach a worse habit than depending on one well-known package. Day 10 already built the vocabulary for exactly this case: run it once, ad hoc, with no project file at all —

uv run --with pytest pytest practice/11_testing_with_pytest.py

uv run --with pytest installs pytest into a temporary environment for that one command only, touching neither a pyproject.toml nor a uv.lock — this course has neither yet. A real project instead runs uv add --dev pytest once, which writes pytest into the dev dependency group Day 10's pyproject.toml example already sketched (tools a developer needs, never installed for an end user) — after that, plain uv run pytest works with no --with flag, the same way every practice file's uv run python3 already works with no flag once a dependency is declared instead of one-off.

2 · What pytest actually replaces: plain assert

Every practice file's check() function has been doing this by hand:

def check(name, cond):
    try:
        ok = bool(cond())
    except Exception:
        ok = False
    print(("✓" if ok else "✗"), name)

pytest replaces all of that machinery with one keyword: a plain assert. Any function whose name starts with test_, in any file whose name starts with test_, is a test — pytest finds it, runs it, and reports pass or fail based on whether an assert inside it fails:

# test_parsing.py
from parsing import safe_int

def test_safe_int_parses_a_valid_number():
    assert safe_int("42") == 42

def test_safe_int_returns_none_on_garbage():
    assert safe_int("nope") is None

No self.assertEqual(...), no test-class boilerplate — that's the older unittest style, and this course doesn't teach it; pytest's whole design point is that a bare assert expr is enough, plus better failure output than the plain interpreter gives when one fails (it shows the actual values on both sides of ==, not just AssertionError). This is exactly Day 8's safe_int() from the exceptions practice file, pytest-ified: same function, same two cases the hand-rolled check() already covered, now as two separate named tests instead of one lambda each.

3 · Fixtures: shared setup, requested by name

Day 6, 9, and 10's practice files each built a throwaway file or directory at the top of the script with tempfile.mkdtemp() before any exercise could run. A fixture is pytest's name for that same pattern, formalized: a function decorated @pytest.fixture that prepares something and hands it to any test that asks for it by naming it as a parameter:

import pytest
import tempfile
from pathlib import Path

@pytest.fixture
def sales_csv():
    tmp = Path(tempfile.mkdtemp())
    path = tmp / "sales.csv"
    path.write_text("city,amount\nHanoi,120\nDanang,80\n")
    yield path                      # hands the path to the test
    # nothing after yield here — no cleanup needed for a temp dir

def test_extract_reads_two_rows(sales_csv):
    rows = list(extract(sales_csv))
    assert len(rows) == 2

pytest sees that test_extract_reads_two_rows has a parameter named sales_csv, matches it to the fixture of the same name, runs the fixture first, and passes its yielded value in as the argument — no manual wiring, no import beyond pytest itself. Code before yield is setup, running once per test that uses the fixture; code after yield is teardown, guaranteed to run once that test finishes, success or failure — the identical "always runs" guarantee Day 6's context managers and Day 8's finally already made, applied here to test cleanup (closing a real file handle, deleting a row from a test database, and so on).

4 · parametrize: one test body, many inputs

Day 8's safe_int() test above needed two separate functions for two cases. @pytest.mark.parametrize collapses that into one test body run once per row of input/expected-output pairs:

@pytest.mark.parametrize("text, expected", [
    ("42", 42),
    ("", None),
    ("nope", None),
    ("-7", -7),
])
def test_safe_int(text, expected):
    assert safe_int(text) == expected

The first argument is a comma-separated string naming the parameters the test function takes; the second is a list of tuples, one per case. pytest runs test_safe_int four times, once per tuple, reporting each as its own pass/fail (test_safe_int[42-42], test_safe_int[--None], ...) instead of one test silently covering four cases inside a loop, where a failure on case 2 would hide whether cases 3 and 4 also passed. This is the direct pytest-native replacement for the "list of lambdas" shape every practice file's results = [check(...), check(...), ...] has used all course — same idea (several small cases against one function), pytest's own idiom instead of a hand-rolled list.

5 · Running it and reading the output

pytest reports itself — no check(), no ✓/✗ tally to write by hand. A dot per passing test, an F per failing one, then a summary:

....F.                                                    [100%]
=================================== FAILURES ===================================
______________________________ test_safe_int[nope-None] ______________________________
    assert safe_int("nope") == None
E   assert 'nope' == None
=================================== 1 failed, 5 passed in 0.02s ===================================

A failing assert shows the actual left- and right-hand values automatically — no need to write a custom message. This is a strictly more capable version of every prior practice file's check() tally, which is why today's practice file abandons the ✓/✗ idiom entirely and lets pytest report for itself, explained further at the bottom of this lesson.

Where pandas goes from here: testing a pandas pipeline uses the exact same pytest/assert/fixture/parametrize mechanics taught today, just asserting on a DataFrame's contents instead of a plain function's return value — not demonstrated further here; the library itself stays data/'s job.

Try it — self-checking practice (~20 min)

Today's practice is a real pytest test file, not a hand-rolled ✓/✗ script — see the note above on why. Open practice/11_testing_with_pytest.py, follow the TODOs (each is a test body with a missing assert, a fixture, or a parametrize list to fill in), and re-run until every test passes:

cd ~/learning/python && uv run --with pytest pytest practice/11_testing_with_pytest.py -v

-v (verbose) prints one line per test instead of just dots — useful while several are still unsolved.
