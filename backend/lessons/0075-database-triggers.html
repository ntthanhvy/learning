Database triggers: code that runs without anyone calling it

Three earlier lessons have already used the word "trigger" as a foil without ever explaining it. Lesson 29's outbox quiz asked you to rule out "a database trigger that fires before that same row commits" as the wrong answer for what a relay is. Lesson 54's generated tsvector column was praised for needing "no trigger to hand-write." Lesson 73's COPY lesson noted that "triggers still fire per row either way." Every one of those sentences assumed you already knew what a trigger actually is. Today closes that gap.

1 · What a trigger actually is

A trigger is a rule, attached to a table, that tells Postgres: whenever a write of this kind happens to this table, automatically run this function first (or after). Nobody calls it. No handler, no migration script, no line of Go decides "now I should run the trigger" — the write itself is the call.

The function a trigger runs is a trigger function, written in a procedural language like PL/pgSQL. A minimal example: keeping an updated_at column honest without trusting every future caller to remember to set it.

CREATE FUNCTION set_updated_at() RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at := now();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER orders_set_updated_at
    BEFORE UPDATE ON orders
    FOR EACH ROW
    EXECUTE FUNCTION set_updated_at();
-- any UPDATE to orders, from anywhere, now stamps updated_at automatically

NEW is the row as the write is about to leave it; a BEFORE trigger can still edit it before it lands, exactly what this one does. OLD is the row as it existed before the write — available in UPDATE and DELETE triggers for comparing the two.

2 · The four choices every trigger makes

A CREATE TRIGGER statement always answers four questions, and each one changes what the trigger function is allowed to see or do:

Choice AChoice B
TimingBEFORE — can edit or cancel the writeAFTER — write already happened, can only react
GranularityFOR EACH ROW — runs once per affected rowFOR EACH STATEMENT — runs once for the whole statement
EventINSERT / UPDATE / DELETEcan combine more than one, e.g. INSERT OR UPDATE
Scopea specific tablea view, via INSTEAD OF (redirects a write on a non-updatable view)

The updated_at example above is BEFORE + FOR EACH ROW + UPDATE: it needs to edit the row before it lands, and it needs to run separately for every row a multi-row UPDATE touches, since each row's own updated_at is independent.

3 · What a trigger buys: the same "every write path" guarantee as CHECK

Lesson 60's CHECK constraint earned its keep by holding even for writes that skip the handler entirely — a backfill script, a console query, next year's admin tool. A trigger earns its keep the same way, for logic a boolean expression can't express. CHECK (price > 0) can reject a bad value; it can't compute a new one, and it can't look at other rows. A trigger can do both — stamp a timestamp, maintain a denormalized counter (Lesson 2's example: keep orders.item_count in sync every time a row is added to order_items, without every caller remembering to update both tables), or block a write based on a check spanning more than the row being written.

4 · What a trigger costs: logic no one can see by reading the code

The real trade-off: a CHECK constraint sits right next to the column it guards in the CREATE TABLE statement — anyone reading the schema sees it. A trigger lives as a separate object, attached to the table but invisible from the table's own definition; Lesson 14's PR-review lesson would flag exactly this as a substance issue, not a style nit. An engineer reading application code that runs a plain UPDATE orders SET status = 'shipped' has no way to know, from that line alone, that a trigger is about to also silently touch updated_at or a denormalized counter on another table. That's precisely why Lesson 29's outbox pattern deliberately avoided a trigger for publishing events: a trigger firing inside the same transaction as the row write would make the event write atomic with the row write, which sounds appealing, but it means the actual message-publishing logic — retries, serialization, what payload shape to send — lives inside a database function instead of ordinary application code any engineer can read, test, and step through a debugger on. The relay pattern (a separate polling process) trades that invisibility for an extra moving part, on purpose.

5 · Trigger vs. the other row-level guards this course already taught

Four mechanisms now sit at the same "the database enforces this, not just the handler" layer. Lining them up by what each one can actually do:

CHECK (L60)Generated column (L54)Trigger
Can reject a writeyesnoyes, from BEFORE
Can compute a new valuenoyes, from that row onlyyes, from anywhere
Can touch other tablesnonoyes
Visible in table definitionyesyesno — separate object

Lesson 54's tsvector column used GENERATED ALWAYS ... STORED specifically because the job was "compute a new value from this row's own columns," nothing more — the narrowest tool that could do the job, which is also why that lesson could say "no trigger to hand-write" as a genuine advantage. Reach for a full trigger only once the job needs something a generated column structurally cannot do: touching another table, or rejecting the write outright rather than just deriving a column.

Q: "When would you reach for a database trigger instead of handling something in application code?" A strong answer, out loud: "Almost never, as a first choice — a trigger hides logic from anyone reading a plain UPDATE statement, which is exactly the kind of thing I'd flag in a PR review. I'd reach for one only when a rule genuinely has to hold no matter which code path writes the row, the same bar Lesson 60 set for CHECK constraints, and the logic itself needs more than a boolean expression can express — computing a value, or touching a second table, like keeping a denormalized counter in sync. Even then I'd prefer a generated column if the job is only 'derive a value from this row's own columns,' since that stays visible in the table definition instead of living as a separate hidden object. I'd never reach for a trigger to publish an event to a queue — that's exactly the dual-write problem Lesson 29 solved with an outbox and a separate relay process instead, on purpose, so the actual publishing logic stays in ordinary application code." The signal: naming the visibility cost specifically, not just "triggers are magic," and knowing the outbox pattern already answered the one case a trigger looks most tempting for.
