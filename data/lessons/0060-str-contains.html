str.contains(): substring filtering, and the NaN trap

Lesson 10 used .str.contains() for one line in passing; Lessons 42/43 went deep on str.extract()/str.extractall() for pulling pieces OUT of text. Today is the other half of the .str toolkit that never got its own lesson: filtering ROWS by whether a text column contains something — and the one dtype-dependent default that quietly changes whether a missing value crashes your filter or not.

1 · The basic filter: SQL LIKE, spelled in pandas

.str.contains(pattern) returns a boolean mask, one row per value, marking which ones contain that substring — index into the DataFrame with it to actually filter, same as any boolean mask:

merged = orders.merge(customers, on="customer", how="left")
merged[merged["region"].str.contains("south", case=False)]
-- both Binh rows: region "South" contains "south" case-insensitively

Confirmed directly against the real orders_raw.csv left-merged with customers.csv: case=False makes the match case-insensitive (the same instinct as SQL's ILIKE vs LIKE, case-sensitive by default) and returns exactly the 2 Binh rows whose region is "South".

2 · The trap: na= default depends on the column's dtype

The left-merge above leaves Chi's region as missing — Chi has an order but no row in customers.csv. What str.contains() does with that missing value is NOT one fixed rule; confirmed directly, it depends entirely on the column's dtype:

# modern pandas "str" dtype (the default for a plain read_csv() column, pandas 3.x) --
# missing values silently become False, no error, no NaN in the result
merged["region"].dtype                          # str
merged["region"].str.contains("north", case=False)  # row 3 (Chi, NaN) -> False, dtype: bool

# legacy "object" dtype -- missing values become NaN, an object-dtype mask with NaN mixed in
obj_region = merged["region"].astype(object)
mask = obj_region.str.contains("north", case=False)  # row 3 -> NaN, dtype: object
merged[mask]
-- ValueError: Cannot mask with non-boolean array containing NA / NaN values

Confirmed directly on this course's own real fixture, on both dtypes: the modern "str" dtype (what a plain pd.read_csv() column now loads as, pandas 3.0.5) defaults missing values to False and never raises. The older object dtype defaults them to NaN instead — filtering with a mask that mixes True/False/NaN then raises ValueError immediately, because pandas refuses to guess whether a missing value should pass the filter. Passing na=False explicitly sidesteps the whole question — it names "missing rows don't match" outright, on any dtype, and is the safest default to reach for by habit before checking which dtype you actually have.

na= is the keyword that controls this directly — set it once, explicitly, rather than trusting whichever default the column's dtype happens to carry.

3 · Negation: ~ flips the mask, missing values included

There's no .str.not_contains() — negate with ~, the same operator used on any boolean mask:

merged[~merged["region"].str.contains("north", case=False, na=False)]
-- 3 rows: both Binh (region "South", doesn't contain "north") PLUS Chi (region NaN)
-- Chi's NaN mapped to False by na=False, then flipped to True by ~ -- a "doesn't
-- contain north" row correctly includes "no region on file at all"

Confirmed directly: this is a real, not hypothetical, edge — a missing value passes the negated filter for exactly the same reason it failed the un-negated one. Decide up front whether "unknown" should count as "doesn't match" for the question actually being asked; na=False before negating is usually the intent, but naming it out loud is the interview-grade move.

4 · regex=True by default — special characters mean something

The pattern is a regex by default, not a plain substring — a character like . means "any character," not a literal dot:

skus = pd.Series(["A.1", "A21", "B.5"])
skus.str.contains("A.")               # True, True, False -- "." matches ANY char, "A21" matches too
skus.str.contains("A.", regex=False)  # True, False, False -- literal dot now, only "A.1" matches

Confirmed directly: searching for a literal SKU code, filename, or version string containing regex-special characters (., +, (, |, ...) without regex=False silently matches more rows than intended — no error, just a quietly wrong filter. str.contains() accepts a full regex pattern too (capture groups aren't needed here — that's what str.extract(), Lesson 42, is for); regex=False is the fix whenever the pattern is meant as a literal string, not a pattern.

5 · SQL bridge

str.contains(pat, case=False, na=False) is column ILIKE '%pat%' (case-sensitive default str.contains() maps to plain LIKE); ~str.contains(..., na=False) is NOT (column ILIKE '%pat%'). The na= question has no clean SQL parallel — SQL's three-valued logic makes NULL LIKE '%x%' evaluate to NULL automatically (which WHERE then treats as "don't include"), while pandas forces the choice explicitly via na= instead of having a built-in three-valued mask.

6 · Why this earns its keep in an interview

"Filter to rows where the description mentions X" is one of the most common live-coding asks, and the dtype-dependent na= default is exactly the kind of thing that works fine on a clean interview dataset and then breaks — or silently drops rows — the moment real data with missing text shows up. Naming na=False explicitly, unprompted, signals the same "I've been burned by this before" instinct as remembering errors="coerce" or validate= on a merge.

Q: "You filter a text column with `.str.contains('refund')` and it raises `ValueError: Cannot mask with non-boolean array containing NA / NaN values` — what happened and how do you fix it?" A strong answer, out loud: "The column has missing values, and on whatever dtype it's stored as here, `str.contains()`'s default `na=` produced an actual `NaN` in the mask instead of `True`/`False` — pandas won't guess whether a missing value counts as a match, so filtering with a mask that isn't purely boolean raises rather than silently including or excluding those rows. The fix is passing `na=False` explicitly, which says 'a missing value never matches' — or `na=True` if the question actually calls for treating unknowns as matches." The signal: knowing the default isn't one fixed value, and naming `na=False` as the deliberate choice rather than a magic fix.
