The operator module: naming what a lambda was already doing

Day 4 taught sorted(rows, key=lambda row: row["amount"]) — a throwaway one-line function whose entire job is "pull one field out of each item." That job is common enough that the standard library ships a small module of ready-made functions for it: operator module. Today covers its three everyday exports — itemgetter, attrgetter, and methodcaller — plus the handful of operator-as-function spellings (operator.add, operator.mul) that pair with Day 36's reduce.

Bridge from SQL: ORDER BY city, amount sorts by more than one column at once, left to right. itemgetter("city", "amount") is the same multi-column sort key spelled as one Python call, instead of a lambda row: (row["city"], row["amount"]) that says the same thing with more punctuation.

1 · itemgetter: the named version of lambda x: x[key]

Day 4's grouping-by-amount example used a lambda whose only job was one square-bracket lookup:

sorted(sales, key=lambda row: row["amount"])

operator.itemgetter builds exactly that callable, without writing the lambda:

from operator import itemgetter

sales = [
    {"city": "Hanoi", "amount": 120},
    {"city": "Danang", "amount": 200},
    {"city": "HCMC", "amount": 80},
]

sorted(sales, key=itemgetter("amount"))
# [{'city': 'HCMC', 'amount': 80}, {'city': 'Hanoi', 'amount': 120}, {'city': 'Danang', 'amount': 200}]

Verified live: identical output to the lambda version above, same order, same items. Read itemgetter("amount") as "build me a function that takes one item and returns item["amount"]" — itemgetter doesn't look anything up itself; it returns a callable that does, the same two-step shape Day 36's partial used (call itemgetter once to build the function, then that result gets called once per item by sorted). itemgetter also works with integer positions, so it reads a plain tuple or list exactly like lambda pair: pair[0] would.

2 · Sorting by more than one field at once

Pass itemgetter more than one key and it returns a tuple of values instead of one — which is exactly what a multi-column sort needs, since Python compares tuples element by element, left to right, falling through to the second element only when the first ties:

from operator import itemgetter

rows = [
    {"city": "Hanoi", "amount": 120},
    {"city": "Hanoi", "amount": 80},
    {"city": "Danang", "amount": 200},
]

sorted(rows, key=itemgetter("city", "amount"))
# [{'city': 'Danang', ...}, {'city': 'Hanoi', 'amount': 80}, {'city': 'Hanoi', 'amount': 120}]
# -- Danang first (alphabetically first city); the two Hanoi rows then break
# their tie on amount, 80 before 120

Verified live: matches the comment exactly, including which of the two Hanoi rows sorts first. The equivalent hand-written key would be lambda row: (row["city"], row["amount"]) — itemgetter with several arguments is just a shorter, faster way to say "build that tuple."

3 · attrgetter: the same idea for objects, not dicts

itemgetter reaches inside with [], so it only works on things that support square-bracket lookup — dicts, lists, tuples. An object's fields are read with a dot instead, so sorting a list of plain objects or namedtuples (Day 53) by a field needs attrgetter:

from operator import attrgetter
from collections import namedtuple

Point = namedtuple("Point", ["x", "y"])
pts = [Point(3, 1), Point(1, 2), Point(2, 0)]

sorted(pts, key=attrgetter("x"))
# [Point(x=1, y=2), Point(x=2, y=0), Point(x=3, y=1)]

Verified live: matches the comment. attrgetter("x") is the named version of lambda p: p.x — same relationship itemgetter has to lambda p: p["x"], just reached with a dot instead of brackets. It works on any object with the named attribute: a namedtuple, a dataclass instance, a plain class instance, or a module. Like itemgetter, multiple names build a tuple for a multi-field sort: attrgetter("last_name", "first_name").

4 · methodcaller: calling a method instead of reading a field

Sometimes the value to sort or map by isn't a field at all — it's the result of calling a method. methodcaller is the named version of that lambda:

from operator import methodcaller

words = ["banana", "Apple", "cherry"]
sorted(words, key=methodcaller("lower"))
# ['Apple', 'banana', 'cherry'] -- case-insensitive order

list(map(methodcaller("upper"), words))
# ['BANANA', 'APPLE', 'CHERRY']

Verified live: both match their comments. methodcaller("lower") is the named version of lambda s: s.lower() — it calls the named method with no arguments on whatever it's given. Extra positional or keyword arguments after the name get forwarded to the method call itself, e.g. methodcaller("replace", "a", "@") is the named version of lambda s: s.replace("a", "@").

Why bother — a lambda already works. Two real reasons, not just style. First, speed: itemgetter/attrgetter/methodcaller are implemented in C and skip the overhead of a Python-level function call on every comparison — on a large sorted() call this is measurably faster than the equivalent lambda, though "measurably" here matters far less than the second reason. Second, and more important day to day: itemgetter("amount") says "get the amount field" in six words of code that read the same way every time it's used, where a lambda row: row["amount"] asks a reader to parse a tiny function definition just to see the same thing. Reach for the operator version when the job is exactly "pull a field" or "call a no-argument method" — reach for a real lambda the moment the key needs any actual computation (Day 4's lambda pair: pair[1] reading a tuple index is a fine lambda; the moment it becomes lambda row: row["amount"] * 1.1, there's real logic, and itemgetter can't express that at all.)

5 · The other half of the module: operators as callables

operator also has a plain function for every built-in operator — operator.add(a, b) is exactly a + b as a callable, operator.mul is *, and so on for every arithmetic and comparison operator. These exist for the same reason as itemgetter: some other function wants a callable, and writing lambda a, b: a + b to hand it one is exactly what operator.add already is:

from functools import reduce
from operator import add, mul

nums = [1, 2, 3, 4]
reduce(add, nums)   # 10 -- same as reduce(lambda acc, x: acc + x, nums)
reduce(mul, nums)   # 24 -- same as reduce(lambda acc, x: acc * x, nums)

Verified live: both match their comments. This is Day 36's reduce paired with the named operator instead of an inline lambda — sum(nums) is still the right call for a plain sum (Day 36's own point about preferring a named built-in when one already exists), but reduce(mul, nums) for a product has no built-in equivalent, and operator.mul reads more directly than lambda a, b: a * b inside the same line.

Where pandas goes from here: nothing pandas-specific — pandas has its own vectorized column operations (df.sort_values(["city", "amount"]) covers the multi-key case) that don't call itemgetter or any plain Python function per row at all; today's module is a plain-Python, per-item mechanism with no DataFrame involved, per MISSION.md.

Q: "Why would you use operator.itemgetter instead of a lambda for a sort key?" A strong answer, out loud: "When the key is exactly 'read one field' or 'read a few fields for a multi-column sort,' itemgetter("city", "amount") says that directly and is implemented in C, so it's a little faster on a large sort than a Python-level lambda doing the same lookup. I'd reach for a real lambda the moment the key needs actual computation — anything past a plain lookup, like scaling a value or combining two fields with an operator, itemgetter can't express, and forcing it there just to avoid a lambda would be the wrong trade." The signal: naming both the readability and performance reasons, and knowing exactly where itemgetter's expressiveness runs out.
