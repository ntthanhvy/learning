File uploads: why your API shouldn't proxy the bytes

You've built upload UIs — a form, a file input, a progress bar — dozens of times, but probably never designed what happens on the backend once "upload" is clicked. The naive answer, "just POST the file to my API like everything else," is the one senior reviewers push back on hardest. Today: what a file upload actually costs a request handler, and the pattern that avoids paying it.

1 · The naive version, and what it costs

The obvious design: the browser sends the file's bytes straight to your API in a multipart/form-data body, your handler reads it, and writes it to disk or a database column. This works for a 10 KB avatar. It breaks down fast for anything bigger, for a reason that traces straight back to Lesson 18's connection pool lesson: every second your handler spends reading a slow client's upload — a user on hotel wifi pushing a 200 MB video — is a second one goroutine, one open connection, and (if the handler touches the database at all, even just to record "upload started") one pooled connection sits occupied doing nothing but waiting on bytes. Multiply by a handful of concurrent uploads and you've reproduced Lesson 18's exhaustion scenario without a single slow query involved — the bottleneck this time is disk/network I/O on a large payload, not the database, but the pool doesn't know the difference between "connection is running a slow query" and "connection is idle while a handler blocks on a slow client."

There's a second cost besides concurrency: memory. A naive handler that reads the whole body into a []byte before doing anything with it holds the entire file in RAM per in-flight upload — a handful of large concurrent uploads can push a modest instance into an out-of-memory kill. Streaming the body straight to disk instead of buffering it fully avoids that specific problem, but the connection-hogging cost above still applies either way, because the handler is still occupied for the full duration of a slow transfer.

2 · The pattern: hand out a permission slip, not a pipe

The fix most production APIs converge on: don't proxy the bytes through your API server at all. Have the client upload directly to object storage — a service built for exactly this job — and keep your API server out of the data path entirely. Your API's only role becomes issuing permission: a presigned URL your handler generates and hands back to the client, who then uploads (or downloads) directly against that URL.

Client                    Your API                  Object storage
  |-- POST /uploads ------->|                              |
  |                         |-- sign upload URL (SDK) ---->|
  |<-- { uploadUrl, key } --|                              |
  |                                                         |
  |-- PUT <uploadUrl> -- file bytes ----------------------->|
  |<---------------------------------------- 200 OK --------|
  |                                                         |
  |-- POST /uploads/{key}/complete ------------------------>|
  |   (your API records the row, only now)                  |

The signature embeds three things the storage service checks itself, entirely outside your process: which object key may be written, which operation is allowed (usually just PUT), and an expiry timestamp after which the URL stops working. Your handler's job shrinks to one cheap operation — generate a signed URL, which is local cryptography, not a network call to anywhere — and returns immediately. No goroutine sits blocked on a slow client's connection; no pooled database connection sits idle waiting for bytes that may take thirty seconds to arrive over hotel wifi.

3 · A presigned URL is a scoped, expiring credential — treat it like one

This is the same shape of idea Lesson 31 covered for service-to-service calls: a presigned URL is delegated permission, not authentication of the caller's identity. Whoever holds the URL can use it — there's no login check baked into the signature, only "this exact operation on this exact key is allowed until this exact time." That has direct design consequences your handler must enforce before it ever generates one: check the requesting user is actually authorized to write to that key (Lesson 12's authorization, not the storage service's problem to solve), pick an expiry short enough that a leaked URL in a browser history or a proxy log stops mattering quickly — minutes, not days — and never let the client choose the object key freely, since an attacker-chosen key could overwrite another user's file or escape the intended prefix entirely. Generate the key server-side (a UUID, or {userID}/{uuid}) and only sign that.

The mistake this retrains: treating "the upload succeeded" and "the file is safe to reference" as the same moment. A presigned PUT only proves the bytes landed in storage — it says nothing about file type, size, or content. Validate after the upload completes: your API's completion endpoint (the POST /uploads/{key}/complete step above) is where you check the actual stored object's size and content type before writing a database row that makes it visible to other users. Trusting the client-reported Content-Type from the upload step alone is exactly the kind of unvalidated-input mistake Lesson 17's input validation lesson warned about, just in a different body shape.

4 · When proxying through your API is still the right call

The presigned-URL pattern isn't a universal rule — it's the right default once files get large or upload volume gets meaningful, but it adds a real round trip and a second service to reason about. A handful of legitimate reasons to still proxy small uploads through your own handler: the file is small and rare enough that connection-hogging never becomes a real problem (a user's profile photo, uploaded once in a while), you need to run synchronous validation or transformation (virus scanning, image resizing) before the bytes are ever considered "landed," or the file needs to be transactionally tied to a database write in a way that's awkward to express as two separate steps. The instinct to build is: reach for direct-to-storage first for anything user-facing and potentially large, and justify proxying explicitly rather than doing it by default because it's the simplest thing to write first.

Q: "Why not just accept the file upload directly in your API handler?" A strong answer, out loud: "For small, infrequent files it's fine. But for anything large or high-volume, the handler is occupied for the entire transfer duration — that's a held goroutine and often a held database connection for as long as a slow client takes to finish sending, which is exactly the connection pool exhaustion problem, just triggered by I/O time instead of query time. The pattern that avoids it is a presigned URL: the API signs a short-lived, scoped credential and the client uploads straight to object storage, so the API's own request only lasts as long as generating that signature. The trade-off is you now have to validate the uploaded object's type and size after the fact, in a completion step, since the presigned PUT itself proves nothing about what actually got uploaded." The signal: connecting the upload problem back to connection-pool reasoning already covered, not treating file uploads as an unrelated new topic.
