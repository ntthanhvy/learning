The bulkhead pattern: giving each dependency its own lifeboat

Lesson 49's closing teaser named two untaught candidates: the bulkhead pattern and ETag/conditional-request headers. Today, the first one — why a single shared connection pool lets one slow dependency starve every request, even the ones that never touch it, and the fix that gives each dependency its own fixed slice instead.

1 · One pool, shared by every dependency, is a single point of failure

Lesson 18 sized a connection pool as if a service only ever talked to one database. Real services rarely do: the same handler process might hold a pool of connections to the primary Postgres database, another pool for calls to a shipping service, and a third for a slow reporting service used by one internal dashboard. If all three share one general-purpose pool — one http.Client, one worker-goroutine limit, one set of database connections — a problem with just the slowest one can consume the entire shared pool, leaving nothing for the other two.

Concretely: say the reporting service starts responding in 10 seconds instead of 100ms. Every request that happens to trigger a reporting call now holds a pool slot for 10 seconds instead of releasing it almost immediately. If report calls arrive steadily, the shared pool fills up entirely with slots waiting on the one slow dependency — and a completely unrelated request that only needed the fast primary database now waits behind them too, because it drew from the same limited pool. One dependency's slowness becomes every dependency's outage, even the healthy ones.

Frontend-habit trap: this is the backend cousin of one slow, unrelated fetch() call starving a browser's per-host connection limit so every other request queues behind it — except a browser's fix (HTTP/2 multiplexing, more connections) is invisible infrastructure, while a backend service has to build the partitioning itself.

2 · The fix: partition the shared resource, don't just grow it

The instinctive fix — make the pool bigger — doesn't solve this; Lesson 18 already established that pool size is bounded by what the database and the machine can actually support, and a bigger shared pool still lets one dependency's slow calls eventually consume all of it, just after a longer delay. The actual fix is to stop sharing the pool at all: give each dependency its own fixed-size slice of capacity, walled off from the others, so exhausting one dependency's slice can never touch what's reserved for the rest.

This is the bulkhead pattern: named after a ship's bulkheads, the internal walls that divide a hull into separate watertight compartments so a single hull breach floods only one compartment instead of sinking the whole ship. Applied to a backend service, each compartment is a fixed slice of some limited resource — most often a connection pool or a bounded number of concurrent goroutines — dedicated to exactly one dependency. A leak or a slowdown in one compartment can fill that compartment, but the walls mean it physically cannot spread into the capacity reserved for any other dependency.

3 · A minimal Go implementation

The mechanism is smaller than it sounds: a map from dependency name to its own small pool, and a lookup before every call.

type Pool struct {
    maxConns int
    inUse    int
    mu       sync.Mutex
}

var ErrPoolFull = errors.New("bulkhead full: no capacity for this dependency")

func (p *Pool) Acquire() (func(), error) {
    p.mu.Lock()
    defer p.mu.Unlock()
    if p.inUse >= p.maxConns {
        return nil, ErrPoolFull
    }
    p.inUse++
    return func() {
        p.mu.Lock()
        p.inUse--
        p.mu.Unlock()
    }, nil
}

// Bulkhead partitions a shared resource into fixed, independent slices per
// dependency, so exhausting one slice can never touch capacity reserved
// for calls to any other dependency.
type Bulkhead struct {
    pools map[string]*Pool
}

func NewBulkhead(limits map[string]int) *Bulkhead {
    pools := make(map[string]*Pool, len(limits))
    for name, limit := range limits {
        pools[name] = &Pool{maxConns: limit}
    }
    return &Bulkhead{pools: pools}
}

// Call runs fn using only the named partition's own capacity -- a
// dependency with no slot free fails immediately with ErrPoolFull instead
// of competing with every other dependency for a shared pool.
func (b *Bulkhead) Call(dependency string, fn func() error) error {
    pool, ok := b.pools[dependency]
    if !ok {
        return fmt.Errorf("no bulkhead partition configured for %q", dependency)
    }
    release, err := pool.Acquire()
    if err != nil {
        return err // this dependency's own slice is full -- others are untouched
    }
    defer release()
    return fn()
}

Setting it up names each dependency's own fixed budget up front: NewBulkhead(map[string]int{"inventory": 8, "shipping": 4, "reports": 2}). A reporting call that finds its 2-slot partition full returns ErrPoolFull immediately — it never even looks at whether the inventory or shipping partitions have room, because it isn't allowed to use them. Sizing each partition follows the same reasoning Lesson 18 taught for a single pool — how much concurrent work does this specific dependency actually need — just applied per-dependency instead of once for everything.

4 · Bulkhead, circuit breaker, and rate limiter protect three different things

All three of Lessons 11, 28, and today's bulkhead reject calls under some condition, which makes them easy to blur together in an interview answer — but each defends a different boundary:

Rate limiter (L11)Circuit breaker (L28)Bulkhead (today)
Protectsthe callee, from too many callersthe caller, from a failing calleeother dependencies, from one saturated one
Triggered byrequest volume crossing a capconsecutive failures crossing a thresholdthis dependency's own slice being full
Reacts tohow much traffic is arrivingwhether calls are failingwhether calls are slow or stuck, failing or not
Failure stays contained tothe caller sending too muchcalls to the one bad dependencyone partition of a shared resource

They compose rather than compete: a bulkhead can give the reporting dependency its own 2-connection partition, and a circuit breaker can additionally wrap calls inside that partition so that once the reporting service starts failing outright (not just running slow), it stops even attempting the call. The bulkhead limits how much of the shared resource one dependency's problem can occupy; the circuit breaker limits how long callers keep trying a dependency that's already shown it's broken. Neither replaces the other — a bulkhead alone still lets a slow-but-not-failing dependency hold its whole partition's connections indefinitely, and a circuit breaker alone still shares one pool across every dependency until it trips.

5 · Partitioning has a cost: idle capacity that can't be borrowed

A bulkhead's protection is also its trade-off. The reporting dependency's 2-connection partition sits unused most of the day — but even while the inventory partition is fully saturated and rejecting calls, those 2 reporting slots cannot be lent to inventory, because the whole point of the wall is that it doesn't flex. That's correct behavior, not a bug: the instant partitions can borrow from each other under pressure, the wall stops being a wall, and the exact cascading failure this pattern exists to prevent becomes possible again. Sizing partitions is therefore a real trade-off, not a free safety net — a partition sized too small rejects legitimate calls to a perfectly healthy dependency during a normal traffic spike, while a partition sized too generously gives back some of the isolation the pattern is for. The right size comes from the same measurement Lesson 18 already taught: watch actual concurrent usage per dependency, not a guess.

Q: "One of your service's downstream dependencies started responding slowly, and now your whole API is timing out — even endpoints that never call that dependency. Why, and how would you prevent it?" A strong answer, out loud: "That's the signature of a shared resource pool with no isolation between dependencies — every call, regardless of which dependency it hits, draws from the same connection pool or goroutine limit, so the slow dependency's calls sit holding slots for the full timeout duration and starve everyone else out of the same pool. I'd apply the bulkhead pattern: give each dependency its own fixed-size partition of the pool, sized to what that dependency actually needs, so one dependency saturating its own slice can never touch capacity reserved for the others. I'd also wrap the slow dependency's calls in a circuit breaker inside its own partition, since a bulkhead alone doesn't stop a dependency that's slow but not yet failing from holding its whole partition indefinitely." The signal: naming the shared-pool-starves-everyone mechanism specifically, and that a bulkhead and a circuit breaker solve different halves of the same incident.
