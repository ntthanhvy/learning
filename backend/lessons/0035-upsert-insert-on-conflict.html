Upsert: INSERT ... ON CONFLICT

Lesson 6 fixed a lost-update race on UPDATE by folding the check into the statement itself. Lesson 33 did the same thing for a slow, human-timescale conflict with a version column. Today's the third member of that family — the same race, but on INSERT instead of UPDATE, and the one-statement fix Postgres ships for it by name.

1 · The bug: check-then-insert, twice, at once

A "claim a username" feature looks safe written the obvious way: check if the username is taken, and if not, insert it.

-- both requests run this first, both see zero rows
SELECT EXISTS(SELECT 1 FROM usernames WHERE username = $1);

-- both requests then run this — both think it's safe
INSERT INTO usernames (account_id, username) VALUES ($1, $2);

Two requests for the same username arrive close together. Both run the SELECT before either has committed an INSERT, so both see "not taken." Both proceed to insert. If username has a UNIQUE constraint, the second INSERT fails outright with a unique violation — an ugly, easy-to-mishandle error the handler has to catch and translate into a sane response. If username has no constraint at all, both inserts succeed and now two rows claim the same name. Either way, this is Lesson 6's exact shape — check-then-act, twice, at once — just landing on INSERT instead of UPDATE.

Frontend-habit trap: a frontend form usually only ever fires one submit per click, so "check availability, then submit" reads as obviously safe — there's no second browser tab racing the same request in most UI flows. A backend handler has no such luxury: two different users, or one user's double-clicked retry, can hit the same handler within the same millisecond, and the database is the only thing positioned to referee that.

2 · The fix: let the constraint do the checking

Postgres has a purpose-built statement for exactly this: upsert — an INSERT ... ON CONFLICT that names what should happen if the row collides with one already there, instead of just erroring:

INSERT INTO usernames (account_id, username)
VALUES ($1, $2)
ON CONFLICT (username) DO NOTHING
RETURNING account_id;

One statement, one round trip to the database. If no row with that username exists, the insert happens normally and RETURNING hands back the row that was just written. If a row already holds that username, Postgres skips the insert entirely — no error, no violation — and RETURNING simply returns nothing. The application code tells the two outcomes apart the same way sql.ErrNoRows already does everywhere else in this course:

// claimUsername is the upsert-shaped fix: one statement, the constraint
// itself is the check, and ON CONFLICT names what to do when it fires.
func claimUsername(ctx context.Context, db DB, accountID int64, username string) error {
    var claimedBy int64
    row := db.QueryRowContext(ctx, `
        INSERT INTO usernames (account_id, username)
        VALUES ($1, $2)
        ON CONFLICT (username) DO NOTHING
        RETURNING account_id`, accountID, username)
    err := row.Scan(&claimedBy)
    if errors.Is(err, sql.ErrNoRows) {
        return ErrAlreadyClaimed // someone else's row already holds this username
    }
    return err
}

Why this actually closes the race and the two-step version doesn't: there's no longer a window between a read and a write for a second request to land in. The uniqueness check is the INSERT — Postgres evaluates the constraint as part of committing the row, and only one of the two concurrent inserts can win it. This is the exact "fold the check into the statement" move Lesson 6 taught for UPDATE, applied to INSERT instead: the constraint the database already enforces becomes the check, rather than a separate SELECT the application runs and then has to trust.

3 · The other half: DO UPDATE

DO NOTHING answers "insert, or silently skip." Often the better answer is "insert, or update the row that's already there" — a single upsert that works whether or not a row exists yet, useful for counters, caches, and any "set this value" operation where the caller doesn't know or care which case applies:

-- recordDailyLoginCount: insert a fresh counter row, or bump the
-- existing one atomically, in one round trip either way.
INSERT INTO daily_logins (account_id, login_date, count)
VALUES ($1, $2, 1)
ON CONFLICT (account_id, login_date)
DO UPDATE SET count = daily_logins.count + 1;

First login of the day for that account: no conflicting row exists, so the plain INSERT runs and count starts at 1. Every login after that: the (account_id, login_date) pair already exists, so instead of erroring, Postgres runs the DO UPDATE clause — note it reads daily_logins.count + 1, the table's own current value, not the 1 from the failed VALUES list — incrementing the existing row instead. One statement handles both the "doesn't exist yet" and "already exists" cases correctly, with no race between checking which case applies and acting on it.
