1 · The question a contract raises but doesn't answer

Day 14's contract: {enforced: true} makes fct_orders a promise: these columns, these types, checked by dbt before every build finishes. That promise is exactly why a straightforward rename — say, order_total renamed to the clearer total_amount — isn't straightforward anymore. Rename the column in fct_orders.sql and ship it, and the next build breaks on purpose: on_schema_change: 'fail' was set precisely to stop a column from silently disappearing underneath Day 14's own delivery_ops_dashboard exposure, which reads order_total directly. The contract did its job — it just didn't say what to do next.

The honest options are limited. Don't rename it, and the project carries an unclear column name forever. Rename it and ship, and the dashboard's next query throws column "order_total" does not exist with no warning beforehand. Add total_amount as a second column alongside the old one, and the model accumulates renamed-but-never-removed cruft every time this happens. Model versions are dbt's actual answer: ship both shapes at once, under one logical name, and let each consumer decide when it moves.

2 · What a versioned model actually looks like on disk

A versioned fct_orders becomes two SQL files instead of one, each a complete, independently buildable model — not a diff, not a shared base file. fct_orders_v1.sql is exactly what Day 14 already has, unchanged. fct_orders_v2.sql is a copy with one line different:

-- models/marts/fct_orders_v2.sql -- the only change from fct_orders_v1.sql
{{ config(
    materialized='incremental',
    unique_key='order_id',
    incremental_strategy='merge',
    on_schema_change='fail',
    contract={'enforced': true}
) }}

select
    order_id,
    customer_id,
    restaurant_id,
    courier_id,
    subtotal,
    delivery_fee,
    subtotal + delivery_fee as total_amount,  -- was "as order_total" in v1
    placed_at
from {{ ref('stg_orders') }}

{% if is_incremental() %}
where placed_at > (select coalesce(max(placed_at), '1900-01-01') from {{ this }})
{% endif %}

The YAML in marts.yml is what actually ties the two files to one logical model and tells dbt which file is which version:

-- models/marts/marts.yml -- replacing Day 14's single fct_orders entry
models:
  - name: fct_orders
    latest_version: 2
    description: "One row per order. Versioned: v1 keeps order_total for the exposure that hasn't migrated yet; v2 renames it to total_amount."
    columns:
      - name: order_id
        data_type: bigint
        constraints: [{type: not_null}, {type: unique}]
        tests: [not_null, unique]
      - name: customer_id
        data_type: bigint
      - name: restaurant_id
        data_type: bigint
      - name: courier_id
        data_type: bigint
      - name: subtotal
        data_type: numeric
      - name: delivery_fee
        data_type: numeric
      - name: placed_at
        data_type: timestamp
    versions:
      - v: 1
        defined_in: fct_orders_v1
        deprecation_date: 2026-11-25
        columns:
          - include: '*'
          - name: order_total
            data_type: numeric
      - v: 2
        defined_in: fct_orders_v2
        columns:
          - include: '*'
          - name: total_amount
            data_type: numeric

Three fields carry the whole mechanism. defined_in points each version entry at the actual file holding its SELECT. latest_version decides what a plain, unpinned ref('fct_orders') resolves to anywhere else in the project, from this point on, with no version number written at the call site at all. And the per-version columns: block — include: '*' plus one override — says each version's actual contracted shape without repeating all seven unchanged columns twice.

3 · Build: ship v2, pin the exposure to v1, prove both resolve correctly

In food_delivery_pipeline/: rename nothing. Copy models/marts/fct_orders.sql to models/marts/fct_orders_v1.sql unchanged, create models/marts/fct_orders_v2.sql with the one-line rename from Section 2, delete the old unversioned fct_orders.sql, and replace marts.yml's fct_orders entry with Section 2's version block. Then pin Day 14's exposure explicitly to v1 — the whole reason it still works unchanged:

-- models/marts/exposures.yml -- the one line that changes
exposures:
  - name: delivery_ops_dashboard
    # ...label, type, maturity, url, description, owner unchanged from Day 14...
    depends_on:
      - ref('fct_orders', v=1)   # was: ref('fct_orders') -- now pinned on purpose
      - ref('mart_delivery_sla')

Now add a brand-new model that deliberately does not pin a version — the point is watching an ordinary, everyday ref() pick up v2 automatically because latest_version: 2 says so, with nobody at the call site typing a version number:

-- models/marts/mart_delivery_sla.sql -- new file, reads the renamed column on purpose
select
    order_id,
    total_amount,
    placed_at
from {{ ref('fct_orders') }}  -- no v= pin -- resolves to v2, because latest_version: 2

4 · deprecation_date: a warning dbt actually prints, not a silent calendar note

Section 2's marts.yml gave v1 a deprecation_date already in the past, on purpose, to show what it actually does. It is not enforcement — nothing fails, nothing blocks a build:

uv run --project ../dbt_env dbt parse

Expected, confirmed live this round against exactly this YAML shape:

[WARNING]: Model fct_orders.v1 has passed its deprecation date of 2026-11-25T00:00:00+07:00.
This model should be disabled or removed.

That line prints on every dbt parse, dbt run and dbt build from now on — a nudge visible to whoever next touches this project, not a one-time note that gets forgotten. It names the exact version, not just "fct_orders" generically, which matters the moment there are three or four live versions of something and only one of them is actually overdue. The real deprecation workflow it's pointing at: once delivery_ops_dashboard migrates its query to total_amount and its exposure's ref() is repinned to v=2, delete fct_orders_v1.sql and its versions: entry entirely — a deprecation_date is a scheduled reminder to finish the migration, not a feature you leave on forever.

5 · Why this is the API-versioning idea, not a new one

A versioned dbt model is the same shape as versioning a REST API endpoint from backend/: old consumers keep working against the version they already call, new consumers get the improved shape by default, and the old version carries an explicit sunset date rather than disappearing without warning. latest_version plays the role an API gateway's default-version routing plays; ref('fct_orders', v=1) plays the role of a client explicitly requesting /v1/orders instead of trusting whatever "current" means today. The mechanism is dbt-specific — two SQL files, one YAML block, resolved at parse time — but the underlying problem (how do you change a contract's shape without breaking whoever already depends on the old one) is exactly backend's, just one layer further upstream, at the warehouse instead of the API.

Q: "You enforce model contracts on your marts. How do you actually change one once something downstream depends on it?" A strong answer, out loud: "A contract stops a column from silently changing shape, but it doesn't answer what to do when a real rename is needed — so dbt has model versions for exactly that. I ship the new shape as a second file, fct_orders_v2.sql, alongside the original, and declare both under one versions: block in the YAML with a latest_version pointing at v2. Every ref('fct_orders') anywhere in the project that doesn't explicitly pin a version automatically gets v2 from that point on — that's the default for anything new. Anything that still needs the old shape, like an exposure a dashboard team owns, pins ref('fct_orders', v=1) explicitly, so it keeps building against the exact columns it was written against, with no surprise break. I also set a deprecation_date on v1, which makes dbt print a real warning on every parse and run naming that specific version until the dashboard migrates and I can delete it. It's the same idea as versioning a REST endpoint — old clients keep working against the version they call, new clients get the improved shape by default, and the old one has a named sunset instead of just disappearing." The signal: naming that latest_version controls the default for unpinned refs specifically, and that a deprecation_date is a visible nudge, not an enforcement mechanism.
