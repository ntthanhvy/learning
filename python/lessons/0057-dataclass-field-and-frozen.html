Bridge from SQL: frozen=True is close to a row from a table with no UPDATE grant — readable, comparable, but never rewritten in place; to "change" one field you build a new row. field(compare=False) is like leaving a column out of a UNIQUE constraint's column list: it still exists on the row, it's just not part of what makes two rows "the same."

1 · The mutable-default trap, and default_factory

Day 1 taught that a mutable default argument is a trap because Python builds the default value once, at function-definition time, and every call that skips the argument shares that one object. A dataclass field with a mutable default would hit the exact same trap — so @dataclass refuses to even let you write it, and raises immediately when the class is defined, not later when it's misused:

from dataclasses import dataclass

@dataclass
class Cart:
    items: list = []   # ValueError: mutable default <class 'list'> for field items is not allowed: use default_factory

Verified live: that exact line raises ValueError at class-definition time — before any Cart() is ever created. The fix is field(default_factory=...), which stores a callable instead of a value — @dataclass calls it fresh for every instance that skips the argument, so no two instances ever share one list:

from dataclasses import dataclass, field

@dataclass
class Cart:
    items: list = field(default_factory=list)   # calls list() fresh per instance, not once

c1 = Cart()
c2 = Cart()
c1.items.append("apple")
c1.items   # ['apple']
c2.items   # [] -- untouched; c1 and c2 never shared one list

Verified live: matches the comments exactly — c2.items stays empty after mutating c1.items. Read field(default_factory=list) as "don't give me a default value, give me a zero-argument function that builds one" — list, dict, and set are the three you'll reach for constantly, and any other zero-argument callable (including a lambda, Day 4) works the same way.

field() vs. a plain default — when each applies: a plain = "VND" default works for anything immutable (str, int, float, bool, None, a tuple of immutables) — Day 7's currency: str = "VND" was always fine. field(default_factory=...) is required the moment the default is mutable (list, dict, set, or another dataclass) — exactly the same immutable/mutable line Day 1 drew for function defaults, now enforced by @dataclass itself instead of silently trusted.

2 · field()'s other two jobs: repr and compare

field() takes more than default_factory. Two more keyword arguments control what the auto-generated __repr__ and __eq__ (Day 7 §2) do with one specific field, without touching how the rest of the class behaves:

from dataclasses import dataclass, field

@dataclass
class User:
    name: str
    password: str = field(repr=False)              # leave this field out of __repr__
    id: int = field(default=0, compare=False)     # leave this field out of __eq__

u1 = User("Ann", "secret", id=1)
u2 = User("Ann", "secret", id=2)
repr(u1)         # "User(name='Ann', id=1)" -- password never printed, even though it's a real field
u1 == u2       # True -- id differs (1 vs 2) but compare=False takes it out of the equality check

Verified live: matches both comments — repr(u1) shows name and id but never password, and u1 == u2 is True despite different ids. repr=False is the direct fix for the obvious problem: a password, token, or any secret field printed by accident the first time someone logs an instance for debugging. compare=False answers a narrower question — "should two records with a different id but otherwise identical data count as equal?" — the same judgment call SQL makes explicit every time a query does or doesn't include a surrogate key in a comparison. Note that field(default=0, ...) is how a plain default is spelled once any keyword argument is needed on that field — field() replaces the bare = 0 entirely, it doesn't stack alongside it.

3 · frozen=True: a dataclass that refuses to be mutated

Day 31 used frozen=True for one sentence, in service of a different topic (why a frozen dataclass gets a safe auto-generated __hash__). What it actually does, on its own merits: every field becomes read-only after __init__ finishes constructing the instance. Any later assignment raises, instead of silently succeeding the way an ordinary dataclass's would:

from dataclasses import dataclass

@dataclass(frozen=True)
class Point:
    x: int
    y: int

p = Point(1, 2)
p.x = 99   # dataclasses.FrozenInstanceError: cannot assign to field 'x'

Verified live: that assignment raises dataclasses.FrozenInstanceError with exactly that message, immediately — not a silent no-op, and not deferred until p is read somewhere else. This is Day 1's immutable idea, now available for a class you write yourself instead of only the built-in types (str, tuple, int) that already had it. The practical payoff is the same reason immutability mattered on Day 1: an instance passed into a function, stored in a shared cache, or handed to another thread can never be mutated out from under whoever else is holding a reference to it — "changing" one always means building a new instance, the same discipline str already forces on every rename or slice.

Why this pairs with Day 31's __hash__ point: a mutable object is unsafe as a dict key or set member because mutating it after insertion can move it to the wrong hash bucket, unreachable by lookup (Day 31's exact bug). frozen=True removes that risk at the source — nothing can mutate a frozen instance's fields at all, ever, so @dataclass(frozen=True) is the one case where @dataclass auto-generates a matching __hash__ for you; an ordinary (non-frozen) dataclass gets __eq__ but no __hash__, and is unhashable by default for exactly this reason.
Where pandas goes from here: nothing pandas-specific — a DataFrame's columns are always mutable in place (df["x"] = ... reassigns a column freely); pandas has no per-row immutability concept resembling frozen=True at all. Not covered here; that's the only sentence in this lesson that mentions it, per MISSION.md.

4 · Putting both together: an immutable record with a hidden field

frozen=True and field() combine freely — a config record that can't drift after being loaded, with a secret kept out of any accidental log line:

from dataclasses import dataclass, field

@dataclass(frozen=True)
class Config:
    host: str
    api_key: str = field(repr=False)
    retries: int = field(default=3, compare=False)

cfg = Config("api.example.com", "sk-secret")
print(cfg)   # Config(host='api.example.com', retries=3) -- api_key never printed

Every field above traces back to a rule already stated this lesson — nothing new past this point, just the four rules (mutable default needs default_factory, repr=False hides a field from printing, compare=False excludes it from equality, frozen=True locks every field after construction) used together on one realistic record.
