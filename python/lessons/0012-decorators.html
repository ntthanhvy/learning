Decorators

Day 11's practice file used @pytest.fixture and @pytest.mark.parametrize without ever explaining what the @ above a function actually does — the lesson said so explicitly, and promised today would fix it. A decorator is just a function that takes a function and returns a new one wrapped around it — nothing more exotic than that, built entirely from Day 4's "a function is a value."

Bridge from SQL: think of a decorator like a BEFORE/AFTER trigger wrapped around a table write — the original INSERT still happens exactly as written, but extra logic runs around it (logging, a check, a timestamp) without touching the statement itself. A decorator wraps a function the same way: the original function still runs, extra behavior runs around the call.

1 · The mechanism: a function that takes a function

Day 4 established that a function is a value — a name bound to a function object, passable to another function like any other argument. Nothing stops a function from also returning a function as its result:

def shout(func):
    def wrapper(*args, **kwargs):
        result = func(*args, **kwargs)
        return result.upper()
    return wrapper

def greet(name):
    return f"hello, {name}"

loud_greet = shout(greet)     # shout() returns wrapper, a NEW function
loud_greet("an")                # "HELLO, AN" — greet() ran, then .upper() ran around it

shout never calls greet itself when shout(greet) runs — it defines a wrapper, a fresh function that calls func (the function it was handed) and does something extra with the result, then hands wrapper back as an ordinary return value. *args, **kwargs inside wrapper is Day 4's recognition-level syntax finally earning its keep: it lets wrapper accept whatever arguments greet would have taken, without shout needing to know what they are in advance — one shout works for any function, not just greet.

2 · @decorator is sugar for func = decorator(func)

Writing loud_greet = shout(greet) and keeping the plain greet around too is one pattern, but the far more common one is: replace greet itself with the wrapped version, permanently, right where it's defined. That rebind-in-place is exactly what @ spells:

@shout
def greet(name):
    return f"hello, {name}"

greet("an")   # "HELLO, AN" — greet the NAME now points at shout's wrapper

This does exactly the same thing as writing the def normally and then, on the next line, greet = shout(greet) — Python performs that rebind automatically the moment it sees @shout above a def. There is no new runtime concept here, only new syntax for something section 1 already showed working: define greet, call shout with it, and rebind the name greet to whatever comes back — Day 1's binding/rebinding vocabulary applies unchanged. After decoration, calling greet(...) anywhere else in the program calls the wrapper, not the original body, by itself.

3 · Why decorators are everywhere in FastAPI

You have not seen FastAPI yet — that's Phase 2b's job, not today's — but it's worth naming the shape now because you will meet it on day one of that phase and it will already make sense: a FastAPI route looks like this.

@app.get("/users/{id}")
def get_user(id):
    return {"id": id}

@app.get("/users/{id}") is a decorator exactly like @shout above — it takes the get_user function, wraps it with the machinery that registers "when a GET request arrives at this URL, call this function and turn its return value into an HTTP response," and hands back a function that still works if you call it directly in a test. Nothing about that machinery is new today; only the fact that it happens to be a decorator, not a special kind of function, is worth landing now — so that FastAPI's routing does not look like new magic when Phase 2b introduces it, only a very well-chosen wrapper.

4 · A decorator that takes arguments of its own

@app.get("/users/{id}") above has parentheses with an argument inside them — different from plain @shout, which has none. That extra call is a second layer: a function that takes an argument and returns a decorator, which then wraps the target function:

def repeat(times):
    def decorator(func):
        def wrapper(*args, **kwargs):
            result = None
            for _ in range(times):
                result = func(*args, **kwargs)
            return result
        return wrapper
    return decorator

@repeat(3)
def greet(name):
    print(f"hi {name}")

greet("an")   # prints "hi an" three times

Read @repeat(3) in two steps: first repeat(3) runs and returns decorator (a real decorator, taking exactly one function argument, same shape as shout); then that returned decorator is applied to greet, same as @shout was. Three nested functions is the most this course will build today — recognizing this shape when it appears in FastAPI's own decorators (most of which take arguments, like the URL path above) is the goal, not writing one from scratch under pressure.

5 · functools.wraps: keeping the original function's identity

One easy-to-miss side effect: after decoration, greet.__name__ reports "wrapper", not "greet" — the name and docstring of the original function are lost, because wrapper really is a different function object. The standard library fixes this with one more decorator, applied to wrapper itself:

from functools import wraps

def shout(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs).upper()
    return wrapper

@wraps(func) copies func's __name__, docstring, and a few other attributes onto wrapper before it's returned — a small detail, but one every well-behaved decorator in real code includes, precisely because it is itself a decorator (taking func, wrapping wrapper) applied to the function you're already writing.

Where pandas goes from here: pandas doesn't lean on custom decorators the way FastAPI does — this is squarely a language mechanism, not a library one, so there is nothing to contrast today; this callout exists only to note the absence, matching the hard rule above.
