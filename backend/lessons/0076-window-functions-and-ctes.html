Window functions and CTEs: SQL that sees more than one row at a time

MISSION.md says SQL syntax and joins were never in question here — and 75 lessons of WHERE, JOIN, and GROUP BY have proven that true. But one whole shape of query has stayed off the table the entire time: a query that ranks, numbers, or compares a row against its neighbors without collapsing them the way GROUP BY does. That shape has a name, and it's one every backend interview and every "top N per group" feature request will eventually ask for.

1 · The gap GROUP BY can't close

GROUP BY answers "one row per group" — total orders per customer, average price per category. It cannot answer "rank each order within its customer's own order history" and still return every order, because the moment you group, the individual rows are gone. A window function is the fix: it looks across a set of related rows to compute its answer, but keeps every row in the output.

SELECT customer_id, id, created_at,
       ROW_NUMBER() OVER (
           PARTITION BY customer_id
           ORDER BY created_at
       ) AS order_seq
FROM orders;
-- every order row survives; order_seq restarts at 1 for each customer

PARTITION BY is doing the job GROUP BY would do — splitting rows into buckets by customer_id — but instead of collapsing each bucket to one row, OVER (...) tells Postgres "compute this function per row, using only the other rows in its own bucket." ORDER BY inside the parentheses controls the order the function walks the bucket in, which is exactly what ROW_NUMBER() needs to count 1, 2, 3, ....

2 · The functions worth knowing by name

FunctionWhat it returns
ROW_NUMBER()1, 2, 3, ... within the partition — no ties, ever
RANK()same rule as a race: tied rows share a rank, next rank skips ahead
LAG(col) / LEAD(col)the same column's value from the previous / next row in the ordering
SUM()/AVG() OVER (...)any existing aggregate, but per-row instead of per-group — a running total

LAG is the one that solves a problem this course has never had a clean answer for: "how long between this order and the customer's previous one?" Without a window function that's a self-join against a slower row; with one, it's one column:

SELECT customer_id, created_at,
       created_at - LAG(created_at) OVER (
           PARTITION BY customer_id ORDER BY created_at
       ) AS gap_since_last_order
FROM orders;
-- first order per customer: gap_since_last_order is NULL, no previous row exists

3 · The classic use: top N per group

"The 3 most recent orders per customer" is a request-shaped query no plain GROUP BY or LIMIT answers alone — LIMIT caps the whole result set, not each customer's slice of it. ROW_NUMBER() makes it a two-step query: number the rows, then filter on the number. Filtering can't happen in the same SELECT a window function appears in (the numbering has to exist before WHERE can check it), so it needs a place to put the first step's result — which is exactly what a CTE is for.

4 · Naming the intermediate step: CTEs

A CTE (common table expression) is a named subquery declared up front with WITH, so the rest of the query can refer to it by name instead of nesting one query inside another:

WITH ranked AS (
    SELECT customer_id, id, created_at,
           ROW_NUMBER() OVER (
               PARTITION BY customer_id
               ORDER BY created_at DESC
           ) AS rn
    FROM orders
)
SELECT customer_id, id, created_at
FROM ranked
WHERE rn <= 3;
-- the 3 most recent orders per customer, no self-join required

Nothing here is new SQL power a nested subquery couldn't already do — a CTE is a readability feature, not a performance feature. WITH ranked AS (...) names the intermediate step in the order a person actually thinks about the problem ("first number them, then keep the top 3"), instead of forcing that same logic to be read inside-out the way a nested FROM (SELECT ...) AS ranked subquery does.

5 · Where this connects to what Lesson 15 already built

Ties to Lesson 15: keyset/cursor pagination's WHERE (created_at, id) > (...) trick works because rows have a stable, total order — the same property ORDER BY inside a window function's OVER (...) depends on. Lesson 15 never needed a window function because it paginates the whole table; the moment a feature needs pagination or ranking scoped per group — "page through each customer's own orders separately," "show each product's rank within its category" — that's the window-function shape, not the plain cursor shape. Recognizing which one a feature request actually needs is the point, not memorizing more syntax.
