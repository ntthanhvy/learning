1 · The gap: a failed dbt_build currently hides Day 41's own dead-letter table

Day 41 built a real dead-letter table, raw.order_events_dead_letter, specifically so a poison event doesn't wedge the Kafka consumer — it quarantines the bad row and the consumer keeps committing offsets. That table is only useful if something actually looks at it. Today's DAG, as it stands after Day 35, has exactly two tasks: load_raw then dbt_build, connected the default way every Airflow dependency connects — dbt_build only runs if load_raw succeeded, and by the same default rule, anything added downstream of dbt_build would only run if dbt_build itself succeeded.

That default is the exact problem for a health check. If dbt_build fails — a planted bad row, a dropped connection, anything Day 3's tests are built to catch — a task meant to report "here's how many poison events are sitting in the dead-letter table right now" would never run on precisely the run where seeing that number matters most: the one that just failed. The fix isn't a different task. It's a different trigger rule on the one new task.

2 · Confirmed from the installed package: the default really is all_success, and it's a real enum

Reading airflow.task.trigger_rule directly (installed locally via uv run --with "apache-airflow==3.3.1", no live scheduler needed — the same read-the-real-install approach Days 20-22, 25 and 35 already used) turns up a plain string enum, not a magic keyword:

class TriggerRule(str, Enum):
    ALL_SUCCESS = "all_success"
    ALL_FAILED = "all_failed"
    ALL_DONE = "all_done"
    ONE_SUCCESS = "one_success"
    ONE_FAILED = "one_failed"
    NONE_FAILED = "none_failed"
    ... (13 members total, confirmed by listing them live)

Every BaseOperator — every task this course has ever defined, including Day 7's load_raw and dbt_build — carries a trigger_rule attribute that defaults to TriggerRule.ALL_SUCCESS whether or not the DAG author ever mentions it. Confirmed this round by loading the real DAG file and reading each task's own attribute back: dbt_build.trigger_rule came back TriggerRule.ALL_SUCCESS, never set explicitly anywhere in this course, present purely because nothing has overridden it before today.

The three rules worth knowing by name for a working-level portfolio, in plain terms:

  • all_success (the default): run only if every direct upstream task succeeded. What dbt_build has always used, correctly — there is no sane reason to build marts on raw data that failed to load.
  • all_done: run once every direct upstream task has finished, regardless of whether it succeeded, failed, or was skipped. Today's choice for check_dead_letters — a health check that should report the same way whether the run it's reporting on went well or badly.
  • one_failed: run as soon as any one direct upstream task fails, without waiting for the others. The natural rule for a dedicated alerting task in a wider DAG, not needed here since check_dead_letters has only one upstream task.
This is a different problem from Day 35's on_retry_callback. A callback observes one task's own attempts and fires as a side effect — it can't make a different task run. A trigger rule decides whether a downstream task is allowed to start at all, based on its upstream tasks' final states. Day 35 asked "what happens when dbt_build retries"; today asks "what runs next, on purpose, whether dbt_build succeeds or not."

5 · Why a working-level answer needs the name, not just the behavior

"I added a task that always runs" is a description. "I set trigger_rule=all_done because the default all_success would have skipped it as upstream_failed on exactly the runs where a dead-letter count matters most" is the same fact stated with the actual mechanism an interviewer can follow up on. The three rules worth being able to name cold — all_success, all_done, one_failed — cover the large majority of real DAGs; the other ten members of the enum (none_skipped, all_done_min_one_success, and others) exist for narrower shapes this portfolio doesn't need, and naming that they exist without claiming to have used them is itself an honest, working-level answer.

This is the same idempotency bridge Day 7 and Day 35 both already made explicit: check_dead_letters is read-only this round (a COUNT(*), per the TODO), so running it twice on a re-run is automatically safe with no extra design needed — a cheap win from keeping today's new task a query, not a write.
