np.digitize(): the raw-array layer under cut() and qcut()

Yesterday's lesson closed with four standing candidates from a fresh curriculum/glossary scan: np.lexsort(), np.partition()/argpartition(), np.histogram()/np.bincount(), and np.digitize() — named as "the raw-array layer under Lesson 18's qcut() binning." Today picks that one: it continues the same "name the NumPy function underneath an already-taught pandas method" lineage as Lessons 93, 100, 102, 109-112, 114, and 117, and today's own probe turned up a genuinely undocumented silent trap worth flagging.

1 · Same binning job as cut(), one layer closer to the metal

Lesson 12's pd.cut() sorts numeric values into fixed value-edge buckets. np.digitize() is the plain-array function doing that same edge-comparison underneath: given a sorted list of bin edges, it returns one integer bin index per input value, with no labels, no Series, no Index — just a NumPy array of bin numbers. Confirmed directly (numpy 2.5.4, pandas 3.1.0), reusing Lesson 18's own amount slice (An/120.0, Binh/35.5, Binh2/180.0, An2/42.0) and Lesson 12's exact bin edges:

import numpy as np
import pandas as pd

amounts = np.array([120.0, 35.5, 180.0, 42.0])
bins = [0, 40, 100, 200]

np.digitize(amounts, bins)
# array([3, 1, 3, 2])  -- one bin index per value, no labels attached

pd.cut(pd.Series(amounts), bins=bins, labels=False)
# 0    2
# 1    0
# 2    2
# 3    1
# dtype: int64  -- SAME buckets, but 0-indexed instead of 1-indexed

Confirmed directly: np.digitize(x, bins) - 1 is element-for-element identical to pd.cut(x, bins=bins, labels=False) on every in-range value — pd.cut() really is np.digitize() wrapped with a category dtype, 0-indexed labels, and (as Section 4 shows) real missing-value handling layered on top.

2 · The index convention: 0 and len(bins) are reserved for out-of-range

Confirmed directly: with bins = [0, 40, 100, 200] (4 edges, 3 intervals), an in-range value gets index 1, 2, or 3 — bin 1 is "between edges 0 and 1" (0 <= x < 40), and so on. Index 0 is reserved for "below every edge," and len(bins) (here, 4) is reserved for "above every edge" — not an error, a real sentinel value that the index can legitimately take:

np.digitize(np.array([-5.0]), bins)
# array([0])  -- below the first edge (0)

np.digitize(np.array([250.0]), bins)
# array([4])  -- above the last edge (200); len(bins) == 4

This is the first thing worth saying out loud in an interview: unlike pd.cut(), which returns NaN for any value outside every bin's range, np.digitize() never returns a missing marker for an out-of-range value — it always returns a valid-looking integer, which downstream code must know how to interpret.

3 · right=: which edge of each bin is inclusive

Confirmed directly against the official NumPy docs: right=False (the default) treats each bin as bins[i-1] <= x < bins[i] — the left edge included, the right edge excluded. right=True flips it to bins[i-1] < x <= bins[i] — right edge included instead. The two only disagree exactly at a boundary value:

np.digitize(np.array([40.0]), bins)
# array([2])  -- right=False (default): 40 is ">= 40", so it joins the NEXT bin up

np.digitize(np.array([40.0]), bins, right=True)
# array([1])  -- right=True: 40 is "<= 40", so it stays in the bin ENDING at 40

Confirmed directly: bins must be monotonically increasing or monotonically decreasing (descending edges are explicitly supported, reversing the index order) — anything else raises ValueError: bins must be monotonically increasing or decreasing immediately, no silent misbehavior.

4 · The trap: NaN gets a real bin index, silently, with no warning

Confirmed directly, and confirmed absent from the official docs page (no mention of NaN handling at all): a NaN value passed to np.digitize() is silently placed in the "above every edge" bucket (len(bins)), the same code a genuinely huge number would get — no exception, no warning, no distinguishable marker: 
vals = np.array([np.nan, 50.0])

np.digitize(vals, bins)
# array([4, 2])  -- the NaN silently lands in bin 4, same code as a too-large value

pd.cut(pd.Series(vals), bins=bins, labels=False)
# 0    NaN
# 1    1.0
# dtype: float64  -- pd.cut() correctly keeps NaN as NaN, no fake bin assignment

This is the sharp, genuinely interview-relevant gotcha: every comparison against NaN is False (the same rule Lesson 117's np.isclose() traded on), so NaN never satisfies "less than this edge" for any edge — it falls through every comparison and lands in the final, catch-all bucket by construction, indistinguishable from a legitimately huge value. Anyone hand-rolling a binning pass with np.digitize() on real data (which always has some missing values) must check for NaN before calling it, or filter/mask bin index len(bins) afterward knowing it might mean "missing" rather than "huge" — pd.cut() (built on top of this exact function) is the one that already handles this correctly, which is reason enough to reach for pd.cut() directly whenever labels or NaN-safety matter and drop to np.digitize() only when a plain NumPy pipeline has no pandas involved at all.

5 · Works directly on a Series, same as recent lessons' NumPy functions

Confirmed directly: np.digitize() accepts a pandas Series for x with no .to_numpy() conversion needed first (same ease as np.isclose() in Lesson 117, unlike the AttributeError traps Lessons 110/112 found calling cummax()/.ravel() the other direction) — and, like np.percentile() (Lesson 111) and np.piecewise() (Lesson 116), it always hands back a plain ndarray, dropping the Index entirely:

s = pd.Series([120.0, 35.5, 180.0, 42.0], index=["An", "Binh", "Binh2", "An2"])

np.digitize(s, bins)
# array([3, 1, 3, 2])  -- plain ndarray; the "An"/"Binh"/... Index is gone
