Testing endpoints with httpx

Every FastAPI practice file since Day 16 has quietly built a TestClient and called it from inside a lambda — that machinery was never explained, just used. Today it gets a name and a real treatment: fastapi.testclient.TestClient is a thin wrapper around httpx, the same library Day 20 used to drive concurrent requests, aimed here at writing test_* functions that call routes in-process — no running server, no network — and assert on the status code and JSON body exactly the way Day 11's pytest already taught.

Bridge from SQL: this is the same discipline as a query-result assertion suite run after a schema migration — "hit this endpoint with this input, the response must be exactly this status and this body, every time." TestClient just gives Python handlers the same repeatable check a saved SELECT + expected-rows comparison gives a schema change.

1 · TestClient is httpx, talking to your app without a network

A real client sends bytes over a socket to a running server. TestClient(app) skips the socket entirely — it hands each request straight to app in the same process via a ASGI interface FastAPI already speaks, and gets the response straight back, no bytes serialized in between:

from fastapi import FastAPI
from fastapi.testclient import TestClient

app = FastAPI()

@app.get("/users/{user_id}")
def get_user(user_id: int):
    return {"user_id": user_id, "name": "an"}

client = TestClient(app)
response = client.get("/users/1")
print(response.status_code)   # 200
print(response.json())        # {'user_id': 1, 'name': 'an'}

TestClient is literally built on httpx.Client — same .get()/.post()/.status_code/.json() shape Day 16 through 21's practice files already called without a second thought, and the exact same httpx package Day 20 used for AsyncClient against a live event loop. Nothing about the request/response vocabulary is new today — what's new is turning those calls into named, repeatable assert-backed tests instead of one-off checks.

2 · A test_* function, the Day 11 shape aimed at a route

Day 11 established the whole convention: any function named test_*, in a file named test_*, is a test pytest finds and runs, and a plain assert inside it is the entire mechanism. An endpoint test is that same function, just calling client.get(...)/client.post(...) instead of a plain function directly:

# test_users.py
from fastapi.testclient import TestClient
from myapp import app

client = TestClient(app)

def test_get_user_returns_200_and_the_right_body():
    response = client.get("/users/1")
    assert response.status_code == 200
    assert response.json() == {"user_id": 1, "name": "an"}

def test_get_missing_user_returns_404():
    response = client.get("/users/999")
    assert response.status_code == 404

Building client = TestClient(app) once, module-level, and reusing it across every test_* function is the standard shape — it costs nothing per call (no real connection ever opens) and matches every practice file since Day 16 already doing exactly this, just without a name for it. Run with the same command Day 11 taught: uv run --with pytest --with fastapi --with httpx pytest test_users.py -v.

3 · Asserting the shape of a response, not just one field

A route test is only as good as what it checks. Checking only status_code misses a handler that returns 200 with the wrong body; checking the whole body with == is strict but brittle the moment a new optional field is added. Both are legitimate choices depending on what's being tested — status code plus a couple of specific keys is the common middle ground:

def test_create_user_returns_201_with_a_new_id():
    response = client.post("/users", json={"name": "chi"})
    body = response.json()
    assert response.status_code == 201
    assert body["name"] == "chi"
    assert "user_id" in body

client.post(path, json=...) is Day 18's request body all over again — json= serializes the dict and sets the right content-type header, the exact same thing a real client does, just without a socket. And Day 17's pydantic validation still runs on every test call: POST a body missing a required field and the response really is a 422, the same status code a live client would get — TestClient exercises the real handler and the real validation, not a mock of either.

4 · Recognition: errors, middleware, and going live are the same app, seen from outside

Three ideas this course won't build today but that a deployable FastAPI app needs, briefly named so they're recognizable later: an exception handler (@app.exception_handler(SomeException)) turns a raised exception into a chosen JSON response for every route at once, instead of every handler catching it individually — testable the same way as any other route, by asserting the status code an endpoint returns when it deliberately raises that exception; middleware (@app.middleware("http")) wraps every request/response passing through the app for cross-cutting work — logging, timing, adding a header — without touching each handler; and a ASGI server like uvicorn is what actually runs the app in production, started once with a fixed worker count rather than the auto-reloading dev command. None of this changes how a route is tested — TestClient exercises exception handlers and middleware exactly like it exercises a plain handler, because both run as part of the same ASGI call it's already driving.

Where pandas goes from here: testing a pandas pipeline means asserting on a DataFrame's shape or values after a transform runs — no client, no status code, no request at all; TestClient is specifically for the request/response contract of a running service, a different thing to verify than "did this transform produce the right table."
