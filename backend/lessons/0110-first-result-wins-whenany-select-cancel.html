First result wins: Task.WhenAny and Go's select, minus the losers

Lessons 108 and 109 both waited for every fan-out task to finish, bounded or not. Some calls don't need that: ask three cache replicas for the same key and take whichever answers first, or race a slow primary against a fast fallback. That's a different shape — "first one back wins, the rest become pointless" — and it's the exact gap Lesson 108's own Scope line and Lesson 109's own Scope line both flagged as still open: Task.WhenAny's manual cancellation pattern. Today's lesson closes it, in C# and in Go.

1 · Why this isn't just WhenAll with fewer tasks

Lesson 108's errgroup/Task.WhenAll shape answers "did all of these succeed, or what's the first error?" This lesson answers a different question: "which one finished first, and can I stop paying for the rest?" The two shapes often get confused because both start by launching several concurrent calls — but WhenAll is wrong here. Waiting for all three cache replicas when the first answer is already usable just adds the slowest replica's latency to every request, for no benefit.

2 · C#: Task.WhenAny tells you who won, and nothing else

Per Microsoft's own docs, Task.WhenAny resolves the instant the fastest of its input tasks finishes:

var cts = new CancellationTokenSource();
var tasks = replicas.Select(r => FetchAsync(r, cts.Token)).ToList();

var winner = await Task.WhenAny(tasks);
cts.Cancel();                 // tell the losers to stop, they won't on their own
var value = await winner;    // unwrap: rethrows if the winner itself faulted

The catch is in Microsoft's own wording, called out as a documented tip on the API page: "when the method returns the first completed task, the other tasks will continue running until completion, even if any of them completed in the Canceled or Faulted state. If that behavior is undesirable, you can cancel all the remaining tasks once the first task completes." WhenAny only tells you who won — it does nothing to the losers. Skip the cts.Cancel() line and all three replica calls keep running to completion anyway, wasting the connections and the downstream load exactly like an unbounded fan-out from Lesson 109, just shaped as "pick one" instead of "wait for all."

3 · Go: select plus a shared context.WithCancel does the same job natively

Go's answer isn't a library method at all — it's select over a channel, combined with the context.WithCancel Lesson 41 already introduced. Each racer writes its answer to one shared channel; whichever write lands first is read by the one select waiting on it, and cancel() tells every goroutine still running to stop:

func firstReply(parent context.Context, replicas []string) (Result, error) {
    ctx, cancel := context.WithCancel(parent)
    defer cancel()               // always cancel: releases every loser the instant we return

    out := make(chan Result, len(replicas))
    for _, r := range replicas {
        r := r
        go func() {
            if v, err := fetch(ctx, r); err == nil {
                select {
                case out <- v:
                case <-ctx.Done():     // someone else already won; drop this result
                }
            }
        }()
    }

    select {
    case v := <-out:
        cancel()                    // winner found: stop every other goroutine now
        return v, nil
    case <-parent.Done():
        return Result{}, parent.Err()
    }
}

Each racing goroutine must itself check ctx.Done() (inside fetch, and in the select guarding the channel write) to actually stop early — cancel() only flips a signal, same as Lesson 41 and Lesson 108 already established; nothing is forcibly killed. The real difference from C# isn't the mechanism, it's the defaults: Go has no "WhenAny that forgets to cancel" trap, because there's no library call to reach for in the first place — cancellation is wired by hand either way, so it's never missing by omission.

Not Lesson 108's fail-fast cancellation: Lesson 108's errgroup cancels siblings on the first error, to stop wasted work after a failure. This lesson cancels siblings on the first success, to stop wasted work after a win. Same mechanism (a derived, cancellable context), opposite trigger.

Scope line

This lesson covers the first-result-wins shape: Task.WhenAny plus manual cancellation in C#, and select over a result channel plus context.WithCancel in Go. It does not cover: timeout/deadline patterns for a single call (context.WithTimeout, CancellationTokenSource's own timeout constructor — Lesson 41 already covers the Go half; the full side-by-side is a natural next lesson); retry-with-backoff composed on top of a race (Lesson 32's territory, one layer below this one); or racing more than one *kind* of result where the loser's partial work must be rolled back, not just dropped — a transactional concern out of scope here.
