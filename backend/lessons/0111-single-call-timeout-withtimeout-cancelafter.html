One call, one deadline: context.WithTimeout vs CancellationTokenSource's timeout

Lessons 108–110 were all about racing or bounding several concurrent calls. Today is the simpler, far more common case underneath all of them: one call, one deadline — "don't let this take longer than N seconds." Lesson 41 already named the Go half of this (context.WithTimeout) back in August. The C# half — CancellationTokenSource's own timeout constructor — was flagged as an open gap by both Lesson 110's and Lesson 109's own Scope lines and never shown. Today closes it, side by side.

1 · The problem one call has, that fan-out doesn't

Every pattern since Lesson 108 assumed multiple concurrent operations — all of them, the first one, or a capped number. Most calls in a real backend aren't that: a handler calls one downstream HTTP service, or runs one query, and needs exactly one guarantee — "give up and return an error after N seconds, instead of hanging forever if the other side never answers." That's not fan-out logic at all. It's a plain deadline attached to a single call, and both ecosystems have a dedicated, minimal shape for it.

2 · Go: context.WithTimeout, already named, now the main character

Lesson 41 introduced context.WithTimeout in passing, as one of two things a context can carry. Per pkg.go.dev's own doc comment, it is literally defined as WithDeadline(parent, time.Now().Add(timeout)) — a convenience wrapper that turns a duration into an absolute point in time:

func fetchPricing(parent context.Context, sku string) (Price, error) {
    ctx, cancel := context.WithTimeout(parent, 3*time.Second)
    defer cancel()  // always: releases the timer even if the call finishes early

    return callPricingService(ctx, sku)
}

If callPricingService respects ctx (checks ctx.Done(), or passes it into an HTTP request so the client aborts the socket on cancellation), the call returns with ctx.Err() — context.DeadlineExceeded — the instant 3 seconds pass, whether or not the pricing service ever answers. Nothing races, nothing forks a goroutine: it's the same single call chain Lesson 41 described, just with a shorter leash than the one the caller handed in.

3 · C#: CancellationTokenSource's own timeout constructor does the same job

Lesson 109 used CancellationTokenSource paired with a SemaphoreSlim for width, and Lesson 110 used it paired with Task.WhenAny for racing. Both times, the token source was created plain and cancelled by hand. Per Microsoft's own docs, there is a constructor overload that needs no hand-written cancel call at all: pass a TimeSpan (or a millisecond count) and the source cancels itself once that delay elapses — "the countdown...starts during the call to the constructor. When the delay expires, the constructed CancellationTokenSource is canceled, if it has not been canceled already":

async Task<Price> FetchPricingAsync(string sku)
{
    using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(3));
    return await CallPricingServiceAsync(sku, cts.Token);
    // if 3s pass before this returns, cts.Token is cancelled on its own --
    // CallPricingServiceAsync must itself observe the token to actually stop
}

There's also a method version for a timeout decided after construction: CancelAfter() (cts.CancelAfter(TimeSpan.FromSeconds(3))) arms the same countdown on a plain CancellationTokenSource(), and per the same docs page, calling CancelAfter again before it fires resets the countdown rather than stacking a second one — useful for a "reset the clock on every heartbeat" shape, out of scope for today's single-call case but worth knowing the method exists.

Same catch as Lesson 110, one layer down. Neither context.WithTimeout nor the timeout constructor stops anything by itself — they only flip a signal (close a channel; cancel a token) once the clock runs out. The downstream call still has to check ctx.Done() or the token, the same cooperative-cancellation fact Lessons 41, 108, 109, and 110 have each independently relied on. A call that ignores its context/token entirely will keep running past its own deadline, deadline or not.

Scope line

This lesson covers attaching a deadline to a single call: Go's context.WithTimeout (first named in Lesson 41, elaborated here) and C#'s CancellationTokenSource(TimeSpan) constructor plus CancelAfter(). It does not cover: racing multiple calls and keeping the fastest (Lesson 110's Task.WhenAny/select territory); retry-with-backoff after a timeout fires (Lesson 32's territory — a timeout tells you to give up on this attempt, not whether to try again); or choosing the right duration for a given downstream service, which is an operational-tuning judgment call, not a mechanism.
