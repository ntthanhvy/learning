Day 4 — functions, key=. In sorted(sales, key=lambda row: row["amount"]), what does sorted actually do with the key function?

Fold-out answer: calls it once per item, and orders the items by whatever it returns — not by comparing the items themselves. row["amount"] is never compared to another whole row dict; each row's key result becomes the value actually compared, which is exactly what makes sorting by one field of a larger structure possible at all.

Day 6 — files & with. If an exception is raised partway through a with open(path) as f: block's body, does f still get closed?

Fold-out answer: yes, always. with's whole guarantee is that __exit__ — which closes the file — runs whether the block ends normally or via an exception, unlike a manual f = open(...) / ... / f.close() sequence, where an exception between those two lines skips the close() call entirely and leaks the handle.

Day 9 — modules & imports. A program has two separate import parsing statements, in two different files. How many times does parsing.py's top-level code actually run?

Fold-out answer: once. The first import anywhere in the program runs the module's code top to bottom and caches the result; every later import parsing, anywhere else, reuses that same cached module instead of re-running the file.

Day 13 — pathlib. What does the / operator do between two Path pieces, and why isn't that "division" a contradiction?

Fold-out answer: it joins them into one new Path, using whatever separator is correct for the operating system actually running the code. It isn't a contradiction because Python always asks the object on the left of an operator what that operator means — the same reason + concatenates two strings but adds two numbers; Path simply defines / to mean "join," not division.

Day 20 — async/await. A plain blocking call like time.sleep() is placed inside an async def route handler. Does Python raise an error?

Fold-out answer: no — nothing raises. The call simply never awaits anything, so it never yields control back to the event loop, and every other in-flight request sits frozen until it finishes. Confirmed in Day 20 by timing five concurrent requests: a genuinely async version came back in ~0.05s total, the same call written as a blocking time.sleep() inside async def took ~0.25s — fully serialized, with no error anywhere to flag the mistake.

Day 36 — functools. Why is @functools.lru_cache unsafe to put on a function that reads the current time or hits a database?

Fold-out answer: lru_cache only works correctly on a pure function — one whose result depends only on its arguments. A cache keyed on arguments has no way to notice that the clock moved or the database changed between two calls with the same arguments; it silently serves the first answer forever instead of a fresh one, which is worse than not caching at all because nothing signals the staleness.
