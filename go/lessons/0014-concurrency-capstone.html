1 · The component: clicks come in a firehose, the database wants batches

Every redirect linkshort serves is a click event. Writing one INSERT per click melts the database under load — the standard production shape is write-behind batching: accumulate counts in memory, flush them as one grouped write. A correct batcher needs three flush triggers, and each one maps to a select case you already know:

  • Size — the batch hit maxBatch events: flush now, don't let memory grow unbounded.
  • Time — a time.Ticker fired: flush whatever's there, so a quiet trickle still reaches the database promptly.
  • Shutdown — ctx.Done(): drain what's buffered, flush one last time, exit clean. Losing accepted clicks at shutdown is the bug.

Where do the counts live? In a plain map[string]int — with no mutex. This is the Day 8 judgment call, resolved the other way this time: exactly one goroutine (Run) ever touches the batch map, and every other goroutine talks to it only by sending on a channel. Share memory by communicating. Compare: Day 8's ClickCounter needed a mutex precisely because many goroutines read and write it in place. Same data shape, opposite ownership, opposite tool — that contrast is an interview answer in itself.

2 · The seam: a one-method Sink

Where do batches go? The aggregator doesn't know, on purpose — it declares a sink interface with one method, consumer-defined, Day 1's rule verbatim:

type Sink interface {
    Flush(ctx context.Context, batch map[string]int) error
}

Tests hand it a fakeSink that just records batches in a slice; production would hand it a PostgresSink whose Flush is one multi-row INSERT INTO clicks inside a transaction (Day 6's material — a good post-course exercise). The aggregator never changes. Note the fake needs a mutex where the aggregator doesn't: the test goroutine reads the recorded flushes while Run's goroutine appends to them — two goroutines, shared slice, Day 8's exact criterion.

3 · Two production decisions worth saying out loud

Backpressure: this one drops. Add is called from the redirect hot path — the handler serving a user. Should a full buffer make the user's redirect wait? For click analytics, no: a lost count beats a slow redirect. So Add uses select-with-default — the non-blocking send from Day 9 — and applies a drop policy: reject the event, count it in an atomic.Int64 (Day 12: one loose counter touched from many goroutines and related to nothing else — the atomic shape, not the mutex shape). Contrast deliberately with Day 9's checker, where the unbuffered jobs channel blocking the feeder was the backpressure we wanted. Same primitive, opposite policy, chosen per component — that's the judgment interviewers probe.

Shutdown: drain, then flush with a context that ignores the cancel. When ctx.Done() fires, events that Add already accepted are still sitting in the channel — abandoning them breaks the component's promise, so the exit path drains the buffer (Day 9's word) into the batch and flushes once more. But there's a trap: that final Flush takes a context, and the only one in hand is already cancelled — a real PostgresSink would see the dead context and refuse the write. Go 1.21 added the tool for exactly this: context.WithoutCancel, a context that survives its parent's cancellation for cleanup that must complete. And one contract, same spirit as "the sender owns the close": producers stop calling Add before the owner is cancelled — events added after cancel may never be flushed. The shutdown-order habit from Day 11 applies to components, not just channels.

Step 1 — new file link/aggregator.go:

package link

import (
    "context"
    "sync/atomic"
    "time"
)

// Sink is where finished batches go. Consumer-defined, one method —
// Day 1's rule: the aggregator declares what it needs, not who provides it.
type Sink interface {
    Flush(ctx context.Context, batch map[string]int) error
}

// Aggregator turns a firehose of single click events into periodic batched
// writes. One goroutine (Run) owns the batch map outright — no mutex, because
// no sharing: every other goroutine talks to it only through the channel.
type Aggregator struct {
    sink     Sink
    interval time.Duration
    maxBatch int

    events  chan string
    dropped atomic.Int64
}

func NewAggregator(sink Sink, interval time.Duration, maxBatch, buffer int) *Aggregator {
    return &Aggregator{
        sink:     sink,
        interval: interval,
        maxBatch: maxBatch,
        events:   make(chan string, buffer),
    }
}

// Add records one click. It never blocks the caller: if the buffer is full,
// the event is dropped and counted instead. Reports whether it was accepted.
func (a *Aggregator) Add(code string) bool {
    select {
    case a.events <- code:
        return true
    default:
        a.dropped.Add(1)
        return false
    }
}

// Dropped reports how many events a full buffer has rejected so far.
func (a *Aggregator) Dropped() int64 { return a.dropped.Load() }

// Run is the owner goroutine: it loops until ctx is cancelled, then drains
// what Add already accepted, flushes one last time, and returns. Callers must
// stop calling Add before cancelling ctx — same rule as "senders own the
// close": the producer side goes quiet first, then the owner shuts down.
func (a *Aggregator) Run(ctx context.Context) error {
    ticker := time.NewTicker(a.interval)
    defer ticker.Stop()

    batch := make(map[string]int)
    total := 0

    flush := func(fctx context.Context) error {   // GIVEN — flushes batch to the sink, resets it
        if total == 0 {
            return nil
        }
        if err := a.sink.Flush(fctx, batch); err != nil {
            return err
        }
        batch = make(map[string]int)
        total = 0
        return nil
    }

    for {
        select {
        // TODO 1: the two missing live cases —
        //   case code := <-a.events: count it into batch (batch[code]++,
        //     total++); if total has reached a.maxBatch, flush(ctx) and
        //     return any non-nil error it gives back.
        //   case <-ticker.C: flush(ctx), same error handling.

        case <-ctx.Done():
            // TODO 2: BEFORE the final flush below, drain the buffer —
            //   loop a nested select: case code := <-a.events counts it
            //   into batch (total++); default means the buffer is empty,
            //   stop looping. (Sections 1 and 3 explain the drain and why
            //   the final flush gets a WithoutCancel context.)
            return flush(context.WithoutCancel(ctx))
        }
    }
}

The file compiles as-is (an owner loop that only knows how to shut down), and the tests tell you what's missing: without TODO 1 nothing ever flushes mid-run, and without TODO 2 TestAggregatorShutdownLosesNothing reports exactly the clicks the drain would have saved.

Step 2 — new file link/aggregator_test.go (given in full — each test pins one of the design decisions from Sections 1–3):

package link

import (
    "context"
    "errors"
    "maps"
    "sync"
    "testing"
    "time"
)

// fakeSink records every flush it receives — mutex-guarded, because the test
// goroutine reads it while Run's goroutine writes it (Day 8's exact shape).
type fakeSink struct {
    mu      sync.Mutex
    flushes []map[string]int
}

func (f *fakeSink) Flush(ctx context.Context, batch map[string]int) error {
    f.mu.Lock()
    defer f.mu.Unlock()
    f.flushes = append(f.flushes, maps.Clone(batch))
    return nil
}

func (f *fakeSink) totalFor(code string) int {
    f.mu.Lock()
    defer f.mu.Unlock()
    n := 0
    for _, b := range f.flushes {
        n += b[code]
    }
    return n
}

func waitFor(t *testing.T, cond func() bool) {
    t.Helper()
    deadline := time.Now().Add(2 * time.Second)
    for time.Now().Before(deadline) {
        if cond() {
            return
        }
        time.Sleep(5 * time.Millisecond)
    }
    t.Fatal("condition never became true within 2s")
}

func TestAggregatorFlushesWhenBatchFills(t *testing.T) {
    sink := &fakeSink{}
    a := NewAggregator(sink, time.Hour, 5, 64) // interval never fires — only size can flush
    ctx, cancel := context.WithCancel(context.Background())
    done := make(chan error, 1)
    go func() { done <- a.Run(ctx) }()

    for range 5 {
        if !a.Add("go") {
            t.Fatal("Add rejected an event with buffer room to spare")
        }
    }
    waitFor(t, func() bool { return sink.totalFor("go") == 5 })
    cancel()
    if err := <-done; err != nil {
        t.Fatalf("Run returned %v", err)
    }
}

func TestAggregatorFlushesOnInterval(t *testing.T) {
    sink := &fakeSink{}
    a := NewAggregator(sink, 20*time.Millisecond, 1000, 64) // batch never fills — only time can flush
    ctx, cancel := context.WithCancel(context.Background())
    defer cancel()
    done := make(chan error, 1)
    go func() { done <- a.Run(ctx) }()

    a.Add("go")
    a.Add("go")
    a.Add("rust")
    waitFor(t, func() bool { return sink.totalFor("go") == 2 && sink.totalFor("rust") == 1 })
}

func TestAggregatorShutdownLosesNothing(t *testing.T) {
    sink := &fakeSink{}
    a := NewAggregator(sink, time.Hour, 1000, 256) // neither trigger fires — only shutdown can flush
    ctx, cancel := context.WithCancel(context.Background())
    done := make(chan error, 1)
    go func() { done <- a.Run(ctx) }()

    const n = 100
    var wg sync.WaitGroup
    for range 4 {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for range n / 4 {
                a.Add("go")
            }
        }()
    }
    wg.Wait() // producers go quiet FIRST…
    cancel()  // …then the owner is told to shut down
    if err := <-done; err != nil {
        t.Fatalf("Run returned %v", err)
    }
    if got := sink.totalFor("go"); got != n {
        t.Fatalf("lost clicks at shutdown: flushed %d, want %d", got, n)
    }
    if a.Dropped() != 0 {
        t.Fatalf("dropped %d events with a roomy buffer", a.Dropped())
    }
}

func TestAggregatorAddNeverBlocks(t *testing.T) {
    a := NewAggregator(&fakeSink{}, time.Hour, 1000, 2) // tiny buffer, Run deliberately NOT started
    if !a.Add("a") || !a.Add("b") {
        t.Fatal("buffer should hold the first two events")
    }
    if a.Add("c") {
        t.Fatal("third Add should be rejected immediately, not block")
    }
    if a.Dropped() != 1 {
        t.Fatalf("Dropped() = %d, want 1", a.Dropped())
    }
}

var errSinkDown = errors.New("sink down")

type failingSink struct{}

func (failingSink) Flush(context.Context, map[string]int) error { return errSinkDown }

func TestAggregatorSurfacesFlushErrors(t *testing.T) {
    a := NewAggregator(failingSink{}, time.Hour, 1, 8)
    ctx, cancel := context.WithCancel(context.Background())
    defer cancel()
    done := make(chan error, 1)
    go func() { done <- a.Run(ctx) }()

    a.Add("go") // maxBatch=1: the first event forces a flush, which fails
    select {
    case err := <-done:
        if !errors.Is(err, errSinkDown) {
            t.Fatalf("Run returned %v, want errSinkDown", err)
        }
    case <-time.After(2 * time.Second):
        t.Fatal("Run never returned — the failing flush was never attempted")
    }
}

func BenchmarkAggregatorAdd(b *testing.B) {
    a := NewAggregator(&fakeSink{}, time.Millisecond, 1024, 4096)
    ctx, cancel := context.WithCancel(context.Background())
    defer cancel()
    go func() { _ = a.Run(ctx) }()
    b.RunParallel(func(pb *testing.PB) {
        for pb.Next() {
            a.Add("go")
        }
    })
}

5 · Interview drills: say it out loud, under pressure

Set a timer: 60–90 seconds per answer, spoken aloud, no notes. Then open the model answer and compare — not for wording, for whether you hit the load-bearing points. Doing each drill a second time in Vietnamese is worth it: explaining Go bằng tiếng Việt cho đồng nghiệp is a real workplace skill, not a lesser version of the English one.

Drill 1 — "When would you use a channel, and when a mutex?"

Load-bearing points: it's about ownership, not fashion. If one goroutine can own the data and others interact through messages, use a channel (today's batch map — no lock anywhere). If many goroutines must touch shared data in place, guard the invariant with a mutex (Day 8's ClickCounter, the fake sink's slice). Bonus: name the third option — atomic for a single independent value like today's dropped counter.

Drill 2 — "Explain how cancellation actually stops your goroutines."

Load-bearing points: cancelling a context does nothing by itself — it closes a channel (ctx.Done()). Goroutines stop only where they watch that channel, so every blocking send/receive needs a select with a ctx.Done() case (Day 10's cancellation-aware select). Miss one and that goroutine leaks. Mention errgroup.WithContext for "one fails, cancel the rest", and today's twist: cleanup that must outlive the cancel gets context.WithoutCancel.

Drill 3 — "Your service leaks goroutines in production. Walk me through finding it."

Load-bearing points: leaks are silent — the runtime only crashes on a full deadlock. Watch runtime.NumGoroutine() before/after an operation in a test (Day 11's leak test), or grab the goroutine profile via pprof in production and look for hundreds of stacks parked on the same line — that line is the unguarded send/receive. -race won't find leaks (it finds races); the fix is almost always a missing ctx.Done() case or an unclosed channel.

Drill 4 — "Design a component that batches writes to a database."

Load-bearing points: today's whole build — one owner goroutine holding the batch (no lock), a channel in front of it, three flush triggers (size, ticker, shutdown), and two named policies: backpressure (drop-and-count on the hot path — the caller must never stall for analytics) and shutdown (producers quiet first, drain the channel, final flush on a non-cancellable context so accepted data isn't lost). If you can also say what the tests pin — nothing lost at shutdown, Add never blocks — you've answered at a senior level.

Drill 5 — "What does select do when multiple cases are ready? When none are?"

Load-bearing points: multiple ready → one is chosen uniformly at random (no priority — that randomness is why the ticker still gets its turn under load). None ready → select blocks until one is, unless there's a default, which runs immediately — the non-blocking send powering today's Add and the drain loop's "buffer is empty" exit.
