1 · Six questions, in the original teaching order

Answer each out loud or on paper before reading the fold-out answer. If one is shaky, note it and go fix it in the practice file below rather than only rereading the old lesson.

Day 46 — f-strings and the format spec. After running label = f"{price:.2f}", what has happened to price itself, and why?

Fold-out answer: nothing — price is still the exact same original float. The format spec after the colon only controls how a value renders into the new string; it never mutates the object being formatted, the same way ROUND(price, 2) in a SQL SELECT never touches the stored row. label is a brand-new string holding the rendered text; price was only ever read, not written.

Day 50 — abstract base classes. A subclass of an abc.ABC forgets to override an @abstractmethod. When, exactly, does Python raise an error, and how is that different from a plain raise NotImplementedError convention?

Fold-out answer: immediately, at instantiation — BrokenPayment() raises TypeError the instant it's constructed, naming the specific missing method, before any call ever happens. A plain raise NotImplementedError inside an ordinary base-class method is only a convention: the subclass instantiates fine, and the mistake only surfaces the moment something eventually calls the missing method — which could be far later, in production. The ABC turns a call-time surprise into a construction-time guarantee.

Day 51 — heapq & bisect. Why does heapq.heappop() stay O(log n) per call instead of needing a full O(n log n) re-sort, when the list isn't actually kept fully sorted?

Fold-out answer: a heap only maintains the weaker "each parent ≤ its children" property, not full sorted order — just enough structure to guarantee the smallest element sits at index 0, and just little enough that fixing that property after one push or pop only costs a walk up or down one path of the tree, O(log n), rather than reordering the whole collection. Sorting the whole list on every insert would repeat O(n log n) work that a heap deliberately avoids by never fully sorting in the first place.

Day 53 — collections.deque & namedtuple. Why is list.pop(0) slow on a long list while deque.popleft() stays cheap regardless of length?

Fold-out answer: a plain list stores its elements contiguously, so removing the first one means every remaining element has to shift left by one slot — O(n) work per call, growing with the list's length. A deque is built as a structure where both ends are equally cheap to add to or remove from, O(1), regardless of length — the trade is that random access into the middle stays O(n) on a deque too, same as a list, so a deque only wins when the two ends are actually what matters.

Day 54 — the random module. Why does calling random.seed(42), then a sequence of random calls, twice in a row, produce the identical sequence both times — and why does that matter for testing?

Fold-out answer: random's output isn't truly random — it's produced by a deterministic algorithm driven by a starting number, the seed. Calling seed(42) resets that starting point to the exact same value each time, so every call that follows reproduces the identical sequence, in order. That's what lets a test assert on a specific "random" result instead of writing a weaker test like "the length didn't change" — without seeding first, the same assertion would be flaky, passing or failing by chance from run to run.

Day 56 — the operator module. itemgetter("city", "amount") works as a sort key equivalent to ORDER BY city, amount. What does passing itemgetter two names actually return, and why does that make it work as a multi-column key?

Fold-out answer: it returns a callable that, given a row, returns a tuple of both values — (row["city"], row["amount"]) — instead of a single value. Python compares tuples element by element, left to right, only falling through to the second element when the first ties, which is exactly the "sort by this column, then break ties with that column" behavior ORDER BY city, amount describes. One itemgetter call with several keys is a shorter way to build the same tuple a hand-written lambda row: (row["city"], row["amount"]) would.
