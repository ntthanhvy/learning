add_prefix() and add_suffix(): renaming a whole axis at once

Lesson 54's own teaser named two remaining zero-hit candidates from its fresh curriculum/glossary scan: add_prefix()/add_suffix() and json_normalize(). This round picks add_prefix()/add_suffix(): a self-contained, single-concept pair of column-renaming utilities that come up directly after a groupby().agg() or pivot_table() call (Lesson 4 and Lesson 6) produces awkward multi-function or generic column names — a genuinely common real-world next step this course hadn't covered yet.

Recap, in one line

Lesson 4's groupby().agg(["sum", "mean", "count"]) and Lesson 6's pivot_table() both produce columns named after the aggregate function alone — sum, mean, count — with no hint of which source column they came from once several aggregated tables get merged together. add_prefix() and its mirror, add_suffix(), fix that in one call — no per-column rename map required.

1 · The basic shape

Called with no other arguments, both stamp every column label with the given string — pure string concatenation, nothing fancier:

clean.columns.tolist()
-- ['order_id', 'customer', 'amount', 'order_date']
clean.add_prefix("raw_").columns.tolist()
-- ['raw_order_id', 'raw_customer', 'raw_amount', 'raw_order_date']
clean.add_suffix("_v1").columns.tolist()
-- ['order_id_v1', 'customer_v1', 'amount_v1', 'order_date_v1']

Confirmed directly: like almost every pandas method, both return a new object and leave the original untouched — no inplace= surprise. The one-liner alternative, df.rename(columns=lambda c: "raw_" + c), does the identical job but needs a lambda; add_prefix()/add_suffix() exist purely so the everyday case doesn't need one.

2 · The real payoff: after groupby().agg() with multiple functions

Running several aggregate functions on one column at once (Lesson 4) produces columns named only after the function, with no trace of which source column they summarize:

clean.groupby("customer")["amount"].agg(["sum", "mean", "count"])
--             sum    mean  count
-- customer
-- An        162.0   81.00      2
-- Binh      215.5  107.75      2

Fine in isolation — but if this table later gets merged with a second aggregation of a different column (say, a headcount by customer), both would independently have a plain count column and collide. add_prefix() disambiguates them cleanly, confirmed directly against the real fixture:

clean.groupby("customer")["amount"].agg(["sum", "mean", "count"]).add_prefix("amount_")
--           amount_sum  amount_mean  amount_count
-- customer
-- An             162.0        81.00             2
-- Binh           215.5       107.75             2

Now every column name carries both the source column and the function that produced it — self-describing, and safe to merge with a same-shaped table built from a different source column.

3 · The sharp edge: MultiIndex columns get prefixed on every level

Aggregating multiple source columns with multiple functions each (or a raw pivot_table() with more than one aggfunc) produces genuine MultiIndex columns (Lesson 52), not the flat one above:

agg = clean.groupby("customer").agg({"amount": ["sum", "mean"], "order_id": "count"})
agg.columns
-- MultiIndex([('amount',   'sum'),
--             ('amount',  'mean'),
--             ('order_id', 'count')])

Confirmed directly: calling add_prefix() on this does NOT prefix only the outer level, and does NOT raise for being "not a plain Index" — it stamps the prefix onto every level of every tuple:

agg.add_prefix("x_").columns.tolist()
-- [('x_amount', 'x_sum'), ('x_amount', 'x_mean'), ('x_order_id', 'x_count')]

That is almost never what's wanted — the usual goal is one flat, readable name like amount_sum, not a MultiIndex where both the outer and inner label now carry the same stray prefix. The working pattern is to flatten the MultiIndex to plain strings first (joining each tuple's parts), and only then call add_prefix()/add_suffix() on the now-flat result:

agg.columns = ["_".join(col).strip("_") for col in agg.columns]
agg.columns.tolist()
-- ['amount_sum', 'amount_mean', 'order_id_count']
agg.add_prefix("agg_").columns.tolist()
-- ['agg_amount_sum', 'agg_amount_mean', 'agg_order_id_count']

The [... for col in agg.columns] line is a Python list comprehension — it runs once over the small list of column tuples to build plain strings, not a per-row loop over the DataFrame's data, so it doesn't violate this course's tables-not-loops rule (Lesson 1).

4 · axis=: the same trick on the row index

Both methods default to the columns axis, but accept axis=0 (or axis="index") to prefix/suffix the row index instead — confirmed directly, useful right before a pd.concat() of two tables whose row labels would otherwise collide:

clean.head(3).add_prefix("row_", axis=0)
--        order_id customer  amount order_date
-- row_0         1       An   120.0 2026-01-05
-- row_1         6       An    42.0 2026-01-10
-- row_2         2     Binh    35.5 2026-01-06

5 · The SQL bridge

SQL's closest equivalent is column aliasing in the SELECT list — SELECT SUM(amount) AS amount_sum, AVG(amount) AS amount_mean FROM ... GROUP BY customer — except SQL requires naming each alias individually, one AS per column, by hand. add_prefix()/add_suffix() apply the same renaming idea to every column at once with a single call, the same "operate on the whole axis, not one column at a time" instinct behind select_dtypes() and rename(columns=...).

Q: "You've aggregated the same table two different ways and need to merge the results — what's the cleanest way to avoid column-name collisions?" A strong answer, out loud: "After each groupby().agg() call, I'd call add_prefix() with a name tied to what that aggregation represents — say amount_ for the spend summary and orders_ for the count summary — before merging on the shared key. That way every column in the merged result is self-describing, and I don't have to hand-write a rename map. The one thing I'd watch for is a MultiIndex column result from aggregating multiple source columns at once — add_prefix() stamps the prefix onto every level of the tuple, not just the outer one, so I'd flatten the MultiIndex to plain strings first, then prefix." The signal: naming the collision problem itself, and the MultiIndex-every-level gotcha rather than assuming it "just works."
