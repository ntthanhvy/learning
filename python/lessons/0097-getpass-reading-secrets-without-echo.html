getpass: reading a secret without echoing it

Day 93's sqlite3 lesson opened a real database from a script; a script like that often needs a password or API key typed in at the terminal, too. Using plain input() for that prints every keystroke back to the screen — visible to anyone glancing over a shoulder, and often captured in a terminal's scrollback or screen-recording. The standard-library getpass module exists for exactly this: a prompt that reads a line the same way a login screen does.

Picked getpass over the rest: Day 93's sqlite3 lesson and Day 77's secrets lesson both assume a secret value already exists in memory, but neither one teaches how that secret gets from a human's keyboard into the program safely in the first place — a short, sharp, real gap this closes directly, with zero pandas/NumPy surface at all (this is pure terminal I/O, nothing either library touches).

1 · input() echoes; getpass.getpass() doesn't

input(prompt) shows every character as it's typed — normal and expected for a username, wrong for a password. getpass.getpass(prompt) uses the same terminal to print the prompt, but turns input echo off at the OS level while reading the line, then turns it back on:

import getpass

password = getpass.getpass("Database password: ")
print("got", len(password), "characters")
# the typed characters never appear on screen, confirmed live via a real tty;
# the returned value is a plain str, same as input()'s return type

Confirmed directly: inspect.signature(getpass.getpass) reports (prompt='Password: ', stream=None) — the prompt defaults to the string "Password: " if left out, and stream lets the prompt itself be redirected to stderr or elsewhere without touching where the input is read from.

2 · When there's no real terminal, it falls back loudly

Echo-suppression needs an actual terminal (a tty) to control. When one isn't available — stdin redirected from a file, or running inside some editors and CI pipelines — getpass can't turn echo off, so it falls back to plain visible input instead of silently failing, and raises a warning so the fallback isn't missed:

import getpass, warnings

with warnings.catch_warnings(record=True) as caught:
    warnings.simplefilter("always")
    pw = getpass.getpass("Password: ")   # stdin redirected from a StringIO here, no real tty
    print(caught[0].category.__name__)   # GetPassWarning -- confirmed live
    print(caught[0].message)           # Can not control echo on the terminal. -- confirmed live

GetPassWarning is a real, catchable warning class — confirmed directly: issubclass(getpass.GetPassWarning, UserWarning) is True, so Day 85's warnings tools (catch_warnings(record=True), filterwarnings) apply to it exactly like any other warning. A script that must refuse to run with a visibly-echoed password can catch this specific category and abort instead of continuing with a silently weaker prompt.

3 · getpass.getuser(): the "who's running this" half

The same module also answers a related but different question — not "what secret did a human just type," but "what account is this process running as." getpass.getuser() takes no arguments and returns the current login name, read from environment variables the OS sets (LOGNAME, USER, or platform equivalents), without prompting for anything:

print(getpass.getuser())
# e.g. 'runner' -- confirmed live, reads straight from the environment, no prompt shown at all

Useful for a default value — "connect as the current OS user unless told otherwise" — never for authentication by itself, since anyone can set those same environment variables to any name they like.

Where pandas/NumPy go from here: nowhere — this is terminal input/output, a layer below anything either library touches. Neither pandas nor NumPy reads credentials; a script using getpass to collect a database password, then loading the resulting table with pandas, is the realistic shape, but that second half is data/'s job and isn't shown here.
