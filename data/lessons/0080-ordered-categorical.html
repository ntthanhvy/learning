Ordered categoricals: making "small < medium < large" sort correctly

Lesson 79's teaser named the groupby/agg leftovers (as_index=False, .get_group()) as the standing candidate, but a fresh gap-scan (grepping all 79 lesson bodies plus the glossary against a wider candidate list) found something with more runway: Lesson 25 taught the category dtype in full — memory, the lookup-table mechanics, the fixed-category silent-NaN gotcha — but its own "Go deeper" line named "ordered categories" as something the pandas docs cover that Lesson 25 itself never did. Grepping ordered= across every lesson body confirmed zero hits anywhere. That's today's topic: the same category dtype, with an order attached.

1 · The problem: category dtype sorts alphabetically by default

Lesson 25's category dtype is a lookup table plus a small integer code per row — great for memory, but by default pandas has no idea that "medium" sits between "small" and "large". Bucket this course's own orders_raw.csv amounts into size tiers and convert to plain category:

clean["size_cat"] = clean["size"].astype("category")
clean.sort_values("size_cat")[["customer", "amount", "size"]]
# customer  amount    size
# Binh       180.0   large    <- sorted FIRST -- wrong, alphabetical: large, medium, small
# An         120.0  medium
# An          42.0   small
# Binh        35.5   small

Confirmed directly: large sorts before medium and small because pandas defaults to alphabetical category order — the same trap as a plain SQL ORDER BY size on a free-text column with no CASE WHEN or lookup-table rank to guide it. A dashboard sorting "Priority: Low/Medium/High" this way would put High in the middle. This is the exact gap Lesson 25 left open.

2 · The fix: CategoricalDtype(categories=[...], ordered=True)

Pass an explicit category list in the order you want, plus ordered=True, and build a ordered categorical:

order = pd.CategoricalDtype(categories=["small", "medium", "large"], ordered=True)
clean["size_ordered"] = clean["size"].astype(order)
clean.sort_values("size_ordered")[["customer", "amount", "size"]]
# customer  amount    size
# An          42.0   small    <- correct business order now
# Binh        35.5   small
# An         120.0  medium
# Binh       180.0   large

Confirmed directly: sort_values() now respects small < medium < large, the order the list was written in, not alphabetical order. Same lookup-table storage as Lesson 25's plain category — this costs nothing extra in memory, it's the identical dtype family with one more piece of metadata (the rank) attached.

3 · What ordering unlocks: real comparisons, not just equality

An unordered category (Lesson 25's default) only supports ==/!= — pandas has no basis to say one category is "more than" another. An ordered one supports the full set:

clean[clean["size_ordered"] > "small"][["customer", "amount", "size"]]
# customer  amount    size
# An         120.0  medium   -- both correctly kept: medium AND large are > small
# Binh       180.0   large
clean["size_ordered"].min(), clean["size_ordered"].max()
# ('small', 'large')

# the unordered version from section 1, same comparison:
clean["size_cat"] > "small"
# TypeError: Unordered Categoricals can only compare equality or not

Confirmed directly on both sides: >/min()/max() work on the ordered column and raise TypeError on the unordered one. This is the real interview tell — "why does comparing my category column raise TypeError?" almost always means the column was converted to plain category when the actual need was an ordered one.

SQL bridge: Lesson 25 mapped plain category to a SQL ENUM/lookup table. An ordered categorical is that same lookup table with a rank column added — the pattern behind a hand-rolled CASE WHEN size='small' THEN 1 WHEN size='medium' THEN 2 WHEN size='large' THEN 3 END AS size_rank just to get ORDER BY right, or a dedicated small ranked lookup table joined in for the same reason. ordered=True is pandas doing that rank-column trick for you, once, at the dtype level — every sort_values()/>/min() afterward just uses it.

4 · A gotcha, and a callback: pd.cut() already returns one

Comparing an ordered category to a value outside its fixed category list doesn't silently misbehave — it raises, unlike Lesson 25's fixed-category astype() gotcha (which silently produced NaN):

clean["size_ordered"] > "huge"
# TypeError: Invalid comparison between dtype=category and str

Confirmed directly: unlike Lesson 25's "no crash, quietly wrong" family, this one fails loudly — "huge" was never one of the three fixed categories, so pandas has nothing to rank it against. A useful, if accidental, safety net: it's easier to notice a crash than a silent alphabetical-sort bug.

Lesson 12's/18's pd.cut()/pd.qcut() binning has been quietly returning an ordered categorical this whole course, worth naming explicitly now:

pd.cut(clean["amount"], bins=[0, 50, 150, 1000], labels=["small", "medium", "large"]).dtype
# category
pd.cut(clean["amount"], bins=[0, 50, 150, 1000], labels=["small", "medium", "large"]).cat.ordered
# True

Confirmed directly: pd.cut()'s output .cat.ordered is True, and its result matches this section's hand-built size_ordered column exactly, row for row. Every bucket pd.cut() ever produced in this course was already sortable/comparable correctly by construction — this lesson just names the mechanism.

Q: "I converted a priority column (Low/Medium/High) to category dtype and sort_values() puts High in the middle. What's wrong?" A strong answer, out loud: "category dtype defaults to alphabetical category order unless told otherwise — High, Low, Medium alphabetically, which is exactly the middle-High bug. The fix is building an ordered categorical instead: pd.CategoricalDtype(categories=['Low','Medium','High'], ordered=True), then .astype() that dtype. That also unlocks real comparisons — greater-than, min, max — which plain unordered category dtype refuses with a TypeError, only == and != work there. It's the same idea as hand-rolling a CASE WHEN rank column in SQL just to get ORDER BY right on a priority field — ordered=True does that once at the dtype level instead of every query. And I'd mention pd.cut()'s bucket output has actually been an ordered categorical all along, if that's ever come up already." The signal: naming the alphabetical-default root cause precisely, not just patching around it, and connecting it to the comparison behavior unprompted.
