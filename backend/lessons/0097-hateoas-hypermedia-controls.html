HATEOAS: letting the response say what to do next

Lesson 3 fixed the API contract's nouns and verbs: resources, GET/POST/PATCH/DELETE, status codes. One question it left open: once a client has GET /orders/42 back, how does it know whether it's still allowed to cancel that order, or pay for it, or that doing either one even requires a different URL? Today's answer: stop making the client guess, and put the available next moves inside the response itself.

1 · The client is hard-coding what the server already knows

A typical JSON API returns the order and nothing else:

{ "id": 42, "status": "pending", "total_cents": 5000 }

To let the user cancel this order, the frontend has to already know — baked into its own code, from reading the docs once — that canceling means PATCH /orders/42 with {"status": "canceled"}, and that this is only valid while status is "pending". Every client reimplements that rule independently. When the backend adds a new state that also blocks cancellation (say, "packed"), every one of those independent copies is wrong until someone remembers to update all of them — the server changed the rule, but the rule's enforcement lived on the other side of the network the whole time.

2 · Put the next moves in the response

HATEOAS is the constraint that fixes this: the server, which already knows the order's state and the rules around it, attaches the legal next actions directly to the response.

{
  "id": 42,
  "status": "pending",
  "total_cents": 5000,
  "links": [
    { "rel": "self",   "href": "/orders/42",          "method": "GET" },
    { "rel": "cancel", "href": "/orders/42",          "method": "PATCH" },
    { "rel": "pay",    "href": "/orders/42/payment", "method": "POST" }
  ]
}

Once the order ships, the server simply stops including the cancel link relation — a client that checks "does this response offer a cancel link?" instead of "is status == pending?" never needs updating when the rule changes, because it never encoded the rule in the first place. The frontend becomes a follower of links, not a reimplementer of business rules.

3 · This is pagination's own trick, generalized

This isn't a new idea — Lesson 15's cursor pagination already does exactly this for one specific case: {"next_cursor": "...", "has_more": true} tells the client whether a next page exists and how to fetch it, instead of the client computing page math itself from a total count. HATEOAS is the same move — "the response carries the next step" — applied to every state transition a resource can have, not only "is there more data."

Frontend-habit trap: this looks a lot like a feature flag check (if (flags.canCancelOrders)) — a boolean the frontend already knows how to branch on. The difference is who decides and how current the answer is: a feature flag is a global, rarely-changing toggle fetched separately and often cached; a hypermedia link is computed fresh, per-resource, per-request, from that exact order's current state — the presence of cancel on order 42 says nothing about order 43, and both are only as stale as the response they arrived in.

4 · Why most APIs skip it anyway

HATEOAS is Roy Fielding's own original REST dissertation's most-cited and least-adopted constraint. The honest trade-off: it pays off when a client follows links generically (a browser following <a href> is the canonical example) and when the rules governing valid next actions actually change often enough to matter. Most internal APIs are consumed by one team's own frontend, deployed together, where "update the docs and the client in the same PR" is cheap enough that the generality doesn't earn its complexity — which is why most real-world JSON APIs (including every one built in this course so far) skip it, and why it's still worth naming: so "we chose not to" is a decision, not a gap nobody noticed.

Q: "What does HATEOAS mean, and would you use it here?" A strong answer, out loud: "It's the REST constraint where the server includes the valid next actions as links in the response, instead of the client hard-coding which state transitions are legal — so changing the business rule only requires a server-side change, not updating every client. I'd reach for it when clients are generic or third-party and the transition rules shift independently of client releases; for an internal API where our own frontend ships in lockstep with the backend, the coordination cost it removes isn't worth the extra response shape and client-side link-following logic — I'd rather keep the simpler contract and accept that both sides redeploy together." The signal: naming the real trade-off instead of treating HATEOAS as something every "proper" REST API must have.

Scope line

This lesson covers only the mental model: links describing legal next actions, attached to a resource's own response. It doesn't cover any specific hypermedia media type's full spec (HAL, JSON:API, Siren each standardize their own links/rel shape slightly differently) or GraphQL's very different answer to "what can I do from here" — those are implementation choices on top of the idea taught today, not needed to reason about whether to use it at all.
