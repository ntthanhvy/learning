1 · mean(), median(), mode(): three different "typical"

A single list of numbers rarely has one obvious "typical value" — it has three different ones, and they disagree the moment the data is skewed:

import statistics

amounts = [20, 25, 22, 21, 500]   # four normal orders, one huge outlier

print(statistics.mean(amounts))     # 117.6 -- dragged hard toward the outlier
print(statistics.median(amounts))   # 22 -- the middle value once sorted, outlier barely matters
print(statistics.mode(amounts))     # 20 -- the single most frequent value (first one, here, since all are unique except ties)

mean() is the familiar sum-divided-by-count average, and exactly because of that it is sensitive to outliers — one huge value drags it far from where most of the data actually sits. median() sorts the data first and takes the middle, which is why the one huge value above barely moves it. mode() answers a different question entirely — not "what's central" but "what repeats most" — and is the only one of the three that also makes sense on non-numeric, categorical data like a list of city names.

Bridge from SQL: statistics.mean(amounts) is AVG(amount) run on a Python list instead of a result set — same arithmetic, no query involved. SQL has no built-in MEDIAN() in most dialects; this module gives Python that for free.

2 · Spread: stdev() and variance()

A single "typical value" hides how spread out the data actually is — two lists can share the same mean while one clusters tightly and the other swings wildly. stdev() measures exactly that, in the same units as the data itself:

tight  = [48, 50, 52, 49, 51]    # mean 50, clustered close
spread = [10, 90, 50, 95, 5]     # mean 50, swinging wildly

print(statistics.mean(tight), statistics.stdev(tight))     # 50.0, ~1.58 -- small spread
print(statistics.mean(spread), statistics.stdev(spread))   # 50.0, ~45.6 -- same mean, huge spread

stdev() requires at least two data points — it raises StatisticsError on a single-item or empty input, since "how spread out is one number" isn't a meaningful question. statistics.variance() returns the same spread measure before the final square root (stdev() is just variance() ** 0.5) — reach for stdev() directly almost always, since it's in the data's own units and variance()'s squared units are rarely what a report needs.

3 · Why a plain function beats hand-rolling the formula

Every one of these is a short loop someone could write by hand — sum(data) / len(data) for mean(), sort-then-index for median() — and that is exactly the trap. A hand-rolled mean() silently returns the wrong thing on an empty list (ZeroDivisionError if careless, or a wrong answer if not), and a hand-rolled median() is easy to get off-by-one on an even-length list (the median of four numbers is the average of the two middle ones, not either one alone):

# a believable-looking bug: forgetting the even-length-list case entirely
def bad_median(data):
    data = sorted(data)
    return data[len(data) // 2]   # wrong for even-length input -- picks one middle value, not their average

print(bad_median([1, 2, 3, 4]))        # 3 -- wrong, real median is 2.5
print(statistics.median([1, 2, 3, 4]))   # 2.5 -- correct

The standard library has already gotten the edge cases right once, for everyone — the same argument Day 59's hashlib made for not hand-rolling a hash function, and Day 56's operator module made for not hand-rolling a lambda for something with a name already.

Where pandas goes from here: df["amount"].mean()/.median()/.std(), or .describe() for all of them plus quartiles in one call, compute the identical statistics over a DataFrame column instead of a plain list — vectorized across potentially millions of rows, with the column's own index and dtype handling built in. Not demonstrated here; that's data/'s job, and this is the only sentence in this lesson that names it.
