fractions: exact rational numbers, no float imprecision

Day 70 fixed one float trap: decimal gives exact base-10 arithmetic, so money adds up correctly. float has a second, different trap decimal doesn't touch — a rational number like one-third has no exact finite form in binary, so 1/3 as a float is already an approximation before any arithmetic even starts. The standard-library fractions module stores a ratio of two integers directly — exact, with no base-10 or base-2 rounding at all.

1 · Why float gets 1/3 wrong before any math happens

float stores numbers in base 2. Some decimal fractions, like 0.1, have no exact finite binary form — that was Day 70's trap. One-third has the same problem in every base except base 3, so it is never exact as a float at all:

print(1/3 + 1/3 + 1/3)        # 1.0 -- looks fine here...
print(0.1 + 0.2)              # 0.30000000000000004 -- confirmed live, Day 70's trap

The first line happens to land on exactly 1.0 by luck of rounding; it is not guaranteed to, and in a longer pipeline of ratios — splitting a bill three ways, scaling a recipe, computing odds — those tiny errors accumulate exactly like Day 70's prices did. decimal.Decimal does not help here either: it is exact for base-10 digits, but one-third is not exact in base 10 any more than it is in base 2 (it is 0.3333... repeating forever either way).

2 · Fraction: a ratio of two integers, stored exactly

fractions.Fraction(numerator, denominator) stores the two integers directly — no binary or decimal rounding involved at all, confirmed live:

from fractions import Fraction

third = Fraction(1, 3)
total = third + third + third
print(total, total == 1)              # 1 True -- exact, not 0.9999999999999998

r = Fraction(6, 8)
print(r, r.numerator, r.denominator)  # 3/4 3 4 -- auto-reduced to lowest terms

Every Fraction auto-reduces to lowest terms on construction, and .denominator is guaranteed positive per the docs — Fraction(16, -10) comes out as Fraction(-8, 5), not Fraction(-16, 10). Arithmetic (+, -, *, /) between two Fractions stays exact and keeps reducing: Fraction(1, 3) + Fraction(1, 6) is exactly Fraction(1, 2), confirmed live. A zero denominator raises ZeroDivisionError immediately, the same exception plain 1/0 raises — not a new exception type invented for this module.

Fraction compares directly against int and float: Fraction(1, 2) > 0.4 is True, confirmed live — no manual conversion needed first. float(some_fraction) converts back to an approximate float when one is actually needed, e.g. to pass to a function that only accepts floats.

3 · The float-construction trap, same shape as Day 70's

Fraction has the exact same construction trap decimal.Decimal does: building one from a float captures that float's own pre-existing binary imprecision, rather than fixing it:

from fractions import Fraction

print(Fraction(0.1))      # 3602879701896397/36028797018963968 -- confirmed live
print(Fraction("0.1"))    # 1/10 -- confirmed live, exact

Fraction(0.1) faithfully reports the exact ratio the float 0.1 already was in memory — a strange-looking huge fraction, because that is genuinely what the nearest binary approximation to one-tenth equals. Building from a str instead — Fraction("0.1"), or Fraction("3/7") for a ratio written directly — never passes through float at all, so it lands on the exact value intended. The docs state this directly: Fraction(1.1) "is not exactly equal to 11/10," for the same reason Decimal(0.1) was never exact in Day 70. The fix is identical in shape: construct from a str (or an int pair), never from a float literal, whenever the exact value matters.

4 · limit_denominator(): the closest simple fraction to a messy number

Sometimes the input really is a float already — a measurement, a computed ratio — and the goal is the simplest fraction close to it, not the float's exact (and ugly) binary value. limit_denominator(max_denominator) finds the closest Fraction with a denominator no larger than the one given:

import math
from fractions import Fraction

approx = Fraction(math.pi).limit_denominator(1000)
print(approx, float(approx))   # 355/113 3.1415929203539825 -- confirmed live
# math.pi itself: 3.141592653589793 -- 355/113 is correct to 6 decimal places

355/113 is a famous historical approximation of π, and limit_denominator() rediscovers it directly from the float value with no hard-coding. This is the opposite move from Section 3: Section 3 preserves an exact value by avoiding float entirely; limit_denominator() deliberately accepts a small amount of error in exchange for a short, human-readable ratio out of a float that was never exact to begin with.

Bridge from Day 70: both modules exist to fix a float precision gap, for different kinds of exactness. Decimal is exact for numbers that are naturally decimal — money, percentages, anything a human writes with a fixed number of digits after the point. Fraction is exact for numbers that are naturally ratios — proportions, odds, fractions of a whole — including ones like 1/3 that no finite decimal or binary expansion ever represents exactly. Reach for whichever one matches how the original number was meant to be written.
Where pandas/NumPy go from here: neither has a dedicated exact-rational column dtype matching Fraction — a NumPy array of Fraction objects works but loses the vectorized-math speed that is the point of using NumPy at all, so this stays a plain-Python tool for exact small-scale ratio work. Not covered further here, per MISSION.md; this course teaches the standard-library mechanism, not a worked pandas/NumPy example.
