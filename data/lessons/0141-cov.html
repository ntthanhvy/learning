Series.cov() and np.cov(): the unscaled number behind corr(), and the matrix-shape trap

Lesson 140's own closing note left no named successor — this round's own fresh scan grepped every lesson body case-insensitively for .cov( and np.cov(: zero hits anywhere across Lessons 1-140, confirmed by a second pass over NOTES.md and the glossary too. .corr() (Lesson 50) got its own lesson back in Lesson 50, but its quieter sibling .cov() — the raw, unscaled number .corr() is actually built from — never has, a genuine gap and a natural companion to Lesson 137's ddof arc.

1 · cov() measures the same "move together" idea as corr() — just not squeezed onto -1..1

Confirmed directly (pandas 3.1.1, numpy 2.5.5), reusing Lesson 50's own reps table:

demo = pd.DataFrame({
    "rep":             ["Mai", "Long", "Chi", "Huy", "Trang"],
    "calls_made":      [10, 25, 15, 40, 30],
    "deals_closed":    [2, 6, 3, 9, 7],
    "office_size_sqm": [12, 30, 15, 8, 45],
})

demo["calls_made"].cov(demo["deals_closed"])    # 34.25
demo["calls_made"].corr(demo["deals_closed"])   # 0.9958962509386671

Both numbers describe the identical relationship between the same two columns, confirmed directly to be mathematically tied together: cov() is corr() multiplied back out by each column's own spread: cov = corr × std(A) × std(B), confirmed directly (0.9958962509386671 × 11.957... × 2.880... lands on the same 34.25). corr() is cov() divided by both standard deviations to force the result onto a fixed -1..1 scale — cov() is the same relationship before that normalization step, still carrying the original columns' own units, which is exactly why a raw 34.25 cannot be compared against a covariance computed from a completely different pair of columns the way a corr() number always can.

2 · Whole-DataFrame cov(): a full matrix, var() sitting on its own diagonal

Confirmed directly, calling cov() on the whole DataFrame (no column selected) computes every pairwise combination at once, the same matrix shape Lesson 50 confirmed for corr():

demo[["calls_made", "deals_closed", "office_size_sqm"]].cov()
--                  calls_made  deals_closed  office_size_sqm
-- calls_made           142.50         34.25            31.25
-- deals_closed          34.25          8.30            10.50
-- office_size_sqm       31.25         10.50           234.50

demo["calls_made"].var()   # 142.5 -- exactly the matrix's own top-left diagonal cell

Confirmed directly: every diagonal cell of a covariance matrix is just that column's own .var() — a column's covariance with itself reduces to its own variance, since ddof's sample-vs-population split (Lesson 137) runs underneath .cov() too, defaulting to the same ddof=1 sample formula. A one-element Series's .cov() inherits the identical single-row trap already confirmed for .std()/.var(): dividing by count - 1 = 0 returns a silent NaN, no crash, confirmed directly on pd.Series([5.0]).cov(pd.Series([3.0])).

3 · The real trap: np.cov() always returns a matrix, even for two plain 1-D arrays

Unlike Lesson 140's median trap (a genuine NaN-handling mismatch), cov()'s cross-library disagreement is about shape, not missing-data defaults. Confirmed directly, both ddof defaults actually already agree here — a pleasant contrast to Lesson 137's .std()/.var() split:

a = demo["calls_made"].to_numpy()
b = demo["deals_closed"].to_numpy()

np.cov(a, b)
-- array([[142.5 ,  34.25],
--        [ 34.25,   8.3 ]])
Confirmed directly, why this is the sharper trap than it looks: np.cov(a, b) does NOT return the single cross-covariance number the way Series.cov() does — it returns the full 2x2 matrix, bundling in each array's own variance along the diagonal. The actual number matching demo["calls_made"].cov(demo["deals_closed"]) sits buried at np.cov(a, b)[0, 1] (or equivalently [1, 0], since the matrix is always symmetric), confirmed directly to equal 34.25 exactly. Code that naively does np.cov(a, b) expecting one number back, the same instinct Series.cov() trains, gets a whole array instead — no error, just the wrong shape silently flowing into whatever runs next. Confirmed directly, np.cov(a, b, ddof=1) (pandas' own implicit default) reproduces the exact matrix above, and np.cov(a, b, ddof=0) gives a different, smaller matrix — so the two libraries' defaults genuinely agree (both sample, ddof=1), unlike Lesson 137's .std()/.var(); np.cov()'s own default parameter is actually spelled ddof=None, which falls back to behaving like ddof=1 unless a separate bias=True keyword is also passed.

4 · min_periods=, and NaN handling matches corr()'s own pairwise rule

Confirmed directly, Series.cov() drops NaN the same pairwise way Lesson 50 confirmed for corr() — only rows missing in either compared column, not a whole-table dropna:

a2 = pd.Series([1.0, 2, np.nan, 4, 5])
b2 = pd.Series([2.0, np.nan, 3, 8, 10])

a2.cov(b2)                   # 8.666666666666668  -- computed from the 3 complete pairs only
a2.cov(b2, min_periods=4)    # NaN  -- refuses: fewer than 4 complete pairs exist

min_periods= is the confirmed guardrail corr() doesn't name as loudly: rather than silently computing from however few complete pairs happen to remain, it returns NaN if the count of usable pairs falls below the threshold given — useful whenever a near-empty overlap between two columns would otherwise produce a technically-real but practically-meaningless number. np.cov() on the raw arrays shows the opposite, blunter failure mode: confirmed directly, a plain NaN anywhere poisons every cell of the matrix that touches it, matching Lesson 140's own np.median()-propagation trap rather than introducing a new one.

Q: "What's the difference between cov() and corr(), and when would you reach for cov() specifically?" A strong answer, out loud: "corr() is cov() divided by both columns' own standard deviations, forced onto a fixed -1 to 1 scale, which is why corr() is comparable across completely different column pairs and cov() isn't -- a covariance of 34 between calls and deals means nothing next to a covariance of 10,000 between revenue in dollars and headcount, since the raw number still carries each column's own units. I'd reach for cov() directly mostly as a building block -- it's literally what variance becomes when you correlate a column with itself, and it's what portfolio-risk and some PCA-style calculations actually operate on -- but for a plain 'do these move together' question in a report, corr() is almost always the more honest number to show, because its scale means the same thing regardless of which columns are being compared." The signal: naming the exact formula relationship (cov = corr × std × std) and the units caveat unprompted, not just repeating "they're related" vaguely.
