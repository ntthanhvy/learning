Resolving output-cache policies dynamically

Lesson 130's scope line named this exact gap and deferred it: everything from Lesson 128 onward assumes every named policy is known at startup, baked into AddOutputCache(options => options.AddPolicy(...)) in code. This lesson is about the one case that assumption can't cover — a policy that has to be looked up per request, from somewhere other than code.

1 · Why a compile-time policy list isn't always enough

options.AddPolicy("CachePost", MyCustomPolicy.Instance) from Lesson 130 only works when every policy name and rule is known when the app starts. That's fine for "cache GET for 20 seconds." It breaks down for a SaaS app where each tenant has its own cache duration stored in a database row, or a feature flag that can flip a policy's behavior without a redeploy. Nothing in OutputCachePolicyBuilder can read a database — the builder's methods only ever see values supplied at startup. Resolving a policy per request, from outside code, means replacing the thing that resolves policies at all, not adding another one.

2 · The IOutputCachePolicyProvider interface

IOutputCachePolicyProvider is the interface the default policy lookup is itself built on. The default implementation is just the one backing AddPolicy/AddBasePolicy — a custom one replaces that lookup entirely:

public sealed class TenantOutputCachePolicyProvider : IOutputCachePolicyProvider
{
    private readonly ITenantPolicyStore _store;

    public TenantOutputCachePolicyProvider(ITenantPolicyStore store)
        => _store = store;

    public IReadOnlyList<IOutputCachePolicy> GetBasePolicies()
        => Array.Empty<IOutputCachePolicy>();

    public async ValueTask<IOutputCachePolicy?> GetPolicyAsync(string policyName)
    {
        var rule = await _store.FindAsync(policyName);
        return rule is null
            ? null
            : new TenantPolicy(rule.Expiry, rule.VaryByTenantHeader);
    }
}

GetBasePolicies returns the base policies applied to every request, replacing every AddBasePolicy call from Lesson 128 onward. GetPolicyAsync resolves one named policy by its string name — the same name a CacheOutput("SomeName") call or [OutputCache(PolicyName = "SomeName")] attribute already passes today, except now the lookup can await a database call instead of returning a value fixed at startup. Returning null from GetPolicyAsync means the same thing a missing dictionary key would: that policy name wasn't found.

3 · Registering it, and the tenant cache-key trap

A custom provider replaces the default one, registered through DI right after AddOutputCache:

builder.Services.AddOutputCache();
builder.Services.AddTransient<IOutputCachePolicyProvider, TenantOutputCachePolicyProvider>();

Registering it this way doesn't disable AddPolicy/AddBasePolicy as a concept — it replaces which code answers "what's the policy for this name," so a custom provider that wants to keep serving some statically-defined policies has to hold onto and delegate to them itself. One documented trap is sharper here than anywhere else so far: for tenant-specific responses, the cache key must vary by tenant, or one tenant's cached response gets served straight to another. A dynamically resolved policy can change what rule applies, but Lesson 128's cache key only varies by what SetVaryByHeader/SetVaryByQuery already told it to vary by — resolving the policy dynamically and forgetting to vary the key by tenant produces a correctly-applied wrong-tenant cache hit, not an error.

Frontend-habit trap: this looks like swapping a React Query queryClient's static defaultOptions for a function that computes options per call — same shape, server-side. The gap that doesn't carry over: a frontend per-tenant query still keys its own cache by whatever the client includes in the query key by habit (a tenant ID in the URL, say). Server-side, nothing varies the output cache's key automatically just because the policy became tenant-aware — that's a second, separate thing this lesson's provider has to get right on its own.

Scope line

This lesson covers the IOutputCachePolicyProvider interface's two methods, registering a custom provider via AddTransient after AddOutputCache, and the tenant-cache-key trap the docs call out by name. It does not cover the SizeLimit/MaximumBodySize cache-wide limits or SetLocking(false)'s resource-locking opt-out — both still named as open follow-ups from Lesson 130, deferred a third round running — nor a full worked ITenantPolicyStore/database-backed implementation, which would be a framework deep-dive past this lesson's one concept.
