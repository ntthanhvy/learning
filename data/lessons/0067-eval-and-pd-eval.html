df.eval() and pd.eval(): SELECT expressions, spelled as a string

Lesson 66 named two zero-hit candidates for next time, df.eval()/pd.eval() and factorize(); a fresh grep of all 66 lessons and the glossary confirmed both are still genuinely uncovered. eval() won out because it sits right next to a lesson already taught: Lesson 22 gave query() a name as "WHERE, spelled as a string" — but a string-expression way to build a new column, the SELECT amount * 2 AS doubled half of the same idea, was never covered. df.eval() is exactly that missing half.

1 · query() filters rows; eval() computes columns

Lesson 22's query() and today's df.eval() are two ends of the same string-expression idea — one filters rows, the other computes a column:

# query() (Lesson 22) — WHERE, as a string
clean.query("amount > 100")

# eval() — SELECT computed_expr AS new_col, as a string
clean.eval("half = amount / 2")
--    order_id customer  amount  order_date   half
--  0        1       An   120.0  2026-01-05  60.00
--  1        6       An    42.0  2026-01-10  21.00
--  2        2     Binh    35.5  2026-01-06  17.75
--  3        5     Binh   180.0  2026-01-09  90.00

Confirmed directly (pandas 3.0.5) on the real orders_raw.csv clean 4-row slice: clean.eval("half = amount / 2") returns a new DataFrame with half added — the original clean is untouched, exactly like assign(). Confirmed byte-identical too: clean.eval("half = amount / 2").equals(clean.assign(half=clean["amount"] / 2)) is True. eval() isn't a new capability over assign() — it's a different, string-based spelling of the same computed-column idea, the same relationship query() has to a boolean mask.

Gotcha, confirmed directly: inplace=True mutates and returns None, matching pandas' usual convention here (unlike Lesson 65's where()/mask() note on a different method). clean.eval("half = amount / 2", inplace=True) returns None and adds half directly onto clean itself. Forgetting inplace=True and just calling clean.eval("half = amount / 2") on its own line silently computes and discards the result — clean never gains the new column, no error either way.

2 · The real trap: pd.eval() and df.eval() resolve names completely differently

The top-level function pd.eval() and the DataFrame method df.eval() look like the same feature but resolve bare names in opposite ways — confirmed directly, this is the single easiest mistake to make:

threshold = 100

# df.eval() (method form): column names are ALREADY bare local variables
clean.eval("amount > @threshold")      # needs @ for the Python variable
-- [True, False, False, True]
clean.eval("amount > threshold")       # WITHOUT @: raises UndefinedVariableError
-- pandas looks for a column literally named "threshold", finds none

# pd.eval() (top-level function): has NO column awareness at all
pd.eval("amount > threshold")          # raises UndefinedVariableError too --
-- "amount" isn't a column here, it's just an undefined Python name
pd.eval("clean.amount > threshold")   # works -- clean and threshold are both
-- [True, False, False, True]              plain Python names in scope, no @ needed

Confirmed directly (pandas 3.0.5): inside df.eval(), every column of the calling DataFrame is injected into the expression's namespace as if it were already a local variable — that's eval()'s whole point, matching query()'s same behavior. @ is reserved for reaching past that column namespace into a genuine outside Python variable, identical to query()'s @. pd.eval(), called as a bare top-level function with no DataFrame receiver, has nothing to inject columns FROM — it just evaluates the string against whatever local/global Python names already exist, the same as writing the equivalent Python line directly. Naming a DataFrame's column there means spelling the DataFrame out, clean.amount or clean["amount"], same as outside any string-expression method.

Rule of thumb, worth saying out loud under interview pressure: reach for the df.eval("col = ...") method form almost always — it's column-aware and mid-chain-friendly, exactly like query(). pd.eval() the bare function is mainly for evaluating one expression against several separate DataFrames/Series by name in a single string, a rarer need; don't confuse its lack of column awareness for a bug.

3 · Multiple assignments in one call

A multi-line string computes several columns in a single eval() call, one assignment per line:

clean.eval("""
half = amount / 2
doubled = amount * 2
""")
-- adds BOTH half and doubled columns in one call

Confirmed directly: this is equivalent to two chained .assign() calls, or one .assign(half=..., doubled=...) — again, a different spelling of the same computed-column idea, not new behavior. Assigning back to an existing column name (clean.eval("amount = amount * 2")) overwrites that column in the result the same way a plain assign() would, and — confirmed directly — still leaves the original clean untouched without inplace=True.

4 · SQL bridge, and where performance fits

df.eval("half = amount / 2") is SELECT *, amount / 2 AS half FROM orders — every existing column carried through, plus one computed expression given a name. The optional engine="numexpr" keyword (needs the separate numexpr package, not installed by default — confirmed directly, engine="numexpr" without it raises ImportError) can evaluate the string expression faster than plain vectorized pandas on a genuinely large DataFrame by avoiding intermediate array allocations, similar in spirit to a query planner choosing a faster execution path for the same logical expression. For the small/medium data this course's interview scope covers, that performance angle is a vocabulary point, not a daily tool — the readability win over assign() mid-chain is the real reason to reach for eval() day to day.

Q: "What's the difference between pd.eval() and df.eval(), and when would each one raise on the exact same-looking expression string?" A strong answer, out loud: "df.eval() is the one to reach for almost always — called as a DataFrame method, it computes a new or overwritten column from a string expression, the SELECT-shaped sibling of query()'s WHERE-shaped filtering from Lesson 22. Its column names are already injected as bare local variables in the expression, so amount alone works; an @ prefix is needed only to pull in a genuine outside Python variable, exactly like query()'s own @ rule. pd.eval(), the bare top-level function, has no DataFrame to inject columns from at all — it just evaluates the string against whatever Python locals and globals already exist, so a bare column name like amount raises UndefinedVariableError there; you'd have to spell out clean.amount instead. Both return a new object by default; inplace=True on df.eval() mutates and returns None instead." The signal: naming the query()/eval() WHERE/SELECT pairing, the @ scoping rule shared with query(), and specifically that pd.eval() has zero column awareness on its own — that asymmetry is the part almost everyone gets wrong on first contact.
