dbt environments: dev/CI/prod targets & generate_schema_name

Today's tangible win: a profiles.yml with three named targets — dev, ci, prod — plus a macros/generate_schema_name.sql override that gives every target its own schema automatically, so your own local dbt build, Day 15's CI workflow, and a hypothetical "real" production run can never collide in the same database, even though all three happen to point at the same Postgres instance in this portfolio.

Where this picks up: every lesson from Day 2 onward has quietly used one target, dev, writing to one schema, dbt_dev, with Day 15's CI workflow writing to that exact same schema name too. That was never actually safe — it only ever worked because CI and local runs never happened at the same moment. Today names that gap and closes it, rather than continuing to rely on luck.

1 · The question this repo has never had to answer, until now

So far, "where does dbt build write to" has had one answer everywhere: whatever profiles.yml's single dev target says, which is dbt_dev. Day 15's CI workflow reused that same target and that same schema, which was fine as a first pass but is a real landmine: nothing stops a local dbt build running at the same moment as a CI job from the same PR, both writing to dbt_dev, one truncating or rebuilding a table the other is mid-query against. In a real job this gets worse — a genuine production schedule (Day 7's Airflow DAG, if it ran against a real warehouse) would be writing to that identical schema too, meaning a developer's typo in a local experiment could, in principle, land in the same tables a dashboard reads from.

The fix dbt ships for exactly this is targets: separate, named connection configs inside one profiles.yml, switched with --target. This project has had the shape of targets since Day 2 (one target, dev) without ever needing a second one. Today adds two more and, more importantly, makes the schema each one writes to derive from the target automatically, instead of being a literal string someone has to remember to change.

2 · Three named targets, one Postgres instance

A real company runs dev, CI and prod as genuinely separate databases, often separate clusters entirely. This portfolio runs one postgres:17 container (Day 1), so today's three targets point at the same host and port — the realistic separation here is the schema, not the server. That's a deliberate, named simplification, not a hidden shortcut: say so if asked in an interview, the same way Day 7 named BashOperator-over-Cosmos as a scoped choice rather than hiding it.

3 · generate_schema_name: let the target decide the schema, not a hardcoded string

Three targets with three different schema: values already stops the dev/CI collision from Section 1 — but it's fragile the way any hand-maintained parallel list is: add a fourth target, or a second developer who clones the repo and picks a different schema name by habit, and nothing enforces consistency. dbt's real answer is a macro every project can override, generate_schema_name — the Jinja function dbt itself calls, for every single model, to decide what schema that model's table or view actually lands in. Override it once, and the rule applies project-wide with no per-model configuration at all.

-- macros/generate_schema_name.sql
{% macro generate_schema_name(custom_schema_name, node) -%}

    {%- set default_schema = target.schema -%}
    {%- if target.name == 'prod' -%}

        {#-- prod: a custom schema config (if any) is honored as-is #}
        {%- if custom_schema_name is none -%}
            {{ default_schema }}
        {%- else -%}
            {{ custom_schema_name | trim }}
        {%- endif -%}

    {%- else -%}

        {#-- dev/ci: every schema is suffixed onto the target's own schema,
             so two developers, or a dev run and a CI run, never collide #}
        {%- if custom_schema_name is none -%}
            {{ default_schema }}
        {%- else -%}
            {{ default_schema }}_{{ custom_schema_name | trim }}
        {%- endif -%}

    {%- endif -%}

{%- endmacro %}

target is the same Jinja object Day 10 introduced for target.name-gated logic — here it's what tells the macro which of the three outputs is currently active, without any model needing to know or care. custom_schema_name is whatever a model's own schema: config says (most of this project's models set none, so it's none for all of them today); node is the model being built, unused in this version but part of the macro's required signature regardless.

The behavior this buys: on prod, every model lands exactly where its target's schema: says (dbt_prod, unless a model explicitly overrides it — honored as a deliberate choice, not suffixed away). On dev or ci, dbt still resolves to dbt_dev/dbt_ci today because no model sets a custom schema — but the moment any model does (say, a future marts folder config setting schema: marts), dev and CI get dbt_dev_marts/dbt_ci_marts automatically, never colliding with whatever prod's own dbt_prod_marts or unsuffixed dbt_prod resolves to. This is dbt Labs's own documented default behavior pattern for exactly this dev-vs-prod problem — today's macro is close to what dbt ships out of the box, written out explicitly so the branching is visible rather than assumed.

4 · Confirm it, then wire ci into Day 15's workflow

uv run --project ../dbt_env dbt run --target prod --select stg_restaurants
uv run --project ../dbt_env dbt run --target dev --select stg_restaurants

Expected: the prod run logs dbt_prod.stg_restaurants; the dev run logs dbt_dev.stg_restaurants — same model, same SQL, two different schemas, decided entirely by --target, with zero change to any model file. That's the actual payoff: the separation lives in one macro and one profile, not scattered across every model's config.
