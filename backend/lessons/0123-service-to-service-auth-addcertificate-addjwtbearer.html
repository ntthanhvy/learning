Service-to-service auth, now in C# too

Lesson 31 covered three ways one backend proves its identity to another with no human and no browser involved: a static API key compared in constant time, an OAuth client credentials grant, and mutual TLS. That lesson never got a C# mirror. Today ports the two stronger options — both genuinely first-party ASP.NET Core authentication handlers, not third-party packages bolted on afterward.

1 · The token side: AddJwtBearer validates what client credentials hands back

Lesson 31's client credentials grant exchanges a long-lived secret for a short-lived access token, typically a JWT, sent on every call after that. Go's version left token validation unshown; ASP.NET Core's answer is AddJwtBearer, a first-party Microsoft package wired in with two calls:

builder.Services.AddAuthentication("Bearer")
    .AddJwtBearer(options =>
    {
        // options.Authority / Audience point at the issuer the calling
        // service got its token from -- the authorization server Lesson 31
        // named as client credentials' one extra moving part.
        options.Authority = "https://auth.internal.example.com";
        options.Audience  = "billing-service";
    });

builder.Services.AddAuthorization();

var app = builder.Build();
app.UseAuthentication();
app.UseAuthorization();

app.MapPost("/charge", (ClaimsPrincipal caller) => Results.Ok())
    .RequireAuthorization();  // no valid bearer token -> 401, handler never runs

Nothing about the grant itself changes crossing languages — the calling service still exchanges its own client id and secret for a token out-of-band, same as Lesson 31 described. What C# adds is the receiving half: AddJwtBearer is a prebuilt handler that fetches the issuer's signing keys, validates the token's signature, expiry, issuer, and audience on every request, and populates a ClaimsPrincipal — all before RequireAuthorization() lets the request reach the handler at all.

2 · The building block: AddCertificate, mTLS as a first-party authentication handler

Lesson 31's mTLS section named the strongest option and then stopped at Go's raw tls.Config, since Go has no higher-level abstraction for it. ASP.NET Core does: AddCertificate:

builder.Services.AddAuthentication(
        CertificateAuthenticationDefaults.AuthenticationScheme)
    .AddCertificate(options =>
    {
        // Both on by default -- named here because Lesson 31's Go version
        // left them implicit inside tls.Config instead of spelled out.
        options.ValidateCertificateUse    = true;  // client-auth EKU, or none
        options.ValidateValidityPeriod    = true;  // rechecked every request
        options.RevocationMode            = X509RevocationMode.Online;

        options.Events = new CertificateAuthenticationEvents
        {
            OnCertificateValidated = context =>
            {
                // Lesson 31's "resolve the certificate to an identity" step --
                // here mapped from the cert's subject to a billing-service claim.
                var claims = new[] { new Claim(ClaimTypes.Name,
                    context.ClientCertificate.Subject) };
                context.Principal = new ClaimsPrincipal(
                    new ClaimsIdentity(claims, context.Scheme.Name));
                context.Success();
                return Task.CompletedTask;
            }
        };
    });

Kestrel itself still has to be told to request a client certificate during the handshake — the same tls.Config{ClientAuth: tls.RequireAndVerifyClientCert} job Go's version did by hand, configured in C# via Kestrel's own HttpsConnectionAdapterOptions.ClientCertificateMode. AddCertificate picks up from there: it never performs the handshake, only validates the certificate the handshake already collected and turns it into the claims the rest of the pipeline reads.

The one easy-to-miss detail, straight from Microsoft's own docs: "If authentication fails, this handler returns a 403 (Forbidden) response rather than a 401 (Unauthorized)... because it expects authentication to occur during the initial TLS connection. By the time it reaches the handler, it's too late. There's no way to upgrade the connection from an anonymous connection to one with a certificate." A caller debugging a failed mTLS call that expects a 401, the usual "you're not authenticated" code, will be confused by a 403 instead — worth knowing before it shows up in a log.

3 · What doesn't change crossing languages

Lesson 31's rule of thumb still applies untouched: static API key for a handful of internal services you fully control; client credentials when a third party or many independent callers need short-lived, revocable tokens; mTLS when the platform already provides certificate infrastructure or the bar genuinely requires no secret in the request at all. None of the three is "more secure" in the abstract — each trades complexity for a different guarantee, same verdict either language.

Scope line

This lesson covers AddJwtBearer as the C# mechanism for validating a client-credentials token, and AddCertificate as the C# mechanism for mTLS identity validation after the TLS handshake. It does not cover Kestrel's own HttpsConnectionAdapterOptions certificate-request configuration in depth, token issuance (running your own authorization server), or certificate-authority/rotation infrastructure — Lesson 31 already scoped certificate-management infrastructure itself as out of bounds per MISSION.md, and that line holds here too. The static-API-key option is not re-ported; Lesson 122's CryptographicOperations.FixedTimeEquals already covers the C# constant-time comparison that option needs.
