1 · The gap Day 33 named and Day 36 deliberately left open

Day 11 introduced dbt_utils and named two macros worth a future look: generate_surrogate_key (built that same day) and, in the same sentence, date_spine/generate_series together as "for the day a calendar table is needed." Day 36 picked up date_spine and built a real fix with it — every (city, order_date) pair in mart_delivery_sla, including the ones with zero orders. Day 33's own closing note then named generate_series by itself as a second, separate candidate, "never built hands-on." It's worth being honest about why it sat untouched for twelve more lessons: date_spine and generate_series look like the same macro with two names, and once date_spine closed the one gap this project actually had on a date axis, nothing forced a second look.

They are not the same macro. date_spine(datepart, start_date, end_date) generates a row per date — it knows about calendars, day/week/month parts, and date arithmetic. dbt_utils.generate_series(upper_bound) generates a row per plain integer, 1 through upper_bound, and knows nothing about dates at all. Using generate_series to build Day 36's calendar would mean manually adding integers to a base date — strictly more work than just calling date_spine, which is exactly why today doesn't reuse Day 36's problem. Today's gap is on a different axis entirely: mart_delivery_sla answers "what share of orders breached the 45-minute SLA," a single number per city per day, but nobody building this repo has ever asked the shape-of-the-whole-distribution question — how many orders land in each 5-minute delivery-time band, from fast to slow. That needs a grid of numbers, not dates, which is precisely what generate_series is for.

2 · generate_series: a plain integer ladder, nothing queried

generate_series takes exactly one argument, upper_bound, and always starts counting at 1 — there is no lower_bound parameter to pass in this version of the package. It compiles to a small recursive CTE (powers-of-two cross joins under the hood, not a loop) that emits a single column, generated_number, holding every integer from 1 to upper_bound — queried from nothing, purely generated, the same "a package macro is still just Jinja producing SQL" habit Day 11 and Day 36 both used. Confirmed this round by reading the installed macro's own source rather than guessing: the call wraps a full with p as (...), unioned as (...) select * from unioned ... order by generated_number statement, so it has to sit inside a CTE's parentheses — with my_cte as ( {{ dbt_utils.generate_series(20) }} ) — not after a bare from the way a table name would.

Two new project variables make the bucket width and count configurable, the same var() habit Day 10 built for the SLA threshold — add them to dbt_project.yml, alongside Day 10's sla_threshold_minutes:

# dbt_project.yml -- alongside the existing sla_threshold_minutes
vars:
  sla_threshold_minutes: 45
  histogram_bucket_minutes: 5
  histogram_bucket_count: 20

Twenty buckets of five minutes each covers 0-100 minutes, comfortably past Day 6's 45-minute SLA line with room to see how long the real tail is — a detail the SLA share alone can never show, since "32% of orders breach 45 minutes" says nothing about whether the breaching orders take 46 minutes or 3 hours.

3 · Build: a bucket grid, left-joined onto real durations

In your food-delivery-pipeline repo, create models/marts/mart_delivery_time_histogram.sql in full — the join shape reuses Day 6's order_durations CTE exactly, then crosses a generate_series-built bucket ladder against it the same way Day 36 crossed date_spine against stg_restaurants' distinct cities:

-- models/marts/mart_delivery_time_histogram.sql
{{ config(materialized='table') }}

with order_durations as (
    -- same join shape as mart_delivery_sla since Day 6: orders, restaurants,
    -- and the placed/delivered pair of stg_order_events rows per order
    select
        o.order_id,
        r.city,
        extract(epoch from (d.delivered_at - p.placed_at)) / 60 as minutes_to_deliver
    from {{ ref('stg_orders') }} as o
    inner join {{ ref('stg_restaurants') }} as r on o.restaurant_id = r.restaurant_id
    inner join {{ ref('stg_order_events') }} as p
        on o.order_id = p.order_id and p.status = 'placed'
    inner join {{ ref('stg_order_events') }} as d
        on o.order_id = d.order_id and d.status = 'delivered'
),

-- the generate_series call must sit inside a CTE's parens -- it compiles to
-- its own full "with ... select ..." statement, not a bare table expression
bucket_series as (
    {{ dbt_utils.generate_series(var('histogram_bucket_count')) }}
),

bucket_grid as (
    select
        (generated_number - 1) * {{ var('histogram_bucket_minutes') }} as bucket_start_minutes,
        generated_number * {{ var('histogram_bucket_minutes') }} as bucket_end_minutes
    from bucket_series
),

bucketed_orders as (
    select
        bucket_grid.bucket_start_minutes,
        bucket_grid.bucket_end_minutes,
        count(order_durations.order_id) as order_count
    from bucket_grid
    left join order_durations
        on order_durations.minutes_to_deliver >= bucket_grid.bucket_start_minutes
        and order_durations.minutes_to_deliver < bucket_grid.bucket_end_minutes
    group by bucket_grid.bucket_start_minutes, bucket_grid.bucket_end_minutes
)

select
    {{ dbt_utils.generate_surrogate_key(['bucket_start_minutes']) }} as bucket_key,
    bucket_start_minutes,
    bucket_end_minutes,
    order_count
from bucketed_orders
order by bucket_start_minutes

The join direction is the entire fix, same lesson Day 36 already taught on the date axis: starting from bucket_grid and left join-ing the real durations onto it means every one of the twenty buckets survives even when zero orders land inside it, and count(order_durations.order_id) — not count(*) — correctly returns 0 rather than 1 for a bucket whose join found nothing, since count() on a named column ignores the nulls a failed left join produces. Add a schema file testing the one thing that actually matters here — that the grid itself is complete and unique, not that any particular bucket holds a particular count:

    description: "One row per delivery-time bucket (5-minute width, 0 to 100 minutes). Every bucket appears even with zero orders in it, built from dbt_utils.generate_series crossed with a left join onto real order durations."

        data_tests:

4 · Why this is a different question than mart_delivery_sla, not a duplicate of it

It's worth being precise about why this mart earns its place next to mart_delivery_sla instead of just restating it. mart_delivery_sla answers one number per city per day: the share over 45 minutes, using is_sla_breach() from Day 10. That number is exactly right for "are we meeting the SLA," and exactly wrong for "how bad is it when we miss" — a city sitting at a 10% breach rate could mean ten orders each five minutes late, or two orders each ninety minutes late, and the share alone can't tell those apart. mart_delivery_time_histogram answers the second question: the full shape of how long deliveries actually take, bucket by bucket, with the zero-order buckets visible so a reader can see exactly where the distribution's real mass and real tail sit, not just where it crosses one line.

The same silent-gap failure mode Day 36 fixed on the date axis exists here on the duration axis, and for an identical reason: before today, a plain group by on a bucketed minutes_to_deliver could only ever produce a row for a bucket that had at least one order in it. A fast-growing city with no deliveries yet in the 95-100 minute bucket — good news — would simply have no row there, indistinguishable from "this bucket doesn't exist" to anyone who doesn't already know the full bucket range by heart. Querying min(bucket_start_minutes)/max(bucket_start_minutes) against today's table will correctly return 0 and 95 regardless of which buckets have real orders in them — proof the grid, not the data, defines the table's shape.

Q: "Your SLA dashboard shows a city breaching 45 minutes 10% of the time. What's missing from that number, and how would you show it?" A strong answer, out loud: "A single breach-rate number collapses the whole distribution of delivery times into one point, so it can't distinguish ten orders five minutes late from two orders ninety minutes late — very different operational problems that look identical in that one percentage. I'd build a histogram mart instead: fixed-width time buckets, one row per bucket, counting how many orders fall in each. The trick is making sure empty buckets still show up as zero instead of silently disappearing, the same gap-filling problem as a sparse calendar — I generate the full bucket grid first with dbt_utils.generate_series, which emits a plain row of integers from 1 to N, then left-join the real order counts onto that grid and coalesce with count() on a named column so an empty bucket reads as a real zero, not a missing row. That gives an operator the actual shape of delivery times, not just whether one line was crossed." The signal: naming the SLA share's real blind spot precisely, and describing the grid-then-left-join fix as the general pattern it is, not a one-off trick.

Scope line

This lesson covers dbt_utils.generate_series as a plain-integer gap-filling grid, applied to a new delivery-time histogram mart. It does not cover city- or restaurant-level breakdowns of the histogram (today's grid is global, across all cities) — a cross join against stg_restaurants' distinct cities, the exact pattern Day 36 used for the date axis, is the direct next step if a per-city breakdown is ever needed. It also does not touch mart_delivery_sla itself; the two marts answer different questions side by side; today neither edits nor replaces Day 6's.
