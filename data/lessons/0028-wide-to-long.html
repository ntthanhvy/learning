pd.wide_to_long(): melting several metrics at once

Lesson 26's other named candidate, deferred once already for .map() — re-grepped every lesson body and the glossary before writing, still genuinely absent. This closes out the reshape family (Lessons 6, 14, 15, 17, 18) with the one tool built specifically for "several related columns share a suffix and belong together as one row."

1 · The shape: several value columns, sharing a naming pattern

Lesson 6's melt() turns wide columns into long rows one value at a time — every non-id column becomes its own row, no matter what it's named. That's fine when there's only one kind of value being un-pivoted. But a common real-world wide table has several related columns per "thing," named with a shared prefix and a distinguishing suffix — amount_1/amount_2, order_date_1/order_date_2 for a customer's first and second visit. Melting that with plain melt() flattens everything into one undifferentiated variable/value pair, losing the fact that amount_1 and order_date_1 belong to the same visit:

wide.melt(id_vars="customer")
#   customer      variable       value
#0       An      amount_1       120.0
#1     Binh      amount_1        35.5
#2       An      amount_2        42.0
#3     Binh      amount_2       180.0
#4       An  order_date_1  2026-01-05
#5     Binh  order_date_1  2026-01-06
#...  -- amount_1 and order_date_1 are now unrelated rows, no way to re-pair them

pd.wide_to_long() is built exactly for this: it melts multiple stub-prefixed column groups at once, re-pairing same-suffix columns back into one row.

2 · Reading the call: stubnames, i, j, sep, suffix

wide.columns.tolist()
# ['customer', 'amount_1', 'amount_2', 'order_date_1', 'order_date_2']

pd.wide_to_long(wide, stubnames=["amount", "order_date"],
                 i="customer", j="visit", sep="_", suffix=r"\d+")
#                amount  order_date
# customer visit
# An       1       120.0  2026-01-05
# Binh     1        35.5  2026-01-06
# An       2        42.0  2026-01-10
# Binh     2       180.0  2026-01-09
  • stubnames — the shared prefixes to melt together: every amount_* column collapses into one amount column; every order_date_* column collapses into one order_date column.
  • i — the existing column(s) that already uniquely identify each entity (like id_vars in melt()) — here, customer. Must be unique per row, or it raises ValueError: the id variables need to uniquely identify each row.
  • j — the name for the new column holding the suffix (1/2 here) — melt()'s var_name, but numeric and paired across every stub at once.
  • sep/suffix — how to split each column name into stub + suffix: sep="_" means split on the underscore, suffix=r"\d+" (a regex) means the suffix must be digits. Both default to "" and r"\d+" — pass sep explicitly whenever your columns use one, as here.

Note the result comes back with customer and visit as a MultiIndex on the rows this time (Lessons 14/15 built one on columns) — call .reset_index() to get plain columns back, same reflex as unstacking.

3 · Building the wide table to see where this fits in a pipeline

In practice you rarely start with columns already named amount_1/amount_2 — you build them, usually with pivot_table (Lesson 6), then reshape back with wide_to_long when a downstream step needs long format again. Numbering each customer's visits first with groupby().cumcount() (Lesson 4's split-apply-combine, computing a per-group running position):

clean["visit"] = clean.groupby("customer").cumcount() + 1
wide = clean.pivot_table(index="customer", columns="visit",
                          values=["amount", "order_date"], aggfunc="first")
wide.columns = [f"{a}_{b}" for a, b in wide.columns]  # flatten the MultiIndex, Lesson 14's move
wide = wide.reset_index()

This round-trip — long → wide (pivot_table) → long again (wide_to_long) — is a realistic ETL shape: a report needs the wide "one row per customer, columns per visit" view, but a downstream aggregation step needs long rows back. melt() alone can't cleanly reverse a multi-metric pivot; wide_to_long() can.

4 · The gotcha: a wrong/missing stubname doesn't raise — it silently NaNs

Hand-verified on this course's fixture: passing a stubnames entry that doesn't match any real column prefix does not error at all — it adds that column to the result filled entirely with NaN, same "no crash, quietly wrong" shape this course has flagged since Lesson 19 (nunique()'s truthy Ellipsis, Lesson 24's NaN-into-default-branch, Lesson 25's fixed-category NaN, Lesson 27's .map() unmatched key):

pd.wide_to_long(wide, stubnames=["amount", "nonexistent"],
                 i="customer", j="visit", sep="_", suffix=r"\d+")
# ...  amount  nonexistent
# ...   120.0          NaN     <- "nonexistent" was never a real column -- no error
# ...    35.5          NaN

Double-check the result's column list and row count against what you expect (rows = original rows × number of suffixes) before trusting a wide_to_long call — a typo'd stub name won't tell you it's wrong.

Q: "melt() vs wide_to_long() — when do you reach for which?" A strong answer, out loud: "melt() un-pivots one kind of value at a time — every non-id column becomes its own variable/value row, with no relationship between them. wide_to_long() handles the case where several columns share a naming pattern, like amount_1/amount_2 and date_1/date_2, and need to be melted together so same-suffix columns land back in the same row. It's the tool for 'multiple repeated measurements per entity' wide tables — survey data with q1_score/q1_time, q2_score/q2_time, or a customer's numbered visits. If I only have one value column to un-pivot, melt() is simpler and I reach for that first." The signal: naming the multi-column-group pairing as the actual differentiator, not just "a fancier melt."
