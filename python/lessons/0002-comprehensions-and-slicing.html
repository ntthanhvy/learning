Comprehensions & slicing: retiring the loop

Day 1 was the object model — what = really does. Today spends that rule: the reason a comprehension always builds a new list, never touching the old one, is exactly the rebinding-vs-mutation split from yesterday. This lesson has one job: read and write a list comprehension without hesitation, plus enough slicing to stop writing manual index loops.

Bridge from SQL: a list comprehension is a SELECT ... FROM ... WHERE ... squeezed onto one line. [x for x in rows if x > 0] reads exactly like select x from rows where x > 0 — same three parts, same order, same meaning. If SQL is comfortable, this is not new logic, only new punctuation.

1 · The loop shape this replaces

Section 6 of Day 1 ended with this clean() function, deliberately written with a plain for loop because comprehensions hadn't been taught yet:

def clean(records):
    out = []
    for r in records:
        out.append({**r, "name": r["name"].strip()})
    return out

Look at its shape, ignoring the details: make an empty list, loop over something, append one transformed item per iteration, return the list. That shape — empty list, loop, append, done — is so common that Python gives it its own syntax. Whenever a loop's only job is building a new list by appending one item per iteration, a comprehension says the same thing in one line, and says it more clearly because there's no empty list to initialize and no append to misspell.

2 · List comprehensions, piece by piece

Start with the plainest case — a loop that transforms every element:

# loop form
prices = [120.0, 35.5, 99.9]
taxed = []
for p in prices:
    taxed.append(p * 1.1)

# comprehension form — same result
taxed = [p * 1.1 for p in prices]

Read the comprehension left to right as: "build a list of p * 1.1, for each p in prices." The part before for is the expression that becomes each output element; the part after for is exactly the loop header you'd write by hand — same for, same in, same variable name rules.

Add a filter with if, and the SQL parallel becomes exact:

# SQL: SELECT amount FROM sales WHERE amount > 50
sales = [120.0, 35.5, 99.9, 10.0]
big = [amount for amount in sales if amount > 50]
print(big)   # [120.0, 99.9]

Three slots, always in this order: expression (what goes in the output — the SELECT part), for-clause (what you're iterating — the FROM part), if-clause, optional (the WHERE part). Now the clean() function from section 1 in one line:

def clean(records):
    return [{**r, "name": r["name"].strip()} for r in records]

No empty list, no append, no return out on a separate line — and it's still building a brand-new list of new dicts, same as Day 1's non-mutating version. That's not a coincidence: a comprehension can only build a new container, never mutate an existing one, so it structurally can't fall into yesterday's mutation trap.

When not to reach for one: if the loop body needs more than one line of real logic, or does something other than build a list (printing, writing to a file, raising an error), keep the for loop. A comprehension that needs a line break to stay readable has stopped being a readability win. This course would rather you write ten years' worth of maintainable loops than one clever unreadable comprehension.

3 · Dict and set comprehensions — same shape, different brackets

The exact same three-slot idea builds a dict comprehension or a set comprehension. Only the brackets and, for dicts, a colon change:

names = ["An", "Binh", "Chi"]

# list: [ expr for ... ]           — square brackets
lengths = [len(n) for n in names]              # [2, 4, 3]

# dict: { key: value for ... }     — curly braces + colon
name_len = {n: len(n) for n in names}          # {'An': 2, 'Binh': 4, 'Chi': 3}

# set: { expr for ... }            — curly braces, no colon
unique_lengths = {len(n) for n in names}       # {2, 3, 4} — duplicates collapse

You don't need mastery of these two yet — that's genuinely Day 3's job, once dict and set as lookup structures have been taught properly. The goal today is just to recognize the shape: curly braces plus a colon is a dict, curly braces with no colon is a set, square brackets is a list. All three read the same way once you know which bracket you're looking at.

4 · Slicing: seq[start:stop:step]

Indexing a single item — names[0] — should already be familiar from reading Python. Slicing is the same square-bracket syntax extended to grab a range at once, with up to three parts separated by colons:

letters = ["a", "b", "c", "d", "e"]
#            0    1    2    3    4     (and -5  -4  -3  -2  -1 from the right)

letters[1:3]     # ['b', 'c']        — start at 1, stop BEFORE 3
letters[:2]      # ['a', 'b']        — start omitted = from the beginning
letters[3:]      # ['d', 'e']        — stop omitted = to the end
letters[:]      # ['a', 'b', 'c', 'd', 'e']   — a full copy (Day 1, section 4)
letters[::2]     # ['a', 'c', 'e']   — step 2: every second item
letters[::-1]    # ['e', 'd', 'c', 'b', 'a']  — step -1: reversed
letters[-2:]     # ['d', 'e']        — negative index: from the right

The one rule that trips everyone up once, exactly once: stop is never included. letters[1:3] stops before index 3, giving indices 1 and 2 only — two items, not three. That's the same convention as range(1, 3), if that's already familiar from reading loops. Slicing also never raises an error for an out-of-range index — letters[2:100] just returns however much exists, which makes it forgiving for messy, variable-length data.

Slicing works on any sequence — lists, tuples, and strings all support it identically:

header, *rows = ["id,name", "1,An", "2,Binh"]  # preview only — unpacking is Day 4
sku = "SKU-2024-00042"
year = sku[4:8]        # "2024" — slicing a string returns a string
first_three_rows = rows[:3]  # however many of the first 3 rows exist, no crash if fewer

Slicing and comprehensions solve different problems and it's worth keeping them apart: slicing takes a contiguous range by position from one sequence; a comprehension builds a new sequence by transforming or filtering, and can skip around, not just take a run. "First 10 rows" is a slice. "Rows where amount > 50" is a comprehension.

Where pandas goes from here: once data/ introduces DataFrames, the same two ideas reappear as df.iloc[1:3] for slicing and a boolean mask or .query() for filtering. Same concepts, different spelling for a different container — not covered here, that's data/'s job.

5 · Nested access: comprehension and slice together

These compose the way you'd expect — a comprehension's expression can itself contain a slice:

codes = ["VN-Hanoi", "VN-HCMC", "US-NYC"]
country = [c[:2] for c in codes]           # ['VN', 'VN', 'US']
vn_only = [c for c in codes if c[:2] == "VN"]   # ['VN-Hanoi', 'VN-HCMC']

Same three slots as always — expression, for, optional if — just with a slice living inside the expression or the condition. Nothing new is happening here syntactically; this is exactly why the shape is worth owning solidly before moving on.

Q: "When would you use a list comprehension instead of a loop, and when not?" A strong answer, out loud: "When the loop's only job is building a new list by transforming or filtering an existing iterable — one line, one append per iteration. It's the same logic as a SQL SELECT/FROM/WHERE, just Python syntax. I'd keep a plain for loop when the body does more than one thing, needs multiple statements, or isn't building a list at all — readability loses to cleverness at that point." The signal: knowing the shape it replaces, not just the syntax.
