The .dt accessor: pulling parts out of a datetime column

Lesson 31's own teaser named no single dangling candidate, so this round is a fresh scan: Lesson 10 taught the .str accessor for vectorized string operations, but its datetime sibling — the .dt accessor — was never taught, despite order_date being parsed with pd.to_datetime() back in Lesson 2. Today closes that gap: getting year/month/weekday out of a date column without a Python loop.

1 · Parsing is step one — text isn't a date until you say so

Lesson 2 already showed that order_date loads as plain text (object/str dtype) until explicitly converted with pd.to_datetime(). That conversion is the prerequisite for everything below — .dt accessor only exists on a Series whose dtype is already datetime — calling it on the still-text version raises immediately, loudly, before anything can go quietly wrong:

raw["order_date"].dt.year
# AttributeError: Can only use .dt accessor with datetimelike values

clean["order_date"] = pd.to_datetime(clean["order_date"])
clean["order_date"].dtype   # datetime64[us] -- NOW .dt is available

Same cleaned 4-row slice as Lessons 6-31 (An 120.0/01-05, An 42.0/01-10, Binh 35.5/01-06, Binh 180.0/01-09), with order_date parsed this time instead of left as text.

2 · One call, every row: year / month / day

Once parsed, every part of the date is a vectorized one-liner — no .apply(lambda d: d.year) loop needed, same vectorization argument this course has made since Lesson 1:

clean["order_date"].dt.year    # [2026, 2026, 2026, 2026]
clean["order_date"].dt.month   # [1, 1, 1, 1]
clean["order_date"].dt.day     # [5, 10, 6, 9]

SQL cousin: EXTRACT(YEAR FROM order_date) / EXTRACT(MONTH FROM ...) / EXTRACT(DAY FROM ...), or Postgres' DATE_PART().

3 · The weekday tools: day_name() and dayofweek

dt.day_name() gives the human-readable weekday; dt.dayofweek gives its 0-6 integer form (Monday = 0), useful for filtering:

clean["order_date"].dt.day_name()   # ['Monday', 'Saturday', 'Tuesday', 'Friday']
clean["order_date"].dt.dayofweek    # [0, 5, 1, 4]

weekend_mask = clean["order_date"].dt.dayofweek.isin([5, 6])
clean[weekend_mask][["customer", "order_date"]]
#   customer order_date
# 1       An 2026-01-10   <- the only Saturday order

That .isin([5, 6]) is Lesson 29's tool doing real work here — "weekend" isn't one value to equal, it's membership in a small set.

4 · Grouping by a date part

A .dt expression can sit directly inside groupby(), same pattern as Lesson 16's groupby()[col] — group by day-of-week to see which weekday brings in the most revenue:

clean.groupby(clean["order_date"].dt.day_name())["amount"].sum()
# order_date
# Friday      180.0
# Monday      120.0
# Saturday     42.0
# Tuesday      35.5
# Name: amount, dtype: float64   <- sorted alphabetically, NOT Mon-Sun order

Worth flagging out loud: the result group order is alphabetical by default (groupby's usual sort-by-key behavior, Lesson 4), not calendar order — a real report would reindex against an explicit Monday-through-Sunday list before presenting it.

5 · Date arithmetic: subtracting two dates gives a Timedelta

Subtracting one datetime Series from another (or from a single pd.Timestamp) doesn't give a number — it gives a Timedelta Series, which has its own .dt accessor to pull the duration out as a plain integer:

today = pd.Timestamp("2026-08-09")
days_since = (today - clean["order_date"]).dt.days
days_since.tolist()   # [216, 211, 215, 212]

SQL cousin: current_date - order_date (Postgres date subtraction already returns an integer number of days directly — pandas needs the explicit .dt.days step since the intermediate Timedelta object carries more precision than just whole days).

6 · The gotcha: .dt on a NaT row doesn't crash, it goes quietly NaN

Lesson 3 introduced NaT as datetime's missing-value marker. Parsing the raw fixture's blank order_date (order_id 4) with errors="coerce" produces one NaT row — and calling .dt on a Series containing it does not raise, continuing this course's "no crash, quietly wrong" family since Lesson 19:

raw["order_date_parsed"] = pd.to_datetime(raw["order_date"], errors="coerce")
raw["order_date_parsed"].dt.year
# [2026.0, 2026.0, 2026.0, nan, 2026.0, 2026.0]
# order_id 4's NaT row silently becomes NaN -- and note the dtype: the whole
# Series becomes float (2026.0, not 2026 as int), because a column that can
# hold NaN can't stay integer

No exception, no warning — just one row quietly turning into a float NaN plus the whole column's dtype flipping from int-like to float. Same instinct as every prior "no crash" entry in this family: check .isna().sum() before trusting a .dt result on real data with any missing dates in it.

Q: "How would you compute revenue by weekday from an orders table?" A strong answer, out loud: "First I'd confirm the date column is actually parsed as datetime64, not still a string — pandas won't let you use .dt otherwise, it raises immediately, which is actually a helpful guard rail. Once it's parsed, `df.groupby(df['order_date'].dt.day_name())['amount'].sum()` does it in one vectorized line — no Python loop over rows extracting weekdays by hand. I'd also flag that the groupby result sorts alphabetically by default, not Monday-through-Sunday, so I'd reindex against an explicit weekday order before presenting it. And I'd check for NaT first — a missing date doesn't error under .dt, it just silently drops out of one group's total instead." The signal: naming the parse-first requirement, the vectorization win, AND the two gotchas unprompted.
