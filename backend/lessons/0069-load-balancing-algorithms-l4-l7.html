Load balancing: the layer named since Lesson 8, taught for the first time

Lesson 8 put a load balancer in front of your instances on day one and moved straight to the state problem behind it. Lesson 47 had it pull an unready instance out of rotation. Lesson 66 named the API gateway as the layer that often sits right next to it. Sixty lessons later, the load balancer itself — how it actually picks an instance, and at which layer of the stack it's even operating — has never been the subject. Today it is.

1 · Two questions every load balancer answers differently

Every load balancer answers two separate questions, and mixing them up is the most common confusion about the term. First: how much of the request does it look at to make its routing decision? Second: which instance does it pick, given that it has to choose one? The first question is about layer; the second is about algorithm. They're independent — any layer can pair with any algorithm — but tutorials often blur them into one idea because a single product (like nginx or an AWS load balancer) usually ships one default combination.

2 · Layer: L4 sees a connection, L7 sees a request

A L4 load balancer operates at the transport layer: it sees a TCP or UDP connection — source and destination IP, port — and forwards packets without ever opening them up to look inside. It doesn't know or care whether the payload is HTTP, gRPC, or raw binary; it's fast precisely because it isn't parsing any of that. A L7 load balancer operates one layer up: it terminates the HTTP connection, actually reads the method, path, and headers, and can route on any of that — sending /api/* to one backend fleet and /static/* to a CDN-fronted one, or routing by a cookie for A/B testing. The trade-off is exactly what you'd expect from doing more work: L7 costs more CPU per request than L4's blind packet-forwarding, in exchange for decisions L4 structurally cannot make.

Lesson 8's load balancer was always implicitly L7 — routing decisions there never depended on parsing HTTP content, so either layer would have worked, but a real deployment fronting a single HTTP API almost always reaches for L7 today (nginx, an ALB in HTTP mode, Envoy) specifically because content-based routing and Lesson 66's API-gateway-style path splitting need it. L4 shows up lower in the stack — in front of a raw TCP service, or as the layer distributing traffic to a fleet of L7 load balancers themselves.

3 · Algorithm: how the instance actually gets picked

Independent of layer, the load balancer needs a rule for which instance gets the next connection or request:

AlgorithmRuleWeak spot
round robincycle through instances in fixed orderignores that requests take very different amounts of work
least connectionssend to whichever instance has fewest active requestsneeds the balancer to track live state per instance
weighted (either above)bias the pick toward instances flagged as more capableweights are set by a human and go stale as capacity changes

Round robin is the simplest: instance 1, then 2, then 3, then back to 1, forever. It needs no memory of past decisions and is trivially fair by request count — but not by cost, since a request that takes 5ms and one that takes 5s count the same in the rotation, and an instance can end up starved of nothing while quietly buried in slow requests. Least connections fixes exactly that blind spot by tracking, in real time, how many requests each instance is currently handling and routing new ones to whichever has the fewest — better matching real load, at the cost of the balancer having to maintain that live count instead of just cycling a pointer. Either algorithm can be made weighted, giving a beefier instance a larger share — useful on a genuinely heterogeneous fleet, but only as good as the weight a human set, and nothing updates that number automatically as real capacity shifts.

Sticky sessions are a routing override, not a fourth algorithm. Lesson 8 already covered this from the state side: sticky sessions pin a client to one instance regardless of what round robin or least connections would otherwise pick, and Lesson 8's own conclusion stands unchanged here — it treats the symptom (which instance a client hits) rather than the disease (state that shouldn't have been instance-local). Nothing about today's algorithms changes that verdict.

4 · The one input health checks add to either algorithm

Neither round robin nor least connections is complete without an eligibility filter underneath: an instance that's down shouldn't receive a "fair share" of anything. This is exactly the readiness check from Lesson 47 doing double duty — the same endpoint a container orchestrator polls to decide whether to keep a process alive is also what the load balancer itself polls to decide whether an instance stays in the rotation pool at all. Round robin only cycles through instances currently passing that check; least connections only compares live counts among them. A load balancer with no health-check integration will happily keep sending traffic to an instance that's already failing every request — which is precisely the fleet-wide-restart scenario Lesson 47 walked through, just from the routing side of the same failure instead of the process-supervision side.

Q: "Walk me through how you'd load balance a fleet of API instances." A strong answer, out loud: "First I'd pick a layer: since it's a plain HTTP API, I'd use an L7 balancer — nginx, an ALB, or Envoy — so it can terminate the request and route on path or headers, not just L4's IP-and-port view. L4 only makes sense if I'm balancing raw TCP or fronting a fleet of L7 balancers themselves. For the algorithm, I'd start with least connections over plain round robin, since our requests vary a lot in cost and round robin would happily bury one instance in slow work while treating it as 'its fair share.' Either way, the balancer has to respect readiness checks — an instance failing its health check gets excluded from rotation entirely, otherwise it keeps receiving a normal share of traffic while already failing every request. And I'd avoid sticky sessions unless something forces my hand, since it just pins state that should have been externalized in the first place." The signal: naming layer and algorithm as two separate decisions, and tying health checks and sticky sessions back to material already covered instead of treating load balancing as one undifferentiated black box.
