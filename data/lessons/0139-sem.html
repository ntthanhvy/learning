1 · sem() is just std() divided by the square root of the count

Confirmed directly (pandas 3.1.1, numpy 2.5.5) on the same 8-value Series Lesson 137 used:

import numpy as np
import pandas as pd

s = pd.Series([2, 4, 4, 4, 5, 5, 7, 9])

s.sem()                        # 0.7559289460184544
s.std() / np.sqrt(len(s))      # 0.7559289460184544  -- identical, confirmed directly

Series.sem() is not an independent formula — it is confirmed directly to be exactly .std()'s own result divided by the square root of the count, the textbook standard-error-of-the-mean relationship, with no separate implementation or separate default to memorize. Because it is built directly on .std(), it inherits Lesson 137's own ddof=1 (sample) default rather than introducing a new one: s.sem(ddof=0) matches s.std(ddof=0) / np.sqrt(len(s)) exactly, confirmed directly, the same split Lesson 137 already named.

2 · Unlike skew()/kurt(), NaN rows are dropped from BOTH the numerator and the denominator

Confirmed directly, adding one NaN to the same 8 values changes nothing:

s_with_na = pd.Series([2, 4, 4, 4, 5, 5, 7, 9, np.nan])

s_with_na.sem()                                   # 0.7559289460184544  -- identical to Section 1's 8-value result
s_with_na.std() / np.sqrt(s_with_na.count())      # 0.7559289460184544  -- .count() excludes NaN too, confirmed directly

Both halves of the ratio drop the NaN consistently — .std() already ignores it when computing the spread, and dividing by .count() (not len()) means the denominator shrinks to match. There is no silent double-counting trap here; the one genuine trap is Section 3's row-count minimum.

Confirmed directly, the constant-column case flips the pattern Lesson 138 established: a constant column (every value identical) makes .skew() and .kurt() both return NaN, since their formulas divide by a power of the standard deviation — zero in the denominator. .sem() instead returns a real number, 0.0, confirmed directly on a 10-value constant Series — its formula multiplies by the standard deviation in the numerator, so a zero standard deviation produces a real zero, not a division-by-zero NaN. Three methods in the same statistics family, three different constant-column behaviors — .std()/.var() also return a real 0.0 on a constant column, matching .sem() here, not .skew()/.kurt().

3 · sem()'s own minimum row count is lower than skew()'s or kurt()'s

Confirmed directly, looping the non-null count from 0 to 3:

for n in range(4):
    pd.Series(range(n), dtype=float).sem()
# n=0 -> NaN   (no data at all)
# n=1 -> NaN   (ddof=1 divides std's own denominator by zero, same Lesson 137 trap)
# n=2 -> 0.5                 -- first real number
# n=3 -> 0.5773502691896258

A single-value Series's .sem() is NaN for the identical reason Lesson 137 confirmed for .std() itself — ddof=1 divides by count - 1 = 0 before .sem() ever gets to divide again. But two values are already enough for a real .sem() result, confirmed directly — a lower minimum than Lesson 138's .skew() (needs 3) or .kurt() (needs 4), because .sem() never needs a third or fourth central moment, only the plain standard deviation Lesson 137 already covers.

4 · No np.sem() — pandas-only, same as skew() and kurt()

Confirmed directly:

hasattr(np, "sem")  # False

Same pattern as Lesson 138's .skew()/.kurt(), not Lesson 137's .std()/.var(): NumPy has no sem function of its own to disagree with, so there is no cross-library default-mismatch trap to watch for here — the only two confirmed traps are the single-row NaN (Section 3, inherited straight from .std()) and the constant-column 0.0 that looks surprising only if you expect it to echo .skew()/.kurt()'s own NaN (the callout above). DataFrame.sem() runs column-by-column exactly like the rest of this statistics family.

Q: "What's the difference between std() and sem(), and when would you report sem() instead?" A strong answer, out loud: "std() measures how spread out the individual values in a sample are. sem() — standard error of the mean — measures how much the sample mean itself would wander if I drew many different samples of that same size; it's exactly std() divided by the square root of the count, so it shrinks as the sample gets bigger even though std() itself doesn't. I'd report sem() instead of std() when the question is about how trustworthy an average is — like a confidence interval around a mean — rather than how spread out the raw data is. One gotcha I'd flag: a constant column gives sem() a real 0.0, not NaN, which is the opposite of what skew() and kurt() do on the same constant column, since sem()'s formula multiplies by the standard deviation instead of dividing by it." The signal: naming the exact std()/sqrt(count) relationship unprompted, and contrasting the constant-column behavior against skew()/kurt() rather than assuming it behaves the same way.
