1 · Three questions, in the original teaching order

Answer each out loud or on paper before reading the fold-out answer. If one is shaky, note it and go fix it in the practice file below rather than only rereading the old lesson.

Day 104 — types.SimpleNamespace. What actually distinguishes a plain @dataclass from types.SimpleNamespace, given that both allow adding a brand-new attribute after construction — and what does reading a never-set attribute on a SimpleNamespace raise?

Fold-out answer: the real difference is required fields, not post-construction freedom — a dataclass's __init__ demands every declared field and raises TypeError immediately if one is missing, confirmed live, while types.SimpleNamespace() with zero keywords at all is perfectly valid, no fields required. Reading a never-set attribute raises a plain AttributeError — not KeyError, since there is no bracket lookup involved at all — confirmed live: 'types.SimpleNamespace' object has no attribute 'missing'.

Day 105 — locale. After calling locale.setlocale(locale.LC_ALL, "en_US.UTF-8") once inside one function, does a second function elsewhere in the same process that never calls setlocale() itself see the new setting — and is an f-string's {n:,} affected the same way?

Fold-out answer: yes, confirmed live — locale.setlocale() mutates global state for the entire process, not anything scoped to the calling function or module, so every later call anywhere sees the new setting. An f-string's {n:,} is not affected the same way: it always groups with a comma and a period as the decimal point in every locale, confirmed live, completely unaffected by whatever setlocale() was most recently called with — a fixed, English-style convention baked into the format-spec mini-language itself, not a locale lookup.

Day 106 — shelve. Why does db["rec"]["tags"].append("c") silently fail to persist on a normally opened shelf, and what fixes it?

Fold-out answer: a Shelf unpickles a fresh copy of a value every single time it's read by key, confirmed live — so db["rec"]["tags"].append("c") mutates that throwaway in-memory copy only; no assignment to db["rec"] ever happens, so nothing gets written back to disk. Re-opening the shelf afterward shows the append never took effect. shelve.open(path, writeback=True) fixes it by caching every accessed entry in memory and writing all of them back when the shelf closes — confirmed live, the identical mutating code persists correctly once opened that way, at the cost of every touched entry staying cached in memory until close.
Where pandas/NumPy go from here: nothing pandas- or NumPy-specific today — this review only revisits Days 104-106's plain-object attribute access, process-wide locale state, and persistent-dict storage, none of which needs a DataFrame or ndarray to demonstrate. Day 104's own boundary callout (a pandas Series's attribute-style access being a different, index-backed mechanism) is recalled by name only, not re-demonstrated.

2 · Why these three, and why no new terms today

Same interleaving logic as every prior review day: a tool for passing arbitrary named data around with no class declared first, a tool for formatting and parsing numbers the way a specific reader's culture expects instead of one fixed convention, and a tool for a dict that survives the process ending with no schema or SQL required. Three different mental models pulled from three lessons, not one idea restated three ways. They also share a quieter throughline worth naming: all three trade a kind of safety for a kind of convenience, and the retrieval goal is remembering exactly what gets traded away — SimpleNamespace gives up required-field enforcement for zero ceremony, locale gives up a fixed convention for one that genuinely depends on invisible global state (mutated for the whole process, not scoped to a caller), and a normally opened shelve.Shelf gives up in-place mutation working at all in exchange for not having to keep every entry cached in memory.
