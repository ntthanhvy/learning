concurrent.futures: running I/O-bound work at the same time

Every pipeline so far has done one thing, then the next thing, in order — read a file, then parse it, then write the result. That is fine when each step is fast. It falls apart the moment a step is "wait for a slow thing to respond": ten URLs fetched one at a time wait ten times longer than they need to, even though the CPU spends almost all of that time doing nothing but waiting. concurrent.futures is the standard-library way to run several such waits at once.

1 · The problem: waiting is not the same as working

Imagine fetching data from five slow endpoints that each take about one second to respond. Doing it the way every lesson so far has done things — a plain loop — takes about five seconds, because each request waits for the previous one to fully finish before starting:

import time

def fetch(n):
    time.sleep(1)   # stands in for a slow network call
    return f"result {n}"

start = time.perf_counter()
results = [fetch(n) for n in range(5)]
print(time.perf_counter() - start)   # ~5.0 seconds

Nothing in that loop is actually using the CPU during time.sleep(1) — it is purely waiting. I/O-bound work like this is exactly what running things at the same time speeds up: while one wait is pending, the CPU is free to go start another one instead of sitting idle.

2 · ThreadPoolExecutor: run several calls at once, collect the results

The ThreadPoolExecutor from concurrent.futures is the easiest way to do that. with (Day 6) manages its startup and shutdown; .map() applies a function to every item of an iterable, the same shape as the built-in map(), but running several calls concurrently instead of one after another:

import time
from concurrent.futures import ThreadPoolExecutor

def fetch(n):
    time.sleep(1)
    return f"result {n}"

start = time.perf_counter()
with ThreadPoolExecutor(max_workers=5) as pool:
    results = list(pool.map(fetch, range(5)))
print(time.perf_counter() - start)   # ~1.0 second, not ~5.0
print(results)                       # ["result 0", "result 1", ..., "result 4"] -- same order as input

Same five calls, same one-second wait each, but all five waits overlap instead of stacking up — total time tracks the slowest single call, not their sum. max_workers=5 caps how many threads run at once; .map() still returns results in the same order the inputs were given, even though the calls themselves may finish in a different order.

Bridge from SQL: this is the same idea as a connection pool issuing several queries concurrently instead of one connection running them strictly one after another — overlapping independent waits instead of serializing them for no reason.

3 · submit() and Future: when calls need different arguments or you need the first one done

.map() assumes every call uses the same function with one argument each, in a fixed order. submit() is more flexible: it starts one call immediately and hands back a Future — a placeholder for a result that may not exist yet. Calling .result() on it blocks until that specific call finishes:

import time
from concurrent.futures import ThreadPoolExecutor

def fetch(name, delay):
    time.sleep(delay)
    return f"{name} done"

with ThreadPoolExecutor(max_workers=3) as pool:
    future_a = pool.submit(fetch, "slow", 2)
    future_b = pool.submit(fetch, "fast", 0.1)

    print(future_b.result())   # "fast done" -- ready almost immediately
    print(future_a.result())   # "slow done" -- this line blocks until the 2s call finishes

Both calls were already running concurrently the moment submit() returned; asking for future_b's result first costs nothing extra, because it was likely already done. If a submitted call raises an exception instead of returning, .result() re-raises that same exception at the point it's called, rather than swallowing it — a failure inside a background thread does not vanish silently.

4 · Why threads help here but wouldn't for pure computation

CPython — the standard Python interpreter this course runs on — has a Global Interpreter Lock (GIL): only one thread runs Python bytecode at any instant, even on a machine with many CPU cores. That sounds like it should make threads useless for speeding anything up — but the GIL is released automatically the moment a thread blocks on I/O (a network call, a disk read, time.sleep()), which is precisely the case in every example above. While one thread is waiting on I/O with the GIL released, another thread is free to run.

Pure number-crunching is the opposite case: a thread doing arithmetic never blocks on I/O, so it never releases the GIL, and running the same computation across several threads does not go faster — sometimes it's even slightly slower from the added overhead. That CPU-bound case needs concurrent.futures.ProcessPoolExecutor instead, which sidesteps the GIL by using separate OS processes rather than threads — named here as the boundary, not demonstrated, since this course's pipelines are I/O-bound (files, subprocesses, eventually a database and HTTP calls) rather than CPU-bound.

5 · threading itself: what concurrent.futures sits on top of

concurrent.futures is deliberately the easier entry point; the lower-level threading module it's built on is still worth recognizing by sight, because it appears in other people's code constantly. The one concept worth knowing without writing it by hand today: a race condition happens when two threads read and modify the same shared value without coordinating, so the final result depends on unpredictable timing rather than the code's logic. The fix, threading.Lock, acquires exclusive access before touching the shared value and releases it after — a mechanism named here so it's recognizable in the wild, not exercised today, since every example above gives each thread its own independent work with no shared state to corrupt.

Where pandas goes from here: nothing pandas-specific today — concurrent I/O (fetching several files or API responses before building a DataFrame from them) is exactly this module's job either way; pandas itself has no threading API of its own. Not covered further here, per MISSION.md.
