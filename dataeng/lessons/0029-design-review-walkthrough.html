1 · Why a design review, and why now

MISSION.md names the finish line for this whole course as a 10-minute interview-style walkthrough: why ELT, why this split between stream and batch, where data quality is enforced, and what would change at 100× volume. Days 26–28 each answered one slice of that out loud (a one-command demo, a data-quality story, a scaling story). Today is different in kind, not degree: instead of writing one more answer, you run the process a real engineering org uses to pressure-test a design before — or after — it ships, pointed at your own finished repo, and you play both roles, builder and reviewer, honestly.

This matters because a design review catches a different class of problem than a test or a quiz does. dbt build tells you the SQL is correct. A design review asks whether the decisions behind the SQL still make sense together, whether a decision from Day 4 quietly conflicts with one from Day 13, and whether you can defend each one to a skeptical listener without checking the code first. That is exactly the skill an interview's system-design round is testing.

2 · The rubric: six questions, each pointed at a real file

A real design review has a shape: someone walks the system, a reviewer asks "why," and every answer either holds up or becomes a follow-up item. The six questions below are built from this project's own decisions — not generic distributed-systems trivia — and each one names the exact file or lesson to check against, so "I think so" is never good enough; the repo has to confirm it.

#Question to answer out loudCheck against
1Why ELT and not ETL for this pipeline specifically?Day 1's pipeline map; does raw.* actually hold untransformed data, or did a loader quietly clean something first?
2Why does Kafka feed the warehouse instead of writing straight to a mart?Day 6's consumer landing raw.order_events, not a mart, before dbt ever runs on it.
3Where does each of this project's three data-quality layers actually live, and why there?Day 27's table — re-derive it from the real files, don't just recite Day 27's prose.
4Which materialization did each mart get, and does today's real config() block still match the reason given for it?grep -A1 "materialized" warehouse/models/marts/*.sql against Day 4/13's stated reasons.
5What's the single biggest bottleneck at 100×, and is the fix already written down anywhere real?Day 28's SCALING.md — are its three TODOs actually filled with your own numbers, or still template text?
6What's the single weakest, least-tested part of this design, named honestly?Day 27 Section 4's point-in-time join gap, or a new one you find today — a review that finds nothing wrong is a review that didn't look hard enough.

Notice the shape: questions 1–4 ask you to defend a decision against its own stated reason, using a real command against a real file. Questions 5–6 ask what's still open. A design review that only produces "everything's fine" answers hasn't actually functioned as a review — Day 27's own closing section already modeled this by naming two unclosed gaps instead of claiming full coverage, and today extends that habit to the whole repo rather than one lesson's slice of it.

3 · Running the review: play both roles honestly

A design review needs a skeptical voice asking "why," not just a presenter reciting decisions. Since there's no second person available, play the reviewer against your own repo deliberately: for each of the six questions above, first answer it out loud (or in writing) the way you would in an interview, then run the matching "check against" command and see whether the real repo actually backs up what you just said. The gap between what you said from memory and what the command shows is the real finding — not a formality, the actual point of today.

Concretely, for question 4 above:

cd warehouse && grep -A1 "materialized" models/marts/*.sql

Before running it, write down from memory what you expect each mart's materialization to be and why (dim_restaurants: a plain table, since restaurant counts don't scale with order volume — Day 28's own point; fct_orders: incremental with unique_key='order_id', no explicit strategy, which Day 13 found actually means dbt-postgres's own default, delete+insert — not merge; mart_delivery_sla: incremental with incremental_strategy='delete+insert' and a lookback window, from Day 13's second half). Then run the command and compare. If your own project's file matches, that's a decision you can genuinely defend, not just recite. If it doesn't match — a mart you changed since, or a detail you misremembered — that mismatch is today's first real review finding, and it goes in the write-up in Section 4, not quietly fixed and forgotten.

5 · What a design review is not

Three things today's walkthrough deliberately isn't, so the scope stays honest: it is not a security review (no secrets/auth surface exists in this local-only project to review — MISSION.md's own "no cloud account, no paid services" constraint rules that out); it is not a performance benchmark (Day 28 already did the back-of-envelope capacity math — today re-derives the decisions, not the arithmetic); and it is not a second code-review pass hunting for bugs in SQL or Python syntax (that's what dbt build and py_compile already do on every prior day). A design review asks only "do the stated decisions, taken together, still make sense," which is a narrower and different question than any of those three.

Q: "Walk me through a design review you'd run on your own project before calling it done." A strong answer, out loud: "I'd run six questions against the real repo, not from memory alone: why ELT over ETL, why Kafka lands into the warehouse rather than writing a mart directly, where each of my three data-quality layers actually lives and why there, whether my materialization choices still match the reasons I gave for them when I check the real config blocks, what the single biggest bottleneck is at 100x and whether the fix is actually written down, and — the one people skip — what's the weakest, least-tested part of this design. For me that's the point-in-time commission join: its correctness depends on a windowing boundary that no generic test shape covers, and until I wrote a dedicated test for it, nothing would have caught a regression there. A review that only finds things that are fine isn't a real review." The signal: naming a real, specific weak point instead of claiming full coverage, and backing every claim with a command against the actual repo rather than reciting from memory.
