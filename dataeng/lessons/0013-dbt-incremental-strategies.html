1 · What Day 4 actually shipped, and the gap in it

Day 4's fct_orders set materialized='incremental' and unique_key='order_id', but never named a incremental_strategy — and on dbt-postgres specifically, that silence has a real, current answer worth knowing rather than assuming: with a unique_key set and no strategy named, dbt-postgres's own default falls back to delete+insert, not the merge a learner coming from Snowflake or BigQuery tutorials might expect. Postgres didn't gain a native MERGE statement until version 15, so for a long time delete+insert was the only sane implementation of "update existing rows, insert new ones" — dbt-postgres still defaults to it today, and only uses a real MERGE when a model asks for it explicitly.

StrategyHow it actually runs on PostgresNeeds unique_key?
appendplain insert of whatever the filtered select returns — no attempt to touch existing rowsno
delete+insertdelete every row whose key appears in the new batch, then insert the whole batch — dbt-postgres's own default once unique_key is setyes
mergea real Postgres MERGE statement: existing keys get updated in place, new keys get inserted, in one statementyes

An incremental strategy is the specific mechanism an incremental model uses to reconcile new data with what's already there — Day 4 taught that an incremental model does less work after the first run; today is about which of three real ways dbt-postgres does that reconciliation, and that the choice is a real, settable config, not a detail dbt hides from you.

2 · Build: make fct_orders's strategy explicit

Add incremental_strategy='merge' to fct_orders.sql's existing config() block — nothing else in the model changes:

-- models/marts/fct_orders.sql -- config() block only, rest of the model unchanged from Day 4
{{
    config(
        materialized='incremental',
        unique_key='order_id',
        incremental_strategy='TODO'
    )
}}

Fill in 'merge'. dbt compile --select fct_orders (against your own live Postgres, which Day 10 already showed needs a real connection, unlike dbt parse) now renders a genuine merge into ... using ... on (...) when matched then update set ... when not matched then insert ... statement instead of the delete from ... where (order_id) in (...); insert into ... pair Day 4's build was silently running. Same end state on a normal run, one SQL statement instead of two — worth naming explicitly, since "one statement" is also why merge is the right choice whenever an incremental model runs inside a transaction alongside other writes and a partial delete-without-the-matching-insert would be a real, if temporary, correctness gap that merge can't have.

3 · The gap neither strategy closes on its own

Run a real test before writing any more SQL. Hand-edit one already-landed order's subtotal directly in raw.orders — the kind of late correction a real upstream system does occasionally send:

docker compose exec -T postgres psql -U fdp -d fdp -c \
  "UPDATE raw.orders SET subtotal = 999.0 WHERE order_id = 101;"
uv run --project ../dbt_env dbt build --select fct_orders

Expected — merge runs, but touches nothing:

1 of 1 OK created sql incremental model dbt_dev.fct_orders ...... [MERGE 0 in 0.13s]

MERGE 0, not an updated row. Check fct_orders itself and the correction isn't there:

docker compose exec -T postgres psql -U fdp -d fdp -c \
  "SELECT order_id, subtotal FROM dbt_dev.fct_orders WHERE order_id = 101;"
 order_id | subtotal
----------+----------
      101 |     50.0
(1 row)

This is the gap the strategy alone can never close, and it's worth being precise about why: fct_orders's {% if is_incremental() %} filter selects rows where placed_at > max(placed_at) already in {{ this }} — and order 101's placed_at never changed, only its subtotal did. The row is never even selected by the incremental query, so merge never gets a chance to update it — merge reconciles whatever the filtered select hands it, and the filter is what decides what that is. A strategy is downstream of the filter, not a substitute for thinking about it.

Say this part out loud in an interview: "incremental strategy" and "incremental filter" are two different decisions. merge vs. delete+insert vs. append answers "once I have the new batch, how do I reconcile it with the table." The is_incremental() filter answers a completely different question — "which rows count as the new batch at all" — and a filter keyed on the wrong column silently drops late corrections no matter which strategy sits underneath it.

The fix that actually reaches order 101 is the blunt one, and it's worth running once here to see it work:

uv run --project ../dbt_env dbt run --select fct_orders --full-refresh
docker compose exec -T postgres psql -U fdp -d fdp -c \
  "SELECT order_id, subtotal FROM dbt_dev.fct_orders WHERE order_id = 101;"
 order_id | subtotal
----------+----------
      101 |    999.0
(1 row)

--full-refresh drops the table and reruns the model's full, unfiltered select — every row, ignoring is_incremental() for this one invocation. Correct, and expensive: for fct_orders today that's 500 rows, trivial; for a table with a year of history it's exactly the cost incremental models exist to avoid. It's the fallback for "the filter missed something," not something to run on a schedule — a scheduled --full-refresh is a full-table rebuild wearing an incremental model's name.

4 · Build: mart_delivery_sla has this problem for real

Undo the test correction (UPDATE raw.orders SET subtotal = 50.0 WHERE order_id = 101;) before continuing. Now look at mart_delivery_sla with today's lens: it's been a plain table since Day 6, rebuilt in full on every run — fine while the whole pipeline is a scratch dataset, genuinely wasteful once raw.order_events has real volume, per the exact same "large, append-heavy, don't reprocess it all" signal Day 4 used to justify fct_orders' own incremental config.

But this mart has a wrinkle fct_orders doesn't: its grain isn't "one row per event," it's one row per city per order_date, built by joining a placed event to a delivered event that can arrive later — Day 6's own SQL deliberately uses an inner join to delivered, so any order still in flight is silently excluded from every day-bucket it touches until its delivered event lands, sometimes a day after placed. A naive incremental filter on "only process new events" would compute that day's aggregate too early, from a delivered event that hadn't shown up yet, and never revisit it — the exact late-arriving event problem this course's own domain has been quietly capable of since Day 6.

delete+insert, not merge, is the right tool here, and the reason is the grain: merge's when matched then update only touches the exact columns of an exact matching row — useful when one key maps to one row whose individual fields might change. Here, a late delivered event changes an aggregate (delivered_orders, avg_minutes_to_deliver, share_over_45_min) computed over a whole day-bucket, so the correct action is "throw away that bucket's row and recompute it from scratch," which is exactly what delete+insert does — delete anything sharing a key with the new batch, then insert the freshly computed replacement.

-- models/marts/mart_delivery_sla.sql -- add this config() block above the existing CTEs
{{
    config(
        materialized='TODO',
        unique_key='sla_key',
        incremental_strategy='TODO'
    )
}}

-- ...Day 6's placed/delivered/order_durations CTEs and final select, unchanged...

-- TODO: add an {% if is_incremental() %} filter as a HAVING clause on the final
-- select's GROUP BY, re-processing any day bucket from the last 2 days already in
-- {{ this }} onward -- a short lookback window, not just "rows newer than last run",
-- specifically so a delivered event landing a day late still gets folded into the
-- right bucket instead of only ever appearing in whatever day dbt happens to run.

Fill in materialized='incremental' and incremental_strategy='delete+insert', and write the HAVING filter yourself — the day's actual skill. A 2-day lookback means: on every run, recompute not just brand-new buckets but also the last couple of days' buckets, in case a delivered event for one of them only just arrived. Pick the window to comfortably exceed how late a delivery event realistically lands; too short and you reproduce today's exact bug, too long and you're most of the way back to a full rebuild.

5 · Prove it against a real late arrival

Confirm before today's fix: pick an order placed roughly a day ago with no delivered event yet (or plant one), run dbt build --select mart_delivery_sla, note that day's bucket has one fewer delivered order than it should, then land that order's delivered event into raw.order_events and run the build again:

uv run --project ../dbt_env dbt build --select mart_delivery_sla

Expected, with a genuinely new delivery bucket plus one late-arriving correction to yesterday's bucket already reflected — this round's own verification reproduced exactly this against a live Postgres, with two delivered orders in one city-day and a late-arriving one-order city-day one day after:

1 of 1 OK created sql incremental model dbt_dev.mart_delivery_sla ...... [INSERT 0 2 in 0.07s]
docker compose exec -T postgres psql -U fdp -d fdp -c \
  "SELECT city, order_date, delivered_orders FROM dbt_dev.mart_delivery_sla ORDER BY order_date;"
  city  | order_date | delivered_orders
--------+------------+-------------------
 Hanoi  | 2026-09-25 |                 2
 Hanoi  | 2026-09-26 |                 1
(2 rows)

INSERT 0 2 is delete+insert visibly doing its job: two day-buckets were deleted and reinserted this run (not just one new row appended), because the lookback window correctly decided both were worth recomputing. Compare that to what an append-only filter would have done: inserted a duplicate, wrong-totals row for whichever bucket the late event landed in, permanently under-reporting delivered orders for that day.

Q: "Walk me through the incremental strategies dbt offers, and how you'd choose between them." A strong answer, out loud: "append is the simplest: no unique_key, just insert whatever the filter selects — fine when a row, once written, never changes again. Once rows can be updated after the fact, you need a unique_key and a real reconciliation strategy: delete+insert deletes any existing row sharing a key with the new batch and reinserts the whole batch, which is dbt-postgres's own default once unique_key is set, since Postgres didn't have a native MERGE until version 15. merge does the same reconciliation as one real MERGE statement, updating matching keys in place instead of delete-then-insert, which matters when you care about single-statement atomicity or need per-column update control. But neither strategy fixes a filter problem: if your is_incremental() condition never re-selects a row that changed, no strategy underneath it gets a chance to touch it — in my project, a correction to an order's subtotal was invisible to fct_orders because the filter only checked placed_at, and the fix was either widening the filter or running --full-refresh. And for a model like a daily SLA aggregate where late-arriving events change whole buckets rather than single rows, I use delete+insert with a short lookback window on the filter itself, specifically so a delivery event landing a day late still lands in the right day's number instead of being silently missed." The signal: strategy and filter are named as two separate decisions, and the choice between merge and delete+insert is grounded in whether the target changes row-by-row or bucket-by-bucket, not just "merge sounds more advanced."
