The write-ahead log: the fourth letter of ACID, finally named

Lesson 6 named atomicity and walked straight into a lost-update bug without ever naming the guarantee that makes a committed transaction survive a crash. Lesson 55 mentioned "one WAL entry per row" in passing, twice, and moved on. Lesson 85 explained that a replica "replays the primary's stream of committed changes" without ever saying what that stream physically is. All three point at the same mechanism. Today names it.

1 · The question Lesson 6 never answered

Lesson 6 split a transaction's guarantee into atomicity (all statements commit together, or none do) and picked apart a lost-update bug from there. It never asked the other obvious question: once COMMIT returns, and the client has already been told "done" — what actually guarantees that row still exists if the machine loses power one millisecond later? That guarantee has a name: durability, the "D" in ACID — atomicity, consistency, isolation (Lesson 37), and durability. Postgres could make every write durable the naive way: before returning from COMMIT, flush every changed data page, wherever it lives across a potentially huge table file, all the way to disk. That works, but it's brutally slow — a single-row update to one column would force a full random-access write of an entire 8KB page, every time.

2 · Write the change down first, worry about the table file later

Postgres's actual answer is the write-ahead log (WAL): before a transaction is allowed to report success, Postgres appends a compact description of the change — "row X in table Y changed like this" — to the end of a sequential log file. Appending to the end of a file already open for writing is one of the cheapest disk operations there is: no seeking, no touching the actual table's data pages at all. Only after that append is safely on disk does COMMIT return. The actual table file — the one SELECT reads from — gets updated separately, lazily, in the background, whenever Postgres gets around to it. That laziness is safe precisely because the WAL already has the full story: if Postgres crashes before the table file catches up, it doesn't lose anything, because durability was never resting on the table file being current.

Why "write-ahead": the rule is in the name — the log entry for a change must hit disk before that change is allowed to be reported as committed. Not after, not "eventually." The name describes the ordering guarantee, not just "a log that happens to exist."

3 · What a crash actually recovers

Say Postgres crashes mid-run: some committed transactions' changes made it into the table file already, some are still sitting only in the WAL. On restart, Postgres runs crash recovery: it replays every WAL entry since the last checkpoint against the table files, bringing them up to exactly the state every successful COMMIT promised. A change whose WAL entry made it to disk before the crash comes back, full stop — that's what "committed" meant all along. A change whose WAL entry never made it to disk never happened, and Postgres never told the client it did. Checkpoints exist so recovery doesn't mean replaying the log all the way back to server install: every checkpoint is a promise that everything before it is already safely reflected in the table files, so recovery only replays the tail.

The one-sentence version: the table file is a cache of the WAL's history that Postgres keeps around for fast reads. The WAL is the actual source of truth for "what committed." That's backwards from how it feels reading SQL, where the table looks like the real thing — but durability is built on the log, not the table.

4 · Two things this explains that you already met

Neither Lesson 55 nor Lesson 85 needs a new mechanism now — both were describing WAL behavior without the name.

Earlier momentWhat was actually happening
Lesson 55: "one WAL entry per row, regardless of indexing"every row a bulk DELETE touches needs its own durably-logged change, which is exactly why dropping a whole partition (a metadata change, one WAL entry total) is so much cheaper
Lesson 85: a replica "replays the primary's stream of committed changes"that stream is the WAL — streaming replication ships the primary's write-ahead log over the network, and the replica runs the same replay logic crash recovery uses, just continuously instead of once after a crash

That second row is the payoff: a read replica isn't running some separate replication-specific protocol. It's running ordinary Postgres crash recovery, permanently, fed by a WAL stream arriving over a network instead of from its own crash. Replication lag (Lesson 85) is just "how far behind is this instance's replay of the WAL" — the identical question crash recovery answers once, that a replica answers continuously.

Q: "Why does Postgres write to a log before updating the actual table, instead of just updating the table directly?" A strong answer, out loud: "It's about durability without paying for a full random-access disk write on every commit. Postgres appends a compact record of the change to the write-ahead log — a cheap, sequential append — and only returns from COMMIT once that's safely on disk. The actual table file gets updated lazily afterward. If Postgres crashes in between, recovery replays the WAL since the last checkpoint and the table ends up exactly where every successful COMMIT promised, because the log was always the real source of truth, not the table file." The signal: naming the WAL as the actual durability mechanism, not "Postgres just handles crashes," and connecting it to why the append is cheap.
