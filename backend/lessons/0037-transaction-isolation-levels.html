Transaction isolation levels

Lesson 6 named this in passing while fixing a lost update: "Postgres also offers stricter isolation levels — REPEATABLE READ, SERIALIZABLE — that catch this class of conflict automatically... worth knowing the knob exists." That knob was never actually turned. Today it gets the full treatment: what each level promises, the anomalies each one closes off, and why SERIALIZABLE trades automatic safety for an obligation the caller must honor.

1 · Isolation is a dial, not a switch

Lesson 6 drew the line between two different transaction guarantees: atomicity (your own statements commit together) and isolation (protection from other transactions running at the same time). What that lesson left unsaid: isolation isn't one fixed guarantee — it's a dial with four standard settings, each closing off a different category of interleaving bug at a different cost. Postgres lets you set it per transaction:

BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
-- ...statements...
COMMIT;

Every level below the strictest one is a deliberate trade: allow some specific category of cross-transaction interference, in exchange for less blocking and better throughput. The four levels are named by which categories of anomaly they promise to prevent.

2 · The three anomalies, in order of severity

Each named anomaly is a concrete way one transaction's view can be corrupted by another's:

  • Dirty read — reading another transaction's uncommitted change. If that transaction later rolls back, you acted on data that never actually existed.
  • Non-repeatable read — reading the same row twice inside one transaction and getting two different answers, because another transaction committed a change in between.
  • Phantom read — re-running the same WHERE query twice and getting a different set of rows, because another transaction inserted or deleted a matching row in between.

Notice the escalation: dirty read is about seeing something that was never real at all; non-repeatable read is about a single row changing under you; phantom read is about the row count changing under you — the hardest of the three to guard against, since there's no single row to lock.

3 · The four levels, and what Postgres actually gives you

READ UNCOMMITTEDallowedallowedallowed
READ COMMITTED (default)preventedallowedallowed
REPEATABLE READpreventedpreventedprevented*
SERIALIZABLEpreventedpreventedprevented

Two Postgres-specific footnotes worth knowing, because they surprise people coming from the SQL standard alone: Postgres's READ UNCOMMITTED actually behaves like READ COMMITTED — dirty reads were never implemented, because Postgres's row-versioning storage engine (MVCC) makes them nearly free to prevent regardless of level. And Postgres's REPEATABLE READ already blocks phantom reads too (marked * above) — stricter than the SQL standard technically requires at that level, again a side effect of how its snapshot mechanism works. SERIALIZABLE is the only level that goes further still: it doesn't just prevent these three named anomalies, it guarantees the outcome is equivalent to running every concurrent transaction one at a time in some order — closing off anomaly categories that don't even have their own names, at the cost of a transaction sometimes aborting and asking the caller to retry.

Ties to Lesson 6: Lesson 6's lost-update bug — two transactions both reading remaining = 1, both writing, one commit overwriting the other's effect — happens under Postgres's default READ COMMITTED precisely because that level never promised to stop it; a lost update isn't dirty, non-repeatable, or phantom, it's a write-write conflict on a value both sides read as a separate earlier statement. Lesson 6's two fixes (fold the check into the WHERE, or take a row lock) solve it without touching the isolation level at all. REPEATABLE READ or SERIALIZABLE would also have caught it — Postgres detects the conflict and aborts one transaction — which is exactly the "catches this class of conflict automatically" Lesson 6 gestured at. The difference: Lesson 6's fixes cost nothing extra when there's no conflict; a stricter isolation level costs the same for every transaction, conflict or not, and hands you a new failure mode (the abort) to handle in every single call site instead of just the ones that need it.

4 · SERIALIZABLE's trade: safety in exchange for a retry loop

Nothing above is free. READ COMMITTED almost never blocks or aborts a transaction for isolation reasons — it's fast precisely because it promises the least. SERIALIZABLE promises the most, and pays for it by sometimes aborting a transaction that touched no row the other transaction touched, purely because Postgres can't otherwise guarantee the "as if run one at a time" property. That failure has a specific, checkable error code (Postgres SQLSTATE 40001), and the contract is explicit: the caller is expected to retry the whole transaction from the top.

// ErrSerializationFailure is the sentinel this snippet translates a Postgres
// serialization_failure (SQLSTATE 40001) into, after checking the error
// with errors.As against pgconn.PgError in real pgx code.
var ErrSerializationFailure = errors.New("serialization failure: retry the transaction")

// transferBalance moves amount from one account to another inside a
// SERIALIZABLE transaction. Postgres may abort this transaction with a
// serialization_failure if it detects a conflict with another concurrent
// SERIALIZABLE transaction — the caller is expected to retry from the top.
func transferBalance(ctx context.Context, db DB, fromID, toID int64, amount int) error {
    tx, err := db.BeginTx(ctx, &sql.TxOptions{Isolation: sql.LevelSerializable})
    if err != nil {
        return err
    }
    defer tx.Rollback()

    var fromBalance int
    if err := tx.QueryRowContext(ctx, `SELECT balance FROM accounts WHERE id = $1`, fromID).Scan(&fromBalance); err != nil {
        return err
    }
    if fromBalance < amount {
        return fmt.Errorf("insufficient balance")
    }
    if _, err := tx.ExecContext(ctx, `UPDATE accounts SET balance = balance - $1 WHERE id = $2`, amount, fromID); err != nil {
        return translateSerializationFailure(err)
    }
    if _, err := tx.ExecContext(ctx, `UPDATE accounts SET balance = balance + $1 WHERE id = $2`, amount, toID); err != nil {
        return translateSerializationFailure(err)
    }
    return translateSerializationFailure(tx.Commit())
}

// runWithSerializableRetry retries a SERIALIZABLE transaction a bounded
// number of times on serialization failure — the pattern Postgres's own
// docs recommend, since SERIALIZABLE hands the retry obligation to the caller.
func runWithSerializableRetry(ctx context.Context, attempt func(ctx context.Context) error) error {
    const maxAttempts = 3
    var err error
    for i := 0; i < maxAttempts; i++ {
        err = attempt(ctx)
        if !errors.Is(err, ErrSerializationFailure) {
            return err
        }
    }
    return err
}

That retry loop is the same shape Lesson 32 already taught for a flaky dependency — bounded attempts, give up and surface the error past the cap — applied here to a transaction the database itself asked to be re-run, not a network call that timed out. And it composes with Lesson 26: if the work inside the retried transaction has any side effect visible outside the database (an email, a queued job), the retry is only safe if that side effect is idempotent — a bare SERIALIZABLE retry loop only makes the database writes safe to repeat, nothing else.

Q: "When would you actually reach for SERIALIZABLE instead of Lesson 6's row-lock or check-in-the-WHERE fixes?" A strong answer, out loud: "Those fixes work when I can name the exact conflict up front and fold it into one statement or one lock. SERIALIZABLE is for the harder case — a transaction that reads a set of rows via a WHERE condition, then writes based on what it saw, where the bug would be a phantom read someone else's INSERT causes, not a single row I can lock. It's still not free: I need a bounded retry loop around it, because Postgres aborts on a genuine conflict and expects the caller to re-run the whole transaction, not just fix a status code and move on." The signal: naming phantom reads specifically as the case row-locking can't cover, and knowing the retry loop is mandatory, not optional cleanup.
