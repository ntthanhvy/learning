Error handling: custom exceptions, exception handlers & a consistent error shape

Bridge from SQL: this is a CHECK constraint's error message, standardized. A failed constraint always reports the same shape — which table, which rule, why — regardless of which query tripped it. An app-wide exception handler is that same discipline for HTTP errors: every route that raises OutOfStock gets back the identical JSON shape, instead of each handler inventing its own error body.

1 · The problem: HTTPException everywhere means repeating yourself everywhere

Day 16 taught raise HTTPException(status_code=404, detail="user not found") — correct, and still the right tool for a one-off "this specific request is bad." But once several routes need the same domain rule, that pattern repeats the same status code and message logic in every handler that needs it:

from fastapi import FastAPI, HTTPException

app = FastAPI()
_stock = {"widget": 0, "gadget": 5}

@app.post("/orders/{item}")
def place_order(item: str):
    if _stock.get(item, 0) <= 0:
        raise HTTPException(status_code=409, detail=f"{item} is out of stock")
    _stock[item] -= 1
    return {"item": item, "remaining": _stock[item]}

Fine for one route. But "out of stock" is a rule the *business* owns, not this one handler — a second route that also touches stock would need to copy that exact if/raise pair, and any drift between the two copies (a typo'd message, a different status code) becomes a real bug. The fix is to raise something that names the rule once, and teach the app how to turn it into a response once.

2 · A custom exception, raised where the rule lives

Day 8 already taught this shape: subclass Exception, give the failure a name, carry the data a caller needs to explain it:

class OutOfStock(Exception):
    def __init__(self, item: str):
        self.item = item

Nothing new here — this is the exact InvalidSalesRow pattern from Day 8, reused unchanged. What's different from Day 8 is where it gets caught. A plain script catches a custom exception with a local except InvalidSalesRow: right where the call happens. A FastAPI app instead registers one function, once, that catches it for every route in the whole app:

from fastapi import Request
from fastapi.responses import JSONResponse

@app.exception_handler(OutOfStock)
def handle_out_of_stock(request: Request, exc: OutOfStock):
    return JSONResponse(
        status_code=409,
        content={"error": "out_of_stock", "item": exc.item},
    )

@app.post("/orders/{item}")
def place_order(item: str):
    if _stock.get(item, 0) <= 0:
        raise OutOfStock(item)
    _stock[item] -= 1
    return {"item": item, "remaining": _stock[item]}

The handler now just raises a plain, named exception — Day 8's raise, once again unchanged — and every ounce of "what status code, what body" logic lives in exactly one place: handle_out_of_stock. A second route that can also run out of stock raises the same OutOfStock(item) and gets the identical response, with zero copy-pasted if/raise logic. This is the mechanism Day 22 named but never built — @app.exception_handler(ExcType) registers a function FastAPI calls automatically whenever ExcType (or a subclass of it) escapes a handler uncaught, converting it into the JSONResponse that function returns.

3 · Overriding pydantic's default 422: RequestValidationError

Day 17 showed pydantic rejecting bad input with a ValidationError; wired into FastAPI, a failed request body validation actually raises a related type, RequestValidationError, and returns FastAPI's own default 422 body — a fairly verbose, deeply nested structure listing every failing field. That default is fine to start, but a real API often wants its error responses in one consistent shape, matching whatever handle_out_of_stock above already returns for business errors:

from fastapi.exceptions import RequestValidationError

@app.exception_handler(RequestValidationError)
def handle_validation_error(request: Request, exc: RequestValidationError):
    first = exc.errors()[0]
    return JSONResponse(
        status_code=422,
        content={"error": "validation_failed", "field": first["loc"][-1], "message": first["msg"]},
    )

@app.exception_handler isn't limited to custom exception classes — it registers on any exception type, including ones FastAPI itself raises internally. exc.errors() is a list of every field that failed, each a dict with "loc" (a path to the field, e.g. ("body", "email")) and "msg" (why); this handler picks just the first failure and reshapes it to match handle_out_of_stock's own {"error": ..., ...} shape — same idea as building one row-shape dataclass in Day 7 instead of passing around raw dicts of varying keys, applied to error responses instead of data.

Where pandas goes from here: a pipeline validating a DataFrame's columns (dtype checks, null checks) raises or logs inline where the check runs — there's no app-wide handler to register, because there's no series of independent HTTP requests hitting the same rule from different routes; that's specifically a web-service problem, not a data-transform one.
