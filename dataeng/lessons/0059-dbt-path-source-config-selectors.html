1 · The gap: three methods named, never built

Day 52's own scope line listed path:, source: and config: among the selection methods dbt ships, then set all three aside as "vocabulary only, same pattern as any method not hands-on this round." Day 53 named the same gap again on its way out, as one of three concrete next steps. Nothing about that was wrong to defer — Day 52's actual job was +/@ and tag:, and three new methods in one sitting would have buried the lesson. But the gap is real, and all three answer a question tag: and fqn (a model's bare name, what Day 52 used by default) can't: path: selects by where a model's file lives, source: selects by which raw table a change actually starts from, and config: selects by a property a model was configured with, not by its name, folder or a tag someone remembered to add.

2 · Confirmed live: what each method actually resolves to

Built against a six-model scratch project shaped like this course's real one (the same stg_orders/stg_restaurants/stg_couriers staging layer, and fct_orders/dim_restaurants/dim_couriers/mart_delivery_sla marts, with marts configured +materialized: table and +tags: ["nightly"] at the folder level in dbt_project.yml, staging left at the default view). Every row below is a real dbt list result, not predicted from the docs' prose:

ExpressionWhat it matchesConfirmed result
path:models/stagingevery node whose file lives under that folderstg_couriers, stg_orders, stg_restaurants

source:raw.orders+ is the one worth sitting with: it starts from the raw table itself, not from a model name, which matters because the actual trigger for a rebuild is often "the loader just dropped new rows into raw.orders," not "someone remembers that stg_orders is the model built on top of it." Day 52's @stg_orders needed a human to already know that mapping; source:raw.orders+ doesn't.

A real finding, confirmed live, not assumed: config.tags:nightly resolved to the exact same four marts as Day 52's own tag:nightly — because tag: is dbt's own shorthand for matching one specific list-valued config, tags, and config.tags: reaches the identical underlying field directly. They are not two unrelated mechanisms; tag: is just config.tags: with a shorter name for the one config people reach for constantly. config: is the general tool underneath it — any config key a model sets (materialized, tags, schema, a custom one) is fair game, not just the one dbt gave its own keyword.

3 · Build: three new named selectors, confirmed against your own project

In your food-delivery-pipeline repo, add three selectors to food_delivery_pipeline/selectors.yml, alongside Day 53's two:

selectors:
  # ... build_changed_orders and nightly_marts from Day 53, unchanged ...

  - name: staging_only
    description: "Every staging model, by folder -- not by name or tag, so a new staging model is included automatically the moment its file lands under models/staging."
    definition:
      method: path
      value: models/staging

  - name: changed_from_orders_source
    description: "Start from the raw table itself, not a model name -- everything that reads raw.orders, directly or transitively, once the loader lands new rows."
    definition:
      method: source
      value: raw.orders
      children: true

  - name: all_tables
    description: "Every model materialized as a real table, regardless of folder or tag -- useful before a schema-change check that only tables can be affected by."
    definition:
      method: config.materialized
      value: table

Note the shape: a graph operator still becomes its own boolean key (children: true for the trailing + on source:raw.orders+, same as Day 53's table), and config.materialized becomes a dotted method string — the part after the dot is the config key, confirmed live to resolve identically whether written as method: config.materialized or as the plain CLI string config.materialized:table.

Q: "Your loader just dropped new rows into raw.orders. What's the narrowest dbt command that rebuilds everything affected, and why not just run dbt build?" A strong answer, out loud: "I'd select by the source itself, not by a model name -- source:raw.orders plus the children graph-operator key, which resolves to stg_orders and everything built on top of it transitively, fct_orders and mart_delivery_sla in this project. That's narrower and more honest than a full dbt build, because it starts from the actual trigger -- new rows in a raw table -- rather than from a model name a human has to already know maps to that table. I'd reach for path: instead if the real question were about where code lives rather than what changed -- rebuilding an entire staging folder regardless of which raw table backs each model -- and I'd reach for config: if the question were about a shared property, like every model materialized as a table, independent of both name and folder. Three different questions, three different methods, and tag: turns out to be config.tags: under a shorter name for the one config key people reach for constantly." The signal: picking the method by what's actually known at trigger time (a source name, a path, a config value) instead of defaulting to tag: or a bare model name out of habit.
