Series.median() and np.median(): the sorted-middle value, and the NaN-propagation trap std() doesn't have

Lessons 137-139 closed out a three-lesson statistics arc (.std()/.var()/ddof, .skew()/.kurt(), .sem()) and left no named successor — this round's own fresh scan grepped every lesson body and every glossary row case-insensitively for np.median( and .median(: .median() appears twice already (Lesson 3's missing-value fill, Lesson 49's describe() byline), but only ever as a value plugged into something else, never as its own topic; np.median( had zero hits anywhere across Lessons 1-139. A genuine gap: the two libraries' median functions disagree on NaN in a way none of Lessons 137-139 covered, since .std()/.var()/.skew()/.kurt()/.sem() all drop NaN on both sides already.

1 · median() is the sorted-order middle value — Lesson 3's fill value, built directly

Confirmed directly (pandas 3.1.1, numpy 2.5.5):

import numpy as np
import pandas as pd

s_odd = pd.Series([2, 4, 4, 5, 5, 7, 9])  # 7 values -- one true middle
s_odd.median()                         # 5.0  -- the 4th value once sorted

s_even = pd.Series([1, 2, 3, 4])            # 4 values -- no single middle
s_even.median()                        # 2.5  -- average of the 2nd and 3rd sorted values

Same median concept Lesson 3 already used to fill missing values (it resists outliers better than the mean, since one huge value can't drag the sorted middle far) and the same number describe() (Lesson 49) prints on its own 50% row — this lesson builds the method directly rather than through something else. np.median() computes the identical sorted-middle value on a plain array:

np.median(s_odd.to_numpy())   # 5.0   -- identical to Series.median() above
np.median(s_even.to_numpy())  # 2.5   -- identical even-count average, same rule

2 · The real trap: np.median() propagates NaN; Series.median() skips it

Unlike Lessons 137-139's whole statistics family, where NaN-handling matched on both sides, median is where pandas and NumPy genuinely disagree. Confirmed directly, adding one NaN to the same 8 values from Lesson 137:

s = pd.Series([2, 4, 4, 4, 5, 5, 7, 9, np.nan])

s.median()                   # 4.5   -- pandas drops the NaN, medians the remaining 8 values
np.median(s.to_numpy())      # nan   -- numpy does NOT drop it -- ONE NaN poisons the whole result
np.nanmedian(s.to_numpy())   # 4.5   -- the NaN-aware cousin, matches pandas exactly
Confirmed directly, why this is a sharper trap than it looks: a single stray NaN anywhere in a large array makes plain np.median() return NaN for the entire result, no error or warning raised — not a dropped row, a completely poisoned answer. Converting a pandas column to a raw array with .to_numpy() or .values and then calling np.median() on it (instead of just calling .median() on the Series directly) is exactly how this trap gets triggered in real code, usually when mixing a NumPy-only pipeline with pandas-sourced data. The fix is np.nanmedian(), confirmed directly to match pandas' own NaN-skipping behavior exactly.

3 · Both libraries agree once there's no NaN to disagree about

Confirmed directly, an empty Series and an all-NaN Series both return NaN on the pandas side, and np.median() on an empty array also returns NaN (with a runtime warning, not a crash):

pd.Series([], dtype=float).median()         # nan  -- no data at all
pd.Series([np.nan, np.nan]).median()      # nan  -- data exists, but none of it is usable
np.median(np.array([]))                   # nan  -- numpy agrees here; raises a RuntimeWarning, not an exception

So the disagreement is specifically about a partial NaN — some real values mixed with some missing ones. When every value is missing (or there are no values), both libraries land on the same NaN, matching the pattern Lesson 137 already confirmed for a single-row .std(): no crash, a quiet result that still needs to be read correctly.

4 · np.median(axis=) reduces one axis of a 2-D array, same as np.std() would

Confirmed directly, median is not Series-only — DataFrame.median() runs column-by-column exactly like the rest of this statistics family, and np.median() takes the same axis= parameter this course has used since np.percentile() (Lesson 111):

arr = np.array([[1, 2, 3], [4, 5, 100]])

np.median(arr, axis=0)   # [2.5, 3.5, 51.5]  -- median DOWN each column
np.median(arr, axis=1)   # [2.0, 5.0]        -- median ACROSS each row
np.median(arr)           # 3.5               -- no axis: flattens first, one single number

The 100 outlier in row 2 drags that row's own mean far up, but barely moves its median (5.0, the middle of 4, 5, 100) — the same outlier-resistance Lesson 3 relied on to justify median over mean as a fill value, now visible directly in the raw array.

Q: "You convert a pandas column to a NumPy array and call np.median() on it, and get NaN back even though you can see the column has real values. What happened?" A strong answer, out loud: "np.median() doesn't skip NaN by default — if even one value in the array is NaN, the whole result comes back NaN, silently, no warning. Series.median() on the pandas side does skip NaN automatically, which is why calling .median() directly on the column gives a real number but converting to a raw array first and calling np.median() on that doesn't. The fix is np.nanmedian(), which matches pandas' own behavior exactly. I'd flag this as a reason to stay on the pandas side for a summary stat whenever there's any chance of missing data, rather than dropping to a raw array first." The signal: naming the exact asymmetry (pandas skips, NumPy propagates), naming np.nanmedian() as the fix unprompted, and tying it to Lesson 137's "no crash, quietly wrong" family.
