np.average(): the weighted mean pandas' own .mean() can't compute

Lesson 113's own closing note named three standing candidates — np.average(), np.piecewise(), and apply(result_type="expand") — rather than pre-committing one. A fresh scan of every lesson and the full glossary confirms np.average() is still a genuine zero-hit, and it closes a real gap: Series.mean() and groupby().mean() have no weights= argument at all.

1 · mean() treats every row as equally important — that's not always true

Series.mean() and np.mean() both compute the plain arithmetic average: every value counted once, divided by the count. That's the right answer when every row genuinely carries equal importance. It's the wrong answer the moment rows represent different-sized things — an average order price across orders of very different quantity, an average rating across reviews with very different vote counts, an average score across classes of very different student counts:

orders = pd.DataFrame({
    "customer": ["An", "An", "Binh", "Binh", "Binh"],
    "price":    [100.0, 120.0, 50.0, 55.0, 60.0],
    "qty":      [1, 3, 2, 2, 4],
})
orders.groupby("customer")["price"].mean()
# customer
# An      110.0   -- (100+120)/2, each ORDER counted once, quantity ignored
# Binh     55.0   -- (50+55+60)/3

An's plain mean treats the 1-unit order and the 3-unit order as equally important, when the 3-unit order actually represents three times the units sold at that price. A genuinely quantity-weighted average price is a different, and often more honest, number.

2 · np.average(): the same mean, with an optional weights= argument

np.average() computes the exact same number as np.mean() when called with no weights= — but accepts one, turning the calculation into a genuine weighted mean: each value is scaled by its own weight before summing, and the total is divided by the sum of the weights instead of the plain row count:

an = orders[orders["customer"] == "An"]
np.average(an["price"], weights=an["qty"])
# 115.0  -- (100*1 + 120*3) / (1 + 3) = 460 / 4, NOT (100+120)/2

# manual check, same formula:
(100*1 + 120*3) / (1 + 3)   # 115.0

Confirmed directly (numpy 2.5.4): with no weights= at all, np.average(arr) is byte-identical to np.mean(arr) — the plain mean is just the special case where every weight is equal. Two sharp edges confirmed directly: weights summing to exactly zero raise ZeroDivisionError immediately ("Weights sum to zero, can't be normalized"), not a silent NaN or inf; and a values/weights length mismatch with no axis= raises TypeError outright rather than guessing how to pair them up.

3 · The actual gap: groupby() + mean() has no weights= at all

This is the part worth naming unprompted in an interview: Series.mean(), DataFrame.mean(), and groupby().mean() have no weights= parameter whatsoever — confirmed directly, passing one raises TypeError: GroupBy.mean() got an unexpected keyword argument 'weights'. A per-group weighted average needs groupby().apply() (Lesson 61) reaching down into np.average() one row-group at a time:

orders.groupby("customer").apply(
    lambda g: np.average(g["price"], weights=g["qty"]),
    include_groups=False,
)
# customer
# An      115.00
# Binh     56.25   -- (50*2 + 55*2 + 60*4) / (2+2+4) = 450/8

There is no shortcut around this — no weighted_mean() method anywhere in pandas. np.average() inside groupby().apply() (or the equivalent sum-of-products-over-sum-of-weights formula inside .agg()) is the standard answer, and knowing that gap exists — rather than guessing at a nonexistent mean(weights=...) call mid-interview — is itself the signal.

The trap: np.average() has no skipna concept, same family as Lesson 111's np.percentile() gap. One NaN anywhere in the values or the weights silently poisons the entire result to NaN — confirmed directly, a single missing weight is enough. Clean (or at least explicitly fill) both columns before weighting, the same discipline Lesson 3 already taught for plain aggregates.

4 · Negative weights run quietly — there's no sign check

Confirmed directly: np.average() performs no validation that weights are non-negative. A negative weight is accepted and folded into the sum like any other number, which can pull the "average" outside the actual range of the values entirely — a genuine footgun if a weight column was meant to represent something like a count or a price and a data-entry error let a negative value through unnoticed.

Scope line

This lesson covers np.average()'s default (unweighted) behavior matching np.mean(), the weights= parameter and its sum-of-products-over-sum-of-weights formula, the confirmed ZeroDivisionError/TypeError edge cases, the fact that no pandas method (mean(), groupby().mean()) accepts weights= at all, and the NaN-poisoning/no-sign-check traps. It does not cover returned=True's secondary sum-of-weights output in depth, multi-dimensional axis= weighting, or any statistics/visualization use of weighted means (out of `MISSION.md`'s scope).
