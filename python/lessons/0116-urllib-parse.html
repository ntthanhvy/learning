urllib.parse: taking a URL apart and putting one together

Day 16's FastAPI handlers get path and query parameters handed to them already parsed — the framework does that work for you on the way in. But plenty of real code sits on the other side: building a URL to call another service, logging the exact request that went out, or parsing a URL string that arrived as plain text (a webhook payload, a config value, a pasted link). urllib.parse is the standard-library module for both directions, with no framework required.

1 · urlparse(): breaking a URL string into its named pieces

A URL is not one opaque string — it has a fixed shape: a scheme, a host, a path, and (often) a query string after a ?. urlparse() reads that shape out directly instead of hand-rolling a split on :// and ?:

from urllib.parse import urlparse

url = "https://api.example.com/search?q=hello+world&page=2"
parsed = urlparse(url)
print(parsed.scheme)   # confirmed live: https
print(parsed.netloc)   # confirmed live: api.example.com
print(parsed.path)     # confirmed live: /search
print(parsed.query)    # confirmed live: q=hello+world&page=2

urlparse() returns a single ParseResult object holding every piece as a named attribute — .query here is still one raw string, "q=hello+world&page=2", not yet broken into individual key/value pairs; that's the next section's job.

2 · parse_qs(): the query string as a dict — of lists

A query string can repeat the same key more than once (?tag=py&tag=web is legal and common — think multi-select filters). parse_qs() handles that by giving every key a list of values, even when there's only one:

from urllib.parse import urlparse, parse_qs

url = "https://api.example.com/search?q=hello+world&page=2&tag=py&tag=web"
qs = parse_qs(urlparse(url).query)
print(qs)
# confirmed live: {'q': ['hello world'], 'page': ['2'], 'tag': ['py', 'web']}
print(type(qs["page"]), qs["page"])
# confirmed live: <class 'list'> ['2']  -- a one-item list, not the bare string '2'

parse_qs() also undoes +-as-space encoding automatically — notice hello+world in the raw query string became the two-word string 'hello world', not a literal plus sign. This is exactly the step Day 16's FastAPI handler never shows: by the time q: str reaches a handler parameter, FastAPI has already done this parsing — parse_qs() is what to reach for when the same URL arrives as a plain string with no framework in front of it.

3 · urlencode(): a dict to a query string, the write direction

Going the other way — building a URL to call another service — starts from ordinary Python values, which need percent-encoding before they're safe to drop into a URL (a space is not a legal character in one):

from urllib.parse import urlencode

params = {"q": "hello world", "page": 2}
print(urlencode(params))
# confirmed live: q=hello+world&page=2

url = "https://api.example.com/search?" + urlencode(params)
# confirmed live: https://api.example.com/search?q=hello+world&page=2

urlencode() converted the int 2 to the text "2" and the space in "hello world" to a + automatically — the same encoding parse_qs() expects and reverses, confirmed live by round-tripping parse_qs(urlparse(url).query) back to {'q': ['hello world'], 'page': ['2']}.

4 · quote()/unquote(): percent-encoding one value by hand

urlencode() handles a whole dict of query parameters; quote() handles a single raw value — useful for a path segment rather than a query parameter, where urlencode() doesn't apply:

from urllib.parse import quote, unquote

print(quote("hello world/slash?q"))
# confirmed live: hello%20world/slash%3Fq
print(quote("hello world/slash?q", safe="/"))
# confirmed live: hello%20world/slash%3Fq  -- safe="/" is the default already; / stays literal
print(unquote("hello%20world%2Fslash%3Fq"))
# confirmed live: hello world/slash?q

quote() left the / alone in both calls because safe="/" is already quote()'s own default — spelled out explicitly in the second call only to show what the default is actually doing. This is the URL equivalent of Day 68's shlex.quote(): both make one untrusted value safe to embed in a larger string, just for two different syntaxes (a URL's reserved characters here, a shell's metacharacters there) — neither function understands the other's rules.

Where pandas/NumPy go from here: neither has any notion of a URL — a pandas pipeline that first downloads data from a paginated API builds each page's URL with urlencode()/quote() (or a dedicated HTTP client's own helpers), fetches it, and only then hands the response body to pd.read_csv() or pd.read_json(). URL construction and parsing is a stdlib/web job, not a data-frame job. Not covered further here, per MISSION.md.
