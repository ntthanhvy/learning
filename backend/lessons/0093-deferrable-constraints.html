Deferrable constraints: checking at commit instead of mid-transaction

Lesson 38 named four things a foreign key can do when its parent disappears, but it quietly assumed when Postgres checks the constraint: immediately, after every statement. Lesson 60's CHECK constraints and Lesson 35's unique violations made the same silent assumption. Ninety-two lessons in, the one question none of them asked out loud: does a constraint have to be checked that instant, or can it wait?

1 · The swap that shouldn't be possible, and clearly is

A todo list has a UNIQUE (list_id, position) constraint — two items in the same list can't share a position, which is exactly the kind of rule Lesson 60 taught a row to enforce on itself. Now swap item A (position 1) and item B (position 2). The obvious way to write it is two plain UPDATEs:

UPDATE items SET position = 2 WHERE list_id = 9 AND position = 1;  -- item A -> 2
UPDATE items SET position = 1 WHERE list_id = 9 AND position = 2;  -- item B -> 1

The instant the first UPDATE runs, item A and item B both sit at position 2 — for exactly one statement's width of time, the table holds two rows that violate the constraint. By default, Postgres checks a UNIQUE constraint at the end of each statement, not at the end of the transaction, so the first UPDATE itself fails with a unique violation before the second one ever gets to run and fix things back up. The swap is logically fine once both statements have landed; Postgres just never lets you reach that end state one statement at a time.

2 · DEFERRABLE: a constraint that waits until commit to look

A deferrable constraint is Postgres's answer: a UNIQUE, PRIMARY KEY, FOREIGN KEY, or EXCLUDE constraint can be declared DEFERRABLE, which allows its check to be pushed all the way to COMMIT instead of running after every statement. It isn't automatic — the constraint has to opt in when it's created:

ALTER TABLE items
  ADD CONSTRAINT unique_list_position UNIQUE (list_id, position) DEFERRABLE INITIALLY IMMEDIATE;

INITIALLY IMMEDIATE means every transaction still checks this constraint after each statement by default, same as before — DEFERRABLE alone only grants permission to delay it. A transaction that actually wants the delay has to ask for it with SET CONSTRAINTS:

BEGIN;
SET CONSTRAINTS unique_list_position DEFERRED;

UPDATE items SET position = 2 WHERE list_id = 9 AND position = 1;  -- two rows at position 2 right now -- not checked yet
UPDATE items SET position = 1 WHERE list_id = 9 AND position = 2;  -- back to one row per position

COMMIT;  -- the constraint is checked here, against the final state, and passes

Nothing about the rule changed — two items still can never permanently share a position. What changed is when Postgres looks: once, at COMMIT, against whatever the data looks like by then, instead of after every single statement along the way.

Frontend-habit trap: this can read like "Postgres skips validation for a while," the same way a frontend form might skip client-side validation until final submit. It doesn't skip anything — the constraint still fires, with the same rule, on the same data. The only thing that moves is the checkpoint: end-of-statement versus end-of-transaction. If the transaction never reaches a valid state by COMMIT, the constraint still fails and the whole transaction still rolls back.

3 · INITIALLY DEFERRED, and what can't be deferred at all

Declaring the constraint DEFERRABLE INITIALLY DEFERRED instead flips the default, so every transaction starts in deferred mode for that constraint without needing its own SET CONSTRAINTS call — useful when almost every transaction touching that table needs the delay, and IMMEDIATE would be the rare exception instead of the rule.

DeclarationDefault mode each transaction starts inCan a transaction still change it with SET CONSTRAINTS?
NOT DEFERRABLE (the default if you say nothing)always checked immediatelyno — this is the one combination SET CONSTRAINTS cannot touch
DEFERRABLE INITIALLY IMMEDIATEchecked after each statementyes — can switch to deferred mid-transaction
DEFERRABLE INITIALLY DEFERREDchecked only at COMMITyes — can switch to immediate mid-transaction

Two constraint types never get a choice in the matter: NOT NULL and CHECK (Lesson 60) are always checked immediately, on the row being inserted or modified, no matter what DEFERRABLE says — only UNIQUE, PRIMARY KEY, FOREIGN KEY, and EXCLUDE can ever be deferred. That lines up with the actual use case: the swap-style problem only ever comes from a constraint that spans multiple rows at once (two rows can't share a position, a child row's key must point at an existing parent) — a single row's own shape, which is all NOT NULL and CHECK ever judge, is never mid-transaction-inconsistent the way two rows briefly colliding can be.

4 · Where this actually shows up: the same swap, in Go

The Go side changes by exactly one statement — SET CONSTRAINTS is sent as plain SQL through the same transaction, the same shape Lesson 92's savepoint calls used:

// swapDisplayOrder exchanges two items' positions inside a UNIQUE(list_id,
// position) constraint. Deferring the constraint to COMMIT lets both
// UPDATEs land before Postgres checks -- without it, the first UPDATE alone
// would violate the constraint and never let the second one run.
func swapDisplayOrder(ctx context.Context, tx *sql.Tx, listID int64, posA, posB int) error {
    if _, err := tx.ExecContext(ctx,
        `SET CONSTRAINTS unique_list_position DEFERRED`); err != nil {
        return fmt.Errorf("defer constraint: %w", err)
    }
    if _, err := tx.ExecContext(ctx,
        `UPDATE items SET position = $1 WHERE list_id = $2 AND position = $3`,
        posB, listID, posA); err != nil {
        return fmt.Errorf("move first row: %w", err)
    }
    if _, err := tx.ExecContext(ctx,
        `UPDATE items SET position = $1 WHERE list_id = $2 AND position = $3`,
        posA, listID, posB); err != nil {
        return fmt.Errorf("move second row: %w", err)
    }
    // caller still calls tx.Commit() -- that's the moment Postgres actually
    // checks unique_list_position against the finished swap
    return nil
}

SET CONSTRAINTS only affects the current transaction — it's not a schema change, and the next transaction starts back at whatever INITIALLY mode the constraint was declared with. If the two UPDATEs above somehow still can't produce a valid final state (say, a bug wrote two items to the exact same position with nothing to swap them back out of), COMMIT itself fails with a unique violation, and the whole transaction rolls back — deferring doesn't weaken the guarantee, it just moves the deadline.

Q: "You need to swap the sort positions of two rows under a UNIQUE(list_id, position) constraint. Two plain UPDATE statements fail partway through. Why, and how would you fix it?" A strong answer, out loud: "Postgres checks a UNIQUE constraint after each statement by default, and the first UPDATE alone puts two rows at the same position for a moment — that's an immediate violation, even though the end state after both UPDATEs is perfectly valid. The fix is marking that constraint DEFERRABLE and running SET CONSTRAINTS ... DEFERRED at the start of the transaction, so Postgres only checks it once, at COMMIT, against the final state instead of after each statement. It's not skipping validation — the same rule still has to hold by commit time, or the transaction still fails." The signal: naming the default per-statement timing as the actual cause, not just reaching for a workaround like a temporary throwaway position value.

Scope line

This lesson covers DEFERRABLE/INITIALLY DEFERRED/SET CONSTRAINTS as Postgres's own constraint-timing mechanism — a different axis from Lesson 92's SAVEPOINT (which controls what gets undone on a per-statement failure) and Lesson 37's isolation levels (which control what concurrent transactions can see of each other). A deferred constraint still only ever affects the single transaction that set it; it is not a way to make a constraint optional, weaker, or visible to other transactions any differently than before.
