1 · The failure Day 41 never covered — because it's on the other end

Day 41 hardened the consumer side of this pipeline: a malformed message quarantined into a dead-letter table instead of crashing the whole loop. Today is the mirror image, on the producer side, and it is a genuinely different mechanism — not the same fix applied twice. A consumer fails on a message it already has in hand. A producer can fail before a message ever leaves the process at all.

Every confluent-kafka producer holds outgoing messages in an in-memory local queue before the broker ever sees them — Day 5's producer.produce() calls, in a tight loop, hand messages into that queue faster than the broker can necessarily drain it. The queue has a fixed size. When it's full, produce() doesn't block and wait — it raises BufferError right there in the calling line, synchronously, before the message is even queued to go anywhere.

Day 5's loop has no try/except around producer.produce() at all. Confirmed directly in the code, no broker needed to see the shape of the gap:

for order_id in (101, 102, 103):
    for status in STATUSES:
        event = make_event(order_id, status)
        producer.produce(TOPIC, key=str(order_id), value=json.dumps(event),
                          callback=delivery_report)   # raises BufferError if the local queue is full
        producer.poll(0)

Three order histories and twelve messages never fill a real queue — Day 5's batch was too small to hit this. A loader script producing thousands of events for a backfill, or a producer running next to a slow or temporarily unreachable broker, hits it routinely. When it does, the exception propagates out of the loop and the process dies mid-batch, with every message not yet queued simply never sent — no dead letter, no log line, nothing: the pipeline just stops partway with no record of where.

2 · The second gap: a delivery report that only prints

Even when produce() itself succeeds, the broker can still reject or fail to acknowledge a message later, asynchronously — a full topic-level queue on the broker side, a leader election mid-send, a network blip. Day 5's delivery_report callback already receives that information:

def delivery_report(err, msg):
    if err is not None:
        print(f"delivery failed: {err}")
    else:
        print(f"delivered to {msg.topic()} [partition {msg.partition()}] @ offset {msg.offset()}, key={msg.key().decode()}")

Printing is not handling. Nothing reads that output in an automated run, so a real delivery failure looks identical to success from the outside: the script still exits 0, the loader still reports "done." Bridge from backend: this is the same gap backend's idempotency-key lessons named for a client that fires a request and never checks the response — logging an error is not the same as a caller being able to detect one. Today's fix makes failed deliveries countable, so the script's own exit status reflects reality.

3 · Build: handle a full queue, and make failed deliveries count

Edit scripts/produce_order_events.py. First, wrap the produce() call so a full queue backs off and retries instead of crashing — producer.poll() with a real timeout gives the client a chance to service delivery callbacks and drain the queue, which is exactly what makes room:

def produce_with_backpressure(producer, topic, key, value, callback, max_retries=5):
    """produce(), retrying through BufferError by letting poll() drain the queue."""
    for attempt in range(max_retries):
        try:
            producer.produce(topic, key=key, value=value, callback=callback)
            return
        except BufferError:
            print(f"local queue full, draining (attempt {attempt + 1}/{max_retries})")
            producer.poll(1.0)   # blocks up to 1s servicing callbacks, which frees queue slots
    raise RuntimeError(f"queue still full after {max_retries} retries, key={key}")

Then make delivery failures countable instead of print-only, using a mutable counter the callback closes over:

failed_deliveries = {"count": 0}

def delivery_report(err, msg):
    if err is not None:
        failed_deliveries["count"] += 1
        print(f"delivery failed: {err}")
    else:
        print(f"delivered to {msg.topic()} [partition {msg.partition()}] @ offset {msg.offset()}, key={msg.key().decode()}")

Replace the loop's bare call with the wrapper, and check the counter after flush() so the script's own exit code tells the truth:

for order_id in (101, 102, 103):
    for status in STATUSES:
        event = make_event(order_id, status)
        produce_with_backpressure(producer, TOPIC, str(order_id), json.dumps(event), delivery_report)
        producer.poll(0)

producer.flush()
if failed_deliveries["count"] > 0:
    raise SystemExit(f"{failed_deliveries['count']} message(s) failed delivery, see log above")

producer.flush() already blocks until every queued message is either delivered or failed — it's what guarantees every callback has actually run by the time the counter is checked. Without that ordering, the count could be read before the last few callbacks fire.

4 · Verify: force a full queue, and watch the retry instead of a crash

A local queue is sized by queue.buffering.max.messages (default 100,000) — too high to hit by accident, but trivial to force down for a test. Configure the producer with a tiny limit and send a burst past it:

uv run --with confluent-kafka python3 -c "
from confluent_kafka import Producer, KafkaError

producer = Producer({'bootstrap.servers': 'localhost:9092', 'queue.buffering.max.messages': 5})

def cb(err, msg):
    print('failed:', err) if err else print('ok:', msg.offset())

def produce_with_backpressure(producer, topic, key, value, callback, max_retries=5):
    for attempt in range(max_retries):
        try:
            producer.produce(topic, key=key, value=value, callback=callback)
            return
        except BufferError:
            print(f'local queue full, draining (attempt {attempt + 1}/{max_retries})')
            producer.poll(1.0)
    raise RuntimeError('queue still full after retries')

for i in range(20):
    produce_with_backpressure(producer, 'order_events', str(i), b'{\"test\": true}', cb)
producer.flush()
print('all 20 sent, zero crashes')
"

Expected — several local queue full, draining lines as the burst of 20 outruns the 5-message limit, interleaved ok: lines as poll() drains the queue, and the script reaching its final line instead of dying on BufferError:

local queue full, draining (attempt 1/5)
ok: 0
ok: 1
local queue full, draining (attempt 1/5)
ok: 2
...
all 20 sent, zero crashes

Q: "Your Kafka producer is about to send a large backfill batch. What could go wrong that your code today doesn't handle, and how would you fix it?" A strong answer, out loud: "produce() hands a message into the client's own local queue, not straight to the broker — and that queue has a fixed size. If I call produce() faster than the broker acknowledges messages, which a tight loop over a large batch easily does, the queue fills and produce() raises BufferError synchronously, right in the calling line. The fix isn't to make the queue bigger and hope — it's to catch BufferError and call poll() with a real timeout, which blocks briefly servicing delivery callbacks and frees queue slots, then retry. Separately, I'd make sure the delivery callback's failures are actually counted and checked after flush(), not just printed, because a script that logs an error but still exits 0 looks identical to a fully successful run from any caller's point of view." The signal: naming that produce() itself can fail, synchronously, before anything about the broker's own health is even in question — not just "handle network errors."

Scope line

This lesson covers BufferError on producer.produce() and a bounded poll()-and-retry fix, plus turning the existing delivery callback's failure count into something the script's exit code reflects. It does not cover producer-side idempotence (the enable.idempotence config preventing broker-side duplicates on retry, Phase 2b's own delivery-semantics lesson, Day 16), tuning queue.buffering.max.messages/linger.ms for real throughput (a production capacity question, out of this course's working-level Kafka scope per MISSION.md), or a producer-side dead-letter destination for messages that exhaust all retries — today's RuntimeError is a deliberate hard stop, on the view that a backfill script failing loudly and re-runnable from the top is simpler and safer than quarantining partial batches, unlike Day 41's live, never-ending consumer loop where stopping forever was the actual bug.
