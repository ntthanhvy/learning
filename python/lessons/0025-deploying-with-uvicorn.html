Deploying with uvicorn: workers, reload & env-based config

Every lesson since Day 16 has called routes in-process through TestClient — no real server has ever run. Day 22's glossary named ASGI server in one recognition-only sentence and moved on. Today closes that gap: what uvicorn actually does when it starts an app, the dev-mode --reload flag versus the production --workers flag (mutually exclusive, for a reason), and reading deploy settings — host, port, worker count — from the environment instead of hardcoding them, reusing Day 17's pydantic_settings.BaseSettings unchanged.

Bridge from SQL: a connection pool sized for a database server — too few connections and requests queue; too many and the server thrashes swapping between them — configured once via a setting, not hardcoded into every client. uvicorn's --workers count is that same sizing decision for the process serving HTTP requests, not SQL, and env-based config is how that number reaches production without editing code.

1 · What uvicorn actually does

uvicorn is an ASGI server: a program that opens a real network socket, accepts real HTTP connections, and calls the FastAPI app object (Day 22's own definition of what app is — a plain callable) once per request, the same call TestClient has been making in-process all course. Run from a shell, not a script:

uv run --with fastapi --with uvicorn uvicorn app:app --host 0.0.0.0 --port 8000

app:app means "in the module named app (Day 9's import-by-name), find the object named app" — the same FastAPI() instance every practice file since Day 16 has built, just imported by uvicorn instead of wrapped in TestClient. --host 0.0.0.0 binds every network interface rather than only localhost; --port 8000 picks which port. Nothing about the FastAPI app itself — routes, dependencies, middleware, exception handlers from Days 16–24 — changes to be served this way; only how it's launched changes.

2 · --reload vs. --workers: dev and production want opposite things

Two flags, and they cannot be combined:

# dev: one process, watches source files, restarts on every save
uvicorn app:app --reload

# production: N worker processes, no file watching, no auto-restart
uvicorn app:app --workers 4

--reload is a development convenience: uvicorn watches every source file and restarts the one running process the instant something changes, so an edited handler is live on the next request with no manual restart. It runs exactly one process. --workers N is the opposite goal: N independent worker processes, each running a full copy of the app, so N requests can be handled at the same instant on N CPU cores — Day 20's event loop explained why a single async def process still serializes CPU-bound work; more worker processes, not more await, is how that gets fixed. Combining the two would mean restarting several independent processes on every file save, which defeats the reason to have several — uvicorn refuses the combination outright.

A commonly cited starting point for worker count, not a strict rule: (2 × cpu_count) + 1 — enough workers that some are always ready to accept a new connection while others finish CPU-bound work, without so many that the machine spends more time switching between them than running them. Confirmed directly against this sandbox's own os.cpu_count() (4): the formula gives 9 — a starting point to tune from under real load, not a number to trust blindly.

3 · Reading deploy config from the environment, not hardcoding it

A port or worker count baked into source code means editing code to change it per environment — dev, staging, production each wanting different values. Day 17's pydantic_settings.BaseSettings solves exactly this, unchanged:

from pydantic_settings import BaseSettings

class DeploySettings(BaseSettings):
    host: str = "127.0.0.1"
    port: int = 8000
    workers: int = 1
    reload: bool = False

settings = DeploySettings()  # reads PORT, WORKERS, RELOAD, HOST from os.environ if set

Confirmed directly: with PORT=9000, WORKERS=4, and RELOAD=true set in the environment, DeploySettings() reads back port=9000 (an int, coerced from the env string), workers=4, and reload=True (a real bool, not the string "true") — the identical coercion Day 17 already demonstrated for request bodies, now aimed at os.environ instead. Any field left unset in the environment keeps its coded default, so host stays "127.0.0.1" here. A real deploy then reads settings.port/settings.workers instead of a number typed directly into a shell command or a route.

4 · The whole shape, put together

A minimal production launch script wires sections 2 and 3 together — settings read once from the environment, then handed to uvicorn.run(), the programmatic sibling of the CLI form from section 1:

import uvicorn
from pydantic_settings import BaseSettings

class DeploySettings(BaseSettings):
    host: str = "0.0.0.0"
    port: int = 8000
    workers: int = 1

if __name__ == "__main__":      # Day 9's own import guard
    settings = DeploySettings()
    uvicorn.run("app:app", host=settings.host, port=settings.port, workers=settings.workers)

Day 9's if __name__ == "__main__": guard does real work here for the first time all course: this file can still be imported elsewhere (say, by a test) without launching a server, and only actually starts one when run directly with python3 deploy.py — the exact distinction Day 9 taught in the abstract, now load-bearing.

Where pandas goes from here: a pandas pipeline is a script that starts, runs, and exits — there is no "deployable shape" question to ask, no port to bind, no worker count to tune, because nothing is waiting to accept the next request. That question only exists once a service, not a one-shot transform, is what's being shipped.
