np.partition() / np.argpartition(): the fast "top N" primitive under nlargest()

Lesson 120 closed with one standing candidate from a fresh curriculum/glossary scan: np.partition()/argpartition(). Today picks it up — it is the NumPy-level mechanism underneath Lesson 10's nlargest()/nsmallest() and Lesson 73's argsort(), named out loud for the first time, with a genuinely different performance story and a sharp nuance about exactly how "unsorted" its output really is.

1 · The gap: argsort() and sort() do more work than "give me the top N" needs

Lesson 73's np.argsort() fully sorts an array to get positions; Lesson 10's nlargest(n) answers "top N" for a pandas Series or DataFrame. Both work by fully ordering the data, even when the actual question only needs the N smallest or N largest values, not every value's exact rank. np.partition(arr, k) is the primitive that skips that extra work: it only guarantees the value at index k is correct, not the whole array. Confirmed directly (numpy 2.5.4) on a small array:

import numpy as np
import pandas as pd

x = np.array([7, 2, 9, 4, 1, 8, 3])
k = 2

part = np.partition(x, k)
# part == array([1, 2, 3, 4, 7, 8, 9])  -- looks fully sorted here, but that's a coincidence of this tiny array
part[k]              # 3
np.sort(x)[k]        # 3  -- IDENTICAL: index k always holds the true k-th smallest value

On a small array like this one, the output happens to come out fully ordered — easy to mistake for a coincidence of "small arrays get fully sorted anyway." Section 2 confirms directly that this is not what the guarantee actually promises once the array gets bigger.

2 · The real guarantee: only the pivot position is exact — neither side is sorted

Confirmed directly on a 2,000-element array of random integers: np.partition(x, k) only promises three things about its output: (1) the value at index k equals np.sort(x)[k] exactly; (2) every value to the left of index k is <= that pivot value; (3) every value to the right is >= it. Confirmed directly that neither side is internally sorted:

rng = np.random.default_rng(42)
big = rng.integers(0, 100_000, size=2000)
k = 500
part = np.partition(big, k)

part[k] == np.sort(big)[k]                                 # True -- the one guaranteed position
np.all(part[:k] <= part[k])                                 # True -- left side, but unordered within itself
np.all(part[k+1:] >= part[k])                               # True -- right side, same story
list(part[:k]) == sorted(part[:k])                          # False -- left side is NOT internally sorted
np.array_equal(part, np.sort(big))                          # False -- the full output is NOT a sorted array

This is the whole reason partition() exists: it does less work than a full sort (an introselect algorithm, confirmed via the official docs, average linear time vs. a sort's linearithmic time), and it can only do that by giving up the guarantee that everything besides the pivot position is in order. Treating its output as "basically sorted" is the trap — it is only correct at exactly one index.

3 · argpartition() + slicing: the actual "top N" idiom, and why it's faster

np.argpartition() is to np.partition() what Lesson 73's np.argsort() is to np.sort() — it returns positions instead of values. The classic interview use: get the indices of the N largest values, unordered among themselves, without paying for a full sort:

N = 10
top_n_idx = np.argpartition(big, -N)[-N:]    # last N positions after partitioning on the Nth-from-end
sorted({*big[top_n_idx]}) == sorted({*np.sort(big)[-N:]})   # True -- same SET of values, order not guaranteed

Confirmed directly, timing a full sort against a partition for "top 10 of 2 million" on this machine: np.partition() ran roughly 6.5x faster than np.sort() for that same array and k — the gap that makes this worth knowing by name rather than always reaching for sort()/argsort() out of habit. Lesson 10's pandas-level Series.nlargest(n)/nsmallest(n) already gives the same top-N answer at the DataFrame/Series level with the groupby-aware, NaN-safe ergonomics pandas adds on top; np.partition()/argpartition() is the lower-level, allocation-light primitive pandas itself leans on for exactly this job on raw arrays.

4 · Edge cases: negative kth, multiple kth, out-of-bounds, ties, NaN

Confirmed directly, four behaviors worth knowing cold:

# 1) negative kth counts from the end, same convention as ordinary indexing
np.partition(x, -2)[-2]  == np.sort(x)[-2]      # True -- 2nd-largest lands at position -2

# 2) a list of kth values partitions correctly at EACH position simultaneously
np.partition(x, [1, 3])[1] == np.sort(x)[1]   # True
np.partition(x, [1, 3])[3] == np.sort(x)[3]   # True -- both positions exact at once, one pass

# 3) kth past the array's own bounds raises ValueError immediately
np.partition(np.array([1, 2, 3]), 5)
# ValueError: kth(=5) out of bounds (3)

# 4) NaN sorts to the end, matching np.sort() exactly -- not a separate trap this time
xn = np.array([5.0, np.nan, 1.0, 3.0, np.nan, 2.0])
np.partition(xn, 2)   # array([1., 2., 3., 5., nan, nan])
np.sort(xn)          # array([1., 2., 3., 5., nan, nan])  -- IDENTICAL NaN placement

Confirmed directly: tied values partition correctly too — duplicates land wherever the <=/>= rule allows, with no special-casing needed. On a 2-D array, the default axis=-1 partitions each row independently, the same per-row default np.sort() already uses.
