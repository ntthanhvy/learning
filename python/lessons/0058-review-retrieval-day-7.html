1 · Six questions, in the original teaching order

Answer each out loud or on paper before reading the fold-out answer. If one is shaky, note it and go fix it in the practice file below rather than only rereading the old lesson.

Day 18 — request/response schemas. A handler's return includes a field its response_model doesn't declare — say, an internal secret_cost. What actually reaches the client?

Fold-out answer: nothing — that extra field is silently filtered out. response_model builds its declared model from whatever the handler returned, using the same construction-time validation and coercion as any other pydantic model, and only the fields that model declares survive into the JSON response. This is why real routes use two schemas per route — one named ...In, one named ...Out — rather than reusing one model for both directions: a field that only belongs on the request side, like a password, can never accidentally leak through a response built from a deliberately narrower response model.

Day 21 — talking to PostgreSQL. cur.execute("... WHERE name = %s", (name,)) versus cur.execute(f"... WHERE name = '{name}'"). Why does only the first one stop SQL injection?

Fold-out answer: the placeholder version sends the SQL text and the values tuple to the server as two separate pieces, so a value can never be interpreted as new SQL syntax, no matter what characters it contains. The f-string version pastes the raw value directly into the query text before it's ever sent — a crafted value like "x' OR '1'='1" becomes part of the query's own grammar and can rewrite what the query matches. This was confirmed directly: the same injection-style string matched every row through the f-string version and zero rows through the placeholder version, treated as one literal string to compare against.

Day 22 — testing with httpx. TestClient(app).get("/users/1") gets a real response back with no server process running anywhere. How?

Fold-out answer: TestClient is built on httpx.Client, and it hands each request straight to the FastAPI app object in the same process through the ASGI interface FastAPI already speaks — no socket opens, no bytes get serialized onto a wire. This is the exact in-process call every FastAPI practice file since Day 16 was already making without a name for it; Day 22 just gave it one. A test_*-named function using assert against it is Day 11's whole pytest convention, unchanged, just calling client.get()/client.post() instead of a plain function.

Day 23 — error handling. Two routes can both raise the same domain rule — say, OutOfStock. Why register one @app.exception_handler(OutOfStock) instead of a local if/raise HTTPException in each route?

Fold-out answer: one place owns the rule instead of repeating it. Registering @app.exception_handler(OutOfStock) once means every route that raises OutOfStock(item) — however many there end up being — gets back the identical status code and JSON body, with zero copy-pasted if/raise logic to drift out of sync between routes. @app.exception_handler isn't limited to custom classes either — it registers on any exception type escaping a route uncaught, including RequestValidationError, the type FastAPI itself raises internally when pydantic rejects a request, letting a service override FastAPI's own default 422 body with one consistent shape.

Day 25 — deploying with uvicorn. uvicorn app:app --reload and uvicorn app:app --workers 4 cannot be combined. Why not, and which one actually lets two requests run on two CPU cores at once?

Fold-out answer: --reload runs exactly one process and restarts it whenever a source file changes — combining it with --workers would mean restarting several independent processes on every save, defeating the entire reason to have several. --workers N is the opposite goal: N independent processes, each a full copy of the app, so N requests really can run on N separate CPU cores at the same instant. More worker processes — not more await written inside a handler — is what buys that; Day 20 already explained why a single async def process still serializes CPU-bound work no matter how it's awaited.

Day 26 — the FastAPI capstone. The capstone's read_task handler never checks whether the requested task exists. Why not, and what happens when it doesn't?

Fold-out answer: Depends(get_task_or_404) runs that dependency before the handler body, and if the task is missing it raises TaskNotFound — the exact Day 19 dependency shape feeding Day 23's exception-handler shape. The route body only ever sees an already-found task; it never needs its own "if missing" branch, because the dependency already handled that case by raising, and the registered @app.exception_handler(TaskNotFound) turns that raise into a clean 404 before the client ever sees a crash. Nothing about the capstone introduced a new mechanism — it is Days 17-20 and 23 wired into one 36-line file.
