Abstract base classes: abc.ABC and @abstractmethod

Day 41's Protocol answered "any object shaped like this, no inheritance needed" — structural typing. Today's is the other half of the same interview question, finally taught rather than only named: abstract base class (ABC): "any object that explicitly inherits from this and fills in the required methods" — nominal typing, enforced by Python itself the moment an instance is created, not just by a type checker reading hints.

Bridge from SQL: an ABC is closer to a CHECK constraint than a schema: it doesn't just describe a shape, it actively refuses to let a broken row (an incomplete subclass) exist at all. Protocol was the schema-as-documentation version — checked by a linter, never enforced at runtime, exactly like a comment claiming a column "should" be non-null. An ABC is the real constraint: violate it and the database (Python) rejects the insert (the instantiation) outright.

1 · The problem: an interface with nothing stopping you from skipping it

Say every payment method in a system needs a charge(amount) method — that's the whole contract. Nothing in plain Python stops a subclass from forgetting to define it:

class PaymentMethod:
    def charge(self, amount):
        raise NotImplementedError

class CardPayment(PaymentMethod):
    def charge(self, amount):
        return f"charged ${amount} to card"

class BrokenPayment(PaymentMethod):
    pass   # forgot to override charge() -- nothing stops this

BrokenPayment()          # creates fine -- no error yet
BrokenPayment().charge(10)  # NotImplementedError -- but only NOW, at call time, maybe in production

The base class's raise NotImplementedError is a convention, not an enforcement — BrokenPayment() instantiates without complaint, and the missing method only surfaces the moment something finally calls .charge(...), which could be long after the class was written and far from where the mistake was made.

2 · abc.ABC and @abstractmethod: the same contract, enforced at instantiation

The standard library's abc module turns that convention into a real rule. Inherit from ABC and mark required methods @abstractmethod; Python then refuses to create an instance of any subclass that hasn't overridden every one of them:

from abc import ABC, abstractmethod

class PaymentMethod(ABC):
    @abstractmethod
    def charge(self, amount):
        ...   # body is never used -- subclasses must supply their own

class CardPayment(PaymentMethod):
    def charge(self, amount):
        return f"charged ${amount} to card"

class BrokenPayment(PaymentMethod):
    pass   # still forgot to override charge()

CardPayment().charge(10)  # "charged $10 to card" -- works fine
BrokenPayment()             # TypeError: Can't instantiate abstract class BrokenPayment
                             #   without an implementation for abstract method 'charge'
PaymentMethod()              # TypeError too -- the ABC itself can never be instantiated directly

Verified live: BrokenPayment() raises TypeError the instant it's constructed — not on the first call to .charge(...), which might be seconds, days, or a deploy later. The mistake is caught at the exact line that created the broken object, with a message naming the specific missing method. PaymentMethod itself is also uninstantiable, on purpose: it exists only to be inherited from, never used directly — unlike section 1's plain-class version, which happily instantiated with no complaint at all.

3 · @abstractmethod can require more than plain methods

Stacking @abstractmethod under Day 32's @classmethod/@staticmethod or Day 30/37's @property requires those too — the enforcement isn't limited to ordinary instance methods:

from abc import ABC, abstractmethod

class Shape(ABC):
    @property
    @abstractmethod
    def area(self) -> float:
        ...

class Square(Shape):
    def __init__(self, side):
        self.side = side

    @property
    def area(self) -> float:
        return self.side ** 2

Square(4).area   # 16 -- area reads like an attribute, enforced like a method

A subclass that defines area as a plain attribute instead of a @property, or omits it entirely, still fails to instantiate — the ABC checks that the name is filled in and overridden, regardless of which kind of member fills it.

4 · Nominal vs. structural: choosing between an ABC and a Protocol

Both answer "does this object satisfy the contract?" but check it in opposite ways, and Day 41's own interview answer named the distinction without the ABC half being taught yet — this closes that loop:

 ABC (today)Protocol (Day 41)
relationship requiredexplicit — subclass must inherit from itnone — any matching shape qualifies
when it's checkedat instantiation, by Python itself, alwaysonly if a type checker runs, or @runtime_checkable + isinstance() is used
couplingevery implementer imports and inherits the ABCzero — implementers never import the Protocol
best fora shared library defining its own plugin contractaccepting objects from code you don't own or control

Reach for an ABC when a class hierarchy is genuinely yours to define and you want Python itself to refuse an incomplete subclass the moment it's built — a plugin system, a base class in your own package. Reach for a Protocol when the objects satisfying the shape come from elsewhere and forcing them all to inherit from a common base isn't realistic or desirable.

Where pandas goes from here: nothing pandas-specific — abc is a general language mechanism. pandas itself uses ABC-like base classes internally (e.g. its extension-array interface), but building one here would mean writing pandas-internals code, out of scope per MISSION.md. Not demonstrated; this is the only sentence in this lesson naming pandas.

Q: "What's the difference between an abstract base class and a Protocol in Python?" A strong answer, out loud: "Both describe a required shape, but an ABC is nominal and enforced — a subclass has to explicitly inherit from it, and Python refuses to instantiate it if an @abstractmethod is left unimplemented. A Protocol is structural and, without @runtime_checkable, only checked by a static type checker — any object with matching method names satisfies it, no inheritance or import required. I'd use an ABC for a plugin contract I own and want enforced at object-creation time; a Protocol for accepting objects from code I don't own, where forcing a shared base class isn't realistic." The signal: naming both the enforcement-timing difference and the coupling difference, not just "one uses inheritance."
