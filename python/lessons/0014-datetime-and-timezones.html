datetime & timezones

Day 13 turned filesystem paths from strings you re-parse by hand into real objects with operations on them. Today does the same for the other value every backend touches constantly: a moment in time. A datetime built without a timezone looks fine, prints fine, and is a silent trap the moment two computers in different timezones compare notes — a bug class that string-based date handling can't even describe, let alone catch. This is also direct prep for the FastAPI/pydantic phase next: request timestamps, database TIMESTAMPTZ columns, and API responses all live or die on getting this right.

Bridge from SQL: a SQL schema usually offers two column types for a moment in time — TIMESTAMP, which stores a date and time with no timezone attached (whose "3pm" is it?), and TIMESTAMPTZ, which stores it unambiguously by normalizing to UTC internally and converting on the way in and out. Python's datetime module has the exact same split, at the object level instead of the column level: a naive datetime is TIMESTAMP's twin (a time with no attached zone, ambiguous the moment it crosses a machine boundary), and an aware datetime is TIMESTAMPTZ's twin (a time anchored to a specific zone, safe to compare). The rule for both is the same: prefer the zone-aware one unless you have a specific reason not to.

1 · Naive vs. aware: the split that matters most

A datetime object can be one of two kinds, and nothing in how it prints tells you which:

from datetime import datetime, timezone

naive = datetime(2026, 8, 11, 15, 0, 0)                  # 3:00pm — but whose 3:00pm?
aware = datetime(2026, 8, 11, 15, 0, 0, tzinfo=timezone.utc)  # 3:00pm UTC — unambiguous

print(naive)   # 2026-08-11 15:00:00
print(aware)   # 2026-08-11 15:00:00+00:00

A naive datetime is missing a tzinfo attribute — it's a time with no attached zone, exactly SQL's plain TIMESTAMP. An aware datetime has a real tzinfo, exactly SQL's TIMESTAMPTZ. The two kinds can't be safely compared or subtracted from each other — Python raises TypeError rather than guess which one you meant, which is the language actively protecting you from the ambiguity a naive value carries.

2 · datetime.now() vs. datetime.now(timezone.utc)

The most common place this bites: datetime.now() called with no argument returns a naive datetime in whatever timezone the local machine happens to be set to — a laptop in Hanoi and a server in a US data center get two different naive answers for "now," neither one saying which zone it's in:

local_naive = datetime.now()                 # naive — local clock, zone unstated
utc_aware   = datetime.now(timezone.utc)     # aware — anchored to UTC, unambiguous anywhere

For anything that leaves one machine — a timestamp saved to a database, sent in an API response, compared against a timestamp from another server — datetime.now(timezone.utc) is the one to reach for by default. Storing everything in UTC and only converting to a human's local zone for display is the same discipline TIMESTAMPTZ already applies at the database layer: one canonical, unambiguous value, converted at the edges.

3 · Why a naive datetime is a footgun

The failure isn't hypothetical. Two servers, each calling datetime.now() at the literal same instant but configured to different local zones, produce two different-looking naive values with no record of the offset between them — subtract one from the other and Python computes a wrong, silently-plausible-looking duration instead of raising an error, because nothing marks either value as being in a different zone to begin with:

server_a = datetime(2026, 8, 11, 15, 0, 0)   # naive "3pm" — recorded in Hanoi's local zone
server_b = datetime(2026, 8, 11, 8, 0, 0)    # naive "8am" — recorded in UTC, same actual instant
server_a - server_b                          # 7:00:00 — looks fine, means nothing; it's actually the same moment

Mixing an aware and a naive value is the one case Python does refuse outright — aware - naive raises TypeError: can't subtract offset-naive and offset-aware datetimes. That error is a feature: it surfaces the bug at the point of comparison instead of letting a wrong duration silently flow downstream into a report or a billing calculation.

4 · timedelta arithmetic

A timedelta represents a span of time, not a point — the result of subtracting two datetimes, or a value you add to shift one forward or back:

from datetime import timedelta

now = datetime.now(timezone.utc)
one_week_later = now + timedelta(days=7)
ninety_min_ago = now - timedelta(minutes=90)

elapsed = one_week_later - now              # timedelta(days=7) — subtracting two datetimes gives a timedelta
elapsed.total_seconds()                     # 604800.0 — the duration as a plain float, for comparisons/thresholds

timedelta arithmetic only works cleanly when both datetimes are the same kind (both naive, or both aware) — the same rule section 3 already established, just applied here to addition and subtraction instead of a bare comparison.

5 · Parsing and formatting

Two different jobs come up constantly and use different tools. Going from a datetime to text uses strftime ("string format time"); going from text to a datetime uses its inverse, strptime ("string parse time") — both driven by the same format codes (%Y four-digit year, %m month, %d day, %H/%M/%S hour/minute/second):

dt = datetime(2026, 8, 11, 15, 30)
dt.strftime("%Y-%m-%d %H:%M")              # "2026-08-11 15:30" — datetime -> custom string

parsed = datetime.strptime("2026-08-11 15:30", "%Y-%m-%d %H:%M")  # string -> datetime

For the one format that comes up constantly in backend work — ISO 8601, the format databases and JSON APIs actually use ("2026-08-11T15:30:00+00:00") — there's a shortcut pair that needs no format string at all: .isoformat() and datetime.fromisoformat():

aware.isoformat()                              # "2026-08-11T15:00:00+00:00"
datetime.fromisoformat("2026-08-11T15:00:00+00:00")  # back to an aware datetime, offset preserved

isoformat()/fromisoformat() is the pair to reach for first whenever the string is ISO-shaped, which is most of the time in a JSON API or a database round trip; strftime/strptime stay the right tool when the format is something else (a log line, a report a human reads).

6 · zoneinfo: real timezone conversions

timezone.utc from section 1 is one specific, fixed offset — enough for "store everything in UTC," but not enough for "what time is it in Ho Chi Minh City right now," because a named zone like Asia/Ho_Chi_Minh or America/New_York can carry rules (daylight saving changes) that a bare fixed offset can't express. That's zoneinfo's job, standard library since Python 3.9 — no third-party pytz package needed:

from zoneinfo import ZoneInfo

utc_now = datetime.now(timezone.utc)
hcmc_time = utc_now.astimezone(ZoneInfo("Asia/Ho_Chi_Minh"))
print(hcmc_time)   # same instant, displayed in Ho Chi Minh City's local offset

.astimezone(zone) doesn't change *when* something happened — it re-expresses the same instant under a different zone's local clock, the same underlying moment section 4's timedelta arithmetic would still measure identically either way. This only works starting from an aware datetime; calling .astimezone() on a naive one forces Python to guess the source zone (assumes the local machine's), which is exactly the ambiguity section 3 flagged — one more reason to build aware datetimes from the start.

Where pandas goes from here: pandas has its own datetime handling built on top of all this — Timestamp, the .dt accessor, vectorized timezone conversion across a whole column — covered in the data/ course; today is stdlib datetime/zoneinfo only, named here once and not demonstrated, matching the hard rule above.
