hmac: keyed hashing for message authentication

Day 59 taught hashlib.sha256 for detecting whether content changed. Day 77 taught secrets.compare_digest() for safely comparing a secret against untrusted input — but neither lesson covered how to actually produce a value that proves a message came from someone holding a shared secret. hmac closes that loop today.

Why today, specifically: Day 88's ChainMap closed out a fresh topic with four named-but-untaught candidates left on the table: hmac, graphlib, weakref, calendar. A fresh grep across every lesson, practice file, reference/glossary.html, and RESOURCES.md confirmed all four are still genuinely untaught. Chose hmac: it directly closes a gap Day 59 and Day 77 each left half-open, it's pure language/stdlib mechanics with zero pandas/NumPy surface, and keyed message authentication is exactly the kind of thing that shows up the moment a real script needs to verify a webhook or a signed API request — this is Day 89, continuing the fresh run Day 88 started; a review of Days 88-90 is due at Day 91.

1 · hashlib has no secret — anyone can compute the same digest

Day 59's hashlib.sha256(data) takes no key at all — it is a pure function of the bytes you give it. That's exactly why it's good at detecting whether content changed: two people with the same file get the same digest, no coordination needed. It's also exactly why it proves nothing about who sent something — anyone holding the same bytes computes the identical digest, attacker included. hmac fixes exactly that gap: it mixes a secret key into the hash, so only someone who already knows that key can produce — or verify — the matching tag:

import hashlib
import hmac

key = b"shared-secret-key"
msg = b'{"order_id": 42, "amount": 19.99}'

mac = hmac.new(key, msg, hashlib.sha256)
mac.hexdigest()
# '59b0217ce452106f4e168d6bd22afc7acb081ddd24f4feb22ac22ec099b5d9c8' -- confirmed live

hmac.new(b"different-key", msg, hashlib.sha256).hexdigest() == mac.hexdigest()
# False -- a different key produces a completely different tag, confirmed live

Same key and same message always reproduce the same tag — confirmed directly, two separate calls with identical inputs matched exactly. A different key, or a changed message, produces a completely different tag, with no partial resemblance. This is the entire mechanism behind verifying a webhook signature or a signed API request: the sender computes hmac.new(shared_secret, body, sha256).hexdigest() and attaches it; the receiver recomputes the same thing over the body it actually got and checks the two tags match.

2 · digestmod is required — hashlib never made you choose anything

hashlib.sha256() needs no arguments to pick an algorithm — the function name is the algorithm. hmac.new() works differently: confirmed directly, calling it without a third argument raises an error rather than picking a default:

hmac.new(key, msg)
# TypeError: Missing required argument 'digestmod'. -- confirmed live, no default algorithm exists

Per the standard library docs, digestmod is required "despite its argument position" — hmac deliberately refuses to guess which hash function the other side expects, since a mismatched algorithm would silently produce a tag that can never match. key must be bytes/bytearray (confirmed directly: a plain str key raises TypeError: key: expected bytes or bytearray, but got 'str') — the same bytes-only rule Day 59's hashlib already enforced.

3 · Not just hash(key + message) stuck together

It's tempting to assume hmac is just a shorthand for hashing the key and message concatenated — confirmed directly, it is not:

hashlib.sha256(key + msg).hexdigest() == hmac.new(key, msg, hashlib.sha256).hexdigest()
# False -- confirmed live: these are genuinely different constructions, not the same thing spelled two ways
Per the standard library's own module description, hmac "implements the HMAC algorithm as described by RFC 2104" — a specific, standardized construction for combining a key and a message, not a shortcut anyone could hand-roll by gluing bytes together before hashing. The exact reason the naive concatenation is weaker is a cryptography-internals question beyond today's scope; the takeaway for everyday code is narrower and firmer: always reach for hmac.new() itself for a keyed tag, never hashlib.sha256(key + msg) as a shortcut, even though both compile and run without error.

4 · Same chunked interface as Day 59, verified with Day 77's tool

hmac objects support .update() exactly like Day 59's hashlib objects — the same constant-memory, chunk-at-a-time pattern for hashing something too large to hold all at once:

mac = hmac.new(key, digestmod=hashlib.sha256)   # no msg yet
mac.update(msg)                                 # fed in a separate step
mac.hexdigest() == hmac.new(key, msg, hashlib.sha256).hexdigest()
# True -- confirmed live: incremental update() matches the one-shot call exactly

And once a tag needs checking against a value supplied by someone else — verifying a webhook's signature header, for instance — Day 77's rule still applies unchanged: compare with hmac.compare_digest(received_tag, mac.hexdigest()), never plain ==, for the same timing-safety reason Day 77 already covered in full.

Q: "How would you verify an incoming webhook actually came from the service that claims to have sent it?" A strong answer, out loud: "I'd recompute hmac.new(shared_secret, raw_body, hashlib.sha256).hexdigest() over the exact raw request body, using the secret both sides already agreed on, then compare that against the signature header the request sent — with hmac.compare_digest(), not ==, so the comparison itself doesn't leak timing information. A plain hashlib.sha256(body) digest wouldn't prove anything here, since anyone could compute that same hash with no secret at all; the key is what proves it came from someone who holds it." The signal: naming that the key is what turns a hash into proof of origin, and reaching for compare_digest() unprompted for the final check.

Scope line

This lesson covers hmac.new(key, msg, digestmod), .hexdigest()/.digest(), .update()'s chunked interface, digestmod's required-argument behavior, and the keyed-vs-unkeyed distinction against Day 59's hashlib, bridging to Day 77's compare_digest() for verification. It does not cover hashlib.pbkdf2_hmac() or password storage (still deferred to a future FastAPI-phase authentication lesson, per Day 59's own note), the HTTP-level conventions of any particular webhook provider's signature header format (an application-protocol topic, not a language-mechanics one), or HMAC's internal padding construction and exactly why naive key-concatenation is weaker (cryptography internals beyond today's scope — RFC 2104 is cited by name only).
