async/await: what it buys, when it doesn't, and blocking-call traps

Every handler from Day 16 onward has been a plain def — and that was never a problem, because FastAPI quietly runs plain def handlers in a background thread pool so one slow one doesn't stall the rest. Today's topic is the other option, async def, which handles the same "don't block everyone else" problem a completely different way: not by using more threads, but by giving up control at every await so other work can run on the very same thread while it waits. That difference is the whole lesson — including the trap: sneak a normal blocking call into an async def function and that giving-up-control never happens, silently serializing every request behind it.

Bridge from SQL: a plain def handler is a query run to completion by one worker connection while other connections wait their turn if the pool is full; async def is closer to how a single database connection can have several statements in flight, interleaved, because each one yields control back while waiting on I/O instead of occupying the connection the whole time.

1 · Two kinds of concurrency, not one

FastAPI supports both handler shapes side by side, and treats them differently: a plain def handler (every handler through Day 19) is automatically run in a worker thread from a background thread pool, so a slow one occupies its own thread while other requests keep moving on other threads. An async def handler instead runs on a single shared event loop: only one piece of Python code actually executes at any instant, and concurrency comes from each async def function — a coroutine — voluntarily pausing at each await so the loop can run someone else's code while the first one's I/O is still pending.

import time
from fastapi import FastAPI

app = FastAPI()

@app.get("/plain")
def plain_route():             # plain def -> FastAPI's thread pool
    time.sleep(0.05)         # blocks its own thread only
    return {"ok": True}

@app.get("/async")
async def async_route():        # async def -> the shared event loop
    await asyncio.sleep(0.05)  # yields control while waiting
    return {"ok": True}

Confirmed directly by firing five concurrent requests at each route with httpx.AsyncClient and asyncio.gather: five /async requests using await asyncio.sleep(0.05) came back in ~0.05s total, all interleaved on the one event loop; five /plain requests using the ordinary blocking time.sleep(0.05) also came back in ~0.05s total — the thread pool ran them on separate threads at the same time. Both shapes gave real concurrency here. The difference shows up in section 3.

2 · What await actually does

An async def function does not run when you call it — calling it just builds a coroutine object, a paused unit of work. It only starts advancing when something awaits it (or FastAPI itself does, for a route). Inside the function body, every await some_call() is a checkpoint: if some_call() has to wait on something external — a network response, a timer, a database round trip — the coroutine pauses there, and the event loop is free to advance any other coroutine that is ready to make progress, resuming this one later exactly where it left off.

async def fetch_two_things():
    a = await call_one()   # pauses here if call_one() is waiting on I/O
    b = await call_two()   # then pauses here
    return a, b

This is exactly Day 5's generator idea, one level up: a generator's yield pauses a function and hands control back to whatever called next() on it; await pauses a coroutine and hands control back to the event loop driving it. Neither is free-floating parallelism — nothing here spawns a new OS thread or process. It's cooperative: each coroutine has to explicitly give control back via await, and a coroutine that never does so runs to completion uninterrupted, holding the entire event loop hostage the whole time. That's the trap.

3 · The blocking-call trap

Put a plain, blocking call — time.sleep(), a synchronous database driver, an old-style requests.get() — inside an async def function, and nothing raises an error. It just silently defeats the entire point: a blocking call never awaits anything, so it never yields control back to the loop. Every other coroutine, on every other in-flight request, sits frozen until it finishes.

@app.get("/async-trap")
async def async_trap():
    time.sleep(0.05)             # blocking call inside async def - never yields!
    return {"ok": True}

Confirmed with the same five-concurrent-requests measurement as section 1: five requests to a /plain-style route with time.sleep(0.05) took ~0.05s total (thread pool, genuinely concurrent); five requests to this async def version with the identical time.sleep(0.05) inside it took ~0.25s total — 5 × 0.05s, fully serialized, one request finishing before the next even starts. Same call, same duration, radically different outcome, purely because of which handler shape it landed in. The fix is either: don't write async def for a handler whose real work is blocking (a plain def gets it the thread pool for free), or use the actually-async version of that call (await asyncio.sleep(...), an async database driver, httpx.AsyncClient instead of requests).

4 · When async def is worth reaching for

async def pays off specifically when a handler spends most of its time waiting on I/O — an external API call, a database query, another microservice — and there could be many such requests in flight at once: the event loop keeps making progress on other requests during every wait, all on one thread, with none of a thread pool's per-thread memory overhead. It buys nothing for CPU-bound work (parsing a huge file, heavy computation) — nothing is waiting there to yield control during, so an async def doing that work blocks the loop exactly like section 3's trap, for the same reason. asyncio.gather() is the tool for firing several awaitable calls off at once and collecting every result, instead of awaiting them one after another:

async def get_all_prices(item_ids: list[int]) -> list[float]:
    return await asyncio.gather(*[fetch_price(i) for i in item_ids])

Confirmed directly: four calls to a small fetch(n) coroutine, each internally doing await asyncio.sleep(0.03), run one await at a time in a plain loop take ~4 × 0.03s = 0.12s total; the same four calls wrapped in one asyncio.gather(...) call take ~0.03s total — all four in flight together, the slowest one setting the total instead of the sum.

Where pandas goes from here: pandas operations are synchronous and CPU/memory-bound by design — there's no await anywhere in a pandas pipeline, and no benefit from one; async def is a backend-service concern for handling many concurrent I/O-bound requests, a different problem than transforming one already-loaded table.
