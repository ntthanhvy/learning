CORS, now in C# too (AddCors, UseCors, AllowCredentials)

Lesson 52 taught CORS as a browser mechanism — same-origin policy, the Origin header, preflight — with a hand-rolled Go handler setting headers manually. ASP.NET Core ships a first-party CORS middleware instead: policies declared in code, applied by name, with its own sharp edge around credentials. Same mechanism, a different (and more common) way of getting it wrong.

1 · A named policy, registered and applied

ASP.NET Core's CORS support is two calls: AddCors registers one or more policies with the DI container, and UseCors adds the middleware that enforces one of them. A AddCors() call takes a lambda, and inside it options.AddPolicy names a policy and configures it with a CorsPolicyBuilder:

var allowedOrigins = "AllowedOrigins";

builder.Services.AddCors(options =>
{
    options.AddPolicy(name: allowedOrigins, policy =>
    {
        policy.WithOrigins("https://app.example.com")
              .AllowAnyHeader()
              .AllowAnyMethod();
    });
});

var app = builder.Build();

app.UseRouting();
app.UseCors(allowedOrigins);
app.UseAuthorization();

app.MapControllers();

WithOrigins is Lesson 52's allowlist, just expressed as a method call instead of a manual string comparison. AllowAnyHeader/AllowAnyMethod widen which request headers and HTTP methods the preflight check accepts — Lesson 52's Access-Control-Allow-Headers/Access-Control-Allow-Methods response headers, generated for you instead of hand-written.

2 · Middleware order is not optional

Microsoft's own docs state the placement rule plainly: UseCors "must be placed after UseRouting, but before UseAuthorization." This is the middleware-pipeline lesson from Lesson 104 showing up again in a new place — CORS has to be decided before authorization runs, because a request the browser will discard anyway shouldn't still pay for an auth check, and because the preflight OPTIONS request usually carries no credentials at all and would fail an auth check that CORS middleware is meant to intercept first.

Frontend-habit trap: a CORS error in DevTools ("No 'Access-Control-Allow-Origin' header is present") almost always gets "fixed" by reaching for the one call that makes the error disappear: AllowAnyOrigin(). That call doesn't fix a misconfigured policy — Lesson 52's own interview trap applies here unchanged: CORS protects browsers, not your API, so loosening it protects nothing on the server side and widens who a signed-in user's browser will silently act on behalf of.

3 · The one combination the CORS service refuses to serve

One combination is not merely bad practice — it is actively rejected at runtime. Microsoft's own docs state it as a warning: "Specifying AllowAnyOrigin and AllowCredentials is an insecure configuration and can result in cross-site request forgery. The CORS service returns an invalid CORS response when an app is configured with both methods."

policy.AllowAnyOrigin()
      .AllowCredentials(); // never both -- CORS middleware returns an invalid response

The reason traces straight back to the CORS spec itself: a wildcard * origin means "any site may read this," while AllowCredentials() means "send the signed-in user's cookies along." Combine both and literally any website could silently ride a logged-in user's session to your API. The CORS specification itself forbids the combination for exactly this reason, which is why the ASP.NET Core implementation refuses it outright rather than emitting a working-but-dangerous response.

Scope line

This lesson covers ASP.NET Core's first-party CORS middleware — AddCors/UseCors, CorsPolicyBuilder's WithOrigins/AllowAnyHeader/AllowAnyMethod/AllowCredentials, the UseRouting-before-UseCors-before-UseAuthorization ordering rule, and the AllowAnyOrigin+AllowCredentials rejection — as the C# shape of Lesson 52's same-origin-policy and preflight concepts, which this lesson does not re-teach. It does not cover the [EnableCors]/[DisableCors] per-endpoint attributes, or wildcard-subdomain matching via SetIsOriginAllowedToAllowWildcardSubdomains — reasonable next steps, not today's.
