Cache-Control, now in C# too

Lesson 9 named Cache-Control as the cheapest possible cache — a header that tells the browser and any proxy in between to reuse a response for N seconds, with no application code involved at all. Lesson 126 then showed ASP.NET Core's typed access to a different response header, ETag, via GetTypedHeaders(). Today ties the two together: the same typed-header mechanism applies to Cache-Control too, through a sibling class next to EntityTagHeaderValue.

1 · The same header, parsed instead of hand-built

A handler could always write Cache-Control as a raw string, the same way Lesson 126's Go handlers wrote ETag by hand: Response.Headers["Cache-Control"] = "public, max-age=600". That works, but it is exactly the string-formatting trap Lesson 126 called out — get the comma placement wrong, forget a directive, or typo max-age, and nothing catches it until a browser or proxy misreads the header. ASP.NET Core's typed-header path fixes this the same way it fixed ETag: GetTypedHeaders() returns a CacheControl property typed as CacheControlHeaderValue, the direct sibling of Lesson 126's EntityTagHeaderValue:

var responseHeaders = HttpContext.Response.GetTypedHeaders();
responseHeaders.CacheControl = new CacheControlHeaderValue
{
    Public = true,
    MaxAge = TimeSpan.FromMinutes(10)
};
// writes: Cache-Control: public, max-age=600

Each property maps onto one directive from Lesson 9's vocabulary: Public/Private are the two directives deciding whether a shared proxy may cache the response at all, and MaxAge is a real TimeSpan? — not an integer of seconds the caller has to remember to convert — that gets rendered as the header's own max-age=600 seconds format automatically.

2 · NoStore and NoCache: the two directives that mean "don't", differently

Lesson 9 framed caching as a trade of staleness for speed, which only makes sense for data that is safe to reuse at all. Two CacheControlHeaderValue properties exist for the opposite case — telling a cache not to help:

var headers = HttpContext.Response.GetTypedHeaders();
headers.CacheControl = new CacheControlHeaderValue { NoStore = true };
// writes: Cache-Control: no-store -- never persist this response, anywhere

NoStore is the strict one: no cache, browser or proxy, may keep a copy of this response at all — the right choice for a response holding a password reset token or a one-time payment confirmation, where even a deleted-later copy sitting briefly on disk is a risk Lesson 9's trade-off should never be allowed to make. NoCache is easy to misread as the same thing, but it is not — despite the name, a cache may store the response under NoCache, it just must revalidate with the origin server before reusing the stored copy for a later request. That revalidation step is exactly what Lesson 126's ETag/If-None-Match pair exists to make cheap: instead of re-sending the whole body, revalidation can come back as a 304 with no body at all.

Frontend-habit trap: a frontend dev who has only ever set cache: "no-store" on a fetch() call to stop the browser's own HTTP cache from reusing a response is already using this exact mechanism — the browser-side fetch option and the server-side CacheControlHeaderValue.NoStore property are two ends of the same header. The backend half of that conversation is deciding, per endpoint, which directive the server should be the one asserting — not leaving it entirely to whatever the caller happened to request.

3 · Reading the header back on the request side

Lesson 126's pattern was symmetric — RequestHeaders on the way in, ResponseHeaders on the way out. Cache-Control can appear on a request too (a client asserting no-cache to force revalidation, or only-if-cached to refuse a network round trip), and the same typed property reads it back:

var requestHeaders = HttpContext.Request.GetTypedHeaders();
CacheControlHeaderValue? requested = requestHeaders.CacheControl;
if (requested?.NoCache == true)
{
    // client is demanding revalidation -- skip any short-circuit and
    // run the same freshness check Lesson 126's handler already does
}

Nothing about the underlying HTTP semantics changed between Lesson 9 and here — Cache-Control is still the same header, the same directives, the same freshness-vs-staleness trade-off. What changed is only the access pattern, and it is the identical change Lesson 126 already made for ETag: a typed C# object instead of a raw string, on both the request and the response side.

Scope line

This lesson covers GetTypedHeaders().CacheControl and CacheControlHeaderValue as the C# mechanism for Lesson 9's Cache-Control header. It does not cover ASP.NET Core's Response Caching Middleware (Microsoft.AspNetCore.ResponseCaching, AddResponseCaching()/UseResponseCaching()) or the newer Output Caching Middleware (Microsoft.AspNetCore.OutputCaching, .NET 7+) — both are a separate, higher-level concern: a server-side cache that actually stores and serves response bodies, built on top of these same header values rather than being the header mechanism itself. Both are real and worth a future lesson, out of scope for a first pass at the header-level building block.
