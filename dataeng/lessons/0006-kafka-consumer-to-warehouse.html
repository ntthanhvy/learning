1 · Why "lands events safely" is the whole day

Day 5 built a read-only inspector: it printed messages, it never wrote anything permanent, so if it crashed halfway through, nothing was lost or duplicated — you'd just run it again. Today's consumer is different in one way that changes everything: it writes to Postgres, a side effect that outlives the process. That side effect is exactly what makes crash recovery a real problem instead of a hypothetical one.

Kafka's own delivery guarantee, undecorated, is at-least-once: a message might be processed more than once, but it is never silently dropped. That's not a bug to eliminate — it's the trade Kafka makes so that "did this write actually happen?" never has a worse answer than "maybe twice," only ever "at least once." The alternative extremes both cost more than they're worth here: at-most-once (commit the offset before writing, so a crash after commit but before write loses the message forever) is wrong for financial-adjacent data like orders, and true exactly-once across a message queue and an external database needs distributed transactions or Kafka-specific transactional APIs — Phase 2b vocabulary, out of scope for a single Postgres sink. At-least-once plus a write that doesn't mind being repeated is simpler and is what real pipelines actually run.

This is the backend course's idempotency-key idea, applied one level down the stack: backend/ already covers designing an API so the same request retried twice produces the same end state. Today applies that identical principle to a consumer instead of an HTTP handler — same input processed twice, same end state — without re-deriving the concept itself.

2 · The write that doesn't mind being repeated

An idempotent write is what makes at-least-once safe rather than dangerous: if the same event arrives twice, the second write must be a no-op, not a second row. Postgres gives you this directly, and it's why Day 1 made event_id the primary key of raw.order_events:

INSERT INTO raw.order_events (event_id, order_id, status, occurred_at)
VALUES (%(event_id)s, %(order_id)s, %(status)s, %(occurred_at)s)
ON CONFLICT (event_id) DO NOTHING

ON CONFLICT (event_id) DO NOTHING means: if a row with this event_id already exists, skip the insert silently instead of raising a duplicate-key error. Redeliver the exact same message ten times and the table still has exactly one row for it. This only works because event_id is a real, stable identity generated once by the producer (Day 5's uuid.uuid4()) — if the table were keyed on something that changes per attempt, or had no unique constraint at all, ON CONFLICT would have nothing to key off and every redelivery would insert a fresh duplicate.

3 · Commit order is the other half

The idempotent write only protects you if the offset commit happens after it, never before. Two orderings, one correct:

OrderCrash between the two stepsResult
commit offset, then writewrite never happensevent silently lost — this is at-most-once, wrong for order data
write, then commit offsetoffset not yet advancedevent redelivered on restart, ON CONFLICT absorbs it — correct

That second row is today's whole consumer, in one sentence: write first, commit second, and let the primary key absorb whatever the gap between them redelivers. This needs manual offset commit — Day 5's inspector used enable.auto.commit: True because it had nothing to protect; today's consumer sets it to False and calls consumer.commit() itself, on the line right after the database transaction commits.

5 · Build: the consumer, scripts/consume_order_events.py

This is today's actual skill, adapted from Day 5's producer/inspector shapes you already have — given in full because the ON CONFLICT SQL and the commit-after-write ordering are precise enough that getting them slightly wrong defeats the whole lesson, per this course's "give full code for scaffolding, partial code only for the day's skill" rule; today's skill is understanding why this shape is correct, which the quiz and interview question below test directly:

"""Consume order_events and land them in raw.order_events, at-least-once
made safe by an idempotent write.

Manual offset commit happens *after* the INSERT commits, never before --
that ordering is the whole lesson. If this process dies between the INSERT
and the commit, Kafka redelivers the same message on restart; ON CONFLICT
(event_id) DO NOTHING makes redelivery a no-op instead of a duplicate row.
"""
import json

import psycopg
from confluent_kafka import Consumer

BOOTSTRAP = "localhost:9092"
TOPIC = "order_events"
GROUP_ID = "warehouse-loader"
PG_DSN = "host=localhost dbname=fdp user=fdp password=fdp"

INSERT_SQL = """
    INSERT INTO raw.order_events (event_id, order_id, status, occurred_at)
    VALUES (%(event_id)s, %(order_id)s, %(status)s, %(occurred_at)s)
    ON CONFLICT (event_id) DO NOTHING
"""


def main():
    consumer = Consumer(
        {
            "bootstrap.servers": BOOTSTRAP,
            "group.id": GROUP_ID,
            "auto.offset.reset": "earliest",
            "enable.auto.commit": False,
        }
    )
    consumer.subscribe([TOPIC])

    conn = psycopg.connect(PG_DSN, autocommit=False)

    try:
        while True:
            msg = consumer.poll(timeout=5.0)
            if msg is None:
                break
            if msg.error():
                print(f"consumer error: {msg.error()}")
                continue

            event = json.loads(msg.value())
            with conn.cursor() as cur:
                cur.execute(INSERT_SQL, event)
            conn.commit()

            # Offset commit happens only after the write is durable in
            # Postgres -- if the process dies before this line, the next
            # start re-reads this message and the ON CONFLICT clause
            # absorbs the duplicate.
            consumer.commit(message=msg, asynchronous=False)
            print(
                f"landed event_id={event['event_id']} order_id={event['order_id']} "
                f"status={event['status']} (partition={msg.partition()} offset={msg.offset()})"
            )
    finally:
        consumer.close()
        conn.close()


if __name__ == "__main__":
    main()

Two choices worth naming out loud, because they're both the kind of thing an interviewer asks about directly: conn.commit() happens on its own line, separate from the INSERT, so the Postgres transaction is fully durable before the code even reaches the Kafka commit call — and consumer.commit(message=msg, asynchronous=False) blocks until Kafka confirms the offset is stored, rather than firing it and moving on, so "the commit happened" is something the code actually knows, not something it assumes.

6 · Verify: kill it mid-stream, restart it, count rows

This is the actual proof, not a claim to take on faith. Produce a fresh batch, start the consumer, and kill it — hard, kill -9, no graceful shutdown — partway through:

uv run --with confluent-kafka python3 scripts/produce_order_events.py   # Day 5's producer, a fresh batch
uv run --with confluent-kafka --with "psycopg[binary]" python3 scripts/consume_order_events.py &

This round's verification did exactly this against a real broker and a real Postgres, with a script that force-exits (os._exit(), the hardest stop short of kill -9 from outside) right after its 3rd write lands but before that 3rd message's offset commits — the precise gap the whole lesson is about. 7 · Build: mart_delivery_sla

With events landing safely, build the mart PLAN.md names as this phase's second headline table: minutes from placed to delivered, and the share of orders over 45 minutes, per city per day. Its grain is one row per city per day — declare that out loud before reading the SQL, per Day 4's Kimball framing. Create models/marts/mart_delivery_sla.sql:

-- models/marts/mart_delivery_sla.sql
with placed as (
    select order_id, occurred_at as placed_at
    from {{ ref('stg_order_events') }}
    where status = 'placed'
),

delivered as (
    select order_id, occurred_at as delivered_at
    from {{ ref('stg_order_events') }}
    where status = 'delivered'
),

order_durations as (
    select
        o.order_id,
        o.restaurant_id,
        r.city,
        p.placed_at,
        d.delivered_at,
        extract(epoch from (d.delivered_at - p.placed_at)) / 60 as minutes_to_deliver
    from {{ ref('stg_orders') }} as o
    inner join placed as p on p.order_id = o.order_id
    inner join delivered as d on d.order_id = o.order_id
    inner join {{ ref('stg_restaurants') }} as r on r.restaurant_id = o.restaurant_id
)

select
    city,
    date_trunc('day', placed_at)::date as order_date,
    count(*) as delivered_orders,
    avg(minutes_to_deliver) as avg_minutes_to_deliver,
    sum(case when minutes_to_deliver > 45 then 1 else 0 end)::numeric
        / count(*) as share_over_45_min
from order_durations
group by
    city,
    date_trunc('day', placed_at)::date

Both inner joins to placed/delivered are deliberate, not an oversight: an order with no delivered event yet (still in flight, or cancelled) has nothing to compute a duration from, so it's correctly excluded from an SLA metric rather than forced into a null-filled row. That's a real modelling choice worth being able to defend — a cancelled-order rate is a different metric, for a different mart, not a row in this one with a null duration.

Add the grain test to models/marts/marts.yml, alongside Day 4's two entries:

    columns:
      - name: city
        tests:
          - not_null

Q: "Your Kafka consumer crashes and restarts mid-stream. Walk me through why the warehouse doesn't end up with duplicate rows." A strong answer, out loud: "Kafka's own guarantee here is at-least-once — a manual-commit consumer might process a message more than once after a crash, but it never silently drops one. That's fine as long as the write on the other end is idempotent. My consumer commits the database write first, then commits the Kafka offset — never the reverse — so if it dies in between, the write already happened and only the offset bookmark is behind. On restart, the consumer group resumes from that stale offset and redelivers the message it already wrote. The INSERT uses ON CONFLICT (event_id) DO NOTHING keyed on the producer-generated event_id, so the redelivered write is a no-op instead of a second row. The result is exactly one row per event no matter how many times a crash forces a redelivery — I tested this directly by killing the consumer mid-write and confirming the final row count matched the distinct event_id count exactly." The signal: naming the two halves separately (commit ordering, then the idempotent key) instead of waving at "idempotency" as one vague fact, and having actually watched a restart redeliver and get absorbed rather than asserting it would.
