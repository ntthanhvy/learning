Dependency injection with Depends() & structuring an app

Every handler so far has been a self-contained function: Day 16 read path/query values straight off its parameters, Day 17 and 18 validated a whole body through a pydantic model. But real routes repeat work — reading the same query params, checking the same auth header, opening the same database connection — and copy-pasting that logic into every handler is exactly the kind of duplication Day 4's functions existed to kill. Today: Depends(), which lets FastAPI call a plain function for a handler and hand it the result — and APIRouter, which lets those handlers live in more than one file as an app grows past a handful of routes.

Bridge from SQL: a shared dependency is a reusable view or a common-table-expression referenced from several queries — write the "get the current user" logic once, and every query (handler) that needs it just references it, instead of re-deriving it inline each time.

1 · Depends(): FastAPI calls a function for you

A handler parameter whose default is Depends(some_function) tells FastAPI: before running this handler, call some_function — itself an ordinary function that can take its own path/query/body parameters exactly like a handler can — and pass whatever it returns as this parameter's value.

from fastapi import FastAPI, Depends

app = FastAPI()

def get_query_params(limit: int = 10, offset: int = 0):
    return {"limit": limit, "offset": offset}

@app.get("/items")
def list_items(params: dict = Depends(get_query_params)):
    return {"received": params}

@app.get("/users")
def list_users(params: dict = Depends(get_query_params)):
    return {"received": params}

get_query_params is not decorated with @app.get — it is never itself a route, only a plain function FastAPI calls on a handler's behalf. Confirmed directly: calling GET /items?limit=5&offset=20 hands list_items a params of {"limit": 5, "offset": 20}, and calling GET /users?limit=3 reuses the exact same function and returns {"limit": 3, "offset": 0} — one function, two unrelated routes, no copy-pasted parameter-reading code in either handler. This is Day 4's "extract the repeated part into a function" idiom, just invoked by FastAPI itself instead of called by hand.

2 · A dependency can reject a request before the handler runs

A dependency function is not limited to reading and returning values — it can raise, and Day 16's HTTPException works exactly the same way here as inside a handler. That turns Depends() into a gate: auth checks, permission checks, anything that should block a request before a handler's own logic runs at all.

from fastapi import Header, HTTPException

def require_token(x_token: str = Header(...)):
    if x_token != "secret":
        raise HTTPException(status_code=401, detail="bad token")
    return x_token

@app.get("/secure")
def secure_route(token: str = Depends(require_token)):
    return {"token": token}

Confirmed with TestClient: a request carrying header x-token: secret reaches secure_route normally and returns 200; a request with the wrong token gets 401 straight from require_token's own raise, and secure_route's body never executes at all; a request with no x-token header gets 422 instead — Header(...) is a required parameter on require_token itself, so a missing header fails FastAPI's own parameter validation (the same "required, no default" rule Day 16 taught) before require_token's body ever runs, one layer earlier than the 401 it would otherwise raise.

3 · Sub-dependencies: a dependency can depend on another

A dependency function's own parameters can themselves default to Depends(...), building a chain — commonly "get a database connection" feeding into "get the current user from that connection." FastAPI resolves the whole chain before your handler runs, and calls each shared dependency once per request, no matter how many other dependencies in the chain ask for it.

def get_db():
    return {"conn": "fake-db"}   # stand-in for a real DB connection

def get_current_user(db: dict = Depends(get_db)):
    return {"user": "alice", "db": db}

@app.get("/whoami")
def whoami(user: dict = Depends(get_current_user)):
    return user

Confirmed by tracking call order with a shared list: for one request to /whoami, get_db runs first, then get_current_user — resolved in dependency order automatically, with no handler ever calling either function by name — and get_db ran exactly once per request even though it sits underneath another dependency, not once per thing that depends on it. That single-call-per-request guarantee is what makes "open one DB connection, reuse it for every dependency in this request" a safe pattern rather than one that silently opens several.

4 · APIRouter: splitting handlers across files

Every lesson so far put every route on one app = FastAPI() object in one file — fine for five routes, unworkable for fifty. APIRouter is a stand-in for app that a separate module can define its own routes on, later attached to the real app with include_router():

# items.py — a route module, no FastAPI() instance of its own
from fastapi import APIRouter

router = APIRouter(prefix="/items", tags=["items"])

@router.get("")
def list_items():
    ...

@router.get("/{item_id}")
def get_item(item_id: int):
    ...

# main.py — assembles the app from route modules
from fastapi import FastAPI
from items import router as items_router

app = FastAPI()
app.include_router(items_router)

@router.get(...) reads exactly like @app.get(...) — same decorator shape, same handler-writing rules from Day 16 onward — because APIRouter is deliberately built to feel identical to FastAPI for defining routes. prefix="/items" means every route on this router is defined relative to /items — a route declared at "" answers GET /items, and one declared at "/{item_id}" answers GET /items/42 — confirmed directly through TestClient against an app assembled with include_router(). This is Day 9's module/package lesson applied to a specific shape: one router module per resource (items.py, users.py, ...), each importable and attachable independently, instead of one file holding every route the service has.

Where pandas goes from here: a shared Depends() dependency that opens a database connection is unrelated to how a pandas script would load a table — pd.read_sql(...) is a one-shot call inside a script, not a per-request object a web framework manages and reuses; that lifecycle difference is the whole reason a backend service needs dependency injection at all.
