collections.ChainMap: layered lookups without merging

1 · The problem: three sources of settings, one priority order

A command-line tool typically has settings from several places at once, with a clear priority: explicit CLI flags should win, then a user's config file, then the program's built-in defaults. The naive fix is merging them into one dict — but merging copies every key, so a later change to the original config file or defaults silently stops reaching the merged copy:

defaults = {"color": "blue", "size": "M"}
user_config = {"size": "L"}
cli_flags = {}  # user passed no flags this run

# the naive way: merge into a new dict, losing the layers
merged = {**defaults, **user_config, **cli_flags}
# merged is now its own object -- editing user_config after this point
# does nothing to merged; the link back to the sources is gone

A ChainMap solves this without copying anything — it keeps the three dicts as separate, live layers, and searches through them in order:

from collections import ChainMap

settings = ChainMap(cli_flags, user_config, defaults)
print(settings["size"])    # L -- found in user_config, cli_flags had nothing
print(settings["color"])   # blue -- found in defaults, the only layer that has it
# both confirmed live

ChainMap(cli_flags, user_config, defaults) checks cli_flags first, then user_config, then defaults — returning the first match it finds and ignoring the rest. Bridge from SQL: this is COALESCE(cli_value, user_value, default_value) applied to a whole dict of keys at once instead of one column — take the first non-missing value, checked in a fixed priority order, without touching the tables (dicts) themselves.

2 · .maps: the layers are still separate, live dicts

A ChainMap never merges its inputs — .maps exposes the exact list of original dicts it's searching, in priority order, and each one stays independently mutable:

print(settings.maps)
# [{}, {'size': 'L'}, {'color': 'blue', 'size': 'M'}] -- confirmed live

user_config["color"] = "red"   # edit the ORIGINAL dict directly
print(settings["color"])       # red -- confirmed live: ChainMap sees it immediately

That last line is the entire point: because settings holds a live reference to user_config rather than a copy, editing user_config after the fact is visible through settings right away — exactly the "merge loses the link" problem from Section 1, solved. len(settings) and settings.keys() count each distinct key once, even though "size" and "color" each appear in more than one layer.

3 · Writes only ever touch the first layer

A ChainMap supports item assignment, but it is not symmetric with lookup — a write always goes into the first dict in the chain, never into whichever layer the value was actually found in:

settings["size"] = "XL"
print(settings["size"])     # XL -- confirmed live
print(cli_flags)             # {'size': 'XL'} -- went here, the FIRST map
print(user_config)           # {'size': 'L', 'color': 'red'} -- untouched, even though
                          #   'size' was originally found here, not in cli_flags
# both confirmed live

This makes sense once named for what it is: writing through a ChainMap means "record an override at the highest-priority layer," not "edit wherever this key currently lives." It is exactly the behavior a CLI tool wants — setting settings["size"] = "XL" should act like the user just passed a flag, landing in cli_flags, leaving the saved config file's own dict alone.

4 · new_child(): pushing a temporary layer on top

new_child(d) returns a new ChainMap with d as its highest-priority layer in front of the existing ones — the original ChainMap is left completely unaffected, which makes it a clean way to apply a temporary override, like one request's or one test's settings, without disturbing the shared chain underneath:

scoped = settings.new_child({"size": "S"})
print(scoped["size"])      # S -- the new top layer wins
print(settings["size"])    # XL -- original ChainMap is untouched
# both confirmed live

This is the same shape as a function call's local scope sitting in front of its enclosing scope and the module's globals behind that — Python's own variable lookup is a chain of layered mappings, which is one reason ChainMap lives in the standard library at all rather than being a niche recipe.

Where pandas/NumPy go from here: neither library has an equivalent — ChainMap layers plain dicts for settings-style key lookup, not tabular data, so there is nothing to contrast; this callout exists only to confirm the absence, per MISSION.md's no-pandas rule.
