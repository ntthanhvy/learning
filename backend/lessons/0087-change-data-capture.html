Change data capture: tapping the WAL instead of polling a table

Lesson 29's outbox relay solved the dual-write problem by polling an outbox table on a timer and publishing whatever it finds. Its own "go deeper" line pointed at a bigger idea it never named: Kleppmann's change data capture, treating a database's writes as a stream other systems can consume. Lesson 86 then named the actual stream every write already produces — the WAL. Today connects them: a second way to get the outbox relay's job done, without polling, without an outbox table at all.

1 · What the relay was actually working around

Lesson 29's relay works, but notice what it's doing: waking up on a timer, running SELECT ... WHERE processed_at IS NULL, and hoping nothing changed between polls that it should have caught sooner. That's a real cost — polling delay, wasted queries when nothing changed, and an extra table (the outbox) that exists purely to be polled. The relay needed *some* durable, ordered record of "what changed, in what order" to read from, and building a bespoke one (the outbox table) was the simplest way to get it inside a single Postgres transaction.

But Lesson 86 already named a durable, ordered record of every change that Postgres maintains anyway, for free, on every single write: the write-ahead log. If something could read the WAL directly — the same stream a replica already reads to replay changes — it wouldn't need a bespoke outbox table or a polling loop at all. That something is change data capture (CDC).

Same goal, two mechanisms: the outbox pattern and CDC both answer "how do other systems find out what changed here?" The outbox answers it by writing a second row a poller reads. CDC answers it by reading the change stream the database was always producing regardless.

2 · The replica's trick, pointed at a message queue instead of a table file

Lesson 85 explained a read replica as an ordinary Postgres instance replaying the primary's shipped WAL to keep its table files current. Postgres exposes a variant of that same stream built for exactly this reuse: logical replication. Where Lesson 85's streaming replication ships raw WAL bytes to a replica that replays them into its own table files, logical replication decodes those same bytes into readable row-level events and hands them to a consumer — no second full copy of the database required on the other end. A replication slot is Postgres's bookmark for this: it remembers exactly how far a given consumer has read, and holds the relevant WAL segments so they aren't recycled before that consumer catches up — the same durability guarantee the outbox table gave a relay, provided by Postgres itself instead of an extra table.

Where the actual tool sits: in practice, something like Debezium (an open-source CDC tool) opens a replication slot, decodes the logical stream, and republishes each row change to a message queue such as Kafka — the same "durable ordered stream of changes" the outbox relay produced, just sourced from Postgres's own WAL instead of a hand-maintained table.

3 · The trade CDC makes, compared to the outbox

Outbox (Lesson 29)CDC / logical replication
Where the change record livesa table you create and write to yourselfthe WAL, which Postgres already writes for every change
Extra write in the handler's transaction?yes — one INSERT into outbox alongside the business writeno — capture happens outside the application entirely
How a consumer notices new eventsa relay polls the table on a timera consumer streams continuously from a replication slot
What it can captureonly events the handler explicitly wrote to outboxevery row-level change to a table, including ones no handler intended to publish
Extra moving infrastructurea relay process your team owns and runsa CDC tool (e.g. Debezium) plus a replication slot to operate

Neither is strictly better. The outbox keeps the "what counts as an event" decision inside application code, deliberately — you write exactly the events you mean to publish, in whatever shape you choose, and nothing else leaks out. CDC captures changes the database already made, which is powerful for retrofitting event streams onto existing tables without touching handler code, but it means every column change becomes a candidate event whether or not it was meant to be one, and the event's shape is whatever the row's columns happen to be, not a shape you designed. Both still hand the same at-least-once delivery problem to whatever consumes the stream — Lesson 29's "a crash can cause a duplicate, never a silent loss" applies to CDC's consumer just as much as the outbox relay's.

Q: "You've built the transactional outbox pattern before. When would you reach for change data capture instead?" A strong answer, out loud: "They solve the same dual-write problem — getting a durable, ordered stream of changes out to other systems — but the outbox keeps that decision in application code: I write exactly the rows I mean to publish, in a shape I control, inside the same transaction as the business write. CDC instead reads Postgres's own write-ahead log through logical replication, so it captures every row-level change to a table automatically, without touching handler code at all. I'd reach for CDC when I'm retrofitting an event stream onto tables I don't want to modify, or feeding a data pipeline that wants every change regardless of whether a developer remembered to publish it. I'd stick with the outbox when I want to deliberately design what an event looks like and only emit specific ones, since CDC gives you the raw row diff, not a shape you chose." The signal: naming the WAL/logical-replication mechanism specifically, not just "CDC watches the database," and picking a concrete reason to prefer one over the other rather than treating them as interchangeable.
