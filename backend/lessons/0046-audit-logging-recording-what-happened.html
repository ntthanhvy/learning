Audit logging: recording what happened, not just what's true now

"Audit trail" has come up three times already — Lesson 14's PR review flagged a missing one, Lesson 20 named it as a review lens, Lesson 34's soft-delete lesson leaned on it to justify keeping a row — but no lesson ever explained what one actually is or how to build it. Today: the difference between a table and an audit log, why "just check updated_at" isn't enough, and a minimal, real pattern for recording who changed what and why.

1 · A table only remembers the present

An accounts row with a status column tells you exactly one thing: what the status is right now. Lesson 39's MVCC lesson explained that Postgres keeps old row versions around briefly for in-flight transactions — but VACUUM cleans those up once nothing needs them. Once a row is updated, the fact that it used to say something else is gone. There's no column recording that suspension happened, who did it, or why — only that it's suspended now.

That's fine for most columns. It stops being fine the moment someone asks a question a plain table structurally cannot answer: "who suspended this account, and when?" "did the discount get changed after the order shipped?" "prove this refund was actually authorized." A audit log exists because the current-state table was never designed to answer "what happened," only "what's true."

The frontend equivalent you already own. This is the same split as Redux DevTools' action list versus the current store state: the store tells you what's true right now, the action log tells you the sequence of dispatches that got it there — and you reach for the action log specifically when "what's true" doesn't explain "how did it get this way." An audit log is that action list, persisted server-side instead of thrown away on page refresh.

2 · Not the same thing as updated_at, and not the same thing as logging

Two things that look like they'd cover this don't. An updated_at timestamptz column (common on most tables already) only ever holds the last change — a second update overwrites the first's timestamp with no trace either happened, and it never says who or what changed, only when. Lesson 13's structured logging is closer but still the wrong tool by default: application logs are optimized for debugging and typically rotate or expire (Lesson 13 never promised permanence), aren't scoped per-entity, and mix operational noise ("connection pool at 80%") in with the one line that actually matters for an audit question. An audit log is deliberately narrower and longer-lived than either: one row per meaningful state change, kept as long as the business or legal requirement demands, queryable by entity rather than by grepping timestamps.

CREATE TABLE audit_log (
  id            bigserial PRIMARY KEY,
  actor_id      bigint NOT NULL REFERENCES accounts(id),
  action        text NOT NULL,        -- e.g. 'account.suspend'
  entity_type   text NOT NULL,        -- e.g. 'account'
  entity_id     bigint NOT NULL,
  change        jsonb NOT NULL,        -- what actually changed
  reason        text,                  -- optional, but valuable when present
  created_at    timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX ON audit_log (entity_type, entity_id, created_at);

change is deliberately JSONB, not more columns — Lesson 44's own rule applies directly: every audit row has the same handful of fixed fields (actor_id, action, entity_type, entity_id), so those stay real typed columns, but what actually changed varies action to action (a suspension changes status; a discount edit changes percent_off) and nobody wants a new migration every time a new field becomes auditable.

3 · Writing the audit row in the same transaction as the change

The insert has to happen atomically with the change it's recording, or it isn't trustworthy — a state change that succeeds while its audit row fails to write (a crash between the two statements, exactly Lesson 6's atomicity problem) leaves an unexplained gap in the trail, which defeats the entire point. Wrapping both statements in one transaction (Lesson 6) fixes it the same way it fixed the outbox pattern's dual-write problem in Lesson 29 — the state change and the record of the state change either both commit or neither does.

type Querier interface {
    Exec(ctx context.Context, sql string, args ...any) error
}

// ActorContext names who is making this change and why -- an audit row
// with no actor is close to useless, so it's a required parameter, not
// an optional extra bolted on later.
type ActorContext struct {
    ActorID int64
    Reason  string
}

// suspendAccount is Lesson 45's SuspendDelinquentAccount, extended to
// write an audit_log row in the SAME transaction as the state change --
// Lesson 6's atomicity, applied to "what happened" instead of just
// "what changed".
func suspendAccount(ctx context.Context, db Querier, actor ActorContext, accountID int64) error {
    if err := db.Exec(ctx,
        `UPDATE accounts SET status = 'suspended' WHERE id = $1`, accountID); err != nil {
        return fmt.Errorf("suspend account %d: %w", accountID, err)
    }

    change, err := json.Marshal(map[string]string{"status": "suspended"})
    if err != nil {
        return fmt.Errorf("marshal audit change: %w", err)
    }

    if err := db.Exec(ctx,
        `INSERT INTO audit_log (actor_id, action, entity_type, entity_id, change, reason)
		 VALUES ($1, $2, $3, $4, $5, $6)`,
        actor.ActorID, "account.suspend", "account", accountID, change, actor.Reason,
    ); err != nil {
        return fmt.Errorf("write audit log for account %d: %w", accountID, err)
    }
    return nil
}

In real code, db here would be a transaction handle (a pgx.Tx, not a bare pool) so both Exec calls are guaranteed atomic — the snippet keeps the same minimal Querier interface shape Lesson 42 used, since the point here is the two-writes-together pattern, not the transaction plumbing itself.

4 · What actually belongs in one, and what doesn't

Not every table needs this. The deciding question is the same shape Lesson 34 already used for soft delete: does something outside the current-state table — a support ticket, a compliance requirement, a "who approved this" question — legitimately need the history to exist, or is "what's true now" actually the whole answer here too? A user's UI theme preference doesn't need an audit trail; a balance change, a permission grant, or anything Lesson 12's authorization lesson gates almost always does. Money movements, permission and role changes, and anything a support agent might need to reconstruct ("why does this account say suspended?") are the recurring real-world candidates — not "every table, just in case."

updated_at columnApplication log (Lesson 13)Audit log
What it keepsOnly the most recent change's timestampEvery operational event, rotated/expired over timeEvery meaningful state change, kept as long as required
Says who changed itNo — timestamp onlySometimes, mixed with unrelated log linesYes — actor is a required field
Queryable per entityN/A — one value per rowAwkward — needs log search/grepYes — indexed by entity_type + entity_id
Survives the next updateNo — overwritten in placeUntil the log rotates outYes — append-only by design

The append-only property is what makes an audit log trustworthy: rows are only ever inserted, never updated or deleted by normal application code — if a row could be edited after the fact, it would stop proving anything. That's also why it's a separate table rather than a "history" JSONB column bolted onto accounts itself: a new row per change keeps every past version intact, where a single mutable column would just repeat the updated_at problem with extra steps.

Q: "How would you add an audit trail for account status changes?" A strong answer, out loud: "A separate, append-only audit_log table — actor id, action, entity type and id, a JSONB column for what actually changed since that varies per action, and a timestamp. I'd write the audit row in the same transaction as the state change itself, so the two can't drift apart if something fails between them — the same atomicity problem Lesson 6 covers and the outbox pattern solves for events. I wouldn't add this to every table; it's for changes someone might later need to explain — money, permissions, anything support or compliance could ask about — not a blanket default." The signal: naming atomicity and append-only explicitly, not just "add a log table."
