csv.DictWriter: the write side of Day 6's DictReader

Day 6 taught csv.DictReader for turning a CSV's rows into dicts keyed by column name — but a pipeline that reads, cleans, and aggregates records eventually has to write a result back out, and Day 6 never covered that half. Today closes it: csv.DictWriter, the dict-in-CSV-out mirror of DictReader, plus the one gotcha (newline="") that silently doubles line endings on Windows if skipped.

Why today, specifically: a fresh-gap grep confirmed csv.DictWriter never appears in any of this course's 65 lessons or in reference/glossary.html, even though Day 6 taught the read side in full and this course's own capstone framing (read → clean → aggregate → write) has always implied a write step that was never actually taught. csv.writer/csv.DictWriter is the natural, concrete half-topic this leaves on the table.

1 · Why DictWriter needs fieldnames= and DictReader doesn't

Recall Day 6's csv.DictReader: it reads the file's first row and uses those column names as dict keys automatically — there's always a header row already sitting in the file to infer them from. Writing has the opposite problem: nothing exists on disk yet, so there is no header row to read column names from. csv.DictWriter has to be told the column order and names up front, via a required fieldnames= argument:

import csv

rows = [
    {"city": "Hanoi", "amount": 120},
    {"city": "Hue", "amount": 45},
]

with open("out.csv", "w", newline="") as f:
    writer = csv.DictWriter(f, fieldnames=["city", "amount"])
    writer.writeheader()
    writer.writerows(rows)

fieldnames does double duty: it fixes the column order in the file, and it's the whitelist DictWriter checks every row's keys against before writing. This is the same "names have to point at something that actually exists" idea Day 1 raised for variables, applied to dict keys instead — DictWriter can't write a column it was never told about, the same way Python can't look up a name nobody ever assigned.

2 · writeheader() then writerows() / writerow()

Unlike DictReader, which consumes the header row automatically, DictWriter never writes one on its own — writeheader() has to be called explicitly, exactly once, before any data rows:

with open("out.csv", "w", newline="") as f:
    writer = csv.DictWriter(f, fieldnames=["city", "amount"])
    writer.writeheader()                 # writes "city,amount\n" — skip this and the file has no column names at all
    writer.writerow({"city": "Hanoi", "amount": 120})   # one row at a time
    writer.writerows(rows)               # or many rows at once, from any iterable of dicts

writerow() takes one dict and writes one line; writerows() takes any iterable of dicts — a list, or even a generator, same as Day 5's lazy pipelines — and writes one line per dict, in the order fieldnames specified, regardless of what order the dict's own keys happen to be in.

3 · The newline="" gotcha

Opening the output file with plain open(path, "w") instead of open(path, "w", newline="") is a real, commonly-hit bug — not a style preference. Python's text mode translates every "\n" a program writes into the current platform's native line ending; on Windows that's "\r\n". The csv module already writes its own "\r\n" line endings itself, per the CSV format's own rule. Stack the two translations and a row ends up with "\r\r\n" — an extra blank-looking character that shows up as a stray blank line in some viewers and breaks strict line counts:

# WRONG on Windows: "w" alone lets text mode ALSO translate \n -> \r\n,
# stacking on top of csv's own \r\n and doubling every line ending
with open("out.csv", "w") as f:
    writer = csv.DictWriter(f, fieldnames=["city", "amount"])
    writer.writeheader()

# RIGHT: newline="" disables text mode's own translation, leaving csv's
# \r\n as the only line ending actually written
with open("out.csv", "w", newline="") as f:
    writer = csv.DictWriter(f, fieldnames=["city", "amount"])
    writer.writeheader()

This is easy to miss on Linux or macOS, where the native line ending is already "\n" and the bug doesn't show up locally — then it ships and breaks the moment the same script runs in CI or on a teammate's Windows machine. The fix costs nothing: always pass newline="" to open() when the file is about to be handed to csv.writer or csv.DictWriter, every time, regardless of platform.

4 · Mismatched keys: extrasaction= and restval=

Real dicts don't always match fieldnames exactly — a row might carry an extra key nobody asked for, or be missing one fieldnames expects. By default, DictWriter raises ValueError on an unexpected extra key, which is often too strict for messy, Day-3-style grouped data coming from multiple sources. extrasaction controls that:

rows = [{"city": "Hanoi", "amount": 120, "note": "q3"}]   # "note" isn't in fieldnames

with open("out.csv", "w", newline="") as f:
    writer = csv.DictWriter(f, fieldnames=["city", "amount"], extrasaction="ignore")
    writer.writeheader()
    writer.writerows(rows)   # "note" is silently dropped instead of raising ValueError

The opposite gap — a dict missing a key that fieldnames expects — doesn't raise by default; the missing cell is written empty. restval= sets what to write there instead, e.g. DictWriter(f, fieldnames=[...], restval="N/A"). Both keywords are about the same underlying idea Day 3's dict work already established: a dict's keys are never guaranteed to match any particular set exactly, so code reading or writing one has to decide, on purpose, how to handle the keys that don't line up.

Where pandas goes from here: DataFrame.to_csv() does the open, newline="", header, and row-writing of sections 1–3 in one eager call. Not covered here; that's data/'s job, and this is the only sentence in this lesson that mentions it.
