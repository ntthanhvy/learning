align(): making two mismatched frames line up on purpose

Chào bạn — closing the last standing gap from the last two lessons' teasers: .align() was named twice (Lesson 68's and Lesson 69's closing lines) as the round's other zero-hit candidate but never picked. A fresh grep of all 69 lessons and the glossary confirms it: still zero taught uses. Today's the day — this is a narrower, more advanced tool than .sample(), but it's the method that explains WHY pandas arithmetic between two mismatched DataFrames "just works," which is exactly the kind of under-the-hood question that separates a candidate who's used pandas from one who understands it.

1 · Two DataFrames with different index labels AND different columns

align() takes two objects — call it on one, pass the other — and returns a NEW pair, both reindexed onto a shared label set. Confirmed directly (pandas 3.0.5), two slices of the cleaned orders_raw.csv fixture recent lessons use, indexed by order_id, with different rows present AND different columns:

left  = clean.set_index("order_id")[["customer", "amount"]].loc[[1, 2, 5]]
right = clean.set_index("order_id")[["amount", "order_date"]].loc[[2, 5, 6]]

a, b = left.align(right)
# a and b BOTH come back with index [1, 2, 5, 6] and
# columns ['amount', 'customer', 'order_date'] -- the UNION of each side,
# missing cells filled with NaN

Confirmed directly: a.index.tolist() and b.index.tolist() both come back [1, 2, 5, 6] — the union of left's [1, 2, 5] and right's [2, 5, 6] — and both frames' .columns.tolist() come back the same three-column union too, even though neither original frame had all three. Row 1 exists only in left, so in the returned b every one of its cells is NaN; row 6 exists only in right, so the returned a is all-NaN there. This default behavior — union on BOTH axes, gaps as NaN — is exactly what pandas does silently inside left + right; align() just does the same reindex step by itself, as an explicit, inspectable operation, before any math happens.

SQL bridge: there's no single-clause SQL equivalent — the closest mental model is a FULL OUTER JOIN on the shared key, except align() works on labels already sitting in an Index, not on a join column, and it aligns COLUMN NAMES too, which a JOIN never does. Two tables with different column sets don't "align" in SQL at all; you'd write out an explicit column list per side. align()'s job is closer to what a spreadsheet does lining up two ranges by their row/column headers before you subtract one from the other.

2 · join= controls which labels survive: outer (default), inner, left, right

The default is join="outer" — every label from both sides survives, gaps become NaN, as shown above. join="inner" keeps only labels present on BOTH sides — no gaps, because nothing missing survives at all:

a, b = left.align(right, join="inner")
# a.index.tolist() == [2, 5]      -- only rows in BOTH left and right
# a.columns.tolist() == ['amount'] -- only the column in BOTH

Confirmed directly: with join="inner", the returned index is [2, 5] (dropping row 1, only in left, and row 6, only in right) and the returned columns are just ['amount'] (dropping customer, only in left, and order_date, only in right) — no NaN anywhere in the result, because every surviving label existed on both sides already. join="left" keeps exactly left's own labels (both frames come back re-indexed to match left's [1, 2, 5], confirmed directly); join="right" is the mirror, keeping right's labels. This is the same four-way vocabulary as SQL join types (Lesson 5) — outer/inner/left/right mean the same "which rows survive" thing here, just applied to labels instead of a join key.

3 · axis= restricts alignment to just rows, or just columns

By default align() reindexes BOTH the index and the columns, as seen above. axis=0 aligns only the row index and leaves each frame's own columns untouched; axis=1 aligns only the columns and leaves each frame's own index untouched. Confirmed directly:

a, b = left.align(right, axis=0)
# a.columns.tolist() == ['customer', 'amount']        -- left's own, unchanged
# b.columns.tolist() == ['amount', 'order_date']       -- right's own, unchanged
# BOTH a.index and b.index == [1, 2, 5, 6]              -- rows still aligned

This is the version most likely to show up in real code: two frames that are meant to share a row axis (e.g. a metrics frame and a targets frame, both keyed by order_id) but legitimately have different, unrelated columns — axis=0 row-matches them without inventing a nonsense column union neither frame ever had.

4 · fill_value=, and the dtype trap it walks into

fill_value= replaces the default NaN gaps with a chosen value instead — but confirmed directly, this only works cleanly when every surviving column can actually hold that value's type:

left_num, right_num = left[["amount"]], right[["amount"]]
a, b = left_num.align(right_num, fill_value=0)
# a["amount"] at row 6 (missing from left) becomes 0.0, not NaN -- works,
# because 'amount' is already a numeric (float) column

left.align(right, fill_value=0)
# TypeError: Invalid value '0' for dtype 'str' -- 'customer' is a string
# column, and 0 (an int) cannot fill a string column's gaps

Confirmed directly: fill_value=0 on the numeric-only amount-column subset works exactly as expected, turning the row-6 gap into a real 0.0. But calling it on the original mixed-dtype frames — where the union of columns includes the string customer column — raises a real TypeError, because 0 is not a valid fill for a string dtype. This is the same "one fill value can't serve every column" trap fillna() hits with a scalar across mixed dtypes (Lesson 3) — align() inherits it exactly, since fill_value= is applied uniformly across the whole result.

Q: "Why would you ever call align() explicitly, if pandas already auto-aligns on arithmetic?" A strong answer, out loud: "Direct arithmetic like left + right does auto-align internally, on a union of both axes by default — that part's true. But align() is what you reach for when the two objects need to stay LABEL-MATCHED across more than one separate operation, not just one math expression — for example, computing several different columns' differences one at a time, or feeding both frames into two different function calls that each need the same row order. Calling align() once up front, usually with join='inner' and axis=0 to row-match without inventing a nonsense column union, gives back two objects guaranteed to share the same index — after that, every later operation on either one is safe without pandas silently re-aligning (or silently introducing NaN) each time. It's also the tool that makes the 'why does arithmetic between two DataFrames sometimes fill in NaN out of nowhere' question answerable: that NaN is align()'s default outer join happening invisibly." The signal: naming that arithmetic ALREADY does this implicitly (most candidates don't know that), and specifically naming join=/axis= as the controls for choosing what survives instead of just accepting the default outer-join-everywhere behavior.
