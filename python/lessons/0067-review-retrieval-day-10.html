1 · Three questions, in the original teaching order

Answer each out loud or on paper before reading the fold-out answer. If one is shaky, note it and go fix it in the practice file below rather than only rereading the old lesson.

Day 64 — zipfile. Why does zf.namelist() never need to extract anything first, and what is the one real risk to guard against when calling extractall() on an archive from an untrusted source?

Fold-out answer: namelist() reads the archive's own internal listing of member paths — it never touches member bytes, extracted or not. The risk with extractall() on an untrusted archive is path traversal: a crafted member name like ../../etc/passwd could, on older extraction code, write outside the intended destination entirely. Modern extractall() guards against that specific escape, but an untrusted archive still deserves the same caution as any other unvalidated input, the way Day 62's rmtree() callout already established for paths in general.

Day 65 — tempfile. Why does a with tempfile.TemporaryDirectory() block clean up its contents even when an exception is raised partway through, and when is delete=False on NamedTemporaryFile() actually the right call?

Fold-out answer: TemporaryDirectory() is a context manager (Day 6) — the with block's exit always runs, whether the block finished normally or an exception interrupted it partway through, so the whole directory and everything written inside it is deleted either way. That is exactly what a hand-written path-plus-manual-delete approach cannot guarantee, since an exception before the delete line skips cleanup entirely. delete=False is the right call only when something else — a library, or a platform limitation — needs to reopen the file by its own path rather than accept an already-open file object; it defers cleanup to the caller, who must then delete it manually or lose the automatic-cleanup benefit.

Day 66 — csv.DictWriter. Why does csv.DictWriter require fieldnames= while csv.DictReader never does, and what actually goes wrong if a CSV file is opened for writing without newline=""?

Fold-out answer: DictReader always has an existing header row already sitting in the file to read column names from. DictWriter is creating a brand-new file with nothing on disk yet, so there is no header row anywhere to infer names from — fieldnames= has to be supplied explicitly, and it doubles as the column order and the whitelist of keys DictWriter will accept. Skipping newline="" lets Python's text mode translate every "\n" the program writes into the platform's native line ending ("\r\n" on Windows) — stacked on top of the csv module's own "\r\n", that doubles every line ending to "\r\r\n". It's invisible on Linux/macOS, where the native ending is already "\n", which is exactly why it ships unnoticed and then breaks on a teammate's Windows machine or in CI.
