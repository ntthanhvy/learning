1 · The gap: a gate that blocks, but pages nobody

Day 64 wired check_kafka_lag as a quality gate — a task upstream of dbt_build whose failure stops dbt_build from starting at all, using Airflow's default all_success trigger rule. That lesson's own closing section named the gap it deliberately left open: "check_kafka_lag's failure is visible in the Airflow UI and in dbt_build simply never starting, but nothing pages a human yet — Day 61's on_failure_callback mechanism would attach here directly if that's ever wanted." Nobody has to be staring at the Airflow UI for a blocked pipeline to matter; a pipeline that silently stops running daily marts is exactly the kind of failure a person should hear about without having to go looking for it.

Day 61 already built that hook once, on dbt_build, and confirmed from Airflow 3.3.1's own installed source that it fires once a task instance has truly run out of retries and lands in the terminal FAILED state — distinct from on_retry_callback, which fires on an attempt that still has another try coming. Today is not a new mechanism: it is the same on_failure_callback keyword argument, attached to a second task in the same DAG, closing the exact gap Day 64 named rather than opening new Airflow vocabulary.

2 · Why check_kafka_lag needs this more than most tasks would

Recall Day 64's other deliberate choice: check_kafka_lag gets retries=0, because a stuck consumer's lag rarely clears within the few seconds a retry would wait. That decision has a direct consequence for today's callback: on dbt_build (retries=2), on_failure_callback only fires after two retries have already failed — there is a window where on_retry_callback alone has already told someone something is wrong. On check_kafka_lag (retries=0), the very first failed attempt is the final one: is_eligible_to_retry() has nothing to grant, the task instance goes straight to FAILED, and on_failure_callback is the only hook that will ever fire for this task — a zero-retry task has no earlier warning to lean on, which is exactly why today's gap mattered more here than it might have on a task with retries already cushioning the first failure.

Q: "You've got a quality gate in your DAG that blocks a downstream dbt build on bad data. How do you make sure a human actually finds out when it fires, instead of just checking the Airflow UI?" A strong answer, out loud: "I attach an on_failure_callback to the gate task itself — the same hook I'd use on any task, since it fires once that task instance has genuinely run out of retries and landed in a final FAILED state. For a gate I've deliberately given zero retries, because its failure mode doesn't self-heal, that callback fires on the very first bad exit — there's no earlier on_retry_callback warning to lean on, so the failure callback is the only alert hook that task will ever get. Today that callback is just a print with the exception's real repr, the same honest placeholder I used on the build task itself, because wiring a real paging integration is a separate decision this portfolio hasn't made yet. The useful part is that it's the identical mechanism on both tasks, so swapping the print for a real Slack call later is one change, not two." The signal: connecting a task's retries setting to which callback can fire first, not treating on_failure_callback as interchangeable with on_retry_callback regardless of configuration.
