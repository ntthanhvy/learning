dict & set: grouping without pandas

Day 2 taught the dict/set comprehension shape on purpose without asking you to use it — curly braces, colon or no colon, and stop. Today spends that recognition: dict and set as real lookup and grouping structures, comprehensions used with full confidence, and the pattern every data job needs before pandas ever enters the picture — GROUP BY, done by hand.

Bridge from SQL: SELECT city, COUNT(*) FROM people GROUP BY city builds one bucket per distinct city and counts what lands in each. That's exactly what today's core pattern does — one dict, one key per bucket, one list (or count) growing inside each bucket as you loop the rows once.

1 · dict: a lookup, not a list you search

A list finds things by position — rows[3]. A dict finds things by key — prices["apple"] — and it does that lookup directly, without scanning every entry to find a match. That's the whole reason to reach for one: whenever you'd otherwise write "loop through this list looking for the row where the id matches," a dict already knows.

prices = {"apple": 3.5, "banana": 1.2, "pear": 2.0}

prices["banana"]        # 1.2 — direct lookup, no scanning
prices["kiwi"]           # KeyError — no such key
prices.get("kiwi")        # None — .get() returns None instead of raising
prices.get("kiwi", 0.0)   # 0.0 — .get() with a fallback default

"banana" in prices      # True — membership test checks keys
prices["kiwi"] = 4.0     # adds a new key, or overwrites an existing one

Two everyday methods pull double duty: .keys() gives every key, .values() gives every value, .items() gives (key, value) pairs — the form you'll loop over constantly:

for name, price in prices.items():
    print(name, price)   # unpacks each (key, value) pair — unpacking gets a full lesson Day 4

One rule worth knowing before it bites: dict keys must be immutable — str, int, tuple, bool all work; a list as a key raises TypeError. That's Day 1's mutable/immutable split showing up again: a key has to stay put to be findable, so Python refuses anything that could change underneath it.

2 · set: uniqueness and membership, fast

A set is a dict with only keys, no values — same immutable-elements rule, same direct membership test, but its whole job is "does this exist" and "what's unique here," not lookup-by-key:

seen = {"An", "Binh", "An"}   # {'An', 'Binh'} — duplicate collapses automatically

"An" in seen           # True — direct membership test, not a scan
seen.add("Chi")         # {'An', 'Binh', 'Chi'}

ids_a = {1, 2, 3}
ids_b = {2, 3, 4}
ids_a & ids_b     # {2, 3}       — intersection: in both
ids_a | ids_b     # {1, 2, 3, 4} — union: in either
ids_a - ids_b     # {1}          — difference: in a, not in b

The two most common everyday uses: de-duplicating a list (set(names)), and fast "have I seen this already?" checks in a loop — checking x in a_set is direct, the same way a dict key lookup is, where checking x in a_list means scanning every item.

3 · Grouping: setdefault, then defaultdict

Here is the pattern this whole lesson is building toward — GROUP BY, by hand. The task: given flat sales rows, group amounts by city. In SQL: SELECT city, amount FROM sales with the bucketing done by GROUP BY city. In plain Python, one bucket per distinct key means one dict, and the first entry for each key needs special handling — you can't .append() into a list that doesn't exist yet:

sales = [
    {"city": "Hanoi", "amount": 120},
    {"city": "HCMC",  "amount": 80},
    {"city": "Hanoi", "amount": 45},
]

by_city = {}
for row in sales:
    city = row["city"]
    if city not in by_city:
        by_city[city] = []          # first time we've seen this city: start a bucket
    by_city[city].append(row["amount"])
# {'Hanoi': [120, 45], 'HCMC': [80]}

That if ... not in ... : by_city[city] = [] guard is so common Python gives it one method — setdefault, which does "get it, or create-and-return a default" in one call:

by_city = {}
for row in sales:
    by_city.setdefault(row["city"], []).append(row["amount"])
# same result: {'Hanoi': [120, 45], 'HCMC': [80]}

Read by_city.setdefault(row["city"], []) as: "give me the list at this city's key — and if there isn't one yet, put an empty list there first, then give me that." The .append() on the end always has a list to land in, first row or not.

The standard library has a second way to say the same thing, from the collections module: defaultdict:

from collections import defaultdict

by_city = defaultdict(list)     # list is the FACTORY — called with no args to build each new bucket
for row in sales:
    by_city[row["city"]].append(row["amount"])
# defaultdict(<class 'list'>, {'Hanoi': [120, 45], 'HCMC': [80]})

No setdefault call needed at all — accessing a missing key runs the factory (list(), giving []) automatically and stores the result before returning it. Both approaches produce identical dicts; defaultdict reads slightly cleaner when every value in the dict follows the same "start empty, then grow" rule, which grouping always does. Either is fine to write; both are worth being able to read on sight, because you'll meet both in other people's code.

Counting is grouping's simplest case: if all you want is how many rows per city, not the rows themselves, collections.Counter is purpose-built: Counter(row["city"] for row in sales) gives {'Hanoi': 2, 'HCMC': 1} in one call — the same family as defaultdict, specialized for counting. (The for ... in ... without brackets here is a generator expression — a preview, not today's lesson; Day 5 explains it properly.)

4 · Comprehensions, now with full confidence

Day 2 asked you to recognize the shape only. Now that dict and set are real tools, the same three-slot grammar — expression, for, optional if — is worth using on purpose. A dict comprehension is the right tool whenever the loop's only job is building a lookup:

names = ["An", "Binh", "Chi"]
ages =  [30, 25, 41]

# SQL: SELECT name, age FROM people  -- then keyed by name for lookup
age_of = {n: a for n, a in zip(names, ages)}
# {'An': 30, 'Binh': 25, 'Chi': 41}

# filtered dict comprehension: only the over-30s (SQL WHERE)
seniors = {n: a for n, a in zip(names, ages) if a > 30}
# {'Chi': 41}

# set comprehension: distinct first letters
first_letters = {n[0] for n in names}
# {'A', 'B', 'C'}

zip(names, ages) pairs the two lists element by element into (name, age) tuples — enough to read today; unpacking it fully is Day 4. The dict comprehension's two slots before for are exactly setdefault's two arguments in different clothing: key: value instead of key, default.

One boundary worth being precise about: a comprehension builds the whole result from one pass with no per-key accumulation, so it's the right tool for "one output value per input row" (like age_of above). The grouping pattern from section 3 needs setdefault or defaultdict instead, because multiple rows share a key and their values must accumulate into the same bucket rather than each simply overwriting the last — a comprehension has no way to say "and also append to what's already there."

Where pandas goes from here: the grouping pattern in section 3 is exactly what df.groupby("city")["amount"].sum() does in one call once data/ introduces DataFrames. Same idea — bucket by key, aggregate within each bucket — different spelling for a different container. Not covered here; that's data/'s job, and this is the only sentence in this lesson that mentions it.
