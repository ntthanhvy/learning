A fixed set of values: Postgres ENUM vs. CHECK-constrained text

Lesson 60 named the example directly, in passing, and moved on: "the strongest case for reaching for [a CHECK constraint]: any rule that must never be false... a status column limited to a fixed set of strings." That example has appeared as plain TEXT with a CHECK in every status column this course has written since Lesson 3's orders table — pending, shipped, canceled — without ever asking whether Postgres has a purpose-built type for exactly this. It does, and today's lesson is the choice between the two.

1 · The pattern already in use: TEXT plus CHECK

Every status-like column this course has shown so far looks like this:

CREATE TABLE orders (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    status TEXT NOT NULL CHECK (status IN ('pending', 'shipped', 'canceled')),
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

This works, and it is exactly Lesson 60's CHECK constraint applied to a set membership rule instead of a numeric range: Postgres rejects any write where status isn't one of the three named strings, on every code path, for the same reasons Lesson 60 gave. Nothing about it is wrong. The question this lesson asks is what a purpose-built alternative buys instead.

2 · The alternative: a native ENUM type

Postgres lets you declare the fixed set once, as its own named type, separate from any one table:

CREATE TYPE order_status AS ENUM ('pending', 'shipped', 'canceled');

CREATE TABLE orders (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    status order_status NOT NULL DEFAULT 'pending',
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

A ENUM type moves the same "only these values" rule out of a per-table expression and into the type system: status's column type is order_status, the same way another column's type is BIGINT or TIMESTAMPTZ. Any table that needs the identical set of statuses — a shipments table, an order_events audit table — references the same order_status type by name instead of retyping the same three strings into a new CHECK expression and hoping they never drift apart.

3 · What the ENUM buys: order and reuse

Two properties fall out of declaring the set as a real type instead of a CHECK list. First, an ENUM's values have a built-in ordinal order — the order they were listed in at CREATE TYPE time — so WHERE status < 'shipped' and ORDER BY status follow the declared pending-before-shipped-before-canceled progression, not alphabetical order (which would wrongly sort canceled before pending). A CHECK (status IN (...)) list gives TEXT no ordering at all; sorting or comparing it correctly needs a separate CASE expression mapping each string to a rank number by hand. Second, the type is reusable by name: five tables can all declare a column as order_status, and the set of valid values is guaranteed identical across every one of them, enforced in one place — the same "one fact, one place" instinct Lesson 2's glossary named for normalization, just applied to a type instead of a table.

Frontend-habit bridge: this is the TypeScript type Status = 'pending' | 'shipped' | 'canceled' union, moved into the database. A union type gives the compiler one named, reusable definition of "these three strings and nothing else" instead of repeating the literal string list at every call site — an ENUM does the identical job for Postgres, checked at write time instead of compile time.

4 · What the ENUM costs: schema-change friction

The reuse comes with a real cost the CHECK version doesn't have. Adding a new value to an ENUM is cheap and safe:

ALTER TYPE order_status ADD VALUE 'refunded';

But removing or renaming a value is not a single statement — Postgres has no ALTER TYPE ... DROP VALUE at all, because existing rows might already hold that value and dropping it would leave them referencing a label the type no longer defines. The only path is building a replacement type, migrating every column and every row across to it, and dropping the old type — real work, and exactly the kind of live-table migration Lesson 19 walked through for a column's type generally. A CHECK (status IN (...)) list has no such asymmetry: adding or removing a value is one ALTER TABLE ... DROP CONSTRAINT plus one ADD CONSTRAINT with the new list, a single migration either direction.

5 · Where this actually gets decided

The set that changes often — anything shaped like a workflow that product will keep extending, feature flags' variant names, a status list still being designed — is the case for staying with TEXT + CHECK: the churn cost of the ENUM's one-way street outweighs the ordering and reuse it buys. A set that is genuinely fixed by the domain itself and rarely touched once chosen — the seven days of the week, a small closed set of currency codes, a payment state machine whose stages are contractually fixed — is where the ENUM's reuse-by-name and built-in ordering earn their keep, because the case that costs the most (removing a value) almost never happens. When in doubt, the CHECK version is the safer default precisely because reversing that choice later is cheap; committing to an ENUM and outgrowing it is the expensive direction to walk back from.

Q: "Would you use a Postgres ENUM type or a CHECK constraint for a status column?" A strong answer, out loud: "It depends on how likely the set of values is to change. An ENUM gives you a named, reusable type with a real ordering baked into the declaration order, so ORDER BY and comparisons follow the workflow's own sequence instead of alphabetical order. The cost is that Postgres can add a new ENUM value cheaply but can't drop or rename one in place — doing that means building a replacement type and migrating every table and row across. A CHECK constraint's IN list has no such asymmetry; adding or removing a value is one constraint swap either direction. So I'd reach for an ENUM only when the set is genuinely stable — something like fixed currency codes — and stick with CHECK for anything still likely to grow a new status as the product evolves." The signal: naming the one-way-street cost specifically, not just "ENUMs are stricter," and tying the decision to how volatile the value set actually is.
