Health checks, now in C# too

Lesson 47 covered the liveness-vs-readiness split in Go: one trivial handler that never touches a dependency, one handler that pings the database with a short timeout, wired to two separate endpoints so a database blip can't trigger a fleet-wide restart. That lesson never got a C# mirror, even though every other Go-only mechanism from that stretch of the course — retry, circuit breaker, bulkhead, worker pool, graceful shutdown — has been ported since Lesson 112. Today closes that gap: the exact same split, built from ASP.NET Core's own health-check middleware instead of two hand-written handlers.

1 · Same two questions, one framework feature instead of two handlers

Lesson 47's rule still holds exactly: liveness answers "is this process alive and unstuck," never checks a dependency, and should be nearly free; readiness answers "can this instance serve real traffic right now," and is allowed to ping a dependency with a bounded timeout. What changes in ASP.NET Core is that both endpoints come from one built-in middleware system instead of two routes you write by hand. The building block is IHealthCheck, registered with AddHealthChecks() and exposed at a route with MapHealthChecks().

Per Microsoft's own docs: "Register health check services with AddHealthChecks in Program.cs. Create a health check endpoint by calling MapHealthChecks." That's the whole wiring — no custom http.ServeMux route needed, because the framework already owns routing.

2 · The split: one predicate, not two separate handler bodies

Lesson 47's Go code kept liveness and readiness apart by writing two separate functions. ASP.NET Core keeps them apart with tags on each registered check plus a Predicate on each mapped endpoint — the liveness endpoint's predicate simply says "run zero of the registered checks":

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddHealthChecks()
    .AddDbContextCheck<AppDbContext>("database", tags: new[] { "ready" });
    // AddDbContextCheck calls EF Core's CanConnectAsync underneath --
    // a connection attempt, not a test query, per the docs' own warning
    // against running a query that could add load to a struggling DB.

var app = builder.Build();

// Liveness: run none of the registered checks. If this handler can
// run at all, the process is alive -- same rule as Lesson 47's Go version.
app.MapHealthChecks("/healthz/live", new HealthCheckOptions {
    Predicate = _ => false
});

// Readiness: run only checks tagged "ready" -- here, just the DB check.
app.MapHealthChecks("/healthz/ready", new HealthCheckOptions {
    Predicate = check => check.Tags.Contains("ready")
});

app.Run();

The docs state the same rule Lesson 47 taught, almost word for word: "Use a liveness probe to describe the liveness of the process, no other checks are run... Use a readiness probe to indicate a 'not ready' state" while a dependency isn't available yet. Same two questions, same two consumers reacting differently — a liveness failure still means "kill and restart," a readiness failure still means "stop routing traffic, leave the process running."

The frontend equivalent you already own. This is the same shape as a feature flag gating one widget versus a kill switch gating the whole app shell. The liveness predicate (_ => false) is the kill switch — if it ever fails, nothing more granular is checked, the whole thing restarts. The readiness predicate, filtered to one tag, is the scoped flag — only the piece that actually depends on something external gets re-evaluated, and the rest of the app keeps running untouched.

3 · HealthStatus has a third value Go's two-handler version didn't need

Lesson 47's Go handlers only ever returned 200 or 503 — alive/not-alive, ready/not-ready, a boolean each way. ASP.NET Core's HealthCheckResult carries a three-way HealthStatus: Healthy, Degraded, or Unhealthy. Degraded has no Go-side equivalent in Lesson 47 at all — it's for "this dependency answered, but slowly, or in a reduced capacity," a state a plain boolean can't express. By default the aggregate endpoint still collapses this to a simple HTTP status for the load balancer (Healthy/Degraded both read as 200, only Unhealthy flips to 503) — the three-way detail is mainly for whoever reads the response body or a dashboard, not the routing decision itself.

Scope line

This lesson covers ASP.NET Core's health-check middleware — IHealthCheck, AddHealthChecks(), MapHealthChecks(), tag-based Predicate filtering for separate liveness/readiness endpoints, AddDbContextCheck<T>(), and the three-way HealthStatus enum — as the C# mirror of Lesson 47's Go liveness-vs-readiness split. It does not cover writing a fully custom IHealthCheck class from scratch beyond the one-method contract already shown, the built-in health-check UI/dashboard packages, or Kubernetes-specific probe configuration (out of scope per MISSION.md). It does not cover Go's select-statement arbitration rules — still deferred; see this round's NOTES.md entry for why.
