The job-status resource: how a client finds out a background job finished

Lesson 10 built the "enqueue now, process later" shape and stopped at the handler returning 202 Accepted. Lesson 63 named "a job finishing" as one of the motivating examples for real-time delivery, then moved on to the four push/poll techniques in general. Neither ever answered the specific question both left open: once a client gets back "accepted, not done yet," how does it actually find out the job is finished? Today closes that gap with one concrete, commonly-tested pattern.

1 · The gap between "accepted" and "done"

Lesson 10's handler wrote a job row and responded 202 Accepted immediately — a deliberate promise of "recorded, in progress," not "finished." That's the right call for the handler. But it leaves the client holding a response with no result and no way to check back. A frontend habit makes the missing piece easy to miss: a browser kicking off a slow operation often just shows a spinner tied to one in-flight fetch() call, because the browser's own APIs (image decode, a Web Worker) report completion back on the same call that started the work. An HTTP request that returns in milliseconds while the real work takes minutes has no such built-in channel — the connection that carried the 202 is already closed by the time the job finishes.

The fix isn't a new transport — it's treating the job itself as a normal, addressable resource, the same "nouns, not verbs" instinct Lesson 3's API contract material already taught for orders or users. If a job is a resource, a client can just ask for its current state with an ordinary GET, the same as it would ask for an order's current state.

2 · The pattern: 202, a Location header, and a resource to poll

Three pieces, each doing one job:

// createReport enqueues the job (Lesson 10's pattern) and, this time,
// tells the client exactly where to check on it.
func createReport(w http.ResponseWriter, r *http.Request) {
    jobID, err := enqueueJob(r.Context(), "generate_report", parseReportRequest(r))
    if err != nil {
        writeError(w, err)
        return
    }
    // the new piece: point the client at a resource representing THIS job
    w.Header().Set("Location", "/jobs/"+jobID)
    w.WriteHeader(http.StatusAccepted) // 202, same as Lesson 10
}

// getJobStatus is a plain, ordinary GET handler -- nothing special about
// it except that the resource it returns happens to change over time.
func getJobStatus(w http.ResponseWriter, r *http.Request) {
    job, ok := loadJob(r.Context(), jobIDFromPath(r))
    if !ok {
        http.NotFound(w, r)
        return
    }
    if job.Status == "running" {
        w.Header().Set("Retry-After", "2") // hint: check back in ~2s
    }
    writeJSON(w, http.StatusOK, job) // {status, result_url, error} -- see below
}

The Location header is the part Lesson 10 skipped: it turns "accepted, not done yet" into "accepted — and here is exactly where to look for the answer," instead of leaving the client to guess or hardcode a URL pattern. The client's job afterward is simple and boring: GET that URL, look at one field, and decide whether to ask again.

3 · Modeling status: a small, closed set of states, not a boolean

A tempting shortcut is a single done: bool column. It fails the first time the job can fail — a report generator that hits a bad row, an image resize that gets a corrupt file — because a bare boolean can't distinguish "still working" from "finished badly." The fix Lesson 60's CHECK-constraint material already previewed for a different column applies directly here: constrain the state to a known, closed set of values instead of a free-form string or a boolean pretending to be three states.

ALTER TABLE jobs
  ADD CONSTRAINT jobs_status_valid
  CHECK (status IN ('pending', 'running', 'succeeded', 'failed'));

succeeded and failed are terminal states: once a job reaches one, it will never move again, and the client polling it should stop. pending and running are not — the client keeps checking back. That single distinction is what lets a status resource answer the question a boolean can't: not just "is it done" but "did it work," with a place for the error itself to live when it didn't.

4 · Why polling this resource, specifically, beats the alternatives

Lesson 63 already covered four techniques for the server telling the client something changed. This is a deliberate, narrow case of the simplest one — plain polling — and it's usually the right one here, for a reason specific to jobs rather than a general endorsement of polling: most background jobs are checked by exactly one client, for a bounded, typically-short window, then never again. Holding a long-polling connection or an SSE stream open for one report generation that finishes in eight seconds spends a held connection and a blocked goroutine (Lesson 63's own cost column) on a problem plain, ordinary polling of a normal resource already solves with zero extra infrastructure. The Retry-After header in the handler above is the whole optimization worth adding: a hint for how long to wait before asking again, so the client isn't left guessing an interval, without needing a held connection at all. A dashboard watching many jobs at once, or a job that reliably takes minutes rather than seconds, is exactly the case where Lesson 63's SSE or WebSocket option earns its extra cost instead — the same "match the shape of the problem" rule Lesson 63 closed on, applied here to one specific shape.

Not a new mechanism — a resource wearing a clock. Nothing here is new machinery: Location is a header this course's 201 Created handlers already use for newly made resources (Lesson 3); a status field constrained to a known set is Lesson 60's CHECK constraint; polling is Lesson 63's simplest technique. The only genuinely new idea is treating "how is my job going" as an ordinary, addressable, gettable resource instead of inventing a special-purpose notification channel for it.

5 · What the client actually does with it

Response fieldClient action
status: "pending" / "running"wait roughly Retry-After seconds, GET the same URL again
status: "succeeded"stop polling; follow result_url to fetch the actual output
status: "failed"stop polling; show the error field, don't silently retry the GET forever

Two failure modes are worth naming because both are easy to ship by accident. A client that never stops polling a terminal state wastes requests forever on an answer that will never change again — a smaller-scale version of Lesson 57's stampede, self-inflicted by one careless client instead of many. A status resource that returns the full result inline once large (the whole generated report body, not just its status) turns a cheap, frequent poll into an expensive one — keep the status check and the result fetch as two different resources, exactly like the table above splits them into two different client actions.

Q: "Your API kicks off a report that takes two minutes to generate. How does the client know when it's ready?" A strong answer, out loud: "The create endpoint returns 202 Accepted with a Location header pointing at a job resource — something like /jobs/{id}. That resource is a plain GET, returning a status field constrained to a small set of values: pending, running, succeeded, failed — not a boolean, because I need to represent 'finished but failed' distinctly from 'still going.' The client polls that URL, using a Retry-After hint for the interval, and stops once it hits a terminal state — succeeded gives it a link to the actual result, failed gives it an error to show. I'd only reach for something like SSE instead if this were a long-lived dashboard watching many jobs continuously rather than one client checking once." The signal: naming the job as a resource with a small closed state set, not inventing a special notification mechanism for what a normal GET already handles.
