1 · The question Day 9 never asked

Day 9 proved a dbt snapshot correctly versions a row that changes — update commission_rate, rerun dbt snapshot, get a closed-out old row and a fresh current one. It never asked the other question a real restaurants table eventually faces: what happens when a row is deleted from raw.restaurants entirely — a restaurant that closed down, or got merged into another's listing?

Try reasoning through Day 9's own snapshot SQL with that case in mind: it's a plain select ... from {{ source('raw', 'restaurants') }}, comparing today's current rows against what it already recorded. If a row simply isn't there anymore, there is nothing left to compare — dbt's default behavior is to do precisely nothing about it. The restaurant's last-known version stays in restaurants_snapshot with dbt_valid_to still null, meaning "still current," forever. fct_orders_with_commission's point-in-time join from Day 9 would keep treating a deleted restaurant as perfectly valid, with no error, no warning, and no row anywhere telling you it's gone.

2 · Naming it: a hard delete is a different event than an update

A hard delete is a fundamentally different event from the updated_at-driven change Day 9's timestamp strategy watches for: an update still has a row to compare against; a hard delete leaves nothing at all. dbt's Snapshots docs (the same primary source Day 9 cited, revisited today) name the fix as the hard_deletes config, with three settings:

SettingWhat happens to a deleted source row
ignore (dbt's default)nothing — the last-known version stays "current" forever, Day 9's actual gap
invalidatethe snapshot closes out that row's dbt_valid_to the next time it runs, the same way an update closes out an old version
new_recordcloses it out and inserts one further marker row recording the deletion itself, so a later restore is distinguishable from the restaurant never having been deleted at all

This replaces an older boolean, invalidate_hard_deletes: true, still readable in older tutorials and pre-1.9 projects; this course pins dbt-core 1.12.4 per MISSION.md, so today uses the current hard_deletes key, which the docs say directly replaces it. invalidate is today's choice — it fixes exactly Day 9's gap with a one-line config change and no new column to learn; new_record is named here as the richer alternative and left as the "go further" option at the end, not built today, since it adds a second marker-row concept Day 9's existing join was never written to expect.

3 · Build: add hard_deletes: 'invalidate'

One line into the same config() block Day 9 wrote:

-- snapshots/restaurants_snapshot.sql
{% snapshot restaurants_snapshot %}

{{
    config(
        target_schema='dbt_dev_snapshots',
        unique_key='restaurant_id',
        strategy='timestamp',
        updated_at='updated_at',
        hard_deletes='invalidate',
    )
}}

select
    restaurant_id,
    name,
    cuisine,
    city,
    commission_rate,
    updated_at
from {{ source('raw', 'restaurants') }}

{% endsnapshot %}

Nothing else about the snapshot changes — the select is identical to Day 9's. The only new behavior is what happens on the next dbt snapshot run after a row vanishes from the source, which is the part worth actually watching happen rather than taking on faith.

4 · Verify: delete a restaurant, rerun, watch it get invalidated

Pick a restaurant with no orders against it yet, so deleting it doesn't also violate Day 3's relationships test on fct_orders — restaurant 40, say, if your seed data leaves it unused. Confirm first, then delete it directly, the same kind of one-time hand-edit Day 9 used to simulate a rate change:

docker compose exec -T postgres psql -U fdp -d fdp -c \
  "SELECT count(*) FROM raw.orders WHERE restaurant_id = 40;"
docker compose exec -T postgres psql -U fdp -d fdp -c \
  "DELETE FROM raw.restaurants WHERE restaurant_id = 40;"

Expected on the first query — 0, confirming it's safe to delete without tripping an unrelated test. Now rerun the snapshot:

uv run --project ../dbt_env dbt snapshot
1 of 1 OK snapshot dbt_dev_snapshots.restaurants_snapshot ...... [INSERT 0 0 in 0.05s]

Done. PASS=1 WARN=0 ERROR=0 SKIP=0 TOTAL=1

The log line looks almost identical to any ordinary run — the real proof is in the row itself, not the console output:

docker compose exec -T postgres psql -U fdp -d fdp -c \
  "SELECT restaurant_id, commission_rate, dbt_valid_from, dbt_valid_to
   FROM dbt_dev_snapshots.restaurants_snapshot
   WHERE restaurant_id = 40 ORDER BY dbt_valid_from;"
 restaurant_id | commission_rate |       dbt_valid_from       |        dbt_valid_to
---------------+------------------+-----------------------------+-----------------------------
            40 |             0.18 | 2026-09-15 09:03:11.20+00   | 2026-10-28 06:00:04.88+00
(1 row)

dbt_valid_to is no longer null — it now carries the timestamp of the snapshot run that noticed restaurant 40 was gone, the same closing-out mechanism Day 9's rate-change update triggered, now triggered by an absence instead of a changed value. Before today's config change, this exact DELETE would have left dbt_valid_to at null forever, and Day 9's own point-in-time join (... or dbt_valid_to is null) would have kept matching restaurant 40 to any order placed after the deletion — there are none here, but at 100 restaurants and real attrition, that's a silent wrong answer waiting to happen, not a hypothetical one.

Where fct_orders_with_commission was already exposed: nothing in that model's own SQL needs to change today — it joins on dbt_valid_from/dbt_valid_to exactly as Day 9 wrote it, and a closed-out row for restaurant 40 simply stops matching any order placed after 2026-10-28 06:00:04.88+00, which is the entire point. The bug hard_deletes: 'invalidate' fixes was never in the join — it was in the snapshot never closing the row out in the first place.

Rerun dbt build once more to confirm nothing else broke, then commit the one-line change to snapshots/restaurants_snapshot.sql.

Q: "Your SCD Type 2 snapshot handles updates correctly. Does it handle a row being deleted from the source?" A strong answer, out loud: "Not by default — dbt's snapshot strategy only compares rows that still exist in the source against what it already recorded, so a row that's been hard-deleted has nothing to compare against, and dbt's default behavior is to leave its last known version marked as still current, with a null dbt_valid_to, forever. I caught this as a real gap in my own restaurants snapshot: I was versioning commission_rate changes correctly, but a restaurant that got deleted from the source would still look valid today in every downstream join. The fix is a config, hard_deletes, with three settings — ignore, the default; invalidate, which closes out the row's dbt_valid_to the next time the snapshot runs, same mechanism as an update; and new_record, which does that plus inserts an explicit marker row, so a later restore is distinguishable from it never having been deleted. I used invalidate, since it closes the actual gap with no new column for downstream joins to learn, and it's a one-line change to an existing config block, not a new mechanism." The signal: knowing a hard delete and an update are different events a snapshot has to be told to handle differently, not assuming "SCD Type 2" by itself covers both for free.

5 · When new_record would be worth the extra concept

invalidate closes Day 9's actual gap and stops here deliberately — it's the smallest change that makes "what was true in the past" queries correct again. new_record buys one more thing invalidate can't: a query that asks "was restaurant 40 ever deleted, and when" without having to infer it from a suspiciously-closed dbt_valid_to next to no newer row. That distinction matters once something downstream specifically needs to tell "deleted" apart from "superseded by a newer version" — a compliance report counting churned restaurants, say. This project's own fct_orders_with_commission never asks that question, so invalidate is the right-sized fix today, the same "generic enough, but does anything here actually need it" filter Day 42 applied to custom tests.
