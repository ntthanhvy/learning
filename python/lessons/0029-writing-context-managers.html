Writing your own context manager

Day 6 named the protocol behind with — __enter__ and __exit__ — then stopped short on purpose: "You won't write __enter__/__exit__ yourself yet — that's a later lesson." This is that lesson. By the end you can write a class that works after with, and the much shorter generator-based shortcut for the common case.

Bridge from SQL: a transaction block — BEGIN, your statements, then COMMIT on success or ROLLBACK on failure, guaranteed one or the other — is the same shape as today's lesson: fixed setup, fixed cleanup, cleanup runs no matter how the middle part ends. Today builds that guarantee as a reusable Python object instead of relying on the database driver to give it to you.

1 · Recap: what with actually calls

Day 6 section 4 showed the desugaring of with without asking you to write either half:

with resource() as r:
    ...
# is roughly:
r = resource().__enter__()
try:
    ...
finally:
    resource().__exit__(exc_type, exc_value, traceback)

Any object with both methods works after with — nothing about with is special-cased to files. __enter__(self) runs first and its return value is what as name binds; __exit__(self, exc_type, exc_value, traceback) runs last, unconditionally, and receives details about an in-flight exception if the block raised one (all three arguments are None if it didn't).

2 · Writing the class form

A minimal timer that logs how long its block took, whether or not the block raised, built from nothing more than a class with two methods:

import time

class Timer:
    def __enter__(self):
        self.start = time.perf_counter()
        return self                      # binds to `as t` — often self, not required to be

    def __exit__(self, exc_type, exc_value, tb):
        self.elapsed = time.perf_counter() - self.start
        print(f"took {self.elapsed:.3f}s")
        return False                       # False = don't swallow an exception; re-raise it

with Timer() as t:
    do_work()
# "took 0.002s" prints even if do_work() raised — __exit__ still ran

__exit__'s return value matters and is easy to miss: if it returns a truthy value, Python treats the exception as suppressed — the with block's surrounding code continues as if nothing raised. Returning False (or nothing at all, since a bare return or falling off the end both give None) lets the exception propagate normally, which is what you want almost always. A context manager that silently eats every exception it sees is a bug, not a feature — this is the single most important rule in this lesson.

3 · The generator shortcut: @contextmanager

Writing a full class for a simple setup/teardown pair is more ceremony than the job needs. The standard library's contextlib.contextmanager decorator turns a yield-based generator function — the exact mechanism Day 5 already taught — into a context manager, with everything before yield as setup and everything after as teardown:

from contextlib import contextmanager
import time

@contextmanager
def timer():
    start = time.perf_counter()
    try:
        yield start                          # whatever is yielded is what `as` binds
    finally:
        print(f"took {time.perf_counter() - start:.3f}s")

with timer() as start_time:
    do_work()
# the finally block runs on the way out, exception or not — same guarantee, far less code

The mapping onto the class form from section 2: code before yield is __enter__, the yielded value is what __enter__ would have returned, and code after yield — inside a finally, exactly like a pytest fixture's teardown (Day 11) — is __exit__. If the with block raises, the exception surfaces at the yield line itself inside the generator, which is precisely why the finally here is not optional: without it, an exception in the block would skip the cleanup code entirely, the identical leak Day 6 opened with.

4 · A real example: a database-style transaction

The transaction shape named in this lesson's opening bridge, written as one reusable @contextmanager function:

from contextlib import contextmanager

@contextmanager
def transaction(log):
    log.append("BEGIN")
    try:
        yield
        log.append("COMMIT")                # only reached if the block didn't raise
    except Exception:
        log.append("ROLLBACK")
        raise                             # re-raise — the caller still needs to know it failed

log = []
with transaction(log):
    log.append("INSERT")
# log == ["BEGIN", "INSERT", "COMMIT"]

The line right after yield only runs if the with block completed without raising — an exception jumps straight from the failing statement inside the block to the except clause wrapped around yield, skipping the commit line entirely. This is Day 8's try/except/raise material applied inside a generator instead of a plain function, catching narrowly and re-raising rather than swallowing, exactly the habit Day 8 emphasized most.

Q: "How would you write a context manager in Python?" A strong answer, out loud: "Two ways. A class with __enter__ and __exit__ — __enter__ does setup and returns whatever as name should bind to, __exit__ does teardown and gets the exception info if the block raised. Or, for the common case, contextlib.contextmanager on a generator function — code before yield is setup, code after yield inside a finally is teardown. The detail people miss: __exit__ returning a truthy value swallows the exception instead of letting it propagate, so unless you deliberately want to suppress something, always return False or nothing." The signal: naming both forms, and knowing the swallow-exception gotcha — the exact thing section 2 flagged as the most missable line in this whole lesson.

Where pandas goes from here: pd.option_context(...) is itself a context manager — used with with to temporarily change a display option and restore it automatically afterward. Not demonstrated here; that's data/'s job, and this is the only sentence in this lesson that names it.
