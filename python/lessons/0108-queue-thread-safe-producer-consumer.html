queue: handing work between threads safely

Day 73 built several ThreadPoolExecutor calls that each ran independently, with no shared state to corrupt. Real threaded programs are rarely that tidy: one thread often needs to hand items to another — a producer finding work, a consumer doing it. Day 73 named the danger of that directly: a race condition on a plain list shared between threads. queue.Queue is the standard-library answer: a FIFO built with every lock already handled internally, safe to hand items through between threads with no manual threading.Lock required.

1 · Queue: a FIFO that locks itself

queue.Queue() creates a thread-safe queue: .put(item) adds to one end, .get() removes and returns from the other, first in, first out — same ordering idea as Day 53's deque, but with locking built in rather than left to the caller:

import queue
import threading

q = queue.Queue()

def producer():
    for n in range(3):
        q.put(f"item-{n}")   # safe to call from any thread, no lock written by hand

def consumer(results):
    for _ in range(3):
        results.append(q.get())      # blocks here if the queue is currently empty

results = []
t1 = threading.Thread(target=producer)
t2 = threading.Thread(target=consumer, args=(results,))
t1.start(); t2.start()
t1.join(); t2.join()
print(results)   # ['item-0', 'item-1', 'item-2'] -- confirmed live, same order they were put in

Both threads touch q with no threading.Lock anywhere in this code — Queue's own methods already do that internally. .get() on an empty queue blocks by default, waiting until something arrives, rather than raising immediately; .put() blocks the same way if the queue has a maxsize and is currently full.

Bridge from Day 73: ThreadPoolExecutor is for "run this same function many times concurrently, collect the results" — no coordination between calls needed. queue.Queue is for "thread A keeps finding work, thread B keeps doing it" — an ongoing hand-off, not a one-shot batch. Different shape of problem, same underlying threading module Day 73 named but didn't build on.

2 · Non-blocking access, and maxsize

Sometimes blocking is wrong — a thread that needs to check "is there anything ready right now?" and move on if not. .get_nowait() and .put_nowait() never wait: they raise immediately instead:

import queue

q = queue.Queue(maxsize=2)   # bounded -- holds at most 2 items at once
q.put("a")
q.put("b")

try:
    q.put_nowait("c")         # queue is full -- confirmed live, raises immediately
except queue.Full:
    print("full, skipping")   # confirmed live: this line runs

q.get(); q.get()
try:
    q.get_nowait()              # queue is now empty -- confirmed live, raises immediately
except queue.Empty:
    print("empty, nothing to do")   # confirmed live: this line runs

maxsize=0 (the default) means unbounded — .put() never blocks on space. A positive maxsize caps how many items can sit in the queue at once, which is often the point: it stops a fast producer from piling up unlimited unprocessed work in memory while a slower consumer falls behind. queue.Empty and queue.Full are the two exceptions the _nowait() pair raises — regular .get()/.put() accept a timeout= seconds argument as the middle ground, raising the same exceptions only once that timeout elapses rather than waiting forever.

3 · Knowing when the work is actually done: task_done() and join()

.get() returning an item doesn't mean the work on it is finished — only that a consumer picked it up. queue.Queue tracks that distinction separately with a counter: every .get() increments an internal count of unfinished items, and .task_done() decrements it once a consumer is actually done processing that item. .join() blocks until the count reaches zero — the standard way for a producer thread to know every item it put in has been fully handled, not merely removed from the queue:

import queue
import threading

q = queue.Queue()
processed = []

def worker():
    while True:
        item = q.get()
        processed.append(item * 2)
        q.task_done()      # must be called, or join() below waits forever

threading.Thread(target=worker, daemon=True).start()
for n in [1, 2, 3]:
    q.put(n)

q.join()   # blocks until all 3 items have had task_done() called -- confirmed live
print(sorted(processed))   # [2, 4, 6] -- confirmed live, all three finished before join() returned

Skipping .task_done() is the one trap here: the unfinished-item count never reaches zero, and .join() blocks forever with no error raised to explain why — confirmed live, removing the q.task_done() line above reproduces exactly that hang.

Two close relatives, named not demonstrated: queue.LifoQueue is the same interface but last-in-first-out (a stack, not a line); queue.PriorityQueue keeps items ordered so the lowest-valued entry (by Day 4's sorted()-style comparison, typically a (priority, item) tuple) comes out of .get() first, rather than whichever arrived earliest — the same ordering idea as Day 51's heapq, wrapped in the same thread-safe interface as today's plain Queue.
Where pandas/NumPy go from here: neither has anything resembling this — moving work safely between threads is a concurrency concern, orthogonal to a DataFrame or array's job. Not covered further here, per MISSION.md.
