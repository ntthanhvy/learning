Request validation: writing the shape down instead of checking it by hand

Lesson 17 drew a line between SQL injection defense and input validation and left validation as one sentence: "is this string actually an email, is this page size a positive integer under some cap." That sentence has been true in every handler since without ever getting its own lesson. This one stays on that side of the line — no SQL, no injection — and asks the question Lesson 17 didn't: where does that checking code live, and what happens once a handler has more than three fields to check.

1 · The habit that doesn't scale

The natural first move is checking fields by hand, inline, at the top of the handler:

func createOrder(w http.ResponseWriter, r *http.Request) {
    var in CreateOrderInput
    json.NewDecoder(r.Body).Decode(&in)

    if in.Quantity <= 0 {
        http.Error(w, "quantity must be positive", 400)
        return
    }
    if in.Quantity > 1000 {
        http.Error(w, "quantity too large", 400)
        return
    }
    if in.Email == "" || !strings.Contains(in.Email, "@") {
        http.Error(w, "invalid email", 400)
        return
    }
    // ...and so on, one if-block per field
}

This works for three fields. It stops working long before twenty: every field needs its own if, every if needs its own error-contract-shaped response (Lesson 3's {"error":{"code","message"}}), the checks drift out of sync with whatever the frontend's form actually sends, and — the part that bites hardest — every other handler in the codebase that also accepts a quantity or an email re-derives the same rule slightly differently, because nothing forces two handlers to agree on what "a valid email" means.

2 · Declaring the shape instead of checking it

The alternative is writing the rules down once, as data, instead of as scattered if statements — a JSON Schema document:

{
  "type": "object",
  "required": ["productId", "quantity", "email"],
  "properties": {
    "productId": { "type": "string", "format": "uuid" },
    "quantity":  { "type": "integer", "minimum": 1, "maximum": 1000 },
    "email":     { "type": "string", "format": "email" }
  },
  "additionalProperties": false
}

Nothing here is executable code — it's a description of a valid CreateOrderInput, handed to a general-purpose validator library that walks the value against the rules and reports every violation at once. The handler's job shrinks to one call — validate, then branch on whether it passed — instead of a wall of hand-written conditionals. additionalProperties: false is doing real work too: without it, a client could attach an unexpected field and the schema would silently allow it through, which is exactly the gap the callout below comes back to.

This is the same instinct as a Postgres CHECK constraint from Lesson 60 — "declare the rule where the data lives, once, instead of trusting every caller to enforce it correctly" — just one layer earlier, at the API boundary instead of the table. A schema doesn't replace the CHECK constraint; it catches the same class of mistake sooner, before a bad request even reaches a query, and it can express things a column constraint can't (required-together fields, string formats, nested object shapes).

3 · Syntactic validation vs. semantic validation

A schema validator only answers one kind of question, and it's worth being precise about which one. syntactic validation is "is this shaped like an email" — a schema handles that completely. semantic validation is "does this product id actually exist, does this user own this order, is there enough stock for this quantity" — a schema cannot answer any of that; it has no access to the database. A syntactically perfect request (a well-formed UUID, a quantity of 5, a valid email) can still be semantically wrong (that UUID belongs to no product, that quantity exceeds stock). The schema is a fast, cheap first gate that rejects garbage before it costs a query — it is never the last check.

4 · Allowlist over denylist, the same rule Lesson 17 already gave

A schema's "type": "string", "format": "email" is an allowlist by construction: it names what's acceptable and rejects everything else, including shapes nobody thought to block explicitly. That's the identical rule Lesson 17 gave for SQL injection defense — "define exactly what's acceptable... rather than a blocklist that tries to guess every bad value in advance" — applied one level up, to the whole request body instead of one field's characters. A schema with additionalProperties: false is what makes that allowlist total: any field the schema didn't name is rejected, not silently passed through.

Why that field matters more than it looks: a request-shape allowlist is also the first line of defense against overexposure — a client attaching fields the handler never meant to accept, like a role or isAdmin field slipped into a signup payload. Rejecting unknown fields at the schema is the same defense named more narrowly by mass-assignment protection, just applied earlier, before the value ever reaches a struct.

5 · Where this sits in a request's lifecycle

Putting the last few lessons' layers in request order for one handler:

request arrives
  → is the body valid JSON at all?           (parse)
  → does it match the schema?                (syntactic validation -- this lesson)
  → am I logged in? am I allowed to do this? (authn/authz -- Lessons 4, 12)
  → does the referenced data exist/agree?    (semantic validation -- handler + DB)
  → query, using $1 placeholders always      (Lesson 17 -- never string-built SQL)

Schema validation runs early and cheap on purpose — rejecting a malformed body before touching auth or the database means a flood of garbage requests never reaches the expensive layers. A 400 for a bad shape should never cost a connection-pool checkout.

Q: "Why put request validation in a schema instead of writing the checks in the handler?" A strong answer, out loud: "Hand-written per-field checks don't scale past a handful of fields, and worse, they drift — two handlers that both accept an email end up validating it slightly differently because nothing forces them to agree. A schema declares the shape once as data, gets enforced by one shared validator, and can express `additionalProperties: false` so unexpected fields are rejected by default instead of silently passed through, which is also a mass-assignment defense. What a schema can't do is anything that needs the database — whether a referenced id actually exists, whether there's enough stock — that's semantic validation, and it still has to happen in handler logic after the schema passes. The schema is the fast, cheap first gate; it's never the whole check." The signal: naming the syntactic/semantic split explicitly, and knowing a schema is a first gate, not a replacement for handler-level checks against real data.
