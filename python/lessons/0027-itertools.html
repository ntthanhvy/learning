itertools: chaining, grouping & combining without hand-rolled loops

Day 26 closed the FastAPI + pydantic capstone, and both of PLAN.md's Phase 2 spines (2a and 2b) are now fully covered. Rather than guess at an unnamed Phase 3 direction, today fills a real, still-open gap named twice already: RESOURCES.md lists itertools alongside collections as one of "the two stdlib modules that replace most hand-written data-munging loops," and Day 5's own closing line pointed here next — but no lesson ever actually taught it. collections (defaultdict, Counter) got its lesson on Day 3; today itertools gets its turn.

Bridge from SQL: itertools.chain is UNION ALL for Python iterables — stack several sources into one stream without copying them into a new table first. itertools.groupby is a poor man's GROUP BY that only works correctly on already-sorted input, unlike SQL's own GROUP BY, which sorts (or hashes) for you invisibly.

1 · The module: importable functions that return iterators

Day 5 taught what an iterable and a generator are, and how to write one by hand with yield. itertools is a standard-library module of ready-made generator functions for the handful of iterable-combining jobs that come up constantly — so instead of writing a new while loop with its own yield every time, one call does the job, lazily, exactly like a hand-written generator would:

from itertools import chain, groupby, islice

nums = [1, 2, 3]
letters = ["a", "b"]
for item in chain(nums, letters):
    print(item)          # 1 2 3 a b — nums then letters, no new list built

Every function in this module returns something you loop over once — nothing is a list, and nothing is computed until something actually pulls a value from it. That's Day 5's lazy evaluation again, applied to combining iterables instead of transforming a single one.

2 · chain: several iterables, one pass, in order

itertools.chain(*iterables) stitches any number of iterables end to end into one stream, without concatenating them into a new list first:

jan_sales = ["Hanoi,120", "HCMC,80"]
feb_sales = ["Hanoi,45", "Danang,200"]

for line in chain(jan_sales, feb_sales):
    print(line)          # all four lines, jan_sales first, no jan_sales + feb_sales copy made

jan_sales + feb_sales would work too here — but that builds a brand-new list holding every element twice over (once in each source, once in the copy). chain never builds that copy; it just visits one source's iterator, then the next's, entirely lazily. The gap widens with Day 6's file objects: chain(open("jan.csv"), open("feb.csv")) streams two files as if they were one, at constant memory, exactly like Day 5's single-generator pipelines already did for one file.

3 · groupby: consecutive runs of a shared key — sorted input required

Day 3's defaultdict(list) groups rows by key regardless of input order, because it scans the whole dict for each key on every lookup, wherever that key last appeared. itertools.groupby(iterable, key=...) is different and narrower: it only groups consecutive items sharing a key, which makes it useless on unsorted data — but very cheap on data that's already sorted (e.g. rows read in order from a database ORDER BY):

rows = [
    {"city": "Hanoi", "amount": 120},
    {"city": "Hanoi", "amount": 45},
    {"city": "HCMC", "amount": 80},
]
for city, group in groupby(rows, key=lambda r: r["city"]):
    print(city, [r["amount"] for r in group])
    # Hanoi [120, 45]
    # HCMC [80]

Two gotchas that trip up first use, both confirmed by running the exact code above: first, key= here is Day 4's own key= argument — a function called once per item to compute the value grouped by, same idea as sorted(key=...), just feeding groupby instead. Second — and this is the one that actually bites — swap the row order so a second "Hanoi" row comes after an "HCMC" row, and groupby silently produces two separate "Hanoi" groups instead of one, because it only merges runs that are already next to each other. groupby never sorts for you; call sorted(rows, key=lambda r: r["city"]) first if the input isn't already grouped, or reach back for Day 3's defaultdict instead, which has no such requirement.

4 · islice and product: slicing an iterator, and every combination

Day 2's slicing (seq[2:5]) only works on a real sequence — a list, not a generator, since slicing needs to jump straight to an index and a generator has no indexes, only a "give me the next one" protocol. itertools.islice(iterable, stop) (or (start, stop, step)) is the generator-safe equivalent — it still only pulls as many items as needed, never materializing the rest:

def counter():
    n = 0
    while True:
        yield n
        n += 1

first_five = list(islice(counter(), 5))   # [0, 1, 2, 3, 4] — counter() never actually ends

counter() is Day 5's kind of generator: infinite, and never finishes on its own. Slicing it with [:5] isn't legal — there's no way to index a generator — but islice(counter(), 5) pulls exactly five values and stops, exactly the SQL LIMIT 5 idea applied to a Python iterator instead of a result set.

itertools.product(*iterables) is the other direction — every combination of one item from each iterable, the same shape as a SQL CROSS JOIN:

from itertools import product
sizes = ["S", "M", "L"]
colors = ["red", "blue"]
list(product(sizes, colors))
# [('S','red'), ('S','blue'), ('M','red'), ('M','blue'), ('L','red'), ('L','blue')]

Same result as a nested for size in sizes: for color in colors: ... loop building tuples — product just names that exact pattern so it doesn't need reinventing at two levels of nesting, or three, or four.

Where pandas goes from here: a pandas pipeline reaches for pd.concat() where this lesson uses chain, and df.groupby() where this lesson uses itertools.groupby — but pandas's version sorts/hashes for you and works on unsorted input, unlike the stdlib version taught here. Not demonstrated here; that's data/'s job, and this is the only sentence in this lesson that names it.
