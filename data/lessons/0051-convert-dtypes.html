convert_dtypes(): the best-guess dtype pass

Lesson 50's own closing teaser named this as the strongest remaining candidate from the Lesson-47-flagged batch: still genuinely uncovered, and unlike .xs()/droplevel() (both MultiIndex-specific, better taught together later), convert_dtypes() applies to any DataFrame. It's the one-call answer to a question every earlier lesson has handled column-by-column: "what's the best dtype for each of these columns, given what's actually in them?"

Recap, in one line

Lessons 3/25/47 taught fixing dtypes one column at a time — pd.to_numeric(), pd.to_datetime(), astype(), each aimed at a single named column. convert_dtypes() runs that same instinct across the whole table in one call, inferring the best-fitting dtype per column from what's actually stored in it.

1 · One call, every column upgraded at once

The real orders_raw.csv fixture, already cleaned through Lessons 6-50's standard path (to_numeric + to_datetime + dropna):

clean.dtypes
-- order_id               int64
-- customer                 str
-- amount               float64
-- order_date    datetime64[us]
-- dtype: object

One call upgrades every column to pandas' own nullable dtypes, each one inferred from the values actually sitting in that column:

clean.convert_dtypes().dtypes
-- order_id               Int64
-- customer              string
-- amount               Float64
-- order_date    datetime64[us]
-- dtype: object

int64 becomes capitalized Int64, float64 becomes Float64, and the text customer column becomes pandas' own dedicated string dtype — the same nullable-numeric family Lesson 47's glossary entry already named (Int64/Float64 reserve a real <NA> marker for missing values, where plain astype(int) has no bit pattern for "missing" and raises IntCastingNaNError on any NaN instead). order_date stays a datetime — nothing to upgrade there, convert_dtypes() only touches columns where a better-fitting dtype actually exists.

2 · The gotcha: it upgrades to the best type it can see — not the type you meant

The trap: convert_dtypes() only ever looks at the values that are actually there. Run it on raw — the uncoerced fixture, before pd.to_numeric() has touched amount, still carrying the stray "unknown" from row 3 that has blocked numeric auto-detection since Lesson 2:

raw["amount"].tolist()
-- ['120.0', '35.5', 'unknown', '99.9', '180.0', '42.0']
raw["amount"].convert_dtypes().dtype
-- string

Not Float64 — string. Every value in that column really is text as far as pandas' own dtype system can tell ("unknown" is a perfectly valid string, so the whole column qualifies as string-typed, nothing to reject). The column now LOOKS converted — it went from generic str/object to pandas' dedicated string dtype, a real change — but the numbers inside it are still stored as text, not floats, and arithmetic on it still fails exactly as before. This is the same "no crash, quietly wrong" family already flagged for describe() (Lesson 49), corr() (Lesson 50), reindex() (Lesson 47), and str.extract() (Lesson 42): convert_dtypes() never asks whether a column's CONTENT is what you intended, only whether its current values fit a better-typed container than the one they're already in. The fix is unchanged from Lesson 2 — pd.to_numeric(raw["amount"], errors="coerce") first, to actually coerce "unknown" into a real missing value, THEN convert_dtypes() to upgrade the result to Float64.

3 · A second surprise: float64 can become Int64, not just Float64

A column doesn't need any missing values to get upgraded — and it doesn't always land on the dtype you'd expect from its current one:

whole = pd.Series([1.0, 2.0, 3.0])
whole.convert_dtypes().dtype
-- Int64

mixed = pd.Series([1.5, 2.0, 3.0])
mixed.convert_dtypes().dtype
-- Float64

whole is stored as float64, but every value happens to be a whole number — so convert_dtypes() looks past the CONTAINER's current dtype and asks what the VALUES actually need, landing on Int64 instead of the expected Float64. mixed has one genuinely fractional value (1.5), so it stays Float64. Worth checking a column's new dtype explicitly rather than assuming "was float64, so becomes Float64" — a downstream .astype("float64") or a merge key comparison written against the old assumption can behave differently once the dtype has quietly shifted to an integer type.

4 · The SQL bridge

SQL columns don't have this problem in the first place — a table's column types are declared at CREATE TABLE time and every insert is checked against them; there's no equivalent moment where SQL "looks at what's already in a column and picks a better type for it," because a column can never silently hold the wrong type to begin with. convert_dtypes() exists because pandas' load path is the opposite: read_csv() guesses per-column types from raw text with no schema to enforce them, so a whole table can end up under-typed (numbers stored as generic strings, missing values blocking a clean integer dtype) with no error at load time. The nearest SQL analogue isn't a single statement — it's closer to running ALTER TABLE ... ALTER COLUMN ... TYPE ... once per column after eyeballing what's actually in each one, except convert_dtypes() proposes the target type for you instead of requiring it named up front, and it never touches the underlying values, only the container.

Q: "You just ran convert_dtypes() on a loaded DataFrame. Does that mean the data is now clean?" A strong answer, out loud: "No — convert_dtypes() only upgrades a column to the best-fitting dtype given the values that are ALREADY there; it never validates or fixes the values themselves. If a numeric column got loaded as text because of one bad row — a stray 'unknown' blocking auto-detection, for example — convert_dtypes() will happily promote that column to pandas' own string dtype instead of a numeric one, since every value genuinely is valid text. It looks converted, but it's still not usable for arithmetic. I'd run convert_dtypes() as a final polish AFTER the real cleaning step — to_numeric()/to_datetime() with errors='coerce' to fix the actual values — not as a substitute for it, the same order Lesson 2's cleaning path already established." The signal: naming that it upgrades containers, not values, and placing it after coercion in the pipeline rather than instead of it.
