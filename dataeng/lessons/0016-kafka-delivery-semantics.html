1 · Three names for the same underlying question

Day 6 already answered the question that matters most for this pipeline: "if a message gets processed twice, does the warehouse end up wrong?" Today names the full spectrum that question lives on, because "exactly-once" gets thrown around in interviews as if it's one simple guarantee, and treating it that way is the single most common wrong answer.

GuaranteeWhat can go wrongWhere it shows up here
at-most-oncemessage silently lostDay 6's rejected ordering: commit offset, then write
at-least-oncemessage processed more than onceDay 6's actual consumer: write, then commit offset
exactly-onceneither, but only for the hop Kafka actually controlstoday's producer→broker hop; not automatically the broker→Postgres hop

Day 6 picked at-least-once plus an idempotent write on purpose, and that choice doesn't change today. What changes is the producer side: Day 5's scripts/produce_order_events.py has been running this whole course with Kafka's default producer behavior, which has its own, narrower at-most/at-least-once question — one level upstream of anything Day 6 touched.

2 · The gap Day 5's producer always had

A plain Kafka producer sends a message and waits for the broker to acknowledge it. If that acknowledgment is lost — a network blip, a broker momentarily unavailable — the producer's client library doesn't know whether the broker actually got the message before the connection dropped. Its only safe option is to retry. But retrying blindly re-introduces exactly the problem Day 6 solved on the consumer side, one hop earlier: if the first send actually succeeded and only the *acknowledgment* was lost, the retry writes a second copy of the same message to the same partition. Nothing before today's config change stopped that.

This is the same shape of problem as backend/'s idempotency-key work — a client can't always tell whether its own request landed, so it retries, and the server needs a way to recognize "this is that same request again" — applied to a producer talking to a broker instead of an HTTP client talking to an API. The mechanism differs; the reason it's needed doesn't.

3 · The idempotent producer: dedup you don't have to build yourself

Kafka's idempotent producer is a broker-side answer, not an application-side one: turn it on, and the broker itself refuses to write a duplicate. It works by giving each producer session a hidden producer ID (PID) and having the producer tag every message with a per-partition sequence number. If a retried send arrives with a sequence number the broker has already seen from that PID on that partition, the broker recognizes it as a retry of something already written and doesn't write it again — no event_id, no ON CONFLICT, no application code at all. One config key turns it on:

# scripts/produce_order_events.py -- one new config key on the Producer()
producer = Producer(
    {
        "bootstrap.servers": BOOTSTRAP,
        "enable.idempotence": True,
        "acks": "all",
        "max.in.flight.requests.per.connection": 5,
        "retries": 5,
    }
)

The three lines under enable.idempotence are what confluent-kafka sets for you automatically the moment idempotence is on — acks: "all" (every in-sync replica must confirm the write, not just the leader), a capped in-flight-requests count, and retries enabled at all. They're written out explicitly here so the trade is visible rather than hidden inside a boolean: idempotence isn't free, it requires the stronger acknowledgment settings to have anything to deduplicate against.

Note what key the broker dedups on: it is not event_id. The (PID, sequence number) pair is assigned per producer session and is invisible to your application code entirely. It has nothing to do with the event_id UUID Day 5's make_event() generates or the event_id primary key Day 6's consumer relies on — those two dedup mechanisms operate at completely different layers (producer→broker vs. Kafka→Postgres) and neither makes the other unnecessary.

That warning line is not an error to fix — it's the producer retrying its own PID handshake against a broker that briefly wasn't ready, exactly the kind of transient failure idempotence is built to make harmless. 6 · What today's fix does not cover

This is the part worth being precise about out loud, because "we use Kafka's exactly-once" is the kind of overclaim that falls apart under one follow-up question. Today's enable.idempotence guarantees exactly-once for exactly one hop: producer session to broker partition. It says nothing about:

HopWhat actually guarantees correctness there
Producer → broker (today)the idempotent producer: broker-side PID + sequence-number dedup
Broker → consumer → Postgres (Day 6)at-least-once delivery plus the consumer's own ON CONFLICT (event_id) DO NOTHING — a completely different mechanism, built by this course's own code, not by Kafka
The producer's own source of truth upstream (out of scope here)whatever generates order_events in the first place — if that system double-submits an order, idempotence at any Kafka hop cannot detect it, because both submissions look like two genuinely different, valid messages

Kafka does have a stronger, transactional exactly-once mode (transactional.id, used by Kafka Streams and consume-transform-produce pipelines) that extends this guarantee across a read-process-write cycle entirely inside Kafka. It's vocabulary for this course, not a build step: this pipeline's sink is Postgres, an external system Kafka's transactions don't reach, which is exactly why Day 6 needed its own idempotent write in the first place and why that design doesn't change today. The honest one-sentence answer to "do you have exactly-once end to end?" here is: exactly-once producer-to-broker, at-least-once broker-to-warehouse made safe by an idempotent write — and that combination is what real pipelines actually run, not a single end-to-end "exactly-once" switch.

Q: "Someone on your team says 'we use Kafka's exactly-once guarantee end to end.' What's your response?" A strong answer, out loud: "I'd ask which hop they mean, because exactly-once isn't one setting that covers a whole pipeline. My producer sets enable.idempotence, so the broker deduplicates retried sends using a hidden producer ID and per-partition sequence number — that's a real exactly-once guarantee, but it only covers the producer-to-broker hop. From the broker to my consumer, Kafka's guarantee is at-least-once: a crash between processing a message and committing its offset means it gets redelivered. I made that safe with an idempotent write — an INSERT with ON CONFLICT DO NOTHING keyed on event_id — so a redelivered message is a no-op, not a duplicate row. Kafka does have a transactional mode that extends exactly-once across a read-process-write cycle, but that's for pipelines that stay inside Kafka end to end, like Kafka Streams. The moment you write to an external system like Postgres, you're back to needing an idempotent write on that system, same as I already have. So the honest claim is exactly-once on one hop, at-least-once made safe on the other — not one guarantee covering everything." The signal: naming the specific hop each guarantee actually covers, instead of treating "exactly-once" as a single fact true or false about the whole pipeline.
