np.minimum() and np.maximum(): elementwise pairwise comparison, and clip()'s hidden engine

Lesson 131 closed its own fresh scan with nothing pre-committed. Today's own fresh scan grepped every lesson body and every glossary row case-insensitively for np.minimum(, np.maximum(, np.fmin(, np.fmax(: zero hits anywhere — a genuine gap, not a narrowing of something already taught. They are a clean, interview-relevant pick on their own merit too: unlike Lesson 102's np.clip() (bound a Series against fixed scalar limits), np.minimum()/np.maximum() compare two full arrays element by element — and, confirmed directly below, clip() is literally built from exactly this pair.

1 · Elementwise pairwise comparison between two arrays — not a reduction, not a scalar bound

np.minimum(a, b) and np.maximum(a, b) take two same-shaped arrays and return the smaller/larger value at every position — not a single reduced number the way bare min()/max() or Series.min()/.max() are. Confirmed directly (numpy 2.5.5, pandas 3.1.1), called on two Series it keeps the original Index and returns a Series:

import numpy as np
import pandas as pd

a = pd.Series([1, 5, 3], index=["x", "y", "z"])
b = pd.Series([4, 2, 3], index=["x", "y", "z"])
np.minimum(a, b)   # x:1, y:2, z:3 -- the smaller of each pair, Index kept
np.maximum(a, b)   # x:4, y:5, z:3 -- the larger of each pair

Confirmed directly, both follow an int-preserving dtype rule when both inputs are already the same integer dtype (int64 in, int64 out) — matching Lesson 129/130's np.abs()/np.floor()/np.ceil(), not the always-upcast rule Lesson 129/131's np.sqrt()/np.log()/np.exp() follow. But a mixed int/float pair upcasts to float64, confirmed directly, the ordinary NumPy type-promotion rule applying to two different input dtypes rather than any special case of this function. A plain scalar as the second argument broadcasts, confirmed directly: np.minimum(a, 2) caps every value at 2 — functionally a one-sided clip, not yet the full two-sided clip() from Section 2.

2 · clip()'s hidden engine: Series.clip(lower=, upper=) is exactly minimum(maximum(x, lower), upper)

Confirmed directly: x.clip(lower=lo, upper=hi) produces bit-identical output to np.minimum(np.maximum(x, lo), hi) on every tested input. Lesson 102's np.clip() is the same two-step composition under one name.
x = pd.Series([1, 10, 5, -3])
lower = pd.Series([0, 0, 0, 0])
upper = pd.Series([8, 8, 8, 8])

x.clip(lower=lower, upper=upper).tolist()            # [1, 8, 5, 0]
np.minimum(np.maximum(x, lower), upper).tolist()      # [1, 8, 5, 0] -- identical, confirmed directly

The practical reason to know this: clip() only ever bounds one Series against fixed (or per-row, via another Series) lower/upper limits in a single call. The moment a wrangling task needs the elementwise min or max of two independent measured columns — "whichever of planned_qty or actual_qty is smaller, row by row" — that is np.minimum() directly, not a clip() call, since there is no single fixed bound to clip against. Confirmed directly, mismatched Series indexes align first, the same outer-join-then-NaN-for-unmatched-labels rule ordinary arithmetic (a + b) follows — a label present in only one of the two Series comes back NaN in the result, not an error.

3 · The trap: NaN poisons the result here — fmin()/fmax() are the NaN-skipping siblings

Confirmed directly: if either input at a given position is NaN, both np.minimum() and np.maximum() return NaN at that position — the comparison itself can't decide a winner against NaN, so the NaN wins by poisoning the result, the same family of silent-NaN-propagation trap as plain arithmetic. This is the opposite default from Series.min()/.max(), which skip NaN by default (skipna=True).

c = pd.Series([1.0, np.nan, 3.0])
d = pd.Series([2.0, 5.0, np.nan])
np.minimum(c, d).tolist()   # [1.0, nan, nan] -- NaN wins both pairs it touches
np.fmin(c, d).tolist()      # [1.0, 5.0, 3.0] -- ignores NaN, picks the real number instead

Confirmed directly, np.fmin()/np.fmax() are the NaN-aware siblings: when exactly one side is NaN, they return the non-NaN value instead of propagating the NaN (only a pair of two NaNs still returns NaN, since there is nothing else to pick). No RuntimeWarning fires for either pair on a NaN input — this is silent by design, confirmed directly, unlike Lesson 131's np.log(0) trap which at least warns.

Q: "What's the difference between np.minimum(a, b) and np.clip(), and when would you reach for each?" A strong answer, out loud: "np.clip() bounds one array against fixed lower/upper limits — a single Series clamped between a floor and a ceiling. np.minimum() and np.maximum() compare two full arrays elementwise and are actually clip()'s engine underneath: clip(x, lo, hi) is just minimum(maximum(x, lo), hi). I'd reach for minimum()/maximum() directly when I need the elementwise min or max between two independently-measured columns, not a fixed bound — like whichever of planned versus actual is smaller, row by row. One trap either way: if either side is NaN at a position, minimum()/maximum() propagate NaN silently with no warning; fmin()/fmax() are the NaN-skipping versions if that's not what I want." The signal: naming the clip() relationship unprompted, and the NaN-propagation default without being asked.
