np.isclose() and np.allclose(): comparing floats without ever using ==

Lesson 89's own note on assert_frame_equal() mentioned "the same idea as NumPy's allclose" in passing — and a fresh curriculum/glossary scan today confirms that comparison, the tool actually named, has never itself been taught: zero hits for np.isclose()/np.allclose() across every lesson body and the glossary, first flagged as a standing candidate back in the round that produced Lesson 102 and left unpicked since. The gap it closes: comparing two floats with plain == is an interview red flag — today is the NumPy-layer tool that replaces it, underneath .equals(), assert_frame_equal(), and np.allclose()-style test assertions alike.

1 · Why == fails on floats that are "the same" number

SQL and plain Python both let a learner reach for == on two numbers without a second thought — until floating-point arithmetic itself gets involved. Confirmed directly (numpy 2.5.4, pandas 3.1.0): 0.1 + 0.2 == 0.3 is False, not because pandas or NumPy did anything wrong, but because 0.1, 0.2, and 0.3 have no exact binary floating-point representation — the tiny rounding error from adding the first two never lines up bit-for-bit with the rounding error baked into the literal 0.3:

import numpy as np

0.1 + 0.2 == 0.3
# False  -- exact equality check, and floats are almost never exactly equal

np.isclose(0.1 + 0.2, 0.3)
# True  -- "close enough" within a small default tolerance

np.isclose() is the element-wise fix: instead of asking "are these bit-for-bit identical," it asks "are these within a small, deliberate tolerance of each other," which is almost always the actually-correct question after any floating-point arithmetic.

2 · isclose() returns an array; allclose() collapses it to one bool

Confirmed directly: np.isclose() is element-wise — given two arrays, it returns a same-shape boolean array, one True/False per pair of elements compared. np.allclose() is simply that result run through .all() — one single True/False for the whole comparison, the natural choice when the question is "do these two whole arrays/columns match," not "which specific elements differ":

a = np.array([1.0, 2.0, 3.0])
b = np.array([1.0 + 1e-9, 2.0, 3.00001])

np.isclose(a, b)
# array([ True,  True,  True])  -- element-wise, one bool per position

np.allclose(a, b)
# True  -- np.isclose(a, b).all(), one single bool for the whole pair

Confirmed directly: both functions work the same way on a pandas Series as on a plain NumPy array — no .to_numpy() conversion is required first, unlike the AttributeError traps Lessons 110/112 found for cummax()/.ravel() called the other direction. np.isclose() on two Series returns a plain ndarray (the Index is dropped, same family as np.percentile()'s behavior in Lesson 111); np.allclose() on two Series returns a plain Python bool.

3 · Both tolerance knobs, and how they combine

The formula, confirmed directly against the official NumPy docs and matched element-for-element with a hand-written version in a scratch script: abs(a - b) <= atol + rtol * abs(b). Two separate knobs combine additively, each catching a different failure mode:

KeywordDefaultWhat it controls
atol=1e-08A flat, absolute cushion — matters most when comparing numbers near zero, where a relative tolerance alone would demand near-perfect precision.
rtol=1e-05Scales with the size of b — matters most for comparing large numbers, where a fixed absolute tolerance would be far too strict (or too loose).

Confirmed directly: widening atol= is exactly how a real rounding-sized difference (e.g. 0.01 off, the kind a re-aggregation bug produces) can be deliberately let through if a test genuinely needs a looser bar — the same deliberate-tolerance idea Lesson 89 found inside assert_frame_equal()'s own default float handling:

e = np.array([1.0, 2.0])
f = np.array([1.01, 2.0])

np.isclose(e, f)
# array([False,  True])  -- 0.01 off is too much for the default atol

np.isclose(e, f, atol=0.02)
# array([ True,  True])  -- widened on purpose; now within tolerance

4 · The NaN trap: isclose() says NaN != NaN by default, same as ==

Confirmed directly: np.isclose(np.nan, np.nan) is False by default — matching plain =='s own "NaN never equals anything, not even itself" rule, not a silent-pass trap. This default is almost never what a data-wrangling test actually wants: two columns that both have a missing value in the exact same spot should usually count as matching there, not as a difference. equal_nan=True flips that one rule, treating a NaN-vs-NaN position as a match while leaving every other comparison exactly as before:
c = np.array([np.nan, 1.0])
d = np.array([np.nan, 1.0])

np.allclose(c, d)
# False  -- the NaN position counts as a mismatch by default

np.allclose(c, d, equal_nan=True)
# True  -- NaN-vs-NaN now counts as matching; the 1.0-vs-1.0 pair was never the issue

This is the one behavior worth naming out loud in an interview: a learner who reaches for np.allclose() to validate a cleaned numeric column against an expected one, where both are allowed to carry missing values in the same places, needs equal_nan=True or the check fails for a reason that has nothing to do with the actual values.

5 · Shape mismatch still raises — no silent broadcasting surprise beyond the usual rules

Confirmed directly: two arrays of genuinely incompatible shapes raise ValueError immediately, the same broadcasting rule Lesson 30 already covers for ordinary arithmetic — np.isclose() introduces no new shape behavior of its own, it is comparison riding on top of standard broadcasting. A scalar compared against a whole Series, by contrast, broadcasts cleanly — the common real case of checking whether every value in a column is close to one target number:

import pandas as pd

s = pd.Series([2.9999999999, 3.0, 3.0000001])
np.allclose(s, 3.0)
# True  -- scalar broadcasts against every element, all three within tolerance
