Kafka on_lost: when a slow message, not a crash, gets a consumer evicted

1 · The gap Day 55 named and left open on purpose

Day 55 wired on_assign and on_revoke into subscribe() and named a third callback, on_lost, only to scope it out: "a corner case closer to Day 50's crash-handling thread than today's assignment-strategy focus." That line undersold it slightly — on_lost isn't about a crash at all. It's about a consumer that is still running, still inside its own poll() loop, and still gets treated by the rest of the group as if it had vanished.

Confirmed directly against the installed confluent-kafka client's own subscribe() docstring: on_revoke fires when a rebalance cleanly asks this consumer to give up partitions it still holds — the handoff Day 55 already saw, cooperative and orderly. on_lost fires in the other case: the group coordinator has already decided, on its own, that this consumer is gone and reassigned its partitions to someone else before this consumer ever got a chance to hand them back. The same docstring is explicit about what happens if a project never bothers to pass on_lost at all: "If not specified, lost partition events will be delivered to on_revoke" — so a consumer that only wired on_revoke, the way today's starting point does, silently treats a forced eviction exactly like a clean handoff, with no way to tell the two apart from inside the callback.

2 · The config that actually causes it: max.poll.interval.ms

A consumer group's coordinator doesn't wait for a crash to declare a member dead. It watches one specific clock per consumer: the time since that consumer's last call to poll(). max.poll.interval.ms is that bound. The confluent-kafka client's own documentation (the same page Days 5–6, 34, 50 and 55 already cite) names its default as 300000 — five minutes — and the reasoning behind it directly: Kafka's heartbeats run on their own background thread in librdkafka, separate from the application thread calling poll(), specifically so a slow message handler doesn't look like a dead process from the network's point of view. max.poll.interval.ms exists precisely to put a ceiling back on that: if the application thread itself — not the heartbeat thread — doesn't get back to poll() within that window, the client proactively leaves the group, and the coordinator reassigns its partitions before this consumer calls poll() again.

Day 41's own per-message try/except handles a message that fails fast — bad JSON, a missing field, caught and dead-lettered in milliseconds. Nothing in this course's consumer loop so far has a step that runs long: a slow downstream call, a large batch write, a retry loop with real sleeps between attempts. The moment one does, max.poll.interval.ms is the clock actually running against it, and it has nothing to do with whether that slow step eventually succeeds.

3 · Build: add on_lost, and see what it actually warns

In your food-delivery-pipeline repo, edit scripts/consume_order_events.py. Add a third callback next to Day 55's two, and pass it to subscribe():

def on_assign(consumer, partitions):
    print(f"assigned: {[p.partition for p in partitions]}")


def on_revoke(consumer, partitions):
    print(f"revoked: {[p.partition for p in partitions]}")


def on_lost(consumer, partitions):
    # Partitions here may already be owned by another consumer --
    # committing an offset from this callback can fail, on purpose,
    # because this consumer no longer has the right to commit for them.
    print(f"LOST (not a clean handoff): {[p.partition for p in partitions]}")


def main():
    consumer = Consumer(
        {
            "bootstrap.servers": BOOTSTRAP,
            "group.id": GROUP_ID,
            "auto.offset.reset": "earliest",
            "enable.auto.commit": False,
            "partition.assignment.strategy": "cooperative-sticky",
            "session.timeout.ms": 6000,       # new today -- librdkafka requires max.poll.interval.ms >= this
            "max.poll.interval.ms": 10000,  # new today -- 10s, shortened only to make Section 4 provable fast
        }
    )
    consumer.subscribe([TOPIC], on_assign=on_assign, on_revoke=on_revoke, on_lost=on_lost)  # on_lost new today

    # everything below -- the psycopg connection, the poll loop, the
    # try/except dead-letter write from Day 41 -- is untouched
    ...

The comment inside on_lost is the actual behavioral difference from on_revoke, not decoration: a clean on_revoke handoff still lets this consumer commit an offset for the partitions it's giving up, if it needs to. By the time on_lost fires, the coordinator has already handed those same partitions to a different consumer — attempting to commit against them from here can fail, which is exactly why the client distinguishes the two cases instead of calling everything a revoke.

4 · Verify: a handler that oversleeps its own poll interval, forced and watched

Reproducing a real eviction needs a handler slow enough to blow past max.poll.interval.ms but not the whole terminal session, so today's build shortens it to 10 seconds (Section 3's comment says so) purely to make this provable in under a minute — production would leave the 300000ms default or tune it deliberately, never shrink it this far. librdkafka enforces one constraint on that shortening directly: max.poll.interval.ms must be greater than or equal to session.timeout.ms — confirmed live this round by hitting the real KafkaException it raises otherwise (val=-186, "max.poll.interval.ms must be >= session.timeout.ms") — which is why Section 3 also shortens session.timeout.ms to 6000 rather than touching only one of the two.

uv run --with confluent-kafka python3 scripts/produce_order_events.py

uv run --with confluent-kafka --with "psycopg[binary]" python3 scripts/consume_order_events.py &
CONSUMER_A=$!
sleep 2
uv run --with confluent-kafka --with "psycopg[binary]" python3 scripts/consume_order_events.py &
CONSUMER_B=$!
sleep 3
kill -STOP $CONSUMER_B   # freezes the process -- simulates a handler stuck past max.poll.interval.ms, no code path taken
sleep 12
kill -CONT $CONSUMER_B
sleep 3

Expected on CONSUMER_A's stdout once the 10-second window on CONSUMER_B expires — the coordinator reassigns CONSUMER_B's partitions to CONSUMER_A as a plain on_assign, because from CONSUMER_A's side this looks like any other member leaving:

assigned: [1]

Expected on CONSUMER_B's own stdout once kill -CONT lets it resume and it finally calls poll() again — this is the actual point of today, and it is not an on_revoke line:

LOST (not a clean handoff): [1]

Q: "A consumer in your group got evicted and its partitions reassigned, but the process never crashed and no error appeared in its logs. What happened, and how would you confirm it?" A strong answer, out loud: "The group coordinator doesn't need a crash to declare a member dead — it watches the time between that consumer's own calls to poll(), bounded by max.poll.interval.ms, defaulting to five minutes. Heartbeats run on a separate background thread in the client, specifically so they keep going even while the application thread is stuck in a slow message handler — which means a slow handler, not a dead process, is enough to blow that window. Once it does, the client itself proactively leaves the group before the coordinator even times it out, and that consumer's partitions get handed to someone else. I'd confirm it by wiring an on_lost callback into subscribe() — it fires specifically for this forced-eviction case, distinct from on_revoke's clean handoff, and if I'd only wired on_revoke, Kafka's own client silently routes a lost-partition event there too, so I'd have had no way to tell a graceful handoff from an eviction apart from checking how long the last message actually took to process." The signal: naming max.poll.interval.ms and the separate-heartbeat-thread mechanism as the actual cause, not "the consumer probably crashed," and knowing on_lost exists specifically to distinguish this case from on_revoke.

Scope line

This lesson covers on_lost's signature and its documented fallback to on_revoke, and max.poll.interval.ms as the config that actually triggers a forced eviction while the process stays alive. It does not cover tuning max.poll.interval.ms for a real production message-processing budget (a capacity question, out of this course's working-level Kafka scope per MISSION.md), session.timeout.ms's own heartbeat-thread semantics beyond the one constraint today needed to shrink it at all (it governs a genuinely dead or network-partitioned process, a different failure mode from today's "alive but too slow to poll"), heartbeat.interval.ms (the third related timer, untouched today), or building a real long-running step into this course's own consumer to force the eviction honestly — today's kill -STOP/kill -CONT models the symptom (application thread not calling poll()) without adding a slow code path to a script every other lesson also edits.
