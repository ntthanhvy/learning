timeit: benchmarking small code correctly

Day 73's concurrent.futures lesson drew a hard line between I/O-bound code (threads help) and CPU-bound code (threads don't) — but that line was asserted from GIL theory, never measured. The obvious next move, wrapping a snippet in time.time() calls, is a trap: one run is noisy — a stray OS scheduling hiccup or a cold cache can swing a single measurement by a large factor, making a slower piece of code look faster by pure chance. The standard-library timeit module exists to measure this correctly instead of guessing.

Picked timeit over the remaining candidates: Day 73 made a real, falsifiable performance claim (I/O-bound threading helps, CPU-bound doesn't) and Day 2's comprehension-vs-loop lesson made another (comprehensions read better and are usually at least as fast) — neither was ever actually measured, so this closes two live claims at once with zero pandas/NumPy surface (benchmarking a snippet of plain Python has no library equivalent either course touches).

1 · timeit.timeit(): run a snippet many times, get a total

timeit.timeit(stmt, setup=..., number=...) runs stmt number times back to back and returns the total elapsed seconds as a plain float — not a per-call average, and not wall-clock time for one run:

import timeit

t = timeit.timeit("x = 1 + 1", number=100_000)
print(t)
# 0.000927... -- confirmed live: total seconds for all 100,000 runs combined
# divide by number yourself for a per-call average: t / 100_000

Running the snippet thousands of times on purpose is the point: any single run is swamped by noise from the OS scheduler, so the total over many runs is what actually separates "fast" from "slow." A callable works too, with no string-quoting needed — handy for timing a real function instead of a one-line expression:

def work():
    return sum(range(100))

t2 = timeit.timeit(work, number=1000)
# 0.000696... -- confirmed live, no quotes, no setup needed for a self-contained function

2 · setup=: build the data once, without timing the building

Timing sorted(data) is meaningless if building data itself is included in every one of the thousand runs — that would measure list construction, not sorting. setup= runs once per call to timeit() (not once per repetition) and its result stays available to stmt without being counted:

t3 = timeit.timeit(
    "sorted(data)",
    setup="data = list(range(1000, 0, -1))",
    number=1000,
)
# 0.00528... -- confirmed live, only sorted() itself is in the timed total

By default, stmt and setup run in a fresh, isolated namespace — a name defined in the calling code is not visible by default, confirmed live by a plain variable reference raising NameError until globals=globals() is passed explicitly to open that namespace up. This isolation is deliberate: it stops a benchmark from accidentally depending on unrelated state left over in the calling scope.

3 · Answering Day 73's and Day 2's open claims

Comparing two snippets under identical number= settles which one is actually faster, instead of trusting an assumption about comprehensions reading better than a loop:

t_comp = timeit.timeit("[x * 2 for x in range(1000)]", number=1000)
t_loop = timeit.timeit(
    "result = []\nfor x in range(1000):\n    result.append(x * 2)",
    number=1000,
)
# confirmed live: t_comp < t_loop -- the comprehension is also measurably faster here,
# not only more idiomatic, closing the claim Day 2 left asserted but unmeasured

A single timeit() call is still one measurement of a total, and totals can vary run to run. timeit.repeat(stmt, number=..., repeat=...) runs the whole number-times measurement repeat times over and returns a list of totals — confirmed live, a 5-repeat call returns a list of exactly 5 floats. The documented recommendation is to trust the minimum of that list, not the average: the minimum is the closest any run got to an uninterrupted measurement, while slower entries mostly reflect noise (another process briefly stealing the CPU) rather than the code actually being slower sometimes.

Where pandas/NumPy go from here: nowhere directly — benchmarking a plain Python snippet is a layer below either library. Comparing a pandas vectorized operation against a manual Python loop over a DataFrame is a realistic next use of this same module, but that comparison is data/'s job and isn't demonstrated here.
