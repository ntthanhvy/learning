Exceptions: catching failure on purpose

Phase 1 built seven tools and one working ETL script — but every example so far assumed the input was clean. Real CSVs have a blank amount cell, a missing file, a stray comma. Today: how Python signals "this failed" with an exception, how to catch exactly the failure you expect (and let everything else propagate), and how to define your own exception type so a caller can tell "bad row" apart from "bad file." First lesson of Phase 2 — open-ended from here, ~20 min/day.

Bridge from SQL: a constraint violation — NOT NULL, a failed FOREIGN KEY, a type mismatch on insert — doesn't return a row saying "error"; it aborts the statement and the driver raises something in your client code. Python's exceptions are that same idea generalized to every operation, not just inserts: something goes wrong, the normal flow stops immediately, and control jumps to whoever said they'd handle it — or all the way out of the program if nobody did.

1 · What happens when nobody catches it

Day 6 and 7's int(row["amount"]) assumed every row had a valid number. It doesn't always:

row = {"city": "Hanoi", "amount": ""}
int(row["amount"])
# ValueError: invalid literal for int() with base 10: ''

That ValueError is an exception: an object carrying a type (ValueError) and a message, raised the instant something goes wrong. Nothing after that line runs. If nothing in the whole call chain says "I'll handle a ValueError here," Python prints a traceback — the exception's type, message, and the chain of calls active when it happened — and the program stops:

Traceback (most recent call last):
  File "pipeline.py", line 12, in <module>
    int(row["amount"])
ValueError: invalid literal for int() with base 10: ''

An uncaught exception is not a special failure mode — it's the default one. "Catching" an exception means writing code that intercepts it before it reaches the top and does something more useful than crashing.

2 · try/except: catching narrowly

A try block runs code that might raise; each except after it names one exception type it knows how to handle. Only a matching except runs — anything else still propagates:

try:
    amount = int(row["amount"])
except ValueError:
    print(f"skipping bad amount: {row}")
    amount = None

Name the exact exception type, never a bare except:. A bare except: catches everything — including a typo'd variable name (NameError), a genuine bug in your own code, even KeyboardInterrupt from Ctrl-C — and silently swallows all of them the same way, turning a real bug into a quiet no-op that's much harder to find later. This is the single most important habit in this lesson:

except:                 # catches literally everything — avoid
except Exception:       # catches nearly everything — usually still too broad
except ValueError:      # catches exactly what you expected — right

One try can list several except clauses for different exception types, checked top to bottom, first match wins — and the exception object itself can be captured with as to read its message:

try:
    amount = int(row["amount"])
    city = row["city"]
except ValueError as e:
    print(f"bad amount: {e}")    # e is the exception object; str(e) is its message
except KeyError as e:
    print(f"missing column: {e}")

3 · else and finally: the other two clauses

else runs only if try raised nothing — useful for code that should run on success but shouldn't itself be covered by the except. finally runs unconditionally, success or failure, exactly like Day 6's context-manager __exit__ always running:

try:
    amount = int(row["amount"])
except ValueError:
    print("bad row, skipped")
else:
    print(f"parsed {amount}")     # only if int() succeeded
finally:
    rows_seen += 1              # always — whether it succeeded, failed, or skipped

finally is the one clause that runs even if the exception isn't caught at all — it fires, then the exception keeps propagating. That makes it the right place for cleanup that must happen no matter what (closing a handle opened outside a with, for instance) — though in practice, Day 6's with already covers the file case better, since it pairs the finally-style guarantee directly with the resource that needs it.

4 · raise: signaling failure on purpose

Catching isn't the only side of this — code you write can raise its own exceptions when a caller does something the function can't handle, using one of Python's built-in types with a message:

def total_for(row):
    if row["amount"] < 0:
        raise ValueError(f"amount can't be negative: {row}")
    return row["amount"] * 1.1

The most common built-ins worth recognizing: ValueError (right type, wrong value — Day 8's int("")), KeyError (dict key missing — Day 3's territory), TypeError (wrong type entirely), FileNotFoundError (Day 6's open() on a missing path), ZeroDivisionError. Reach for the one that already matches before inventing a new one.

5 · Custom exceptions: naming your own failure

When none of the built-ins say what actually went wrong, define a custom exception — a class subclassing Exception, often with no body at all beyond pass:

class InvalidSalesRow(Exception):
    pass

def parse_row(row):
    try:
        return int(row["amount"])
    except ValueError:
        raise InvalidSalesRow(f"bad amount in row: {row}")

This is exactly what a dataclass's fixed shape (Day 7) and a custom exception have in common: both give a caller a precise, named thing to check for, instead of a generic dict or a generic Exception that could mean anything. A caller can now write except InvalidSalesRow: and know specifically "a sales row failed to parse" — not "something, somewhere, went wrong."

for row in raw_rows:
    try:
        parsed.append(parse_row(row))
    except InvalidSalesRow as e:
        print(f"skipped: {e}")    # one bad row doesn't stop the whole pipeline
Where pandas goes from here: pd.to_numeric(col, errors="coerce") turns unparseable values into NaN across a whole column in one vectorized call, instead of a per-row try/except. Not covered here; that's data/'s job, and this is the only sentence in this lesson that mentions it.

6 · Wiring it into the capstone

Day 7's extract() crashed the whole pipeline on the first bad row. A narrow except around just the risky line fixes that without hiding real bugs:

def extract(path: str):
    with open(path) as f:
        reader = csv.DictReader(f)
        for row in reader:
            try:
                yield SalesRow(city=row["city"], amount=int(row["amount"]))
            except ValueError:
                continue              # skip this row, keep the generator going

The except ValueError catches exactly the "amount isn't a number" failure and moves on; a genuinely different bug (say, a TypeError from a code change elsewhere) still propagates and crashes loudly, which is what you want — a silent bare except: here would have hidden it instead.
