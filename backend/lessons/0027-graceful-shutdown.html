Graceful shutdown: what happens the instant before a process dies

Lesson 8 taught that instances come and go — horizontal scaling, restarts, deploys all kill and start processes routinely. Every lesson since has quietly assumed a process dies at a clean boundary between requests. Today: it doesn't, unless you write the code that makes it stop cleanly first.

1 · The moment nobody's mental model covers

A deploy, an autoscaler scaling down, a crashed node being replaced — all of these end with the platform sending your running process a SIGTERM, then killing it outright (SIGKILL) a fixed number of seconds later if it hasn't exited by then. A Go binary that never intercepts SIGTERM just dies on the spot the instant it arrives — mid-request, mid-transaction, wherever it happened to be.

That's not a corner case; it's what a rolling deploy does to every instance, every time. Say instance A is mid-way through handling POST /orders — the row already inserted, the response not yet written — when SIGTERM lands. The client that sent that request gets a dropped connection or a 502 for an order that, in the database, already exists. That's the same "did it actually happen?" ambiguity Lesson 26 built a whole mechanism (idempotency keys) to survive on the client's retry path — but graceful shutdown is the server's half of the same problem: stop creating new half-finished work in the first place, and give the work already in flight a real chance to finish before the process is gone.

Frontend-habit trap: closing a browser tab mid-fetch is a single user's problem — the request just fails, and nobody else is affected. A server process dying mid-request affects whoever that in-flight request belonged to, but also every future request the load balancer was about to send it in the next few hundred milliseconds, unless the process actively tells the load balancer to stop first.

2 · The two things shutdown has to do, in order

A clean exit is two separate steps, and doing them in the wrong order is the most common mistake:

  1. Stop accepting new work. Tell the load balancer this instance is going away — Lesson 13's readiness check is exactly this lever: flip it to failing the moment SIGTERM arrives, so the load balancer stops routing new requests here within one or two health-check intervals, while existing connections are left alone.
  2. Let in-flight work finish, up to a deadline. Requests already being handled — and background work already claimed from Lesson 10's job queue — get a bounded window to complete normally. Only after that window (or once everything genuinely finishes early) does the process actually exit.

Skip step 1 and step 2 is fighting a losing battle: the load balancer keeps sending fresh requests into a process that's actively trying to leave, so "in-flight work" never shrinks to zero. Skip step 2 and step 1 alone buys nothing — the requests already accepted still die mid-flight exactly as if nothing had changed.

3 · The shape in Go

net/http's Server.Shutdown already implements step 2 for HTTP connections: called once, it stops the listener from accepting new connections and blocks until every already-open connection's handler returns (or the passed-in context's deadline expires, whichever comes first). The wiring that's still your job is catching the signal and calling it:

ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGTERM, syscall.SIGINT)
defer stop()

srv := &http.Server{Addr: ":8080", Handler: mux}

go func() {
    if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
        log.Fatalf("listen: %v", err)
    }
}()

<-ctx.Done() // blocks here until SIGTERM/SIGINT arrives
log.Println("shutdown signal received, no longer accepting new connections")

shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()

if err := srv.Shutdown(shutdownCtx); err != nil {
    log.Printf("forced shutdown: %v", err) // deadline hit with requests still running
}
log.Println("shutdown complete")

signal.NotifyContext turns the incoming OS signal into a context that cancels the moment SIGTERM or SIGINT (Ctrl-C locally) arrives, so the main goroutine can simply block on ctx.Done() instead of writing a raw signal.Notify channel by hand. srv.ListenAndServe() runs on its own goroutine because it blocks forever on success — the main goroutine's job is only to wait for the shutdown signal, then drive the shutdown sequence. The 10-second timeout on shutdownCtx is the deadline from step 2: long enough for realistic in-flight requests to finish, short enough that a genuinely stuck request doesn't block the deploy indefinitely — it should always be shorter than however long the deployment platform waits before sending SIGKILL.

4 · Readiness first, or the shutdown races the load balancer

The snippet above handles in-flight requests correctly, but on its own it still has a gap: the instant SIGTERM arrives, the load balancer doesn't know yet — it's still happily routing new requests here based on the last readiness check it saw, which could be several seconds stale. The fix is Lesson 13's readiness check again: the SIGTERM handler should flip a shared flag the readiness handler reads, so it starts returning unhealthy immediately, before calling srv.Shutdown. Most deployment platforms (Kubernetes among them) build in a short pause between "mark unready" and "send SIGTERM" for exactly this reason — the shutdown timeout has to budget for that gap too, not just the requests already running.

Q: "What happens to in-flight requests when you deploy a new version of this service?" A strong answer, out loud: "Without explicit handling, whatever the deploy platform sends — usually SIGTERM — kills the process immediately, so any request being handled at that instant just drops. I'd catch SIGTERM, immediately flip the readiness check to unhealthy so the load balancer stops sending new traffic, then call the HTTP server's Shutdown method with a bounded timeout — it stops accepting new connections and waits for in-flight ones to finish on their own. If a request is still running when the timeout hits, I'd rather log that and let the platform force-kill it than block the deploy forever." The signal: naming the readiness-first ordering unprompted, not just "call Shutdown."
